[.lead]
A research-grounded specification for promoting ProximaDB from "vector database with bolted-on
modalities" to a coherent multi-model system with one record envelope, one type system, one
buffer pool, one logical algebra, and one security boundary. Companion to
link:techdebt/WORKSPACE_REFACTOR_PLAN_2026_05_07.adoc[WORKSPACE_REFACTOR_PLAN_2026_05_07.adoc].

== Executive Summary

ProximaDB started as a narrow vector database. The product expanded to documents, graphs,
observability data, time-series, event sourcing, hybrid search, and a PostgreSQL wire surface.
The expansion was correct in direction, but the implementation accumulated three structural
weaknesses:

. **Three parallel scalar value systems** (`PropertyValue` for graph, `SqlValue` for
  relational/document, `TypedField` for metadata) plus a richer `CatalogDataType` enum at the
  catalog layer that wire types do not faithfully carry. RDBMS workloads through pgwire lose
  precision (Decimal, Timestamp_TZ, UUID) by squeezing through the loose `SqlValue` oneof.
. **No unified record envelope.** `EmbeddingVersion`, `Node`/`Edge`, `SqlRow`, trace span,
  metric data, and event entries are independent record types. Cross-modality features
  (tenant_id, time, provenance, schema variation, RLS policy) are reinvented per modality or
  missing entirely.
. **Asymmetric workspace decomposition.** Graph has a real `proximadb-graph` modality crate;
  vector / document / observability runtimes still live in the root crate. Foundation crates
  are not yet pure (`proximadb-kernel` depends on `tonic`).

This specification proposes a converged design backed by 30 papers from the arxive corpus
(see `Bibliography`):

* a single **`ProximaRecord` envelope** with identity, version, tenancy, time, provenance,
  properties, references, optional topology, optional embeddings, optional sequence, labels,
  and forward-compatible extensions;
* a single **`ProximaType` system** with the full catalog datatype set as a wire type, plus
  schema variations and subschema-checked evolution;
* a **three-layer storage model** -- record storage (NF², PAX, columnar) + topology storage
  (CSR/COO with mappers) + vector index storage (predicate-aware HNSW per modality), all
  sharing a unified buffer pool;
* a **single logical algebra** with `HybridTraverse`, `CrossModelJoin`, and `VectorTopK` as
  first-class operators; multiple syntactic surfaces (SQL, Cypher/GQL, AQL, UQL,
  pseudo-functions) compile to the same algebra;
* **engine-level row filtering and atomic metadata+vector writes** for tenant safety;
* a **disaggregated runtime** (Paxos-backed log service, three-level cache, Arrow Flight
  transport) following OceanBase Bacchus.

The roadmap is seven phases (A through G) over 12-18 months, sequenced to maintain
backward compatibility through the existing transitional facade pattern.

=== 1.2 Critical Gaps (Ordered)

==== G1: Type-System Fragmentation [P0]

**Three parallel value oneofs** carry the same scalars under different names with different
coverage:

[cols="1,1,3"]
|===
| OneOf | Used By | Coverage

| `PropertyValue` | Graph (`proto/proximadb/v1/graph.proto`) | string, int64, double, bool, bytes, **vector**, array, object
| `SqlValue` | SQL/document/metadata (`proto/proximadb/v1/types.proto:21-32`) | string, double, bool, int64, bytes, null, array, object -- **no vector, no decimal, no uuid**
| `TypedField` / `MetadataValue` | Vector metadata, filters | string, int64, double, bool
|===

The catalog's `CatalogDataType` enum (`src/catalog/types.rs:121-162`) declares Boolean, Int8/16/32/64,
Float32/64, Decimal, String, Binary, Date, Time, Timestamp, TimestampTz, Json, Uuid, Vector,
SparseVector, BinaryVector -- **none of which travel faithfully through `SqlValue` on the
wire**. RDBMS-style queries through Postgres wire (port 5433) lose financial precision
(Decimal), timezone-aware timestamps, and UUID identity. Aligned filter pushdown is impossible
because `FilterableDataType` (proto) does not match `CatalogDataType` (catalog) does not match
`SqlValue` variants.

==== G2: No Unified Record Envelope [P0]

Each modality has a distinct record type:

* `EmbeddingVersion` + `VectorRecord` (vector) -- `crates/foundation/proximadb-proto/src/proto/proximadb.v1.rs:112-129`
* `Node` / `Edge` (graph) -- `crates/foundation/proximadb-proto/src/proto/proximadb.v1.rs:3521-3572`
* `SqlValue`-shaped JSONB blob (document) -- shared with relational
* `SqlRow` (relational/pgwire) -- `crates/foundation/proximadb-proto/src/proto/proximadb.v1.rs:52-58`
* OTLP-shaped span / metric / log (observability) -- separate trace/metric/log records, no unified type
* Append-only opaque entry (event log) -- per `src/storage/engines/eventlog/`

Cross-cutting fields that should exist exactly once -- tenant_id, permitted_principals,
created_at/updated_at, valid_from/valid_to, provenance (origin/actor/method),
record_version/supersedes, structural_variation_id, RLS policy id -- are reinvented per
modality (or missing). Multi-model joins, federated security, and CDC out are all harder
than they need to be.

==== G3: No Predicate-Aware Vector Index [P1]

`src/index/axis/` provides HNSW, IVF, LSH, Annoy. Filtering today is post-filter; the
research consensus (ACORN, NaviX, FilterAgnosticPG, HMGI) is that this gives 10-1000x worse
performance than predicate-aware HNSW under most filter selectivity values. The current
metadata layer cannot pass a predicate callback into HNSW navigation, cannot do
predicate-agnostic edge expansion at construction, and cannot fall back to brute-force
prefilter when selectivity drops below `s_min`.

==== G4: Phase 2.5 Execution Layer Pending [P0]

Per `STRATEGIC_ROADMAP.adoc:274-444`: a vectorized executor exists in
`vectorized_executor.rs` but the primary query path in `unified_reader.rs` still uses
scalar loops (TD-041). DataChunks, morsel-driven parallelism, Arrow as cross-model lingua
franca, row-group statistics pruning, spill-to-disk -- all queued. Without these, the
multi-model claim cannot be substantiated under analytical workloads.

==== G5: Asymmetric Workspace Decomposition [P1]

Graph extraction is real (`proximadb-graph`, `proximadb-graph-subset`,
`proximadb-graph-arrow`); vector / document / observability are still in the root crate.
Foundation impurity: `proximadb-kernel` depends on `tonic`; `proximadb-proto` carries
`num_cpus`, `sysinfo`, `tracing`. Per WORKSPACE_REFACTOR_PLAN §"Validated Boundary Findings"
this caps the rebuild-time payoff and contaminates foundation contracts.

==== G6: Application-Layer Tenant Filtering [P0]

RBAC and rate limiting exist (`src/security/`), but tenant scoping happens above the engine
in most paths. Per arXiv:2605.03275 §6.4, application-level tenant filtering had a 0.2%
leakage rate over 1000 simulated cross-tenant queries. ProximaDB needs **engine-level row
filtering** with `tenant_id` and `permitted_principals` columns indexed and pushdown-able
into vector search and pattern matching.

==== G7: No Hybrid Cross-Model Operator [P1]

Cross-model joins go through `LATERAL` SQL joins or federated executor materialization.
There is no specialized **MSHJ-style** (M2, arXiv:2508.02508 §4) inter-model operator and
no **hybrid traversal `→`** (GredoDB, arXiv:2603.01598 Algorithm 1) that pins one tile
while crossing engine boundaries. Result: every cross-model query materializes through a
least-common-denominator format.

==== G8: Schema Evolution Lacks Variation Awareness [P2]

Schema migration exists at the column level (DDL ALTER) but the catalog does not encode
**structural variations** per entity type (U-Schema, arXiv:2105.06494) -- the recognition
that a "document" collection naturally has multiple co-existing shapes that should each be
queryable as their own first-class projection. Subschema-preservation is not enforced
(arXiv:2603.25306, arXiv:1911.12651). Schema-version lineage is partial.

==== G9: Wire Types and Storage Types Drift [P1]

Proto `EmbeddingVersion` carries `model_id`, `model_version`, `dimension`, `created_at_ms`,
`model_params`, `modality` (proto) but the storage `VectorRecord` carries `id`, `vector`,
`metadata` (HashMap<String, SqlValue>), `timestamp`, `expires_at`, `version`, `source` --
overlapping but not identical fields. The catalog's `FilterableColumnSpec` declares column
shape with yet another vocabulary. Each layer translates with hand-written converters
(`src/core/conversions.rs`).

==== G10: Observability Records Are Three Things [P2]

`src/observability/` has separate `traces.rs`, `metrics.rs`, and a log ingestion path that
does not unify into one record type. Cross-correlation queries (e.g., "errors in last hour
on services that depend on X") need a unified spine. The Knows model (arXiv:2604.17309)
and the Stonebraker RUBICON model (arXiv:2604.21413) both argue for one structured record
with explicit relations.

==== G11: Storage Layout And External Format Authority Are Underspecified [P0]

The current code has multiple internal engines and already uses Arrow/Parquet-related paths, while
the platform roadmap calls for Delta/Iceberg/Hudi and object-store interoperability. Without a
cataloged authority model, format support can accidentally become another source-of-truth split.

ProximaDB needs explicit catalog contracts for:

* authority mode: internal canonical, external authoritative, imported snapshot, exported
  publication, or rebuildable projection;
* storage layout: row/record, LSM, PAX, columnar, append-only event, graph topology, ANN, time
  block, or external table;
* snapshot/isolation semantics;
* `ProximaType` mapping and lossy conversion flags;
* policy/RLS enforcement boundary;
* freshness, rebuild, repair, and retention behavior.

==== G12: Relational Integrity Is Not Yet A First-Class Capability Set [P1]

The platform direction includes PostgreSQL/Oracle-style adoption paths, but relational semantics
cannot be treated as pgwire-only behavior. Primary keys, unique indexes, secondary indexes, foreign
keys, check constraints, materialized views, transaction profiles, and stricter schema evolution
must be optional cataloged capabilities. When enabled, they are durable semantics enforced below all
protocols and recovered through WAL/log/manifest.

==== G13: Hybrid Retrieval, Reranking, And Observability/SIEM Product Surfaces Are Not Yet Unified [P1]

Competitive systems increasingly combine BM25/full-text, dense and sparse vectors, filters, graph
context, recency, and semantic reranking. Observability/SIEM systems combine logs, metrics, traces,
profiles, alerts, anomaly detection, retention tiers, service maps, and now LLM/agent
observability. ProximaDB has the ingredients but needs shared operators, catalog metadata, and
projection families so these surfaces do not grow as separate products inside the codebase.

== Section 2: Research-Grounded Design Direction

=== 2.1 Convergent Themes

Thirty papers from the arxive corpus (see `Bibliography`) converge on six themes that bear
directly on the gaps in Section 1.

==== T1: Single Logical Record Envelope, Multiple Physical Projections

GredoDB (arXiv:2603.01598 §4.1-4.2) keeps relational tuples, JSONB documents, and graph
vertices/edges in one **NF² unified record storage** identified by `(oid, vid)` for
vertices and `(oid, soid, svid, toid, tvid)` for edges. U-Schema (arXiv:2105.06494, Table 2)
formalizes the projection: column → attribute, nested object → aggregation, FK → reference,
vertex label → label set, edge → relationship type, vector → typed array attribute. The
unified-RAG paper (arXiv:2605.03275 §5.2) materializes this for production: a single
`documents` table with `tenant_id`, `updated_at`, `category`, `permitted_users`, `content`,
`embedding` columns and HNSW on the embedding -- 92% latency reduction on date-filtered
queries vs split systems, zero inconsistency window.

==== T2: Specialized Engines Behind a Unified Buffer Pool

M2 (arXiv:2508.02508 §3.1-3.2) argues against single-engine multi-model and against
polyglot persistence. The right design is multiple specialized engines behind one query
language, sharing a **unified buffer pool** with engine-supplied `isEvictable`/`doEviction`
callbacks. Inter-model joins use specialized operators (Multi-Stage Hash Join for
array×relation; cost `O(D·N + D·N·log M)` for sparse tiles). GredoDB confirms with its
"dual storage engine" of unified record storage + dedicated topology storage with
`nidMap`/`vertexMap`/`edgeMap` mappers between the two layers.

==== T3: Predicate-Aware HNSW with Adaptive-Local Heuristic

Five papers converge on the same prescription:

* ACORN (arXiv:2403.04871): collect `M·γ` candidate edges per node; **predicate-agnostic
  prune** at construction; predicate subgraph traversal at search; fall back to pre-filter
  when selectivity `s < 1/γ`; emulates an oracle partition index above the threshold.
* NaviX (arXiv:2506.23397): **adaptive-local heuristic** chooses between `onehop-s`,
  `directed`, and `blind` 2-hop expansion at every search iteration based on local
  selectivity around the current frontier. Beats fixed heuristics across selectivity ranges.
* FilterAgnosticPG (arXiv:2603.23710): in production, **page accesses and tuple
  indirection** dominate the cost model -- not distance computations. PAX co-location of
  vector + filter columns wins; ScaNN-style clustering should sit alongside HNSW for low
  selectivity.
* HMGI (arXiv:2510.10123): **per-modality HNSW partitioning** reduces search space 70% and
  resolves polysemy (95% accuracy vs 80% on monolithic).
* LSM-VEC (arXiv:2505.17152): for write-heavy collections, **distribute HNSW across LSM
  levels** with sampling-aware reordering -- 2.6× lower update latency than DiskANN, 66%
  memory reduction.

==== T4: One Algebra, Multiple Surfaces

Eight papers (M2, GredoDB, unified-RAG, AV-SQL, DBPlanBench, RUBICON, flexvec, GraphAr) all
land on **one logical algebra** with `Filter, Project, Sort, Limit, Aggregate, Union, Join,
HybridTraverse, PatternMatch, CrossModelJoin, VectorTopK, ModulationOp, MatrixOp,
SemanticJoin, ModelConvert`. Multiple syntactic surfaces compile down: SQL (with pgvector
operators and SQL/PGQ for graph), Cypher/GQL, RUBICON-style AQL (`Find/From/Where`),
flexvec-style pseudo-functions intercepted before SQL parsing, plan-as-JSON for LLM/RL
optimization.

==== T5: Engine-Level Tenancy and Atomic Metadata+Vector Writes

The unified-RAG paper (arXiv:2605.03275 §5.3, §6.4) is unambiguous: application-layer
tenant filtering leaks (0.2% rate measured); engine-level row filtering with `tenant_id`
and `permitted_principals` as indexed columns is non-negotiable. RUBICON (arXiv:2604.21413)
adds wrapper-layer auth at every per-source connector. Atomic metadata + embedding
writes in one transaction give zero inconsistency window -- the alternative measured a
3.54 ms inconsistency window in split-system stacks.

==== T6: Disaggregated Cloud-Native Runtime

OceanBase Bacchus (arXiv:2602.23571) describes the full pattern: PALF/Paxos log service
decoupled from storage and compute; three-level cache (memory → local persistent NVMe →
distributed shared block cache); LSM tuned for S3 append-only model; 59% storage cost
reduction OLTP, 89% OLAP. Arrow Flight at 6 GB/s (arXiv:2204.03032) is the canonical
cross-tier transport. GraphAr (arXiv:2312.09577) is the right cold-tier on-disk format
for graph + relational + document, with PAC label columns and SIMD interval decoding.

=== 2.2 Adopted Mental Model

ProximaDB **is**:

* A **multi-model database** with one record envelope (`ProximaRecord`), one type system
  (`ProximaType`), one buffer pool, one logical algebra, one security boundary, and many
  specialized engines.
* The **Context Database** for AI agents and real-time applications -- vectors, documents,
  graphs, time-series, events, and relational data accessed through one data plane.
* **Format-first**: the on-disk layout (PAX columnar with co-located vector + filter
  columns; CSR/COO topology; Parquet/GraphAr cold tier) is the contract; engines are
  pluggable above it.
* **Tenant-safe by construction**: row-level filters are pushed into engines; metadata and
  embeddings commit atomically.
* **Agent-native**: physical plans are inspectable JSON; AQL is a thin layer over the
  unified algebra; records carry version triples, provenance, typed relations.

ProximaDB **is not**:

* A federation layer over external databases.
* A polyglot persistence wrapper.
* A general-purpose OLTP RDBMS replacement (SQL-via-pgwire is contextual, not full
  PostgreSQL semantics).
* A petabyte-scale OLAP warehouse (DuckDB / Snowflake live above).

== Section 3: The Unified `ProximaRecord` Envelope

=== 3.1 Goals

. **One record type** that vector, graph node, graph edge, document, relational tuple,
  event, log line, metric point, and trace span all project onto.
. **Cross-cutting fields exist exactly once**: identity, version triple, tenancy, time,
  provenance, schema variation, RLS policy.
. **Forward-compatible**: per-record `x_extensions` allow new fields without schema bump.
. **Lossless wire/storage round-trip**: proto encoding equals storage encoding equals
  Arrow encoding (modulo physical layout) so converters in `src/core/conversions.rs`
  shrink to schema mappings.
. **Engine-friendly**: physical layouts (PAX, CSR, HNSW relationship table) project
  naturally from the envelope.

=== 3.2 Field-by-Field Specification

[source,rust]
----
/// The canonical record envelope for ProximaDB. Lives in `proximadb-records`
/// (new foundation crate, see Section 10). Every modality projects onto this.
pub struct ProximaRecord {
    // ---- 1. Identity ----------------------------------------------------------
    /// Entity-type id (catalog-assigned). Stable across the cluster lifetime.
    pub oid:         EntityTypeId,        // u64
    /// Local id within the entity-type / variation namespace.
    pub local_id:    LocalId,             // u64
    /// Global tuple id assignable for cross-engine join. Optional; engines may
    /// store it lazily.
    pub tid:         Option<TupleId>,     // u64

    // ---- 2. Catalog and version ------------------------------------------------
    /// Structural variation within the entity type. Distinct documents in one
    /// collection may have different shapes; each shape is a `variation_id`.
    pub variation_id: VariationId,        // u32
    /// Spec version: schema-level semantic version (additive vs breaking).
    pub spec_version: SemVer,
    /// Profile namespace: e.g. `paper@1`, `session@1`, `edge@1`.
    pub profile:      ProfileRef,
    /// Per-record version counter (monotonic per local_id).
    pub record_version: u32,
    /// If this record supersedes an earlier version (event-sourced or versioned data).
    pub supersedes:   Option<RecordRef>,

    // ---- 3. Tenancy and ACL ---------------------------------------------------
    /// Tenant id. Indexed in every engine. Pushdown-able into vector search.
    pub tenant_id:    TenantId,           // u64
    /// Bitmap of principals permitted to read this record (NULL = use rls_policy).
    pub permitted_principals: Option<PrincipalBitset>,
    /// Row-level-security policy id (catalog-managed).
    pub rls_policy_id: PolicyId,          // u32

    // ---- 4. Temporal ----------------------------------------------------------
    /// Microsecond UTC. Server-assigned; monotonic per node.
    pub created_at:   Timestamp,
    /// Last modification (NULL = never modified).
    pub updated_at:   Option<Timestamp>,
    /// Validity window for bitemporal data (NULL valid_to = open).
    pub valid_from:   Timestamp,
    pub valid_to:     Option<Timestamp>,

    // ---- 5. Provenance --------------------------------------------------------
    pub origin:       OriginRef,           // ingest source / collector
    pub actor:        ActorRef,             // system or user that wrote
    pub method:       String,               // ingest method: rest, grpc, cdc, ...
    pub verification: VerificationStatus,   // unverified / signed / hash-chained
    pub signature:    Option<Signature>,    // optional cryptographic signature

    // ---- 6. Properties (NF² JSONB tree) --------------------------------------
    /// Subschema-checked at write. Stored columnar (PAX) when shape stable;
    /// JSONB blob when variation_id is open.
    pub props:        ProximaTree,

    // ---- 7. References --------------------------------------------------------
    /// Typed cross-record references. `intent` carries CiTO-style relation kinds.
    pub refs:         Vec<TypedRef>,

    // ---- 8. Topology (only for vertex/edge records) ---------------------------
    /// Edge endpoints. Present when this record IS an edge.
    pub edge:         Option<EdgeShape>,    // (soid, svid, toid, tvid, label)

    // ---- 9. Multi-modal payload ----------------------------------------------
    /// Zero or more embeddings. Each tagged by modality and dimension.
    pub embeddings:   Vec<EmbeddingCell>,
    /// Optional ordered token sequence (text, audio, action stream, ...).
    pub sequence:     Option<TokenSequence>,
    /// Label set as bitset (RLE-encoded on disk per GraphAr §3.2).
    pub labels:       LabelSet,

    // ---- 10. Forward-compatible extensions -----------------------------------
    pub x_extensions: ProximaTree,
}

pub struct EdgeShape {
    pub soid:    EntityTypeId,
    pub svid:    LocalId,
    pub toid:    EntityTypeId,
    pub tvid:    LocalId,
    pub label:   LabelId,
    pub weight:  Option<f64>,
}

pub struct EmbeddingCell {
    pub modality:    ModalityTag,           // text, image, audio, action, ...
    pub model_ref:   ModelRef,              // (model_id, model_version)
    pub dim:         u32,
    pub vector:      VectorPayload,         // dense / sparse / binary
    pub index_id:    Option<IndexId>,       // pointer into HNSW relationship table
}
----

The shape is taken directly from the convergent design picture: identity / variation /
provenance from U-Schema and Knows; tenancy from the unified-RAG paper; topology shape
from GredoDB §4.2; embedding cells from HMGI §3.1; sequence from VectorMaton §2.1; labels
from GraphAr §3.2; extensions from Knows §III.

=== 3.3 Per-Modality Projections

[cols="1,3,3"]
|===
| Modality | What is filled | What stays empty / default

| **Vector**
| identity, tenancy, time, embeddings (1+ cells), props (metadata), labels
| edge, sequence (often), refs (often)

| **Graph node**
| identity, tenancy, time, props, embeddings (optional, semantic node search), labels (= node labels)
| edge

| **Graph edge**
| identity, tenancy, time, props, edge (REQUIRED), labels (= edge type as singleton bitset)
| embeddings (usually), sequence

| **Document**
| identity, tenancy, time, provenance, props (the JSON tree), embeddings (optional), sequence (full text)
| edge

| **Relational tuple**
| identity, tenancy, time, props (typed columns)
| edge, embeddings (unless `EMBED COLUMN ...` declared), sequence

| **Event-log entry**
| identity (with strict monotonic local_id), tenancy, time, provenance (with hash chain), props (event payload), refs (correlation)
| edge

| **Time-series point**
| identity, tenancy, time (created_at = sample time), props (the measurement)
| edge, embeddings, sequence

| **Observability log line**
| identity, tenancy, time, props (structured fields), sequence (raw line tokens), labels (severity, namespace)
| edge

| **Observability metric**
| identity, tenancy, time, props (value, unit, dimensions), labels
| edge, embeddings, sequence

| **Observability trace span**
| identity (trace_id, span_id), tenancy, time, props (attributes), refs (parent_span, links), labels
| edge, embeddings (unless semantic span search enabled)
|===

The **same record envelope** carries all ten modalities. Different sets of fields are
populated; the unused fields cost zero on the wire (proto field absence) and one bit per
field on disk (PAX nullability bitmap). Cross-modality queries (e.g., "for tenants T,
join error spans of last hour with the dependency graph and rank by document similarity
to the incident description") work because every modality has the same identity / tenancy
/ time / props shape.

=== 3.4 Wire Format

The `ProximaRecord` proto definition (new file `proto/proximadb/v1/record.proto`) replaces
the per-modality record protos as the canonical wire type. Existing modality protos
(`vector_types.proto`, `graph.proto`, `document.proto`, `entity.proto`,
`observability.proto`) are reduced to thin transport-flavor messages that wrap
`ProximaRecord` with modality-specific request fields.

Migration order (see Section 11 Phase B):

. Introduce `ProximaRecord` proto alongside existing protos. Mark current protos `// LEGACY`.
. Add `From<EmbeddingVersion> for ProximaRecord`, `From<Node>`, `From<Edge>`,
  `From<SqlRow>`, `From<TraceSpan>` etc. in `proximadb-records` crate.
. Migrate one engine at a time to write `ProximaRecord`. SST first (smallest blast radius
  for vector) then VIPER (already columnar PAX-friendly).
. Migrate query layer: `OptimizedSearchRecord` becomes `ProximaRecord` + score + rank.
. Remove legacy protos in a single major version bump (v0.3.0).

== Section 4: The Unified `ProximaType` System

=== 4.1 Goals

. **One scalar type tree** that the catalog, wire types, storage layout, and SQL semantics
  all share.
. **Lossless across layers**: a `Decimal(38, 8)` declared in the catalog reaches the
  storage as `Decimal(38, 8)`, returns through pgwire as `numeric(38, 8)`, ships through
  Arrow Flight as `Decimal128`.
. **Subschema-checked**: writes that violate the declared schema fail at the boundary, not
  silently as oneof variant mismatches.
. **Variation-aware**: a single entity type may have multiple `structural_variation`s; the
  union schema with common-vs-specific properties is a first-class catalog object.

=== 4.3 Schema, Variation, Subschema

A **schema** declares an entity type's union shape. Each entity type owns 1..n
**structural variations**, each variation is a set of properties classified per
U-Schema (arXiv:2105.06494):

* **attribute** -- typed scalar or struct
* **aggregation** -- nested object / array embedded in the parent
* **key** -- candidate identifier
* **reference** -- typed cross-entity pointer
* **relationship** -- (graph entity types only) edge type with cardinality

The catalog stores variations explicitly. Open-shape collections (`document` profile)
allow ad-hoc variations created on first write; closed-shape collections (`relational`
profile) reject writes that do not match a registered variation.

==== 4.3.1 Schema Modes and Insert Semantics

ProximaDB supports multiple schema disciplines, but all of them are cataloged and all
write paths converge before WAL/storage:

* **Strict relational**: table schema, keys, constraints, generated columns, indexes,
  and type coercions are resolved from xCatalog before insert/update. Unknown fields
  are rejected unless a cataloged JSON/Map/Struct column accepts them.
* **Flexible document/entity**: records in one collection may carry different shapes.
  First write of a new shape creates or references a structural variation; configured
  validation rules, required fields, and indexed paths are checked before commit.
* **Graph property records**: node and edge labels/types plus property maps are
  `ProximaRecord` labels, edge shape, and `ProximaValue` props. Adjacency/CSR/COO
  structures are projections over committed node/edge records.
* **Schema-on-write**: adapters validate known fields, infer/register allowed
  variation metadata, and reject non-preserving drift when policy requires it.
* **Schema-on-read**: query/projection code can discover and project fields lazily,
  but this is a planner/projection behavior, not a separate durable type system.

Every insert/upsert surface follows the same sequence:

. Parse protocol payload (SQL row, REST JSON, gRPC message, Arrow batch, Mongo-like
  document command, Gremlin/Cypher/PGQ graph mutation, SDK/embedded object).
. Convert edge values into `ProximaValue`/`ProximaTree`/`EmbeddingCell` without
  preserving protocol-specific scalar types internally.
. Resolve namespace/table/collection/graph/entity type, schema mode, structural
  variation, policy, branch/time context, and physical layout from xCatalog.
. Validate/coerce values using `ProximaType`; enforce keys, constraints, RLS/masking,
  retention, and schema-evolution policy.
. Build one or more canonical `ProximaRecord` instances and append the canonical WAL/log
  operation.
. Update access methods/projections (indexes, adjacency, CSR/COO, HNSW, columnar,
  full-text, rollups) as cataloged rebuildable structures.

PostgreSQL/MariaDB-style strictness, MongoDB-style flexible documents, Neptune/Titan/
JanusGraph-style property graph mutations, and Arrow-native batches are therefore
different ingress ergonomics over one catalog/type/write pipeline. Legacy v1
`SqlValue` remains an adapter shape only; it must not become the insertion contract for
new semantics.

Schema evolution operations follow EvoSchema's 10 op types (arXiv:2603.10697):

[cols="1,1,2"]
|===
| Level | Op | Subschema-Preserving?

| Column | Add | Yes (NULL-defaulted)
| Column | Remove | No (must preserve via deprecation window)
| Column | Rename | No (alias support)
| Column | Split | No (migration script required)
| Column | Merge | No (migration script required)
| Table  | Add | Yes
| Table  | Remove | No (with retention policy override)
| Table  | Rename | No (alias support)
| Table  | Split | No (migration script required)
| Table  | Merge | No (migration script required)
|===

DDL that is subschema-preserving applies online; non-preserving DDL requires explicit
migration. Subschema check uses refutational normalization (arXiv:2603.25306) for fast
incomplete dispatch with witness-completeness on demand.

=== 4.4 Variation-Aware Query Planning

The optimizer (`proximadb-query`) reads `(entity_type, variation_id)` from each candidate
record's `ProximaRecord` envelope, prunes plans that do not apply, and chooses physical
operators per variation. For vector search, this means: per-modality HNSW shards keyed by
`(oid, variation, modality_tag)`. For document scan, this means columnar projection per
variation when the variation's shape is stable.

* **Layer 3** is owned by AXIS. Per-(oid, variation, modality_tag) HNSW shard;

=== 5.2 Unified Buffer Pool

[source,rust]

Replaces the per-engine `UnifiedCachingFilesystem` page cache. Cross-engine memory

materializes record batches at Arrow boundaries for cross-model query handoff.

=== 5.3 PAX Co-Location of Filter and Vector Columns

Per FilterAgnosticPG (arXiv:2603.23710 §2): in a real engine, page accesses dominate
distance computations. The filter columns most queried alongside an embedding (tenant_id,
created_at, category) must live on the **same physical page** as the embedding column.
PAX (Partition Attributes Across) layout already supports this; ProximaDB needs to:

. Detect frequently-filtered-with-vector columns from query traces (RL planner already
  collects this telemetry).
. Promote those columns into the same row group as the embedding.
. Flush column groups together so a hot block fetches both in one IO.

Implementation lives in `src/storage/engines/viper/` (layout planner), VIPER's
metadata-write phase, and `src/storage/persistence/serialization/`.

=== 5.4 Hot/Warm/Cold Tier Policy

Convergent recommendation (unified-RAG §7.3 + Bacchus §2 + columnar-eval §3):

[cols="1,3,3"]
|===
| Tier | Contents | Engine

| Hot
| Last 7-30 days; ~10-30% of records; ~80-90% of queries
| SST/SWIFT/HELIX (write-optimized) for vector-heavy; SST + DataFusion for relational

| Warm
| 30 days - 12 months; pure ANN long-tail; specialized index access
| VIPER/NOVA/RAPTOR (columnar, analytics-optimized)

| Cold
| 1+ years; archival; query rate <1%
| Object storage (S3/GCS/Azure) in GraphAr/Parquet format with PAC label columns
|===

The catalog declares per-collection tier policy; a background **TierMover** service in
`src/services/tiering/` (new) migrates records on age/access-frequency thresholds. The
LRU-K decision is recorded in audit log. Query planner reads tier-availability from
catalog; cross-tier queries broadcast to all relevant tiers in parallel.

=== 5.5 LSM-on-Graph for Write-Heavy Vector Collections

For collections with high update rates (LSM-VEC pattern, arXiv:2505.17152): the HNSW
proximity graph is distributed across LSM levels. Out-of-place updates write a new node;
background compaction merges levels. **Sampling-aware reordering** records actual query
trace edges and co-locates frequently-traversed neighbors. ProximaDB's HELIX engine is
the right starting point; the code already has Hilbert-curve locality and can be extended
with the LSM layout.

==== 5.6.1 Catalog Asset And Collection Service Boundary

The catalog asset is the durable metadata primitive. "Collection" is a compatibility/API term for
a cataloged asset with one or more modality capabilities. Vector collections, document collections,
graphs, relational tables, observability datasets, streams, feature tables, model registry objects,
agent stores, projections, and open-format publications share the same xCatalog identity model.

The canonical name is:

[source,text]
----
catalog.namespace.asset_name[@branch_or_snapshot]
----

`TableIdentifier`-style namespace plus asset name is the internal logical key, backed by a stable
catalog asset id. Modality-specific ids such as `collection_id`, `graph_id`, `stream_id`, or
`model_id` are typed views or aliases over that asset id. Renames update catalog alias/history
metadata and must not rewrite record identity, WAL lineage, branch ancestry, or projection
ownership.

`CollectionService` may remain as a lifecycle facade for legacy vector/document collection APIs. It
must delegate durable metadata reads and writes to xCatalog and must not own a separate metadata
registry, schema model, path authority, index definition store, stats store, or recovery state.
Create/alter/drop flows should be:

[source,text]
----
surface API -> CollectionService or DDL facade -> xCatalog metadata transaction
            -> WAL/log/manifest record -> storage/projection/index initialization
----

As record-native table APIs become stable, the service should become a thin compatibility alias or
a generalized catalog asset lifecycle service rather than a second catalog.

==== 5.6.2 Schema Registry And AI Asset Metadata

xCatalog is also the schema registry and AI asset metadata authority:

* Avro, JSON Schema, Protobuf, Confluent Schema Registry, and AWS Glue Schema Registry subjects map
  to xCatalog schema objects with version history, compatibility/evolution policy, fingerprints,
  and canonical `ProximaType` mappings.
* Hive/Glue/Unity/Polaris/Iceberg/Delta/Hudi catalog entries map to external references,
  imported snapshots, exported publications, rebuildable projections, or explicit external
  authority assets.
* MLflow-compatible experiments, runs, params, metrics, artifacts, model versions, aliases/stages,
  signatures, deployments, evaluations, drift monitors, labels, feedback, and prompts are cataloged
  under the MLOps asset model. Large artifacts may live outside ProximaDB, but their location,
  checksum, lineage, policy, and lifecycle state are xCatalog metadata.
* Kafka/Flink/Kinesis stream schemas, topics, partitions, offsets, watermarks, consumer groups, and
  dead-letter policies are stream asset metadata tied to schema and lineage entries.

No schema registry, model registry, stream connector, or open-format adapter may become a hidden
source of metadata truth.

== Section 6: Modality-Specific Specifications

=== 6.1 Vector Modality (`proximadb-vector`)

Currently in root crate. Extract to `crates/modalities/proximadb-vector` per workspace
plan §"Recommended First Implementation Slice" item 7.

==== 6.1.1 AXIS Refactor

Replace per-engine isolated index implementations with the SOLID redesign already
proposed in `docs/SOLID_VECTOR_FRAMEWORK_REDESIGN.md`:

* **EngineCapabilities** trait declares supported indexes / quant / pruning / search modes.
* **SearchStrategy** trait separates strategies (DirectScan, Hnsw, Ivf, Ann, ProgressiveQuant,
  CentroidPrune, HilbertPrune, ZoneMapPrune).
* **QuantizationPipeline** unifies the four duplicate progressive-quantization
  implementations.
* **CapabilityAwareRLPlanner** queries the registry; no hardcoded engine paths.

Net: ~62% LOC reduction in vector framework (per the redesign doc); cross-engine strategy
sharing.

==== 6.1.2 Predicate-Aware HNSW

. HNSW construction collects `M·γ` candidate edges per node (configurable; default
  `γ=2`). Stores as a relationship table keyed by `(modality_tag, variation_id, node_id)`.
. Construction prune is **predicate-agnostic**: keep edges that any anticipated predicate
  could traverse. The current RNG triangle-prune is too aggressive for filtered search.
. Search exposes a **predicate callback** (`fn(&ProximaRecord) -> bool`) that wraps the
  filter expression. The HNSW navigator skips nodes where predicate returns false.
. **Adaptive-local heuristic** (NaviX §3): at every iteration, count selected neighbors at
  the current frontier; if >threshold, do `onehop-s` (selected only); if low, do
  `directed` 2-hop (rank by distance); if very low, do `blind` 2-hop expansion.
. **Selectivity threshold `s_min`**: catalog config; default `1/γ`. When estimator says
  selectivity below this, plan switches to pre-filter + brute force.
. **Per-modality partitioning**: separate HNSW shard per `(oid, variation, modality_tag)`
  per HMGI §3.1.

==== 6.1.3 Sequence-Predicate Vector Search (Optional)

For collections that carry both an embedding and a token sequence and need
substring/CONTAINS predicates, build a **suffix automaton** over the sequences and attach
a per-state HNSW (VectorMaton, arXiv:2603.01525 §3). Worst-case space `O(m^1.5)`. Engine
flag: `vector.collections.<name>.sequence_index = "suffix-automaton"`.

==== 6.1.4 LSM-Distributed HNSW (Optional)

For collections with high update rates: HELIX engine adopts LSM-VEC layout. Catalog flag:
`vector.collections.<name>.layout = "lsm-graph"`.

=== 6.2 Graph Modality (`proximadb-graph`)

Already extracted. This section specifies the additions the overhaul requires.

==== 6.2.1 Three Storage Layers (GredoDB-Aligned)

Split internals into:

* `proximadb-graph::record` -- vertex/edge records as `ProximaRecord` in Layer 1.
* `proximadb-graph::topology` -- adjacency `Ω = (Ns, Nt, I)` (GredoDB §4.2),
  `nidMap`/`vertexMap`/`edgeMap` deserialized at engine start.
* `proximadb-graph::index` -- label, attribute, embedding indexes built over Layer 1+2.

==== 6.2.2 Hybrid Traversal Operator `→`

GredoDB Algorithm 1, with operands in `{V×I, I×V, I×I, I×E}`. Pins one tile at a time;
returns a stream of `(tail_record, edge_record, head_record)` triples. Implemented in
`proximadb-graph::operators::hybrid_traverse`. Cost-based decision (Algorithm 2) on
whether to push attribute predicates first or traverse first uses cardinality estimates
from each entity's structural variation.

==== 6.2.3 Higher-Order Graph Constructs

Hyperedges and motifs reified as heterogeneous LPG (Higher-Order GDBs,
arXiv:2506.19661): a `:Family` hyperedge becomes a vertex with `:Member` edges to its
constituents. No HO-graph engine; lifting/lowering happens in `proximadb-graph::lifting`.

==== 6.2.4 Native Vector Index Inside the Graph

NaviX-aligned: vector index over a graph collection becomes a relationship table over the
graph CSR. The graph buffer manager loans frames directly; distance computation reads
on-frame bytes (zero copy). Runtime: ORION. Size-bound deployments use xCatalog/storage
projection tiering rather than a separate graph engine.

==== 6.2.5 Distributed Graph Requirements

Distributed graph scale-out is a relational substrate requirement. ORION supplies graph
planning hints; the relational distributed planner owns placement, fanout/fanin, shard
movement, and consistency. Graph partitioning keys remain based on canonical identity:
`(oid, tenant_id, hash(local_id))`.

  No more silent string-to-numeric coercion.

==== 6.4.2 Subset of SQL Supported

ProximaDB is **not** a general OLTP RDBMS. The supported SQL surface is:

* SELECT with WHERE, ORDER BY, GROUP BY, LIMIT, OFFSET, common aggregations.
* JOIN (inner, LEFT, LATERAL).
* INSERT / UPDATE / DELETE (single-collection ACID; cross-modal via 2PC).
* DDL: CREATE/ALTER/DROP COLLECTION (with optional vector / graph / document profile).
* CTEs (WITH ... AS).
* Subqueries (correlated and uncorrelated).
* Window functions (ROW_NUMBER, RANK, OVER PARTITION BY, LAG/LEAD).
* SQL/PGQ-style graph patterns (per ISO SQL:2023) for graph traversal in SQL.
* `<->`, `<#>`, `<=>` distance operators (pgvector compat).

Out of scope: stored procedures, triggers, full SQL transactional semantics across
arbitrary table sets (saga pattern only), foreign-key enforcement on insert (informational
only).

==== 6.4.3 Predicate Pushdown to Vector

Predicates on filterable columns push into `VectorTopK`'s predicate callback. The
adaptive-local heuristic and pre-filter fallback (Section 6.1.2) handle selectivity
range automatically.

==== 6.4.4 Cross-Model Joins via MSHJ and Hybrid Traversal

`JOIN ... ON GRAPH_PATH(...)` lowers to `HybridTraverse`. `JOIN ... ON VECTOR_DISTANCE(...) <
τ` lowers to a Multi-Stage Hash Join (M2 §4) where the vector-bearing side is the
"array-tile" probe.

=== 6.5 Event-Log Modality

Currently in `src/storage/engines/eventlog/`. The EventLog engine is append-only and
implements `UnifiedStorageEngine`. The overhaul:

==== 6.5.1 Knows-Style Structured Events

Event entries become `ProximaRecord` instances with profile `event@1`. Required fields:

* `local_id` is a strict-monotonic per-stream sequence (gap-detectable).
* `created_at` is microsecond UTC, monotonic per node.
* `provenance.verification = HashChained`; `signature` carries SHA-256 of
  `(prev_hash || record_bytes)`. The hash chain enables tamper detection.
* `props.event_type` (Symbol) and `props.payload` (Struct) carry the application data.
* `refs` carries correlation_id and causation_id as typed references.

==== 6.5.2 MiFID II / SEC Compliance

* **Immutability**: WAL marks event records as `immutable=true` at write; engine rejects
  UPDATE/DELETE. Retention policy in catalog enforces minimum retention (5y orders, 7y
  trades).
* **Tamper detection**: hash-chain validator runs at boundary; compromised chains alert
  via observability.
* **PITR**: existing PITR works because event entries are ordered by `(stream, local_id)`
  and snapshots checkpoint at fixed intervals.

==== 6.5.3 CDC-Out

Outbound CDC consumes the event stream; the Knows-style record format is
self-describing, so consumers (Kafka, webhooks) can decode without out-of-band schema
fetches. Existing sinks in `src/cdc/sinks/` already work with `ProximaRecord` if migrated.

=== 6.6 Time-Series Modality

CEDAR, CHRONO, TST engines exist (`src/storage/engines/cedar/`, `chrono/`, `tst/`).
Already complete per STRATEGIC_ROADMAP.adoc. Overhaul touches:

==== 6.6.1 Records as ProximaRecord

Time-series points are `ProximaRecord` with profile `tspoint@1`:

* `created_at` = sample time
* `props.measurement` = the value (typed, not stringified)
* `labels` = symbol set (e.g., `{symbol: AAPL, exchange: NASDAQ}`)
* `tenant_id` indexed for tenant-scoped queries.

==== 6.6.2 ASOF Join Through HybridTraverse

ASOF JOIN is a temporal restriction of `HybridTraverse` (left side: events; right side:
time-keyed series). Implementation in `proximadb-query::operators::asof_join`.

==== 6.6.3 Downsampling as a Catalog Policy

Each TS collection declares downsampling rules per granularity: `5s, 15s, 30s, 1m, 5m,
15m, 30m, 1h, 4h, 1d`. Background service materializes to per-granularity child
collections using Gorilla compression.

=== 6.7 Observability Modality (`proximadb-observability`)

Currently in root crate. Extract to `crates/modalities/proximadb-observability`.

==== 6.7.1 Three Profiles, One Envelope

Logs, metrics, and traces are three profiles of `ProximaRecord`:

* `log@1` -- props = structured fields; sequence = raw line tokens; labels = (severity,
  namespace, host).
* `metric@1` -- props = (value, unit, dimensions); labels = dimensions for cardinality
  control.
* `trace.span@1` -- identity = (trace_id, span_id); refs = (parent_span, span_links);
  props = attributes; labels = (service, operation).

Cross-correlation queries (e.g., "errors in last hour for services that depend on X")
become hybrid traversals over the dependency graph plus filter on log records.

==== 6.7.2 Production Readiness

Remove "EXPERIMENTAL" warnings once: (a) ingestion adapters carry full OTLP semantic
conventions parity, (b) tier policy is configured per profile, (c) cardinality protection
is enforced at write (deny labels with > N dimensions).

==== 6.7.3 PromQL/LogQL Parser

Add `proximadb-observability::query::promql` and `proximadb-observability::query::logql`
parsers that compile to the unified algebra. Existing SQL-via-LOGS/METRICS pseudo-functions
remain as a parallel surface.

=== 7.3 Filter-Aware Vector Search Plan Selection

The optimizer's choice for `VectorTopK(input, q, k, predicate)`:

[source,text]
----
let s = estimate_selectivity(predicate, input.statistics);
match s {
  s if s >= s_min  => HnswWithPredicate(γ-expanded, adaptive-local),
  s if s >= s_pre  => Ivf(prefilter-then-probe),
  _                => BruteForce(prefilter-rest),
}
----

Defaults: `s_min = 1/γ` (= 0.5 for γ=2), `s_pre = 0.05`. Both tunable per collection.

=== 7.4 Plan Exposure for Agent-Driven Optimization

Per DBPlanBench (arXiv:2602.10387), expose the physical plan as serialized JSON. The RL
planner already collects execution telemetry; LLM-proposed plan edits go through an
`evolutionary` advisor (already in `proximadb-query::evolutionary` per the workspace
plan). Validated by execution; rejected if reward drops.

Surface: REST endpoint `POST /api/v1/query/plan` returns the plan; `POST
/api/v1/query/plan/edit` accepts a modified plan; the executor validates and runs.

=== 7.5 Cross-Model Join Operators

==== 7.5.1 Multi-Stage Hash Join (M2)

For `vector × relational` joins where vector side is array-tile shaped: build D ordered
radix-bucket stages over array dimensions; one tile-pinned probe pass. Cost
`O(D·N + D·N·log M)` for sparse tiles, beats relational join + conversion under 30M rows.
Implementation: `proximadb-query::operators::mshj`.

==== 7.5.2 Hybrid Traversal `→`

For `graph × relational` and `graph × vector` joins: pin one tile while crossing into
another engine. Implementation: `proximadb-graph::operators::hybrid_traverse`.

==== 7.5.3 Block-Batched Semantic Join (NLP)

For `LLM-judged` predicates: pack batches of rows from both inputs into a single LLM
prompt; cost model derives optimal batch size from selectivity, token budget, per-token
cost (arXiv:2510.08489). Implementation: `proximadb-query::operators::semantic_join`.

== Section 8: Security & Multi-Tenancy

=== 8.1 Engine-Level Row Filtering (RLS)

Every `ProximaRecord` carries `tenant_id`, `permitted_principals`, `rls_policy_id`. The
optimizer pushes the active-principal filter into the engine's scan iterator. The
unified-RAG paper (arXiv:2605.03275 §6.4) measured 0.2% leakage at application level and
0.0% at engine level over 1000 cross-tenant queries.

Implementation:

. `tenant_id` indexed in every engine's primary index.
. Scan iterator constructor accepts `principal_context: PrincipalContext`.
. RLS policy DSL in catalog: `policy "tenant_isolation" allows reads where
  record.tenant_id = principal.tenant_id`. More complex policies (roles, groups) compile
  to predicates.
. **No SET ROLE override**: privileged superuser role is per-cluster, granted via mTLS
  client cert with explicit OU.

=== 8.2 Atomic Metadata + Embedding Writes

Every write to a vector-bearing collection goes through one `ProximaRecord` proto;
metadata fields and embedding cells are in the same record, the same WAL operation, and
the same engine flush. No application-managed split between "vector store" and "metadata
store".

=== 8.3 Wrapper-Layer Authentication (RUBICON)

Per-source connectors (CDC, S3 import, Kafka stream, REST) carry their auth contracts
explicitly (`src/security/auth/wrappers/`). Records produced by a wrapper carry the
wrapper's `actor` identity in `ProximaRecord.actor`; records produced from one tenant's
wrapper cannot be ingested into another tenant's space.

=== 8.4 Audit and Compliance

* All RLS-policy decisions logged at debug level; the audit log records denied-access
  events at info level.
* `record.signature` (when present) is verified at read on `verify_signatures = true`
  collections.
* The catalog records DDL changes with actor + before-state + after-state.
* SOC 2 / GDPR / SEC / MiFID II: existing TD items (TD-014 backup, TD-016 encryption at
  rest) cover the bulk; the remaining gap is documented in PRD.adoc and tracked.

=== 8.5 Encryption

* **In transit**: mTLS for inter-node (TD-006 resolved); TLS 1.3 for client; per-collection
  cert-CN-mapped access.
* **At rest**: AES-256-GCM (TD-016 resolved). The unified buffer pool decrypts on load,
  encrypts on flush; key rotation per file.
* **Field-level** (P3): per-column AES-256-GCM with column-master-key wrapping.

=== 9.1 Three-Component Disaggregated Runtime (Bacchus)

[source,mermaid]

=== 9.2 Arrow Flight as Canonical Cross-Tier Transport

* Cross-engine record-batch handoff (inter-buffer materialization).
* Cross-node query result shipping.
* Cold-tier read (Arrow Flight from a Parquet/GraphAr reader service).
* Client-side bulk export.

Port 5680 (Arrow Flight) becomes the recommended bulk transport; REST/gRPC remain for
small-result OLTP.

=== 9.3 Cold Tier Format

GraphAr (arXiv:2312.09577) for graph + relational + document + vector cold tier:

* Per-vertex-type Parquet table with internal-id + property columns + per-label binary
  columns (RLE compressed).
* Per-edge-type Parquet table sorted by `(svid, tvid)` with COO + auxiliary CSR offset.
* PAC (Page-Aligned Collections) for fast neighbor retrieval.
* SIMD/BMI interval decoding for label filters: 14.8× faster than plain Parquet.

== Section 12: Architecture Decision Records

Each ADR is a sticky decision; new turns should not relitigate without explicit reason.

=== ADR-2026-05-08-001: Adopt `ProximaRecord` Envelope

* **Decision**: Define a single `ProximaRecord` envelope (Section 3) with identity,
  variation, tenancy, time, provenance, props, refs, edge, embeddings, sequence, labels,
  extensions. Replace per-modality record protos.
* **Why**: Three competing record shapes today (G2). Cross-modality queries are limited
  by the least-common-denominator. Convergent across GredoDB, U-Schema, unified-RAG, and
  Knows.
* **Consequences**: One large proto change with a long backward-compat tail. Engines and
  query results migrate one at a time. Old protos kept as `// LEGACY` until v0.3.0.
* **Alternatives considered**: (a) keep per-modality types and add a thin wrapper trait
  (rejected: doesn't fix the cross-cutting field reinvention); (b) make each modality's
  record carry a shared `Header` struct (rejected: same outcome with less coverage).

=== ADR-2026-05-08-002: Adopt `ProximaValue` as Wire Type

* **Decision**: Promote `CatalogDataType` to a true wire type as `ProximaValue` (Section
  4.2). Decimal, TimestampTz, Uuid, Json, Vector, etc. are first-class proto variants.
* **Why**: pgwire RDBMS workloads silently lose precision through `SqlValue` (G1).
* **Consequences**: Wire format is wider; clients need updated decoders.
* **Alternatives considered**: extend `SqlValue` with new oneof variants (rejected:
  perpetuates the loose-typed legacy design).

=== ADR-2026-05-08-003: Predicate-Aware HNSW with Adaptive-Local Heuristic

* **Decision**: AXIS HNSW becomes γ-expanded with predicate-agnostic prune (ACORN); search
  uses adaptive-local heuristic (NaviX); per-modality sharding (HMGI); PAX co-location of
  filter columns (FilterAgnosticPG).
* **Why**: post-filter HNSW is 10-1000× slower than predicate-aware HNSW across the
  selectivity range; production cost dominated by page accesses, not float ops.
* **Consequences**: Slightly larger index size (γ=2 doubles candidate edges); construction
  time +20-30%.
* **Alternatives considered**: keep HNSW + IVF as separate indexes and route per query
  (rejected: HMGI-style partitioning subsumes this and adds polysemy resolution).

=== ADR-2026-05-08-004: Engine-Level Row-Level Security

* **Decision**: `tenant_id` and `permitted_principals` are ProximaRecord fields, indexed
  in every engine, pushed into scan iterators.
* **Why**: 0.2% application-level leakage measured (unified-RAG §6.4); enterprise
  multi-tenancy requires zero leakage.
* **Consequences**: Every collection grows by ~20 bytes per record (tenant_id + bitset
  pointer). Indexes need a leading tenant_id column.
* **Alternatives considered**: middleware-only filtering (rejected: leakage); per-tenant
  collections (rejected: explodes catalog and breaks cross-tenant analytic queries the
  application owner is allowed to run).

=== ADR-2026-05-08-005: PAX Co-Location of Filter and Vector Columns

* **Decision**: VIPER and other columnar engines co-locate frequently-filtered columns in
  the same row group (and same physical page where size permits) as the embedding column.
* **Why**: page accesses dominate distance computations in production
  (FilterAgnosticPG §2).
* **Consequences**: Layout planner needs query-trace input; some collections need a
  re-flush after promotion. Background.

=== ADR-2026-05-08-006: Three-Layer Storage Model

* **Decision**: Adopt GredoDB's record / topology / index three-layer model. Records live
  in unified columnar PAX; topology stored as CSR/COO over edge records; vector indexes
  stored as relationship tables.
* **Why**: Convergent across GredoDB, M2, GraphAr, NaviX. Cleanly separates concerns;
  topology cache and vector index can be rebuilt from records.
* **Consequences**: Background cache-warming and reindex jobs become first-class.

=== ADR-2026-05-08-007: Disaggregated WAL Log Service

* **Decision**: WAL evolves to a Paxos-backed log service (PALF-style) for cluster
  deployments. Single-binary embedded mode keeps co-located log.
* **Why**: Cloud-native scaling per Bacchus §2.
* **Consequences**: Cluster deployment requires log-service nodes; configuration shape
  changes. Phase G work; not blocking earlier phases.

=== ADR-2026-05-08-008: Plan-as-JSON for Agent-Driven Optimization

* **Decision**: Physical plans are serializable JSON; REST endpoints expose plan and
  accept edits; LLM/RL planner advisor runs in `proximadb-query::evolutionary`.
* **Why**: DBPlanBench reports 4.78× speedup from LLM-edited plans; ProximaDB's RL
  planner already collects telemetry and benefits from a richer action space.
* **Consequences**: Plan schema becomes part of public surface; security implication
  (plan exposure is gated to authenticated, tenant-scoped sessions).

=== ADR-2026-05-08-009: Open-Shape Documents With Variation Catalog

* **Decision**: Document collections accept ad-hoc variations on first write; the catalog
  records each variation with U-Schema-style property classification. Closed-shape
  (relational) collections reject non-matching writes.
* **Why**: Real document workloads have heterogeneous shapes; pretending they don't loses
  information and forces application-side normalization.
* **Consequences**: Catalog grows linearly with variation count per collection; periodic
  variation pruning is needed.

=== ADR-2026-05-08-010: One Logical Algebra, Multiple Surfaces

* **Decision**: Operators are defined once in the algebra (Section 7.1). SQL, Cypher/GQL,
  AQL, UQL, PromQL, LogQL all compile to the same operators.
* **Why**: Convergent across M2, GredoDB, RUBICON, AV-SQL, flexvec, GraphAr.
* **Consequences**: New surface languages are cheap (parser + lowering only). Optimizer
  rules are written once.

== Section 13: Migration and Compatibility

* The legacy proto types stay alive through compatibility shims (the existing pattern
  used for `proximadb-graph` extraction). No public API breaks within v0.2.x.
* `ProximaRecord` and `ProximaValue` ship in v0.2.0 as the recommended types. Legacy
  wire types still work; converters live in the `proximadb-records` crate.
* v0.3.0 removes legacy proto types in one major version bump. Migration script
  (`scripts/migrate_v02_v03.py`) re-flushes existing data to the new layout.
* Embedded bindings (Python, Java, Node.js) get auto-generated client types from the
  new protos; thin wrappers expose ergonomic constructors.
* External catalogs (Iceberg, Delta, Glue, Polaris, Unity) publish a manifest of mapped
  types per `ProximaType` variant; type promotion follows U-Schema mapping table
  (Section 4).

== Bottom Line

The current architecture is directionally correct -- specialized engines, unified WAL,
proto-first design, format-first storage. The next 12-18 months should consolidate the
foundation under one record envelope, one type system, one buffer pool, one logical
algebra, and one security boundary -- not scatter the design surface further.

The deliverable is not "more crates" or "more engines"; it is **less divergence at the
seams that matter most**: types, records, tenancy, plans. Once those are unified, every
new modality, every new index family, every new query surface, and every new transport
becomes a small, local addition rather than a system-wide change.
