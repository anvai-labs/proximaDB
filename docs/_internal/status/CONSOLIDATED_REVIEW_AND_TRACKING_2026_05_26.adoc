Audit of current code, API surfaces, deployment shapes, and feature dashboards. This file is a reconciliation layer, not a new support contract.

== Executive Summary

ProximaDB has one clearly supported customer-safe path today: canonical ProximaRecord vector CRUD/search over REST v2 and gRPC v2. Most other product surfaces are implemented but correctly belong in Beta or Experimental until canonical WAL/xCatalog authority, API parity, route explanations, and production validation are finished.

The largest honesty risk is not missing code; it is proliferation:

* Dashboard summary rows have been refreshed, but detailed dashboard rows still contain stale "complete/planned" contradictions.
* API contracts exist in at least four layers: `docs/openapi/proximadb-openapi.yaml`, `src/network/rest/*`, `crates/platform/proximadb-api/src/rest/*`, and `src/api_handlers/*`.
* Deployment artifacts have a canonical Helm chart plus divergent infrastructure Helm, plain Kubernetes, enterprise release, systemd, Docker, and two Terraform shapes.
* The storage/query naming migration still carries both `multimodal` and `multimodel` paths.

The fastest path to a more honest release is to finish the small pre-release safety items first, quarantine stale dashboards/deployment manifests, then complete API parity and hot-path correctness gaps.

* New customer-facing claims must cite `docs/SUPPORTED_SURFACE.adoc`.
