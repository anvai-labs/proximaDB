= ADR-097 P2.4 exit gate — TPC-DS load + MATERIALIZE memory (2026-10-23)
:toc: left
:icons: font
// status-as-of: 2026-10-23

[.lead]
The P2.4 gate is "TPC-DS SF1 loads on a release build without OOM, peak RSS recorded"
(TD-SEAM-4). **It did not pass at SF1 here**, and not because of memory: with the Layer A
spill on (the default), an INSERT into a table that has spilled decodes every spill segment
per row (link:../../10-quality/td/TD-USUB-21-insert-existence-probe-decodes-every-spill-segment.adoc[TD-USUB-21]),
so load time grows quadratically and SF1 does not finish. Streaming MATERIALIZE itself
is bounded: at every scale measured it added 0.3–0.4 GiB over the loaded state and published
all 22 tables, including from spilled segments.

== Setup

----
 commit    develop @ 6d71e9e83 + the per-table timing change in this PR
 build     cargo test --release (opt-level 3, thin LTO), CARGO_BUILD_JOBS=2
 host      4 vCPU, 15.7 GiB RAM, 8 GiB swap; cgroup v1 memory.limit_in_bytes = 13,677 MiB
 harness   tests/tpc_perf_ledger_e2e.rs, TPC_PERF_BENCHMARK=tpcds TPC_PERF_LOAD_ONLY=1
           (load over pgwire, parallelism 1, then ALTER TABLE … MATERIALIZE per table)
 scale>0.05 also TPC_PERF_ALLOW_LARGE_SCALE=I_ACCEPT_ISOLATED_OOM TPC_PERF_HOST_HEADROOM_MIB=2048
 memory    per phase: VmHWM (reset via /proc/self/clear_refs) and the cgroup v1 peak
           (memory.max_usage_in_bytes, reset per phase); whole run: VmHWM sampled every 5 s
----

`scripts/run_tpc_perf_ledger.sh` needs systemd and cgroup v2; this host has neither, so the
runs used the shell's existing 13.7 GiB cgroup v1 limit (13.4 GiB, 2.4 GiB short of the host).
The cgroup peak includes page cache, so it reaches the limit without an OOM kill; VmHWM is the
process's peak RSS.

== Reading

* **MATERIALIZE is bounded.** Its peak over the loaded state was +366 MiB (SF 0.01), +329 MiB
  (SF 0.1) and +405 MiB (SF 0.2) while the data grew 20×. This is the P2.4 claim (chunked scan,
  sort under a capped pool, multipart part writer), and it holds over spilled segments too.
* **Load is the blocker, in two ways.**
  . With spill on, every INSERT probes for an existing row; a miss in the memtable reads and
    decodes every spill segment whole (TD-USUB-21). Cost per row grows with the spilled
    data, so load is quadratic. That code is the P2.2 spill path (default on since
    2026-10-22, `c62ab32b7`), not P2.4's.
  . With spill off, the memtable holds every row at ≈ 6.5 KiB each, so SF1 needs ≈ 39 GiB.
* **The ≈ 3.3 GiB baseline** is present 5 s into an SF 0.01 run, before most of the 57 k rows
  arrive. It is not explained here; it bounds how small a host can run the gate at all.

== What it takes to close the gate

Fix TD-USUB-21 (skip the probe for generated oids; prune the point lookup by the segments'
oid sort and Bloom filters), then rerun at SF1 with spill on:

----
TPC_PERF_SCALE=1 TPC_PERF_BENCHMARK=tpcds TPC_PERF_LOAD_ONLY=1 \
TPC_PERF_ALLOW_LARGE_SCALE=I_ACCEPT_ISOLATED_OOM TPC_PERF_HOST_HEADROOM_MIB=2048 \
  cargo test --release --test tpc_perf_ledger_e2e -- --ignored --nocapture
----

Disk: the spill-off runs peaked at 1.0 GiB (SF 0.1) and 2.0 GiB (SF 0.2) of temp data, so a
spill-off SF1 would need ≈ 10 GiB against the 8.8 GiB free here. With spill on the WAL is
truncated behind flushed segments (P2.2), so the SF1 rerun is expected to need less; measure it.
