= TD-TIER-1 E1: fixed-object repeated range-cap sweep (4 / 16 / 40 MiB)

**Date:** 2026-10-26 · **Branch:** `bench/tier1-e1-fixed` @ `eb1dd04e2` (binary built in-worktree at `f5aef1b0b`; the two later commits are harness/tests-only) · **TD:** link:../../10-quality/td/TD-TIER-1-collection-storage-policy-and-residency.adoc[TD-TIER-1] SC0/E1 · **Supersedes the pilot's −50% figure:** link:../../history/evidence/TIER1_SC0_RANGE_CAP_SWEEP_2026_10_26.adoc[the #2249 pilot] measured fresh beds per arm (21/25/26 cells) and overstated the cap effect; this run eliminates that confound.

== Protocol (the E1 gate from STORAGE_PLAN §E1)

One bed built **once** (`sift1m_get_reduction.py` full run: 1M×128 SIFT1M, settle flags, MinIO + Toxiproxy 5+5 ms ≈ 13 ms RTT); its prefix — one 1M-row PAX segment, **36 coarse cells**, and the centroid directory (the 4-object prefix: segment, 2 directory generations, warm-cache sidecar) — is the **fixture**, ETag-fingerprinted before and verified unchanged after all arms (only the `_cache/warm_cache.json` sidecar rewrote: cache state, not fixture data). Each arm runs `--skip-ingest` (the harness mode this slice adds): a fresh server registers the collection against the same prefix — **failing closed if its catalog assigns an id other than the fixture's** — and measures the identical 1,000 query IDs (object_cold phase, concurrency 1, `--read-ranges-inflight 16`, P5b defaults on, sweep gates armed). Two repeats per cap; the only variable is `--coalesce-range-mb`.

== Findings

. **The request plan is a pure function of (cap, objects, queries):** every repeat reproduced its arm's request count **exactly** — 18.462/18.462, 13.169/13.169, 12.880/12.880 — across independent servers and cold caches. Run-to-run variance lives entirely in wall-clock (p50 spread ≤ 6 ms except cap40-r1's noisy 144; p99 spread 15–109 ms; CPU spread ≤ 7 s except cap40-r1). [M]
. **4 → 16 MiB cuts requests 29%** (18.462 → 13.169): the honest magnitude. The pilot's fresh-bed design measured −50%; on identical objects the geometry confound accounted for the difference. Recall and waves (p50 3, p95 4) unchanged; bytes **+4.5%** (50,746,626 → 53,030,980 B/q, identical within arm — the coalescing overread, not noise). [M]
. **16 → 40 MiB is the plateau AND a latency/CPU loss:** 0.289 requests saved (13.169 → 12.880) while mean p50 rises 111.5 → 128 ms, mean p99 177.8 → 228 ms (cap40-r1's 283 inflates the mean, but even the clean r2 repeat costs +3 ms p99 and the CPU means separate cleanly: 111.5 vs 125.9 s — over-merged GETs drag useless tails through the transfer). **16 MiB is the optimum on this bed: −29% requests, best p99, flat CPU.** [M]
. **Tail behavior separates where medians don't:** cap4 and cap16 have near-identical p50s (109.3 vs 111.5 mean) but cap16's p99 is materially better in both repeats (168/170 vs 229/283... cap4-r2 168, cap16 170/185 — comparable; cap4-r1 229 and cap40-r1 283 are the noisy pair). With n=2, p99 claims are directional only; the p50/CPU/request findings are the load-bearing ones. [M]

== What this run does NOT establish (per the design's stop rule)

Fragmented segments, filtered queries, 10M rows and 768d remain unmeasured — no production default change and no pricing claim rides on this run (production S3 already targets 8 MiB ranges via `IopsBudget`; a default change needs the finalist arms). The warm phases under fixture reuse need re-definition before they can gate anything. Missing telemetry still: request-size distribution and useful/fetched/overread byte split (server-side instrumentation, separate slice); p99/RSS/CPU landed here.
