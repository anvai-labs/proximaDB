== Round-2 blockers (new — fixed in this session)

[cols="1,3,2", options="header"]
|===
| Severity | Blocker | Fix

| P0
| `POST /api/v2/collections/{missing}/records/batch` returned HTTP 200 with
  `BatchOperationResult::failure` body — same silent-failure shape that hid
  the v2 INSERT→SEARCH gap. The REST handler at `src/network/rest/v2/records.rs:1133`
  wrapped the handler's `Ok(failure(NOT_FOUND))` and forwarded it as success.
| `src/network/rest/v2/records.rs` now maps the `NOT_FOUND` error_code onto
  `ApiError::NotFound`, which translates to HTTP 404 via the existing
  `errors/mod.rs:142` mapping. Regression test:
  `tests/release_smoke_v2.rs::rest_v2_insert_to_missing_collection_returns_404`.

| P1
| v2 search `top_k` had no upper bound — adversarial client could request
  unbounded result-buffer allocation (`src/network/rest/v2/records.rs:1369`
  only validated `top_k > 0`).
| Added a default cap of `10_000`, overridable via
  `PROXIMADB_MAX_SEARCH_TOP_K` (renamed to `PROXIMADB_SEARCH_MAX_TOP_K` in
  v0.3.0, #1207; the old name is no longer read). Above-cap requests return HTTP 400.
  Regression test:
  `tests/release_smoke_v2.rs::rest_v2_search_top_k_above_cap_returns_400`.

| P1
| Arrow Flight INSERT (`src/network/arrow_ipc/service.rs:834`) routed to
  `handle_record_insert_batch_for_tenant`, which was **missing the precision-
  coercion block** that `handle_record_batch_for_tenant` (the upsert path)
  already applied. Arrow Flight INSERT into an fp16 collection would land
  fp32 records, divergent from REST/gRPC v2 behaviour. Same class of bug as
  the Round-1 v2 metric gap.
| `src/api_handlers/request_handlers.rs` `handle_record_insert_batch_for_tenant`
  now applies the same precision-resolver coercion. Parity test deferred to
  TD-082.

|===

== Round-2 blockers (new — deferred to TD entries)

[cols="1,3,1", options="header"]
|===
| Severity | Blocker | Tracker

| P1
| `precision_resolver` is wired only when `catalog_manager.default_catalog()`
  succeeds (`src/database.rs:159`). In embedded test harnesses that don't
  register a default catalog, the resolver stays unwired and the fp16
  canonical-bytes metric is emitted under `precision="fp32"`. Surfaced this
  session when `rest_v2_insert_into_fp16_collection_accumulates_canonical_bytes_metric`
  failed after the WS3 fixes; the test is `#[ignore]`'d with a note. Production
  wires the resolver correctly.
| TD-080

| P1
| `tests/release_smoke_v2.rs` is Rust-only — no Python SDK equivalent. A
  regression in `clients/python/src/proximadb_sdk/protocols/rest_sync.py`
  insert→search round-trip would not be caught by `make release-check`. The
  existing Python unit test mocks HTTP rather than exercising the live path.
| TD-081

| P1
| `handle_record_insert_batch_for_tenant` and `handle_record_batch_for_tenant`
  now both have the precision-coercion block, but no test asserts they remain
  behaviourally equivalent under identical input. Another precision/validation
  block could regress only one in a future change.
| TD-082

| Medium
| Rust SDK (`clients/rust/src/collection.rs:621`) exposes v2 upsert only — no
  full INSERT with `props` / `text_fields`. Rust SDK users are constrained to
  v1-shape metadata dict.
| TD-083

| Medium
| PostgreSQL wire (`src/network/postgres/protocol.rs`) does not expose v2
  `props` / `text_fields` typed-field insert. pgvector users stay on v1-shape
  SQL.
| TD-084
|===
