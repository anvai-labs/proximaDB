= PostgreSQL Wire Protocol Reference
:toc: left
:toclevels: 2
:icons: font

[.lead]
ProximaDB exposes the PostgreSQL wire protocol on port `5433` by default, bound to
`127.0.0.1`. This reference covers the current release's SQL surface and the v2 record-typed
INSERT syntax that closes TD-084.

== Connection

[IMPORTANT]
====
*The default bind is loopback, which makes the examples below host-local.* Under the trust
auth default the boot-time listener preflight
(`validate_trust_only_listener`) admits an unauthenticated single-tenant pgwire listener on
**loopback only**. So:

* a locally-run `proximadb-server` → `localhost:5433` works as shown;
* the published container image → pgwire listens on `127.0.0.1:5433` *inside* the
  container, so a published `5433` accepts no connections. Reach it from inside the
  container's network namespace
  (`docker run --rm -it --network container:proximadb postgres:16 psql -h 127.0.0.1 -p 5433 ...`),
  since the image ships no psql client;
* to serve it off loopback, give the listener per-connection authentication first (SCRAM,
  below) and *then* set `[api] pg_port`. Setting `pg_port` without SCRAM is fail-closed:
  the preflight refuses the listener and the server exits 1.

Tracked in `TD-PGWIRE-CONTAINER-1`.
====

[source,bash]
----
# psql client
psql "host=localhost port=5433 user=postgres dbname=proximadb sslmode=disable"

# tokio-postgres (Rust)
tokio_postgres::connect(
    "host=127.0.0.1 port=5433 user=postgres dbname=proximadb sslmode=disable",
    tokio_postgres::NoTls,
).await?;
----

pgwire authentication follows a fail-closed ladder (TD-PGWIRE-AUTH-1): with
`[security.authentication] enabled`, SCRAM-SHA-256 is REQUIRED (provision identities under
`[security.authentication.scram_users]`); otherwise `PROXIMADB_PGWIRE_AUTH=password`
(or `[security.pgwire] auth`) raises pgwire to SCRAM while the deployment stays in trust
elsewhere. Absent any of these, the dev default is trust (any user name, no credential).
mTLS remains tracked under TD-TENANT-1 (b).

=== Tenant selection

The connection **`dbname` selects the tenant** — a connection to `dbname=acme`
scopes every read and write to tenant `acme` when open header trust is configured. The value is literal, so
`dbname=proximadb` selects tenant `proximadb`; it is not an alias for a default.
Only an omitted database selects the configured `[server.tenant] default_tenant`
in single-tenant mode, while multi-tenant mode rejects an omission. Under
authenticated-only or gateway-only trust, pgwire has no credential binding and
therefore rejects explicit non-default database and session-variable assertions
with SQLSTATE `28000`; the reserved literal `default` remains accepted. Pgwire
uses the same deployment-mode and tenant-trust primitives as REST, gRPC, and
Flight. Under a policy that accepts the assertion, a session may override the
write tenant with `SET proximadb.write.tenant_id = '<tenant>'`. Tenant
isolation is *structural* — the tenant is composed into the storage key at the
service boundary, never applied as a per-query predicate — so a row written under
one tenant is invisible to another even under an identical logical
collection/table name. See link:./client-surface-map.adoc[Client Surface Map]
for the tenant-identity-per-transport table.

== Supported today

The pgwire surface is **Beta** (see link:../SUPPORTED_SURFACE.adoc[the support contract]). Each
line below names the test that proves it.

* **DDL** — `CREATE TABLE` with typed columns (BIGINT, VARCHAR, FLOAT, BOOLEAN, JSON, VECTOR, …;
  full list in `crates/control/proximadb-catalog/src/lib.rs::CatalogDataType`), including
  `WITH (canonical_embedding_precision = 'fp16')`; `DROP TABLE IF EXISTS`; `ALTER TABLE …
  MATERIALIZE` to publish a Parquet-backed copy that analytical queries route to DataFusion.
* **Queries** — ANSI `SELECT` with joins, aggregates, `GROUP BY`, `ORDER BY` and subqueries.
  TPC-H (22) and TPC-DS run over pgwire as counted ratchets (`tests/tpch_pgwire_e2e.rs`,
  `tests/tpcds_pgwire_e2e.rs`).
* **Writes** — single- and multi-row `INSERT … VALUES` (`tests/pgwire_fk_referential_actions_e2e.rs`);
  `UPDATE` and `DELETE` (`tests/pgwire_relational_native_read_after_write_e2e.rs`); `INSERT … SELECT`
  (implemented, but no end-to-end pgwire test yet); `INSERT … ON CONFLICT … DO UPDATE` with UNIQUE and
  foreign-key enforcement (`tests/pgwire_upsert_constraints_e2e.rs`); `COPY … FROM STDIN`
  (`tests/pgwire_td064_write_tenant_isolation_e2e.rs`). Typed values land in `ProximaRecord.props`
  (`tests/pgwire_insert_props_e2e.rs`).
* **Foreign keys** — `ON DELETE RESTRICT | CASCADE | SET NULL` on single-column keys
  (`tests/pgwire_fk_referential_actions_e2e.rs`).
* **Transactions** — `BEGIN` / `COMMIT` / `ROLLBACK` and read-only transactions (ADR-018 P2.D,
  `tests/pgwire_transaction_e2e.rs`). *Unreleased (on `develop`, ships in v0.5):* with the opt-in
  `[oltp] atomic_commit`, COMMIT is all-or-nothing and crash-atomic (ADR-095,
  `tests/pgwire_atomic_commit_e2e.rs`).
* **Vectors (Beta)** — `ORDER BY embedding <-> '<literal>'::vector LIMIT k`, over a collection
  created through REST or the SDK, and over a pgwire table that also has a JSON or JSONB column, such as
  `(id VARCHAR PRIMARY KEY, embedding VECTOR(n), payload JSONB)` (`tests/mem0_pgwire_filter_e2e.rs`).
  Not yet: projecting the distance as a column (wrong result, TD-PGVEC-1), the `vector_search()`
  table function over pgwire, and `VECTOR(n)` in a table without a JSON or JSONB column, where inserts are
  checked against dimension 1 and fail (TD-XMODAL-4, TD-SQLCOLL-1).
* **Protocol** — the extended query protocol with bound parameters for vector search through
  tokio-postgres and asyncpg (`tests/pgwire_extended_param_e2e.rs`; see TD-PGEXT-1 for the drivers
  that fail), query cancellation (`tests/pgwire_cancel_e2e.rs`),
  SCRAM-SHA-256 authentication (`tests/pgwire_scram_auth_e2e.rs`), and the `pg_catalog` views psql
  needs for `\d` (`tests/pgwire_psql_introspection_e2e.rs`).

[NOTE]
====
**v2 record `text_fields` via pgwire** — the v2 REST `text_fields` field is
syntactic sugar that the REST handler folds into `props` as `String` entries
before the canonical write path
(`src/network/rest/v2/records.rs::insert_records`). The canonical
`ProximaRecord` has no separate `text_fields` field. Pgwire INSERT into a
`VARCHAR` / `TEXT` column is functionally equivalent: the typed value lands in
`props` as `ProximaValue::String(...)`, the same shape REST text_fields
produces. The example below shows the round trip.
====

== v2 Record-Typed INSERT Example

[source,sql]
----
CREATE TABLE products (
    id        VARCHAR PRIMARY KEY,
    title     VARCHAR,
    price     FLOAT,
    stock     BIGINT,
    active    BOOLEAN,
    metadata  JSON
);

INSERT INTO products (id, title, price, stock, active, metadata)
VALUES ('p-1001', 'Widget', 9.99, 42, true, '{"brand":"Acme","tags":["new"]}');
----

After commit, the row is reachable via:

* `SELECT ... FROM products WHERE id = 'p-1001'` (pgwire).
* `GET /api/v2/collections/products/records/p-1001` (REST canonical record
  fetch).

Each non-primary-key column lands in `ProximaRecord.props` as a typed
`ProximaValue`. The `id` column populates `ProximaRecord.oid`; vector columns
(if any) populate `ProximaRecord.embeddings[]`.

== Not supported today

=== Refused with an error

These return a specific SQLSTATE instead of running:

* **Savepoints and two-phase commit** (`SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, `RELEASE`,
  `PREPARE TRANSACTION`) — `0A000`; ADR-018 defers them to Phase 3.
* **DDL and `COPY` inside a transaction** — `0A000` (ADR-018 P2.D).
* **`INSERT … SELECT` inside an atomic transaction** — `0A000`, only when the unreleased
  `[oltp] atomic_commit` gate is on (TD-PGOLTP-1).
* **Literal-only predicates on vector-profile tables** (`WHERE 1 = 1`) — `XX000`
  (TD-PGWIRE-LITPRED-1).
* **Triggers, stored procedures and PL/pgSQL** — not on the ADR-095 path.
* **`ON UPDATE` foreign-key actions and composite foreign keys** — TD-110.

=== Known divergences from PostgreSQL

These run, but the result can differ from what PostgreSQL would return:

* **`WHERE id = <value>` misses rows in a table without a primary key** that has a column named
  `id` or `record_id` (also `IN (...)`): `SELECT` returns no rows while `count(*)` counts them,
  and `UPDATE` / `DELETE` report 0 rows and change nothing (TD-RELIDEQ-1). Declare a primary key.
* **Extended-protocol clients fail on many queries.** The server describes relational SELECTs as
  returning zero columns and every `$N` parameter as `text` (TD-PGEXT-1). Observed on 0.4.1:
  asyncpg cannot read a relational table (parameterized vector search works); psycopg 3 fails on
  any parameterized query, vector search included, and on a repeated query once it auto-prepares
  it (6th execution; `prepare_threshold=None` or `ClientCursor` avoids that); psql `\bind` fails on
  both. JDBC and ORMs use the same protocol and are expected to be affected (not
  yet tested). The simple query protocol (psql, psycopg 2, `simple_query`) works.
* **No read-your-own-writes for `SELECT` inside a transaction.** A `SELECT` in an open transaction
  does not see the transaction's own uncommitted writes. DML is buffered until COMMIT and then
  applied in order, so later statements do act on earlier ones' rows. This holds in v0.4.x and on
  `develop`, with or without `[oltp] atomic_commit` (ADR-018 P2.D; TD-PGOLTP-4).
* **`UPDATE`, `DELETE` and `INSERT … SELECT` report zero rows inside a transaction.** Buffered
  statements are acknowledged as `UPDATE 0` / `DELETE 0` / `INSERT 0 0` whatever they will affect
  (`INSERT … VALUES` reports its real count), so ORM
  rowcount checks (SQLAlchemy, Django) fail inside transactions.
* **Constraint violations inside a transaction surface at COMMIT**, not at the statement that
  causes them.
* **No snapshot isolation or row locks.** Concurrent readers can observe a committed transaction
  while it is being applied (TD-PGOLTP-4).
* **COMMIT is not atomic.** A COMMIT that fails partway leaves its earlier statements durable. v0.4.x
  has no opt-in; on `develop`, `[oltp] atomic_commit` (unreleased, ships in v0.5) makes it
  all-or-nothing (TD-PGOLTP-1).
* **`INSERT … SELECT` is not one atomic unit** — it writes in 1,024-row batches (TD-PGOLTP-1).
* **`RETURNING` is not implemented** — the clause is not applied to DML results; sequences are
  also missing (TD-PGOLTP-5).

=== Not available

* **Reaching pgwire through a published container port** — in the published image pgwire listens
  on `127.0.0.1` only until authenticated exposure lands (TD-PGWIRE-CONTAINER-1, roadmap v0.5).
* **Optimistic versioning / conditional writes** — see link:./rest.adoc[REST API Reference].

== Cross-Protocol Contract

Pgwire writes share the same catalog identifier as REST/gRPC v2 record writes.
A row inserted via SQL is readable via REST v2 (and vice versa). Both protocols
go through the same `UnifiedHandlers::handle_record_batch_for_tenant` path
(`src/api_handlers/request_handlers.rs:903`) after parsing, so precision
coercion, schema validation, and freshness modes apply uniformly.
