= REST API Reference
:toc: left
:toclevels: 2
:icons: font

[.lead]
Developer‑first REST API reference. Base URL: `http://localhost:5678`.

== Status Notes

* Canonical REST record/table APIs live under `/api/v2`.
* REST `/api/v1/*` routes are deprecated compatibility facades for existing clients and emit deprecation metadata.
* Document, graph, and observability APIs are beta.
* Cross-model SQL should prefer pgwire/SQL. REST v1 unified query routes remain compatibility facades while record-native query APIs mature.

[WARNING]
====
**Not supported today** (the live source of truth is the `writes` block on
the route-health diagnostic endpoint `GET /api/v2/_diagnostics/collections/:id/route-health`):

* Optimistic versioning / compare-and-set on insert or upsert.
* Conditional writes (predicate-gated insert / upsert / delete).
* Update-by-filter and delete-by-filter.
* Patch / partial-record update.
* Collection-default freshness mode (per-request `freshness_mode` only).

Search-side limits today:

* `top_k` is capped at **10000** by default on EVERY search surface (REST,
  gRPC, Arrow Flight, pgwire), not REST alone. Override via env var
  `PROXIMADB_SEARCH_MAX_TOP_K`. Requests above the cap are rejected
  (HTTP 400 / `INVALID_ARGUMENT`).

See link:../SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`] "Not Supported
in the current release" for the full list and TD pointers.
====

=== Key Differentiator

ProximaDB's multi-model query engine enables cross-model joins that are impossible with single-model databases (Pinecone, Weaviate, Milvus). Use pgwire SQL as the canonical query surface; `POST /api/v1/unified/federated` remains available only as a deprecated REST compatibility facade.

== REST v1 Compatibility Examples

These routes remain for existing clients. They are deprecated compatibility
facades and responses include `Deprecation: true`,
`X-ProximaDB-API-Status: deprecated-compatibility`, and replacement-surface
headers.

=== POST /api/v1/collections

[source,bash]
----
curl -X POST http://localhost:5678/api/v1/collections \
  -H "Content-Type: application/json" \
  -d '{
    "collection_id": "docs",
    "collection_config": {
      "dimension": 768,
      "storage_engine": "sst",
      "distance_metric": "cosine"
    }
  }'
----

Optional field `canonical_embedding_precision` (default `fp32`) sets the
on-disk + in-memory scalar type for the embedding column. Non-`fp32`
values trade a small recall delta for ~50% storage reduction (`fp16` /
`bf16`) or up to ~75% (`int8` / `uint8`). The field accepts either the
SCREAMING proto label or a shorthand (`fp16`, `f16`, `half`, `float16`,
`bf16`, `int8`, `uint8`); unknown values fall back to `fp32`.

[source,bash]
----
curl -X POST http://localhost:5678/api/v1/collections \
  -H "Content-Type: application/json" \
  -d '{
    "collection_id": "embeddings_fp16",
    "collection_config": {
      "dimension": 768,
      "storage_engine": "sst",
      "distance_metric": "cosine",
      "canonical_embedding_precision": 2
    }
  }'
----

The proto enum discriminants are: 1=`fp32`, 2=`fp16`, 3=`bf16`,
4=`int8`, 5=`uint8`. String forms (`"fp16"`, `"EMBEDDING_PRECISION_FP16"`)
are accepted via the same field. Once set on a collection, every
ingest path — REST `vectors/batch`, gRPC, Arrow Flight `do_action` (experimental),
the async embedding drainer — coerces records to the collection's
canonical precision before WAL append, and compaction preserves it
through rewrites.

Observability: `proximadb_embedding_precision_canonical_bytes` exposes
the per-(collection, precision) byte total at the
`/metrics/prometheus` endpoint. Operators can verify a collection is
storing fp16 by scraping after some ingest:

[source,bash]
----
curl -s http://localhost:5678/metrics/prometheus | grep canonical_bytes
# proximadb_embedding_precision_canonical_bytes{collection="embeddings_fp16",precision="fp16"} N
----

NOTE: `/metrics/prometheus` and `/metrics/json` are operator endpoints: their
series carry every tenant's `tenant_id` and collection names. With
authentication enabled they require the `ViewSystemMetrics` permission (the
`admin` role); without authentication (single-tenant development) they are
open, so do not expose the listener to tenants in that mode.

== Unified Multi‑Model Query (Stable)

ProximaDB's multi-model query engine is the key differentiator vs single-model databases (Pinecone, Weaviate, Milvus). It enables cross-model joins in a single SQL query.

=== POST /api/v2/query

**Shared query facade.** Use this for UQL/AQL/federated non-pgwire flows. For
plain SQL, prefer pgwire; for token-authenticated SQL over gRPC, use
`proximadb.v2.ProximaRecordService.ExecuteQuery`.

[source,bash]
----
curl -X POST http://localhost:5678/api/v2/query \
  -H "Content-Type: application/json" \
  -d '{"query": "SELECT * FROM VECTOR_SEARCH('products', '[0.1, 0.2, 0.3]', 10)"}'
----

==== SQL Extensions

[WARNING]
====
This is the legacy federated path (TD-FEDPATH-1). Only `VECTOR_SEARCH` and `DOCUMENT_QUERY` (with
an existing document collection) are known to work, and `VECTOR_SEARCH` repeats a collection's first
result on every later call (TD-FEDVEC-1). The cross-model examples below are not verified
(TD-SDKDOC-1). For pgvector `<->`, use pgwire (see the PostgreSQL reference).
====

|===
| Extension | Syntax | Example

| Vector Search | `VECTOR_SEARCH(collection, vector, top_k)` | `SELECT * FROM VECTOR_SEARCH('products', '[0.1,0.2]', 10)`
| Graph Query | `GRAPH_QUERY('cypher')` | `SELECT * FROM GRAPH_QUERY('MATCH (a)-[:KNOWS]->(b) RETURN b.name')`
| Document Query | `DOCUMENT_QUERY(collection, filter)` | `SELECT * FROM DOCUMENT_QUERY('orders', 'status = "pending"')`
| Log Query | `LOGS(namespace)` | `SELECT * FROM LOGS('production') WHERE timestamp > now() - interval '1h'`
| Metric Query | `METRICS(namespace)` | `SELECT * FROM METRICS('cpu') WHERE value > 90`
|===

==== Cross-Model Join Examples

**Vector + Document: Find similar products and their reviews**
[source,sql]
----
SELECT v.product_id, v.score, d.review_text
FROM VECTOR_SEARCH('products', '[0.1,0.2,0.3]', 10) v
JOIN LATERAL DOCUMENT_QUERY('reviews', 'product_id = "' || v.product_id || '"') d ON true;
----

**Vector + Graph: Filter by category relationships**
[source,sql]
----
SELECT * FROM VECTOR_SEARCH('products', '[0.1,0.2]', 100)
WHERE id IN (
  SELECT target FROM GRAPH_QUERY('MATCH (:Category {name:"Electronics"})-[:CONTAINS]->(p) RETURN p.id')
);
----

**Logs + Graph: Errors with service dependency context**
[source,sql]
----
SELECT l.timestamp, l.message, g.dependency
FROM LOGS('errors') l
JOIN LATERAL GRAPH_QUERY('MATCH (s:Service {name: "' || l.service || '"})-[:DEPENDS_ON]->(d) RETURN d.name as dependency') g ON true
WHERE l.timestamp > now() - interval '5m';
----

=== Deprecated REST v1 Unified Routes

`/api/v1/unified/federated`, `/api/v1/unified/execute`,
`/api/v1/unified/multi-model`, and `/api/v1/unified/explain` are deprecated
compatibility facades. New work should target `/api/v2/query`, pgwire,
`ProximaRecordService.ExecuteQuery`, or a dedicated v2 modality/fusion endpoint.

The old `multi-model` route accepted explicit components like:

[source,bash]
----
curl -X POST http://localhost:5678/api/v1/unified/multi-model \
  -H "Content-Type: application/json" \
  -d '{
    "query": "SELECT * FROM products WHERE $.category = 'electronics' AND VECTOR_SIMILAR(embedding, ?, 0.8)",
    "query_vector": [0.1, 0.2, 0.3],
    "fusion_strategy": "intersection",
    "limit": 100
  }'
----

==== Fusion Strategies

|===
| Strategy | Description

| `intersection` | Records must match all sub-queries (AND)
| `union` | Records from any sub-query (OR)
| `rrf` | Reciprocal Rank Fusion - weighted rank combination
| `ranked` | Custom weights per model
|===

=== POST /api/v2/query/explain

**Explain query execution plan.** Shows how a query will be decomposed and executed.

[source,bash]
----
curl -X POST http://localhost:5678/api/v2/query/explain \
  -H "Content-Type: application/json" \
  -d '{"query": "SELECT * FROM VECTOR_SEARCH('products', '[0.1,0.2]', 10) v JOIN GRAPH_QUERY('...') g ON v.id = g.id"}'
----

Response:
[source,json]
----
{
  "components": [
    {"model": "Vector", "estimated_cost": 1.0, "parallelizable": true},
    {"model": "Graph", "estimated_cost": 3.0, "parallelizable": true}
  ],
  "fusion_strategy": "Intersection",
  "estimated_total_cost": 3.0
}
----
