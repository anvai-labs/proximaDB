== Overview

ProximaDB features 6 specialized storage engines with intelligent workload optimization. **Important**: Despite historical terminology, SST, SWIFT, and HELIX are **NOT row-based** - they use **ProximaBlocks**, a hybrid columnar format where all metadata is columnar and vectors use configurable encoding strategies.

ProximaDB's intelligent storage engines automatically optimize for your specific workload, eliminating the guesswork in database performance tuning. Instead of forcing you to choose a storage format, our system analyzes your application patterns and automatically selects the best approach.

**Business Benefits:**
- **Zero Configuration**: No manual tuning or complex setup required
- **Automatic Optimization**: System adapts as your application evolves
- **Cost Efficiency**: Intelligent compression reduces storage costs by 4-32x
- **Predictable Performance**: Consistent response times regardless of data size
- **Future-Proof**: Add new workloads without redesigning your architecture

== ProximaBlocks: Hybrid Architecture Foundation

=== Overview

ProximaBlocks represent a revolutionary hybrid storage architecture that combines the benefits of row-group organization with columnar efficiency within each block. This design enables SIMD-optimized operations while maintaining transactional consistency and write performance.

=== ProximaBlock Structure

**Core Components**:
```rust
pub struct ProximaDataBlock {
    /// Row group organization
    row_groups: Vec<RowGroup>,
    /// Columnar data within each row group
    columnar_data: HashMap<String, ColumnChunk>,
    /// SIMD-optimized vector layout
    vector_layout: VectorEncodingLayout,
    /// Unified compression configuration
    compression_config: BlockCompressionConfig,
    /// Block-level metadata
    block_metadata: BlockMetadata,
}

pub struct RowGroup {
    /// Row group ID
    id: u16,
    /// Number of vectors in this group
    vector_count: u32,
    /// Columnar data for this row group
    columnar_data: ColumnarBlock,
    /// Row group statistics
    statistics: RowGroupStatistics,
}

pub struct ColumnarBlock {
    /// Vector data stored column-wise within the row group
    vector_columns: TransposedVectors,
    /// Metadata columns
    metadata_columns: MetadataColumns,
    /// Quantized vector representations
    quantized_data: Option<QuantizedColumnarData>,
    /// Compression information
    compression_info: CompressionInfo,
}
```

=== Hybrid Storage Benefits

**Row Group Organization**:
- Maintains data locality for transactional operations
- Enables efficient batch processing within groups
- Supports ACID properties at row group level

**Columnar Storage Within Blocks**:
- SIMD-optimized vector operations
- Efficient compression and encoding
- Optimal cache utilization for analytical queries

**Matrix Operations Support**:
- P² + K² + P×K matrix layouts for RAPTOR engine
- Hilbert curve clustering for HELIX engine
- Progressive quantization levels for NOVA engine

```rust
        &self,

    ) -> Result<Vec<OptimizedSearchRecord>> {
        let strategy = self.select_search_strategy(ctx).await?;

    }
```

**Strategy Selection Logic**:

- **Filtered queries**: Direct strategy leveraging bloom filter pipeline
- **Simple queries**: Direct strategy for optimal performance

=== Three-Stage Filtering Pipeline

**Location**: `src/storage/engines/impls/sst/search/three_stage_filter.rs`

The SST engine implements a sophisticated three-stage filtering system:

**Stage 1: Bloom Filter Pre-filtering**
- Rapid existence checks using space-efficient bloom filters
- Eliminates 80-95% of irrelevant data before expensive operations
- Configurable false positive rates (typically 1-5%)

**Stage 2: Metadata Filtering**
- Zone map-based range filtering
- Dictionary encoding for categorical data
- Statistical pruning using min/max values

**Stage 3: Vector Filtering**
- Quantized vector comparisons
- Progressive refinement from coarse to fine-grained
- Hardware-accelerated distance computations

```rust
pub struct ThreeStageFilter {
    bloom_filters: Vec<BloomFilter>,
    metadata_filters: Vec<MetadataFilter>,
    vector_filters: Vec<VectorFilter>,
}

impl ThreeStageFilter {
    pub async fn apply_filter(
        &self,
        candidates: Vec<VectorRecord>,
        context: &FilterContext,
    ) -> Result<Vec<VectorRecord>> {
        let stage1 = self.apply_bloom_filter(candidates, context).await?;
        let stage2 = self.apply_metadata_filter(stage1, context).await?;
        let stage3 = self.apply_vector_filter(stage2, context).await?;
        Ok(stage3)
    }
}
```

```rust
pub struct FastLanesEncoder {
    bit_packing: BitPackingEngine,
    delta_encoding: DeltaEncoder,
    rle_compression: RLEEncoder,
    dictionary: DictionaryEncoder,
}

impl FastLanesEncoder {
    pub fn encode_record(&self, record: &VectorRecord) -> Result<EncodedRecord> {
        let metadata = self.dictionary.encode_metadata(&record.metadata)?;
        let vector = self.bit_packing.encode_vector(&record.vector)?;
        let deltas = self.delta_encoding.encode_timestamps(&record.timestamps)?;

        Ok(EncodedRecord {
            metadata,
            vector,
            deltas,
            compression_ratio: self.calculate_compression_ratio(),
        })
    }
}
```

=== Architecture Overview

**Location**: `src/storage/engines/impls/raptor/`

The RAPTOR engine implements the revolutionary Matrix Trinity architecture, replacing traditional graph-based navigation (HNSW) with a mathematically optimal P² + K² + P×K matrix system for ultra-efficient vector search and clustering.

=== Matrix Trinity Formula: P² + K² + P×K

**Mathematical Foundation**:
- **P²**: Intra-rowgroup distance matrices (P×P per rowgroup)
- **K²**: Inter-centroid distance matrix (K×K globally)
- **P×K**: Vector-to-centroid distance matrices (P×K per rowgroup)

**Matrix Components**:
```rust
/// Complete Matrix Trinity implementation
pub struct RowGroup {
    /// Row group metadata
    pub id: u16,
    pub vector_count: u32,
    pub centroid_id: u16,

    /// Columnar data storage
    pub columnar_data: Option<ColumnarBlock>,

    /// Matrix Trinity storage
    pub p2_matrix: Option<P2Matrix>,           // Intra-rowgroup distances
    pub pxk_matrix: Option<VectorCentroidMatrix>, // Vector-to-centroid distances
}

/// P² Matrix: Intra-rowgroup navigation (replaces local HNSW)
pub struct P2Matrix {
    /// Upper triangle distance matrix (n×(n-1)/2)
    distances: Vec<f32>,
    /// Vector count in this rowgroup
    vector_count: usize,
    /// Quantization parameters
    quantization: QuantizationParams,
}

/// K² Matrix: Inter-centroid navigation (centralized storage)
pub struct K2Matrix {
    /// Upper triangle centroid distance matrix
    centroid_distances: Vec<f32>,
    /// Number of centroids
    centroid_count: usize,
    /// Compression parameters
    compression: CompressionConfig,
}

/// P×K Matrix: Vector-to-centroid boosting
pub struct VectorCentroidMatrix {
    /// Vector-to-centroid distances (p×k matrix)
    distances: Vec<Vec<f32>>,
    /// Rowgroup size (P)
    rowgroup_size: usize,
    /// Number of centroids (K)
    centroid_count: usize,
}
```

=== Matrix Trinity Search Algorithm

**Three-Stage Search Process**:
1. **K² Navigation**: Use inter-centroid matrix to select closest centroids
2. **P×K Filtering**: Use vector-to-centroid matrices to rank rowgroups
3. **P² Exact Search**: Use intra-rowgroup matrices for exact nearest neighbors

**Smart Row Group Sizing**:
```rust
pub struct SmartRowGroupSizer {
    /// Current optimal size based on Matrix Trinity parameters
    optimal_size: OptimalRowGroupSize,
    /// Hardware cache constraints
    cache_constraints: CacheConstraints,
    /// Workload-based optimization
    workload_optimizer: WorkloadOptimizer,
}

impl SmartRowGroupSizer {
    pub fn calculate_optimal_rowgroup_size(&self) -> Result<OptimalRowGroupSize> {
        // Matrix Trinity optimal parameters: P² + K² + P×K
        let k = self.calculate_optimal_k()?;  // Number of centroids
        let p = self.calculate_optimal_p(k)?; // Rowgroup size

        let rationale = format!(
            "Matrix Trinity: P={}, K={}, optimized for cache efficiency and matrix operations",
            p, k
        );

        Ok(OptimalRowGroupSize {
            size: p,
            centroid_count: k,
            rationale,
            matrix_memory_mb: self.estimate_matrix_memory(p, k),
        })
    }

    fn calculate_optimal_k(&self) -> Result<usize> {
        // k = sqrt(n) for optimal complexity in Matrix Trinity
        let total_vectors = self.estimate_total_vectors();
        let k = (total_vectors as f64).sqrt().max(1.0) as usize;
        Ok(k.clamp(1, 1024)) // Reasonable bounds for K² matrix
    }

    fn calculate_optimal_p(&self, k: usize) -> Result<usize> {
        // P optimized for L3 cache efficiency
        let l3_cache_mb = self.cache_constraints.l3_cache_mb;
        let vector_dimension = self.cache_constraints.vector_dimension;

        // Target: 10-20% of L3 cache for P² matrix
        let target_cache_mb = l3_cache_mb * 0.15;
        let bytes_per_distance = 4; // f32

        // P² matrix size: P×(P-1)/2 distances
        let max_p = ((2.0 * target_cache_mb * 1024.0 * 1024.0 / bytes_per_distance as f64).sqrt()) as usize;

        Ok(max_p.clamp(1000, 100_000))
    }
}
```

=== Matrix Storage Optimization

**Four-Stage Compression Pipeline**:
1. **Upper Triangle Storage**: Store only upper triangle of symmetric matrices
2. **Quantization**: Compress distances using INT8 or INT16 quantization
3. **Delta Encoding**: Apply delta encoding for sequential distance values
4. **Block Compression**: Final ZSTD compression on quantized data

```rust
pub struct EngineSelector {

impl EngineSelector {
    pub async fn select_optimal_engine(
        &self,
        collection_config: &CollectionConfig,
        workload_hints: &WorkloadHints,
    ) -> Result<EngineType> {
        let workload_pattern = self.workload_analyzer.analyze(workload_hints).await?;

        match workload_pattern {
            WorkloadPattern::RealTimeQueries => Ok(EngineType::Swift),   // Hierarchical ProximaBlocks
            WorkloadPattern::WriteHeavy => Ok(EngineType::Sst),          // Modular ProximaBlocks
            WorkloadPattern::DynamicWorkload => Ok(EngineType::Raptor),  // Matrix Trinity Architecture
            WorkloadPattern::AnalyticalQueries => Ok(EngineType::Viper), // Pure Columnar
            WorkloadPattern::ProgressiveSearch => Ok(EngineType::Nova),  // Progressive Columnar
            WorkloadPattern::SpatialQueries => Ok(EngineType::Helix),   // Hilbert Columnar
        }
    }
}
```

== Best Practices

=== Engine Selection Guidelines

1. **Choose SST for**:
   - Real-time applications requiring immediate write visibility
   - Workloads with frequent updates and deletes
   - Applications requiring strong consistency guarantees

2. **Choose SWIFT for**:
   - Ultra-low latency requirements (<1ms)
   - High-frequency trading applications
   - Real-time recommendation systems

3. **Choose RAPTOR for**:
   - Dynamic workloads with changing patterns
   - Applications with unpredictable query patterns
   - Multi-tenant environments with diverse requirements
