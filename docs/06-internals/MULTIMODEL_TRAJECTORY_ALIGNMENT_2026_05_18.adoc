== Directional Rule

Every modality service is a facade over the canonical stack:

[source,text]
----
Protocol/API facade
  -> modality/query service
  -> shared logical algebra and xCatalog validation
  -> ProximaRecord / ProximaType / ProximaValue
  -> WAL/log/manifest
  -> storage layouts and rebuildable projections
----

No new vector, document, graph, or observability feature may introduce an independent durable
record envelope, hidden catalog, separate WAL, or protocol-owned type system.

== Immediate Corrections

=== Vector

Current state:

* Root `VectorOperationsService` is still the real production path.
* Extracted `proximadb-vector` must stay dependency-light and must not fabricate search results.
* AXIS has a predicate-aware HNSW primitive, but metadata lookup and result materialization are
  still incomplete at the manager layer.
* Hybrid search has several fusion implementations, including an existing projection-style engine
  under root search code, but projection-aware fusion is not yet a shared cross-model query runtime
  default.

Required trajectory:

* Keep `VectorQueryService` returning canonical `ProximaRecord`.
* Expose AXIS/search behind a narrow root-independent trait before moving production search into
  `crates/modalities/proximadb-vector`.
* Retire `VectorRecord` as an SDK, embedded, server, WAL, and storage target. During migration it
  may exist only as a quarantined import adapter for old generated v1 clients; no new server,
  SDK, embedded, WAL, storage, query, or projection code should accept it as the durable or
  internal contract.
* Do not maintain parallel v1 and v2 write APIs as product surfaces. The working strategy is:
  build the record-native v2 implementation as the sole target, route old v1 names through that
  implementation only while migration is active, then remove the old vector-shaped v1 surface and
  rename/promote the record-native API as the stable v1 surface at finalization.
* Python SDK and embedded mode now follow this trajectory natively: `insert_records` /
  `upsert_records` are typed around `ProximaRecord` or record-shaped dictionaries. SDK adapters
  remain only transport adapters, while vector-named methods are compatibility aliases over the
  record boundary rather than independent writers.
* Python embedded exposes explicit `ProximaRecord` / `ProximaValue` public types plus
  `insert_proxima_records` / `upsert_proxima_records`; legacy metadata maps lower immediately into
  canonical `props`.
* Python sync gRPC uses generated v2 `ProximaRecordService` stubs for record writes; v1 vector
  gRPC remains only for vector-named compatibility methods and read/search migration surfaces.
* Python embedded HTTP writes use the v2 record batch endpoint; vector-named embedded helpers
  delegate to record writes and are not maintained as a separate API surface.
* Python batching exposes `batch_insert_records` as the native helper; vector-named batching
  delegates to it for migration compatibility.
* Python insert builders build record-shaped dictionaries natively; vector-named builder helpers
  are retained only as compatibility conveniences.
* Python chunking pipelines expose record-native helpers (`create_records`, `prepare_records`,
  `chunk_and_embed_records`); vector-named helpers wrap those outputs for compatibility.
* Python optional integrations, including LangChain/LlamaIndex/Haystack/CrewAI/AutoGen/Agentic IO,
  Victor, dual-use embeddings, and agentic vector memory, build record-shaped payloads and prefer
  `insert_records`; vector insert calls are compatibility fallbacks for older clients only.
* Python embedded multi-model code indexing writes vector-bearing chunks through record-shaped
  payloads and `insert_records`.
* Python legacy unified client insert/upsert, CLI, and code-knowledge ingestion helpers now prefer
  record-native write methods; vector-named CLI commands remain compatibility entry points over
  record payloads.
* Python `client_v1` remains a compatibility facade, but its insert path now writes through the
  record batch API rather than REST `/api/v1/vectors/batch`.
* Rust SDK and Node embedded write builders now target the record batch API and expose
  `ProximaRecord` as the canonical record shape, with `VectorRecord` retained only as a
  compatibility alias.
* Go REST adapter writes now target the record batch API and expose `ProximaRecord` for new code,
  while `VectorRecord` remains accepted as compatibility input.
* Replace `VectorRecord` internals one engine and one protocol surface at a time, starting with
  paths that already have benchmark/test coverage.
* Add context-disentangled chunk representations as rebuildable vector projections: centroid
  embedding plus residual/topic embeddings, with xCatalog metadata for model, freshness, and
  repair source.
* Promote projection-aware fusion only after it is implemented in the shared query runtime and
  benchmarked against RRF/weighted fusion for latency, recall, and diversity.

Touchpoints:

* `src/services/operations/vectors/legacy.rs`
* `crates/modalities/proximadb-vector/src/service.rs`
* `src/index/axis/management/filtered_search.rs`
* `src/index/axis/indexes/hnsw_index.rs`
* `src/storage/engines/{sst,swift,viper,nova,raptor}/`
* `src/core/search/hybrid/fusion.rs`
* `crates/query/proximadb-query-fusion/src/lib.rs`
* `crates/modalities/proximadb-vector/src/transform_index.rs`

Done criteria:

* v1 protocol conversion happens only at REST/gRPC/SDK edges.
* SDKs and embedded libraries expose `ProximaRecord`/`ProximaValue`-style records as the primary
  shape; vector-only helpers are deprecated wrappers over the record normalizer.
* There is one maintained write contract: xCatalog-validated `ProximaRecord`/`ProximaValue`.
  `/api/v1/vectors/*` and v1 generated clients are temporary aliases during migration, not
  independent API products.
* `search_vectors_unified` consumes rich predicates with tenant/RLS pushdown.
* Filtered ANN returns materialized records, not placeholder candidate counts.
* Projection fusion has shared-runtime execution, explain output, and benchmark evidence before it
  is exposed as a default.
* Centroid/residual embeddings are cataloged projections, not a second document/vector truth store.
* Transform projections carry repair source, freshness lag, projection epoch, and source record
  version before they can be registered or refreshed.

=== Document

Current state:

* `proximadb-document` defines canonical document mapping.
* `DocumentService` can use a canonical record store behind `canonical-document-store`.
* CEDAR is correctly described as a projection/access method.

Required trajectory:

* Make canonical record storage the default server wiring for document CRUD.
* Keep JSON path, full-text, and shape variation indexes rebuildable.
* Move legacy `SqlObject` to compatibility adapters only.

Touchpoints:

* `crates/modalities/proximadb-document/src/record.rs`
* `src/storage/document/service.rs`
* `src/storage/document/indexes/`
* `src/storage/engines/cedar/mod.rs`
* `src/network/rest/v1/document.rs`
* `src/network/grpc/document_service.rs`

Done criteria:

* Insert/update/delete paths write canonical `ProximaRecord` before projection maintenance.
* xCatalog owns schema mode and variation metadata.
* Recovery replays canonical record operations, then rebuilds projections.

=== Graph

Current state:

* Graph node/edge canonical mapping exists.
* `GraphOperationsService` can mirror writes into `RecordStore`.
* Adjacency projections and ORION CSR freshness epochs exist.
* ORION carries a compatibility WAL/recovery path for rebuildable graph projections.

Required trajectory:

* Make canonical record store mandatory in production graph service wiring.
* Treat ORION as a topology/query projection unless an ADR promotes specific retained aggregates.
* Route Cypher/PGQ pattern matching through shared logical operators and projection-aware
  planning.
* Expose bounded graph traversal as an agent tool contract (`GraphWalkTool`) so agents navigate
  graph neighborhoods iteratively instead of receiving large prompt-sized subgraphs.

Touchpoints:

* `crates/modalities/proximadb-graph/src/record.rs`
* `src/graph/service.rs`
* `src/graph/service_edge_ops.rs`
* `src/graph/adjacency_projection.rs`
* `crates/modalities/proximadb-orion-engine/src/`
* `src/query/graph_lowering.rs`
* `crates/modalities/proximadb-graph/src/graphwalk.rs`

Done criteria:

* Graph CRUD writes are canonical by default.
* Endpoint-bound queries prefer fresh CSR/projection and can rebuild from canonical edge records.
* Legacy graph WAL does not define durable graph truth.
* GraphWalk responses include canonical records plus projection freshness metadata and always carry
  tenant/RLS context.

=== Observability

Current state:

* Root observability service has ingestion/query, partitioned storage, Tantivy log search, trace
  storage, and CHRONO.
* CHRONO is an `ObservabilityStorageEngine`, now wired when configured.
* `proximadb-observability` now defines canonical `ProximaRecord` mapping for logs, metric samples,
  and trace spans.
* Partitioned log storage, metric storage, and trace storage expose namespace-aware canonical
  projection helpers for replay into shared record/PAX storage.
* Root storage still writes legacy log/metric/span shapes before those records are replayed through
  shared canonical record storage.

Required trajectory:

* Extend canonical observability record mapping to alerts, profiles, exemplars, and retained rollups.
* Wire log, metric, and span writes into the shared record store/WAL path before projection
  maintenance.
* Keep time partitions, rollups, Tantivy indexes, trace assembly, and service graphs as
  projections over canonical records or retained aggregate records.
* Preserve compatibility with OTLP/PromQL/LogQL style inputs as adapters.

Touchpoints:

* `src/observability/mod.rs`
* `src/observability/storage/`
* `src/observability/query/`
* `src/storage/engines/chrono/mod.rs`
* `crates/modalities/proximadb-observability/src/lib.rs`
* `src/observability/graph_linking.rs`

Done criteria:

* CHRONO ingest/query is exercised by service-level tests.
* Observability records can be replayed from WAL into canonical record storage.
* Correlation queries can traverse log/span/service dependency records without a separate truth
  store.

== Cross-Cutting Workstreams

=== Storage Spine

Use `ProximaRecord` plus ADR-010 PAX segments as the forward internal contract. Existing
`VectorRecord` storage internals are migration debt, not target design.

Required work:

* Select one storage engine for first full `ProximaRecord` conversion.
* Add conversion parity tests before replacing internals.
* Quarantine existing v1 protocol compatibility in edge adapters with explicit retirement tasks;
  do not add new behavior or tests that make v1/vector-shaped payloads a maintained target.
* Keep PAX blocks/segments as ADR-010 Layer 2 rebuildable projections over canonical records.
  OLTP row directories, OLAP stripes, Iceberg/Arrow/OpenTable facades, and catalog manifests must
  derive from xCatalog + WAL/record authority rather than defining separate durability.

=== Query Plane

Shared logical operators must become the convergence point for:

* `VectorTopK`
* `Filter`
* `Project`
* `PatternMatch`
* `HybridTraverse`
* `CrossModelJoin`
* `SemanticJoin`
* `LogTimeFilter`
* `MetricAggregate`

Every operator must carry tenant/RLS predicates and xCatalog table/collection identity.

Research-backed additions must land as shared query/runtime contracts:

* AV-SQL style agentic view decomposition becomes a logical-plan rewrite that emits named,
  inspectable subviews over vector/document/graph/observability sources.
* Evolutionary planning is an optimizer mode that samples physical alternatives against catalog
  statistics and bounded execution probes; it is not a language-specific execution path.
* Projection fusion is a `FusionStrategy` contract first, then a runtime implementation with
  benchmarks and explain output.
* GraphWalk is a graph operator/tool surface over canonical edge/node records and fresh topology
  projections.
* Agentic views are either ephemeral logical views or xCatalog-managed rebuildable projections.
  Materialized agentic views must declare projection name, repair source, and freshness contract;
  they cannot define durable authority.
* All SQL/UQL/AQL/AV-SQL lowering must call shared `MultiModelQuery::validate()` or
  `AgenticViewPlan::validate()` before execution, optimization, or materialization. Invalid
  component dependencies, empty targets, malformed semantic joins, zero limits, and invalid fusion
  parameters must fail at the shared IR boundary rather than in protocol handlers.

=== xCatalog

xCatalog must own:

* schema mode;
* variation id;
* index/projection descriptors;
* storage authority mode;
* freshness and rebuild semantics;
* external table authority boundaries;
* type mapping and lossy conversion flags.

=== Product Surface

Supported-surface documents must distinguish:

* production-ready path;
* beta path;
* experimental path;
* architectural target only.

No release note, README, or API doc should imply production parity with Milvus, Neo4j, MongoDB,
Splunk, Datadog, Loki, Elastic, or Tempo until the corresponding benchmark and recovery tests
exist.

== Best-in-Class Alignment

ProximaDB should not chase four isolated databases. It should match the critical primitives that
make each class credible, then expose combinations that single-model systems do not make cheap.

[cols="1,2,2,2",options="header"]
|===
|Class
|Best systems to respect
|Must-have parity work
|ProximaDB wedge

|Vector
|Milvus, Weaviate, Pinecone, Vespa
|Predicate-aware ANN, hybrid BM25+dense+sparse retrieval, reranking, filtered recall benchmarks,
tenant/RLS pushdown
|Canonical records plus graph/document/time predicates in one query plan

|Graph
|Neo4j, TigerGraph, Neptune, JanusGraph
|Pattern matching, bounded/deep traversal performance, fresh topology projections, explainable
projection choice, recovery from canonical edges
|Semantic traversal over graph neighborhoods with vector and telemetry context

|Document
|MongoDB, CouchDB
|Flexible schema evolution, JSON path indexing, full-text, secondary indexes, schema variation
cataloging, update semantics
|Documents participate in relational constraints, vector retrieval, and graph projections without
a separate durable document store

|Observability
|Splunk, Datadog, Loki, Elastic, Tempo
|High-throughput log/metric/span ingest, time partition pruning, text search, trace assembly,
retention/rollups, correlation queries
|Native semantic incident search across logs, traces, service graph, deployments, and runbooks
|===

== Positioning

ProximaDB is the primary context store for agentic systems: one canonical record, catalog, policy,
and projection plane for semantic vectors, documents, graph topology, and telemetry. Its durable
moat is not a faster clone of any one category; it is cross-model retrieval where agents can ask
for meaning, relationships, time, provenance, and operational state in a single governed query.

== Phase Roadmap

=== Phase 0: Stop Drift

* Remove fabricated/mock behavior from query-facing services.
* Wire configured engines into service paths.
* Add canonical-authority checks in service constructors.
* Update supported-surface claims.

=== Phase 1: Canonical Default

* Make document and graph canonical record stores default in server composition.
* Add canonical observability mapping.
* Complete AXIS filtered-search materialization.
* Add engine-level tenant/RLS predicates to vector and graph projection scans.

=== Phase 2: Engine Conversion

* Convert one storage engine to native `ProximaRecord` internals.
* Move PAX segment writer/scanner into an actual engine flush/read path.
* Rebuild indexes/projections from canonical records in recovery tests.

=== Phase 3: Best-in-Class Proof

* Publish repeatable benchmark suites against vector, graph, document, and observability systems.
* Add explain plans for cross-model queries.
* Validate distributed ownership, freshness, and rebuild semantics.
* Treat semantic + graph + telemetry as the product wedge, not four separate databases.
