== Problem & Goals

ProximaDB needs a quantizer that is (a) training-free so streaming ingest is not gated on a separate train phase, (b) **competitive on recall at low bit-widths** so 16× compression is viable for hot ANN paths, and (c) **kernel-aware of allowlist filters** so selective filters do not collapse recall through oversample-post-filter. The existing PQ/SQ stack misses on all three.

This HLD specifies the architecture for adding **TurboQuant + TQ+ + length-renormalization + in-kernel allowlist** as a new variant inside the existing `UnifiedQuantizationEngine`, gated behind `experimental-turboquant`.

=== Non-goals

* **Not** a replacement for HNSW/IVF coarse partitioning. TurboQuant is a leaf scoring layer; AXIS still does coarse filtering and recall control.
* **Not** a change to the canonical `ProximaRecord` shape, WAL format, or open-format catalog contracts (`OPEN_FORMAT_CATALOG_2026_05_17.adoc`).
* **Not** a change to existing `QuantizationLevel` variants (`Binary`, `Uniform`, `Pq`, `Scalar`, `Custom`). TurboQuant is additive.
* **Not** a port of turbovec's MIT code. ADR-021 commits to clean-room reimplementation from the published papers.

== Algorithm Overview

TurboQuant exploits a single fact: a unit vector on the (d-1)-sphere, after multiplication by a random orthogonal matrix, has coordinates that *independently* follow a known distribution — Beta((d-1)/2, (d-1)/2) shifted to [-1, 1], converging to Gaussian N(0, 1/d) in high dimensions. Once the distribution is known, the optimal scalar quantizer can be computed **once from the math**, with no training, no codebook drift, no need to re-fit as the corpus grows.

The full encode pipeline:

[cols="1,4,3", options="header"]
|===
| Step | What | Why

| 1. Normalize
| Strip `||v||`; store as a single f32.
| Decouples direction from magnitude. Quantizer operates on the direction; magnitude is restored at scoring.

| 2. Random rotation
| Multiply by a seeded orthogonal matrix R. Same R for the entire collection.
| After rotation, each coordinate independently follows the canonical Beta marginal regardless of input data anisotropy.

| 3. TQ+ calibration
| Per-coordinate (shift, scale) fit from empirical 5/95% quantiles of the first batch (≥1000 vectors). Frozen.
| Beta marginal is asymptotic. At finite d, real coordinates drift. TQ+ maps empirical quantiles onto the canonical Beta's quantiles so the codebook fits the data.

| 4. Lloyd-Max codebook
| Compute boundaries and centroids from the canonical Beta CDF + PDF. No data involved.
| Optimal MSE quantizer for the *theoretical* marginal. One-time computation per (bit_width, dim) pair.

| 5. Bit-pack
| 2/3/4 bits per coord packed into bytes.
| 16× compression at 2-bit for d=1536 (6144 bytes → 384 bytes).

| 6. Length renormalization
| Compute `scale_i = ||v_i|| / <u_rot,i, x_hat,i>` (one extra dot product at encode). Store per vector.
| Lloyd-Max's reconstruction shrinks the unit vector; multiplying by `scale_i` at scoring removes the downward bias on the inner-product estimator. Recall gain is largest at 2-bit.
|===

Search reverses steps 1–2 (rotate the query once per request, apply the inverse TQ+ calibration), then scores via a SIMD lookup table indexed by the quantized codes. The query LUT bakes in `scale_i` so the inner product `<v, q>` is recovered as `scale_i × Σ centroid_codebook[code] × q_rot`.

[source,mermaid]
----

    V[Input vector v] --> N[Normalize<br/>u = v / ||v||]
    N --> R[Rotate<br/>u_rot = R · u]
    R --> C[Apply TQ+<br/>u_calib = u_rot * scale_tq + shift]
    C --> Q[Lloyd-Max<br/>codes = quantize(u_calib)]

----

The runtime artifacts are: per-collection rotation seed (xCatalog), per-coord (shift, scale_tq) calibration (persisted with codes), per-vector `scale_i` (in `TurboQuantVectorData`), and the bit-packed codes.

== In-Kernel Allowlist

The recall problem in selective ANN is structural: oversample-post-filter inflates `top_k` to compensate for the fraction discarded, but at small selectivity (e.g. 1% match), the oversample factor explodes and recall still collapses because the SIMD kernel spends its time scoring vectors that will be thrown away. The turbovec approach reframes filtering as a **kernel input**:

* The candidate set is supplied as a packed u64 bitmap (`bitmap[i >> 6] & (1 << (i & 63))` selects slot `i`).
* Before scoring any 32-vector block, the kernel checks the relevant 32-bit window of the bitmap; if zero, the entire block is skipped — no LUT lookup, no FMA, no heap update.
* On AVX-512BW the pair-block kernel skips 64 vectors per u64 word that's all-zero.
* A process-global counter `proximadb_turboquant_blocks_skipped_by_mask_total` records skips for observability.

The integration into ProximaDB is via a new `CandidateSet` impl (`CandidateMaskSet`), not a new trait method. AXIS adapters downcast the supplied `CandidateSet` and route to the kernel-mask path when the concrete type matches; otherwise they fall back to the existing oversample-post-filter logic. This preserves the existing trait surface (`src/core/search/filter_contract.rs:199-248`).

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant C as Caller
    participant A as AXIS Adapter
    participant K as TurboQuant Kernel
    participant M as MaskBitmap

    C->>A: search(query, top_k, CandidateMaskSet)
    A->>A: downcast::<CandidateMaskSet>()
    alt downcast succeeds
        A->>K: search_with_mask(query, k, &[u64] bitmap)
        loop for each 32-vec block b
            K->>M: word = bitmap[b >> 1]
            alt word slice == 0
                K-->>K: skip block (counter++)
            else
                K->>K: SIMD score + heap update
            end
        end
        K-->>A: top-k scores + slot ids
        A-->>C: top-k results
    else downcast fails
        A->>A: legacy oversample-post-filter
        A-->>C: top-k results
    end
----

The pair-block early-exit on AVX-512BW is the largest single optimization for selective workloads: at 1% selectivity, ~98% of u64 words are zero, so ~98% of pairs short-circuit and the kernel spends almost no time on excluded vectors.

== Concurrency Model

The runtime layout is built once per `(collection, bit_width)` and cached in `OnceLock`-equivalent state:

* **Rotation matrix R** — deterministic function of `(dim, rotation_seed)`. Cached for the collection's lifetime.
* **Lloyd-Max boundaries + centroids** — deterministic function of `(bit_width, dim)`. Cached.
* **TQ+ calibration (shift, scale_tq)** — fitted on first qualifying batch. Frozen.
* **SIMD-blocked code layout** — derived from the bit-packed codes. Invalidated on `add()` / epoch bump; rebuilt lazily on next `search()`.

Search takes `&self` and runs concurrently from many threads. The first caller pays the one-time blocked-layout materialization; subsequent callers read the cache lock-free. Mutation (`add()` / re-encode) flows through `&mut self` and resets the blocked-layout cache.

This matches turbovec's `OnceLock` pattern but composes with proximaDB's existing `Arc<UnifiedQuantizationEngine>` orchestrator (`src/compute/quantization/quantization_engine.rs:84-100`) — the cache lives inside a per-collection state object owned by the engine.

== Hardware Capability Integration

Per `EMBEDDING_PRECISION_LLD_2026_05_22.adoc` Q14, ProximaDB has a startup micro-bench and cached `HardwareCapabilities` registry. TurboQuant integrates as follows:

* **NEON (aarch64)** — always available on macOS arm64; primary kernel.
* **AVX-512BW + AVX-512F (x86_64)** — runtime-detected via `is_x86_feature_detected!`. Preferred when available; pair-block kernel.
* **AVX2 + FMA (x86_64)** — fallback on Sapphire Rapids predecessors and below.
* **Scalar fallback** — always available. Required for ARM CPUs without NEON (none in practice) and x86_64 CPUs without AVX2 (rare; needed for correctness in VMs without exposed CPU features).

Kernel selection is recorded in `RoutedExecutionPlan` per ADR-004 and ADR-021 via the `kernel_arch` hint field (`"neon" | "avx2" | "avx512bw" | "scalar"`).

== Numerical Equivalence Across Architectures

The kernels MUST produce bit-identical scores across NEON and AVX2/AVX-512BW for any given (rotation seed, calibration, codes, query) tuple. The technique (lifted from FAISS FastScan and adapted in turbovec) is **periodic flush every 256 byte-groups (FLUSH_EVERY = 256)**: the integer accumulator overflows are bounded so a single shared `max_lut = 127` keeps both arches identical. This avoids the historical ARM-vs-x86 recall gap where higher-dim queries silently quantized to different LUT precision.

Bit-identical scoring is a testable property and the LLD specifies the test (encode on macOS arm64, search on Linux x86_64, assert `scores == scores`).

== Route Cataloging (ADR-021 + ADR-004)

Every search that selects TurboQuant must produce a `RoutedExecutionPlan` that records:

[cols="1,3", options="header"]
|===
| Field | Source

| `authority_mode` | Constant `projection` per ADR-021.
| `compute_route` | `simd_brute_force_with_mask`.
| `storage_specialization` | `turboquant_{2,3,4}bit` per the chosen `bit_width`.
| `kernel_arch` | Runtime SIMD dispatch result.
| `mask_pushed_to_kernel` | `true` iff the `CandidateSet` downcast to `CandidateMaskSet`.
| `calibration_mode` | `"identity"` or `"tq_plus"` per the stored calibration state.
| `blocks_skipped_by_mask` | Per-search counter delta.
| `length_renorm_applied` | Always `true` for TurboQuant.
|===

A planner that fails any of the rejected-route reasons in ADR-021 §"Rejected route reasons" produces a `RoutedExecutionPlan` with `valid=false` and a populated `rejected_route` reason, surfacing the decision to EXPLAIN clients.

== Sequencing & Multi-Session Tracking

This work spans multiple implementation sessions. The LLD owns the **Implementation Status table** that each session updates. The status table mirrors the Phase table in ADR-021's "File Plan" and `dreamy-finding-clover.md` plan:

* P1 — Foundation types
* P2 — Encode pipeline (rotation, codebook, bit-pack)
* P3 — TQ+ calibration + length renorm
* P4 — SIMD scoring kernel (NEON / AVX2 / AVX-512BW / scalar)
* P5 — `CandidateMaskSet`
* P6 — AXIS adapter integration
* P7 — RaBitQ length renorm for existing PQ/SQ (independent)
* P8 — xCatalog + EXPLAIN + Prometheus wiring
* P9 — Benchmarks + recall validation

Each phase ships independently behind the feature flag. P5–P7 have no dependency on P2–P4 and can land in parallel. P9 gates the promotion from `experimental` to `beta` tier.
