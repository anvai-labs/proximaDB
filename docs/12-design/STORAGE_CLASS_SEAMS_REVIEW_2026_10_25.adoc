=== V3-first implementation decision (owner amendment, 2026-10-25)

The target is decided: v3, not another v2 feature cycle. The earlier v2 proposal served
external-reader compatibility; it does not justify implementing v2 position deletes now.
Reuse the landed Puffin/DV engine. Sequence:

----
 current v2 tables --legacy reads--> unchanged visibility
          |
          +-- atomic, persisted v3 upgrade (reuse compatible data files)
                         |
 new tables ---------- v3 publication / one authoritative writer
                         |
              delete-aware internal readers
                         |
        pinned external readers: values + deletes + snapshot chain
                         |
              enable incremental DV publication
----

The arrows express readiness dependencies, not permission to emit deletes before readers.
Replace type-based format selection with a stored monotonic version; validate required
row lineage, parent/sequence inheritance, upgrade races and crash recovery. Unsupported
legacy delete encodings fail closed. No new dual-format feature implementation; no forced
whole-data rewrite merely to change the metadata version. Optional variant support is
separate from establishing the v3 publication contract. Update ADR-097 D3 and its callers
in the implementation slice; this review updates the decision but changes no Rust behavior.

The https://iceberg.apache.org/spec/[Iceberg specification] defines v3 DVs and row lineage,
allows existing v2 position deletes after upgrade, and forbids adding new position-delete
files to v3 tables. New DVs must incorporate applicable earlier position deletes.

== 1. Decision summary

. Separate collection policy, durable placement, local residency, provider access tier,
  and physical disk profile. They are independent dimensions with explicit compatibility checks.
. A cache pin is a capacity reservation plus protected coverage of a committed object set.
  Changing an eviction priority does not create a reservation or a guarantee.
. Preserve old behavior when policy is absent. New non-default behavior is opt-in and
  unsupported configurations fail at policy admission, not later inside a data write.
. For v1, admit performance residency only for explicitly supported object-backed SST/PAX
  collections on one serving owner. Do not claim all modalities or fleet-wide warmth.
. Initial quota failure rejects the policy change. Later disk failure or dataset growth
  preserves durable writes and reports degraded coverage. Never report READY after falling back.
. Reuse the persistent byte store, typed path resolution, publication hooks, and metering sink.
  Do not introduce another durable table, manifest authority, cache implementation, or pricing engine.
. Keep TD-PAXDIR-2 separately owned, but make it an explicit dependency of a zero-total-request
  promise. Until then, measure zero payload GETs and remaining control requests separately.
. Choose range size from measured useful-byte density, latency, and tier costs. No global
  40 MiB default and no fixed depth-first ordering independent of the deployment profile.

----
                    CollectionPolicy (desired, versioned)
                    /            |                 \
             durable location  residency intent   access-tier intent
                    |            |                 |
             typed path +     quota + pool       object-kind +
             authorization    reservation        backend capability
                    |            |                 |
                    +------ publication ------ object PUT
                                 |
                       committed object inventory
                                 |
                    cache coverage reconciliation
                      /                       \
             READY(generation)          WARMING / DEGRADED
                      \                       /
                  normal query correctness + remote fallback
                                 |
                physical usage + reservation-time records
                                 |
                  AnvaiOps: prices, commitments, invoices

 Disk-pool profile: gp3 | gp2 | st1 | sc1 | local NVMe
   constrains capacity / IOPS / throughput / queueing, not durable authority.
----

== 2. Premise audit: corrections that prevent wasted implementation

|===

| Named locations already exist
| `StorageLocation` in `proximadb-config/src/lib.rs` has URL, weight, tags and optional io_budget, but no name/id. `StorageConfig::register_io_budgets` is called by `src/database.rs`; the registry already does boundary-aware longest-prefix matching.
| Reuse this registry. Decide whether the smallest API needs an operator-defined location id; do not assume a name field or build a second registry. Admission must authorize selection, not merely recognize a URL scheme.
| Set `StorageAssignment.base_location` from the request

| `cache_on_write=all` makes every warm query local

| Access tiers are almost-free plumbing and GCS support is absent
| Current GCS writes set storage class, and `ProximaObjectStore::put_with_tier` exists; ADR-036's residual notes are stale. Coverage of every atomic/multipart/compaction caller still needs verification.
| Reuse existing mappings; fix ADR-036's premise. Test real production write paths, not just the enum conversion. MinIO is not an access-tier enforcement oracle.
| Footer can stay Hot while its segment is Cool
| PAX header/footer/A/B/D are ranges inside one object. Object-store access tier applies to the object.

| Keep ownership separate, dependency explicit. Do not weaken consistency or hide LIST/HEAD to pass the test.
| Current store is always remotely authoritative
| Local storage locations and a local canonical WAL remain supported; object-store spill is opt-in.

== 4. Refined interfaces and v1 behavior

=== 4.1 Collection policy and placement

Keep one versioned desired policy in the canonical collection config, projected into the
catalog as required by existing conventions. `Collection` reports it through that config;
do not independently mutate both a top-level class and a config class. Proto enum zero is
UNSPECIFIED, resolving to balanced for compatibility. Validate unrecognized numeric values.

Proposed policy concepts (names are interface sketches, not a mandate to add all fields):

* `storage_class`: economy / balanced / performance.
* resolved durable location: existing assignment, chosen through an authorized configured target.
* optional `default_access_tier`: online tiers only in the first supported provider path.
* performance request: reservation bytes and a supported local pool selector; quota is
  operator/tenant policy, not a client-supplied entitlement.
* observed status: state, reason, policy generation, serving owner/pool, committed generation
  covered, reserved bytes, resident bytes, covered bytes, and last transition.

Proposed precise class semantics:

[cols="1,3,3",options="header"]
|===
| Class | Data residency | Promise
| balanced | Preserve current shared caches and their existing defaults | Best effort; no reservation and no new latency guarantee.
| economy | No persistent payload admission or proactive payload warming; bounded common control metadata may still cache | Lower local footprint; object requests remain metered. It does not force a colder object access tier or a different index.
| performance | Explicitly admitted protected disk bytes; demand and post-publication reconciliation of covered objects | Admitted bytes survive ordinary cache pressure while the owner/pool is healthy; readiness reports actual coverage. No reserved CPU or p99 guarantee in v1.
|===

If economy's difference from balanced is not wanted, do not ship two identical promises:
defer economy activation until the product choice is settled. Config-only SC1 can persist
intent behind a gate but must report NOT_ACTIVE, never imply a working reservation.

Changing durable location remains a separate migration. Policy changes are versioned and
idempotent; access-tier changes affect future objects only unless a separate migration is
requested. Old explicit local configurations continue to work with balanced behavior.

=== 4.2 Reservation and coverage lifecycle

----
 request --validate capabilities/quota--> REJECTED (old policy unchanged)
              |
              v
          RESERVED --> WARMING(g) --> READY(g, profile)
              |             |             |
              +-------------+-------------+--> DEGRADED(reason)
                            |                       |
                       reconcile <------------------+
                            |
                  downgrade/drop --> RELEASING --> RELEASED
----

Use one reservation authority for a physical pool. For v1, a process owns the pool exclusively;
acquire an exclusive pool lock and reject a second owner. Persist/reconcile grants through the
existing durable catalog/control path; do not invent a distributed quota service. Tenant quota
scope must be explicit: this v1 is a deployment/owner scope, not independently enforced global
limits on multiple nodes. Fleet rollout requires control-plane grants whose sum obeys the global cap.

Charge physical capacity once per actual reservation replica/pool. Reserve bytes for entry
headers/checksums, temporary warming, and old/new generation overlap. Capacity reservation is
not free disk space observed once. Do not hold a global reservation lock while doing network I/O.
A kill switch releases/bypasses residency safely; it cannot erase policy or remove the remote copy.

Use `PersistentByteStore::put_file_range` / `get_range` for a small whole-immutable-object
prototype. Extend ownership/protection independently of `L2Class`. Verify every read path
consults the same resident object through a thin adapter; retain existing derived DRAM caches.
Avoid storing duplicate A/B parent ranges and a full object without counting both bytes.
Do not build an alternative object cache if the existing store can be adapted.

An object key includes stable tenant/collection incarnation and canonical immutable object
identity/revision. Bind coverage to the published segment set and directory/sidecar revisions.
Use checksums for local integrity; an ETag is an opaque validator, not assumed content hashing.
Derive a residency inventory from the existing committed read set; it is a cache descriptor,
not a second publication manifest or latest-snapshot authority.

READY is conditional on owner health, admitted capacity, generation and query profile.
New publication does not wait for warming and cannot lose acknowledged writes because of it.
Queries keep the normal freshness/ABAC/deletion logic and read remote bytes on a miss.
Expose reduced coverage immediately; preserve already-admitted pins until released or retired.
Strict uninterrupted readiness during arbitrary growth is out of scope unless the product
accepts write backpressure and reserves the necessary transition capacity.

=== 4.3 Usage versus billing

Add a neutral usage schema, not dollar arithmetic in OSS:

* object bytes by physical location, provider class (observed/unknown), object kind and owner;
* reserved bytes, actual disk-resident bytes, and ready-covered bytes as separate levels;
* reservation byte-seconds with interval boundaries and producer/lease epoch + sequence;
* remote operations separated as GET, HEAD, LIST page, PUT, DELETE, retry/error where measurable;
* remote retrieved bytes, local bytes read/written, query CPU time, warming and compaction work.

Keep operation/object-class/media/product-class labels distinct. Avoid per-object metric labels;
collection detail can live in bounded durable records/status while Prometheus aggregates by tenant/pool.
Count background work outside query traces. Never sample or compile out billing-required events.
Record a metric as partial where the SDK hides retry/page detail; do not claim invoice equivalence.

Extend `MeteringWriter` with additive/versioned events and periodic reconciliation, reusing its
typed tenant paths. Durable sequence/interval keys support downstream deduplication. A gauge
alone cannot recover idle accrual across process loss. Report uncertainty after an unobserved
interval instead of fabricating exact usage. Count retained snapshots/orphans until confirmed
physical retirement; do not infer physical release from row deletion. Rate-card treatment of
reserved-but-degraded capacity is an AnvaiOps product decision; record both reservation and
readiness so it can apply credits without guessing.

=== 4.4 Provider access tier

Implement only after the selected backend and production write paths prove support. The
canonical enum maps to provider classes, but service semantics are not identical. Strictly
validate new public policy; leave legacy lenient FileOptions parsing unchanged unless separately
migrated. Reject unsupported explicit requests rather than silently ignoring the user's intent.

Set the final object's tier on atomic and multipart publication and compaction output. A helper
that overwrites with `put_with_tier` must not replace create-only or conditional commit semantics.
Separate manifests/directories/control objects stay explicitly Hot where supported; embedded
headers/footers inherit their data object's tier. Account lifecycle rules can subsequently
change it: distinguish desired, last-written and observed tier, with unknown allowed.
No Archive, automatic lifecycle controller, backend migration, or split-file layout in this work.

== 5. 8 MiB versus 40 MiB, and local disks versus EBS

Eight MiB is a size, not a locality classification. Reads at offsets 0, 8, 16 MiB are sequential;
8 MiB reads at unrelated offsets or in different objects are random between contiguous extents.
An HTTP GET is not an EBS I/O: the filesystem/block layer may split it into many requests.

Keep three knobs separate: remote coalescing cap/gap, local prefetch/read size, and integrity
chunk size. ADR-085's 64 KiB checksum unit addressed local read amplification; increasing the
cloud cap must not enlarge that unit. With 16 concurrent 40 MiB buffers, nominal payload alone
is 640 MiB per active wave, before decode and overlapping requests. Add an in-flight byte budget.

Measure fixed geometry first. Changing the IOPS target may also change `k_G` at compaction;
that would confound a range-cap experiment. Pin the object set/ETags, trained cells, nprobe,
coalescing gap, concurrency, query sequence, return payload, binary and cache policy. Inspect
actual geometry: the local D8 10 ms result JSON contains 27 coarse cells, while the narrative
summarizes about 34. Record the JSON geometry, not the summary as an invariant.

Sweep 4/8/16/32/40/64 MiB in stages: first 4/16/40, then refine around the Pareto frontier.
For each arm record useful and fetched bytes, overread gap bytes, actual request-size distribution,
GET/HEAD/LIST, waves, p50/p95/p99, CPU, peak RSS, in-flight bytes, throughput and recall.
A larger cap may make no difference if selected extents remain disjoint; never pad reads to it.
Keep SIFT1M recall >= 0.98 and compare the same query identities. Extend finalists to fragmented
segments, filters, 10M rows and 768d before any global default change. Unknowns stay unknown.

Proposed disk profiles:

[cols="1,2,3",options="header"]
|===
| Medium | Use in this design | Qualification
| gp3 | Default EBS candidate for shared/reserved query residency | Baseline 3,000 IOPS and 125 MiB/s; provision throughput/IOPS independently and include the EC2 instance cap. Capacity alone does not guarantee query throughput.
| gp2 | Existing deployments; migration comparison | Size-coupled baseline and burst behavior. Do not assume small-volume burst throughput is sustained or that converting to default gp3 preserves the old throughput.
| st1 | Sequential scan/compaction staging candidate | At 1 TiB: 40 MiB/s sustained baseline, 250 MiB/s burst; large/random ANN scatter needs a real trace test. Not the default performance pool.
| sc1 | Rare sequential staging candidate | At 1 TiB: 12 MiB/s baseline, 80 MiB/s burst. Low capacity price can be erased by sizing for throughput. Not a latency promise.
| Local NVMe | Fast serving residency, rebuildable on node loss | Compare incremental instance cost and replacement/warm-up work. Do not call bundled capacity free.
|===

Use a task-owned test file, direct I/O where available, sequential and randomized offsets,
and bounded queue depths. WSL/VHD/Windows caching remains a caveat even with guest O_DIRECT;
do not call that a raw-NVMe or EBS measurement. Never drop host caches or alter another workload.

For extrapolation use constraints, not a blanket NVMe-to-EBS multiplier:

----
effective_bandwidth <= min(volume bandwidth, instance EBS bandwidth,
                           network limit, measured application consumption)
QPS <= min(effective_bandwidth / local_bytes_per_query,
           effective_IOPS / block_IOs_per_query,
           available_CPU_seconds / CPU_seconds_per_query)
EBS latency model = backend/queue term + critical-path bytes/bandwidth
                   + unchanged decode/merge/compute work
----

For HDDs include the seek/locality term and exhausted-credit baseline. For gp3 account for
additional throughput/IOPS prices. Rewarm time is bounded by bytes / bottleneck bandwidth plus
request/decode overhead; regional placement does not make a large failover cheap or immediate.
Measure local-L2 bytes/query: remote 54.7 MB/query is not automatically the local read demand.

=== 6.2 Three ledgers, not one misleading comparison

. *Physical usage:* bytes, operations, CPU seconds, capacity-time, rewrites, rewarming.
. *Our COGS:* rated physical usage plus allocated idle capacity, replicas, support/operations,
  control-plane/network services, durability overhead and amortized warming/compaction.
. *Customer invoice:* stable logical units or explicit reserved capacity with published limits,
  mapped by AnvaiOps. Never expose implementation GET count as the only user planning unit.

----
monthly_COGS = object_storage + retained_versions + requests + retrieval
             + disk_capacity + provisioned_IOPS_throughput + compute
             + network/services + warming/compaction + operational allocation

cost_per_query = monthly_COGS / successful_queries
minimum_price_for_margin_m = COGS / (1 - m)

Q_break_even = (additional_reserved_capacity_cost + rewarming + fixed_overhead)
               / (shared_variable_cost_per_query - reserved_variable_cost_per_query)
----

Require a positive denominator; otherwise no cost breakeven exists. Do not count avoided
compute unless measured, subtract retained S3 storage, or divide by peak QPS when billing an
idle month. Model capacity at provisioned bytes / utilization, and each serving replica separately.

=== 6.4 Recommended commercial experiments

* *Shared balanced:* simple logical storage plus query-work allowance/overage and a small
  transparent account minimum. Pool capacity across tenants; measure hit-rate distribution and
  idle utilization. Publish an estimate before expensive query shapes; enforce compute/concurrency
  budgets without silently reducing recall or freshness.
* *Reserved performance:* sell explicit capacity-time and, only when implemented, separately
  admitted compute/concurrency. Include a stated query-work allowance, not unlimited QPS.
  Avoid charging full usage-based query work and the same reserved resource twice. Rewarming,
  upgrades, grace periods and degraded-service credits need explicit rules in AnvaiOps.
* *Economy:* target large, rarely queried context with optional online colder tiers. Price
  retrieval risk and minimum retention; use a forecast/advisor before tiering. Low $/GB alone
  does not establish low total cost.
* *Commitments:* discount predictable baseline consumption only when pooled utilization and
  reservation savings support it. Use interruptible compute for rebuildable background work
  after measuring restart cost, not as an unqualified serving-SLO assumption.
* *BYOC option:* show customer cloud charges plus software/control-plane fees separately;
  this can avoid double storage margin and strengthen open-table positioning. Do not build a
  new deployment mode in TD-TIER-1.
* *Multimodal value:* compare complete workflow cost (copies, ETL, joins, operational services)
  only for capabilities proven end to end. Never use unimplemented lakehouse/graph guarantees
  to justify a current price premium.

For each candidate rate card, calculate contribution margin at low/base/high utilization,
one/two serving replicas, cold-start frequency, update/compaction amplification, tail concurrency
and all four storage media. Price off a conservative cost envelope, not a single mean trace.
Use actual workload commitments to amortize warming; do not introduce punitive time minima
solely because a competitor has them. Customer spending caps and reservation previews are
product controls; internal physical meters remain available for audit and optimization.

EBS capacity assumptions for the worksheet only: gp3 $0.08, gp2 $0.10, st1 $0.045,
sc1 $0.015 per provisioned billed-GB-month, plus gp3 extra IOPS/throughput where needed.
Recheck region, unit basis, size minima and current rates at
https://aws.amazon.com/ebs/pricing/[EBS pricing]. Example of throughput sizing, not a recommendation:
100 MiB/s sustained requires about 2.5 TiB st1 or 8.33 TiB sc1 using baseline rates; 1 TiB
of cheap capacity cannot be compared with gp3 solely on its capacity bill. Include the
instance cap and cache utilization before choosing a pool.

== 7. Experiments, emulator constraints and stop rules

E0: inventory available source/binary, dataset, hardware, active services, credentials by
reference, cache paths and real read call sites. Record hashes and commit; never log secrets.
Use task-owned data/config/prefixes/ports. No modification of another session's benchmark bed.

E1: fixed-geometry query cap sweep on local S3-compatible MinIO plus owned Toxiproxy latency
profile; ds3 is an alternative only after its endpoint/access is known. Baseline 4 MiB, then
16/40; refine 8/32/64 when informative. First restart with L2 absent, then L2 warm with new
queries and result-cache bypass. Keep actual server path, not an adapter-only microbenchmark.
The existing harness's `OwnedServer` accepts a cap, but its CLI currently hard-codes the
4 MiB cap into arms and reporting. Expose/record/verify cap and gap in one harness-only change
before running a claimed CLI sweep; inherited env variables are scrubbed and cannot override it.

E2: direct local range tests (sequential/random, 4–64 MiB, queue depths 1 and 8), then
application traces. Guest direct I/O does not prove Windows host cache coldness. These tests
can identify local decode/I/O limits but cannot emulate HDD seek or EBS credits.

E3: one whole-object protected-residency prototype versus existing A/B L2 on the same PAX
objects. Inventory the residual GETs; do not implement a broad pinning subsystem before
proving the production read path can serve verified ranges locally. Track duplicate cache bytes.

E4: access-tier option round-trip through the existing LocalStack scope; MinIO does not validate
the same tier semantics. Real AWS smoke is required for lifecycle/retrieval economics; emulators
cannot measure provider prices, minimum-duration charges, or availability.

E5: finalists on actual gp3, then st1/sc1 only if sequential locality and forecast justify them.
Run beyond burst-credit exhaustion, record volume AND instance limits. Until authorized hardware
is available, supply optimistic/base/pessimistic bounds labeled [D]/[A], never [M].

Stop/replan when: the production reader bypasses the intended adapter; a class lacks a distinct
contract; remote write durability is being silently changed; pin coverage cannot be enumerated;
range gains disappear at fixed geometry; larger ranges violate memory/recall/p95 constraints;
or vendor price is below credible COGS without a measured differentiation. Preserve negative
results. Do not build deferred D4 co-location, a new cache, or a new manifest merely because
earlier effort has already been spent.
