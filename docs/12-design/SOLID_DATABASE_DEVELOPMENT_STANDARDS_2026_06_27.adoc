[IMPORTANT]
====
**Why this exists:** A recurring pattern of PR failures — stale imports (`pv1`), fragile unit
tests, merge-conflict pile-ups, and drift-stale branches — traced to *ad-hoc dependencies*
("duck typing" in a compiled language: it works until the internal shape changes, then everything
breaks). These standards codify the SOLID fix: make dependencies **explicit and stable** via
traits/ports, so internal refactors (proto migration, god-object decomposition, engine extraction)
don't cascade-break dependents.
====

== The five rules

=== Rule 1 — Dependency Inversion: depend on stable seams, not internal paths

Services depend on **stable crate paths** (`proximadb_proto::`) or **port traits**
(`Arc<dyn Port>`), **never** on internal module paths (`crate::proto::...`) that may be
shimmed/removed during decomposition. Proto *types* (for wire data) are fine at the gRPC/REST
boundary — the issue is the *path* to reach them, not the type itself.

Two levels of compliance:

[source,adoc]
----
// ❌ Fragile (internal path — breaks when proto is decomposed into a crate):
use crate::proto::proximadb_v1 as pv1;          // #267's actual failure

// ✅ Minimum (stable crate path — survives decomposition):
use proximadb_proto::proximadb_v1;               // the proto crate's public API

// ✅✅ Ideal (port trait — survives proto refactors entirely):
use crate::services::DocumentPort;                // behavior contract, not data shape
----

*Why:* the proto decomposition (root-crate → `proximadb-proto` crate) moved `proximadb_v1`.
Internal paths (`crate::proto::proximadb_v1`) were shimmed temporarily, then removed — breaking
every service that imported them (the #267 `pv1` error). The stable crate path
(`proximadb_proto::proximadb_v1`) survives; the port trait doesn't even see the refactor.

*Scope:* all v2 gRPC services, REST handlers, embedded entry points. The TD-104 port extraction
(`ApiHandlersPort`, `CollectionPort`, `RecordOpsPort`, `GraphPort`, `QueryAdapterPort`) is the
ideal-level implementation.

=== Rule 2 — Test against ports, not internal paths

Unit tests exercise behavior through **trait objects** (`Arc<dyn IndexQuery>`, `Arc<dyn
CollectionPort>`), not internal module paths. A proto/internal refactor should **never** break a
test — only a behavior change should.

[source,adoc]
----
// ❌ Fragile test (breaks when the module path changes):
let result = crate::proto::pv1::convert::typed_value_to_proxima(value);

// ✅ Stable test (exercises behavior through the port):
let result = port.execute_sql_v1(query, params, collection, tenant).await?;
assert!(result.is_ok());
----

*Scope:* all `#[test]` + `#[cfg(test)]` code. Contract tests (proto compatibility, OpenAPI drift)
verify wire stability; unit tests verify behavior — neither should depend on internal import paths.

=== Rule 3 — Test isolation: unique state, no sharing

Every test uses a **unique tempdir** (leaked via `std::mem::forget` for file-backed stores like
`NativeCatalog`, `MetricsPersistenceLayer`). No shared `/tmp` paths. No process-global mutable
state that persists across tests in the same process.

[source,rust]
----
// ✅ Isolated — each test gets a fresh directory:
let temp_dir = tempfile::TempDir::new()?;
let storage_path = format!("file://{}", temp_dir.path().display());
std::mem::forget(temp_dir);  // file-backed store needs the dir alive for the test
----

*Why:* the file-backed catalog (`NativeCatalog`) persists JSON under `storage_path`. If two tests
share the path, one test's state contaminates the next (the flushcoordinator + semantic-analysis
flakes this session were exactly this).

=== Rule 4 — Single Responsibility: split before it conflicts

No PR should modify a file that **>2 other open PRs** also touch. If it does, extract the shared
concern into a new module/port first (Open/Closed), then the PRs diverge.

*Why:* the `UnifiedHandlers` god-object meant every feature PR touched `request_handlers.rs` →
every PR conflicted with every other. The TD-104 decomposition (extract services onto `AppState`
fields) is the fix: PRs now touch different files.

*Practice:* before opening a PR that modifies a hot file (multi_server.rs, proto definitions,
shared traits), check `gh pr list` for other open PRs touching the same file. If >2, extract first.

=== Rule 5 — Short-lived branches: merge or rebase within 48h

Feature branches merge within **48 hours** or rebase **daily** onto `origin/develop`. Stale
branches (>3 days) accumulate drift (compile/clippy/fmt/proto drift) that blocks CI.

*Why:* the merge-bot loop this session spent hours rebasing stale PRs (#266/#267/#390/#405) that
hadn't been rebased in days. The drift was pure accumulation — the code was correct, but develop
moved. Daily rebasing prevents this.

== Database-specific extensions

These build on the existing CLAUDE.md mandates (Directive 8: storage-format migration, Directive
10: quality ratchets, Directive 11: test hygiene) with the SOLID framing:

* **Schema migration = mixed-read-safe + version-gated** (Directive 8). A format change must not
  break existing readers. This is Open/Closed at the storage layer.
* **Catalog as sole authority** — collections resolve via the catalog (`collection_from_catalog_asset`),
  not direct store access. This is Dependency Inversion at the data layer.
* **Storage-format version byte** — old and new formats coexist, detected by magic/version byte,
  never a flag-day (Directive 8). This is the Liskov substitution at the serialization layer.

== Anti-patterns to avoid

|===
| Anti-pattern | Why it recurs | SOLID fix
| Direct proto import (`use crate::proto::pv1::...`) | Proto migration renames the module → import breaks | Depend on a port/trait
| Shared `/tmp` test path | State accumulates across runs → flaky tests | Unique tempdir per test
| God-object modification (`request_handlers.rs`) | Every PR conflicts | Split → modify different files
| Long-lived branch (>3 days) | Develop moves → drift accumulates | Rebase daily or merge fast
| Test on internal path (`crate::proto::pv1::convert::...`) | Internal refactor breaks the test | Test via port/trait
|===

== How to apply

When opening a PR or reviewing one:
1. **Does any service import a concrete proto/internal module?** → extract to a port (Rule 1).
2. **Do any tests reference internal module paths?** → rewrite to test via ports (Rule 2).
3. **Does any test share a `/tmp` path?** → switch to unique tempdir (Rule 3).
4. **Does the PR modify a file touched by >2 other open PRs?** → extract the shared concern (Rule 4).
5. **Is the branch >3 days old?** → rebase before pushing (Rule 5).

These rules are **ratchets** — existing violations are tracked as TD items; new code must comply.
