= Native OLAP Engine Blueprint — PAX-Columnar Scan, DataFusion-Interim (2026-06-22)
:toc: macro
:icons: font

Blueprint for ProximaDB's **native, Rust-built columnar OLAP engine** whose natural scan
input is the **PAX column-stripe format** (not Parquet). It is the bridge document
referenced by ADR-027 (PAX as the single internal format) and is consistent with the
co-design spine (`CODESIGN_DIMENSIONAL_ARCHITECTURE_2026_06_19.adoc`, "vertical inside /
standard outside") and the multi-engine routing decision in
`DATA_WAREHOUSE_AND_ENGINEERING_COURSE_CORRECTION_2026_06_04.adoc`.

[IMPORTANT]
====
This blueprint *scopes the interim → native transition*; it does not retire DataFusion now.
DataFusion-over-Parquet remains the **interim** OLAP/MPP executor (course-correction §1.4,
§2.1) while the native engine matures. The end state is: the native engine scans PAX column
stripes for the internal hot path; Parquet/Iceberg is the **interop seam** (external
tools / federated / export), not the internal scan format.
====

[IMPORTANT]
====
**Superseded in part by ADR-052 (Accepted 2026-07-04).**
`docs/12-design/adr/ADR-052-analytics-execution-competitiveness-codesign.adoc` retires the
native-*operator*-engine end state: §3's framing of `NativeOlap` as a peer execution route,
§4 P3's promotion of the native route *over* DataFusion (DataFusion as fallback), and the
end-state box above are superseded. Under ADR-052 the "NativeOlap route" is a **PAX-native
SCAN operator emitting Arrow `RecordBatch`es into DataFusion's vectorized operators**
(tracked TD-OLAP-1); native HashAgg/HashJoin/Sort are an explicit non-goal. The scan scope
of this blueprint — §2 substrate capabilities, §4 P0–P2, and the TD-154/TD-151/TD-162a
prerequisites — **remains authoritative**.

== 1. Why a native engine (and why PAX-columnar, not Parquet)

Per the co-design mandate, the dominant cost term for a cloud DB is I/O round-trips +
egress, optimized **across** the storage↔compute boundary. Scanning the *internal* OLAP
path over Parquet forces a second on-disk format, a second reader, and a second SQL
lowering beside the PAX vector/record path — the storage fork ADR-027 collapses. A native
engine that scans the **same PAX column stripes** the LSM already writes:

* reuses one writer, one reader (`read_segment_records` → `RecordReader` trait, TD-162a-3),
  one zone-map/prune stack, and one I/O-trace path (TD-158);
* co-designs the scan with the storage geometry (block/row-group/stripe, TD-156) and the
  quant tiers (RaBitQ/SQ8 for embedding columns; raw/zstd typed stripes for relational),
  rather than inheriting Parquet's fixed row-group model;
* keeps Parquet at the **boundary** where it is cheap and standard (Arrow Flight serves
  decoded record batches, so on-disk format is invisible to clients).

== 2. Scan input — the PAX column stripe

The native engine consumes a PAX segment (magic `PBLK` … `PAXSEG01`) via the
`RecordReader` trait. Required capabilities (tracked under ADR-026 / ADR-027 TDs):

[cols="1,3,2", options="header"]
|===
| Capability | What the engine needs | Tracked
| Typed user-column stripes | Relational columns as typed, projectable stripes (not opaque
msgpack `props_bytes`) so projection + zone-map pruning work | TD-162a-2
| Zone maps / hierarchical pruning | min/max + null-count per stripe/row-group; skip excluded
blocks before fetch | TD-154
| Configurable geometry | 8–16 MiB row groups for scan/aggregate; small for point-lookup;
per-collection | TD-155 / TD-156
| Range coalescing | contiguous stripe fetches in few large GETs (vs per-block fragmentation) | TD-151
| Query-scoped I/O trace | `range_gets` / `bytes_read` per scan for the cost model | TD-158
|===

== 3. Engine seam (pluggable, mandate "vertical inside / standard outside")

----
SQL → relational frontend/planner → logical plan
   → ComputeScheduler::route_select  (src/query/compute_scheduler.rs)
       ├─ DataFusion (INTERIM): parquet-backed / MATERIALIZE'd tables
       └─ NativeOlap   (TARGET): PAX-backed tables, scans column stripes via RecordReader
----

The router (`relational_pipeline.rs`, `compute_scheduler.rs`) already owns engine
selection; the native engine is added as a route, selected when a table is PAX-backed and
the workload is scan/aggregate. The logical-plane contract is unchanged (course-correction
§3 "all engines consume the same logical plane"), so adding the native arm is non-breaking.

== 4. Migration phases (interim → native; mixed-read-safe, default-off)

. *P0 — seam exists (today).* DataFusion behind `datafusion-integration` (UNWIRED per
  course-correction §4); `ComputeScheduler::route_select` routes parquet-backed → DataFusion,
  else Volcano/native record path.
. *P1 — PAX columnar substrate.* TD-162a-2 typed user-column stripes + TD-154 zone maps +
  TD-162a-3 `RecordReader` trait. The native engine's scan input becomes available.
. *P2 — native scan operator (default-off).* A `NativeOlap` route that scans PAX stripes
  (projection + zone-map prune + range coalescing TD-151), gated behind a feature/per-
  collection opt-in; DataFusion stays the default. Conformance: the TPC-H/TPC-DS pgwire
  ratchets (counts only go up, mandate #10) must not regress when a table is moved to the
  native route.
. *P3 — promote by measured cost.* Promote the native route where the **measured** per-query
  trace (TD-158) shows it beats DataFusion on the dominant cost term; Parquet/DataFusion
  remains for federated/external/interop and as the fallback. RL routing (course-correction
  §3 `RLPlanner`) tunes the equilibrium.

== 5. Non-goals
* *Not* removing Parquet/DataFusion — they are the interop seam + interim warehouse executor.
* *Not* a distributed MPP rewrite here — single-node/pseudo-distributed first (course-
  correction §1.4); distribution via the pluggable `ExecutionEngine` trait later.
* *Not* a new on-disk format — the native engine scans the **existing** PAX stripes.

== 6. Relationship to ADR-027 and the course-correction
ADR-027 makes PAX the single *internal* format and demotes Parquet to the interop seam;
this blueprint is the engine that makes that concrete on the OLAP path. It **partially
supersedes** the course-correction's "Parquet/Iceberg = OLAP base/publication tier" clause:
Parquet/Iceberg remains the **publication/interop** tier and the **interim** scan format,
but the durable *internal* OLAP scan format becomes PAX once P1–P3 land. See ADR-027
§"Reconciliation with the 2026-06-04 course-correction".
