Scope: Python notebook/procedural API, PySpark-style lazy planning, Rust-backed execution, embedded
Arrow exchange, DataFusion integration, local pseudo-distributed execution, and Spark connector
convergence.

== Purpose

ProximaDB should support notebook and PySpark-style procedural development without moving execution
authority into Python. The target experience is Python ergonomics with Rust execution:

* users build plans procedurally in Python notebooks;
* Python objects stay as facades over a lazy DataFusion `LogicalPlan`, similar to Spark DataFrames;
* execution is pushed into the Rust engine through embedded PyO3/Arrow surfaces;
* All SQL, relational, and multi-modal transforms are routed through **DataFusion** running over decoupled object storage;
* **MLflow-compatible MLOps and Model Management** APIs are exposed natively on the DataFrame facade. Users can track experiments, log models, register artifacts, and execute distributed scoring or Ray-style training workflows utilizing the same Rust-native distributed architecture, all managed by xCatalog (`mlops.*`);
* vector, document, graph, and observability paths utilize DataFusion User Defined Logical Nodes (UDLNs) wrapping Proxima-native operations;
* a single-node pseudo-distributed mode using DataFusion workers proves the object-store coordination before real multi-node cluster maturity is claimed.

This blueprint does not introduce a new durable authority. Notebook, Spark, DataFusion, and local
pseudo-distributed execution are compute facades/routes over xCatalog, canonical records, canonical
WAL, shared policy, and explainable route metadata.

== Py4J Equivalent For Rust

PySpark uses Py4J because Python drives a JVM Spark runtime. For ProximaDB's Rust-backed notebook
surface, Py4J is not the right primary mechanism.

[cols="1,2,3"]
|===
| Mechanism | Fit | ProximaDB use

| PyO3 / maturin
| Best fit for in-process Python -> Rust calls.
| Already used by `src/embedded/python.rs` and `clients/python-embedded/`. This should be the primary
notebook path.

| Arrow IPC / Arrow C Data Interface
| Best fit for batch data exchange without Python object-per-row overhead.
| Already present as embedded Arrow IPC insert helpers. Extend to query/result streams and plan
execution.

| JNI
| Best fit for JVM/Spark executor integration.
| Already present in `crates/binding/proximadb-spark-jni` wrapping `src/connectors/spark.rs`.

| Arrow Flight / Flight SQL
| Best fit for out-of-process bulk query and delegated compute.
| Keep for server/remote mode and future cluster/external engine interop.

| Py4J
| Useful only if Python is intentionally controlling a JVM process.
| Do not use for the main Rust notebook engine. It would add a JVM dependency and extra copying
without improving Rust execution.
|===

The practical answer: use PyO3 plus Arrow for notebook/procedural Python, and keep JNI for actual
Spark JVM integration.

== Target User Experience

The notebook API should feel like PySpark, but should not pretend to be Spark:

[source,python]
----
from proximadb_embedded import ProximaSession, col

px = (
    ProximaSession.builder()
    .data_dir("./data")
    .master("proxima-local[8]")
    .memory_limit("8g")
    .get_or_create()
)

events = px.table("events")

result = (
    events.where(col("tenant_id") == "acme")
    .select("id", "ts", "message", "embedding")
    .vector_search(column="embedding", query=query_vector, top_k=50)
    .group_by("service")
    .count()
)

result.explain(format="json")
pdf = result.to_pandas()
----

Supported notebook actions:

* `collect()` returns Python rows for small results only.
* `to_pandas()` materializes through Arrow batches.
* `to_arrow()` returns `pyarrow.Table` or a streaming reader.
* `write.table(...)` writes canonical `ProximaRecord` batches.
* `explain()` returns the same route/write diagnostics governed by ADR-004.

== HLD

The refined HLD is *DataFusion-first*: DataFusion's own partition-parallel physical plan provides
intra-node ("pseudo-distributed") execution, so there is no bespoke worker pool on the hot path.
A single `ComputeScheduler` picks between two real providers — `Native` (vector/point/simple scans
and writes) and `DataFusionLocalProvider` (joins/aggregates/windows/relational). The dormant
`query/distributed` coordinator is demoted to a future role: cluster-proof and cross-engine fragment
orchestration only — not the primary single-node engine.

== Plan Contract

The Python facade builds a lazy `NotebookPlanEnvelope`. It is not a durable schema and not a new
query authority; it is an edge transport shape into the existing Rust planner.

Required fields:

* `plan_id`: stable execution id for diagnostics and cancellation.
* `source_surface`: `python_notebook`.
* `session_config`: local process worker count, memory limit, batch size, spill directory, timeout.
* `catalog_snapshot`: optional pinned catalog snapshot/version.
* `logical_plan`: shared logical algebra or a DataFusion-compatible logical plan fragment.
* `route_constraints`: requested route, freshness, policy, isolation, and approximate/exact behavior.
* `output_format`: Arrow stream, Arrow table, JSON rows, or write result.

Lowering rules:

* SQL strings parse through the existing SQL frontend and DataFusion-compatible lowering where
  possible.
* DataFrame-style relational operators lower to shared algebra and/or `ComputePlan`.
* Vector search lowers to Proxima native vector operators, not a Python UDF.
* Document, graph, and observability operators lower to their existing logical services.
* Writes lower to `ProximaRecord`/`ProximaValue` through xCatalog validation before WAL/storage.
* UDFs are residual Python only when explicitly requested; default UDF execution should be Rust,
  DataFusion UDF, or rejected with explain diagnostics.

== Arrow Exchange Boundary

Results leave Rust as Arrow over the *Arrow C Data Interface* (FFI), not as Arrow IPC bytes. The C
Data Interface hands pyarrow the same buffers Rust already owns (a refcount bump), whereas IPC forces
a full serialize/memcpy/deserialize round trip. For a beat-Spark-on-a-box target, zero-copy out is
the central single-node win and replaces the JVM row-encoding overhead entirely.

Canonical converter (closes a convergence gap and a real bug):

* New `crates/storage/proximadb-storage-common/src/proxima_arrow.rs` with
  `proxima_records_to_record_batch(records: &[ProximaRecord], schema: &ProximaSchema) -> RecordBatch`.
* Output schema comes from `ProximaSchema::to_arrow_schema()` (catalog-driven, *not* inferred
  per-batch — per-batch inference yields mismatched partition schemas and `RecordBatch::try_new`
  failures, the known pre-existing Arrow Flight bug).
* It emits *every* `ProximaColumn` as a typed Arrow column from the full `ProximaTree`, plus the
  vector as `FixedSizeList<Float32>` only when the schema has a vector column. This replaces the
  `codec.rs` path that collapses `props` to a single key/value StructArray.
* `codec.rs::vector_records_to_batch` and `search_results_to_batch` are refactored to call this
  function, so Arrow Flight, Arrow IPC insert, and the notebook result path share one mapping and one
  nullable-field discipline.

Streaming reader and PyO3 surface:

* `src/embedded/arrow_results.rs`: `EmbeddedRecordBatchReader` implements `arrow::RecordBatchReader`
  by pulling `scan_records_filtered` cursor pages and converting each page — it never materializes
  the whole table (the property the `snapshot_table_for_relational` path lacks).
* `src/embedded/python.rs` (`PyProximaDB`): add `scan_arrow(collection, batch_size, filter_json) ->
  pyarrow.RecordBatchReader`, `execute_plan_arrow(plan_json) -> pyarrow.RecordBatchReader`, and
  `explain_plan(plan_json) -> str`.
* Enable `arrow = { features = ["pyarrow"] }` *only under the `python` feature* to keep default
  server binaries lean (per ADR-006 / CLAUDE.md). Verify the `arrow 57.1` to `pyo3 0.25` ABI pairing
  before adopting — the C Data Interface couples these versions.

== Pseudo-Distributed Local Mode

Single-node pseudo-distributed mode is a development and architecture-proof mode. It simulates a
cluster inside one process while keeping all durable state local and Proxima-authoritative.

NOTE: Under the DataFusion-first decision (2026-06-04), DataFusion's own partition-parallel physical
plan provides single-node parallelism, so the components below are *not* the primary single-node hot
path. They are the cluster-proof scaffold — the seams (coordinator, split planner, shuffle, memory
manager, route explain) that must exist cluster-shaped so a future `DataFusionDistributedProvider`
slots in without a rewrite. For single-node "beat Spark on a box", prefer the DataFusion path
(Split Generation + DataFusion Role + Route Selection sections); build the coordinator/worker/shuffle
runtime out only when proving multi-node decomposition. The split planner and route-explain emitter
are shared with the DataFusion path today.

=== Execution Scope

Pseudo-distributed mode should report:

* `compute_route = DataFusionDistributed` or native distributed route when plan decomposition is
  distributed-shaped;
* `execution_scope = local_process`;
* `authority_mode = ProximaAuthoritative` for native tables unless xCatalog says otherwise;
* `policy_boundary = engine-enforced` only when tenant/RLS predicates are applied before worker
  execution;
* `freshness_sla` derived from cataloged table/projection metadata.

This keeps the route compatible with future real cluster execution while making the single-node
simulation explicit.

== Split Generation

Real intra-node parallelism requires multiple scan partitions. The `FileSplit` / `SplitStatistics` /
`SplitPlanner` infrastructure in `format_splits.rs` is real but unfed. Rather than add
`generate_splits` to the six-engine `UnifiedStorageEngine` trait (which would force all engines to
implement it at once and invites proliferation), introduce a focused `SplitSource` trait in
`proximadb-storage-common` that engines opt into:

[source,rust]
----
// crates/storage/proximadb-storage-common/src/format_splits.rs (extend)
trait SplitSource {
    async fn generate_splits(&self, collection: &str, target_partitions: usize,
                             filters: &[ScalarPredicate]) -> Result<Vec<FileSplit>>;
}
----

Three-tier cascade, safe by construction:

. *Segment metadata available* (VIPER Parquet files, SST blocks): emit `FileSplit::new_row_group` /
  `new_block` per row-group/block with real `SplitStatistics` for pruning. Promote the existing
  `viper_adapter` `discover_files` / `create_splits_from_files` logic behind `SplitSource`.
. *No segment metadata*: emit N cursor-range splits over the single collection — a new
  `SplitType::CursorRange { start, end }` plus `FileSplit::new_cursor_range`. `EmbeddedScanReader`
  seeds its cursor from `start` and stops at `end`, giving parallelism for flushed data that has no
  per-file manifest.
. *Unknown*: one `FileSplit::whole_collection` — correct and single-threaded. This is exactly today's
  `plan_partitions` floor, so it is the guaranteed fallback.

`EmbeddedProximaDB::plan_partitions` is rewired onto `SplitSource::generate_splits`, so the Spark
connector (`SparkInputPartition`) and the DataFusion scan (`ProximaScanExec` partitions) consume one
split generator — no parallel split logic.

Cursor-range correctness caveat: TD-099(3d) added a lazy, deduped,
time-ordered in-memory scan index for the unflushed WAL/memtable path, so warm
cursor seeks can be efficient. That does **not** by itself make parallel live
cursor ranges safe under concurrent writes. Tier 2 is only valid over
flushed/segment data, a pinned snapshot/branch, or a read epoch that freezes the
split boundary for the query; otherwise live-memtable collections fall back to
tier 3 (single split).

== DataFusion Role

DataFusion should be used where it is strong:

* SQL projection/filter/aggregate/sort/window/join over Arrow batches;
* local relational query execution;
* logical/physical plan inspection;
* table provider integration for Proxima storage scans;
* custom scalar/aggregate functions for supported vector/distance operations when exact semantics
  can be preserved.

DataFusion should not own:

* WAL or write authority;
* xCatalog schema/policy authority;
* vector ANN index freshness;
* document/graph/observability durable semantics;
* route selection outside the Proxima planner.

=== Live Wiring Over Real Table Data

The relational pipeline's `GLOBAL_ENGINE` is the *legacy in-memory demo* path and is not seeded by
real-table writes; the notebook/DataFusion read path deliberately bypasses it and sources rows
directly from storage. The adapter chain, top to bottom:

[source,text]
----
DataFusion LogicalPlan TableScan
  -> ProximaDataFusionTable (impl TableProvider)        src/datafusion/proxima_table_provider.rs
       .scan(state, projection, filters, limit)
         -> SplitSource::generate_splits(...)            (Split Generation)
         -> SplitPlanner::plan_splits(splits, target_partitions)
         -> ProximaScanExec                              src/datafusion/proxima_scan_exec.rs
              partition i -> EmbeddedScanReader (impl SplitReader)
                              src/datafusion/engine_adapters/embedded_reader.rs
                  -> EmbeddedProximaDB::scan_records_filtered(collection, cursor, batch, filter)
                  -> proxima_records_to_record_batch(...)   (Arrow Exchange Boundary)
                  -> SendableRecordBatchStream
----

* Predicate pushdown reuses `predicate_pushdown::convert_expr_to_filter`. `supports_filters_pushdown`
  returns `Exact` for filters that lower to a `FilterExpression`, `Unsupported` otherwise; DataFusion
  re-applies `Inexact`/`Unsupported` filters above the scan, so correctness holds under partial
  lowering.
* Projection pushdown passes column indices into the reader; v1 projects in the converter after
  fetch (pushing projection into the record store is a follow-up).
* A `ProximaCatalog` `SchemaProvider` (`src/datafusion/proxima_catalog.rs`) lazily resolves
  collection name -> `ProximaDataFusionTable` and is registered into `create_session_context()`
  (closing the `mod.rs:137` deferred-catalog TODO).

=== Notebook Plan Lowering And Vector Splice

`NotebookPlanEnvelope` lowers to DataFusion's `LogicalPlanBuilder` (not the `proximadb_relational`
algebra, which carries the `GLOBAL_ENGINE` real-data gap). DataFrame operators map 1:1 —
`select`/`filter`/`groupBy`/`agg`/`join`/`limit`/`sort` — and inherit DataFusion's optimizer and
parallel physical planner. Lowering lives in `src/datafusion/notebook_plan.rs`.

Vector search lowers to a `VectorSearchNode` (`UserDefinedLogicalNodeCore`) that plans to a
`VectorSearchExec` *leaf* (`src/datafusion/vector_search_node.rs`). The exec calls the existing
`core::search` / `VectorOperationsService` path and yields top-k as a `RecordBatch` stream via the
canonical converter. Treating vector search as a scan-like source keeps `vector_search().filter()
.join().group_by()` fully streaming and optimizable, instead of forcing a native-then-materialize
barrier before the relational operators.

== Route Selection And EXPLAIN

Routing authority stays single: the `ComputeScheduler`, driven from `ComputeBridge`. The embedded
PyO3 methods are thin callers — they do not route (a second router would violate the convergence
gate).

* Reuse the `ComputeBackend` enum (`Native` / `DataFusionLocal` / ...) as the route label.
* New `DataFusionLocalProvider: ComputeProvider` (`src/compute/provider/datafusion_local.rs`) builds
  the `SessionContext`, registers the catalog, lowers the plan, and returns a
  `SendableRecordBatchStream`. It *replaces* the stubbed `LocalComputeProvider::execute`. Its
  `capabilities()` advertise filter/projection/window/streaming = true, distributed = false.
* The Native-vs-DataFusion discriminator reuses `query_engages_relational_engine`
  (`relational_pipeline.rs:161`): joins / group-by / aggregates / windows / set-ops -> DataFusionLocal;
  vector top-k, point lookups, simple filtered scans, and writes -> Native. pgwire SQL and the
  notebook therefore agree on the boundary.
* EXPLAIN: add a read-side `RoutedReadPlan` (sibling of the write-only `RoutedExecutionPlan` in
  `table_write_plan.rs`) carrying `compute_route`, `partition_count`, `pushed_filters`,
  `rejected_pushdowns`, the DataFusion physical-plan string, and the ADR-004 / Architecture-Mandate
  fields `authority_mode` (current-snapshot read), `policy_boundary`, and `freshness_sla`. The PyO3
  `explain_plan` renders it.

This keeps a future `DataFusionDistributedProvider` a drop-in beside the local provider, with no
router rewrite — the cluster-shaped interface the single-node mode is proving.

== Memory And Speed Requirements

The design cannot guarantee every notebook query is faster than Python, PySpark, or external Spark.
It can guarantee the execution boundary:

* Python builds plans and displays results.
* Rust owns scan, filtering, vector kernels, SQL execution route, joins, aggregation, writes, and
  memory accounting.
* Data moves in Arrow batches, not Python rows.
* Batch sizes are bounded and configurable.
* `collect()` has a row/byte safety limit.
* `to_pandas()` and `to_arrow()` use Arrow materialization.
* Worker tasks respect cancellation and timeout.
* Spills are explicit and visible in explain.

Benchmark gates should compare:

* Python row loop vs embedded Arrow batch execution;
* current one-partition Spark/embedded scan vs split-aware local scan;
* DataFusionLocal vs native fallback for relational scans;
* pseudo-distributed local workers vs single local worker;
* memory peak, batch count, spill count, and rows/sec.

== Databricks/Spark Performance Comparison And Trade-offs

The goal is to be comparably fast to Databricks on a single box. The realistic Rust advantages, and
the honest trade-offs, are:

[cols="1,3"]
|===
| Lever | How it competes / where it costs

| No JVM, no row encoding
| PySpark crosses Py4J and serializes rows to/from a JVM. The notebook path keeps data columnar Arrow
end-to-end with no JVM in the loop — the largest constant-factor win.

| Arrow C Data Interface (zero-copy)
| Results reach pandas/pyarrow as a refcount bump, not a serialize/memcpy/deserialize round trip.

| DataFusion morsel/partition parallelism
| DataFusion is the Rust analog of Spark Tungsten/Photon: vectorized, partition-parallel hash joins,
hash aggregates, and sorts. Intra-node "pseudo-distributed" execution is effectively free — no
bespoke worker pool on the hot path.

| Split-aware scans + predicate/projection pushdown
| Multiple `FileSplit` partitions drive parallel scans; filters lower into `scan_records_filtered`
and prune via `SplitStatistics` before I/O.

| Out-of-core via DataFusion memory pool + spill
| Enabling the `SessionConfig` memory pool and disk spill gives Databricks-parity behavior on large
joins/aggregates that exceed RAM.

| Native fast-path
| Vector top-k, point lookups, and writes skip DataFusion planning latency entirely, staying on the
lowest-latency Proxima path.
|===

Trade-offs to state plainly (do not over-claim):

* Single-node memory/CPU ceiling — this mode does not scale horizontally; that is the future cluster
  role of the demoted coordinator.
* No Spark RDD-style lineage / fault recovery. Mitigation: read fragments are idempotent and
  retryable; there is no speculative re-execution.
* Cursor-range splits are unsafe over live (unflushed) memtable data without a pinned snapshot,
  immutable segment inventory, or read epoch. TD-099(3d)'s scan index makes seeks efficient once
  warm; it is not the split-boundary correctness guard.
* DataFusion 51 / Arrow 57.1 / pyo3 0.25 are coupled across the C Data Interface — a real, ongoing
  upgrade tax.
* The design guarantees the *execution boundary* (Rust owns scan/filter/kernels/join/agg/write/memory;
  Python only builds plans and displays results), not that every individual query beats external
  Spark on a large cluster.

== Implementation Plan

Phases are ordered by dependency and shippability. Phase 0 has no DataFusion dependency and is
independently shippable; each later phase produces a measurable capability.

=== Phase 0: Arrow Result Foundation

Deliverables:

* `proxima_arrow.rs::proxima_records_to_record_batch` — canonical, lossless `ProximaRecord` ->
  `RecordBatch` driven by `ProximaSchema::to_arrow_schema()` (emits all props as typed columns).
* Refactor `codec.rs::vector_records_to_batch` / `search_results_to_batch` onto it (convergence; fixes
  the single-prop StructArray-collapse bug; one nullable-field discipline).
* `EmbeddedRecordBatchReader` streaming over `scan_records_filtered` cursor pages.
* PyO3 `scan_arrow(...) -> pyarrow.RecordBatchReader`; enable `arrow/pyarrow` only under the `python`
  feature.

Acceptance:

* Python gets zero-copy streaming Arrow from any collection, with all props preserved.
* `cargo test -p proximadb-storage-common proxima_arrow` and a pandas round-trip pytest pass.

=== Phase 1: DataFusion Live Over Real Data (single partition)

Deliverables:

* `EmbeddedScanReader` (`SplitReader` over `scan_records_filtered`) replacing the stubbed readers.
* Implement `ProximaDataFusionTable::scan` + `supports_filters_pushdown` (reuse
  `convert_expr_to_filter`).
* `ProximaCatalog` `SchemaProvider`, registered into `create_session_context()`.

Acceptance:

* `ctx.sql("SELECT ... FROM real_collection WHERE ...")` returns rows from storage end-to-end.
* Pushed filters report `Exact`; residual filters are re-applied above the scan. Single partition is
  correct (not yet parallel).

=== Phase 2: Split-Aware Parallelism

Deliverables:

* `SplitSource` trait + tiered `generate_splits` (segment / cursor-range / whole-collection).
* Promote `viper_adapter` file discovery behind `SplitSource`; add `SplitType::CursorRange` +
  `FileSplit::new_cursor_range`.
* Rewire `EmbeddedProximaDB::plan_partitions` onto `SplitSource` (unifies Spark + DataFusion).
* Add a pinned snapshot/read-epoch guard before enabling cursor-range splits over live WAL/memtable
  data; TD-099(3d)'s scan index is the seek primitive, not the correctness guard.

Acceptance:

* A multi-segment collection produces multiple partitions; single-segment / live-memtable produces
  one (cursor-range safety). Split-planning tests cover missing-collection, one-split, multi-split.
* "Beat-Spark-on-a-box" becomes measurable.

=== Phase 3: Router, Notebook Plan, Vector Splice

Deliverables:

* `DataFusionLocalProvider: ComputeProvider` replacing the `LocalComputeProvider::execute` stub.
* `notebook_plan.rs` lowering to `LogicalPlanBuilder`; `VectorSearchNode` / `VectorSearchExec` leaf.
* Routing via `ComputeBridge` / `ComputeScheduler` reusing `query_engages_relational_engine`;
  `RoutedReadPlan` + PyO3 `explain_plan` / `execute_plan_arrow`.
* Python `ProximaSession` / `ProximaFrame` / `Column` lazy plan builders.

Acceptance:

* The notebook example executes with no server running.
* `explain()` shows compute route, partition count, pushed/residual predicates, and policy boundary.
* `vector_search().filter().group_by()` returns correct top-k with no materialization barrier.

=== Phase 4: DataFusion Route Maturity

Deliverables:

* Register exact-semantics Proxima vector/distance scalar UDFs.
* Route rejection for unsupported UDFs, unsafe policy boundaries, stale projections, lossy coercions
  (surfaced in EXPLAIN).
* Enable DataFusion memory pool + spill; benchmark gates (Native vs DataFusionLocal; 1 vs N
  partitions; vs PySpark row loop) recorded in this doc.

Acceptance:

* DataFusionLocal is selected only when capabilities and policy match; rejected routes are visible in
  EXPLAIN with concrete reasons. SQL and DataFrame plans agree for supported operators.

=== Phase 5: Spark/JVM Connector Convergence (lower priority)

Deliverables:

* Build the Java/Scala DataSource V2 around the existing JNI functions.
* DataSource V2 filter/projection reporting so Spark reapplies residual predicates.
* Use the *same* `SplitSource` as notebook and embedded mode.

Acceptance:

* Spark reads/writes ProximaDB without placeholder paths; shares split/filter/write semantics with the
  notebook planner; no Spark path bypasses xCatalog, `ProximaRecord`, WAL, or policy.

== Risks And Guardrails

* Do not create a second DataFrame engine in Python. Python objects are plan builders only.
* Do not make DataFusion a write authority. Writes still commit through Proxima record/WAL paths.
* Do not claim distributed maturity from pseudo-distributed mode. Label it local-process execution.
* Do not push filters partially. Unsupported predicates must become residual predicates or route
  rejection reasons.
* Do not add new catalog/record/wal authority for notebook sessions.
* Do not expose Python UDFs as silent slow paths. Require explicit opt-in and explain warnings.
* `ProximaRecord` <-> Arrow fidelity is the highest-risk item: schema must come from the catalog, with
  correct null masking for absent props, or partition schemas diverge and `RecordBatch::try_new`
  fails (the known Arrow Flight bug). Build the actual server binary and the maturin/`pylib` wheel —
  `cargo check --lib` hides feature-gated breakage.
