= How to File a TD or ADR — the canonical, collision-free convention
:toc: macro
:icons: font

**This is the single source of truth for filing Technical Debt (TD) items and
Architecture Decision Records (ADRs).** It lives in the repo, so it is identical
on every developer machine. The per-agent rule files (`CLAUDE.md`, `GEMINI.md`,
`AGENTS.md`) are **gitignored and per-developer-local** — they are *not* committed,
so each developer keeps their own copy. Shared defaults ship under
`docs/agent-rules/*.seed` (copy one to the repo root to seed a new machine — see
link:../agent-rules/README.adoc[docs/agent-rules/README.adoc]). Those rule files only *point* here;
they do not duplicate these rules. Read this doc; do not re-derive the convention
from the per-agent files.

toc::[]

== Why this exists

This repo is worked on by many concurrent agent sessions. Sequential numbering in
a shared space has no atomic allocator, so two sessions branched off the same base
both pick the same "next" number — `ADR-031`, `ADR-032`, `ADR-033`, `TD-167` were
each claimed twice in a single week, surfacing only at merge (or coexisting
silently). And a single monolithic registry file makes every concurrent filing a
textual merge conflict. The convention below removes both failure modes.

== The rules (do this)

1. **One file per entry.**
   * ADRs: `docs/12-design/adr/ADR-<NNN>-<slug>.adoc` (already the norm).
   * TDs: `docs/10-quality/td/TD-<id>-<slug>.adoc` — the per-file directory.
   Two sessions adding *different* entries touch *different* files, so there is no
   textual conflict.

2. **Declare the id in the title heading**, not just the filename. The first
   AsciiDoc heading is authoritative:
   `= TD-167: short title` / `= ADR-037: short title`. The uniqueness guard reads
   the id from this heading (the filename slug uses hyphens too, so it is
   ambiguous; the heading delimits the id with `:`/space).

3. **Prefer a topic-scoped id for any multi-step effort** —
   `TD-<TOPIC>-N` (e.g. `TD-CAT-1`, `TD-SC-2`, `TD-CG3`). One initiative owns its
   prefix, so parallel sessions on *different* initiatives never collide. This is
   the collision-free path and is already proven in this repo. Reserve global
   sequential `TD-NNN` for genuinely standalone one-offs.

4. **For a global number, claim the next free one by scanning the directory**
   (the highest existing `ADR-NNN` / `TD-NNN`, +1). Never reuse a number already on
   `develop`, even if your branch was cut before it landed — rebase first
   (mandated within 48h) and re-check.

5. **The `td-adr-unique` CI guard is the backstop.** `scripts/check_td_adr_unique.py`
   fails any PR that introduces a duplicate ADR number or a duplicate TD id (across
   both the legacy table and the per-file directory). Because a rebased PR re-runs
   CI, your `ADR-037` colliding with a freshly-merged `ADR-037` is caught *before*
   merge — you renumber then. It is a backstop, not a lock; rule 4 is how you avoid
   needing it.

6. **Index new ADRs** in `docs/12-design/adr/README.adoc`. (The guard *warns* on an
   unindexed ADR; keeping the index current is expected hygiene.)

7. **Verify the premise before acting on it — then correct the record.** A TD or ADR
   is a *claim about the code at the time it was written*, not an instruction to be
   executed. Before implementing one, check its load-bearing assertions against
   current source. When one is wrong, **fix the document in the same PR** as the
   work, stating what was claimed, what is actually true, and how you verified it.
   See "Premise verification" below — this is a rule, not a nicety.

== Premise verification (required before implementing a TD or ADR)

A filed entry ages the moment it is written: the code moves, adjacent work lands,
and the author's mental model was a snapshot. Treating a TD as a work order rather
than a hypothesis is how a plan's stale detail becomes a shipped defect.

=== The check, before you write code

For each assertion the plan *depends on* — not every sentence, the load-bearing ones:

* **Does the thing it names still exist, at the path/line it cites?** Line numbers
  drift; identifiers get renamed or deleted.
* **Does the mechanism it says to BUILD already exist?** Grep for it and count its
  callers. A capability with **zero or one caller** is the common case: the machinery
  is present and simply unwired, and the work collapses from "architect X" to "call X".
* **Is the quantity it cites still the quantity?** Counts, depths, sizes and ratios
  are the first things to rot, and they are usually the justification.
* **Does the fix it proposes hold for every path, or only the one the author had in
  mind?** A rule that is correct for one modality is often unachievable for another.

=== When a premise is wrong

Do **not** quietly implement around it, and do **not** silently follow it.

1. **Stop before writing the code the stale premise implies.** A plan whose premise
   fails will not produce a correct change by being followed harder.
2. **Correct the document in the same PR as the work** — or as a docs-only PR when the
   correction changes what the work should be. A TD nobody fixed will send the next
   person down the same path.
3. **State the correction concretely:** what was claimed, what is true, how you
   verified it (command, test, file:line), and what it changes about the plan.
4. **Amend the parent ADR too** when the premise came from one. A TD note does not
   reach someone reading the ADR.
5. **Record a negative result.** "I implemented this, it worked, and it was wrong"
   is worth more than silence — it stops the idea being re-attempted. Reverting and
   documenting beats shipping something you have stopped believing in.

=== Why this is a rule

It is the highest-yield step in the whole filing convention, measured on this repo.
Across the ADR-094 unified-substrate programme, nearly every filed TD named a real
goal while containing a detail that would have broken it — and several of those would
have shipped *silent* wrong answers (a dropped tombstone, lost props, mis-attributed
cost cells, rows unioned across generations). None was visible from the plan. Each
surfaced only from checking the premise before building.

A corollary worth internalising: **an existing test that fails your change is
evidence, not an obstacle.** Determine whether it pins an intended invariant or
encodes a defect, and say which. Both happen. Deleting or relaxing it to get green is
how a real invariant is lost.

== Legacy entries (do NOT migrate ad hoc)

The ~100 existing TDs in `docs/10-quality/TECHNICAL_DEBT.adoc` stay in that table —
they are referenced ~900× across code and docs, and rewriting the file would
conflict with every open PR. The guard treats those table rows as declarations, so
a new per-file TD cannot reuse a legacy id. Migrating the legacy table to per-file
is a separate, batched, post-merge effort — not something to do incidentally.

== Quick reference

[cols="1,3", options="header"]
|===
| Want to… | Do this

| File a TD for an initiative | `docs/10-quality/td/TD-<TOPIC>-N-<slug>.adoc`, heading `= TD-<TOPIC>-N: …` (topic-scoped → collision-free)
| File a standalone numbered TD | scan `docs/10-quality/td/` + the legacy table for the highest `TD-NNN`, use +1, heading `= TD-NNN: …`
| File an ADR | scan `docs/12-design/adr/` for the highest `ADR-NNN`, use +1; `ADR-NNN-<slug>.adoc`, heading `= ADR-NNN: …`; add a row to `adr/README.adoc`
| Check before pushing | `python3 scripts/check_td_adr_unique.py` (exit 0 = unique)
| **Implement an existing TD/ADR** | **verify its load-bearing premises against current source FIRST; grep whether the thing it says to build already exists and count callers; correct the document in the same PR when a premise is wrong** (see "Premise verification")
|===

== Verification

`python3 scripts/check_td_adr_unique.py` — exits 0 when all ADR numbers and TD ids
are unique; exits 1 (with a specific message) on a duplicate. Add `--strict` to
also fail on the unindexed-ADR warnings. The CI **Docs Validation** job runs it on
every PR.
