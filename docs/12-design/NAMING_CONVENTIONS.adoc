= Naming Conventions
:toc:
:toclevels: 3

This document captures the naming conventions applied across the
ProximaDB Rust crates to keep struct, enum, and trait names
distinguishable across modules. It was extracted from the multi-round
disambiguation pass logged in
the
nomenclature pass roadmap and the commit series tagged
`refactor: disambiguate ...` (rounds 1-16, May 2026).

== Motivation

A repository-wide audit of `pub struct` definitions found ~54 type
families where the same leaf name was reused across 3-15 unrelated
modules — each with different fields, different invariants, and
different concerns. The most extreme case was `CacheStats` defined
×15 in distinct cache subsystems.

This duplication hurt:

* *Code search / IDE go-to-definition* — every "find usage" returned
  noise across unrelated layers.
* *Code graph analysis* — leaf-name based cross-file CALLS resolution
  (Victor CCG) produced spurious edges between unrelated calls because
  names alone were not enough to identify the target.
* *Code review* — reviewers had to chase the `use` line to know which
  `CacheStats` a snippet referred to.
* *Cross-module refactoring* — moving a type required disambiguating
  imports at every call site.

The disambiguation pass renamed ~395 struct definitions to give every
type a unique leaf name while preserving every existing import via
backwards-compat type aliases.

== Naming rule

[NOTE]
====
For every newly introduced `pub struct`, `pub enum`, or `pub trait`
that represents a concept that already exists under the same leaf name
elsewhere in the workspace, *use a domain-distinctive prefix* such
that the leaf name is unique repository-wide.
====

=== Choosing the prefix

Prefer prefixes in this priority order:

1. *Engine / layer name* (most specific): `SstQueryCacheStats`,
   `ViperFactoryCompactionConfig`, `OrionTraversalStats`,
   `RelationalRouteStats`.
2. *Module path leaf* when no canonical engine name exists:
   `MultimodalGraphStoreParticipant`, `ColumnarUtilsOperationMetrics`,
   `MetadataFilterAnalyzer`.
3. *Domain keyword* when the layer is generic but the use is specific:
   `IngestSchedulerConfig`, `CompactionSchedulerConfig`,
   `ComputeSchedulerConfig`.
4. *`Legacy*` prefix* for soft-deprecated parallel-spelling modules
   (e.g. the `multimodal/` vs `multimodel/` typo-twin pair):
   `LegacyMultimodelTransactionCoordinator`.

Avoid:

* Generic prefixes like `My*`, `Inner*`, `Helper*` — they convey no
  domain meaning.
* Numbered prefixes (`Cache1Stats`, `Cache2Stats`) — they don't survive
  refactors.
* Prefixes that duplicate the module name when the module name is
  itself the disambiguator
  (e.g. don't write `metrics/exporters/mod.rs::MetricsExportersCacheMetrics`
  — `ExporterCacheMetrics` is enough).

== Backwards-compat alias pattern

Every disambiguation rename adds a type alias next to the renamed
struct so existing imports do not break:

[source,rust]
----
/// Backwards-compat alias for [`SstQueryCacheStats`].
pub type CacheStats = SstQueryCacheStats;

/// Cache metrics for monitoring and optimization
#[derive(Debug, Default)]
pub struct SstQueryCacheStats {
    // ...
}
----

This lets pre-disambiguation `use crate::storage::engines::sst::readers::sst_query_engine::CacheStats;`
keep resolving, while new code can use the unique name.

[IMPORTANT]
====
The alias is a *migration window*, not a permanent surface. Aim to
remove aliases ~6 months after the disambiguation rename ships and
all callers have migrated to the new name.
====

== Engines → formats convergence

ProximaDB's storage "engines" (SST, VIPER, HELIX, NOVA, SWIFT, RAPTOR,
…) are conceptually *format/layout specializations*. The catalog layer
already speaks this vocabulary (`CatalogPhysicalFormat`,
`CatalogStorageLayoutKind`); the runtime is converging on it. Following
the alias pattern above, the runtime now ships **format aliases** next
to the existing engine names (back-compat, zero call-site churn):

[cols="1,1", options="header"]
|===
| Engine name (legacy) | Format alias (new)

| `UnifiedStorageEngine` (trait, `storage/traits/mod.rs`)
| `UnifiedStorageFormat`

| `StorageEngineStrategy` (enum, `storage/traits/types.rs`)
| `StorageFormatStrategy`

| `StorageEngineFactory` (`storage/engines/factory.rs`)
| `StorageFormatFactory`
|===

New code should prefer the format names; the engine names remain during
the migration window and are migrated opportunistically.

*Explicitly preserved (wire-breaking — do NOT rename):* the proto
`StorageEngine` enum and the `storage_engine` gRPC/JSON/REST collection
field are client-visible contract and stay as-is.

*Deferred (high churn):* the directory rename `src/storage/engines/` →
`src/storage/formats/` (~385 files, and it name-collides with the
existing `engines/core/formats/` on-disk-format subtree), plus
migration of the ~421 `UnifiedStorageEngine` / ~262
`StorageEngineStrategy` call sites. Unrelated `*Engine`/`*EngineType`
enums (metrics and RL planner) and the ORION graph runtime are out of scope.

== Substring-regression hazard

When using `replace_all` on a short type name, watch out for sibling
types that contain the short name as a substring. The disambiguation
pass hit this ~10 times:

* `Alert` → `XAlert` rename also caught `AlertManager`,
  `AlertThresholds`, `AlertSeverity`, `AlertEngine`, `AlertRule`,
  `AlertRuleId`, `AlertSubscriber`, …
* `SearchResult` → `XSearchResult` rename caught
  `ChunkSearchResult`, `RpcSearchResult`, `DistributedSearchResult`,
  `StreamingSearchResult`, plus proto refs `proximadb_v1::SearchResult`.
* `EngineStats` → `XEngineStats` rename caught `EngineStatsSnapshot`.
* `CompactionStats` → `XCompactionStats` rename caught
  `ZeroCopyCompactionStats`.
* `RowGroupStats` → `XRowGroupStats` rename caught
  `EnhancedRowGroupStats`.

=== Mitigation: protection-marker dance

For a file containing both the target struct and sibling types that
share a substring, use temporary markers to protect the siblings:

[source,bash]
----
# Step 1: protect each sibling with a unique marker
sed -i 's/\bAlertManager\b/__SAVED_AM__/g'
sed -i 's/\bAlertThresholds\b/__SAVED_AT__/g'
sed -i 's/\bAlertSeverity\b/__SAVED_AV__/g'

# Step 2: do the bare rename
sed -i 's/\bAlert\b/MetricsAlert/g'

# Step 3: restore siblings
sed -i 's/__SAVED_AM__/AlertManager/g'
sed -i 's/__SAVED_AT__/AlertThresholds/g'
sed -i 's/__SAVED_AV__/AlertSeverity/g'
----

(In practice the Edit tool's `old_string=Alert` with `replace_all=true`
does the same thing in one step — only the marker dance is needed when
the bare-name rename would mangle siblings.)

=== Mitigation: scope-aware verification

After each batch of renames in a module that has both the renamed
struct and sibling `X*` types, run:

[source,bash]
----
grep -rn "X<NewName>" src/ | grep -vE "^(/.*<file_that_was_renamed>)"
----

Any hits in OTHER files indicate substring damage that needs reverting.

== When NOT to disambiguate

The disambiguation pass deliberately stopped at the ×3-collision long
tail (46 types remaining as of round 15). Some collisions are
legitimate per-layer concerns and should not be touched:

* `QueryPlan` exists distinctly in `proto::v1`, `query::federated`,
  `graph::query::planner`, `compute::plan` — each is the canonical
  shape for its respective layer.
* `QueryExecutor` in `graph::query::executor` vs `query::execution`
  vs `compute::executor` — distinct runtime executors per query model.
* `GraphEdge` was disambiguated (×5) because each module had different
  *fields* (some had `weight`, some had `outgoing`, some had
  `properties`); had they been structurally identical, the right move
  would be to consolidate, not to rename.

The rule of thumb is: *disambiguate when the structs are different
shapes that happen to share a name; consolidate when the structs are
the same shape that diverged*.

== Audit query

To check for ≥N-collision raw struct definitions:

[source,bash]
----
grep -rn "^pub struct [A-Z][a-zA-Z0-9_]*[^<{]" src/ --include="*.rs" \
  | awk -F'pub struct ' '{print $2}' \
  | awk '{print $1}' \
  | sed 's/[<{].*//' \
  | sort | uniq -c | sort -rn | awk '$1 >= 3'
----

To check for graph/edge/node-specific duplicates:

[source,bash]
----
grep -rn "^pub struct [A-Z][a-zA-Z0-9_]*[^<{]" src/ --include="*.rs" \
  | awk -F'pub struct ' '{print $2}' \
  | awk '{print $1}' \
  | sed 's/[<{].*//' \
  | grep -iE "(Node|Edge|Graph|Vertex|Traversal|Adjacency|Subgraph)" \
  | sort | uniq -c | sort -rn | awk '$1 >= 2'
----

== Disambiguation pass history

Sixteen rounds were applied between 2026-05-22 and 2026-05-24,
covering every type with ≥4 raw definitions and 25 of the 71 types at
×3. Total: ~395 struct renames + ~395 backwards-compat aliases.

== Alias retirement schedule

|===
| Round shipped | Alias retirement target | Rationale

| 1-10 (P0 ≥4)
| 2026-11-30
| 6 months after first round; covers all heaviest-traffic renames.

| 11-15 (×3 partial)
| 2027-02-28
| 9 months after; lower-traffic types may need longer migration.

| 16 (graph audit)
| 2027-02-28
| Same window as above.
|===

Before retirement, run:

[source,bash]
----
grep -rn "pub type <OldName> = <NewName>;" src/
# For each, grep callers and ensure they've migrated:
grep -rn "use .*::<OldName>\b\|::<OldName>\b" src/ tests/ benches/ examples/
----

Only remove the alias when no caller uses the old name.
