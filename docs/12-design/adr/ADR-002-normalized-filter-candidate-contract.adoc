== Context

Filters in ProximaDB are represented by at least 4 separate type systems:

1. `FilterExpression` in `src/core/search/mod.rs:372` — AST with Comparison/And/Or/Not using serde_json::Value
2. `MetadataFilter` in `src/index/axis/management/manager.rs:1779` — flat struct with field/operator/value
3. `FilterOperation` enum in `proto/proximadb/v1/vector_types.proto:189` — 11 proto operations
4. `DocumentFilter` in `proto/proximadb/v1/document.proto` — document-specific filter model

When a filtered vector search arrives, there is no canonical normalization step. Each execution path translates filters ad-hoc into the backend format it needs. This causes:

* Inconsistent filter semantics across backends (HNSW vs IVF vs direct scan)
* No residual verification — if a filter cannot be pushed into ANN, results may silently miss matching records
* No candidate-set abstraction — filters are either fully pushed or fully post-filtered, with no efficient middle ground

The existing `HybridQuery` in `src/index/axis/management/manager.rs:1755` is well-designed but lacks a formal contract for how filters become candidates and how residuals are tracked.

== Decision

Introduce a **single normalization layer** that converts all filter representations into a canonical `NormalizedFilterExpr`, and a **candidate contract** that tracks what was pushed into the index vs what must be re-verified.

=== Normalized Filter Expression

[source,rust]
----
/// Canonical filter representation after normalization.
/// All filter sources (REST, gRPC, SQL, proto) are lowered into this form.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum NormalizedFilterExpr {
    And(Vec<NormalizedFilterExpr>),
    Or(Vec<NormalizedFilterExpr>),
    Not(Box<NormalizedFilterExpr>),
    Predicate(FilterAtom),
}

/// Single predicate after normalization
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct FilterAtom {
    pub field: String,
    pub operator: NormalizedOp,
    pub value: FilterValue,
}

/// Normalized comparison operators (superset of all backend ops)
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum NormalizedOp {
    Eq,
    Neq,
    Gt,
    Gte,
    Lt,
    Lte,
    In,
    NotIn,
    Contains,
    StartsWith,
    EndsWith,
    IsNull,
    IsNotNull,
    Between,
    Regex,
}

/// Type-safe filter values
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum FilterValue {
    String(String),
    Integer(i64),
    Float(f64),
    Boolean(bool),
    Null,
    List(Vec<FilterValue>),
    Range(Box<FilterValue>, Box<FilterValue>),
}
----

=== Candidate Contract

[source,rust]
----
/// Result of planning how to evaluate a filter against an index
pub struct CandidateSet {
    /// How candidates were generated
    pub mode: CandidateMode,
    /// Estimated number of matching records
    pub estimated_cardinality: Option<usize>,
    /// Explicit record IDs (for small sets)
    pub exact_ids: Option<Vec<RecordId>>,
    /// Bitmap of matching record positions (for large sets)
    pub bitmap: Option<RoaringBitmap>,
    /// Filter predicates NOT handled by the index (must be re-verified post-retrieval)
    pub residual_predicate: Option<NormalizedFilterExpr>,
}

pub enum CandidateMode {
    /// Index fully covers the filter — no residual needed
    IndexCovered,
    /// Partial index coverage — residual must be applied
    PartialIndex,
    /// No index available — full scan with post-filter
    FullScan,
    /// Pre-computed bitmap (e.g., from inverted index)
    BitmapBacked,
}

/// Complete result of building a hybrid query
pub struct BuiltHybridQuery {
    /// The HybridQuery for AXIS execution
    pub hybrid_query: HybridQuery,
    /// Candidate set with residual tracking
    pub candidate_set: Option<CandidateSet>,
    /// Any filter predicates not pushed into the candidate
    pub residual_predicate: Option<NormalizedFilterExpr>,
    /// Diagnostics about filter planning decisions
    pub diagnostics: QueryBuildDiagnostics,
}

pub struct QueryBuildDiagnostics {
    pub pushed_predicates: Vec<String>,
    pub residual_predicates: Vec<String>,
    pub index_used: Option<String>,
    pub estimated_selectivity: Option<f64>,
}
----

=== Execution Contract

[source,text]
----
1. Normalize: FilterExpression|ProtoFilter → NormalizedFilterExpr
2. Plan: NormalizedFilterExpr → CandidateSet (with residual tracking)
3. Execute: HybridQuery + CandidateSet → approximate ANN results
4. Verify: Apply residual_predicate to ANN results (mandatory unless IndexCovered)
5. Return: Only results passing both index and residual verification
----

**Invariant**: ANN execution is NEVER the final arbiter of filter correctness. Step 4 is mandatory unless `CandidateMode::IndexCovered`.

== ANN Filtering Mode Selection

The `CandidateMode` from ADR-002 determines *whether* the filter is pushed. A separate
routing decision determines *how*: as a pre-filter, an inline (predicate-aware) HNSW
traversal, or a post-filter over ANN results. This routing is formalized in ADR-011.

The connection between the two ADRs:

[source,text]
----
ADR-002: normalize → candidate set → residual predicate
ADR-011: estimated_selectivity → PreFilter / Inline / PostFilter mode
            ↓
         CandidateMode is set by routing:
           PreFilter  → CandidateMode::BitmapBacked (filter first, ANN over bitmap)
           Inline     → CandidateMode::PartialIndex  (filter during traversal)
           PostFilter → CandidateMode::IndexCovered  (ANN first, residual after)
----

`QueryBuildDiagnostics` is extended with:

[source,rust]
----
pub struct QueryBuildDiagnostics {
    pub pushed_predicates: Vec<String>,
    pub residual_predicates: Vec<String>,
    pub index_used: Option<String>,
    pub estimated_selectivity: Option<f64>,
    /// ANN routing mode selected for this query.
    pub ann_filtering_mode: Option<AnnFilteringMode>,
    /// Whether the routing mode was forced by a catalog policy override.
    pub ann_mode_forced_by_policy: bool,
}
----

See ADR-011 for the complete routing logic, selectivity thresholds, and EXPLAIN surface.

== Consequences

* One normalization layer per concern (not per backend)
* Filters from any source produce identical execution behavior
* Residual verification catches ANN recall gaps and index coverage gaps
* Backend-specific filter support is declared via `CapabilityDescriptor` (ADR-001)
* `QueryBuildDiagnostics` feeds into Explain (ADR-004)
* ANN routing mode (PreFilter/Inline/PostFilter) is derived from selectivity and declared in ADR-011
