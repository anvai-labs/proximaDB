== 1. Context + the question

Four design questions surfaced from the SF=0.01 measured posture (TD-OLAP-15) and a co-design reading of the router:

1. Are *native-Volcano* and *native-vectorized* two different wirings, or one wiring with two modes?
2. DataFusion lives behind a seam; how do we keep introducing new plugin engines cheaply?
3. The cost-based router must not add per-query latency — how do we keep routing cheap as engines multiply?
4. The router today uses a heuristic ("all parquet → DataFusion"); should that become a router-managed dimension with fixed per-dimension weights, so it scales?
5. *(added in review)* Footer-stats elision trusts the parquet writer's metadata; for *external* parquet we did not write, is that trust safe — and should elision-vs-scan be a pluggable router dimension?

This ADR gives a definite position on each, grounded in what the code *actually does* today (§2) and a co-design/first-principles reading (§3–§4), then pressure-tested by an adversarial pass (§6).

== 3. The foundational insight — the router conflates *eligibility* with *selection*

A query router makes two logically distinct decisions:

- **Eligibility** (a *soundness* question): *can* engine E serve query Q over storage S correctly? This is a property of the engine's *capabilities* (does it have a reader for S's format? does it implement Q's operators — spill-capable agg, join, window?) — never of cost.
- **Selection** (a *cost* question): among the engines *eligible* for (Q,S), which is cheapest on the dominant cost term?

ProximaDB's router today answers **both with one mechanism** — a `match` on `(engages_relational, parquet_backed)`. Storage *format* is doing selection's job. This is the root diagnosis behind questions 4 and 5, and it has two symptoms:

1. **A soundness boundary is mislabeled as a heuristic.** "Parquet → DataFusion" looks like a cost heuristic but is actually a *soundness* rule: DataFusion implements the full OLAP algebra (spilling agg, hash/sort join, window, grouping sets), while native's aggregate is in-memory/non-spilling with no predicate or projection pushdown (TD-OLAP-15 §the four skip-guards). Sending a real `GROUP BY` over a large parquet table to native because "the EWMA says it's cheaper" is a path to OOM and wrong answers — the format gate is *correct by construction*, not a lazy heuristic.
2. **A missing dimension.** Stats *trust* is neither eligibility nor selection — it is a third, *safety* axis orthogonal to both. An elision that trusts an untrusted writer is wrong at any cost.

The fix is therefore **not** "let the cost model route everything" (that would dissolve the soundness boundary). It is to (a) keep eligibility as a hard, capability-driven gate; (b) make selection a cost decision *only among eligible engines*; (c) add trust as a hard safety gate on elision. Ownership seam with TD-EXEC-2: **TD-EXEC-2 owns how selection *scores* the eligible engines** (plan-geometry → the cost cell); **ADR-058 owns the eligibility gate and the trust gate that bound which engines selection may even consider.**

== 4. Co-design / first-principles reasoning (the cost-term lens)

Per the co-design mandate (name the dominant dimensional cost term; optimize across the storage↔compute boundary), each decision below states which term it moves:

- **Eligibility** moves *correctness risk*, not a cost term — it is the floor below which cost is meaningless (a wrong answer is not "cheap").
- **Selection** moves the cloud-OLAP dominant term — *bytes-scanned* (ADR-052), realized as `range_gets`/`bytes_read`/`egress` in the cost model. The fixed weights already encode this (per_get=20 ≫ egress=25 ≫ read=5 ≫ cpu=1): round-trips + egress dominate, CPU is the floor. The static format rule happens to *select* the bytes-cheapest engine today because DataFusion over parquet prunes row groups + columns; native's no-pushdown scan would read strictly more bytes.
- **Trust** moves *bytes-scanned* on the agg path: elision = 0 bytes; full-scan = Σ(column-width × rows). The cheapest *safe* strategy is the optimization; trust is the gate that defines "safe."
- **Routing latency** is itself a dimensional cost (per-query overhead × QPS). The frozen-`ArcSwap` consult makes selection O(1) **only while the frozen table is dense**; finer-grained selection classes risk thinning it (§6, P3).

First-principles check against the ecosystem: Postgres separates these concerns explicitly — a *foreign-data wrapper* (capability/eligibility) is distinct from the *planner's cost estimates* (selection), and `constraint_exclusion`/`parallel` are opt-in knobs (not default-on rewrites). Spark AQE's cost-based re-planning is also **opt-in and barrier-gated** (the pipeline-breaker theorem, ADR-056 §2). ProximaDB's `PROXIMADB_ROUTE_COST_OVERRIDE` (default OFF) is the same posture; this ADR keeps it.

== 5. The decision

|===
| # | Decision | Rationale
| **D1** | Native stays **one backend, two modes**; governed by a *single* capability descriptor `vectorized_supports(plan) -> {Full, Partial(reasons), None}` consulted by both the lowering decline and the shadow probe. | The fast-path-with-graceful-decline pattern (Postgres seqscan fallback, DataFusion repartition decline) is correct; splitting vectorized into a peer backend would force the router to choose between two engines over the *same* storage and move decline logic to the wrong layer. The *bug* today is two duplicated coverage statements (the lowering decline + the shadow probe's 4 skip-guards) that can drift silently. `Partial(reasons)` records *why*, not just *whether*.
| **D2** | `ComputeBackend` **stays an enum**; backends expose a **`BackendDescriptor` struct** (authority/freshness/access/label/data-plane) keyed off the enum — *not* a trait, *not* a registry yet. | A trait trades a 4-line match for `dyn`-dispatch on the hot path + 7 method impls/backend, to save adding an enum variant every ~2 years. The enum is already open (`ExternalDelegated(String)`). A descriptor struct collapses the 4 scattered property helpers without polymorphism. A registry is deferred until a 3rd real engine (e.g. GPU/libcudaf) lands — YAGNI until then.
| **D3** | Routing stays **eligibility-gated, consult-O(1)**; the load-bearing invariant is *frozen-table density*, not just O(1). | Consult = one hash-lookup against a frozen `ArcSwap` table built off-hot-path (observe→ingest→act). Finer selection classes must be tested to keep the table dense on hot queries; a class that returns `None` on the hot path is a bug. Selection never recomputes on the query path. **Falsifiable check:** emit a `route_consult_miss{class}` counter; the density invariant fails if any hot query class (top-N by QPS) has a nonzero miss rate after warm-up.
| **D4** | "Parquet → DataFusion" stays as a **soundness (eligibility) boundary**, NOT a cost heuristic. The cost override (`PROXIMADB_ROUTE_COST_OVERRIDE`) stays **opt-in, default OFF**. Native becomes eligible for parquet *only after* a shipped, default-ON, spill-capable native parquet scan lands. | Dissolving the format gate would let cost send real OLAP to an engine (native) that cannot yet execute it soundly — OOM/wrong-answer risk. The override knob (with TD-170 RTT-budget + `min_advantage` gates) is the responsible mechanism for cost-based flips; it must stay opt-in because the EWMA *lags* exactly the workload shifts where the static rule is right (cold start, burst). See §6.
| **D5** | Add a **`StatsTrust {Trusted, Verified, Untrusted}`** per-table catalog dimension (derived from authority mode). **Untrusted → elision disabled**, regardless of cost. "Verified" means *provenance* ("ProximaDB wrote this file; stats authoritative"), **not** sampling. Elision stays **binary** (elide-or-full-scan); the `AggStrategy` enum is deferred. | Trust is a *safety* gate (a wrong `COUNT(*)` from a federated file's stale `num_rows` is a correctness bug, not a slow query — invariant #16 territory). Sampling cannot prove correctness, only a full rescan can, which defeats elision → "Verified" must be a provenance claim. `ScanSmallestColumn` only helps COUNT and only with per-*column* trust (a narrow window with no caller yet) → defer the strategy enum; ship the gate.
|===

== 6. Alternatives rejected (adversarial review, 2026-07-10)

A four-agent adversarial pass attacked §5. What it killed, and why:

- **Reject: trait-ify `ComputeBackend` (my initial P2).** Over-engineering. The enum + `ExternalDelegated(String)` is open enough; the 4 property helpers are trivial. A trait adds `dyn`-dispatch + 7 methods/backend for ~zero gain. → D2 (descriptor struct) instead.
- **Reject: default-ON the cost override (my initial P4).** Two holes: (a) native can't *soundly* serve production parquet OLAP yet (non-spilling agg, no pushdown — making it "eligible" is a lie the cost model would act on); (b) cost-on-every-query re-introduces per-query float compares where there was one branch, against the frozen-table design whose whole point was to amortize cost *off* the hot path. The EWMA also lags workload shifts. → D4 (override stays opt-in).
- **Reject: "Verified by sampled scan" (my initial P5).** Unsafe. A sampled scan can verify a stat is *plausible*, not *correct*; only a full rescan proves correctness, which pays the cost elision was trying to avoid. → D5 ("Verified" = provenance).
- **Defer: the `AggStrategy {Elide, ScanSmallestColumn, ScanFirstColumn, Constant, FullScan}` enum.** YAGNI. Elision is binary today and fine for COUNT/MIN/MAX. `ScanSmallestColumn` is only valid for COUNT (any column gives row existence) and only when some column's null_count is trustworthy — a narrow window. `ScanFirstColumn`/`Constant(v)` have no caller. → D5 (ship the gate, defer the enum).
- **Sharpen: P3's invariant.** "Consult is O(1)" is necessary but not sufficient — a frozen table that returns `None` on hot queries is a no-op router. The real invariant is *density*: hot query classes must resolve to a non-`None` recommendation. → D3.

One factual correction from the review, recorded for fidelity: the reviewer initially claimed `native_parquet_scan.rs` "does not exist" — it had inspected the wrong branch (`codex/critical-architecture-trajectory`, not `origin/develop`). The file exists (`ParquetScanOperator`, `StatsAggregateOperator`); its conclusion (native-parquet is not production-wired) holds because all call-sites are inside the default-OFF shadow probe, not because the reader is absent.

== 7. Consequences

*Positive:* one source of truth for native-vectorized coverage (D1) removes a silent-drift correctness risk; the stats-trust gate (D5) closes the wrong-aggregate-on-external-parquet hole; the descriptor struct (D2) makes adding a future engine a single-file change without hot-path `dyn`-dispatch; eligibility-as-soundness (D4) keeps a correct-by-construction floor that the cost model refines rather than replaces.

*Negative / trade-offs:* cost-based engine selection remains opt-in, so the router will not *automatically* discover that native beats DataFusion on some shape until the override is enabled per-deployment (acceptable: the static rule is already bytes-cheap for the parquet/native split, per §4). Native-parquet stays measurement-only until a spill-capable scan ships — the DuckDB join gap (25–70×, TD-OLAP-15) is therefore closed by *DataFusion* improvements (join order/CBO via TD-OLAP-2) in the near term, not by native.

*Non-goals:* this ADR does not build a plugin registry (D2), does not default-on the override (D4), does not introduce the `AggStrategy` enum (D5), and does not make native production-eligible for parquet — each is explicitly deferred with the gate that unblocks it.

== 8. Rollout (announced here; implemented in follow-up PRs)

1. **P1 — `vectorized_supports` descriptor (D1).** Small, mechanical, *correctness-first*. Define `vectorized_supports(plan) -> SupportLevel`; route the lowering decline + the shadow probe through it. Eliminates the duplicated coverage statements.
2. **P5-trust-gate — `StatsTrust::Untrusted → no elision` (D5).** Derive `StatsTrust` from the authority mode `catalog_table_is_parquet_backed` already detects; gate `statistics_from_splits` elision on `Trusted|Verified`. Closes the external-parquet wrong-answer hole. Per-table now; per-column deferred with the `AggStrategy` enum.
3. *(Deferred, gated)* **D2 descriptor struct** — when a 3rd engine is real. **D4 native-parquet eligibility** — when a default-ON spill-capable scan ships. **D5 `AggStrategy` enum** — when a measured COUNT-via-smallest-column case appears.

Each step ships default-safe + ledger-gated, mixed-read-safe, behind the ADR-054 progressive-cutover discipline.

== 9. Grounded review addendum — from the OLAP/native implementation session (2026-07-10)

Filed from the in-flight "favor native by operation" route (PR #853) and the TD-EXEC-2 slices (PR #850/#851/#854), cross-checking §5's decisions against the exact code paths they govern. Every claim cites a call-site verified on `origin/develop` + PR #853 (rebased on develop). Three grounded points: one **support+extension** for D5, one **nuance** on D4, one **suggestion** for D1. None changes a decision — they sharpen the gates the decider is signing off.

=== A. Support + extension for D5 — there are TWO footer-trust paths, not one

§2 and the P5 rollout gate elision at `statistics_from_splits` (`src/datafusion/schema_inference.rs:110`). But the native route reaches parquet-footer trust by a *second, independent* path: `ParquetScanOperator::new_count_only` (`src/query/execution/native_parquet_scan.rs`) answers an unfiltered `COUNT(*)` from the parquet **footer row-count metadata** — not from `statistics_from_splits`. On PR #853 both footer-trusting branches are live production call-sites: `elidable_aggregate_batch` → `StatsAggregateOperator` (`relational_pipeline.rs:1065`, MIN/MAX/COUNT via column stats) **and** `new_count_only` (`relational_pipeline.rs:1082`, COUNT via footer `num_rows`). Both trust a writer we may not have written; the route today admits `FederatedRead | ExternalAuthoritative | ImportedSnapshot` (`relational_pipeline.rs:1187-1189`) — i.e. **untrusted external parquet flows into both**.

**Refinement:** the D5 `StatsTrust::Untrusted → no elision` gate MUST cover **both** the `statistics_from_splits` elision *and* the footer-row-count `COUNT(*)` path (`new_count_only`), or the wrong-answer hole stays open on the single most common analytic query. (The value-scan path — `ParquetScanOperator::new` at `relational_pipeline.rs:1131`, which reads *real* column data and aggregates — is trust-safe and needs no gate; this cleanly separates the trust-gated metadata paths from the trust-safe data path.)

=== B. Nuance on D4 — the sound unfiltered-elidable / scalar-aggregate subset predates the spill-capable scan

D4 makes native parquet-eligible "only after a shipped, default-ON, spill-capable native parquet scan lands," and holds native-parquet "measurement-only" until then. Grounded observation: an **unfiltered scalar aggregate** (no `GROUP BY` ⇒ nothing to spill; no `WHERE` ⇒ no pushdown needed) and **footer elision** (zero column bytes) are precisely the shapes that need *neither* spilling *nor* pushdown — they are sound on native **today**, and are the shapes TD-OLAP-15 measured native *winning* (1.8× on scan-heavy ClickBench). PR #853 routes exactly this subset: its eligibility guards (single-table, unfiltered, not-grouped, width-capped — `relational_pipeline.rs:1014`) decline everything that would require spill or pushdown to DataFusion.

So D4's blanket "measurement-only until the spill-capable scan" is *stronger than soundness requires*. **Suggestion (decider's call):** carve the eligibility explicitly — native is parquet-eligible for `{unfiltered footer-elidable aggregate} ∪ {unfiltered narrow scalar aggregate}`, **bounded by the trust gate of §9.A**, and remains ineligible for grouped / filtered / wide / join until the spill-capable + pushdown scan ships. This preserves D4's correct-by-construction soundness floor while not deferring an already-sound, measured-win subset. Either way, PR #853 must (i) gate its two elision paths on trust (§9.A) and (ii) stay **opt-in default-OFF** (consistent with D4's override posture) — which it is (`PROXIMADB_NATIVE_ROUTE` + `PROXIMADB_ROUTE_COST_OVERRIDE`, both default OFF).

=== C. Suggestion for D1 — the descriptor should own route-level eligibility too

D1's `vectorized_supports(plan)` descriptor is scoped to two coverage sites: the lowering decline and the shadow probe's four skip-guards. PR #853 introduces a **third** eligibility site — the route-level guards in `try_native_over_parquet` (`relational_pipeline.rs:1014`) that decide whether native serves parquet as PRIMARY. That is the *same* coverage question at a different layer, and D1's own rationale ("one capability descriptor, no silent drift between duplicated coverage statements") applies to it identically. **Suggestion:** make D1's descriptor the single source consulted by all **three** sites — lowering decline, shadow probe, and production route — so the sound-subset boundary (§9.B) has exactly one definition and cannot drift as the native surface grows.
