== Context

ADR-031 introduced stable, immutable, rename-stable numeric ids for catalog
objects (`object_id: u64`; per-table/column stable ids; the typed base62 path
`accounts/{b62 acct}/{b62 ns}/{b62 coll}/`). It established that the **catalog**
keys on stable ids ("stable across renames"). But the **identity/path layer
above it** did not follow: the request/tenant contexts and the legacy
string-resolved path (`data/{tenant}/{namespace}/{collection}/`) treat the
**display string** as authoritative and the stable numeric id as a mere
optimization. Concretely, `MiddlewareTenantContext::tenant_stable_id` is
documented as _"always an optimization for catalog/storage keying, never a
second source of truth (the string `tenant_id` remains authoritative)"_.

That inversion is a **rename-safety defect**. A path rendered from a mutable
display string (`data/acme/…`) breaks the moment `acme` is renamed, even though
the stable id is unchanged. It also leaks tenant/namespace **names** into
object-store keys (an isolation/hygiene concern), is larger than the base62 id,
and has no ordering guarantee (zero-padded base62 gives `LIST` lexicographic ==
numeric, enabling prefix pruning — display strings do not).

The stable-ID-only path **already exists** — ADR-031's typed path
(`build_from_identity`, env-gated `PROXIMADB_TYPED_PATHS`) renders base62 of the
numeric ids with no display strings. It is additive and default-OFF, so legacy
data under the string path is still readable (mixed-read-safe). The gap is one
of **authority**, not capability: the system treats strings as truth and stable
ids as optional, when it should be the reverse.

== Decision

**Stable numeric ids are the AUTHORITATIVE identity** across the catalog and the
path/filesystem layer; display strings are a **derived, legacy-compat** form.

* **Authoritative ids** (ADR-031 types): `account_id: u32`, `tenant_stable_id:
  u64`, `namespace_stable_id: u16` (`NamespaceId`), `collection_id: u32`
  (`CollectionId`), catalog `object_id: u64`. These are immutable, rename-safe,
  compact, and (zero-padded base62) lexicographically ordered.
* **Display strings** (`tenant_id`, `namespace_id`, collection **name**) are a
  presentation/UX concern resolved to a stable id at the **identity seam**
  (ADR-074's alias→id resolution). They are NOT a source of truth for paths or
  storage keys.
* The **path contract** (`DrPathBuilder` / `DrResolvedPath`) keys on stable ids.
  The legacy string-resolved path (`data/{tenant}/{ns}/{coll}/`) is retained
  solely as a **mixed-read-safe reader** for data written before typed paths;
  new writes prefer the typed (stable-id) path. The string path is deprecated,
  removed once the migration (below) completes.

This amends ADR-031's _"string remains authoritative"_ framing and ADR-027's
implicit string-keyed path contract: the DrPath authority is the **stable id**,
and the string segment is a derived compat render.

=== Runtime representation rule

Numeric identities remain numeric wherever the receiving type system can carry
them. In particular:

* catalog-global collection identity is `object_id: u64`;
* path-local collection identity is `CollectionId(u32)` and is meaningful only
  inside its `(AccountId(u32), NamespaceId(u16))` scope;
* tenant fairness, scheduling, admission, and cache isolation key on the
  authoritative numeric tenant/collection ids;
* base62 is an object-key rendering at the path boundary, never an in-memory
  identity; and
* aliases and decimal text are accepted only at lookup or transitional
  storage-port boundaries, then resolved once through the catalog.

The global `object_id` and path-local `CollectionId` are not interchangeable.
Code must name the distinction rather than narrowing a global id into the path
id or widening a path id and treating it as globally unique.

The admission-first flush and persistent PAX warm-tier slices apply this rule:
collection scheduling uses catalog-global `u64` ids, cache tenant scopes compare
stable `u64` ids directly, and display aliases cannot impersonate an equal
decimal stable id. Existing string-bearing storage traits are migration seams,
not precedent for new runtime identity fields.

== Consequences

* **Rename-safe paths** — renaming a tenant/namespace/collection never moves or
  orphans data (the stable id is unchanged; only the alias remaps).
* **Compact, ordered, opaque** — base62 ids are shorter than display strings,
  `LIST`-ordered (prefix pruning), and leak no names into object-store keys.
* **One source of truth** — eliminates the string-vs-id divergence hazard (today
  both are carried with conflicting authority).
* **Migration cost** — existing data under string paths must remain readable
  until typed paths are default-on (dual-read), and the `u16` namespace allocator
  must be fenced before typed paths ship in production (it wraps at 65 536/account
  today — `id_allocator.rs`, TD-NS-1 S4).

== Migration / gating (ordered)

1. **Thread the stable ids through the seam** — ADR-074 S1 (PR #1221 C.1 lands
   the `From<&MiddlewareTenantContext> for StorageTenantContext` bridge carrying
   account/tenant_stable/namespace/namespace_stable; C.2 migrates the call sites
   and deletes the storage-layer string constants). ✅ in progress.
2. **Fence the `u16` namespace allocator** (S4) — widen or wrap-check
   `mint_namespace_id` (`id_allocator.rs`) before typed paths go production; a
   wrap silently collides two namespaces on one typed path.
3. **Dual-read** — the reader resolves a path by stable id (typed) and falls back
   to the legacy string path for pre-migration data; both coexist (mixed-read-safe,
   no flag-day — mandate #8).
4. **Flip `PROXIMADB_TYPED_PATHS` default-on** — new collections write the typed
  (stable-id) path; the legacy string path becomes read-only-backfill.
5. **Deprecate the string path** — once backfilled, remove the string segment
   from `DrPathBuilder` and the `tenant_id`/`namespace_id` string fields from the
   contexts (the stable ids remain).

Steps 1–2 are unblocks; 3–5 are the phased cutover. Each is independently
shippable and reversible.

== Acceptance

* Rename a tenant and a namespace → the physical object-store path is
  **byte-identical** before/after (stable id unchanged).
* `PROXIMADB_TYPED_PATHS` default-on: new writes land under the typed path; old
  data still reads (dual-read).
* No new code introduces a display string into a path or storage key (the path
  contract accepts only stable ids; the string is a derived render at the seam).
* The `u16` namespace allocator is fenced (no silent wrap collision).

== Out of scope

* The **alias→stable-id authz resolution** (the registry, `Namespace*`
  permissions, default binding, negative caching) — that is ADR-074 S2/S3.
* The **metering** attribution (stable id as the KU/KRU label) — ADR-060;
  this ADR only establishes the id's authority, not its billing semantics.
