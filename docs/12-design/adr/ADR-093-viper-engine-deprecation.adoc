== Context

ADR-026 standardized on one vector path (AXIS graph + PAX stacked quantization)
and folded the legacy engines' *design ideas* into PAX while explicitly deferring
their retirement: "Retirement needs a deprecate → migrate → remove plan and is
larger than it looks (43 `StorageEngineType` match sites / ~19 files)."

Since then, four facts have accumulated that single out **VIPER** as the first
engine to retire:

1. **Its niche was structurally eliminated by the pivot.** VIPER's pitch is
   columnar Parquet, scan/aggregate analytics, 5-10x compression
   (`SUPPORTED_SURFACE.adoc`: "analytics-leaning"). Post-pivot that story is
   covered twice over: *analytics* runs on the DataFusion-over-Parquet/Iceberg
   path (ADR-052, Accepted), and *ANN serving* on SST (Supported, default) —
   while **NOVA occupies the same "columnar analytics vector engine" Beta slot
   with active investment** (TD-040 bounds pruning, zone maps, hierarchical
   stats, ADR-089's read-side fold). VIPER is a redundancy between two funded
   paths.

2. **No known production exposure.** Until #1743 (2026-08-27), VIPER's
   point-read was broken *for its own writer's output* — the writer emits
   `vector_fp32` as Arrow `FixedSizeList`, the reader demanded `ListArray`, so
   every point read of an engine-written file errored ("Missing or invalid
   'vector_fp32' column"). There are no known user reports of this failure,
   which is strong evidence of low exposure but not proof that no persisted
   VIPER collections exist. Retirement therefore remains migration-safe.

3. **No conformance ratchet, correctly capped.** `SUPPORTED_SURFACE.adoc`
   already caps VIPER at Beta with "no per-engine conformance ratchet published
   — do not market above Beta by name." Keeping it means building that ratchet
   and paying its debt (e.g., the hardcoded `FixedSizeList(Float32, 128)`
   factory schema filed via #1768) to justify a tier with no remaining niche.

4. **The maintenance tax is recurring and real.** VIPER is ungated and loops
   through every cross-engine surface: 7 test files, capabilities/compression
   tables, conversion maps, compaction, flush routing. Post-#1743, embedded
   flushes *genuinely* construct and write VIPER files where they previously
   (accidentally) wrote SST — activating previously-dead write paths. Every
   future routing/format sweep pays for a redundant engine (TD-DSEFF-1's
   program alone spent three items on VIPER).

HELIX and NOVA are explicitly **not** in scope: HELIX keeps its spatial-locality
story (and TD-HELIX-1 is open work, not debt), NOVA is the funded
columnar-analytics Beta. SWIFT/RAPTOR remain `experimental-engines`-gated
dead code, a separate future cleanup.

== Adversarial re-check (2026-08-29, before merge)

Re-examined the decision under active attempts to falsify it, given this is
architecturally significant. Two things surfaced that change the PR's scope
(both addressed in this same PR) — nothing surfaced that changes the decision:

* **`engine_capabilities.rs::is_feature_supported` marks `Quantization`,
  `FilterPushdown`, and `ColumnProjection` as VIPER-exclusive** — on its
  face, evidence VIPER has a real capability gap NOVA doesn't cover. Checked:
  this function has **zero callers anywhere in the codebase** outside its own
  declaration (a certified-dead-code pattern, not a routing/planning input),
  and it predates ADR-026's pivot, which already answers the underlying
  question at the architecture level — RaBitQ/SQ8 stacked quantization is a
  **PAX embedding-column feature applied via AXIS across engines**, not an
  engine-specific one (ADR-026 §"PAX across modalities"). The matrix is stale
  documentation debt, correctly subject to removal at stage 3, not evidence
  against retirement. NOVA's own `quantized_columns` write site
  (`nova/engine.rs`) currently constructs `Default::default()` rather than
  real quantized data at that call site — noted as a candidate follow-up
  (separate from this ADR; NOVA is not being deprecated).
* **The Python and Node.js embedded-client READMEs actively recommended
  VIPER** ("Use `sst` for real-time, `viper` for analytics") — customer-facing
  guidance this ADR's own SUPPORTED_SURFACE change would otherwise
  contradict. This is now fixed in the same PR (both READMEs point to `nova`
  for analytics/mixed workloads and flag `viper` as deprecated with a link to
  this ADR). Rust/Go SDKs carry no VIPER guidance and needed no change.

No niche, capability, or customer-facing justification for keeping VIPER
survived this pass. The decision stands.

A second pressure test immediately before merge (repo-wide grep for stray
references, empirical validation of the merged #1772 catalog-cache fix
against the pre-fix code, and a line-by-line re-read of this PR's diff)
found two more cosmetic-only issues, both fixed in the same commit: both
`warn!` deprecation messages in `factory.rs` had literal multi-space gaps
baked into the string content from an unescaped multi-line literal (garbled
log text, no functional effect), and a comment in
`discovery_job_republish_test.rs` did not match the then-proposed test loop.
Neither cosmetic defect affected the decision or its evidence; the subsequent
pass below superseded the proposed coverage removal itself.

A third adversarial pass found that removing VIPER from existing conformance
loops would violate the repository's conformance-ratchet rule, and that the
original stage-2 wording assigned "new versus existing collection" policy to
factory constructors that have no collection-lifecycle context. Both are
corrected below: existing coverage remains, new-selection rejection belongs at
the collection create/update boundary, and implementation removal requires a
verified empty persisted-VIPER inventory after migration.
== Decision

Retire VIPER in three stages, mirroring the Chrono/TST retirement pattern
(proto variant retained for wire compatibility; factory gates new use).

**Stage 1 — soft deprecate (this ADR, ships now):**
* `SUPPORTED_SURFACE.adoc`: VIPER moves to *Deprecated* — selectable per
  collection but discouraged; pointer here and to TD-VIPER-1.
* Both factory constructors emit a `warn!` deprecation notice naming ADR-093
  and the replacement guidance (SST default; NOVA for columnar-analytics
  vector; DataFusion path for analytics) on every VIPER construction.
* VIPER is removed from benchmark promotion sweeps, but remains in the
  existing *all-engines conformance loops* while it is selectable and while
  existing data is promised readable. This preserves the repository rule
  that conformance ratchets only go up. VIPER-specific tests also remain
  until stage 3.
* The TD-DSEFF-1 viper hardcoded-128 debt row is marked *subsumed*: retire,
  don't fix.

**Stage 2 — wire-compat retirement (gate: stage-1 soak + migration note):**
* Collection create/update validation rejects selecting VIPER for a NEW
  collection ("use SST, HELIX, or NOVA"). The context-free factory remains
  available to open and read existing VIPER collections.
* Existing VIPER collections remain readable while operators migrate them;
  migration is engine swap / re-ingest. Plain Parquet storage avoids file
  lock-in, but does not by itself replace the VIPER reader implementation.
* `StorageEngine::Viper` proto variant + string conversions are retained
  forever (wire compatibility; existing clients must keep parsing).

**Stage 3 — code removal (gate: stage-2 soak, zero telemetry signals, and a
verified empty persisted-VIPER inventory after migration):**
* Delete the engine module and its match-site references (~19 files per
  ADR-026's census), keeping the proto variant and conversion stubs.

== Consequences

* The vector portfolio converges on the funded story: SST (Supported,
  default) + NOVA (columnar-analytics Beta) + HELIX (spatial Beta), with
  AXIS+PAX as the shared read path per ADR-026.
* Benchmark promotion sweeps stop paying the VIPER tax in stage 1.
  Conformance and compatibility coverage remains until the implementation is
  removed in stage 3.
* No user-visible breakage at any stage: stage 1 is a warning, stage 2 blocks
  only NEW selections while old data stays readable, and stage 3 is forbidden
  until persisted VIPER inventory is empty after migration.
* Beta-tier documentation debt is retired rather than paid down: no new VIPER
  conformance ratchet will be built, while existing coverage is preserved.

== Alternatives considered

* **Keep as Beta + build the conformance ratchet** — rejected: funds a
  redundancy between SST and NOVA; no product evidence for a distinct
  quantized-Parquet vector story.
* **Retire NOVA instead** — rejected: NOVA has active investment
  (TD-040, ADR-089 integration). #1743 gave NOVA a real `vector_by_id`
  (previously a hardcoded `Ok(None)` stub) where VIPER's equivalent gap was
  never even noticed until routing was corrected — but an adversarial
  re-review of #1743 found NOVA's new implementation still lacks MVCC
  version resolution and tombstone filtering that VIPER's has (tracked
  separately, not a reason to retire NOVA — it's an active-development gap,
  not a structural one).
* **Retire all of VIPER/NOVA/HELIX now** — rejected: ADR-026's census says
  the blast radius is large; one engine at a time, evidence first.

== Amendment (2026-10-04): RAPTOR stage-3 executed under this ADR's pattern

The ADR's scope note ("SWIFT/RAPTOR remain `experimental-engines`-gated dead
code, a separate future cleanup") is executed for RAPTOR. Its baseline was
already stage-2-equivalent (compile-gated off by default, factory bail on
default builds, zero production configs, deprecated 2026-04-03), so stage 3
collapsed to the deletion:

- Removed: `src/storage/engines/raptor/` (7.7K), `crates/storage/
  proximadb-raptor-engine` (11.4K), `crates/storage/proximadb-raptor-common`
  (2.5K; audited — external consumers were raptor-only), the four factory
  dispatch arms + `create_raptor{,_async}` constructors (now CHRONO-style
  bails), the feature-gated progressive-search pipeline
  (`create_raptor_pipeline` + RAPTOR stage arm), the
  `RaptorFormatAdapter`/`create_raptor_adapter` surface, the
  `StorageEngineType::RAPTOR` extractor arm (SST fallback), and
  `tests/raptor_recall_test.rs`. `experimental-engines` now = `axis` only
  (SWIFT remains gated).
- Kept for wire compat: `StorageEngineType::Raptor` proto variant,
  `StorageEngine::Raptor` / `FormatType::Raptor` enum variants and their
  match arms (hybrid strategy → SST fallback with a warn).
- Fixed: `EXPERIMENTAL_ENGINES_STATUS.md` migration guide no longer
  recommends the (itself deprecated) VIPER.
- Removed ~21.6K LOC from the root build unit (decomposition
  build-economics goal) and the repo's highest fan-out file
  (`raptor/engine.rs`, fan-out 65 — codegraph audit 2026-10-04).
