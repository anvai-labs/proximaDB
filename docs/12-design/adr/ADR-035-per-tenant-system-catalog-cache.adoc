== Context

Object storage is the canonical authority for **all** data, including the system catalog. But resolving a collection's metadata on a cold cache costs **1 + N + M object-store round-trips** — `list_namespaces` + per-namespace `list_tables` + per-table `get_table` (e.g. ~111 GETs for 10 namespaces / 100 tables) in `CollectionService::collection_from_catalog_asset` / `list_collections_from_catalog` (`src/services/collection/manager.rs`). That dominates query latency for metadata-only work and is paid afresh after every pod restart (the in-memory `CatalogCache` is empty). For a cloud DB whose dominant cost term is I/O round-trips, this is the wrong bill to pay on the hot path.

We want metadata reads to be **snappy**: a tenant's catalog objects loaded once into a bounded per-tenant in-memory cache (≤1 MB/tenant, 5-min TTL, invalidated on schema change), backed by an on-disk warm tier hydrated at pod start so reads hit the **OS page cache** instead of object storage. The system catalog also needs a **per-tenant lifecycle** (a bare-minimum skeleton pre-created at signup; system-managed rows added as users create tables) and **special rules** (read-heavy, *system-writable-only*). Finally, because object **names are identical across tenants**, objects must be differentiated by a **global `u64` object_id** (ADR-031), not by name.

Already on `develop` (this ADR composes, it does not invent): `TenantCache` (byte-budgeted per-tenant LRU + TTL), `CorpusVersionRegistry` (per-`(tenant,collection)` monotonic version, durable-store trait), `CacheInvalidationCoordinator` (bumps the corpus version on every DDL/DML), `IdAllocator` + `CatalogTableSchema.object_id: Option<u64>` (ADR-031), and the durable `_metering` writer (TD-161, #407). The one gap for the id requirement: metadata objects are still **name-keyed** on disk (`metadata/tables/<ns>/<table>.json`).

This changes on-disk metadata addressing (object_id-keyed) and adds a warm-cache tier, so per the storage-format-migration mandate it needs this ADR, must be **mixed-read-safe**, and ships **default-OFF/additive** per slice.

== Decision

=== D1 — Two object-store groups (canonical authority, grouped by access pattern)
Under each tenant prefix (`data/{tenant}/…`, ADR-032/TD-CAT-2), split the system catalog by access pattern:

* **METADATA group — read-heavy, low-volume, cached.** The per-tenant registry (namespaces / tables / columns / indexes), **keyed by global `u64` object_id** (names collide across tenants): `…/_syscat/objects/{object_id}.json`, plus a small per-tenant `…/_syscat/index.json` mapping `name → object_id` (and `namespace → object_ids`) for name resolution and bulk hydrate.
* **OPERATIONAL group — write-heavy append, never cached for reads.** `_metering/`, `_trace/`, `_billing/`, log — coalesced SST/LSM append (TD-161). Distinct lifecycle (append/compact), distinct durability (always-on full-fidelity billing). Served by its own readers, never the metadata read cache.

=== D2 — 3-tier read path for metadata
`hot (in-memory, ≤1 MB/tenant, 5-min TTL) → warm (local disk, OS page cache) → canonical (object store)`. A `TenantSysCatCache` composes `TenantCache<CatalogMetadata>` (hot) over a `WarmDiskStore` (`CatalogMetadataStore` impl, JSON under `{cache_dir}/_syscat/{tenant}/{object_id}.json`) over the object-store catalog (canonical). Every cached entry carries a `stamped_corpus_version`; reads compare it to `CorpusVersionRegistry::current(tenant, name)` and drop on mismatch (stale-safe). The hot tier reuses `TenantCache` admission (over-ceiling ⇒ serve-but-don't-cache), so 1 MB/tenant is a hard ceiling, not a crash.

=== D3 — Provisioning lifecycle (signup → growth)
* **Signup** → `provision_tenant_system_catalog(tenant)` idempotently pre-creates the **bare-minimum skeleton**: the per-tenant `_syscat/index.json` (empty), the system registry namespace, and the operational sink roots (`_metering`/`_trace`/`_billing` markers). No user tables.
* **User DDL** → the *system* (not the tenant) allocates `oid = IdAllocator::allocate()`, writes `_syscat/objects/{oid}.json` (METADATA group), upserts `index.json[name]=oid`, then `CorpusVersionRegistry.bump(tenant, name)` and invalidates the cache. Tenants never write `_syscat/*` directly (ADR-032 D3 / reserved-segment rule).

=== D4 — Hydration triggers
* **pgwire** (the only true per-connection session): after `send_ready_for_query` (`src/network/postgres/protocol.rs`), spawn a **non-blocking** warm task for the session's tenant.
* **REST / gRPC / Flight** (stateless per-request): **lazy warm-on-first-miss** via `TenantCache::get_or_load`, which dedupes concurrent first-touches — no per-request hydration cost after the first.
* **Pod start**: lazy (warm-on-first-touch) by default for MVP; optional bounded eager prewarm of the K most-recently-active tenants into the warm tier.

== Decision tree (all branches)

[cols="1,4", options="header"]
|===
| Path | Branches

| READ `resolve(tenant,name)`
| (1) hot hit && version matches ⇒ return (0 I/O). (1b) hot hit && version mismatch ⇒ evict, go (2). (1c) hot miss / TTL-expired ⇒ go (2). (2) warm hit && version matches ⇒ promote to hot, return (OS page cache, no object GET). (2b) warm hit && mismatch, or warm miss ⇒ go (3). (3) canonical found ⇒ write-through warm+hot (hot admission-gated at 1 MB), stamp version, return. (3b) canonical not-found ⇒ return None (the authority's "Table not found"). (4) cache unwired ⇒ direct canonical read (today's behavior).

| WRITE (system, on user DDL)
| (1) skeleton present ⇒ allocate oid, write `_syscat/objects/{oid}.json`, upsert `index.json`. (1b) skeleton missing (defensive) ⇒ provision (repair), then write. (2) post-commit ⇒ invalidate (bumps corpus version) ⇒ hot version-mismatch drop + warm-file delete (no stale read, invariant #16b). (3) cross-tenant name collision ⇒ impossible (key is the global u64 oid).

| PROVISION (signup)
| Each step an idempotent upsert (re-signup ⇒ no-op; partial failure ⇒ safe retry, upserts converge). Never creates user tables.

| POD START
| Lazy warm-on-first-touch (default); optional eager prewarm bounded to K tenants. Warm tier stale vs object store (another pod wrote) ⇒ caught by version mismatch on read ⇒ reload (3).

| INVALIDATION
| Schema change ⇒ bump ⇒ lazy version-mismatch drop (hot) + warm-file delete. 5-min TTL = freshness ceiling regardless. Multi-pod: a process-local corpus version lets pod B serve up to TTL-stale unless `CorpusVersionRegistry` is backed by a **durable shared store** (TD-SC-5); the TTL already bounds staleness, so single-pod/per-pod is correct for MVP.
|===

== Consequences

*Positive.* Metadata-only queries drop from 1+N+M object GETs to 0 (hot) / 0-object (warm) after first touch; pod restarts re-warm from local disk (OS page cache) instead of object storage — snappy UI. Isolation stays structural (cache keyed by `tenant_id`, 1 MB hard ceiling per tenant). Global `u64` object_id keying makes cross-tenant name collisions impossible and gives a stable physical key for the metadata group. The operational/metadata split keeps write-heavy billing/trace off the read cache.

*Negative / cost.* A new cache tier + warm-disk store to maintain (bounded: 1 MB/tenant, 5-min TTL, LRU). The object_id re-keying (D1) is an on-disk format change (mixed-read-safe migration, TD-SC-3). Multi-pod tightening needs the shared version store (TD-SC-5). Local warm-disk consumes pod disk (bounded + LRU-evicted).

== Alternatives considered
* **Bigger global in-memory cache, no per-tenant bound.** Rejected: unbounded per-tenant blast radius; a noisy tenant evicts everyone. `TenantCache`'s per-tenant ceiling is the isolation primitive.
* **No warm disk tier (memory + object store only).** Rejected: pod restart pays the full 1+N+M cold cost on the first query for every tenant; the warm tier + OS page cache is the snappiness win the requirement calls for.
* **Keep name-keyed metadata objects.** Rejected: identical names across tenants can't be distinguished by a global physical key, blocking object_id-addressed reads and a clean per-tenant `_syscat` layout (the user requirement).
* **Eager full prewarm of all tenants at boot.** Rejected for MVP: unbounded boot I/O; lazy warm-on-touch + bounded K-tenant prewarm is cheaper and sufficient.

== Rollout (phased; one gated PR per slice, CLAUDE.md #7/#8)
. **TD-SC-1** — `TenantSysCatCache` hot tier (`TenantCache<CatalogMetadata>`, 1 MB ceiling, 5-min TTL) + corpus-version stamping + global OnceLock init (mirror `init_segment_caches`), fronting `CollectionService::collection()`. *Pure read accelerator; default-on; no format change.* (The immediate snappiness win; independent of the rest.)
. **TD-SC-2** — `WarmDiskStore` + pod-start hydration + pgwire session-ready warm hook + lazy warm-on-miss for the stateless edges.
. **TD-SC-3** — object_id-keyed metadata layout (`_syscat/objects/{oid}.json` + `index.json`); mixed-read-safe (name-keyed legacy fallback + marker + migration); completes ADR-031 O2 for catalog objects; depends on TD-CAT-2.
. **TD-SC-4** — `provision_tenant_system_catalog` at signup + system-only write guard for `_syscat/*`.
. **TD-SC-5** — durable shared `CorpusVersionStore` (object-store-backed) for cross-pod invalidation.

== Testing & gating
* Unit: each READ branch (hot-hit / stale-version-drop / warm-hit / cold-load / not-found / over-1MB-bypass) table-driven; provisioning idempotency; **object_id global-uniqueness across two tenants with identical table names**.
* Trace/bench (co-design mandate #2): a cold collection resolve emits 1+N+M object GETs **once**, then 0 (hot) / 0-object (warm) — asserted via the query-scoped I/O trace (ADR-030).
* E2E: pod restart ⇒ first query warms, second query 0 object GETs; `CREATE TABLE` bumps the version and the next read reflects the new schema (no stale read); two tenants' identically-named tables resolve to distinct object_ids.
* Gates: `cargo nextest run --lib --profile unit` green; clippy/fmt; tenant-path guard clean; ANN recall/ratchets unaffected.
