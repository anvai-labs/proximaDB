= ADR-0083: Consolidated catalog identity model — the composite (account, namespace, collection_id) is the SOLE canonical identity; retire the global u64

== Why this ADR exists

ProximaDB's catalog identity was fragmented (ADR-031/074/075/077/032/048) and,
worse, carried **two parallel identity systems** — a global `object_id` (`u64`)
*and* a composite `(account, namespace, collection)` — which is an
inconsistency seam. PR #1325 proved it: the embedded flush plan parsed
`Collection.id` as a `u64` while the field held a UUID, because the two systems
could disagree. This ADR collapses to **one identity system**.

== The hard constraint that decides it

The composite `(account_id, namespace_id, collection_id)` **cannot be
eliminated** — two non-negotiables force it to exist:

1. **Structural path isolation (mandate #1):** every object-store write is
   `data/{tenant}/{namespace}/{collection}/…`. The path *is* the composite; a
   bare `u64` cannot build a structurally-isolated path without a catalog
   lookup.
2. **Catalog-free engines (embedded):** they have no catalog to resolve
   `u64 → composite` and must carry the triple (ADR-031 Phase 4d already does,
   on `StorageAssignment`).

So the composite is **carried on the object regardless**. The question was never
"composite *or* u64" — the composite is forced. The question is whether the
`u64` earns its place alongside a composite that is already carried. It does not.

== Decision — the composite is the sole canonical identity

[cols="2,4", options="header"]
|===
| Identity | `CollectionIdentity { account_id: u32, namespace_id: u16, collection_id: u32 }` — immutable, globally unique via the triple, **self-describing** (the path is the identity's segments).
| Carried on | the typed triple on `StorageAssignment` (already there per ADR-031 4d); `Collection.id` (legacy string) is derived or deprecated.
| Drives | object-store path (directly — structural isolation by construction), name→id resolution at the catalog seam, WAL/memtable/admission/compaction keying.
| Global `object_id` u64 | **RETIRED as an identity.** Optionally retained as a global *ordering* sequence only; never a key.
| Display name | `CollectionConfig.name` — mutable, unique per `(account, namespace)`; never an identity.
|===

=== D1 — one identity, not two

The composite is the identity. There is no second stored identity. The catalog
mints the composite on every create (including embedded) — one mint, one
identity, no `object_id` to drift against it. This is the direct fix for the
#1325 class of bug: there is no longer a `Collection.id`-holds-X-while-the-
composite-holds-Y seam, because the composite is the only identity.

=== D2 — admission / scheduling / flush / compaction key on the composite

The hot path keys on the composite triple (a Rust tuple hashes/compares in a
handful of cycles). This is acceptable because the collection identity is keyed
*per write / per flush-batch / per query-route* — **not** on the genuinely hot
paths (distance computation, segment/cell lookup, cache), which key on
`SegmentId` / record-oid / offset. The `u64`-vs-composite performance gap is
therefore irrelevant for the collection identity (full analysis in the research
doc). Where a single integer is genuinely more convenient — lock-striping,
hash-map shard index — **derive a `u64` handle deterministically from the
composite** (a hash). It is a *non-stored, derived* handle, so it cannot drift.

=== D3 — self-describing: the path is the identity

Because the identity *is* the hierarchy, the object-store path is derivable
from the identity alone — no catalog lookup. This is strictly better than a
`u64` identity for catalog-free engines, recovery, and offline tooling (you
always know where an object's data lives from its identity). It also makes
isolation structural *by construction*: the identity is the isolation boundary.

=== D4 — scales down the hierarchy to columns/fields

The composite extends naturally: a column/field identity is
`(account, namespace, collection, field_id)` — self-describing all the way down
(Iceberg field-id style). A global `u64` would *lose* the lineage at the column
level (a column `u64` tells you nothing about its parent table without
metadata). For a multi-modal DB with a deep hierarchy, the composite is the
natural identity at every level.

=== D5 — resolution happens once, at the catalog seam

Name (`CollectionConfig.name`) → composite → path resolution happens **once**,
at the catalog boundary, authz-gated (ADR-074). Downstream paths receive the
resolved composite and never re-resolve from a string (ADR-077 applied to
identity).

== First-principles: why one identity, and why the composite

(Full pressure-test in the research doc; summary here.) The cross-system
invariant is that every serious storage engine separates an immutable internal
key from a mutable name. The open question was *one key or two*. Two keys
(ADR-031's `u64` + the composite) is an inconsistency seam (#1325). One key is
required — and because ProximaDB's constraints (structural path isolation +
catalog-free engines) **force the composite to be carried**, the composite is
the one key that costs nothing extra to carry. The `u64` is the redundant
second system; it is retired.

[cols="2,3,3", options="header"]
|===
| Choice | Verdict | Why
| Composite as sole identity (this ADR) | ✅ chosen | Forced to be carried anyway; self-describing; structurally isolating; one system; perf-irrelevant for the collection id; scales to columns.
| Global `u64` as sole identity | ✗ rejected | Cannot build structurally-isolated paths or serve catalog-free engines without carrying the composite alongside → back to two systems.
| Both (`u64` + composite) — ADR-031 / ADR-0083 rev1 | ✗ rejected | Two identity systems → drift seam (the #1325 bug).
|===

== Consequences

* **Reverses ADR-031's `object_id` u64-as-identity.** ADR-031's path-isolation
  intent survives (the composite carries it); its `u64`-as-physical-key decision
  is superseded. Migration: re-key flush plan / WAL / memtable / admission /
  compaction from `parse::<u64>()` to the composite triple. The composite types
  and `CatalogIdService` already exist — mechanical-but-wide, not greenfield.
  The #1325 flush plan stops parsing `Collection.id` as `u64` and keys on the
  composite (or the derived-hash handle).
* **`Collection.id` (proto)** ceases to be a numeric-identity field. The typed
  triple on `StorageAssignment` is the identity; the legacy string field is
  derived (e.g., the path-qualified form) or deprecated. Readers that
  `parse::<u64>()` `Collection.id` are migration debt to re-key on the
  composite.
* **No `object_id` column** in the catalog schema as an identity (a global
  ordering sequence may remain, separate from identity, if needed).
* **One identity system** — the consistency goal that motivated this ADR.

== Open items (not blocking)

* **Lock-striping / shard handle:** derive a `u64` from the composite (hash) —
  non-stored, so it cannot drift.
* **Global ordering:** if a system-wide creation order is ever needed, maintain
  a sequence separate from identity (not a key).
* **Namespace `u16` wrap (ADR-074 D4):** 65,536 namespaces/account is a hard
  cap, not a silent wrap — fence it. Tracked separately.

== Addendum: ABAC `tenant_stable_id` (TD-TENANT-1 item 3)

The ABAC layer keys enforcement on `tenant_stable_id: u64` (the binding filter
`b.tenant_stable_id == tenant_stable_id`; ABAC/ADR-075). This u64 is **the
ADR-0083 account u32 widened** — the composite's tenant component
(`{account(u32), namespace(u16), collection(u32)}`; Phase 5: tenant≡account).
The catalog does **not** mint a separate tenant u64.

Rationale: ADR-0083 retired the global u64-as-identity; a fresh `IdAllocator` u64
tenant space would reintroduce it. Reusing the account u32 (the existing durable
`account_registry`, with its sidecar + floor recovery) is ADR-consistent and
structurally guarantees binding consistency — there is exactly one minting
authority for the tenant u64, consumed by both the request path
(`TenantStableIdResolver`) and the (future) ABAC binding-provisioning path.

* `TenantStableIdResolver::stable_id_of(tenant)` returns `account_u32(tenant)
  as u64` (lookup-only, no mint).
* `None` (unminted / brief lock contention) ⇒ fail-closed deny — the id is an
optimization, never a second source of truth (ADR-075).
