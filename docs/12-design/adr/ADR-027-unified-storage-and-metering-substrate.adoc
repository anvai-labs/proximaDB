== Context

Three design threads converged and forced one answer:

. **A storage fork.** Today: *PAX* for the vector path (SST writes PAX when gated on), *Parquet* for the warehouse/relational path (DataFusion), *ProximaBlocks* legacy. Three formats, two readers, two SQL lowerings — a fork.
. **Trace + metering cost/fidelity.** `io_trace` must be cheap when off, yet some traces **drive billing** (KEU/KOU/KRU/KIU) and so can never be off and need full fidelity. And its write path is *write-heavy, small-record* (per-query meters) — exactly the small-files problem on object storage.
. **Where metering lands.** Every peer (Aurora, Neon, Turso, Supabase, CockroachDB Serverless) meters **externally** (platform/OTLP), not in DB system tables. ProximaDB's object-store-native + per-tenant-path model could do better (durable, tenant-owned metering) but must also speak the standard sink.

== Decision 1 — PAX is the single internal format

The SST/LSM **writes PAX for every modality** — vectors *and* relational *and* OLAP *and* the metering/trace segments — not only vectors. PAX becomes the one internal format the LSM produces and every engine consumes:

[NOTE]
====
**Target vs current state (audited 2026-06-25, see `PAX_SUBSTRATE_DESIGN_PLAN_2026_06_25.adoc`).**
This Decision is the *target*. Today `write_pax_segment` is **vector-specific**
(`segment_format.rs:113` — mandatory `embedding_count` + `VectorQuant`, `.max(1)` clamp);
the canonical columns (`oids`/timestamps/`edge_*`/`props_bytes`/`labels_bytes`) are already
modality-neutral, but there is **no typed user-column stripe** (relational payload lands in
opaque msgpack `props_bytes`, defeating columnar projection/pruning). Making the writer
modality-neutral + adding typed user-column stripes + the `RecordReader` trait is **TD-162a**.
This Decision must not start before ADR-027 is `Accepted` with the course-correction
reconciled (see "Reconciliation" below).
====

====
**Amendment (ADR-094, 2026-09-21) — three corrections to the note above.**

. **The gate is lifted.** This ADR is now `Accepted` as narrowed, so TD-162 may begin.
. **The audit note is stale on two facts.** (i) `write_pax_segment` does **not** hard-require
  embeddings: centroid accumulation early-returns on empty vectors
  (`proximadb-storage-common/src/pax_block.rs:1476-1478`) and coalesced-RaBitQ falls back to
  the legacy layout "rather than failing the flush" (`:1669-1671`); only an *empty segment*
  bails (`:1665-1667`). (ii) A typed user-column stripe now exists — ADR-055's P-Shred
  (`ColumnRole::UserDefined`, `block-format/src/writer.rs:1250`) — though it is currently a
  **duplicated** advisory index rather than authoritative; making it authoritative is
  TD-USUB-6.
. **Decision 1 is narrowed to _landing / LSM output_.** "PAX is the single internal format"
  is retained as the statement that the LSM emits one landing format per modality — not as a
  claim about which engine executes queries, and not as a claim that relational tables must
  land in `PBLK`. Per ADR-094, **format follows modality**: relational-only tables land in a
  Parquet-encoded Layer A carrying PAX layout discipline; vector/multimodal tables land in
  `PBLK`/`PXH1`.
====

* **One record reader** — `read_segment_records` → `PaxSegmentScanner` for all data (magic-detect router exists for PAX + legacy `ProximaBlocks`; the `RecordReader` trait + the Parquet `PAR1` arm are **new work**, TD-162a-3 / TD-162b).
* [.line-through]#**One SQL lowering** — relational SQL lowers to a PAX scan; the native OLAP engine's natural input is PAX columnar (DataFusion is interim, per the native-OLAP blueprint).#
+
**WITHDRAWN by ADR-094 (2026-09-21).** This clause is the *only* part of Decision 1 that
conflicted with ADR-033, and it was already settled against — without reference to either
document — by **ADR-052 invariant 1** (OLAP execution is vectorized-over-Arrow via
DataFusion; native Volcano is the OLTP/point-lookup floor) and **ADR-054** (operator plane,
ledger-gated). The native investment is a PAX **scan operator** feeding DataFusion, not a
replacement lowering. Withdrawing this row is what allows ADR-027 and ADR-033 to both be
`Accepted`.
* **One I/O-trace path** — TD-158's emission, one place, all data.
* **One quant/zone-map/prune stack** — PAX column stripes + zone maps + RaBitQ/SQ8 tiers serve ANN *and* relational projection/pruning uniformly.
* **Completes ADR-024** — the type unified to `ProximaRecord`; unifying the *format* to PAX closes the loop.

**Parquet stays at the interop seam, not the hot path**: external tools (Spark/DuckDB/Trino/Iceberg), federated/external tables, warehouse *export*. Read/written at the boundary via the format-agnostic router; never scanned in the internal query path. This is "vertical inside (PAX), standard outside (Parquet)" made concrete.

[IMPORTANT]
====
**Amended by ADR-094 (2026-09-21).** The clause "never scanned in the internal query path"
is withdrawn. ADR-033's survey established that Parquet is within ~2× of a custom format on
sequential scans *and* is the Iceberg seam, so for the **relational-only** arm it is the
correct landing format, not merely an export target — it is scanned internally, by
DataFusion, by design. Parquet remains "interop-only" for the **vector/multimodal** arm,
where the custom format's ~100× random-access advantage is decisive. The principle survives
in its precise form: *vertical where the access pattern pays for it, standard everywhere
else.*
====

**If a second internal format is ever needed, the router makes it safe** — `SegmentFormat::detect` is O(1) magic-byte (**today**: `PBLK` + legacy `0x01`; the `PAR1`/Parquet arm is **TD-162b**, default-off behind `datafusion-integration`); a `RecordReader` trait (PAX/Parquet/legacy each implement) — **new work, TD-162a-3** (it does not exist yet; `read_segment_records` is an inline `match` today) — decouples SQL lowering from on-disk layout; Arrow Flight serves *decoded records* (Arrow batches), so on-disk format is invisible to clients. No fork in the hot path; the fork (if any) is at the boundary where it is cheap and standard. Mixed-read-safe (mandate #8).

== Decision 2 — two trace/metering classes

[cols="2,4,4", options="header"]
|===
| | Billing meters (KEU/KOU/KRU/KIU) | Perf / geometry trace (GET-count, bytes/block, route)
| Can it be off? | **No** — the metering authority (SaaS billing) | **Yes** — zero-cost compile-time gate (feature/macro); off in normal mode
| Fidelity | **Full** — never sampled/dropped; per-tenant | Aggregated/sampled OK (drives the adaptive engine, TD-157/159)
| Encoding | u64 counters + int enums (compact) | u64 counters + int enums; route/engine = int enum, not `String`
|===

The compile-time gate (TD-160) applies to the **perf/geometry class only**. Billing is always-on but still cheap (compact ints).

[IMPORTANT]
====
**Billing authority is `consumption_metrics.rs`, NOT `IoTrace` (audited 2026-06-25).** The
two classes are *already structurally separate*: the billing meters — `KOU_BYTES_TOTAL`,
`KEU_UNITS_TOTAL`, `OBJECT_STORE_OPS_TOTAL` (`src/metrics/consumption_metrics.rs`) — are
per-tenant Prometheus counters that **do not live behind any gate**. The task-local `IoTrace`
(`src/observability/io_trace.rs`) is the **entire perf/geometry class**; its `egress_bytes`/
`embedding_*` fields are *derived copies* fed *from* the consumption recorders
(`record_kou_bytes`→`record_egress_bytes`; `record_keu_units`→`record_embedding`). Therefore
TD-160 gates **`IoTrace` wholesale** behind a new `io-trace` cargo feature (none exists today);
when off, every `record_*` free fn compiles to an `#[inline(always)]` no-op (call sites
unchanged — they already no-op outside a scope). Billing **cannot be silenced by the gate
because it does not live behind it**. *Do not* attempt to "split the IoTrace counters into
billing vs perf" — that would manufacture the entanglement the invariant forbids. A CI guard
asserts no `cfg(feature)` wraps any symbol in `consumption_metrics.rs`.
====

The per-query `route`/`compute_ms` `String` fields (perf class) become int enums
(`ShapeClass`/`EngineId`); add `route` to `IoTraceSnapshot` (omitted today).

== Decision 3 — coalesced write-path (reuse the SST/LSM; avoid small-files)

Both classes are write-heavy, small-record workloads (per-query meters/traces), the same shape as OLTP writes. Writing each to object storage = the small-files problem (per-PUT fee + read amplification + list cost). Aurora, Neon, and Turso all solve it the same way, and it is the primitive ProximaDB already runs:

* **Aurora** ("log is database") — redo-log stream to a storage fleet; **continuous log stream to S3**; never per-page writes.
* **Neon** (pageserver) — WAL → ~1 GiB **L0 layer file** → background **compaction merges L0 → larger L1** on S3.
* **Turso** (libSQL) — **WAL frames → S3** as the durable write path.

**Pattern:** append small records to an in-memory buffer → **threshold-flush a large immutable segment** → **background compaction merges small→large.** ProximaDB's SST/LSM (memtable → flush → PAX segment → compaction) IS this primitive, so the metering/trace writer (TD-161) and OLTP writes reuse it — no per-query object writes, no new machinery.

* **Billing = full fidelity, but batched** (N query-meters coalesced into one segment — batching preserves fidelity, not sampling).
* **Perf = may aggregate/sample** (a signal, not an invoice).

== Decision 4 — dual-sink metering (durable per-tenant + standard OTLP)

Peers meter **externally** (platform/OTLP); ProximaDB's object-store-native + per-tenant-path model is a **differentiator**: durable, **tenant-owned** metering in the tenant's own object-store path (auditable, no platform lock-in for the meter). Do **both**:

* **Durable per-tenant in object store** under `DrPathBuilder` — `data/{tenant}/_metering/billing/` (always-on, full-fidelity, PAX segments via the coalesced writer) + `data/{tenant}/_trace/perf/` (gateable). *The differentiator.*
* **External OTLP/Prometheus** → AnvaiOps billing pipeline + dashboards — *the industry-standard sink* (what peers do). NOTE (audited 2026-06-25): today this is the **pull-only** `/metrics/prometheus` endpoint (`src/network/metrics_service.rs:163`); a periodic **push** emitter (OTLP/pushgateway, ≈30s) **does not exist yet** and is **new work in TD-161** (mirror the `src/metrics/cache.rs:108` interval task / `MetricsPersistenceLayer` snapshot pattern).

== Storage layout (under DrPathBuilder — structural tenant isolation)

----
data/{tenant}/{namespace}/{collection}/...        # records (PAX, per ADR-026)
data/{tenant}/_metering/billing/                  # billing meters (PAX, always-on, full-fidelity)
data/{tenant}/_trace/perf/                        # perf/geometry trace (PAX, gateable, sampled ok)
----

All writes are `TenantContext`-stamped (isolation + billing attribution); all metering is a TAM surface priced downstream in AnvaiOps (OSS = mechanism).

== Rollout

. **TD-160** — compile-time gate for the **perf/geometry trace class only** (feature `io-trace`, default off → `record_*` no-op; billing class stays always-on). Prerequisite to wiring per-read trace at scale.
. **TD-158** — emit the perf/geometry trace on the live AXIS/SST read path (gateable; builds against this two-class spec).
. **TD-162a-1** — make the PAX writer **modality-neutral** (optional `embedding_count`/`quant`; 0-embedding segments skip the embedding stripe + AXIS indexing). *Prerequisite for TD-161* — the metering writer emits 0-embedding PAX segments. (audit-added sequencing)
. **TD-164** — `DrPathBuilder` per-tenant system paths (`tenant_root()`/`metering_subprefix()`/`trace_subprefix()`) + `validate_id` system-segment denylist. *Prerequisite for TD-161* (the durable sink has no path API today). (audit-added)
. **TD-161** — coalesced SST/LSM-backed metering/trace writer (threshold-flush 0-embedding PAX segments → compaction; dual-sink: durable per-tenant under `_metering`/`_trace` + **new** periodic OTLP push emitter). Billing full-fidelity-batched; perf sampled. **Deps: TD-162a-1, TD-160, TD-164.**
. **TD-162** — PAX as the single internal format: SST writes PAX for all modalities; unify the reader (`RecordReader` trait, TD-162a-3) + SQL lowering onto PAX; the typed user-column stripe (TD-162a-2) enables relational projection/pruning; Parquet demoted to the interop seam (`PAR1` arm = TD-162b). Phased with the native-OLAP engine. **Gov dep: this ADR `Accepted` + course-correction reconciled (above).**

== Non-goals

* **Not** removing Parquet from the codebase — it stays as the interop seam (federated/external/export) and the interim warehouse format until the native OLAP engine scans PAX.
* **Not** building the learned/RL tuning layer here — that is the future layer-3 ADR (needs TD-158 trace substrate + TD-159 geometry-aware adaptive engine + the recall ratchet as floor), per ADR-026.
* **Not** billing *pricing* — the per-tenant meters are the OSS mechanism; the $ rate card is AnvaiOps policy (open-core boundary).

== Consequences

* One internal format, one reader, one SQL lowering, one I/O-trace path — the storage fork collapses.
* Metering is durable, tenant-owned, auditable (differentiator) AND speaks the standard OTLP sink.
* The coalesced write-path means no per-query object writes anywhere (data or metering) — the small-files problem is solved once, for both.
* The recall ratchet (ADR-026) remains the safety floor under every quant/format change; no metering or format work may regress it.
