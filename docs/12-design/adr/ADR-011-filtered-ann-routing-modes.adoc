== Context

ADR-002 defines the normalized filter contract and candidate set abstraction for hybrid
scalar+ANN queries. It establishes that scalar filters must either be pushed into the ANN
index or tracked as residual predicates. What it does not define is *which routing strategy
to use* and *how to choose between them based on data statistics*.

Three routing strategies exist for ANN queries that carry scalar filter predicates:

[cols="1,2,2,2"]
|===
| Mode | Algorithm | Best when | Risk

| PreFilter
| Apply scalar filter first → ANN search over survivors
| Selectivity < 5 % (very few records pass filter)
| If survivors < ef_construction the ANN recall degrades; surviving set must be large enough for
  ef_construction to find ef_search candidates.

| Inline
| Interleave predicate evaluation during HNSW/IVF graph traversal (predicate-aware index)
| Selectivity 5 %–50 %
| Requires predicate-aware index support in AXIS; latency higher than PostFilter for dense graphs.

| PostFilter
| ANN over full corpus → oversample by factor F → scalar filter results
| Selectivity > 50 % (most records pass filter)
| Misses results when selectivity is lower than expected and oversample factor is too small.
|===

Without a catalog-declared routing policy, each query path makes an ad-hoc choice,
resulting in inconsistent recall and unpredictable latency.

Literature basis:

* FAVOR: Efficient Filter-Agnostic Vector ANNS Based on Selectivity-Aware Routing
  (arXiv:2605.07770, May 2026). Directly validates selectivity-driven routing and measures
  recall/latency tradeoffs per mode.
* Filtered Approximate Nearest Neighbor Search: System Survey and Taxonomy
  (arXiv:2602.11443, Feb 2026). Enumerates pre-filter, post-filter, and intra-filter
  (inline) strategy families with recall and throughput comparisons.
* Efficient Filtered-ANN via Learning-based Query Planning (arXiv:2602.17914, Feb 2026).
  Proposes learned routing between strategies; validates that selectivity is the dominant
  feature for plan selection.
* SIEVE: Effective Filtered Vector Search with Collection of Indexes (arXiv:2507.11907).
  Shows that no single strategy dominates; a collection of indexes per selectivity regime
  achieves Pareto-optimal recall/throughput.
* In-Place Updates of a Graph Index for Streaming ANN (arXiv:2502.13826, Feb 2025).
  Addresses HNSW update freshness, which interacts with PreFilter: a fresh HNSW is required
  for PreFilter recall to be reliable.

== Decision

The AXIS engine MUST support three routing modes for filtered vector search. Mode selection
MUST be driven by `estimated_selectivity` from `FilterDiagnostics` (ADR-004) and the
`AnnFilteringPolicy` catalog knob registered in `CatalogTableSchema`.

=== Routing Logic

[source,rust]
----
// Implemented in proximadb-catalog::AnnFilteringPolicy::routing_mode
pub fn routing_mode(&self, estimated_selectivity: f64) -> AnnFilteringMode {
    if let Some(forced) = self.force_mode { return forced; }
    if estimated_selectivity < self.pre_filter_threshold {   // default 0.05
        AnnFilteringMode::PreFilter
    } else if estimated_selectivity > self.post_filter_threshold { // default 0.50
        AnnFilteringMode::PostFilter
    } else {
        AnnFilteringMode::Inline
    }
}
----

Default thresholds are grounded in the FAVOR paper (arXiv:2605.07770):

* `pre_filter_threshold = 0.05` — fewer than 5 % of corpus records pass the filter
* `post_filter_threshold = 0.50` — more than 50 % of corpus records pass the filter

=== PreFilter Mode — Implementation Contract

[source,text]
----
1. Evaluate NormalizedFilterExpr against ProximaRecord PAX blocks or secondary indexes.
2. Build a CandidateSet bitmap of passing record positions.
3. If |CandidateSet| < ef_construction: degrade to Inline mode with a warning in EXPLAIN.
4. Execute HNSW/IVF search restricted to CandidateSet positions.
5. No residual predicate needed (filter was applied before ANN).
----

Minimum viable candidate size before degradation:

* For HNSW with ef_search = E: require |CandidateSet| ≥ max(E × 4, top_k × 10).
* If this minimum is not met, emit `ExecutionMode::Degraded` in the explain plan.

=== Inline Mode — Implementation Contract

[source,text]
----
1. AXIS HNSW/IVF traversal evaluates NormalizedFilterExpr on each candidate during graph walk.
2. Non-passing candidates are skipped and do not count toward ef_search quota.
3. Traversal continues until top_k passing candidates are found or graph is exhausted.
4. Residual predicate from ADR-002 is still applied on final results to catch
   any candidates where inline evaluation was approximate.
5. Emit filter statistics in ExplainOperator.hints: {passed_inline, skipped_inline, recall_estimate}.
----

Inline mode requires AXIS to expose a `predicate_fn: Option<&dyn Fn(RecordId) -> bool>`
parameter on HNSW search paths. This is the AXIS predicate-aware primitive already partially
implemented.

=== PostFilter Mode — Implementation Contract

[source,text]
----
1. ANN search over full corpus with top_k × oversample_factor candidates (default 2×).
   See AnnFilteringPolicy::effective_top_k_for_post_filter.
2. Apply NormalizedFilterExpr as residual predicate to ANN results.
3. Return up to top_k passing candidates.
4. If fewer than top_k candidates pass: emit ExecutionMode::Degraded and return all
   passing candidates with a recall warning in EXPLAIN.
----

=== EXPLAIN Surface

The routing mode selection MUST appear in `ExplainOperator.hints` (ADR-004):

[source,json]
----
{
  "ann_filtering_mode": "inline",
  "estimated_selectivity": 0.12,
  "selectivity_source": "catalog_stats",
  "oversample_factor": null,
  "pre_filter_threshold": 0.05,
  "post_filter_threshold": 0.50
}
----

When `force_mode` is set in the catalog policy:

[source,json]
----
{
  "ann_filtering_mode": "pre_filter",
  "forced_by_catalog_policy": true
}
----

=== Catalog Registration

`AnnFilteringPolicy` is stored in `CatalogTableSchema.ann_filtering_policy` and is
planner-visible. It is created with catalog defaults on `CREATE TABLE` / `CREATE COLLECTION`
and can be updated via `ALTER TABLE SET (ann_filtering = ...)`.

Default thresholds are appropriate for most workloads. Operators with domain-specific
selectivity distributions (e.g., very high cardinality tag filters) should tune thresholds
after running `ANALYZE`.

== Consequences

=== Positive

* Consistent routing behavior across all protocol surfaces (pgwire, REST, gRPC, Arrow Flight).
* Recall guarantees become explicit via EXPLAIN (know when `Degraded` before serving results).
* Catalog policy is tunable per table without code changes.
* FAVOR/SIEVE literature validates the threshold approach at production scale.

=== Constraints / Risks

* Inline mode requires predicate-aware HNSW — AXIS must expose a predicate callback on
  graph traversal. This is partially implemented; full coverage of `NormalizedFilterExpr`
  operators is required.
* Selectivity estimation is only as good as catalog statistics. Cold tables with no
  `ANALYZE` history default to 0.10 (Inline mode), which is conservative but safe.
* PostFilter oversample is a fixed factor; adaptive oversample (increasing factor when
  first pass misses top_k) is future work.
