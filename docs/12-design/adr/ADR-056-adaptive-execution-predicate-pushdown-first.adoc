== 1. Context + the question

The question on the table: *"Do we handle Adaptive Query Execution (AQE), and what can we learn from the open-source ecosystem (Spark, Trino, Impala, Hive, DuckDB, ClickHouse, Polars, Pandas) to implement with a first-principles + co-design lens — not micro-optimizations?"*

This ADR answers it with a **definite architectural position** (§5) grounded in a measured substrate inventory (§3) and a cited ecosystem survey (§4, §8). It is the companion to ADR-054 (the native operators) — ADR-054 builds the *operators*; this ADR decides how they *adapt* to real data at runtime.

== 2. The foundational insight — AQE is two schools, and the substrate dictates which fits

AQE is **not one technique**; it is two architectural schools, and which one fits ProximaDB is dictated by the execution substrate, not preference:

[cols="1,3,2",options="header"]
|===
| School | Adapts | Requires
| **Re-plan** (Spark AQE, SQL Server adaptive join, Oracle, Photon) | the *plan shape* mid-query (join algo, partition count, order, skew split) | **synchronous pipeline breakers** — you can only cheaply re-plan where the substrate already materializes
| **Predicate-pushdown** (Trino, Snowflake, F1, DuckDB v1.1, ClickHouse runtime filters, Polars) | *which data the scan reads* (files/partitions/rows), never the plan shape | a build-side whose stats can be pushed to a probe-side scan; **no barrier needed**
|===

**The pipeline-breaker theorem** (Graefe, *Encapsulation of Parallelism in the Volcano Query Processing System*, SIGMOD 1990 — the exchange operator; restated in the Photon AQE paper, Xue et al., PVLDB 17(12) 2024 §3.3; Trino docs explicit on it): *re-planning is cheap only where the execution substrate already materializes.* Spark gets the barrier **for free** from shuffle-disk (shuffles materialize for fault-tolerance); Trino's streaming exchange deliberately **trades re-planning away** to keep intermediates in-network (its one adaptive-replan feature, join reordering, is gated behind fault-tolerant mode, which materializes exchange data to spool). This is a dimensional trade along the **local-disk / network** axis — exactly the cost spine of the co-design mandate.

**The implication for ProximaDB:** the existence + placement of pipeline breakers is a *storage/network co-design decision*, not just a query-engine one. Where the architecture forces materialization (object-store writes, Iceberg manifest commits, spill, blocking operators), we get free re-plan hooks. Where we pipeline through (Arrow Flight, in-memory exchange), we must use the predicate-pushdown school. **ProximaDB's substrate (single-node/embedded-first, object-storage, morsel-pipelined) is streaming, not shuffle-materializing** → the predicate-pushdown school is the natural lead.

== 3. What we already have (the substrate inventory — verified in-code)

The survey surfaced a **stronger predicate-pushdown substrate than the question assumed**:

1. **TD-OLAP-3 dynamic runtime filters — default-ON, measured −10.9% TPC-DS total / ≈30–57% `bytes_read` on star joins** (measured per-query 29.9–56.7%; ledger: `docs/_internal/status/TPC_PERF_GATE_EVIDENCE_V6_2026_07_06.adoc`). `src/datafusion/proxima_scan_exec.rs`: the scan carries `dynamic_filters`, gated `runtime_filter_prune_enabled()` (env `PROXIMADB_DF_RUNTIME_FILTER_PRUNE`, default ON), applied via `split_pruned_by_runtime_filters` which **awaits the dynamic filter's `wait_complete()` with a 10s timeout**. **This `wait_complete()` rendezvous is exactly the intra-query sync barrier the re-plan school needs** — a free hook, default-ON, waiting to be exploited beyond filter-propagation.
2. **Bloom semi-join — now default-ON** (`PROXIMADB_DF_BLOOM_SEMIJOIN`, `object_store_parquet_reader.rs`; `.unwrap_or(true)`, promoted in **#784** = MVP-1/AQE-S1, opt out with `=0`). Load-bearing direction: bloom over the in-list/dimension keys; split keys tested against it. _(Was default-OFF when this ADR was filed; landed 2026-07-08.)_
3. **The lock-free inter-query learn loop.** `src/query/route_cost_model.rs`: `RouteCostModel` with `ArcSwap<RouteRecommendationTable>`; consult = one load + one HashMap get; `observe_by_label` debounces recompute every 64 obs. The score function is a **co-design cost model** — `per_mib_egress` weighted 25.0 (the dominant *bandwidth* term) sitting under `per_get`=20.0 *per ranged GET*, whose `round-trip ≫ egress ≫ read-bw(5.0) ≫ CPU(1.0)` ordering (the source's own `CostWeights` doc) makes the **I/O round-trip** the dominant cost term overall — a cardinality-free model, exactly ADR-052's cost spine.
4. **Per-block + per-row-group PAX zone maps** (`crates/storage/proximadb-block-format`: `ColumnMeta` min/max/null_count/distinct_hint/bloom; `ROW_GROUP_SIZE=8192`). `BlockZoneSource` abstracts zone-map access over full-object + ranged reads.
5. **TupleDomain-equivalent predicate types** (`format_splits.rs`: `ScalarPredicate`, `ColumnBounds`) + the translation layers (`predicate_pushdown.rs`, `physical_filter_translate.rs`).

**The gap:** no intra-query *plan-shape* re-optimization, no native stage/materialization abstraction (`engine.rs:execute_physical` builds one pull-pipeline and drains it). `JoinStrategy` is static/planning-time. **And that gap is the least-relevant school for us** (§4).

== 4. The ecosystem survey — first-principles convergence

Four research agents surveyed Spark+Trino, DuckDB+ClickHouse, Impala+Hive, Polars+Pandas. They **converged independently** on:

=== 4.1 Scan-avoidance is the dominant lever on object-storage (all four)
Runtime filters (bloom + min/max) are *the* adaptive technique worth keeping — because their *effect* is scan-avoidance (moves `bytes_scanned`/`egress`, ADR-052's cost spine). Everything else (join-strategy switch, skew split) is CPU/memory-side on **already-read data** — high-leverage on self-hosted/distributed, low on object-storage. *DuckDB v1.1 (Sept 2024) runtime filters are min/max, not bloom* (verified verbatim); they **compound with bloom** (min/max prunes "entire block outside range"; bloom prunes "key absent within range") — complementary, same scan-pushdown seam.

=== 4.2 Operator-internal adaptation > plan-shape rewriting for single-node
DuckDB, ClickHouse, AND Polars all do **operator-internal** adaptation (spill, memory redistribution, runtime filters), **not** plan-shape rewriting. **DuckDB does NOT do hash↔NLJ switching** (that's SQL Server); it picks the join algorithm at plan time. Spark AQE is the shuffle-centric outlier — its headline wins (coalesce, skew) are **distributed-shuffle problems that evaporate single-node**. Polars proves a thin adaptive surface (cardinality-driven strategy picks) + strong static pushdown is enough for single-node competitiveness.

=== 4.3 The MemoryPool must be unified (DuckDB TMM), not per-operator
DuckDB's *Saving Private Hash Join* (Kuiper et al., PVLDB 18(8) 2025): per-operator independent limits cause **OOM *or* over-spill**; one global budget with **observed (not estimated) cardinalities** + operator-side spill callbacks is the answer. **Avoid sort-merge as the spill fallback** — grace-hash (radix + spill, no re-sort) is the converged answer (ClickHouse displaced `partial_merge` with `grace_hash`; DuckDB PVLDB calls sort-merge "orders of magnitude slower"). Adaptive re-bucketing under skew bounds memory on heavy keys.

=== 4.4 The scan-avoidance stack (ClickHouse is the deepest reference)
ClickHouse composes **three orthogonal layers**, all cutting `bytes_read`: (a) **PREWHERE** (`optimize_move_to_prewhere`, default ON) — filter column-by-column, load the next column's granules only for rows that survived the previous filter (~3.5× less bytes); (b) **lazy materialization** (default ON, LIMIT ≤ 10) — defer fat SELECT columns past sort+LIMIT (1,576× on a Top-N case); (c) **byte-bound adaptive granularity** (10 MiB OR 8192 rows) — ties the pruning+parallelism unit to bytes. **PREWHERE maps directly onto PAX** (columnar within a block): filter cheap metadata columns first, defer fat vector columns — directly applicable to our vector+filter workload.

=== 4.5 What is NOT transferable (budget nowhere)
* **LLVM codegen** (Impala) — moves CPU at a per-query compile tax; Impala auto-disables it <50K rows/daemon (`DISABLE_CODEGEN_ROWS_THRESHOLD`). ADR-052 rules it out.
* **HDFS short-circuit reads / data locality** — no DataNode to bypass on S3/ADLS/GCS; *this is why the bytes-scanned-dominant thesis holds*. Budget nowhere.
* **Shuffle coalescing / skew-split** (Spark AQE a/c) — shuffle-centric by definition; meaningless without a native shuffle. Single-node/embedded-first → defer until/unless distributed (Ballista/MPP).
* **Runtime hash↔NLJ switching** — SQL Server feature; DuckDB/ClickHouse prefer operator-internal spill adaptation. Pick NLJ at plan time instead.

== 5. The decision — predicate-pushdown-first

**Commit to the predicate-pushdown school as the lead**, with a thin, targeted set of operator-internal adaptations, and **defer the full re-plan school** until a native stage abstraction + distributed execution exist. This matches (a) our streaming substrate (§2), (b) ADR-052's scan-avoidance thesis (§4.1), and (c) the single-node convergence (§4.2). The actionable set (full detail + sequence in link:../../10-quality/td/TD-AQE-1-adaptive-execution-roadmap.adoc[TD-AQE-1]):

**Tier 1 — high leverage, cheap, reuses existing seams:**
. **Promote bloom semi-join to default-ON** (MVP-1, TD-OLAP-3 completion). Correctness-neutral (no false negatives); qa-gate `bytes_read` ratchet verifies. **✅ Landed (#784, 2026-07-08).**
. **Surface `splits_pruned` + observed build cardinality into `CostQuantities`/`IoTrace`** (MVP-2) — the measurement substrate every AQE decision needs; composes with the existing debounced learn-loop, no new mechanism.
. **DuckDB-style build-min/max → probe scan** (MVP-3) — 2 scalars observed at the build pipeline-breaker (free), pushed through TD-OLAP-3's seam; complements bloom.
. **Exploit `wait_complete()` for build/probe swap + SMJ→BHJ** (MVP-4) — the barrier already exists; this is Spark-AQE-(b) for free.
. **Sort-on-materialize (TD-OLAP-6) framed as a runtime-filter force-multiplier** (MVP-5) — sorted data → tighter min/max → more blocks pruned (Trino's Hive docs state it explicitly; measured 0→19.2% TPC-DS).
. **PREWHERE at PAX-block granularity** (MVP-6) — filter cheap columns first, defer fat vector columns; the vector+filter win.

**Tier 2 — robustness/correctness (enabler):**
. **Unified `MemoryPool` (DuckDB TMM)** for TD-OLAP-11 — one global budget, observed cardinalities, operator spill callbacks.
. **Optimistic hash→grace_hash on memory threshold** — single HJ algorithm, graceful degrade; avoid sort-merge fallback.

**Tier 3 — deferred (gated on substrate we don't have):**
. Full Spark-AQE re-plan loop (stage abstraction, `QueryStage` event loop — Photon PVLDB 2024 is the blueprint).
. Skew-split (only earns its keep with a native shuffle + multi-worker; Snowflake file-stealing is the apt reference when we do).
. Shuffle coalescing (meaningless without a native shuffle).

== 6. Design directives (binding)

1. **`HashJoinBuild`/`HashJoinProbe` (TD-OLAP-11, #779) MUST be an explicit materialization boundary from day one** — not an in-memory handoff. This preserves the future re-plan option (Tier 3) *without paying for it now* (the OnceLock handoff already is a barrier; declare it the stage boundary). Amends ADR-054 §5. **✅ Satisfied by #779** (`src/query/execution/native_join_ops.rs`): `HashJoinBuildOperator::is_blocking()==true` fully collects + `concat_batches` the build side, freezes it into an `Arc<JoinHashTable>`, and publishes via `Arc<OnceLock<…>>`; the probe gates on `table_slot.get()` ("join probe ran before build published"). The boundary is explicit but **in-memory only (Phase 3.0 — no spill yet)**; the spill gap is closed by Tier 2 (AQE-S7 MemoryPool + AQE-S8 grace-hash).
2. **Cache-composition fix (invariant 16b/16c interaction):** adaptive plans are data-dependent — the same SQL can yield different plans across runs. The plan cache must become **plan-shape-aware** (key on plan, not SQL) or **bypass for adaptive plans**. Model: the existing Strong-bypass (`query_result_cache.rs:freshness_eligible`) — an "AQE-bypass" gate.
3. **The runtime-filter wait-time becomes a configurable dial** (Impala `RUNTIME_FILTER_WAIT_TIME_MS` — effective default 1000 ms / 1 s; the query option itself defaults to `0` = inherit the impalad `--runtime_filter_wait_time_ms` startup flag, which is 1000 ms; time-zero rule, graceful late-arrival) — our hardcoded 10s has no knob. On object-storage the wait is *more* favorable than HDFS (each skipped ranged GET = round-trip + egress $), so default short + emit the dial's value into IoTrace so the router learns per-workload.
4. **"Observed not estimated" is the rule** for MemoryPool/spill decisions — our Parquet regime has weak stats, exactly the case DuckDB designed the TMM for.

== 7. Citation corrections (folded in from the survey)

* The "Kaloilidis runtime-filter-injection-in-Impala paper" does not exist under that name (web + academic search find no such author/paper — a hallucinated citation; do not use it). The correct modern academic citation is **Yang et al., *Predicate Transfer: Efficient Pre-Filtering on Multi-Join Queries*, CIDR 2024** (3.1× on average over Bloom join on TPC-H — *not* "3.3×"; the "~19× join-input reduction" figure is unverified and dropped), plus the published follow-up **Qiao et al., *Robust Predicate Transfer with Dynamic Execution*, PVLDB 19(6):1278–1290, 2026** (published — not a "VLDB '26 preprint").
* **Hive's Calcite-based CBO explores both left-deep AND bushy join trees and *favors bushy plans*** (Apache Hive CBO wiki: "the current model favors bushy plans … and is execution-engine agnostic" — chosen for parallelism / smaller intermediates). An earlier draft asserted a phased "Phase 1 left-deep only, Phase 2 bushy" scheme; **no such phasing is documented — corrected here.** Hive is therefore a *bushy-plan* precedent, not a left-deep one.
* **DuckDB v1.1 runtime filters are min/max, not bloom** (verified verbatim against the v1.1 announcement).
* **DuckDB does NOT do hash↔NLJ adaptive switching** (that is SQL Server's batch-mode adaptive join).

== 9. Why this, not the alternatives

* *Not "build full Spark-AQE now"* — needs a stage/materialization abstraction we don't have, and three of its four features (coalesce/skew/broadcast-switch) are shuffle-centric (irrelevant single-node). The one that transfers (runtime bloom = SPARK-32268) is already TD-OLAP-3.
* *Not "build LLVM codegen"* — CPU-side tax; ADR-052 rules it out; the vectorized-over-Arrow seam gets the CPU win without it.
* *Not "operator-internal-only"* — predicate-pushdown to the scan is the higher-leverage half (bytes-scanned), and we already have the seam; operator-internal (MemoryPool/grace-hash) is the robustness enabler, not the lead.

The predicate-pushdown-first bet is the **co-design-correct** one: it leads with the adaptation that moves the dominant cloud cost term, reuses the substrate we already built, and preserves the re-plan option via the join materialization boundary — at minimum mechanism cost.
