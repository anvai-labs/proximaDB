= ADR-060: Commercial Rust crate extension seam (open-core)

:status: Accepted (seam + rules + placement = Option A)
:date: 2026-07-12
:deciders: architecture
:supersedes: none — amends `docs/12-design/OSS_ENTERPRISE_BOUNDARY_2026_06_17.adoc` §1 (adds a 4th sanctioned seam)

== Status
**Accepted** for the seam + its four non-negotiable rules (§3) **and the placement decision (§5 = Option A, a separate commercial Rust workspace, decided 2026-07-12)**.

Applied by link:ADR-084-oss-commercial-placement-worm-and-distribution.adoc[ADR-084] (2026-07-30) to WORM/compliance and multi-node distribution placement; TD-OSS-1 (tenant mechanism/policy audit) Done.

== Context

`OSS_ENTERPRISE_BOUNDARY_2026_06_17.adoc` is the governing OSS↔enterprise spec. Its principle — *"OSS ships capability + mechanism; the enterprise layer supplies commercial policy, data, authority, go-to-market"* — is unchanged and endorsed here. It sanctions **three** commercial-extension seams:

1. **Feature gates** — commercial *surfaces* are `#[cfg(feature=...)]`, OFF by default.
2. **Ports & Adapters** — OSS defines a port (trait/fn); the control plane supplies the adapter as operator config (JSON/TOML) + request claims (`TenantContext.tier`).
3. **Neutral naming** — no commercial tier/SKU names in OSS public types.

The spec then closes with: *"No cross-language Rust plugin (anvaiops is TS/Python)."* That constraint was a **consequence** of the chosen control plane (`anvaiops` = TS/Python), **not** a fundamental rule. Several commercial concerns — tier→cost multiplier resolution, billing *compute* (not just data), enterprise RBAC *policy* evaluation, quota-capping logic — are *type-bound* to OSS value types (`TenantContext`, the cost-model score, the `TierPolicy` shape) and are awkward to express through a config/claim string seam or a TS/Python FFI. A Rust↔Rust extension gets full type safety, zero-copy access to the same value types, and reuses the OSS crates directly.

The decomposition now in flight (extracting clean OSS crates — `proximadb-tenant`, `proximadb-storage-ports`, the engines, etc.) produces **stable, semver-able public crate APIs**. That creates the substrate a commercial Rust extension can depend on without forking or coupling to root-internal module paths.

== Decision

Sanction a **fourth seam: commercial Rust crates that depend on OSS crates** (open-core), providing commercial *policy/compute* that benefits from type-bound Rust integration. This **amends** `OSS_ENTERPRISE_BOUNDARY_2026_06_17.adoc` §1's seam list.

Definition — a commercial Rust crate:
- **Depends on** OSS `proximadb-*` crates (commercial → OSS). It is *never* a dependency of the OSS workspace.
- Supplies commercial *policy/values/compute* — **not** mechanism. The mechanism stays OSS (per the spec's principle).
- Is **not loaded by the OSS engine at runtime.** The OSS build is unchanged and standalone. The commercial crate is consumed by a commercial binary/service (or the `anvaiops` sidecar), not linked into the OSS engine.

This is the standard **open-core** shape. It is complementary to (not a replacement for) the existing three seams and the `anvaiops` TS/Python control plane.

== Non-negotiable rules (the boundary, restated + extended)

1. **Dependency direction: commercial → OSS only.** A commercial crate may `use proximadb_tenant::TenantContext`. The OSS workspace **never** depends on a commercial crate. The existing `check_oss_boundary.py` CI guard (§5 of the spec) is **extended** to also assert the OSS workspace's dependency graph has **no edge into any commercial crate** (by name/glob), failing the build otherwise.
2. **OSS standalone.** The OSS tree compiles + runs with zero commercial code (Apache-2.0). This is the license + community guarantee; the commercial Rust seam does not weaken it because the commercial crates live *outside* the OSS build.
3. **Neutral naming in OSS.** OSS public types/APIs carry no commercial tier/SKU names (the spec's existing rule — see `StoragePoolClass` remediation). Commercial names live **only** in commercial crates. Commercial crates may freely use commercial naming; OSS cannot.
4. **Stable public API surface.** Commercial crates depend on the **public** API of OSS crates (not root-internal module paths). The decomposition is the means by which those public APIs exist + stay semver-stable. A breaking change to an OSS crate's public API is a coordinated event (the commercial crate bumps in lockstep), same as any external consumer.

== Placement — DECISION: Option A (2026-07-12)

Commercial Rust crates live in a **separate commercial Rust workspace** that depends on the OSS `proximadb-*` crates from outside. The OSS repo (`proximadb`) stays a pure, single-license Apache-2.0 artifact with zero commercial code or dependency edges.

[cols="1,3,1",options="header"]
|===
| Option | Shape | Status
| **A. Separate commercial Rust workspace/repo** ✓ CHOSEN | A commercial workspace (e.g. `proximadb-enterprise-rs`, or a Rust workspace within `anvaiops`) that depends on OSS crates via git/path/private-registry deps. | **DECISION** — cleanest license + distribution separation; OSS repo pure Apache-2.0; commercial release cycle independent; the commercial→OSS direction is structural (a separate workspace cannot be a dependency of the OSS one).
| B. Feature-gated `commercial/` crates in this repo | crates under `commercial/`, behind a `commercial` feature, excluded from the OSS build + the boundary guard's OSS scope. | Rejected — commercial code in the OSS repo blurs license/distro + risks boundary drift.
| C. Hybrid | In-repo feature-gated + separate repo. | Rejected — two mechanisms to maintain.
|===

**Concrete shape (Option A):**

* **Location:** a sibling commercial Rust workspace. Two viable homes — (a) a dedicated `proximadb-enterprise-rs` repo, or (b) a `rust/` (or `engine-extensions/`) workspace *within* `anvaiops` (the existing commercial repo at `../anvaiops`). Recommend (b) initially — co-locates with the commercial control plane + avoids a brand-new repo — promoting to a dedicated repo if the Rust surface grows.
* **Dependency on OSS:** each commercial crate depends on the **published public API** of OSS crates via git deps pinned to a rev/tag (`proximadb-tenant = { git = ".../proximaDB", tag = "..." }`), a private registry, or path deps in a monorepo checkout. Never root-internal module paths (rule 4).
* **Initial commercial crates** (the type-bound policy/compute the OSS config/claim seam can't express well):
  **`proximadb-enterprise-tenant-policy`** — tier→cost-multiplier **values**, paid-tier **quota caps**, enterprise **RBAC policy** (permission→tier mapping); implements the OSS `set_tier_multiplier_resolver` / `LimitsResolver` / RBAC ports with commercial policy.
  **`proximadb-enterprise-billing`** — billing **compute** (applies the per-`(cloud, kou_locality)` KOU $ rate, NST premium, the GCP/azure add-ons to the OSS `proximadb_kou_bytes_total` meter); implements the OSS `MeteringSink`/meter port.
* **Build:** the commercial workspace builds standalone against the OSS crates; the OSS workspace is unchanged + has no knowledge of it. The `check_oss_boundary.py` guard asserts the OSS workspace has no edge into any `proximadb-enterprise-*` crate + that the OSS workspace builds without them present.
* **Versioning:** OSS crate public-API breaking changes are a coordinated bump (the commercial workspace updates its git-dep pin in lockstep), same as any external consumer. The decomposition's stable crate APIs (§7) are the contract.

== Application: the tenant layer (resolves the "move tenant to anvaiops?" question)

This ADR resolves the earlier question directly — **do not move `proximadb-tenant` to `anvaiops`** (anvaiops is TS/Python; it cannot host a Rust foundation crate the engine links against, and `TenantContext` is OSS *mechanism*). Instead, split by mechanism-vs-policy:

[cols="2,3,1",options="header"]
|===
| Layer | Contents | Home
| **`proximadb-tenant` (OSS, mechanism)** | `TenantContext`, `UnifiedUserContext`/`RbacTenantContext`, `UnifiedPermission`/`UnifiedAuthMethod` (authN/authZ *identity mechanism* — per the spec §2 Security), generic tier hooks/ports, `TierPolicy` parser, `tenant_tier_types` (generic). **Neutral-named.** | OSS, stays in this repo
| **Commercial Rust crate (policy)** | tier→cost-**multiplier values**, billing **compute**, paid-tier **quota caps**, enterprise **RBAC policy** (permission→tier mapping, commercial-gated permission grants), pricing-model code. Depends on `proximadb-tenant` + the OSS cost-model ports. | Commercial (Option A/B/C per §5)
| **`anvaiops` (TS/Python, control plane)** | orchestration, provisioning, UX, the billing *data/stores*, go-to-market. Consumes the commercial Rust crate where type-safe policy is needed (or calls it as a service). | `anvaiops` repo (unchanged)
|===

So PR #901 (RBAC identity types → `proximadb-tenant`) is **directionally correct**: those are authN/authZ *mechanism* (OSS). The commercial *policy* (which permissions map to paid tiers) is the new commercial Rust crate, layered on top. A follow-up **TD audits `proximadb-tenant`'s contents against this split** + flags any non-neutral names (e.g. commercial variant names in `UnifiedPermission`'s 40 variants) for the neutral-rename remediation.

== Relationship to `anvaiops` + the other seams

- **`anvaiops` stays the control plane.** Commercial Rust crates (this seam) handle *type-bound policy/compute*; anvaiops handles orchestration/UX/billing-data/go-to-market. Complementary, not competing.
- This seam **does not remove** the config/claim adapter seam (seam #2) — operators who don't license the commercial crate still configure behavior via `tier-config.json` + claims. The commercial Rust crate is the *type-safe* path for licensed deployments; the config seam is the *universal* path.
- Feature gates (seam #1) still apply to any commercial *surface* that must ship inside the OSS binary (rare under Option A).

== Synergy with the root-crate decomposition

The decomposition (extracting clean OSS crates — `proximadb-tenant`, `proximadb-storage-ports`, the engine-port-traits, the engines) is **what makes this seam viable**: it produces the stable public crate APIs a commercial Rust crate depends on. The two efforts are synergistic — every OSS crate extracted is a potential dependency target for commercial extensions. Decomposition is no longer "just" a build-RSS/OOM play; it's also the **open-core contract surface**.

== Enforcement

Extend the CI boundary guard (`check_oss_boundary.py`, wired in `.github/workflows/layering-check.yml`):
- Assert the OSS workspace dependency graph has **no edge into any commercial crate** (fail otherwise).
- Assert the OSS workspace builds with **no commercial crate present** (the standalone guarantee).
- Existing rules unchanged (neutral naming, feature-gate OFF defaults, no commercial content in non-gated OSS).

== Consequences

*Positive:* type-safe commercial extension without TS/Python FFI; OSS stays clean/standalone/Apache-2.0; the decomposition gets a concrete consumer rationale (the open-core contract surface); a clear answer to "where does commercial policy live" (on top, not inside).
*Negative:* OSS crate public APIs must be treated as a stable contract (breaking changes coordinate with commercial consumers); a placement decision is still owed (§5); the boundary guard must cover a new dimension (no OSS→commercial edge).
*Neutral:* this is an additive seam — it changes no existing OSS code, only sanctions a new commercial extension pattern + tightens the guard.
