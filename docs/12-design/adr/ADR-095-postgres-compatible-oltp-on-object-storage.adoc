== 1. The ask

Serve **PostgreSQL-compatible OLTP**, at least the SQL and transaction semantics an application
or ORM depends on, with data on **object storage**. The write-ahead log may live on a
**network-attached durable volume** (AWS EBS / EFS, Azure Premium SSD / Azure Files, GCP
Persistent Disk / Hyperdisk / Filestore). That volume outlives the compute instance and can be
**reattached to a replacement machine**, which recovers and resumes serving.

**Correction (2026-10-16, found while implementing TD-PGOLTP-1).** Two rows above describe the
*collection* WAL (`disk_manager`, `SyncMode`, `batch_sync_coordinator`). Relational pgwire writes
never touch it. They go to **one shared framed log**, `<data_dir>/pgwire/canonical-records.wal`
(`FramedTableWalAppender`), which wrote one frame per operation, so a torn write could persist a
prefix of a single multi-row INSERT. D3 is therefore implemented as a **group frame in that log**
(TD-PGOLTP-1 premise correction). `BatchSyncCoordinator` has no production caller.

**Reading:** the storage spine (WAL → memtable → PAX/Parquet on object store, LSN-tracked
truncation) is in place. What is missing is the **transaction layer on top of it**: atomic commit,
snapshots, row-level concurrency, integrity enforced in the same atomic unit, and a WAL that can
**move between machines without split-brain**.

| Replicated nodes; failover promotes a replica

| Stock Postgres WAL on an attached volume
| Instances; Multigres (Vitess-style) is alpha. OrioleDB (undo log, no VACUUM) targets production in 2026.
| Compatibility is "stock Postgres", so it inherits everything. OrioleDB's undo-log design is a reference for avoiding VACUUM-style bloat in our MVCC.

| **Snowflake Postgres / pg_lake** (ex-Crunchy)

=== 3.1 The design space, reduced

There are three ways to make a commit durable while compute stays replaceable:

. **Quorum log service** (Aurora, Neon, HorizonDB, AlloyDB): lowest RPO across AZs, but it is a
  distributed storage system to build and operate. TD-LTAP-3 already rejected it, and ADR-084 D2
  puts multi-node coordination in the commercial layer.
. **Commit = object-store PUT** (today's object-store WAL, SlateDB, WarpStream): durable across AZs
  with nothing to operate, but each commit costs one PUT round trip (tens of ms on S3 Standard).
  Batch ingest can amortise that. Per-transaction OLTP cannot.
. **Commit = fsync on a durable network volume** (classic RDS; this ask): sub-ms to low-ms
  commits, durable within the volume's replication domain, and recovery by reattach. The cloud
  runs the replication; we only have to guarantee **one writer at a time**.

**ProximaDB takes (3) for the WAL tail and (2) for everything else.** The volume holds only the
uncheckpointed WAL. The object store holds the base data, checkpoints, the catalog, and archived
WAL segments. That keeps the volume small, which makes it cheap and fast to move and bounds
replay time. It is still the same engine and the same WAL code. The volume is a *placement* of the
existing ADR-069 local WAL root, not a new subsystem.

=== D1 — One durable volume root holds every piece of state not yet in object storage

A new `[oltp.durable_volume] root` (env override `PROXIMADB_OLTP_DURABLE_VOLUME`) is the single
local path that must survive compute loss. It contains the record WAL, the system-catalog WAL, the
key-constraint log (folded in by D3), the checkpoint LSN and the epoch fence file. **Everything else
on local disk is cache** and must rebuild from object storage. The invariant is: _durable = on the
volume or in object storage; anything else is a cache._ The boot path enforces it by refusing to
start (fail closed) when a durable role (`RootRole::{WalLocalDir, WalWriteBuffer, Metadata}`)
resolves outside the volume root while the volume is configured. The existing `root_plan` /
`durable_locations` machinery already enumerates these roles, so this is a new check over an
existing list, not new plumbing.

Supported volume classes, and what each gives:

[cols="2,2,2,3", options="header"]
|===
| Volume | Replication domain (RPO 0 within) | Hardware fence | Notes

| AWS EBS gp3 / io2 (single-attach)
| One AZ
| Single attach is exclusive (the cloud refuses a second attach)
| Default recommendation. io2 Block Express gives sub-ms fsync.

| AWS EBS io2 Multi-Attach
| One AZ
| **NVMe reservations** (register / acquire / preempt)
| For hot-standby takeover without a detach. The new owner *preempts* the old reservation.

| Azure Premium SSD v2 / Ultra
| One zone (LRS)
| Single attach; shared disks use SCSI persistent reservations
| Lowest latency on Azure.

| Azure Premium SSD **ZRS**
| **Three zones, synchronous**
| As above
| Cross-zone RPO 0 with no extra machinery. Check per-region availability.

| GCP regional PD / Hyperdisk Balanced HA
| **Two zones, synchronous**
| Single writer attach; force-attach for failover
| Cross-zone RPO 0.

| AWS EFS / Azure Files / Filestore (NFS)
| Region (EFS)
| **None.** NFS locks are leases
| Allowed, but fsync costs several ms and the **object-store epoch (D2) is the only fence**. Suits a low commit rate.
|===

Volume sizing is set by the ADR-069 D6 WAL budget (the uncheckpointed tail), not by data size.

=== D2 — Exactly one writer, enforced by an epoch at two layers

1. **Object-store epoch (authoritative; works for every volume class).** At boot the server
   appends a **create-only successor slot** `_control/{deployment_id}/writer/v{n}.manifest`
   (epoch = n + 1) via `ManifestCommitter::commit_fenced`. Create-only (`If-None-Match: *` on S3,
   the equivalents on Azure/GCS, `O_EXCL` on `file://`) is the one conditional write that is
   atomic on every backend. An If-Match update of a single `writer.json` (this ADR's first draft)
   cannot be done on `file://`. Losing the race is fatal: the process exits and never serves.
   *(Implemented, TD-PGOLTP-2 S2.)* The epoch is then stamped into *(S3, open)*:
   * every WAL segment header and commit record on the volume. This is a **new** `writer_epoch`
     field. The existing `precision_epoch` in `proximadb-wal-segment-header` is the
     quantization-policy epoch and is unrelated: do not reuse it;
   * every manifest/head commit, which **rejects a lower epoch** as part of its existing CAS
     (`ManifestCommitter`);
   * every object-store data key or metadata, via the existing `RecoveryToken.epoch` (ADR-063).
2. **Volume fence (defence in depth).** The new writer writes `epoch.fence` on the volume and
   fsyncs it before replay. A writer that later reads a higher epoch in that file stops acking.
   Where the platform offers a hardware fence (single-attach, NVMe reservations, SCSI PR), the
   orchestrator uses it, so a zombie's I/O fails with `EIO` before it can acknowledge anything.

The zombie case drives this design. The old process may survive a network partition, lose its
volume, and keep running. As built (TD-PGOLTP-2 S2), the pgwire WAL refuses appends once the
process's **ownership lease** lapses. The lease is renewed only by a successful epoch check and is
timed on the monotonic clock, so a partitioned, stalled or paused owner stops acknowledging within
one lease. A new owner waits out that lease before opening the WAL. On single-attach volumes the
cloud additionally fails the old owner's I/O. **Not yet fenced (S3):** flush, compaction, spill,
the collection WAL and catalog writes, and manifest publication. Stamping the epoch into manifest
commits so that a lower epoch is rejected is the open S3 slice. The same-host `flock` lease stays
in place unchanged.

*Who moves the volume:* the orchestrator. In Kubernetes that is a StatefulSet pod with a
ReadWriteOnce PVC, which the CSI driver reattaches on reschedule. Otherwise it is the commercial
operator (ADR-084 D2). The engine's contract is narrow: **win the epoch, replay, serve; never serve
without the epoch.** No consensus code is added to the OSS engine.

=== D3 — A transaction is one WAL commit record; acknowledge after a group-commit fsync

* At COMMIT, the transaction's write set (record puts, tombstones, unique/PK/FK key claims,
  sequence advances, and catalog mutations once D7 lands) is encoded as **one framed, CRC-checked
  WAL batch** carrying `{txn_id, commit_lsn, epoch}`. This replaces the per-statement replay. A
  torn tail fails its CRC and is discarded on recovery, so **a transaction is either entirely
  present or entirely absent**.
* **Group commit:** concurrent COMMITs coalesce into one `write + fsync`. This uses the
  `batch_sync_coordinator` pattern with a small `commit_delay` (Postgres semantics, default 0).
  A COMMIT is acknowledged only after the fsync covering its record returns.
* **Durability ladder:** `synchronous_commit = on` (default for pgwire OLTP tables) maps to
  `SyncMode::Always` with group commit. `off` maps to `PerBatch` / `Periodic`: an explicit, opt-in
  risk of losing the last few ms, never a silent default. Bulk-ingest paths keep `PerBatch`.
* **Key-constraint log folded in:** PK/UNIQUE/FK claims stop going to the separate
  `oltp-cks.wal` and become entries in the same commit record. Two logs cannot be atomic with each
  other. This is what lets `oltp-integrity` become **default ON** for relational tables.
* **Autocommit statements** take the same path as a one-statement transaction. There is only one
  write path.

=== D4 — Snapshot = commit LSN; MVCC in the memtable; row-level locks

* **Versioning:** the memtable keeps a short **version chain per primary key**, tagged with
  `commit_lsn` (and a tombstone flag), instead of overwriting in place. Flushed PAX/Parquet
  segments are immutable and carry their max LSN. ADR-046's LSN-coherent merge read is the read
  rule: `visible(v, snap) = v.commit_lsn ≤ snap` and the newest such version wins. That is the
  mandate #16 merge read with a snapshot bound added.
* **READ COMMITTED** (the default, as in Postgres): each statement reads at the latest committed
  LSN.
* **REPEATABLE READ** (snapshot isolation): the snapshot is taken at the transaction's first
  statement. On commit, **first-committer-wins**: if any key in the write set has a version newer
  than the snapshot, fail with `40001` (`could not serialize access`), as Postgres RR does.
* **SERIALIZABLE:** stays fail-closed until an SSI design is filed. We do not silently downgrade.
  CockroachDB-style "serializable only, retry everything" is an explicit anti-goal.
* **Read-your-own-writes:** the session's uncommitted write set is overlaid on reads. This closes
  the P2.D "store-only reads" divergence.
* **Row locks:** UPDATE/DELETE/`SELECT … FOR UPDATE|SHARE [NOWAIT|SKIP LOCKED]` take
  `(table, pk)` key locks in an in-memory lock table held to end of transaction, with deadlock
  detection by wait-for-graph timeout (`40P01`). The table-level DML lock is kept **only** for DDL
  and bulk writes. This is the change that takes write concurrency from "one writer per table" to
  "one writer per row".
* **Version GC:** a version older than the oldest active snapshot is pruned at flush, so no
  VACUUM is exposed to users. Long-running snapshots are bounded by a configured
  `max_snapshot_age` (the OrioleDB / undo-log lesson: bloat must have a hard bound).

=== D5 — Point and range access without scans

* **PK index:** the memtable `BTreeMap` (already the scan index) is the in-memory index.
  Flushed segments get a per-segment PK range in the catalog-resident serving metadata
  (ADR-094 Layer B) plus a bloom filter, so a cold point read is one ranged GET. Composite PKs
  are included (closes TD-DML-2).
* **Secondary indexes:** `CREATE INDEX` on relational tables becomes an LSM **index table**
  (`index_key → pk`), maintained inside the same commit record (D3), so the index is never stale
  against its base. The planner uses it for equality and range predicates under a selectivity
  threshold. Otherwise the scan stays on the existing route.

=== D6 — Checkpoints bound recovery; the archive gives PITR and cross-AZ restore

* **Checkpoint** = flush memtable versions to object-store segments, commit the manifest (with
  epoch), then record `checkpoint_lsn` on the volume. WAL before `checkpoint_lsn` may be truncated
  only after the manifest commit is durable. That is the existing TD-USUB-1 truncation obligation,
  unchanged.
* **Recovery time objective:** `RTO ≈ reattach (cloud, ~30–60 s) + epoch CAS (one round trip) +
  replay(WAL tail)`. The tail is capped by the WAL budget, so replay time is bounded by
  configuration rather than by data size. The gate (TD-PGOLTP-2) **measures** RTO; this ADR does
  not assert a number (mandate #6).
* **Archive:** sealed WAL segments are shipped asynchronously to
  `data/{tenant}/{ns}/_wal_archive/{epoch}/{lsn_range}` under `DrPathBuilder`, metered as KSU.
  This enables:
  ** **PITR / branching** (TD-LTAP-4, TD-116), restoring at an LSN;
  ** **loss of the volume's AZ:** restore from base + archive on a fresh volume. RPO equals the
     archive lag (configurable; target ≤ 1 s for OLTP tables). On Azure ZRS or GCP regional
     disks, the RPO is 0 without the archive;
  ** **read replicas** that tail the archive. These are later work, and ADR-084 places them in
     the commercial layer.

=== D7 — Transactional DDL and savepoints (after D3/D4)

* Catalog mutations are written as entries in the same commit record, so `BEGIN; CREATE TABLE …;
  INSERT …; ROLLBACK;` leaves nothing behind. This is the PG behaviour ORMs' migration runners
  rely on.
* **Savepoints** are write-set marks: `ROLLBACK TO` truncates the write set and releases key locks
  taken after the mark. No storage change is needed, because the write set is not durable before
  COMMIT.

=== D8 — PG compatibility is declared in levels and gated by ratchets

ProximaDB declares compatibility by level, as DSQL does, rather than claiming "Postgres-compatible"
without qualification:

| **PG-OLTP-1** (this ADR)

| Test-only until TD-OLTP-WIRING-1 wired it, and it is still default-OFF.

| TD-USUB-1 spill store
| —
| Dead code until #1945. Wiring it surfaced a vacuously-true safety comment.
|===

About 9,200 lines of transaction code exist, and the pgwire `COMMIT` path uses none of them. It
replays statements one at a time. Code that is not on the request path is not tested by the
request path, so its assumptions (here, a multi-participant 2PC model) drift from what the
product needs: a single-writer, single-log atomic commit. Building a fourth system in isolation
would repeat this.

**Rules:**

. **One new crate, pure logic only:** `crates/storage/proximadb-txn-core`. It holds the
  `TxnCommit` record codec, the snapshot/visibility rule, the key-lock table, the group-commit
  queue and the epoch-fence state machine. Its I/O goes through **ports** (`WalAppender`,
  `DurableSync`, `EpochStore`), so it can be property-tested and deterministically simulated
  (crash at every await point) **without** the server. That is where isolation helps: the logic
  gets tested hard in isolation.
. **Wiring lands in the same PR as the logic, every slice.** Each slice is reachable from pgwire
  behind `[oltp]` flags, and each slice adds a TD-PGOLTP-6 ratchet row exercised through pgwire on
  the server binary. No slice merges without a production caller.
. **Do not revive the three existing transaction subsystems.** They solve a different problem
  (cross-engine 2PC). They may be mined for parts, for example the isolation-level enum
  (`proximadb-storage-common/src/transaction_isolation.rs`), with a premise check before any
  reuse. Their retirement is tracked (TD-PGOLTP-10) so a fifth system does not appear.

== 6. Consequences

* **Positive:** a defensible "Postgres-compatible OLTP" claim at a declared level. One WAL and one
  write path. A small, cheap, fast-to-move volume. Object storage stays the source of truth, so
  OLAP (DataFusion) and vector routes read the same data with no CDC copy, which avoids Lakebase's
  two-copy bridge and pg_lake's non-ACID seam.
* **Negative / cost:** single-writer throughput is capped by one node. Memtable version chains
  raise memory per hot key, bounded by `max_snapshot_age`. Group commit adds a small latency floor
  under low concurrency. On AWS, cross-AZ RPO is the archive lag, not 0, unless a quorum
  (TD-LTAP-3, commercial) is added later.
* **Format:** the commit record is a WAL **format change**. Per mandate #8 it is mixed-read-safe:
  a new record kind behind a version byte, legacy batches still replay, and it ships behind
  `[oltp] atomic_commit = false` until the TD-PGOLTP-6 ratchet is green, then flips under the
  pre-GA directive.
* **Docs:** `SUPPORTED_SURFACE.adoc` keeps "PostgreSQL-style OLTP parity" under Experimental until
  PG-OLTP-1 is green. ADR-018 P3.B points here.

== 7. Alternatives considered

* **Become a Postgres extension / fork (OrioleDB, pg_lake).** Rejected again, for the reasons in the
  lakehouse-PG study §8: the Table-AM TID constraint blocks the vector and columnar arms, and it
  would introduce a second engine.
* **Commit = object-store PUT for OLTP.** Rejected for per-transaction latency. Still the right
  answer for batch ingest, which keeps it.
* **Quorum WAL (Safekeeper-style).** Deferred (TD-LTAP-3, ADR-084 D2). Cloud-replicated volumes
  give the same within-domain durability with zero code.
* **Keep the whole database on the volume (classic RDS).** Rejected: it loses object-storage
  economics and separation from the OLAP/vector readers, and makes the volume large and slow to
  move.
* **Optimistic-only concurrency (DSQL).** Rejected as the default: Postgres applications expect
  blocking row locks and `FOR UPDATE`. OCC appears only as RR's first-committer-wins check.
