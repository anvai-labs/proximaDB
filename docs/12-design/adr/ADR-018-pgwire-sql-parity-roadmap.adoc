== v0.2 Release Status

**Beta — basic DML and vector-distance syntax only.** ADR-018 Phase 1 (basic DML, DROP TABLE IF
EXISTS, vector-distance operators) is wired. Phase 2 (SQLite parity — `ORDER BY` semantics,
`COUNT/SUM/GROUP BY`, joins, `xcatalog.namespaces`, `pg_class`) and Phase 3 (Postgres parity) are
**out of scope for v0.2** and must not be claimed as supported. See
link:../../SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`] "Experimental in v0.2" and
link:../../_internal/status/MVP_RELEASE_READINESS_RECONCILIATION_2026_05_28.adoc[MVP Release
Readiness Reconciliation — 2026-05-28].

2026-06-04 refinement: this ADR tracks SQL/pgwire surface parity. PostgreSQL-style storage and
transaction semantics require the TD-110 foundation first: xCatalog constraint metadata, WAL plus
native row/delta commit, primary-key/unique/check/foreign-key enforcement, MVCC visibility,
Volcano strong-freshness execution, DataFusion snapshot-plus-delta reads, and distributed
consistency gates.

2026-07-15 safety amendment: until the transaction gates in Phase 2/3 pass, pgwire is explicitly
autocommit-only. All transaction-control statements return SQLSTATE `0A000`. In the simple-query
protocol, a batch containing transaction control is rejected before any statement executes. This
supersedes the earlier Phase 1 no-op command-tag posture, which allowed clients to infer atomicity
that the storage layer could not provide.

== Context

The pgwire surface (`src/network/postgres/`) is currently sufficient
for ProximaDB's vector-search-via-SQL story but is **not** sufficient
to host metadata/system tables (tenant tier, DR policies, RBAC,
audit log, billing) or to be addressed by standard ORMs (SQLx,
Diesel, Prisma, Django, SQLAlchemy, Hibernate).

A live probe against the running server in 2026-05-25 confirmed the
gap. The probe found:

* **Silent transaction bug** — `BEGIN; INSERT ...; COMMIT;` returned
  "OK" with the INSERT silently dropped, because pgwire only matched
  the first keyword and the multi-statement string was never split.
  Fixed in commit ac969aa12.
* **Server crashes on:** `SELECT COUNT(*)`, `SELECT SUM(...)`,
  `GROUP BY`, any `JOIN`, `xcatalog.namespaces`, `pg_class`.
  Connections close without an error — clients with auto-reconnect
  silently mask the bug.
* **`ORDER BY` parsed but ignored** — silent semantic drop.
* **`INSERT INTO t VALUES (...)` without column list rejected** —
  "Column count (0) doesn't match value count (2)".
* **`information_schema.tables`** returns the ProximaDB-extended
  shape (9 columns) instead of the standard 4-column shape that
  ORM probes expect.

Three target audiences pull on this surface:

* **Engine team**, who wants to store DR / tenant / RBAC / audit
  metadata in OLTP-backed tables rather than dedicated collections.
  Blocked by the silent-transaction bug and the crashers above.
* **Self-hosters** running their own application stack against
  ProximaDB. They need at minimum SQLite-parity to write applications.
* **AnvaiOps** (and any future managed-service operator) wiring
  their billing/control-plane onto ProximaDB OLTP tables.

This ADR is the multi-phase plan. It commits to specific feature
sets per phase, names the gating tests, and gives realistic effort
estimates so engineering scheduling has a real anchor.

== Decision

**Three phases, in order. Each phase has a hard test gate; later
phases can begin only when earlier-phase tests pass.**

* **Phase 1: MVP unblock.** Stop today's footguns so storing
  metadata in OLTP tables is *safe*. Goal: no silent data loss, no
  unexpected disconnects, every supported feature behaves as
  documented. ~1–2 weeks.
* **Phase 2: SQLite-parity.** Enough SQL surface that a simple
  ORM (SQLx, Diesel) can connect, run migrations, do typical CRUD.
  ~3–4 weeks.
* **Phase 3: Postgres-parity.** Real PostgreSQL query/protocol semantics — full `pg_catalog`,
  CTEs, window functions, sequences, and ORM-compatible metadata. MVCC transactions, foreign keys
  with referential actions, and constraint enforcement depend on the TD-110 OLTP/HTAP storage
  foundation and cannot be claimed from parser/protocol work alone. ~4–6 weeks for the SQL-surface
  portion, plus the TD-110 storage work for true PostgreSQL-style OLTP claims.

**Total to Postgres-parity: ~3 months of focused engineering** for
one or two senior engineers. SQLite-parity alone is roughly one
month. There is no defensible shortcut — every ORM probes
`pg_class` on connect; every migration tool walks
`information_schema`; every multi-statement workflow assumes
transactions are real.

== Phase 2 — SQLite-parity (ORM viability)

Goal: a simple ORM (SQLx, Diesel) can connect to ProximaDB, run
its built-in migration helper, and do typical CRUD without
special-casing.

=== Wire protocol fidelity (P2.A)

* **Extended Query Protocol**: `Parse` / `Bind` / `Describe` /
  `Execute` / `Sync` flow with prepared statements and parameter
  binding (`$1`, `$2`). Today only Simple Query works.
  - `src/network/postgres/extended.rs` (new)
  - Effort: 3–5d
* **Result OID returns** on INSERT (`InsertOid` in
  CommandComplete). Today returns `INSERT 0 N`; some clients
  parse the oid.
  - Effort: 1d
* **`SHOW` commands** with real semantics (`SHOW search_path`,
  `SHOW server_version_num`, etc.). Today most are hard-coded
  literals.
  - Effort: 1d

=== Catalog introspection (P2.B)

Minimum surface ORMs probe on connect:

* `pg_class` (relations) — relation_id, relname, relkind, relnatts
* `pg_attribute` (columns) — attname, atttypid, attnotnull, attnum,
  atthasdef, attlen
* `pg_namespace` (schemas) — nspname, nspowner
* `pg_type` (types) — typname, oid (need to seed common types:
  int4, int8, text, bool, float4, float8, timestamptz, jsonb, etc.)
* `pg_index` — at least empty / schema-correct
* `pg_constraint` — at least empty / schema-correct
* `information_schema.{tables, columns, key_column_usage,
  referential_constraints, schemata}` — standard column shapes

Lives in `src/services/catalog_introspection.rs` extended. Effort:
5–7d total.

=== SQL feature surface (P2.C)

Beyond Phase 1, ORMs require:

* `JOIN` (INNER, LEFT, RIGHT, CROSS — no full-outer needed for
  SQLite-parity)
* Aggregates: `COUNT(col)`, `SUM`, `AVG`, `MIN`, `MAX`
* `GROUP BY` + `HAVING`
* `DISTINCT`
* Subqueries in `WHERE` (`x IN (SELECT ...)`, `EXISTS (...)`)
* `LIMIT n OFFSET m`
* `ORDER BY a, b NULLS LAST` (multi-column, NULLS handling)
* `ALTER TABLE`: `ADD COLUMN`, `DROP COLUMN`, `RENAME COLUMN`,
  `RENAME TO`
* `CREATE INDEX` / `DROP INDEX`
* `CREATE SCHEMA` / `DROP SCHEMA` (minimum: `public` always exists)
* Sequences: `CREATE SEQUENCE`, `nextval()`, `currval()`,
  `SERIAL` / `BIGSERIAL` column type
* `DEFAULT` clause, `NOT NULL`, `UNIQUE` constraints
* `CHECK` constraints (parsing-level; enforcement optional)
* Foreign keys (declaration; referential-action enforcement is P3)

Implementation: needs a real relational query planner, not the
current keyword-match dispatch. The natural home is
`crates/query/proximadb-query/` with a new `pgwire-relational`
module that:

1. Parses via `sqlparser-rs` (already a workspace dep).
2. Lowers to an algebra tree (`Scan`, `Filter`, `Project`,
   `Sort`, `Join`, `Aggregate`, `Distinct`, `Limit`).
3. Plans against the existing `xcatalog_*` tables + new sequence
   support.
4. Executes via either the existing `DmlService` (for DML) or a
   new relational executor (for SELECT with JOIN/GROUP BY).

Effort: 10–15d for the planner + executor + integration with
existing DML path.

=== Real transactions (P2.D)

* Per-session transaction state machine.
* Write-buffer with deferred commit (in-memory until COMMIT).
* `ROLLBACK` discards the buffer.
* Statement timeout (`SET statement_timeout`).
* Read-only transactions (`SET TRANSACTION READ ONLY`).
* No savepoints yet (deferred to P3).
* Isolation level: default to `READ COMMITTED` (autocommit-per-
  statement semantics still — real MVCC is P3).

Effort: 5–7d.

=== Type system (P2.E)

Minimum types most ORMs require:

* INTEGER family: `INT`, `INTEGER`, `BIGINT`, `SMALLINT`
* `TEXT`, `VARCHAR(n)`, `CHAR(n)`
* `BOOLEAN`
* `REAL`, `FLOAT`, `DOUBLE PRECISION`, `NUMERIC(p, s)`
* `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ`
* `JSON`, `JSONB`
* `BYTEA`

Effort: 3–5d (includes wire-format binary encoders).

=== Functions (P2.F)

Common minimum:

* Math: `abs`, `round`, `floor`, `ceil`, `power`, `sqrt`
* String: `length`, `lower`, `upper`, `trim`, `substring`, `||`,
  `concat`
* Date/time: `now()`, `current_timestamp`, `date_trunc`,
  `extract(field FROM ts)`
* Conditional: `CASE WHEN ... THEN ... ELSE ... END`, `COALESCE`,
  `NULLIF`
* JSON: `->`, `->>`, `jsonb_extract_path` (partially done by the
  translator today)

Effort: 5–7d.

**Phase 2 exit gate**:
- Diesel + SQLx integration tests pass against a live ProximaDB
  server.
- A new `tests/pgwire_orm_compat.rs` runs SQLx's standard test
  suite against ProximaDB.
- DR / tenant_tier / audit metadata tables created via DDL,
  populated via INSERT, queried by ORM, results match.

**Cumulative effort: ~4–6 weeks beyond Phase 1.**

== Phase 3 — Postgres-parity (real ORM use)

Goal: SQLAlchemy / Django / Prisma / Hibernate / TypeORM / etc. can
run real applications against ProximaDB as if it were PostgreSQL.

=== Full pg_catalog surface (P3.A)

* `pg_proc` (functions)
* `pg_operator` (operators)
* `pg_database`
* `pg_authid` / `pg_roles` / `pg_user`
* `pg_depend` (object dependencies — Django migrations probe this)
* `pg_description` (comments)
* `pg_partition` (if we ship partitioning)
* `pg_statistic` / `pg_stats` (planner statistics)
* `pg_settings` (server settings)
* `pg_locks` / `pg_stat_activity` (concurrency views)

All as queryable system views over the existing engine catalog.
Effort: 7–10d.

=== Real MVCC transactions (P3.B)

* Per-policy transaction snapshot.
* Isolation: `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`.
* Savepoints: `SAVEPOINT name`, `ROLLBACK TO name`, `RELEASE name`.
* Two-phase commit (`PREPARE TRANSACTION`, `COMMIT PREPARED`) —
  optional, ship behind a feature flag.
* Locking: row-level locks for `SELECT FOR UPDATE`,
  `SELECT FOR SHARE`, advisory locks (`pg_advisory_lock`).

This requires real MVCC support at the storage layer. Likely
implemented by extending PAX block format with row visibility
metadata + a per-transaction snapshot manager.

Effort: 15–20d (storage-layer integration is the big cost).

=== Advanced SQL (P3.C)

* CTEs: `WITH cte AS (...) SELECT ...`, including `RECURSIVE`.
* Window functions: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `NTILE`,
  `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE`, `SUM/AVG OVER ()`,
  `PARTITION BY`, `ORDER BY` within window.
* Subqueries everywhere: `SELECT`, `FROM`, `WHERE`, `HAVING`.
* `UNION` / `INTERSECT` / `EXCEPT` (+ `ALL` variants).
* Set returning functions: `generate_series`, `unnest`.
* Lateral joins: `JOIN LATERAL`, `CROSS JOIN LATERAL`.
* Arrays: literal `'{1,2,3}'`, `ARRAY[1,2,3]`, indexing `arr[1]`,
  `unnest`, `ANY`, `ALL`.
* `RETURNING` clause on INSERT/UPDATE/DELETE.
* `INSERT ... ON CONFLICT DO UPDATE / DO NOTHING` (UPSERT).
* `MERGE` (Postgres 15+).

Effort: 15–20d (CTEs + window functions are the biggest pieces).

=== Foreign keys with referential actions (P3.D)

* Declaration: `REFERENCES other_table(col) ON DELETE CASCADE
  / SET NULL / RESTRICT / NO ACTION`.
* Enforcement at INSERT/UPDATE/DELETE time.
* `DEFERRABLE` / `INITIALLY DEFERRED` constraints (deferred to
  end-of-transaction).

Effort: 5–7d.

=== Type system completeness (P3.E)

* `UUID` (with `gen_random_uuid()`)
* `INET` / `CIDR` / `MACADDR`
* `INTERVAL`
* `ARRAY` types fully (any base type + multi-dimensional)
* Enumerated types (`CREATE TYPE name AS ENUM ('a', 'b', 'c')`)
* Composite types (`CREATE TYPE name AS (a INT, b TEXT)`)
* `XML` type (parse + serialize, no XPath)
* Range types (`int4range`, `tsrange`, etc.) — optional

Effort: 5–7d.

=== Sequences (P3.F)

* `CREATE SEQUENCE` with `START WITH`, `INCREMENT BY`, `MINVALUE`,
  `MAXVALUE`, `CYCLE`.
* `nextval()`, `currval()`, `setval()`.
* `SERIAL` / `BIGSERIAL` / `IDENTITY` columns.
* Sequence ownership tied to column lifecycle.

Effort: 3–5d.

=== Triggers + procedures (P3.G)

* `CREATE TRIGGER ... BEFORE/AFTER INSERT/UPDATE/DELETE`.
* `CREATE FUNCTION ... RETURNS ... LANGUAGE SQL` (SQL-only
  functions; plpgsql is out of scope).
* `EXECUTE FUNCTION` for trigger-attached procedures.

Optional for Postgres-parity but commonly used. Effort: 5–7d (SQL
functions only — plpgsql is a separate multi-month effort).

=== Wire protocol completeness (P3.H)

* `COPY FROM STDIN` / `COPY TO STDOUT` real implementation (today's
  is a stub).
* `LISTEN` / `NOTIFY` (optional — most ORMs don't need it).
* SSL / TLS native pgwire negotiation.
* SCRAM-SHA-256 authentication (today is cleartext-only).
* Connection pooling-friendly: pgwire flow respects `Sync` boundaries
  cleanly under pgBouncer transaction-pool mode.

Effort: 7–10d.

**Phase 3 exit gate**:
- SQLAlchemy ORM tutorial passes against ProximaDB unchanged.
- Django sample app's test suite passes.
- Prisma `db push` migration runs cleanly.
- pgBouncer (transaction pool mode) in front of ProximaDB does
  not break clients.
- A representative TPC-C-like workload runs without crashes.

**Cumulative effort: ~4–6 weeks beyond Phase 2.**

== Amendment 2026-09-10: P2.D DELIVERED (TD-076)

Phase 2.D (real transactions) is implemented exactly as specified here, with the
following concrete semantics and honestly-documented divergences:

* `BEGIN` / `START TRANSACTION` / `COMMIT` / `END` / `ROLLBACK` / `ABORT` execute for real
  over both wire protocols. `SET TRANSACTION READ ONLY|WRITE` and `SET statement_timeout`
  are honored (timeout enforced on COMMIT replay via 57014).
* **Write buffer**: DML inside an explicit transaction accumulates in a bounded per-connection
  buffer (10k statements / 8 MiB; exceeding = 54000 + the transaction aborts). The
  primary-pod and tenant-visibility gates run at BUFFER time. COMMIT drains sequentially.
* **Documented divergences** (until P3.B MVCC): reads are store-only (a transaction does not
  see its own uncommitted writes); a mid-COMMIT replay failure leaves already-replayed
  statements durable and fails the transaction; the connection-drop = implicit-rollback
  guarantee holds because the buffer is in-memory.
* **Still fail-closed with reasons**: SAVEPOINT / RELEASE / ROLLBACK TO (Phase 3 savepoints),
  PREPARE/COMMIT/ROLLBACK PREPARED (no 2PC), SET CONSTRAINTS, AND CHAIN, and any transaction
  mode we cannot honor (SERIALIZABLE / REPEATABLE READ — only READ COMMITTED is provided).
* **DDL inside a transaction is rejected** (0A000): the buffer is DML-only — executing DDL
  immediately would make ROLLBACK silently not undo it.
* Any ERROR inside an active transaction fails it (25P02 until ROLLBACK), enforced centrally
  in the protocol error path so every statement path behaves identically.

== Sequencing rules

1. **Phase 1 must ship before any metadata-in-OLTP work proceeds.**
   The silent-transaction bug is a data-loss footgun; everything
   else is a stability and correctness gap that masks bugs from
   clients.
2. **Phase 2's catalog introspection (P2.B) gates ORM connection
   tests.** Without `pg_class` + `pg_attribute`, every modern ORM
   refuses to connect on first probe.
3. **Phase 2's real transactions (P2.D) gate any multi-statement
   write workflow.** Until P2.D lands, every transaction-control
   statement fails with SQLSTATE `0A000`; clients must not infer atomicity.
4. **Phase 3's MVCC (P3.B) gates real concurrent workloads.**
   Until P3.B, ProximaDB is functionally an autocommit database —
   fine for read-mostly workloads, unsafe for write-contended ones.
5. **Phase 3 work can be parallelized**: P3.A (catalog), P3.C
   (advanced SQL), P3.D (FK), P3.E (types) all have low coupling
   and can be split across engineers.

== Test gates and evidence

Each phase ships with:

* A new integration test file under `tests/` exercising the
  phase's feature surface end-to-end against a live server.
* Updates to `docs/12-design/adr/ADR-018-pgwire-sql-parity-roadmap.adoc`
  (this doc) checking off completed items.
* A live psql probe script (`scripts/pgwire_phase_N_probe.sh`)
  the on-call can run to validate phase health post-deploy.

== Consequences

* **Engine team unblocked** to store DR / tenant_tier / RBAC /
  audit metadata in OLTP tables once Phase 1 ships (no silent
  transactions, no crashes). Full SQL queryability over those
  tables comes with Phase 2.
* **Self-hosters get a viable SQLite-replacement story** at the
  end of Phase 2. Phase 3 makes ProximaDB a viable
  PostgreSQL-replacement for ORM-driven applications.
* **Operator team (AnvaiOps) can wire control-plane queries**
  against ProximaDB at the end of Phase 2 with confidence.
* **Scope discipline**: each phase has a hard exit gate. Skipping
  ahead (e.g., adding window functions before catalog
  introspection works) creates more support burden than it
  delivers value.
