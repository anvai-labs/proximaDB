== Context

The pgwire conformance suites (`tests/{tpch,tpcds,graph_ldbc,document_json,events_tsbs}_pgwire_e2e.rs`)
each carry a ratchet — `TPCH_RATCHET=22`, `TPCDS_RATCHET=16`, graph 10, document 11, timeseries 10 —
described as "full ANSI SQL over pgwire" conformance. But the ratchet is computed as
`passed.len() >= RATCHET`, where a query is "passed" iff it **executes without a SQL error**
("each query that executes cleanly counts toward the ratchet"). Only a *handful* of queries carry a
value-correctness assertion: **TPC-H verifies exactly one query's answer (Q1); the other 21 are
execution-only.** Same shape across suites (~1 answer-checked query each).

So the ratchet measures the **demo** (the query ran), not the **eval** (it returned the right
answer) — the exact anti-pattern the engineering mandates call out. A query that returns wrong or
empty results raises no alarm and still counts toward "22/22 passing".

**This is not hypothetical.** The dual-engine cost-trace harness (PR #455), which runs each query on
the native/Volcano engine AND DataFusion, caught — among queries the suites mark "passed":

* **`document` `d04`/`d08`/`d10` return 0 rows on both engines** (`SELECT doc_id, doc->>'title' …
  LIMIT 10` over thousands of docs) while `count(*)`/`GROUP BY kind` show the table is non-empty —
  i.e. **projecting a JSON path in the SELECT list silently yields empty**. A real defect.
* **Same query, different answers per engine:** `g04` two-hop-FoF returns 16 rows on native vs 32 on
  DataFusion; `d06` returns 0 vs 1. At least one engine is wrong on each.

Execution-ratcheting let all of these through. We need the ratchet to mean *correct*.

== Decision

**A query counts toward a conformance ratchet only when its result is verified CORRECT.** Correctness
is established by two complementary oracles; a conformance query MUST satisfy at least one, and where
both apply, both:

. **Differential cross-engine equivalence (the broad, near-free net).** Run the query on BOTH
  physical engines behind the ADR-039 seam (native/Volcano *and* DataFusion — pre/post-`MATERIALIZE`)
  and assert **identical** results after canonicalization (stable row sort + `ProximaValue`-level
  value/type normalization). Disagreement ⇒ at least one engine is wrong ⇒ the query does **not**
  count and **CI fails**. This requires no hand-graded answers and already finds real bugs.
  *Caveat:* it cannot catch "both engines wrong the same way", and it does not apply to queries only
  one engine supports (native has known lowering gaps) — those require oracle (2).
. **Anchored expected answer (absolute truth).** Each conformance query carries an **expected result**
  computed from the deterministic seed; the actual result must match it exactly. This anchors
  absolute correctness (catches the "both agree, both wrong" case) and is **required** for any query
  that runs on only one engine.

The ratchet then counts **accurate** queries (executed *and* correct), never merely executed. The
existing execution counts become a ceiling the accuracy count climbs toward; converting a suite may
*lower its effective accurate-count until the revealed bugs are fixed* — that is the point, and a
correct, mandated outcome (a real regression must fail CI).

**External reference oracle (real PostgreSQL / embedded DuckDB row-for-row) is explicitly deferred** —
differential + anchored is sufficient, dependency-free, and the pgwire surface is already
Postgres-modeled. An external oracle is a future strengthening for the heavy TPC-H/TPC-DS suites, not
a prerequisite.

== Mechanism (reuse, don't rebuild)

Reuse the dual-engine harness infrastructure from PR #455 (embedded pgwire boot, the per-modality
query sets, the pre/post-`MATERIALIZE` dual-engine run). Add:

* a `canonicalize(rows) -> Vec<Vec<ProximaValue>>` (stable sort + type/format normalization) so two
  engines' results compare structurally, independent of row order and engine-specific formatting;
* a `differential(query)` assertion (native result == DataFusion result, or one-engine-only ⇒ skip
  differential, require anchored);
* per-query `expected: Vec<Vec<&str>>` tables (anchored answers on the fixed seed);
* the ratchet recomputed over **accurate** queries.

Conversion is **mixed-safe**: add the accuracy layer alongside the existing execution ratchet per
suite; do not flag-day. Each suite's execution ratchet stays until that suite is converted.

== Rollout (phased — one suite per PR, each files the bugs it finds)

. **`document`** first — it has a *known* defect (the JSON-projection 0-rows) the accuracy layer will
  pin; converting it proves the pattern end-to-end and produces the first bug TD + fix.
. **`graph`** — pins the `g04`/`g06` divergences.
. **`timeseries`**, then **TPC-H**, then **TPC-DS** (the largest answer sets — anchored tables are
  most work here; differential carries most of the load).

== Consequences

* **Surfaces real product defects** as TDs (JSON-projection empty result; native↔DataFusion
  divergences; native lowering gaps already enumerated by the harness) instead of hiding them behind
  "executes cleanly".
* The conformance ratchet finally measures the **eval**, satisfying mandate #13 ("set the bar at the
  eval, not the demo") and hardening #10 (quality ratchets only go up — now on *correctness*).
* Differential testing makes the **two engines keep each other honest** — a powerful, cheap oracle
  that scales to every query without hand-grading, and a forcing function for the ADR-039 dual-path
  to stay semantically identical (which the shared `proximadb-functions` registry already targets).
* Short-term: some suites' effective accurate-count drops below the old execution count until fixes
  land. That is the gap becoming visible, not a regression of capability.

== Verification

The accuracy harness fails CI when any conformance query's two engines disagree (after
canonicalization) or its anchored answer mismatches. Ratchet asserts move from `passed.len()` (ran)
to `accurate.len()` (ran + correct). The first conversion (document) must turn the `d04/d08/d10`
0-row results from "passing" into failing — the proof the bar moved.
