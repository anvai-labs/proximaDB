== Context

ProximaDB exposes its data directly — REST v2, gRPC v2, pgwire/SQL, Arrow Flight. That makes it a multimodal data platform whose consumers are increasingly **agents, not only humans**. The first principle that governs an agent consumer: **an agent is context-bounded, not compute-bounded** — it cannot pull a multi-terabyte collection into its context window, so it must be handed the *minimal sufficient statistic* about the data and decide its next query from that. The engine is **the only component co-located with the data**, so producing that statistic is structurally the engine's job — an agent cannot profile data it cannot fit in context, and shipping the raw data to it to be profiled would defeat the purpose (and burn KRU). Profiling is a privileged engine operation.

A reconnaissance pass (2026-06-26) found the engine is **most of the way there already**, and the gap is aggregation + projection, not new machinery:

[cols="2,3", options="header"]
|===
| Already exists | Where
| Per-column min/max prune statistics (zone maps) | PAX column stripes + zone maps (ADR-027 "PAX column stripes + zone maps + RaBitQ/SQ8 tiers serve ANN *and* relational projection/pruning")
| A coalesced write/flush/compaction boundary | SST/LSM memtable→flush→PAX→compaction (ADR-027 Decision 3); KSU resident-bytes accrues here (ADR-030 sibling)
| EXPLAIN slots for selectivity/rows/cost, plus a "stats freshness" diagnostic | `ExplainOperator.estimated_selectivity`/`estimated_rows`, `FilterDiagnostics`, `ExplainDiagnostics` (ADR-004) — **defined but unfed**
| Graph stats | `GetGraphStats` (node/edge counts, label/edge-type distribution)
| BM25 corpus machinery | `crates/modalities/proximadb-rank-features/src/bm25.rs`
| Catalog introspection | `xcatalog.{tables,columns,indexes}`, `information_schema`, `pg_catalog` (CatalogIntrospectionService)
| Agent-state primitives | `AgentMemoryService`/`AgentCheckpointService`/`AgentEventService` (ADR-022)
| The "one seam, N readers" co-design pattern | ADR-030 (instrument once; route-cost + cache + billing all read the same snapshot)
|===

What is missing: (1) **column/field-level distribution statistics** (cardinality, null rate, value histogram, example values) aggregated from the zone maps into a collection-level summary; (2) **per-modality corpus statistics** surfaced uniformly (BM25 term/IDF, vector centroid/spread/cluster, graph degree/centrality, trace span/service distribution, time-series range/point-count); (3) a wiring of those into **ADR-004's empty selectivity/rows slots**; and (4) a **reference MCP surface** so an agent can `list → describe → stats → explain → search` without bespoke client code. None of these is a new storage path, a new scan, or a new authority.

This ADR sits **exactly on the open-core seam** — the same seam ADR-027/030 already drew for metering. It produces **neutral statistics (units and distributions), never meaning and never dollars**. Turning a statistic into a business glossary entry, a data-quality grade, or a per-account governed answer is **AnvaiOps policy** (AnvaiOps ADR-0027), exactly as turning a metered unit into a bill is.

== Decision 1 — Statistics is "measured once at the write boundary, read many"; never a scan-to-answer `ANALYZE`

The single load-bearing constraint. Column distribution statistics are maintained **incrementally at the flush/compaction boundary** — the same boundary where PAX zone maps are already written and where ADR-030's sibling KSU resident-bytes accrues — using bounded streaming sketches:

[cols="1,2", options="header"]
|===
| Statistic | Sketch (bounded state, mergeable on compaction)
| Distinct cardinality | HyperLogLog
| Value distribution / quantiles | t-digest (numeric); aggregated zone-map min/max as the coarse band
| Null rate, row count | exact counters (already on the write path)
| Frequent values / examples | reservoir sample + count-min for heavy hitters
|===

The sketches are **mergeable**, so compaction merges segment-level sketches into collection-level statistics with no rescan — exactly the small→large coalescing ADR-027 Decision 3 already runs for records and meters. A statistic is therefore always available from a tiny resident summary; **the engine never scans the corpus to answer "what is in here?"**. A scan-to-answer `ANALYZE` is explicitly rejected (Rejected alternatives) because it would charge KRU to produce the very artifact whose purpose is to let an agent *avoid* scanning.

This is the ADR-030 co-design pattern applied to the **write** boundary: instrument the flush/compaction pass once; **zone-map pruning, KSU storage accrual, and the statistics envelope all read the same written segment.** One pass, three readers.

== Decision 2 — The statistics envelope is the boundary object: versioned, modality-neutral, units-only

The engine emits one **versioned, modality-neutral statistics envelope** per collection, exposed on the existing introspection surface (`xcatalog`, the collection-stats endpoint, the `_diagnostics` route-health surface) — not a new transport. Its shape:

* `envelope_version` (semver; the engine bumps it, the consumer pins/validates — mirrors the ADR-016 digest-pinning + status-sync discipline);
* `collection_id`, `freshness` (the snapshot's flush/compaction watermark — the engine *attests* staleness, it does not interpret it);
* `record_count`, `storage_size_bytes`, `index_size_bytes` (already emitted);
* `fields[]` — per field: `name`, canonical `data_type` (ADR-024), `null_rate`, `distinct_estimate`, `quantiles`/`histogram`, `examples[]`, `indexed`/`filterable`;
* `modality[]` — a tagged union of the per-modality blocks from Decision 3.

**Invariant — the envelope carries units and distributions, never meaning and never money.** No field description text, no business glossary, no data-quality grade, no PII classification, no per-account scoping, no `$`. Those are AnvaiOps ADR-0027's to add. This is the same non-entanglement law ADR-027/030 enforce for billing-vs-perf and units-vs-pricing; violating it here would refork the wire contract the way the AnvaiOps runtime contract was once forked across call-sites.

== Decision 3 — Per-modality extractors reuse the existing modality engines

No modality gets a new subsystem; each block is an aggregation over machinery that already runs:

[cols="1,2", options="header"]
|===
| Modality block | Source (reuse)
| Document / text | BM25 corpus term/IDF, doc length distribution — `proximadb-rank-features/src/bm25.rs`
| Vector | centroid, spread, coarse cluster occupancy — derived from the AXIS/quant tiers already built at index time (ADR-026/021)
| Graph | degree distribution, label/edge-type counts, centrality/rank band — **extends `GetGraphStats`** (don't fork it)
| Trace / log | span count, service distribution, trace-depth band — over the observability-ingest records
| Time-series | point count, time range, downsample state — over the TST engine
|===

Each block is `modality`-tagged inside the one envelope (Decision 2), so a consumer that understands only the generic `fields[]` still works; modality-aware consumers read the extra block. Backward- and forward-compatible by construction (the `envelope_version` gate).

== Decision 4 — Statistics feed ADR-004's selectivity/rows slots — they do not create a parallel explain

ADR-004 already defined the consumer interface: `ExplainOperator.estimated_selectivity`, `estimated_rows`, `estimated_cost`, `FilterDiagnostics.estimated_selectivity`, and `ExplainDiagnostics` ("stats freshness, data-movement estimate"). Those slots are **defined but unfed** today. This ADR makes the statistics envelope the **producer** that fills them: the planner reads field/modality stats to estimate selectivity and output rows for each operator, and stamps the envelope `freshness` into `ExplainDiagnostics`.

Hard rule (restating ADR-004 Contract Rule 5): there is **one** explain, mechanically derived from the validated plan; statistics are an *input* to it, not a second explain format. An agent asking "what will this cost / how selective is this filter" gets the answer through the existing unified EXPLAIN, now populated — across REST/gRPC/SQL/pgwire identically (ADR-004 transport adapters), with no agent-specific cost surface to drift.

== Decision 5 — A thin reference MCP surface: OSS projection, no pricing, no governance

Ship a **reference MCP server** in OSS that projects what the engine already exposes, so an agent (or any MCP client) can self-serve without bespoke gRPC/REST glue:

[cols="1,2", options="header"]
|===
| MCP primitive | Backed by (existing)
| `list_collections` / `describe` | catalog introspection (`xcatalog`/`information_schema`)
| `stats` | the Decision 2 envelope
| `explain` | the ADR-004 unified explain (now fed, Decision 4)
| `search` | REST v2 hybrid search
| `memory` / `checkpoint` / `event` | ADR-022 agentic services
|===

It is **generic and unprivileged**: no `$`, no rate card, no per-account entitlement, no PII redaction, no multi-tenant policy projection — those belong to AnvaiOps ADR-0027's governed gateway, which *composes* this reference surface. The reference server is adoption fuel (every database now ships an MCP server) and the conformance target for the boundary object; it is the lower half of the agent surface, deliberately stopping at the open-core line. MCP itself is treated as one *projection* of the engine's affordances, not a new authority — if a different agent protocol displaces it, the projection is re-skinned; the envelope, EXPLAIN, and introspection underneath do not move.

== Open-core boundary: what stays OSS (proximaDB) vs moves to AnvaiOps

Consistent with ADR-027/030 ("OSS = mechanism; the $ rate card is AnvaiOps policy"), extended from *metering* to *statistics*:

[cols="1,2,2", options="header"]
|===
| Concern | Home | Why
| **Statistics mechanism** — zone-map aggregation, streaming sketches at flush/compaction, per-modality extractors, the versioned envelope | **proximaDB (OSS)** | You can only profile data where the data lives; the sketches ride the write boundary the engine already owns. It emits **units/distributions**, never meaning.
| **Selectivity → EXPLAIN** — feeding ADR-004's `estimated_selectivity`/`estimated_rows` slots; planner cost estimation | **proximaDB (OSS)** | Estimation is a runtime *engine* decision (it picks plans/routes); the numbers are cost-curve quantities, not an invoice — same status as the ADR-030 routing cost model.
| **Reference MCP surface** (list/describe/stats/explain/search/memory) | **proximaDB (OSS)** | Generic, unprivileged projection of existing surfaces; the conformance target for the boundary object.
| **Semantic enrichment** — column/collection descriptions, business glossary, cross-modal co-statistics, data-quality grading, PII classification, freshness *SLA* (vs the engine's freshness *fact*) | **AnvaiOps** | Account-specific *meaning* over the engine's neutral stats; runs through AnvaiOps's metered LLM seam.
| **Governed agent gateway** — per-account entitlement, capability gating, cost ceilings, PII redaction, the $ cost estimate | **AnvaiOps** | Multi-tenant *policy*; reuses AnvaiOps's existing capability + metering + egress spine.
| **Pricing** — units/stats → dollars, tier entitlement | **AnvaiOps** | Already the law (ADR-027/030); the engine never prices.
|===

**Net:** statistics keeps *mechanism* in OSS (it has nowhere else to live — it is bound to the data and the write boundary) and emits a **neutral envelope**; turning that envelope into *meaning, governance, and a bill* is AnvaiOps reading the OSS surface and applying its policy. A freely-adopted, self-describing OSS engine is the top of the funnel; the curated/governed/priced agent data-plane monetizes on top.

== Co-design seam with AnvaiOps ADR-0027 (the boundary object contract)

The two ADRs are designed against **one boundary object — the statistics envelope (Decision 2)** — and must agree on it. Stated identically on both sides:

[cols="1,3", options="header"]
|===
| Property | Contract
| **Owner / producer** | proximaDB (OSS). The engine defines the envelope shape and `envelope_version`, and is the *only* writer.
| **Consumer** | AnvaiOps (commercial). Reads the tiny envelope, never the data; enriches, governs, prices.
| **Flow direction** | Stats flow **up** (engine → AnvaiOps), like the durable per-tenant metering sink (ADR-027/030). Pricing/entitlement flow **down** (AnvaiOps → engine config — the tier-config delivery ladder recorded in the 2026-08-19 amendment below; the former `sync_pricing_to_proximadb.sh` mechanism was retired). Status flows as a **ceiling** down (engine surface status caps the AnvaiOps capability status, the existing `sync_proximadb_status.py` / ADR-0014 inheritance). Semantics **stay in AnvaiOps** — never pushed into `xcatalog`.
| **Must not cross (engine side)** | The envelope carries no `$`, no descriptions, no per-account scope, no quality grade. The engine attests freshness as a *fact* (a watermark), never an *SLA*.
| **Must not cross (consumer side)** | AnvaiOps must not push semantic/pricing concerns into the engine stats path (that reforks the wire contract), and cannot surface a statistic the engine does not emit, nor a capability status above the engine's surface status.
| **Versioning** | `envelope_version` is engine-owned; the consumer pins + validates (mirror of ADR-016 digest pinning + the status-sync guard).
|===

This is the ADR-030 lesson generalized: **one boundary, two halves that each own exactly their side, and a contract neither can silently fork.**

== Authority and route declaration

Per the route-declaration mandate (`RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20.adoc`):

[cols="1,3", options="header"]
|===
| Field | Value
| `authority_mode` | `projection` / `facade` — the envelope is a *derived summary* over PAX segments + zone maps; canonical WAL + xCatalog remain authoritative. Statistics introduce no new durable authority.
| `policy_boundary` | Per-tenant via `TenantContext`/RLS — a tenant reads only its own collections' stats. The reference MCP enforces tenant scope but **no** per-account entitlement (that is AnvaiOps).
| `workload_profile` | `read_mostly` — stats are maintained on the existing write/compaction pass; reads are tiny envelope fetches.
| `freshness_sla` | The envelope *attests* its own freshness watermark (`eventual`, advanced at flush/compaction). It states the fact; it does not promise an SLA — that is AnvaiOps policy.
| `compute_route` | Reuses the existing flush/compaction write path (sketch maintenance) and the existing introspection read path (envelope fetch). No new route.
| `policy/RLS` | Tenant-scoped via `TenantContext`; same RLS as record reads.
|===

== Consequences

* **Closes ADR-004's input gap.** The unified EXPLAIN's selectivity/rows slots finally have a producer, across all four protocols at once — agents and the planner both benefit, no agent-specific surface.
* **Self-describing engine, zero new scan.** Reusing zone maps + the coalesced write path means statistics are always-fresh and ~free; the "data cannot be offloaded to the agent" constraint is honored by construction (the agent reads a summary, never the corpus).
* **One pass, three write-boundary readers** — zone-map pruning, KSU accrual (ADR-030 sibling), and the stats envelope read the same written segment; the same co-design economy ADR-030 achieved on the read boundary.
* **Open-core line held.** Mechanism (stats/selectivity/reference MCP) stays OSS and neutral; meaning + governance + pricing stay AnvaiOps. The boundary object is the only coupling, and it is versioned and one-directional.
* **Cost / risk:** sketch maintenance adds bounded state + a small per-flush merge cost (acceptable — it rides an existing pass); the envelope is a new contract surface, so it must be versioned and conformance-tested against the reference MCP and the AnvaiOps consumer. Per-modality extractor accuracy (esp. vector cluster occupancy) is best-effort and must be labeled approximate in the envelope.
* **Gated:** depends on the ADR-027 zone-map + coalesced-writer substrate (TD-162a/TD-161 lineage); the reference MCP must not leak any pricing/governance surface (CI guard, mirroring the ADR-030 billing-never-gated guard).

== Rejected alternatives

* **A scan-to-answer `ANALYZE` command.** Rejected: charges KRU to scan the corpus to produce the artifact whose purpose is to let agents *avoid* scanning; violates Decision 1. Stats must ride the write boundary, not a read scan.
* **A bespoke statistics storage engine / new authority.** Rejected: reuse-first (CLAUDE.md). Zone maps + the coalesced PAX writer already exist; statistics is an aggregation over them, not a new durable path.
* **Baking semantics (descriptions/glossary/quality/PII) into `xcatalog`.** Rejected: that is meaning, not mechanism — it is AnvaiOps ADR-0027's half, and putting it in the engine forks the open-core boundary and the wire contract.
* **An agent-specific cost/explain surface separate from ADR-004.** Rejected: ADR-004 Contract Rule 5 — one explain, mechanically derived; a parallel agent explain would drift from execution.
* **A full, governed MCP *product* in OSS.** Rejected: per-account entitlement, pricing, and PII redaction are policy; the OSS server stops at the open-core line and AnvaiOps composes it (Decision 5 / boundary table).

== Amendment (2026-08-19, ADR-0053 co-design review): tier-config delivery, minimal projection, and claim trust

Pressure-tested against AnvaiOps `REVIEW-commercial-image-overlay.md` (outcome:
AnvaiOps ADR-0053). Three corrections and two additions to this ADR's seam:

**1 — Tier-config delivery is a three-layer ladder, not the (retired) sync script.**
The "pricing flows down" clause above originally named
`anvaiops/scripts/sync_pricing_to_proximadb.sh`, which has since been replaced by
a hard-error stub. The engine's actual contract (`config/TIER_CONFIG.md`,
`tenant_tier_types.rs resolve_tier_config_source`) is, first-hit-wins:

. A file at `PROXIMADB_TIER_CONFIG_PATH` (default `/config/tier-config.json`) —
  satisfied by a mounted file (k8s ConfigMap / bind mount) or a build-time COPY.
. `PROXIMADB_TIER_CONFIG_URL` — the container entrypoint curl-fetches at boot,
  atomic-replaces, sanity-checks, and falls back to the baked file on failure.
. The compile-time baked OSS baseline (air-gapped fallback).

`TIER_CONFIG` is a `OnceLock` resolved once at process start: **a restart is
required under every mechanism** — no hot reload exists (by design). Mount/URL
delivery makes a tier change a config update + rolling restart (no image
rebuild); baking remains correct for appliance/air-gapped substrates.

**2 — Minimal-projection rule (normative for commercial operators).** The engine
deserializes exactly: `schema_version`, `default_tier`, and per tier `id`,
`prom_label`, `soft_caps{scan_budget_gb, ef_search_cap, freshness_sla_seconds}`,
`cost_multiplier`. Everything else in an operator's pricing file (currency,
`unit_rates`, `platform_fee_usd`, display/marketing blocks, margin policy) is
inert to the engine and — per AnvaiOps ADR-0053 D1 — commercially confidential.
An operator projecting tiers into engine config MUST ship only the listed
fields (a ~20-line projector); **never bake a full rate card**. The tier ids
themselves may be the operator's own (`free_trial`/`team`/… deserialize via
serde aliases onto `Tier::Tier1..Tier5` — alias-aware startup validation).

**3 — Enforcement truth.** Hard `allowances` (storage/ingest/scan caps) are NOT
enforced by the engine today: `catalog::budget_guard::enforce` has no callers
(ADR-0015 Phase 3a is observe-only; pod-level gating was explicitly rejected as
an AnvaiOps concern). What a tier actually buys today: cache floors/ceilings/
weight (via `PROXIMADB_CACHE_TIERS_PATH` + the LimitsResolver), the C5 route
cost multiplier (observability; routing-neutral), and boot-warm priority.
Nobody should believe a baked tier config buys data-plane quota protection.

**4 — Tier claims are trust-gated (this repo, ADR-0053 W8).** The entitlement
claim (`X-Tenant-Tier` REST, `x-tenant-tier` gRPC, `proximadb_tier` pgwire
startup param) was previously honored from ANY client — a client with direct
port access could self-stamp `enterprise`. It is now governed by
`PROXIMADB_TIER_HEADER_TRUST` (`[security.tenant] tier_header_trust`), the same
`open | authenticated-only | gateway-only` ladder as `PROXIMADB_TENANT_HEADER_TRUST`
(TD-TENANT-1). A rejected claim is **dropped** (warned once per tenant), never a
4xx — the request proceeds at the tenant's default tier. Stamps stay insert-only
(clearing on rejection would let an anonymous request strip a legitimate stamp).

**4b — One claim vocabulary (TD-TENANT-3).** Gating the claim exposed that the
*names* were never shared: Arrow Flight accepted four tenant spellings while
REST and gRPC accepted one, so a claim honored on one port was silently ignored
on another; Flight had no tier claim surface at all; and the stamped claim was
read in two vocabularies downstream, so `pro` and `tier3` — one entitlement —
landed in different cache buckets. The wire names now live in one foundation
module, Flight gained the tier hook, and the claim is normalized to a canonical
tier id at the stamp (probing canonical-then-operator-spelling, so an
alias-keyed `cache_tiers.json` needs no flag day). Operators projecting tiers
per point 2 may therefore key cache policy by either spelling.

**5 — Citation correction.** The co-designed counterpart is AnvaiOps
**ADR-0027** ("agent-facing catalog statistics semantics boundary"), not
ADR-0021 (that number in the AnvaiOps repo is the tenant-isolation primitive —
a cross-repo numbering collision). All citations corrected above.
