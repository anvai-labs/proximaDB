== Context

The vertical copilot demos (manufacturing, fraud-AML, internet, insurance) each run four
modalities — timeseries, vector, graph, RAG — and claim ProximaDB's thesis: *one engine, one
query plane, no ETL between a metrics store, a vector DB, a graph DB, and a search index.*

Wiring those demos to the real engine surfaced that the thesis is currently delivered by **client
glue**, not by the engine. Each `copilot_live.py` does three different kinds of work, and two of
them are in the wrong place:

[cols="1,2,2", options="header"]
|===
| Work | In the demos | Correct locus
| **Agentic reasoning** — which modality next, how to phrase the answer, when to stop | the investigate/narrate loop | **client / agent** (the LLM, via MCP) — *correct today*
| **Data-plane fan-out** — ingest + aggregate N per-entity series | `for entity in …: 3× REST calls` (≈ 90 round-trips) | **engine** (set-oriented) — *wrong today*
| **Cross-modal join** — graph-reachable ∩ timeseries-failing, pick the sink | done in Python over two result sets | **engine** (data-local) — *wrong today*
|===

This is a direct violation of the co-design mandate the demos exist to showcase. The dominant cost
terms for a cloud database are **I/O round-trips and egress**, not CPU. The current wiring
**maximises both**: an N+1 per-entity fan-out (row-at-a-time, not set-oriented), and a client-side
join that ships intermediate result sets over the wire (metered KOU) only to intersect them and
discard most. "One engine" is really *four engines glued in Python*.

== Decision

Expose the four modalities as **composable relations in the SQL/relational plane** (the plane
ProximaDB is already driving toward per the pgwire/DataFusion investment, ADR-052/039), so a
cross-modal JOIN is a **query executed data-local in the engine**, not client glue.

1. **Each non-relational modality becomes a table source** (a DataFusion `TableProvider`, surfaced
   as a table-valued function so it is expressible in ANSI SQL and reachable from pgwire):
   * `vector_search(collection, query, k)` → `(id, score)` — *already exists* (Track B, §8 moat;
     `src/datafusion/cross_modal.rs`).
   * `timeseries_range(collection, start_ms, end_ms)` → `(timestamp, metric, value)` — *this ADR's
     first increment*.
   * `graph_traverse(graph, start, edge, max_depth)` → `(node_id, depth)` — next increment, over
     the variable-length traversal (TD-GRAPH-3); a fixed schema sidesteps the dynamic-RETURN
     schema problem of general Cypher.
2. **The cross-modal join is SQL**, planned and executed by DataFusion (OLAP) / native Volcano
   (OLTP) behind the `ComputeBackend` seam (ADR-052). The engine ships the **answer**, not the
   intermediate sets — one round-trip, one metered plan, isolation enforced structurally at one
   boundary.
3. **The agentic copilot brain stays in the client/agent (MCP) layer.** The database does NOT
   embed a vertical's workflow — no hard-coded "fraud copilot". The reference MCP surface projects
   Layer-1 primitives + Layer-2 relations as tools; the agent composes them; **AnvaiOps** governs
   every call (metering, entitlement, PII redaction) at the gateway seam (ADR-022 `event`/`memory`
   for state).
4. **No new DSL.** Reuse SQL + table functions (Invent & Simplify). The frontend source-node path
   (lowering into the shared logical plane) is a later optimisation (TD-XMODAL-4); the UDTF path
   makes it work today over the DataFusion ANSI route.

This is a three-layer architecture: **(L1) native per-modality surfaces** (unchanged) → **(L2) the
cross-modal query fabric** (this ADR, in the engine) → **(L3) the agentic copilot + governance**
(MCP + AnvaiOps). The demos put L2 and part of the data plane in the client; this ADR moves them
into the engine.

== First increment (landed with this ADR)

`timeseries_range(...)` as a live-backed, SQL-joinable relation, mirroring the existing
`vector_search` UDTF exactly (`src/datafusion/cross_modal.rs`, registered in
`src/datafusion/mod.rs::build_session_context` guarded on the process `timeseries_service()`):

* `TimeseriesScanPort` (injectable, unit-testable) + a `TimeSeriesService` production adapter.
* `TimeseriesRangeTableProvider::scan` reads the range live and bridges points to a
  `(timestamp, metric, value)` `RecordBatch`, delegating projection/filter/limit to `MemTable`.
* `TimeseriesRangeTableFunction: TableFunctionImpl` parses `(collection, start_ms, end_ms)`.
* Ratchet tests: schema shape; a timeseries anomaly-scan (`MAX(value) … GROUP BY metric`) ⋈ a
  relational dimension in **one** DataFusion SQL plan; input validation.

This proves the second modality-as-relation and establishes the pattern the remaining sources
reuse. It does not by itself collapse a demo's ~90 calls — that lands when `graph_traverse`
(TD-XMODAL-2) and multi-entity timeseries collections + a set-oriented anomaly scan (TD-XMODAL-3)
follow, at which point the internet root-cause turn (`graph-reachable ∩ timeseries-failing`) is a
single SQL query and the demos are refactored to emit SQL instead of client loops.

== Consequences

*Positive.* Co-design: the join is where the data is — no intermediate egress, one round-trip.
Well-Architected — *Performance/Cost*: fewer round-trips + no intermediate KOU; *Reliability*: one
consistent plan vs a racy multi-call client; *Security*: isolation is structural at one seam;
*Operational Excellence*: one tested join path vs N copy-pasted client scripts. The "one query
plane" thesis becomes literally true, and it is a durable moat (no competitor lets you
`vector-similarity ⋈ timeseries-anomaly ⋈ graph-reachability ⋈ relational-aggregate` in one query).

*Negative / cost.* More engine surface (one `TableProvider` + UDTF per modality). Graph's
dynamic-RETURN schema is constrained to a fixed `(node_id, depth)` for the traversal source (general
Cypher-as-a-relation is out of scope). The UDTF path rides DataFusion's ANSI planner (the shared
relational frontend lowering is deferred). Governance must meter the fused plan as one unit.

== Alternatives considered

* **Keep client-side orchestration (status quo).** Rejected: maximises the dominant cost terms;
  re-implements the join per client; "one engine" is false.
* **A bespoke cross-modal orchestration operator in `ComputeScheduler`** (not general SQL).
  Rejected as the primary path: less general than SQL, a new DSL to learn; the SQL/UDTF plane
  already exists and composes. May still appear as a *physical* fusion optimisation later.
* **An AnvaiOps middleware service outside the engine** that orchestrates modality calls
  server-side. Rejected: the join would still cross the engine boundary (not fully data-local);
  splits query planning across two systems. Governance belongs at the gateway; *joining* belongs in
  the engine.
* **Hard-code the copilot workflow in the DB.** Rejected: business logic in the data tier; the
  agentic brain is the LLM's job (MCP), and verticals must not fork the engine.

== Governance & the boundary

Every cross-modal plan carries `TenantContext` and reads under `DrPathBuilder`; isolation is
structural, never a per-query predicate. The fused plan is metered as one unit (KRU read/compute,
KOU outgress on the result direction). The MCP surface exposes the relations as tools; AnvaiOps
entitlement-checks and PII-redacts at the gateway. New sources MUST emit the query-scoped I/O trace
(TD-XMODAL-5) so the `ComputeScheduler` costs cross-modal routes from measured quantities.
