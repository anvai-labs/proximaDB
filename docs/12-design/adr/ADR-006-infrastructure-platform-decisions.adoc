== Context

Several infrastructure and platform decisions cut across multiple issues and affect the overall system reliability, developer experience, and production readiness. This ADR consolidates decisions for:

1. Test binary compilation issue (cdylib crate-type)
2. CDC PostgreSQL network layer
3. Experimental engine lifecycle (SWIFT/RAPTOR)
4. Distributed graph engine posture (Pulsar)
5. Security chain completion (mTLS, identity, audit)
6. Distributed transport (RPC stubs)
7. PromQL completeness

== Decision

=== 1. Test Binary Fix (Issue #55)

**Problem**: `crate-type = ["rlib", "cdylib"]` in `Cargo.toml` causes `cargo test --lib` to produce a test binary that excludes `#[cfg(test)]` modules from certain submodules. 48+ tests from the gap implementation sprint are not visible in test runs.

**Root cause**: When Cargo builds a cdylib, it may use different codegen units or dead-code elimination that strips test-only code. The test binary hash changes unpredictably.

**Decision**: Use a **feature-gated crate type**.

[source,toml]
----
[lib]
name = "proximadb"
# Default: rlib only (for testing and normal Rust usage)
# cdylib is opt-in for Python/FFI builds only
crate-type = ["rlib"]

[features]
# Enable cdylib output for PyO3 / FFI builds
pylib = []

# In build.rs or via cargo config:
# When building for Python: cargo build --features pylib
# This triggers cdylib output via a separate [[lib]] or build.rs logic
----

Alternative (simpler): Add a dedicated `tests/lib_test.rs` that imports and tests all new modules:

[source,rust]
----
// tests/gap_implementation_tests.rs
use proximadb::transaction::engine_wiring;
use proximadb::observability::alerting::{escalation, history, persistence};
// ... exercises all new modules
----

**Recommended approach**: Simpler alternative first (dedicated test file), feature-gated crate-type as follow-up.

=== 2. CDC PostgreSQL Network Layer (Issue #54)

**Problem**: `ReplicationStream::connect()` returns an error. The PgOutput decoder and SQL generation are complete but no actual TCP/replication protocol is wired.

**Decision**: Implement a **three-layer architecture**:

[source,text]
----
Layer 1: Transport (tokio_postgres)
  - TCP connection with TLS (native-tls or rustls)
  - Connection string parsing
  - Connection pooling (for snapshot queries)

Layer 2: Replication Protocol
  - CREATE_REPLICATION_SLOT via simple query
  - START_REPLICATION via copy-both duplex
  - XLogData → PgOutputDecoder (existing)
  - PrimaryKeepalive → StandbyStatusUpdate (existing wire format)
  - Periodic status updates via background task

Layer 3: Lifecycle
  - Reconnection with exponential backoff (1s → 2s → 4s → ... → 60s max)
  - Slot management (create if missing, verify on reconnect)
  - LSN tracking and offset persistence (via existing OffsetStore)
  - Graceful shutdown (flush LSN, close connection)
----

Implementation approach:

[source,rust]
----
// src/cdc/connectors/postgres/transport.rs
pub struct PgTransport {
    client: tokio_postgres::Client,
    connection_handle: JoinHandle<()>,
}

impl PgTransport {
    pub async fn connect(config: &PostgresConfig) -> Result<Self> {
        let (client, connection) = tokio_postgres::connect(
            &config.connection_string,
            tokio_postgres::NoTls, // or native-tls
        ).await?;

        let connection_handle = tokio::spawn(async move {
            if let Err(e) = connection.await {
                tracing::error!("PostgreSQL connection error: {}", e);
            }
        });

        Ok(Self { client, connection_handle })
    }

    pub async fn start_replication(
        &self,
        slot: &str,
        publication: &str,
        from_lsn: u64,
    ) -> Result<CopyBothDuplex<Bytes>> {
        // Use simple_query for CREATE_REPLICATION_SLOT
        // Use copy_both_simple for START_REPLICATION
    }
}
----

**Feature gate**: `experimental-cdc-connectors` (existing flag, no new flag).

**Testing**: Unit tests with mock protocol messages. Integration test with `testcontainers` PostgreSQL (ignored in CI by default, can be enabled via `test-integration` feature).

=== 3. SWIFT/RAPTOR Engine Lifecycle (Issue #60)

**Decision**: **Deprecate both engines**.

Rationale:
* SWIFT: Incomplete 3-tier hierarchy, limited test coverage, no unique value over SST/NOVA
* RAPTOR: 35+ TODOs, Matrix Trinity architecture is research-grade, not production-viable
* Both behind `experimental-engines` flag — no users depend on them
* Maintenance burden (compilation time, clippy warnings, cognitive overhead)

Implementation:
1. Move `src/storage/engines/impls/swift/` to `src/storage/engines/archive/swift/`
2. Move `src/storage/engines/impls/raptor/` to `src/storage/engines/archive/raptor/`
3. Remove from `src/storage/engines/factory.rs` engine creation paths
4. Keep `experimental-engines` feature flag but document it as "archived research engines"
5. Add ADR entry in `DESIGN_PATTERNS.adoc` documenting the deprecation decision

**Do NOT delete** — the code has research value and may be revived if the architecture matures.

=== 4. Pulsar Distributed Graph Posture (Issue #61)

**Superseded June 2026**: Pulsar was retired as a separate graph engine. Runtime
selection now accepts ORION only; distributed graph behavior is a relational
distributed-substrate requirement.

**Decision**: **Formal experimental designation with API warnings**.

Rationale:
* Cross-shard traversal incomplete (may miss edges)
* No distributed WAL (data loss risk on shard failure)
* Async replication only (eventual consistency)
* ORION + application-level sharding is the recommended production pattern

Implementation:
1. Add runtime warning when Pulsar is selected via `GraphServiceFactory`
2. Return structured warning in graph query responses when using Pulsar
3. Update `docs/05-concepts/graph-engines.adoc` with explicit recommendation matrix
4. Add `CapabilityDescriptor` for Pulsar with `tier: Experimental` and explicit limits
5. Do NOT attempt to complete — focus engineering effort on ORION improvements instead

=== 5. Security Chain (Issue #28)

**Decision**: Implement in three stages.

**Stage 1: mTLS Certificate Revocation**
* Add CRL (Certificate Revocation List) and OCSP checking to `src/network/middleware/tls.rs`
* Use `rustls` CRL verification (already a dependency)
* Periodic CRL refresh (configurable interval, default 1 hour)

**Stage 2: Identity Mapping**
* Map TLS client certificate CN/SAN to ProximaDB identity
* Bridge to `CapabilitySubject` for capability-aware access control
* Create `src/security/identity/tls_mapper.rs`

**Stage 3: Audit Evidence**
* Write security-relevant events to WAL (authentication, authorization, capability checks)
* Create `src/security/audit/wal_audit.rs`
* Schema: timestamp, principal, action, resource, outcome, metadata

=== 6. Distributed Transport (Issue #27)

**Decision**: Replace RPC stubs with **tonic-based node-to-node transport**.

* Use existing tonic infrastructure (already a dependency)
* Define `proto/proximadb/v1/internal.proto` for inter-node messages
* Implement `NodeTransport` trait with tonic client/server
* Integrate with `src/cluster/` coordinator
* Feature-gate behind `cluster` flag (existing)

=== 7. PromQL Completeness (Issue #56)

**Decision**: Extend the existing parser in `src/observability/query/promql.rs` incrementally:

**Phase 1**: Binary expression support
* Arithmetic: +, -, *, /, %, ^
* Comparison: ==, !=, <, >, <=, >=
* Proper operator precedence

**Phase 2**: Vector matching
* `on()`, `ignoring()` label selectors
* `group_left()`, `group_right()` for many-to-one/one-to-many

**Phase 3**: Missing functions
* `absent()`, `changes()`, `delta()`, `deriv()`, `predict_linear()`
* `histogram_quantile()` improvements

Each phase is independently deployable and testable.

== Consequences

* Test binary issue resolved — all 48+ new tests become visible
* CDC PostgreSQL gets a production-grade transport layer
* SWIFT/RAPTOR removed from cognitive load (archived, not deleted)
* Pulsar gets explicit experimental warnings (no silent data loss)
* Security chain closes the biggest enterprise gap
* PromQL improvements are incremental and safe
