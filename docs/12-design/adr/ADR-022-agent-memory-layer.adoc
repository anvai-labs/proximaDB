== Context

Two agent-memory frameworks define the current practitioner landscape:

* **mem0** (`mem0ai`) — an LLM-driven memory *orchestration layer*, not a database. It runs a two-phase
  pipeline: an extraction phase that pulls salient facts from each new message pair, and an
  update/consolidation phase that retrieves the top-_s_ semantically similar existing memories and lets
  an LLM choose `ADD` / `UPDATE` / `DELETE` / `NOOP` to dedupe and reconcile. It delegates persistence to
  a pluggable external vector store (Qdrant default; 20–24+ providers via a `VectorStoreFactory` +
  `VectorStoreBase` interface) plus an optional graph store (Neo4j default for the `Mem0g` variant).
  Primary source: arXiv:2504.19413.
* **agentmemory** (Moon / Autonomous Research Group, PyPI) — a thin CRUD-plus-semantic-search function
  library over categorized collections (`create_memory` / `search_memory` / `get_memories` / …), backed
  by ChromaDB by default or Postgres/pgvector via `CLIENT_TYPE=POSTGRES`. No automatic LLM extraction or
  consolidation. Effectively dormant (last release ~Oct 2023).

The architectural fact that drives this ADR: **both are orchestration libraries layered on top of a
storage backend.** ProximaDB occupies that storage/infrastructure layer — it is the peer of
Qdrant/Chroma/pgvector/Neo4j, not of mem0/agentmemory. A reconnaissance pass (2026-05-30) found ProximaDB
already ships the substrate an agent-memory layer needs:

[cols="2,3", options="header"]
|===
| Agent-memory primitive | Existing ProximaDB surface

| Auditable retrieval / provenance | AQL + RUBICON audit trails — `src/query/aql/` (TD-050), `docs/12-design/RUBICON_ALIGNMENT.adoc`
| Salience / re-ranking | RERANK SRF — `crates/modalities/proximadb-rank-{core,features,onnx,profile,expr}`, `ProductionHybridBackend`
| Entity-linking / graph memory | Graph RAG (RGL) + ORION — `src/graph/rag/` (TD-045)
| Hybrid retrieval (semantic + lexical) | RRF + 11 fusion strategies — `src/core/search/hybrid/fusion.rs`; BM25 leg `crates/modalities/proximadb-rank-features/src/bm25.rs`
| Typed memory categories | `ProximaRecord.memory_type` (Memanto 13-category, TD-055) — `crates/foundation/proximadb-records/src/lib.rs`
| Scope (user/tenant/actor) | `ProximaRecord.tenant_id` / `actor` + engine-level RLS — `src/security/rls/`
| Extraction / consolidation engine | LLM function-calling via `LLMIntegrationEngine` + AV-SQL agents — `src/ai/llm_integration/engine.rs`, `src/query/nl/`
| External-framework integration | pgvector-compatible pgwire (port 5433) — `src/network/postgres/`
|===

The gaps are orchestration and a small amount of scoping, not storage: no extraction/consolidation
agent loop wired for the *memory* use case, no explicit session scope, and the Phase 6 encoding gates
(TD-053/054) and proactive retrieval (TD-052) remain open.

== Decision

**Adopt a native Agent Memory Layer as a thin orchestration facade that reuses existing ProximaDB
surfaces, and treat mem0 and agentmemory as first-class compatible consumers — not as components to
re-implement and not as components to vendor.**

Concretely:

1. **Reuse, do not rebuild.** The agent-memory layer composes AQL (auditable retrieval), Graph RAG
   (entity-linking), the RERANK framework (salience), hybrid fusion (recall), and
   `ProximaRecord.memory_type` (typed memory). It introduces NO new storage engine, WAL path, or catalog
   contract. This is mandated by the reuse-first rules in `CLAUDE.md`.

2. **External frameworks integrate as consumers over existing wire surfaces.**
   * *mem0* connects either (a) via its existing PGVector provider over ProximaDB's pgvector-compatible
     pgwire (port 5433), or (b) via a dedicated `VectorStoreBase` provider registered in mem0's
     `VectorStoreFactory`. mem0g's graph store can target ProximaDB's native graph engine, collapsing the
     usual Qdrant+Neo4j pair into one backend.
   * *agentmemory* connects via its `CLIENT_TYPE=POSTGRES` (pgvector) path.

3. **Native orchestration is optional and built from existing parts.** Where ProximaDB drives extraction
   and consolidation itself (rather than delegating to mem0), it reuses `LLMIntegrationEngine` +
   the AV-SQL multi-agent decomposition pattern (`src/query/nl/`) for extraction, and Graph RAG + fusion
   + an LLM `ADD/UPDATE/DELETE/NOOP` decision for consolidation. No new LLM-provider abstraction.

4. **Scoping extension is minimal.** Session scope is added via `props["session_id"]` first; a first-class
   `ProximaRecord.session_id` field is deferred unless a query-path need is proven (avoids a record-shape
   change for a property that `props` already carries).

=== Authority and route declaration

Per the route-declaration mandate (`RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20.adoc`):

[cols="1,3", options="header"]
|===
| Field | Value

| `authority_mode`
| `projection` / `facade` — memories are `ProximaRecord`s; canonical WAL + xCatalog remain authoritative. The memory layer is an orchestration facade, not a new authority.

| `policy_boundary`
| Per-tenant via `ProximaRecord.tenant_id` + `permitted_principals` + RLS. Session scope nested under tenant.

| `workload_profile`
| `agentic_read_write` — write = extract+consolidate; read = retrieve+fuse+rerank+audit.

| `freshness_sla`
| `read_your_writes` within a session; long-term memory is `eventual` after consolidation.

| `compute_route`
| Reuses the existing search route (AXIS/DiskANN → distance → fusion → RERANK). No new route.

| `policy/RLS`
| Multi-agent sharing uses `permitted_principals`; single-agent memory uses `tenant_id == agent_id`.
|===

== Consequences

* **Positive:** ProximaDB becomes a drop-in, *unified* backend for mem0/agentmemory (one engine replacing
  the vector+graph pair), with auditable retrieval and learned re-ranking the commodity backends lack. No
  new durable authority, no proliferation of storage paths.
* **Negative / risk:** mem0's PGVector provider may exercise pgvector surface (operators, index/ANN
  syntax) that ProximaDB's pgwire does not yet fully implement — must be validated (see HLD open
  questions). Native orchestration adds LLM-call cost and latency that belongs behind the existing AQL
  audit trail for explainability.
* **Tracking:** implementation is staged as TD-100…TD-103 (see
  link:../../10-quality/TECHNICAL_DEBT.adoc[TECHNICAL_DEBT.adoc]), all targeting the **v0.2** release;
  Phase 6 gates TD-053/054 and proactive retrieval TD-052 are pre-existing roadmap items that P4 aligns to.

== Rejected alternatives

* **Re-implement mem0's storage/consolidation inside ProximaDB as a bespoke subsystem.** Rejected:
  duplicates the orchestration layer the ecosystem already standardizes on, and violates reuse-first.
* **Vendor mem0/agentmemory code into the repo.** Rejected: license/maintenance coupling (agentmemory is
  dormant) and it would invert the layering — ProximaDB is the backend, not the orchestrator.
* **Add a first-class `session_id` record field now.** Deferred: `props["session_id"]` covers the need
  without a record-shape migration until a query-path justification exists.
