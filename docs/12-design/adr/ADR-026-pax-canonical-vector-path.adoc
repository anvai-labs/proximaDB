== Context

ProximaDB carries two vector-search architectures side by side:

* **PAX stacked quantization (write-side, new).** A segment encodes, at write
  time, a RaBitQ (~30x) tier-1 column, a co-located SQ8 (4x) rerank column, and
  an optional f32 tier-3. The read cascade is zone-prune -> RaBitQ rank ->
  SQ8 rerank -> top-k. This is the 2025-2026 industry-standard pattern: stored
  write-side codes + read-side rerank (Lance v2, Qdrant, Milvus, Weaviate,
  pgvector all converged here).
* **Legacy read-side progressive search.** The NOVA / VIPER / HELIX / SWIFT /
  RAPTOR engines re-quantize the *query* per stage (Binary -> INT8 -> PQ -> FP32)
  over largely raw vectors. This is an older, scan-centric design: six divergent
  copies, no storage savings (raw f32), and re-quantizing the query every stage.
  The AXIS graph index (HNSW / IVF) already does the candidate reduction these
  pipelines were invented to provide.

**What is wired today.** The live ANN path is `query -> search_vectors_unified ->
AXIS (HNSW/IVF) -> SST mixed-format segment reads`. AXIS carries recall; PAX
quantization is **flag-gated OFF** (`PROXIMADB_PAX_VECTOR_SEGMENTS` +
`PROXIMADB_PAX_VECTOR_QUANT`, both default off). PR #262 already stripped the
vestigial AXIS coupling from every engine except SST + Orion. SST/HELIX/NOVA/
VIPER are *live* production engines; SWIFT/RAPTOR are dead and
`experimental-engines`-gated. `TurboQuant` (ADR-021) is an *experimental,
training-free, data-oblivious* parallel quantizer — a future tier-1 candidate,
not a cascade member today, and unrelated to Qdrant's same-named binary+SQ8 stack.

== Decision

Standardize on **one** vector path: **AXIS graph (HNSW/IVF) + PAX stacked
quantization (RaBitQ -> SQ8 -> f32).** Retire the legacy read-side progressive
engines and **fold** their few genuinely-valuable design ideas into PAX rather
than maintaining six divergent pipelines. Treat TurboQuant as an optional future
PAX tier-1, gated behind its own validation.

=== Measured evidence backing the decision (BENCHMARK_EVIDENCE.toml)
* **Recall gate holds at scale.** The RaBitQ -> SQ8 cascade keeps `recall@10
  >= 0.93` at both N=1k (0.934) and N=100k (0.932, with a 1000-wide stage-1
  pool). The gate *caught* a real regression: REFINE=200 at N=100k gave 0.708.
  Promoted to a develop->qa ratchet (qa-gate `pax-recall-ratchet`).
* **Mixed-read-safe.** Legacy `ProximaBlocks` and new PAX segments coexist and
  both read back through the single `read_segment_records` router (magic-byte
  detected) — the property that makes a staged default-on flip safe.
* **Footer-cache fragmentation finding.** Footer caching works (95% hit) but
  naive per-block ranged reads fragment into one GET per block. Validated across
  clouds in `PAX_RANGED_READ_MULTICLOUD_COST_2026_06_25.adoc`: in the real
  deployment (k8s colocated in-region with the store, so storage-read egress is
  *free*), cost is **GET-count × the locality-independent per-request fee**
  (Azure ~10× cheaper than S3/GCS); access is **selective, not full-scan**, so
  the fix is **range coalescing + block pruning (TD-151)** of the reads a query
  issues, with **per-modality geometry (TD-155/TD-157)** — point-lookup modalities
  want small row-groups (avoid over-read), scan/aggregate modalities want large
  row-groups + projection + pruning toward the 8-16 MiB optimum.

== Rollout (staged; storage-format mandate #8 — mixed-read-safe, default-off until the ratchet is green)
. **Recall gate** — develop->qa ratchet + N=100k harness (done, PR #331).
. **Staged prep** — mixed-read coexistence proof + rollout docs, no flip (done, PR #335).
. **Default-on flip** — flip the write default to PAX+RaBitQ behind the green ratchet; ship default-off one release, then flip (TD-150).
. **Folds** — Hilbert locality (TD-153), hierarchical zone maps (TD-154), range-coalescing + pruning (TD-151) into PAX; per-collection `VectorQuant` config (TD-155).
. **Retire dead engines** — remove SWIFT + RAPTOR atomically (internal enum + proto variants) at v1.0 (TD-152).

== PAX across modalities (the shared columnar substrate)

This ADR's concrete decision is the **vector** path, but PAX is not vector-only.
The PAX *block format* is modality-neutral columnar storage: it carries any
`ProximaRecord`-shaped data — document bodies, graph nodes/edges, observability
spans, relational rows (ADR-024's single canonical type makes this clean). The
**stacked RaBitQ/SQ8 quant tiers are an embedding-column feature**, not a
segment-level requirement; non-vector modalities use PAX blocks with zstd + zone
maps + their own column types and no quant tiers.

* **Recommended approach.** PAX is the single **internal** columnar substrate
  across record modalities ("vertical inside, standard outside" — co-design
  mandate #4). The warehouse/relational *interop seam* stays Parquet + Iceberg
  (DataFusion) so external tools read standard Parquet; PAX serves the hot /
  record / ANN paths that benefit from the vertical co-design. One internal
  columnar format, reused across modalities; vector quant is an opt-in embedding
  layer; Parquet at the boundary. This reuses the block-format + segment code
  (already largely modality-neutral via `ProximaRecord`) and lets each modality
  add its column types + zone maps rather than a parallel format.
* **Implication.** The configurable-geometry + tuning work below applies to
  *every* modality stored in PAX, not only vectors.

== Configurable block / row-group / stripe geometry

Block size, row-group size, and stripe size are the co-design I/O-granularity
tunables that trade per-request overhead vs over-read. The footer-cache
fragmentation finding makes the case concretely: a 16 KiB target block size
fragmented a column scan into ~6,000 small ranged GETs (fee-dominated) where a
handful of ~8-16 MiB GETs would sit at the S3 cost-throughput optimum.

* **Make them configurable** (per-collection and per-deployment), surfaced
  through the same config seam as `VectorQuant` (TD-155). Today the writer takes
  a fixed `target_block` (e.g. `build_segment_bytes` passes `16 * 1024`); expose
  it (TD-156).
* **Default by storage class.** Small geometry (tens of KiB) for local / embedded
  (cheap random read); large geometry (8-16 MiB row groups) for object storage
  (coalesce toward the per-request-fee + throughput optimum). The
  `SegmentReadStats.range_gets` / average-GET-size signal (co-design §2.1) is the
  ratchet that proves a geometry change actually reduces request count.

== Tuning hierarchy: user override -> adaptive -> learned

Who picks the geometry / quant tier / recall target? Three layers, in order of
sophistication — all subordinate to *"cost from measured quantities, not static
heuristics"* (co-design mandate):

. **User override (static, explicit).** Per-collection config: quant tier, block
   / row-group size, recall target — the deterministic escape hatch for a user
   who knows their vector dim, selectivity, and SLA (TD-155). Always available;
   always wins.
. **Adaptive (policy-driven from the measured per-query trace).** The system
   picks geometry / quant from observed workload + storage class — quant tier <-
   recall target + collection size + dim; block size <- storage class; nprobe /
   ef <- search-effort. The co-design `Cost(q)` loop is the substrate; the
   per-query I/O trace (`SegmentReadStats`, `io_trace`) is the input (TD-157).
. **Learned (RL / ML cost model — future).** A learned policy over the trace
   distribution that tunes geometry, quant tier, prefetch depth, and routing to
   minimize the measured dominant cost (I/O round-trips). Long-horizon: it needs
   the trace substrate + a stable objective + safety rails (recall ratchet as the
   floor). Flagged as a future ADR once (1) and (2) are in; **not** built now.

*Current state (audited 2026-06-26) — the gap to "enough" for geometry tuning:*
* **Trace: partial.** `io_trace` + `SegmentReadStats` exist and the protocol/
  scheduler layer emits route + bytes; block-level `record_range_gets` fires in
  the RaBitQ cascade (`segment_format`) and `record_store`. **But it is NOT
  emitted on the live AXIS/SST read path** (which reads whole-byte local-FS), so
  the per-query GET-count / bytes-per-block signal geometry tuning needs is not
  collected in production. The C0 cloud-I/O-trace gap is open for the live read.
* **Adaptive/ML: narrow, latency-only, not geometry-aware.** `src/automl/` + the
  AXIS `adaptive_engine` ARE wired and running, but they (a) tune HNSW/IVF index
  params (`ef_search`/`nprobe`/`M`/`nlist`) **plus a defined quantization
  param-space** (`quantization_level`, `codebook_size` — `automl/tuning.rs:902-920`),
  all driven by **latency heuristics (p50/p99)**, (b) do **not** consume `io_trace`,
  and (c) do **not** tune **storage geometry** (block/row-group size). So the tuner is
  *latency-driven, not trace/geometry-aware*: quant is in its search space but is not
  refined from the measured I/O trace, and geometry is not tunable at all today.
  (Corrected 2026-06-25 — the earlier "do not tune quant" was inaccurate; see
  `docs/history/planning/PAX_SUBSTRATE_DESIGN_PLAN_2026_06_25.adoc`.)

*Sequencing (measure before you tune — co-design mandate):*
. **TD-158** — wire block-level `range_gets`/bytes into the live AXIS/SST read
   path (+ the object-store ranged reader when TD-151 lands). Prerequisite
   observability; without it there is no signal to tune against.
. **TD-159** — extend the adaptive engine to consume `io_trace` (not just
   latency), add **storage geometry** (block/row-group, TD-156) to its tunable set,
   and make quant tuning **trace-driven + recall-ratchet-gated** (today quant is in
   the param-space but tuned from latency only, and geometry is absent).
. Then **TD-157** (full adaptive geometry/quant) and the future RL ADR (layer 3).

The recall ratchet is the safety floor under all of it: no tuning layer may
regress measured recall.

== Non-goals
* **Do NOT retire NOVA/VIPER/HELIX** — they are *live* production engines (no
  feature gate). Retirement needs a deprecate -> migrate -> remove plan and is
  larger than it looks (43 `StorageEngineType` match sites / ~19 files). Only
  their *design ideas* are folded into PAX; the engines stay until a migration.
* **Do NOT promote TurboQuant** out of `experimental-turboquant` until its SIMD
  kernels (P4) and real-dataset recall validation (P9) land.

== Consequences
* One vector path to optimize, test, and reason about — instead of six.
* The recall ratchet + mixed-read-safe guarantee become the hard gates for every
  future PAX format change.
* Read-path cloud-economics improvements must be *measured* (the footer-cache
  lesson): bytes AND GET count, against the S3 cost model — not assumed.
