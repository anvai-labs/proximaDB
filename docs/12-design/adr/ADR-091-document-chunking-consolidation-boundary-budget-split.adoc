== Context

=== The same five algorithms are implemented nine times, and the best one is never called

ADR-029 recorded the document chunker as existing three times and declared it out of scope. A census
across the four repositories finds it worse than that. Measured, with dead code separated from live:

[cols="3,1,3",options="header"]
|===
| Implementation | Lines | State
| ProximaDB SDK `chunking_strategies/` (7 text strategies) | ~2,400 | **Live**, and consumed by anvaiops
| victor-rag `chunker.py` + `handlers.py` | 735 | **Live** in the vertical; two unrelated chunkers in one package
| anvaiops connector-sdk `chunking.py` | 357 | **Live**, 20+ connectors — but it *delegates to the ProximaDB SDK*
| ProximaDB Rust `text_search/{text_storage,sdp}.rs` | ~1,400 | Tests only, no product caller
| ProximaDB Rust `proximadb-embedding/chunker.rs` | 127 | **Zero callers**; its `Heading` variant falls back to paragraph
| Victor `framework/ingestion/` | 1,415 | **Dead** — zero importers; a *verbatim fork* of victor-rag's chunker
| Victor `core/chunking/` | 1,559 | **Dead** — reachable only via a deprecated shim with no registered entry points
| Victor `processing/native/chunking.py` | 258 | **Dead** — zero callers, including tests
| Victor `rust/…/chunking.rs` | 541 | **Half dead** — built and shipped as `victor_native`; its 4 line-aware functions are live, its 5 document functions never called
|===

Consequences of that fan-out, each independently verified:

* **Sentence splitting exists eight independent times**, twice inside the ProximaDB SDK alone. The best
  implementation — abbreviation-aware, in compiled and shipped Rust — is **never called**, while five
  Python regexes do the same job worse.
* **Three incompatible strategy vocabularies.** anvaiops maintains a hand-written translation table with
  the comment "ProximaDB has no heading strategy". The Rust `ChunkStrategy` is persisted per-collection
  in the catalog and offers a `Heading` policy that neither the server implements nor the SDK can
  produce.
* **17 distinct `Chunk`-shaped dataclasses** and **six separate extension-to-doctype maps** (18, 26, 35,
  44 entries, plus two more).
* **The defects reach the SaaS product.** anvaiops's connector SDK calls
  `proximadb_sdk.chunking.TextChunker` directly, so ProximaDB's chunking correctness *is* anvaiops's
  ingest correctness for 20-plus sources. Its Jira connector selects the strategy measured losing up to
  100% of a document; its delegation hardcodes `source_id="doc"`, so every document in every tenant
  emits colliding chunk ids.

=== The finding that decides this ADR

ProximaDB and victor-rag are **independent implementations** — zero shared regex literals, zero
identical docstrings, disjoint helper vocabulary, different return contracts. And they contain the
**same bug**: a span below `min_chunk_size` is *dropped* rather than merged into its neighbour, so both
return **zero chunks** on header-dense Markdown — a silent, total loss — from entirely unrelated code.

When two independent teams produce the same defect, it is not a coding error. It is a **missing
specification**. Nobody ever wrote down that chunking must be total over its input. That is the artefact
this ADR must produce; a fourth rewrite would reproduce the same bug a fourth time.

=== The mechanical cause of the fan-out

`victor_contracts` exposes a live `TextChunkerProtocol` with two implementations and real consumers — and
**no document-chunking port at all**, only an untyped, deprecated `register_chunker(chunker_instance:
Any)`. Where a port existed, the ecosystem converged (code chunking, via ADR-029). Where none existed,
five codebases forked. The absence of the port is the cause; the nine implementations are the symptom.

== First principles

Five axioms. Each one, applied, kills a measured defect — which is the test of whether an axiom is
load-bearing or decorative.

. **Chunking is a total, order-preserving partition of the input with declared overlap.** Every byte of
  the input lies in at least one chunk; bytes lie in more than one chunk only where overlap was
  requested. *Kills:* the min-size drop in both implementations (silent total loss on header-dense
  Markdown), the un-headed-body gap (29% loss on prose), the omitted heading line, and the
  `max_chunk_size` overrun — because a chunk exceeding the cap means the partition must be *refined*,
  not that the cap is advisory.
. **A chunk is a span; its text is derived.** The span is primary and must be exact: `source[span] ==
  chunk.text`, byte-for-byte, with the basis declared. Text cannot reconstruct a span, so a chunker that
  rebuilds text by joining pieces has destroyed its own primary datum. *Kills:* the offset defect in six
  of seven SDK strategies and the fabricated HTML/JSON offsets in victor-rag, both of which arise from
  exactly that join-then-guess pattern.
. **The size budget belongs to the model, not to the storage layer.** Characters are a proxy that fails
  per-tokenizer and per-language: English runs ~4 characters per token, CJK closer to 1, so a
  character-sized chunker silently emits 4× the intended tokens on Chinese text. The canonical budget is
  therefore **tokens**, counted by the tokenizer of the collection's configured embedding model, with
  character sizing retained only as a compatibility mode. *Kills:* the CJK failures on both sides and the
  "4 characters per token" assumption hardcoded in victor-rag.
. **Structure is a boundary source and a metadata contribution — never a peer strategy.** "Heading" is
  not a sibling of "sliding window": it proposes *where* a split may occur and *what the span means* in
  the document's hierarchy, then the same segmenter enforces the budget. Modelling it as a strategy is
  precisely what forced anvaiops's translation table and left `Heading` declared-but-unimplemented in the
  Rust enum. *Kills:* the three-vocabulary problem, structurally rather than by reconciliation.
. **Isolation is structural, and chunk count is the billable quantity.** Chunking runs per (tenant,
  document) and must carry `TenantContext` at the point its output becomes records, because chunk count ×
  dimension is what the tenant is charged for — in embedding once and in storage forever.

=== The architectural consequence: split boundary proposal from segmentation

Axioms 1–4 together say the concept has been mis-factored everywhere. One responsibility is *proposing
candidate boundaries with meaning* — sentence ends, paragraph breaks, heading spans and their hierarchy
path, code-fence limits, table row groups, JSON/XML node edges, embedding-distance breakpoints. A
separate responsibility is *choosing the final cut* to satisfy a token budget with overlap while keeping
the partition total and the spans exact.

ProximaDB already has this shape and does not know it. `ChunkingStrategyInterface.preferred_boundaries()`
is the boundary-proposal seam, and `TokenBudgetStrategy` is the segmenter — and, not coincidentally, the
token-budget layer is the only part of the subsystem that survived audit with its offsets intact,
because it slices the *original* text rather than rejoining pieces. The eight "strategies" collapse into
a set of boundary sources plus **one** segmenter.

This is also what makes the vocabulary problem evaporate rather than get negotiated: anvaiops's
`HEADING` stops being a strategy needing a translation-table entry and becomes
`boundary_sources=[Heading(levels=[1,2])]`, composable with any budget.

== Co-design: the dimensional cost terms chunking actually moves

Chunking is not a text utility; it is the **write-side cost allocator**. It decides how many vectors
exist, which fixes cost in four dimensions before the first byte is stored.

[cols="1,2,3",options="header"]
|===
| Dim | Cost term | How chunking moves it
| D4 | **KEU** — embedding, paid once per chunk | Chunk count is the multiplier. Duplicate and near-duplicate chunks are pure waste; the Rust SDP pipeline's stage-4 topic dedup is an unused KEU lever sitting in the tree.
| D1 | **KSU** — GB-month, paid forever | Chunk count × dimension. Over-chunking is the most expensive reversible decision in the system: re-chunking means re-embedding the corpus.
| D1/D3 | **I/O round-trips** — the dominant term for a cloud DB | Chunk count sets vector count, which sets ANN probe count and GETs per query. "More, smaller chunks" is *not* free; it trades recall for a permanently higher read cost.
| D2 | **KOU** — outgress at pgwire/REST/Flight | Chunk text is returned in results. Oversized chunks inflate every result payload, which is why an unenforced cap is a metered cost and not only a model-limit risk.
|===

Two obligations follow from the co-design mandate, and both are requirements of this decision rather
than nice-to-haves:

* **Trace before you tune.** The chunker MUST emit a per-document, tenant-tagged trace — `bytes_in`,
  `bytes_covered`, `bytes_duplicated`, `spans_dropped`, `chunk_count`, `tokens_out`, `boundary_source`
  histogram. Every measured defect in this ADR's evidence base would have been visible as a trace field:
  `bytes_covered < bytes_in` is the loss bug, `spans_dropped > 0` is the min-size drop. A chunker that
  cannot report its own coverage is unauditable, and today none of the nine can.
* **Meter every dimension.** The trace is the pre-embedding KEU/KSU estimate, so a tenant's ingest cost
  becomes predictable *before* the spend, not reconcilable after it.

**Vertical inside, standard outside.** Boundary sources, the segmenter and the trace are internal and
free to change. What is stable is the port, the `TextChunk` span contract, and the metered trace schema.

== Decision

=== D1 — ProximaDB owns document chunking; it is canonical

Ratify what is already true: anvaiops's connector SDK calls `proximadb_sdk.chunking.TextChunker`
directly. ProximaDB is the de facto owner, which is exactly why its defects propagate into SaaS ingest.
Making it the *de jure* owner means the correctness work has one home and one test bed.

=== D2 — Define the missing document-chunking port, in ProximaDB, mirrored into `victor_contracts`

The counterpart to the working `TextChunkerProtocol`. It carries the axioms as its signature, not as
documentation:

* `BoundarySource` — proposes `(span, kind, meaning)` candidates; `meaning` carries the heading path, the
  table identity, or the JSON pointer. Composable; several may run over one document.
* `Segmenter` — consumes candidates plus a `TokenBudget` and returns a **total** partition of exact
  spans with declared overlap.
* `ChunkTrace` — the metered emission above, non-optional.

Defined in ProximaDB because ProximaDB is canonical; re-exported from `victor_contracts` so Victor code
depends on a neutral name. Dependency direction: consumers depend on the SDK, which is already true for
anvaiops and adds no new edge for Victor (`victor-rag` currently has zero ProximaDB references and would
gain one optional extra).

=== D3 — One segmenter, many boundary sources; the three vocabularies converge on that model

Retire the strategy enums as the primary interface. `SLIDING_WINDOW` and `FIXED_SIZE` become the
degenerate case (no boundary source); `SENTENCE`, `PARAGRAPH`, `SEMANTIC`, `SEMANTIC_EMBEDDING` and
`HEADING` become boundary sources; `RECURSIVE` disappears as a concept, since a cascade is what a
segmenter does natively when candidates are exhausted. The existing enum stays as a compatibility facade
that maps onto source sets, so no caller breaks.

=== D4 — The invariant suite and the corpus are part of the contract, not of the implementation

Ship them as a shared fixture package that every consumer runs — ProximaDB, victor-rag, anvaiops. A port
that is not jointly tested is a suggestion. This is the direct remedy for two independent teams having
produced the same bug, and for the audit finding that each suite chose inputs flattering to its own
implementation.

=== D5 — Pull down what is genuinely built; build the rest, and do not mistake one for the other

[NOTE]
====
**Corrected 2026-08-18.** As accepted, this decision claimed three of four missing capabilities
already existed in the Rust SDP pipeline and needed only wiring. Reading `sdp.rs` disproves it: the
four stages are *named* for those capabilities and implement none of them. Stage 1 is
`text.split("\n\n")` (its own comment says a real one "would use a Markdown/HTML parser"); stage 2
prefixes every chunk with the first chunk's first line, which is a document title, not per-chunk
contextual retrieval; stage 3 writes a metadata flag; stage 4 merges neighbours under a hardcoded
100-character threshold with no topic signal. `use_sdp` defaults false and nothing sets it true.

The distinction changes the plan, not just the wording: *stranded* means wire it up, *absent* means
design, build and evaluate. Executing D5 as originally written would have ported stubs under names
that promise real capabilities — worse than starting fresh, because the names would have suppressed
the design work. Detail in TD-CHUNK-3.
====

Genuinely built and merely in the wrong layer — these become boundary sources or post-segmentation
passes behind the D2 port:

* heading-aware splitting with a hierarchy path — **anvaiops connector-sdk**, in production use
* the abbreviation-aware sentence splitter — Victor's shipped Rust `victor_native`, never called

Genuinely absent, and therefore new work requiring an eval rubric before implementation:

* context-conditioned enrichment (contextual retrieval)
* topic-aware deduplication
* semantic boundary refinement
* **parent-document / small-to-big**, which ProximaDB is uniquely placed to do because the parent
  edge is an ORION graph edge rather than a duplicated metadata copy

=== D6 — Retire the duplicates, dead code first

Roughly 3,900 lines are deletable before any behaviour changes: Victor's `framework/ingestion/` (zero
importers), `core/chunking/` (deprecated shim only), `processing/native/chunking.py` (zero callers), the
unbuilt second Rust chunker, and ProximaDB's zero-caller `proximadb-embedding/chunker.rs`. Stop
persisting a catalog `Heading` policy that silently degrades to paragraph.

=== D7 — A second seam for what happens AFTER the partition: the three faces of a chunk (added 2026-08-19)

D3's grid/measure/budget split covers every capability that decides **where a cut lands**. Executing
TD-CHUNK-3 showed it covers nothing else, and that three of the five inventory items move no cut at
all. Forcing them into the grid is what made them look like unrelated features.

They are one shape. A chunk conflates three things, and each remaining capability is a deliberate
divergence between two of them:

[cols="1,3,2",options="header"]
|===
| Face | What it is | Cost term
| `span` | which part of the document this chunk **is** | -- (axiom 1)
| `embedded` | the text sent to the model to make the vector | **KEU**, paid once
| `retrieved` | the text a caller gets back for generation | read cost, recall
|===

* **heading paths** -- touches neither; pure metadata, which is *why* it is free and why it is the
  one capability that defaults ON.
* **dedup** -- decides whether a span is materialised at all (KEU and KSU down).
* **context enrichment** -- `embedded != span` (KEU up).
* **small-to-big** -- `retrieved != embedded` (KSU up, read cost down).

**Decision: one `ChunkPass` port, each pass declaring exactly one face.** Ordering follows from the
faces (`metadata -> selection -> embedded -> retrieved`) and configuration order is *ignored*. Each
adjacency is forced rather than conventional: a survivor must keep the heading path of the duplicates
it absorbed; enriching a chunk that is about to be dropped spends KEU on nothing (this is also why
dedup must be lexical -- the decision has to precede the spend); linkage refers to what survives.

**The face is declared and then checked.** A pass that declares `METADATA` and quietly drops a chunk
is deleting tenant content, and its own tests would never catch it because they assert what it means
to do. `run_passes` verifies after every pass, which makes the abstraction load-bearing rather than
decorative -- the same move `ChunkingStrategyInterface.__init_subclass__` already makes for
`max_chunk_size`.

**Why this is a seam and not four flags.** The two shipped capabilities were `if` statements inline in
`TextDocumentProcessor.chunk`, each with a paragraph of comment explaining its position. Four flags
have twenty-four orderings and no rule; the faces give one.

**Consequence worth stating: the KEU question becomes askable.** With one text per chunk, "what does
enrichment cost" could only be estimated from the template. `enrichment_tax` (`embedded_chars /
span_chars`) reports the multiplier actually applied, per document -- the denominator TD-CHUNK-3
requires enrichment to be gated on.

**Links are emitted as intents, not written.** Small-to-big needs a parent larger than its child.
Copying the parent's text onto each child is the obvious implementation and multiplies KSU by the
fan-out. Parents are emitted once, referenced by `parent_id`, and the relationship leaves as a
`ChunkEdge` for the caller to materialise -- an ORION edge in the server, which is the linkage this
database can offer that a pure vector store cannot. It also keeps the chunking layer free of any
client or transport, as its package docstring promises.

**The rubric's boundary is part of the decision.** `conformance/evals.py` can gate small-to-big
(measured: containment 0.75 -> 0.875 on the returned unit, at ~1.74x KSU) and **structurally cannot
gate enrichment**, because enrichment leaves every span identical and every metric there scores
exactly those. A rubric that reacted would have to score a model's output, and a red gate could then
no longer be attributed to chunking -- the property the harness exists to protect. Enrichment's recall
gate belongs in the ANN harnesses; this one owns the cost half of the ratio and says so. Stating the
boundary is better than filling it with a proxy metric.

== Why code chunking leaves the SDK but document chunking stays

This asymmetry against ADR-029 is the crux, and it must be principled rather than convenient.

**A code chunker encodes knowledge of a language ecosystem** — which node type names a function in the
Kotlin grammar, how Ruby spells a module. That knowledge is unrelated to how records are stored, changes
on the grammars' release cadence rather than the database's, and belongs to the consumer that maintains a
Code Property Graph. ADR-029 is right.

**A document chunker encodes knowledge of the store's own record model.** Three properties make it
inseparable:

. **The span is the inverse of the read path.** A stored chunk must map back to its provenance in the
  source document. Exactness and totality are properties of the store's round-trip guarantee — the same
  class of invariant as the read/write correctness mandate, not an application concern.
. **The budget is a function of catalog state.** The correct chunk size depends on the collection's
  configured embedding model and its tokenizer, which is persisted in the ProximaDB catalog and surfaced
  via the embedding-config endpoint. Only the database knows it. A chunker outside the database must be
  *told* its budget and will drift when the collection is re-configured.
. **The output is the billable quantity.** Chunk count sets KEU and KSU. Metering is structural and
  fail-closed at the I/O boundary, so the component that decides the count must sit inside the boundary
  that meters it.

The line is therefore: **domain knowledge about a source language leaves; knowledge about the store's own
record, budget and meter stays.** Code chunking is the former, document chunking the latter.

== Alternatives considered

* **A1 — Extract `victor-docchunk`, mirroring ADR-029.** ADR-029's own straw man. Rejected: it inverts
  the boundary for a capability that *is* generic-DB business by the three tests above, adds a release
  pipeline, and moves the code away from the only consumer that already treats it as canonical. The
  symmetry with ADR-029 is aesthetic, not architectural.
* **A2 — Rust-canonical: implement once in the server, bind Python to it.** Genuinely attractive — the
  best splitter is already Rust, server-side chunking removes a client round-trip, and the budget lives
  next to the catalog. Rejected **for now**, on two grounds: the SDK must chunk client-side with no
  server (that is its main use, including offline ingest), and the Rust chunkers are unproven — both are
  currently unconsumed and one silently degrades. Explicitly retained as the Phase-3 option *behind the
  D2 port*, which is chosen so that swapping the segmenter for a native one is a backend change and not
  a rewrite. This mirrors ADR-052's posture: keep the seam, hold the option open, do not make it a build
  target.
* **A3 — Keep victor-rag independent; document the overlap.** Rejected: the two independent
  implementations already converged on the same bug. Documentation does not fix a missing specification,
  and victor-rag has no tests for its chunker at all.
* **A4 — Do nothing.** Rejected: the fan-out is eight sentence splitters and nine implementations, the
  known defects reach paying-tenant ingest, and both prior ADRs already deferred this once.

== TDD mechanism

The order is not negotiable: **the suite, the corpus and the trace land first, red, with their failures
published.** The audit that motivated this ADR found 426 passing tests that caught none of the defects
because they asserted execution rather than invariants; writing the implementation first would reproduce
exactly that.

=== Phase 0 artefacts, written before any production change

**The invariant suite**, parameterised over every boundary-source set × corpus, asserting the axioms:

. **Totality** — every non-whitespace byte of the input is covered by ≥1 chunk. *(axiom 1)*
. **Exactness** — `source[span] == chunk.text` under the declared basis, including non-ASCII. *(axiom 2)*
. **Cap** — `tokens(chunk) <= budget` for every chunk, counted by the collection's tokenizer. *(axiom 3)*
. **Non-empty** — non-empty input yields ≥1 chunk; a document below the minimum is emitted as one short
  chunk or rejected loudly, never dropped. *(axiom 1)*
. **No containment** — no chunk's span is strictly inside another's, outside declared overlap.
. **Batch/stream equivalence** under randomised piece sizes — the fuzz that found 303 mismatches the
  hand-picked fixtures could not, because they always placed a period before a capital.
. **Config safety** — no configuration hangs. victor-rag infinite-loops whenever `min_chunk_size <
  chunk_overlap`; ProximaDB's normalisation makes that unreachable. The suite encodes the property so
  neither can regress.
. **Idempotence** — re-chunking a chunk with the same budget is a fixed point.

**The corpus** is part of the contract, and its composition is chosen so each entry has previously caught
a real defect: prose, header-dense Markdown, CJK, boundary-free text, whitespace-heavy scraped output,
sub-minimum documents, table-heavy Markdown, code-fenced Markdown, HTML, JSON. Every consumer runs the
same bed; no implementation may bring its own flattering inputs.

**The trace schema**, because an invariant nobody can observe in production will regress there.

=== Evals, for the parts tests cannot cover

Boundary quality is a ranked, non-deterministic surface, so per the evals mandate it needs a rubric, not
an assertion. Gate on both **output** (does retrieval return the span that answers the question) and
**trajectory** (was the boundary source chosen the right one for the document's shape). Measured as
recall@k against the f32 baseline on the fixed corpus, threshold-gated in CI, with prompts and suites
versioned in the PR that changes behaviour.

=== Ratchet

Invariant counts and eval thresholds only go up. A change that regresses either fails CI — the same
discipline as the TPC-H/TPC-DS and ANN-recall ratchets, and the mechanism that makes the specification
enforceable rather than aspirational.

== Migration — phased, mixed-read-safe, default-OFF

**P0 (TD-CHUNK-1)** — invariant suite, corpus, trace. All red. Publish the numbers; this ADR's evidence
base is the baseline.

**P1** — fix the SDK to green. Most are plain bug fixes needing no gate. The **exception is the offset
basis**: `start_pos`/`end_pos` are persisted by `document_processor.py`, so changing their meaning is a
stored-contract change. Per the storage-migration mandate it ships as an *additive* marker
(`offset_basis`), readers default to the legacy interpretation when it is absent, and there is no flag
day. TD-CG2 sets the same contract on the code path first.

**P2 (TD-CHUNK-2)** — land the port and the boundary/budget split behind the compatibility facade. Migrate
anvaiops (drop its translation table; `HEADING` becomes a boundary source) and victor-rag. Fix
anvaiops's hardcoded `source_id="doc"` while the seam is open.

**P3 (TD-CHUNK-3)** — pull down heading paths, SDP context enrichment and topic dedup; evaluate the Rust
splitter and the native segmenter behind the port. Build parent-document/small-to-big on ORION edges.

**P4 (TD-CHUNK-4)** — retire the duplicates, dead code first.

== Consequences

* **Positive:** one specification, one segmenter, one test bed; the defects stop reaching tenant ingest;
  two genuinely-built capabilities become available without being rebuilt (see the D5 correction — three
  more turned out to be absent rather than stranded); chunk-count cost becomes observable
  and predictable per tenant; ~3,900 dead lines deleted; the native-segmenter option stays open behind a
  seam.
* **Negative:** ProximaDB takes on ownership it could have exported, which sits in tension with
  ADR-029's "the SDK gets smaller and stays neutral". The tension is resolved by arithmetic and by the
  asymmetry argument: TD-CG2 removes ~4,200 lines of code-domain parsing, while this ADR adds a port and
  a segmenter to strategies that already exist. Net, the SDK shrinks substantially and becomes *more*
  neutral, because what remains is store-model logic rather than language-ecosystem logic.
* **Negative:** a cross-repo port means coordinated releases, and the shared corpus means a consumer can
  be broken by a fixture addition. Mitigated by the ratchet being additive-only.
* **Neutral:** the strategy enums survive as a facade indefinitely; no caller is forced to adopt the
  boundary/source model to keep working.

== Verification

* **Invariants:** the eight properties above, green across every boundary-source set × corpus entry, in
  the feat→develop lane — the tier that currently does not run the chunking suite at all.
* **Parity:** the consolidated chunker reproduces each donor's output on the shared corpus where the
  donor was correct, and provably differs where it was not, with each difference named in the PR.
* **Cost:** the trace shows `bytes_covered == bytes_in` and `spans_dropped == 0` on the whole corpus, and
  chunk count per document does not regress against the pre-migration baseline — the KEU/KSU guard.
* **Evals:** recall@k within tolerance of the f32 baseline, thresholds ratcheted.
* **Boundary:** `scripts/check_oss_boundary.py` stays green; `TenantContext` present at every seam where
  chunks become records.
* **Truthfulness:** chunking gains a support-tier row in `docs/SUPPORTED_SURFACE.adoc`, which it has
  never had — the governance gap that let a subsystem this size ship with 57 red tests and no declared
  tier.
