== Context

The directive is to **remove v1 entirely**. Today ProximaDB carries two models: the v1 proto package (`proto/proximadb/v1/` — 17 gRPC services, the `CollectionConfig`/`VectorRecord`/`SearchQuery` internal types, ~2,940 references across ~491 files) and the native runtime model (`ProximaRecord`/`ProximaValue`/`ProximaType`, surfaced on the wire as `proximadb.v2`, with the typed catalog `CatalogTableSchema` as authority — ADR-048).

The decisive observation: **most of the core is already native.** The WAL (`CanonicalOperation::RecordUpsert { record: Box<ProximaRecord> }`), the record-store trait (`TableRecordStore::write_mutations`), the runtime ports (`RecordOpsPort`, `handle_record_batch_for_tenant`), pgwire/SQL (catalog + Arrow), the embedded PyO3 surface, and the cluster plumbing all run `ProximaRecord` natively. v1 is load-bearing in only three places: (1) the **storage engines** (SST/VIPER/HELIX/NOVA read/write v1 `VectorRecord` internally + serialize v1 proto on disk — the keystone, ~60% of the effort); (2) the **v1 API edge** (17 gRPC services — only 2 proto-deprecated; REST `/api/v1/*` always-on); and (3) **~11 admin/cluster/specialized v1 services with no v2 home** (Catalog/Security/Observability/Consensus/Replication/SearchFanout/Health/Streaming/Relations/Rank/HybridSearch). The collection/schema domain retires its v1 derivation via ADR-048.

So the migration is **convergence, not a rewrite** — finish the spokes that still leak v1; the hub already runs the native model.

== Decision

**There is exactly one canonical data model: `ProximaRecord` / `ProximaValue` / `ProximaType` (ADR-024), persisted via the typed system catalog (ADR-048), surfaced on the wire as `proximadb.v2`.** The v1 proto package ceases to be a model — it survives only as a pure edge adapter that translates legacy wire into native shapes, and is deleted entirely at M4.

**D1. Runtime is the model; v1 proto is an edge adapter.** Internal trait signatures, on-disk formats, and the catalog reference only `ProximaRecord` / `CatalogTableSchema`. v1 proto survives solely inside `network/{grpc,rest}/v1/*` translation layers.

**D2. Mixed-read-safe at every step.** No flag-day. Legacy v1 SST files decode on read until naturally compacted away (mirrors the ADR-045 durable-core/overflow carrier precedent).

**D3. Downward-only ratchet (TD-123).** `scripts/check_v1_proto_usage.py --mode no-regression` makes the v1-reference count monotone non-increasing; each phase lands behind it. The count is the progress signal, not a guess.

**D4. Bounded PRs targeting `develop`.** Each milestone decomposes into PRs small enough to review and revert independently.

**D5. ADR-019 closure at M4.** When the ratchet reads ≈ 0, delete `proto/proximadb/v1/`, the conversion seam (`proxima_record_to_vector`), and the v1 edge adapters in one final PR (the TD-121 gate).

**D6. Adjacent implementation work moves toward v2/native, never deeper into
v1.** A feature that encounters a v1 DTO or port must not add new identity or
cache semantics to that DTO. It either uses the existing adapter temporarily or
introduces a bounded native/v2 seam, and the no-regression ratchet must remain
green. Catalog `object_id: u64` is the authoritative collection identity;
string `Collection.id` fields are transitional views, not a second authority.
This rule does not waive mixed-read support for durable v1 segment bytes.

== Considered alternatives (rejected)

* **Big-bang rewrite.** Re-implement storage/API on v2 from scratch, cutover on a flag-day. Rejected: violates the no-flag-day constraint; legacy on-disk v1 SST files demand mixed-read for years; ~2,940 references make a single coherent change un-reviewable; and the converged PAX/block-format write path would be discarded.
* **Indefinite dual-model (status quo).** Keep v1 as a permanent second model behind `enable_grpc_v1_compat`. Rejected: the cohesion costs ADR-048 D1 names (re-derivation, drift, stringly-typed introspection) recur at the data layer; two models double the test surface and foreclose ADR-019 relational completeness. TD-121 already dates the hard removal.

== M0 — the enabling slice

* **M0-a (this PR):** revive `scripts/check_v1_proto_usage.py` (TD-123 downward-only ratchet), wire `v1-proto-usage-no-regression` into `ci-success.needs`, and refresh the baseline once to the post-ADR-048 floor (the prior open ratchet was red only because its baseline predated the catalog-authoritative PRs #606/#609/#612 — drift, not regression). This refresh is the *only* non-ratcheted refresh; subsequent ones require explicit justification or the gate loses meaning.
* **M0-b (follow-on PR):** proto-deprecate all 17 v1 services (`option deprecated = true` + this ADR / TD-121 comment) — advisory only; v1 stays working through M4.
* **M0-c (✅ landed):** REST `/api/v1/*` is gated behind `PROXIMADB_REST_V1_COMPAT` (on by default; off → `410 Gone` + RFC 8594 `Deprecation`/`Link`/optional `Sunset` headers), mirroring the gRPC v1 gate. Implemented as `network::middleware::v1_sunset` applied at both REST router-assembly sites; `/api/v2/*` is never affected. Optional `PROXIMADB_REST_V1_SUNSET` sets the `Sunset` HTTP-date.

== Consequences

* The ratchet makes v1 removal measurable + enforced: every PR that removes v1 references advances the count; every PR that adds them is blocked (or must justify a baseline refresh).
* v1 stays fully functional (gRPC default-off + REST on-default) until M4 — no client flag-day.
* The storage-engine keystone (M1) is the riskiest piece; it carries a byte-identical golden-file parity requirement (encode the same records via the v1 path and the new PAX path, assert block equality) before any default flip — that gate is what makes M1 mixed-read-safe rather than a flag-day.
* On completion, the codebase has one model, one wire surface (`proximadb.v2`), one authority (the catalog), and the v1 package is gone — ADR-019's removal clause closed.
