== Context

The Azure-MVP work surfaced a latent mismatch between how *our code* names Azure
storage and how *Azure itself* organizes it. We registered **four** schemes
(`adls://`, `abfs://`, `az://`, `azure://`) for the Azure backend as if they were
distinct storage systems, the module was titled "ADLS Gen2", and the per-object
**access tier** — the single largest object-storage cost lever — was carried on
`FileOptions.storage_class` but **silently dropped** by every cloud `write`
(`azure_blob.rs` took `_options` and ignored it). This ADR records the ground
truth and re-orients the code to it.

=== Azure ground truth (verified)

* **One account, two endpoints.** An Azure Storage account exposes the **Blob
  endpoint** (`{acct}.blob.core.windows.net`, flat object keys) and — *only if
  Hierarchical Namespace (HNS) is enabled* — the **DFS endpoint**
  (`{acct}.dfs.core.windows.net`, ADLS Gen2 directory semantics). **ADLS Gen2 is
  not a separate product**; it is a Blob account with HNS turned on.
* **What the schemes actually mean.** `abfs(s)://` is the **Hadoop ABFS driver**
  → DFS endpoint (HNS). `az://`/`azure://` are the Rust `object_store` schemes →
  **Blob endpoint** by default. `adls://` is a non-standard alias. In *our* code,
  all four resolve to the **same** `MicrosoftAzureBuilder`-backed
  `AzureBlobFileSystem`, which talks to the **Blob endpoint with flat keys** — so
  `adls://`/`abfs://` were **misleading**: they never engaged ABFS/DFS/HNS.
* **The cost lever is the access tier, not the scheme or the namespace.** Hot /
  Cool / Cold / Archive (`x-ms-access-tier`) trade retrieval latency+cost for a
  far lower at-rest GB-month price. The tier is a property of the **object PUT**
  and is available on a **flat Blob account** — it does **not** require HNS.
* **HNS is a cost *add*, not a benefit, for our workload.** Our objects are
  flat-key, immutable, ranged-read (PAX segments, WAL, manifests, graph payloads).
  HNS adds per-operation metadata cost and directory semantics we never use.

This mirrors the other clouds (S3 `x-amz-storage-class`: STANDARD / STANDARD_IA /
GLACIER_IR / GLACIER; GCS storageClass: STANDARD / NEARLINE / COLDLINE / ARCHIVE),
so the orientation generalizes: **flat keys + a per-object access tier**, chosen
per cloud at the I/O boundary.

== Decision

. **Run flat Blob, HNS-off.** ProximaDB targets the Azure **Blob endpoint** with
  flat object keys. We do not require, assume, or benefit from ADLS Gen2 HNS. The
  default cold posture is **flat Blob + Cool/Cold access tier**.
. **The access tier is the object-storage cost lever — plumb it end to end.**
  `FileOptions.storage_class` carries a **canonical, cloud-neutral** tier
  (`hot`|`cool`|`cold`|`archive`), resolved by `ObjectAccessTier` and mapped to the
  provider-native class at each backend's I/O boundary (Azure `x-ms-access-tier`,
  S3 `x-amz-storage-class`) via `object_store`'s generic `Attribute::StorageClass`.
  Unset or unrecognized ⇒ the account default tier (today's behavior, unchanged) —
  a tier typo never fails a write.
. **Scheme honesty.** `az`/`azure` are the **canonical** schemes; `adls`/`abfs`
  remain accepted **aliases** for ergonomics, but the factory documents (doc
  comment + a one-time `INFO` log at registration) that all four route to the
  **Blob endpoint** and that the aliases do **not** engage DFS/ABFS/HNS. No scheme
  is a cost lever; only the tier is.
. **Canonical tier, not per-cloud strings at call sites.** Call sites pick a
  *canonical* `ObjectAccessTier`; they never hard-code `"Cool"` vs `"STANDARD_IA"`.
  This keeps the cost decision portable across clouds and is the single place the
  native mapping lives.

== Applied

[cols="1,3",options="header"]
|===
| Surface | Change
| `ObjectAccessTier` (new) | Canonical `hot`/`cool`/`cold`/`archive` enum in `proximadb-storage-filesystem-types`, with lenient `parse` (accepts native spellings, `None` ⇒ default) and `as_azure_access_tier` / `as_s3_storage_class` / `as_gcs_storage_class` mappings. Distinct from `FileStorageTier` (physical media latency).
| `FileOptions::access_tier()` (new) | Resolves `storage_class` → `Option<ObjectAccessTier>`, defaulting safely on unset/typo.
| `AzureBlobFileSystem::write` | Now honors `options`: when a tier resolves, `put_opts` with `Attribute::StorageClass(tier.as_azure_access_tier())` → `x-ms-access-tier`; else the plain `put` (default tier). Module doc rewritten to the Blob-endpoint/HNS-off truth.
| `AwsS3FileSystem::write` | Symmetric: `Attribute::StorageClass(tier.as_s3_storage_class())` → `x-amz-storage-class`.
| `FilesystemFactory` (Azure registration) | Canonical-first scheme order (`az`,`azure`,`adls`,`abfs`) + doc + one-time `INFO` log stating the aliasing and the Blob-endpoint/HNS-off posture. `extract_bucket_from_url` now treats `az`/`azure` as host=container (matching the backend's flat parse).
| GCS, `ProximaObjectStore::put` | **Deferred (TD-173).** GCS Simple media upload cannot carry a storage class (needs a metadata/resumable upload); `ProximaObjectStore` is backend-agnostic and does not track its scheme post-build, so canonical→native mapping there needs backend awareness it lacks, and has no tier-setting caller yet. Both carry doc notes; neither is the Azure MVP path.
|===

== Cross-cuts

* **Default-safe, no flag-day.** Every write with `storage_class == None` behaves
  exactly as before (account default tier). The tier is purely additive and
  opt-in per write — no migration, no mixed-read concern (the tier is metadata on
  the object, not a format change).
* **Co-design framing (per CLAUDE.md mandate).** The dimensional cost term moved is
  **object-storage at-rest GB-month**, via the access tier on cold/immutable
  payloads (PAX segments, graph payloads, manifests). It does **not** touch the
  read round-trip count (ADR-034) — it is the *residency price* of bytes the access
  path already minimizes the *round-trips* to.
* **Isolation/billing unchanged.** Writes still go under `DrPathBuilder` with
  `TenantContext`; the tier rides the same PUT.

== Consequences

* Cold tiers (Cool/Cold) become reachable per-object across Azure and S3 from one
  canonical knob — the cost lever the MVP needs for cold payloads (e.g. the
  object-storage-native graph's cold payload tier, TD-168 Phase 2).
* The `adls`/`abfs` aliases stay for compatibility but are no longer *misleading*:
  the code and an operator-visible log state they are Blob-endpoint writes, so no
  one assumes DFS/HNS semantics from a scheme name.
* GCS and `ProximaObjectStore` tier support remain open (TD-173) — explicitly
  scoped out rather than half-wired, since neither is the Azure MVP path and both
  need backend-aware mapping that would be speculative today.

== Verification

* Unit: `ObjectAccessTier` parse/mapping round-trips; `FileOptions::access_tier`
  defaults safely on unset/typo (in `proximadb-storage-filesystem-types`).
* Build: the `azure` and `aws` feature-gated backends compile with the new
  `put_opts` path; server binary builds in both feature states.
* Behavioral equivalence: a write with `storage_class == None` issues the same
  plain `put` as before (no tier header) — today's path is untouched.
* (e2e, where an emulator is available) a `storage_class="Cool"` Azure write sets
  `x-ms-access-tier: Cool`; Azurite does not enforce tiers, so this is asserted at
  the `Attribute` layer, with real-Azure validation deferred to the cloud smoke.
