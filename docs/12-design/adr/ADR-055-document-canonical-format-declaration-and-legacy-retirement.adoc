NOTE: **Reuse, don't rebuild.** Since this ADR was drafted, TD-OLAP-1 landed the PAX→Arrow DataFusion
path on develop: `PaxTableProvider` (#748, `src/datafusion/engine_adapters/pax_table_provider.rs`)
and `PaxSplitReader` (#736, `pax_adapter.rs`) already do PAX-native scan → Arrow with zone-map/bloom
pruning + projection + (Inexact) filter pushdown, default-OFF (`PROXIMADB_DF_PAX_READER`). The
P-DFSource / P-Pushdown phases below therefore **wire documents onto that existing infrastructure**
(a `documents(collection)` surface + document metadata-predicate translation) rather than building a
parallel scan. The P-Trace baseline has landed (#734): a document read fetches the whole 329 KB
segment (`range_gets = 0`) — the number pushdown must beat.

== Context

The document modality historically had a **store-split**: REST v2 document ingest wrote to the
per-collection record/vector store, while the gRPC `ProximaDocumentService` + `DocumentService`
wrote to their own `document_wal` (a row-wise WAL of `DocumentOperation` entries) projected into an
in-memory `DashMap`. A document written on one surface was invisible on the other, was double-stored
(GB-month paid twice), and the gRPC write path was unmetered.

TD-DOC-CONV-2 closed the capability and cut over the default:

* The convergence route sends document writes through the shared record/vector store — one store,
  cross-surface, metered, durable via the vector WAL, O(log n) point-get (TD-DOC-CONV-1).
* The bake measured recall@10 = 1.000, single-store (0 `document_wal` bytes), and full restart
  recovery; the per-tenant write-metering gap was closed (#718).
* The gate `doc_canonical_vector_enabled` was flipped **DEFAULT-ON** with a global kill-switch, made
  mixed-write-safe by a capability check (`RecordRoutePort::collection_exists`): a collection routes
  canonical only when it actually exists as a canonical/vector collection (#726).

**But legacy is only half-retired, and two structural facts block full retirement:**

. **The `DocumentService` durable store is still legacy in production.** The real server constructs
  `DocumentService::new_with_wal()` (`src/network/shared_services.rs:1690`,
  `src/network/multi_server.rs:536/545/999/1008`) — `document_wal` + `DashMap` — not the canonical
  `with_canonical_record_store_and_wal()`. The convergence *route* is wired; the service's *own*
  backing store is not.
. **Vectorless (pure-document) collections never converge.** The capability check routes canonical
  only for *vector* collections. A metadata-only document collection — a supported, GA-adjacent
  pattern — is not a vector collection, so it stays on the legacy path indefinitely.

The canonical format itself already exists in pieces, but is not *declared* as the document
format-of-record:

* **Model** — `ProximaRecord` (`props: ProximaTree`, `schema_version` V1/V2, bi-temporal,
  tenant-stamped) is the Accepted canonical durable model
  (`RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc`). The legacy `SqlObject`/`DocumentRecord`
  are adapter-only (TD-106 Group C is the in-flight migration).
* **On-disk** — the **PAX** block format (`magic PBLK`, `FORMAT_VERSION = 2`,
  `crates/storage/proximadb-block-format`) is the sanctioned vector/document substrate (deprecated
  for warehouse/relational — those use Parquet+Iceberg, ADR-033). PAX carries a
  magic+version byte, which is what makes a format migration **mixed-read-safe** (old and new
  coexist, detected by the marker — the RABITQ phased pattern).

What is missing is (a) a *declaration* that documents — including vectorless ones — are
ProximaRecord-in-PAX, (b) an *optimized document profile* of PAX so vectorless documents are not
penalized, and (c) a *phased, mixed-read-safe retirement* of the legacy `document_wal` path.

== Decision

=== 1. Declare the canonical document format

The canonical, durable, on-disk format for a document is:

**`ProximaRecord` (the record model) serialized into the PAX block format's _document profile_ with
_hybrid props shredding_.**

The design target is **general-purpose / mixed** — the format must be competent at the three document
access patterns (point-get, filtered scan, vector search), not over-fit to one.

* **Record model** — `ProximaRecord`: `oid`/`local_id` identity, `props: ProximaTree` body,
  `schema_version` for evolution, `tenant_id` for structural isolation, `valid_from_ns`/`valid_to_ns`
  for the dead-record predicate (read-correctness invariant). `SqlObject`/`DocumentRecord` are
  compatibility adapters at the facade boundary only — never a new internal contract.
* **PAX document profile** — the SAME PAX container (`PBLK`, `FORMAT_VERSION = 2`), specialized for the
  document access pattern:
  ** **embedding columns are OPTIONAL** (`EMBED_BASE = 20`) — a vectorless document writes none, is
     excluded from the ANN index, and remains point-gettable + scannable (this already holds today);
  ** **hybrid `props` encoding** — declared/hot fields are **shredded** into typed PAX user-columns
     (`USER_BASE = 100+`, each with zone-map min/max + bloom + HLL cardinality) so
     `query_documents`/`aggregate_documents` get block pruning + projection pushdown; the dynamic
     long tail stays in the **msgpack `props` stripe (col 8)**, which remains the **source of truth**
     for every non-shredded field. The shred-list is the existing catalog primitive
     `CatalogTableSchema.props_auto_promotion.promoted_keys` (columns `props__<key>`, id ≥ 100);
  ** **point-get is O(log n)** via the bloom + B+ tree (TD-DOC-CONV-1);
  ** filter columns (`id`, `tenant_id`) are co-located first (PAX layout), so tenant isolation is
     structural, not a per-query predicate.

**No PAX format-version bump.** The reader locates columns by `column_id` presence, and
`FlatRow::from_block_reader` reconstructs `ProximaRecord` **entirely from the msgpack tail (col 8),
deliberately ignoring user-columns ≥ 100**. So shredded columns are a **duplicated pruning/projection
index** — a legacy blob-only segment and a new shredded segment both reconstruct from the tail. The
change is **additive**, mixed-read-safe *for free* (`FORMAT_VERSION` stays 2), and shredded
detection is pure column-presence (`any(column_id ≥ 100)`).

**Load-bearing invariant — clone, never remove.** Shredding MUST copy the hot field into the typed
column while leaving it in the msgpack tail (clone-not-remove). The existing
`FlatRow::from_record_with_user_columns` *strips* the key from the tail; using it with the
tail-only reader would **silently drop the field** (data loss). The write path clones; a round-trip
losslessness ratchet (write-with-shred → `PaxSegmentScanner::read_records` → props byte-identical)
gates it. This keeps "shredded value == tail value" and "tail is source of truth" true by construction.

**Standard-outside: documents are a DataFusion table source.** The shredded typed columns ARE a
relational schema, so documents are exposed as a SQL relation (a `documents(collection)` table
function, ADR-053 cross-modal) whose filters/projection push into a **PAX-native scan → Arrow
`RecordBatch`** (ADR-052 / TD-OLAP-1) — filtered scans and aggregation run data-local in the engine
via `ComputeScheduler::route_select`, retiring the in-memory bounded-scan
(`CANONICAL_DOC_SCAN_LIMIT`) path. Point-get and vector search keep their PAX-native paths.

This is the co-design win: one format gives documents *shredded columnar metadata + optional vectors +
a dynamic tail* under a single metered, tenant-isolated, ranged-read substrate that is both
point-get-fast and OLAP-queryable — replacing the row-wise `document_wal`/`DashMap`.

=== 1a. Evidence posture — trace-first

There is **no measured document workload trace** today (the io_trace substrate is live but unwired for
documents). Per the co-design mandate ("trace before you tune"), the format's open cost knobs — WHICH
fields to shred, tail compression (e.g. zstd), and per-collection access tier (Hot/Cool) — are decided
from a **measured trace** (bytes_read / range_gets / bytes_written / egress on a representative
general-purpose workload), recorded in `BENCHMARK_EVIDENCE.toml`, NOT baked as assumptions. Wiring the
document io_trace is therefore the FIRST implementation phase (Phase-Trace below), before any tuning.

=== 2. Optimize the format + retire the legacy document_wal path in phases

Each phase is a scoped, CI-amortized PR following the ADR-041 deprecation shape and the RABITQ
mixed-read-safe pattern (never a flag-day), gated on round-trip + recall parity.

=== 3. Invariants (non-negotiable through P5)

* **Mixed-read-safe, no flag-day.** Old (`document_wal`) and new (PAX document profile) coexist,
  detected by the PAX magic+version byte and the `document` label. Readers fall back to legacy when
  the marker is absent (mandate #8). The read-fallback is removed only in P5, only when provably
  unused.
* **Kill-switch survives until P5.** `PROXIMADB_DOC_CANONICAL_VECTOR=off` must force the legacy path
  for as long as the legacy path exists (default-reversible until fully baked).
* **Recall/quality-gated.** Any format change holds recall@k within tolerance of the f32 baseline
  (Quality-Ratchet mandate); vectorless documents must not pollute ANN.
* **Metered + isolated.** Every write funnels through the per-tenant metered flush
  (`materialize_collection`, #718) and `DrPathBuilder` paths; tenant isolation stays structural.
* **Tail is source of truth; never strip it.** Shredding clones hot fields into typed columns
  (clone-not-remove); the msgpack tail remains authoritative. Reconstruction reads only the tail, so
  no format-version bump is needed. A future variant that *strips* the tail WOULD require a
  per-segment marker + version bump — explicitly out of scope.

== Consequences

**Positive**

* One document store: closes the double-GB-month, the unmetered gRPC path, and the cross-surface
  invisibility — realized in production, not latent.
* An optimized, columnar, ranged-read document format (projection + zone-map pruning + O(log n)
  point-get) replacing a row-wise in-memory map — the co-design cost-term win.
* Vectorless documents become first-class on the canonical store (P1), which is the precondition for
  ever deleting the legacy path.
* A single versioned format declaration to build SDKs/readers against — vertical inside, standard
  outside.

**Negative / cost**

* Real work across P1–P5 (provisioning, server rewiring, a migration replay, feature-gating,
  removal). Mitigated by phasing + the existing v0.4 removal window already on record.
* A transitional `legacy-document-wal` feature + kill-switch add temporary surface area (removed in
  P5).
* Hybrid shredding adds write-path work (typed-stripe emission, catalog `PromotePropsKey` wiring) and
  a data-loss trap if done wrong (the clone-not-remove invariant). Mitigated: additive (no format
  bump), per-collection gated (fires only when `promoted_keys` non-empty), and ratchet-gated on
  props losslessness.

**Neutral**

* Facades (REST v2, gRPC v2, pgwire, SDK) are unchanged — the change is durable-format + routing,
  behind stable seams.

== Alternatives considered

* **Keep two document stores indefinitely.** Rejected: leaves the motivating costs (double
  GB-month, unmetered writes) permanently unrealized and doubles maintenance.
* **Store vectorless documents in Parquet+Iceberg (the warehouse format).** Rejected for the
  document access pattern: documents are point-get / small-ranged-read / cross-surface with optional
  vectors; PAX's co-located filter columns + bloom + B+ tree fit that, whereas Parquet is optimized
  for large analytical scans. (Warehouse *relational* tables still use Parquet — ADR-033 unchanged.)
* **Flag-day cutover (delete legacy at the flip).** Rejected: violates the mixed-read-safe,
  storage-format-migration mandate (#8). The phased, marker-detected coexistence is required.
* **A brand-new document format unrelated to PAX/ProximaRecord.** Rejected: ProximaRecord is the
  Accepted canonical model and PAX is the sanctioned substrate; a document *profile* of PAX reuses
  the metered flush, `DrPathBuilder` isolation, versioning, and readers rather than reinventing them.
