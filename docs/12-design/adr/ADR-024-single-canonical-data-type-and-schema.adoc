= ADR-024: Single Canonical Data Type (`ProximaType`) and Schema

:toclevels: 3

== Status

Accepted — **rollout complete** (Steps 1–5 shipped; reconciled 2026-10-15). See
<<_implementation_history>>.

Scope: convergence of the three parallel data-type enums and two schema structs onto a single canonical logical type + schema. Tracker: CONVERGENCE_AUDIT seam *S8*; TD-111. Supersedes the implicit "three-parallel-type" tolerance noted in `roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc` §4.2.

== Context

The codebase carried three parallel "data type" enums — `ProximaType`
(`crates/foundation/proximadb-data-model`, ~42 variants, the mandated canonical type),
`ProximaDataType` (`proximadb-storage-common`, ~28 variants, mixing in *physical* quantization
parameters) and `CatalogDataType` (`proximadb-catalog`, ~19 variants, **durably persisted**,
carrying proto-v1 wire codes) — plus two schema structs, with no bridges between some pairs, so
every new schema-aware path was tempted to add another. The Convergence Gate treats this
duplicate-abstraction class as a regression. Key distinction: quantization parameters are
physical storage detail that the logical type must deliberately omit.

== Decision

. **One canonical logical type: `ProximaType`.** It is the single authority for column/field types across catalog, storage, query, and protocol layers. `ProximaDataType` and `CatalogDataType` are deprecated and collapsed into it.
. **Logical vs physical separation.** `ProximaType` describes the *logical* type only (e.g. `DenseVector { element, dim }`). Physical encoding — quantization (int8 scale/zero-point, PQ segments/bits), compression, layout — is an **orthogonal storage attribute**, not a logical-type variant. The quantized `ProximaDataType` variants therefore do **not** become `ProximaType` variants; on collapse they map to their logical type (`DenseVector`/`BinaryVector`) plus a separate encoding descriptor on the storage column. `VectorElement` gains `BFloat16` to match the prior element set.
. **One bridge per concern, hosted on `ProximaType`.** The Arrow projection (`ProximaType::to_arrow_type`/`from_arrow_type`), pgwire OIDs (`pgwire_oid`), and proto wire-code mapping live on (or key off) `ProximaType`. The previously scattered converters (`CatalogDataType::to_arrow_datatype`, `ProximaDataType::to_arrow_type`) delegate to it, then are removed with their enums. Dense vectors project to `FixedSizeBinary(dim * element_width)` little-endian; this is the canonical, lossy *physical projection* (the logical type stays authoritative).
. **One canonical schema struct.** `CatalogTableSchema` (durable authority: columns, primary key, indexes, storage layouts, projections, relational capabilities, workload/specialization/policy) and `ProximaSchema` (in-memory Arrow + evolution: schema_id/version/parent/fingerprint) merge into a single schema type whose columns carry `ProximaType`.
. **Proto enums remain versioned wire edges.** Proto v1 `DataType`/`SqlValue`/`SqlObject` and v2 `ColumnDataType`/`TypedValue` are NOT deleted (that would break the wire); each gets exactly one bridge ⇄ `ProximaType`/`ProximaValue`. Variant wire codes are never renumbered.
. **REST/gRPC funnel through `ProximaType`.** REST v2's stringly-typed `data_type` parses via the one canonical `ProximaType` parser; gRPC conversions route through the single bridge.

== Implementation history

All five rollout steps landed (each compiled and landed independently; the durable steps 3–4
shipped with serde deserialize-compat for legacy tags; proto wire codes never renumbered):

* Step 1 — `ProximaType` becomes the logical superset (`BFloat16`, `to_arrow_type` /
  `from_arrow_type`, extended `pgwire_oid`): `7d78df773`.
* Step 2 — `ProximaDataType` bridged (`335665ea1`) then **deleted**; `ProximaColumn` carries
  `ProximaType`: `320d62747`.
* Step 3 — proto-i32 wire-code mapping (`be1c0b2f6`); `CatalogDataType` **deleted**, catalog
  carries `ProximaType`: `8009ab052`.
* Step 4 — `ProximaSchema` merged into `CatalogTableSchema`: `fcac4f5fe`.
* Step 5 — REST v2 column-type vocabulary derived from `ProximaType`: `d6e897689`.
* Follow-on (value types, not this ADR's scope): TD-V1SUNSET-2 / -3.

== Consequences

* Positive: one logical type and one schema struct; the bridge web collapses to a single Arrow/pgwire/proto mapping; new code stops minting parallel types; logical/physical separation makes the type model honest about quantization.
* Negative / cost: a durable migration for persisted catalog schemas (mitigated by serde compat shims); a multi-step rollout that temporarily keeps deprecated aliases; coordination with in-flight catalog (TD-061/TD-110) and storage (F-series) work.
* The Convergence Gate is satisfied: this ADR is the cited justification for the type/schema seam change; seam S8 in `CONVERGENCE_AUDIT_2026_05_30.adoc` tracks it to closure.

== Addendum (2026-06-27): object identity is a separate concern from the logical type

[NOTE]
====
**Superseded in part by link:ADR-0083-consolidated-catalog-identity-model.adoc[ADR-0083]
(2026-07-30).** The catalog-object row below (`u64 object_id`, ADR-031) is no longer the identity
scheme: ADR-0083 retires the global `u64` and makes the composite `(account, namespace,
collection_id)` the sole canonical identity. The addendum's point — value type vs object identity
vs pgwire type-OID are three separate concerns — still stands; read "ADR-031 / `object_id`" below
as "ADR-0083 / the composite".
====

`ProximaType` is the type of a *value* in a column — including id columns. It does **not** prescribe the *identity scheme* of an object (who mints the id, its uniqueness scope, its mutability). That is a separate decision, and the two object classes deliberately use different schemes:

[cols="1,2,2", options="header"]
|===
| Object class | Identity | Why different
| **Catalog object** (account / namespace / table-collection / column / index — metadata) | an immutable **`u64` `object_id`** from the central catalog sequence; the *name* is a mutable attribute (**ADR-031**) | Low-rate, centrally-serialized DDL ⇒ coordination is free; fixed-width `u64` is fast to join/FK/index and survives rename
| **Data record** (a row in a user table) | `ProximaRecord.oid: String` — a user-provided natural key, or an engine-minted **ULID** (settled; separate from catalog identity) | High write-rate, distributed ⇒ coordination-free; ULID is time-sortable + index-friendly
|===

Both id *values* are themselves `ProximaType`s — `UInt64` for the catalog `object_id`, `String`/`ULID` for the record oid — so the canonical type system carries them, and this ADR stays the authority for the *value type*. The *identity strategy* for catalog objects is owned by **ADR-031** (`object_id`); the data-record handle is the settled `String`/`ULID` concern (described above), not this ADR. And `pgwire_oid()` (Decision §3) is a **third, unrelated** concept: the PostgreSQL *type* OID for wire compatibility — not an object identity at all. Keeping these three apart — value type vs object identity vs pgwire type-OID — is the point of this addendum.
