== Context

Flush→AXIS and compaction→AXIS each had **two** implementations. In both cases
one worked and the redundant one silently did nothing or did needless I/O.

=== Flush was split by engine

* **SST** called `AxisManager::handle_flushed_vectors` **directly**, passing the
  in-memory `ProximaRecord`s already present on `FlushParameters.vector_records`
  — zero I/O.
* **VIPER / HELIX / NOVA** published a metadata event (`IndexEvent`: file paths,
  counts, flags — no vector data) to the AXIS queue. The consumer then called
  `read_vectors_from_files(&event.file_paths, …)`, **reading those same vectors
  back out of storage**. On object storage that is N round-trips to recover
  bytes the flush had in hand — the dominant cost term, paid to move data that
  never needed to move.

The reason those three took the queue route is mundane and was not a design
choice: their `axis_manager` field is constructed `None` and **nothing ever set
it** (only SST had a registered global, `set_sst_axis_manager`). They had no
direct handle to call.

=== Compaction had a working path and a broken one

* **Working:** `compaction_coordinator` →
  `IndexMaintenance::update_indexes_after_compaction` → applies
  `deleted_vector_ids` removals, updates merged vectors, rebuilds static indexes.
* **Broken:** the queue's `AxisManager::rebuild_indexes_after_compaction`. The
  signature is `(collection_id, old_files, new_files)`; the consumer passes
  `(collection_id, event.file_paths /* "New compacted files" */, &[] /* "Old
  files already deleted" */)` — **arguments swapped relative to the caller's own
  comments**. Because `new_files` receives an empty slice, the body's
  `for old { for new { … } }` inner loop **never executes**. The body was a
  self-described placeholder regardless. It then increments
  `metrics.successful_migrations`, **reporting success for work that never
  happened**.

=== Further findings

* `EventType::Delete` is **never emitted** anywhere; the consumer logs "not yet
  implemented".
* `can_compact` **fails open** (`is_none_or(|s| s.ready_for_compaction)` — "if
  not tracked, allow"). Consequence is milder than it first appears: compaction
  *rewrites* data rather than destroying it, so this is a recall risk, not a
  durability one.
* The queue persists state to object storage (a **full-state PUT per event**) and
  recovers it — but that state is semantically stale after a restart, because the
  file paths it references may already have been compacted away.
* **The queue is not part of restart recovery at all.** AXIS recovers
  independently by lazily warm-loading its persisted `ivf.bin` on the next query.
* Terraform provisions a `queue_container` that nothing uses.

== Decision

=== D1 — one flush→AXIS mechanism: the direct in-memory call

Every engine indexes through one shared hook,
`storage::common::axis_flush_hook::index_flushed_into_axis`, which holds the
single copy of the co-design guard (ADR-070: absent config ⇒ no AXIS) and the
`PROXIMADB_SKIP_AXIS_INDEXING` override. `SharedServices` registers the AXIS
manager for it at boot, giving VIPER/HELIX/NOVA the handle they lacked.

**Records are passed by value.** This is the substantive property, not an
implementation detail: it removes the file-lifetime coupling entirely. AXIS no
longer depends on the flushed files still existing when indexing runs — which is
exactly what the queue's compaction barrier existed to guarantee. The barrier
becomes unnecessary rather than merely fixed.

=== D2 — one compaction→AXIS mechanism: the existing port

`IndexMaintenance::update_indexes_after_compaction` is already correct and
becomes the only compaction path. `rebuild_indexes_after_compaction` is
**deleted, not repaired**: fixing the swapped arguments would resurrect a second
indexing path alongside the working one and create a genuine double-index hazard
that does not exist today.

Compaction notification remains necessary — it is where tombstones materialize,
where file references would otherwise dangle, and where PCA/IVF retraining
invalidates the existing encoding. Compaction is *not* a no-op for AXIS; it is
simply already handled.

=== D3 — retire the AXIS event queue

With D1 and D2 there is no remaining consumer. Removing it resolves, structurally
rather than by patching each: the fail-open barrier, the storage re-reads, the
per-event full-state PUT, the no-op compaction leg, the dead `Delete` leg, the
false success metric, and the unused `queue_container`.

*Phasing.* D1 (the convergence) lands first — it is the load-bearing change and is
independently valuable (every engine indexes through one hook, no storage re-reads).
D3's removal is a **phased follow-up**, not a single delete: the `src/index/axis/
eventlog/` module is not *only* the queue — it also defines `IndexEvent` /
`ExtractionMode` / `EventLogConfig` / `IndexEventBuilder` that **live** HNSW/IVF/LSH
indexes import, and `services/events/log.rs` is shared with the experimental SWIFT
engine. Retiring the queue therefore means *extracting the shared types* and
deleting only the queue runtime (`EventLogManager`, the consumer, the service
adapter), tracked in TD-AXIS-3 S2. The dead queue is harmless to retain until then
(no-ops + wasted I/O; no correctness impact).

=== D4 — reconciliation replaces the barrier's intent

The queue's stated purpose was preventing un-indexed data. One real gap remains
after D1–D3: a segment flushed but not indexed before an **unclean** restart is
never re-indexed — nothing reconciles manifest segments against index coverage,
so those vectors stay durable but silently unsearchable. That is a **recall**
defect and is tracked as TD-AXIS-4; it is not a reason to retain the queue, which
never addressed it either.

== Consequences

* One code path per direction; the guard exists once instead of four times.
* Flush no longer performs storage reads to index data it already holds.
* `hilbert_range` is dropped from the HELIX flush notification — AXIS never
  consumed it (the DataFusion HELIX adapter derives its own via
  `estimate_hilbert_range`).
* **Behavioural change for VIPER/HELIX/NOVA:** indexing moves from asynchronous
  (queue consumer) to inline-on-flush, governed by the per-collection
  `IndexUpdateMode` like SST. The ADR-070 guard means collections without
  `index_configs` skip it entirely, so the default path is unaffected.
* Recall must be re-verified for all four engines — this changes the indexing
  path, and a green compile proves nothing (mandate #10).

== Alternatives considered

* **Fix the queue in place** (repair swapped args, fail-closed barrier, keep
  async) — rejected: preserves two parallel mechanisms and the object-store
  re-reads, and re-creates the double-index hazard D2 avoids.
* **Keep the queue for flush, drop only its compaction leg** — rejected: the
  re-read waste and the fail-open barrier both live on the flush leg.
* **Make the queue ephemeral (instance store) rather than removing it** —
  rejected: correct about the cost (its persistence is waste), but it addresses
  the symptom. With records passed by value there is no coordination state left
  to store anywhere.
