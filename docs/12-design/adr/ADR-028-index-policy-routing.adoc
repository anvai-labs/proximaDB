== Context

TD-165 found the post-flush/cold SST search returning the **wrong** nearest
neighbour: a query identical to an indexed vector got an approximate AXIS HNSW
result whose 100-wide candidate pool *excluded the exact match*, and the
orchestrated SST path **ignored the query's `SearchMode`** entirely. The first
fix honoured `SearchMode` and gated exact-vs-approximate on a hardcoded vector
count (`≤ 10_000 → exact`). That violates the co-design mandate ("cost from
measured quantities, not static heuristics"): the true cost is **bytes
(`N · dim · 4`)**, not vectors, and is storage-class dependent. The
first-principles cost model is in `EXACT_VS_ANN_ROUTING_COST_MODEL_2026_06_26.adoc`.

Two further facts shape this decision:

* **Serverless ⇒ cold-start-dominant.** The in-memory HNSW graph is not durable
  across scale-to-zero. On a cold query HNSW must read the same `N · dim` bytes
  exact would read, *then* pay `O(N · log N)` rebuild, *then* return an
  approximate (possibly NN-excluding) result — so **cold HNSW is strictly
  dominated by exact up to a byte budget**, and a persisted IVF / Hilbert-sorted
  HELIX layout is the correct large-N cold path, never a full HNSW rebuild.
* **The cheap cold path is currently broken (IVF Defect B).** The ADR-023 v2/v3
  separable IVF tier (cold ~1/32 codes + lazily range-fetched warm fp32) is
  implemented, but `train_ivf_for_batch` persists the freshly-trained index
  *before* the batch insert loop populates its posting lists, so `ivf.bin` is
  saved with **0 vectors**. The serverless-friendly machinery loads nothing.

The question this ADR answers: **who decides** exact-vs-ANN and which engine — a
per-collection user knob, or the system? In a multi-tenant SaaS the decision is
one users most often get wrong (intrinsic dimensionality, HNSW-rebuild cost, and
their own QPS distribution are not things a user can reason about), yet a minority
of owners have hard SLAs that need an override.

== Decision

Adopt **paved road + escape hatch**, layered as a strict precedence:

[source]
----
per-query SearchMode  >  collection index_policy  >  cost-model auto-default
----

This adds exactly one layer beneath the two override layers that already exist
(`SearchMode` per-query; `storage_engine`/`quantization` per-collection), and
mirrors ADR-026's user→adaptive→learned tuning hierarchy and ADR-011's
per-collection routing-policy precedent.

=== 1. Default = automatic, cost-derived (`mode = "auto"`)

The default `SearchMode` is `Adaptive{threshold}`, and the SST adaptive route
takes the exact brute-force scan when the whole scan fits one efficient ranged
GET (`N · dim · 4 ≤ byte_budget`), else the persisted/approximate index. The byte
budget is **`f(storage_class)`** (object store is round-trip-bound — one
sequential read beats several posting-list round-trips for small N; local NVMe is
bandwidth-bound, higher threshold), not a scalar. The interim static
`EXACT_SCAN_MAX_BYTES = 64 MiB` is an explicit stand-in until the SST path
consumes the measured `route_cost_model` trace (ADR-027 two-class trace; TD-158/
TD-159).

=== 2. Optional per-collection `index_policy` override

A new typed `IndexPolicy` on `CollectionConfig` (proto `collection_types.proto`,
field 28), absent ⇒ `mode="auto"`:

[source]
----
message IndexPolicy {
  string mode      = 1;  // "auto"(default) | "exact" | "ivf" | "hnsw" | "helix"
  string rehydrate = 2;  // "auto"(default) | "eager" | "lazy" | "never"
  uint64 byte_budget = 3; // 0 => cost-model default for the storage class
  uint32 nprobe    = 4;  // 0 => cost-derived; index modes only
}
----

* `mode` — `auto` defers to the cost model; `exact` always brute-forces (the
  "small critical collection, always 100%" SLA); `ivf`/`hnsw`/`helix` force the
  collection onto that engine/route at create time. `exact` is a *search route*,
  not an engine — it is honoured at the search layer on whatever engine the
  heuristic picks, so it does **not** force an engine.
* `rehydrate` — cold-start index warming (composes with ADR-023
  `ColdPathLoadPolicy`). Index/auto modes only.
* `byte_budget` — expert override of `f(storage_class)` for owners who know their
  round-trip economics. Meaningful for `exact` too (it caps the auto gate).
* `nprobe` — index-mode recall/cost dial.

**Validity matrix is fail-closed at create** (co-design "boundary is the
contract"): `rehydrate`/`nprobe` are index concepts and are rejected when
`mode="exact"`. Unknown `mode`/`rehydrate` strings are rejected.

=== 3. Auto-router improvement (mode=auto), env-gated default-OFF

The create-time engine selector historically pinned **quantization-only vector
collections** (the OpenAI-embedding shape) to the SST cold path — whose AXIS HNSW
is rebuilt every cold start and can exclude the true NN. Under `mode=auto` we
prefer **HELIX** (quantization-native, persisted PCA, Hilbert-sorted,
rebuild-free cold) when `PROXIMADB_AUTOROUTE_QUANT_HELIX=1`. Default-OFF, bake-in
discipline (A6-fence precedent): the SST `SearchMode` exact gate already corrects
SST cold recall, so this is an optimization, not a correctness fix. Owners can
force HELIX explicitly any time via `index_policy.mode="helix"`.

=== 4. Fix IVF Defect B (the unlock)

Re-persist the IVF index **after** the batch insert loop populates its posting
lists, so the cheap cold-load path the auto-default wants to use actually returns
vectors. Best-effort, gated on the batch-training threshold (no extra I/O on the
incremental path).

== Consequences

* **Mixed-read-safe / default-OFF** (storage-format migration mandate): an absent
  `index_policy` ⇒ `mode="auto"` ⇒ today's behaviour; `index_policy` carries
  `#[serde(default)]` so old persisted collection records remain readable; the
  auto-router improvement is env-gated default-OFF.
* **Metered as a TAM surface** (co-design #5): exact = more read-units (KRU) /
  bytes, zero index storage; index = index storage (KSU) + fewer read bytes. The
  route is observable via the ADR-027 trace.
* The typed external surface costs the all-language SDK-codegen-drift regen
  (mandate #15) — accepted deliberately for a first-class, discoverable knob over
  an opaque `indexing_config` string map.

== Phasing

* **This PR (TD-165):** typed `IndexPolicy` end-to-end (proto → core →
  REST/OpenAPI/SDKs), the 3-layer precedence wired at the SST search route +
  engine selector, the env-gated auto-router→HELIX, and the IVF Defect-B fix.
  The byte budget is the static `EXACT_SCAN_MAX_BYTES` stand-in.
* **Serverless follow-up (TD-158/TD-159):** SST/AXIS search consumes the measured
  `route_cost_model` trace so the auto byte budget is `f(storage_class)` from real
  bytes/round-trips, not a constant; full `rehydrate` execution semantics on the
  IVF/HELIX warm path; flip `PROXIMADB_AUTOROUTE_QUANT_HELIX` default-ON after bake.

== Alternatives considered

* **Pure-auto, no override.** Rejected: blocks the expert with a hard SLA.
* **Pure-config, user always decides.** Rejected: invites the classic footguns
  (HNSW-rebuild-per-cold-query, exact-scan on a huge collection,
  approximate-NN-exclusion on a tiny one). The system has the trace; it picks
  better than the median user.
* **Interim `indexing_config` string-map seam** (no proto change). Rejected here
  in favour of a typed, discoverable, drift-gated surface (the owner explicitly
  chose the typed field despite the SDK-regen cost).
