== Context

`DrPathBuilder` renders `data/{tenant_id}/{namespace_id}/{collection_id}/`
(account-rooted: `accounts/{account_id}/{tenant_id}/{namespace_id}/{collection_id}/`).
The namespace segment is structurally required and fail-closed — `validate_id`
rejects empty and `build()` returns `MissingNamespaceId`
(`path_resolver.rs:744`, `:922`). Nothing in the identity flow populates it.

The gap is closed today by **hardcoded constants inside the storage layer**:
`DEFAULT_NAMESPACE_ID = "ns_default"` (`src/services/dml/mod.rs:94`) and a
literal `mock_namespace` construction in `src/services/record_store.rs:305`,
committed under `#[allow(clippy::expect_used)]` justified as "infallible for
this internally-constructed namespace". Paths are therefore well-formed, but
every tenant in a deployment shares **one global namespace id**, chosen by
storage rather than resolved from identity — the exact shape structural
isolation forbids. The `expect` is sound only while the namespace is a
constant; it becomes a panic-policy violation the moment it is resolved input.

Meanwhile the ingress context already models the tier *above* namespace and the
typed-id question *around* it, and models neither for namespace itself.
`MiddlewareTenantContext` (`src/network/middleware/tenant.rs:64-85`) carries
`account_id: Option<String>` with `account_or_default()` →
`DrPathBuilder::DEFAULT_ACCOUNT_ID`, `tenant_stable_id: Option<u64>`, and a
`TenantIdSource` provenance enum — but has no namespace field at all.

[NOTE]
====
**This ADR is not motivated by the 2026-07-26 Azurite ingest failure.** That
symptom was initially attributed to an unpopulated `namespace_id`; the
attribution is wrong (`DrPathBuilder` is fail-closed, so a missing namespace
errors rather than producing the observed malformed path). The two real defects
are tracked as TD-CACHE-5 and TD-FLUSH-6. This ADR stands on the isolation
argument alone and must not be scoped or sequenced against that bug.
====

== Decision

Address namespaces by a **client-facing alias** resolved **server-side,
authz-gated, per-tenant** to an **opaque immutable `namespace_id`** that is the
physical path component and the metering attribution key.

=== D1 — Two-layer naming

* **Alias** — client-facing, mutable, tenant-scoped, human-friendly (`prod`,
  `eu-1`). Never trusted as an isolation boundary, never reaches
  `DrPathBuilder`.
* **`namespace_id`** — server-assigned, opaque, immutable, rename-stable. The
  path segment and the metering key.
* **Registry** — `(tenant_id, alias) → namespace_id`, authz-gated, with
  uniqueness enforced by conditional write (see D6).

Minting already exists: `NativeCatalog` assigns `ns_{uuid4}`
(`native.rs:1214`, `:1247`), and `catalog.get_namespace(&fqn)` is already the
alias→id lookup on the materialize path (`dml/mod.rs:1549`). What is missing is
the **authz gate**, the **default binding**, and the **wire surface** — not the
registry.

=== D2 — Resolution happens once, at the identity seam, and travels in the context

`namespace_id` is added to `MiddlewareTenantContext` and flows to every I/O
boundary alongside `tenant_id` and `account_id`. Storage never re-derives it.
`DEFAULT_NAMESPACE_ID`, the `mock_namespace` literal, and the accompanying
`expect` are deleted.

Resolution order, mirroring `account_or_default()` exactly: explicit alias →
principal's declared default → tenant's default → the reserved default id.
**Every level is a real, resolvable id; none is empty, and there is no shared
global default across tenants.** In single-tenant mode the principal and tenant
defaults collapse to one id by construction — stated here so the isolation
acceptance test has a coherent single-tenant analogue.

=== D3 — The seam is enforced by types, not by convention

* `NamespaceId` is constructible **only** by the resolver; it is the only type
  `DrPathBuilder` accepts for that segment. `NamespaceAlias` has no
  path-rendering method.
* `DrResolvedPath` is split by meaning: `DrCollectionPath` (exposes
  `root_prefix`, `manifests_subprefix`, `segments_subprefix`, …) and
  `DrTenantSystemPath` (exposes `tenant_root`, `metering_subprefix`,
  `trace_subprefix`, `cache_subprefix`).

The second point is not hygiene. One struct carrying two meanings, where method
validity depends on which constructor ran and is enforced only by a doc
comment, is what produced TD-CACHE-5. After the split that defect does not
compile. N1's claim that isolation is "structural" is only true if the compiler
carries it.

=== D4 — String id is authoritative; the typed id is a derived optimization

ADR-031's typed path (`accounts/{base62(u32)}/{base62(u16)}/{base62(u32)}/`,
env-gated `PROXIMADB_TYPED_PATHS`, Proposed) does not compete with this design.
We adopt the precedent already set one field over in the same struct for
`tenant_stable_id`: *"always an optimization for catalog/storage keying, never a
second source of truth — the string remains authoritative."* The string
`namespace_id` is the registry value and the isolation key; the typed `u16` is a
derived encoding for the typed-path layout.

**Capacity constraint (new).** `CatalogIdService::mint_namespace_id` is an
`AtomicU16::fetch_add` per account (`id_allocator.rs:139-144`) in an allocator
documented as *never reused*, with no overflow check. At 65,536 namespaces in
one account it wraps onto a live id and two namespaces collide on one typed
path — silent cross-namespace data mixing. This is unreachable today and
becomes reachable precisely under this ADR's own affordances (fork/branch/
archive as new ids; auto-create). Therefore: namespace creation is bounded and
explicit (D5), and widening or fencing the typed id is a prerequisite of
enabling `PROXIMADB_TYPED_PATHS` in production.

=== D5 — Creation is explicit; there is no auto-create on write

A write to an unresolvable alias is a `403`, never an implicit
`CreateNamespace`. Exactly one default namespace is provisioned at **tenant
create** (a control-plane event), which satisfies single-tenant/no-auth
deployments without silent proliferation. Auto-create would undermine metering
attribution (D7), the fail-closed posture (D8), and the D4 capacity bound
simultaneously.

=== D6 — Alias mutation, reuse, and caching

* **Rename** remaps the alias only; `namespace_id` and every physical path are
  byte-identical. Uniqueness of `(tenant_id, alias)` is enforced by conditional
  write / CAS on the registry — without it, concurrent renames land two aliases
  on one id or one alias on two ids and isolation becomes advisory.
* **Delete then recreate** the same alias mints a **new** id. Retired ids are
  reserved forever and never reused, so a recreated alias can never reach the
  prior incarnation's objects. (Same discipline as the env-gate registry's
  "Retired names".)
* **Caching.** Resolution sits on every request, so an uncached registry lookup
  is a per-request object-store round-trip against the dominant cost term. The
  resolution cache is bounded and tenant-keyed, reusing the ADR-035 per-tenant
  system-catalog cache / `TenantCache::get_or_load` rather than adding a cache.
  It **must** cache negatives — unauthorized aliases are the cheapest thing an
  attacker can generate, and an uncached 403 path is a catalog-DoS amplifier.
  Rename/delete invalidates the resolution cache **and** the
  `(tenant, namespace, query)` plan/result caches (read/write-correctness
  invariant (b)).

=== D7 — Metering: a dimension, not a new unit

`namespace_id` is added as an attribution **label** on the existing per-tenant
KSU/KRU/KOU/KEU series. ADR-060's per-tenant unit definitions are unchanged and
tenant rollups stay exact. Namespace does not become a billing unit.

=== D8 — Authorization

* New `Namespace*` variants (`NamespaceCreate`, `NamespaceRead(id)`,
  `NamespaceWrite(id)`, `NamespaceAdmin(id)`) with the same implication
  structure the `Domain*` tier already uses
  (`src/security/rbac_service.rs:569-571`).
+
[IMPORTANT]
====
Do **not** repurpose `Domain*` for namespace. It is wired (implication logic,
elevated-admin handling in `advanced_features.rs:129`) and means
*knowledge-graph domain* (`can_access_domain`,
`src/storage/knowledge_graph/types.rs:655`). Overloading it is a semantic
collision, not a clean pre-GA break.
====
* **Permission-enum authority must be designated.** Three parallel enums carry
  duplicate variants today: `proximadb-tenant::UnifiedPermission`
  (`rbac_context.rs:28`), `proximadb-storage-tenant::rbac::Permission`
  (`rbac.rs:62-68`), and `knowledge_graph::types::Permission`
  (`types.rs:248-251`). A namespace check that lands in only one of the three
  is an isolation hole. This ADR designates `UnifiedPermission` as the
  authority for the namespace dimension and requires the other two to delegate
  or be fenced; the wider consolidation is out of scope.
* `RbacTenantContext` (`rbac_context.rs:197-202`) gains the namespace
  dimension. Bindings attach to principal/tenant, never to an API key, so key
  rotation does not break them (`UserInfo` in `auth.rs:42-49` has no namespace
  field and does not gain one).
* Resolution failure and authorization failure are **the same `403`**, and
  neither ever falls through to another namespace or tenant.

=== D9 — Wire surface

`X-ProximaDB-Namespace`, symmetric with how tenant already enters. A path
segment (`/api/v2/{alias}/…`) would fork every route in the generated OpenAPI
spec and force regeneration of all four SDKs for no isolation benefit.

The header **inherits `HeaderTrustPolicy` unchanged** — the existing policy for
bare `X-Tenant-ID` states the reason in code: *"a tenant asserted via bare
header without an authenticated binding is a masquerade vector, not an
identity."* A namespace header without that policy re-opens exactly what D8
closes. A `NamespaceIdSource` provenance enum mirrors `TenantIdSource` so audit
can distinguish header-asserted from default-resolved from grant-bound.

**pgwire, gRPC, and Arrow Flight are deferred to a follow-up ADR**, not left
implicit: pgwire (5433) has no headers and needs a `search_path`/database
mapping, gRPC needs metadata, Flight needs the descriptor. A surface that
silently defaults is a surface where every principal shares one namespace, so
these must be closed before the multi-tenant posture is claimed — but they
carry SDK-regeneration cost that would stall the seam decision.

== Consequences

* One resolution point, compiler-enforced, replacing a storage-layer constant.
* Rename without rewrite; fork/branch/archive as new ids behind aliases; per-
  namespace storage-pool-class / access-tier routing (ADR-036) by remapping the
  id.
* Cost: one cached lookup per request (negative-cached), a context field, a
  registry with CAS semantics, and namespace-dimension permission checks.
* Deployments unchanged on disk: single-tenant continues to resolve the literal
  `ns_default`, so **existing paths are byte-identical** and the change is
  mixed-read-safe by construction rather than by migration.

== Explicitly out of scope

* The 2026-07-26 ingest failure (TD-FLUSH-6) and the warm-manifest path defect
  (TD-CACHE-5).
* A backfill/migration for empty-namespace data. Because of the hardcoded
  `ns_default`, existing objects are at `data/{tenant}/ns_default/{coll}/`, and
  fail-closed validation makes `data/{tenant}//…` unreachable. **Verify by
  listing a production container before writing any migration** — as far as the
  code shows, there is nothing to backfill.
* Cross-namespace query federation. Namespace is a hard boundary for data
  (paths are disjoint; letting the planner join across namespaces would
  reintroduce isolation-as-predicate). Catalog LIST stays a control-plane
  operation gated by `NamespaceRead`, so discovery works without weakening it.
* The account tier's own design — it exists (`account_id` +
  `account_or_default()` + `DEFAULT_ACCOUNT_ID`) and is the worked example this
  ADR mirrors, not a question this ADR reopens.
* Consolidating the three `Permission` enums beyond designating an authority
  for the namespace dimension.
* Changing authn mechanisms or the physical path contract.

== Acceptance

. **Path-identity ratchet** — rendered paths byte-identical before/after the
  context/threading slice, for every existing collection. This is the
  mixed-read-safety proof.
. Two tenants each omitting an alias resolve to **different** `namespace_id`s,
  and neither is a shared constant. Single-tenant: principal and tenant
  defaults resolve to the same id, and it is a real id.
. Unauthorized alias ⇒ `403` with **no catalog read on the second attempt**
  (proves negative caching; closes the DoS amplifier).
. Alias rename ⇒ physical path unchanged **and** resolution + query caches
  invalidated; concurrent double-rename leaves exactly one binding.
. Delete-then-recreate the same alias ⇒ new id; objects under the retired id
  unreachable through the new alias.
. Bare `X-ProximaDB-Namespace` under `AuthenticatedOnly` without an
  authenticated binding ⇒ rejected, with the source recorded.
. Metering rows carry the resolved `namespace_id` label and roll up to the
  per-tenant total exactly.
. No `PROXIMADB_TYPED_PATHS` production enablement until the D4 `u16`
  wrap is fenced.

== Sequencing

ADR-027 (the DrPath authority this amends) and ADR-031 (typed paths) are **both
Proposed**. Filing a third Proposed ADR that depends on two unaccepted ones
compounds design debt, so one of the following is required before
implementation lands:

* fold this decision into ADR-027 as an amendment (it already owns the path
  contract), **or**
* accept ADR-027 first and state the acceptance ordering explicitly here.

Implementation slices are tracked in TD-NS-1:

* **S1 — structural, zero behavior change.** Split `DrResolvedPath` by meaning;
  add `namespace_id` to the ingress context and thread it; delete the
  storage-layer constants and the `expect`; resolve single-tenant to the
  literal `ns_default` so paths are byte-identical.
* **S2 — the seam.** Registry with CAS uniqueness and retired-id reservation;
  `Namespace*` authorization; per-tenant default bound at tenant create;
  resolution cache with negative caching and rename invalidation.
* **S3 — wire surface.** REST header + trust policy + provenance; then the
  pgwire/gRPC/Flight follow-up ADR, with SDK regeneration in the same PR.
