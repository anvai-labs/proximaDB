== Context

ADR-086 prevents a serving process from beginning a compaction whose measured
in-memory projection cannot fit its RAM budget. That is the correct safety
floor, but it deliberately leaves the LSM tree horizontal when no pair of
whole segments fits. The 3.3M-vector release run retained three query-visible
segments under a 5 GiB compaction ceiling. Its largest comparable writer task
fell from 30.86x to 8.44x incremental RSS, but the maximum observed task still
used 10.75 bytes of incremental RSS per byte of compressed input. A single
882 MiB consolidation therefore projects beyond 10 GiB before the serving
process's WAL, caches, queries, and allocator baseline are counted.

Keeping additional immutable segments is stable but directly multiplies vector
search work. The same run measured 58.63 object-cold GETs/query across three
segments at recall@10 0.981. Existing one-segment 3.3M geometry measured 24.478
GETs/query at recall@10 0.980. Consolidation is therefore an object-operation
cost lever, not merely storage housekeeping.

The rejected shortcuts do not solve the system problem:

* raising the in-memory input cap converts an explicit admission failure into
  an OOM risk because process baseline RSS is outside that reservation;
* OS swap lets an unbounded allocator decide which serving/query pages to evict
  and provides no per-task capacity, cleanup, or cancellation contract;
* spilling the already-materialized `Vec<ProximaRecord>` is too late;
* staging intermediate runs in Azure/S3/GCS adds PUT/GET/DELETE operations for
  disposable data and turns local construction into a cloud cost;
* a dedicated Spot compactor is an optional placement policy, not a prerequisite
  for making the engine memory-safe; and
* one giant file is not itself more selective. The read win comes from fewer
  independently probed segments plus a retrained IVF geometry.

== Decision

=== D1 — Spill is an OSS execution mechanism; placement remains policy

ProximaDB implements deterministic application-managed compaction spill to an
operator-selected *local filesystem* directory. The name is storage-neutral:
HDD, managed SSD, instance SSD, and NVMe are all valid correctness targets.
Latency and durability differ, but scratch is disposable and never authoritative.

The OSS engine owns resource admission, record ordering, MVCC/deletion-vector
correctness, bounded construction, recovery cleanup, atomic publication, and
neutral metrics. Anvaiops may decide tenant priority, whether to enable spill,
local versus remote worker placement, Spot/on-demand choice, and provider-price
economics. The engine does not contain prices or commercial tier policy.

=== D2 — RAM and scratch are independent currencies

Enabling spill does **not** raise or bypass ADR-086's in-memory ceiling. The
planner chooses one complete execution plan before reading or training:

----
in-memory: projected_ram = input_bytes * measured_memory_amplification
           projected_scratch = 0

local-spill: projected_ram = configured bounded working set
             projected_scratch = input_bytes * conservative scratch amplification
----

The release/Azurite 3.3M proof on 2026-08-03 invalidated the initial 4x scratch
assumption. A 706,307,501-byte four-segment input reached 5,319,977,219 bytes of
simultaneously live scratch (7.532x) while holding the external cell-order run,
ordered-f32 spool, Region-D blocks, and encoded regions. The default is therefore
10x: 33% headroom over that measured peak. This reservation is intentionally
conservative; it does not cause extra writes. Future schema/dimension evidence
may raise the ratchet or replace the ratio with a footer-derived byte model, but
must never silently lower it below the measured envelope.

The exact rebased cache-promotion run independently measured 7.492x live scratch
for a 690,242,135-byte / 2.58M-row spill, inside its 10x reservation. Its whole-
process RSS delta was 8.51 GB because the sampling window also contained flush,
in-memory compaction, WAL, cache, and allocator state; it is not evidence that
the complete serving process fits the 512 MiB spill working-set reservation.

The spill plan is admitted only when its fixed RAM reservation fits current
cgroup/process headroom *and* its scratch reservation fits both process-wide
reserved scratch and current filesystem availability. Reservations are RAII
owned and released on success, error, cancellation, or shutdown. Every task
uses the same resource acquisition order. A task that fits neither plan stays
queued; it does not start sorting, sampling, clustering, or encoding.

Initial rollout is runtime default-OFF (`spill_enabled = false`). This is a
construction-path gate, not a PAX format gate: both paths produce the existing
PAX layout, so no Cargo feature or new on-disk version is introduced.

=== D3 — Two external orderings are necessary

The bounded pipeline is:

----
immutable PAX blocks
  -> external runs sorted by (oid, effective_version, created_at, updated_at, ordinal)
  -> k-way MVCC merge (one OID group resident)
  -> deterministic strided IVF training sample
  -> external runs sorted by (cell_rank, PC1, source_ordinal)
  -> k-way cell-order merge into the PAX writer
----

MVCC resolution and PAX locality require different orderings. Combining them
would either keep every winner in RAM or make version resolution incorrect.
Every tie has a stable source ordinal derived from deterministic input-file,
block, and row order, so morsel size and worker scheduling cannot change output.

For feature-gated deletion vectors, the input stream applies each immutable
segment's versioned deletion vector by source row position before source identity
is discarded. This removes the current corpus-sized deleted-OID set from the
spill path. Input deletion-vector objects remain live until the replacement is
published and the old inputs are retired.

The implementation also closes a pre-existing authority gap found by the real
PAX spill test: `ProximaRecord.record_version` was not persisted in PAX, so any
post-flush compaction could reinterpret every row as legacy version 1. Column 14
is now an additive, fixed-width `u64` version stripe. Its presence is the format
marker; old blocks omit it and decode to the resolver's existing zero/version-1
sentinel, while a present but malformed stripe fails closed. General PAX writes
remain behind the default-OFF `PROXIMADB_PAX_RECORD_VERSION` bake gate. Local-
spill output enables it under spill's own default-OFF gate so a later rewrite
does not discard MVCC authority. The uncompressed cost is exactly 8 bytes/row
(7.45 GiB at one billion rows) before the existing optional lossless scalar
compression layer.

=== D4 — Train once from a bounded deterministic sample

The MVCC pass reports survivor and usable-vector counts. A second sequential
scan selects the same deterministic stride law used by the existing compaction
planner, bounded by the configured IVF training cap. PCA and seeded k-means are
fit only from that sample. Every survivor is then projected and assigned while
cell-sort runs are produced; only centroid/radius/count accumulators remain in
RAM.

The resulting `CoarseModel` is the existing Region A0 model. Cell count remains
IOP-derived and `nprobe` remains a read policy. Spill does not introduce a
second quantizer, change recall thresholds, or treat radii as a correctness
bound.

=== D5 — PAX construction is disk-backed, not a final materialization

The spill writer preserves the existing PAX bytes and region order while using
bounded local components:

* Region D blocks are compressed one block at a time directly into a local file;
* ordered f32 vectors are written once to a fixed-width local spool;
* RaBitQ centroid and SQ8 min/max are fit by sequential reduction;
* bounded encode batches write Region A and B code files directly;
* the OID-position resolver is serialized in stream order without retaining a
  `Vec<String>` plus `HashMap` for every row;
* the existing block index, cell counts/radii, and small control metadata remain
  in RAM; and
* final assembly copies header/A0/A/B/resolver/D/footer/tail sequentially into
  one local final file.

Only the completed final file is uploaded. Temporary runs and regions are never
written to object storage. After publication, cache-on-write reads bounded
control metadata (header, A0, RaBitQ parameters, footer) from the retained local
PAX and streams immutable Region A and, for policy `all`, Region B directly
into the persistent disk cache in 64 KiB chunks. It neither rereads the object
nor constructs a segment-sized `Arc`. If the persistent tier is disabled,
bounded control metadata is still admitted to DRAM and large regions retain
the normal read-through behavior.

=== D6 — Publication is the only visibility boundary

Each task owns a scratch directory named from its immutable task identity. A
task manifest records its source paths, source sizes, output path, admitted
resources, and phase; the directory name carries a stable immutable-task
fingerprint. Scratch files carry length framing and checksums; a truncated/
corrupt run fails the task.

One process-owned directory holds an exclusive advisory lock on a `.lease`
file for its full lifetime. A root-scoped cleanup lock serializes owner creation
and stale cleanup across server processes sharing one local or managed RWO
disk. PID and process-start fields remain audit metadata only: they never decide
liveness because PID namespaces can give multiple containers the same PID.
Startup may reclaim only a ProximaDB-prefixed owner whose lease lock can be
acquired non-blocking; unknown directories and locked owners are preserved.
Platforms without this lock contract fail spill initialization closed.

No intermediate is query-visible. The final local PAX is validated and, for an
object store, multipart-uploaded once to its unique final object key. Multipart
parts remain uncommitted and invisible; completion of the block/part manifest is
the object visibility boundary. The coordinator tracks this caller-managed
publication but does not upload a second remote `__compact` object and COPY it
to the final key. `file://` retains local staging plus atomic rename. Input
files, input deletion vectors, and their cache entries are retired only after
the final-object commit succeeds. Failure or cancellation leaves the source
segments authoritative. Startup removes abandoned task directories whose
owners hold no live filesystem lease; resume is not part of the first
implementation.

This distinction is part of the memory bound, not only a throughput tweak. The
10M/Azurite qualification constructed and uploaded a valid 2,757,638,547-byte
PAX, then failed publication because the Azure compatibility `move_file`
implemented COPY as whole-object GET into a `Vec<u8>` followed by PUT. Direct
multipart publication removes that segment-sized allocation, one full read,
one full write, and the temporary object-store copy. Azure's asynchronous
`Copy Blob` is not substituted here: its initial success response may still
carry `x-ms-copy-status: pending`, so deleting staging immediately would require
an additional completion protocol.

Remote publication is admitted only when the selected filesystem implementation
declares a bounded local-file upload path. Azure block upload, S3 multipart
upload, and GCS resumable upload qualify. GCS advances only after the service
acknowledges the complete requested range and cancels/fails closed on a partial
acknowledgement. Whole-object compatibility and encryption paths fail closed.
Decorators must forward the capability explicitly rather than infer it from a
URL scheme. This capability is checked before run generation, training, or PAX
construction so an unsupported publication target cannot waste compaction CPU.

Local publication is deliberately different. `file://` and bare paths write a
hidden temporary file in the final file's own directory, then rename that file
to the final name. The temporary file must not live in the configurable spill
directory: it may be a different filesystem, and cross-filesystem rename cannot
provide the required atomic visibility boundary. Arrow sidecars, when present,
are renamed first; the segment rename remains the reader-visible commit point.

The training guard is also a rescan obligation. It remains held across every
task in a follow-up chain, including a long higher-level spill. The terminal
worker checks L0 again at threshold one before releasing the guard. This closes
the measured race where a final flush published an untrained L0 during a 76.8s
L1 spill and no subsequent write existed to re-arm compaction.

== Consequences

* Small merges retain the faster in-memory path.
* A serving node can consolidate beyond its in-memory input cap when inexpensive
  local disk exists, without adding a compaction fleet.
* Spill trades additional sequential local bytes and wall time for bounded RSS
  and lower steady-state object-store GET fanout.
* Scratch capacity and local-disk bandwidth become explicit shared resources;
  only admitted tasks may consume them.
* The planner may still retain multiple output segments when rewrite time,
  failure domain, or scratch capacity makes a single segment unattractive.
* The first release does not use OS swap, remote scratch, resumable intermediate
  state, or commercial scheduling heuristics.

== Verification

The gate may be promoted only after all of the following pass:

. byte-for-byte deterministic output across repeated runs and different run/
  encode batch sizes for a fixed input and configuration;
. semantic parity with in-memory MVCC output, including version gaps, duplicate
  versions, tombstones, TTL expiry, append-only rows, non-fp32 precision, and
  source-position deletion vectors;
. injected ENOSPC, checksum corruption, cancellation, and publication failure
  leave all source segments readable and reclaim scratch;
. process-wide RAM and scratch reservations prevent cross-collection
  oversubscription and release through every exit path;
. a flush that publishes L0 during a higher-level spill is discovered by the
  completion rescan and promoted without requiring another write;
. spill disabled is behavior-identical to ADR-086;
. release/Azurite 3.3M compaction consolidates beyond the 5 GiB in-memory cap,
  keeps every explicitly accounted spill buffer within its working-set
  reservation, reports whole-process RSS separately, preserves recall@10 of at
  least 0.98, and improves GETs/query over the three-segment control;
. no temporary object-store writes are observed; and
. `cargo clippy -- -D warnings`, the cold-deletion-vector feature build, restart
  recovery, and the server release build are green.
