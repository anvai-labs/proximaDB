== Context

A first-principles + competitor review (2026-07-03) of ProximaDB's analytics/OLAP path
against Apache Gluten, Apache Comet, Velox, DataFusion, Databricks Photon, Snowflake, AWS
EMR, and Onehouse Quanton surfaced three findings:

. **The seams are excellent; the native OLAP *execution* is embryonic.** ADR-039 freezes an
engine-neutral `LogicalNode → ExecutionPipelineResult` seam with DataFusion as one swappable
backend; ADR-050 makes routing cost-based; ADR-033 ratifies Parquet+Iceberg for OLAP and PAX
for vectors; the Iceberg REST catalog is live (ADR-007). But the native relational executor
itself is a *row-wise Volcano iterator*: `crates/query/proximadb-relational-executor/src/lib.rs:1`
("Volcano-style executor… Pure pull model"), evaluating expressions row-at-a-time over
`ProximaValue` (`.eval(&row, …)`, `row.push(…)`). That is the model the entire field
abandoned — Kersten et al. (PVLDB 2018) show Volcano is 1–2 orders of magnitude slower than
vectorized or code-generated execution. And this Volcano is *today's engine for OLAP shapes
over PAX/native-backed tables*: `route_select` sends only parquet-backed relational plans to
DataFusion, everything else to Native — so invariant 1 is a real routing change for that arm,
not a relabeling. The function registry ships 10 base scalars (+6 aliases) and one
aggregate demonstrator (`crates/foundation/proximadb-functions/src/lib.rs`); window functions
are absent.

. **TPC-DS/TPC-H are CONFORMANCE ratchets, not PERFORMANCE evidence.**
`tests/{tpcds,tpch}_pgwire_e2e.rs` assert query counts (TPC-H 22, TPC-DS 16) over a tiny
deterministic dataset, gated in `.github/workflows/qa-gate.yml`. No scale factor, no
latency/throughput, no baseline vs DuckDB/DataFusion/ClickHouse. Per the co-design mandate
(principle #11: reject component microbenchmarks masquerading as end-to-end claims; method
step 2: capture the trace first), "competitive with Photon/Snowflake" is today an
*unmeasured* assertion.

. **The statistics substrate is DESIGNED, not WIRED into the DataFusion planner.**
ADR-037/038 specify a mergeable statistics envelope (min/max, NDV/HLL, TDigest, null-count,
freshness watermark) and `src/core/statistics/{summary,sketches,registry}` implement the
sketches. Today's consumers are the pgwire EXPLAIN selectivity surface
(`src/network/postgres/relational_pipeline.rs` → `statistics_registry().equality_selectivity`)
and the federated optimizer (`src/query/federated/optimizer/{selectivity,plan_calibration}.rs`)
— but **none of it reaches cost-based physical planning**: `schema_inference.rs` returns
`ColumnStatistics::new_unknown()`, its `extract_statistics` has *no call site*, and the
table providers default `statistics: None`, so the DataFusion planner plans blind (ADR-050
D2 / TD-DFR-1 is the close, in flight). No runtime filters (Dynamic Partition Pruning, bloom
semi-joins), no Adaptive Query Execution.

== First principles (why this shape)

* **Attack the DOMINANT cost term — and in cloud OLAP that is bytes scanned, not CPU.**
  Snowflake's entire thesis (SIGMOD 2016 §3.3.3) and the Iceberg manifest architecture are
  scan-avoidance systems; Quanton's wedge is work proportional to the data *differential*
  since the last run. Photon/Velox/Comet win ~2–3× on CPU (vectorization) but pruning +
  runtime filters win 10–100× on I/O. Therefore ProximaDB's competitive order of work is:
  scan-avoidance first (zone maps, bloom, runtime filters, deletion vectors, late
  materialization, materialized aggregates), vectorized execution second. This inverts the
  naive "build a faster engine" instinct and is the co-design spine applied to analytics.
  *Deployment caveat:* the bytes-scanned-dominant ordering holds for the object-store
  lakehouse target; on embedded / single-node local-NVMe (the "win single-node first"
  non-goal, where DuckDB's CPU efficiency sets the bar) CPU is the binding constraint —
  which reusing DataFusion's vectorized kernels covers. The TD-OLAP-4 ledger measures the
  two regimes separately, never averaged.

* **Vectorized-first; do NOT reimplement operators.** The 2020–2026 consensus (Photon,
  SIGMOD 2022 Best Industry Paper; DuckDB; ClickHouse; Velox; DataFusion) is
  vectorized-interpreted execution over columnar Arrow batches, chosen for development
  velocity, observability, and runtime adaptivity — not peak microbenchmark throughput.
  Photon explicitly *"chose to build the engine using the vectorized-interpreted model in
  lieu of code generation."* Only HyPer/Umbra/CedarDB remain codegen-flagships, and even
  they hybridize (Data Blocks; Incremental Fusion, ICDE 2024). ProximaDB already has
  DataFusion behind a frozen seam (ADR-039) and cost-based routing toward it (ADR-050).
  Reusing DataFusion's vectorized scan/filter/agg/join/sort kernels — instead of growing a
  parallel native operator engine — collapses years of work into integration and keeps one
  function definition (ADR-039 invariant 4).

* **The native work that is WORTH doing is the SCAN, co-designed with ANN.** ProximaDB's
  unique asset is a PAX substrate already co-designed for vectors (RaBitQ/SQ8 tiers, zone
  maps, bloom, `RecordReader`). No incumbent co-designs ANN + OLAP scan on one format:
  Lance concedes OLAP; Snowflake's `VECTOR` is a 4096-dim, no-quantization bolt-on with no
  Iceberg-table support and ANN = a separate Cortex Search object; ClickHouse ANN
  pre-filtering falls back to brute-force scan; pgvector is single-node. A PAX-native scan
  operator that emits Arrow `RecordBatch`es to DataFusion is *both* the performance lever
  (one reader, one prune stack, one I/O-trace path — ADR-027) *and* the structural
  differentiator (ANN index and OLAP scan over the same geometry), eliminating the
  CDC/replica/cache Frankenstein stack that causes vector+SQL to "silently discard over 30%
  of correct results" on JOINs (arXiv 2506.23071).

* **The boundary is the contract; keep it standard outside.** Iceberg+Parquet is the
  interop seam (the format war is decided: AWS S3 Tables chose Iceberg Dec 2024; Databricks
  acquired Tabular Jun 2024; Apache Polaris graduated TLP Feb 2026 and now owns the catalog
  fight). ProximaDB keeps internal verticality (PAX scan + ANN co-design) and external
  standardness. The *working* federation seam today is **Iceberg REST** (ADR-007, live — Spark/Trino/DuckDB/Snowflake read the tables natively) plus **Arrow Flight SQL**; the engine-neutral `LogicalNode` IR is *structurally compatible* with a future Substrait binding, but Substrait is not yet production-federation-ready for the Spark/Trino mainstream: Spark/Trino do not natively consume it (Gluten bridges Spark), and DataFusion's own Substrait plan-validation suite is still landing (apache/datafusion#15069). ADR-033/039 unchanged.

== Decision (invariants)

. **OLAP execution = vectorized-over-Arrow via DataFusion; the native Volcano is OLTP-only.**
  Bulk scan/filter/project/aggregate/join/sort over analytical tables executes in DataFusion's
  vectorized kernel set. The row-wise `proximadb-relational-executor` Volcano is the floor for
  OLTP / point-lookup / low-cardinality shapes (where row-wise is fine) and the
  no-DataFusion build floor (ADR-039 Verification §3 — the "TD-181" number is overloaded in
  the ledger) — *not* the OLAP execution engine. Conformance
  is identical either way (TPC-H/TPC-DS bind to the `LogicalNode` seam, not the engine).

. **The "NativeOlap route" (blueprint P2) is a PAX-native SCAN operator, not a parallel
  operator engine.** It lowers `LogicalNode::Scan` (with pushed predicate + projection) to a
  `RecordReader`-backed scan that applies hierarchical pruning (zone maps TD-154, bloom,
  range coalescing TD-151) and emits Arrow `RecordBatch` consumed by ordinary DataFusion
  operators. Do NOT reimplement HashAgg/HashJoin/Sort natively. This refines blueprint §3/§4
  and is tracked under TD-OLAP-1.
+
NOTE: **The "do NOT reimplement HashAgg/HashJoin/Sort natively" prohibition is REVERSED by
link:ADR-054-native-execution-engine-progressive-cutover.adoc[ADR-054] (Accepted 2026-07-09).**
The PAX-native *scan* role stated here is unchanged; ADR-054 adds an operator plane behind the
`proximadb-execution-contracts` seam, default-off, promoted only through the TD-OLAP-4 ledger
gate. See the Erratum below ("Invariant 2's operator prohibition reversed").

. **Scan-avoidance is the primary competitive work order.** Before any execution-kernel
  optimization, the work that moves the cloud-dominant cost term (bytes scanned) is: wire real
  statistics into the planner (ADR-050 D2 / ADR-037/038 → TD-OLAP-2); add runtime filters —
  Dynamic Partition Pruning + bloom semi-join (TD-OLAP-3, the Photon signature lever);
  deletion vectors (ADR-025) and relational late-materialization (TD-OLAP-5). Each is
  flag-gated, default-off, and promoted only after the per-query I/O trace (TD-158) shows it
  moves the dominant cost term — observe→ingest→act (co-design method §3).

. **Competitiveness is measured, not asserted.** TPC-DS/TPC-H gain a *performance* tier
  (SF1, then SF10) with an evidence ledger: latency + bytes-scanned vs DuckDB, plain
  DataFusion-on-Parquet, and ClickHouse, on the same object store, in CI. The conformance
  ratchets (counts only go up) remain. No "beats Photon/Snowflake" claim enters a doc without
  a ledger entry (mandate #11). TD-OLAP-4.

. **Non-goals (explicit, to protect focus).**
  * No LLVM/Cranelift query codegen now — vectorized-first; codegen layered later *only* on
    measured hot expressions (Velox/ClickHouse do this experimentally; Photon explicitly
    declined for velocity/observability/adaptivity).
  * No distributed MPP/Ballista now — win single-node / pseudo-distributed / embedded first
    (the DuckDB / InfluxDB-IOx / GreptimeDB path); distribution via the pluggable
    `ExecutionEngine` trait later.
  * Do not overclaim five-mode parity — the defensible competitive niche is **vector + OLAP +
    lakehouse (3-mode) co-design**; graph/document are stretch modes.

== Execution order (SOLID seam discipline)

The TD-OLAP work is sequenced so every slice lands behind a **stable seam** (SOLID applied to
database engineering — depend on ports, extend behind frozen boundaries, keep each component's
responsibility narrow; see `SOLID_DATABASE_DEVELOPMENT_STANDARDS_2026_06_27.adoc`):

[cols="1,3,4", options="header"]
|===
| Pri | Work | SOLID / engineering rationale
| P0a | TD-OLAP-2 slice 1 (TD-DFR-1: `SegmentStatistics` → `ColumnStatistics`)
| **DIP** — the planner consumes the ADR-042 statistics *port*, never engine internals;
  cheapest unlock; feeds cost routing (ADR-050) and P2a runtime filters.
| P0b | TD-OLAP-4 harness skeleton (SF1 advisory ledger)
| **Measure-before-optimize** (co-design method step 2) — the ledger is the promotion gate
  for every later slice; it lands before any tuning so regressions have a floor.
| P1a | TD-OLAP-1 PAX-scan → Arrow (gated on TD-154/TD-162a-2/-3)
| **SRP** — the scan owns scan+prune only, operators stay DataFusion's; **OCP** — a new
  route added behind the frozen ADR-039/`ComputeBackend` seam, no existing path modified;
  **LSP** — the scan `ExecutionPlan` is substitutable: identical conformance ratchets on
  both routes.
| P1b | TD-OLAP-5 function tranches + window framing
| **OCP** — one `ProximaValue` kernel, N bindings (ADR-039 invariant 4); coverage is
  additive behind the registry, tracked as a monotone ratchet.
| P2a | TD-OLAP-3 runtime filters (DPP + bloom semi-join)
| Blocked by P0a (stats cost the filter decision); **ISP** — one `proximadb-bloom`
  primitive, two narrow consumers (ANN pre-filter ADR-011 + OLAP semi-join): converge,
  don't duplicate.
| P2b | TD-OLAP-5 late-materialization (needs P1a) + tenant-keyed result cache
| Structural tenant isolation in the cache key (co-design mandate: isolation is never a
  predicate); LSN eligibility per ADR-051/ADR-046.
|===

Cross-cutting rule: no slice may depend on another slice's *internals* — only on the named
seams (`ComputeBackend`, `RecordReader`, `SegmentStatistics`, `ProximaFunctionRegistry`,
`proximadb-bloom`, the TD-158 trace). That is what keeps each TD independently landable,
testable via ports, and reversible (every slice is flag-gated, default-off).

== Consequences

* **Positive.** Reusing DataFusion execution avoids reimplementing a vectorized operator
  library, a function library of 100+, codegen, spill, and morsel scheduling — the multi-year
  tail that makes "build a competitive OLAP engine" intractable for a small team. The
  PAX-native scan is the one place ProximaDB adds *unique* value (ANN+OLAP co-design) and is
  additive behind the frozen seam. Scan-avoidance attacks the term that actually dominates
  cloud cost.
* **Costs / watch-items.**
  - The PAX-scan→Arrow bridge must be **single-materialization** — stripe bytes are decoded
    into Arrow buffers exactly once (a compressed/quantized stripe cannot be "zero-copy");
    from there, no further copies across the DataFusion `TableProvider`/`ExecutionPlan`
    boundary (Arc'd buffers, same shape as `src/datafusion/proxima_scan_exec.rs` today) —
    and prune-stack semantics must be preserved across it.
  - DataFusion's hash-join does not yet spill (Comet 0.15 caveat) — mitigation is owned by
    the TD-OLAP-1 route step: route large joins to sort-merge above a size threshold until
    upstream spill lands; the ledger must flag every query affected.
  - Vectorized-first accepts DataFusion's per-op microbenchmark ceiling vs Velox (EDBT 2026,
    Zhao & Fang, SFU: DataFusion 1.45× vs Velox 1.98× over Spark on TPC-DS top-20) in
    exchange for the Rust/Arrow ecosystem, the seam, and development velocity — the ledger
    makes the trade explicit rather than hidden.
* **Relationship to ADR-050.** ADR-050 activates cost-based routing to DataFusion for
  Parquet-backed tables and feeds real stats. ADR-052 extends that posture to the PAX-backed
  native path (the scan operator) and fixes the execution-model + dominant-cost-term +
  measurement framing that ADR-050 does not cover. The two compose; they do not conflict.

== Erratum (2026-07-06)

A re-research pass (5 agents, primary-sourced) corrected three framing points. **None alters invariants 1–5**; they retire an unfalsifiable claim and record context the original omitted.

* **Federation seam (corrects the prior "Substrait-ready `LogicalNode`" phrasing).** Substrait is *not* production-federation-ready for the Spark/Trino mainstream in 2026 — Spark/Trino do not natively produce/consume it (Gluten is the de-facto Spark bridge, not Spark itself), and DataFusion's own Substrait plan-validation suite is still landing (apache/datafusion#15069, epic #16248; earlier plan-validity gaps tracked in #12244). The *actual* working federation seam today is **Iceberg REST** (ADR-007, live — Spark/Trino/DuckDB/Snowflake read the tables natively) + **Arrow Flight SQL**. `LogicalNode` remains structurally compatible with a future Substrait binding (engine-neutral, zero DataFusion deps per ADR-039); the correction is to stop calling it "ready."
* **Distributed execution (context for the "no Ballista now" non-goal).** The deferral is behind an *existing sequenced* blueprint — `DATAFUSION_BALLISTA_DISTRIBUTED_EXECUTION_2026_06_05.adoc` (P0 contract → P1 DataFusionLocal splits → P2 Ballista adapter → P3 multi-node): the path exists and is deferred, not absent. Re-research reaffirmed single-node/elastic is the correct 2026 posture: only **0.03% of Redshift queries scan >10 TB** (MotherDuck "Redshift Files" analysis of AWS's public Redset fleet dataset — VLDB 2024, PVLDB vol. 17 — ~500M queries); DuckDB runs **TPC-H SF100,000 (100 TB)** on a single `i8g.48xlarge` (1.5 TB RAM, 192 Graviton4 cores); MotherDuck's **<100 ms per-tenant cold-start / scale-to-zero** (Duckling spin-up — not query latency) is the production proof that single-node elastic competes; Ballista's production footprint is thin (Spice AI — its most advanced user — built multi-active HA, mTLS, and an object-store shuffle serialized with Vortex IPC — Vortex itself is SpiralDB / Linux Foundation — themselves, in a fork).
* **Elastic-single-node posture (recorded, not actioned).** The defensible Rust wedge is **not** "scale to zero" (table-stakes in 2026 — every vendor markets it; PointFive May 2026: 34% of Snowflake warehouse spend is idle warehouses) and **not** "no GC pauses" (Generational ZGC, Java 21+, drives pause times to sub-millisecond in production — Netflix 2024). It is **no JIT warmup + 5–10× lower memory + single-binary density** (Spice AI: 2–8× faster at ~8× less RAM than Spark, per benchmark; Arroyo: a single ~50 MB Rust binary vs a JVM Flink stack — faster startup, smaller footprint). The only honest claim is a *measured* cold-start number on a real ProximaDB analytical workload — recorded as a Phase-4 measurement target (a TD-OLAP-4-style evidence ledger), off the critical path while TD-OLAP-1..6 prove single-node competitiveness.
* **Tracked set extended.** TD-OLAP-6 (sort-on-materialize — team), TD-OLAP-7 (selective GPU OLAP — the only analytics cohort the original plan didn't address; libcudf-via-FFI behind the `ExecutionEngine` seam + the fused ANN+filter+agg wedge), TD-OLAP-8 (incremental / materialized-view / streaming-OLAP — attacks bytes-RECOMPUTED, Quanton's wedge) — all Phase-2/strategic (P3), sequenced after the TD-OLAP-1..6 scan-avoidance foundation; none gates current execution.
* **Invariant 2's operator prohibition reversed — 2026-07-09 (ratified).** The "native-operator-engine end state is retired, not deferred" stance above (Supersedes field + invariant 2 "do NOT reimplement HashAgg/HashJoin/Sort natively") is **reversed** by link:ADR-054-native-execution-engine-progressive-cutover.adoc[ADR-054] (Accepted 2026-07-09) on evidence this ADR did not have at acceptance (ClickBench Phase A 2026-07-06 + the TPC-H SF=0.01 join micro-ledger: the residual gap is compute-bound, not bytes-bound, for heavy joins / the q07 kernel pathology / multimodal co-execution). ADR-054 reverses **only** invariant 2's operator prohibition — an operator plane is added behind contracts, default-off, promoted only through the TD-OLAP-4 ledger gate; **invariant 2's scan role and invariants 3/4/5 stand** (the latter strengthened — every native operator is ledger-gated). Read invariant 2 below together with this reversal (a NOTE marks it inline).
