== Context

The SIFT1M end-to-end benchmark (2026-07-29, post-async-compaction develop)
measured **205 GETs/query** cold — 10× the competitive threshold (~20). This
makes retrieval COGS ($141.83/M queries on Azure) exceed the rate-card KRU
($50/M) by 2.8× → negative margin. At 33% margin the price would be $211/mo —
uncompetitive with Turbopuffer ($16) or S3 Vectors ($2.53).

Root cause: **9 segments** (3 L0 + 1 L1 + 5 L2). Each segment adds ~7-8 reads
per cold query (header + A0 + probed RaBitQ subset + footer + SQ8 ranges +
OIDs). The 5 L2 segments (~1GB total) never merge because the compaction
framework's `level_multiplier = 2.0` sets the L2 threshold to 20 files (5 ×
2² = 20) — unreachable with only 5 files.

== Decision

**Tune the compaction for GET-count minimization, not write-amplification
minimization.**

RocksDB's `level_multiplier = 2.0` is tuned for write amplification (each level
holds ~2× the data of the one below → fewer total rewrites). For ProximaDB's
vector search over object storage, the dominant cost is **GET round-trips per
query** (the co-design cost spine, ADR-052), not write amplification. Fewer
segments = proportionally fewer GETs, regardless of write cost.

=== D1 — `level_multiplier: 1.0` plus pair consolidation

Change `CompactionConfig.level_multiplier` default from `2.0` to `1.0`. Every
query-visible level uses the same multiplier. L0 retains its write-batching
threshold (5), while L1+ use `higher_level_file_threshold = 2`: two immutable
segments are the smallest input that can reduce fanout, and a single-file
guard prevents pointless promotion/retraining.

Effect at 1M scale:
- The historical five L2 files trigger under the corrected policy.
- The current two-L1 benchmark geometry also triggers instead of permanently
  stranding two complete search cascades.
- Segment count: 9 → 1-3.
- Cold GETs/query is expected to fall proportionally; the final value is an
  acceptance measurement, not assumed from file count.

The default MUST carry a strong comment explaining the co-design rationale so
future agentic sessions don't "fix" it back to 2.0:

```rust
/// Vector-search compaction level multiplier.
///
/// Controls how aggressively higher LSM levels (L1, L2, ...) compact relative
/// to the higher-level base. The file-count threshold at level N >= 1 is:
///   threshold_N = higher_level_file_threshold × level_multiplier^(N - 1)
///
/// DEFAULT: 1.0, with higher_level_file_threshold=2.
///
/// WHY 1.0 for vector search (not RocksDB's 2.0):
///   The dominant cloud cost for a vector DB is GET round-trips per query
///   (ADR-052). The historical policy coupled the L0 base (5) to a 2.0
///   multiplier, making the L2 threshold 20 and stranding five L2 files.
///   The current policy separates L0 write batching from L1+ read fanout.
///
///   At 1.0, any pair at L1+ consolidates. A separate single-file guard
///   prevents size triggers from cascading one immutable file through levels.
///
///   Write amplification remains material in bytes, CPU, and model-training
///   time even when request charges are small, so it is measured separately.
///
/// BOUNDED [1.0, 1.5]: the config validator WARNS if the value is outside
/// this range. Below 1.0 has no useful pair-reduction benefit once the
/// single-file guard is applied. Above 1.5 increasingly strands multiple
/// query-visible files. TOML override CAN exceed the bound but gets a warning.
pub level_multiplier: f64,  // default: 1.0
```

**Bounding rationale [1.0, 1.5]:**

[cols="1,2,2"]
|===
| Value | L2 threshold (2 × value) | Recommendation

| 0.5 | 1 | ❌ Over-compaction — single-file triggers require a guard.
| 1.0 | 2 | ✅ **Default** — every pair at L1+ consolidates.
| 1.25 | 3 | ✅ Acceptable — slightly conservative for write-heavy workloads.
| 1.5 | 3 | ⚠️ Upper bound — allows two segments to remain at L2+.
| 2.0 | 4 | ❌ Segment fanout grows faster than the read-cost target permits.
|===

=== D2 — Worker-driven settle pass

During sustained ingest, the L0 early-return can starve the higher-level loop.
After every successful background compaction the same worker immediately calls
`check_compaction_needed` again and enqueues the next due level. Settlement
therefore follows publication without depending on a new flush or an
unmeasured wall-clock tick.

=== D3 — One effective SST configuration

`level_multiplier` and `higher_level_file_threshold` remain TOML-controllable.
`StorageConfig::effective_sst_config()` applies the common
`storage.compaction_config` to every runtime SST instance unless an explicit
`storage.sst_config.compaction_config` override exists. This closes a measured
split-brain where TOML parsed correctly but a default-constructed search/flush
engine silently ignored it. Validation rejects thresholds below 2 and warns
when the multiplier is outside [1.0, 1.5].

=== D4 — Explicit compaction must not false-succeed

The Arrow Flight `compact_collection` action resolves the authoritative
catalog collection, passes its numeric stable object ID and storage assignment
to SST, admits a real compaction task, and optionally waits for worker
quiescence. The former implementation returned success with zero work from a
stub, which made operator-triggered verification invalid.

== Co-design analysis

The dominant query-path cost term is **I/O round-trips + egress** (ADR-052),
but compaction CPU, memory, and rewritten bytes remain capacity constraints.
For vector search on Azure Blob:

- Hot-tier GET pricing is operation-based; the economic model uses
  $0.005/10K reads and records bytes separately for latency, network, egress,
  and non-Hot tiers.
- The earlier ~7-8 GETs/segment model was a planning simplification. The
  measured two-segment cold path was ~42 GETs/query, so per-region physical
  traces are authoritative.
- Read requests and bytes are measured independently. Hot-tier request pricing
  makes GET coalescing valuable; bytes still affect latency/network and become
  directly billable on other access tiers.
- Compaction request charges may be small, but retraining and rewriting are not
  declared negligible without end-to-end CPU/RSS/byte evidence.

Therefore: **minimize query-visible segments subject to measured compaction
capacity.** The pair policy is the most aggressive threshold that reduces
fanout while the single-file guard avoids guaranteed no-benefit rewrites.

== Extreme co-design pressure test

. **Scale to 10M**: a threshold of two behaves like a leveled binary counter:
  at most one settled segment per occupied level, not one segment globally.
  Query fanout can therefore grow logarithmically. Cross-level universal
  consolidation or a target-segment-size policy is still required before
  claiming 1-2 segments at arbitrary scale.
. **Cache budget = 0**: the measured two-segment cold path was ~42 GETs/query,
  disproving the earlier static “8 reads/segment” estimate. The actual
  per-region trace, not the simplified cascade diagram, is the gate.
. **Write amplification**: pair compaction rewrites the full input pair and
  retrains the merged PAX model. Record elapsed time, peak RSS, bytes read, and
  bytes written before tuning beyond the pair floor.
. **Recall**: a merged model may improve representation, but this is a
  hypothesis. `recall@10 >= 0.98` is a hard post-merge measurement.
. **Compaction CPU**: workers keep flush non-blocking, but admission bounds
  concurrency rather than making CPU free. Search-vs-compaction interference
  remains part of the release benchmark.
. **L0 starvation during ingest**: the worker follow-up (D2) re-checks all
  levels immediately after each successful merge. The final benchmark must
  prove quiescence under the actual ingestion schedule.

== Acceptance criteria

. `level_multiplier` = 1.0 and `higher_level_file_threshold` = 2 by default,
  both TOML-controllable and inherited by every runtime SST instance.
. After 1M SIFT ingest + 120s settle: 1 query-visible segment.
. Cold GETs/query ≤ 20; local-disk-warm ≤10; first-query-after-write ≤5.
. Recall@10 ≥ 0.98 maintained.
. Local-file benchmark cold p50 ≤50ms; do not present it as Azure WAN latency.
. Retrieval margin > 50% at $50/M KRU.
