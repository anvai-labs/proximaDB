== Context

ProximaDB has **five** separate append-only log / queue implementations. Each re-rolls the
same machinery — a sequence counter, a path scheme, a recovery scan, an in-memory index — on
top of the raw `FileSystem`/`UnifiedCachingFilesystem`, and each has drifted on correctness:

* **AXIS EventLogQueue** (`src/index/axis/eventlog/`) — flush/compaction → index coordination.
  Its compaction leg receives **swapped arguments** so the body never runs, then increments
  `successful_migrations` (ADR-078); its persisted state is semantically stale after a restart.
* **audit EventLogEngine** (`src/storage/engines/eventlog/`) — MCP checkpoint / temporal /
  audit. Its index is **in-memory only** and its sequence counter resets on restart → silent
  data loss (TD-EVENTLOG-1, P1).
* **`services/events` EventLogService / EventLogWAL** — shared with the experimental SWIFT
  engine; partial.
* **audit sinks** (`src/services/{audit_sink,agent_memory}.rs`) — thin wrappers.
* **user-facing Queue modality** (`crates/.../proximadb-queue/`) — a first-class data model.

The duplication is the cost the codebase pays because **the shared primitive exists but was
never adopted for internal use.** `proximadb-queue` already centralizes the exact shape:

* **Segment-based, each topic in its own directory**: `{queue_root}/{topic}/{partition_id}/{segment_id}.qseg`.
* **Producer/consumer**: `Producer`, `Consumer`, `QueueClient`; per-tenant partitioning
  (`partition_for(tenant_id)` → per-tenant FIFO); per-partition **exclusive consumer leases**
  (cross-process CAS via `lease.meta`).
* **Three tiers**: memory (`crossbeam ArrayQueue`) → disk segment (group-commit fsync) →
  object-store archive (sealed segments uploaded via the injected `QueueFs` adapter →
  `adls://`/`s3://`/`gcs://`/`file://`; the reaper deletes the local copy once acked past).
* **Crash recovery**: replay sealed segments past the per-partition committed offset
  (`offset_store`, atomic commit), skipping already-acked messages.

It is **complete and tested** — 74 tests pass, covering disk→object→recovery round-trips,
restart (recover unconsumed, skip acked, fresh-node-from-archive), lease renew/reclaim,
offset atomicity, reaper, and metrics. Its own "Phase 1B scaffold" header was stale and is
corrected by this ADR's tracking PR. It is a **leaf crate** (only external deps: tokio,
crossbeam, serde, bincode), already wired into the runtime (`database.rs` builds
`QueueClient::open_with_fs`; `multi_server.rs` holds it).

This is not new architecture. **ADR-072 (Accepted) + TD-FOUNDATION-1 already ratify it:**
"ledger/queue/TS dedicated WALs become *impls of this contract*, not off-contract silos
(ratifies ADR-071)"; "siloed modalities consume tiering instead of re-rolling." The
`ConditionalKeyStore` atomic primitive is part of the same contract set. The codebase simply
has not caught up to its own decision.

== Decision

=== D1 — `proximadb-queue` is THE durable append-only log primitive, in `crates/horizontal/`

Repositioned from `crates/modalities/` (engines cannot depend on a modality crate — the
layering rule forbids it). It is leaf, so any layer may depend on it. The user-facing Queue
*modality* stays a product feature; it simply calls the same primitive. One
`QueueClient` per process (already constructed); each former silo becomes a **topic** with
its own directory under `data/{tenant}/{ns}/queue/{topic}/…` — flat keys (ADR-036), one
prefix-LIST per topic to recover, structural per-tenant isolation via `DrPathBuilder`
(not a predicate).

=== D2 — both producer/consumer AND pub/sub, via Kafka consumer-group semantics

Today the crate is **producer/consumer only**: each partition carries one exclusive lease +
one committed offset, so within a topic messages go to exactly one consumer (the work-queue
case). To serve fan-out consumers (audit: compliance + security + analytics each need *all*
events — per-subscriber topics would duplicate the data N times), the crate adopts
**consumer-group semantics**: exclusive *within* a group (two consumers in the same group
compete for a partition), independent *across* groups (group-A and group-B each consume all
messages with their own cursor). Mechanism: leases + offsets keyed by `(group, topic,
partition)`. Point-to-point is the one-group degenerate case.

=== D3 — migrate the siloed EventLogs onto topics, mixed-read-safe

Each silo becomes a topic, migrated per mandate #8 (read the legacy layout **and** the new
`.qseg`, suffix/magic-detected, default-OFF per topic until baked, round-trip + recovery
tests):

* `audit` (Strict, MiFID retention, archive tier) — fixes TD-EVENTLOG-1's restart data loss
  *structurally* (the queue's persisted sequence survives restart by construction).
* `axis-index` (per-collection partition) — **absorbs** TD-AXIS-3 S2: the "extract shared
  types, retire the queue runtime" work becomes "publish to the `axis-index` topic." The
  swapped-args no-op and the false metric go away by removal.
* `agent-state` (keyed by entity via `ConditionalKeyStore` `put_if_absent`, ADR-072) —
  MCP checkpoint get-by-thread. Resolves TD-EVENTLOG-1's end-state **and** the entity re-key
  together (one prefix-LIST read, concurrent-collision-safe).

Key-based reads (MCP checkpoint get-by-thread) are **not** a queue operation — they need the
`ConditionalKeyStore` index. The queue delivers ordered appends; the key index serves point
lookups. The audit/MCP construct = queue **+** ConditionalKeyStore, not queue alone.

=== D4 — deliberately separate from the collection WAL

The WAL (`canonical_wal.rs`) is the write-path durability floor with different
stability/access semantics (ADR-071). The queue is the **async/coordination** plane. They
are not merged.

== Consequences

* One storage↔compute boundary optimized once (the dominant cost — I/O round-trips — is
  minimized for *all* consumers, not per-silo); per-topic directories are the object-store
  flat-key layout; sealed segments tier Hot→Cool→Archive per-PUT (the at-rest cost lever).
* Three verified correctness defects (restart data loss, the swapped-args no-op, the false
  metric) are fixed *by removal* as each silo migrates, not by patching each.
* Semantics expand from point-to-point to producer/consumer + pub/sub without a second
  primitive (consumer-group model).
* Metering consolidates: storage (KSU), read/compute (KRU/KIU), outgress (KOU at the
  consumer) — per tenant, per topic.

== Alternatives considered

* **Keep the silos, patch each defect in place** — rejected: preserves five parallel
  recovery paths (three already wrong), five I/O patterns, and the naming collision; the
  defects recur. ADR-072 already rejected this.
* **Fan-out via per-subscriber topics** (one topic per audit consumer) — rejected: duplicates
  the data N times and multiplies I/O; consumer-group fan-out (D2) is the efficient, standard
  answer.
* **Merge the queue into the WAL** — rejected (D4): divergent stability/access semantics;
  ADR-071 keeps them split.
