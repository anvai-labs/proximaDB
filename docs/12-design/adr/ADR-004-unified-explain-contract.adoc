== Context

ProximaDB's explain output is currently protocol-specific:

* `src/query/explain.rs` provides `ExplainPlan` with `orchestration_steps` (list of strings), `VectorHints`, `GraphHints`, and cost breakdowns
* REST, gRPC, SQL, and UQL each format explain differently
* The explain plan is disconnected from the actual validated execution plan
* There is no way to see capability requirements, missing capabilities, or fallback decisions in explain output

The design resolution doc mandates: "Explain must be protocol-neutral and mechanically derivable from the validated plan."

== Decision

Replace the current orchestration-step-based explain with a **protocol-neutral ExplainPlan** that is derived from the `MultiModelPlanV1` (ADR-003) and shows the full operator graph with capability status.

=== Core Types

[source,rust]
----
/// Protocol-neutral explain plan derived from MultiModelPlanV1
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct UnifiedExplainPlan {
    /// Plan identifier (correlates with execution)
    pub plan_id: String,
    /// Whether this plan would execute successfully
    pub valid: bool,
    /// Operators in the plan with cost and capability info
    pub operators: Vec<ExplainOperator>,
    /// Capabilities required by the full plan
    pub required_capabilities: Vec<ExplainCapability>,
    /// Capabilities that are missing or degraded
    pub missing_capabilities: Vec<ExplainCapability>,
    /// Service bindings and their availability
    pub bindings: Vec<ExplainBinding>,
    /// Fallback decisions that were made
    pub fallbacks: Vec<ExplainFallback>,
    /// Overall diagnostics
    pub diagnostics: ExplainDiagnostics,
}

/// Single operator in the explain tree
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExplainOperator {
    /// Stable operator ID (matches PlanOperator.id)
    pub id: usize,
    /// Operator type name (e.g., "VectorSearch", "HashJoin")
    pub operator_type: String,
    /// Human-readable description
    pub description: String,
    /// Input operator IDs
    pub inputs: Vec<usize>,
    /// Estimated cost
    pub estimated_cost: Option<f64>,
    /// Estimated output rows
    pub estimated_rows: Option<u64>,
    /// Execution mode: Exact, Approximate, Degraded, Unsupported
    pub execution_mode: ExecutionMode,
    /// Model-specific hints (vector, graph, etc.)
    pub hints: HashMap<String, serde_json::Value>,
    /// Filter diagnostics (pushed vs residual)
    pub filter_diagnostics: Option<FilterDiagnostics>,
}

#[derive(Debug, Clone, Copy, Serialize, Deserialize)]
pub enum ExecutionMode {
    Exact,
    Approximate,
    Degraded,
    Unsupported,
}

/// Filter handling diagnostics for an operator
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FilterDiagnostics {
    pub pushed_predicates: Vec<String>,
    pub residual_predicates: Vec<String>,
    pub index_used: Option<String>,
    pub estimated_selectivity: Option<f64>,
}

/// Capability in the explain output
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExplainCapability {
    pub subject: String,
    pub operation: String,
    pub tier: String,
    pub reason: Option<String>,
}

/// Service binding status
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExplainBinding {
    pub service: String,
    pub available: bool,
    pub engine: Option<String>,
}

/// Fallback decision that was made during planning
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExplainFallback {
    pub operator_id: usize,
    pub original_strategy: String,
    pub fallback_strategy: String,
    pub reason: String,
}

/// Overall plan diagnostics
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExplainDiagnostics {
    pub source_protocol: String,
    pub planning_time_us: u64,
    pub optimization_rules: Vec<String>,
    pub warnings: Vec<String>,
    pub total_estimated_cost: Option<f64>,
}

=== Contract Rules

1. All protocols expose the same operator IDs and dependency graph
2. Explain must state execution mode (Exact/Approximate/Degraded/Unsupported) per operator
3. If execution would fail due to capability validation, explain returns `valid=false` with structurally valid plan
4. Filter diagnostics show pushed vs residual predicates for every filter-capable operator
5. Explain follows the same lowering and validation path as execution (same code, different output format)

== Consequences

* One explain format, mechanically derived, consistent across all protocols
* Users see capability status, not just cost estimates
* Filter pushdown decisions are visible in explain output
* Invalid plans still produce useful explain output (for debugging)
* Existing VectorHints/GraphHints content is preserved in operator.hints map

== 2026-05 Route And Write-Plan Extension

The unified explain contract also governs workload route selection and table-write planning. The
active implementation blueprint is
link:../RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20.adoc[RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20].

For `INSERT ... SELECT`, `INSERT OVERWRITE`, CTAS, MERGE, large scans, delegated compute, and
open-format routes, explain output must include a route section derived from the validated
`RoutedExecutionPlan`, not from protocol-specific formatting.

Required route diagnostics:

* selected compute route and access method;
* authority mode and commit owner;
* write lane, durability, isolation, and projection freshness requirement;
* policy boundary and tenant/RLS pushdown status;
* source snapshot, target write mode, and idempotency requirement;
* estimated rows/bytes and data movement;
* considered candidate paths;
* rejected candidate paths and rejected write lanes with concrete reasons;
* source-reader and projection freshness warnings when relevant.

Mapping to `UnifiedExplainPlan`:

[cols="1,3"]
|===
| Unified field | Route/write-plan mapping

| `operators`
| Logical scan, source read, write transform, commit, projection update, and external commit nodes.

| `required_capabilities`
| Write mode support, source snapshot pinning, target write capability, RLS enforcement,
idempotency, external atomic commit, projection freshness.

| `missing_capabilities`
| Unsupported merge predicate, unsupported overwrite lane, missing RLS boundary, missing
snapshot/manifest support, stale projection, unsupported type conversion.

| `bindings`
| Native runtime, DataFusion, Arrow Flight, external compute adapter, open-format commit protocol,
`TableRecordStore`, and projection scheduler availability.

| `fallbacks`
| Rejected or degraded routes. Fallbacks must include why a route was rejected and whether the
selected route is exact, planned-only, degraded, or unsupported.

| `diagnostics`
| Planning time, stats freshness, data-movement estimate, policy warnings, maturity/support status,
and benchmark gate warnings.
|===

Routes that are planned-only must still produce `valid=true` only for planning/explain mode. For
execution mode, a planned-only route must either return an explicit unsupported error or select a
fully executable route with guards satisfied.
