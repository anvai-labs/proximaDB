= ADR-020: Canonical WAL Authority Model
:toc: left
:toclevels: 3
:icons: font
:last-updated: 2026-05-26

== Status

Accepted

== Context

`RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc` (the stacked-durability mandate) and `MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc` both establish that durable authority for records lives in **xCatalog + canonical WAL + `ProximaRecord` + policy/RLS + version/time/provenance**. Modality-specific engines (PAX layouts, LSM, columnar, ANN, JSON, graph topology, observability, Arrow/Parquet/Iceberg/Delta/Hudi) are projections, layouts, adapters, or explicit external-authority modes.

The 2026-05-26 design-doc audit (a snapshot since superseded by `docs/12-design/WORK_LEDGER_2026_10_15.adoc`) confirmed that this mandate is mostly wired but four implementation gaps remain, all currently OPEN in `docs/10-quality/TECHNICAL_DEBT.adoc`:

* **TD-065** — `DocumentService.documents` (`RwLock<HashMap>`) is the primary durable source. The canonical `UpsertCanonicalDocumentRecord` WAL variant exists but is opt-in behind the `canonical-document-store` feature flag.
* **TD-066** — `OrionGraphEngine::flush_wal()` and `OrionPersistence::save_snapshot()` write to an engine-local WAL that runs in parallel with the canonical `RecordUpsert` WAL. Recovery from the engine WAL alone misses tenant/RLS/versioning/provenance semantics.
* **TD-067** — Projection keys (JSON path index, full-text index, columnar variation) use the facade `document_id` string instead of the canonical `ProximaRecord::oid`, forcing a join through the facade-id → OID map on every projection lookup.
* **TD-068** — QUASAR's cold-tier path writes to a separate JSON/SST file format and bypasses the canonical WAL entirely.

Each of these has its own remediation in the TD register, but addressing them piecemeal would produce four inconsistent recovery models. The recovery semantics need a single contract that all engines and projections follow.

This ADR is that contract.

== Decision

=== 1. Authority model

The canonical WAL is the **single durable authority** for record state. All other persistent state (in-memory maps, engine-local WALs, snapshot files, projection indexes, cold-tier blobs) is either:

* a **projection cache** of canonical state (rebuildable from canonical WAL replay),
* a **performance buffer** in front of the canonical WAL (must be flushed-through before commit acknowledgement), or
* an **explicit external authority** mode (governed by xCatalog with `authority_mode = external`).

Recovery on restart MUST read from the canonical WAL first. Engine-local WALs are best-effort fast-path replay validated against canonical records; if the two disagree, canonical wins.

=== 2. Per-TD remediation

==== TD-065 — Document store

**Decision**: The `canonical-document-store` feature becomes default-enabled in v0.2 (the next release). The existing opt-out flag is preserved during one minor-release migration window so operators with the legacy in-memory-map durability assumption have an explicit downgrade path. Flag removal is targeted for v0.3 (the release after v0.2).

* In the default (canonical) mode: every `self.documents.write()` call site in `src/storage/document/service.rs` becomes a *cache write*, performed after the canonical WAL append. The map's purpose is read-hit acceleration, not durability.
* Crash recovery: rebuild the in-memory map from canonical WAL replay. The map is empty at process start and warmed by replay; the legacy "WAL-replays-into-map" path is removed.
* Race-condition window between map write and WAL write is closed because WAL append is the authoritative commit and the map write is downstream of (and gated by) WAL success.

The Tier-2 implementation step (T2.2) flips the feature default; the per-call-site cleanup (turning the map into a pure cache) is a follow-up because each call site needs individual audit. Default-enabling the feature is the safety win; the cleanup is hygiene.

**Resolves**: TD-065.

==== TD-066 — ORION graph engine WAL

**Decision**: ORION's engine WAL is demoted to a performance buffer. `GraphOperationsService::flush_wal()` and `OrionGraphEngine::flush_wal()` MUST append a `CanonicalOperation::Checkpoint` entry to the canonical WAL before any ORION engine WAL flush is considered durable.

* Canonical WAL ordering: `RecordUpsert` (graph fact) → `CanonicalOperation::Checkpoint` (after engine ack).
* Recovery: canonical WAL replay produces the authoritative graph state. ORION engine WAL replay runs second as a fast-path performance optimization and is validated against canonical replay; if they diverge, canonical wins and ORION WAL state is discarded.
* This preserves the existing ORION engine WAL as a recovery accelerator without making it a parallel durable truth.

PULSAR and QUASAR no longer add graph-engine WAL paths; their useful concerns are handled by the relational/storage substrate below ORION.

**Resolves**: TD-066. Implementation is deferred from this ADR's writing session — Tier 5 of the pre-release plan.

==== TD-067 — Projection key contract

**Decision**: All projection layers (`IndexManager` for JSON path, full-text, columnar variation, and future projections) MUST key by canonical `ProximaRecord::oid`, NOT by facade `document_id`.

* The facade `document_id` remains in `ProximaRecord` as a user-facing identifier; the canonical OID is the engine-facing key.
* Migration: existing projection indexes are re-keyed via a one-time migration that walks the facade-id → OID map. The migration is idempotent and resumable.
* Query executor support: `plan_executor.rs` MUST produce OID-addressed candidate sets from `VectorTopK` / `Filter` / `Scan` operators before the projection-key switch lands.

**Resolves**: TD-067. Sequencing: depends on query-executor OID candidate-set support (separately tracked); ADR-020 records the eventual contract.

==== TD-068 — QUASAR cold-tier

**Decision**: QUASAR cold-tier path is retired in favor of canonical-record-backed tiering. The replacement is a tiering policy in xCatalog (`freshness_sla` + `retention_tier`) that the query/storage runtime honors automatically. Cold tier becomes a placement decision on canonical records, not a separate engine path.

Rejected alternative (Option A from TD-068): rewrite QUASAR cold tier to write through the canonical WAL + projection directives. Rejected because (a) the canonical-record-backed tiering subsumes QUASAR's value proposition with less surface area, and (b) QUASAR cold-tier has no production users to justify maintaining a parallel format.

* Migration path: existing QUASAR cold-tier data is exported to canonical records via a one-time tool; the cold-tier format itself is removed.
* `SUPPORTED_SURFACES.adoc` lists QUASAR as retired; this ADR closes the authority-model decision.

**Resolves**: TD-068 (by retirement, not by rewrite).

=== 3. Boundary contract for new engines and projections

Every new engine, projection layer, or external-format adapter MUST declare, in the doc/PR that introduces it:

* **Authority mode**: canonical / external / projection-cache / performance-buffer.
* **Recovery source**: canonical WAL / external authority / rebuildable from canonical.
* **Commit ordering**: when does this layer acknowledge a write relative to canonical WAL append?
* **Tenant / RLS / version / provenance preservation**: how does this layer maintain canonical semantics?

A new engine that violates this contract (e.g. "this engine has its own durable WAL parallel to canonical") requires an explicit ADR amending this one.

== Consequences

* TD-065 + TD-068 are resolved in this ADR window (default-enable + retire). TD-066 is resolved-by-decision; implementation deferred. TD-067 is resolved-by-decision; depends on query-executor OID candidate-set support.
* The convergence mandate (`RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc`) gets a concrete authority-model boundary that future engines can be validated against.
* QUASAR is retired as a graph engine variant; SUPPORTED_SURFACES.adoc downgrade is finalized.
* PULSAR is retired as a graph engine variant; distributed graph behavior is a relational substrate requirement.
* Operators on the legacy non-canonical-document-store path get one minor-release migration window before the feature flag is removed entirely (target: v0.4).
* Recovery semantics become uniform across modalities — single recovery contract instead of four engine-specific replays.

== Rejected alternatives

=== Option: keep all four current paths

Treat each engine WAL / in-memory durability path as legitimate parallel authority. Rejected because the convergence mandate explicitly forbids hidden durable authority outside canonical WAL + xCatalog (`docs/12-design/RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc` "Decision" section). Recovery correctness demands a single source.

=== Option: rewrite QUASAR cold tier through canonical WAL

Build canonical-WAL writes into QUASAR's cold-tier path; preserve QUASAR as a graph engine variant. Rejected because (a) no production users, (b) canonical-record-backed tiering achieves the same goal with less surface area, and (c) maintaining a parallel cold-tier format costs more than it pays.

=== Option: defer the entire ADR until all four TDs have impl PRs

Wait for each TD to land before formalizing the contract. Rejected because the four TDs are coupled — they share the recovery-semantics design boundary. Implementing them piecemeal without an authority-model contract produces four inconsistent recovery models. The ADR has to land first.

== Reconciliation (2026-06-30 — where the WAL physically lives)

A prior external comparison (Lakebase/LTAP; deep-research workflow `wf_93aa09c8-12b`) initially
mistook the canonical WAL for local-disk-only. It is not. In cloud deployments the canonical WAL
writes through `FilesystemFactory` → `object_store`
(`src/storage/persistence/filesystem/aws_s3.rs:179` — `store.put(...).await` blocks until the object
store acknowledges before the commit ack returns; `sync_file` is a no-op for cloud backends because
the PUT is already durable). On restart the pod replays the WAL into the memtable
(`RecoveryMode::ViaMemtable`).

Consequences for this ADR's authority model:

* Pods are **stateless** and restart is **non-lossy** — the same properties Lakebase/Neon's
  SafeKeeper provides, achieved via object-storage durability (S3 Standard = 11 nines) **without a
  separate quorum service**. This ADR's "performance buffer... must be flushed-through before commit
  acknowledgement" still holds: the object-store PUT *is* that flush.
* A SafeKeeper-style quorum WAL is **not needed for durability** — it would buy only per-tx commit
  latency (quorum-local-SSD fsync ≈ single-digit ms vs object-store PUT ≈ tens-to-hundreds of ms),
  which is moot for ProximaDB's batch-ingestion profile. Recorded as
  link:../../10-quality/td/TD-LTAP-3-quorum-wal-latency-only-wontdo.adoc[TD-LTAP-3] (Won't Do).
  Open caveat: multi-AZ durability *at commit* would require cross-region S3 replication or a
  lightweight quorum on the object-store seam — tracked as an open question there, not work now.

Sources: https://neon.com/docs/introduction/architecture-overview[Neon architecture — object
storage deliberately off the commit path],
https://github.com/neondatabase/neon/blob/main/docs/safekeeper-protocol.md[Neon SafeKeeper protocol],
https://arxiv.org/html/2603.02108v1[Milliscale — object-store commit latency is not automatically
competitive for per-tx].
