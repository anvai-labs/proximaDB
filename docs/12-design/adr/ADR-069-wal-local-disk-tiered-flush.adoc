== 1. Context — first principles

A WAL is, from first principles, **the per-write durability record**: every insert appends to it before
the write is acknowledged, so its I/O volume is `O(writes)` — it is the single most frequent writer in the
engine. Where that log physically lives therefore sets the cost and latency floor of the entire write path.

Object storage and local disk have *categorically different* cost curves:

[cols="1,2,2",options="header"]
|===
| Substrate | Charging model | Consequence for a per-write log
| Object store (flat Blob Hot LRS) | **per operation** (~$0.065 / 10K writes) + per-GB-month at-rest | WAL cost = `O(write ops)` — **unbounded**, and it is the dominant op source
| Object store (ADLS Gen2 / HNS) | **per *iterative* operation** (~$0.05 / 100 — ~100× flat) | catastrophic for a per-write log (ADR-036 already routes us off HNS)
| Local managed disk (StandardSSD) | **flat $/GB-month, $0 per operation** | WAL cost = flat, independent of write rate; ~10–50× lower write latency
|===

Two measured facts anchor this:

* A Spot testbed with the WAL pointed at object storage produced **~9,000,000 flat-Blob write operations in
  one day** (~$58 that day) while storing almost no bytes — the cost was pure *operation count* (write
  amplification), and it scales linearly and unbounded with write volume.
* The same workload on a **local StandardSSD costs a flat ~$2.40/month** with **zero per-op charge** and
  sub-millisecond fsync latency.

The historical reason the WAL sat on object storage is a good one: **durability across node loss**. On a
Spot/ephemeral node, a local WAL is worthless *if the disk dies with the node*. But that premise is false for
a **persistent, reattachable volume**: a Kubernetes `PersistentVolumeClaim` backed by a managed disk (or any
detach/reattach block device) **survives node reaping** — it force-detaches from the dead node and reattaches
to the rescheduled pod, data intact. So the real choice is not "durable object store vs. ephemeral local
disk"; it is **"per-op-billed network log vs. flat-cost reattachable local log, both durable."** Framed that
way, the local disk wins the hot path decisively; the object store's advantage (instant cross-node/cross-AZ
read, no reattach wait) matters only for the *bulk-at-rest* data and for RTO — exactly the tiers that are
*not* per-write.

**Filing-time engine reality (2026-07-20).** This evidence motivated the decision; it is not a
current implementation inventory. The reconciled shipped/residual inventory is in §7 and TD-WAL-1.

* **Per-tier backend selection already works.** Every tier resolves its root through one
  `FilesystemFactory` keyed by URL scheme (`file://`/`s3://`/`gs://`/`adls://`/`az://`/`abfs://`/`hdfs://`;
  `filesystem/mod.rs:538`, `scheme_validation.rs:11`). The WAL root (`write_buffer_directory`) and the SST
  root (`storage.storage_locations[].url`) are looked up **independently**, so running **WAL `file://` +
  SST `adls://` in the same process is supported today** — no engine change needed to *place* the WAL
  locally. The WAL is **per-collection** (`{write_buffer_directory}/{collection_id}/wal/`,
  `disk_manager.rs:170`), and the queue already runs on a local root (`file:///var/lib/proximadb/queue`).
* **Flush is size-only + manual.** A memtable→SST flush fires when a collection's unflushed bytes exceed
  `memory_flush_size_bytes` (`bincode_serialization_strategy.rs:279`, `memtable_manager.rs:177`) or via
  `Database::force_flush_collection()`. `WalPerformanceConfig` (`write_ahead_log/config.rs:78`) carries a
  `global_flush_threshold` (enforcement unclear) and — importantly — **no time-based and no
  disk-capacity/watermark trigger exists**. (`vector_count_threshold` was parsed but *never* wired as a
  flush trigger — **retired 2026-08 (#1526)**: the field and its dead `batch_threshold` copy were removed
  rather than wired, since a record-count trigger would fight the TD-FLUSH-3 predicted-byte segment floor,
  and this ADR's size/time/capacity envelope covers the intent; old TOMLs carrying the key still parse
  (unknown keys are ignored). `sync_interval_seconds` controls fsync cadence, **not** memtable flush.)
* **Truncation exists but is marker-gated.** `UnifiedWALWriter::truncate_through_canonical_marker(lsn)`
  (`wal_operations.rs:692`) deletes WAL segments below a `CanonicalEmission` marker — but the marker is
  emitted after downstream durability confirmation, so **under sustained flush lag without marker emission
  the WAL can grow unbounded**. So truncation is present, not *guaranteed to keep pace*.
* **fsync is real per `sync_mode`.** `SyncMode ∈ {Never, Always, Periodic, PerBatch, MemoryOnly}`
  (`config.rs:151`); `PerBatch` (default) fsyncs per batch via the batch-sync coordinator
  (`batch_sync_coordinator.rs:272`, `DurabilityLevel::SyncData`=fdatasync / `SyncFull`=fsync). So the RPO-0
  primitive exists; it needs an explicit, tested contract.
* **No backpressure / ENOSPC handling** on the write path — a full WAL disk surfaces as a raw OS error and
  crashes the write, rather than shedding load. `wal_size_bytes` + `last_flush_duration_ms` metrics exist;
  trigger-attribution, disk-util, and truncation counters do not.

So the engine can *place* the WAL locally today and already has the truncation + fsync primitives — but it
lacks the **adaptive flush control (time + capacity), the backpressure safety, and the guaranteed truncation
cadence** that make a bounded local WAL + coalesced object-store durability actually safe. That machinery is
the work of this ADR.

== 2. Decision

=== D1 — Tier by write-frequency: local WAL, object-store bulk

The WAL lives on a **local, reattachable filesystem** (`file://` root, e.g. `file:///var/lib/proximadb/wal`),
**never** on object storage. The object store remains the **durable tier for the coalesced, infrequent
writers** — SST, VIPER, metadata, and periodic checkpoints — which are large, batched, and cheap per-GB.
This *refines* ADR-036: ADR-036 says "when you use the object store, use the flat Blob endpoint, HNS-off,
access-tier as the lever"; D1 says "the per-write log does not use the object store at all."

=== D2 — Three flush triggers; the memtable flushes on `min(size, time, capacity-budget)`

A memtable→SST flush (which is also what advances durability into the object store and lets the WAL truncate)
is triggered by **whichever fires first** of:

* **Size** — the existing `memory_flush_size_bytes` (the throughput optimizer: bigger ⇒ fewer, larger SST
  objects).
* **Time — NEW: `flush_interval_secs`** — the **RPO floor**. Without it, a *low-write* workload never hits a
  size or capacity threshold, so the object store's durable copy can lag arbitrarily; if the local volume is
  then lost (reattach failure / AZ loss), everything since the last flush is gone. A periodic flush caps
  worst-case loss-on-volume-loss to the interval. **This is the non-negotiable durability addition** — a
  capacity-only design has unbounded RPO.
* **Capacity — NEW: high-watermark of a WAL *budget*** (see D6) — the **ceiling** that forces a flush +
  truncation when the WAL backs up (SST flushing has fallen behind), reclaiming local space.

=== D3 — Two watermarks + write backpressure; never ENOSPC-crash

Local capacity is finite, so the WAL disk must degrade gracefully, not fatally:

* **High watermark** (e.g. 80% of the WAL budget) → start/accelerate the flush + truncation.
* **Critical watermark** (e.g. 95%) → apply **write backpressure** (slow / reject with a retryable
  `ResourceExhausted`/503), so the engine sheds load rather than hitting `ENOSPC` and crashing.

The flush runs **asynchronously and concurrently** with the write path — flushing never blocks or stalls
writes below the critical watermark.

=== D4 — Truncation must keep pace, not merely exist

The scheme depends on the WAL **shrinking** after its records are durable. The mechanism already exists —
`truncate_through_canonical_marker(lsn)` deletes segments below a `CanonicalEmission` marker — but it is
**gated on marker emission**, so under sustained flush lag it can grow unbounded (the real risk). The work is
therefore to **guarantee truncation keeps pace**: every memtable→SST flush that lands durably in the object
store advances the canonical marker and drives truncation, so per-collection WAL bytes stay bounded by the
flush cadence + budget (D2/D6). An unbounded-growth WAL under sustained writes is a **correctness bug**, not a
tuning issue, and is gated by a soak test (§6).

=== D5 — Explicit fsync durability contract per `sync_mode`

The existing `SyncMode` values (`config.rs:151`; via `DurabilityLevel::SyncData`=fdatasync /
`SyncFull`=fsync in `batch_sync_coordinator.rs`) must carry a **documented, tested** durability meaning:

* `PerBatch` (the deployed default) — **fsync/fdatasync to the local disk per batch** ⇒ RPO 0 for any
  acknowledged, fsync'd batch even on a hard node kill (the reattached volume replays it). A crash-consistency
  test asserts this (write N batches, `SIGKILL`, remount the volume, assert all N replay).
* `Never` / `MemoryOnly` — page-cache-only / no-disk-WAL; faster, but acknowledged writes can be lost on
  crash. Must be *opt-in* and labelled non-durable.

The RPO-0 claim of D2's time trigger rests entirely on D5 being true — the primitive exists; this ADR makes
it a *contract with a test*.

=== D6 — Trigger on a WAL *size budget*, not raw disk percentage

The capacity trigger is expressed as a percentage of a configured **`wal_max_bytes` budget**, not of the raw
filesystem free space. Rationale: the WAL may share a volume with the data_dir / queue, so raw disk % is
polluted by data growth (a data-heavy day would spuriously trip the WAL flush, and vice versa). A budget
decouples the trigger from disk sizing and makes the behavior deterministic. **Recommendation (not mandate):
a dedicated WAL volume in production**, so WAL capacity accounting is fully isolated and can be tiered
independently (e.g. Premium SSD for WAL IOPS, Standard for bulk).

=== D7 — Observability + a stated durability contract

Emit (and alert on): **WAL-disk / budget utilisation %**, **flush count + duration**, **WAL replay time on
boot**, and — the regression canary — the **object-store write-operation rate** (if this climbs, the WAL has
silently drifted back onto object storage). Publish the contract explicitly:

* **RPO** — volume reattaches ⇒ **0** (fsync'd WAL replayed, D5). Volume permanently lost ⇒ **≤
  `flush_interval_secs`** (D2 time trigger).
* **RTO** — node/Spot eviction ⇒ **volume force-detach + reattach (~minutes) + WAL replay** (bounded by the
  checkpoint cadence).
* **Cost** — WAL writes: **$0/op** (flat local disk). Object store sees only coalesced SST + periodic
  checkpoints (few, large ops).

=== D8 — Config-as-code (TOML-first, env-override), safe defaults

New `[storage.wal_config]` keys: `flush_interval_secs`, `wal_max_bytes`, `high_watermark_pct`,
`critical_watermark_pct`. Defaults are chosen so an operator who sets none still gets bounded, durable
behavior (a sane time interval + a budget derived from the volume). No runtime mutation — the config is the
version-controlled source of truth (repo convention).

== 3. Co-design dimensional analysis (ADR-052 spine)

Per ADR-052, design against the **dominant cost term** and *measure* every dimension:

* **Cost (the dominant term here).** Object-store *operations* on the write path were the runaway cost
  (measured ~9M ops/day). D1 removes them entirely from the hot path; the object store now sees only
  coalesced SST + checkpoint writes. Hot-path cost goes from `O(write ops) × $/op` (unbounded) to a **flat
  $/GB-month** disk already provisioned.
* **Latency.** Local fsync (~0.1–1 ms) replaces a network PUT (~10–50 ms) per durable batch → 10–50× lower
  write-commit latency, higher sustained write throughput.
* **Durability (RPO).** Preserved and made *explicit* (D7). The time trigger (D2) bounds the only new failure
  mode (volume-loss between flushes); D5's fsync bounds the crash case to 0.
* **Availability (RTO).** The one regression: a fresh node waits for volume reattach (~minutes) instead of
  reading state from object storage instantly. Acceptable for cost-sensitive / RTO-tolerant tiers; for
  low-RTO tiers, keep the WAL on object storage or run on non-evictable (on-demand) nodes — a **per-tier
  deployment choice**, not an engine constraint.
* **Capacity / operability.** Bounded WAL (D4 truncation) + backpressure (D3) turn "disk fills → crash" into
  "disk pressure → shed load + flush." Observability (D7) makes the whole loop visible.

== 4. Alternatives considered — and rejected

* **Keep the WAL on object storage (status quo).** Rejected: `O(write ops)` cost, unbounded and
  workload-driven (the measured $58/day spike), plus 10–50× worse write latency.
* **Capacity-only trigger (the naive "flush at 80%").** Rejected as *sufficient*: a low-write workload never
  reaches 80%, so the durable copy lags without bound and RPO-on-volume-loss is unbounded. Capacity is the
  ceiling; it needs the time floor (D2).
* **All tiers local (WAL + SST + VIPER on the PVC).** Rejected as the *default*: loses the object store's
  cheap per-GB bulk storage, cross-node durability, and instant fresh-node start; caps the dataset at the
  disk size. (Viable as an option for fully-local small deployments.)
* **`emptyDir` / tmpfs WAL.** Rejected: not reattachable — lost on eviction, defeating the durability premise.
* **`sync_mode` = per-write fsync.** Rejected as default: correct but throughput-limited; `PerBatch` fsync
  (D5) is the durability/throughput sweet spot.
* **HNS/ADLS-Gen2 for the WAL.** Rejected by ADR-036 already (~100× iterative-op billing); this ADR removes
  the WAL from object storage entirely, mooting it.

== 5. Consequences & migration

* **Positive.** Hot-path write-op cost → ~0; write latency down 10–50×; durability preserved + explicit;
  disk-full becomes graceful backpressure; a cost-regression canary is wired in.
* **Cost of the change.** New engine work (D2 time + capacity triggers, D3 backpressure, D4 truncation
  guarantee + soak test, D5 fsync contract + crash test, D7 metrics). One RTO tradeoff (reattach wait on
  eviction), stated and bounded.
* **Deployment migration.** Consumers point `write_buffer_directory` at a `file://` root on a persistent
  reattachable volume (the AnvaiOps AKS profile already provisions the PVC at `/var/lib/proximadb`; the
  config flip is a few lines) and set the new thresholds. A downstream **ratchet** should assert the WAL root
  is `file://`, not an object-store scheme, so it can't regress.

== 6. Acceptance conditions (first-principles pressure test)

. **RPO floor holds** — with `flush_interval_secs = T`, kill the node between writes and lose the volume;
  data loss ≤ T of writes (never unbounded).
. **Truncation reclaims space** — a multi-hour sustained-write soak keeps WAL utilisation bounded (no
  monotonic growth); truncation demonstrably runs after each flush.
. **Backpressure, not crash** — drive writes past the critical watermark with flush stalled; the engine
  returns retryable pressure errors and never hits `ENOSPC`/panic.
. **fsync is real** — `PerBatch`: write N batches, `SIGKILL`, remount the volume, assert all N replay (RPO 0).
. **Cost canary flat** — under sustained high write volume, the object-store **write-operation rate stays
  flat** (only coalesced SST/checkpoint ops), verified via the D7 metric — the regression that started this
  ADR cannot recur silently.
. **Tier split verified** — the engine runs with WAL `file://` and SST/VIPER/metadata `adls://` in the same
  process (mixed-scheme config), confirming per-tier backend selection.

== 7. Status of related work (reconciled 2026-07-21)

* **Exists today** (grounds this ADR; TD-WAL-1 §Evidence pins file:line): per-tier backend selection via
  `FilesystemFactory` (WAL `file://` + SST `adls://` in one process — *already works*); per-collection WAL
  layout; size-based + manual (`force_flush_collection`) flush; **truncation** via
  `truncate_through_canonical_marker` (marker-gated); `PerBatch` **fsync** via the batch-sync coordinator;
  `wal_size_bytes` + `last_flush_duration_ms` metrics.
* **Shipped core (#1117/#1118):** **time-based flush** (D2) and **capacity-budget watermark flush** (D2/D6) —
  implemented by the live auto-flush driver; durable flush retirement reclaims the WAL by construction.
  Trigger attribution, WAL budget/watermark gauges, backpressure observation, and the existing
  object-store flush-write meter are live. Verification also fixed zero live batch-size accounting and
  an infinite periodic re-flush caused by stale coordinator batches.
* **S4 core (#1132):** critical-watermark admission control rejects the client WAL-append path with
  retryable `WalBackpressure`, default-OFF when no WAL byte budget is configured; recovery replay is
  excluded. gRPC, Flight, bulk, and propagating-error paths map it to resource exhaustion/HTTP 429.
* **Residual acceptance work:** thread the S4 discriminant through the primary REST batch result path,
  provide the explicit fsync + SIGKILL/remount proof (D5), add reclaimed-segment and boot-replay metrics
  (D7), ship the `file://` startup guardrail, and run the sustained bounded-util/flat-object-op soak.
  TD-WAL-1 is the detailed status authority.
* **Downstream (consumer) work**: point `write_buffer_directory` at a `file://` PVC root + set thresholds;
  add the "WAL root must be `file://`" cost ratchet. (AnvaiOps: the `/var/lib/proximadb` persistent tree +
  object-store-shape ratchets already landed; the WAL flip is the remaining few lines once these engine
  knobs exist.)
