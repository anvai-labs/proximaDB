== The Industry Signal

=== One-line thesis

Vector retrieval solved the *first* problem of the AI-data era, not the final one. As AI moves from
static assistants to continuously running agents, teams no longer just want to *retrieve* their
unstructured data -- they want to *improve* it (deduplicate, recluster, re-embed, evaluate, detect
drift/bias, analyze agent trajectories) and feed those improvements back into production. That
demands a new architecture shape, not just a faster index.

=== The historical analogy the article draws

[cols="1,2,2"]
|===
| Era | Pressure | Architectural answer

| Mobile internet (~2010)
| Semi-structured event/telemetry data outgrew rigid relational schemas
| MongoDB: "ingest first, structure later"

| BI / warehouse era (~2015)
| "Now that the data exists, how do we use it?"
| Snowflake / Redshift: operational store -> analytical asset

| Lakehouse era (~2020)
| Fragile, expensive OLTP<->OLAP pipelines copying the same data repeatedly
| Databricks / Iceberg / Hudi: one logical copy, many compute models

| AI-data era (2023+)
| RAG needs embeddings + ANN; vector DBs become foundational infra
| Vector databases (Milvus, ProximaDB, ...): semantic representation as a first-class abstraction

| Continuous-AI era (2026+)
| Serving alone cannot close the loop; iteration speed -- not model capability -- is the bottleneck
| *Vector Lakebase*: serving + discovery + elastic compute over one logical unstructured-data store
|===

The article's central claim is that vector DBs are now at the same inflection OLTP databases hit
when the Lakehouse arrived: they do not disappear, they become *one layer* (the serving engine)
inside a larger continuous system.

=== CS/CD -- Continuous Serving + Continuous Discovery

The architectural core is a flywheel:

* *Serving layer* -- high-throughput ingestion, low-latency retrieval for online RAG,
  recommendation, personalization, AI memory, real-time agents.
* *Discovery layer* -- clustering, deduplication, re-embedding, offline evaluation, quality/drift
  analysis, fine-tuning-data preparation, agent-trajectory analysis.

These are not independent. Serving generates feedback and new data; discovery analyzes and improves
it; improvements (better embeddings, cleaner datasets, refined indexes, richer metadata) flow back
into serving. Every turn should make the next turn better.

The article's key observation: most organizations *cannot run this loop today* because the
infrastructure is fragmented. Moving a billion vectors out of a serving system into a batch
environment, reprocessing, and re-importing "could take days. Not hours. Days." Because the loop is
so expensive, teams simply skip continuous discovery -- the data sits retrievable but unexplored.

=== Why both incumbent shapes hit limits

* *Vector databases* are optimized for online retrieval. Cold-data processing is expensive,
  billion-scale clustering is awkward through online search APIs, and many systems assume data must
  stay resident to remain queryable -- which forces migration and governance fragmentation for data
  already in a lake.
* *Lakehouses* are optimized for structured data and batch. Vectors are treated as float arrays,
  not first-class semantic objects; Parquet was not designed for ANN/inverted indexes; a brute-force
  Spark scan was measured ~1000x slower than IVF-indexed retrieval; and object storage causes severe
  *I/O amplification* on the small point reads that serving needs.

== Engineering Pillars in the Article (and the numbers)

[cols="1,3"]
|===
| Pillar | What the article reports

| *Cold-start under scale-to-zero*
| A 1B x 768-dim HNSW index ~= 340 GB; pulling it from S3 can take >4 minutes. Their answer:
RaBitQ-style 1+3-bit quantization compresses it to ~13 GB; two-stage search (1-bit coarse filter
~85-90% recall -> 1+3-bit rerank ~95% recall); IVF clustering touches ~3% of data per query. Net:
340 GB index -> 13 GB cold path -> ~400 MB touched per query; cold start minutes -> ~5-10 s.

| *I/O amplification on point reads*
| Vector search returns IDs; apps need full records (text, metadata, permissions, timestamps).
A small Parquet point read can drag a whole row group. They built a storage engine ("Loon": mixed
file formats, row alignment, manifest-based versioning) over the open *Vortex* format (Linux
Foundation). Measured: Parquet ~9.4 MB downloaded per point read vs Vortex ~0.07 MB -- a 135x
reduction -- without sacrificing scan throughput.

| *Three compute modes over one logical store*
| (1) *Long-running* -- resident production serving, hot indexes preloaded, ms latency. (2)
*On-demand* -- starts in seconds, minute-level billing, for interactive exploration / cold-data
retrieval. (3) *Offline batch* -- clustering, dedup, re-embed, index rebuild; resources allocated to
the job then released. Handoff back to serving is a *new Catalog snapshot*: serving reads the old
snapshot until the new data+indexes are ready, then the switch is atomic.

| *Elastic resource scheduling*
| Schedule data *and* compute together: a Warm Pool of prepared nodes, attach data quickly when work
arrives, keep warm briefly, release when idle. The economic unit is minute-level usage, not
per-request serverless or fixed monthly capacity. The control plane shifts from "manage a static
kernel" to "a kernel that understands resources, cache state, snapshots, and cost."

| *External Collection -- meet data where it lives*
| Not merely a zero-copy mapping: build an *independent indexing layer* (vector, inverted, JSON
indexes) over external Lance/Iceberg/Parquet/object-store data, while the original data stays
governed by the customer's platform. Principle: "One Data. One Index. No duplicated storage. No
dual-write pipelines. No fragmented discovery paths."
|===

=== The six things a first-gen Vector Lakebase must get right

1. Storage/compute separation *with multi-layer caching* (scale to zero, but cache-aware so hot
   queries stay ms-level).
2. *Unified management for multimodal unstructured data* -- vectors plus source documents, images,
   audio, video, embeddings, scalar metadata, permissions, and indexes. "A system that only stores
   vectors is an index service, not a data foundation."
3. *Native vector-database capabilities* built in -- ms ANN, index lifecycle, hybrid search, scalar
   filtering, full-text, JSON filtering, multiple similarity metrics. Bolting a lakehouse onto an
   external vector DB just creates another pipeline.
4. *Multiple compute modes* over the same logical data; on-demand is the bridge between serving and
   offline processing.
5. *Open formats, no forced migration* -- storage readable by Spark/Ray/Daft; existing
   Iceberg/Lance/Parquet join without copying. "Data belongs to the user, not the engine."
6. *Resources follow the data* -- compute disappears when idle while metadata stays queryable; a
   request brings compute back in seconds. Resource decisions are made *together with* data
   decisions, not as generic autoscaling.

=== Summary read

ProximaDB is *structurally well-positioned* for the Vector Lakebase thesis -- arguably better
positioned than a pure vector DB, because the multimodal "one data foundation" pillar (#2) and the
open-format / route-once pillars (#5, plus workload routing) are already core, not retrofits. The
"Context Database" framing is a superset of "Vector Lakebase."

The gaps are concentrated on the *continuous / elastic* half of the thesis -- the parts that make
the CS/CD flywheel economically viable at scale:

1. *No discovery loop.* We can serve; we cannot yet systematically improve data and republish it.
2. *No scale-to-zero economics.* Cold-start cost and point-read amplification from object storage are
   not engineered down, so "compute that disappears when idle" is not yet practical for large vector
   workloads.
3. *No elastic compute-mode product.* The three-mode model and resources-follow-data scheduler do
   not exist.

These are precisely the things the article argues separate "elastic vector search as an idea" from
"elastic vector search as a usable system."

== Recommendations

Each recommendation is phrased to (a) reuse existing ProximaDB surfaces per the reuse-first mandate
and (b) declare authority/freshness behavior per the architecture mandates. New TD items are
proposed in `docs/10-quality/TECHNICAL_DEBT.adoc` (TD-086..TD-091) and a new roadmap phase is
proposed in the strategic roadmap.

=== R0 -- Parity Sprint [TD-092, TD-093] — REVISED after live-path audit (2026-05-28)

The original R0 claimed two "finished-but-un-wired primitives." A live-path audit on 2026-05-28
(before writing any code) found the framing was wrong on both — a textbook case of the
`feedback-survey-live-paths` lesson:

* *RankServices startup wiring (TD-093) — ALREADY DONE.* `build_rank_services()` runs at startup
  (`src/network/shared_services.rs:1232`), constructs the production `RankServices` over
  `ProductionHybridBackend`, and wires it into both the SQL federated context and REST. SQL `RERANK`
  dispatches the full pipeline. The "not wired" belief came from a stale memory note; TD-093 is
  marked Resolved, no code needed.
* *BM25↔vector hybrid fusion (TD-092) — RE-SCOPED.* The fusion engine, `RestHybridPortImpl`
  (`/api/v1/hybrid/*`), and `ProductionHybridBackend` *already fuse real Tantivy BM25 + vector*. The
  `bm25_wrapper.rs` "stub" was a dead, never-referenced scaffold (removed 2026-05-28) — it is what
  made the gap look like trivial wiring. The *genuine* residual is write-path, not parity-wiring:
  (1) the hybrid BM25 index is populated only via the explicit `BM25IndexPort::index_documents`
  endpoint, **not on the canonical INSERT path**, so inserted records aren't hybrid-BM25-searchable
  until separately indexed; (2) `request_handlers.rs::execute_hybrid_search` has BM25 hardcoded
  disabled. See TD-092 (re-scoped, ~3-6 weeks, gated by the `enable_fulltext_index` schema flag).

Net: R0 collapsed to one dead-code removal (done) + one already-done item + one re-scoped write-path
task. The "Parity Sprint as cheap pre-Phase-8 wiring" assumption did not survive contact with the
code — verify live caller chains before scheduling.

=== R1 -- Continuous Discovery surface + atomic snapshot republish (CS/CD) [TD-086]

Make discovery a first-class, cataloged workflow rather than an external pipeline:

* Define a `DiscoveryJob` catalog asset (dedup, recluster, re-embed, quality/drift scan,
  agent-trajectory analysis) that reads a *pinned* manifest snapshot of a collection.
* Reuse the existing projection freshness state machine
  (`Fresh/Updating/Stale/RebuildRequired/...`) and manifest/branch versioning so a completed job
  publishes a *new snapshot* (new data + rebuilt indexes/embeddings) that serving switches to
  *atomically*. Serving reads the prior snapshot until the switch -- no half-built indexes exposed.
* Route discovery compute through the existing `compute_route` knob (Native batch /
  DataFusionDistributed / Spark / Ray), declaring `authority_mode` and `freshness_sla` so the
  republish is explainable in unified EXPLAIN.
* This converts `src/automl/` from "tuning" into the offline arm of the flywheel.

*Close the loop -- the trigger arm (do not omit).* The current Phase 8 spec builds the discovery
*execution + atomic republish* but not what makes the loop *continuous* rather than manually invoked.
The flywheel is "serving generates feedback -> discovery refines -> republish": ProximaDB has the
refine and republish halves, but nothing feeds signals back to *trigger* a job. Outbound CDC exists
(`src/cdc/`) but never enqueues a `DiscoveryJob`, and AutoML's `WorkloadAnalyzer` /
`PerformancePredictor` already detect drift and access-pattern shifts but are not wired to discovery.
Wire recall-probe failures + freshness-SLA breaches + AutoML drift signals to auto-enqueue
`DiscoveryJob`s, and *reuse AutoML as the cost-aware scheduler* rather than building a new one. This
is the difference between "batch jobs you invoke" and a genuine CS/CD flywheel.

*First real pass: recluster, not dedup.* The walking skeleton (S0-S2) already lands; the first
*real* refinement pass should be `Recluster` (pure reuse of the existing `UnifiedIvfIndex` k-means ->
a measurable index-quality win, no external model dependency), then `ReEmbed` (highest customer pain
per the article -- "embedding models change", "moving a billion vectors takes days" -- reusing the
`proximadb-embedding` OpenAI/BGE/BYO backends), then `Dedup`. Recluster is the cleanest end-to-end
proof of the loop with maximal reuse.

This is the highest-leverage gap to close: it is what makes ProximaDB a *data foundation* rather
than a serving engine, and it is mostly composition over existing primitives (manifest snapshots,
branches, freshness state machine, route selection).

=== R2 -- Scale-to-zero cold-path: binary-first two-stage retrieval + IVF pruning [TD-087]

Engineer the cold path so compute can scale to zero without a multi-minute first query:

* Add a "cold-path" index profile: persist a compact binary/RaBitQ-style representation alongside
  the full index so the *first* representation pulled from object storage is ~1/30th the size.
* Two-stage search: coarse filter on the 1-bit representation, then rerank on a higher-fidelity
  representation, with the recall envelope disclosed (reuse `RecallProbeGate`, TD-075, and the
  predicate-aware disclosure contract, TD-064).
* IVF cluster pruning to bound bytes-touched-per-query.
* Builds directly on `compute/quantization/unified.rs`; the new work is the *cold-load ordering* and
  the two-stage execution path, not a new quantizer.

=== R3 -- Point-read-optimized lake layout (mitigate I/O amplification) [TD-088]

Address point-read amplification for serving over object storage:

* Extend the PAX block format (ADR-010) with a row-aligned column-group mode so a point lookup
  fetches only the needed fields' bytes instead of a whole row group/stripe.
* Evaluate the open *Vortex* format as an interoperable layout option for point-read-heavy
  collections (it is Linux-Foundation, aligning with the open-format mandate), benchmarked against
  PAX and Parquet for both point reads and scans.
* Keep serving (point read) and discovery (scan) access patterns over *one logical copy* -- do not
  introduce a second physical store users must maintain.

*Scope narrowing (plan refinement).* PAX already has an `BlockMode::Oltp` row-directory mode --
conceptually the same row alignment Loon uses -- so the genuine gap is narrow: *object-storage
range-request granularity* (fetch the byte ranges for N matched IDs without dragging whole row
groups/stripes). Frame R3 as "S3 range-read coalescing over the existing PAX OLTP layout", with
Vortex as a *measured fallback only* if PAX cannot hit the byte-amplification target. Adopting Vortex
wholesale would duplicate the `proximadb-block-format` investment and violate the reuse-first
mandate -- it must be a benchmark-justified decision, not a default.

=== R4 -- Elastic compute modes + resources-follow-data scheduler [TD-089, TD-094]

Introduce the three-mode model behind the existing deployment-neutrality story -- but *split it by
what is actually blocked*, because the plan should not bury the unblocked, high-value half behind
the distributed-transport gap.

*R4a -- single-node scale-to-zero (TD-094, UNBLOCKED).* Evict a collection's compute/index from
memory while keeping its catalog metadata queryable, and lazy-warm on first query. This reuses
already-built surfaces -- `CollectionPinRegistry`, `DirectoryLoadStatus`, route-health diagnostics,
and the tiering engine -- and delivers most of the "idle tenants don't pay" economics for embedded /
single-node deployments *today*, with no dependency on TD-077. It chains directly off R2: scale-to-
zero is only viable if cold-start is fast. Sequence it right after R2, parallel to R1.

*R4b -- multi-node elastic modes (TD-089, BLOCKED on TD-077).* `OnDemand` (seconds to start,
minute-billed) and `OfflineBatch` (job-scoped) pods plus a warm-pool scheduler that attaches a pinned
snapshot to prepared compute on request and releases on idle, cluster-wide. This is the full
realization of the 2028 VISION "serverless deployment mode" milestone and depends on closing the
distributed transport gap (TD-077). Sequence it *after* R1/R2/R3/R4a.

=== R5 -- External Collection: ProximaDB-owned indexes over external-resident data [TD-090]

Extend the open-format story from "read/federate" to "index-in-place":

* Add an authority mode (or a sub-mode of `FederatedRead`) where the external table
  (Iceberg/Lance/Parquet) remains externally governed and *un-copied*, but ProximaDB builds and
  maintains vector/inverted/JSON indexes that route through the same retrieval path as native data.
* Declare freshness behavior explicitly (index staleness vs source commits) and the repair source,
  per the architecture mandates.
* Principle to adopt verbatim: "One Data. One Index. No duplicated storage. No dual-write
  pipelines." This lets the CS/CD loop (R1) cover data the enterprise already has in its lake, not
  just data imported into ProximaDB.

=== R6 -- Lance format interoperability [TD-091]

Add Lance as a read/import/external-index substrate alongside Iceberg/Delta/Hudi/Parquet, since it
is a primary vector-native lake format in this ecosystem. Lowest priority of the six; gates R5 for
Lance-resident corpora.

== Positioning Note (VISION / roadmap)

ProximaDB should *not* rebrand to "Vector Lakebase" -- "The Context Database" is a broader, more
defensible category (multimodal context assembly, not just vector serving + lake). But the VISION
and roadmap should explicitly internalize the *continuous-loop* idea, because it reframes the
product from "a database you query" to "a system that continuously improves your unstructured data."

Recommended framing to fold in (see the VISION and roadmap edits accompanying this doc):

* Add *Continuous Serving + Continuous Discovery (CS/CD)* as a named design principle: serving
  generates feedback, discovery improves data, improvements republish atomically into serving.
* Position the existing open-format + route-once + multimodal pillars as the *serving + lake-native*
  foundation already in place, and the discovery loop + elastic compute modes as the next frontier.
* Keep the explicit non-goal boundary: ProximaDB is not a general-purpose OLAP warehouse; discovery
  here means *unstructured-data refinement for AI*, not BI.

*Wedge to name explicitly: governed continuous discovery.* ProximaDB's discovery loop runs over
governed `ProximaRecord` with RLS + policy + lineage, not raw vectors in a lake. Zilliz's lakebase
has a weaker governance story on the *offline* arm. "Governed continuous discovery" -- dedup /
recluster / re-embed that respects row-level security and tenant isolation and emits lineage to
EXPLAIN -- is a differentiator a pure vector DB structurally cannot match, because it lacks the
relational/policy substrate. This is reinforced by the companion Zilliz piece (vector DB vs
object-relational DB), which argues the vector/relational convergence "is just beginning":
ProximaDB *already* sits at that convergence (`ProximaRecord`/`ProximaType` rich types + pgwire +
RLS + canonical WAL), so the CS/CD story over a governed multi-model record is stronger than the
vectors-plus-lake framing -- and it costs nothing extra, the substrate already exists.
