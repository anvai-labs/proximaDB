== Goals

* Make the public OSS documentation easy to navigate from `README` and `docs/README.md`.
* Keep active architecture in `docs/12-design/` and accepted decisions in `docs/12-design/adr/`.
* Keep implementation reports, session summaries, and superseded plans out of public navigation.
* Preserve obsolete material under `docs/_archive/` instead of deleting it.
* Keep SaaS/control-plane details documented as boundaries around the OSS core, not as hidden
  behavior inside storage/query docs.

== Archive Rules

Archive a document when any of these are true:

* It is a phase/session/progress report rather than a current guide, reference, concept, ADR, or
  active blueprint.
* It duplicates another current doc and is not the selected canonical format.
* It describes a retired API, route, feature flag, engine maturity, or packaging workflow.
* It makes product support claims that conflict with the canonical product
  support contract at `docs/SUPPORTED_SURFACE.adoc` or technical
  API/projection status in `docs/12-design/SUPPORTED_SURFACES.adoc`.
* It is useful historical context but not useful as a current implementation instruction.

Do not delete obsolete docs in this repository cleanup pass. Move them under `docs/_archive/` with
the original filename preserved, and add an archive manifest entry explaining what superseded them.

== Public Navigation Standard

Public docs should follow this shape:

[source,text]
----
README
  -> docs/README.md
      -> Quick Start
      -> Guides
      -> API Reference
      -> Operations
      -> Concepts
      -> Internals
      -> Architecture and ADRs
      -> Supported Surface
----

Any doc linked from the public navigation should have:

* clear audience;
* current status;
* supported/experimental maturity when it describes a feature;
* code/API references that still exist;
* no private SaaS assumptions unless explicitly marked as hosted-control-plane context.

== SaaS/Core Documentation Boundary

SaaS-specific documentation belongs in one of these categories:

* hosted service design: control plane, tenant hierarchy, metering, billing, audit, support;
* operator runbooks: deployment, incident response, SLOs, migrations;
* policy docs: tenant isolation, security, compliance, data retention;
* integration docs: how SaaS invokes the OSS core APIs.

Core database docs should not imply hidden SaaS-only semantics. If a SaaS feature requires a core
hook, document the hook as an explicit policy boundary, catalog field, feature flag, or protocol
extension.

== Maintenance Checklist

Before merging documentation changes:

* Run a link/path scan for moved docs.
* Keep old docs recoverable under `docs/_archive/`.
* Update `docs/README.md`, `docs/INDEX.adoc`, or `docs/12-design/README.adoc` only when navigation
  changes.
* Cite the superseding doc in each archive manifest.
* Avoid embedding volatile benchmark claims unless the benchmark command/date is present.
* Keep OpenAPI/proto/SDK docs aligned when API behavior changes.
