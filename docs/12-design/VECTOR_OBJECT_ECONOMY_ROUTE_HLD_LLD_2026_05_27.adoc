== Purpose

This document turns the object-storage vector architecture comparison into a ProximaDB
implementation plan. The target is a cataloged vector route that competes on object-storage price
economics without introducing a second durability authority or a parallel vector-only database
inside ProximaDB.

The route name is **Vector Object Economy**. It is an execution route, not a new storage authority.

This blueprint is governed by:

* `docs/12-design/README.adoc` - canonical architecture index.
* `docs/12-design/COMPETITIVE_OLTP_OLAP_MPP_TRAJECTORY_2026_05_20.adoc` - cataloged and explainable
  route knobs.
* `docs/12-design/RELATIONAL_STORAGE_FORMAT_AND_INTEROPERABILITY_2026_05_19.adoc` - canonical
  record, PAX/SST, MVCC, and open-format shape.
* `docs/12-design/adr/ADR-020-canonical-wal-authority.adoc` - canonical WAL authority model.
* `docs/12-design/adr/ADR-004-unified-explain-contract.adoc` - route/write-plan EXPLAIN contract.

== Competitive Target

turbopuffer's public architecture optimizes for:

* object storage as durable storage,
* a per-namespace WAL on object storage,
* centroid-based ANN rather than graph-heavy ANN,
* a small number of large object-storage round trips,
* NVMe/memory cache after first query,
* cache-local query routing,
* strong consistency by default with an eventual-consistency knob.

ProximaDB should match that cost shape while preserving its stronger architecture:

* `xCatalog + canonical WAL + ProximaRecord + policy/RLS + version/time/provenance` remain the
  durable authority.
* SST/HELIX/IVF/PQ/centroid indexes remain access methods or rebuildable projections.
* Route decisions are cataloged and visible in EXPLAIN.
* Freshness and policy boundaries are explicit; stale or unsafe routes are rejected or labeled.

== Decision

The first production implementation MUST use the existing SST/HELIX centroid block path as the
canonical object-storage vector route.

The IVF dual-store implementation remains valuable, but object-store IVF posting lists are a later
projection track until disk/cloud `put` and `get` are implemented with real SST/VIPER reads,
coalesced range access, and recovery tests.

This is NOT an IVF-only route. IVF is one access method in a larger cataloged vector access-method
family. The object-economy route is centered on cold/warm object-storage economics: "how many
remote round trips and bytes does this query need?" Any ANN family can participate when it can
answer that question safely and expose freshness, policy, repair, and cost metadata.

=== Route Identity

[source,rust]
----
enum VectorRouteKind {
    NativeExact,
    NativeQuantizedProgressive,
    VectorObjectEconomy,
    VectorProjection,
    ExternalDelegated,
}

enum VectorAccessMethodFamily {
    CentroidBlocks,   // SST/HELIX/SWIFT block centroids and spatial codes
    Ivf,              // centroid to posting-list projection
    Hnsw,             // navigable small-world graph projection
    DiskAnn,          // disk-optimized graph projection
    Annoy,            // immutable random-projection tree projection
    Lsh,              // hash bucket candidate projection
    Flat,             // exact scan over canonical/projection blocks
    QuantizedFlat,    // binary/int8/PQ candidate generation over blocks
    ExternalAnn,      // explicitly external-authoritative or federated ANN
}

enum VectorFreshnessMode {
    Strong,        // canonical WAL/memtable delta searched and merged
    BoundedStale,  // uses catalog freshness SLA
    StaleOk,       // skips freshness round trip and WAL delta
}
----

`VectorObjectEconomy` is selected when:

* authority mode is internal/canonical or imported snapshot with an allowed policy boundary,
* physical format is SST/HELIX/ProximaBlocks over object-capable storage,
* centroid directory or SST index metadata is available,
* requested freshness mode is compatible with projection state,
* tenant scan budget permits the estimated object bytes,
* query mode is approximate/adaptive, or exact mode accepts block scan after pruning is disabled.

Exact search over object storage is still allowed, but it must explain that it scans all visible
blocks or all selected shards.

== Access-Method Family Matrix

The planner chooses an access method based on storage temperature, freshness, recall target, update
rate, filter selectivity, and object-read economics. No index family owns durable truth.

[cols="1,2,3,3,3"]
|===
| Family | Best route role | Object-storage economics | Freshness model | ProximaDB status/fit

| Centroid blocks
| Primary cold/warm object-economy route.
| Strong fit. Reads compact directory/index metadata and coalesced block ranges. Avoids graph
  pointer chasing.
| Native canonical projection from SST/HELIX flush and compaction. Strong route merges WAL/memtable
  delta.
| First production target because SST already persists centroids, FP16 centroids, Z-order codes,
  zone maps, and bloom filters.

| IVF
| Centroid candidate generator with posting-list projection.
| Strong fit when posting lists are stored as few large ranges. Poor fit if every posting list turns
  into a small object read.
| Rebuildable projection with freshness watermark. Strong route merges WAL/memtable delta.
| Design shape exists; disk/cloud posting-list reads must be completed before object-economy claims.

| HNSW
| Warm in-memory/NVMe projection for low-latency high-recall queries.
| Weak cold S3 fit. Graph traversal causes many dependent reads unless graph layers and neighbor
  pages are heavily cached or packed into large slabs.
| Rebuildable or bounded-async projection. Mutations require graph maintenance or delta overlay.
| Keep as warm accelerator and exact-rerank candidate source, not the first cold-object route.

| DiskANN
| SSD/NVMe-resident graph projection for high-recall large collections.
| Good local-disk/NVMe fit, weak direct object-store fit for cold queries because graph walk is
  latency-sensitive.
| Rebuildable projection with delta overlay. Strong route merges canonical delta.
| Useful for BYOC/local-disk economics; object-store route should cache slabs before use.

| Annoy
| Immutable tree projection for read-heavy or snapshot collections.
| Moderate fit. Tree pages can be packed and cached; random tree descent still risks multiple
  object reads unless pages are bundled.
| Snapshot/rebuild projection. Better for batch refresh than high-churn writes.
| Useful as cataloged projection for read-mostly workloads.

| LSH
| Cheap candidate generator and dedup/filter pre-stage.
| Moderate fit if buckets are compact and batched. Can over-read many buckets for high recall.
| Rebuildable hash projection with bounded staleness.
| Good complement to centroid blocks for specific metrics or near-duplicate search.

| Flat / quantized flat
| Exact fallback and progressive candidate generation.
| Good when blocks are coalesced and compressed; expensive if full scan over object storage.
| Native canonical/projection blocks plus WAL delta.
| Required fallback for correctness, small datasets, recall probes, and benchmark labels.

| External ANN
| Federated or external-authoritative adapter.
| Depends on external service.
| Must declare external authority, policy boundary, freshness, and repair source.
| Not enabled by default for Proxima-authoritative collections.
|===

=== Why Centroid Blocks First

Object storage punishes dependent random reads more than sequential or coalesced range reads. HNSW,
DiskANN, and tree/hash projections can be excellent warm accelerators, but the first cold-object
route should minimize remote dependencies:

1. load directory/index metadata,
2. score centroids/spatial codes locally,
3. fetch selected blocks in merged ranges,
4. rerank full precision or progressive quantized candidates,
5. merge fresh WAL/memtable delta.

That route is index-family-neutral at the planner boundary, but centroid blocks are the best first
physical implementation because ProximaDB already writes the needed metadata in SST/HELIX paths.

== V2 Stacked Modality Model

The v2 architecture stacks vector, document, graph, observability, and relational modalities on top
of canonical relational/table-record storage:

[source,text]
----
Protocol/API modality facade
  -> modality analyzer/lowering
  -> canonical table-record write/read contract
  -> xCatalog schema, policy, version, freshness, projection registry
  -> canonical WAL and ProximaRecord authority
  -> physical layout/access methods/projections
       - PAX row family
       - SST/ProximaBlocks
       - HELIX/SWIFT/RAPTOR/NOVA/VIPER
       - HNSW/IVF/Annoy/LSH/DiskANN projections
       - Parquet/Iceberg/Delta/Hudi adapters/publications/imports
----

In this model, specialty formats are not modality authorities. They are one of:

* native physical layouts over canonical records,
* rebuildable projections/access methods,
* imported snapshots,
* exported publications,
* federated reads,
* explicit external-authoritative assets.

The catalog entry, not the file format or index type, determines authority.

=== V2 Route Contract

Every vector/object-economy route in v2 must bind to a cataloged table or collection with:

* `authority_mode`,
* `workload_profile`,
* `storage_specialization`,
* `physical_format`,
* `projection/access_method family`,
* `freshness_sla`,
* `policy_boundary`,
* `repair_source`,
* `supported_maturity`.

Vector search becomes a relational access-method selection problem:

[source,text]
----
VectorTopK(table.embedding, query, k, filters)
  -> planner resolves candidate access methods
  -> rejects unsafe/stale/lossy paths for requested semantics
  -> selects cheapest admissible route
  -> executes native/projection/external route
  -> applies MVCC/RLS/provenance visibility
  -> returns canonical records or requested facade shape
----

=== Specialty Format Responsibilities In V2

[cols="1,4"]
|===
| Format/index | V2 responsibility

| PAX
| Default relational row-family layout for OLTP/HTAP/OLAP. Vector embeddings may be co-located as
  typed columns/stripes with late materialization.

| SST/ProximaBlocks
| Write-optimized native layout and first object-economy vector route. Blocks carry centroid,
  spatial, bloom, zone-map, quantization, MVCC, and metadata stats.

| HELIX
| Clustered semantic projection/layout over canonical records, using Hilbert/PCA/locality and
  compaction-time reorganization.

| VIPER/Parquet
| Columnar analytics layout or publication/import adapter. Not authority unless catalog says
  external-authoritative.

| Iceberg/Delta/Hudi
| Open-format publication, import, federated read, or external-authoritative table. Their logs do
  not replace ProximaDB canonical WAL for Proxima-authoritative data.

| HNSW/IVF/DiskANN/Annoy/LSH
| Cataloged vector access methods. Each must declare rebuild source, freshness watermark, delta
  overlay behavior, and exact fallback.

| Graph topology indexes
| Projections over canonical edge/node records. They must preserve tenant/RLS/version/provenance.

| Document JSON/full-text/path indexes
| Projections keyed by canonical OID, not facade-local IDs.
|===

=== Implication For This Blueprint

`VectorObjectEconomy` should be implemented as a v2-compatible route from the start:

* It consumes canonical table/collection metadata from xCatalog.
* It returns canonical OID-addressed candidate sets internally.
* It applies MVCC/RLS before returning facade results.
* It declares specialty indexes as projections with freshness and repair metadata.
* It does not embed vector-only authority in SST, IVF, HNSW, Annoy, LSH, or Parquet.

== HLD

=== Write Path

[source,text]
----
Client write
  -> protocol facade
  -> canonical ProximaRecord lowering
  -> canonical WAL append
  -> memtable/current-state apply
  -> flush trigger by size/global threshold
  -> SST/HELIX block writer
       - build ProximaDataBlock
       - compute block centroid and FP16 centroid
       - compute metadata stats and bloom filters
       - compute PCA projection and Z-order/Hilbert code
       - write object segment atomically
  -> update object-economy centroid directory
  -> update manifest with freshness watermark
  -> async compaction reclusters/rebuilds directory
----

Durability acknowledgement remains tied to the canonical WAL according to configured sync mode.
Object segments are access-method materialization, not the commit authority.

=== Strong Read Path

[source,text]
----
Client query
  -> route request
  -> resolve xCatalog collection/table metadata
  -> enforce tenant policy and budget caps
  -> select VectorObjectEconomy route
  -> route to cache-affine query node when possible
  -> read or cache namespace manifest + centroid directory
  -> compute query PCA/Z-order code
  -> select candidate files and blocks
  -> build coalesced object range plan
  -> read selected ranges through cache-aware range reader
  -> deserialize blocks
  -> search selected records with metadata/RLS/MVCC visibility
  -> search WAL/memtable delta for writes newer than directory watermark
  -> merge/deduplicate/rerank top-k
  -> emit EXPLAIN and search-plan trace
----

=== Eventually Consistent Read Path

`VectorFreshnessMode::StaleOk` skips the WAL/memtable delta and may use a cached centroid directory
until its TTL or catalog freshness SLA expires. The response and EXPLAIN must include:

* route kind: `vector_object_economy`,
* freshness mode: `stale_ok`,
* directory watermark,
* maximum staleness estimate,
* skipped fresh-write source.

=== Cache-Affinity Routing

Routing should prefer a node with warm cache for:

* centroid directory object,
* PCA model object,
* SST index region,
* selected data block ranges,
* recent WAL delta for the namespace, when available.

Cache affinity is a preference, not correctness. Any query node can serve the namespace by reading
object storage and WAL.

Target cache-affinity key:

[source,text]
----
tenant_id / namespace_id / collection_id / route_kind / storage_epoch
----

The routing decision should include:

* `cache_affinity_key`,
* `cache_status`: `cold`, `metadata_warm`, `index_warm`, `data_warm`,
* `affinity_node_id`,
* `fallback_reason` when affinity is unavailable.

=== Object Layout

Target object layout for native Proxima-authoritative collections:

[source,text]
----
{base}/{tenant_or_namespace}/{collection}/

    current.json
    versions/{version}.json
  centroid/

* record `AccessOperation::RangeRead`,

=== WAL/Memtable Delta Search

Strong consistency requires all records committed after the directory watermark to be searched.

Required contract:

* directory has `freshness_watermark_lsn`,
* query obtains current committed LSN or collection WAL cursor,
* if current LSN > directory watermark, search WAL/memtable delta for the collection,
* merge by canonical OID and MVCC visibility,
* tombstones in the delta suppress older object results,
* result trace includes `wal_delta_records_scanned` and `wal_delta_bytes`.

This path must obey ADR-020: WAL is authority, object segments and indexes are projections.

=== IVF Projection Track

The IVF dual-store path should become a rebuildable projection over canonical records:

* centroids are inelastic and memory-resident,
* posting lists are elastic and tiered,
* disk/cloud posting lists must use real SST/VIPER read/write implementations,
* projection freshness is cataloged,
* exact/strong queries must search WAL/memtable delta in addition to IVF candidates,
* stale IVF projection routes must be rejected unless request opts into stale reads.

Do not make IVF cloud posting lists the production object-economy route until:

* `CloudSst::get` and `CloudViper::get` are implemented,
* disk `get` returns real posting-list entries,
* object range reads are coalesced,
* projection rebuild/recovery tests exist,
* EXPLAIN shows projection freshness and fallback behavior.

== Acceptance Metrics

The route is not production-ready until CI or a repeatable benchmark reports:

[cols="2,3"]
|===
| Metric | Acceptance target

| Cold object-storage GET count
| Metadata/directory GETs plus coalesced data ranges; target <= 4 logical remote round trips for
  1M-vector clustered datasets.

| Cold bytes read
| Explainable and bounded by route budget. Track selected-block useful bytes and overfetch bytes.

| Warm p50 latency
| Must show cache-hit path separately from cold path. Warm route should avoid object reads for
  directory/index and hot data ranges.

| Strong consistency
| A write acknowledged by canonical WAL is visible to a following strong query, including deletes.

| Stale-ok behavior
| Query may skip WAL delta only when request opts in and EXPLAIN reports staleness.

| Recall
| Approximate route must publish recall bands by dataset shape and route settings. Exact mode must
  preserve exact recall.

| Price economics
| Benchmark output must include object GETs/query, bytes/query, cache hit ratio, and estimated
  storage/request cost per million queries.
|===

== Risks And Mitigations

[cols="2,4,4"]
|===
| Risk | Impact | Mitigation

| Over-pruning centroids hurts recall
| Approximate results degrade silently.
| Keep exact default for accuracy-critical paths; expose recall target, nprobe/block-prune settings,
  and route trace. Add deterministic recall tests.

| Coalescing overfetch reads too many bytes
| Object request count improves but bandwidth cost rises.
| Make max range bytes and gap threshold configurable and visible in EXPLAIN.

| Cache-affinity creates hotspots
| Hot namespaces overload one node.
| Treat affinity as preference. Add load/capacity guard and fallback.

| Directory sidecar becomes stale
| Query misses recently flushed blocks.
| Use versioned atomic writes, manifest cross-check, and WAL freshness watermarks.

| IVF projection becomes hidden authority
| Violates ADR-020 and creates recovery bugs.
| Catalog IVF as rebuildable projection only; strong route always checks canonical WAL/memtable
  freshness.
|===

== First Code Exploration Summary

The first TDD implementation should start in the SST reader, not IVF:

* `src/storage/engines/sst/writer.rs` already computes block centroids, FP16 centroids, and Z-order
  codes.
* `src/storage/engines/sst/readers/block_pruning.rs` already selects blocks by Z-order and centroid.
* `src/storage/engines/sst/readers/sst_query_engine.rs` already has offsets and block sizes needed
  to build a coalesced object range plan.
* `src/storage/persistence/filesystem/caching_filesystem.rs` is the right place to make range reads
  cache-aware.
* `src/cluster/routing.rs` has the routing knobs needed for cache affinity, but it needs a
  namespace cache-status input.
* `src/index/axis/storage/ivf_posting_list_storage.rs` must not be marketed as object-store ready
  until its placeholder `get` implementations are replaced.

== Open Questions

* Should `VectorObjectEconomyOptions` become a typed `SearchParams` field immediately, or should the
  first implementation use `custom_hints` until route semantics settle?
* Should the centroid directory be embedded in the SST manifest or stored as a separate compact
  binary object? This blueprint recommends a separate object because cold queries should not parse
  full manifest history.
* Should HELIX and SST share one directory schema from day one? This blueprint recommends yes, with
  curve type captured per file/block.
* Should cache-affinity live in OSS routing or the SaaS gateway? The route key and metrics should
  live in OSS; capacity policy may live in SaaS/operator code.

== Definition Of Done

This blueprint is done when:

* `VectorObjectEconomy` is a cataloged and explainable vector route.
* Cold query planning uses centroid directory or embedded SST index metadata.
* Selected blocks are fetched through coalesced range reads.
* Strong queries merge WAL/memtable deltas.
* Stale-ok queries are explicit and traceable.
* Cache-affinity routing is implemented as a preference.
* IVF object-store posting lists are either completed as a projection or explicitly excluded from
  supported object-economy claims.
* Benchmarks publish object request count, bytes read, cache hit rate, recall, and estimated cost.
