== History

*Principle (still governing):* **OSS ships capability + mechanism; the enterprise layer supplies
commercial policy, data, authority and go-to-market surfaces.** The enterprise layer is `anvaiops`, a
separate TS/Python repo that consumes the SDK. The OSS engine compiles and runs standalone.
Commercial behaviour enters only through three sanctioned seams:

* default-OFF feature gates;
* ports with neutral default adapters, fed by operator config and request claims such as
  `TenantContext.tier`;
* neutral naming: no tier or SKU names in OSS public types.

*Decisions that still apply:*

* OSS emits **neutral quantities only**. Examples are the KOU egress meter
  `proximadb_kou_bytes_total{tenant_id, kou_locality, direction}` and neutral-unit `Cost(q)`. The $
  rates, the cloud/region→locality topology, the tenant→tier authority and the tier→multiplier values
  all live in anvaiops.
* `set_tier_multiplier_resolver` and `set_tenant_tier_resolver` are ports with an inert OSS default:
  `1.0`, and every tenant on the default tier. The multiplier is **routing-neutral**. It scales every
  candidate equally, so engine selection can never depend on a commercial tier.
* `StoragePoolClass` is `Pooled/Standard/Premium/Dedicated`. The old commercial names survive only as
  serde aliases.

*Lesson:* an audit of names that "look commercial" over-flags. `Tier1..Tier5`, `pooled`/`dedicated`,
`SecurityMode::Enterprise` and `*_cost_per_vector` (latency, not money) were all correctly generic.

*Evidence:* `python3 scripts/check_oss_boundary.py` runs in `.github/workflows/layering-check.yml`.
Outside gated code it denies commercial tier identifiers, pricing units (`ksu|kru|kiu|keu|kou|…`) and
non-doc `anvai*` references.
