== 1. Problem

The PAX cascade has the right shape (coarse cells → RaBitQ → SQ8 rerank → rows), but its
coarse level is **per segment**. A cold query today, per segment and with segments run in
parallel (`src/storage/engines/sst/search/mod.rs` `fallback_to_direct_search_arc`):

[cols="1,4",options="header"]
|===
| Wave | Read
| 1 | Header prefix (`PROXIMADB_PAX_PREFIX_PREFETCH_BYTES`, default 1 MiB; usually also covers A0 and the Region-A header).
| 2 | Region-A cells of this segment's `nprobe` nearest A0 cells, plus the footer (`coarse_probe_survivors`, `segment_format.rs`).
| 3 | Region-B survivor ranges (SQ8 rerank).
| 4 | Region-D OID chunks for the per-segment top-k.
| 5 | Rehydrate blocks (`read_records_by_positions`).
|===

Plus the discovery LIST before wave 1, and the stage-F pass for filtered queries. Three
structural costs follow:

. **GETs scale with segments, not with the answer.** Every segment pays its own header,
  cell, rerank and row waves; `nprobe` is chosen per segment (`geometric_nprobe`,
  `ceil(sqrt(k_c) × 2)`), so `S` segments probe `S × nprobe` cells.
. **Depth is 5 sequential waves**, not 3, because A and B are separate regions (B can only
  be addressed after A ranks survivors) and the per-segment header must precede any cell read.
. **Every compaction retrains** PCA + k-means for its output (`cluster_plan_ivf_probe`,
  `block_cluster.rs`). There is no shared cell space, so nothing can be ranked across
  segments in one place.

Recorded reference figures: 20–80 GET/query cold, 3–9 s at 100 ms RTT (seams doc §5).
Target (seams doc §6 P5b): **cold ≤ 3 sequential waves, ≤ 20 GET/query at 1M, recall ≥ 0.98;
warm 0–1 wave.**

== 3. Design

=== 3.1 (a) The collection centroid directory

==== Object and placement

One immutable object per directory generation, in the collection's data directory beside the
segments:

----
<collection data dir>/centroids-<generation:016x>.pxcd
----

The seams doc names it `centroids.pax`. The extension is deliberately **not** `.pax`:
discovery treats every `*.pax` in the directory as a segment. Placing it in the same
directory means the LIST that discovery already issues returns it, so locating the directory
costs **no extra round trip**.

The directory is an **S7 projection** (ADR-097): derived only from segment bytes, rebuildable
from them at any time, never authoritative, and validated against the live segment set
through its stamp. Losing or corrupting it degrades a query to today's per-segment path; it
can never change a result set's correctness, only its cost.

==== Contents

[source]
----
[magic "PXCD"][version u8][flags u8][reserved u16]
[generation u64][built_at_unix_ms u64]
[dim u32][metric u8][pad 3]
[models:   n_models × { model_id u64, n_comp u16, pca_mean dim×f32,
                         pca_components n_comp×dim×f32 }]
[segments: n_segments × { name (len-prefixed UTF-8), size_bytes u64, row_count u64,
                          model_idx u32, decode_key (§3.4, slice D6) }]
[cells:    n_cells × { model_idx u32, segment_idx u32, centroid n_comp×f32, radius f32,
                       row_begin u64, row_end u64, a_off u64, a_len u64,
                       b_off u64, b_len u64, d_block_begin u32, d_block_end u32 }]
[checksum u64]   (FNV-1a over all preceding bytes, as A0)
----

* **Models are a table, not a single model.** Today every segment carries its own PCA model
  (one model per segment). After slice D3 (shared model) every compacted segment references
  the same model, and the table holds one entry plus whatever L0/legacy segments remain. One
  format covers the migration and the steady state.
* `model_id` is the FNV-1a of the model's serialized PCA bytes, so two segments written with
  the same model are recognised as sharing a cell space.
* Cell entries copy A0's `CoarseCellEntry` extents verbatim. The directory never derives
  offsets; the writer of the segment owns its layout (the A0 rule).
* The **stamp** is the `segments` table: the exact set of segment names (and sizes) whose cells
  the directory covers.

Size: SIFT1M at the settled geometry (`k_c = 30` per segment, `dim = 128`, `n_comp ≈ 16`)
costs ≈ 8.7 KiB per model and ≈ 140 B per cell, so four segments come to ≈ 52 KiB. At the A0
worst corner (`k_c = 4096`, `dim = 3072`), each segment is bounded by the A0 budget test
(`a0_size_budget_tests`), times the segment count. With the shared model (D3) the model term
is paid once.

==== Build and publish (at compaction)

. **Incremental build** at the end of a successful compaction, after the inputs are retired
  (`retire_inputs_with_retry`): start from the newest valid directory, drop entries for the
  retired inputs, add the output segment's A0 (the writer holds it in memory; no read-back).
. **Full rebuild** when no valid directory exists or the incremental base fails validation:
  list the live set and read each segment's A0 from its header prefix (one ranged GET per
  segment, off the query path). Segments without A0 are simply not covered.
. **Publish** `centroids-<g+1>.pxcd` **create-only** (`put_if_absent`; `O_EXCL` on local
  disk). If the key exists, another compaction published first: reload the newest directory
  and retry the incremental step (bounded retries, then skip; the next compaction repairs).
. **GC:** keep the newest two generations; delete older ones best-effort. A reader holding an
  older generation still answers correctly (stamp rule below).

Write gate: `PROXIMADB_PAX_WRITE_CENTROID_DIRECTORY` (default **OFF** until the P5b gate passes).

==== Query use (global cell selection)

. Discovery returns the live segment set `L` and the newest directory key from the same LIST.
  The directory is fetched once per generation and cached (wave 0; warm it is free).
. **Coverage.** Covered segments are `C = L ∩ stamp`. Segments in `L \ C` (new flushes, A0-less
  or legacy segments) run today's per-segment cascade unchanged. Directory entries for segments
  not in `L` (retired since publish) are ignored; their rows live in a newer segment that is
  either covered by a newer generation or in `L \ C`. Correctness never depends on the
  directory being current.
. **Global ranking across cell spaces.** Project the query once per model. For a cell `c` of
  model `m` with PCA mean `μ_m` and orthonormal components `P_m`, rank by the squared distance
  from the query to the centroid's reconstruction `μ_m + P_mᵀ c` in the **original** space:
+
----
score(q, c) = ‖P_m(q − μ_m) − c‖²  +  (‖q − μ_m‖² − ‖P_m(q − μ_m)‖²)
              └ today's in-segment PCA distance ┘  └ per-model residual, one value per model ┘
----
+
Within one model the residual is a constant, so the order equals today's A0 order exactly.
Across models the scores are commensurable, so one sorted list serves all segments. With one
shared model (D3) the residual term vanishes from the comparison.
. **Selection.** Walk cells in score order; take a cell if non-empty (and, under a filter, if
  its row range intersects the allow-set, as `coarse_probe_survivors` does today). Stop when
  at least `nprobe_global` cells **and** at least the survivor-pool rows
  (`pax_rabitq_pool_for_top_k(k, rows_covered)`) are selected.
  `nprobe_global = ceil(sqrt(total_cells) × multiplier)` reuses `geometric_nprobe` and the
  `[storage.sst_config.coarse_probe]` settings; `PROXIMADB_PAX_READ_CENTROID_DIRECTORY_NPROBE`
  overrides it for sweeps.
. Each covered segment receives its **preselected cell list**; a covered segment with no
  selected cell is **skipped with zero reads**. The per-segment cascade then runs from the
  Region-A wave with that list instead of ranking its own A0.

Read gate: `PROXIMADB_PAX_READ_CENTROID_DIRECTORY` (default **OFF**). Fail-safe: a missing,
corrupt, or dimension-mismatched directory means "no coverage" and the query runs exactly as
today.

=== 3.2 (b) Cluster-contiguous compaction

The directory alone removes per-segment ranking and skips segments, but with `S` segments that
all span every cell a probed cell still costs up to `S` ranged reads. Two compaction changes
make a cell cost one read:

. **Shared collection model (D3).** Compaction classifies its output with the directory's
  model (`IvfProbeClassifier` built from the persisted PCA and centroids) instead of training a
  new one, provided `dim` matches and the model is not stale. The classifier/training split
  already exists (`finish_ivf_probe_classifier` vs `classify_coords`), so this is a new
  constructor, not a new algorithm. *As built (D3):* the shared model is the **cell space**
  (model plus exact centroid table) covering the most rows; its centroids and radii come from
  that space's largest segment. Retraining is triggered when any of these holds:
  ** the dimension differs;
  ** the collection's rows (the space's covered rows, or the output if larger) need more than
     `2 ×` the model's cells, or fewer than half of them (the model no longer suits the
     collection);
  ** more than 5% of a strided sample (up to 4096 rows) falls outside its cell's trained radius
     (the data drifted). The radius test replaced the draft's "1.5 × training-time mean
     distance": a training-time mean is not persisted, and per-segment max radii are. Radii
     come from one template segment, never a max over segments, so accepted outliers cannot
     ratchet the test open.
+
The cheap checks run before any row is classified. The tag-partitioned plan (TD-FPRUNE-1)
still trains its own model in D3. A retrain produces a new model; segments keep their own model
id until rewritten, which the model table already handles. The read side counts `nprobe` over
**distinct** cells `(cell space, a0_cell)` and probes a selected cell in every usable segment
holding it. `k` for the collection model is sized on the **collection's**
covered rows, so each cell's A+B bytes approach the coalescer's target range on the storage
class: `k_G = clamp(N · (a_row + b_row) / (IopsBudget.target / 2), 16, 4096)`.
For SIFT1M on S3 (8 MiB target; A+B ≈ 152 B/row once co-located) that is ≈ 36 cells, and
geometric `nprobe = ceil(sqrt(36) × 2) = 12` probed cells. This matches the settled one-segment
geometry (30 cells, 11 probed, recall@10 ≥ 0.98) and fits the §3.5 budget. The D7 nprobe sweep
calibrates the constant, and the directory records the chosen `k_G`.
. **Cell-range partitioned outputs (D4).** A major compaction writes its outputs partitioned
  by **contiguous ranges of global cells in Hilbert order**, each output bounded by the existing
  segment size target. Every cell then lives in exactly one compacted segment (plus the
  uncompacted L0 tail), so `nprobe` probed cells cost `nprobe` ranged reads, and
  Hilbert-adjacent probed cells usually fall in the same segment and coalesce into fewer
  reads. Minor compactions that only fold L0 into the tail keep today's behaviour; the
  partitioned rewrite runs when the tail exceeds a fraction of the collection (or on explicit
  `OPTIMIZE`).

The tag-partitioned layout (TD-FPRUNE-1, `cluster_plan_ivf_probe_partitioned`) composes:
partition-by-tag then cell within, under one shared PCA; the directory treats each
(partition, cell) as a cell.

=== 3.3 (c) RaBitQ and SQ8 co-located per cell (D5)

Today Region A holds all cells' RaBitQ codes and Region B all cells' SQ8 codes, so a cell's
SQ8 bytes are a second, dependent wave after RaBitQ ranks survivors. The co-located layout
interleaves per cell:

----
[prefix][A0][ cell_0: A codes | B codes ][ cell_1: A codes | B codes ] ... [D][footer]
----

* A header-prefix flag selects it; A0 extents stay absolute, so the probe code does not
  change. The whole-region fallback (used on a probe miss) walks cells instead of assuming one
  stride; that is the one reader change.
* A probed cell is then **one** ranged GET for A+B. RaBitQ ranks and SQ8 reranks from the same
  bytes: the rerank wave disappears.
* Cost: B is read for every row of a probed cell, not only for survivors. For SIFT
  (`dim = 128`): A ≈ 24 B/row, B = 128 B/row, so a cell's bytes grow ≈ 6×. On object storage a
  GET of a few MiB costs about the same latency as a small one, so this is the right trade
  there; on local disk survivor-only B remains better. The writer emits the co-located layout
  when the destination's `IopsBudget` profile is an object store (S3, Azure, GCS) and keeps
  separate regions on local disk. Both layouts are readable everywhere.

*As built (D5, owner decision 2026-10-23):* the first step is a same-wave fetch rather than a
new layout. The probe appends each probed cell's Region-B extent (already in A0) to its cold
Region-A wave, and the rerank reads survivors from those buffers
(`PROXIMADB_PAX_READ_SAME_WAVE_RERANK`). The rerank wave disappears with no format change; a
probed cell costs up to two ranges instead of one. The co-located layout above is built only
if D7 shows the second range breaks the request budget.

=== 3.4 Collapsing the per-segment metadata waves (D6)

The remaining per-segment reads before a cell read are the header prefix, A0 and the
Region-A header (RaBitQ centroid and seed), and the footer (SQ8 dequant key, block/row-group
table for row rehydration). Per ADR-094 D4, the directory carries a **decode key** per covered
segment: the Region-A header bytes, `sq8_min/sq8_scale`, and the footer's block and row-group
OID-chunk tables. The segment keeps its self-describing copy. A covered segment then needs no
header, A0 or footer read on the query path.

*As built (D6):* behind the write gate `PROXIMADB_PAX_WRITE_DIRECTORY_DECODE_KEYS` (default OFF;
off, a directory is the D1 v1 format byte for byte), the directory format is `PXCD` v2 (a keyless
directory is still written as v1, and both parse). Each covered segment entry may carry a decode
key: the 88-byte header prefix, the Region-A header, the
A0 model's seed and training count, the footer's row count, SQ8 dequant key and schema facts, and
its block table with the row-group OID-chunk stats (the footer's own entry wire form). The
directory rebuilds the segment's Region A0 from its model and cells plus the key
(`PaxCentroidDirectory::segment_decode`); the publisher keeps a key only when that rebuild is
byte-identical to the segment's A0. Since a key replaces the segment's own metadata, it is bound
to the object it was read from: it records the listed ETag, and readers use it only when the
current listing reports the same one (backends that list no ETag keep the `(name, size)` stamp).
Behind `PROXIMADB_PAX_READ_DIRECTORY_DECODE_KEYS` (default
OFF), a directory-planned, unfiltered scan that misses the invariants cache takes this metadata
from the directory. The rebuilt footer carries only the ANN cascade's fields, so it is never
admitted to the invariants cache; the top-k rehydration takes its block table from the key too.
Because rehydration fetches the top-k row-group blocks anyway, a decoded scan reads those blocks
whole in one wave (bounded to 8 IOP-sized blocks; larger sets keep the OID-chunk fetch), resolves
the OIDs from them, and hands the bytes to the rehydration: wave 2 of §3.5 is one request per
block instead of an OID chunk plus a block, in two dependent waves. Measured under
`LatencyFileSystem` (4 segments × 1,500 rows, `dim = 32`, header-only prefix reads): a cold query
against a loaded directory is 3 waves and 20 requests with decode keys, against 7 waves and 40
requests without them and 7 and 38 with the directory off. A segment no larger than the scan's
cold prefix read (`PROXIMADB_PAX_PREFIX_PREFETCH_BYTES`, 1 MiB) keeps that read instead of its key:
the one request returns the whole object and caches it, which beats the key on waves and requests
(measured: with whole-segment prefix reads, keys would cost 236 reads over 30 queries against 188
without them; with header-only reads, 236 against 284). Keys are added when a segment is
(re)loaded by a publish: entries carried over keyless (from a v1 base, or published while the
write gate was off) gain a key only when compaction rewrites their segment. A carried key whose
ETag no longer matches the listing reloads its segment, cells included; turning the write gate
off republishes the directory as v1 at the next publish even with no live change.

=== 3.5 The resulting cold query

[cols="1,3,2",options="header"]
|===
| Wave | Reads | GETs at 1M (budget)
| 0 | LIST (already issued by discovery) + directory GET (cached by generation) | 2
| 1 | All probed cells' co-located A+B extents across covered segments, coalesced, issued in parallel; uncovered L0 tail scanned exactly (WAL-tail rule, seams doc) | ≤ 12
| 2 | Top-k row rehydration: OID chunks and row-group blocks of the global top-k, coalesced, in parallel | ≤ 6
|===

**3 waves, ≤ 20 requests.** Warm: wave 0 is cached, and wave 1 hits the L2/survivor caches,
so 0–1 waves. Reads within a wave must actually run in parallel:
`PROXIMADB_READ_RANGES_INFLIGHT` defaults to sequential today, and D6 sets a parallel default
for object-store profiles. *As built (D6):* with `PROXIMADB_READ_RANGES_INFLIGHT` unset, waves
on object-store paths run 16 wide; local paths keep deferring to
`PROXIMADB_FS_READ_RANGES_PARALLEL`, and an explicit `0` restores the deferral everywhere. Wave 0
is two dependent requests (the LIST names the generation), but the directory GET is paid once per
generation, so a query against a loaded directory is LIST → cells → rows. `minio://` URLs resolve
as local; the MinIO gate bed is addressed as `s3://` (`--s3-endpoint`), so it gets the parallel
default.

== 4. (d) Measurement harness and gates

=== 4.1 Instruments

* **GETs per query:** delta of `proximadb_object_store_gets_total` across the query phase divided
  by queries, already reported as `gets_per_query` by `sift1m_get_reduction.py`. LIST and HEAD
  are counted as requests too. D7 adds a `requests_per_query` column that includes them, and the
  gate uses that column.
* **Waves per query (new, D7):** a query-scoped wave counter. Each object read records
  `(issue_t, done_t)`; waves are the number of maximal groups of overlapping intervals along the
  query's critical path. It is reported as `proximadb_pax_query_waves` (histogram) and as a
  harness column. A test-only `LatencyFileSystem` wrapper (fixed injected delay per read; there
  is no in-process latency wrapper today) makes the count deterministic in CI: with delay `L`
  and parallel reads inside a wave, `query latency ÷ L` must equal the reported waves.
* **Injected latency for the gate:** MinIO behind Toxiproxy 2.12.0 adding fixed latency in
  each direction. **Realigned 2026-10-25 (owner decision): the canonical profile is
  intra-region, 5 + 5 ms** (measured 11.4 ms RTT; intra-region S3 GET p50 is ~5–15 ms) — no
  cross-region deployments are planned. The original 25 + 25 ms profile is retained as a
  robustness stress column. Waves and requests are latency-independent; p50 re-prices per
  profile (at 10 ms the ~74 ms non-wave compute residual dominates — see the D8 artifact).

== 5. (e) Implementation slices (PR-sized, in order)

Each slice is one PR, behind default-off gates until D8. Every slice adds tests on a small
synthetic dataset: Gaussian clusters, `dim = 32`, about 20k rows written as 3–4 segments. That
is enough for `MIN_ROWS_FOR_IVF` and multi-cell A0s and runs in seconds.

[cols="1,4,3",options="header"]
|===
| Slice | Change | Tests
| **D1** directory format + compaction build/publish
| `centroid_directory.rs` in `proximadb-storage-common`: `PaxCentroidDirectory` (§3.1 layout, minus decode keys), deterministic `to_bytes`/`parse` (fail-closed), `build_from_a0s`, incremental `apply_compaction(retired, added)`, global `rank_cells` with the cross-model score. Compaction publishes `centroids-<gen>.pxcd` create-only after retiring inputs, behind `PROXIMADB_PAX_WRITE_CENTROID_DIRECTORY` (default ON since D8/#2241; `0` disables); GC keeps two generations.
| Round-trip and byte determinism; corruption, truncation and version are rejected; the cross-model score equals the full-space reconstruction distance, and its order equals A0 order within one model; incremental build equals full rebuild; create-only conflict path; a compaction with the gate on publishes a directory that covers exactly the live set; with the gate off, nothing is written.
| **D2** query-side global cell selection

== 6. Risks and open questions

* **Cross-model ranking quality.** Before D3, cells from differently trained models are ranked
  through their reconstructions. The score is exact for the reconstruction, but a
  reconstruction is a coarser stand-in for a cell than the in-segment PCA distance. The pool
  floor in §3.1 (select until the survivor pool rows are covered) guards recall; D2's test
  measures it.
* **Directory staleness under heavy ingest.** Uncovered L0 segments fall back to the
  per-segment path. If the tail grows faster than compaction, GETs regress toward today's
  figures but never below today's correctness. The tail-exact-scan rule and the D4 major
  compaction trigger bound it.
* **Concurrent compactions.** Create-only publish serialises generations. A loser retries
  incrementally; a skipped publish only delays coverage.
* **Object-store LIST consistency.** S3 and GCS are strongly consistent for LIST after PUT.
  Readers never require the newest generation, only a valid one.
* **TD-PAXMETA-1 interaction.** When the collection segment manifest lands, the directory's
  stamp becomes a manifest snapshot id and publication can ride the same CAS commit. The
  format reserves `flags` for that; nothing here blocks it.
