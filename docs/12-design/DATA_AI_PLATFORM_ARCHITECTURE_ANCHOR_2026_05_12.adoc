== Executive Position

ProximaDB should become the **context data and AI operating system**: one catalog, one policy
plane, one logical schema model, and one explainable planner spanning OLTP, OLAP, vector,
document, graph, event, streaming, feature, model, and agent state workloads.

The platform must explicitly compete with Databricks, Snowflake, and Trino by offering a unified, high-performance **PostgreSQL wire-compatible SQL warehouse** and **modern distributed data engineering engine**. The winning wedge is:

* **PostgreSQL wire compatibility first** as the primary ingestion and query surface for frictionless adoption by BI tools, dbt, and existing data warehouse workloads.
* **Relational foundation first**, with multi-modal (vector, graph, document) capabilities stacked as zero-ETL extensions rather than isolated silos.
* **Decoupled object-storage-first architecture** utilizing local filesystem APIs that seamlessly scale to S3/GCS/Azure, enabling independent scaling of storage and compute.
* **Rust-native distributed execution** via DataFusion/Ballista, replacing JVM-heavy Spark dependencies with a highly efficient, async I/O optimized engine for both SQL and PySpark-style DataFrame workloads.
* A single, robust multi-engine routing layer (Volcano for OLTP/Freshness, DataFusion for OLAP/MPP, Specialized for Vector) all orchestrated under one xCatalog policy plane.

The moat is not proprietary lock-in. The moat is **Zero-ETL Multimodal HTAP + Lakehouse on a single Rust binary**: semantic control where ProximaDB understands records, embeddings, graph relationships, event history, model lineage, and PySpark-like data engineering workloads together, executing them over highly optimized header/filter-driven caches on open formats (Parquet/Iceberg).

== North Star

ProximaDB should provide:

* **Open compatibility**: pgwire for JDBC/SQLAlchemy/ODBC/psql/BI/Calcite, Arrow Flight for
  columnar exchange, REST/gRPC for lifecycle APIs, SDKs for ergonomic embedded and AI workflows.
* **One catalog**: xCatalog stores schema, physical layout, statistics, governance, lineage,
  model metadata, feature definitions, streams, branches, and connector state.
* **One logical algebra**: SQL, Cypher/GQL, AQL, UQL, PromQL/LogQL, vector search, and agent
  memory APIs lower into the same logical operators from the multi-modal overhaul spec.
* **Many execution engines**: native Rust and DataFusion local/distributed as the primary
  Proxima-owned routes; Spark, Trino, Ray, Flink, Kafka Streams, Kinesis consumers, and future
  warehouse/lakehouse adapters as external/delegated integration routes.
* **Many storage layouts**: hot row/record, hybrid PAX, columnar Parquet/Arrow, Avro row
  interchange, append-only event logs, graph topology, vector index segments, and external
  lakehouse table formats.
* **Branchable state**: Neon-style copy-on-write branches, Supabase-style preview environments,
  point-in-time restore, schema-only branches, masked-data branches, and TTL branches for
  agentic/git workflows.
* **AI lifecycle**: feature store, experiment tracking, MLflow-compatible registry metadata,
  AutoML orchestration, model serving metadata, evaluation, drift, feedback, and agent traces.

== Competitive Lessons To Absorb

=== Databricks

Databricks teaches that a unified governance/catalog layer over data and AI assets is strategic.
Unity Catalog-style governance now extends beyond tables into models, functions, connections,
lineage, and AI traffic. They also successfully combined Lakehouse storage (Parquet/Delta) with scalable data engineering (Spark) and MLOps (MLflow).

Design response:

* **xCatalog as the Unified Policy Plane:** xCatalog governs data and AI assets with the same policy system. Feature tables, model versions, MLflow-compatible experiments/runs, prompts, tools, agent traces, and external connections are all first-class catalog objects (`mlops.*`, `agent.*`).
* **Rust-Native Data Engineering (Spark Replacement):** Spark is no longer the target for heavy lifting; it is replaced by our **Rust-native distributed execution engine** (DataFusion/Ballista). We will expose PySpark-like DataFrame APIs via our Python SDK, lowering directly into Rust-native async I/O physical plans. This eliminates JVM overhead and provides single-binary efficiency for CPU-intensive/Monte Carlo workloads.
* **MLflow & Model Management:** ProximaDB maps the MLflow landscape directly into xCatalog. MLflow compatibility is implemented as a native facade, allowing users to track experiments, manage the model registry, and orchestrate AutoML directly within the ProximaDB ecosystem without needing a separate MLflow tracking server.
* **DataFusion Local/Distributed:** is the primary Proxima-owned data-engineering route, replacing the need for external JVM clusters while keeping the object-storage-first Lakehouse paradigm.

=== Snowflake and Polaris

Snowflake/Polaris proves that the catalog is the interoperability point. Apache Polaris
implements Iceberg REST catalog semantics for multi-engine interoperability. ProximaDB should
support Iceberg REST/Polaris interoperability, but xCatalog must be broader than table metadata:
it must include online serving state, vector/graph indexes, feature freshness, branch lineage,
and agent execution history.

Design response:

* xCatalog has an Iceberg/Polaris-compatible facade where applicable.
* Pgwire exposes catalog tables for SQL-native clients.
* The native catalog owns cross-modal metadata that Iceberg cannot express cleanly.
* External catalogs are peers and publication targets, not the internal source of truth.

=== AWS, Azure, Redshift, Synapse, and Managed Services

Cloud platforms teach operational breadth: ingestion, streaming, warehouse analytics, serverless
scaling, materialized views, result cache, event buses, object storage, IAM, monitoring, and
managed ML. ProximaDB cannot out-cloud every service early; it should compose with them while
owning the local-to-distributed developer experience and cross-modal semantics.

Design response:

* Treat S3/Azure Blob/GCS as storage backends.
* Treat Kafka/Kinesis/Event Hubs/PubSub as stream sources/sinks.
* Treat Redshift/Synapse/BigQuery/Snowflake as federation targets and external tables.
* Adopt Redshift-style materialized views, result cache, workload isolation, and federated
  query as later platform features.

=== Google Spanner

Spanner teaches that global consistency needs explicit time, MVCC, synchronous replication,
schema-change safety, and clear read semantics. ProximaDB should not claim Spanner semantics
without foundation; it should design early for hybrid logical clocks, transaction timestamps,
point-in-time reads, branchable snapshots, and schema-versioned catalog changes.

Design response:

* Every record has version/time/provenance fields per the multi-modal overhaul spec.
* Catalog mutations are versioned and atomically applied.
* Distributed phase introduces HLC/uncertainty-aware timestamps, quorum replication, and
  bounded-staleness reads before global active-active claims.

=== Fivetran

Fivetran teaches that connectors win by automating schema drift, incremental sync, cursors,
CDC, retries, and operational visibility. ProximaDB should not become a connector company first,
but it needs ingestion contracts that make connectors durable and catalog-visible.

Design response:

* Connector state is cataloged: cursor, source schema, target schema, last sync, error state,
  lag, and schema drift.
* First-class CDC ingest and CDC out use the event log and xCatalog lineage.
* Support custom Python connector SDK later, but begin with Postgres logical replication,
  Kafka, file/object storage, and webhooks.

=== dbt

dbt teaches that transformations, tests, contracts, metrics, lineage, documentation, and
developer workflow matter as much as storage. ProximaDB should provide dbt-compatible targets
through pgwire while also exposing native semantic metadata in xCatalog.

Design response:

* Pgwire must be good enough for dbt models, tests, seeds, snapshots, and docs workflows.
* xCatalog stores model contracts, metrics/semantic definitions, lineage, freshness, quality
  checks, and run artifacts.
* Transform execution can route to native Rust/DataFusion locally, then Spark/Trino/Ray/Flink
  in distributed phases.

=== Vector, Graph, Search, Document, OLAP, And Observability Platforms

The 2026 competitive landscape is converging on a common pattern: specialized physical access
methods are moving closer to general-purpose data systems, not farther away from them.

Vector systems such as Pinecone, Qdrant, Milvus, pgvector, Oracle AI Vector Search, MongoDB Atlas
Vector Search, Elasticsearch/OpenSearch, Neo4j vector indexes, Databricks Vector Search, Snowflake
Cortex Search, and S3 Vectors all validate that vector search is now a table/document/graph/search
capability. The durable authority varies by vendor: relational tables, Delta tables, document
collections, Lucene segments, graph nodes, object-store vector buckets, or managed service indexes.
The common feature pressure is filtered ANN, hybrid lexical+semantic retrieval, reranking,
freshness, multi-tenancy, and cost-controlled object-storage-backed serving.

Graph systems show the value of graph-native APIs, graph algorithms, and vector-on-graph
retrieval. OLAP systems show the value of columnar/vectorized execution, rollups, materialized
views, and real-time ingest. Document/search systems show the value of JSON/document ergonomics,
full-text search, analyzers, faceting, and aggregation. SIEM and observability systems show that
logs, metrics, traces, profiles, alerts, anomaly detection, retention tiers, dashboards, and
AI/LLM observability are product surfaces, not just storage schemas.

Design response:

* ProximaDB should not become a clone of any one category. It should be a typed context data
  platform where relational, document, graph, vector, event, observability, feature, model, and
  agent state share one catalog and policy plane.
* Vector search must be predicate-aware by default for tenant/RLS, branch/time, and typed metadata.
  Post-filter or overfetch approaches are compatibility fallbacks, not the long-term correctness
  path.
* Hybrid retrieval must be a first-class query plan shape: BM25/full-text, dense/sparse vectors,
  graph neighborhood, document paths, time predicates, and rerankers should compose through one
  logical algebra and one explainable optimizer.
* Observability/SIEM workloads require canonical log/metric/span/profile records plus rebuildable
  time, full-text, trace-assembly, rollup, anomaly, service-map, and alert projections.
* OLAP credibility requires Arrow-native batches, vectorized execution, column pruning,
  statistics, late materialization, spill, materialized views, and workload-aware row/PAX/columnar
  layout selection.
* Document/search credibility requires JSON path indexes, variation-aware schema discovery,
  full-text analyzers, faceting/aggregation, and lexical+semantic ranking without splitting
  document truth from canonical records.

=== Neon and Supabase

Neon and Supabase teach that developer workflow is a product surface: branch data like code,
preview environments, instant restore, schema-only branches, seeded branches, and GitHub/CI
integration. ProximaDB should generalize this beyond relational tables into vector indexes,
agent checkpoints, event logs, graph state, and ML metadata.

Design response:

* Branching is a catalog/log/storage primitive, not a dashboard-only feature.
* Branches can be data-full, schema-only, masked, seeded, or TTL-based.
* Branches cover records, vector index manifests, graph topology deltas, event streams,
  feature/model metadata, and agent checkpoint history.

== Storage And Format Fungibility

The platform should be strict about semantic authority and flexible about physical shape.
ProximaDB should not enforce one internal format, one row store, one column store, or one external
lake format for every workload.

The invariant is:

[source,text]
----
semantic authority:
  xCatalog + ProximaRecord + ProximaType/ProximaValue + WAL/log/manifest +
  tenant/RLS + version/time/provenance + retention policy

physical choices:
  LSM row/record, B-tree/range indexes, PAX, columnar segments, Parquet files,
  Arrow batches, ANN fragments, graph topology projections, time-series blocks,
  event streams, external Iceberg/Delta/Hudi tables
----

Design response:

* Internal hot-state layouts may be LSM, row/record, PAX, columnar, append-only event, or
  workload-specific projection families.
* Relational features such as primary keys, unique indexes, secondary indexes, referential
  integrity, check constraints, materialized views, and stronger transaction/isolation modes are
  table capabilities declared in xCatalog. They are optional by workload, but when enabled they are
  enforced below protocols and consistently exposed through pgwire, REST/gRPC, Arrow Flight, and
  SDKs.
* Columnar and record-oriented stores are layout plugins/access methods below xCatalog. They should
  not introduce separate record envelopes, type systems, policy rules, or recovery semantics.
* Arrow is the primary in-memory and wire interchange shape. Parquet is an analytical file layout.
  Iceberg/Delta/Hudi are external table/snapshot interoperability layers. None of these should be
  treated as the universal internal ceiling.
* External tables can be authoritative only when xCatalog explicitly registers their ownership,
  snapshot semantics, schema/type mapping, policy enforcement boundary, and write/refresh mode.
  Otherwise they are imports, exports, publications, or rebuildable projections over ProximaDB
  canonical records.
* Every non-canonical projection must declare freshness, rebuild source, invalidation policy,
  retention impact, and benchmark criteria before it becomes a default path.

== Strategic Moat

ProximaDB should build stickiness through capabilities that open engines and cloud services do
not provide as a coherent unit:

* **Cross-modal query planning**: one optimizer that can combine relational predicates, vector
  similarity, JSONB paths, graph traversal, event time, and model/agent lineage.
* **Catalog-native AI state**: features, models, prompts, tools, checkpoints, memories, traces,
  evaluations, predictions, labels, drift, and feedback are queryable together.
* **Branchable context**: data branches for software development, agent replay, model evaluation,
  migration rehearsal, and incident recovery.
* **Local-to-cloud continuity**: embedded Python/Rust first, same catalog and SQL contracts when
  promoted to server and distributed modes.
* **Engine autopilot**: cost/model-aware recommendations for SST vs VIPER vs HELIX vs external
  Spark/Trino/Ray/Flink execution.
* **Open but better native format**: publish to Parquet/Iceberg/Delta where needed, but use a
  native context format for hot mutable multi-modal state that table formats do not optimize for.
* **Policy once**: RLS, masking, tenancy, retention, audit, and egress controls enforced across
  pgwire, REST, gRPC, Arrow Flight, SDK, streaming, and embedded execution.
* **Optional relational rigor**: tables can opt into keys, uniqueness, referential integrity,
  constraints, materialized views, and stronger isolation without forcing OLAP, vector, document,
  or observability workloads into the same cost profile.
* **Observability plus AI context**: logs, metrics, traces, profiles, agent traces, evaluations,
  prompts, tool calls, and retrieval evidence can be queried together under one policy model.

== Success-Odds Anchor Trajectories

The Hadoop, MPP appliance, lakehouse, and cloud warehouse history should refine ProximaDB's path in
one direction: keep proven file/split/vectorized mechanics, but do not make them the product
center. The durable product center is the control plane, semantic authority, policy boundary,
developer workflow, and explainable router.

Anchor trajectories:

* **Semantic authority first**: xCatalog, `ProximaRecord`, `ProximaType`/`ProximaValue`, WAL,
  MVCC/branch metadata, tenant/RLS, and retention are the product spine. Pgwire, REST/gRPC, Arrow
  Flight, SDKs, Iceberg REST, Delta/Hudi adapters, and modal APIs are views over that spine.
* **Managed-local simplicity before distributed ambition**: win the embedded/single-server
  developer path before claiming warehouse-scale MPP. Local startup, pgwire compatibility,
  predictable DDL/DML, Arrow export, Python ergonomics, and clear `EXPLAIN` output should feel
  boring and reliable.
* **Tiered HTAP as the native wedge**: use WAL plus native row/delta state for PostgreSQL-style
  freshness and constraints, PAX row-family blocks where mixed point/scan access is useful, and
  Parquet/Iceberg/Arrow publications for OLAP. This gives ProximaDB a native story that is
  stronger than "just another Parquet reader" while still exporting to open formats.
* **Open lakehouse as interoperability, not abdication**: Iceberg/Delta/Hudi/Parquet/ORC/CSV are
  cataloged publications, imported snapshots, federated reads, or explicit external authorities.
  They should never silently replace ProximaDB's hot record/log/catalog authority for
  Proxima-owned assets.
* **Compute routing over engine sprawl**: native Rust, DataFusion, Spark, Trino, Ray, and Flink are
  routes selected by xCatalog metadata, stats, freshness, policy, and cost. Add route evidence,
  rejection reasons, and benchmark gates before adding more engines.
* **Policy and governance as a default path**: routes that cannot enforce tenant/RLS/masking before
  data leaves the boundary must be rejected by default. This is a warehouse/cloud lesson as much as
  a security requirement.
* **Autonomous optimization only after observability**: auto-indexing, auto-projection, result
  caching, workload queues, and route recommendations must be driven by cataloged workload
  observations and benchmark gates, not static heuristics hidden inside handlers.
* **Branchable AI/data workflows as differentiation**: Redshift, BigQuery, and Snowflake won by
  removing operational work; ProximaDB's differentiator should be local-to-cloud continuity plus
  branchable data, agent state, evaluations, lineage, and policy-managed context.

Default path by phase:

* Phase 1 should prove semantic authority, pgwire/embedded adoption, DML correctness,
  predicate-aware vector search, local Arrow/DataFusion scans, and the TD-110 seams for future
  PostgreSQL-style constraint/isolation work.
* Phase 2 should prove the same contracts survive multi-machine storage, connector sidecars,
  branch manifests, and distributed compute delegation.
* Phase 3 should add warehouse inheritance only where catalog, policy, statistics, workload
  isolation, and route explanation are mature enough to make it operationally simple.

== Required Platform Planes

=== 1. Compatibility Plane

Purpose: meet developers and tools where they already are.

Required surfaces:

* PostgreSQL wire protocol for SQLAlchemy, JDBC, ODBC, psql, BI tools, dbt, and Calcite.
* Arrow Flight for high-throughput columnar data movement.
* REST/gRPC for lifecycle APIs that are awkward over SQL: branch management, model registry,
  artifact registration, long-running jobs, connector lifecycle, streaming subscriptions.
* Python/Rust SDKs for embedded, agentic, ML, AutoML, and local development workflows.
* SQL dialect compatibility gates: PostgreSQL core first, pgvector-compatible vector syntax,
  JSONB operations, limited catalog tables, then dbt/BI compatibility.

Pgwire is the common SQL contract, not the only API.

=== 2. xCatalog Control Plane

Purpose: the catalog is the platform.

xCatalog is the durable metadata authority. Collection, document, graph, vector, relational,
observability, stream, feature, model, agent, and open-table services are facades over cataloged
assets; they do not own parallel metadata truth. A "collection" is the API word for a cataloged
asset with a modality profile and storage/index policy. A "table", "graph", "stream",
"feature table", or "model registry entry" is the same control-plane shape with different
capabilities.

xCatalog must store:

* namespace/database/schema/table/collection/index/stream/branch;
* logical schema: ProximaType, constraints, schema variations, JSONB paths, vector dimensions;
* physical layout: engine, layout, file format, partitioning, clustering, compaction, cache,
  tiering, index placement;
* storage stack metadata: canonical WAL/log/manifest ranges, row/record layouts, LSM levels, PAX
  segment descriptors, columnar segments, open table publications, and projection repair sources;
* external catalog references: Hive/Glue/Unity/Polaris/Iceberg REST/Delta metadata and explicit
  external-authority/federation contracts;
* query stats: cardinality, histograms, vector distributions, graph degrees, event lag,
  feature freshness;
* governance: RLS, ACL, tenant isolation, masking, retention, legal hold, audit;
* lineage: source, transformations, connector cursors, model training runs, feature versions,
  branch ancestry, agent executions;
* AI assets: features, experiments, runs, metrics, artifacts, registered models, aliases/stages,
  prompts, tools, evaluations, deployments;
* streaming assets: topics, shards, partitions, offsets, watermarks, consumer groups, dead-letter
  queues, exactly-once/idempotency metadata;
* branch metadata: parent, snapshot timestamp, WAL range, schema mode, masking policy, TTL,
  merge status.
* schema registry metadata: subject/name, version, compatibility mode, canonical `ProximaType`
  mapping, wire format, fingerprint, owner, lifecycle state, and references to assets that use it.

Expose catalog through:

* `information_schema` and selected `pg_catalog` compatibility tables;
* Proxima-specific SQL schemas such as `xcatalog.*`, `mlops.*`, `agent.*`, `stream.*`;
* REST/gRPC lifecycle APIs;
* Arrow schema metadata;
* Iceberg REST/Polaris-compatible facade for analytic tables where viable.

==== Collection Service Position

`CollectionService` should be kept as a compatibility and lifecycle facade while the product still
has vector/document collection APIs. It should create, alter, drop, describe, and list cataloged
assets by calling xCatalog and the DDL/lifecycle services. It may coordinate default storage
placement, index initialization, and projection bootstrap, but xCatalog remains authoritative for
the resulting metadata.

Do not add new durable metadata fields to `CollectionService` unless they are persisted in
xCatalog in the same transaction or have a clear migration issue attached. Long term, the service
should become either:

* a thin alias over record/table lifecycle APIs for backwards compatibility; or
* a generalized `AssetLifecycleService` / `CatalogLifecycleService` if the name becomes misleading.

==== Naming Strategy

Use a single catalog naming strategy across all modalities:

[source,text]
----
catalog.namespace.asset_name
catalog.namespace.asset_name@branch
catalog.namespace.asset_name#snapshot
----

The canonical internal key is `TableIdentifier`-style namespace plus asset name, backed by a
stable catalog asset id. Surface-specific names are aliases:

* vector/document `collection` -> catalog asset with vector/document capability;
* graph -> catalog asset with node/edge profile and graph projections;
* observability dataset -> catalog asset with log/metric/trace/profile profiles;
* stream/topic -> catalog asset with append-only/event profile and offsets;
* feature table -> catalog asset with feature freshness and serving metadata;
* MLflow experiment/model -> catalog asset under `mlops.*`;
* Iceberg/Delta/Hudi table -> publication, import, projection, or external-authority asset.

Renames update catalog aliases and history. They must not rewrite record identity, WAL lineage,
branch ancestry, model lineage, or projection ownership.

==== Required xCatalog Expansions

The current catalog shape must grow in these directions before it can be the single metadata plane:

* `assets`: stable asset id, namespace/name, modality capabilities, lifecycle state, owner, aliases,
  branch/snapshot visibility, and supported-surface status.
* `schemas` and `schema_versions`: `ProximaType` fields, constraints, defaults, generated columns,
  compatibility policy, fingerprints, and source registry references.
* `schema_variations`: document/entity/open-shape structural variations, JSON paths, observed
  optionality, promotion policy, and validation status.
* `storage_layouts`: authority mode, layout kind, engine, physical format, PAX/row/columnar
  options, partitioning, clustering, tiering, compaction, retention, and repair source.
* `pax_segments` / `segment_stats`: segment location, block stats, tenant/time min-max,
  column stats, MVCC bounds, checksum, freshness, and projection lineage.
* `indexes` and `projections`: HNSW/IVF/PQ, JSON path, full-text, graph topology, time-series,
  rollup, materialized view, rebuild policy, invalidation policy, and benchmark/support status.
* `external_mappings`: Iceberg/Delta/Hudi/Hive/Glue/Unity/Polaris references, snapshot semantics,
  ownership mode, type mapping, policy boundary, write/refresh mode, and consistency limits.
* `streams`: topics, partitions/shards, offsets, watermarks, consumer groups, schema subjects,
  idempotency keys, dead-letter policy, lag, and CDC publication state.
* `mlops_assets`: experiments, runs, model versions, artifacts, signatures, aliases/stages,
  deployments, evaluations, drift monitors, feature freshness, predictions, labels, and feedback.
* `lineage_policy_audit`: source/transform/model/agent lineage, tenant/RLS policy, masking,
  retention, legal hold, audit events, and branch ancestry.

==== Schema Registry Interoperability

Confluent Schema Registry, AWS Glue Schema Registry, and similar registries are compatibility
adapters around xCatalog schema objects, not separate authorities inside ProximaDB.

Required behavior:

* Avro, JSON Schema, and Protobuf subjects map to xCatalog schema objects with version history and
  canonical `ProximaType` mappings.
* Compatibility modes (`BACKWARD`, `FORWARD`, `FULL`, transitive variants, and `NONE`) map to
  xCatalog schema evolution policies.
* Kafka/Flink/Kinesis connectors record subject, version, fingerprint, source topic, target asset,
  cursor/offset, watermark, and dead-letter policy in xCatalog.
* Glue-style databases, tables, partitions, classifiers, crawlers, and schema registry entries map
  to external catalog references or imported schema variations with explicit ownership.
* Schema inference may propose variations, but committed schema changes are catalog mutations and
  must pass the same policy/evolution checks as SQL, REST, gRPC, Arrow Flight, SDK, and embedded
  writes.

==== MLOps And MLflow Catalog Objects

MLflow compatibility should be implemented as an MLOps facade over xCatalog objects plus canonical
records/artifacts:

* experiments, runs, params, metrics, tags, artifacts, model versions, aliases/stages, signatures,
  environments, prompts, evaluations, deployments, labels, feedback, and drift monitors are
  cataloged assets or child metadata under `mlops.*`;
* metric time series, prediction logs, evaluation rows, feature values, and feedback are canonical
  records with retention and lineage metadata;
* large artifacts live in object storage or external artifact repositories with xCatalog location,
  checksum, policy, and lineage references;
* model registry transitions are catalog transactions with policy checks, audit entries, and branch
  awareness;
* MLflow REST/API compatibility is an adapter. It must not create a second model registry or
  experiment metadata store that bypasses xCatalog.

=== 3. Storage Plane

Purpose: separate logical schema from physical layout.

Required layouts:

* **Record/row hot layout**: OLTP row/delta state, agent memory, checkpoint, metadata, online
  features, and constraint-sensitive writes.
* **Hybrid PAX layout**: optional mixed OLTP/OLAP local serving and selective scans.
* **Columnar layout**: Parquet/Iceberg/Arrow snapshots for analytics, offline ML, and
  DataFusion/Spark/Trino reads.
* **Avro row interchange**: streaming and schema-evolution-friendly row payloads.
* **Event log layout**: append-only streams for CDC, audit, agent replay, MLOps lineage.
* **Graph topology layout**: CSR/COO adjacency and property projections.
* **Vector index layout**: predicate-aware HNSW and other ANN fragments with cataloged build
  parameters and data/version linkage.
* **External table layout**: Iceberg/Delta/Hudi publication and federation.

==== Native Context Format

Parquet, Avro, Iceberg, Delta, and Hudi are table/file formats or table metadata layers. They are
excellent for interoperability but weak as the only internal representation for low-latency,
high-frequency, multi-modal state:

* Parquet is immutable columnar storage; updates require rewrite/delta machinery.
* Avro is excellent row serialization and streaming interchange but not an indexed database.
* Iceberg/Delta/Hudi provide ACID/time travel/schema evolution over lake files but are optimized
  around analytical tables, not vector indexes, graph adjacency, agent checkpoints, or
  branch-per-developer hot state.

ProximaDB should define a native **Proxima Context Segment** format:

* append-friendly record deltas for hot writes;
* PAX/columnar materialized segments for scans;
* embedded min/max/bloom/vector/JSONB path statistics;
* vector index fragment references bound to record versions;
* graph topology delta references;
* branch-aware manifests with copy-on-write ancestry;
* exportable Parquet/Avro views and Iceberg/Delta publication.

The native format is the moat for context workloads. Open formats remain interoperability
surfaces.

==== Research-Grounded Storage Stance

The current paper review in
link:RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc[RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14]
sharpens the storage-plane rule:

* **Canonical durability is stacked, not isolated.** Records, types, catalog metadata, WAL/log/manifest,
  tenant/RLS, version/time, provenance, and retention rules are shared across relational, document,
  graph, vector, observability, SKS/entity, agent, and event workloads.
* **Physical specialization is mandatory.** LSM levels, PAX, columnar segments, adjacency tables,
  CSR/COO, GraphAr-style lake projections, HNSW/IVF/PQ/DiskANN-style ANN fragments, time-series
  compression blocks, trace indexes, and event streams are valid storage/index families when they are
  cataloged and rebuildable from canonical truth.
* **Open lake formats are publication and analytic surfaces.** Parquet, Avro, Iceberg, Delta, and
  Hudi are important interoperability targets, but they should not replace the native hot-state format
  for low-latency mutable context, graph traversal, ANN freshness, branches, and agent checkpoints.
* **No modality creates a hidden source of truth.** `DocumentService`, graph services, observability
  services, vector indexes, SKS/entity services, and protocol handlers may own facade behavior and
  projection maintenance, but durable semantics flow through `ProximaRecord`/`ProximaType`, xCatalog,
  WAL/log/manifest, and policy contracts.
* **Every default projection needs evidence.** The planner may auto-materialize JSON path indexes,
  columnar variation projections, CSR/COO, vector index fragments, time-series rollups, or trace
  assembly indexes only when catalog statistics, workload observations, and benchmarks justify the
  freshness and rebuild cost.

=== 4. Compute and Execution Plane

Purpose: route work transparently across engines.

Compute targets:

* **Native Rust / Volcano**: low-latency OLTP, constraint-sensitive DML, vector serving, graph
  traversal, event append, embedded.
* **DataFusion**: local and server-side vectorized SQL/Arrow/Parquet execution over cataloged
  snapshots and explicit delta-union routes.
* **Spark**: large offline feature engineering, lakehouse reads/writes, training datasets.
* **Trino**: federated SQL and BI across ProximaDB, warehouses, and lake tables.
* **Ray**: Python-native distributed ML, feature processing, AutoML, batch inference, model
  tuning, and agent/eval workloads.
* **Flink**: stateful stream processing, event-time joins, watermarks, exactly-once pipelines.
* **Kafka/Kinesis/Event Hubs/PubSub**: stream ingestion and fan-out, not the internal catalog.
* **Warehouse adapters**: Redshift, BigQuery, Snowflake, Synapse for federation/export.

Planner obligations:

* choose engine based on query shape, data volume, freshness, latency budget, cost, locality,
  governance, and format;
* push predicates/vector filters/JSONB paths/projections to storage;
* explain engine selection in `EXPLAIN`;
* keep results deterministic under branch, time travel, and RLS policies;
* expose fallback when a target engine lacks capability.

=== 5. Streaming and Ingestion Plane

Purpose: cover real-time data movement and CDC without becoming brittle ETL glue.

Required primitives:

* source connectors: Postgres CDC, Kafka, Kinesis, files/object storage, webhooks first;
* sink connectors: Kafka, object storage, webhooks, warehouse export;
* connector state in xCatalog: offsets, cursors, watermarks, lag, schema version, drift events;
* event-time and processing-time fields in ProximaRecord;
* idempotency keys and exactly-once where supported by source/target;
* dead-letter streams and replay;
* schema registry integration for Avro/JSON/Protobuf payloads;
* Flink integration for advanced stateful streaming and stream/batch SQL;
* CDC out from ProximaDB event log for downstream systems.

=== 6. Transformation and Semantic Plane

Purpose: cover dbt-like transformations, contracts, testing, metrics, and lineage.

Required primitives:

* SQL models over pgwire;
* model contracts and schema tests stored in xCatalog;
* seeds and snapshots;
* semantic metrics definitions and dimensions;
* lineage graph from sources to models to features to models/predictions;
* transformation run metadata, failures, durations, compiled SQL, and result stats;
* ability to execute transforms locally with DataFusion, then distributed via Spark/Trino/Ray.

=== 7. Agentic Plane

Purpose: make agent state durable, queryable, branchable, and governable.

Required objects:

* long-term memory: `(tenant, namespace, key) -> JSONB payload`, optional embeddings;
* checkpoint store: thread id, checkpoint namespace/id, parent, pending writes, replay;
* event streams: append-only tool/run/action events with causality IDs;
* trace store: prompt, tool, model, latency, token/cost, errors, evaluations;
* code/symbol store: documents, graph edges, embeddings, repository branch lineage;
* branch support: branch agent state with code branches, replay from checkpoint, compare outputs.

Do not create a hardcoded Rust/proto agent schema as source-of-truth. Use pgwire DDL plus xCatalog
metadata and SDK conveniences.

=== 8. ML, AutoML, and MLOps Plane

Purpose: cover the full data-oriented ML lifecycle.

Required capabilities:

* feature store: online/offline features, point-in-time correctness, freshness, lineage;
* experiment tracking: runs, params, metrics, artifacts, datasets, environment, code version;
* MLflow compatibility: import/export or tracking/registry adapter, model versions, aliases,
  stages, signatures, tags, annotations;
* model registry: model lifecycle, approval, deployment state, artifact URI, lineage;
* AutoML: AutoGluon/PyCaret orchestration in Python SDK; Ray Tune/Train later for distributed;
* batch inference: DataFusion/Ray/Spark execution, prediction tables, labels, feedback joins;
* online inference metadata: deployments, routes, latency, tokens/cost, errors, guardrails;
* monitoring: drift, data quality, model quality, bias/fairness hooks, rollback triggers;
* evaluation: offline eval sets, agent eval traces, prompt/model/tool comparisons.

SQL/pgwire is correct for feature tables, metrics, predictions, and metadata. SDK/REST/gRPC are
required for long-running jobs, artifacts, model promotion, and deployment lifecycle.

=== 9. Governance, Security, and Compliance Plane

Purpose: make governance a shared substrate, not per-surface middleware.

Required primitives:

* engine-level RLS and tenant filtering;
* column/path/embedding masking;
* policy inheritance from namespace/table/branch/model/stream;
* audit log for query, branch, connector, model, and agent operations;
* retention and legal hold for records, events, artifacts, and branches;
* external identity integration later: OIDC/SAML/IAM/workload identity;
* egress controls for AI tools, external connectors, and model endpoints.

== Phasewise Roadmap

=== Phase 0: Anchor and Guardrails

Goal: prevent churn before implementation accelerates.

Deliverables:

* Adopt this architecture anchor in AGENTS/CLAUDE/GEMINI.
* Keep multi-modal overhaul spec and workspace refactor plan as hard constraints.
* Remove hardcoded agent schemas as source-of-truth.
* Define maturity labels for Supported/Beta/Experimental claims.
* Keep public API additions aligned across pgwire, REST, gRPC, Arrow Flight, and SDKs.

Exit criteria:

* Every new roadmap item can be mapped to a platform plane and phase.
* No new storage or protocol path bypasses xCatalog and ProximaRecord/ProximaType direction.

=== Phase 1: Single-Device Developer MVP

Goal: win developer engagement locally with relational + vector + schema catalog + pgwire,
covering OLTP and light OLAP mechanics on one machine.

Scope:

* Embedded and single-server mode.
* Pgwire DDL/DML/query for relational, JSONB, VECTOR(n), indexes, primary keys.
* xCatalog schema persistence for table, fields, JSONB paths, vector dimensions, engine/layout.
* Storage engine selection via SQL options: `storage_engine`, `layout`, `table_format`.
* Native Rust serving path for OLTP/vector lookups.
* DataFusion execution (pseudo-distributed worker seam) for scans, projection, filter, aggregate over Parquet and Object Storage.
* VIPER/Parquet import/export and Avro import/export for streaming-style records.
* Arrow Flight export/import for feature/training datasets.
* Python SDK DDL helpers for agentic and MLOps tables.
* Minimal branchable state: named snapshots, point-in-time restore, branch metadata in xCatalog.
* dbt smoke path through pgwire: models/tests/seeds against local server.

Critical foundations:

* ProximaRecord and ProximaType direction respected even if compatibility shims remain.
* xCatalog tables visible over pgwire.
* Write-ahead log is the branch/time-travel foundation.
* `EXPLAIN` includes storage engine and compute engine choices.

Non-goals:

* Distributed consensus.
* Full Iceberg/Delta implementation.
* Full MLflow tracking server replacement.
* Full Kafka/Flink production connector suite.

=== Phase 2: Multi-Machine Data Platform

Goal: extend the same contracts from local developer use to a small distributed data platform.

Scope:

* Disaggregated storage on object store or shared filesystem.
* Catalog service with HA metadata backend.
* Log/manifest service for snapshots, branches, recovery, and replication.
* Distributed query execution through Rust-native workers (e.g. DataFusion over object storage). Spark/Trino remain as supported external adapters, but are not the primary MPP strategy.
* Kafka/Kinesis ingestion sidecars with cataloged offsets/watermarks.
* Flink source/sink and table connector for stateful streaming pipelines.
* Ray dataset and training adapter for distributed Python ML/AutoML.
* Branch manager: copy-on-write branch manifests, TTL branches, masked branches, schema-only
  branches, branch diff, branch reset.
* CDC out from ProximaDB event log.
* Basic workload isolation and resource groups.

Critical sidecars:

* catalog sidecar;
* log/manifest sidecar;
* pgwire coordinator;
* Arrow Flight data plane;
* streaming connector sidecars;
* compute adapter sidecars for Spark/Trino/Ray/Flink;
* branch manager sidecar.

Exit criteria:

* One logical SQL query can route to native Rust or DataFusion locally and to distributed
  compute for larger scans without changing client code.
* Branch and restore work across at least relational, vector, JSONB, and event metadata.

=== Phase 3: Enterprise Warehouse and Global Database Inheritance

Goal: absorb proven advantages from Redshift, Spanner, and cloud warehouses without losing
ProximaDB's local-first and multi-modal identity.

Scope:

* Redshift-like materialized views, incremental refresh, result cache, workload queues, and
  federated query.
* Spanner-inspired MVCC with explicit commit timestamps, bounded-staleness reads, point-in-time
  reads, atomic schema/catalog changes, and HLC/uncertainty-aware transaction metadata.
* External federation to Redshift, BigQuery, Snowflake, Synapse, Spanner, Postgres, and object
  lake tables.
* Region/zone-aware placement and replication policies.
* Catalog-level failover and recovery runbooks.
* Stronger governance: audit, retention, masking, external identity, tenant isolation.

Exit criteria:

* Enterprise users can query across ProximaDB and cloud warehouses with cataloged lineage.
* Global consistency claims are bounded and explicit; no vague "globally consistent" marketing.

=== Phase 4: Full Multi-Modal Runtime

Goal: complete data modalities beyond relational/vector/document.

Scope:

* Graph projection and Cypher/GQL lowering into logical algebra.
* Event store with snapshots, replay, subscriptions, and audit queries.
* Time-series engine with ASOF joins, downsampling, retention, calendar/timezone correctness.
* Observability store for logs, metrics, traces, profiles, and service dependency graph.
* Geospatial and temporal indexing.
* Multimodal unstructured assets: images/audio/video/document chunks as metadata + object/blob
  references + embeddings + provenance.

== API Shape Rules

=== Pgwire/SQL

Use SQL for:

* schema/table/index/view/materialized view definitions;
* relational, JSONB, vector, feature, prediction, run metric, and lineage queries;
* catalog introspection;
* dbt/BI/SQLAlchemy/JDBC/ODBC/Calcite compatibility.

Do not force SQL to own:

* model artifact upload/download;
* long-running job lifecycle;
* streaming subscription lifecycle;
* branch environment orchestration;
* agent checkpoint/event ergonomic APIs;
* connector secret management.

=== REST/gRPC

Use REST/gRPC for:

* branch lifecycle and restore;
* connector create/update/pause/resume/status;
* ML model registry lifecycle and artifact references;
* AutoML/job orchestration;
* agent memory/checkpoint/event operations;
* policy/admin/governance lifecycle.

REST/gRPC should also expose rich data-plane commands when they improve ergonomics:
`InsertRecords`, `UpsertRecords`, `DocumentQuery`, `GraphTraverse`, `VectorSearch`,
`ExecuteSql`, `ExecuteLogicalPlan`, and `InsertArrowBatch` are valid API shapes. They
must remain adapters over the shared xCatalog/type/planner/write path rather than
protocol-owned semantics. A gRPC message or REST JSON body is parsed into
`ProximaValue`, `ProximaRecord`, Arrow batches, or a logical plan before policy,
schema, branch/time, WAL, and storage execution.

Mongo-like document commands, Gremlin/Cypher/PGQ graph commands, Neptune/Titan/
JanusGraph-style compatibility endpoints, and SDK/embedded helpers follow the same rule:
they provide ingress ergonomics and compatibility, not independent durable stores,
catalogs, RLS models, or WAL/recovery paths.

=== Arrow Flight

Use Arrow Flight for:

* bulk dataset export/import;
* training data exchange;
* high-throughput analytical scans;
* inter-engine data movement.

Arrow is the primary batch interchange and vectorized execution plane. Arrow schemas map
to `ProximaType`; Arrow arrays map to `ProximaValue` vectors, canonical records, or
cataloged columnar projections. Large pandas/numpy/embedded inserts should prefer Arrow
batch ingress, but ownership, schema evolution, tenant/RLS, branch/time, and recovery
semantics still come from xCatalog plus WAL/log/manifest.

=== SDKs

Use SDKs for:

* ergonomic embedded operation;
* schema/DDL helpers;
* LangGraph/Victor/agent adapters;
* MLflow/AutoGluon/PyCaret/Ray adapters;
* branch-aware developer workflows.

== Foundational Shapes That Must Not Churn

These shapes should be treated as stable architectural axes:

* ProximaRecord envelope.
* ProximaType/ProximaValue.
* xCatalog as source of truth.
* Logical schema separate from physical layout.
* Pgwire as SQL compatibility plane.
* Arrow as data interchange plane.
* REST/gRPC as lifecycle plane.
* WAL/log/manifest as recovery, branch, and CDC foundation.
* Native Context Segment for hot multi-modal state.
* Parquet/Avro/Iceberg/Delta as interoperability, not the internal ceiling.
* Branching as a core data-plane primitive.
* Compute adapters as sidecars behind a common planning contract.
* Governance enforced at engine/catalog level.
