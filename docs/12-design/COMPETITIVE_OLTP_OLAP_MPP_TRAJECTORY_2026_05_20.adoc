== Purpose

This document translates the competitive architecture review of PostgreSQL/Oracle, Exadata,
Teradata, Netezza, Redshift, Spark, Impala, Presto/Trino, Vertica, ClickHouse, Snowflake,
BigQuery, and adjacent systems into ProximaDB implementation direction.

It is not a new durability ADR. It refines how existing accepted mandates should be implemented:

* `roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc`
* `docs/12-design/RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc`
* `docs/12-design/RELATIONAL_STORAGE_FORMAT_AND_INTEROPERABILITY_2026_05_19.adoc`
* `docs/12-design/RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20.adoc`
* `docs/12-design/adr/ADR-009-schema-modes-and-proximarecord-surfaces.adoc`
* `docs/12-design/adr/ADR-010-pax-block-format.adoc`

The core conclusion: ProximaDB should combine the best proven design choices without copying any
single warehouse, query engine, or OLTP database. The product shape is a semantic data and AI
platform with one record/type/catalog/policy spine, many physical layouts, and workload-aware
compute routing.

== Market Lesson To Internalize

Hadoop, Vertica, Netezza, Greenplum, VoltDB, Trino/Presto, and Spark each proved durable technical
ideas, but the largest cloud warehouse successes won on product shape as much as execution shape.
The split/file reader model survived because it is a useful physical contract over immutable files
and object storage. It is not, by itself, the warehouse product.

[cols="1,2,3"]
|===
| Lesson | What survived | ProximaDB implication

| Hadoop and Hive
| Parallel split planning, schema-on-read, object/file-scale batch processing, ORC/Parquet-style
columnar files
| Keep split readers and open table compatibility, but avoid operational stack complexity becoming
the user experience.

| Vertica, Netezza, Greenplum, Teradata
| MPP, columnar/projection design, distribution keys, pruning, function shipping, workload queues
| Make placement, projections, skew, pushdown, and workload class cataloged and explainable rather
than hidden per-engine tuning.

| Trino/Presto and Spark
| Connector split APIs, broad federation, large-scale batch execution, Arrow/Parquet/lakehouse
interoperability
| Treat external compute as delegated interoperability, not the primary Proxima-owned MPP route.
Keep writes, policy, record identity, and catalog authority inside ProximaDB unless an asset is
explicitly external-authoritative. Build the native MPP path around DataFusion/Rust workers first.

| Redshift, BigQuery, Snowflake
| Managed operations, storage/compute separation, elastic scheduling, SQL-first adoption,
governance, integrated metadata, workload isolation
| Optimize for low operational burden, strong defaults, route explanation, policy enforcement, and
supportable maturity labels before broadening claims.

| Delta, Iceberg, Hudi
| Transaction logs, snapshots, manifests, schema/partition evolution, time travel, delete/update
metadata over immutable data files
| Use open table formats as publications, imports, federated reads, and explicit external
authorities. Do not confuse their table logs with ProximaDB's canonical hot WAL/record authority.
|===

Therefore, ProximaDB should not frame success as "better compute over Parquet." The stronger
trajectory is "semantic authority plus Rust-native open compute": a product where xCatalog,
canonical records, policy, freshness, lineage, and route selection make native storage, PAX,
Arrow/DataFusion, Iceberg/Delta/Hudi, Spark, and Trino feel like one governed system while keeping
Proxima-owned MPP execution in Rust by default.

== Competitive Design Principles To Adopt

[cols="1,2,3,3"]
|===
| Competitive family | Proven design choice | Why it exists | ProximaDB adoption

| PostgreSQL / Oracle OLTP
| WAL, MVCC, constraints, indexes, stable transaction semantics
| Correctness and operational trust dominate single-row and small-transaction workloads.
| Keep WAL, record identity, versioning, constraints, and policy below every protocol facade.
Do not let pgwire, REST, Arrow Flight, SDKs, or modality APIs own semantics.

| Exadata / Netezza
| Function shipping and predicate/projection pushdown near storage
| Moving fewer rows and columns is more important than raw scan bandwidth.
| Push tenant, time, column, JSON path, graph edge, observability, and vector predicates into PAX
blocks, ANN fragments, topology projections, and open-format split planning.

| Teradata / Redshift
| Shared-nothing MPP with distribution keys, slices/AMPs, workload management
| Parallelism works only when data placement, skew, and concurrency are explicit.
| xCatalog must record partition keys, distribution strategy, skew stats, placement, workload class,
and queue/slot policy. The planner must explain when data movement is required.

| Vertica / ClickHouse
| Columnar layout, projections, compression, vectorized execution, late materialization
| Analytical performance comes from reading fewer bytes and processing column batches.
| Make PAX/columnar projections optimizer-visible. Build Arrow/DataFusion scan paths with pruning,
late materialization, vectorized operators, spill, and projection freshness metadata.

| Spark
| Fault-tolerant distributed batch execution over external/object storage
| Large transforms benefit from replayable stages.
| **Course Correction:** Build Rust-native MPP (Spark-like distributed execution) using DataFusion, outcompeting Spark/Trino on efficiency while removing JVM overhead. Spark remains a supported external option, but the primary distributed execution is Rust-native.

| Impala / Trino
| Coordinator-worker SQL, connector split planning, pushdown contracts
| Open query engines scale when connectors expose splits, statistics, and predicates clearly.
| Expose ProximaDB through Iceberg REST, Arrow Flight tickets, and split metadata. Keep
`ProximaRecord`, xCatalog, WAL, and policy as the semantic authority.

| Snowflake / BigQuery
| Storage/compute separation, managed capacity, elastic scheduling, shared data plane
| Operational simplicity and independent scaling matter at cloud scale.
| Adopt disaggregation incrementally: native embedded/single-node first, then DataFusion and
external compute routes, then distributed control and compute capacity management.
|===

== Design Knobs

The following knobs must be cataloged, planner-visible, and explainable. They should not be hidden
inside protocol handlers or one-off engine options.

[cols="1,2,3"]
|===
| Knob | Values | Design role

| `authority_mode`
| `ProximaAuthoritative`, `ExternalAuthoritative`, `ImportedSnapshot`, `ExportedProjection`,
`FederatedRead`
| Determines who owns writes, snapshots, repair source, policy boundary, and recovery.

| `workload_profile`
| `Oltp`, `Olap`, `Htap`, `Vector`, `Document`, `Graph`, `Observability`, `Event`, `Mixed`
| Drives default execution route, layout choice, concurrency model, and benchmark profile.

| `storage_specialization`
| `PaxRowFamily`, `PaxOltp`, `PaxOlap`, `ColumnarAnalytics`, `VectorAnn`, `DocumentJson`,
`GraphTopology`, `ObservabilityTimeSeries`, `ExternalOpenTable`, `LsmWriteOptimized`
| Defines physical access-method families without changing record semantics.

| `freshness_sla`
| `Synchronous`, `BoundedAsync`, `StaleOk`, `RebuildOnDemand`
| Controls whether projections must be updated inline, queued, or rebuilt from WAL/storage.

| `compute_route`
| `Native`, `DataFusionLocal`, `DataFusionDistributed`, `PolarsLocal`, `Spark`, `Trino`, `Ray`,
`Flink`, `ExternalDelegated`
| Selects the execution engine while preserving ProximaDB ownership of catalog, policy, and commits.

| `partitioning`
| tenant, hash key, range key, time, vector model, graph locality, hot/cold tier
| Determines locality, pruning, skew, and shuffle pressure.

| `isolation_profile`
| read committed, snapshot, serializable, event replay, external snapshot
| Determines visibility, version retention, and retry/idempotency requirements.

| `policy_boundary`
| engine-enforced, connector-enforced, external-policy, unsupported
| Determines whether a route is safe for tenant/RLS data. Unsafe routes must be rejected, not
silently allowed.
|===

== xCatalog Planner Metadata Contract

The implementation anchor for planner metadata is `crates/control/proximadb-catalog/src/lib.rs`.
Generated code should extend these catalog concepts before adding handler-local booleans, ad hoc
string properties, or storage-private route decisions.

Required table-level planner fields:

[cols="1,2,3"]
|===
| Field | Current implementation type | Contract

| workload profile
| `CatalogWorkloadProfile`
| Describes intended route class: `Oltp`, `Olap`, `Htap`, `Vector`, `Document`, `Graph`,
`Observability`, or `Mixed`.

| storage specialization
| `CatalogStorageSpecialization`
| Selects the primary physical/access-method family: PAX row family, PAX OLTP/OLAP,
LSM-write-optimized, columnar analytics, vector ANN, document JSON, graph topology, observability
time series, external open table, or generic relational.

| authority mode
| `CatalogAuthorityMode`
| States who owns durable truth: Proxima-authoritative, external-authoritative, imported snapshot,
projection/publication, rebuildable projection, or federated read.

| physical format
| `CatalogPhysicalFormat`
| Names the physical interchange/layout format: native Proxima block, SST, Arrow, CSV, JSON, XML,
Avro, Parquet, ORC, Iceberg, Delta, Hudi, GraphAr, or external format.

| storage layouts
| `CatalogStorageLayout`
| Cataloged layout descriptors. Must carry enough metadata for authority, write mode, location,
partitioning, clustering, compaction, and repair decisions.

| projections
| `CatalogProjection`
| Cataloged rebuildable projections/access methods. Must carry freshness, rebuild, invalidation,
and policy-boundary metadata before becoming optimizer-visible.

| relational capabilities
| `RelationalCapabilities`
| Optional SQL semantics such as constraints, indexes, transaction profile, schema evolution, and
materialized views. These are capability gates, not marketing claims.

| statistics
| `CatalogTableStatistics` and `CatalogColumnStatistics`
| Row/byte/file counts, last analyzed time, min/max, nulls, distinct counts, and average sizes.
Route selection must degrade visibly when stats are absent or stale.
|===

Planner metadata rules:

* xCatalog values are the source of truth for route selection; SQL options and API parameters are
  requests that become catalog metadata only after validation.
* `properties: HashMap<String, String>` may hold transitional details, but any field that affects
  authority, policy, write semantics, freshness, or default routing must graduate to a typed catalog
  field or a documented typed sub-structure.
* A new enum variant is preferred over a magic string when behavior changes route selection,
  commit semantics, or policy boundaries.
* Statistics are advisory for cost, but authority mode, policy boundary, write capability, and
  snapshot freshness are hard guards.
* Missing stats must produce `unknown` estimates and lower route confidence in `EXPLAIN`; they must
  not silently authorize unsafe distributed or external routes.
* Catalog migrations must preserve old metadata with explicit defaulting rules and should update
  supported-surface docs when a field becomes user-visible.

Minimum metadata required before a path can be default-routable:

[source,text]
----
workload_profile
storage_specialization
authority_mode
policy_boundary
freshness_sla
write_mode/capability
snapshot/isolation profile
route maturity/support status
stats freshness or explicit unknown-stats behavior
----

== Router And Runtime Multiplexer Shape

ProximaDB should have a standalone route-selection boundary, but it must remain a control-plane
planner component, not a new semantic authority and not a per-row hot-loop dispatcher.

Recommended split:

[cols="1,3,3"]
|===
| Layer | Owns | Must not own

| Surface lowerers
| protocol syntax, request/session context, SQL/API/modal lowering into shared logical algebra
| storage choice, compute route, WAL/MVCC, policy truth

| Route planner
| xCatalog/statistics/policy/freshness lookup, candidate route generation, cost/guard evaluation,
selected route, rejected routes, `EXPLAIN`
| physical execution loops, protocol response formatting, record mutation semantics

| Runtime multiplexer
| coarse dispatch from a validated routed plan to a leaf executor: native, DataFusion, external
compute, vector, graph, document, observability, open-table commit
| route recomputation per row/batch, hidden fallback, catalog mutation rules

| Leaf executors/readers
| hot data-plane work for their access method/API: scans, ANN, graph traversal, Arrow batches,
source reads, commits through `TableRecordStore` or external commit protocol
| selecting themselves without a routed plan, bypassing policy/freshness guards
|===

The router should behave like a query optimizer and capability gate:

* Input: logical plan or write intent plus xCatalog asset metadata, stats, policy context, branch,
  snapshot, freshness, and session knobs.
* Output: immutable `RoutedPlan`/`RoutedExecutionPlan` with selected route, candidate routes,
  rejected routes, required guards, source-reader contract, write lane, projection freshness, and
  data-movement estimate.
* Execution: the runtime multiplexer dispatches once per plan or fragment. After that, leaf
  executors operate on typed plans, Arrow batches, `ProximaRecord` streams, or storage-native
  cursors without consulting the global router for each row.

Performance rules:

* Do route selection before execution and cache route fragments by asset id, schema version,
  policy version, branch/snapshot, stats epoch, freshness state, and relevant session knobs.
* Invalidate cached routes when xCatalog schema/layout/policy/stats/freshness/branch metadata
  changes.
* Keep dynamic dispatch at coarse boundaries: plan, fragment, split, or batch. Do not use stringly
  route lookup or protocol DTO conversion inside tight scan/vector/graph loops.
* Push predicates, projection, tenant/RLS, snapshot, and freshness decisions into leaf scan
  contracts so the multiplexer is not a row filter.
* Prefer typed enums and capability structs for route decisions; use trait objects only where a
  leaf implementation boundary is needed.
* A rejected route is a first-class outcome. The multiplexer must not silently fall back to a route
  that lacks policy, freshness, idempotency, or authority guards.

This gives ProximaDB the maintainability benefit of a standalone router while preserving the data
path shape used by successful systems: plan once, execute fragments/splits/batches directly, and
keep hot loops local to specialized readers/executors.

== Implementation Trajectory

=== Phase 1: Semantic spine and OLTP correctness

Goal: make the PostgreSQL/Oracle lesson real before broadening the warehouse story.

Deliverables:

* route relational/PAX/document/graph/observability writes through direct WAL/table-record writer;
* close prior visible versions on update/delete according to MVCC policy;
* enforce primary key, unique, check, and basic secondary-index capabilities below protocols;
* make tenant/RLS fields mandatory in scan/write boundaries;
* add cross-surface DML parity tests for pgwire, REST/gRPC, Arrow Flight, and embedded ingestion.

=== Phase 2: PAX/Arrow local HTAP

Goal: make the Exadata, Vertica, ClickHouse, and Redshift lessons visible on one machine.

Deliverables:

* PAX row-directory point lookup and column-stripe scan readers;
* block/stripe pruning on tenant, time, min/max, null counts, and selected user columns;
* Arrow `RecordBatch` sources for cataloged tables;
* DataFusion local scan, projection, filter, aggregate, join, and INSERT SELECT source reader;
* projection freshness tracking and `EXPLAIN` output.

=== Phase 3: Rust-Native MPP and Open Split Interoperability

Goal: Build a Rust-native distributed execution engine (starting via DataFusion pseudo-distributed seam) while making Trino, Impala, Spark, Snowflake, and BigQuery lessons interoperate without moving semantic authority out of ProximaDB.

Deliverables:

* Iceberg REST metadata that exposes ProximaDB splits with Arrow Flight tickets;
* split-level tenant/time/predicate pushdown metadata;
* Rust-native distributed worker nodes for Spark-like execution;
* external-authoritative commit registration in xCatalog;
* MPP smoke tests for native Rust distribution and Spark/Trino reads.

=== Phase 4: Autonomous optimization

Goal: reduce manual layout and route tuning while preserving explainability.

Deliverables:

* statistics-backed CBO over native/DataFusion/external routes;
* workload management classes for latency, throughput, background rebuilds, and tenant fairness;
* automatic projection recommendations for PAX, columnar, ANN, JSON, graph, and time-series paths;
* branch/snapshot-aware optimization and retention;
* benchmark gates for OLTP, OLAP, HTAP, and cross-modal workloads.

=== RL Planner Positioning

The existing `[query.rl_planner]` configuration (Thompson Sampling) MUST NOT run on the
query hot path. Thompson Sampling is a multi-armed bandit algorithm with an exploration phase
that intentionally selects suboptimal plans to gather reward signal. For production OLTP
queries with millisecond SLA requirements, exploration-phase choices produce SLA violations.

**Correct architecture for the RL planner (Phase 4):**

[cols="1,2,2"]
|===
| Layer | Role | Algorithm

| Query hot path
| Deterministic cost-based optimization using xCatalog statistics, selectivity estimates,
  freshness state, and policy guards. Emits `RoutedExecutionPlan` with EXPLAIN.
| Rule-based + statistics-backed CBO. No exploration. Deterministic given the same catalog state.

| AutoML background optimizer
| Observes query execution outcomes (latency, recall, recall@k, bytes read, CPU). Updates
  cost model parameters: selectivity multipliers, ANN freshness penalty, CSR vs. L1 scan
  crossover point, DataFusion vs. native crossover point.
| Thompson Sampling or Bayesian optimization over the cost model parameter space, not the
  query plan space. Runs asynchronously, never blocks query execution.

| Layout advisor
| Recommends PAX block size, projection rebuild schedules, props auto-promotion candidates,
  workload class changes, and partition key candidates based on observed access patterns.
| Workload profiling + rule-based recommendations. Outputs `ALTER TABLE` suggestions to operators.
|===

Literature basis: "Piece of CAKE: Adaptive Execution Engines via Microsecond-Scale Learning"
(arXiv:2602.04181) demonstrates that learning-based adaptation at DB latency budgets IS
achievable — but applies learning to execution *parameters* (buffer sizes, parallelism,
operator order), not to plan *selection* on the cold path. "Improving DBMS Scheduling
Decisions with Fine-grained Performance Prediction" (arXiv:2501.16256) shows the correct
pattern: ML improves cost model accuracy, deterministic CBO selects the plan.

This repositioning does not remove the RL planner; it constrains it to the correct scope
(background cost model tuning) and removes it from latency-sensitive plan selection.

== Default Enablement Gates

The trajectory should bias toward disabled, planned-only, or experimental paths until the control
plane can prove they are safe. This keeps implementation work from copying the shape of successful
systems without copying the operational discipline that made them successful.

[cols="1,2,3"]
|===
| Capability | May be merged when | May be default-enabled when

| New storage specialization
| xCatalog stores authority mode, layout kind, partitioning/clustering, stats surface, freshness,
repair source, and supported-surface status
| read/write paths enforce snapshot visibility, tenant/RLS policy, projection freshness, and at
least one focused benchmark gate

| New compute route
| route appears in `compute_route`, has `ExecutionGuard`s, rejected-route reasons, and
`EXPLAIN`/`RoutedExecutionPlan` or read-side `RoutedReadPlan` metadata
| route has policy-boundary enforcement, cost/freshness checks, failure behavior, and smoke tests
against a Proxima-owned table

| New open-format adapter
| xCatalog records external location, snapshot semantics, type mapping, lossy conversions, refresh
mode, repair source, and ownership mode
| connector rejects unsupported RLS/isolation cases and registers external snapshots or Proxima
publications consistently

| New projection or index
| projection metadata includes source record range, rebuild policy, invalidation policy, and
freshness watermark
| queries that require current data either update the projection synchronously, wait for freshness,
or reject stale projection routes

| New protocol/API surface
| surface lowers into shared algebra, xCatalog schemas, and `ProximaRecord`/`ProximaValue` records
| cross-surface parity tests prove the same write/read semantics through at least two facades

| Supported maturity claim
| docs identify owner, scope, limitations, and relevant feature flags
| validation matrix has a passing smoke or benchmark gate and supported-surface docs are updated
|===

Required `EXPLAIN` fields before a non-native route is default-enabled:

* selected `compute_route` and storage/projection path;
* authority mode and commit owner;
* policy boundary and whether tenant/RLS predicates were pushed down;
* source snapshot and target write mode;
* projection freshness or reason no projection was used;
* estimated rows/bytes and expected shuffle or data movement;
* rejected routes with concrete reasons.

== LLM Code-Generation Guardrails

Generated code should follow these alignment checks before implementation details are invented:

* Start from the active blueprint, not from a protocol handler or storage module that appears close
  to the failing test.
* Add metadata before behavior when the behavior depends on authority, freshness, policy, layout,
  route, or maturity.
* Add a route as a cataloged and explainable candidate before making it the default execution path.
* Add adapters at the edge. Do not let Arrow, Parquet, Iceberg, Delta, Hudi, pgwire, or SDK DTOs
  become the internal durable model.
* When a compatibility path is reused, name its retirement condition. Compatibility code should not
  become the silent target architecture.
* Prefer a planned-only result with explicit rejected-route reasons over a partial implementation
  that silently falls back to an unsafe route.

== Refactors Worth Doing

* Replace transitional `VectorOps` write ownership for non-vector tables with direct
`TableRecordStore` + canonical WAL.
* Make `ProximaRecord`/`ProximaType`/`ProximaValue` the internal contract in all new code paths.
* Extract reusable source-reader and projection-rebuild contracts from root service code.
* Add xCatalog route knobs and `EXPLAIN` metadata before adding more physical engines.
* Build policy-aware scan traits that every storage/projection reader must implement.

== Refactors Not Worth Doing Now

* Do not clone Spark, Trino, or Snowflake wholesale inside the root crate; build the Rust MPP engine
as cleanly separated DataFusion/Rust worker components.
* Do not put ProximaDB's hot durable core inside PostgreSQL, DuckDB, or another external RDBMS.
* Do not create separate durable systems for document, graph, observability, or vector semantics.
* Do not split every storage engine into its own crate until the record/log/catalog contracts are
stable and used by at least two consumers.
* Do not optimize for petabyte-scale MPP before embedded/single-node OLTP and local HTAP semantics
are correct.

== Open Decisions

files, and open-table snapshots?
* Should PAX segment freshness be synchronous for small OLTP tables and asynchronous for HTAP/OLAP
tables by default?
* What minimum `EXPLAIN` fields are required before external compute routes are allowed by default?
* Which benchmark gates become release-blocking for "supported" versus "beta" relational/warehouse
claims?
