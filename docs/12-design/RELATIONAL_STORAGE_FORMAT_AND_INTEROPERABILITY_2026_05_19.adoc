== Decision

ProximaDB relational storage MUST be shaped as a `ProximaRecord`/`ProximaType`/`ProximaValue`
system with xCatalog as the schema and capability authority. SQL/pgwire is a protocol facade over
that model. It MUST NOT define a protocol-specific row envelope, table catalog, transaction model,
or storage authority.

The relational hot path should converge on a tiered HTAP layout, not a single physical format:

* Layer 0: WAL / `CanonicalOperation::RecordUpsert` is the commit and replay authority.
* Layer 1: `ProximaRecord` is the semantic row/document/node/edge/span/event authority.
* Layer 2a: an OLTP row/delta tier provides low-latency point lookup, current-state reads,
  MVCC visibility, and primary-key/unique/check/foreign-key enforcement before commit.
* Layer 2b: PAX row-family blocks remain the internal HTAP candidate for row-directory access
  plus column stripes where a mixed point-and-scan layout is required.
* Layer 2c: Parquet/Iceberg/Arrow publications provide OLAP snapshots, open-format
  interoperability, and DataFusion/MPP scan surfaces. They are not the only write-path authority
  for PostgreSQL-style OLTP tables.
* Layer 3: pgwire, Arrow Flight, Iceberg REST, REST/gRPC, SDKs, and external table adapters expose
  views over the same cataloged records.

Legacy SST/LSM layouts may remain write-optimized access methods, especially for vector-heavy and
append-heavy workloads, but they must carry the shared identity, version, timestamp, tenant, and
tombstone metadata. They are not the target relational authority.

== Recommendation

Adopt the following shape for relational work:

1. Build `proximadb-relational` behavior on canonical `ProximaRecord` records, xCatalog table
   schemas, and shared logical plans.
2. Use WAL plus an OLTP row/delta store as the latency-sensitive relational commit/read tier for
   mutable PostgreSQL-style tables.
3. Use **Parquet/Iceberg** over decoupled `object_store` as the OLAP base/publication format for
   analytical snapshots, DataFusion/MPP scans, and external interoperability.
4. Continue evaluating PAX row-family as an internal HTAP layout for mutable relational tables that
   need both row-directory point access and column-stripe scans. Do not make PAX a hidden schema or
   durability authority; xCatalog/WAL/`ProximaRecord` remain authoritative.
5. Reserve specialized SST/HELIX/NOVA/VIPER/RAPTOR/SWIFT access paths for vector-heavy and
   write-optimized projections unless they explicitly implement the shared relational metadata,
   visibility, and constraint contracts.
6. Reserve SQL-visible internal columns with the double-underscore `__proxima_*` prefix. Do not
   make generic names such as `_deleted` or `_version` canonical.
7. Treat CSV, Avro, ORC, JSON, XML, Arrow IPC, Delta, Hudi, Hive, Glue, Unity,
   and Polaris as cataloged adapters, projections, or explicitly declared external authorities.

== Comparison With PostgreSQL Storage

PostgreSQL is the compatibility model for SQL behavior, not the physical storage blueprint.

[cols="2,3,3"]
|===
| Area | PostgreSQL heap and indexes | ProximaDB target shape

| Durable row authority
| Heap tuple pages; tuple headers carry MVCC fields; WAL replays page changes.
| WAL records plus `ProximaRecord`; PAX/SST/columnar layouts are record access methods or
projections over the same semantic envelope.

| MVCC
| Tuple versions use `xmin`, `xmax`, command ids, snapshots, visibility maps, and vacuum.
| Record versions use cataloged identity plus `valid_from_ns`, `valid_to_ns`, optional transaction
or branch snapshot fields, and tombstone flags. Compaction removes obsolete versions only after
retention and snapshot rules allow it.

| Row identity
| Physical `ctid` plus logical primary keys and indexes.
| Stable `oid`/record id, cataloged primary keys, optional row-directory hash, and rebuildable
physical locations. Physical offsets are never exposed as durable identity.

| Indexes
| B-tree, GiST, GIN, BRIN, hash, extensions.
| Primary/secondary indexes, vector ANN fragments, JSON path indexes, full-text indexes, graph
adjacency projections, time indexes, and zone-map/bloom pruning metadata, all cataloged as access
methods with freshness/rebuild rules.

| Storage orientation
| Row-first heap with separate indexes; columnar behavior comes from extensions or foreign tables.
| Tiered HTAP: WAL plus OLTP row/delta and indexes for point operations, optional PAX row-family
blocks for mixed point/scan workloads, and Parquet/Iceberg/Arrow snapshots for vectorized OLAP
scans and open-format publication.

| Catalog
| PostgreSQL system catalogs are the SQL metadata authority.
| xCatalog is the product-wide control plane for relational tables, collections, graphs,
observability datasets, projections, branches, schemas, policies, and external ownership.

| Extensions and modalities
| Extensions add types, operators, indexes, and FDWs around PostgreSQL's heap/catalog model.
| Vector, document, graph, observability, SKS/entity, and event surfaces are facades and projections
over the same record/catalog/log spine.

| External tables
| FDWs and table access methods can delegate reads/writes to external systems.
| External formats are cataloged with explicit ownership, snapshot/isolation, type mapping, RLS
boundary, write/refresh mode, repair source, and freshness watermark.
|===

The design intentionally borrows PostgreSQL's relational rigor: DDL, constraints, primary keys,
foreign keys, indexes, snapshots, and SQL metadata must be real when enabled. It does not copy
PostgreSQL's heap tuple format, system column names, or vacuum model as ProximaDB's internal
authority.

== PostgreSQL-Style OLTP Contract

PostgreSQL-compatible latency-sensitive workloads need stronger write-path semantics than
Parquet/Iceberg can provide directly. For mutable OLTP and HTAP tables:

* primary-key, unique, not-null, check, and foreign-key metadata lives in xCatalog;
* `DmlService`/`CatalogRow` validate values and compute constraint checks before `TableRecordStore`
  commits a mutation;
* primary-key and unique indexes must be current enough to reject duplicate commits;
* foreign-key checks initially target same-table/same-partition or catalog-declared local
  references. Cross-shard FKs, deferred constraints, and cascading actions require a transaction
  coordinator and are post-MVP until explicitly implemented;
* the native/Volcano route owns point DML, strong-freshness reads, row visibility, and constraint
  enforcement;
* DataFusion reads cataloged snapshots and, for fresh HTAP reads, an explicit base-plus-delta union
  with a visible freshness watermark. DataFusion does not become the write authority for mutable
  OLTP tables.

For single-node MVP the critical guarantees are ACID/MVCC semantics, not distributed CAP tradeoffs.
For distributed OLTP, transactional shards should prefer CP behavior for committed state; OLAP
projections may be asynchronous or stale only when `freshness_sla` and `authority_mode` make that
visible and route guards reject unsafe plans.

== Internal Columns

SQL users need optional introspection columns for debugging, replication, audit, and compatibility.
The reserved prefix is `__proxima_`.

[cols="2,2,4"]
|===
| SQL alias | Canonical source | Purpose

| `__proxima_oid`
| column id 0 / `oid`
| Stable record identity.

| `__proxima_tenant_id`
| column id 1 / `tenant_id`
| Engine-level tenant and RLS partition key.

| `__proxima_record_version`
| row version metadata
| Monotonic or snapshot-scoped record version used for optimistic concurrency and CDC ordering.

| `__proxima_created_at_ns`
| column id 2 / `created_at_ns`
| Insert timestamp in nanoseconds.

| `__proxima_updated_at_ns`
| column id 3 / `updated_at_ns`
| Last mutation timestamp in nanoseconds.

| `__proxima_valid_from_ns`
| column id 4 / `valid_from_ns`
| MVCC/bi-temporal lower bound.

| `__proxima_valid_to_ns`
| column id 5 / `valid_to_ns`
| MVCC/bi-temporal upper bound.

| `__proxima_actor`
| column id 6 / `actor`
| Write actor or principal.

| `__proxima_origin`
| column id 7 / `origin`
| Source system, pipeline, or protocol.

| `__proxima_deleted`
| row flags / tombstone state
| Derived visibility flag. DELETE writes a tombstone or closes the previous version; it does not
physically erase the record at commit time.

| `__proxima_branch_id`
| snapshot/branch metadata
| Branchable state and time-travel isolation.

| `__proxima_schema_version`
| xCatalog schema fingerprint
| Schema version used for coercion, evolution, and replay.
|===

Single-underscore names such as `_deleted` may be accepted as import/export aliases when an
external format already uses them, but they are not canonical ProximaDB internal columns. The
double-underscore prefix reduces collision risk with application columns and makes the namespace
explicit.

== MVCC And DML Semantics

Relational DML follows append/version semantics:

* `INSERT` writes a new `ProximaRecord` with identity, tenant, timestamps, schema fingerprint, and
  typed user columns.
* `UPSERT` writes a new version for the same logical identity and closes the prior visible version
  for the affected snapshot.
* `UPDATE` is an upsert of a new version plus retention-governed invalidation of the old version.
* `DELETE` writes a tombstone or closes the current version. Physical removal is deferred to
  compaction after snapshot, retention, CDC, and branch rules allow it.
* `SELECT` evaluates snapshot visibility before projection and before returning rows through
  pgwire, Arrow Flight, REST/gRPC, or open-format scans.

The row visibility predicate is conceptually:

[source,text]
----
tenant_id matches policy
AND valid_from_ns <= snapshot_time_ns
AND (valid_to_ns IS NULL OR snapshot_time_ns < valid_to_ns)
AND tombstone is not visible for the requested snapshot
AND branch/snapshot lineage includes the version
----

This makes SQL updates/deletes, vector freshness, graph edge mutation, document replacement, and
observability retention use one version model.

=== Canonical Table-Record Write API

SQL/pgwire, REST/gRPC record APIs, Arrow Flight batches, document/graph/vector facades, and embedded
writers must lower DML into a canonical table-record write boundary before WAL/storage. They must
not call `VectorOps` as the semantic owner of relational row writes.

Frontend ownership split:

[source,text]
----
SQL parser
  -> Parsed DML / CopyIntoPlan syntax shape, no catalog routing

DML analyzer / planner
  -> resolves xCatalog source/target metadata
  -> validates target capabilities and schema mapping
  -> asks TableWriteRouter for candidate paths
  -> returns RoutedExecutionPlan

DML/write executor
  -> executes selected path
  -> commits through TableRecordStore or open-format commit protocol
----

The parser may create syntax-level `CopyIntoPlan` objects for convenience, but it must not decide
native vs DataFusion vs Polars vs DuckDB vs external delegation. `DmlService` executes planned row
DML and table-record writes; it must not become the optimizer.

Target service shape:

[source,rust]
----
TableRecordStore::write_mutations(
    table_id,
    Vec<TableRecordMutation { kind, record: ProximaRecord }>,
    WriteContext { tenant, snapshot, actor, policy }
)

TableRecordStore::get_by_key(table_id, key, Snapshot)
TableRecordStore::scan(table_id, projection, predicate, Snapshot)
----

Concrete contract shape:

[source,rust]
----
enum TableRecordMutationKind {
    Insert,
    Upsert,
    Update,
    Delete,
    OverwriteSnapshot,
    ReplacePartitions,
    Merge,
}

struct TableRecordMutation {
    kind: TableRecordMutationKind,
    record: ProximaRecord,
    conflict_policy: ConflictPolicy,
    expected_version: Option<u64>,
}

struct TableWriteContext {
    tenant_id: Option<String>,
    actor: Option<String>,
    snapshot_id: Option<String>,
    branch: Option<String>,
    write_mode: WriteMode,
    isolation: IsolationLevel,
    rls_policy_id: Option<String>,
    idempotency_key: Option<String>,
}

enum WriteMode {
    Append,
    InsertOnly,
    Upsert,
    OverwriteTable,
    ReplacePartitions(Vec<PartitionKey>),
    Merge,
}
----

Rules:

* `TableRecordStore` is the canonical service-layer contract for row/record mutation semantics.
* DML routing is driven by xCatalog table metadata: workload profile, storage specialization,
  authority mode, physical layout, and projection freshness.
* `VectorOps` is a facade for vector-bearing records and ANN/search behavior. It may call the
  table-record store after convergence, but SQL DML must not depend on vector-specific duplicate
  checks, dimension validation, tombstone heuristics, or collection terminology.
* During migration, `VectorOpsTableRecordStore` may adapt `TableRecordStore` calls into existing
  `VectorOps::insert_records_with_tenant_context` and point lookup paths. This adapter is a
  compatibility bridge, not an authority boundary.
* `VectorAnn`, vector workload, and legacy SST/LSM-specialized tables may route through the
  compatibility adapter until they are migrated. PAX/OLTP/OLAP/HTAP/generic relational tables route
  through the canonical table-record branch.
* Prior-version closure for `UPSERT`/`UPDATE` belongs in the table-record writer/WAL mutation
  layer, because it is a record-version invariant shared by SQL, document, graph, vector, and
  observability facades.
* The eventual direct implementation writes `RecordMutation` entries to WAL and routes physical
  layout decisions through xCatalog table metadata (`PAX`, `OLTP`, `OLAP`, `HTAP`, SST/LSM,
  columnar, ANN, JSON, topology, observability, external table projection).
* Bulk write operations are planned as table writes first, then split into WAL append, PAX block
  construction, open-format commits, and projection refresh tasks.
* A write is successful only after the authoritative layer records the catalog/snapshot/WAL commit.
  Rebuildable projections may lag if xCatalog records their freshness watermark.

=== INSERT SELECT, INSERT OVERWRITE, And Compute Engine Routing

`INSERT INTO target SELECT ... FROM source` and `INSERT OVERWRITE target SELECT ... FROM source`
are table-to-table data movement operations, not protocol-specific shortcuts. The SQL frontend
must lower them into a logical copy/write plan:

[source,text]
----
ReadPlan(source tables/external files/snapshots)
  -> LogicalPlan(Filter/Project/Join/Aggregate/Vector/Graph/Document operators)
  -> WritePlan(target table, mode: append | overwrite | replace_partitions | merge)
  -> TableRecordStore or open-format writer
----

SQL support phases:

[cols="1,2,2"]
|===
| Phase | Statements | Notes

| P0
| `INSERT INTO t VALUES (...)`, `UPSERT`, primary-key `UPDATE`, primary-key `DELETE`
| Already lowered through catalog row validation and `TableRecordStore`.

| P1
| `INSERT INTO target SELECT ... FROM source`
| Append/upsert from an internal table, external file, or open-table source. Requires source
scan, projection, target validation, and batched table-record writes.

| P2
| `INSERT OVERWRITE target SELECT ...`
| Snapshot replacement for full table or cataloged partitions. Requires atomic catalog commit and
old snapshot retention.

| P3
| `CREATE TABLE target AS SELECT ...`, `CREATE TABLE target WITH (...) AS SELECT ...`
| DDL plus write plan. Target schema is explicit or inferred from the source logical plan and then
registered in xCatalog before data commit.

| P4
| `MERGE INTO target USING source ...`
| Upsert/update/delete by join key with explicit conflict policy and prior-version closure.
|===

Write semantics:

* `INSERT INTO ... SELECT` appends or upserts according to the target table capability and conflict
  policy.
* `INSERT OVERWRITE ... SELECT` creates a new target snapshot/version for the affected table or
  partitions. For Proxima-authoritative tables this is a WAL/catalog transaction; for Iceberg,
  Delta, Hudi, or external-authoritative tables it is delegated to that format's commit protocol
  through an xCatalog ownership contract.
* Overwrite must not physically erase old files/blocks before snapshot, branch, CDC, retention, and
  recovery rules allow it.
* Source and target type conversion goes through xCatalog `ProximaType`/`ProximaValue` mappings;
  engine-native types are adapter details.
* `INSERT OVERWRITE` against external-authoritative Iceberg/Delta/Hudi tables must use the external
  table's atomic commit protocol. Against Proxima-authoritative tables it creates a ProximaDB
  snapshot and marks prior versions invisible through MVCC/catalog metadata.
* `INSERT OVERWRITE` against mutable OLTP tables is allowed only when the table capability permits
  snapshot/table replacement. Default OLTP tables should reject full overwrite unless the statement
  targets explicit partitions or a staging branch.

Compute engine strategy:

[cols="1,2,2"]
|===
| Engine | Primary role | Boundary

| Native ProximaDB planner/writer
| OLTP point writes, MVCC closure, WAL authority, PAX row-family writes, vector/document/graph
mutation semantics
| Always authoritative for Proxima-owned tables.

| DataFusion
| Default Rust SQL/Arrow execution engine for relational scans, joins, projections, aggregates,
external Parquet/CSV/JSON/Arrow reads, and distributed query plans.
| Execution engine only. It does not own ProximaDB WAL, catalog, RLS, or record semantics.

| Polars
| Fast local/pseudo-distributed dataframe execution for batch transforms, expression-heavy ETL, and
single-node analytical materialization.
| Optional execution backend selected by cost/profile. It is not the distributed SQL authority.

| DuckDB
| Compatibility/interop engine for DuckDB users, local analytics, SQL dialect fallback, and external
format smoke/conformance.
| Optional adapter. Do not make DuckDB the internal semantic owner of table writes.

| Spark/Flink/Trino
| External engines through Iceberg REST, Arrow Flight, JDBC/pgwire, and open-table formats.
| Connectors/federated compute, not embedded hot-state authority.
|===

Cost-based routing should choose between native, DataFusion, Polars, DuckDB, or external engine
delegation using:

* target/source authority mode and format;
* table size, partition count, and snapshot freshness;
* workload profile (`OLTP`, `OLAP`, `HTAP`, vector/document/graph/observability);
* operator coverage and pushdown ability;
* write mode (`append`, `overwrite`, `merge`, `replace_partitions`);
* distribution mode and available executors;
* data movement cost across Arrow batches/files/network;
* RLS/policy enforcement location;
* expected latency, spill, memory, and retry behavior.

The competitive trajectory makes these route inputs mandatory xCatalog/planner dimensions rather
than informal engine hints:

[cols="1,2,3"]
|===
| xCatalog / planner dimension | Required examples | Why it matters

| `authority_mode`
| Proxima-authoritative, external-authoritative, imported snapshot, exported projection,
federated read
| Prevents Spark/Trino/DuckDB/DataFusion from accidentally becoming write or recovery authority
for Proxima-owned records.

| `workload_profile`
| OLTP, OLAP, HTAP, vector, document, graph, observability, event, mixed
| Separates point-write correctness, selective HTAP, analytical scans, and modal access-method
needs without adding protocol-specific behavior.

| `storage_specialization`
| PAX row-family, PAX OLTP, PAX OLAP, columnar analytics, vector ANN, document JSON, graph topology,
observability time-series, external open table, legacy LSM
| Selects physical access methods while preserving `ProximaRecord` as semantic authority.

| `freshness_sla`
| synchronous, bounded async, stale-ok, rebuild-on-demand
| Makes projection freshness explicit for PAX stripes, ANN fragments, JSON indexes, graph topology,
time rollups, and open-format manifests.

| `compute_route`
| native, DataFusion local/distributed, Spark, Trino, Ray, Flink, external delegated
| Lets `EXPLAIN` show why execution stays native, moves to Arrow/DataFusion, or delegates to MPP.

| `partitioning`
| tenant, hash key, range key, time, vector model, graph locality, hot/cold tier
| Controls pruning, skew, shuffle pressure, and distributed ownership.

| `isolation_profile`
| read committed, snapshot, serializable, event replay, external snapshot
| Ties query visibility, overwrite semantics, branch behavior, and retries to explicit metadata.

| `policy_boundary`
| engine-enforced, connector-enforced, external-policy, unsupported
| Rejects unsafe routes when tenant/RLS/masking cannot be enforced before data leaves ProximaDB.
|===

Default recommendation:

* Use native `TableRecordStore` for OLTP DML and Proxima-owned mutation semantics.
* Use DataFusion as the default Arrow SQL execution substrate, including distributed execution work.
* Use Polars for local/pseudo-distributed dataframe-style transforms when it wins on cost and
operator coverage.
* Use DuckDB as an optional compatibility and conformance path, especially for external file/table
interop, not as ProximaDB's internal store.
* Do not build a Spark clone first. DataFusion already gives Rust-native SQL planning/execution and
Arrow interoperability; add ProximaDB-specific distributed scheduling, catalog, WAL, vector/graph,
and policy capabilities around it.

Route rejection is part of the contract, not a best-effort warning. The planner must reject or mark
unsupported any route where:

* policy cannot be enforced inside the required boundary;
* a stale projection is chosen for a current-snapshot query;
* a full-table overwrite targets an OLTP table without snapshot/overwrite capability;
* external compute would require a lossy `ProximaType` conversion not accepted by the query;
* a delegated write cannot prove atomic commit or idempotent retry behavior.

==== Execution Plan Contracts

The SQL frontend should not directly call a compute engine. It should emit ProximaDB logical plan
nodes that can be lowered into DataFusion, Polars, DuckDB, native record scans, or external engine
delegation:

[source,rust]
----
struct CopyIntoPlan {
    source: ReadSource,
    projection: LogicalProjection,
    target: TableIdentifier,
    write_mode: WriteMode,
    conflict_policy: ConflictPolicy,
    distribution: DistributionMode,
}

enum ReadSource {
    CatalogTable(TableIdentifier, SnapshotRef),
    ExternalLocation(ExternalFormat, String, Option<CatalogTableSchema>),
    Query(Box<LogicalPlan>),
    ArrowStream(FlightTicket),
}

enum ComputeBackend {
    Native,
    DataFusionLocal,
    DataFusionDistributed,
    PolarsLocal,
    DuckDbCompat,
    ExternalDelegated(ExternalEngine),
}

struct RoutedExecutionPlan {
    backend: ComputeBackend,
    read_plan: LogicalPlan,
    write_plan: WritePlan,
    estimated_cost: CostEstimate,
    required_guards: Vec<ExecutionGuard>,
}
----

Candidate path shape:

[source,rust]
----
struct CandidateWritePath {
    backend: ComputeBackend,
    access_method: AccessMethodFamily,
    supports_pushdown: PushdownCapabilities,
    requires_recheck: Vec<Predicate>,
    cost: CostEstimate,
    guards: Vec<ExecutionGuard>,
}

struct AccessMethodCostHints {
    row_lookup_cost: f64,
    scan_setup_cost: f64,
    sequential_scan_cost_per_mb: f64,
    remote_read_cost_per_mb: f64,
    write_amplification: f64,
    compaction_debt: f64,
    projection_lag_penalty: f64,
}
----

Path generation order:

1. Resolve xCatalog source and target metadata.
2. Generate native paths for Proxima-authoritative record/PAX/SST/ANN/topology layouts.
3. Generate DataFusion paths for Arrow-compatible scans, joins, aggregates, and distributed plans.
4. Generate Polars paths for compatible local dataframe transforms.
5. Generate DuckDB compatibility paths only when dialect/interop/file behavior requires it.
6. Generate external-commit paths for external-authoritative open table formats.
7. Reject paths that cannot enforce RLS, snapshot visibility, type mapping, or target write mode.
8. Pick the lowest-cost valid path; retain the rejected path reasons for EXPLAIN.

Execution guards:

* xCatalog schema version and snapshot ID are pinned before execution starts.
* RLS/tenant filters are pushed into source scans or applied by a trusted ProximaDB operator before
  any data leaves the policy boundary.
* Target write capabilities are checked before reading large source inputs.
* Open-format writers must stage data and commit metadata atomically.
* Retriable writes use idempotency keys and deterministic output file/segment naming where possible.
* Partial writes are visible only after the authoritative commit marker is durable.

==== Cost Router Policy

The first cost router can be rule-based with cost annotations. It should become CBO over time as
xCatalog statistics mature.

Planner design is intentionally inspired by PostgreSQL's separation between lightweight candidate
paths and executable plans, and by MariaDB's ability for storage engines to tune optimizer costs.
ProximaDB extends both patterns for multi-format, multi-engine, and distributed data:

* Candidate paths are cheap descriptors: native point write, PAX scan/write, DataFusion local,
  DataFusion distributed, Polars local transform, DuckDB compatibility, external table commit,
  vector ANN assisted path, graph topology assisted path, JSON/path index assisted path.
* Executable plans are created only after the router chooses a path and all execution guards are
  known.
* Storage/access-method families expose cost hints through xCatalog rather than hidden engine
  globals: row lookup cost, scan setup cost, write amplification, compaction pressure, projection
  freshness, remote read cost, file/partition count, index selectivity, and policy enforcement
  location.
* External/open-format adapters are similar to foreign-table paths: they can advertise pushdown,
  required rechecks, snapshot semantics, and commit capability without owning ProximaDB's internal
  WAL or `ProximaRecord` semantics.
* INSERT/UPDATE/DELETE/MERGE all flow into a write node analogous to a top-level modify node:
  read/query subplans produce target rows or keys, and the write node performs catalog validation,
  MVCC closure, constraint checks, and authoritative commit.

Initial routing rules:

[cols="1,2,2"]
|===
| Situation | Backend | Reason

| Single-row or small primary-key DML into Proxima-authoritative tables
| Native
| Needs WAL/MVCC/constraint authority with low latency.

| PAX/columnar/internal table scan plus SQL projection/filter/join/aggregate
| DataFusionLocal or DataFusionDistributed
| Arrow-native SQL execution and pushdown.

| Large distributed scan/join, remote partitions, or cluster execution mode
| DataFusionDistributed
| DataFusion provides the Rust execution substrate; ProximaDB supplies scheduling, catalog,
policy, vector/graph extensions, and storage connectors.

| Single-node ETL/materialization with dataframe-heavy expressions and limited SQL semantics
| PolarsLocal
| Fast local vectorized transforms when operator coverage and type semantics are compatible.

| DuckDB dialect compatibility, local file conformance, or user-requested DuckDB integration
| DuckDbCompat
| Compatibility surface and external analytics engine interop.

| External-authoritative Iceberg/Delta/Hudi write
| ExternalDelegated or DataFusion plus open-format writer
| Must use the table format's commit protocol and xCatalog ownership contract.

| Vector/graph/document hybrid query with Proxima-specific operators
| Native plus DataFusion extension nodes
| Keep modality semantics and indexes under ProximaDB authority while using Arrow execution where
profitable.
|===

Cost metrics:

* estimated rows, bytes, partitions, file count, and selectivity;
* available min/max, bloom, zone-map, HNSW, JSON-path, full-text, graph-topology, and time indexes;
* target write amplification and compaction cost;
* shuffle/network cost and executor locality;
* memory/spill estimate;
* RLS and masking enforcement cost;
* expected freshness lag for rebuildable projections;
* engine startup/interop overhead.

==== Engine Integration Boundaries

DataFusion integration:

* Implement ProximaDB table providers over xCatalog tables, external tables, and snapshots.
* Implement execution plan nodes for native point lookup, PAX scan, vector top-k, graph pattern
  expansion, JSON path access, observability time filters, and table-record writes.
* Use DataFusion's distributed execution substrate where available, but keep ProximaDB responsible
  for catalog, policy, WAL, snapshot, branch, and storage ownership.

Polars integration:

* Treat Polars as an optional local dataframe backend for staged Arrow batches.
* Only route to Polars when the plan can be represented without losing `ProximaType`, RLS, or MVCC
  semantics.
* Do not expose Polars-specific semantics through pgwire.

DuckDB integration:

* Keep DuckDB as a connector/compatibility surface for users that want to query ProximaDB from
  DuckDB or validate external file behavior.
* A DuckDB execution path may be selected for local read-only or staged write compatibility, but
  authoritative writes still commit through xCatalog plus `TableRecordStore` or the open-format
  commit protocol.

Spark/Flink/Trino integration:

* Prefer external interoperability through Iceberg REST, Arrow Flight, pgwire/JDBC, and open-table
  formats.
* Do not embed these engines in the hot write path.
* Publish ProximaDB snapshots/projections to them with explicit freshness and ownership metadata.

==== Failure And Transaction Semantics

For `INSERT INTO ... SELECT`:

* Source snapshot is pinned before execution.
* Target write batches may stream, but rows become visible only after the authoritative commit.
* On failure before commit, staged files/segments are garbage-collected by manifest cleanup.
* On retry, idempotency keys avoid duplicate append if the prior commit succeeded.

For `INSERT OVERWRITE ... SELECT`:

* Target creates a new snapshot/branch head.
* Old versions remain available to readers pinned to previous snapshots.
* Partition overwrite replaces only cataloged partition keys in the write plan.
* Overwrite cannot bypass RLS, retention, CDC, or branch protection.

For external tables:

* External-authoritative tables use external transactions/commits and record the resulting snapshot
  in xCatalog.
* Proxima-authoritative projection publications write derived files and record freshness, but
  repair source remains ProximaDB WAL/records.

== Format Schema

=== Logical Table Shape

xCatalog owns the logical schema:

[source,text]
----
TableAsset {
  asset_id
  namespace
  name
  schema_mode: strict | write | read | flexible
  columns: [ProximaColumn { name, type, nullable, default, constraints, column_id }]
  primary_key
  unique_indexes
  foreign_keys
  check_constraints
  access_methods
  retention_policy
  rls_policy
  external_mappings
}
----

Every relational row lowers to `ProximaRecord`:

[source,text]
----
ProximaRecord {
  oid, tenant_id, created_at_ns, updated_at_ns,
  valid_from_ns, valid_to_ns,
  actor, origin,
  props / typed user columns,
  labels,
  embeddings,
  graph edge fields when applicable,
  extensions
}
----

Strict relational tables reject unknown fields. Schema-on-write tables validate and catalog
evolution before accepting new fields. Flexible document/graph/entity collections record structural
variations. Schema-on-read external tables project source columns into `ProximaType` during scans.

=== PAX Row-Family Layout

PAX is the default internal relational block family:

[source,text]
----
[BlockHeader]
  tenant hash, schema fingerprint, min/max timestamps, mode, counts, checksums

[RowDirectory]
  oid hash, primary-key hash, valid_from_ns, valid_to_ns, flags, row ordinal

[ColumnStripes]
  system columns
  primary-key and partition columns
  frequently filtered scalar columns
  user columns
  JSON/path projected columns
  embedding columns
  graph edge columns
  observability time/service/trace columns
  props/labels/extension blobs

[ColumnMeta]
  min/max, null counts, bloom refs, offsets, encodings
----

Modes:

* `Oltp`: row directory first; optimized for small tables, point lookups, indexes, and DML.
* `Pax`: row directory plus column stripes; default HTAP shape.
* `Olap`: column stripes first; optimized for scans, Arrow batches, and open-format publication.

=== SST/LSM Compatibility

SST/LSM layouts remain useful for high ingest and write-optimized compaction. To participate in
relational semantics, each entry must carry or derive:

* stable `oid` and cataloged primary key;
* tenant/RLS key;
* `created_at_ns`, `updated_at_ns`, `valid_from_ns`, `valid_to_ns`;
* record version or commit sequence;
* tombstone/update flags;
* schema fingerprint;
* optional branch/snapshot metadata;
* index freshness and compaction watermark.

The LSM key order may optimize for vector id, tenant/time, primary key, or graph adjacency, but the
value must still decode to canonical `ProximaRecord` fields.

== Cross-Modal Mapping

[cols="1,3,3"]
|===
| Surface | Canonical record shape | Rebuildable projections and indexes

| Relational
| Typed columns, primary keys, constraints, tenant/time/provenance metadata.
| Primary/secondary indexes, PAX stripes, materialized views, Arrow/Iceberg publications.

| Document
| `Map`, `Json`, `Struct`, typed extracted columns, labels, structural variations.
| JSON path indexes, inverted indexes, stable-shape column stripes, schema variation stats.

| Graph
| Node and edge records. Edge records use source, target, type, weight, properties, and validity.
| Adjacency tables, CSR/COO topology, GraphAr/open graph lake publications, path indexes.

| Vector
| Embedding columns plus scalar metadata and labels on the same record.
| HNSW/IVF/PQ/DiskANN fragments, predicate-aware ANN indexes, quantized stripes.

| Observability
| Logs, metrics, spans, profiles, service dependency edges, and events as timestamped records.
| Time partitions, rollups, trace assembly indexes, service maps, SIEM/full-text indexes.

| Event streams
| Append-only event records with sequence, key, timestamp, headers, payload, and provenance.
| Consumer offsets, CDC publications, current-state materializations, compacted views.
|===

== OLTP And OLAP Query Shape

OLTP:

* point lookup uses primary-key index plus row directory;
* writes append to WAL before becoming visible;
* secondary indexes and projections update through cataloged freshness rules;
* transactions and snapshots are expressed in shared version metadata.

OLAP:

* scans use column stripes, min/max stats, bloom filters, tenant/time pruning, and Arrow batches;
* SQL aggregates, joins, filters, vector predicates, graph traversals, and document path filters
  lower to shared logical algebra;
* external engines consume Iceberg/Arrow/Parquet-compatible projections without owning hot state.

HTAP:

* one record/version model serves both paths;
* compaction can rewrite row-heavy segments into PAX or OLAP mode;
* freshness and snapshot watermarks are cataloged, visible, and testable.

== External Table Interoperability

External file and table formats are first-class cataloged assets. xCatalog must record:

* format: Parquet, CSV, Avro, ORC, JSON, XML, Arrow IPC, Iceberg, Delta, Hudi, Hive, Glue, Unity,
  Polaris, or connector-specific formats;
* location and credentials boundary;
* ownership mode;
* `ProximaType` mapping and lossy conversions;
* snapshot/isolation semantics;
* tenant/RLS enforcement boundary;
* read/write/refresh mode;
* schema evolution policy;
* repair or rebuild source;
* freshness watermark and stats;
* publication lineage and branch/snapshot mapping.

Ownership modes:

[cols="1,4"]
|===
| Mode | Meaning

| `ProximaAuthoritative`
| ProximaDB WAL and `ProximaRecord` storage own truth. External files are publications.

| `ProjectionPublication`
| A rebuildable PAX/Parquet/Iceberg/Delta/Hudi/GraphAr/Arrow projection published from
ProximaDB-owned records.

| `ImportedSnapshot`
| A point-in-time import from external files. ProximaDB owns the imported records after load.

| `ExternalAuthoritative`
| The external table owns truth. xCatalog records snapshot, isolation, policy, write mode, and
repair semantics explicitly.

| `FederatedRead`
| ProximaDB plans reads against external data without importing or owning record state.
|===

Every external row must project into `ProximaRecord`/`ProximaValue` before shared planning. Every
write back to an external authority must pass through the xCatalog ownership and policy contract.

== Migration Implications

The pgwire compatibility path should move in this order:

1. Keep parser and wire compatibility improvements covered by psql and SQLAlchemy smoke tests.
2. Replace vector-collection shims in SQL DDL/DML with xCatalog table assets and canonical
   `ProximaRecord` writes.
3. Route `INSERT`, `UPSERT`, `UPDATE`, and `DELETE` through WAL plus record storage, with tombstone
   semantics for deletes.
4. Route `SELECT` through shared logical plans and record/PAX scanners, then project PostgreSQL
   wire row descriptions from catalog metadata. The pgwire smoke path now supports point SELECT and
   full-table SELECT through `DmlService` plus `TableRecordStore::scan_records`; simple non-PK
   `AND` predicates over comparisons, `IN`, `LIKE`, and `IS NULL` are evaluated as a pgwire
   compatibility filter. OR predicates, joins, aggregates, and direct PAX-backed scans still need
   the shared logical-plan path.
5. Add PostgreSQL metadata views as compatibility projections over xCatalog, not as independent
   catalogs.
6. Modernize SST/LSM entries to carry shared MVCC metadata before using them for mutable SQL tables.
7. Publish analytical snapshots through Arrow Flight and Iceberg/OpenTable adapters with explicit
   freshness watermarks.

=== xCatalog Storage Layout Contract

Every table/collection/profile that participates in SQL or open-format interoperability must carry
at least one `CatalogStorageLayout`:

[source,text]
----
CatalogStorageLayout {
  name
  authority: ProximaAuthoritative | ProjectionPublication |
             ImportedSnapshot | ExternalAuthoritative | FederatedRead
  layout_kind: RowRecord | LsmRecord | Pax | Columnar | AppendOnlyEvent |
               VectorAnn | GraphTopology | TimeSeriesBlock | ExternalTable
  physical_format: ProximaBlock | Sst | Arrow | Csv | Json | Xml | Avro |
                   Parquet | Orc | Iceberg | Delta | Hudi | GraphAr | External(...)
  write_mode: Mutable | AppendOnly | CopyOnWrite | ExternalRefresh |
              StreamingIngest | ReadOnly
  location
  snapshot_semantics
  policy_enforced_in_proxima
  lossy_type_mappings
  properties
}
----

Rules:

* ProximaDB-authoritative mutable relational tables SHOULD use a PAX primary layout.
* External-authoritative and federated-read layouts MUST declare `location`, snapshot/isolation
  semantics, policy boundary, write/refresh mode, and `ProximaType` mapping.
* Projection publications MUST declare rebuild source and freshness watermark.
* SST/LSM layouts MUST expose the same identity, tenant, version, timestamp, schema fingerprint,
  and tombstone metadata as PAX.

=== Reserved System Columns

The catalog crate owns the SQL-visible reserved column registry. User schemas must reject any column
starting with `__proxima_`.

[cols="2,2,3"]
|===
| Name | Type | Source
| `__proxima_oid` | `TEXT` | `ProximaRecord.oid`
| `__proxima_tenant_id` | `TEXT` | `ProximaRecord.tenant_id`
| `__proxima_record_version` | `BIGINT` | `ProximaRecord.record_version`
| `__proxima_created_at_ns` | `BIGINT` | `ProximaRecord.created_at_ns`
| `__proxima_updated_at_ns` | `BIGINT` | `ProximaRecord.updated_at_ns`
| `__proxima_valid_from_ns` | `BIGINT` | `ProximaRecord.valid_from_ns`
| `__proxima_valid_to_ns` | `BIGINT` | `ProximaRecord.valid_to_ns`
| `__proxima_actor` | `TEXT` | `ProximaRecord.actor`
| `__proxima_origin` | `TEXT` | `ProximaRecord.origin`
| `__proxima_deleted` | `BOOLEAN` | derived tombstone/visibility state
| `__proxima_branch_id` | `TEXT` | branch/snapshot metadata
| `__proxima_schema_version` | `INTEGER` | xCatalog schema version/fingerprint
|===

Compatibility aliases such as `_deleted` and `_version` may be recognized during import/export or
connector mapping, but they must canonicalize to `__proxima_deleted` and
`__proxima_record_version`.

=== Relational Mutation Contract

SQL DML lowers into `RelationalMutationKind` plus a catalog-validated `CatalogRow`, then writes the
result through `TableRecordStore`:

[source,text]
----
INSERT -> new ProximaRecord
UPSERT -> new ProximaRecord version; close prior visible version when present
UPDATE -> new ProximaRecord version with projected changed fields
DELETE -> tombstone ProximaRecord and/or close prior visible version
----

Shared helpers must set:

* stable oid from primary-key values when a primary key exists;
* `tenant_id`, actor, origin, method, created/updated timestamps;
* `record_version` when the caller has OCC/CDC ordering;
* `valid_from_ns` and `valid_to_ns` for snapshot visibility;
* no embeddings on delete tombstones.

Visibility is exclusive at the upper bound:

[source,text]
----
visible_at(t) = valid_from_ns <= t AND t < valid_to_ns
----

`valid_to_ns = NULL` means current/open-ended. Legacy tombstones using `valid_to_ns = 0` remain
recognized until storage compaction migrates them to full version-chain closure.

=== PAX Row Directory Contract

The PAX row directory is the OLTP access path for PAX and OLTP blocks:

[source,text]
----
RowEntry {
  row_id_hash: u64
  valid_from_ns: i64
  valid_to_ns: i64
  flags: DELETED | UPDATED | TOMBSTONE
  row_index: u32
}
----

Rules:

* `valid_to_ns` is exclusive.
* `i64::MAX` means current/open-ended.
* Point lookup returns only rows visible at the requested snapshot.
* Hash collisions and MVCC chains must scan the same-hash range and choose the visible version.
* Column stripes remain authoritative for projected values; row directory is an access path.

=== Pgwire Compatibility Contract

pgwire must expose PostgreSQL-like behavior while lowering immediately into shared contracts:

* DDL creates/updates xCatalog schemas and storage-layout descriptors.
* DML validates through `CatalogRow` and writes canonical mutations through `TableRecordStore`.
* `information_schema` and `pg_catalog` compatibility views project from xCatalog.
* SQLAlchemy reflection paths must not require a hidden PostgreSQL catalog.
* Unsupported PostgreSQL features must fail deterministically with SQLSTATE-like errors, not panic.

==== SQL DDL Option Shape

The pgwire path accepts PostgreSQL-style `CREATE TABLE ... WITH (...)` options as an xCatalog
control surface. These options are metadata first: they select storage/access-method shape and
external interoperability contracts; they do not create a separate SQL-owned durable model.

[source,sql]
----
CREATE TABLE facts (
  id BIGINT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  payload JSONB,
  embedding VECTOR(384)
) WITH (
  workload = 'htap',              -- oltp | olap | htap | vector | document | graph | observability | mixed
  layout = 'pax',                 -- pax | oltp | olap | sst | lsm | columnar | vector | document | graph
  open_table_format = 'iceberg',  -- parquet | csv | avro | orc | json | xml | arrow | iceberg | delta | hudi
  ownership = 'projection',       -- proxima | projection | import | external | federated
  location = 's3://warehouse/facts',
  refresh = 'manual'
);
----

Typed lowering:

* `workload` maps to `CatalogWorkloadProfile`.
* `layout`, `storage_layout`, `specialization`, or `storage_engine` maps to
  `CatalogStorageSpecialization`.
* `open_table_format`, `table_format`, or `format` maps to `CatalogPhysicalFormat`.
* `ownership` or `authority` maps to `CatalogAuthorityMode`.
* `location`, `external_location`, or `path` becomes the external/publication URI.

Defaulting:

* Plain relational tables default to `workload = 'htap'` and PAX row-family.
* `workload = 'oltp'` defaults to PAX `Oltp` mode.
* `workload = 'olap'` defaults to PAX `Olap` mode.
* JSON columns add a rebuildable JSON/path projection descriptor.
* Vector columns add a rebuildable vector ANN projection descriptor.
* `storage_engine = 'sst'` or `layout = 'lsm'` keeps the legacy SST/LSM write-optimized primary
  layout while still requiring shared MVCC/tombstone metadata.

Open-table ownership:

* `ownership = 'projection'`: ProximaDB owns records; the external table is a publication.
* `ownership = 'import'`: external data is imported as a point-in-time snapshot.
* `ownership = 'external'`: external table owns truth; location and snapshot semantics are required.
* `ownership = 'federated'`: ProximaDB reads externally without importing record state.

=== External Table Contract

`CREATE EXTERNAL TABLE` and catalog imports must specify:

* physical format and location;
* ownership mode;
* schema mapping into `ProximaType`;
* snapshot/isolation semantics;
* tenant/RLS policy boundary;
* read/write/refresh mode;
* lossy conversions;
* repair/rebuild source;
* freshness watermark;
* schema evolution policy.

For source formats:

* CSV/XML require declared or inferred schemas before planning.
* JSON/Avro/ORC/Parquet/Arrow can infer richer types but must still record the `ProximaType`
  mapping and lossy conversions.
* Iceberg/Delta/Hudi expose table snapshots/manifests but do not become internal hot-state
  authorities unless `ExternalAuthoritative` is explicitly cataloged.

== Non-Goals

* Do not put ProximaDB's hot durable core inside PostgreSQL, DuckDB, or another external database.
* Do not make Iceberg, Delta, Hudi, Parquet, or ORC the only internal hot-state representation.
* Do not create separate durable row envelopes for SQL, document, graph, vector, or observability.
* Do not expose PostgreSQL system columns as ProximaDB's internal canonical field names.
* Do not treat `_deleted` or `_version` as canonical names; use `__proxima_deleted` and
  `__proxima_record_version`.

== Acceptance Criteria

Relational storage work is aligned with this design when:

* DDL creates xCatalog table assets with `ProximaType` columns and capability metadata.
* DML writes canonical `ProximaRecord` mutations through WAL.
* UPDATE and DELETE preserve MVCC visibility and tombstone semantics.
* pgwire, Arrow Flight, REST/gRPC, and embedded clients see consistent rows and metadata.
* PAX/SST/ANN/JSON/graph/time-series projections declare freshness and rebuild semantics.
* External table reads and writes declare ownership and convert through `ProximaValue`.
* psql, SQLAlchemy, BenchBase OLTP, and TPC-H/TPC-DS-style analytical tests run against the same
  relational/catalog/storage path instead of protocol-specific shims.
