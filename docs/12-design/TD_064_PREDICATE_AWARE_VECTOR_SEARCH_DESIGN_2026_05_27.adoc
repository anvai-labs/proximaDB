== Executive Summary

TD-064 addresses a **critical correctness and security surface** where post-filtered ANN (Approximate Nearest Neighbor) search can return fewer than the requested matching top-k results under tenant/RLS, time, branch, and typed metadata filters.

**Problem**: Legacy and partially-wired paths can perform vector search first, then apply metadata filters as a residual post-filter. If the filter eliminates most candidates, the client can receive fewer results than requested without a route-level indication that the selected plan was degraded.

**Solution**: Complete the existing ADR-011 filtered-ANN routing contract so `VectorTopK` planning distinguishes three execution strategies:
1. **PreFilter** — evaluate scalar predicates first, then run exact or restricted vector scoring over the candidate set
2. **Inline** — predicate-aware ANN via HNSW/IVF predicate callbacks
3. **PostFilter** — overfetch from ANN, apply residual predicates, and disclose degraded/shortfall risk in `EXPLAIN`

This design coordinates with Phase C of the multimodal overhaul spec (`roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc`).

## Architecture Design

### Three Execution Strategies

The routing thresholds must reuse ADR-011 `AnnFilteringPolicy`, not introduce a second policy with different constants.

==== 1. PreFilter / Exact Candidate Scoring (Very Low Selectivity)

When metadata filter selectivity is below `pre_filter_threshold` (default `< 5%`):

[source, text]
----
┌─────────────────────────────────────────────────────────────┐
│  Metadata Scan (Parquet/Columnar)                           │
│  - Apply filter first                                      │
│  - Extract matching vectors                                │
│  - Compute distances in batch                             │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │  Top-K Sort     │
                    │  (Exact k)      │
                    └─────────────────┘
----

*Use case*: Very selective metadata filters (e.g., `tenant_id = 'X' AND status = 'active'` when fewer than 5% of records match)
*Guarantee*: Returns exactly k results if enough records match the filter
*Trade-off**: Higher latency, lower compute efficiency

==== 2. Inline Predicate-Aware ANN (Moderate Selectivity)

When metadata filter selectivity is between `pre_filter_threshold` and `post_filter_threshold` (default `5%-50%`) and a predicate-aware ANN index is fresh enough for the requested snapshot:

[source, text]
----
┌─────────────────────────────────────────────────────────────┐
│  HNSW/IVF predicate-aware traversal                         │
│  - Predicate callback evaluates visible record metadata     │
│  - Skip-through traversal keeps graph connectivity          │
│  - Residual filter verifies final candidates                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │  Post-Filter    │
                    │  (should be rare)│
                    └─────────────────┘
----

*Use case*: Moderate selectivity where predicate-aware traversal avoids materializing a large prefilter candidate set
*Guarantee*: Approximate ANN recall; residual predicates prevent false positives, but recall risk must be visible when the predicate bridge or projection freshness is degraded
*Trade-off**: Approximate but fast

*Candidate Budget Formula*:
[source, rust]
----
let selectivity = selectivity.max(MIN_SELECTIVITY);
let requested_k = ((k as f64) / selectivity)
    .ceil()
    .min((k as f64) * MAX_OVERSAMPLE) as usize;
// e.g., k=100, selectivity=0.2 → request_k=500
----

This is a candidate budget, not a correctness guarantee. The previous `k * (k / selectivity)` formula was incorrect because it scaled by `k` twice.

==== 3. PostFilter Fallback (High Selectivity)

When metadata filter selectivity is above `post_filter_threshold` (default `> 50%`):

[source, text]
----
┌─────────────────────────────────────────────────────────────┐
│  Traditional ANN Search                                     │
│  - Request k × post_filter_oversample_factor candidates     │
│  - Post-filter metadata                                     │
│  - Return whatever matches (may be < k)                    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │  EXPLAIN        │
                    │  Disclosure     │
                    │  " shortfall=87"│
                    └─────────────────┘
----

*Use case*: Non-selective filters where most ANN neighbors are expected to survive the filter
*Guarantee*: Best-effort k results
*Trade-off**: Fastest but may return incomplete results (explicitly disclosed)

## Component Design

### 1. VectorTopK / ADR-011 Route Planning

Do not create a second `PredicatePlanningPolicy` with different thresholds. The route decision must extend the existing catalog contract:

* `CatalogTableSchema.ann_filtering_policy`
* `AnnFilteringPolicy::routing_mode(estimated_selectivity)`
* `AnnFilteringPolicy::effective_top_k_for_post_filter(top_k)`
* ADR-004 `FilterDiagnostics` and route/rejection metadata

The planner output should be a typed `VectorTopK` route descriptor carrying:

* selected `AnnFilteringMode`
* selectivity estimate and source (`catalog_stats`, `sample`, `heuristic`, or `forced`)
* pushed predicates and residual predicates
* projection/index freshness state
* candidate budget or post-filter overfetch factor
* degraded/rejected-route reasons

### 2. Mandatory Tenant/RLS Predicate Compilation

Tenant, RLS, branch/time, and typed metadata predicates must be compiled into the same normalized predicate expression before route selection. A standalone placeholder builder that checks only `rls_policy_id` is not sufficient.

The correct boundary is:

1. Resolve tenant/session/policy context from catalog and request context.
2. Compile mandatory policy predicates into `FilterExpression` / normalized filter form.
3. `AND` mandatory predicates with user predicates.
4. Validate against xCatalog schema and supported-surface maturity.
5. Pass the combined expression into `VectorTopK` planning.

### 3. HNSW Predicate Bridge

Extend the existing AXIS bridge rather than adding a parallel one:

* `src/index/axis/management/filtered_search.rs::make_id_predicate()` currently handles ID-only clauses.
* `src/index/axis/management/manager.rs::query_hnsw_with_predicate()` currently calls `search_with_predicate()`.
* `src/core/search/filter_contract.rs::MetadataLookup` already defines single and batch lookup hooks.

TD-064 should replace ID-only pass-through behavior with a record-aware bridge:

[source, rust]
----
fn predicate_for_filter(
    filter: Arc<dyn FilterContract>,
    lookup: Arc<dyn MetadataLookup>,
) -> impl Fn(&str) -> bool + Send + Sync {
    move |id| {
        let metadata = match lookup.get_metadata(id) {
            Ok(Some(metadata)) => metadata,
            _ => return false, // fail closed for policy-bearing predicates
        };
        filter.evaluate_row(&metadata).unwrap_or(false)
    }
}
----

This bridge must distinguish mandatory policy predicates from optional user filters. Missing metadata may safely degrade optional filters to residual evaluation only when the route explicitly records that degradation; missing metadata for tenant/RLS must reject or route to an exact canonical scan.

### 4. Record Metadata Lookup

Do not invent a non-existent `ZeroCopyMetadataCache` API or describe the WAL as the normal point-read source. The authority chain is WAL/log/manifest plus canonical record storage; runtime lookups should use cataloged record/PAX/SST/columnar access methods and their existing cache/filesystem layers.

The implementation target is a `MetadataLookup` backed by the same record source used for canonical visibility:

* hot current-state/memtable or `collection_vectors` during the migration period
* PAX/SST/columnar row-directory or ID lookup for flushed records
* cataloged secondary/path indexes for `PreFilter` candidate generation
* cache/filesystem zero-copy helpers as an optimization, not a separate authority

Key design points:

1. **No hidden authority** — metadata values come from visible `ProximaRecord` state.
2. **Secondary indexes are allowed** — JSON/path/inverted/range indexes are Layer 2 projections and can be used for `PreFilter`; they are not durable truth.
3. **Batch first** — HNSW predicate callbacks are per-ID, but the bridge should prefetch/batch candidates when the executor can expose the frontier or candidate set.
4. **Freshness explicit** — bounded-lag projections can be used only when the requested snapshot and policy boundary allow them.

### 5. EXPLAIN Integration

File: `src/observability/search_plan_trace.rs` (extend existing)

[source, rust]
----
/// Extended search plan trace with predicate-aware information

}

## Security Considerations

=== Tenant Isolation
* **Tenant filter MUST be injected at the earliest possible point** — before any storage or index access
* **Tenant filter CANNOT be bypassed by user query** — always ANDed with user-provided filters
* **Cross-tenant access MUST return empty results, not error** — prevents tenant enumeration

=== RLS Enforcement
* **RLS policy lookup MUST happen at query time, not insert time** — policies can change
* **RLS filter CANNOT be overridden by user query** — always applied regardless of user filters
* **RLS violations MUST be logged** — for security audit trails

=== Filter Injection Safety
* **User-provided filters MUST be validated against schema** — prevent injection attacks
* **Filter evaluation MUST be sandboxed** — prevent code execution via malicious JSON
* **Filter errors MUST fail closed** — exclude record on error rather than include

## Performance Considerations

=== Selectivity Estimation
* **Use catalog statistics when available** — accurate estimates from histograms
* **Fall back to heuristics when not** — default selectivity per operator type
* **Cache estimates per collection** — avoid repeated catalog lookups

=== Oversampling Trade-offs
* **Candidate budget = min(k / selectivity, k × MAX_OVERSAMPLE)** — balances recall vs latency without double-scaling by `k`
* **Monitor actual vs expected shortfall** — adjust thresholds based on real data
* **Cap oversampling at 10× by default** — prevent pathological cases

=== Caching Strategy
* **Cache metadata lookups during predicate execution** — reuse across candidates
* **Treat cache as projection state** — visibility, freshness, and invalidation must be explicit
* **Size cache by collection and policy boundary** — prevent memory bloat and cross-tenant reuse

=== Current Implementation Delta

Current code does not yet fully match the target:

* `AxisHnswIndex` stores vector payloads in `ZeroOverheadCollection` and quantized side maps, not IDs only.
* `AxisManager` keeps `collection_vectors` as an in-memory `ProximaRecord` map for exact filtered fallback and MVCC expiration lookup.
* `crate::index::MetadataIndex`, `GlobalIdIndex`, `DenseVectorIndex`, and `SparseVectorIndex` in `src/index/mod.rs` are placeholders, while storage-engine-specific metadata indexes also exist.
* `make_id_predicate()` evaluates only ID clauses; non-ID metadata predicates pass through and are handled, if at all, as residual/exact fallback.
* `AxisMetadataLookup` currently returns `None`; it is not a production record metadata bridge.

This is acceptable as a migration state, but TD-064 should be explicit: the work is to converge AXIS and storage lookup onto the canonical authority/projection contract, not to remove all metadata indexes. Secondary indexes are valid Layer 2 projections when cataloged, rebuildable, freshness-aware, and never treated as durable truth.

=== Key Patterns TD-064 Must Follow

1. **Canonical authority** — xCatalog + WAL/log/manifest + visible `ProximaRecord` state owns semantics.
2. **Cataloged projections** — HNSW/IVF/PQ, JSON/path/range indexes, row-group stats, and caches are rebuildable access methods.
3. **Freshness-aware routing** — route to projections only when their freshness satisfies the request and policy boundary.
4. **Record-aware predicates** — tenant/RLS/time/typed props must be available to candidate generation or force an exact canonical route.
5. **Explicit degradation** — post-filter, stale projection, missing metadata, and unsupported predicate cases must surface in EXPLAIN.
