== Shared HLD: the CS/CD control plane

ProximaDB already serves (vector / hybrid / cross-model retrieval). Phase 8 adds the *continuous*
half of the Vector Lakebase thesis: a flywheel where serving generates data and feedback, discovery
refines it, and improvements republish atomically back into serving.

----

The six features map onto this control plane:

* **F1** is the loop itself (discovery job → atomic republish).
* **F2 / F3** make serving over object storage economical (cold start, point-read amplification) so
  compute can scale to zero between loop turns.
* **F5** extends the loop to cover external lake data without copying it.
* **F4** is the elastic compute substrate the loop runs on (offline-batch is the home for F1 jobs).
* **F6** adds Lance as an external substrate for F5.

=== Cross-cutting mandates (apply to every feature)

Per the `CLAUDE.md` generated-code and architecture mandates, every new route / reader / index in
this spec must, before default enablement:

1. Declare `authority_mode` (e.g. `InternalCanonical`, `ProjectionPublication`, `FederatedRead`) on
   its `CatalogStorageLayout` / `CatalogProjection`.
2. Declare freshness behavior and runtime `freshness_state`, plus the repair/rebuild source.
3. Declare policy boundary (engine-enforced vs external) and RLS behavior.
4. Surface its decision in unified EXPLAIN (ADR-004) and, where relevant, route-health.
5. Carry an explicit `support_status` (`experimental` → `beta` → `supported`).

== F1 — Continuous Discovery loop + atomic snapshot republish (TD-086) [DEEP]

=== HLD

A `DiscoveryJob` is a first-class cataloged asset with the lifecycle:
_schedule → pin snapshot → refine → build new indexes → register new projection → atomic publish →
serving switch_. Serving keeps reading the prior snapshot until the new data + indexes are ready;
the catalog then flips the active projection pointer atomically — no half-built index is ever
visible mid-run. This is the difference between "discovery as an external pipeline" and "discovery
as part of the same operational system."

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant C as Client / scheduler
    participant R as DiscoveryRegistry
    participant E as DiscoveryJobExecutor
    participant M as GlobalManifest
    participant X as xCatalog
    participant S as Serving

    C->>R: POST /discovery-jobs (kind=Dedup)
    R->>M: pin checkpoint (from_lsn..to_lsn)
    R->>X: register DiscoveryJob (Running), projection freshness=Updating
    R->>E: spawn
    E->>E: refine on pinned snapshot (branch_id=discovery_<id>)
    E->>E: rebuild indexes for refined set
    E->>X: register new CatalogStorageLayout (ProjectionPublication)
    Note over S: serving still reads OLD snapshot
    E->>X: atomic swap active pointer; freshness=Fresh; with_lineage(...)
    X-->>S: new snapshot now visible (atomic)
    E->>X: DiscoveryJob (Complete) + quality_metrics
----

Refinement kinds: `Dedup`, `Recluster`, `ReEmbed`, `QualityScan`, `TrajectoryAnalysis`.

==== Trigger arm — what makes the loop *continuous* (do not omit)

The execution + atomic-republish path above is the *refine → republish* half. A flywheel also needs
a *feedback → trigger* half, or it is just batch jobs an operator invokes by hand. ProximaDB has the
signals already; they are simply not wired to enqueue jobs:

* `RecallProbeGate` FAIL streaks (recall degradation) → enqueue a `Recluster` / `ReEmbed` job.
* Freshness-SLA breaches (projection `Stale`/`RebuildRequired`) → enqueue a refresh/rebuild job.
* AutoML `WorkloadAnalyzer` / `PerformancePredictor` drift + access-pattern shift (`src/automl/`) →
  enqueue the appropriate refinement.
* Outbound CDC (`src/cdc/`) volume/pattern signals → optional trigger source.

Reuse AutoML as the *cost-aware scheduler* (it already models workload patterns and optimization
goals) rather than building a new scheduler. Add a thin `DiscoveryTrigger` that subscribes to these
signals and calls `DiscoveryRegistry::enqueue`. This is also where R4a single-node scale-to-zero
interacts: a suspended collection's triggers queue jobs that warm it only when discovery actually
runs.

==== First real pass: `Recluster`, then `ReEmbed`, then `Dedup`

The S0–S2 walking skeleton runs every kind as an identity pass. When implementing the *first real*
pass, prefer `Recluster` (pure reuse of `UnifiedIvfIndex` k-means → a measurable index-quality win,
no external model dependency, smallest end-to-end proof), then `ReEmbed` (highest customer value —
"embedding models change", "moving a billion vectors takes days" — reusing the `proximadb-embedding`
OpenAI/BGE/BYO backends and the R0 rank/hybrid surfaces), then `Dedup`.

=== Success criteria

1. `DiscoveryJob` is cataloged and queryable.
2. A job pins an LSN snapshot range and runs without blocking serving.
3. Completion republishes new data + rebuilt indexes via an **atomic** snapshot switch — no
   half-built index ever visible mid-run.
4. `freshness_state` transition `Updating → Fresh` is observable in the catalog.
5. EXPLAIN discloses `authority_mode` + freshness + snapshot lineage for the republished projection.
6. Integration test proves the old snapshot is served throughout the run and the refined snapshot
   immediately after the switch.
7. *Trigger arm*: at least one feedback signal (RecallProbeGate FAIL streak, freshness-SLA breach,
   or AutoML drift) auto-enqueues a `DiscoveryJob` without operator action — the loop is continuous,
   not manually invoked.

== F2 — Scale-to-zero cold path: binary-first two-stage + IVF pruning (TD-087) [DEEP]

=== HLD

When compute scales to zero, the first query hits cold object storage. Instead of pulling the full
index (which can be hundreds of GB), load a compact 1-bit representation *first* (~1/30 the size),
serve a coarse two-stage search (binary filter → higher-fidelity rerank), IVF-prune to bound the
bytes touched per query, and lazily fetch the rerank tier. The recall envelope is gated and
disclosed.

----

    L1["Load 1-bit binary tier first<br/>(~1/30 of full index)"]
    PR["IVF prune: nearest centroids<br/>(bounds bytes touched)"]
    S1["Stage 1: binary coarse filter"]
    S2["Stage 2: lazy-load rerank tier"]
    G{"RecallProbeGate<br/>open?"}
    FB["Fallback: non-quantized route<br/>(EXPLAIN degraded-route reason)"]
    OUT["Top-k with disclosed recall envelope"]

    CQ --> L1 --> PR --> G
    G -- open --> S1 --> S2 --> OUT
    G -- FAIL streak --> FB --> OUT

== F3 — Point-read-optimized lake layout (I/O amplification) (TD-088) [DEEP]

=== HLD

A vector search returns IDs; serving then needs full records (text, metadata, permissions,
timestamps). Today the VIPER path deserializes a whole Parquet row group per point read — large I/O
amplification over object storage. Serving (point reads) and discovery (scans) stay over *one
logical copy*.

*Scope narrowing (plan refinement).* PAX already ships `BlockMode::Oltp` with an O(log N) row
directory — conceptually the same row alignment Loon uses — so this is **not** a new-format build.
The genuine gap is narrow: *object-storage range-request granularity*, i.e. coalescing and issuing
byte-range reads for the matched IDs' columns instead of pulling whole row groups/stripes. The
work is a column-group grouping on the existing PAX OLTP layout plus a range-read fetch path; the
**Vortex** evaluation is a *benchmark-justified fallback only* if PAX-grouped reads cannot hit the
byte-amplification target. Adopting Vortex by default would duplicate the `proximadb-block-format`
investment and violate the reuse-first mandate.

=== LLD

Reuse map:

[cols="1,3", options="header"]
|===
| Concern | Reuse

| Block format
| `proximadb-block-format` (`crates/storage/proximadb-block-format/`). `BlockMode::Oltp` already
provides an O(log N) `RowDirectory::find_visible() -> row_index`; `ColumnMeta` already carries
`stripe_offset`/`stripe_len`. NEW: a column-group grouping so a point read reads only its group's
stripe byte ranges instead of all stripes.

| Fetch-path fix
| `VIPER internal_vector_by_id_with_path()` (`src/storage/engines/viper/engine.rs:1076+`) — replace
full-row-group deserialize with byte-range projection reads when backed by the PAX point-read
layout; keep the existing `CrossCacheOrchestrator` cache check.

| Vortex
| Evaluation spike only (no adoption commitment in this feature) — add behind an interoperability
shim and benchmark vs PAX-grouped and Parquet for both point reads and scans. Vortex is
Linux-Foundation, aligning with the open-format mandate.
|===

== F5 — External Collection: ProximaDB-owned indexes over external-resident data (TD-090) [DEEP]

=== HLD

Register an external lake table (Iceberg / Lance / Parquet) **un-copied and externally governed**;
ProximaDB builds and maintains vector + inverted (+ JSON) indexes over it that route through the same
retrieval path as native data. Index staleness vs source commits is declared; a source-commit
advance flips the projection to `RebuildRequired`. This lets F1's discovery loop cover lake data, not
just imported data. Principle (adopted verbatim): "One Data. One Index. No duplicated storage. No
dual-write pipelines."

== F4 — Elastic compute modes + resources-follow-data scheduler [SPLIT]

The original single F4 is **split by what is actually blocked**, so the unblocked, high-value half
is not buried behind the distributed-transport gap. F4a is single-node and unblocked; F4b is the
multi-node warm-pool that genuinely needs TD-077.

=== F4a — Single-node scale-to-zero / collection suspend-resume (TD-094) [OUTLINE, UNBLOCKED]

==== HLD (outline)

Within one node: evict a collection's compute/index from memory while keeping its catalog metadata
queryable, then lazy-warm on first query (via the F2 cold path). This delivers most of the "idle
tenants don't pay" economics for embedded / single-node deployments with **no dependency on
TD-077**. It reuses surfaces that already exist:

* `CollectionPinRegistry` (`src/storage/collection_pinning.rs`) — pin/unpin + tier override.
* `DirectoryLoadStatus` (`src/storage/engines/sst/object_economy_directory.rs`) — warm/cold marker.
* Route-health diagnostics (`GET /api/v2/_diagnostics/collections/:id/route-health`) — observability.
* Tiering engine (`src/storage/tiering/`) — eviction/promotion mechanics.

Chains off F2: suspend/resume is only attractive if the warm-up is in the seconds class. Pairs with
F1's trigger arm: a suspended collection warms only when a triggered discovery job (or a live query)
actually needs it.

==== Outline tasks

* [ ] `suspend(collection)` — release compute/index, mark sidecar cold, keep catalog metadata live.
* [ ] `resume`-on-query — lazy-warm via the F2 cold path on first access.
* [ ] Surface suspend/resume state in route-health.
* [ ] Bench: metadata-query latency while suspended + first-query warm latency.

==== Outline success criteria

1. A collection can be suspended (compute/index released) with metadata still queryable.
2. First query after suspend lazy-warms via the F2 cold path (seconds class).
3. Suspend/resume state is observable in route-health.
4. No dependency on TD-077.

_Maps to_: TD-094 · Roadmap Phase 8 / Elastic Compute And Scale-To-Zero. **Unblocked** — sequence
after F2, can run parallel to F1.

=== F4b — Multi-node elastic modes + warm-pool scheduler (TD-089) [OUTLINE, BLOCKED on TD-077]

==== HLD (outline)

Three compute modes over one logical store, cluster-wide:

* `Long-running` — today's resident server (production serving, hot indexes preloaded).
* `OnDemand` — starts in seconds, minute-billed, for interactive / cold-data work.
* `OfflineBatch` — job-scoped, released on completion; the home for F1 discovery jobs.

A warm-pool scheduler attaches a pinned snapshot to prepared compute on request and releases it on
idle, while catalog/metadata stay queryable with **zero resident compute** cluster-wide. Built on
`ClusterManager` / `NodeInfo` (`src/cluster/`) by adding a `ComputeMode` and extending
`NodeInfo.capabilities` / `load` / heartbeat.

==== Dependency and deferral

BLOCKED on **TD-077** (distributed RPC transport / failover). Sequence after F1/F2/F3/F4a make
scale-to-zero economical first. This is the full realization of the 2028 VISION "serverless
deployment mode" milestone.

==== Outline tasks

* [ ] `ComputeMode` enum + per-collection/per-request mode resolution.
* [ ] Warm-pool scheduler (attach pinned snapshot on request, release on idle) across nodes.
* [ ] Metadata queryable with no resident compute cluster-wide.
* [ ] Cost/latency model documented.

==== Outline success criteria

1. Three modes operate over the same logical store.
2. Warm-pool attach-on-request / release-on-idle works across nodes.
3. Metadata is queryable with zero resident compute.
4. A cost/latency model is documented.

_Full LLD deferred to a follow-up spec once TD-077 lands._ _Maps to_: TD-089 · Roadmap Phase 8 /
Elastic Compute And Scale-To-Zero.
