== Overview

This document catalogs the design patterns used in ProximaDB, patterns planned for adoption, and anti-patterns to avoid. It serves as a reference for contributors and architects extending the system.

ProximaDB is a multi-model vector database with six specialized storage engines, three graph engines, and a unified query layer. The patterns described here reflect deliberate architectural choices -- some proven in production, some planned for future iterations. Each pattern includes its rationale, trade-offs, and reference implementations so that contributors can make informed decisions when extending the system.

== Storage Engine Patterns

=== LSM-Tree (Log-Structured Merge-Tree)

**Used by**: SST Engine

**When to use**: Write-heavy workloads with read-mostly search patterns. Real-time vector ingestion.

**How ProximaDB uses it**: The SST engine implements a classic LSM-Tree pipeline:

. WAL write for durability
. Insert into active Memtable
. Memtable becomes Immutable Memtable when full
. Background flush to SSTable on disk
. Periodic compaction merges SSTables across levels

Search follows a three-stage path: memtable (in-memory, latest data) -> L0 SSTables (recently flushed) -> merged levels (compacted, optimized).

**Trade-offs**:

* Excellent write throughput (~5ms search at 10K vectors)
* Write amplification during compaction (data rewritten multiple times)
* Space amplification from maintaining multiple levels before compaction
* Read amplification for point lookups (must check multiple levels)

**Reference implementations**: RocksDB, LevelDB, Apache Cassandra

=== B-Tree

**Used by**: SWIFT Engine (internal index structures)

**When to use**: Point lookups and range scans on small datasets (<5K vectors). Low-latency reads where write volume is modest.

**How ProximaDB uses it**: The SWIFT engine uses a three-tier architecture for ultra-low latency. B-Tree indexes enable fast traversal and ordered access. Optimized for datasets where the entire index fits in memory.

**Trade-offs**:

* Fast reads with predictable latency
* Slower writes than LSM (in-place updates, page splits)
* Good for static or slowly-changing datasets
* Not ideal for bulk ingestion scenarios

**Reference implementations**: PostgreSQL, SQLite, BoltDB

=== Columnar Storage

**Used by**: VIPER (Parquet), NOVA (Progressive Columnar)

**When to use**: Analytics workloads, batch processing, column-level filtering. Arrow-native ML pipelines where only specific dimensions are needed.

**How ProximaDB uses it**: VIPER uses Apache Parquet format natively, providing excellent compression and compatibility with the broader data ecosystem. NOVA uses progressive columnar storage with hierarchical statistics, enabling early termination when query predicates can be resolved from column metadata alone.

**Trade-offs**:

* Excellent compression ratios (similar values stored together)
* Strong analytical query performance (read only needed columns)
* Slower point lookups (must reconstruct rows from columns)
* Better for read-heavy analytics than real-time ingestion

**Reference implementations**: Apache Parquet, Apache Arrow, DuckDB

=== Time-Partitioned Storage

**Used by**: TST Engine (`src/storage/engines/tst/` — partitions, ASOF join, OHLC, downsampling, recovery; implemented, status corrected 2026-10-15)

**When to use**: Time-series data with natural time ordering. OHLC bars, sensor readings, metrics, and any data with a dominant time dimension.

**Implementation** (originally planned shape):

* Time-partitioned columnar segments where each partition covers a fixed time window (e.g., 1 day)
* Automatic partition pruning on time-range queries eliminates scanning irrelevant data
* ASOF join support for point-in-time lookups (find the last known value at a given timestamp)
* Partition lifecycle management (automatic archival, compression tier changes, partition dropping)

**Trade-offs**:

* Excellent time-range query performance through partition pruning
* Natural data lifecycle management (drop old partitions without rewriting)
* Not suited for non-temporal data or queries without time predicates
* Partition boundary effects (queries spanning partitions incur merge overhead)

**Reference implementations**: QuestDB, TimescaleDB, InfluxDB

=== Hilbert Curve Mapping

**Used by**: HELIX Engine

**When to use**: Spatial locality optimization. High-dimensional vectors with locality-sensitive access patterns where preserving neighborhood relationships improves cache performance.

**How ProximaDB uses it**: The HELIX engine maps high-dimensional vectors to 1-D Hilbert curve values. This preserves spatial locality -- vectors that are close in high-dimensional space remain close on the 1-D curve. PCA dimensionality reduction is applied before mapping to manage computational cost.

----

    VEC[High-Dimensional Vector] --> PCA[PCA Reduction]
    PCA --> HILBERT[Hilbert Curve Mapping]
    HILBERT --> SORT[1-D Sorted Storage]
    SORT --> SCAN[Cache-Friendly Sequential Scan]

    style VEC fill:#4a90e2,stroke:#2e5c8a,color:#000
    style PCA fill:#4a90e2,stroke:#2e5c8a,color:#000

    style SORT fill:#4a90e2,stroke:#2e5c8a,color:#000

----

**Trade-offs**:

* Excellent locality preservation for cache-friendly access patterns
* Novel approach -- a unique differentiator for ProximaDB
* Computational overhead for Hilbert mapping (amortized at write time)
* PCA step introduces approximation (dimensionality loss)

**Reference implementations**: Unique to ProximaDB

== Consensus and Replication Patterns

=== Raft Consensus (Planned)

**When to use**: Metadata replication, leader election, and linearizable reads in distributed deployment. Required when ProximaDB scales beyond a single node.

**Planned approach**: Multi-Raft pattern -- one Raft group per collection shard, not a single global Raft group. This avoids the bottleneck of a single consensus group handling all writes. Inspired by TiKV's Multi-Raft architecture.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph Shard1[Collection Shard 1]
        L1[Leader] --> F1A[Follower A]
        L1 --> F1B[Follower B]
    end
    subgraph Shard2[Collection Shard 2]
        L2[Leader] --> F2A[Follower A]
        L2 --> F2B[Follower B]
    end
    subgraph Shard3[Collection Shard 3]
        L3[Leader] --> F3A[Follower A]
        L3 --> F3B[Follower B]
    end

    style L1 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style L2 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style L3 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style F1A fill:#fff,stroke:#2e5c8a,color:#000
    style F1B fill:#fff,stroke:#2e5c8a,color:#000
    style F2A fill:#fff,stroke:#2e5c8a,color:#000
    style F2B fill:#fff,stroke:#2e5c8a,color:#000
    style F3A fill:#fff,stroke:#2e5c8a,color:#000
    style F3B fill:#fff,stroke:#2e5c8a,color:#000
----

**Trade-offs**:

* Strong consistency guarantees (linearizable reads and writes)
* Higher write latency (quorum required for every write)
* Minimum 3 nodes for fault tolerance
* Operational complexity (member changes, snapshotting, log compaction)

**Reference implementations**: TiKV (Multi-Raft), CockroachDB, etcd

=== WAL-First Durability

**Used by**: All engines, ORION graph engine

**Pattern**: Every write follows a strict ordering:

. Write to WAL (persistent)
. Insert into memtable (in-memory)
. Acknowledge to client
. Background flush from memtable to persistent storage

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart LR
    CLIENT[Client Write] --> WAL[WAL Write]
    WAL --> MEM[Memtable Insert]
    MEM --> ACK[Ack to Client]
    MEM -.-> FLUSH[Background Flush]
    FLUSH -.-> DISK[Persistent Storage]

    style CLIENT fill:#fff,stroke:#2e5c8a,color:#000
    style WAL fill:#4a90e2,stroke:#2e5c8a,color:#000
    style MEM fill:#4a90e2,stroke:#2e5c8a,color:#000
    style ACK fill:#fff,stroke:#2e5c8a,color:#000
    style FLUSH fill:#fff,stroke:#2e5c8a,color:#000
    style DISK fill:#fff,stroke:#2e5c8a,color:#000
----

**How ProximaDB uses it**: Global WAL manifest with parallel recovery (10 threads). Cloud-optimized for S3, Azure Blob, and GCS backends. Graph operations in ORION await WAL writes before acknowledging, ensuring durability even for graph mutations.

**Key property**: Crash recovery replays WAL to restore all committed state. No committed write is ever lost.

**Reference implementations**: PostgreSQL, SQLite, RocksDB

== Query Optimization Patterns

=== Cost-Based Optimization (CBO)

**Used by**: FederatedQueryContext, CrossModelOptimizer

**Pattern**: Estimate cost of different query plans based on statistics (cardinality, selectivity, I/O cost). Enumerate candidate plans and choose the one with the lowest estimated cost.

**How ProximaDB uses it**: Cross-model cost estimation spanning vector, graph, document, and observability queries. Join reordering and predicate pushdown across models. The optimizer considers engine-specific costs -- an SST search has different cost characteristics than a VIPER columnar scan.

=== RL-Based Adaptive Planning

**Used by**: RL Query Planner (`src/query/rl_planner/`)

**Pattern**: Thompson Sampling for exploration-exploitation balance. Experience replay buffer for batch learning from past query executions.

**How ProximaDB uses it**: The RL planner learns optimal query strategies over time by observing actual execution metrics. It supports multiple optimization goals: MinLatency, MaxRecall, MaxThroughput, and Balanced. All executions are logged to JSONL for offline analysis and model retraining.

**Trade-offs**:

* Adapts to workload patterns over time (outperforms static CBO for recurring query types)
* Cold start problem -- needs initial exploration phase where some queries may be suboptimal
* Requires sufficient query volume to converge on good strategies
* Unique to ProximaDB

=== Progressive Cascade Search

**Used by**: All vector engines

**Pattern**: Multi-stage filtering pipeline that progressively refines the candidate set, reducing the number of expensive exact distance computations.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    INPUT[Query Vector] --> S1[Stage 1: Binary Quantization Filter]
    S1 -->|Candidates reduced 10x| S2[Stage 2: INT8 Re-ranking]
    S2 -->|Candidates reduced 10x| S3[Stage 3: Exact Distance Computation]
    S3 --> RESULT[Top-K Results]

    style INPUT fill:#fff,stroke:#2e5c8a,color:#000
    style S1 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style S2 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style S3 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style RESULT fill:#fff,stroke:#2e5c8a,color:#000
----

**How ProximaDB uses it**:

* Stage 1: Binary quantization (1-bit per dimension) -- extremely cheap Hamming distance, eliminates ~90% of candidates
* Stage 2: INT8 quantization -- moderate cost, SIMD-accelerated dot products
* Stage 3: Full-precision distance computation on the surviving candidate set

This typically results in 10-100x fewer exact distance computations compared to brute-force search. Every stage is SIMD-accelerated (AVX2/AVX512 on x86_64, NEON on ARM64).

== Caching Patterns

=== Cache-Aside

**Used by**: UnifiedCachingFilesystem

**Pattern**: Application checks cache first. On cache miss, reads from storage and populates cache for subsequent requests.

**How ProximaDB uses it**: Multi-tier cache hierarchy:

. Memory cache (fastest, limited by RAM)
. Disk cache (fast, larger capacity)
. Cloud storage (slowest, unlimited capacity)

CacheOrchestrator manages tier promotion and eviction. Supports LRU, LFU, and Adaptive eviction policies that can be configured per collection.

=== Write-Through (WAL)

**Used by**: WAL subsystem

**Pattern**: Writes go to both cache (memtable) and persistent store (WAL) synchronously. The write is only acknowledged after both succeed.

**Key property**: Data is durable immediately after acknowledgment. No data loss on crash. This differs from write-back caching where persistence is deferred.

=== Read-Through Codebook Cache

**Used by**: Product Quantization system

**Pattern**: Global codebook cache shared across all concurrent queries. On cache miss, the codebook is loaded from storage and cached. Subsequent queries reuse the cached codebook.

**How ProximaDB uses it**: PQ codebooks are expensive to load (they contain the centroids learned during quantization training). The global cache ensures each codebook is loaded at most once, amortizing the cost across all queries that use that codebook.

== Architectural Patterns

=== Engine-Per-Workload

This is the core ProximaDB architectural pattern. Instead of one storage engine for all data, ProximaDB uses specialized engines optimized for each workload type.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    API[Unified API Layer] --> SVC[Service Layer]
    SVC --> FACTORY[Engine Factory]
    FACTORY --> SST[SST Engine\nWrite-Heavy]
    FACTORY --> HELIX[HELIX Engine\nSpatial Locality]
    FACTORY --> VIPER[VIPER Engine\nColumnar Analytics]
    FACTORY --> SWIFT[SWIFT Engine\nUltra-Low Latency]
    FACTORY --> NOVA[NOVA Engine\nProgressive Columnar]
    FACTORY --> RAPTOR[RAPTOR Engine\nAdaptive Row-Group]

    style API fill:#4a90e2,stroke:#2e5c8a,color:#000
    style SVC fill:#4a90e2,stroke:#2e5c8a,color:#000
    style FACTORY fill:#4a90e2,stroke:#2e5c8a,color:#000
    style SST fill:#fff,stroke:#2e5c8a,color:#000
    style HELIX fill:#fff,stroke:#2e5c8a,color:#000
    style VIPER fill:#fff,stroke:#2e5c8a,color:#000
    style SWIFT fill:#fff,stroke:#2e5c8a,color:#000
    style NOVA fill:#fff,stroke:#2e5c8a,color:#000
    style RAPTOR fill:#fff,stroke:#2e5c8a,color:#000
----

**Rationale**: A vector search engine optimized for LSM (SST) has fundamentally different requirements than a columnar analytics engine (VIPER) or a time-series engine (TST). No single design can be optimal for all workloads.

**Implementation**: The `UnifiedStorageEngine` trait defines the contract all engines must satisfy. A factory pattern in `src/storage/engines/factory.rs` handles engine selection. AutoML-based engine recommendation is planned to automatically choose the best engine based on workload profiling.

**Trade-offs**:

* Best-in-class performance for each workload type
* Higher system complexity (six engines to maintain)
* Users must understand engine differences (mitigated by automatic selection and documentation)

=== Proto-First Pipeline

All API types are defined in Protocol Buffers. The `VectorRecord` type flows from the API layer through the service layer to storage without intermediate type conversions.

**Rationale**: Zero-copy principle -- eliminating serialization/deserialization between layers. Single source of truth for types across Rust, Python, Java, and other language bindings. Cross-language compatibility is automatic.

**Implementation**: Types defined in `proto/proximadb.proto` and `proto/proximadb/v1/*.proto`. Serde compatibility annotations enable JSON/REST serialization without additional type definitions.

=== Zero-Copy Memory Sharing

**Used by**: ORION graph engine, Arrow integration

**Pattern**: Arc-based (atomically reference counted) memory sharing instead of data copying. Multiple readers share the same memory allocation through reference counting.

**How ProximaDB uses it**:

* CSR (Compressed Sparse Row) graph format with Arc-based adjacency lists -- graph traversals share the underlying edge data without copying
* Arrow RecordBatch sharing for query results -- results are passed between pipeline stages without serialization

**Reference**: Apache Arrow zero-copy semantics

== Application-Level Patterns

=== CQRS (Command Query Responsibility Segregation)

**Planned for**: Trading workloads, event-driven architectures

**Pattern**: Separate the write path (commands) from the read path (queries). Commands go through validation, then to an event store, then to projections that build materialized views. Queries read exclusively from materialized views.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph Commands[Command Path]
        CMD[Write Command] --> VAL[Validation]
        VAL --> EVT[Event Store]
        EVT --> PROJ[Projections]
    end
    subgraph Queries[Query Path]
        QRY[Read Query] --> MAT[Materialized Views]
        MAT --> IDX[Indexes]
    end
    PROJ --> MAT

    style CMD fill:#4a90e2,stroke:#2e5c8a,color:#000
    style VAL fill:#4a90e2,stroke:#2e5c8a,color:#000
    style EVT fill:#4a90e2,stroke:#2e5c8a,color:#000
    style PROJ fill:#4a90e2,stroke:#2e5c8a,color:#000
    style QRY fill:#fff,stroke:#2e5c8a,color:#000
    style MAT fill:#fff,stroke:#2e5c8a,color:#000
    style IDX fill:#fff,stroke:#2e5c8a,color:#000
----

**Why for ProximaDB**: Trading applications like ibkrtrading use CQRS naturally -- order commands are validated and persisted separately from position queries that read materialized state. ProximaDB formalizes this with an event sourcing engine for the command path and document store materialized views for the query path.

=== Event Sourcing

**Planned for**: Audit trails, compliance, trading event logs

**Pattern**: An append-only immutable event log. Current state is derived by replaying events from the log. Events are never updated or deleted.

**Key properties**:

* Complete audit trail -- every state change is recorded
* Temporal queries -- reconstruct state at any point in time
* Natural CDC source -- the event log _is_ the change stream
* Compliance-ready -- immutability satisfies regulatory requirements

**Why for ProximaDB**: MiFID II and SEC compliance require immutable event logs for trading activity. Applications like ibkrtrading generate 119MB of events per day that must be stored immutably and queryable historically.

=== Saga Pattern

**Planned for**: Cross-model transactions

**Pattern**: A sequence of local transactions with compensating actions. If step N fails, compensate steps 1 through N-1 in reverse order.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart LR
    T1[Step 1:\nVector Insert] --> T2[Step 2:\nGraph Edge]
    T2 --> T3[Step 3:\nDocument Write]
    T3 -->|Success| DONE[Committed]
    T3 -->|Failure| C2[Compensate:\nRemove Edge]
    C2 --> C1[Compensate:\nDelete Vector]

    style T1 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style T2 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style T3 fill:#4a90e2,stroke:#2e5c8a,color:#000
    style DONE fill:#fff,stroke:#2e5c8a,color:#000
    style C2 fill:#fff,stroke:#2e5c8a,color:#000
    style C1 fill:#fff,stroke:#2e5c8a,color:#000
----

**Why for ProximaDB**: Atomic writes across vector + graph + document + event stores require coordination. Full two-phase commit (2PC) is too expensive and brittle for multi-model writes. The saga pattern provides eventual consistency with explicit compensation logic.

=== Sidecar Deployment

**Used by**: Embedded mode

**Pattern**: The database runs in-process alongside the application. Zero network latency between application logic and database operations.

**How ProximaDB uses it**: Language bindings enable embedded deployment:

* PyO3 bindings for Python
* JNI for Java
* NAPI-RS for Node.js
* C FFI for Go, C, and C++

**Why**: Trading applications require sub-millisecond latency. Embedded mode eliminates network overhead entirely -- a vector search that takes 5ms over the network takes 5ms in embedded mode minus the network round trip.

== Anti-Patterns to Avoid

[cols="1,2,2"]
|===
| Anti-Pattern | Why It Is Bad | What to Do Instead

| Using `unwrap()`/`expect()` in production code
| Panics crash the entire process. There are currently 11,536 instances in the codebase.
| Use `Result<T, Error>` and the `?` operator. Reserve `unwrap()` for truly impossible cases with extensive justification comments.

| Advertising experimental features as production-ready
| Erodes user trust when features break or underperform. PULSAR and QUASAR were retired as graph engine surfaces to remove this risk.
| Prefer removing unsupported surfaces over advertising partial implementations. Document maturity levels clearly in both code and user-facing docs.

| One-size-fits-all storage engine
| No single engine design is optimal for all workloads. Forcing all data through one path creates performance bottlenecks.
| Engine-per-workload pattern. Automatic engine selection based on workload profiling.

| Tight coupling between API and storage layers
| Makes it impossible to swap engines, add new data models, or evolve the API independently.
| Service layer abstraction. All storage access through the `UnifiedStorageEngine` trait.

| Custom SQL parser for everything
| Cannot compete with mature, battle-tested parsers. Custom parsers accumulate edge-case bugs.
| Use DataFusion or sqlparser-rs as the SQL execution layer. Custom extensions only for multi-model functions (VECTOR_SEARCH, GRAPH_QUERY, etc.).

| Premature distributed architecture
| Distributed consensus adds massive complexity to debugging, testing, and operations.
| Prove single-node correctness first. Add Raft only when scaling demands require it.

| Mocking in tests
| Masks real integration issues. Tests pass in CI but production fails because the mock did not match reality.
| Test against real implementations. Use temporary directories and real engine instances. Reserve mocks for external service boundaries only.
|===
