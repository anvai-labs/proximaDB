== Wire / Storage Layouts

This section locks every byte that goes to disk or the wire under the new
precision contract. Examples assume a single 1024-dim BGE-large embedding;
the contract generalizes to any dim.

=== WAL segment header (Q5)

Each WAL segment begins with a header that advertises the default precision
the segment was written under. Readers fast-path against this for buffer
sizing; per-record tags (below) are the authoritative source.

[source]
----
| magic (4 B)  | version (2 B) | header_len (2 B) | flags (4 B)
| segment_id (16 B = u128 ULID) | created_at_ns (8 B = i64)
| canonical_default_precision (1 B = EmbeddingScalarType discriminant)
| precision_epoch (8 B = u64)
| policy_id_len (2 B) | policy_id (UTF-8 bytes)
| policy_version (8 B = u64)
| reserved (8 B = zero, future use)
----

`magic` = `b"PWAL"`. `version` starts at 2 when the precision-aware schema
ships; v1 segments (pre-precision) have `version = 1` and no precision
fields after the timestamp.

Read path:

. Read first 6 bytes, check magic + version.
. If `version == 1`, dispatch to the legacy reader (today's path); treat
  every embedding as `Fp32`.
. If `version >= 2`, parse header fully, then read records.

`canonical_default_precision` is an optimization hint, not a contract:
records inside the segment MAY override it via their per-record tag.
This supports mixed-precision segments during epoch transitions without
forcing compaction first.

=== Per-record `EmbeddingCell` byte layout (Q5, Q6, Q8)

Custom `Serialize`/`Deserialize` impls live on `EmbeddingValues` in
`crates/foundation/proximadb-records/src/lib.rs`. Bincode handles the
surrounding `EmbeddingCell` struct; we override only the values payload.

Single `EmbeddingCell` on disk:

[source]
----
| model_id_len (varint)        | model_id bytes (UTF-8)
| modality_len (varint)        | modality bytes (UTF-8)
| dim (varint = u32)
| precision (1 B = EmbeddingScalarType discriminant)
| values_payload (variable, see below)
| precision_epoch (1 B tag = 0 None | 1 Some) | epoch_bytes (8 B if Some)
----

Discriminant byte for `EmbeddingScalarType`:

[cols="1,1,3"]
|===
| Value | Variant | Notes

| 0x01 | Fp32 | 4N bytes LE
| 0x02 | Fp16 | 2N bytes LE
| 0x03 | Bf16 | 2N bytes LE (reserved Phase 6)
| 0x04 | Int8Scalar | 1N bytes + 4 B scale (f32 LE) + 1 B zero_point
| 0x05 | UInt8Scalar | 1N bytes + 4 B scale (f32 LE) + 1 B zero_point
| 0x00 | Reserved | Reject on read; never written
| 0xFE | Reserved migration | Reject on read; explicit "do not deserialize"
|===

`values_payload` per variant (LE, no padding):

[source]
----
Fp32:
  | f32_le * dim (= 4*dim bytes)

Fp16:
  | u16_le * dim (= 2*dim bytes, bit-cast from half::f16)

Bf16:
  | u16_le * dim (reserved)

Int8Scalar:
  | i8 * dim (= dim bytes)
  | scale (4 B f32 LE)
  | zero_point (1 B i8)

UInt8Scalar:
  | u8 * dim (= dim bytes)
  | scale (4 B f32 LE)
  | zero_point (1 B u8)
----

The `u16` bit-cast approach (Q6, option C-equivalent in implementation
even though we labeled it B) avoids any dependency on `half` crate's
serde impls. The custom `Serialize` implementation:

[source,rust]
----
impl Serialize for EmbeddingValues {
    fn serialize<S: Serializer>(&self, s: S) -> Result<S::Ok, S::Error> {
        let mut seq = s.serialize_tuple(2)?;
        match self {
            Self::Fp32(v) => {
                seq.serialize_element(&0x01u8)?;
                seq.serialize_element(&v[..])?;
            }
            Self::Fp16(v) => {
                seq.serialize_element(&0x02u8)?;
                let bits: Vec<u16> = v.iter().map(|x| x.to_bits()).collect();
                seq.serialize_element(&bits)?;
            }
            // ... bf16, int8, uint8
        }
        seq.end()
    }
}
----

Endianness (Q8): all multi-byte scalars are little-endian. At server
startup, `apps/proximadb-server/src/main.rs` asserts:

[source,rust]
----
#[cfg(target_endian = "big")]
compile_error!("proximadb does not support big-endian targets; \
                target a little-endian arch (x86_64, aarch64, etc.)");
----

This is a compile-time check, not runtime — even cleaner.

=== `EmbeddingScalarType` and `EmbeddingValues` (Q6, Q9)

[source,rust]
----
// crates/foundation/proximadb-records/src/lib.rs

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[repr(u8)]
pub enum EmbeddingScalarType {
    Fp32 = 0x01,
    Fp16 = 0x02,
    Bf16 = 0x03,    // reserved Phase 6
    Int8Scalar = 0x04,
    UInt8Scalar = 0x05,
}

#[derive(Debug, Clone, PartialEq)]
pub enum EmbeddingValues {
    Fp32(Vec<f32>),
    Fp16(Vec<half::f16>),
    Bf16(Vec<half::bf16>),
    Int8Scalar { values: Vec<i8>, scale: f32, zero_point: i8 },
    UInt8Scalar { values: Vec<u8>, scale: f32, zero_point: u8 },
}

pub struct EmbeddingCell {
    pub model_id: String,
    pub modality: String,
    pub dim: u32,
    pub precision: EmbeddingScalarType,
    pub values: EmbeddingValues,
    /// Snapshot of the precision epoch the cell was written under. None when
    /// migration-state metadata is absent (pre-policy records).
    pub precision_epoch: Option<u64>,
}

impl EmbeddingCell {
    /// Borrow as `&[f32]` if the cell is already fp32. Returns None if
    /// the cell is in any other precision — callers must explicitly
    /// promote via `to_fp32_owned`.
    pub fn as_fp32_slice(&self) -> Option<&[f32]> { ... }

    /// Promote to owned `Vec<f32>` from any precision. Allocates.
    /// Used by legacy fp32-only code paths during the migration window.
    pub fn to_fp32_owned(&self) -> Vec<f32> { ... }

    /// Byte size of the on-disk payload for this cell (without the
    /// surrounding metadata). Used by storage budget enforcement.
    pub fn values_byte_size(&self) -> usize { ... }
}
----

Per-cell precision inherits from the model route (Q9): when the embedding
service produces an `EmbeddingCell`, it sets `precision` from the
`EmbedRoute`'s declared precision. There is no per-cell client API. This
keeps multi-modal records (text + image cells with different routes)
naturally heterogeneous without client-side burden.

=== PAX block per-column alignment (Q7)

PAX block header gets a per-column alignment table.

[source]
----
PAX block header:
  | magic (4 B) | version (2 B) | num_columns (2 B)
  | column_table (num_columns entries of 8 B each):
      | column_id (2 B) | scalar_type (1 B) | alignment (1 B)
      | offset (4 B = u32 from block start)
  | row_count (4 B)
  | reserved (4 B)
  | per-column payloads, each padded to its declared alignment
----

`alignment` is encoded as `log2(bytes)` so 1 byte covers 1, 2, 4, 8, 16-byte
alignments. fp32 → 2 (4 B), fp16/bf16 → 1 (2 B), int8/uint8 → 0 (1 B).

Reader path:

. Parse block header.
. For each column, seek to `offset` (which respects alignment).
. Memmap'd reads against fp16 columns are 2-byte aligned and safe to cast
  to `&[u16]` then bit-cast to `&[f16]`.

=== Schema version dispatch on read (Q17)

`ProximaRecord` gains a `schema_version` byte:

[source,rust]
----
pub struct ProximaRecord {
    pub schema_version: u8,    // NEW: 1 = legacy, 2 = precision-aware
    pub oid: String,
    pub embeddings: Vec<EmbeddingCell>,
    pub props: ProximaTree,
    // ... existing fields
}
----

`schema_version == 1` deserialization path: every `EmbeddingCell.values`
is read as `Vec<f32>` (the current shape); `precision` is set to
`Fp32`; `precision_epoch` is `None`.

`schema_version == 2` deserialization path: read the explicit precision
discriminant and dispatch to the correct payload reader.

Default for newly serialized records: 2 (once the feature flag is on).
Default while the feature flag is off: 1 (backward compatible).

== Feature Flag and Rolling Deploy (Q18)

Env var: `PROXIMADB_EMBED_PRECISION_SCHEMA_V2` (`true` | `false`, default `false`).

Behavior:

[cols="1,3"]
|===
| Setting | Effect

| `false` (default)
| Server READS both v1 and v2 records (dispatches by `schema_version` byte).
Server WRITES v1 records. Old binaries can keep up.

| `true`
| Server READS both v1 and v2. Server WRITES v2. Operator flips this only
after every node in the cluster is on a binary that supports both reads.
|===

Rollout sequence:

. Phase 2 binaries deploy with flag OFF. Cluster is unchanged on the wire.
. Operator verifies every node is on the new binary (`/version` endpoint
  returns `precision_schema_v2_capable: true`).
. Operator flips the flag ON, one node at a time, rolling restart.
. Once all nodes are flipped, the cluster is writing v2.
. Old segments stay v1 until compaction rewrites them (lazy migration);
  per-segment header already declares the schema version so readers
  dispatch correctly forever.

Rollback: flip the flag OFF. Server returns to writing v1. Previously-
written v2 records remain on disk and are readable by all nodes
(because every Phase 2+ binary can read both).

=== Per-metric recall gate defaults (Q13)

Hardcoded defaults that operators can override per policy:

[cols="2,1,1,1"]
|===
| Distance metric | recall@10 default | recall@100 default | Rationale

| Cosine
| 0.99
| 0.995
| L2-normalized vectors; fp16 truncation is masked by the normalization step.

| L2
| 0.99
| 0.995
| Similar to cosine in fp16 truncation sensitivity for typical embeddings.

| Dot product (un-normalized)
| 0.995
| 0.998
| Raw magnitude matters; fp16 small-magnitude truncation directly affects ranking.

| Hamming (binary)
| n/a (binary path uses different gating)
| n/a
| Binary precision is derived-only; gate handled by binary candidate count.
|===

=== Embedding service boundary downconversion (Q15)

Inside `BgeModel::embed_batch_onnx` and the external HTTP clients
(OpenAI/Cohere/Azure/Byo), each path returns its native output type. A
shared adapter then downcasts to the collection's canonical precision
BEFORE writing to the canonical store:

[source,rust]
----
// crates/modalities/proximadb-embedding/src/precision/boundary.rs

pub fn project_to_canonical(
    output: EmbeddingOutput,
    canonical: EmbeddingScalarType,
) -> EmbeddingValues {
    match (output, canonical) {
        (EmbeddingOutput::Fp32(v), EmbeddingScalarType::Fp32) => EmbeddingValues::Fp32(v),
        (EmbeddingOutput::Fp32(v), EmbeddingScalarType::Fp16) => {
            EmbeddingValues::Fp16(v.iter().map(|&x| half::f16::from_f32(x)).collect())
        }
        (EmbeddingOutput::Fp16(v), EmbeddingScalarType::Fp32) => {
            EmbeddingValues::Fp32(v.iter().map(|x| x.to_f32()).collect())
        }
        (EmbeddingOutput::Fp16(v), EmbeddingScalarType::Fp16) => EmbeddingValues::Fp16(v),
        // ... bf16 + int8 paths
    }
}
----

External OpenAI/Cohere clients use this projector; the inference path is:

[source]
----
HTTP response (fp32 JSON / ProtoBuf)
    -> Vec<f32>
    -> project_to_canonical(Fp32(v), collection.canonical_precision)
    -> EmbeddingValues (canonical type)
    -> EmbeddingCell { precision, values, ... }
    -> ProximaRecord write
----

== EmbedRoute Schema Additions (Q16)

[source,rust]
----
// crates/modalities/proximadb-embedding/src/config.rs

pub enum EmbedRoute {
    BgeSmall,
    BgeLarge,
    BgeM3,
    AzureOpenAi { model: AzureModel },
    OpenAi { model: OpenAiModel },
    Cohere { model: CohereModel },
    Byo {
        url: String,
        auth: ByoAuth,
        declared_dim: usize,
        declared_precision: EmbeddingScalarType,  // NEW (Q16)
        batch_size: usize,
        timeout_ms: u64,
    },
}

impl EmbedRoute {
    /// Native precision the route's model emits at the wire level.
    pub fn native_precision(&self) -> EmbeddingScalarType {
        match self {
            // BGE in-process: emits fp32 (current ORT default) or fp16
            // depending on which ONNX is staged. Detect from session metadata.
            Self::BgeSmall | Self::BgeLarge | Self::BgeM3 => {
                // Resolved at session-load time; cached on the BgeModel.
                bge::current_loaded_precision()
            }
            // External APIs all return fp32 JSON at the wire today.
            Self::AzureOpenAi { .. } | Self::OpenAi { .. } | Self::Cohere { .. } => {
                EmbeddingScalarType::Fp32
            }
            Self::Byo { declared_precision, .. } => *declared_precision,
        }
    }
}
----

Bincode/serde compat: missing `declared_precision` on legacy `Byo` JSON
defaults to `Fp32` (matches today's behavior).

    Fresh,
    /// Canonical precision changed since training; safe for lossy candidate
    /// generation (rerank against canonical is still correct), but should
    /// be retrained.
    Stale { since_epoch: u64 },
    /// Currently being retrained against the new canonical precision.
    Retraining,
}
----

Precision epoch bump flow:

. xCatalog bumps `current_precision_epoch` on a collection.
. Migration job (`src/storage/operations/requantization.rs`) marks all
  codebooks for that collection as `Stale { since_epoch: <new_epoch> }`.
. New writes route to new precision; reads still use stale codebooks for
  candidate generation (with rerank-against-canonical guaranteeing
  correctness).
. Background retraining task picks up stale codebooks, samples vectors
  from the new precision, trains new centroids, atomically swaps to
  `Fresh`.
. Once all codebooks are `Fresh` and all segments are at the new epoch,
  `precision_migration_state.status` flips to `completed`.

== Acceptance Criteria

A precision change is shippable to a tenant tier when ALL of:

. The recall harness (PR 11) reports recall@10 / recall@100 within the
  per-metric gates (Q13).
. Storage overhead stays below the policy's `max_overhead_ratio`.
. Search latency p95 regression is within the policy's
  `max_latency_regression_pct`.
. EXPLAIN ANALYZE exposes the new precision config and references the
  recall report.
. Migration progress observability (Q11) reports `status: completed`
  for at least one synthetic collection of representative size.
. Rolling-deploy validation: bring up a 3-node cluster with mixed
  binaries (one OFF flag, two ON flag), verify reads succeed across all
  nodes.

== Phase 3 Plan: Int8 Canonical

=== Why int8 deserves a phase of its own

Int8 canonical is the next storage tier after fp16 — 4× compression vs fp32 (vs fp16's 2×) and ~2–3× QPS over fp16 on hardware with native int8 dot product (Intel VNNI / AVX-512 VPDPBUSD, ARM SDOT/UDOT, NVIDIA DP4A). On a 100M-row 1024-dim BGE-large collection, that's 800 GB → 200 GB raw storage and a roughly 4× total throughput improvement over the fp32 baseline.

The cost is that int8 is fundamentally lossy in a way fp16 isn't. fp16 has 11-bit mantissa precision; int8 has 8 bits *total* and depends on a per-vector scale to reconstruct the original range. Calibration mistakes show up as recall regressions that the §Q13 gates would (correctly) refuse to ship. Phase 3 exists to make calibration disciplined and rerank-against-canonical non-negotiable so the lossy storage is invisible to the user-facing recall.

=== Acceptance gates (stricter than Phase 2)

A precision change to int8 canonical is shippable when ALL of:

. **Recall@10 ≥ 0.95** on the candidate-only path (no rerank), measured by the PR 11 harness on three datasets: SIFT-1M, GloVe-100, AND a production-distribution sample.
. **Recall@10 ≥ 0.99 with rerank-against-canonical** (the LLD's `rerank_with: Fp32Promoted` policy). Rerank cannot be disabled by the user for int8 canonical collections.
. **Storage overhead ratio ≤ 1.25×** the int8 canonical size (vs Phase 2's 2× allowance) — int8's compression budget is too tight to spend on derived levels.
. **CREATE TABLE refuses to set `canonical = Int8Scalar` without an explicit `ACKNOWLEDGE LOSSY` clause** (UX disclosure requirement called out in the deferred-items rationale).
. **30-day production trial** on at least one Business or Enterprise tenant collection before the default-policy flip to int8-allowed.
. **Calibration metadata is committed to the catalog**, not recomputed at write-time, so rolling a single bad calibration is a catalog operation rather than a re-quantization sweep.

=== Phase 3 PR sequence (twelve PRs, same isolation discipline as Phase 2)

==== Calibration infrastructure

`crates/modalities/proximadb-embedding/src/precision/calibration/`:

* **PR 3.1 — Calibrator trait + builtin strategies.** Plug-in `Calibrator` trait with `SymmetricMaxAbs` (today's naive default), `AsymmetricMinMax`, `PercentileClip { p99_5 }`, `KlDivergence`. Per-strategy unit tests on synthetic distributions. The PR 1 `EmbeddingValues::from_fp32_lossy` becomes a thin wrapper that delegates to the selected `Calibrator`.
* **PR 3.2 — Offline collection-level calibration job.** Samples N vectors from a collection's current canonical store, fits per-strategy scales, picks the strategy that minimizes round-trip MSE under the recall harness's worst-case top-K shift metric. Result is `CollectionCalibrationProfile { strategy, per_subvector_scales, fit_at_epoch }` and lives on the catalog row.

==== Distance kernels

`src/compute/distance/`:

* **PR 3.3 — int8×int8 dot product with int16 accumulators.** SIMD-vectorized: VPDPBUSD on x86 with VNNI (Cascade Lake+), SDOT on ARMv8.2+, scalar fallback elsewhere. Dequant once at the end using per-vector or per-collection scale. Per-platform throughput micro-bench feeds `HardwareCapabilities::probe()` (PR 7a extension).
* **PR 3.4 — int8 L2 distance.** Decomposes to `||a||² + ||b||² - 2·a·b`; `||x||²` can be precomputed and stored alongside the vector. Cosine reduces to dot product when vectors are L2-normalized (the common case).

==== Storage path

* **PR 3.5 — PAX per-column quantizer metadata.** Extends the PR 5 PAX header so each int8 column carries `scale: f32` and `zero_point: i8` inline. Backward-compatible: fp32/fp16 columns have a zero-length metadata trailer.
* **PR 3.6 — WAL writer emits int8 records.** Reuses the PR 3a `PROXIMADB_EMBED_PRECISION_SCHEMA_V2` feature flag + PR 8 boundary downconverter for the fp32→int8 conversion at the write boundary. WAL bytes per vector drop from 2N (fp16) to N+5 (int8 + scale + zero_point).

==== Recall safety net

* **PR 3.7 — Mandatory rerank-against-canonical for int8 collections.** Default search level becomes `int8_candidates + fp32_rerank`. The user can NOT set `rerank_with = None` on an int8 canonical collection; the catalog DDL validator refuses. Rerank pulls fp32 *shadow* vectors (PR 6a's `retain_fp32_shadow: true` for int8 collections is non-optional during Phase 3).
* **PR 3.8 — Recall harness extension.** Adds production-distribution datasets to the PR 11 harness: BEIR (12 retrieval tasks), MIRACL (multilingual), and an anonymized customer sample loader. SIFT/GloVe alone don't stress int8 calibration because they're already well-conditioned.

==== UX and disclosure

* **PR 3.9 — `ACKNOWLEDGE LOSSY` DDL clause.** `CREATE TABLE ... WITH (canonical_embedding_precision = 'int8_scalar')` returns an error unless followed by `ACKNOWLEDGE LOSSY 'recall_floor=0.95'` or similar. The acknowledgement string is recorded in the catalog row for audit.
* **PR 3.10 — Capability + dashboard.** `/version` advertises `int8_canonical_capable: true`. Grafana dashboard adds an "lossy collections" panel that surfaces `recall_at_10` prominently, with a default alert when it crosses the 0.95 floor.

==== Tier policy and rollout

* **PR 3.11 — Tier policy update.** Int8 canonical only available to Business and Enterprise tiers initially. Standard and Pro tiers can use int8-*derived* (PR 6a `QuantizationMaterialization::StorageAux`) but not int8-canonical. Free/Team blocked entirely.
* **PR 3.12 — End-to-end int8 collection scaffold.** Same pattern as PR 12 for fp16: integration test that builds an int8 collection from a synthetic corpus, exercises rerank-against-canonical, verifies recall + storage gates. Lives in `proximadb-recall-bench/tests/int8_e2e.rs`.

=== Risks and mitigations

[cols="2,3"]
|===
| Risk | Mitigation

| Calibration strategy that works on benchmark datasets fails on production distributions
| PR 3.8 requires the production-distribution sample in the harness; the PR 3.2 offline calibrator picks strategy per-collection, not globally.

| User disables rerank to chase QPS and ships recall < 0.95 to customers
| PR 3.7 makes rerank-disable structurally impossible on int8 canonical collections via the catalog DDL validator, not a runtime check.

| fp32 shadow doubles storage (defeating the int8 win)
| PR 3.7 keeps shadow only for the rerank top-K candidate set, not every vector. The shadow is a per-segment side-file that compaction sparsifies as confidence in the calibration grows.

| int8 calibration drifts as the collection's distribution evolves
| PR 3.2's profile lives in the catalog with a `fit_at_epoch`; the migration job from PR 10 marks the collection's PQ codebooks AND the calibration profile stale together on epoch bump.

| Hardware without int8 SIMD (older x86, Apple M1 pre-Neon-dot) takes a latency hit
| PR 3.3 scalar fallback is correct but slow; `HardwareCapabilities::probe()` (PR 7a) gates int8 default via a `min_int8_speedup_ratio` threshold mirroring Phase 2's fp16 gate.

| Different calibration on writer vs query side silently corrupts scores
| Reuse the PR 8 `prepare_query_matches_writer_quantization_byte_for_byte` invariant test pattern — the int8 path needs its own version covering all four `Calibrator` strategies.
|===

=== When Phase 3 starts

After Phase 2's deferred integrations land (WAL writer hookup, PAX writer hookup, BGE/HTTP client `project_to_canonical` wiring) AND at least one fp16 canonical collection is in production with 30 days of recall data showing the gates hold under real workload. The Phase 2 production data tells us where the int8 floor actually is, not where benchmark datasets suggest it might be.

== Open Items Deferred to Phase 4+

These were considered and deliberately deferred:

. **Native fp16-fp16 distance kernels.** Promote-at-compute first per Q10.
  Native kernels land in Phase 6 only if `HardwareCapabilities::probe()`
  shows a measurable win.
. **bf16 canonical.** Reserved in the enum but not implemented; Apple
  Silicon's AMX favors fp16, x86_64 AVX-512 favors bf16. Cross-platform
  policy is non-trivial. Defer until customer demand.
. **Adaptive policy auto-flip.** Phase 2 ships fixed-mode policies only.
  Adaptive (telemetry-driven default flips) lands in Phase 5 once we have
  enough production recall data.
. **1-bit / binary canonical.** 32× compression but extreme recall floor;
  only viable with mandatory rerank AND a binary-index-aware ANN engine
  (e.g. IndexBinaryFlat). Defer until int8 canonical (Phase 3) ships and
  customer demand justifies the index work.
