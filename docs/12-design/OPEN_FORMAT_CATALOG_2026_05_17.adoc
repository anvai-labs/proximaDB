= ProximaDB Open Format Catalog Architecture
:date: 2026-05-17
:revision: 1.0
:toc:
:toclevels: 3

== Overview

This document describes ProximaDB's open-format catalog architecture: the Iceberg REST Catalog server
(ADR-007), OLTP catalog backends (ADR-008), the canonical ProximaRecord → Iceberg column mapping
(ADR-ICE-001), and the size-based catalog routing policy (ADR-OLTP-001).

The goal is for ProximaDB to be a first-class catalog authority that any open-format compute engine
(Spark, Trino, DuckDB, Flink, PyIceberg) can connect to without a custom connector, while supporting
the full range from embedded SQLite-backed small datasets to petabyte-scale Parquet/Iceberg lakehouse.

For the current SQL/pgwire DML, `CopyIntoPlan`, compute-router, and external delegated write path
tracker, see
link:RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20.adoc[RELATIONAL_PGWIRE_DML_COMPUTE_BLUEPRINT_2026_05_20].

Open-format catalog support is a facade over the broader xCatalog control plane. xCatalog is not
only an Iceberg/Hive-style table catalog. It is the metadata authority for relational tables,
vector/document collections, graphs, observability datasets, streams, features, model registry
objects, agent state, projections, branches, and external authority mappings. Iceberg REST, Glue,
Hive, Unity, Polaris, Delta, and Hudi compatibility expose the subset of this metadata that those
systems can represent.

== Relation to Stacked Durability Mandate

The open-format catalog layer sits entirely at Layers 2–3 of the stacked durability hierarchy:

----
Layer 0: WAL / CanonicalOperation journal (always durable, always first)
Layer 1: ProximaRecord in VIPER/NOVA/HELIX storage engines (canonical record store)
Layer 2: Rebuildable projections — PAX segments, Iceberg manifests, CSR/COO graph topology,
         HNSW ANN fragments, time-series blocks, schema-registry publications
Layer 3: Protocol facades — Iceberg REST, Arrow Flight, REST/gRPC handlers (never own durable state)
----

* xCatalog (OLTP or lakehouse backend) stores ONLY catalog metadata: namespaces, schemas, statistics, snapshots, layouts, projections, policies, and external mappings.
* Record data always stays in ProximaDB's Layer 1 storage engines.
* PAX segments, Iceberg manifests, ANN fragments, graph topology, and time-series blocks are Layer
  2 layout/projection families with explicit freshness and repair metadata.
* Iceberg REST, Arrow Flight, Glue/Hive/Unity/Polaris adapters, and REST/gRPC handlers are Layer 3 protocol facades.

This means:

1. A catalog DB failure does NOT lose records — WAL + storage engines are the authority.
2. A catalog DB can be rebuilt from WAL replay and storage engine statistics.
3. External engines that read via Iceberg REST get a consistent view of the catalog without
   ProximaDB delegating its hot durable core to an external RDBMS.

See: `docs/12-design/RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc` §stacked durability.
See also: `docs/12-design/adr/ADR-009-schema-modes-and-proximarecord-surfaces.adoc` for the
schema-on-read/schema-on-write and API-surface convergence mandate.

== Catalog Asset Model

Every open-format object maps to a cataloged asset:

[cols="2,3,3"]
|===
| External shape | xCatalog asset role | Authority mode

| Iceberg/Delta/Hudi table
| analytical publication, imported snapshot, federated external table, or explicit external authority
| `ExportedPublication`, `ImportedSnapshot`, `RebuildableProjection`, or `ExternalAuthoritative`

| Hive/Glue database and table
| namespace plus table/asset metadata, partition metadata, classifier/source mapping
| usually external reference or imported schema; external authority only when declared

| Glue/Confluent schema subject
| schema object with version history and `ProximaType` mapping
| catalog schema authority for ProximaDB-owned assets; external reference for externally-owned streams

| Kafka/Flink/Kinesis topic
| stream asset with schema, offsets, watermarks, consumer groups, and lineage
| append-only canonical when written through ProximaDB; external authority when topic owns truth

| MLflow experiment/model
| MLOps asset under `mlops.*` with lineage, artifact references, metrics, aliases/stages
| catalog metadata authority; artifacts may live in external stores
|===

The same asset can have multiple names or protocol views. For example, a vector collection can
appear as a REST collection, a pgwire table, an Arrow Flight dataset, and an Iceberg table
publication. Those are aliases/views over one catalog asset id, not separate metadata objects.

== Open Table Authority Contract

Iceberg, Delta, and Hudi are table metadata/transaction layers over immutable data files, usually
Parquet, ORC, or Avro. They are not automatically ProximaDB's canonical durable model. Every
open-table mapping must declare one authority mode and one commit owner.

[cols="1,2,3,3"]
|===
| Mode | Commit owner | Allowed writes | Required xCatalog metadata

| `ProximaAuthoritative`
| ProximaDB WAL + `ProximaRecord`
| Writes commit through `TableRecordStore`; open-table files/manifests are publications
| source WAL range, publication snapshot, manifest/version id, freshness watermark, repair source,
policy boundary

| `ProjectionPublication`
| ProximaDB projection publisher
| Writes are indirect: canonical records first, publication after projection/update
| source asset id, source snapshot/WAL range, projection freshness, publication location,
manifest/version id, rebuild policy

| `ImportedSnapshot`
| Import job at a pinned external snapshot
| ProximaDB may write imported canonical records after validation; external source remains unchanged
| external snapshot id/version, import timestamp, schema mapping, lossy conversions, provenance,
repair/reimport source

| `FederatedRead`
| External table/source
| Read-only from ProximaDB's perspective
| external catalog reference, snapshot semantics, refresh mode, type mapping, policy boundary,
unsupported write reason

| `ExternalAuthoritative`
| External table format commit protocol
| Writes use Iceberg/Delta/Hudi atomic commit semantics and register resulting snapshot in xCatalog
| external commit protocol, snapshot/version id, isolation semantics, conflict behavior, policy
boundary, repair source, refresh mode
|===

Format-specific adapter obligations:

[cols="1,3"]
|===
| Format | Adapter must model

| Iceberg
| snapshot id, metadata file location, manifest list, manifests, data/delete files, partition spec,
schema id, sequence numbers where used, equality/position delete handling, REST catalog namespace
and table identifiers

| Delta
| table version, `_delta_log` commit files/checkpoints, add/remove file actions, protocol version,
metadata/schema action, transaction/app ids where used, deletion vectors when supported, checkpoint
loading and retention limits

| Hudi
| timeline instant, table type, base/log files, commit/delta-commit/compaction actions, record key,
precombine field, partition path, incremental query boundary, cleaner/archival retention

| Hive/Glue-style external table
| database/table, storage descriptor, partition list, serde/input format, object location,
schema/classifier source, partition refresh mode, and lack of ACID guarantees unless backed by a
table format that supplies them
|===

== Props Auto-Promotion for Iceberg Federation

The `props` column (PAX column ID 8, Iceberg type `map<string, binary>`) stores the
user-defined properties map as msgpack. External engines (Spark, Trino, DuckDB) reading
via Iceberg REST receive opaque binary values and cannot push predicates into document
fields without deserializing msgpack client-side.

**This is the primary limitation for document workloads accessed via Iceberg REST.**

=== Auto-Promotion Mechanism

`PropsAutoPromotionPolicy` (in `proximadb-catalog::lib.rs`) controls automatic promotion
of high-frequency props keys to typed PAX user columns (IDs 100+) and corresponding
Iceberg typed columns.

When promotion is enabled and a key meets the frequency threshold:

[source,text]
----
1. Background compaction job evaluates props key frequency across all PAX blocks.
2. Keys meeting frequency_threshold (default 50 %) and min_record_count (default 10,000)
   are promoted candidates.
3. xCatalog registers a schema evolution (SchemaChange::AddColumn) for the new typed column.
4. PAX compaction rewrites blocks, extracting the promoted key from the msgpack blob
   into the new typed column stripe.
5. Iceberg publication is updated with the new typed column in the next snapshot.
6. Predicate pushdown becomes available for the promoted key in Spark/Trino immediately
   after the snapshot is committed.
----

=== Manual Promotion

[source,sql]
----
-- Explicitly promote a props key before frequency threshold is reached
ALTER TABLE documents PROMOTE PROPS KEY (category TYPE text);
ALTER TABLE events    PROMOTE PROPS KEY (user_id TYPE bigint);
ALTER TABLE metrics   PROMOTE PROPS KEY (region TYPE text);
----

=== Promoted Column Naming Convention

Promoted columns use the naming convention `props__<key>` (double underscore separator)
to avoid collisions with user-defined columns and to signal their origin in the schema.
The original key remains readable from the msgpack `props` blob during the compaction
window for backwards compatibility.

=== Iceberg Type Mapping for Promoted Keys

[cols="2,2,2"]
|===
| Promoted ProximaType | Iceberg column type | Predicate pushdown in Spark/Trino

| `String`  | `string`         | Yes — full equality, `LIKE`, `IN`
| `Int64`   | `long`           | Yes — range, equality, `BETWEEN`
| `Float64` | `double`         | Yes — range, equality
| `Boolean` | `boolean`        | Yes — equality
| `TimestampTz` | `timestamptz` | Yes — range, equality
| `Json` (nested) | `string`   | No — stored as JSON string; UDF required
| `ProximaValue::Map` (nested) | Not promotable | No
|===

See ADR-013 for the full type coercion matrix including non-promotable types.

=== Enabling Auto-Promotion

[source,sql]
----
-- Enable auto-promotion on an existing document table
ALTER TABLE documents SET (
  props_auto_promotion = 'enabled',
  props_promotion_threshold = 0.4,     -- promote if key appears in 40 % of rows
  props_promotion_max_columns = 50     -- promote up to 50 keys
);

-- Check promotion candidates (dry run)
SELECT * FROM proximadb_catalog.props_promotion_candidates('documents');
----

Open-format guardrails:

* Do not expose a Proxima-owned asset to external readers until the publication snapshot is
  registered in xCatalog.
* Do not treat external table metadata as fresh unless its refresh mode and snapshot id/version are
  known.
* Do not allow external compute writes to Proxima-owned assets unless the output returns through
  `TableRecordStore` or a staged commit protocol that writes canonical records first.
* Do not allow `ExternalAuthoritative` writes unless the adapter can surface conflict/isolation
  errors from the table format.
* Do not silently ignore delete files, deletion vectors, schema evolution, partition evolution, or
  lossy type conversions. Unsupported semantics must reject the route or mark it experimental.
* For tenant/RLS data, the adapter must prove predicates are enforced before data leaves the
  ProximaDB boundary or mark the route unsupported.

== Schema-On-Read And Schema-On-Write Positioning

Open file/table formats are supported, but they do not replace the canonical record and catalog
model.

=== Schema-On-Read External Tables

Schema-on-read is a cataloged projection behavior for external or lake-style data:

[source,sql]
----
CREATE EXTERNAL TABLE raw_events
STORED AS PARQUET
LOCATION 's3://bucket/events/'
WITH (
  schema_mode = 'read',
  ownership = 'external',
  snapshot_isolation = 'manifest',
  refresh = 'manual'
);
----

xCatalog must record:

* physical format and location;
* ownership mode (`external`, `projection`, `proximadb_authoritative`, or explicit external authority);
* inferred or declared `ProximaType` mapping;
* lossy conversions and unsupported fields;
* snapshot/isolation semantics;
* tenant/RLS enforcement boundary;
* write/refresh mode;
* repair/rebuild source.
* schema registry subject/version/fingerprint when the external data uses Avro, JSON Schema,
  Protobuf, or a Glue/Confluent-compatible schema registry.

Reads from Parquet, Arrow IPC, ORC, JSON, CSV, Iceberg, Delta, Hudi, or Hadoop-style key/value files
project rows into `ProximaRecord`/`ProximaValue` before planning. For key/value sources, the key maps
to identity, partition, or an indexed column; the value maps to `Map`, `Json`, `Struct`, `Binary`, or
a declared `ProximaType`.

The ownership modes, SQL-visible internal columns, MVCC expectations, PAX/SST layout guidance, and
external-table interoperability contract are refined in
`docs/12-design/RELATIONAL_STORAGE_FORMAT_AND_INTEROPERABILITY_2026_05_19.adoc`. Open-format
adapters must follow that document when deciding whether an asset is ProximaDB-authoritative, a
projection publication, an imported snapshot, an external authority, or a federated read.

=== Schema-On-Write Tables

Schema-on-write is the default for OLTP-style relational loads:

[source,sql]
----
CREATE TABLE orders (
  order_id TEXT PRIMARY KEY,
  amount DECIMAL(18, 2),
  attrs JSON,
  embedding VECTOR(768)
);
----

SQL/pgwire `INSERT`/`COPY`, REST/gRPC `InsertRecords`, Arrow Flight batches, and embedded
pandas/Arrow/numpy loads all validate against the same xCatalog schema and write canonical
`ProximaRecord`s. Relational constraints are enforced below protocol handlers and recovered through
WAL/log/manifest.

Tenant context for these tables is owned by xCatalog namespace/schema/table metadata plus the
protocol/service session. Applications may add a business `tenant_id` column, but ProximaDB does not
require one for logical tenancy. Internal layouts may materialize `__tenant_id`, `tenant_id_hash`,
or segment/table tenant metadata only when needed for engine-level RLS, pruning, replay, CDC, or
mixed-tenant physical storage.

=== Surface Rule

REST, gRPC, Arrow Flight, pgwire/SQL, SDKs, and embedded mode are ingestion/query surfaces over
xCatalog and `ProximaRecord`. They must not define protocol-specific durable record shapes. Legacy
vector-shaped payloads (`VectorRecord`, metadata maps, or `SqlValue`-centric DTOs) are deprecated
migration artifacts, not target contracts for new open-format work.

== Iceberg REST Catalog Server (ADR-007)

=== What It Is

ProximaDB serves a full Apache Iceberg REST Catalog v1 at `/iceberg/v1` (port 5678).
Any Iceberg-aware engine connects without a custom connector:

----
catalog URI: http://host:5678/iceberg/v1
----

=== Hadoop Split Mental Model

External engines apply the Hadoop InputFormat model through ProximaDB's Iceberg REST:

[source]
----
Coordinator phase  (cheap, metadata-only):
  GET /iceberg/v1/namespaces/{ns}/tables/{t}
  → parse snapshot → manifest entries → one split per ProximaDB storage shard

Worker phase  (actual I/O):
  exchange Arrow Flight ticket (from manifest data-file descriptor)
  at grpc://localhost:5680
  → read Arrow IPC batches of ProximaRecord rows
----

This is Trino `ConnectorSplitSource` + `ConnectorPageSource` and Spark `DataSource V2
Scan.planInputPartitions()` with zero custom connector code.

=== Implementation Files

[cols="3,5"]
|===
| File | Role

| `src/catalog/iceberg_rest_service.rs` | Service layer; `CatalogTableSchema ↔ IcebergTableMetadata`; synthetic snapshot + manifest generation; Arrow Flight ticket embedding
| `src/network/rest/v1/iceberg_rest_catalog.rs` | Axum route handlers; `IcebergRestState { service }`;  `create_iceberg_rest_router()` with all 15 endpoints
| `src/network/rest/v1/handlers.rs` | `create_router()` nests `/iceberg/v1` unconditionally (no feature gate)
| `src/catalog/iceberg.rs` | Existing Iceberg client types — `IcebergTableMetadata`, `IcebergSchema`, `IcebergSnapshot`; reused by service layer
|===

=== ProximaRecord → Iceberg Canonical Column Mapping (ADR-ICE-001)

The fixed column prefix every ProximaDB collection projected as an Iceberg table exposes —
the compatibility contract with external compute engines — is defined once in the ADR:
link:adr/ADR-007-iceberg-rest-catalog-server.adoc[ADR-007] § _ProximaRecord → Iceberg
Canonical Schema (ADR-ICE-001)_ carries the authoritative field/column/type table (including
the `tenant_id` policy note and the `labels` IN-predicate pushdown) and the HNSW-discovery
table-properties block. Do not restate it here; a second copy would drift from the contract.

== OLTP Catalog Backends (ADR-008)

WARNING: *Status corrected 2026-10-15 — retired.* `OltpCatalog` never worked (feature-off it was a
silent in-memory no-op reporting success; feature-on it did not compile) and is now an explicit opt-in
`#[cfg(feature = "oltp-catalog")]` module in `crates/control/proximadb-catalog/src/oltp.rs`, retired
rather than rescued — see link:../10-quality/td/TD-CAT-10-oltp-catalog-retirement.adoc[TD-CAT-10]
(#1721). The section below is the original design; the file paths under `src/catalog/` have moved to
the catalog crate. The production catalog authority is `SystemCatalog` (ADR-048).

=== Motivation

For collections < 1 GB, lakehouse metadata overhead (transaction logs, manifest files, compaction) is
disproportionate.  A relational OLTP backend provides:

* Fast ACID point lookups on namespace and table metadata
* Simple operational model (one Postgres/SQLite database)
* Strict schema history and statistics tracking with `UNIQUE` constraints

=== Supported Backends and Feature Flags

[source,bash]
----
cargo build --features oltp-catalog-postgres   # PostgreSQL / Neon / Supabase / CockroachDB
cargo build --features oltp-catalog-mysql      # MariaDB / MySQL / TiDB / PlanetScale
cargo build --features oltp-catalog-sqlite     # SQLite (dev / embedded)
cargo build --features oltp-catalog-full       # All three
----

Detection is automatic from connection string prefix (`postgres://`, `mysql://`, `sqlite:///`).

=== Size-Based Routing

[source]
----
collection size < 1 GB  →  OLTP catalog  (registered under name "oltp-{backend}")
collection size ≥ 1 GB  →  lakehouse / native catalog (default catalog)
----

[source,rust]
----
// Insert path (pseudocode)
let catalog = catalog_manager.catalog_for_size(estimated_bytes, threshold_bytes);
catalog.create_table(namespace, schema).await?;
----

`namespaces`, `tables`, `snapshots`, `schema_history`, `statistics`.

Full DDL in `src/catalog/oltp.rs` `generate_ddl()`.  Auto-migrated on startup when `auto_migrate = true`.

== ProximaValue Type System in the Open Format Layer

When ProximaDB projects records into Iceberg/Parquet or returns Arrow batches via Flight,
`ProximaValue` scalars are mapped as follows.  Do not use legacy `SqlValue` in any catalog or
open-format path.

[cols="2,2,2,3"]
|===
| ProximaType | Arrow type | Parquet type | Notes

| `Boolean` | `Boolean` | `BOOLEAN` |
| `Int8`…`Int64` | `Int8`…`Int64` | `INT(8..64)` |
| `Float32` / `Float64` | `Float32` / `Float64` | `FLOAT` / `DOUBLE` |
| `Decimal` | `Decimal128(p,s)` | `DECIMAL(p,s)` | precision/scale from catalog schema
| `String` | `Utf8` | `BYTE_ARRAY (UTF8)` |
| `Binary` | `LargeBinary` | `BYTE_ARRAY` |
| `TimestampTz` | `Timestamp(us, UTC)` | `INT64 (TIMESTAMP_MICROS)` |
| `Uuid` | `FixedSizeBinary(16)` | `FIXED_LEN_BYTE_ARRAY(16)` |
| `Json` / `Jsonb` | `Utf8` | `BYTE_ARRAY (UTF8)` | structured JSON string
| `DenseVector` | `FixedSizeList<Float32>` | `LIST (FLOAT)` | dim in schema metadata
| `SparseVector` | `Map<Int32, Float32>` | `MAP` |
| `Array` | `List<ProximaValue>` | `LIST` |
| `Map` | `Map<Utf8, ProximaValue>` | `MAP` |
| `Null` | `Null` | `NULL` |
|===

`props` column in Iceberg schema is `map<string, binary>` where values are msgpack-encoded `ProximaValue` blobs.  External engines that cannot decode msgpack treat `props` as opaque binary — this is intentional.

== Schema Registry Facades

ProximaDB should expose Confluent- and Glue-style schema registry compatibility as adapters over
xCatalog schema objects:

* Subjects map to catalog schema names under a namespace.
* Schema versions map to xCatalog schema history entries.
* Compatibility levels map to xCatalog schema evolution policies.
* Avro, JSON Schema, and Protobuf fields map into `ProximaType`; unsupported or lossy mappings are
  recorded and surfaced in inspection/EXPLAIN paths.
* Stream connectors bind `(topic, subject, version, fingerprint)` to a catalog stream/table asset,
  offset/watermark state, and lineage entry.

The registry facade may cache decoded schemas, but committed schema state lives in xCatalog. A
connector, REST handler, or stream processor must not infer and persist schema changes outside the
catalog transaction path.

== External Engine Quick-Start

=== PyIceberg

[source,python]
----
from pyiceberg.catalog.rest import RestCatalog
cat = RestCatalog("proximadb", **{"uri": "http://localhost:5678/iceberg/v1"})
namespaces = cat.list_namespaces()
tables     = cat.list_tables(("default",))
tbl        = cat.load_table(("default", "my_collection"))
arrow_tbl  = tbl.scan().to_arrow()
----

----
