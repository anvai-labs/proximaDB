== Purpose

This document is the high-level and low-level blueprint for the current SQL/pgwire relational
write and compute-routing architecture. It records both the target shape and the transitional
implementation currently in the repository, so development can continue without losing the
architectural thread.

* `docs/12-design/RELATIONAL_STORAGE_FORMAT_AND_INTEROPERABILITY_2026_05_19.adoc`

Key principle: pgwire, REST/gRPC, Arrow Flight, embedded APIs, document APIs, graph APIs, and vector
APIs are facades over xCatalog plus canonical `ProximaRecord`/`ProximaValue` semantics. The
architecture is tiered:

1. **PostgreSQL-style OLTP workloads:** Native/Volcano execution over WAL plus the OLTP row/delta
   store. This path owns point DML, strong-freshness reads, MVCC visibility, and
   primary-key/unique/check/foreign-key enforcement.
2. **Relational warehouse/OLAP workloads:** DataFusion local/distributed execution over cataloged
   Parquet/Iceberg/Arrow snapshots, with explicit base-plus-delta union when a query requires
   fresher HTAP visibility than the last published snapshot.
3. **Vector/ANN workloads:** Specialized high-performance engines (SST, HELIX, RAPTOR, SWIFT, NOVA,
   VIPER) with shared identity/version/freshness metadata and no independent schema authority.

All paths converge on xCatalog, canonical WAL/log semantics, and decoupled `object_store`
persistence where applicable.

Competitive trajectory principle: ProximaDB adopts OLTP correctness from PostgreSQL/Oracle,
storage pushdown from Exadata/Netezza, projection/vectorization from Vertica/ClickHouse, MPP
routing discipline from Teradata/Redshift, and builds a **Rust-native distributed execution engine** (Spark-like) using DataFusion. The storage layer is fully decoupled over object storage, competing directly with Snowflake and Databricks.

== Route Selection Matrix

[cols="1,2,2,2,2"]
|===
| Workload / table shape | xCatalog signal | Preferred backend | Write target | Notes

| OLTP relational / PAX row-family
| `workload_profile = Oltp`, `storage_specialization = PaxOltp` or `PaxRowFamily`
| `Native`
| `TableRecordStore` -> direct WAL/table writer
| Point DML, row-level MVCC, constraints, idempotent writes, and prior-version closure belong here.

| OLAP / columnar
| `workload_profile = Olap`, `storage_specialization = PaxOlap` or `ColumnarAnalytics`
| `DataFusionLocal` or `DataFusionDistributed`
| `TableRecordStore` for Proxima-owned tables; open-table writer for external-authoritative tables
| DataFusion handles vectorized scans/joins/aggregates; ProximaDB owns commit semantics.

| HTAP / mixed
| `workload_profile = Htap` or `Mixed`
| Cost router chooses `Native` for write-heavy/point writes, DataFusion for analytical transforms
| `TableRecordStore`
| Requires stats-backed CBO and freshness-aware projection selection.

| Vector ANN / legacy vector tables
| `workload_profile = Vector` or `storage_specialization = VectorAnn`
| Native vector/query facade for search; compatibility write route during migration
| `VectorOpsTableRecordStore` -> `VectorOps`
| Transitional only. Vector search behavior can remain facade-specific, but durable record writes
must converge on table-record semantics.

| Legacy SST/LSM write-optimized
| `storage_specialization = LsmWriteOptimized`
| Native compatibility route initially
| `VectorOpsTableRecordStore` -> `VectorOps`
| Keeps old behavior working while direct WAL/table-record writer and PAX/LSM convergence land.

| Document / graph / observability
| `DocumentJson`, `GraphTopology`, `ObservabilityTimeSeries`
| Native facade operators plus DataFusion where relational/Arrow-compatible
| `TableRecordStore` plus rebuildable projections
| Durable truth remains canonical records. JSON path indexes, topology, rollups, and trace indexes
are projections/access methods.

| External authoritative Iceberg/Delta/Hudi
| primary layout authority is external and format is open-table
| `ExternalDelegated(format)` or DataFusion plus external commit writer
| External atomic commit protocol
| xCatalog records ownership, snapshot, type mapping, policy boundary, refresh/repair source.

| Polars compatibility
| local dataframe transform wins on cost and operator coverage
| `PolarsLocal`
| staged Arrow/record batches then `TableRecordStore`
| Optional backend. It never owns SQL semantics, WAL, catalog, RLS, or record identity.

| DuckDB compatibility
| dialect/file interoperability or user-requested DuckDB path
| `DuckDbCompat`
| staged Arrow/record batches then `TableRecordStore` or external commit
| Optional adapter for compatibility/conformance, not ProximaDB's internal durable engine.
|===

== LLM Implementation Alignment Contract

This section is intentionally prescriptive. It exists so generated implementation work does not
drift into protocol-owned semantics, duplicate durable paths, or hidden engine selection.

=== Non-Negotiable Invariants

Generated code must preserve these invariants:

* Protocol handlers parse, authenticate, shape responses, and attach session context. They do not
  own catalog authority, record identity, WAL semantics, MVCC, RLS, or compute routing.
* `DmlService` coordinates DML after catalog resolution. It validates through catalog contracts and
  delegates writes to `TableRecordStore`; it does not choose storage engines directly.
* `DmlWritePlanner` and `TableWriteRouter` own table-to-table route selection. Any new backend must
  appear as a `ComputeBackend`/candidate route with guards and rejected-route reasons.
* `TableRecordStore` is the only Proxima-owned mutation boundary below services. New relational,
  document, graph, observability, or table-like writes must pass through it unless a doc/ADR marks
  the asset as external-authoritative.
* `VectorOpsTableRecordStore` is a compatibility bridge, not a template for new table semantics.
* `ProximaRecord`, `ProximaType`, and `ProximaValue` are the internal data contract. Protocol DTOs,
  legacy `VectorRecord`, `SqlValue`, Arrow arrays, JSON objects, and open-format rows are adapters.
* xCatalog metadata must be read before route selection and written when capabilities, layout,
  projection freshness, external snapshots, or supported-surface status change.
* RLS, tenant, masking, branch/snapshot, and retention checks must be applied before data leaves a
  ProximaDB policy boundary.

=== Required Shape For New Routes

Every new compute or source route must add or update these concepts together:

[source,text]
----
ComputeBackend variant
CandidateWritePath or CandidateReadPath
ExecutionGuard list
PolicyBoundary declaration
AuthorityMode compatibility
Freshness requirement
RejectedRouteReason values
EXPLAIN fields
Focused smoke test
----

The route must stay disabled or planned-only until:

* source snapshot pinning is implemented or explicitly unnecessary;
* target write capability checks are implemented;
* tenant/RLS behavior is clear for every input row;
* lossy type conversions are recorded or rejected;
* projection freshness is updated, preserved, or marked stale;
* retries are idempotent or explicitly non-retriable.

=== Router/Multiplexer Boundary

`DmlWritePlanner` + `TableWriteRouter` are the route-selection boundary. A future standalone router
or router crate may own this responsibility, but the ownership rules stay the same:

* route selection happens once per plan, fragment, split set, or write intent;
* the result is a typed `RoutedExecutionPlan`, not a handler-local callback or string route;
* `TableWriteExecutor` is the runtime multiplexer for table writes: it validates guards and
  dispatches to native, DataFusion, external, or planned-only execution;
* leaf executors/readers own tight-loop performance and must receive typed plans/cursors, not
  protocol DTOs;
* no leaf executor may select itself without a routed plan and no protocol handler may bypass the
  router for a non-trivial route decision.

Codegen rule: if a change adds a new leaf executor, it must add the route candidate and rejected
route reason first. If it adds a new route candidate, it must update `EXPLAIN` before the route is
enabled by default.

=== Required Shape For New Source Readers

Every `TableRecordSourceReader` implementation must document and test:

* source authority mode: Proxima-owned, imported snapshot, federated read, or external authority;
* snapshot semantics: current, pinned catalog snapshot, file manifest snapshot, stream offset, or
  unsupported;
* type mapping into `ProximaType`/`ProximaValue`;
* policy behavior: Proxima-enforced before read, connector-enforced, external-policy, or rejected;
* null/default/generated-column behavior;
* batch ordering and idempotency expectations;
* how errors surface as retryable, permanent, policy violation, type violation, or stale snapshot.

Reader output is `ProximaRecord` or Arrow batches with a deterministic conversion into
`ProximaRecord`. A reader must not return protocol DTOs as internal write payloads.

=== Required Shape For Projection Updates

Whenever a write path updates or invalidates PAX, columnar, ANN, JSON, graph, time-series, open
table, materialized view, or cache projections, generated code must choose one of these outcomes:

* synchronous projection update before commit is visible;
* asynchronous projection directive enqueued with xCatalog freshness watermark;
* projection marked stale with repair source and rejected for current-snapshot queries;
* external-authoritative snapshot registered through the external format commit protocol.

Silent best-effort projection updates are not allowed for supported paths.

=== Anti-Patterns To Reject In Review

Reject generated code that:

* adds a new service-local `HashMap`/file/table as durable metadata without xCatalog registration;
* writes records directly from pgwire, REST/gRPC, Flight, or SDK handlers;
* calls `VectorOps` for new relational, document, graph, or observability semantics;
* chooses DataFusion, Spark, Trino, Polars, DuckDB, or a storage engine inside a parser or protocol
  handler;
* exposes external compute for tenant/RLS data without a policy-boundary guard;
* treats Parquet, Arrow, Delta, Iceberg, or Hudi as canonical record authority for Proxima-owned
  hot tables;
* introduces a new DTO/type envelope when `ProximaRecord`/`ProximaValue` can represent the data;
* reports success when WAL commit succeeded but required synchronous projections failed;
* documents a feature as supported without a supported-surface entry and a benchmark or smoke gate.

=== DmlService

`DmlService` is the catalog-aware DML coordinator:

* resolves target table with `CatalogManager::resolve_table`;
* verifies table existence;
* validates and coerces values through `CatalogRow`;
* constructs `ProximaRecord` mutation envelopes;
* calls `TableRecordStore` for VALUES DML;
* calls `DmlWritePlanner` and `TableWriteExecutor` for table-to-table writes.

`DmlService` must not:

* choose compute engines directly;
* own physical layout decisions;
* call VectorOps directly except through injected compatibility store construction;
* become the source of truth for catalog, WAL, MVCC, RLS, or storage semantics.

== Execution Guards

Every routed plan must carry guards. Guards are not advisory; they define what must be true before
execution can safely commit.

[cols="1,2,2"]
|===
| Guard | Meaning | Current status

| `PinSourceSnapshot`
| Source table/file/open-table snapshot is stable for the read.
| Planned and validated as required. Concrete readers must enforce it.

| `CheckTargetWriteCapabilities`
| Target supports append/upsert/overwrite/replace/merge mode.
| Planned and validated as required. Capability enforcement needs richer xCatalog flags.

| `EnforceRlsInProxima`
| Tenant/RLS predicates are applied before rows leave the policy boundary.
| Planned. Requires source readers to include policy context.

| `RequireExternalAtomicCommit`
| External authoritative tables must commit through their format protocol.
| Planned. External commit executor is pending.

| `RequireIdempotencyKey`
| Retriable overwrite/replace writes need deterministic idempotency.
| Planned for overwrite/replace. Key plumbing is pending.

| `PreservePreviousSnapshot`
| Old data remains recoverable until retention/branch/CDC rules allow cleanup.
| Planned for overwrite/replace. Snapshot catalog mutation is pending.
|===

== Route Explanation Contract

The route explanation is the mechanical bridge between the planner, `EXPLAIN`, tests, and LLM/code
review. Every routed table write must be able to produce a stable, protocol-neutral explanation.

Current implementation anchor: `src/query/table_write_plan.rs` exposes
`RoutedExecutionPlan::route_explanation()` and the stable explanation structs:

* `TableWriteRouteExplanation`
* `TableWriteIntentExplanation`

== Source Reader LLD

`TableRecordSourceReader` is the stable boundary for native source reads. DataFusion, Arrow Flight,
external files, and open-table readers should adapt into this boundary or into Arrow batches with a
deterministic `ProximaRecord` conversion.

Current implementation anchor:

* `TableRecordStoreSourceReader` reads `ReadSource::CatalogTable` through
  `TableRecordStore::scan_records`.
* It is valid only for simple catalog-table source reads after route selection chooses the native
  path.
* General `QuerySql`, joins, aggregates, file scans, and Flight tickets must use a compute adapter
  and then yield canonical records.

Required reader metadata:

[cols="1,3"]
|===
| Reader | Required semantics before default use

| `TableRecordStoreSourceReader`
| pinned source snapshot, tenant/RLS context, branch visibility, scan limit behavior, current-state
visibility, and table/schema match validation

| `DataFusionRecordSourceReader`
| logical/physical DataFusion plan id, Arrow schema to `ProximaType` mapping, pushed/residual
predicates, spill behavior, lossy conversion rejection, and deterministic row identity mapping

| `ArrowFlightSourceReader`
| ticket authority, endpoint trust boundary, tenant/RLS enforcement location, schema fingerprint,
batch ordering, retry semantics, and backpressure behavior

| `ExternalFileSourceReader`
| file format, location, schema hint/inference result, split boundaries, CSV line-boundary behavior,
null/default coercion, lossy conversion handling, and object-store consistency assumption

| `OpenTableSourceReader`
| Iceberg/Delta/Hudi snapshot id, manifest/version metadata, delete-file handling, partition
evolution mapping, schema evolution mapping, refresh mode, and external authority mode
|===

Reader failure classes:

* `RetryableReadFailure`: transient I/O, throttling, network, or retry-safe compute failure.
* `PermanentReadFailure`: missing object, unsupported format, corrupt file, unsupported operator.
* `PolicyViolation`: tenant/RLS/masking cannot be enforced before data leaves the boundary.
* `TypeViolation`: source values cannot be losslessly coerced into target `ProximaType`.
* `StaleSnapshot`: requested snapshot/freshness cannot satisfy the route.

The executor should surface these classes as structured errors over time. Until structured errors
exist, error strings must include the class name.

== Projection Freshness State Machine

Layer-2 structures are useful only when freshness is explicit. Writes that affect PAX, columnar,
ANN, JSON, graph, observability, materialized view, cache, or open-format projections must move the
projection through a cataloged state.

[source,text]
----
Fresh
  Projection includes all committed records required by its declared snapshot/freshness SLA.

Updating
  Synchronous or bounded-async update is in progress. Current-snapshot queries may wait, route to
  canonical records, or reject depending on freshness_sla.

Stale
  Projection is known behind the canonical WAL/record state. Current-snapshot queries must not use
  it unless the query accepts stale reads.

RebuildRequired
  Projection cannot be incrementally repaired and must be rebuilt from WAL/record storage.

ExternalSnapshotRegistered
  External authoritative snapshot or Proxima publication has been atomically registered in xCatalog.

Unavailable
  Projection metadata exists but the physical projection cannot be used.
----

Required xCatalog fields for each projection:

* projection id and owning asset id;
* projection kind and access-method family;
* source WAL range or source snapshot;
* last included commit/snapshot;
* freshness state and freshness SLA;
* rebuild source and invalidation policy;
* policy boundary and tenant/RLS pushdown capability;
* checksum or manifest fingerprint where applicable;
* support/maturity status and benchmark gate.

Freshness rules:

* A route requiring current snapshot semantics may use only `Fresh` projections or canonical
  records.
* A `BoundedAsync` projection must expose lag and reject routes when lag exceeds the SLA.
* `StaleOk` must be a query/session/catalog choice, not a silent fallback.
* Projection update failure after WAL commit must either leave the projection `Stale` with repair
  metadata or fail the write if the projection was declared synchronous.
* Open-format publications must register a snapshot/manifest atomically before external readers see
  the new version.

== Data And Mutation Semantics

=== INSERT

* Validates target columns and values against `CatalogTableSchema`.
* Constructs a new `ProximaRecord`.
* Commits `TableRecordMutationKind::Insert`.
* Duplicate handling depends on primary key/unique enforcement in the direct writer; current
  compatibility route inherits legacy behavior.

=== UPSERT

* Validates insert row and conflict metadata.
* Constructs canonical upsert record.
* Commits `TableRecordMutationKind::Upsert`.
* Direct writer must close prior visible version or preserve it according to snapshot/MVCC policy.

=== UPDATE

* Requires primary-key targeted predicates in the current implementation.
* Reads existing visible row with `TableRecordStore::get_by_key`.
* Reconstructs full row shape, applies validated assignments, and writes a new update record.
* Direct writer must close prior visible version and reject stale expected versions when OCC is
  enabled.

=== DELETE

* Requires primary-key targeted predicates in the current implementation.
* Builds a catalog-shaped tombstone record.
* Direct writer must make the tombstone visible at the mutation snapshot and close prior visible
  row versions.

=== INSERT SELECT

* Parser lowers syntax to `CopyIntoPlan`.
* `DmlWritePlanner` resolves target catalog metadata.
* `TableWriteRouter` selects native/DataFusion/external route.
* `NativeTableWriteExecutor` can already commit record batches once a source reader exists.
* DataFusion/external execution remains pending.

=== INSERT OVERWRITE

* Uses `WriteMode::OverwriteTable`.
* Requires previous snapshot preservation and idempotency.
* Native executor maps to `TableRecordMutationKind::OverwriteSnapshot`; direct writer still needs
  atomic snapshot replacement semantics.
* External authoritative targets must use Iceberg/Delta/Hudi atomic commit protocols.

=== MERGE

* Planned in contract only.
* Current native executor rejects MERGE until join predicate, conflict policy, matched/not matched
  actions, and prior-version closure are specified and implemented.

== HLD: Write Path Fast Lanes

Verification snapshot:

* REST and gRPC record/vector writes already skip SQL parsing. They lower protocol payloads into
  `ProximaRecord` batches and call `UnifiedHandlers` / `VectorOperationsService`.
* Arrow Flight `DoPut` / `DoExchange` skips SQL parsing and accepts Arrow `RecordBatch` payloads.
  Relational descriptors still validate through xCatalog via `CatalogBulkWriteService` before
  records are written.
* `VectorOperationsService` has a bulk-write router, but the current large-batch branch still writes
  through `wal_manager.write_vector_batch_native_arc(...)`. The code deliberately preserves WAL
  durability until WAL-skip safety is resolved; comments and metrics now describe this as a
  WAL-backed bulk lane.
* gRPC v2 record writes can also emit a fire-and-forget PAX projection after successful engine
  insert. That projection is not authoritative and must remain rebuildable.

Recommended shape:

[cols="1,2,3,3"]
|===
| Surface | Parsing/lowering | Default write lane | Fast-lane rule

| REST / gRPC
| Typed API payload -> `ProximaRecord` batch.
| Catalog validation -> canonical WAL/current-state writer.
| May skip SQL planner. Must not skip xCatalog validation, RLS/tenant coercion, constraints, or
  WAL unless the request is explicitly a bulk-load direct-commit mode.

| Arrow Flight
| Arrow `RecordBatch` -> `ProximaRecord` batch, with optional table descriptor -> xCatalog schema.
| Batch validation -> WAL/current-state writer; optional rebuildable PAX/columnar projection.
| Best bulk path. May use a direct segment commit only for append/overwrite snapshot loads where
  ACK waits for durable segment+manifest commit. Upsert/update/delete/merge must use WAL/MVCC
  because they need conflict checks, prior-version closure, tombstones, and replay ordering.

| pgwire SQL
| SQL parser -> `DmlStatement` / `CopyIntoPlan` -> `DmlService` / `TableWriteRouter`.
| Same canonical write lane as REST/gRPC after parsing.
| Should use fast lanes only after SQL lowering proves the operation is batch append/overwrite and
  xCatalog route guards allow it. SQL should not call the slow general optimizer for simple
  `INSERT VALUES`, PK `UPDATE`, PK `DELETE`, or safe `INSERT INTO ... SELECT * FROM table`; it should
  lower to the same record-batch/direct-source executor used by typed APIs.

| External open-table engines
| Format metadata/splits -> Arrow/record batches or external commit protocol.
| External-authoritative mode commits through Iceberg/Delta/Hudi with xCatalog authority metadata.
| Proxima-authoritative mode must return through canonical WAL/current-state writer; external files
  are read sources or projections.
|===

Write-mode contract:

* `WalCurrentState`: default OLTP/HTAP path. Append canonical WAL, update current-state/PAX row
  family, return after WAL durability. Required for insert/upsert/update/delete/merge.
* `BulkAppendCommit`: large append-only load. Convert Arrow/record batches, validate catalog and
  constraints that can be checked batch-locally, write durable PAX/columnar/LSM segment and manifest,
  then return. No WAL skip unless the segment+manifest commit itself is the durable journal entry or
  an equivalent canonical checkpoint/barrier is written.
* `OverwriteSnapshotCommit`: replace table or partition snapshot. Requires xCatalog snapshot
  transaction, atomic manifest swap, and rollback/repair source. Not valid for row-level update
  semantics.
* `ProjectionOnly`: rebuildable PAX/ANN/JSON/graph/observability projections after an authoritative
  write. Fire-and-forget is acceptable only when freshness metadata records lag/staleness.

The optimization target is therefore not “SQL versus API.” The target is to keep protocol adapters
thin and route every surface into a shared write planner with explicit operation semantics,
durability mode, catalog policy, and projection freshness.

Plan refinement:

* Add a shared `WriteIntent` / `WriteLane` contract below protocol adapters. It should carry
  operation kind, idempotency key, tenant context, actor, table identity, catalog schema version,
  durability mode, isolation requirement, projection freshness requirement, and whether batch-local
  constraint checks are sufficient.
* Keep SQL parsing as a pgwire-only syntax adapter. Once parsed, pgwire must call the same
  record-batch and copy-plan executor used by REST/gRPC/Arrow Flight instead of inventing a SQL-only
  write path.
* Keep Arrow Flight as the preferred high-throughput ingress. Its optimization is Arrow-native
  schema/batch transport and direct batch validation, not bypassing authoritative semantics.
* Treat WAL-skip/direct commit as an explicit durability mode, not a hidden optimization. It is
  valid only when the target commit protocol provides equivalent crash recovery, idempotency,
  manifest atomicity, and repair source semantics.
* Correct legacy VectorOps naming/metrics so “direct” means direct segment/manifest commit only
  after that path exists. Until then, bulk-routed VectorOps writes are still WAL-backed.

=== Tenant / RLS Boundary

Tenant ownership is primarily a control-plane property, not a mandatory user-visible table column.
xCatalog owns workspace/account, namespace/schema, table ownership, policy boundary, and default
tenant context. Protocol sessions and service calls carry tenant context into planning and
execution; user DDL should not need to declare `tenant_id` unless the application deliberately
models tenant as business data.

Internal physical metadata may still carry tenant information for enforcement and pruning:

* table or namespace metadata when a physical table is dedicated to one tenant;
* segment/block metadata such as `tenant_id_hash` when all rows in a block share the same tenant;
* internal system fields such as `__tenant_id` only when a physical table/segment intentionally
  mixes tenants and row-level isolation must be enforced below scan/index iterators;
* WAL, CDC, audit, backup, and repair records so replay does not depend on a protocol session that
  no longer exists.

Rule: tenant/RLS fields are system context. They may be exposed through explicit introspection or
open-format projection columns, but they are not logical user columns by default. Physical layouts
should elide per-row tenant storage when the tenant is constant at table/segment scope and must
preserve enough internal metadata for engine-level RLS, snapshot repair, and projection rebuild.

== Open Design Decisions

1. Direct writer commit protocol:
   `DirectWalTableRecordStore` now writes canonical `RecordUpsert`/`RecordDelete` operations and
   returns insert conflicts before WAL append. The first production WAL shape is framed binary, not
   JSONL: headers carry magic, format version, codec id, sequence number, payload length, and CRC;
   payloads use MessagePack named-field encoding until a protobuf/Avro schema is promoted as the
   durable cross-language wire contract. Recovery truncates only a trailing partial frame; complete
   frame corruption is a hard error. Remaining protocol work: segmented manifests,
   version-chain closing, idempotency keys, snapshot/partition overwrite commits, and constraint
   helpers for primary key, unique, check, and foreign-key enforcement.

2. Source scan shape:
   `TableRecordSourceReader` is now record-batch-native with an executor-local cursor for native
   catalog-table paths. pgwire full-table SELECT currently uses the same `TableRecordStore`
   scan contract directly through `DmlService`; simple non-PK `AND` predicates over comparisons,
   `IN`, `LIKE`, and `IS NULL` are evaluated as a pgwire compatibility filter. Rich predicates and
   analytical scans still need logical-plan/DataFusion/PAX scanner integration. Decide whether
   DataFusion/open-format paths should expose Arrow batches directly before conversion into
   `ProximaRecord` batches.

3. Snapshot and branch context:
   Add explicit `TableWriteContext` to table-to-table execution so source snapshot, target branch,
   idempotency key, actor, tenant, and isolation travel together.

4. Constraint enforcement:
   Place primary key, unique, check, and foreign-key enforcement below all facades, likely in the
   direct table-record writer with catalog/index helpers.

5. Overwrite semantics:
   Specify table-level vs partition-level overwrite commits for Proxima-authoritative PAX/columnar
   tables and how old snapshots are retained.

6. EXPLAIN:
   Expose `DmlWritePlanner` and `TableWriteRouter` candidate paths, selected backend, guards, and
   rejected reasons through pgwire/REST explain surfaces.

7. Legacy retirement:
   Define objective gates for removing VectorOps from canonical relational branches and keeping it
   only as vector facade/query functionality.

8. WAL-skip direct commits:
   Decide the exact durable proof required before any path may skip canonical WAL. At minimum this
   needs atomic segment+manifest commit, idempotency/retry behavior, recovery replay or repair
   source, catalog snapshot isolation, and CDC/replication semantics. Until this is accepted, “direct”
   write requests must either use WAL or fail with a route-rejection reason.

== Non-Goals

* Do not make VectorOps, DataFusion, Polars, DuckDB, Spark, Trino, or an open-table format the
  internal semantic authority for ProximaDB record writes.
* Do not add protocol-specific DML semantics below pgwire that REST/gRPC/Arrow/embedded cannot
  share.
* Do not hide schema inference, type coercion, RLS, MVCC, or ownership semantics in source readers
  or compute engines.
* Do not physically delete old data during overwrite before snapshot, branch, retention, and CDC
  rules permit cleanup.
