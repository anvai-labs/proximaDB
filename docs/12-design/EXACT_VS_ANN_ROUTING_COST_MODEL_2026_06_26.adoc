== Why this exists

TD-165 found the post-flush/cold orchestrated search returning the *wrong* nearest
neighbour: a query identical to an indexed vector got an approximate HNSW result
whose 100-wide candidate pool *excluded the exact match*. The first fix gated on a
hardcoded vector count (`≤ 10_000 → exact`). That violates co-design mandate #2/#6
("trace before you tune; cost from measured quantities, not static heuristics"): it
ignores dimension (cost is bytes, not vectors) and storage class, and duplicates the
existing `SearchMode` intent knob.

== First-principles cost decomposition

For a cloud DB the dominant cost term is *I/O round-trips + egress bytes, not CPU*.

[cols="1,2,1,1,1,1",options="header"]
|===
| Route | Cold I/O (object store) | CPU | Memory | Persistence | Recall
| Exact brute-force | read `N·dim·4` bytes (1 sequential/ranged GET) | `N·dim` MACs (SIMD) | streaming ~0 | none | *100%*
| HNSW | *cold: read all `N·dim·4` to rebuild* | build `O(N·log N)` + query `O(ef·log N)` | *full graph resident* | poor (in-mem; rebuilt on cold) | <100%, *can exclude the exact NN*
| IVF (quantized) | cold-load footer + read `nprobe/nlist` partitions (ranged) + f32 rerank | k-means build; cheap query | centroids + posting lists | *good* (persisted, ranged, quantized) | tunable (nprobe + rerank)
|===

== The serverless insight (the crux)

Serverless ⇒ scale-to-zero ⇒ *cold-start-dominant*; the in-memory HNSW graph is not
durable across cold starts. On a cold query:

[NOTE]
====
*HNSW reads the same `N·dim` bytes that exact reads, then additionally pays
`O(N·log N)` build CPU, and still returns an approximate (possibly NN-excluding)
result.* So *cold HNSW is strictly dominated by exact* (same I/O, more CPU, worse
recall, plus rebuild). HNSW wins only *warm + large-N*, amortized over many queries —
which serverless rarely is.
====

Consequences:

* *HNSW-rebuild-on-cold (the current TD-112 path) is an anti-pattern for serverless.*
  The cold/large path should be *persisted IVF* (cold-load + ranged `nprobe` reads +
  f32 rerank), never a full HNSW rebuild.
* *Exact is the cold-start-optimal route up to a byte budget*, not merely a
  small-collection fallback — the alternative reads the same bytes and does more.

== The threshold is a byte budget, not a vector count

Cost is `N·dim·4` bytes. `10k×64` (2.5 MB) vs `10k×1536` (61 MB) differ ~25×. The
crossover is storage-class-dependent: object store is *round-trip-bound* (one
sequential exact read beats several index-metadata round-trips for small N); local
NVMe is *bandwidth-bound* (higher threshold). So:

[source]
----
exact  if  N · dim · bytes_per_elem  ≤  EXACT_SCAN_BYTE_BUDGET   // one efficient ranged GET, ~32–64 MB, per storage class
----

== When to use what — scenario matrix + interplay

[cols="1,1,2,3",options="header"]
|===
| Index state | N | Route | Rationale
| Cold (serverless typical) | small (≤ budget) | *Exact* | bytes cheap; HNSW rebuild wasteful; 100% recall free
| Cold | large | *IVF cold-load + ranged nprobe + f32 rerank* | read a fraction of bytes; never full-rebuild HNSW
| Warm | small | Exact (or index — both ~free) | guarantee recall
| Warm | large | Approximate IVF/HNSW (nprobe/ef from request) | amortized graph wins
| `SearchMode::Exact` | any | Exact, or IVF + *full* f32 rerank over enough candidates | honor the 100%-recall contract
| `SearchMode::Approximate{nprobe}` | any | Index with requested nprobe | caller accepts the recall trade
|===

*Interplay rules*

. *Cold ⇒ exact ⪯ index* up to the byte budget (rebuild reads the same bytes anyway).
. *f32 rerank only rescues recall if the candidate generator surfaces the NN.* IVF
  with adequate nprobe can; *HNSW cannot* (it excluded the exact match in the TD-165
  trace), so rerank pairs with IVF, not as a cure for HNSW.
. *Prefer IVF over HNSW on the cold/serverless path* (persisted + ranged + quantized
  vs in-memory + rebuild). ⇒ *populating the persisted IVF at flush is load-bearing*
  for serverless large-N, not a nicety.
. *Meter the route* (co-design #5): exact = more read-units (KRU) / bytes, zero index
  storage; index = index storage (KSU) + fewer read bytes. The route is a metered TAM
  surface; the cost model should consume the per-segment read trace.

== Recommendation

. *Default `SearchMode::Adaptive{threshold}`* (was `Exact`). The decision is
  cost-derived: exact when `N·dim·4 ≤ EXACT_SCAN_BYTE_BUDGET`; the per-query
  `threshold` (vector count) is an explicit override/cap. `Exact` and
  `Approximate` remain explicit opt-ins.
. *Honor `SearchMode` in the SST orchestrated path* — the actual TD-165 bug was that
  `execute_orchestrated_search` ignored it and always ran HNSW.
. *Cold/large ⇒ IVF ranged + f32 rerank, not HNSW rebuild* — finish the persisted,
  populated IVF (TD-165 Defect B) and stop rebuilding HNSW on cold for large
  collections.
. *End state:* route via the existing `route_cost_model`/`ComputeScheduler` (measured
  bytes/round-trips). The byte-budget heuristic above is the principled interim until
  the SST search path consumes the cost model.

=== Phasing

* *This change (TD-165):* recommendation #1 + #2 — honor `SearchMode`, replace the
  magic count with a dim-aware byte budget, default `Adaptive`. Makes cold recall
  correct and the routing principled.
* *Serverless follow-up:* #3 (persisted IVF + IVF-over-HNSW cold path) and #4
  (cost-model-driven routing).

== Engine-level grounding: HELIX vs IVF vs HNSW (code-mapped 2026-06-26)

Three code maps reframed *where* the cold-read recall problem lives and which engine is
serverless-optimal. The TD-165 miss is *not fundamental* — it is *specific to the SST
engine's physical layout*.

=== Root cause is SST's block ordering, not ANN per se

* *SST* sorts blocks by *OID (lexicographic)*, so its zone-maps / centroid pruning do
  *not* reflect spatial proximity → pruning collapses; and its AXIS *HNSW is rebuilt
  in-memory every cold start* (`sst/search/mod.rs` `ensure_axis_index_from_sst` — read
  all records + `O(N·log N)`, zero persistence) and the rebuilt graph *excluded the
  exact-match NN* (TD-165 trace).
* *HELIX* sorts blocks by *PCA→Hilbert key*, so zone-maps reflect *real spatial
  clusters* → reliable Hilbert-range pruning, *no rebuild*, *no cold-read bug*
  (`helix/mod.rs:1578-1839`; `tests/helix_cold_search_recall_test.rs` asserts ≥90% cold
  recall). HELIX already honors `SearchMode::Exact` (`mod.rs:1922` `force_exact`).

=== Serverless cost comparison (object storage = round-trips + bytes dominant)

[cols="1,2,2,2",options="header"]
|===
| Property | HELIX | IVF (ADR-023 v3) | AXIS HNSW
| Cold rebuild | *none* — PCA model `__model/pca_model.bin` loaded <1 ms; layout *is* the index | none — COLD tier ~1/32 (centroids + 1-bit codes) + lazy warm | *full rebuild every cold start* (`O(N·log N)`)
| Reads | *contiguous* Hilbert-ordered ranged GETs (`proxima.rs:908` `read_range`, exact block size) | *scattered* — `1 + nprobe` posting-list `.get()`s (`dual_store_ivf.rs:1595`) | read-all to rebuild
| PCA / dim-reduction | *yes, persisted* (1536→8–64D adaptive) | *no* (k-means on full dim) | no
| Recall recovery | progressive binary→INT8→*fp32 rerank* (`progressive_search.rs`) | cold 1-bit → *warm fp32 rerank* per cluster | approximate, no rerank
| Honors `SearchMode::Exact` | *yes* | n/a (index) | *no* (the TD-165 bug)
|===

*HNSW is unambiguously worst for serverless* (rebuild every cold start). *HELIX wins
round-trips* (contiguous Hilbert reads) and is *rebuild-free*; *IVF v3 wins cold-load
footprint* (1/32 tier + survivor-aware lazy warm) but reads *scattered* clusters and
*uses no PCA*.

=== Why this matters at 1536D (OpenAI embeddings)

A Hilbert curve on raw 1536D is intractable (24 Kbit keys) and locality-free (curse of
dimensionality). *PCA→8–64D is the enabling precondition* (`clustering.rs:341`
`project_and_compute_hilbert`), and the PCA loss only drives *pruning* — the *full-1536D
fp32 rerank* restores recall. At 6 KB/vector the contiguous-ranged-read + dim-reduction
win is largest exactly here.

=== Recommendation (grounded, refined)

. *Route serverless / vector-search-heavy collections to HELIX* (`engine: "helix"`).
  Engine choice is *per-collection routing* (`engine_selector.rs:99-150`;
  `resolver.rs:125-168` dispatches to the collection's own `search_vectors_unified`), so
  this needs no SST-path change — HELIX is already the serverless-optimal, bug-free path.
. *Fix the auto-router heuristic* (`engine_selector.rs:137-150`): it currently sends
  vector collections *with quantization* to *SST* (the buggy cold path); those (e.g.
  OpenAI-embedding) collections are better on HELIX, whose progressive cascade is
  quantization-native.
. *Unify PCA* on the shared `EnhancedPCAModel` (`core/pca/model.rs`, "used by SST/HELIX/
  SWIFT"); today HELIX uses a *local* `PCAModel` (`helix/clustering.rs`) and IVF uses no
  PCA. One persisted PCA, reused across engines.
. *Converge the layout (the synergy):* PCA(shared) → k-means partitions (IVF nprobe
  pruning) → *Hilbert order within each partition* (HELIX contiguity) → tiered cold-codes
  + warm-fp32-ranged → fp32 rerank. Cluster pruning *and* contiguous ranged reads *and*
  dim reduction *and* recall recovery — the co-design end state.
. *TD-165 SST fix stands* — honoring `SearchMode` + the byte-budget exact gate is the
  correct *SST-engine-local* correctness fix for collections that remain on SST; HELIX
  collections are unaffected.

The current PR delivers recommendation #5 (SST-local). Items #1–#4 are the serverless
engine-strategy follow-up.
