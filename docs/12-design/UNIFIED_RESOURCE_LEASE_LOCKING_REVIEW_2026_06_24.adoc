== First-principles position

Object-store CAS is a strong primitive for coarse ownership, manifest publication,
and generation fencing. It is not, by itself, a high-frequency distributed lock
manager.

Use object-store CAS for:

* resource ownership and leaseholder election;
* fenced manifest and metadata commits;
* WAL/table-shard authority handoff;
* durable operation epochs where the write path validates the epoch.

Do not use object-store CAS as the hot path for every row-level DML lock unless
the write is low-frequency and the storage layer validates the acquired fencing
token before committing.

The target shape is:

* `ResourceKey` is the canonical identity for all lease-protected resources.
* Every durable lease path is tenant-isolated and path-safe.
* Legacy collection leases remain mixed-read-safe during migration.
* DML lock guards are scoped to real tenant/schema/table identity.
* Locks that claim hierarchy enforce ancestor and descendant conflicts.
* A writer carries a fencing generation or operation epoch into the storage layer.
* Protocol handlers map lock outcomes, but do not become the source of
  correctness.

== DML lock semantic decision

MVP DML locking should start with exclusive write/schema locks. Shared read
locks should not be exposed until the durable representation supports multiple
holders and release/reference semantics.

Rationale:

* Most DML mutations need write exclusion, not read locks.
* A single-owner lease maps cleanly to object-store CAS.
* Claiming shared reads on top of a single-holder lease misleads protocol
  integrations.
* Read consistency should primarily come from MVCC/WAL snapshot semantics and
  storage-level visibility, not a distributed read lock on every select.

If shared read locks are required later, introduce a separate durable lock record
shape with:

* holder ids and per-holder expirations;
* monotonically fenced write epoch;
* compare-and-swap update of the holder set;
* bounded holder cardinality or sharded reader tickets;
* explicit garbage collection of expired holders.

== DML integration rules

`DmlService` integration must happen below protocol handlers and above
`TableRecordStore::write_mutations`, after catalog resolution:

1. Resolve tenant/table with `resolve_table_scoped`.
2. Build a DML lock scope from the resolved table identity, not from raw SQL
   text alone.
3. Acquire a write lock guard for INSERT/UPDATE/DELETE/UPSERT and table-write
   plans.
4. Pass the guard fencing generation into the write request once the storage
   trait supports it.
5. Release/complete the guard after success or failure; natural TTL expiry is
   only for crash recovery.

For statement shapes:

* INSERT/UPSERT: table-level write lock for MVP; later row/partition locks only
  after key extraction and deadlock ordering are defined.
* UPDATE/DELETE: table-level write lock for MVP. Row locks can follow once
  predicate-to-key extraction is complete and ordered.
* INSERT SELECT / INSERT OVERWRITE: table-level write lock on the target; source
  reads rely on snapshot semantics.

== Protocol mapping

Protocol handlers should not acquire their own independent locks once
`DmlService` owns lock acquisition. They should only translate lock errors:

[cols="1,3", options="header"]
|===
| Surface | Conflict mapping

| REST
| `409 Conflict` for fail-fast conflict, or `423 Locked` if the API surface
documents lock semantics.

| gRPC
| Prefer `ABORTED` for concurrency conflicts. Use `FAILED_PRECONDITION` when
the request cannot proceed because a prerequisite lock state is absent.

| pgwire
| SQLSTATE `55P03` (`lock_not_available`) for fail-fast lock acquisition.

| Arrow Flight
| Return a structured Flight error that maps to concurrency conflict and carries
retry-after metadata when available.
|===

== Phase 2 (gated) — not in this branch

The foundation gates A1-A5 + A9 are complete; A6 is landed as the non-breaking
seam + contract; F7 durable release is done. The remaining work is **gated**
behind the A6-enforcement TD and must NOT be wired into protocol handlers until
it lands (a protocol-level lock that is not fenced at the storage writer is only
advisory — see the IMPORTANT block at the top):

* **A6-enforcement TD:** thread the fencing token from `WriteIntent` through the
  WAL intermediate to the flush boundary, and have each storage engine call
  `validate_fencing(write_gen, current_durable_gen)` before committing. This is
  the split-brain defense that makes DML locks non-advisory. (`FlushParameters`
  was deliberately NOT extended with the field: ~150 test construction sites are
  full literals, so a required field would break the test build for a field with
  zero current consumers — the enforcement TD will thread via `..Default::default()`
  or a dedicated write context.)
* **A7:** `DmlService::execute_scoped` acquires locks after catalog resolution,
  using real tenant/schema/table identity.
* **A8:** protocol error mapping (REST 409/423, gRPC ABORTED, pgwire
  SQLSTATE 55P03, Arrow Flight structured conflict).

Round-2 verification: `cargo check --lib` green; 46 `partition_lease` +
`dml_lock_metrics` + `validate_fencing` nextest cases pass (F5 hierarchy, F7
tombstone, A6 validator, A9 metrics — no regressions).
