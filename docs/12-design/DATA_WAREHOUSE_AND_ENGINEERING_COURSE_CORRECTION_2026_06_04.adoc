= Data Warehouse & Enterprise Data Engineering Course Correction
:toc: left
:toclevels: 3
:icons: font
:sectnums:
:revdate: 2026-06-04

[.lead]
This document defines a strategic course correction for ProximaDB's architecture, shifting focus towards direct competition with enterprise data warehouses (Snowflake, Databricks, BigQuery, Trino) and modern distributed data engineering engines (Spark, Ray). While the vector and multi-modal capabilities remain important, the foundational MVP and initial product wedge will now explicitly prioritize relational semantics, object-storage-first decoupled architecture, and Rust-native distributed execution.

== 1. Strategic Shifts

=== 1.1. Postgres Wire Compatibility as the Primary Wedge
To directly compete for SQL data warehouse workloads against Trino, Snowflake, and Databricks, ProximaDB must present a frictionless adoption path. The primary ingestion, DDL, DML, and query surface will be **100% PostgreSQL wire protocol compatible**. 
* **Why:** BI tools (Tableau, Looker, Metabase), dbt, and existing enterprise SQL workloads expect a Postgres or MySQL dialect. By prioritizing full Postgres compatibility, ProximaDB can be a drop-in replacement for existing analytical query engines.

=== 1.2. Relational Foundation First
While ProximaDB supports documents, graphs, and vectors, the core execution and storage models must optimize for the relational algebra first. 
* **Why:** The enterprise data engineering landscape runs on tables, columns, joins, and aggregates. The multi-modal features (vector search, graph traversal) will be implemented as extensions to the relational algebra, not completely separate paths.

=== 1.3. Object Storage First (Decoupled Storage & Compute)
The storage layer must be fully decoupled from the execution layer from day one, utilizing local filesystem API-driven object storage abstractions (e.g., `object_store` crate) that can seamlessly scale to S3/GCS/Azure Blob.
* **Why:** Snowflake and Databricks won by scaling compute independently from storage. ProximaDB's OLAP layout will prioritize open table formats (Parquet/Arrow/Iceberg) layered over object storage, utilizing advanced optimizations like header/filter-driven caches and late materialization to minimize I/O overhead. Mutable PostgreSQL-style OLTP tables still require a native WAL plus row/delta authority for low-latency DML, MVCC visibility, and constraint enforcement before they are published into OLAP snapshots.

=== 1.4. Rust-Native Distributed Execution (Spark-like)
Instead of purely delegating large-scale transformations to external Spark clusters, ProximaDB will build a **Rust-native distributed execution engine** close to the data, capable of PySpark-style API execution.
* **MVP:** The initial implementation will leverage **DataFusion** running in a single-node or pseudo-distributed seam (e.g., multi-process or multi-threaded worker model).
* **Future-proofing:** The execution architecture will remain flexible via a pluggable engine trait, allowing us to swap or enhance DataFusion with custom Rust-based distributed workers for CPU-intensive (Monte Carlo style) jobs and async I/O heavy workloads.
* **Why:** A unified Rust engine removes the JVM overhead of Spark, drastically lowers memory pressure, and simplifies the deployment topology while providing the same distributed data engineering capabilities.

=== 1.5. MLflow & MLOps Model Management Natively
To fully compete with Databricks in the data and AI space, the enterprise ML landscape (MLOps, MLflow, model management) must be integrated tightly into the data warehouse fabric. 
* **Why:** Data engineering pipelines inevitably feed ML training and inference. By mapping the MLflow landscape directly into ProximaDB's `xCatalog` (under `mlops.*`), the system provides a zero-ETL path from Parquet/Iceberg data engineering to model registry and artifact management, utilizing the same single-node/pseudo-distributed Rust engine for processing.

== 2. Blueprint for the MVP

=== 2.1. Pseudo-Distributed DataFusion Seam
The MVP will construct a single-node platform that simulates distributed execution. 
1. **Coordinator/Worker Abstraction:** A master coordinator process (or thread pool) handles Postgres wire connections, parses SQL/DataFrame logic, and creates logical plans.
2. **Pluggable Execution:** The logical plan is lowered into a physical plan executed by DataFusion workers. The design must isolate DataFusion behind an `ExecutionEngine` trait so it can be swapped.
3. **Async I/O Efficiency:** Workers will use Tokio async patterns to fetch Parquet/Arrow blocks from the object storage layer concurrently.

=== 2.2. Object Storage & Caching Layer
* **Storage Interface:** All data reads/writes go through an `ObjectStore` trait implementation. For MVP, this points to a local directory structure mimicking an S3 bucket layout.
* **Header/Filter Caching:** To achieve high performance, the system will implement aggressive caching of Parquet footers/headers and Iceberg manifests. 
* **Predicate Pushdown:** Query planning will utilize these caches to perform partition pruning and row-group skipping before any network/disk read occurs.

=== 2.3. Data Engineering Experience
* Provide a Python DataFrame API (via PyO3) that mimics PySpark's lazy execution model, compiling down into the same DataFusion/Rust logical plan that the SQL engine uses.
* Allow users to write UDFs in Rust or Python, executed safely within the worker processes.

== 3. Impact on Existing Architecture

* **Update to `DATA_AI_PLATFORM_ARCHITECTURE_ANCHOR`:** The anchor must reflect that local Rust execution is not just for HTAP, but the foundation for a distributed MPP warehouse.
* **Update to `COMPETITIVE_OLTP_OLAP_MPP_TRAJECTORY`:** Shift from "Delegate MPP to Spark/Trino" to "Build Rust-native MPP using DataFusion/Ballista concepts, outcompeting Spark/Trino on efficiency."

== 5. Intelligent Multi-Engine Routing (Policy to RL Evolution)

DECISION (2026-06-04): The architecture is not a binary choice between Volcano and DataFusion. The system utilizes an **Intelligent Multi-Engine Routing** multiplexer. To prevent fragmentation, all engines consume the same logical plane:

* **Shared logical plane, split physical plane.** All queries pass through `proximadb-relational-frontend` → `proximadb-relational-algebra` (`LogicalNode`). They diverge ONLY at the physical planner/executor. 

### 5.1. The Routing Destinations
The Query Router evaluates cardinality, partition counts, and freshness SLAs to select the optimal physical engine:
* **Volcano (OLTP):** Selected for point lookups, high-concurrency single-row DML (INSERT/UPDATE/DELETE), and queries demanding immediate, strong freshness against the WAL/Memtable.
  Also selected for primary-key/unique/check/foreign-key enforcement and any plan that cannot
  safely tolerate an OLAP snapshot watermark.
* **Polars (Local Analytics):** Selected for single-partition queries, lightweight aggregations, and local data transformations. Bypasses the overhead of DataFusion's distributed worker context, acting as the high-speed local execution seam.
* **DataFusion (MPP/OLAP):** Selected for multi-table joins, distributed processing, large-scale Parquet/Iceberg object storage scans, and complex window functions.
* **Specialized Engines (Vector/ANN):** Selected for similarity search, routing execution down to SST, VIPER, NOVA, HELIX, RAPTOR, SWIFT via the PAX block layout.

[NOTE]
.Implementation priority — Polars is benchmark-gated, not a day-one third engine (2026-06-04)
====
The four destinations above are the *target* taxonomy. For build order, the two
load-bearing analytical pillars are **Volcano** (OLTP + strong-freshness reads over
live WAL/`RecordStorage`) and **DataFusion** (OLAP/MPP over object-store
Parquet/Iceberg). DataFusion is strategically non-negotiable: it is the *only*
destination with a distributed/MPP path (Ballista-style), which is the entire point
of the Rust-native warehouse — Polars is single-node by design and cannot be the MPP
engine.

**Polars is an optimization, not a pillar.** Its niche — single-partition, lightweight
OLAP over Parquet — overlaps DataFusion's (already fast) low end and is adjacent to
Volcano's OLTP fast-path. Standing up a second Arrow analytical engine (a second
logical-lowering target in P4, more to maintain) is exactly the kind of parallel
surface the Convergence Gate says to justify with data, not speculation. **Therefore:
ship DataFusion-only first; add the `PolarsLocal` arm (P2) ONLY when profiling shows
DataFusion's small/single-partition OLAP overhead is a *measured* problem.** The
`ComputeBackend::PolarsLocal` slot stays reserved so the arm can drop in later behind
a benchmark, without reshaping the seam.
====

### 5.2. Routing Evolution: From Policy to Reinforcement Learning
* **Phase 1: Policy & Heuristic-Driven (MVP)**
  For the SaaS MVP, routing must be predictable and explicitly tied to SLAs and budgets. The `ComputeScheduler` relies on strict, rule-based policies. For example: if `partitions == 1` and `join_count == 0`, route to Polars. If `point_lookup == true`, route to Volcano.
* **Phase 2: RL-Driven Autonomous Routing**
  Leveraging the existing `RLPlanner` (Thompson sampling, Contextual Bandits), the system observes the execution of the policy-driven routes. It continually learns cost models based on observed latency, throughput, and I/O. As the cluster matures, the RL engine autonomously tunes the routing logic to find the perfect equilibrium between Polars' speed, DataFusion's scale, and Volcano's freshness for complex HTAP workloads.

* **Convergence-Gate registration.** This multi-engine seam is a deliberate by-design separation; record it in `CONVERGENCE_AUDIT_2026_05_30.adoc`.

== 8. Stacked Modalities over the Relational Spine (The Multi-Modal Moat)

ProximaDB’s foundational "moat" is providing zero-ETL multimodal capabilities over a single **canonical relational spine**. Instead of running three separate databases for SQL, Document, and Graph data, ProximaDB stacks all modalities on the same durable foundation.

* **The Relational Spine:** Every piece of data is durably stored as a canonical `ProximaRecord` containing a `ProximaValue` tuple, aligned with a standard tabular schema.
* **Document Modality (JSON):** Documents are stored as `JSONB`/`msgpack` typed columns within standard relational tables. `xCatalog` can automatically shred highly-structured, recurring JSON paths into virtual relational columns (using Iceberg path-level metadata and Parquet structural stripes) for vectorized DataFusion/Polars scans.
* **Graph Modality:** Graph topology is not a distinct durable silo. Nodes and Edges are standard relational tables. Specialized Graph algorithms (Cypher traversals, PageRank) operate over **derived, rebuildable projections** (e.g., compressed CSR/CSC neighbor lists stored in PAX/Parquet). If the graph projection is stale or lost, it is deterministically rebuilt from the canonical edge table.
* **Vector/ANN Modality:** Vector embeddings are stored as `List<Float32>` columns. The high-performance search indices (HNSW, LSH, IVF) are projections managed by specialized execution engines (SST, VIPER, NOVA, HELIX, RAPTOR, SWIFT). These engines handle SIMD acceleration and spatial co-location via the specialized PAX block layout, operating alongside the relational pathways.
* **Observability Modality:** Logs, metrics, and traces are time-partitioned relational rows, natively pushed into DataFusion/Polars for aggregations and rollups.

This architecture ensures that a single pgwire or REST request can join a Graph traversal result with a relational aggregation, filtered by a Vector similarity score—all without ever moving data outside the cluster.

== 9. SaaS MVP Rollout and Commercial Strategy

To sustain development and fund the complex, fully distributed MPP roadmap, ProximaDB will be brought to market quickly via a focused **SaaS MVP offering**. This establishes a revenue generation loop and real-world operational feedback.

### 9.1. The SaaS MVP Scope
* **Deployment:** Single-node robust execution (pseudo-distributed worker seam) running in a managed Kubernetes or ECS environment.
* **Storage:** Fully decoupled Object Storage (S3/GCS) utilizing the `object_store` crate.
* **Workloads Supported:** 
  1. **Transactional (Volcano/Polars):** Low-latency point lookups, single-row DML, and Vector Search (via SST/VIPER/HELIX) exposed over REST, gRPC, and Postgres wire.
  2. **Analytical (DataFusion):** Core aggregation, filtering, and projection via Postgres wire over Parquet/Iceberg.
* **Multi-Tenancy:** Hardened tenant isolation via `xCatalog` policy boundaries, RLS (Row-Level Security), and tenant-aware metrics.
* **Billing/Quota:** Built-in budget guards, rate limiting, and exact request/byte-level metering.

== 10. Operational SaaS Mandates (The Non-Negotiables)

To execute the SaaS MVP securely and profitably, the codebase must adhere to three strict operational mandates. These bridge the gap between "it works locally" and "it is a secure, billable SaaS platform".

### 10.1. SaaS Path Isolation & Security
Bypassing the tenant path hierarchy is a critical multi-tenant security risk.
* **Mandate:** The `ObjectStoreBridge` and all underlying `TableRecordStore` implementations **MUST** utilize `DrPathBuilder` (from `src/storage/trait_components/path_resolver.rs`) to resolve paths. 
* **Structure:** Every object written to decoupled storage must strictly adhere to the `data/{tenant_id}/{namespace_id}/{collection_id}/` prefix. Code must never use `schema.location` directly for internal ProximaDB tables.

### 10.2. Financial Accuracy & Billing Telemetry
To support a consumption-based pricing model, resource usage must be auditable and strictly attributed to the correct tenant.
* **Mandate:** The `ObjectStoreBridge` must emit Prometheus metrics for every I/O operation.
* **Required Metrics:** 
  - `proximadb_object_store_ops_total{tenant_id="..."}` (counters for put/get/delete).
  - `proximadb_storage_bytes_seconds{tenant_id="..."}` (gauge for GB-seconds stored).
* **DataFusion Overhead:** The `DataFusionTableWriteExecutor` must capture `task_execution_time_ms` attributed to `TenantContext` to bill for analytical compute separately from storage.

### 10.3. Operational Robustness & The Bootstrap Problem
The `tenant_tier` collection defines the tenant's capabilities, budget, and storage limits.
* **Gotcha:** If the SDK/read path for system collections moves to Object Storage, we risk a cyclic dependency (deadlock): we cannot resolve the tenant's tier to get their storage path because we need their storage path to read the tier database.
* **Mandate:** System configuration and the `TenantTierStore` must maintain a highly available, aggressively cached (or memory-pinned) tier registry that does not rely on heavy DataFusion execution or complex object-store lookups in the critical bootstrap path.
