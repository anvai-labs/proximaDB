== Design Decision

Precision policy must separate two different concepts:

. **Canonical embedding encoding**: the durable embedding value carried by
  `ProximaRecord`, WAL, and authoritative storage. Examples: `fp32`, `fp16`,
  later `bf16`, and only in explicitly lossy collection modes `int8`.
. **Derived quantization representations**: rebuildable auxiliary structures
  for filtering, approximate ranking, ANN compression, or cold-tier search.
  Examples: binary sketches, scalar int8, PQ8, PQ4/int4. These belong in
  `QuantizedSection`, index payloads, or columnar projection fields, not as a
  second source of truth.

The current code already points in this direction:

* `proto/proximadb/v1/vector_types.proto` removed `quantized_vector` from
  `VectorRecord` and states that quantization is internalized during
  flush/compaction.
* `src/storage/engines/core/formats/proximablocks/block_structures.rs` stores
  auxiliary `binary_vectors`, `int8_vectors`, `pq_vectors`, and `codebooks` in
  `QuantizedSection`.
* `src/compute/quantization/storage_engine.rs` already models progressive
  filter/fast/primary quantization levels.
* `crates/foundation/proximadb-quantization-types/src/lib.rs` already has
  common `QuantizationType` and `QuantizationLevel` concepts including
  `FP16`, `FP32`, `Int8`, `UInt8`, and `Int4`.

Therefore the policy should not introduce a parallel quantized-vector field in
records. It should decide:

* what canonical precision is durable;
* which auxiliary quantized levels are materialized;
* whether those auxiliary levels are storage-local, index-local, or both;
* when a tenant/collection/tier may move to a different precision epoch;
* how recall, freshness, and storage overhead are enforced.

== Motivation

The fp16 ONNX export of bge-large reduced model size from 1337 MB to 669 MB.
However, today the inference win is mostly lost after ORT returns the tensor:
`BgeModel::embed_batch_onnx` accepts `tensor(float16)` but promotes it into
`Vec<Vec<f32>>`, and `EmbeddingCell.values: Vec<f32>` is hardcoded in
`crates/foundation/proximadb-records/src/lib.rs`.

End-to-end `fp16` as canonical embedding precision would unlock:

[cols="2,1,3"]
|===
| Axis | Win | Notes

| Storage size
| 2x
| 1024-dim embeddings: 4096 B at fp32 versus 2048 B at fp16.

| WAL write throughput
| Up to 2x payload reduction
| Less data per append and fsync. Actual throughput depends on batching,
  compression, and storage engine overhead.

| Memtable and cache density
| 2x vector density
| More hot vectors per page before flush or cache eviction.

| Client/server bandwidth
| 2x for binary protocols
| Requires gRPC/Arrow/REST binary vector encodings. JSON float arrays do not
  automatically gain this.

| Distance compute
| Storage and memory win first
| Native fp16 kernels can improve compute, but promote-at-compute still gives
  the storage/memory win.
|===

Quantization has a different goal. Scalar int8, binary, PQ8, and PQ4 can shrink
or accelerate candidate generation, but they are lossy and usually need a
rerank path. They should be policy-controlled auxiliary layouts unless the user
explicitly opts into a lossy canonical collection.

== Storage Bloat Risk

Yes: the existing auxiliary quantization path can increase storage when it is
materialized in addition to the original vector.

For a 1024-dim vector, approximate per-vector payloads are:

[cols="2,1,3"]
|===
| Representation | Bytes | Notes

| Canonical fp32
| 4096
| Current durable value.

| Canonical fp16
| 2048
| Target durable value for standard lossy-float compression.

| Scalar int8 auxiliary
| ~1024 plus scale/zero-point metadata
| Good fast-rank level, still needs recall validation.

| Binary auxiliary
| 128
| Good coarse filter level.

| PQ auxiliary
| Depends on subvector count and code width
| Usually compact, but requires codebooks and training metadata.
|===

If we keep canonical fp32 and add int8 plus binary, the row becomes roughly
4096 + 1024 + 128 bytes before metadata and codebooks: about 28% larger than
fp32 alone. Adding PQ can be worthwhile for search, but it is still an
additional projection unless the policy explicitly replaces canonical storage.

Policy implication: auxiliary quantization must have a `max_overhead_ratio`,
and cold-tier or cost-sensitive policies should either:

* switch canonical precision to fp16;
* materialize only the levels needed by the active index/search plan;
* keep derived quantization index-local instead of storing all levels in every
  data block;
* allow dropping and rebuilding auxiliary levels from canonical embeddings.

Existing storage quantization is then an add-on at flush, compaction, or index

[source]
----

    |
    +--> ProximaDataBlock vectors
    |

           int8_vectors,

         }

That add-on model is useful for progressive search, but it does not reduce the

== Target Model

[source]
----
Tenant tier + collection config + global defaults
    |
    v
xCatalog EmbeddingPrecisionPolicy epoch
    |
    v
Inference route emits typed payload: fp32 or fp16
    |
    v
ProximaRecord.EmbeddingCell stores canonical values with declared precision
    |
    v
WAL stores canonical bytes once
    |
    +--> storage layout writes canonical precision
    |
    +--> optional derived quantization levels, bounded by policy
    |
    v
Planner chooses search precision/rerank path from cataloged capabilities
----

The important rule: dynamic policy may change the next epoch's storage and
search layout, but it must never silently reinterpret existing bytes.

== Policy Shape

Precision policy should be a typed xCatalog asset attribute, mirrored into
runtime config for defaults and tenant-tier rules. Collection metadata stores
the effective policy version/epoch so writes, compaction, and readers can reason
about mixed historical segments.

[source,rust]
----
pub struct EmbeddingPrecisionPolicy {
    pub policy_id: String,
    pub policy_version: u64,

    /// global_default, tenant_tier, collection_override, or query_hint.
    pub source: PolicySource,

    /// Fixed is deterministic. Adaptive may change epochs when telemetry
    /// proves the new encoding still satisfies recall and storage budgets.
    pub mode: PrecisionPolicyMode,

    /// Durable value stored in ProximaRecord/WAL/storage.
    pub canonical: CanonicalEmbeddingEncoding,

    /// Rebuildable auxiliary levels for search/filter/index acceleration.
    pub derived: DerivedQuantizationPolicy,

    /// Query-time execution and rerank behavior.
    pub query: QueryPrecisionPolicy,

    /// Safety gates applied before a policy is accepted or promoted.
    pub gates: PrecisionPolicyGates,
}

pub enum PolicySource {
    GlobalDefault,
    TenantTier,
    CollectionOverride,
    QueryHint,
}

pub enum PrecisionPolicyMode {
    Fixed,
    Adaptive,
}

pub struct CanonicalEmbeddingEncoding {
    pub default_precision: EmbeddingScalarType,
    pub allowed_precisions: Vec<EmbeddingScalarType>,

    /// reject, convert_once_at_boundary, or accept_mixed_segments.
    pub ingest_mismatch: IngestMismatchPolicy,

    /// false for fp16-first collections; true only when exact source
    /// reconstruction or audits require it.
    pub retain_fp32_shadow: bool,

    /// How precision changes are rolled out for existing collections.
    pub migration: PrecisionMigrationPolicy,
}

pub enum EmbeddingScalarType {
    Fp32,
    Fp16,
    Bf16,
    Int8Scalar,
    UInt8Scalar,
}

pub struct DerivedQuantizationPolicy {
    pub enabled: bool,
    pub levels: Vec<DerivedQuantizationLevel>,

    /// none, index_only, storage_auxiliary, or storage_and_index.
    pub materialization: QuantizationMaterialization,

    /// Example: 1.10 means derived structures may add at most 10% over the
    /// canonical embedding footprint unless an index explicitly owns them.
    pub max_storage_overhead_ratio: f32,

    /// Drop/rebuild derived levels from canonical data when stale or over
    /// budget instead of treating them as authority.
    pub rebuildable: bool,
}

pub enum DerivedQuantizationLevel {
    BinarySketch,
    ScalarInt8 { per: QuantizationScaleScope },
    ProductQuantization { bits: u8, subvectors: u16 },
    Int4Scalar,
}

pub enum QuantizationScaleScope {
    PerTensor,
    PerVector,
    PerBlock,
    PerDimension,
}

pub struct QueryPrecisionPolicy {
    pub default_search_level: SearchPrecisionLevel,
    pub allowed_query_hints: Vec<SearchPrecisionLevel>,
    pub rerank_with: RerankPrecision,
    pub reject_when_recall_slo_unknown: bool,
}

pub enum SearchPrecisionLevel {
    Canonical,
    Fp32Promoted,
    Fp16Native,
    Int8Approx,
    BinaryFilter,
    PqApprox,
}

pub enum RerankPrecision {
    None,
    Canonical,
    Fp32Promoted,
}

pub struct PrecisionPolicyGates {
    pub min_recall_at_10: f32,
    pub min_recall_at_100: f32,
    pub max_latency_regression_pct: f32,
    pub max_storage_overhead_ratio: f32,
    pub require_hardware_capability: bool,
    pub require_explain_visibility: bool,
}
----

=== Tier comparison: Business / Pro and Cold / Cost-Optimized

The Standard tier above is the full YAML skeleton — every tier sets the same keys, so the
other two tiers are shown here as deltas from it rather than as two more near-identical
blocks (the shared boilerplate — `source`, `ingest_mismatch`, `retain_fp32_shadow`,
`migration`, `derived.enabled`, `rebuildable`, `reject_when_recall_slo_unknown`,
`require_explain_visibility` — is unchanged in all three):

[cols="2,2,2", options="header"]
|===
| Knob | Business / Pro Tier | Cold / Cost-Optimized Tier

| `mode`
| `adaptive`
| `adaptive`

| `canonical.default_precision` / `allowed_precisions`
| `fp16` / `[fp32, fp16]`
| `fp16` / `[fp16]` (fp32 not retained)

| `derived.levels`
| `binary_sketch` + `scalar_int8` **per_block** + `product_quantization` (bits 8, subvectors 64)
| `product_quantization` (bits 8, subvectors 64) first, then `binary_sketch`

| `derived.materialization` / `max_storage_overhead_ratio`
| `storage_and_index` / `1.55`
| `storage_auxiliary` / `1.20`

| `query.default_search_level` / `allowed_query_hints`
| `fp32_promoted` / `[canonical, fp16_native, int8_approx, pq_approx]`
| `pq_approx` / `[pq_approx, canonical]`

| `query.rerank_with`
| `fp32_promoted`
| `canonical`

| `gates` (recall@10 / recall@100 / latency regression / storage overhead / hardware)
| `0.99` / `0.995` / `5%` / `1.55` / **required**
| `0.97` / `0.99` / `15%` / `1.20` / not required
|===

The shape of the progression: Standard serves canonical fp32 with cheap derived hints; Pro
pays storage (`storage_and_index`, 1.55x) to make fp16-native and PQApprox first-class query
levels under a 5% latency gate and a hardware-capability requirement; Cold drops fp32
entirely (`allowed_precisions: [fp16]`), serves straight from PQ with only canonical as the
escape hatch, and relaxes recall/latency gates (0.97/15%) in exchange for the tightest
storage bound (1.20x).

== Dynamic Resolution Rules

Policy resolution order:

. Query hint, if present, may select only among catalog-allowed search levels.
  It cannot change durable canonical precision.
. Collection override wins for canonical storage on that collection.
. Tenant tier supplies defaults for new collections and permitted policy ranges.
. Global config supplies defaults when tenant metadata is absent.
. Engine capability and hardware checks prune unsupported levels.
. Recall and storage gates must pass before an adaptive policy becomes the
  default for a collection or tier.

Canonical precision changes must use policy epochs:

. xCatalog records `embedding_precision_policy_id`,
  `embedding_precision_policy_version`, and `precision_epoch`.
. New writes use the latest active epoch.
. Existing segments keep their recorded precision until background rewrite or
  compaction converts them.
. Readers and ANN planners must accept mixed segments by reading segment-level
  precision metadata.
. EXPLAIN must show effective precision, auxiliary quantization levels, rerank
  precision, fallback, and rejected levels with reasons.

This gives dynamic behavior without per-row ambiguity or silent downgrade.

== Schema Changes

=== `proximadb-records`

`EmbeddingCell` should stop hardcoding `Vec<f32>` as the only durable
representation. The first implementation can add `F16` while leaving int8/PQ
as derived quantization.

[source,rust]
----

    Fp16,

    UInt8Scalar,

#[derive(Debug, Clone, Serialize, Deserialize)]

    Fp32(Vec<f32>),
    Fp16(Vec<half::f16>),
    Bf16(Vec<half::bf16>),

    // Explicit lossy canonical modes only. Not the default path for current
    // vector collections.
    Int8Scalar {
        values: Vec<i8>,

        values: Vec<u8>,

Compatibility helpers should provide:

* borrowed `&[f32]` for fp32;
* owned promotion for fp16/bf16/int8 when legacy code requires fp32;

== Ingest And Conversion Boundaries

Ingest rules:

. Client-supplied fp32 into fp16 collection: convert once at protocol boundary
  after validation, record conversion metadata, and write fp16.
. Client-supplied fp16 into fp32 collection: either promote to fp32 or reject
  based on `ingest_mismatch`.
. Server-side embedding: request model route plus desired output precision when
  supported. If ORT/model output is fp16 and collection is fp16, avoid
  promotion.
. Lossy canonical int8/uint8: require an explicit collection policy and
  surface a lossy-conversion warning in create/alter responses and EXPLAIN.
. Derived quantization: never enters the record API as an authoritative value.
  It is built during flush, compaction, index build, or background
  re-quantization.

== Search And Rerank

Search should have staged precision:

. **Filter stage**: optional binary sketch or coarse PQ/int8 filter.
. **Approximate rank stage**: optional int8/PQ ranking.
. **Rerank stage**: canonical precision or fp32-promoted canonical precision.

For fp16, the incremental path is:

. Store canonical fp16.
. Promote queries once at search entry when the distance engine expects fp32.
. Add `compute_dot_f16_f32` / `distance_f16_f32` paths that promote vector lanes
  inside the kernel.
. Add native fp16 kernels only after recall and hardware benchmarks justify it.

For int8/PQ/binary, use them as derived candidates first. Canonical lossy int8
should be a separate feature gate because exact fp32/fp16 reconstruction is not
possible.

== Re-Quantization And Tier Transitions

Dynamic tenant or business-tier changes should not rewrite bytes inline on the
request path. They should create a cataloged transition:

. Validate target policy against tier, engine capabilities, hardware, recall
  baselines, and storage budget.
. Create a new precision epoch in xCatalog.
. Route new writes to the new epoch.
. Queue compaction/rewrite/re-quantization for old segments.
. Mark derived quantization stale when codebooks, model route, scale scope, or
  canonical precision changes.
. Rebuild/drop derived auxiliary levels from canonical embeddings.
. Publish transition state and fallback through EXPLAIN and catalog
  introspection.

The existing `src/storage/operations/requantization.rs` can be aligned with this
policy as the manager for derived quantization refresh. Canonical precision
migration should be tracked separately because it changes the durable
`ProximaRecord` representation.

== Recall Validation

Recall gates should be policy values, not hardcoded global constants.

Minimum validation before enabling a new default:

. Compare fp32 canonical baseline with fp16 canonical and derived quantization
  plans.
. Use representative tenant data where available; fall back to SIFT-1M,
  GloVe-100, and an embedding-model-specific corpus.
. Measure recall@10, recall@100, latency p50/p95/p99, storage bytes per vector,
  WAL bytes per write, and rerank candidate counts.
. Validate mixed-epoch reads: fp32 and fp16 segments must return stable results
  under the same query policy.
. Fail closed: if recall metrics are missing for a requested adaptive default,
  keep fp32 or the previous active policy.

Suggested default gates:

[cols="2,2,2"]
|===
| Policy class | recall@10 | recall@100

| Compatibility / fp32
| Baseline
| Baseline

| fp16 canonical
| >= 99% of fp32
| >= 99.5% of fp32

| int8/PQ derived with fp32/fp16 rerank
| >= 99% of reranked baseline
| >= 99.5% of reranked baseline

| Cold/cost optimized
| >= 97% of fp32
| >= 99% of fp32
|===

== EXPLAIN Contract

Search and write plans should include:

* `canonical_embedding_precision`
* `precision_epoch`
* `policy_id` and `policy_version`
* `derived_quantization_levels`
* `quantization_materialization`
* `search_precision_level`
* `rerank_precision`
* `storage_overhead_ratio`
* `recall_slo`
* rejected precision/quantization levels and reasons
* fallback reason, if a requested hint is pruned

This keeps precision changes explainable instead of hidden in storage-engine
heuristics.

== Phasing

. **Phase 1: current fp16 inference compatibility**
  * Keep fp32 `EmbeddingCell.values`.
  * Accept fp16 ORT output and promote to fp32.
  * Record the current limitation in this design and benchmark artifacts.

. **Phase 2: policy metadata and type unification**
  * Add `EmbeddingScalarType` / `EmbeddingValues` to
    `proximadb-records`.
  * Reuse and converge with `proximadb-quantization-types` instead of adding
    another independent quantization enum.
  * Add xCatalog precision policy fields and default all existing collections
    to fp32.

. **Phase 3: fp16 canonical storage**
  * WAL, memtable, PAX/SST/ProximaDataBlock, Arrow bridge, and record
    conversion support fp16.
  * Legacy APIs keep accepting fp32 and convert at the boundary.
  * Search promotes fp16 to fp32 for distance compute.

. **Phase 4: derived quantization policy enforcement**
  * Tie existing `QuantizedSection` creation to the catalog policy.
  * Enforce `max_storage_overhead_ratio`.
  * Support index-only versus storage-auxiliary materialization.
  * Expose EXPLAIN metadata.

. **Phase 5: adaptive tier transitions**
  * Implement precision epochs.
  * Route new writes to the active epoch.
  * Add background canonical precision rewrite and derived re-quantization.
  * Validate mixed-epoch search.

. **Phase 6: native kernels and lossy canonical modes**
  * Add fp16-native distance kernels where hardware proves useful.
  * Add explicit lossy canonical int8/uint8 only with opt-in collection policy,
    recall gates, and supported-surface documentation.
  * Keep PQ/binary as derived by default.

== Backward Compatibility

Strict requirements:

* Existing fp32 collections remain fp32 until explicitly migrated.
* Missing precision metadata deserializes as fp32.
* Old clients sending `repeated float vector` continue to work.
* New clients requesting unsupported precision get an explicit rejection, not a
  silent downgrade.
* Derived quantization remains rebuildable and non-authoritative unless a future
  supported-surface document explicitly marks a lossy canonical mode supported.

== Open Questions

. Should `EmbeddingScalarType` live in `proximadb-records`, or should
  `proximadb-records` directly depend on the foundation
  `proximadb-quantization-types::QuantizationLevel`? Recommendation: define
  record-specific `EmbeddingScalarType` for durable scalar encoding and provide
  explicit conversions to shared quantization types.
. Should fp16 be allowed as a per-collection immutable choice first, with
  epochs added later? Recommendation: yes. Start immutable for v1 and introduce
  epochs when background rewrite is ready.
. Should bf16 ship with fp16? Recommendation: no. Keep it in the enum/design if
  the dependency is cheap, but do not advertise support until model output,
  storage, and hardware paths are tested.
. Can canonical int8 replace fp16 for cost-sensitive tiers? Recommendation:
  only as an explicit lossy collection mode after recall validation. For normal
  vector collections, int8 remains derived and reranked.
