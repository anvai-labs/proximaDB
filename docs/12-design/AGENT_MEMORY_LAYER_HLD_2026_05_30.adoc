== Problem & Goals

AI agents need long-term, cross-session memory: a place to write distilled facts and read back the
salient ones, with provenance and dedup. The ecosystem solves the *orchestration* of this (mem0,
agentmemory); ProximaDB owns the *substrate* (durable multi-model storage, retrieval, fusion, ranking,
audit). The goal of this HLD is to make ProximaDB a first-class agent-memory backend by **reusing** its
existing surfaces and positioning mem0/agentmemory as compatible consumers — per ADR-022.

=== Non-goals

* **Not** a new storage engine, WAL path, or catalog contract — memories are `ProximaRecord`s.
* **Not** a re-implementation of mem0's pipeline or a vendoring of agentmemory's code.
* **Not** a new LLM-provider abstraction — extraction/consolidation reuse `LLMIntegrationEngine`.

== Layering — orchestration vs storage

The single most important framing: mem0 and agentmemory are *orchestration libraries*; ProximaDB is the
*storage/infrastructure layer* they sit on top of. They are complementary, not competitive.

== What mem0 and agentmemory are (cited)

[cols="1,2,2", options="header"]
|===
| | mem0 (`mem0ai`) | agentmemory (Moon, PyPI)

| Kind
| LLM-driven memory orchestration layer
| Thin CRUD + semantic-search function library

| Pipeline
| Two-phase: *extraction* (salient facts per message pair) + *update/consolidation* (retrieve top-_s_ similar → LLM picks `ADD`/`UPDATE`/`DELETE`/`NOOP`)
| None — manual `create_memory` / `search_memory`; similarity-threshold dedup only

| Retrieval
| Hybrid: semantic + BM25 + entity match
| Semantic embedding search

| Storage backend
| Pluggable, 20–24+ vector stores (Qdrant default) + optional graph store (Neo4j default, `Mem0g`)
| ChromaDB default, or Postgres/pgvector via `CLIENT_TYPE`

| Own storage engine?
| No (bundles a SQLite history/audit log only)
| No

| Source
| arXiv:2504.19413; `docs.mem0.ai`; `mem0/utils/factory.py`, `mem0/vector_stores/base.py`
| PyPI `agentmemory`; README function list
|===

[cols="2,3,1", options="header"]
|===

| Entropy-based lazy loading (L-RAG)

| External-framework integration
| pgvector-compatible pgwire — `src/network/postgres/{mod.rs,types.rs,translator.rs}`
| Reuse
|===

== Phased plan

All phases below target the **v0.2** release in development (P1→P4 sequenced within v0.2, not deferred).
The Phase-6 active-memory gates (TD-052/053/054) are pre-existing roadmap items that P4 aligns to.

[cols="1,3,1", options="header"]
|===
| Phase | Work | Tracker

| P1 — Read surface
| Wire AQL memory queries with tenant/session/`memory_type` scope over existing fusion + RERANK; emit RUBICON audit per query. Validate mem0 PGVector provider against pgwire 5433.
| TD-100 — *Done* (closed 2026-05-30)

| P2 — Write surface
| Extraction wrapper (`LLMIntegrationEngine` + AV-SQL pattern) → consolidation decision (retrieve + LLM `ADD/UPDATE/DELETE/NOOP`) → `ProximaRecord` write. `props["session_id"]` scope.
| TD-101 — *In Progress*

| P3 — Framework adapters
| mem0 `VectorStoreBase` provider + (optional) graph-store mapping to native graph; agentmemory pgvector path notes; conformance tests.
| TD-102 — *Partial* (Slice B open: Python mem0 `VectorStoreBase` provider, mem0g graph mapping, binary param decode)

| P4 — Active memory (Phase 6 align)
| Encoding gates (Novelty/Salience/Error, TD-053), entropy-based lazy loading (TD-054), proactive retrieval (TD-052).
| TD-053/054/052 — *Open*
|===

== Open questions

* Does ProximaDB's pgwire implement enough of the pgvector surface (operators, index types, ANN query
  syntax) that mem0's PGVector provider works unmodified? (Validate in P1.)
* Can one ProximaDB collection back *both* mem0's vector store and mem0g's graph store, and do mem0g's
  graph operations map onto the native graph engine? (P3.)
* Is a first-class `ProximaRecord.session_id` field warranted, or is `props["session_id"]` sufficient for
  the query paths agents actually use? (Revisit after P2.)
