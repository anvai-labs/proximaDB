=== Working conventions (owner directives)

* **Foundational items first,** in dependency order (P2 before P3 before P4). Where there is a choice, take the performant and robust approach rather than the expedient one.
* **Commit and merge continuously; always build on the current baseline.**
** Rebase every branch on `origin/develop` before building, pushing, or merging.
** Merge a PR with a **merge commit** once CI is green on a head that is current with `develop`.
** With several lanes merging (see §4.1), "current" means: re-run CI after a rebase only when `develop`'s new commits touch files the PR touches, or GitHub reports the PR not cleanly mergeable. Otherwise a green PR merges directly — re-running CI after every unrelated merge would livelock the lanes; the merge commit's own CI on `develop` is the backstop.
** Start the next slice while CI runs.
* **PRs.**
** One slice per PR.
** Body follows `.github/PULL_REQUEST_TEMPLATE.md`.
** Check the body with `python3 scripts/check_no_agent_attribution.py --stdin < body.md` before creating it.
* **Before pushing,** run:

* **Progress reports:** an ASCII roadmap with per-phase percentages (format in §2).

=== Build and CI notes (small dev boxes)

* **Memory and disk.** The root crate's lib and test builds need roughly 10 GB or more of RAM.
** Use swap plus `CARGO_BUILD_JOBS=2` and `CARGO_INCREMENTAL=0`.
** Share one `CARGO_TARGET_DIR` across worktrees.
** Prune stale `libproximadb*` rlib/rmeta files and old test binaries when the disk fills.
** Run one large build at a time.
* **Lib unit tests.** These run in CI under nextest, which is process-per-test, so env-gate tests do not leak between tests.
** Locally, filter and serialise: `cargo test --lib -- record_spill:: record_store::tests:: --test-threads=1`.
* **Integration tests:** `cargo test --test <name> -- --test-threads=1`. The CI storage lane runs `tests/*sst*.rs`, `tests/*storage*.rs` and `tests/*wal*.rs` this way.
* **When the CI job-log blob host is unreachable:**
** read check-run annotations and failing step names through the REST API (`gh api .../check-runs/<id>/annotations`, `.../actions/jobs/<id>`);
** reproduce locally;
** GraphQL `gh pr` commands may be blocked; use `gh api` REST.

== 5. Next-work queue (in order)

=== 5.1 Spill encoder uses the catalog schema (P2.2)

Facts from a code survey on 2026-10-20:

* `flush` builds its schema with `infer_proxima_schema(&written)`. The batch comes from `proxima_records_to_record_batch_with_system_columns`.
* `ProximaSchema` *is* `CatalogTableSchema` (`proximadb-storage-common/src/proxima_schema.rs`), so no conversion is needed.
* The partition factory receives only `(tenant_id, collection)`. The schema is available at `DirectWalTableRecordStore::partitions_for(tenant, &CatalogTableSchema)` and on every write and scan path, but not during WAL replay.

Plan:

. Add a schema hint to the partition: a `RecordStorage` method with a no-op default, overridden by `SpillRecordStorage` and set from `partitions_for`.
. Encode with the catalog column types and **append** any inferred prop the catalog lacks, so no prop is ever dropped (a column added after the hint must survive).
. Partitions created by replay fall back to inference until a write sets the hint.
. Gate: a round-trip with typed columns (DECIMAL, INT, DATE) reads back exactly, and an unknown prop survives.

=== 5.2 Durable branch merge-base (TD-SEAM-12 hazard 2) — design 2026-10-21

Today: branch merge reads the whole retained WAL; the merge base is an LSN
(`find_merge_base_lsn` = first branch write − 1), never stored; base records =
latest untagged upsert ≤ base per oid (`latest_base_records`, `src/graph/merge.rs`).
Since 2026-10-21 the merge refuses (410) once any history is truncated.

Chosen design (option D): a main-line **base image** per branched
`(tenant, collection)`, kept in the WAL by checkpoint-style appends (the
`RankProfileStore::checkpoint` pattern). Rejected: flooring at the oldest branch entry
(deletes the base), reading the base from the record tier (replay ignores `branch_id`;
no as-of reads), per-branch snapshots of touched oids (future first touches unknown).

* `T = min(oldest retained branch entry, head+1) − 1`; the image holds latest
  untagged upsert per oid as of `through = T`; base at M = image(T) + retained
  untagged upserts in (T, M] — identical to today's result.
* New `WalFloorSource` `BranchMergeBase` replaces `BranchEntriesGuard`: floor =
  oldest retained branch entry; refuses on read/append failure or a broken
  `through + 1 < retained_from` invariant. Appends, so it runs after the read-only
  sources.
* Commits: (1) `canonical_wal` per-segment `first_branch_seq` + branched collection
  set, `branch_summary()`, `collections_below()`; (2) `graph/merge`
  `MergeBaseImage` + `merge_branches_with_base`; (3) `services/branch_base_store`
  (rows in `__proxima_branch_bases__`: image rows, a header written last, truncated
  marks; replay ignores image rows newer than the header); (4) truncator source swap +
  ordering; (5) REST: pin history above the image during a merge, `MergeBaseTruncated`
  → 410, `tests/wal_branch_merge_base_test.rs` (truncate below a branch point, merge
  identical to the untruncated result); (6) docs.
* Follow-ups found in review: write-back keeps the source `branch_id` (no branch ever
  closes → floor never advances); default `target_branch = "main"` never matches
  untagged main records; `latest_base_records` ignores main-line deletes; a branch
  first created after its collection's history was truncated needs explicit branch
  registration (`BranchRef`).

=== 5.3 P2.4 streaming MATERIALIZE — design 2026-10-21

Findings that shape it: `publish_iceberg_snapshot` *lists* the data prefix into the
manifest (multi-part output would mix generations); the DuckDB route reads the whole
directory; the DataFusion reader falls back to listing on any manifest error; the
Iceberg publish runs after the catalog flip and treats `Conflict` as success; spill
`merged_records` loads every segment; and the TPC harness cannot generate SF1 (it
builds the whole statement `Vec`; preflight ~87 GiB), so the gate needs harness work.

Ordered PRs:

. Readers fail closed: `manifest_selected_files` → `Result` (list only when no
  metadata log exists); DuckDB view reads the manifest's file list.
. `publish_iceberg_files(files, parent, …)` with an explicit file list,
  generation-unique Avro paths written `put_if_absent`, `Conflict` is an error.
. `ParquetWritePolicy` `target_file_rows` / `target_file_bytes`;
  `MultipartParquetWriter` (`AsyncArrowWriter` over object_store; `finish`/`abort`).
. Streaming scan: `RecordScan::scan_record_chunks` (memtable by key snapshot; spill
  k-way merge over oid-sorted segments with ranged row-group reads),
  `TableRecordStore::scan_records_chunked` (primary-over-legacy),
  `DmlService::scan_table_records_chunked`.
. MATERIALIZE rewrite: chunked scan → DataFusion `SortExec` under a memory-limited
  pool with spill → part writer; real oids; streaming NDV accumulator; generation
  names; GC of files older than V−1.
. Fenced advance: per-table publish lock, `PublishFence` re-checked before commit,
  Iceberg `put_if_absent` commit **before** the catalog flip, forward-only layout.
. Harness: streaming `gen_tpcds`, `TPC_PERF_LOAD_ONLY`, VmHWM / cgroup
  `memory.peak` per phase; run the SF1 gate (spill gate on) and record peak RSS.
. Slice 2: hidden `__proxima_oid` in published files, explicit key SBBF,
  insert-only incremental append classified by manifest bounds + SBBF, full-rewrite
  fallback. Slice 3: Iceberg v2 position deletes, writer and readers together.

Layer A segments are **not** reused as Iceberg data files in P2.4: local disk,
overlapping versions, persisted tombstones, per-segment schemas, no field ids.

=== 5.4 P3.1 `LayerATableProvider` — design 2026-10-21

Today native SQL goes `try_run_select` → `route_select_inner` (`DataFusionLocal`, gate
`PROXIMADB_NATIVE_TABLE_PROVIDER`, default OFF) → `prepare_dataframe`
(`src/query/execution/datafusion_engine.rs:165-206`): `full_table_records` →
`scan_table_relational(limit=cap+1)` → one `MemTable` (1M-row cap; `None` over it).

Design: a flush-consistent snapshot port (`RecordScan::scan_view` → resident rows,
tombstones, segment paths oldest→newest, taken under the segment lock), a
`TableRecordStore::layer_a_snapshot` / `NativeTableSource::layer_a_snapshot` (identity +
ABAC prelude shared with `scan_table_relational`), and `LayerAScanExec`: k-way merge of
oid-sorted segments (newest wins, masks per batch, O(k × batch) memory), memory shadow
(resident oids + tombstones drop segment rows), liveness/tenant/variation filters
vectorized on system columns, catalog-schema conformance (cast / NULL-fill; slow path
through `record_batch_to_proxima_records` for residual / vector / null-PK rows), ABAC
before the limit, resident rows last. Filters are pushed down **Inexact**. Pruning (PR B)
must respect newest-wins (key spine for overlapping row groups), the residual (never prune
a row group with residual rows), type mismatch and PK nulls.

Ordered PRs: (0) legacy path declines a bare window function on a native table (fixes the
silent `lag()` wrong answer, TD-USUB-2); (1) `scan_view` + `merged_records` rebuilt on it —
**fixes a likely live race**: today a flush between the segment-list clone and the
memtable read can lose rows from a scan (also used by unique-index builds); (2) snapshot
port; (3) `FileSystemParquetReader` (`AsyncFileReader` over `read_range`); (4) provider +
exec behind a MemTable kill switch, gate `native_table_capability_parity_e2e` + a new spill
e2e; (5) pruning; (6) residual-aware pruning; (7) dynamic filters, oid-range partitions,
`pk = lit` → oid lookup; (8) mixed Parquet + native; (9) port the OLAP read-merge onto the
exec (retire the second MemTable); (10) default-ON flip after a soak.
