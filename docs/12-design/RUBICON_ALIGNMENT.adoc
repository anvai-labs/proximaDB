= RUBICON Alignment: Auditable Agentic Query Layer (AQL)
:toc: left
:toclevels: 3
:sectnums:
:icons: font

== Executive Summary

This document specifies how ProximaDB will align with the RUBICON
architecture proposed by Wenz, Treutwein, Arenja, Demiralp, and
Stonebraker in arXiv:2604.21413 ("An Alternate Agentic AI Architecture
(It's About the Data)"). The paper's central thesis: *enterprises do
not need stronger LLM reasoning; they need better data integration with
**traceability, determinism, and trust***. RUBICON achieves that by
replacing opaque LLM agent chains with **explicit, auditable query
plans** expressed in AQL — an Agentic Query Language with `Find`,
`From`, and `Where` operators executed through source-specific
wrappers.

The goal of this work is *not* to ship a new query language. It is to
make ProximaDB's existing federated multi-model query surface satisfy
RUBICON's audit contract: every cross-model query the database executes
must produce a structured trace that names every source it touched,
every filter it applied, every cost it paid, and which engine returned
which row.

[IMPORTANT]
====
This is a **design specification**, not an implementation plan. No code
is shipped by this document. Implementation tasks are listed in
section <<acceptance>> and tracked in
`docs/10-quality/TECHNICAL_DEBT.adoc` TD-050.
====

== Paper attribution and verified scope

The paper was fetched and verified on April 25, 2026 (first pass) and
April 26, 2026 (second pass against deeper sections). Verified
findings:

- RUBICON is an architectural pattern, not a database engine.
- AQL operators are `Find`, `From`, `Where` — three primitives, each
  with a *source-specific wrapper*.
- The paper's contribution is *traceability, determinism, and trust*
  — not novel reasoning capabilities.
- The paper does **not** discuss DBOS, durable execution, or persistent
  agent memory. Earlier ProximaDB design drafts conflated RUBICON with
  a "Context Lake" memory store; that conflation has been corrected.

== Substrate already in place

ProximaDB already ships most of what RUBICON needs as primitives:

[cols="3,3,2", options="header"]
|===
| Capability | Where | RUBICON role

| Cross-model joins (vector / graph / document / observability)
| `src/query/federated/`
| AQL `From` source dispatch

| SQL extensions: `VECTOR_SEARCH()`, `GRAPH_QUERY()`, `DOCUMENT_QUERY()`
| `src/query/unified/`
| Per-source wrappers AQL invokes

| Federated optimizer producing `OptimizedPlan`
| `src/query/unified/optimizer.rs`
| Plan generation prior to execution

| Plan + selectivity hints + execution order
| `OptimizedPlan { execution_order, selectivity_estimates, … }`
| Audit-trail content

| Audit logging
| `src/security/`
| Persistent storage of audit traces
|===

What is *missing* is the structured audit-trail emitter. The
`UnifiedQueryEngine::explain()` method (`src/query/unified/mod.rs:319`)
returns a `QueryPlan` summary, but it is a *static plan estimate* —
not a *runtime trace* of what actually happened during execution.
RUBICON requires the latter.

== AQL operator design for ProximaDB

=== Operator surface

|===
| AQL operator | Maps to | Wrapper

| `Find <projection>`
| `SELECT … FROM` clause head
| All

| `From <source>`
| Multi-model `From` source dispatch
| One per data model

| `Where <predicate>`
| Federated query `WHERE` clause + per-engine filter pushdown
| All
|===

The mapping is intentionally one-to-one with existing federated query
primitives. AQL is *not a new SQL dialect*; it is a structured
abstract syntax that callers can construct directly without going
through SQL parsing, and that ProximaDB always produces an audit trace
for.

=== Source-specific wrappers

Each data model gets one `From` wrapper. For ProximaDB's six models
(vector, graph, document, observability, relational, event):

[source,rust]
----
// New trait, lives in src/query/aql/source.rs (proposed).
pub trait AqlSource: Send + Sync {
    /// The data model this wrapper resolves.
    fn model(&self) -> DataModel;

    /// Translate an AQL `Where` predicate into the source's native
    /// filter representation. Returning Err here means "this filter
    /// cannot be pushed down" -- the federated executor will apply
    /// it post-fetch instead, and the audit trace will record that
    /// fact.
    fn translate_predicate(
        &self,
        predicate: &AqlPredicate,
    ) -> Result<NativeFilter, PushdownError>;

    /// Execute the wrapped operation and emit a structured audit
    /// frame describing what it did.
    async fn execute(
        &self,
        find: &AqlFind,
        from: &AqlFrom,
        where_clause: &AqlWhere,
        ctx: &mut AuditContext,
    ) -> Result<SourceResult>;
}
----

Existing per-model executors (`execute_vector_search`,
`execute_document_query`, etc. in `src/query/unified/executor.rs`)
become the bodies of the corresponding `AqlSource::execute` impls.
The `AuditContext` parameter is the load-bearing change.

=== AQL AST

[source,rust]
----
pub struct AqlQuery {
    pub find:  AqlFind,
    pub from:  AqlFrom,
    pub where_clause: AqlWhere,
}

pub struct AqlFind {
    pub projections: Vec<AqlProjection>,
}

pub enum AqlFrom {
    Source { name: String, alias: Option<String> },
    Join { left: Box<AqlFrom>, right: Box<AqlFrom>, on: AqlPredicate },
}

pub enum AqlPredicate {
    Equals     { field: String, value: AqlValue },
    GreaterThan{ field: String, value: AqlValue },
    Contains   { field: String, value: AqlValue },
    And        { lhs: Box<AqlPredicate>, rhs: Box<AqlPredicate> },
    Or         { lhs: Box<AqlPredicate>, rhs: Box<AqlPredicate> },
    Not        { inner: Box<AqlPredicate> },
    SemanticMatch { field: String, query: String, threshold: f32 },
}
----

This AST is constructible from three places:

1. **Direct programmatic use** — agents emit AQL JSON, the database
   parses it. No SQL parsing involved.
2. **From the existing UQL / SQL surface** — a translator turns the
   parsed plan into AQL so the audit-trail emitter sees the same
   shape regardless of how the query came in.
3. **From AV-SQL (TD-048) decomposition** — the agentic
   view-decomposer emits AQL fragments per view, joined into a final
   plan.

== Audit-trail design (the load-bearing change)

=== Goals

. Every cross-model query produces an `AuditTrail` artifact.
. The trail names: every source touched, every filter applied (with
  pushdown vs. post-filter status), every measured cost, and which
  engine returned which rows.
. The trail is structurally serializable to JSON for compliance
  archival and to a human-readable form for `EXPLAIN VERBOSE`.
. The trail is deterministic — given the same plan and the same data,
  two runs produce equivalent trails (modulo wall-time).

=== Schema

[source,rust]
----
pub struct AuditTrail {
    pub query_id: Uuid,
    pub started_at_ms: i64,
    pub finished_at_ms: i64,
    pub plan: AqlQuery,
    pub frames: Vec<AuditFrame>,
    pub outcome: AuditOutcome,
}

pub struct AuditFrame {
    pub frame_id: u64,
    pub source: DataModel,
    pub op: AuditOp,
    pub filters_pushed: Vec<PushedFilter>,
    pub filters_post: Vec<UnpushedFilter>,
    pub records_scanned: u64,
    pub records_returned: u64,
    pub wall_time_us: u64,
    pub error: Option<String>,
}

pub enum AuditOp {
    VectorSearch { collection: String, top_k: u32, metric: DistanceMetric },
    GraphTraversal { graph_id: String, depth: u32 },
    DocumentQuery { collection: String },
    LogQuery { namespace: String },
    MetricAggregate { namespace: String, metric: String },
    Join { join_type: JoinType, left_frame: u64, right_frame: u64 },
}

pub enum AuditOutcome {
    Success,
    PartialFailure { failed_frames: Vec<u64> },
    Failure { reason: String },
}
----

=== Invariants (testable)

. `frames.len() >= 1` whenever the plan has at least one source.
. Every frame's `records_returned <= records_scanned`.
. Every frame's `wall_time_us > 0` on success (timing is mandatory).
. `query_id` is unique per call, suitable for log correlation.
. JSON round-trip: `serde_json::to_string` followed by `from_str`
  yields an equivalent `AuditTrail` (no info loss).
. No PII smuggling: filter values that match a configured PII pattern
  are *redacted* in the trail (see <<pii>>).

=== Storage and retention

Audit trails persist in ProximaDB's existing event-sourcing engine
(`src/storage/engines/impls/eventlog/`, TD-010 already shipped) under
collection `_aql_audit`. Retention follows the configured compliance
policy in `[security]` config; default 365 days for SOC 2 / MiFID II.

[#pii]
=== PII redaction

`Where` predicates carry user-supplied values that may include PII
(emails, customer IDs, secrets in metadata filters). The audit
emitter redacts values matching configured patterns before persisting
the trail. Patterns live in `[security.pii_redaction]`:

[source,toml]
----
[security.pii_redaction]
patterns = [
    "email",         # value matches RFC 5322
    "ssn",           # value matches SSN format
    "credit_card",   # value matches Luhn-validated card
]
fields = [
    "user.email",
    "customer.id",
    "*.password",
]
----

Field-name matching takes precedence over pattern matching. Redacted
values are replaced with `<redacted:<reason>>` in the trail; the
`AuditFrame.filters_pushed` and `filters_post` carry redacted values,
and a `redaction_count` field is appended to the frame so callers
know redaction happened without seeing what was redacted.

== EXPLAIN VERBOSE surface

=== SQL pathway

[source,sql]
----
EXPLAIN VERBOSE SELECT * FROM products
JOIN reviews ON products.id = reviews.product_id
WHERE products.embedding <-> $1 < 0.3;
----

Returns a JSON-encoded `AuditTrail` with `outcome = Success` and one
synthetic frame per planned source (no rows actually scanned —
EXPLAIN does not execute). Frame metadata reflects the *estimated*
cost from the optimizer; `wall_time_us` is `None` for synthetic
frames.

=== AQL JSON pathway

[source,bash]
----
POST /api/v1/query/aql
{
  "find":  { "projections": [ { "field": "*" } ] },
  "from":  { "Join": { "left":  { "Source": { "name": "products" } },
                       "right": { "Source": { "name": "reviews" } },
                       "on":    { "Equals": { "field": "products.id",
                                              "value": "reviews.product_id" } } } },
  "where": { "SemanticMatch": { "field": "products.embedding",
                                "query": "wireless headphones", "threshold": 0.3 } },
  "explain": "verbose"
}
----

Response includes the executed result *and* the `AuditTrail` populated
with real measurements. When `explain: "plan"`, the response is the
plan-only trail (no execution).

=== Real-time tracing

For long-running queries, a `Server-Sent Events` endpoint
`POST /api/v1/query/aql/stream` emits frames as they complete. Useful
for debugging slow cross-model joins where one source is the
bottleneck.

== Migration path

The change is additive. Existing surfaces continue to work unchanged
during the transition:

[cols="2,3,3", options="header"]
|===
| Phase | What changes | What stays

| 1. Skeleton (1-2 weeks)
| `src/query/aql/` module with AST + `AqlSource` trait + `AuditContext`. No execution wiring.
| All existing query paths.

| 2. Wrap existing executors (2-3 weeks)
| Per-model `AqlSource` impls forward to the existing executor functions, but emit `AuditFrame` on the way through.
| SQL frontend, federated parser, REST handlers — none call AQL yet.

| 3. EXPLAIN VERBOSE (1 week)
| Parse the SQL plan into AQL, run a *plan-only* AQL pass to produce an `AuditTrail` with synthetic frames.
| Result-returning queries unchanged.

| 4. Real-trace audit (2-3 weeks)
| Federated executor optionally produces an `AuditTrail` alongside results when `explain: "verbose"` is set on the request.
| Default request shape unchanged.

| 5. Persistent audit log (1 week)
| Eventlog-backed `_aql_audit` collection populated on every query.
| Existing audit logging coexists.

| 6. Direct AQL endpoint (1-2 weeks)
| `POST /api/v1/query/aql` surface for callers that want to skip SQL.
| SQL surface remains primary.
|===

[#acceptance]
== Acceptance criteria

. **Spec reviewed and merged** (this document, after maintainer review).
. **`EXPLAIN VERBOSE`** for any federated query produces a trace where:
  * Every source is named.
  * Every filter is classified as pushed-down or post-filter.
  * Each frame carries records_scanned and records_returned.
. **Compliance trail**: an end-to-end test demonstrates a customer
  scenario — an agentic NL query → AQL plan → audit trail with at
  least vector + graph + document sources joined — that an auditor
  could review without seeing PII.
. **Determinism test**: two runs of the same plan over the same
  database produce trails that are equivalent modulo wall-time and
  `query_id`. Specifically: same source list, same filter pushdown
  classifications, same join graph, same record counts.
. **JSON round-trip test**: `to_string` + `from_str` yields
  equivalent `AuditTrail`.
. **PII redaction test**: a query with a configured PII field has
  the value replaced with `<redacted:<reason>>` in the persisted
  trail.

== Out of scope

These are explicitly *not* part of TD-050 even though the paper or
adjacent literature touches on them:

. **Persistent agent memory / "Context Lake"** — the paper does not
  propose a memory store; conflated in earlier drafts. Tracked
  separately as TD-052 if pursued.
. **Durable execution semantics** (à la DBOS) — not in the paper.
. **A new SQL dialect** — AQL is structural, callers may construct
  it directly; the SQL frontend continues to accept SQL.
. **LLM-driven query rewrite** — handled by AV-SQL (TD-048), which
  *consumes* AQL and the audit trail rather than redesigning them.
. **Cross-tenant audit visibility** — tenant isolation rules apply
  unchanged; one tenant's trails are not visible to another.

== Open questions for maintainers

. **Where should `AuditTrail` storage live**: the existing audit
  logging system, the eventlog engine, or a new dedicated
  `_aql_audit` collection? Spec proposes the eventlog engine
  for ordering guarantees, but compliance teams may prefer the
  existing audit pipeline.
. **PII pattern catalog** — start with a hardcoded set or expose a
  configurable one? Spec proposes configurable in `[security]` but
  ships with sane defaults (email / SSN / credit card).
. **Real-time SSE endpoint** — useful but adds operational surface.
  Defer to phase 6 unless an early customer requests it.
. **Snapshot of plan at audit time vs. lazy reference**: the
  `AuditTrail.plan` field as specified is a deep copy. For very
  large plans, that bloats the audit log. Alternative: store a
  hash of the plan and resolve via `_aql_audit_plans` collection
  on demand. Decide before phase 5.
