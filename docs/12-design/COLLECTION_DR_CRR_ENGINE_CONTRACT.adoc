== Purpose

This document is the open-source engine contract for collection-level DR and
cross-region object replication. It defines what the ProximaDB engine
guarantees and exposes; it does **not** define how a SaaS operator monetizes,
prices, or operationalizes DR. The SaaS operationalization that AnvaiOps
provides lives in the private AnvaiOps repo and is intentionally out of
scope here.

Two layers, two homes:

* This engine contract: path layout, policy schema, state machine, resolver
  invariants, reconciler interface, provider adapter contract, engine-emitted
  metrics, restore primitives.
* SaaS operator doc (private): tier-to-pool mapping, bucket/account naming,
  provider rule JSON, IAM role examples, region-pair eligibility curated by
  ops, billing SKUs, failover runbook, private connectivity, support
  workflows.

=== Mode Applicability

The DR contract applies to ProximaDB in **server mode** only. Embedded
ProximaDB (PyO3, JNI, NAPI-RS, C FFI bindings in `src/embedded/`) does not
run a reconciler, does not expose the policy management API, and does not
ship provider adapters. Embedded callers that need replication must lift to
server mode or arrange their own storage-layer replication outside this
contract.

== Decision Index

[cols="1,3,4"]
|===
| ID | Question | Decision

| D1
| Is DR configured per collection, namespace, or tenant?
| Customer-facing DR is per collection. Namespace and tenant define the
  authority boundary and physical prefix. Tenant-level defaults may auto-apply
  to new collections, but xCatalog still materializes one policy per
  collection.

| D2
| Is namespace tied to tenant ID? How does that relate to the existing
  Iceberg-REST `CatalogNamespace`?
| Yes, and we reuse the existing `CatalogNamespace`
  (`crates/control/proximadb-catalog/src/lib.rs:23-79`) rather than
  introducing a parallel concept. The Iceberg-REST `levels` field stays for
  federation. We add four new fields — `namespace_id` (server-issued ULID,
  stable, drives physical paths and IAM scoping), `tenant_id` (mandatory
  owning tenant), `region_home` (where authoritative writes land), and
  `default_dr_region_pair_id` (optional inheritance default). Human
  namespace names (`levels`, `name`) are labels and must not drive object
  movement on rename. See "Namespace As The DR Authority Boundary" below.

| D3
| Can customers turn DR off?
| Not as an immediate toggle. Disable is a retirement workflow:
  `Active -> PendingRetirement -> Retired`. The engine enforces monotonic
  transitions and refuses `Active -> Disabled`. Operator policy may add
  billing/retention acknowledgement on top.

| D4
| Can prefix replication enforce collection scope?
| Yes. The path resolver guarantees that every byte for a collection lives
  under `data/{tenant_id}/{namespace_id}/{collection_id}/`. Provider
  adapters are required to filter on exactly that prefix.

| D5
| Does the engine assume a single provider replication mechanism?
| No. The engine defines a provider adapter contract. Implementations include
  AWS S3 replication, Azure Blob object replication, and a ProximaDB-managed
  worker for environments (such as Azure HNS source accounts) where native
  replication is not available.

| D6
| Do deletes replicate?
| Default: no. Delete marker replication requires explicit policy and
  retention validation. Collection delete schedules DR retirement; it does
  not immediately erase replicated destination versions.

| D7
| How does the engine prevent unbilled provider charges?
| The engine refuses to leave `PendingBillingApproval` without a non-null
  `billing_approval_id` and a non-null `cost_owner_tenant_id`. The reconciler
  marks any provider rule observed without an active billing binding as
  `BillingBlocked`. Concrete billing SKUs and approval UX are operator
  concerns.

| D8
| What about collections backed by external-authority tables (Iceberg /
  Delta / Hudi)?
| The engine refuses to create a `CollectionDrPolicy` for any collection
  whose xCatalog authority mode is `ExternalAuthoritative`. Those
  collections do not own their own commits; the external table owner must
  arrange replication via their own catalog (Iceberg snapshot replication,
  Delta clone, etc.). DR policy creation returns an explicit error citing
  the authority mode. See `docs/12-design/OPEN_FORMAT_CATALOG_2026_05_17.adoc`.
|===

== HLD: Policy Boundaries

=== Namespace As The DR Authority Boundary

The engine extends the existing `CatalogNamespace`
(`crates/control/proximadb-catalog/src/lib.rs:23-79`) rather than
introducing a parallel multi-tenant container. `CatalogNamespace` already
serves Iceberg-REST federation via hierarchical `levels: Vec<String>`,
plus `properties`, `owner`, `location`, and `created_at_ms` /
`updated_at_ms`. DR adds four engine-authoritative fields on top:

[source,rust]
----
pub struct CatalogNamespace {
    // --- Existing Iceberg-REST federation fields (unchanged) ---
    pub levels: Vec<String>,                   // hierarchy, mutable
    pub properties: HashMap<String, String>,
    pub owner: Option<String>,
    pub location: Option<String>,
    pub created_at_ms: i64,
    pub updated_at_ms: i64,

    // --- New fields added by this contract ---
    /// Opaque, stable, server-issued ULID. Never reused, never changes on
    /// rename. Drives physical paths and provider rule filters.
    pub namespace_id: String,
    /// Owning tenant. Mandatory. A namespace cannot be re-parented.
    pub tenant_id: String,
    /// Region where authoritative writes land for this namespace.
    pub region_home: Option<String>,
    /// Optional operator-curated default that new collections in this
    /// namespace inherit at DR enablement time.
    pub default_dr_region_pair_id: Option<String>,
    /// Storage pool class. Set by the operator at namespace provisioning;
    /// the path resolver refuses writes that target a bucket/container
    /// outside the matching pool class. See "Storage Pool Classes".
    pub storage_pool_class: StoragePoolClass,
}
----

How the two roles coexist:

* `levels` and `name` are human-readable labels used by Iceberg-REST clients
  and the SQL surface. They are mutable, do not drive object paths, and do
  not appear in provider rule filters.
* `namespace_id` is the engine's authoritative identifier. It drives the
  physical path layout `data/{tenant_id}/{namespace_id}/{collection_id}/`
  and the prefix filter passed to provider replication rules. Rename of
  `levels` does not move objects or invalidate provider rules.
* `tenant_id` is the multi-tenant authority root. The engine refuses to
  load any `CatalogNamespace` row without a non-null `tenant_id` once the
  contract's P1 migration completes.

Per-collection DR policy is created underneath this boundary, never across
it. The provider replication filter is therefore always a subtree of
`data/{tenant_id}/{namespace_id}/`.

=== Region Home Routing

A namespace's `region_home` is the only region authorized to accept
writes for any collection in that namespace. The engine enforces this:

* the path resolver refuses to construct a write path for a collection
  whose owning namespace `region_home` differs from the current process's
  configured region;
* router/multiplexer write routes (`docs/12-design/COMPETITIVE_OLTP_OLAP_MPP_TRAJECTORY_2026_05_20.adoc`)
  emit a `RoutedExecutionPlan` rejection with reason `region_home_mismatch`
  when a write hits the wrong region's data plane;
* reads MAY be served from the destination region while DR is active and
  healthy, subject to the freshness policy on the collection;
* a namespace `region_home` change is not supported while any child
  collection has an active DR policy. The operator must retire DR, change
  `region_home`, and re-enable DR with a new region pair.

`region_home` is nullable to keep migration safe for legacy namespaces
that were created before this contract. The path resolver allows writes
under a null `region_home` only for collections whose DR policy state is
`Disabled`.

=== Backwards Compatibility For Existing Namespaces

The xCatalog schema migration that adds `namespace_id`, `tenant_id`,
`region_home`, and `default_dr_region_pair_id` follows these rules:

. Existing `CatalogNamespace` rows are backfilled with new ULIDs
  (`namespace_id`).
. Existing rows are assigned a default tenant id
  (`tenant_id = "tnt_legacy_system"`) so the NOT NULL constraint can be
  added safely. Operator policy is responsible for re-parenting legacy
  namespaces to real tenants before exposing them to DR.
. `region_home` and `default_dr_region_pair_id` stay nullable; only
  namespaces participating in DR need them set.
. `storage_pool_class` is backfilled to `Pooled` for legacy rows so the
  NOT NULL constraint is safe. Operator policy upgrades a namespace to a
  higher class before exposing it to DR.
. `CatalogNamespace::new()` and other constructors are extended to take
  `tenant_id` (mandatory) and to generate `namespace_id` automatically.
. The Iceberg-REST handler returns only the federation fields to keep wire
  compatibility with external Iceberg clients.

=== Tenant, Namespace, Collection

DR policy is collection-level, but collection identity must be nested under a
tenant-bound namespace:

[source]
----
tenant_id
  namespace_id
    collection_id
      CollectionDrPolicy
----

Rules enforced by the engine:

* A namespace belongs to exactly one tenant.
* A collection belongs to exactly one namespace.
* A collection DR policy cannot target a prefix outside that
  tenant/namespace.
* Namespace renames do not change object prefixes.
* Collection renames do not change object prefixes.
* Namespace delete is rejected while any child collection has active or
  pending DR retirement.
* Re-parenting a collection between namespaces is not supported while DR is
  active.

=== Authority Mode

`CollectionDrPolicy` is the metadata authority for DR. Provider rules are
rebuildable projections of that policy. If provider state diverges from
xCatalog, xCatalog wins and the reconciler either repairs provider state or
marks the collection unhealthy.

DR replication does not change:

* collection schema authority;
* WAL commit authority;
* RLS/policy authority;
* tenant ownership;
* billing ownership (held by the operator layer);
* supported-surface maturity.

=== External-Authority Collections

ProximaDB xCatalog supports an `ExternalAuthoritative` mode for collections
backed by externally-owned open-format tables (Iceberg / Delta / Hudi). The
catalog tracks these as publications, imports, or federated reads, not as
canonical-WAL-owned data
(see `docs/12-design/OPEN_FORMAT_CATALOG_2026_05_17.adoc`).

The engine refuses to create a `CollectionDrPolicy` when the owning
collection's `CatalogAuthorityMode` is `ExternalAuthoritative`. The
returned error names the authority mode and points the caller at the
table owner's replication mechanism. The reconciler ignores
`ExternalAuthoritative` collections entirely; it does not attempt to
observe or repair provider state for them.

=== Storage Pool Classes

The engine defines an abstract `StoragePoolClass` enum. The mapping from
tenant tier to pool class is operator policy and lives in the operator
layer. The engine only knows that:

* every namespace carries a `storage_pool_class` field (set by the operator
  at namespace provisioning) on the extended `CatalogNamespace`;
* a collection inherits the class from its owning namespace; the engine
  does not store a separate per-collection pool class;
* the path resolver refuses to write a collection's bytes outside the
  bucket/container that matches its namespace's pool class.

Enum values (used by the path resolver and reconciler; not tier names):

* `Pooled`
* `Business`
* `Enterprise`
* `EnterpriseDedicated`

== LLD: Physical Path Contract

All DR-eligible collection data uses this root:

[source]
----
data/{tenant_id}/{namespace_id}/{collection_id}/
----

[NOTE]
====
*Two-tier operator/account model (Phase 5).* When a collection's owning
namespace carries an `account_id` (the SaaS customer = billing/isolation
boundary that sits *above* `tenant_id`, where a tenant is a workspace/sub-org
inside the account), `DrResolvedPath::root_prefix()` renders the account-rooted
form instead, and every subprefix below hangs off it unchanged:

[source]
----
accounts/{account_id}/{tenant_id}/{namespace_id}/{collection_id}/
----

A namespace with no `account_id` keeps the legacy flat `data/...` render
byte-for-byte (mixed-safe; the account tier is inert until provisioned). The
SaaS provider's own *control plane* — the **operator catalog** registering all
accounts (entitlements, storage bindings, billing; metadata-about-accounts,
never tenant data) — lives under the reserved `_operator/` root, lexically
separate from the per-account `accounts/...` data tree. `DrPathBuilder` is the
single validated emitter of all three roots (`data/`, `accounts/`, `_operator/`).
====

Subprefixes:

[source]
----
data/{tenant_id}/{namespace_id}/{collection_id}/wal/
data/{tenant_id}/{namespace_id}/{collection_id}/manifests/
data/{tenant_id}/{namespace_id}/{collection_id}/snapshots/
data/{tenant_id}/{namespace_id}/{collection_id}/segments/
data/{tenant_id}/{namespace_id}/{collection_id}/indexes/
data/{tenant_id}/{namespace_id}/{collection_id}/restore-checkpoints/
----

Rules:

* Temporary compaction files use `_tmp/` under the same collection root only
  if they are safe to replicate. Otherwise they must live outside the DR
  prefix.
* Provider lifecycle rules must not delete source bytes before manifest and
  WAL retention prove that restore RPO is still satisfied.
* Destination lifecycle rules are owned by DR policy, not by generic
  cold-tier lifecycle automation.
* A collection cannot be moved to a new physical prefix without a cataloged
  relocation workflow.
* All PAX blocks (`docs/12-design/PAX_CODEC_LAYOUT_COMPRESSION_LLD_2026_05_20.adoc`)
  replicate as byte-identical objects. The provider adapter never re-
  encodes block contents; if a provider supports server-side compression
  for replicated objects, it must be disabled for DR destinations so the
  destination bytes match the source manifest checksums.

=== Path Resolver Guard

The storage path resolver is the only component that emits collection object
paths. It enforces:

. Every write resolves to
  `data/{tenant_id}/{namespace_id}/{collection_id}/...` with all three IDs
  proven against xCatalog before any byte leaves the writer.
. `tenant_id`, `namespace_id`, and `collection_id` are read-only after
  creation. Path resolver refuses to resolve any path with a mutated
  component.
. Provider replication automation accepts only prefixes produced by the path
  resolver. A direct prefix specified in an API request is rejected unless it
  matches the resolver output byte for byte.
. The resolver refuses to emit any path under a collection whose `state` is
  `Retired` or `Tombstoned`, blocking accidental re-population of a retired
  prefix.
. Bucket/container choice is decided by the `StoragePoolClass` of the owning
  tenant. The resolver refuses to write a Business/Enterprise collection
  to a `Pooled` bucket, and vice versa, even if a misconfigured callsite
  requests it.

This is the single enforcement point that turns the rule "only allow
replication for bucket prefix `data/{tenant_id}/{namespace_id}/...`" into a
runtime invariant. Provider rules can only ever observe paths the resolver
produced; no other code path is permitted to write under DR-eligible
buckets.

== LLD: State Machine

`DrState` and `DrHealthState` are intentionally orthogonal:

* `DrState` is *intent* — what the policy says should be true. Customer
  and operator actions move it.
* `DrHealthState` is *observation* — what the reconciler last saw at the
  provider. Reconciler movement only.

An `Active` policy can be `Healthy` (normal), `Degraded` (lag rising but
still inside RPO), `Drifted` (provider state diverged but reconciler
can repair), `BillingBlocked`, or `ProviderBlocked`. The reverse is also
true: a `PendingRetirement` policy can still be `Healthy` until the
provider rule is disabled. Never collapse the two into one enum; the
reconciler needs both axes to decide whether to repair, alert, or wait.

[source,mermaid]
----
stateDiagram-v2
  [*] --> Disabled
  Disabled --> PendingBillingApproval: request_enable
  PendingBillingApproval --> PendingProviderProvisioning: approve_billing
  PendingBillingApproval --> Disabled: cancel_before_provider
  PendingProviderProvisioning --> Active: provider_rule_created
  PendingProviderProvisioning --> Disabled: provisioning_failed_no_rule
  Active --> SuspendedByOps: ops_suspend
  SuspendedByOps --> Active: ops_resume
  Active --> PendingRetirement: request_retire
  PendingRetirement --> Retired: provider_rule_disabled_and_retention_recorded
  Retired --> [*]
----

Invalid transitions (engine rejects):

* `Active -> Disabled`
* `PendingProviderProvisioning -> Disabled` after a provider rule exists
  without an explicit cleanup event;
* `Retired -> Active` with the same provider rule ID;
* `SuspendedByOps -> Disabled` (must go through retirement);
* `SuspendedByOps -> Retired` directly without first resuming and then
  requesting retirement, so the reconciler observes a clean handover;
* any state -> `SuspendedByOps` from a non-`Active` source;
* tenant downgrade while any policy is `Active`, `SuspendedByOps`, or
  `PendingRetirement` unless the operator has marked billing active for the
  retirement window.

=== Policy Version Bump Rules

`policy_version: u64` is the optimistic-concurrency counter the reconciler
keys against. The engine increments it on every change that requires a
provider adapter call, and only those changes:

[cols="2,1"]
|===
| Change | Bump?

| RPO target (`rpo_target_seconds`)
| No (observed-only — drives alerts, not provider rules)

| Destination retention days
| No (lifecycle is reconciler-driven without provider mutation)

| `replicate_existing_objects` flag flipped
| Yes (triggers a new provider job)

| `replicate_deletes` flag flipped
| Yes (changes provider rule shape)

| `destination_region` or `region_pair_id`
| Yes (new provider rule, old one tombstoned)

| Source/destination bucket or prefix
| Yes

| `kms_key_id`
| Yes (KMS binding revalidates)

| State transition
| Yes (durable transitions always bump)
|===

When `policy_version` increments, the reconciler treats the in-flight
provider rule as stale: it issues a new `ensure_rule` call with the new
content-addressed ID, then retires the previous binding after the new one
is confirmed `Active`.

== LLD: Reconciler Interface

The reconciler is idempotent and runs from xCatalog policy state.

Loop:

. Load all policies in `PendingProviderProvisioning`, `Active`,
  `SuspendedByOps`, and `PendingRetirement`.
. For each policy, ask the provider adapter for current provider state.
. Validate provider state:
  * rule exists;
  * prefix matches exactly;
  * destination bucket/container matches;
  * versioning/change feed prerequisites remain enabled;
  * IAM/KMS binding is intact;
  * provider rule status matches desired xCatalog state.
. Repair safe drift automatically.
. Mark unsafe drift as `DrHealthState::Drifted` or `ProviderBlocked`.
. Emit `xcatalog_collection_dr_events`.
. Update engine metrics with destination bytes, versions, requests, and lag.

Unsafe drift examples:

* prefix changed;
* rule removed manually;
* destination changed;
* versioning disabled/suspended;
* KMS key policy revoked;
* destination accepts application writes.

=== Scheduling And Backpressure

The reconciler runs as a single async task per shard, where a shard is a
contiguous range of `policy_id` ULIDs. Default deployment is one shard;
operators scale out by sharding when policy count justifies it.

Per-shard behavior:

* poll interval default: 60 seconds (configurable via
  `[dr.reconciler] poll_interval_seconds`);
* per-policy reconcile is rate-limited to one provider call per 5 seconds
  unless the provider returns success faster;
* on `ProviderError::Transient`, exponential backoff 30s → 30m with
  jitter, max 12 attempts before escalating to `ProviderBlocked`;
* on `ProviderError::QuotaExceeded`, the shard pauses provider mutations
  for at least 60 seconds and emits
  `proximadb_dr_reconciler_paused_total{reason="quota"}`;
* read-only `fetch_state` calls are not rate-limited the same way and run
  on every poll to keep drift detection responsive.

The reconciler is **not** wall-clock-driven for correctness — it is
state-driven. Skipped polls (process restart, leader change) are safe
because every operation is idempotent against `(policy_id, policy_version)`.

=== Concurrency And Provider Rule Locking

The reconciler must be safe under multiple concurrent runners, partial
failures, and provider-side retries:

* xCatalog policy rows carry `policy_version` and a `reconcile_lease_token`
  with TTL. Only the current lease holder may issue provider mutations.
* Provider API calls use deterministic, content-addressed IDs derived from
  `(policy_id, policy_version)`, so a retried call is idempotent rather than
  creating a duplicate rule.
* If the reconciler detects an in-flight provider rule that does not match
  the catalog's intended ID, it does not delete the unknown rule; it flags
  the policy `ProviderBlocked` and surfaces an alert.
* Provider rule deletes only fire when both `state = Retired` and
  `policy_version` matches the rule's tagged version.
* Reconciler emits `xcatalog_collection_dr_events` for every state-changing call,
  including the lease holder and provider response IDs.

== LLD: Engine API Surface

Operators interact with the engine via an internal Rust crate API, not via
the customer-facing REST/gRPC surface. The engine exposes the DR control
operations as a single trait:

[source,rust]
----
#[async_trait::async_trait]
pub trait CollectionDrPolicyStore: Send + Sync {
    /// Create a new policy in `PendingBillingApproval`. Refuses
    /// ExternalAuthoritative collections; refuses if any IDs are unknown
    /// or if the namespace has no `region_home`.
    async fn create(&self, req: CreatePolicyRequest)
        -> Result<CollectionDrPolicy, DrApiError>;

    /// Move from PendingBillingApproval -> PendingProviderProvisioning.
    /// Requires `billing_approval_id` and `cost_owner_tenant_id` to be set.
    async fn approve_billing(&self, policy_id: &str, approval: BillingApproval)
        -> Result<CollectionDrPolicy, DrApiError>;

    /// Begin retirement. Customer-initiated.
    async fn request_retire(&self, policy_id: &str, ack: RetirementAck)
        -> Result<CollectionDrPolicy, DrApiError>;

    /// Ops-only emergency suspend.
    async fn suspend(&self, policy_id: &str, reason: &str)
        -> Result<CollectionDrPolicy, DrApiError>;

    /// Ops-only resume from suspension.
    async fn resume(&self, policy_id: &str)
        -> Result<CollectionDrPolicy, DrApiError>;

    /// Read-only fetches.
    async fn get(&self, policy_id: &str)
        -> Result<Option<CollectionDrPolicy>, DrApiError>;
    async fn list_by_tenant(&self, tenant_id: &str)
        -> Result<Vec<CollectionDrPolicy>, DrApiError>;
    async fn list_by_collection(&self, tenant_id: &str, collection_id: &str)
        -> Result<Option<CollectionDrPolicy>, DrApiError>;
}
----

`DrApiError` distinguishes:

* `ValidationFailed` (caller error — wrong IDs, missing fields);
* `Unauthorized` (caller lacks the operator service-account capability);
* `InvalidStateTransition` (state machine refused);
* `ExternalAuthoritativeRefused` (per D8);
* `UnsupportedProvider` (per S13);
* `StoreUnavailable` (xCatalog transient error — retryable).

The operator's customer-facing HTTP/gRPC layer is a thin facade over this
trait. The trait is the only sanctioned way to mutate DR state; any code
path that touches `xcatalog_collection_dr_policies` directly is treated as
a bug.

== LLD: Provider Adapter Contract

The engine does not embed provider-specific rule shapes. It calls a provider
adapter via a small async trait. All adapter methods are async because real
provider SDKs (`aws-sdk-s3`, `azure_storage_blobs`) only expose async APIs;
making the engine trait async avoids `block_on` smuggling inside the
reconciler.

[source,rust]
----
#[async_trait::async_trait]
pub trait DrProviderAdapter: Send + Sync {
    /// Create or update the provider rule to match the policy. Must be
    /// idempotent against (policy_id, policy_version).
    async fn ensure_rule(&self, policy: &CollectionDrPolicy)
        -> Result<ProviderReplicationBinding, ProviderError>;

    /// Fetch current provider state for drift detection. Read-only.
    async fn fetch_state(&self, policy: &CollectionDrPolicy)
        -> Result<ProviderObservedState, ProviderError>;

    /// Disable and tombstone the provider rule. Must be idempotent.
    async fn retire_rule(&self, policy: &CollectionDrPolicy)
        -> Result<(), ProviderError>;
}
----

=== Error Taxonomy

Adapter errors carry one of four canonical kinds so the reconciler can make
a retry or escalate decision without parsing provider-specific strings:

[source,rust]
----
#[derive(Debug, thiserror::Error)]
pub enum ProviderError {
    /// Transient provider failure — network blip, 5xx, throttling that the
    /// SDK already retried past. Reconciler retries with exponential
    /// backoff. Does not change `DrHealthState`.
    #[error("transient provider error: {0}")]
    Transient(String),

    /// Provider rejected the call because preconditions are wrong (bucket
    /// missing, versioning disabled, KMS key not usable, IAM policy
    /// invalid). Reconciler marks `ProviderBlocked` and pages ops. No
    /// further provider calls until human action.
    #[error("provider misconfiguration: {0}")]
    Misconfiguration(String),

    /// Provider account hit a hard limit (S3 replication rule count, Azure
    /// object replication policy count, request-rate ceiling). Reconciler
    /// marks `ProviderBlocked` and alerts ops with the limit name.
    #[error("provider quota exceeded: {0}")]
    QuotaExceeded(String),

    /// Provider returned 401/403 / role assumption failed. Reconciler
    /// marks `ProviderBlocked` and pages ops immediately because this
    /// usually means a credential rotation is mid-flight or an IAM policy
    /// regressed.
    #[error("provider auth denied: {0}")]
    AuthDenied(String),
}
----

Reconciler retry policy:

* `Transient` → exponential backoff (default 30s → 30m, jittered), max 12
  attempts before treating as `ProviderBlocked`.
* `Misconfiguration` / `QuotaExceeded` / `AuthDenied` → no retry until a
  human ack or a follow-up xCatalog event clears the block.

Adapter implementations live outside this contract. Examples that the
project expects to ship:

* `AwsS3ReplicationAdapter` — wraps S3 bucket replication rules.
* `AzureBlobObjectReplicationAdapter` — wraps Azure Blob object replication
  policies.
* `ProximaDbWorkerReplicationAdapter` — engine-side worker that tails
  WAL/manifest checkpoints and copies committed objects, used when native
  provider replication is unavailable (for example Azure HNS source
  accounts).

Concrete provider-side artifacts (replication rule JSON, IAM role
ARNs, bucket naming) belong in the operator's documentation, not here.

== LLD: Schema Evolution Under DR

A collection's schema can evolve while DR is active. Schema evolution
modes are governed by
`roadmap/MULTIMODAL_OVERHAUL_SPEC_2026_05_08.adoc` (Migration / AppendMode /
SafeShape). The DR contract guarantees:

* the destination is byte-identical to the source. Schema metadata is
  carried in manifest objects, which replicate via the same provider rule
  as segment objects.
* the engine does not "translate" schemas at the destination. A restore
  reconstructs the schema from replicated manifests, not from a separately
  exported schema descriptor.
* a schema change that requires a new collection format (e.g.,
  `Tier::Migration` re-shape) does not bump `policy_version` by itself.
  Provider rule shape is unchanged; only collection bytes change, and
  those flow through the existing replication path.
* the reconciler does not inspect collection schema. It is schema-blind.

The one exception: a schema migration that renames the collection's
physical prefix (rare, requires a cataloged relocation workflow) creates a
new policy at the new prefix and retires the old policy through the normal
`PendingRetirement` flow. The migration is not atomic across regions — the
operator must coordinate cutover.

== LLD: Delete, Retention, And Legal Holds

Collection delete:

. Reject immediate delete when DR policy is active.
. Create a retention-aware delete plan.
. Transition DR policy to `PendingRetirement`.
. Disable provider rule after final checkpoint and retention acknowledgement.
. Keep destination versions until `destination_retention_days` expires or
  legal hold releases.
. Mark collection tombstoned in xCatalog only after the authoritative delete
  commit is durable.

Namespace delete:

* Rejected while any child collection DR policy is not `Retired`.

Tenant delete:

* Requires all namespaces/collections to complete DR retirement.

Delete replication:

* Default `replicate_deletes = false`.
* If true, S3 delete marker replication or Azure delete behavior must be
  explicitly validated by the operator for the collection restore model.

== LLD: Restore Primitives

The engine exposes the primitives a restore workflow needs; the workflow
itself (failover/failback runbook) lives in the operator layer.

The contract anchors restore semantics on the existing
`GlobalManifestService` (`src/storage/persistence/write_ahead_log/manifest/`).
Each `GlobalManifestEntry` carries `global_lsn`, `collection_id`,
`batch_id`, `file_path`, `storage_url`, `status` (`Active` / `Flushed` /
`Archived` / `RolledBack`), `checkpoint_id`, and `timestamp_ms`. The
restore-readiness checker treats those rows as the source of truth and
asks whether their referenced objects are present at the destination.

Restore readiness requires:

* every `GlobalManifestEntry` up to `target_lsn` has its referenced
  object present at the destination;
* `target_lsn` was committed at the source within `rpo_target_seconds`
  of the observation time (RPO satisfied);
* segment/snapshot objects referenced from the latest replicated
  manifest entries are present;
* index rebuild metadata or replicated index objects are present (rebuild
  permitted — see open question on index replication);
* tenant and collection metadata exported to the DR control plane;
* KMS/decryption access is available in the DR region.

The engine exposes a restore-readiness checker:

[source,rust]
----
pub struct RestoreReadiness {
    pub policy_id: String,
    pub target_lsn: u64,
    pub observed_rpo_seconds: u32,
    pub latest_replicated_manifest_entry: Option<GlobalManifestEntry>,
    pub missing_objects: Vec<String>,
    pub missing_metadata: Vec<String>,
    pub kms_accessible: bool,
}

pub trait DrRestoreReadinessChecker {
    fn check(&self, policy: &CollectionDrPolicy)
        -> Result<RestoreReadiness, ProviderError>;
}
----

The checker is read-only. It never mutates xCatalog state, never calls
provider write APIs, and is safe to invoke from operator runbooks at any
time.

=== RPO Observation

`proximadb_dr_provider_lag_seconds` and the checker's `observed_rpo_seconds`
both use the manifest as the clock:

* source-side commit time = `GlobalManifestEntry::timestamp_ms` at the
  source for the latest committed batch;
* destination-side commit time = `timestamp_ms` of the same entry as
  observed at the destination after replication finishes;
* lag = source commit time minus destination commit time, in seconds.

Wall-clock skew between regions is irrelevant because both timestamps come
from the manifest, which is written once at the source and replicated as
bytes.

== Security

IAM/RBAC (engine surface):

* Customers cannot create provider replication rules directly through the
  engine API.
* The engine's DR APIs require a privileged operator service account for
  provider-binding-related mutations.
* The path resolver refuses to write to any DR destination bucket/container
  from application code paths.

KMS:

* The engine treats `provider_kms_key_id` as an opaque identifier and
  refuses to leave `PendingProviderProvisioning` if the provider adapter
  reports the key is unusable.
* KMS policy drift is a `ProviderBlocked` DR health error.

Audit:

* Every policy state transition is recorded in `xcatalog_collection_dr_events`.
* Every provider adapter call (create/update/delete) is audit-logged with
  policy_id, policy_version, and the adapter response.
* Every blocked delete/downgrade due to DR is audit-logged.

== Out Of Scope

The following concerns are real but explicitly outside this contract; they
are tracked in separate docs or operator runbooks:

* **xCatalog multi-region availability.** If xCatalog itself lives in one
  region and that region fails, the reconciler stops driving. Data-plane
  bytes continue to replicate at the provider, but no state transitions
  happen until xCatalog comes back. Cross-region xCatalog is a separate
  control-plane story.
* **Cross-region failover of customer-facing endpoints.** Routing customer
  traffic to the DR region is an operator/DNS concern, not engine state.
* **Index byte-equivalence at the destination.** Today the contract treats
  indexes as rebuildable from segments. A future addition may replicate
  index objects for lower RTO; see open questions.
* **Backup/restore for the engine's own metadata stores** (xCatalog
  database, manifest store). Handled by the operator's general
  backup/restore policy, not this contract.
