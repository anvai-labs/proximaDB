== History (shipped)

*Problem:* ORION replayed its engine WAL from the beginning. The canonical checkpoint LSN is an
`edge_epoch` value with no correlation to engine-WAL frame ordering. So "replay only after the
canonical checkpoint" was not a filter you could write; the correlation had to be *established*.

*Decision (five options surveyed):*

* **Option E** (Prometheus metric `orion_recovery_canonical_checkpoint_age_seconds`) shipped first as
  zero-risk visibility.
* **Option A** shipped next, as a `GraphMarker(CanonicalEmission(lsn))` marker frame. It is appended
  last and is mixed-read-safe. `OrionSnapshot.checkpoint_lsn` is versioned. `flush_wal` orders
  marker → flush → snapshot, and recovery replays only post-marker frames.
* **(d)** truncation then deletes whole segments below the marker, strictly *after* the durable
  snapshot. The full order is marker → flush → snapshot → truncate.

*Rejected, with reasons that still hold:*

* **B** (snapshot + truncate on every `flush_wal`) breaks `flush_wal`'s lightweight contract.
* **D** (skip engine-WAL replay when a canonical checkpoint exists) **loses acknowledged writes**
  made between the last flush and the crash.

*Lessons:*

* Two precursor fixes were needed for non-contiguous segment layouts. The reader must enumerate and
  sort segments and tolerate a missing low prefix. The writer must resume at `max_index+1`, not at
  the file count.
* Scoped replay is crash-safe without idempotent replay only because of that write ordering.

*Evidence:* a crash matrix covers before-snapshot, after-snapshot-before-truncate, mid-truncate and
after-truncate. There are also prefix-gap and renumber tests.

== Open

=== Default-ON flip of scoped replay

Scoped replay and marker emission are gated by `PROXIMADB_GRAPH_CANONICAL_REPLAY_SCOPE=1`
(`canonical_replay_scope_enabled()`), **default OFF** per the storage-format-migration mandate. With
the gate off, recovery does a full replay and writes no marker frames. The remaining step is to flip
the gate fleet-wide after baking.

=== (d-2) within-segment reclaim

Truncation works at segment granularity. Reclaiming space *inside* a segment (rewrite-compaction) is
deferred. Segment granularity already bounds WAL growth, and `PROXIMADB_GRAPH_WAL_SEGMENT_MB`
(default 64, embedded profiles 8) controls how much is reclaimable.

=== Option C — Canonical WAL becomes the authoritative write log (end-state, not started)

Every graph mutation writes a `CanonicalOperation::RecordUpsert`
(node/edge as canonical record) to the shared canonical WAL FIRST, then
mutates engine state. Engine WAL becomes a per-process in-memory journal
that's flushed periodically as a perf optimization. On recovery:

* Read canonical WAL.
* Find latest Checkpoint for this graph.
* Replay `RecordUpsert` entries after the checkpoint LSN through a
  graph-specific `ProjectionRebuilder`.
* Engine WAL is discarded as stale cache.

Scope:

* Every graph mutation path (`create_node`, `update_node`, `delete_node`,
  edge variants, batch variants) now emits a canonical record before
  touching engine state.
* New `GraphProjectionRebuilder` impl that translates canonical records
  to graph operations.
* Engine WAL becomes purely an in-memory journal; on-disk format can be
  deprecated.
* ~3-5 weeks of work; touches every graph write path.

Tradeoffs:

* **Pros**: precise match to ADR-020 architecture — single source of
  durable truth; same model as records/document path; recovery is
  uniform across all modalities.
* **Cons**: huge scope; every write path doubles its I/O cost (canonical
  WAL append + projection update) unless the canonical WAL append is
  buffered/batched.

Defer Option C to a separate design doc + workstream when ADR-020 is ready to flip from
"ORION engine WAL is compatibility buffer" to "ORION engine WAL is in-memory journal." That decision
needs RFC-level community input. Option A is a stepping stone, not a permanent answer.

=== Not decided by this design

* Relational distributed graph placement and storage projection tiering. The design here is
  ORION projection-WAL-specific.
* What happens if the canonical WAL is unreadable on recovery. Part 1 logs a warning and falls back
  to engine-WAL-only behavior; Option A inherits that fallback.
