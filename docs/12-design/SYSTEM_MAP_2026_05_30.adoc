[.lead]
This is the **single pane of glass** for ProximaDB. It exists to answer one question fast — "where does
a thing live, and what does it converge on?" Current checkout reality: 152 workspace members across
the root package, `crates/`, `apps/`, bindings, integrations, and clients, plus 42 real top-level
`src/` module directories. It is navigation-first: it does not
duplicate the per-module detail in the feeder docs, it indexes and ties them together so they stop
diverging.

[IMPORTANT]
====
**Why this doc exists.** The codebase grew three partially-overlapping whole-system maps
(`ARCHITECTURE_ATLAS_2026_05_22`, `MODULE_COMPONENT_LLD_2026_05_22`, `docs/05-concepts/architecture.adoc`).
Each is correct but none is canonical, so they drift. This doc is declared the apex; the three become
subordinate feeders. New whole-system diagrams belong here or in a feeder linked from here — **not in a
fourth competing map**. That rule is itself a convergence gate (see
link:CONVERGENCE_AUDIT_2026_05_30.adoc[CONVERGENCE_AUDIT_2026_05_30]).

Production composition is still mostly rooted in the root crate (`src/database.rs`,
`src/network/shared_services.rs`, `src/network/multi_server.rs`). The sole production
`ApiHandlersPort` implementation has moved to `proximadb-runtime`; `proximadb-api` remains a contract
and extraction boundary rather than the composition root. Workspace
decomposition therefore remains a first-principles build-scaling requirement: split ownership only
where it reduces compile fan-out, enables independent worktrees, and lets CI coverage shards
(`cargo llvm-cov`, Tarpaulin, and focused `cargo test -p ...`) compile smaller units without timeout
or OOM pressure.

[#solution]
== Solution Architecture at a glance

ProximaDB is converging on a context-database architecture: many protocol and modality facades at the
edge, one canonical durable authority in the core, and workload-aware execution behind a shared logical
plane. The supported product surface is intentionally narrower than the code inventory; code presence
does not imply support level.

Load-bearing invariants:

* Protocols and modalities are facades. Durable truth converges on `ProximaRecord`, xCatalog,
canonical WAL/log/manifest state, and tenant-isolated paths. ADR-024/048 make the type/catalog
direction explicit: typed native schema metadata becomes the authority, while v1
`Collection`/`CollectionConfig` and proto-v1 DTOs are compatibility views rather than a second truth.
* Routing happens in the logical plane. Native Volcano, DataFusionLocal, specialized vector engines,
and modality runtimes are physical execution choices behind one contract. Standard and metered native
physical plans execute through the query-layer `NativeVolcanoEngine` adapter; pgwire owns wire
shaping, not executor construction.
* `TenantContext` and `DrPathBuilder` are SaaS gates, not optional helpers. Any I/O or heavy compute
boundary that bypasses tenant context or raw-builds paths is architectural debt. ADR-032/TD-CAT-2
make catalog metadata the remaining high-risk tenant-prefix gap.
* Support level comes from link:../SUPPORTED_SURFACE.adoc[docs/SUPPORTED_SURFACE.adoc], not from the
existence of modules, feature flags, or demos. The storage-engine names in the diagrams below are
illustrative; the canonical per-engine inventory + tiers (including gated, internal, removed, and
fallback engines) is SUPPORTED_SURFACE §"Storage Engine Matrix" (TD-TAXO-1) — do not re-enumerate
engines in design docs.

[#components]
== Component ownership and responsibilities

[cols="2,2,3,3", options="header"]
|===
| Component family | Primary code locations | Owns | Must not own

| Protocol edge
| `src/network/`, `src/api_handlers/`, `crates/platform/proximadb-api`
| Wire compatibility, request parsing, auth/tenant extraction, response shaping, compatibility
facades, protocol-specific error mapping.
| Durable schema truth, storage layout decisions, independent business logic per protocol.

| Runtime composition
| `src/server/`, `src/database.rs`, `src/network/shared_services.rs`,
`crates/platform/proximadb-runtime`, `apps/proximadb-server`
| Lifecycle, dependency wiring, the sole production `ApiHandlersPort` implementation, port
composition, startup/shutdown, health exposure.
| Protocol-specific behavior or storage-engine policy that should live in services/catalog.

| Service layer
| `src/services/`, `src/services/record_store.rs`, `src/services/record_memtable.rs`,
`crates/foundation/proximadb-records/src/store.rs`, `src/search/`
| Collection lifecycle, DDL/DML orchestration, record operations, search/hybrid orchestration,
document/graph/observability service facades.
| Raw physical paths, protocol DTO leakage, or duplicated query-planning rules.

| Query and route planning
| `src/query/`, `src/datafusion/`, `crates/query/*`, `crates/foundation/proximadb-functions`
| Shared logical lowering, SQL/AQL/UQL semantics, function registry, compute-route selection,
EXPLAIN, route-health signals, `ExecutionControls`, and the `ExecutionEngine` /
`NativeVolcanoEngine` seams. `execute_sql_with_backend` serves DataFusion and optional DuckDB
compatibility; native execution follows its separate planned-snapshot path.
| Separate semantics per engine. Volcano and DataFusion should bind the same logical/function
contract.

| Durable catalog and authority
| `crates/control/proximadb-catalog`, `src/catalog/`, `src/storage/persistence/`
| xCatalog metadata, canonical WAL/log/manifest state, projection metadata, route knobs, replayable
authority.
| Customer-facing support claims or protocol-specific shortcuts.

| Physical storage and indexing
| `src/storage/`, `crates/storage/*`, `src/index/`, `src/compute/`
| Storage engines, filesystem/object-store access, block formats, compaction/flush, ANN indexes,
distance kernels, quantization. `UnifiedStorageFormat` is the canonical trait name;
`UnifiedStorageEngine` is a compatibility re-export, not a separate engine abstraction.
| Tenant identity inference from raw strings; path construction outside `DrPathBuilder`.

| Modality runtimes
| `src/storage/document`, `src/graph/`, `src/observability/`, `crates/modalities/*`
| Document, ORION graph, observability, queue, rank and embedding behavior as product/modality
facades or rebuildable projections.
| A second durable truth that bypasses canonical records, catalog, WAL/log/manifest policy, or
tenant isolation.

| Integration and data movement
| `src/connectors/`, `src/cdc/`, `src/streaming/`, `src/ingest/`, `clients/`,
`crates/binding/*` (including `proximadb-embedded`)
| External connectors, ingestion, CDC, SDKs, embedded surfaces, Spark/JVM bridges.
| Claims of external-authoritative storage unless xCatalog and the supported-surface contract say so.

| SaaS and operations controls
| `src/security/`, `src/auth/`, `src/audit/`, `src/metrics/`, `src/monitoring/`, `src/deployment/`,
`src/operations/`, `src/storage/tenant`
| Identity, tenant context, neutral consumption/metering hooks, auditability, deployment, backup/restore and
operator visibility.
| Best-effort add-ons after data paths are designed. These are cross-cutting release gates.
|===

[#convergence]

that every live modality already follows one universal linear pipeline. New work must lower toward

[#seams]
== Where the seams are

This map is the apex; it points at the live divergent seams rather than hiding them. The authoritative
catalog with reconcile directions and queued TD items is
link:CONVERGENCE_AUDIT_2026_05_30.adoc[CONVERGENCE_AUDIT_2026_05_30]. Summary:

[cols="2,3", options="header"]
|===
| Seam | One-line status

| Handler/service extraction
| `crates/platform/proximadb-runtime/src/handlers.rs` is the sole production `ApiHandlersPort`
implementation and `src/network/shared_services.rs` constructs it from root service ports.
`src/api_handlers` retains support/record-operation modules; `request_handlers.rs` no longer exists.

| Retired wire generations
| REST `/api/v2` is canonical. One residual compatibility router remains live at
`/api/v1/collections/{collection_id}/entities` (plus `/{entity_id}` and `/search`) over
`ProximaEntityStore`; all other ProximaDB REST `/api/v1` routes and `/api/v3` are removed.
Canonical external ProximaDB application RPCs are `proximadb.v2`; the v2
`ProximaEntityService` is always registered and `proximadb.v1` service registration is gone.
Standard `grpc.health.v1`, optional reflection, and experimental cluster-mode
`proximadb.cluster.v1` RPCs are separate infrastructure/internal protocols, not the retired external
v1 product surface. Internal v1 DTO code remains migration debt.

| Proto-v1 internal mirrors
| `VectorRecord`/`SqlValue`/`SqlObject` still used internally; canonical is `ProximaRecord`/`ProximaValue`.

| Record storage
| The stable store trait lives in `proximadb-records/src/store.rs`; root
`services/record_store.rs` and `services/record_memtable.rs` are adapters. Avoid reintroducing a root
contract twin.

| Relational route and execution
| `RoutedReadPlan` is typed route/EXPLAIN/telemetry vocabulary, not a universal dispatcher. Live
relational dispatch consumes `SelectRouteDecision.backend`: native uses
`plan_over_snapshot` → `execute_physical`/`NativeVolcanoEngine`; `execute_sql_with_backend` handles
DataFusion and the optional, correctness-floor `DuckDbCompat` path.

| Read-side distributed execution
| `ComputeScheduler` and `RoutedReadPlan` exist; DataFusionLocal is the first OLAP route, while
Ballista-backed `DataFusionDistributed` remains a planned/experimental adapter behind the same route
contract.

| Native-to-Arrow scans
| SST split discovery is implemented, but `SstBlockStream::poll_next` currently returns EOF without
reading, decoding, or producing a `RecordBatch`. PAX `PaxSplitReader`/`PaxTableProvider` and ranged
tests exist; row-group Region D storage writes default ON, while the production PAX OLAP query route
remains default OFF and is not fully wired.
|===

[#state]
== Current state and MVP readiness

This section intentionally separates *code presence* from *product maturity*. The support contract is
link:../SUPPORTED_SURFACE.adoc[docs/SUPPORTED_SURFACE.adoc]; this map summarizes it in system terms.

[cols="2,2,3", options="header"]
|===
| Area | Current system state | MVP readiness

| Durable authority
| xCatalog + canonical WAL/log/manifest + `ProximaRecord`/`ProximaType`/`ProximaValue` are the
target spine. Proto v1 DTOs and legacy `VectorRecord`/`SqlValue`/`SqlObject` remain edge adapters or
internal migration debt. ADR-024 is accepted and partially rolled out; ADR-031/048 keep identity and
native catalog authority separate from compatibility collection views.
| Usable only through the flows explicitly listed in the support contract. Full internal type/schema
and v1 DTO migration remains TD-106/TD-123/ADR-024 work; package-version strings are not a maturity
signal.

| Vector path
| REST `/api/v2` and external gRPC v2 record CRUD/vector search are the supported product path.
Multiple vector storage engines and AXIS index families exist. REST v1 vector/collection/search
routes, REST `/api/v3`, and external `proximadb.v1` RPCs are not served; the entity-only REST v1
compatibility exception does not expose vector CRUD/search. Internal v1 DTO presence is not wire
compatibility.
`bench_24_recall_at_k_engine` is registered as a real index-vs-ground-truth Recall@k benchmark with
deterministic vectors, bounded search-readiness probing, and optional `PROXIMADB_BENCH_TOPK=K`
single-K runs for isolating low-effort Recall@K/latency curves.
| The MVP trust corridor is single-tenant, single-node SST through canonical REST v2. Hybrid,
per-collection filtered-ANN policy,
recall-gate enforcement, and object-economy claims stay Beta/Experimental unless explicitly scoped.
The real-engine recall benchmark is evidence plumbing, not a published recall SLA until run outputs
are captured and reviewed.

| Document / graph / observability
| Document, ORION graph, and observability runtimes exist and are useful. ORION is the only graph
runtime; former PULSAR/QUASAR names are retired. These modalities should be treated as projections or
facades over canonical authority, not separate durable truths. The v2 graph service path is live for
the scoped API set, while deeper graph planner/executor work remains open.
| Beta at the runtime/product-maturity level. Good for controlled workflows; not yet the same
maturity as the supported vector surface. Do not infer a separate durable entity/document/graph store
from compatibility surfaces.

| SQL / pgwire / relational
| pgwire and gRPC v2 `ExecuteQuery` are Beta, scoped SQL adapters and remain outside the MVP trust
corridor. Relational frontend/algebra/planner/executor crates, DML routing, `ComputeScheduler`,
DataFusionLocal route vocabulary, `RoutedReadPlan` telemetry vocabulary, and query-layer execution
seams exist. Live dispatch consumes `SelectRouteDecision.backend`: DataFusion and optional DuckDB
compatibility run through `execute_sql_with_backend`; native physical plans use
`plan_over_snapshot` → `execute_physical`/`NativeVolcanoEngine`. Eligible pgwire relational OLAP
shapes consult `route_select_advised` against the global `RouteCostModel`, but pgvector, environment
opt-out, result-cache, in-memory, and legacy simple-SELECT paths bypass that advice. Observe-mode is
the default, with a landed but flag-gated live override
(`PROXIMADB_ROUTE_COST_OVERRIDE`, default OFF; explore/exploit over freshness-safe candidates plus
the TD-170 round-trip hard gate, enablement gated by TD-ROUTE-1). Full PostgreSQL parity, complete
constraints, MVCC/index state, HTAP delta union, accuracy ratchets, and distributed consistency gates
remain TD-076/TD-110/TD-115/ADR-040 work.
| Beta for explicitly scoped single-node SQL cases, not a PostgreSQL replacement or MVP-corridor
surface. Broad ORM/BI parity, full OLTP/HTAP semantics, engine-native streaming/backpressure, and
distributed SQL are not supported claims.

| DataFusion / distributed execution
| DataFusion integration, local Parquet registration, shared relational lowering, typed
`ExecutionError`, request-scoped `ExecutionControls` (cooperative cancellation, row-limit
truncate/error modes, and pre-collect row-cap pushdown), and the `DataFusionLocal` execution seam
exist. Live DataFusion contexts can register the `vector_search(collection, query, k)` table function
when supplied a `VectorOpsPort`, making vector results joinable in SQL over the OLAP path. The
production route requires the shared logical plane by default; direct DataFusion SQL fallback is an
explicit context flag for controlled compatibility gaps. Embedded Python DataFrame sessions register
collection schemas for DataFusion planning with a canonical vector-record fallback when no relational
table schema exists; the Python facade exports the DataFrame expression helpers, supports sort
expressions, exposes a DataFrame `vector_search()` bridge, makes table refresh idempotent for
long-lived sessions, and returns typed empty PyArrow tables from `to_arrow()`. Blank SQL/table/column
names, empty aggregate expression lists, keyless joins, and invalid vector-search arguments are
rejected at the Python and/or DataFusion table-function boundary before execution. SST split
discovery exists, but `SstBlockStream` still returns EOF without reading or decoding its split, so
that adapter is not row-producing. PAX row-group Region D writes default ON; `PaxSplitReader`,
`PaxTableProvider`, and ranged-read tests exist, but the production PAX OLAP query route remains
default OFF and is not fully wired.
| Local parquet/interop OLAP route is Beta. ADR-052 narrows the near-term aspiration: win
single-node/vectorized OLAP and PAX-native scan competitiveness before MPP claims. `DataFusionDistributed`
remains route vocabulary only: Ballista execution, scheduler/executor deployment, distributed
cross-engine joins, SST row-producing scans, production PAX OLAP routing, and no-overlap/failure tests are not
complete.

| SaaS tenancy and metering boundaries
| REST `/api/v2`, gRPC v2, Arrow Flight, and pgwire use the shared tenant-ingress vocabulary and can
fail closed when a deployment requires a tenant but none resolves. `TenantContext` reaches storage
paths and `DrPathBuilder` owns tenant-isolated physical path construction. pgwire currently uses
trust authentication with a bare tenant assertion; strict header-trust policy therefore disables
tenant selection rather than credential-binding it. Neutral consumption signals exist for object
GETs/bytes, task time, KOU/KEU/cache quantities, and `MeteringEvent`; they are observability inputs,
not a billing authority or entitlement system. Catalog tenant namespacing remains default OFF/raw,
and stable-ID, modality, and in-memory isolation gaps remain.
| Mandatory architectural gate. New I/O and heavy-compute boundaries must accept or derive tenant
context deliberately, and physical data paths must flow through `DrPathBuilder`. Multi-tenant
production claims remain scoped until catalog path isolation/migration, credential-bound pgwire
identity, stable IDs, and cross-modality isolation close.

| Open formats and object economy
| Object-store and Iceberg engine crates are in the workspace; Parquet/Arrow/Iceberg are the
interop/publication seam and current local OLAP bridge. ADR-027 proposes PAX as the single internal
format and ADR-033/052 keep open formats at the boundary unless xCatalog explicitly marks an
external-authority mode.
| Beta/Experimental depending on path. Safe claim is interoperability direction and one-way publish
where tested, not default external-table durable authority or warehouse-scale object economy.

| Security / ops / deployment
| Principal/API-key registry and fail-closed identity-store boot, relational-transport ABAC/grants,
OIDC role allowlisting, optional REST rate limiting, mTLS/JWT hooks, observability, backup/restore
code, and deployment assets exist. Remaining gaps include pgwire authentication, audit
integrity/retention, write and `System` authorization bypasses, key lifecycle/revocation/MFA,
self-service operations, modality isolation, BYOK/residency, atomic stores, and demonstrated remote
restore/deployment behavior.
| Constrain claims to developer and single-node evaluation deployments. Enterprise or disaster-
recovery positioning requires tenant-catalog isolation, operational evidence, authz closure,
conformance accuracy, and release-smoke evidence.

| Deterministic validation guardrails
| `scripts/check_deterministic_commit_contract.py`, `make work-commit-check`, CI
`deterministic-commit-contract`, branch-promotion/design/status/status-as-of checks,
`docs-claim-check`, MVP contract/smoke checks, context-benchmark validation, capability-matrix and
workspace-boundary checks, tenant ingress/catalog seal/tenant-path checks, silent-failure and env-gate
checks, panic-policy checks, and the retry-budgeted nextest unit profile (`retries = 2`, with
survivors reported as flaky and exhausted failures still failing) form the fast guard chain.
| Mandatory for commit hygiene. The guard chain validates that deterministic test policy, support
claims, architecture invariants, SaaS path constraints, and conflict-marker absence stay wired as the
codebase evolves.
|===

MVP posture: the trust corridor is **single-tenant, single-node SST through canonical REST v2 record
operations**. pgwire/gRPC SQL, hybrid retrieval, alternate engines, multimodal projections, cloud
backends, and distributed execution remain outside that promise at their documented Beta or
Experimental tiers. ProximaDB is not yet ready to position as a mature distributed database, full PostgreSQL-compatible
OLTP/HTAP system, or warehouse-scale MPP engine. The architecture is aligned for that aspiration
through xCatalog, route-once planning, the ADR-039 physical-backend seam, ADR-052's vectorized OLAP
direction, and canonical record convergence, but the implementation is still slice-based and must
keep support claims narrow.

== Agent-memory note

orchestration libraries are specified in
link:adr/ADR-022-agent-memory-layer.adoc[ADR-022] +
link:AGENT_MEMORY_LAYER_HLD_2026_05_30.adoc[AGENT_MEMORY_LAYER_HLD_2026_05_30]. The short version: the
agent-memory layer is a *consumer* of the surfaces mapped above (AQL, Graph RAG, RERANK, hybrid fusion,
