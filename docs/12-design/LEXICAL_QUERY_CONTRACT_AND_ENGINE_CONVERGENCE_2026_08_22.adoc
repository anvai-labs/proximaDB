== Decision

Lexical search has two explicit meanings:

* `NaturalLanguage` is the default. The configured analyzer produces terms, terms are combined with
  OR, punctuation is input data, and query-parser syntax is never inferred.
* `AdvancedSyntax` is opt-in. It uses the selected engine's documented syntax and fails rather than
  silently falling back or rewriting an invalid expression.

Converge the document Tantivy projection and canonical hybrid BM25 implementation on this semantic
contract before considering implementation convergence. Tantivy supports both modes. The canonical
in-memory BM25 implementation supports natural language and returns a typed unsupported-mode error
for advanced syntax. Do not expose advanced syntax on a surface that cannot route to a capable
engine.

This change does not add a wire field. Existing public hybrid requests remain natural-language
requests. A later versioned surface change must carry query mode and capability explicitly rather
than assigning a new interpretation to the existing `text_query` string.

== Working backwards from the user

A user typing `Bugs & Drugs in Pork: Yersinia?` expects relevant documents, not a parser error or an
accidental search for a field named `Pork`. A user deliberately typing `title:yersinia` expects field
syntax to be honored or rejected clearly. One string cannot distinguish those intents by inspection:
punctuation and colons occur in both prose and syntax.

The minimum safe contract therefore has three properties:

. ordinary text cannot enter a syntax parser;
. advanced syntax requires an explicit caller choice and an engine capability;
. unsupported or malformed advanced syntax fails loudly and observably.

Escaping prose before passing it to a parser is not equivalent. It couples behavior to parser
grammar, makes analyzers harder to reason about, and can change again on a library upgrade. Natural
mode constructs term queries directly from the field analyzers.

== Code boundaries

`LexicalQueryMode` lives in the foundation search-types crate. It describes caller intent without a
Tantivy dependency. Each lexical adapter implements that intent:

* document Tantivy tokenizes the input with every configured field's registered analyzer and builds
  deterministic OR term clauses in field-ID order for natural mode;
* its advanced mode alone invokes `QueryParser`;
* canonical BM25 keeps its existing natural tokenization and rejects advanced mode as unsupported;
* production canonical-hybrid callers select natural mode explicitly, making future routing audits
  grep-visible;
* both implementations break equal-score ties by stable document ID at their owned ranking seam.

`score_lexical_corpus` is an evidence adapter, not a third search implementation. It routes to either
production component, emits 100 source candidates per query with deterministic zero-score fill, and
seals hashes for the runner, query contract, selected engine implementation, inputs, and run.

== Why the engines do not collapse yet

Replacing canonical BM25 with Tantivy would reduce implementation count but would also change field
modeling, analysis, scores, persistence, and operational ownership at once. The held-out evidence
does not justify that bundle: Recall@100 is a statistical tie, while canonical BM25 has materially
better NDCG@10 and NDCG@100. A smaller code graph is not a user outcome if ranking quality regresses.

Implementation convergence is admissible only after a controlled candidate matches or improves:

* complete source-aware Recall@100;
* NDCG@10 and NDCG@100 under paired query comparison;
* index build/update behavior and persistence correctness;
* serving latency, memory and object/local-storage economics on a quiet host;
* explainability of analyzer, field model, query mode and selected engine.

Until then the duplication is bounded behind one typed semantic seam. A capability-routed facade may
later hide the implementation choice, but xCatalog should record the materialized projection's
analyzer/field/schema identity; it should not infer a query language from model or collection names.

== MLOps and observability seams

The query contract is related to, but distinct from, the embedding-model catalog. The model contract
governs tokenizer, context, role rendering and dimensions. A lexical projection contract governs
analyzer, fields, scorer, query modes and implementation revision. They may be linked by a retrieval
pipeline/run record, while remaining independently versioned artifacts.

For MLflow/OpenLineage compatibility, an evaluation run should export these as parameters/facets:

* `lexical.engine`, `lexical.query_mode`, analyzer and field-model identity;
* engine/query-contract/runner source hashes;
* corpus, query and qrels hashes;
* query-error count/policy and source-depth completeness;
* per-query artifact hashes and aggregate metrics.

This is why the benchmark manifest schema hashes the implementation behind the runner. A runner hash
alone cannot prove which transitive engine code produced a result.

== Rollout and compatibility

. Natural mode is the component default and preserves the meaning already intended by the public
  hybrid text query.
. Advanced syntax remains component-internal until a versioned public field and capability route are
  designed across REST, gRPC and SDK generation.
. No automatic `NaturalLanguage` to `AdvancedSyntax` fallback is permitted.
. If a projection's analyzer or field model changes, build a new projection identity and retain
  mixed-read safety until cutover.
. Default-on promotion requires the retrieval and operational gates above; recall/conformance
  ratchets only increase.

== Next evidence gate

Use the canonical natural-language baseline for a development-first open cross-encoder reranker.
Require complete source-aware Recall@100, NDCG, citation-span precision, downstream answer quality,
latency and cost. In parallel, design a versioned public query-mode field with engine-capability
reporting; do not block reranker evidence on exposing advanced syntax.

The ranking-only portion of this gate is now measured in
link:../_internal/status/OPEN_CROSS_ENCODER_RERANKER_GATE_2026_08_22.adoc[the open cross-encoder

held-out NDCG@10 by 7.50%, but Recall@100 was exactly invariant. Citation-span, generator-quality
and production ONNX latency gates remain open, so reranking remains opt-in.
