== Why this matters

ProximaDB's storage stack has two read paths with very different
affinity characteristics:

[cols="1,3,3"]
|===
| Path | Where the authority lives | Affinity sensitivity

| WAL memtable
| In-process, per-collection, NOT durable until flush
| **HIGH** — the unflushed records exist *only* on the pod that wrote
them. Any reader on another pod must do a cross-pod fetch or accept
stale results.

| Flushed SST + AXIS index
| Object storage (durable) + per-pod local cache (rebuildable)
| **LOW** — any pod can hot-load the index from object storage; the
WAL manifest is the source of truth.
|===

This asymmetry means that **collection-to-pod placement is a control-plane
decision, not just a load-balancing one**:

* Writes for a collection should pin to the pod that owns its memtable.
* Reads for the same collection should prefer that pod so the 3-stage
  search (`src/services/operations/vectors/legacy.rs:2827-2858`) returns
  consistent recent results without cross-pod chatter.
* Reads can fall back to other pods for flushed-data-only queries —
  AXIS indexes are rebuildable from object storage on any pod (see
  `src/index/axis/storage/recovery.rs:173-240`).

== Current state (verified 2026-05-27)

* WAL memtable search: `src/services/operations/vectors/legacy.rs:2827-2858`
  three-stage search. Stage 1 is `wal_manager.search_unflushed_vectors()`
  on the local pod's memtable — there's no cross-pod fetch fallback.
* AXIS only observes Flush / Compaction / Delete events
  (`src/index/axis/eventlog/event_log.rs:57-64`). It is `not` notified of
  live writes, so a pod that hasn't seen the flush event can't satisfy
  a read against fresh records via its index.
* AXIS recovery on cold start is implemented
  (`src/index/axis/storage/recovery.rs:173-240`) — any pod can hot-load
  indexes from object storage with bounded parallelism + checksum
  verification.
* Tier-migration triggers landed 2026-05-27 — search records access,
  flush determines target tier, compaction triggers evaluate the
  collection. Physical migration between tier paths is still deferred.
* AnvaiOps `apps/api/src/services/placement_planner.py` maps **tier →
  storage pool class** (pooled / business / enterprise / dedicated) but
  does not yet implement **collection → pod** affinity routing.
* Partition lease primitive landed as an implementation slice:
  `src/cluster/partition_lease.rs` stores per `(tenant, collection)` leases
  in a generation-fenced manifest log and reconciles durable ownership into
  `PrimaryPodRegistry`. This closes the durable ownership primitive, but not
  the server bootstrap / failover detector wiring.

== Recommendation

=== Control plane: tenant + collection → pod routing

For each (tenant_id, collection_id), the control plane should publish a
primary-pod assignment. Writes route there unconditionally; reads
prefer it. Concretely:

1. **xCatalog stamps a `primary_pod` field** on the collection record
   when the collection is created. Migration of `primary_pod` is an
   explicit control-plane operation (drain memtable → flush → publish
   new primary).
2. **REST / gRPC gateways consult xCatalog** before dispatching a
   request. The data-plane request handler routes to the primary pod
   for writes, and to the primary pod with a short fallback list for
   reads.
3. **The fallback list** is operator-configured: same AZ first, then
   same region, then any. The fallback only matters for the *flushed*
   data path; if it kicks in, the consumer must accept that
   stage-1 (memtable) returned empty.

=== Data plane: bounded staleness disclosure

When a read falls back to a non-primary pod, the response must
disclose that stage-1 was skipped. This is the same EXPLAIN /
SearchPlanTrace surface as TD-064 — add a new failure-class variant
or a structured `staleness_source: BoundedStale { primary_pod, last_flush_ts }`
field on the trace.

This makes "I read from a fallback pod and missed a 5-second-old write"
a *visible* event, not a silent correctness bug.

=== Anti-pattern: round-robin across pods

A naive load balancer that hashes requests across all pods would
guarantee that **roughly N/pods of writes never become visible to
roughly N/pods of reads** until the next flush completes — a
deceptively serious correctness bug that looks like "tail latency
spike" in dashboards.

Anything implementing read affinity must respect the (tenant_id,
collection_id) sticky-routing contract.

== Coordination points

* **xCatalog ADR (open)** — defines `primary_pod` as a first-class
  collection attribute. Migration semantics, durability of the
  reassignment, and how the data plane discovers new assignments.
* **AnvaiOps placement_planner.py** — current tier-to-pool mapping
  needs to extend with a tenant-collection-to-pod mapping. The pool
  class still drives storage; the pod assignment drives
  request-routing.
* **TD-064 EXPLAIN surface** — extend `SearchPlanTrace` with a
  `staleness_disclosure` block so callers can distinguish
  fresh-from-primary-pod from bounded-stale-from-fallback.
* **WAL replication** — orthogonal but related: if WAL becomes
  multi-pod-replicated, the stage-1 read could fall back to a replica
  rather than a different primary, preserving freshness. This is a
  larger architectural piece (multi-region durability) — out of scope
  for this note.

== Open questions

* What's the failover behavior when the primary pod crashes? The partition
  lease primitive now supports expiry takeover with a higher generation and
  split-brain-safe step-down of stale owners. The remaining open work is the
  control-plane detector/renewal loop wiring: a live process must run renewals,
  detect missed owners, call `PartitionLeaseManager::acquire`, and only then
  route writes to the new primary.
* Cross-tenant noisy-neighbor isolation: should the primary-pod
  assignment respect tier-based pool boundaries (free_trial vs
  enterprise-dedicated)? Probably yes; this is where
  `placement_planner.py`'s pool mapping intersects with the affinity
  contract.
* AXIS index hot-load time after a primary-pod re-assignment: the
  `IndexRecoveryManager` is bounded-parallel — measure the cold-start
  P99 for large collections so the control plane can keep a warm
  standby pod that has the index pre-loaded.
