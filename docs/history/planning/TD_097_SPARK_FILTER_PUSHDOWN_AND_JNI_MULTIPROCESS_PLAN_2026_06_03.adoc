== Context

Two smaller TD-097 follow-ups landed in scope after the 2026-06-02 sprint:

. **Spark filter pushdown**: `spark_plan_input_partitions(emb, table, filters_json, num_partitions)` originally accepted `filters_json` but ignored it. The Rust-side foundation now lowers supported Spark predicates into the canonical scan filter path; JVM DataSource V2 reporting remains post-MVP.
. **Multi-process JNI safety**: `EMBEDDED: OnceLock<Arc<EmbeddedProximaDB>>` is process-level and set-once-strict. JVM class-loader reloads (Spark executor reuse, IDE hot-reload) leave the singleton pinned to its first data dir, with no teardown. Two JVM processes loading the cdylib share the OS-cached library but get independent ProximaDB instances, relying on the file-lock coordination in `src/embedded/coordination/`.

This plan separates the two — they ship independently — but they're grouped because both touch the JNI surface and both are smaller than a full TD on their own.

=== Current state (verified)

**Filter surface**: `spark_plan_input_partitions(emb, table, filters_json, num_partitions)` now lowers Spark filter JSON into the canonical `FilterExpression` where possible. The Rust foundation is real; the JVM DataSource V2 layer that would report pushed/residual filters to Spark is still missing and remains Beta/post-MVP.

**Scan predicate plumbing**: `EmbeddedProximaDB::scan_records_filtered` forwards the optional filter to `VectorOperationsService::scan_records_paginated`, where tenant/RLS predicates and pushed filters are applied before the limit. TD-099(3d) added the deduped, time-ordered scan index that makes repeated cursor-page drains efficient once warm.

**JNI singleton**: `crates/binding/proximadb-spark-jni/src/lib.rs` defines a process-local OnceLock. `initialize` sets it strictly. A diagnostic `JNI_OnUnload` hook now logs unload state and performs a best-effort flush when initialized, but there is still no `_reset` hook. Cross-process safety relies on `src/embedded/coordination/mod.rs` (`AccessMode::Exclusive` / `SharedRead` / `LeaderFollower`).

=== Design (as-built plus deferred seam)

Lower `SparkFilter` JSON → the canonical predicate IR → push into `scan_records_filtered`. Two key questions:

. **Which IR?** `FilterExpression` is now the canonical reusable predicate shape for this path. Reuse it; do not create a Spark-specific predicate IR.

. **Where does pruning happen?** Two layers:
   * *Record-level prune*: shipped. `scan_records_filtered` evaluates the pushed predicate before the page limit so cursor pagination stays correct.
   * *Split/partition-level prune*: deferred into the shared split-aware read planning seam, not a Spark-only `plan_partitions` tweak. See `roadmap/techdebt/TD_097_SHARD_AWARE_PARTITION_PLAN_2026_06_03.adoc`, which is now refined around `SplitSource`, `SplitPlanner`, `RoutedReadPlan`, DataFusion, and Spark as one consumer.

== Part 2 — Multi-Process / Class-Loader JNI Safety

=== Design

Three failure modes to harden against:

. **JVM class-loader reload**: Spark sometimes evicts and reloads classes (e.g. dynamic SQL, structured streaming hot-reload). The `OnceLock` outlives class reload because it lives in the OS-loaded cdylib, not the JVM's class-loaded state. A second `NativeProximaDB.initialize(dataDir)` after reload returns `false` (we set-once-strict). **Acceptable behavior**: log clearly, document the constraint.

. **Two-JVM-on-same-host**: each JVM loads its own cdylib instance (OS deduplicates the file on disk but each process gets its own data segment), then both call `EmbeddedProximaDB::new(dataDir)`. The data dir's file-lock coordination layer (`src/embedded/coordination/`) handles this — `AccessMode::Exclusive` prevents concurrent initialization; today this normally blocks the contender until the holder exits.

. **JVM-exit recovery**: a crashed JVM leaves the file lock; the next JVM should detect a stale lock and reclaim. Today's coordination layer handles this (verified — `LockHeartbeat` timeout).

=== Slice M2 — `JNI_OnUnload` graceful shutdown hook (1 commit)

When the cdylib is unloaded (JVM exit, never class reload — the cdylib survives class reload), call a graceful flush + close on the embedded DB. This is correctness-improving for cold-shutdown scenarios where Spark hits a `System.exit(0)` without explicit `commitWriter`.

Critical files:
* `crates/binding/proximadb-spark-jni/src/lib.rs` — add `extern "system" fn JNI_OnUnload(_vm: JavaVM, _: *mut c_void)`. Tries to `take` from the OnceLock (rare — `OnceLock::take` isn't available; use `Box::leak` pattern + a `AtomicPtr` or `OnceCell<Mutex<Option<Arc<…>>>>` if we want true unload semantics). Pragmatically: log a structured shutdown line + best-effort flush via a shared shutdown channel.

Note: `JNI_OnUnload` is only called when the cdylib is unloaded, which the JVM almost never does. Document this clearly in the README. Don't over-invest.

TDD: a single integration test in `crates/binding/proximadb-spark-jni/tests/` — invoking `JNI_OnUnload` directly (it's safe; we control the function) and asserting a "shutdown logged" trace line.

== Out of scope

* True JVM class-loader unload semantics (`JNI_OnLoad` re-entry on class reload) — Java reality is that `System.loadLibrary` is a no-op on reload, so there's no second `JNI_OnLoad`. The OnceLock survives class reload; documented behavior, not a fixable defect.
* Coordinated reset across JVMs (e.g. "kick the other JVM out of its Exclusive lock") — out of scope. Operator concern, not a connector concern.
* Filter pushdown for nested-struct columns (`StructField` paths) — `SparkFilter` already serializes them; lowering them into `FilterExpression` requires path-expression support that doesn't exist yet. Drop them in F1 (silent rejection is the spec-compliant behavior).
* Cost-based filter ordering (apply selective filters first) — not needed at our current scale; revisit when Spark's `Filter` count routinely exceeds 5+ per scan.

== Convergence summary (Convergence Gate)

* Single predicate IR: `FilterExpression` is reused for Spark filter lowering and record-scan predicates; no Spark-local IR was introduced.
* Split/partition pruning moves to the shared read-planning seam (`RoutedReadPlan` + `SplitSource` + `SplitPlanner`) so DataFusion/notebook/Spark/Flight consume one split contract.
* JNI lifecycle docs go in the binding crate's README — not in the Rust top-level docs, since the lifecycle is JNI-specific. Pyo3/NAPI/CFFI bindings have their own equivalent constraints, documented in their own READMEs.
