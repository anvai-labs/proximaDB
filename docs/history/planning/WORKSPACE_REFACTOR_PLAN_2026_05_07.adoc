== Decision

Yes, the codebase should move deeper into a real workspace-oriented structure, but *not* as a one-shot crate explosion.

The current repository already declares a Cargo workspace, but the root `proximadb` crate still owns nearly all modality, query, storage, server, and embedded concerns. That keeps the dependency graph wide, increases rebuild scope, and makes ownership boundaries fuzzy.

The right target is:

* modality crates for `vector`, `graph`, `document`, `relational`, and `observability`
* a *small* set of common/foundation crates
* a thin cross-model/query layer depending on modality traits, not modality internals
* application crates for server, benchmarks, and embedded/bindings
* a compatibility period where the existing root crate re-exports the new internal crates

This is a technical-debt reduction and build-productivity initiative first, not just a directory cleanup.

== Why This Refactor Is Worth Doing

=== Current Problems

* The root crate mixes storage engines, graph services, query planning, network protocols, bindings, security, and observability.
* A change in one modality often forces a much larger rebuild than necessary.
* Public API concerns and engine concerns are too close together.
* Cross-model code can reach directly into concrete implementations instead of stable service traits.
* Optional dependency weight is concentrated in one crate, which increases compile time and complicates feature gating.

=== Expected Payoff

* touching graph internals should not rebuild unrelated vector/document internals
* touching pgwire or REST should mostly rebuild API/server crates
* touching Python embedded glue should not force broad engine recompiles beyond its real dependencies
* modality ownership becomes explicit
* cross-model query logic becomes easier to reason about because it depends on stable contracts

== Design Principles

=== 1. Split by bounded context, not by file count

The first split should follow architectural ownership, not arbitrary folder moves.

=== 2. Keep common layers small

Only genuinely shared types and contracts go into common crates. Common crates must not become a new monolith.

=== 3. Query depends on traits, not concrete engines

Cross-model planning and execution should consume modality service traits and capability contracts.

=== 4. Avoid per-engine crate proliferation initially

Do *not* create a crate for every storage engine (`sst`, `viper`, `nova`, etc.) in phase 1. That would create too many edges and too much churn too early.

=== 5. Preserve compatibility during migration

The root `proximadb` crate should remain as a transitional facade until downstream imports, binaries, and bindings are stable.

=== 6. Optimize for incremental rebuilds

Crate boundaries should align with change frequency and dependency weight.

=== 7. Align crate boundaries to the platform planes

The workspace isolation strategy must follow
link:../../12-design/DATA_AI_PLATFORM_ARCHITECTURE_ANCHOR_2026_05_12.adoc[the data and AI
platform architecture anchor], not just today's module tree. The anchor adds product planes that
need explicit ownership boundaries:

* compatibility plane: pgwire, REST/gRPC, Arrow Flight, SDK, and streaming protocol adapters
* xCatalog/control plane: schema, policy, branches, lineage, model metadata, stream metadata, and
  optimization statistics
* planning/runtime plane: logical algebra, policy-aware planner/router, native runtime,
  DataFusion, and external compute adapters
* storage/format plane: WAL/log/manifest, context segments, row/PAX/columnar layouts, vector
  index fragments, graph topology, events, and open-format publication
* data/AI workload planes: agent state, MLOps, feature store, AutoML, streaming, and connectors

These planes should refine workspace isolation without creating a crate for every future feature.
New crates are justified only when they establish a reusable contract, remove concrete root/runtime
coupling, or isolate a materially heavy dependency edge.

=== 8. Keep xCatalog, policy, and branch semantics below protocols

The architecture anchor makes xCatalog, engine-level governance, and branchable state platform
foundations. Pgwire, REST/gRPC, Arrow Flight, SDKs, and streaming APIs must all call into shared
catalog/policy/branch contracts instead of each owning parallel metadata logic.

Implication for isolation:

* catalog schema and catalog-facing contracts belong below `proximadb-api` and above foundation
  primitives
* policy context and enforcement contracts must be reusable by query, storage, and modality crates
* branch/log/manifest contracts should be isolated from any one storage engine or protocol surface
* protocol crates may shape requests and responses, but they must not become the source of truth for
  catalog, policy, branch, connector, agent, or MLOps state

=== 9. Split modality facades from durable authority

The convergence mandate in
link:../../12-design/RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14.adoc[RELATIONAL_DOCUMENT_GRAPH_CONVERGENCE_2026_05_14]
is now an explicit workspace constraint. Modality crates should isolate behavior that is truly
modality-specific, but they must not recreate isolated durable systems.

Implication for isolation:

* `proximadb-document` owns document API semantics, JSON path/update behavior, full-text/path
  projection logic, and document query adaptation; canonical document writes flow through record
  store/catalog/log contracts.
* `proximadb-graph` owns graph AST/planner/runtime behavior, traversal capability contracts, and
  topology projection APIs; durable nodes and edges remain canonical records/tables.
* `proximadb-vector` owns ANN index families, scoring, quantization, and freshness/rebuild policy;
  vector metadata and embeddings remain record fields with cataloged index manifests.
* `proximadb-observability` owns log/metric/span/profile facades, compression, rollup, and trace
  projection logic; raw and retained aggregate facts remain canonical records/events.
* future catalog, policy, branch, log/manifest, and record crates must sit below these modality crates
  so the root crate does not merely move duplicated durable semantics into smaller boxes.

== Non-Goals

* No big-bang rewrite.
* No immediate rename of every public Rust path.
* No splitting every submodule into its own crate.
* No protocol-specific duplication of business logic.

== Crate Responsibilities

=== `proximadb-kernel`

Purpose:

* core error/result types
* IDs, metadata primitives, capability enums, common schemas
* stable traits shared across modalities

Must not contain:

* transport code
* engine implementations
* modality-specific service logic

=== `proximadb-config`

Purpose:

* config models
* feature/profile/config loading primitives
* validated runtime configuration objects

Rationale:

* config changes should not rebuild engine code unless types actually flow into those crates

=== `proximadb-proto`

Purpose:

* protobuf-generated types
* tonic/prost codegen ownership
* protocol conversion helpers

Rationale:

* `build.rs` and proto generation move out of the root monolith
* proto-only changes rebuild protocol dependents, not everything else first

=== `proximadb-telemetry`

Purpose:

* tracing, metrics facade, instrumentation helpers
* shared observability contracts

=== `proximadb-storage-common`

Purpose:

* storage abstractions genuinely shared across modalities
* object store adapters, file abstraction, mmap helpers, WAL/IO primitives where truly common

Must not become:

* a second monolith that all modalities dump code into

Rule:

* if a storage abstraction is only used by one modality, keep it in that modality crate

=== Future `proximadb-log-manifest`

Purpose:

* WAL/log/manifest contracts shared by recovery, CDC, branching, and distributed replication
* snapshot and branch ancestry metadata that is not tied to one storage engine
* idempotency, replay, and time-travel primitives used by storage and streaming planes

Admission rule:

* extract only when at least two of storage, branch manager, CDC/streaming, or distributed runtime
  need the same contract without depending on root services

=== Future `proximadb-catalog`

Purpose:

* xCatalog contracts for schemas, indexes, layout options, statistics, governance metadata,
  lineage, branches, connector state, AI assets, and stream metadata
* catalog introspection shapes consumed by pgwire, REST/gRPC, Arrow Flight, SDKs, and runtime
  planning

Must not contain:

* concrete protocol handlers
* storage engine implementations
* UI/admin workflow code

Rule:

* keep catalog contracts below protocol/API crates; keep catalog service composition in platform
  runtime until the service boundary is stable enough to extract

=== `proximadb-vector`

Owns:

* vector search engines and indexing
* quantization, ANN, scoring, vector operations services
* vector-specific storage engines and execution contracts

Current source gravity:

* `src/core/search/**`
* vector portions of `src/index/**`
* vector-specific `src/storage/engines/**`
* vector operations in `src/services/**`

=== `proximadb-graph`

Owns:

* graph engines
* graph services and traversal APIs
* graph query parser/executor/planner
* graph hybrid/rag internals

Current source gravity:

* `src/graph/**`
* graph-specific storage and service wiring
* graph subset/runtime helpers after stabilization

=== `proximadb-document`

Owns:

* document store
* full-text indexing/querying
* document ingestion and query service contracts

Current source gravity:

* document portions of `src/storage/document/**`
* document query operations and text retrieval pieces

=== `proximadb-relational`

Owns:

* SQL frontend pieces that are fundamentally relational/tabular
* pgwire-facing relational semantics
* table/schema/row-layer contracts

Current source gravity:

* SQL parser integration and relational execution pieces
* `src/network/postgres/**` once split from server glue

=== `proximadb-observability`

Owns:

* logs, metrics, traces, event-log style observability services
* observability-specific ingestion and query contracts

Current source gravity:

* `src/observability/**`
* observability parts of `src/storage/**`

=== `proximadb-query`

Purpose:

* unified/federated/facade/cross-model planning and execution
* capability registry
* lowering and fusion

Depends on:

* modality traits/contracts
* kernel/proto/config

Must not depend on:

* server transport code
* embedded Python details

=== `proximadb-api`

Purpose:

* REST, gRPC, Arrow Flight, pgwire adapters
* request/response shaping
* protocol-level validation and mapping

Rule:

* protocol crates call into runtime/query/service contracts
* business logic stays out

=== `proximadb-runtime`

Purpose:

* top-level orchestration
* service composition
* auth/security/middleware integration
* cluster/runtime wiring

=== App and Binding Crates

`apps/proximadb-server`:

* binary entrypoint only

`bindings/*`:

* embedded/language binding glue only
* should consume runtime/query/modality contracts rather than define them

== Dependency Rules

The workspace should enforce a mostly one-way flow:

[source,text]
----
foundation
  -> storage-common / horizontal contracts
  -> modality crates / catalog-policy-branch contracts
  -> query runtime / control services
  -> api/runtime / integrations
  -> apps/bindings
----

Detailed rules:

* `foundation/*` must not depend on modality crates.
* modality crates may depend on `foundation/*` and `storage-common`.
* `proximadb-query` may depend on modality traits and shared contracts, but not server glue.
* `proximadb-api` may depend on `proximadb-query` and `proximadb-runtime`, but not concrete engine internals directly.
* bindings must depend on stable runtime/query/modality surfaces, not reach back into random internal modules.
* catalog, policy, branch, log/manifest, and connector-state contracts must sit below protocol
  adapters; pgwire/REST/gRPC/Flight/SDK layers may not each define their own source-of-truth metadata
  shapes.
* DataFusion, Spark, Trino, Ray, Flink, Kafka, Kinesis, Iceberg, Delta, and MLflow integration
  crates are adapter or sidecar boundaries unless and until their contracts become internal
  platform abstractions.
* agent and MLOps APIs should start as SDK/API conveniences over cataloged schemas and shared
  lifecycle contracts, not as hardcoded low-level source-of-truth schemas.

== Transitional Compatibility Strategy

The existing root crate should remain temporarily as:

* a facade/re-export crate
* a migration shell for downstream imports
* a compatibility point for existing binaries and embedded builds

During transition:

* move code physically into new crates
* re-export public paths from root where needed
* gradually update binaries, tests, and bindings to target new crates directly
* only remove root re-export layers after consumers are stable

=== Phase 0: Workspace Hygiene

Do first:

* normalize `[workspace]` metadata and shared dependency versions
* introduce workspace-wide lint/profile policy
* create `xtask` or scripts for crate graph checks, forbidden dependency edges, and coverage/build workflows

Output:

* reproducible workspace conventions before code movement

=== Phase 1: Extract Foundation Crates

Move first because they are lowest-risk and highest rebuild leverage:

* `proximadb-proto`
* `proximadb-kernel`
* `proximadb-config`
* `proximadb-telemetry`

Why first:

* these reduce root crate breadth immediately
* they establish clean dependency anchors for later crate extraction

=== Phase 2: Extract Modality Service Boundaries

Before moving large code volumes:

* define modality service traits and stable request/result types
* make cross-model/query code depend on those traits
* reduce direct cross-module concrete calls

This is the most important design phase because it prevents cyclic crates later.

=== Phase 3: Extract `proximadb-graph` and `proximadb-vector`

These are the highest-value first modality crates because:

* they are large
* they change frequently
* they have the most obvious ownership boundaries
* they drive many rebuilds today

Important:

* keep graph query parser/executor with graph
* keep vector engines/indexing with vector
* do not strand shared cross-model query logic inside either crate

=== Phase 4: Extract `proximadb-document`, `proximadb-observability`, and `proximadb-relational`

After graph/vector boundaries are proven:

* move document services and text indexing
* move logs/metrics/traces/event-log behavior
* move relational/tabular SQL execution pieces

=== Phase 5: Extract `proximadb-query`, `proximadb-api`, and `proximadb-runtime`

Once modality crates are real:

* shrink the current `src/query/**` into a true cross-model crate
* move transport adapters into `proximadb-api`
* move orchestration/security/cluster composition into `proximadb-runtime`

=== Phase 6: Isolate xCatalog, Branching, Policy, and Log/Manifest Contracts

After modality/query/runtime dependency direction is stable:

* extract catalog contract shapes used by schema, index, storage-layout, statistics, lineage,
  branch, connector-state, MLOps, and agent metadata
* extract policy context/enforcement contracts shared by query, storage, modality, and API layers
* extract log/manifest/branch contract shapes only when recovery, CDC, snapshot/restore, and branch
  management need the same lower abstraction
* keep concrete catalog service composition and runtime wiring in `proximadb-runtime` until the
  service boundary is independently testable

This phase aligns the workspace with the anchor's "one catalog, one policy plane, one branch/log
foundation" requirement without prematurely moving every control-plane service.

=== Phase 7: Isolate External Integration and Sidecar Adapter Crates

Once internal planning/catalog contracts are stable:

* isolate DataFusion, Spark, Trino, Ray, Flink, Kafka/Kinesis, Iceberg/Delta/Hudi, MLflow, AutoML,
  and agent-framework adapters behind feature-gated crates
* keep adapter dependencies out of foundation, modality, storage-common, and query-contract crates
* route external execution through planner/runtime contracts so `EXPLAIN`, policy, branch, and
  catalog semantics remain deterministic across engines

=== Phase 8: Thin Root Crate and Direct App Wiring

Final state:

* root crate is minimal compatibility shell or removed from hot-path development
* `apps/proximadb-server` depends on runtime/api/query/modality crates explicitly
* bindings depend on stable exported contracts

== Rebuild Impact Model

This refactor is justified only if rebuild scope becomes materially smaller.

Examples:

* changing `proximadb-graph` query runtime should rebuild `proximadb-graph`, `proximadb-query`, `proximadb-api/runtime`, and dependent apps, but not vector/document internals
* changing `proximadb-vector` ANN logic should not rebuild graph internals
* changing REST handler serialization should mostly rebuild `proximadb-api` and app crates
* changing protobufs should rebuild `proximadb-proto` dependents, not force a full monolith-style recompilation first
* changing Python embedded binding code should rebuild the binding crate and its direct runtime dependencies, not unrelated modality internals

== Critical Risks

=== Risk 1: Cyclic dependencies

Mitigation:

* trait-first extraction before crate extraction
* dependency graph checks in CI

=== Risk 2: “Common” crates becoming junk drawers

Mitigation:

* strict admission rule for shared crates
* if code is not used by multiple bounded contexts, it stays local

=== Risk 3: Over-splitting too early

Mitigation:

* start with modality crates, not engine-per-crate
* delay finer-grained engine extraction until compile telemetry proves it is worth it

=== Risk 4: Public API churn

Mitigation:

* transitional root facade
* staged re-exports
* binding/client migration after internal boundaries settle

== CI and Tooling Changes Required

The workspace plan should be accompanied by:

* per-crate `cargo check` and `cargo test` CI targets
* dependency direction linting
* crate-level coverage baselines
* incremental build timing capture before and after each phase
* `cargo hakari` or equivalent only if dependency unification becomes painful

== Success Metrics

Success should be measured, not assumed.

Target metrics:

* materially lower incremental rebuild time for graph/vector-only changes
* smaller average crate dependency fan-in/out
* fewer direct imports across unrelated modalities
* reduced root crate LOC and dependency count
* clearer ownership for graph, vector, document, relational, and observability code

== Recommended First Implementation Slice

Do *not* start by moving everything.

Start with:

1. `proximadb-proto`
2. `proximadb-kernel`
3. `proximadb-config`
4. `proximadb-telemetry`
5. graph/vector service trait cleanup in place
6. extract `proximadb-graph`
7. extract `proximadb-vector`

This sequence gives the best signal on whether workspace modularization is improving rebuild scope without destabilizing the entire product.

== Refined First Cut

The initial implementation should be even narrower than the original phase list:

1. extract `proximadb-proto` first
2. keep the generated Rust sources as the temporary single source of truth
3. re-export the new proto crate from `src/proto/mod.rs` so `crate::proto::...` keeps working
4. add workspace-wide package/dependency metadata only for the crates that are actually extracted
5. measure `cargo check -p proximadb-proto` and root-crate rebuild behavior before extracting the next foundation crate

Why this order is better:

* it creates a real workspace dependency edge immediately
* it avoids a repo-wide import rewrite
* it turns the proto surface into a reusable leaf crate for server, bindings, and clients
* it gives us a repeatable extraction pattern for later crates

== Implementation Status

Current status after the first refinement:

* `proximadb-proto` is the first extracted foundation crate
* `proximadb-kernel` now owns the legacy shared error contract used across graph, query, storage, and transport layers
* `proximadb-kernel` no longer depends on `tonic`; gRPC `ProtocolError -> tonic::Status` mapping now lives at the root protocol layer instead of in the foundation crate
* `proximadb-kernel` now also owns the generic foundation traits/helpers previously under `src/core/foundation`
* `proximadb-graph` now exists as the first modality crate and owns the engine-agnostic graph query execution contracts (`QueryValue`, `ResultTuple`, `PhysicalOperator`, `ExecutionStats`)
* the graph query operator layer (`scan`, `expand`, `filter`, `project`, `limit`) now also lives under `proximadb-graph`, behind a narrow `GraphQueryStorage` trait instead of direct root-engine coupling
* the graph query language layer (`ast`, `parser`, `cypher_ast`, `cypher_parser`, `unified_parser`) now also lives under `proximadb-graph`, with root modules reduced to compatibility reexports
* the graph planner and Cypher function library now also live under `proximadb-graph`; the root planner module is reduced to a compatibility wrapper that only adapts `GraphMemoryPool` statistics into the extracted planner’s snapshot API
* the canonical graph pattern-matching runtime now also lives under `proximadb-graph`; the root `pattern` module is reduced to a compatibility wrapper that adapts `GraphMemoryPool` into `GraphQueryStorage`
* the canonical graph query executor runtime now also lives under `proximadb-graph`, behind a narrow async node/edge query contract; the root `executor` module is reduced to a compatibility wrapper that adapts `GraphOperationsService` and keeps Arrow conversion local to root query infrastructure
* `proximadb-kernel` now also owns a small modality-neutral `ExecutionContext`/`ExecutionLimits` contract for request metadata, tenant/principal scope, parameters, and resource limits; modality crates must embed or adapt this instead of inventing parallel timeout/parameter context structs when the semantics are shared
* graph query context/result contracts now live under the lower `proximadb-graph-query` contract crate as graph-specific names (`GraphQueryContext`, `GraphQueryStats`, `GraphQueryExecutionResult`, `GraphQueryRow`), while `proximadb-graph` keeps the historical `QueryContext`/`QueryStats`/`QueryExecutionResult`/`QueryRow` aliases for compatibility
* `proximadb-graph-subset` is now explicitly treated as a query-adapter crate, not a pure query-contract crate: it owns supported graph-subset parsing/validation, read-only subset execution helpers, and row-shaping/legacy-row conversion helpers reused by facade, federated, lowering, and runtime layers
* `proximadb-graph-query` now owns the canonical lowered declarative graph-query descriptor (`LoweredGraphQuery` / `SupportedGraphQueryDescriptor`), while `proximadb-graph-subset` keeps parsing/execution behavior and reexports the descriptor for compatibility
* `proximadb-graph-query` now also owns the stable declarative graph-query row-id helper, so query-runtime result shaping no longer depends on `proximadb-graph-subset` just to identify graph rows
* the root unified AST no longer defines its own duplicate lowered declarative graph-query struct; `GraphQueryExpr` now reuses the `proximadb-graph-query` lowered contract directly, which removes another root-owned graph IR seam before the larger `proximadb-query` split
* the shared `FilterOperator`/`FilterValue` contract now lives in a new leaf crate, `proximadb-query-filter`, and the graph traversal IR (`GraphTraversalExpr`, `StartNodeSpec`, traversal/node/edge/property filters) now lives in `proximadb-graph`; the root unified AST re-exports both instead of owning another graph-specific IR island
* the document query IR (`DocumentQueryExpr`, `PathFilter`, `DocumentSort`) now lives in a new leaf crate, `proximadb-document-query`, so the root unified AST no longer owns modality-specific document request shape either
* the observability query IR (`LogQueryExpr`, `MetricQueryExpr`, `MetricAggregation`) now lives in a new leaf crate, `proximadb-observability-query`, so the root unified AST is continuing to shrink into a composition/re-export shell rather than a monolithic owner of every modality request shape
* the vector query IR (`VectorSearchExpr`, `VectorSearchParams`, `DistanceMetric`) now also lives in a new leaf crate, `proximadb-vector-query`, so the root unified AST no longer owns vector request shape either and is getting closer to a pure cross-model composition layer
* `proximadb-vector-query`, `proximadb-document-query`, and `proximadb-observability-query` now also own narrow async service contracts for read/query execution; root runtime code can implement or adapt those contracts while protocol/query layers depend on capability views instead of concrete root services
* AXIS transform/disentangled projection contracts now live in `proximadb-vector`; root `src/index/axis` keeps only a compatibility re-export so context-disentangled vector work can compile and test below the root crate.
* vector REST/unified protocol wiring has started consuming the extracted `VectorQueryService` contract at the composition edge; the concrete `VectorOperationsService` remains available for legacy paths, but new vector-search routing can prefer the contract seam
* root `DocumentService` now implements the extracted `DocumentQueryService` contract for document
  search and get-by-id, giving query/runtime callers a stable document capability view while concrete
  document indexing, filter parsing, and storage execution remain in the root document service for now
* the generic cross-model clause IR (`Filter`, `OrderBy`) now also lives in a new leaf crate, `proximadb-query-clauses`, so the root unified AST is no longer the owner of generic reusable clause shape either
* the canonical data-model discriminator (`StoreType`) now lives in a new foundation leaf crate, `proximadb-data-model`, so query, security, storage, and protocol layers no longer need the root multimodel router just to name a model kind
* the shared search filter contract (`FilterExpression`, `ComparisonOperator`) now lives in a new foundation leaf crate, `proximadb-filter-expression`, so query planning/lowering, compute pipeline execution, storage filtering, and services can converge on one reusable contract instead of pulling those types through the root search module
* the shared pipeline operator contract (`PipelineOperator`) now lives in a new foundation leaf crate, `proximadb-pipeline-operator`, so query planning, compute pipeline execution, and storage readers can share the same operator shape without depending on the root compute module
* the unified multimodel `FusionStrategy` enum now also lives in a new leaf crate, `proximadb-query-fusion`, so the root unified fusion module retains execution logic while the reusable fusion-strategy contract becomes independently buildable

== Boundary Validation And Course Correction

The extraction work completed so far is directionally correct, but it needs a stricter boundary policy to achieve the original goals of lower rebuild cost, clearer ownership, and better runtime encapsulation.

=== What Is Working

* the root `query::unified::ast` surface is shrinking into compatibility glue instead of remaining the owner of every modality IR
* the graph query/runtime path now has real non-root build units (`proximadb-graph`, `proximadb-graph-subset`, `proximadb-graph-arrow`)
* shared contracts such as data-model, filter expression, pipeline operator, fusion strategy, and multimodel plan shape are now explicitly owned instead of being hidden in root modules

=== Current Strategic Risks

* too much of the recent extraction has focused on *lightweight IR crates* rather than the *heavy runtime/build boundaries* that dominate `cargo check --lib` and end-to-end server/embedded rebuild time
* several "foundation" or "leaf" crates still carry dependencies that are too heavy or too transport-specific for their intended role
* some cross-model crates still depend on heavier modality runtime crates instead of depending only on narrow contracts
* the root `proximadb` crate is still the effective runtime/application monolith, so the build-time payoff is still capped until higher-level runtime and app crates move out

=== Validated Boundary Findings

==== 1. `proximadb-kernel` transport purity is now guarded

The plan says `proximadb-kernel` must not contain transport code. That cleanup has landed:
`proximadb-kernel` no longer depends on `tonic` or `tonic-prost`.

Implication:

* this keeps gRPC/transport concerns isolated from core error and contract code

Correction:

* keep `proximadb-kernel` limited to transport-agnostic errors, IDs, metadata, and stable traits
* `workspace-boundaries-check` now guards against reintroducing `tonic`/`tonic-prost` into
  `proximadb-kernel`

==== 2. `proximadb-proto` host-runtime helper drift is now guarded

The proto crate should own generated protobuf/gRPC DTOs, serde shims, and protocol conversion
helpers. It no longer carries host/runtime helper dependencies such as `num_cpus`, `sysinfo`, or
`tracing`. `serde_json` remains because `serde_impls.rs` owns JSON-compatible serde conversion
helpers for protocol DTOs.

Implication:

* protocol DTO/codegen changes should not pull host/runtime concerns into foundation builds

Correction:

* keep generated protobuf types, serde/default shims, and protocol conversion helpers in `proximadb-proto`
* keep host/runtime/system helpers in `proximadb-runtime`, `proximadb-telemetry`, or other higher-layer crates as appropriate
* `workspace-boundaries-check` now guards against reintroducing `num_cpus`, `sysinfo`, or `tracing`
  into `proximadb-proto`
* `proximadb-runtime` now owns the runtime proto defaulting helper, including host CPU/memory inspection
  and tracing diagnostics; the root proto module remains a facade for packaging/runtime compatibility
* the source migration map now has a file-level override for `src/proto/defaults.rs`, so future agents
  do not misclassify the compatibility shim as protocol-foundation ownership
* `workspace-boundaries-check` now also applies crate-specific disallowed dependency rules beyond
  foundation crates, so horizontal telemetry cannot quietly absorb REST/gRPC/client transport helpers

==== 3. `proximadb-multimodel-query` graph dependency has been narrowed

The multimodel query IR crate previously depended on heavier graph crates for declarative graph
query shape.

Implication:

* graph runtime, parser, or subset execution changes could force recompilation of crates that only
  need cross-model IR
* this violated the intent that cross-model/query layers depend on modality contracts rather than
  modality internals

Correction:

* reusable graph request-shape contracts now live in `proximadb-graph-query`
* `proximadb-multimodel-query` now depends on graph IR/contracts only, not on
  `proximadb-graph` or `proximadb-graph-subset`

==== 4. `proximadb-graph-subset` mixes syntax/descriptor ownership with execution/runtime ownership

The crate description says "parsing and descriptor layer", but it also owns read-only execution helpers and shaped runtime behavior.

Implication:

* syntax-only changes and runtime-only changes are coupled together
* the crate is less cohesive than its name suggests

Correction:

* either split the crate into syntax/descriptor and runtime-adapter layers
* or explicitly rename/reposition it as a graph-query adapter/runtime crate instead of presenting it as a pure descriptor leaf

==== 5. `proximadb-multimodel-plan` planner behavior is now classified

The logical plan crate owns not only plan/operator structures but also validation, optimization, and compute-operator conversion helpers.

Implication:

* a crate intended as a reusable contract layer is also becoming a planner/behavior layer
* this will make later query-runtime extraction more coupled than necessary

Correction:

* keep the current shape temporarily if it accelerates migration
* but plan a later split between pure logical-plan IR and planner/optimizer behavior once `unified/lower`, fusion, and runtime execution move out of root
* `workspace-boundaries-check` now classifies `proximadb-multimodel-plan` as `query-planner`,
  prevents pure query-contract crates from depending on planner/optimizer behavior crates, and
  prevents planner crates from depending upward into runtime, adapter, or concrete modality crates

=== Revised Isolation Strategy

From this point forward, the workspace refactor should prioritize *heavier architectural seams* over additional micro-crate extraction.

==== Priority Order

1. purify existing foundation crates (`kernel`, `proto`) so they match their intended architectural role
2. finish the first real runtime cut for the unified query stack:
   * lowering
   * fusion/result-shaping
   * cross-model execution orchestration
3. extract higher-cost modality/runtime crates that materially reduce rebuild scope:
   * `proximadb-vector`
   * `proximadb-document`
   * `proximadb-observability`
   * `proximadb-storage-common` where truly shared
4. extract platform/application crates:
   * `proximadb-api`
   * `proximadb-runtime`
   * `apps/proximadb-server`
   * embedded/binding-specific crates

==== New Rule For Additional Crates

Do *not* create another new crate unless it satisfies at least one of these:

* it severs a heavy rebuild dependency edge
* it removes concrete root runtime coupling from another layer
* it creates a stable reusable contract that multiple heavier crates will actually consume

If a candidate crate only moves a small IR type but does not materially improve rebuild scope or dependency direction, prefer keeping it in the next higher cohesive crate.

==== Recommended Layering Model

The dependency direction should converge to:

* foundation:
  `kernel`, `data-model`, `filter-expression`, `pipeline-operator`, `proto`
* contracts/IR:
  reusable modality and query-shape contracts
* modality/runtime:
  graph, vector, document, observability, relational
* cross-model query:
  parsing, lowering, planning, fusion, federated execution
* platform/runtime:
  API, server runtime, protocol surfaces, embedded wiring
* apps/bindings:
  server binaries, benchmark binaries, embedded/binding entrypoints

And the following dependency directions should remain forbidden:

* foundation -> platform/application
* foundation -> transport/runtime-specific crates
* contracts/IR -> concrete modality runtimes where a narrower contract can exist
* modality runtime -> root compatibility shims
* cross-model query -> protocol/server/bootstrap code

=== Practical Next-Step Recommendation

The next implementation work should *not* keep peeling tiny AST fragments.

The best next sequence is:

1. purify `proximadb-kernel` and `proximadb-proto`
2. expand the new `proximadb-query` crate beyond lowering into the remaining query runtime behavior
3. group remaining root query runtime behavior into `proximadb-query` instead of creating more micro query crates
4. begin the first heavy modality extraction with `proximadb-vector`
5. only introduce more leaf crates when they clearly support those heavier cuts

== Skeleton-First Stabilization

The refactor now needs a *stable high-level skeleton* more than additional low-level extraction. The main risk is no longer "not enough crates"; it is *surface churn* caused by moving small pieces without freezing the higher-level abstraction map.

=== Stable Target Skeleton

From this point forward, the target architecture should be treated as the following stable layers:

1. *Foundation*
   * transport-agnostic kernel contracts
   * protocol/codegen contracts
   * small shared value types and reusable expressions
2. *Contracts*
   * reusable modality request/IR contracts
   * reusable logical-plan and query-shape contracts
   * no concrete runtime behavior unless it is purely structural and serialization-safe
3. *Modality Runtime*
   * graph, vector, document, observability, relational runtime behavior
   * storage/index/query execution internals for a single modality
4. *Cross-Model Query Runtime*
   * UQL/lowering/planning/fusion/federation/orchestration
   * depends on modality contracts/capabilities, not concrete platform/runtime wiring
5. *Platform Runtime*
   * API handlers
   * REST/gRPC/pgwire/Flight wiring
   * server runtime bootstrap
   * embedded/runtime composition
6. *Apps And Bindings*
   * server binary
   * benchmark binaries
   * embedded/binding entrypoints

=== Current Suboptimal Boundaries, Prioritized

==== P0: Root `proximadb` is still the effective runtime monolith

This is still the largest structural problem. Even with many extracted leaves, the main runtime, protocol wiring, query orchestration, storage ownership, and embedded/server composition still converge in the root crate.

Why it matters:

* rebuild scope is still dominated by the root crate
* ownership remains fuzzy
* compatibility shims remain too central instead of being transitional edges

Required direction:

* move toward explicit `proximadb-query`, `proximadb-api`, `proximadb-runtime`, and app crates

==== P0: Foundation crates are not yet pure enough

`proximadb-kernel` and `proximadb-proto` still violate the intended layering rules.

Why it matters:

* impure foundations contaminate every higher layer
* they make future extraction harder because transport/runtime concerns leak downward

Required direction:

* keep `kernel` transport-agnostic
* keep `proto` protocol/codegen focused
* move runtime/host/system behavior upward

==== P1: Query/runtime behavior is still too fragmented across root and micro-crates

The current set of extracted query leaves was useful to break ownership out of root AST modules, but the long-term abstraction should not be "dozens of tiny query crates". The stable boundary should be one *contracts stratum* plus one *query runtime stratum*.

Why it matters:

* the current surface is easy to churn
* runtime behavior is still split between root and multiple small crates
* future turns risk optimizing crate count instead of runtime cohesion

Required direction:

* stop creating tiny query crates unless they sever a heavy edge
* consolidate the behavior layer into a real `proximadb-query` runtime crate
* treat the existing small query crates as contract leaves, not as the final runtime shape

==== P1: Graph boundaries are improved, but not yet cleanly layered

Graph has the strongest extraction progress so far, but the graph surface is still split across:

* `proximadb-graph`
* `proximadb-graph-subset`
* `proximadb-graph-arrow`
* root compatibility shims

The suboptimal part is not the number of crates by itself; it is that syntax/descriptor, runtime adaptation, and presentation are not yet crisply separated.

Required direction:

* keep `proximadb-graph` as the canonical graph runtime/modality crate
* keep `proximadb-graph-arrow` only if columnar presentation remains a reusable cross-layer seam
* either narrow `proximadb-graph-subset` to pure subset analysis or reposition it explicitly as a graph-query adapter/runtime layer

==== P1: Missing heavy modality crates still cap build-time payoff

There is still no real extracted `vector`, `document`, or `observability` runtime crate.

Why it matters:

* graph extraction alone cannot deliver the intended workspace benefit
* the heaviest storage/query/runtime code is still in root

Required direction:

* after foundation cleanup and query-runtime extraction, move to `proximadb-vector` first
* then `proximadb-document` and `proximadb-observability`

==== P2: Compatibility shims are still necessary, but must stop growing

Compatibility shims are serving the migration correctly, but they must remain a transitional facade, not a second API layer.

Required direction:

* keep root re-export modules stable
* do not add new public wrapper behavior to root unless it is purely transitional
* move real behavior behind extracted crates, not into shims

=== Skeleton Freeze Rules

These rules should guide each subsequent turn:

1. Do not change the high-level layer map above unless a boundary is clearly wrong.
2. Do not create a new crate just to move a few structs unless it severs a heavy dependency edge or stabilizes a real shared contract.
3. Prefer moving *behavior* behind an already-agreed layer over extracting another tiny IR surface.
4. Keep root public compatibility modules stable:
   * `src/query/unified/ast.rs`
   * `src/query/unified/uql.rs`
   * `src/query/multimodal/plan.rs`
   * similar re-export shells
5. New work should reduce one of these on each turn:
   * root concrete runtime coupling
   * foundation impurity
   * modality-to-platform leakage
   * rebuild scope for a heavy subsystem
6. Avoid renaming crates or public surfaces casually during the transition. Move internals first; rename only when the boundary is already stable.

=== Boundary Rules For Horizontal Layers

To keep the skeleton clean, the horizontal layers above must obey stricter rules than modality crates.

* security is a shared policy/runtime concern, not a dumping ground for transport handlers
* networking owns shared protocol/runtime mechanics, not business logic for graph/vector/document
* cluster/consensus owns distributed coordination and placement, not query planning logic
* catalog owns metadata/control-plane state, not modality execution behavior
* storage-common must stay small and only hold truly shared primitives
* runtime-common/helpers must not absorb domain behavior just because it is "used in many places"
* integrations must adapt external systems to internal contracts; they should not become a second core runtime

=== Dependency Direction For The Full Product

The dependency trajectory should converge toward:

* foundation -> nothing higher
* horizontal infrastructure -> foundation
* modality runtimes -> foundation + selected horizontal layers
* cross-model query runtime -> foundation + modality contracts/capabilities + selected horizontal layers
* platform runtime -> query runtime + modality runtimes + horizontal infrastructure
* external integrations -> foundation + horizontal layers + modality/query contracts as needed
* apps/bindings -> platform/runtime crates only

And specifically:

* networking should not depend on API business logic
* security should not depend on REST/gRPC/pgwire handler code
* cluster/consensus should not depend on query lowering or modality internals unless through narrow contracts
* modality runtimes should not depend on app/bootstrap code
* external integrations should terminate at stable internal contracts rather than reaching into root internals

=== Trajectory For Subsequent Turns

To avoid shifting the surface every turn, future work should follow this trajectory:

1. purify the foundation layer
2. stabilize one real query-runtime crate
3. extract one heavy modality at a time
4. extract platform/runtime crates only after query and modality seams are stable
5. let root compatibility shrink naturally instead of redesigning it repeatedly

This preserves a clear abstraction trajectory:

* first stabilize the skeleton
* then move internals behind it
* then reduce the transitional root facade

=== Recent Query-Runtime Boundary Refinement

The pure observability adaptation layer now also lives in `proximadb-query`:

* `observability_adapter` owns log severity normalization, metric aggregation/label/group-by
  request shaping, and log/metric unified-record shaping
* the root unified executor keeps only `ObservabilityService` invocation plus the final bridge
  into the internal observability aggregation enum
* this fixed a real root-path bug where metric execution had been hardcoding `Avg`, dropping
  `label_filters`, and dropping `group_by` from the observability query IR

The graph adapter boundary in `proximadb-query` is now broader and cleaner:

* `graph_adapter` now owns declarative graph-row shaping, traversal-node shaping, and
  start-node resolution against the narrow `GraphQueryReadService` contract
* `graph_adapter` also now owns the deterministic multi-start traversal execution loop and the
  explicit-input traversal shaping path against the narrow graph traversal contracts
* the root unified executor keeps only actual graph-service traversal/query invocation, instead of
  re-owning canonical node-query construction, traversal dedup orchestration, and record shaping
* this further reduces root executor drift while keeping graph engine/runtime ownership in
  `proximadb-graph` and query-runtime ownership in `proximadb-query`

The vector/document adaptation layer in `proximadb-query` is also broader now:

* `vector_adapter` owns unified vector-hit metadata formatting and vector search record shaping
* `document_adapter` now owns document query record shaping in addition to SQL/document filter
  and JSON adaptation
* the root unified executor keeps only vector/document service invocation plus `SubQueryResult`
  assembly, instead of re-owning modality-specific `UnifiedRecord` construction

The root unified executor now also sits on an extracted component-execution seam:

* `proximadb-query::execution` now owns cross-modal component dispatch, execution-time stamping,
  and dependency-join application behind a narrow `QueryComponentExecutionService` contract
* the root unified executor now adapts concrete vector/document/graph/observability services to
  that contract instead of owning another copy of `ModelOperation` dispatch and dependency-aware
  component orchestration
* this keeps pure query-runtime component behavior in `proximadb-query` while leaving actual
  service invocation and platform wiring in root where they still belong today

That execution seam is now broader:

* `proximadb-query::execution` now also owns the pure batch/runtime orchestration for
  multimodel execution: partitioning parallelizable vs dependent components, bounded parallel
  fan-out, prior-result context construction, and dependency-aware sequential follow-up
* the root `ParallelExecutor` now keeps RBAC and concrete service/LLM wiring, but no longer owns
  another copy of query-runtime scheduling logic or a root-local concurrency primitive
* this is the right shape for the next steps because additional executor/runtime behavior can now
  move behind the same `QueryComponentExecutionService` boundary instead of requiring new surfaces

The join/runtime boundary is also cleaner now:

* `proximadb-query::joins` now owns the semantic-join dispatch contract itself via a narrow
  `BlockBatchSemanticJoinService` seam plus extracted `execute_join_with_services`
* the root unified executor no longer owns the exact-vs-semantic join decision tree or the
  cosine-vs-block-batch routing logic; it now only adapts the concrete root cosine distance
  engine and the existing LLM-backed block-batch implementation to the extracted join-runtime
  contract
* this keeps reusable join behavior in `proximadb-query` while leaving only the platform-bound
  LLM prompt path in root

=== Recent Graph Contract Boundary Refinement

The graph query contract layer is now lower than the graph runtime:

* foundation-level execution metadata belongs in `proximadb-kernel` as `ExecutionContext` and
  `ExecutionLimits`; modality identity such as `graph_id`, collection, namespace, or table must
  stay in modality-specific contexts that embed the common execution context
* `proximadb-graph-query` now owns traversal IR and the graph read/stats/traversal service

* `workspace-boundaries-check` is now clean for the current extracted graph/query crates; do not

* `workspace-boundaries-check` now treats query-runtime -> modality-runtime edges as errors, so

* `workspace-boundaries-check` also blocks `proximadb-query` from depending on

* `workspace-boundaries-check` now reports query-adapter crates separately from query-contract

* `workspace-boundaries-check` now expresses layer restrictions through a centralized policy table,

* the boundary checker now recognizes planned future crate directories for `crates/storage`,

* `proximadb-catalog` now exists as the first control-plane contract crate and owns the serializable

* `workspace-boundaries-check` now has an explicit `control` layer for catalog/branch/policy/log

|query, compute, and storage callers consume the same contract without root shims

|P2
|truly shared storage IO/WAL/object-store abstractions
|future `proximadb-storage-common`
|used by multiple modalities; no modality/query/platform dependency edge
|===

Foundation extraction rule:

* move a helper downward only when it is transport-neutral, modality-neutral, and consumed by more
  than one heavier layer
* keep runtime composition, caches with service ownership, host inspection, and protocol handler
  behavior out of foundation crates
* validate every step with `python3 scripts/check_workspace_boundaries.py --strict`, the relevant
  `cargo check -p ... --lib`, and the rebuild baseline harness when the move is expected to reduce
  rebuild scope

=== Storage Layout And External Format Isolation Checklist

Storage fungibility is a platform requirement, but it must not recreate hidden durable truth in
format-specific crates. Internal and external formats should plug into shared record, catalog,
policy, log/manifest, and projection contracts.

[cols="1,2,2,2", options="header"]
|===
|Priority
|Current gravity
|Target
|Acceptance gate

|P0
|physical layout selection scattered across storage engines and service options
|catalog-facing `StorageLayout` / `Projection` / `AuthorityMode` contracts in root-compatible modules first; future `proximadb-storage-common`
|query planner, storage engines, imports/exports, and protocol introspection describe layouts with one vocabulary

|P0
|ANN, JSON path, full-text, graph topology, time, and rollup indexes as engine-specific metadata
|cataloged projection metadata with freshness, rebuild source, invalidation, retention impact, and benchmark status
|`EXPLAIN` can report projection authority/freshness and whether a result came from a fallback

|P1
|Parquet/Arrow import/export and columnar internals coupled to individual engines
|format adapters behind `proximadb-storage-common` contracts; Arrow remains interchange, Parquet remains file layout
|format code does not own record/type/policy semantics and can be feature-gated independently

|P1
|Iceberg/Delta/Hudi integration pressure
|future integration crates or sidecars for external table/catalog adapters
|external tables declare ownership mode, snapshot semantics, type mapping, policy boundary, write/refresh mode, and repair source in xCatalog

|P1
|relational index and constraint semantics emerging inside SQL/pgwire paths
|future `proximadb-relational` plus lower catalog/storage contracts for keys, unique indexes, secondary indexes, FKs, checks, materialized views, and transaction profiles
|constraints are enforced below protocols and recovered through WAL/log/manifest when enabled

|P2
|observability/SIEM structures mixed between storage, services, and query paths
|`proximadb-observability` owns log/metric/span/profile semantics and projection builders; shared time/full-text/rollup contracts stay lower
|alerts, anomalies, rollups, and service maps are catalog-visible projections or canonical derived records with provenance
|===

Storage-layout migration rule:

* physical flexibility is encouraged; semantic authority is centralized
* LSM, row/record, PAX, columnar, Arrow, Parquet, Iceberg, Delta, Hudi, graph topology, vector, and
  observability formats are access methods, projections, or external authority modes declared in
  xCatalog
* do not introduce a format-specific crate that defines its own record envelope, scalar type system,
  policy model, WAL/recovery semantics, or catalog
* optional relational constraints are table capabilities and durable semantics when enabled; they
  belong below protocol handlers and above physical index/layout details
* feature-gate heavyweight external format dependencies until more than one runtime or protocol
  surface consumes the contract

== Bottom Line

Refactor into a deeper workspace, yes.

Do it as a staged architectural split with trait-first boundaries and a temporary compatibility facade, not as a one-shot file move or a crate-per-folder explosion.

That approach is the best fit for:

* faster rebuilds
* cleaner modality ownership
* better long-term maintainability
* scalable cross-model evolution without duplicating logic across graph, vector, document, relational, and embedded surfaces
