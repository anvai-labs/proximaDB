mutation, with `PROXIMADB_SCAN_INDEX_DISABLE=1` as an operational kill-switch.

== Context

The 2026-06-02 connector-conformance sprint closed TD-099(3a) (cursor codec) and TD-099(3b) (Hadoop sync-bridge). The remaining gap is push-down: today, every paginated scan materializes the *entire* unflushed-WAL record set into a `Vec<ProximaRecord>` before `apply_scan_cursor` sorts, filters, and truncates it. Both *peak memory* and *sort CPU* are O(collection_size), regardless of `limit` or cursor position.

This plan pushes the cursor tuple + limit into the WAL streaming surface so the *materialization* cost (heap + page) is O(limit) and the *sort* cost drops from O(N log N) to O(N log limit).

[IMPORTANT]
====
*Scope of the win — read this first.* The unflushed memtable is partitioned *one partition per collection* (`GlobalPartitionedMemtable.collections: HashMap<collection_id, CollectionPartition>`), and within a partition records live in an *unordered* `wal_batches: HashMap<batch_id, WALVectorBatch>` with no per-batch or per-partition timestamp index. There is no time-ordered sub-structure to seek into. Therefore a cursor scan *must still visit every unflushed record of the collection* to find the `limit` smallest records greater than the cursor.

What push-down buys here:

* *Peak memory:* O(N) full sorted `Vec` → O(limit) bounded heap + page. **Real, primary win.**
* *Sort CPU:* O(N log N) full sort → O(N log limit) heap maintenance. **Real, secondary win.**
* *Record visits / wall-clock:* stays O(N). **NOT improved by this plan.**

A true O(log N + limit) *seek* requires a time-ordered index on the memtable partition (e.g. a `BTreeMap<(updated_at_ns, oid), batch_ref>`). That is a larger, separately-gated change tracked as the TD-099(3d) follow-up (see <<followup>>); it is explicitly *not* in this plan.
====

  → apply_scan_cursor(records, cursor, limit, collection_id, now_ns)    # src/services/scan_cursor.rs:109
    # sorts by (updated_at_ns, oid), filters strictly-greater-than cursor, takes limit, derives next cursor
----

`apply_scan_cursor` is the source-of-truth for paginated ordering: the canonical tuple is `(updated_at_ns, oid)`, and it *also* derives the next cursor (5-arg signature: `(records, cursor, limit, collection_id, now_ns) -> (Vec<ProximaRecord>, Option<ScanCursor>)`). The WAL does NOT maintain that order — the sort happens post-fetch.

=== Surface-name corrections (vs. a draft of this plan)

These are the real symbols this plan edits; an earlier draft named several that do not exist:

* There is *no `WalBehavior` trait*. The public surface is the `WALBehaviorWrapper` struct (`wal_behavior.rs:221`); `get_unflushed_batches` (`wal_behavior.rs:671`) and `get_collection_vectors` (`wal_behavior.rs:844`) are concrete async methods on it, reached from `WALManager` (`mod.rs:2913`). The streaming method is *additive on `WALBehaviorWrapper` + a `WALManager` passthrough*, not a trait default-impl.
* The memtable file is `src/storage/memtable/implementations/global_partitioned.rs` (not `.../specialized/...`). `get_unflushed_batches` lives on the wrapper / its internal `batch_coordinator`, not on `GlobalPartitionedMemtable`.
* `CollectionPartition` (global_partitioned.rs:94) tracks only `timestamp` / `created_at` (`SystemTime`) — *no* `max_updated_at_ns` watermark, *no* time ordering.
* The REST entry point is the method `state.request_handlers.handle_record_scan_for_tenant(...)` (called from `src/network/rest/v2/records.rs:~2118`), not a free function in `records.rs`.
* `benches/wal_scan_pagination.rs` does not exist yet (net-new in this plan).

=== Why push-down matters

* For a 10M-record collection with `limit=100`, today's scan loads 10M records *and builds a 10M-element sorted `Vec`*, then returns 100. Push-down keeps peak resident set at ~`limit` records and skips the full sort.
* Hadoop's `next_record()` blocking ABI drives this loop per page; each cursor refill pays the full-sort + full-Vec cost.
* Spark's per-partition reader does the same.
* Cursors expire after 24h (`SCAN_CURSOR_MAX_AGE_NS`, scan_cursor.rs:22) — long-running batch reads currently risk a re-walk against shifting state.

== Design

=== Phase 1 — streaming (heap-bounded) surface on `WALBehaviorWrapper`

Add an additive method on `WALBehaviorWrapper`, plus a thin `WALManager` passthrough (mirroring `get_collection_vectors`):

[source,rust]
----
// WALBehaviorWrapper (wal_behavior.rs) and WALManager (mod.rs)
pub async fn stream_unflushed_records(
    &self,
    collection_id: &str,
    cursor: Option<&ScanCursor>,
    limit: usize,
) -> Result<Vec<ProximaRecord>>;   // returns AT MOST `limit` records, already in (updated_at_ns, oid) order
----

Implementation contract (bounded-heap selection — the achievable win):

1. Acquire the collection's `CollectionPartition` and iterate its `wal_batches` (each `WALVectorBatch.vector_records: Vec<ProximaRecord>`). This is an O(N) visit; there is no time index to skip into.
2. Maintain a *max-heap of size ≤ `limit`* keyed by `(updated_at_ns, oid)`:
   * skip any record `≤` the cursor tuple (strictly-greater-than semantics, matching `apply_scan_cursor`);
   * push surviving records; when the heap exceeds `limit`, pop the current max.
3. Drain the heap and sort ascending → the page (≤ `limit` records, in canonical order).
4. Peak extra memory is O(limit); no full sorted `Vec<ProximaRecord>` is ever built.

The legacy `get_collection_vectors` / `get_unflushed_batches` stay unchanged (still used by flush, recovery, replay). The new method is purely additive.

=== Phase 2 — `VectorOperationsService` and downstream wiring

Add `scan_records_paginated` to `VectorOperationsService` (legacy.rs) that takes `(cursor, limit, include_vector, include_props, tenant_context)`, reuses tenant-context resolution, calls `WALManager::stream_unflushed_records`, then strips `embedding`/`props` per flags. Legacy `scan_records_with_tenant_context` stays for non-paginated callers (audit/recovery).

Split `apply_scan_cursor` (scan_cursor.rs) into two pure fns so the pushed path does not re-sort:

* `select_page(records, cursor, limit) -> Vec<ProximaRecord>` — the sort+filter+take body, used *only* by the legacy non-pushed path.
* `derive_next_cursor(page: &[ProximaRecord], limit, collection_id, now_ns) -> Option<ScanCursor>` — the existing "emit a cursor only when the page is full" logic, called by *both* paths.

The pushed path: WAL returns an already-ordered ≤`limit` page → service calls only `derive_next_cursor`. The `(page, next_cursor)` return shape is unchanged. `apply_scan_cursor` is retained as a thin wrapper (`select_page` + `derive_next_cursor`) for the legacy path.

=== Phase 3 — wire the two entry points

* `EmbeddedProximaDB::scan_records` (embedded/mod.rs:2023, today → `scan_records_with_tenant_context`) → route to `scan_records_paginated`.
* `state.request_handlers.handle_record_scan_for_tenant` (the method invoked from rest/v2/records.rs:~2118) → route to `scan_records_paginated`.

All four connectors (DuckDB / Hadoop / Trino / Spark JNI) funnel through one of these two entry points, so all benefit automatically.

== Out of scope

[[followup]]
== Follow-up: TD-099(3d) — time-ordered memtable index (separately gated)

The asymptotic O(log N + limit) *seek* this plan does NOT deliver requires a real change to the memtable partition: maintain a time-ordered index — e.g. `BTreeMap<(updated_at_ns, oid), batch_ref>` (or a skiplist) on `CollectionPartition` — updated on every `add_batch`, so a cursor scan can `range((cursor, ..)).take(limit)` without visiting older records. This is a Convergence-Gated design item (it adds durable in-memory structure and write-path cost) and must be proposed on its own with `authority_mode` / write-amplification analysis. It is intentionally split out so TD-099(3c) can ship the low-risk memory/sort win first.

== Convergence summary (Convergence Gate)

* *New abstraction declared:* one additive method `stream_unflushed_records` on the existing `WALBehaviorWrapper` (+ `WALManager` passthrough). No new trait, struct, endpoint, planner, or storage path is introduced — it converges on the existing WAL memtable surface and the existing `ScanCursor` codec.
* `apply_scan_cursor` is refactored into two pure fns (`select_page` + `derive_next_cursor`) within `src/services/scan_cursor.rs`; the cursor codec stays single-source-of-truth there.
* All four connectors (DuckDB / Hadoop / Trino / Spark JNI) automatically benefit — they all funnel through `EmbeddedProximaDB::scan_records` or `request_handlers.handle_record_scan_for_tenant`, both of which migrate to the paginated surface.
* The asymptotic-seek work that would touch durable memtable structure is *deferred* to TD-099(3d) under its own gate, keeping this slice free of hidden write-path coupling.
