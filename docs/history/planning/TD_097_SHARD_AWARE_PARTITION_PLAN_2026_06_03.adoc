* `docs/12-design/COMPETITIVE_OLTP_OLAP_MPP_TRAJECTORY_2026_05_20.adoc`

* `docs/12-design/adr/ADR-004-unified-explain-contract.adoc` requires route

Therefore the objective is no longer "make Spark partition planning smarter" in
isolation. The objective is: build one split-aware read contract that feeds
DataFusion local/pseudo-distributed execution, embedded notebook scans, Arrow
Flight tickets, and the Spark JNI connector. Spark is an external/Beta consumer
of this seam, not the canonical execution engine.
====

== Vision

ProximaDB read parallelism should come from a shared, catalog-aware split
contract:

* xCatalog and the route planner decide whether a read is safe, fresh enough,
  and policy-compliant.
* A `RoutedReadPlan` (read-side sibling of the existing write
  `RoutedExecutionPlan`) records compute route, split count, pushed/residual
  predicates, authority mode, policy boundary, freshness SLA, and rejected
  routes for ADR-004 EXPLAIN.
* `SplitSource` emits `FileSplit` values with `SplitStatistics` and locality
  hints.
* `SplitPlanner` groups those splits into partitions for the selected backend.
* Leaf readers execute typed splits directly without per-row route
  recomputation.

The same split generator must serve DataFusion `ProximaScanExec`, Spark
`SparkInputPartition`, notebook Arrow readers, and future Arrow Flight split
tickets. No connector gets its own parallel-scan truth.

== Objective

Replace `EmbeddedProximaDB::plan_partitions`'s one
`FileSplit::whole_collection(collection)` fallback with a shared split-generation
path, while preserving the fallback whenever metadata or safety guards are
missing.

Success means:

* DataFusion and Spark consume the same `FileSplit` inventory.
* Split pruning uses canonical `FilterExpression`/DataFusion predicate lowering
  and `SplitStatistics`; unsupported predicates remain residual.
* Live reads do not double-count or gap records across partitions.
* Policy and tenant/RLS predicates are applied before data leaves the ProximaDB
  policy boundary.
* EXPLAIN shows selected route, partition count, split type, pushed/residual
  predicates, freshness state, and rejected split/route reasons.

== Non-Objectives

* Do not claim distributed execution maturity. Multi-split local execution is
  not a multi-node cluster.
* Do not make Spark the primary MPP route. Spark remains a Beta/external
  connector consumer.
* Do not add a connector-local `ScanFilter` or encode policy semantics only in a
  `collection://...?shard=...` string.
* Do not route per row or per record batch. Route once per plan/fragment/split.
* Do not create new durable authority, WAL semantics, or catalog state for
  splits.

`FileSplit`, `SplitStatistics`, `SplitLocality`, `SplitGenerator`, and

The existing write-side `RoutedExecutionPlan` and `ComputeBackend` are real for

notebook/DataFusion blueprint.

Fallback order:

. Segment-backed splits when engine/catalog metadata is present (row groups,

. Pinned cursor-range splits only when a stable read snapshot/range contract is
  available.
. `FileSplit::whole_collection` when split metadata or safety guards are absent.

== LLD Seams

=== Seam A: `SplitSource`

Add an opt-in split source in storage-common rather than forcing every
`UnifiedStorageEngine` implementation to grow a method at once.

[source,rust]
----
pub struct SplitRequest<'a> {
    pub collection: &'a str,
    pub target_partitions: usize,
    pub filter: Option<&'a FilterExpression>,
    pub snapshot: SnapshotRef,
    pub require_policy_enforced: bool,
}

#[async_trait::async_trait]
pub trait SplitSource: Send + Sync {
    async fn generate_splits(&self, request: SplitRequest<'_>) -> anyhow::Result<Vec<FileSplit>>;
}
----

The exact module/type names can evolve with the DataFusion blueprint, but the
ownership rule is fixed: split generation is a shared storage/query seam, not a
Spark connector helper.

=== Seam B: Split Types

Use existing `FileSplit` constructors where possible:

* `RowGroup` for VIPER/NOVA/RAPTOR Parquet row groups.
* `Block` for SST/PAX blocks when block metadata is available.
* `HilbertRange`, `SuperBlock`, and `ZOrderRange` where engines already expose
  such metadata.
* `ByteRange` only for real byte ranges or the current whole-collection
  fallback.

Add a `CursorRange` split only after defining a pinned-range contract:

[source,rust]
----
CursorRange {
    start: Option<ScanCursor>,
    end: Option<ScanCursor>,
    snapshot: SnapshotRef,
}
----

TD-099(3d)'s scan index makes range seeking cheap once warm, but it does not by
itself make parallel live cursor ranges safe under concurrent writes. Cursor
ranges require one of:

* a pinned snapshot/branch;
* immutable flushed segment inventory;
* or a read epoch that freezes the split boundary for the query.

Without one of those guards, fall back to the single whole-collection split.

=== Seam C: Reader Contract

Readers consume typed split metadata, not connector-local strings. The
`collection://` URI can remain a compatibility serialization format for Spark
JSON, but the Rust-side reader should parse it immediately into a typed split
plan and reject unknown split attributes explicitly.

Reader execution rules:

* tenant/RLS predicates are part of the pushed predicate before the limit;
* unsupported predicates are residual and must be visible in EXPLAIN;
* each split owns a disjoint range, row group, block, or segment inventory;
* a split reader must not silently broaden to whole-collection scan unless the
  routed plan records that fallback.

=== Seam D: `RoutedReadPlan` / EXPLAIN

Before split-aware reads become default-routable, define a read-side route plan
with at least:

* `compute_route`: `Native`, `DataFusionLocal`, `DataFusionDistributed`,
  `ExternalDelegated("spark")`, etc.
* `authority_mode`, `policy_boundary`, `freshness_sla`;
* `split_strategy`: `Segment`, `CursorRange`, `WholeCollection`;
* `partition_count`, estimated rows/bytes, and stats freshness;
* pushed filters, residual filters, and rejected pushdowns;
* rejected routes/split strategies with concrete reasons.

This is the read equivalent of the existing write `RoutedExecutionPlan` and is
governed by ADR-004.

== Out of Scope

* JVM DataSource V2 `SupportsPushDownFilters` and residual-filter reporting.
* Gradle/JUnit migration for the Spark smoke harness.
* Multi-node worker scheduling and shuffle.
* Claiming Spark, SQL parity, or distributed execution as supported v0.2
  surfaces.
* External-authoritative open-table commits.

== Convergence Summary

* Split generation is a shared storage/query seam; Spark is only a consumer.
* xCatalog and routed read plans own authority, freshness, policy, route, and
  maturity decisions.
* `FileSplit` / `SplitPlanner` remain the common parallel-read physical
  contract.
* `scan_records_filtered` remains the canonical cursor-paginated record scan
  path until segment-native readers are wired.
* All fallback and rejection decisions must be visible in unified EXPLAIN.
