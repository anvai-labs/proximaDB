== Context

TD-097(5) shipped the CI smoke job `spark-jni-smoke` and TD-097(3) shipped 13 real-data checks in `NativeProximaDBTest.java`. The harness today is a plain `public static void main(...)` with a hand-rolled `ThrowingCheck` interface and `assertContains` helper, compiled via `javac` and run via `java` from `run-smoke.sh`.

TD-097 M3 also added `crates/binding/proximadb-spark-jni/tests/cross_process_smoke.sh`, which proves a second JVM cannot initialize concurrently against the same exclusive embedded data dir and a later JVM can initialize after release. Gradle/JUnit may wrap that smoke later, but it does not need to rediscover the lifecycle contract.

This plan migrates the harness to Gradle + JUnit 5 to (a) get per-test reporting, (b) align with the existing Maven `clients/java-embedded` module, (c) make per-method conformance assertions trivial to author and discover.

== Design

=== Why Gradle, not Maven

* Maven is already used by `clients/java-embedded` — using Gradle here is a small divergence, but Gradle is the Spark-ecosystem norm (Apache Spark itself uses SBT; Spark connector projects overwhelmingly use Gradle).
* Gradle's incremental-test cache speeds CI vs Maven's all-or-nothing test phase.
* Gradle has first-class `gradle-toolchain` support for JDK 17 pinning regardless of CI host JDK.

If the team prefers consistency, swap to Maven — the rest of this plan applies with `pom.xml` instead of `build.gradle.kts`. Effort delta is small (~30 LOC of build config).

Why split `NativeProximaDB.java` into `src/main`: it's a production class (the JNI shim), not test code. JUnit 5 tests in `src/test` reference it via project classpath.

=== `build.gradle.kts` shape

[source,kotlin]
----
plugins {
    java
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

repositories { mavenCentral() }

dependencies {
    testImplementation(platform("org.junit:junit-bom:5.10.2"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testImplementation("org.assertj:assertj-core:3.25.3")
}

tasks.test {
    useJUnitPlatform()
    systemProperty("java.library.path", findProperty("native.library.path") ?: "${rootDir}/../../../target/debug")
    // run-smoke.sh sets -Pnative.library.path to the cargo build output
    testLogging {
        events("passed", "failed", "skipped")
        showStandardStreams = true
    }
}

tasks.register<Exec>("cargoBuild") {
    workingDir = file("${rootDir}/../../..")
    commandLine("cargo", "build", "-p", "proximadb-spark-jni")
}

tasks.test { dependsOn("cargoBuild") }
----

=== Per-method conformance tests

Five test classes group the 10 JNI methods by lifecycle phase:

1. **`NativeProximaDBInitializeTest`** (3 methods): `initialize_returns_true_on_first_call`, `initialize_returns_false_on_second_call_with_different_dir`, `initialize_with_empty_string_returns_false`.

2. **`NativeProximaDBPartitionPlanningTest`** (4 methods): `get_table_schema_returns_non_empty_json`, `get_table_schema_for_unknown_collection_returns_error_envelope`, `plan_input_partitions_returns_non_empty_array`, `plan_input_partitions_for_unknown_collection_returns_error_envelope`.

3. **`NativeProximaDBPartitionReaderTest`** (4 methods): `create_partition_reader_with_invalid_json_throws`, `read_next_batch_on_uninitialized_handle_throws`, `close_partition_reader_with_zero_handle_no_op`, `read_next_batch_returns_empty_when_finished`.

4. **`NativeProximaDBWriterTest`** (4 methods): `create_data_writer_returns_non_zero_handle`, `write_batch_with_uninitialized_handle_throws`, `commit_writer_returns_non_empty_json`, `abort_writer_releases_handle`.

5. **`NativeProximaDBSmokeRoundTripTest`** (1 method, the existing e2e): `write_then_read_round_trip_yields_distinct_oids_across_pages`.

Total: 16 `@Test` methods, replacing the 13 hand-rolled main()-checks with proper test isolation, per-test temp dirs (`@TempDir`), and AssertJ fluent assertions.

=== JNI initialize lifecycle across test classes

Critical complexity: `EMBEDDED: OnceLock<Arc<EmbeddedProximaDB>>` is **set-once-strict** — JUnit can't reset it. Two options:

* **Option A (recommended for v1):** Each test class uses a JVM fork (`forkEvery = 1` in `tasks.test`). One DB per test class, ~10× test runtime but bulletproof isolation.
* **Option B (follow-up):** Add a `Java_*_test_reset()` JNI entry point gated by `#[cfg(any(test, feature="testing"))]` that swaps the OnceLock for a single-test fixture. Faster but introduces a test-only JNI surface.

Take Option A in this plan; track Option B as a follow-up TD.

=== Slice B — Migrate 13 main() checks to 16 `@Test` methods across 5 classes (1 commit)

Critical files: the 5 test classes + `support/EmbeddedFixture.java` + `support/JniLibrary.java`.

`support/JniLibrary.java` loads the cdylib via `System.load(...)` resolving from `java.library.path`.
`support/EmbeddedFixture.java` exposes a `static initializeOnceForJvm()` that calls `NativeProximaDB.initialize(tempDir)` with a fresh `@TempDir` per JVM (Option A: one JVM per class).

Delete `NativeProximaDBTest.java` (the old main()).

== Out of scope

* Maven alternative path (call out in the plan; if the team prefers Maven for repo consistency, swap `build.gradle.kts`/`settings.gradle.kts` for `pom.xml` — design unchanged).
* Test-only JNI `_reset()` entry point (Option B; a follow-up TD for test runtime perf).
* IDE-specific config files (let users import via Gradle).
* Spark version matrix (`spark.dependencies.compileOnly` adding `org.apache.spark:spark-sql_2.13`) — separate plan; this plan is harness-only.
* DataFusion/notebook split-aware read planning — separate canonical plan; this harness consumes that contract only after it exists.
* Coverage tooling (JaCoCo) — separate plan.
* Publishing artifacts to Maven Central — out of scope for the smoke harness.

== Convergence summary (Convergence Gate)

* No new JNI surface area (uses existing 10 `Java_*` methods).
* No new Rust code — Slice A/B/C/D are entirely build-config and Java-side test reshape.
* CI smoke job stays as one job; output shape becomes richer (per-test pass/fail reports).
* Aligns with team's Java 17 guidance (`docs/_internal/roadmap/implementation/114-121-sdk-development-guide.adoc`).
