[IMPORTANT]
.AS-BUILT (supersedes the design below)
====
Implemented 2026-06-03 across 5 commits (`b01605042` A, `a2f292901` B, `9b3143157` C, `d13d4f2c6` D, + E). Two deviations from this plan, both deliberate:

. *No decision gate / not incrementally maintained.* This plan proposed a write-path-maintained `BTreeMap` updated on every insert/flush (Slice A gate first). The discovery that the read path *must* MVCC-dedup + TTL-filter (an O(distinct) pass) made incremental maintenance under flush a minefield (latest-unflushed-per-oid repointing). The as-built is instead a *lazy-rebuild cache*: `CollectionPartition.scan_index: Option<ScanIndex>`, **invalidated on every mutation** and **rebuilt on the next read from the authoritative `get_all_vectors` logic**. This dissolves the maintenance problem (parity is automatic) and delivers the same O(log d + limit) per-page win for the dominant pattern — draining many pages between writes. Mixed read+write degrades gracefully to today's O(N)/page, never worse. No gate was needed because the cache is always correct and its overhead is O(distinct *locators*), small.

. *3c was not separately shipped.* The O(distinct) dedup floor means the original 3c bounded-heap couldn't lower peak memory, so 3c folded into this work rather than landing first.

Other as-built specifics: storage takes the raw `(last_updated_at_ns, last_oid)` `after` tuple (not `ScanCursor`); the tenant predicate is pushed INTO the range scan before the limit (multi-tenant correctness); empty-oid partitions fall back to the legacy full scan; operational kill-switch `PROXIMADB_SCAN_INDEX_DISABLE=1`. The Convergence Gate table below holds as-built (derived/non-authoritative projection, synchronous freshness, rebuilt from `wal_batches`). The design sections below are retained for historical context; where they describe incremental `BTreeMap` maintenance or the Slice A gate, the as-built lazy cache supersedes them.
====

== Context

TD-099(3c) (`TD_099_3C_WAL_SCAN_PUSHDOWN_PLAN_2026_06_03.adoc`) proposed a *low-risk* bounded-heap half of WAL scan push-down: lower per-page sort work without improving *record visits / wall-clock*, which would stay O(collection_size) per page. That design was not shipped separately; the MVCC/TTL discovery described above folded the work into this TD-099(3d) lazy scan-index implementation.

The reason is structural (see memory `[[project-wal-memtable-no-time-index-2026-06-03]]`): the unflushed memtable is *one partition per collection* (`GlobalPartitionedMemtable.collections: HashMap<collection_id, CollectionPartition>`, `src/storage/memtable/implementations/global_partitioned.rs:612`), and within a partition records live in an *unordered* `wal_batches: HashMap<batch_id, WALVectorBatch>` (struct at global_partitioned.rs:94) with no timestamp ordering. The canonical scan order `(updated_at_ns, oid)` is materialized only at query time.

This plan adds an in-memory time-ordered index on the partition so a cursor scan becomes `index.range((cursor, ..)).take(limit)` — **O(log N + limit)** seek, no full-collection visit.

[IMPORTANT]
====
*This is design-gated, not a foregone conclusion.* The O(N) per-page visit is only a real cost when a collection accumulates a *large unflushed backlog*. In steady state the WAL flushes the memtable to the storage engine periodically, so the unflushed N is normally small and TD-099(3c)'s memory/sort win already suffices. *Slice A is a decision gate*: instrument the live unflushed-set size distribution; proceed to build the index only if P99 unflushed N is large enough to justify the write-path cost. Otherwise close this TD as won't-fix with 3c declared sufficient.
====

== Convergence Gate declarations (required before default enablement)

[cols="1,3"]
|===
| Field | Value

| Canonical surface
| Extends the existing `CollectionPartition` (`global_partitioned.rs`) and the additive `WALBehaviorWrapper::stream_unflushed_records` introduced in 3c. *No new struct/trait/endpoint/engine.* The index is a private field + maintenance calls at existing mutation sites.

| `authority_mode`
| *Derived / non-authoritative.* The index is a pure in-memory *projection* of `wal_batches`. It holds no durable authority and is never serialized.

| Repair source
| Rebuilt deterministically from the batch set. On process start / WAL recovery, `add_batch` is replayed (the same path that populates `wal_batches`), so the index reconstructs for free — *no durable format change, no migration*.

| `freshness`
| Synchronously consistent. The index is mutated under the *same* `RwLock` as `wal_batches`, in the same critical section as every insert/flag-flush/remove. No staleness window.

| `policy_boundary`
| Unchanged. No new RLS/tenant surface — scan still goes through `validate_tenant_collection_access` in `VectorOperationsService` (3c, legacy.rs).

| Write-amplification
| Each `add_batch` of B records does O(B log N) BTreeMap inserts; each mark-flushed/remove does O(B log N) removes. Per-record memory overhead ≈ `(i64 key + oid String + (CompactBatchId, u32) value)`. *Measured and gated in Slice D* — this is the main cost and the reason for the Slice A gate.

| Maturity
| Behind a per-collection size threshold (default-off until Slice D bench justifies a default-on threshold). Falls back to the 3c heap path when the index is absent.
|===

== Design

=== The index

Add a private field to `CollectionPartition` (global_partitioned.rs:94):

[source,rust]
----
/// Time-ordered index over UNFLUSHED records only: (updated_at_ns, oid) -> location.
/// In-memory projection of `wal_batches`; rebuilt on replay; never serialized.
/// Present only when the partition crosses the push-down size threshold.
time_index: Option<BTreeMap<(i64, String), (CompactBatchId, u32)>>,
----

* Key `(updated_at_ns, oid)` is exactly the canonical scan tuple, so `range((last_updated_at_ns, last_oid).. )` + `.take(limit)` yields the next page directly, no sort.
* Value `(CompactBatchId, u32)` locates the physical record (batch + index into `WALVectorBatch.vector_records`) without duplicating the `ProximaRecord`.
* *Unflushed-only invariant:* the index contains an entry **iff** the owning batch is present AND `!is_flushed`. This is what preserves the O(log N + limit) bound — a tail of flushed-but-uncleared batches never consumes the `limit` budget.

=== Maintenance sites (all already exist; index updated in the same critical section)

[cols="1,2,2"]
|===
| Event | Site (global_partitioned.rs) | Index action

| Insert
| `CollectionPartition::add_batch` (~234, `wal_batches.insert`)
| For each record, `time_index.insert((updated_at_ns, oid.clone()), (batch_id, idx))`.

| Mark flushed
| `values_mut().is_flushed = true` (~1123, ~1313)
| Remove the batch's records from `time_index` (they leave the unflushed set).

| Clear flushed
| `clear_flushed` (~313, removes flushed batches ~326)
| No-op for the index (entries already removed at mark-flushed) — assert-only in debug.

| Remove batch
| `remove_batch` (~1131) / `clear_flushed` row removal
| Remove the batch's records from `time_index`.
|===

=== Read path

`WALBehaviorWrapper::stream_unflushed_records` (added in 3c):

* *Index present* → `time_index.range((cursor_tuple, Unbounded)).take(limit)`, resolve each `(batch_id, idx)` to a `ProximaRecord` (clone/Arc per include-flags). O(log N + limit).
* *Index absent* → existing 3c bounded-heap path. O(N) visit, O(limit) memory.

The two paths return identical pages, so 3c's tests are the parity oracle.

=== Open design questions (resolve in Slice B)

1. *Duplicate (oid, version) semantics.* An oid can appear in multiple unflushed batches (old + new version before dedup/flush). The 3c streaming path does **not** dedup (it mirrors `apply_scan_cursor`, scan_cursor.rs, which sorts all physical records). Keying on `(updated_at_ns, oid)` is collision-free per physical version, so the index naturally preserves this. *Decision: match 3c exactly — no dedup in the index path.* If product wants latest-only scan semantics, that is a separate change applied to *both* paths.
2. *Concurrency primitive.* `BTreeMap` under the partition's existing `RwLock` (chosen — converges on the current locking model). *Rejected:* `crossbeam_skiplist` lock-free map — adds a new concurrency primitive for no benefit given the partition is already coarse-locked.
3. *Memory ceiling / eviction.* If a single collection's unflushed backlog is pathological, the index could dominate. Slice D decides whether to cap (e.g. disable index above a hard ceiling and revert to heap) — gated on measured overhead.

== Slices (4 commits)

=== Slice A — DECISION GATE: instrument unflushed-set size (1 commit)

Critical files:

* `src/storage/memtable/implementations/global_partitioned.rs` — emit a per-collection gauge of *unflushed record count* (derivable from `vector_count` minus flushed) on flush boundaries.
* Prometheus surface (existing metrics module) — `proximadb_wal_unflushed_records{collection}`.

Exit criteria: gather the distribution under representative load (connector batch ingest + flush cadence). **If P99 unflushed N is small** (heap visit cost negligible vs. page-fetch + network), **STOP — close TD-099(3d) won't-fix, 3c is sufficient.** Only if P99 N is large does the index pay off; proceed to Slice B. Record the decision + the numbers in `docs/10-quality/TECHNICAL_DEBT.adoc`.

TDD: a test asserting the gauge tracks insert/flush transitions correctly.

=== Slice B — `time_index` field + synchronous maintenance (1 commit)

Critical file: `src/storage/memtable/implementations/global_partitioned.rs`.

Adds the `Option<BTreeMap<...>>` field and the four maintenance hooks; index materializes when the partition crosses the size threshold (config knob, default off). Resolve the three open design questions above.

TDD (the load-bearing invariant tests):

* `index_matches_wal_batches_after_inserts` — index entries == unflushed records, exactly.
* `index_drops_entries_on_mark_flushed` — flushing a batch removes its keys.
* `index_drops_entries_on_remove_batch`.
* `index_consistent_after_interleaved_insert_flush_remove` — randomized sequence; assert `index ⇔ {unflushed records}` invariant at the end (this is the correctness crux).
* `index_handles_duplicate_oid_distinct_updated_at` — two versions of one oid both present (no-dedup parity).

=== Slice C — range-seek read path + heap fallback (1 commit)

Critical file: `src/storage/memtable/specialized/wal_behavior.rs` (`stream_unflushed_records`).

Use `time_index.range(...).take(limit)` when present; fall back to the 3c heap when absent.

TDD:

* `stream_index_path_equals_heap_path` — same collection, same cursor/limit, assert *byte-identical pages* from both paths (parity against 3c as oracle).
* `stream_index_path_visits_at_most_limit_plus_logn` — counting fixture asserts the index path resolves ≤ `limit` records (the asymptotic win that the 3c heap path could NOT make).

=== Slice D — bench, threshold tuning, default-on decision, close-out (1 commit)

Critical files:

* `benches/wal_scan_pagination.rs` (extend the 3c bench) — add an index-on variant: 1M unflushed records, cursor near tail, `limit=100`.
  ** assert record-visits ≈ `limit` (NOT O(N)) — the genuine O(log N + limit) claim, valid *only here*;
  ** measure index *memory overhead* (bytes/record) and *insert write-amp* (added latency per `add_batch`).
* `docs/10-quality/TECHNICAL_DEBT.adoc` — set the default-on size threshold from the bench, or keep default-off if write-amp/memory outweigh the gain at realistic N; mark TD-099(3d) DONE with the decision + commit refs.

== Out of scope

* Flushed-segment (on-disk) scan seek — storage engines own their own predicate plumbing.
* `branch_id` predicate push-down (TD-072 follow-up).
* Latest-only / dedup scan semantics — would change BOTH the 3c and index paths; separate product decision.
* Durable/serialized form of the index — it stays an in-memory projection; recovery rebuilds it via `add_batch` replay.
