= ADR-097 P2.4 exit gate — TPC-DS load + MATERIALIZE memory (2026-10-23)
:toc: left
:icons: font
// status-as-of: 2026-10-24

[.lead]
The P2.4 gate is "TPC-DS SF1 loads on a release build without OOM, peak RSS recorded"
(TD-SEAM-4). **It passes (2026-10-24)** with two load-path fixes: per-segment key filters
(link:../../10-quality/td/TD-USUB-21-insert-existence-probe-decodes-every-spill-segment.adoc[TD-USUB-21])
and the lag flush that lets small tables stop pinning WAL truncation
(link:../../10-quality/td/TD-USUB-22-an-unflushed-small-partition-pins-wal-truncation.adoc[TD-USUB-22]).
SF1, spill on, default truncation: 5.84 M rows loaded in 1,655 s, 22/22 tables published by
MATERIALIZE in 225 s, peak RSS 10,401 MiB (load) and 10,773 MiB (MATERIALIZE) inside a 13,677 MiB
cgroup, no OOM, peak temp data 4.8 GB. The sections after "SF1 gate run" record the 2026-10-23 runs
on develop before the fixes.

== SF1 gate run (2026-10-24): passed

           + TD-USUB-22 (p24-wal-lag-flush @ 7d83d254a), merged as local-gate-combined @ 4421f1bc2

           TPC_PERF_ALLOW_LARGE_SCALE=I_ACCEPT_ISOLATED_OOM TPC_PERF_HOST_HEADROOM_MIB=2048
           MALLOC_ARENA_MAX=2; spill, rotation and truncation at their defaults
           (65,536 resident rows, 64 MiB WAL segments, 300 s truncation interval,
           1,000,000-entry retention and flush lag)
----

Reading:

* The fact tables load at 41–54 ms per 200-row batch. The two keyed tables past the spill
  threshold, `customer` and `customer_address`, take 600 ms and 265 ms per batch: 434 s of the
  1,655 s. Not profiled; the likely cause is that a keyed row is probed twice (the key-constraint
  lookup as well as the existence check) and that a keyed segment's range check never excludes
  (an INT key is a decimal string, so each segment spans the whole domain), leaving only the Bloom
  filter. Not a gate blocker; worth a profile.
* `MALLOC_ARENA_MAX=2` is set because glibc's per-thread arenas keep freed flush buffers: SF 0.1
  with spill on peaked at 12,251 MiB with the default arenas and 8,021 MiB with two. Without it SF1
  may not fit this cgroup. A server deployment should set it, or the binary should use an
  allocator that returns memory (follow-up).
* With spill on, RSS still exceeds the spill-off run at the same scale: at SF 0.1, 9,336 MiB (load
  peak, two arenas, truncation every 20 s with 100,000-entry retention and lag) against 6,992 MiB
  spill off. The resident rows are bounded, so the difference is flush and allocator working
  memory rather than data; at SF1 the load phase peaked at 10,401 MiB.

== Setup

----
 commit    develop @ 6d71e9e83 + the per-table timing change in this PR
 build     cargo test --release (opt-level 3, thin LTO), CARGO_BUILD_JOBS=2
 host      4 vCPU, 15.7 GiB RAM, 8 GiB swap; cgroup v1 memory.limit_in_bytes = 13,677 MiB
 harness   tests/tpc_perf_ledger_e2e.rs, TPC_PERF_BENCHMARK=tpcds TPC_PERF_LOAD_ONLY=1
           (load over pgwire, parallelism 1, then ALTER TABLE … MATERIALIZE per table)
 scale>0.05 also TPC_PERF_ALLOW_LARGE_SCALE=I_ACCEPT_ISOLATED_OOM TPC_PERF_HOST_HEADROOM_MIB=2048
 memory    per phase: VmHWM (reset via /proc/self/clear_refs) and the cgroup v1 peak
           (memory.max_usage_in_bytes, reset per phase); whole run: VmHWM sampled every 5 s
----

`scripts/run_tpc_perf_ledger.sh` needs systemd and cgroup v2; this host has neither, so the
runs used the shell's existing cgroup v1 limit of 13,677 MiB (13.4 GiB), which leaves 2.4 GiB
of the host's 15.7 GiB. The cgroup peak includes page cache, so it reaches the limit without an
OOM kill; VmHWM is the process's peak RSS.

Row counts below are the generator's (`scaled(…)` in the harness; they match the INSERT batch
counts exactly): 61,187 rows at SF 0.01, 586,787 at SF 0.1, 1,170,787 at SF 0.2, 5,842,787 at
SF1. `store_sales` is 28,800 rows at SF 0.01 and 288,000 at SF 0.1.

== Results

=== Spill on

A partition flushes its memtable to a segment when resident rows reach the threshold, default
65,536.

[cols="1,1,1,3",options="header"]
|===
| Scale | Spill threshold | Load wall | Note
| 0.01 | 65,536 (default) | 6.7 s | no table reaches the threshold, so nothing spills
| 0.01 | 16,384 | **1,746 s** (29.1 min) | only `store_sales` spills: one 16,384-row segment, then each of the remaining 12,416 rows decodes it. **257×** the spill-off load (6.8 s); ≈ 8.6 µs per decoded row
| 0.1 | 65,536 (default) | stopped at 712 s, load unfinished | `top` showed the process at 100 % of one core; 4 of 4 gdb samples of the busy thread inside `SpillRecordStorage::get_record` → `read_segment`
|===

The 16,384 run went on to publish all 22 tables (`store_sales` in 879 ms from its segment plus
memtable) with MATERIALIZE peaking at 4,175 MiB against the load phase's 3,910 MiB (+265 MiB).

A run at 4,096 panicked 15 s in on a missing `store_sales` segment file. It started when the
16,384 run was killed, and a `find /tmp -name '.tmp*' -exec rm -rf` cleanup ran while it was
starting; the sampled `/tmp` usage drops 168 → 150 MiB between 10 s and 15 s, consistent with that
cleanup removing its data directory. Rerun at the same setting with a 240 s timeout, it ran to the
timeout with no panic, and two `store_sales` segment files were on disk afterwards.

== Reading

* **MATERIALIZE's peak stayed 0.2–0.4 GiB above the load peak** while the data grew 19×
  (spill off, SF 0.01 → 0.2), consistent with the P2.4 design (chunked scan, sort under a capped
  pool, multipart part writer). Δ is MATERIALIZE peak minus load peak, so it understates growth
  over the RSS at MATERIALIZE start. Over spilled segments it was measured once (one 16,384-row
  segment, +265 MiB); the SF1 rerun is the real test of that path.
* **Load is the blocker.**
  . With spill on, every INSERT probes for an existing row, and a memtable miss reads and decodes
    every spill segment whole (TD-USUB-21), so loading `n` rows decodes about `n²/2` rows. That
    code is the P2.2 spill path (default on since 2026-10-22, `c62ab32b7`), not P2.4's.
  . With spill off, the memtable holds every row (≈ 6.4 KiB each).
* **The ≈ 3.3 GiB baseline**: the SF 0.1 spill-off run was at 3,467 MiB RSS 5 s into a 61 s load.
  It is not explained here; it bounds how small a host can run the gate at all.

== What it took to close the gate (2026-10-23 plan)

Fix TD-USUB-21, then run SF1 with spill on:

----
TPC_PERF_SCALE=1 TPC_PERF_BENCHMARK=tpcds TPC_PERF_LOAD_ONLY=1 \
TPC_PERF_ALLOW_LARGE_SCALE=I_ACCEPT_ISOLATED_OOM TPC_PERF_HOST_HEADROOM_MIB=2048 \
  cargo test --release --test tpc_perf_ledger_e2e -- --ignored --nocapture
----

Disk: the spill-off runs peaked at 1.0 GiB (SF 0.1) and 2.0 GiB (SF 0.2) of temp data, so a
spill-off SF1 would need ≈ 10 GiB against the 8.8 GiB free here. With spill on the WAL is
truncated behind flushed segments (P2.2), so the SF1 run is expected to need less; measure it.
