= TD-TIER-1 SC6: first integrated MinIO release run — balanced vs admitted residency
// status-as-of: 2026-11-01

== Question

The runbook's Phase-0 exit gate: on the **release binary** against **MinIO**, does a
PERFORMANCE-granted collection serve the same recall as a balanced one, and what does
admitted residency eliminate on the payload request path? (link:../../current/TIER1_OPT_IN_ROLLOUT_RUNBOOK.adoc[runbook],
link:../../current/TIER1_SC6_COST_WORKSHEET.adoc[worksheet].)

== Protocol

* Binary: `release-server` profile, `--features aws`, source `efa9517d3` (harness
  revision `bench/sc6-release-runs` adds `--storage-class`,
  `--reservation-pool-{allocatable,grant}-gb`, and a `storage_class_status` READY gate
  that pins the status into `result.json`).
* One bed per arm (SIFT 1M fvecs, full-base GT, 1,000 REST-v2 queries per phase, top-10,
  default nprobe, `--max-segments 1`), object store = **owned MinIO** `127.0.0.1:12100`
  (bucket `sc6`), no added latency. Ingest via Flight.
* Arms differ ONLY in the class/pool knobs:
** `sc6-balanced-1m`: no pool, no class (byte-identical server config otherwise).
** `sc6-granted-1m`: `storage_class=performance`, pool 8 GiB allocatable / 4 GiB grant;
   the warm sweep runs only after `storage_class_status.state == READY`.
* n=1 per cell — directions, not distributions. Beds are independent (per-arm L0
   geometry varies slightly; cross-bed request counts are not exact contrasts).

== Result (SIFT 1M, release binary, MinIO)

[cols="1,2,2,2,2",options="header"]
|===
| Phase | Balanced GETs/q (bytes/q) | Granted GETs/q (bytes/q) | p50 bal→grant | recall@10 bal→grant
| post-write (warm DRAM) | 4.84 (11.97 MB) | **0.00 (0 B)** | 40.4→37.9 ms | 0.9847→0.9842
| restart + store (warm) | 4.95 (12.29 MB) | **0.00 (0 B)** | 70.5→65.2 ms | 0.9828→0.9827
| restart, no store (cold) | 18.22 (56.93 MB) | 17.53 (53.09 MB) | 57.3→56.9 ms | 0.9838→0.9835
|===

* **Zero payload requests on the granted arm in both warm phases** — and the warm phase
  is a full server restart: the grant re-arms at open, the backfill warms live segments,
  and the READY gate holds the sweep until coverage is proven. The ungranted arm's
  best-effort local-disk tier (same store path, no admission) still pays ~4.9 GETs/q —
  residency without admission is partial by construction.
* **Recall parity across classes** in every phase (max delta 0.0005, at the harness's
  `--max-recall-regression` tolerance): the runbook's correctness gate holds.
* Residency status at sweep time (granted): `ready` — "all 2 objects of generation
  0xf8dea49957b4d are resident and protected (profile pax-ann-v1)";
  covered = resident = 757,830,877 B; reserved 4 GiB → utilization 0.177.
* Pool ledger (`pool/reservations.json`): one grant, tenant `default`, 4 GiB
  `Reserved`, **both residency prefixes registered** (legacy `{id}/data/` and typed
  `accounts/000001/001/000001/data/`), clean ownership handoff across three server
  generations (`producer_epoch` 3). GB-month accrual inputs: 4 GiB × the run window
  (~40 min ≈ 0.0027 GiB-month); the idle-month case is the priced one.

== Disclosures

* Both arms miss the harness's default `object_cold: p50 ≤ 50 ms` gate by the same
  margin (57.31 / 56.91 ms) — a local-condition artifact versus the E1 calibration
  (MinIO on the same host, shared box), identical across arms, so the arm contrast is
  unaffected. Recorded in each `result.json` `gate_failures`.
* Cross-phase p50 is order-confounded (the cold phase runs last with OS/MinIO caches
  hot); do not read warm-vs-cold p50 as a tier effect.
* The 100k plumbing smoke (same protocol, prefix corpus against the FULL-base GT) is
  recorded as instrumentation validation only: its low recall is a GT-scope artifact,
  and its `local_disk_warm 0.0 GETs/q` + READY status first proved the chain.
* Not yet measured: added-latency arms (Toxiproxy), multi-tenant pools, tier mix (SC5
  emulator round-trip), repeats. No pricing claim rides on this run.
