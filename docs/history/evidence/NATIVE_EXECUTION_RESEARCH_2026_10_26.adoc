= Native execution differentiation: literature review and falsifiable hypotheses
:toc:
:toclevels: 2

Research date: 2026-10-26. Repository baseline: develop `2f5b1ee7d`.
Status: completed desk research; *no comparative benchmark or novel algorithm claim*.
This is a dated evidence catalog, not a second execution roadmap. Pending experiments and
contracts live in link:../../current/LAKEHOUSE_PLAN.adoc#native-execution-research[current plan];
link:../../current/TRACKER.adoc[tracker] owns assignment. Public documentation can change:
pin actual engine/extension versions and configurations in each experiment manifest.

== Recommendation

Invest in native execution where owning record visibility, index candidates, object fetches
and scheduling together eliminates work. Start with a fused multimodal retrieval pipeline,
not a second complete SQL implementation. Keep the accepted logical IR and substitute native
physical regions through ADR-097 adapters. A whole native executor becomes justified only
when measured scheduler/materialization boundaries prevent those substitutions from winning.

The proposed advantage is *governed, fresh multimodal context at predictable cost*: carry
compact record references through relational predicates, vector ranking and graph expansion;
resolve versions and authorization consistently; fetch payloads late; share a bounded resource
budget across index work, WAL reconciliation and object I/O. Each ingredient has prior art.
Their integration over ProximaDB's authoritative data is an engineering hypothesis, not a
claim to have invented filtered ANN, late materialization, HTAP or adaptive execution.

== Correct the historical model

Spark did not remove shuffle. It introduced reusable distributed datasets and a more flexible
execution graph; joins/grouping can still require redistribution, serialization and spill.
Its current SQL engine also has AQE and storage-partition joins that can avoid exchanges when
layout permits. Trino uses distributed stages, tasks, drivers and operators; it does not use
Spark RDDs. Arrow describes a
columnar interchange/memory layout, not a rule that an engine must load its dataset into RAM.
Rust does not by itself solve join skew, query admission, shuffle, bad estimates or remote I/O.

Sources: https://spark.apache.org/docs/latest/rdd-programming-guide.html[Spark RDD/shuffle guide],
https://spark.apache.org/docs/latest/sql-performance-tuning.html[Spark SQL tuning],
https://trino.io/docs/current/overview/concepts.html[Trino execution concepts],
https://datafusion.apache.org/blog/2025/09/10/dynamic-filters/[DataFusion execution and dynamic filters].

== Quickwit and ClickHouse: inspect the mechanism behind the headline

Quickwit's https://quickwit.io/docs/main-branch/overview/architecture[architecture] combines
inverted postings, columnar fast fields for aggregation and a document store in immutable
splits on object storage. Its https://quickwit.io/docs/overview/concepts/querying[query path]
prunes splits using time/tags, assigns search work for cache locality and merges results.
The documentation itself calls the distributed pattern map-reduce: the relevant distinction
is what gets read, materialized and moved, not whether a design contains a map/reduce stage.
Its split-local document IDs change across merges, which is why ProximaDB must preserve a
separate stable, versioned record identity when using a similar projection.

The https://quickwit.io/blog/benchmarking-quickwit-engine-on-an-adversarial-dataset[September 2023 benchmark]
reports sub-second simple search over a 23 TB source dataset with eight CPUs. That is an indexed
search claim, not scanning 23 TB in one second: its term query matches about 22,000 documents
and returns ten. The sub-second result uses cached split metadata; the uncached cases expose
substantial object I/O. The report separates a full-dataset date histogram from selective
queries and adjusts merge policy during indexing. Its historic prices are not current quotes.
The https://quickwit.io/blog/benchmarking-quickwit-loki[May 2024 Loki comparison] explicitly
limits compared query semantics and identifies the ingestion-versus-query cost tradeoff.
This is useful evidence about mechanisms, not a head-to-head ProximaDB performance result.

ClickHouse's https://clickhouse.com/uploads/Click_House_Schulze_1_c12ecfaed4.pdf[2024 VLDB paper]
describes sorted immutable parts, compressed columns, pruning, vectorized processing and
background transformations. Its newer
https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization[lazy materialization]
delays wide payload reads. These gains combine avoiding work with executing unavoidable work
efficiently; they are not explained by C++ alone. Physical ordering, granularity, workload,
cache preparation and maintenance must be held accountable in a comparison.

Crucially, this is *not* a search-versus-scan dichotomy. ClickHouse announced
https://clickhouse.com/blog/full-text-search-ga-release[GA inverted text indexes in March 2026],
integrated with columnar execution. Its claimed 7–10x cold-query gains are vendor-reported
comparisons with traditional approaches for the described workload, not a universal advantage
or a Quickwit comparison. Any new ProximaDB search/columnar prototype must face this current
baseline rather than an old Bloom-only ClickHouse configuration.

What our architecture should permit is a choice within one query: postings for selective
text/ID predicates, column scans for broad predicates, candidate fusion for vector/graph
work, and late payload access. It should also allow postings to feed an aggregate over selected
column values without constructing document objects first. This requires semantic capabilities,
snapshot-bound locator translation and resource ownership; an opaque execute-query plugin
or an eager MemTable boundary would lose much of the benefit. Reusing Tantivy is an option to
measure against our existing index work, not an instruction to clone Quickwit's complete service.

== Research that constrains a novelty claim

* https://www.microsoft.com/en-us/research/publication/vbase-unifying-online-vector-similarity-search-and-relational-queries-via-relaxed-monotonicity/[VBASE, OSDI 2023]: fixed top-k interfaces impede complex vector/relational execution; relaxed-monotonicity techniques support more compositional retrieval. Candidate continuation is prior art.
* https://arxiv.org/abs/2403.04871[ACORN, 2024]: predicate-aware HNSW traversal is prior art. A ProximaDB implementation needs object-store and workload evidence, not an invented name for the same filtering idea.
* https://arxiv.org/abs/2510.27141v5[Compass, September 2026 revision]: coordinated candidate generation and structured predicate evaluation across existing indexes. The abstract alone invalidates a broad claim that cooperative vector/relational execution is new; detailed algorithm reproduction remains a prototype prerequisite if we borrow it.
* https://www.vldb.org/cidrdb/papers/2026/p2-liu.pdf[PostgreSQL-V, CIDR 2026]: separating vector indexes from relational execution raises consistency obligations, and the paper describes a mechanism for them. Owning both modalities does not automatically produce coherent visibility.

No speedup reported by these papers is transferred to ProximaDB. No patentability or exhaustive
novelty search was performed. The defensible product claim must be a reproducible workload
result plus durable operational semantics, not the absence of an identical marketing phrase.

== Thought experiments and falsifiers

These are analytical experiments, not executed benchmarks. Execution definitions are in the
current plan. The point is to identify necessary contracts before investing in implementations.

. *The nearest tickets belong to ineligible customers.* Let all globally nearest 1,000 tickets
belong to active customers, while the request asks for the nearest 20 tickets of churned
customers. Taking global top-20 and joining later returns nothing. Taking top-1,000 still
fails. A relational eligibility set followed by distance ordering answers the requested query;
a resumable candidate source may also work. Fixed oversampling is not a correctness argument.
Now add one-to-many joins: top-k joined rows and top-k distinct tickets are different queries.
A generic optimizer cannot silently replace one with the other. This forces explicit candidate
semantics, cardinality and exact/approximate modes before fusion.

. *The data is the same, the payload is 100 times wider.* Add large documents/log bodies without
changing any filter or distance. A compact-ID pipeline should mostly leave predicate/search
work unchanged and fetch bodies only for surviving rows. If latency rises with total payload
width before final fetch, the pipeline materializes too early. If winners are scattered over
hundreds of objects, late fetch may lose to a sequential scan: measure that crossover instead
of asserting it away. ClickHouse/DataFusion already provide meaningful controls for this test.

. *An update arrives between ANN and hydration.* A candidate found in projection generation G
is updated or deleted before its body is read; an authorization policy also changes. A query
must use its declared read/policy boundary or fail/restart, not combine a stale score, current
body and unrelated authorization decision. An oid alone is insufficient: use versioned record
identity plus a snapshot-bound locator. Explicit emergency revocation can require aborting
in-flight queries; snapshot authorization does not grant indefinite access after revocation.

. *Ten thousand tenants wake up together.* Cache affinity works for a hot tenant but a bulk scan
can evict many small working sets. Measure queueing, object GET waves, pinned bytes, query
state, WAL-tail work and compaction together. More cache can worsen admission pressure; a
memory-only query limit misses decoded vectors, object buffers and shared resident bytes.
A cheaper request is not cheaper service if it forces idle reserved capacity for p99.

. *The graph frontier explodes.* A two-hop query from a celebrity node visits millions of edges;
from an ordinary node it visits dozens. A fixed hop-count rule is not a cost model. Decide
between indexed expansion, semi-join and scan using frontier size, fanout and locality. Keep
path multiplicity/cycle semantics distinct from reachable-node sets. Cancellation must bound
work rather than silently returning an incomplete SQL aggregate.

. *A broad aggregate defeats every index.* Uniform broad filters and high-cardinality joins
remove most selectivity benefits. ProximaDB should use a mature vectorized/spilling path or
prove its native equivalent; an indexed pipeline must not grind through random lookups when
scanning is cheaper. This is the essential negative control against benchmark cherry-picking.

. *A result looks correct only because the tail is small.* Grow unindexed writes, updates and
tombstones while holding the published snapshot fixed. Merge by record version and reconcile
both candidate search and payload visibility. When the tail overwhelms the latency budget,
admit less work, accelerate indexing or offer an explicitly chosen freshness mode; do not
silently omit it. A scan of the tail for every query may erase the economics of a cheap base.

. *A performance win disappears on the bill.* Compare broad scan, ID-first lookup and cached
plans at equal recall, freshness, durability and p99 under the same tenant mix. Include idle
capacity, object requests, bandwidth, cache media, write/compaction amplification, recovery,
replicas and maintenance. Do not equate total GET count to sequential dependency depth or
cost per query to the vendor's billed logical bytes. An 8 MiB read is not intrinsically random
or sequential; access pattern, locality and the device matter, as the storage plan records.

== Cost model and economic tests

Use measured resource demand and service constraints, rather than a universal ranking of
engine names. ADR-033's depth-first heuristic remains useful for cold remote I/O; warm
compute-bound or saturated mixed workloads require measured coefficients and queueing.

----
T_query = queue + planning + critical_path(I/O, decode, search, join, aggregate, spill)
C_service = capacity + storage + requests + transfer + writes/compaction + recovery + operations
C_per_success = C_service / successful queries meeting declared correctness/recall/freshness/SLO
----

Critical-path components overlap; do not sum all CPU and I/O elapsed times as independent
serial work. Shared capacity has to be allocated once, not charged in full to every query.
Record both marginal and fully allocated cost. Persist calibrated estimates and their error;
use conservative admission when inputs are unknown. A recall target is measured against exact
eligible-set answers on a defined dataset, not guaranteed by an ANN confidence score.

Potential pricing: durable bytes + ingestion + measured execution, with an optional resident
capacity/SLO tier only after reservation and isolation work lands (SC1–6). Test whether saved
context-assembly compute pays for ProximaDB's index and maintenance overhead. Do not promise
lower pure-vector prices than S3 Vectors or turbopuffer before representative measurements.
Their billing bases differ; use their dated calculators/API pricing alongside our actual bill,
not a conversion from physical bytes to billed bytes assumed to be universal.
Sources: https://aws.amazon.com/s3/pricing/[AWS S3 pricing],
https://turbopuffer.com/pricing[turbopuffer pricing]. No price quote is fixed by this report.

== Repository reality and reconciliation

* `src/query/compute_scheduler.rs::route_select_inner` selects DataFusion for production OLAP
  shapes, including registerable native relational tables. It is not comparison-only today.
* `src/query/execution/duckdb_engine.rs` describes the ledger baseline and an optional
  `PROXIMADB_DUCKDB_ROUTE` route. Keep comparison correctness; this research does not authorize
  expanding DuckDB's product role or tuning its internals.
* `crates/query/proximadb-execution-contracts/src/lib.rs` already defines native Arrow batch
  streams, operators, pipelines and scheduler contracts. Its operator interface does not itself
  specify a shared visibility token, candidate continuation or common memory/I/O budget.
  Extend existing contracts if an experiment requires them; do not create a competing IR.
* Native route/join/morsel gates in `src/query/execution/native_engine.rs` are default OFF.
  Existing code and old measured wins are reuse candidates, not proof of a general advantage.
* The June native blueprint/comparative study retain ADR-052-era banners. ADR-054 later reopened
  measured native operators; ADR-097 fixes the logical-IR boundary. Current planning must read
  those decisions in sequence, not restart the June proposal or treat its old code audit as current.
* P2 deletion readers are a correctness dependency of any native executor. The ongoing
  continuation found wrong DuckDB predicate composition, invalid URI mapping, pruned-row-group
  count errors, stale cache reuse and unsafe MATERIALIZE rewrite. These illustrate missing
  visibility contracts, not a reason to optimize another engine's general-purpose kernels.
