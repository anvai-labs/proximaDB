== Design correction: the fragmentation dial

The planned dial was wrong. `--max-segments` in the harness is **only the settle gate** (`wait_for_materialization`: `segment_count <= max`) — it configures nothing on the server. The scouting run proved it: a 3M corpus with `--max-segments 12` settled at **one** 741,332,209-byte segment (`e1f-sift3m-m12-build`) because the whole corpus fits the default compaction admission budget.

The real dial is `--compaction-max-memory-mb` → server config `[storage.compaction_config] max_memory_mb` → `StorageConfig::effective_sst_config()` → the compaction **admission ceiling**: `max_input_bytes = min(total×0.25, avail×0.5, max_memory_mb when > 0) / 12.0` (0 = auto — the fractions govern). Compaction is leveled — L0 holds untrained flush outputs (the TD-COMPACT-5 training arm merges whatever fits into a trained v3/A0 segment at L1+), and higher levels merge **pairs that fit** (`higher_level_file_threshold = 2`; "oversized files remain horizontal"). A settled bed is therefore stable exactly when **no pair of segments fits `max_input`** (verified on every bed: smallest pair sums 707.0/363.6/314.8 MiB vs `max_input` 500/350/250). Segment sizes are only bounded above by `max_input`; a small tail segment below `max_input/2` survives whenever no partner fits alongside it.

== Protocol

Fixed 3M corpus (the same ANN_SIFT1B learn split prefix as the 3M scale arms), fixed binary, fixed query IDs; **only the admission ceiling varies across beds** (settled segment count 1/2/3/4), and only the coalescing cap (4 → 16 MiB) varies within each bed. Per fresh point: a build run (cap 4 baseline, full phases) plus one cap16 reuse arm via `--skip-ingest` — identical objects, model and query IDs. The m1 point reuses the scouting bed as its cap4 build. **Every reuse arm passes the same `--compaction-max-memory-mb` as its build** — an arm server with the default (auto) budget would merge the settled geometry mid-measurement. Corpus and ground truth identical to the 3M scale arms (learn split disclosed there). **n=1 per cell** (exploratory, consistent with the scale arms).

== Findings

. **The cap lever collapses at first fragmentation, then plateaus.** 4 → 16 MiB cuts object-store requests **−33.1%** on the single-segment bed but only **−13.5% / −13.1% / −16.4%** on the 2/3/4-segment beds. One fragmentation step erases ~55–60% of the lever's power; beyond that the effect is flat within n=1 noise. This is the fixed-corpus, single-dial confirmation of the scale arms' inference: under segment fan-out each segment issues its own probe ranges — a per-segment request floor the coalescing cap cannot merge across. [M]
. **Segment count alone does not explain the 10M saturation.** The 10M 3-segment bed measured −5.5% (scale arms) — *below* this ladder's 3-segment rung (−13.1%) at a 3.3× smaller corpus. The second factor is probe density: at 3M the 3-segment bed probes 45 cells over 741 MB (≈60.7 cells/GB); at 10M the 3-segment bed probes 43 cells over 2.47 GB (≈17.4 cells/GB) — sparser probes leave fewer adjacent ranges for the cap to merge. Corpus size is the density variable the ladder's own data supports (within 3M, cells/q per byte *rises* with segmentation, so density does not explain the 1→2 rung drop); segment count and corpus size are not separable in the 10M comparison without a 10M fragment ladder. [M]
. **Cross-binary reproduction (parity check):** the m1 rung reproduces the e1s 3M family within n=1 noise — cap4 36.73 vs 36.342 req/q, cap16 24.56 vs 23.634, Δ −33.1% vs −34.97%, same 5→4 wave drop, recall 0.9736 vs 0.9740 — on a different binary (`48d4aaaf…` vs `11b6a8a1…`) built from a different base tree. The single-segment finding is not binary-specific. [M]
. **Cells/q co-varies with geometry, not just segment count.** Per-segment IVF cell counts scale with segment rows (3.0M→57c, 1.4–1.6M→52–58c, 0.66–0.88M→23–28c), and the directory planner's total probed cells per query came out 16 / 32 / 45 / 23.6 across the rungs — non-monotone. Absolute cross-rung request counts are therefore mediated by the probe plan and are **not** presented as a curve; the cap Δ within each rung controls it (identical probe plan within a bed). [M]
. **Warm-phase numbers are protocol-asymmetric and excluded from the cap comparison.** Build-run warm phases (`post_write`, `local_disk_warm`) run cache-hot from ingest (`PROXIMADB_CACHE_ON_WRITE=all`); reuse-arm warm phases run on a cold-boot server — visible in the e1s family too (cap4 build 10.17 req/q vs cap4 *arm* 35.56 req/q at the same cap). Only `object_cold` is protocol-comparable across build-vs-arm; it is the only phase used for the cap claims. Full per-phase values in the appendix for the record. [M]

== Non-producibility: the 6-segment rung (and the flush floor)

A 6-segment bed is **not producible** with this single-dial protocol. The m6 attempt (ceiling 1620 MB → 135 MiB `max_input`) settled at four **untrained** L0 segments and never quiesced: the measured flush outputs at 3M are **140.5 / 208.2 / 159.8 / 198.5 MiB** (flush outputs 140.5–208.2 MiB — `flush_floor_predicted_mb = 128` governs their size; not the ~24.7 MB (23.6 MiB) the 100k-vector flush threshold would suggest), so a 135 MiB ceiling is below even the smallest flush output and no L0 segment can ever be trained or merged (server log: the TD-COMPACT-5 arm fires every 14–29 s, `⏸️ L0 remains horizontal because no file pair fits the current memory budget`, `max_input_bytes=141557760`; the WAL quiesced but the settle gate never completed — `rows=footer-snapshot-pending` forever). Untrained beds are not comparable (~180 GETs/q measured stake per TD-COMPACT-5). The run was killed at diagnosis; the settle timeout would have fired at 3600 s. The producible ceiling window for N segments at 3M is **[largest flush, smallest pair sum) = [208.2, 300.2) MiB → 4 segments is the ladder's top rung** (smallest pair sum 147,280,091 + 167,538,529 B = 300.24 MiB); more fragmentation requires a second write-path knob (lower `flush_floor_predicted_mb`), which would break the vary-one-dial design. Same treatment as the 10M single-segment non-producibility in the scale arms: a policy floor, recorded as the blocker. [M]

== What this does NOT establish

n=1 per cell (no repeats) — directions, not distributions. The corpus is the learn split, not the base split. The ladder tops at 4 segments at 3M; no fragment ladder was run at 10M (its 3-segment bed exists, but the corpus-size factor is unseparated there). No warm-phase cap claims (protocol asymmetry above). **No default change and no pricing claim rides on this run** — production S3 already targets 8 MiB ranges; this ladder *reinforces* the scale arms' conclusion that the cap lever is weak under fan-out, and keeps TD-PAXDIR-2 (LIST cache) as the top request lever at scale.
