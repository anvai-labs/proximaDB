== Status

Accepted

== Context

This document defines the production readiness criteria for ProximaDB features, engines, and capabilities. These criteria ensure that features marked as "Production Ready" in docs/SUPPORTED_SURFACE.adoc meet the quality, performance, and operational standards required for production deployments.

== Purpose

* Provide clear, objective criteria for production readiness
* Guide feature development from experimental to production-ready
* Enable users to make informed decisions about feature adoption
* Maintain ProximaDB's reputation for reliability and performance

== Production Readiness Framework

=== Maturity Levels

[cols="1,4"]
|===
| Level | Description

| **Alpha**
| Experimental, under active development. Breaking changes likely. Limited testing. Not for production use. Example: PULSAR distributed graph engine.

| **Beta**
| Feature complete, actively being tested. Limited production use acceptable with caveats. Backward compatibility best effort. Example: Java SDK, Node.js SDK.

| **Production Ready**
| Extensively tested, meets all criteria below. Backward compatibility guaranteed. Fully documented. Example: ORION graph engine, SST storage engine.

|**Deprecated**
| Superseded by better alternatives. Will be removed in future version. Do not use in new deployments. Migration path provided.

|**Archived**
| Removed from active development. Moved to archive/ directory. Maintained for historical reference only.
|===]

=== Core Criteria

==== 1. Test Coverage

[cols="1,2,3"]
|===
| Component | Minimum Coverage | Notes

| Core features (search, storage)
| 80%+
| Critical path: vector operations, indexing, queries

| Optional features (CDC, streaming)
| 70%+
| Non-critical but important integration points

| Experimental features
| 50%+
| Acceptable for alpha/beta features

| Documentation examples
| 90%+
| Code examples in docs must be accurate
|===]

**Measurement**:
[source,bash]
----
# Run with coverage report
cargo llvm-cov --lib --html --output-dir coverage

# Check specific module coverage
cargo llvm-cov --lib -- proximadb::storage::engines::sst
----

**Acceptance**: Coverage report shows ≥80% for core features

==== 2. Performance Benchmarks

All production-ready features must meet documented performance benchmarks:

[cols="1,3,2"]
|===
| Capability | Benchmark Target | Measurement Method

| Vector search (10K vectors)
| <10ms p99 latency
| `cargo bench --bench vector_search`

| Write throughput
| >100K ops/sec
| `cargo bench --bench write_throughput`

| Filtered ANN
| <15ms p99 latency
| `cargo bench --bench filtered_ann`

| Graph traversal (1M edges)
| <100ms p99 latency
| `cargo bench --bench graph_traversal`

| WAL recovery
| <30s for 10GB data
| Integration test with crash recovery

| Query planning
| <50ms for complex queries
| `cargo bench --bench query_planning`

| Memory usage
| <2GB for 1M vectors (768d)
| `cargo test --lib -- --test-threads=1 | grep memory`
|===]

**Acceptance**: All benchmarks meet or exceed targets in CI

==== 3. Security Validation

Production-ready features must pass security validation:

[cols="1,4"]
|===
| Requirement | Validation Method

| No `unwrap()` or `expect()` in production code
| `#![warn(clippy::unwrap_used)]` enforced, CI blocks violations

| No unsafe code without extensive justification
| Code review + SAFETY comments required

| Input validation on all public APIs
| Security audit of REST/gRPC handlers

| SQL injection protection
| Parameterized queries only, no string concatenation

| Authentication and authorization
| JWT/API key/mTLS implemented correctly

| Encryption at rest
| AES-256-GCM for sensitive data

| Encryption in transit
| TLS 1.2+ required for all network traffic
|===]

**Acceptance**: Security audit passes with no critical findings

==== 4. Documentation Standards

Production-ready features require comprehensive documentation:

[cols="1,4"]
|===
| Documentation | Requirements

| API Reference
| Complete REST/gRPC/proto documentation with examples

| Usage Guide
| Getting started guide, common patterns, best practices

| Performance Characteristics
| Documented latency, throughput, resource usage

| Operational Guidance
| Deployment, monitoring, troubleshooting

| Migration Guide
| How to upgrade from previous versions

| Backward Compatibility
| Documented breaking changes and migration paths
|===]

**Acceptance**: All documentation complete and reviewed

==== 5. Error Handling

Production-ready features must handle errors gracefully:

[cols="1,4"]
|===
| Requirement | Implementation

| No panics in production code
| All errors return `Result<T, Error>`

| Meaningful error messages
| Include context, suggested fixes

| Proper error codes
| HTTP status codes, gRPC Status, error types

| Error propagation
| Errors bubble up correctly, not swallowed

| Graceful degradation
| Fail-safe behavior when possible
|===**

**Acceptance**: Error handling review passes

==== 6. Backward Compatibility

Production-ready features maintain backward compatibility:

[cols="1,4"]
|===
| Requirement | Policy

| API stability
| No breaking changes without major version bump

| Configuration compatibility
| Old configs work with deprecation warnings

| Data format compatibility
| Can read data from previous versions

| Protocol compatibility
| Old clients can talk to new servers (within major version)
|===**

**Acceptance**: Migration guide provided for any breaking changes

==== 7. Operational Readiness

Production-ready features must be operable at scale:

[cols="1,4"]
|===
| Capability | Requirements

| Monitoring
| Prometheus metrics, structured logging

| Debugging
| Traces, profiling support, debug endpoints

| Health checks
| `/health` endpoint, dependency health

| Configuration
| Sensible defaults, environment variable override

| Deployment
| Docker images, platform packages (RPM/DEB/MSI)

| Testing
| Integration tests, load tests, chaos tests
|===**

**Acceptance**: Operations review passes

== Feature Evaluation Process

=== Phase 1: Self-Assessment

Feature owner completes self-assessment checklist:

* Test coverage ≥80%
* Performance benchmarks meet targets
* Security review passes
* Documentation complete
* Error handling reviewed
* Backward compatibility documented
* Operational readiness verified

=== Phase 2: Peer Review

Two reviewers evaluate feature against criteria:

* Code review for quality and patterns
* Security review for vulnerabilities
* Performance review for benchmarks
* Documentation review for completeness

=== Phase 3: Integration Testing

Feature tested in production-like environment:

* Integration tests pass
* Load tests validate performance
* Chaos tests validate resilience
* Upgrade tests validate migration path

=== Phase 4: Staged Rollout

Gradual rollout to production:

* Canary deployment (5% of traffic)
* Monitor metrics and logs
* Gradual rollout to 100%
* Rollback plan ready

=== Phase 5: Production Validation

One week in production with:

* No critical bugs
* Performance meets SLA
* No user complaints
* Metrics stable

== Current Product Status

[IMPORTANT]
====
This status summary is subordinate to
link:../SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`], the canonical
product support contract. A compiled feature, protocol, SDK, or integration
does not acquire a support tier merely by appearing in the repository.
====

=== Supported Default

* **SST** - ✅ Supported default storage engine for the canonical single-node vector path.
* **Canonical REST `/api/v2` vector CRUD/search** - ✅ Supported. Other
  query languages and modality projections retain their own tiers below.

=== Beta

* **HELIX / NOVA** - 🟡 Beta alternate vector engines.
* **ORION graph operations** - 🟡 Beta; ORION is a rebuildable projection,
  and graph creation/DDL is REST-only.
* **Federated SQL** - 🟡 Beta; full PostgreSQL/OLTP/HTAP parity is not
  supported.
* **Document CRUD/query/aggregation** - 🟡 Beta; canonical record
  storage is not yet the default authority across all server wiring.
* **Graph query** - 🟡 Beta for the documented openCypher subset.
* **Security runtime** - 🟡 Beta; authentication mechanisms exist, but
  admin/status APIs, stronger online revocation, and pgwire credential binding
  remain incomplete.
* **PostgreSQL wire protocol** - 🟡 Beta on port 5433 (autocommit SQL
  subset).
* **Hybrid retrieval, time-series, and event foundations** - 🟡 Beta.

=== Transport Modes

* **REST `/api/v2`** is the canonical customer surface on port 5678.
* The shipped `config/config.toml` and Docker image enable `unified_mode`, so
  port 5678 multiplexes REST, gRPC, and Arrow Flight. **Arrow Flight / gRPC
  multiplexing as a customer-facing transport remains Experimental.**
* The shipped Kubernetes/Helm manifests omit `unified_mode` and therefore use
  legacy multi-port mode: REST 5678, gRPC 5679, and Arrow Flight 5680. A port
  choice does not promote the protocol or operation behind it.

=== Experimental, Deprecated, And Retired

* **Distributed cluster execution** - ⚠️ Experimental; transport and
  remote execution remain partial. Multi-region operation is not Beta.
* **SWIFT / RAPTOR** - ⚠️ Experimental, feature-gated engines; neither is
  a supported migration target.
* **VIPER** - ⚠️ Deprecated per ADR-093; existing collections remain
  readable while migration proceeds, but new deployments should use SST.
* **PULSAR / QUASAR** - ❌ Retired names, not experimental engines. Use ORION.
* **Full SQL parity, LLM joins, and AVX512 paths** - ⚠️ Experimental or
  unsupported as scoped by the canonical matrix.

=== SDK And Framework Integrations

SDK packages and framework adapters are not blanket Production Ready features.
Use their own conformance evidence and the canonical matrix for the specific
operation being invoked; repository presence alone is not a support claim.

== Exception Process

=== Granting Exceptions to Criteria

In rare cases, exceptions to criteria may be granted:

1. **Document justification** for exception
2. **Risk assessment** for production use
3. **Mitigation plan** for documented gaps
4. **User notification** of known limitations
5. **Review date** for re-evaluation

Example: LLK Joins marked as Experimental due to LLM dependency, but available for users who accept the risk.

=== CI Tiers and Branch Protection

Feature maturity is enforced operationally by a three-tier CI gate matched to the
`feat → develop → qa → main` promotion flow. Each protected branch merges only when the
single `CI Success` aggregator check is green (chosen over many individually-required
contexts to avoid skipped-check deadlock).

[cols="1,1,3,1",options="header"]
|===
| Promotion | Tier | Checks (summary) | Workflows

| feat → `develop`
| LIGHT
| compile + fmt/clippy + layering + proto + panic-policy + security-audit + docs
| `ci.yml`

| `develop` → `qa`
| MEDIUM
| LIGHT + unit/integration tests + feature-matrix
| `ci.yml`, `qa-gate.yml`

| `qa` → `main`
| FULL
| MEDIUM + coverage + python multi-version + docker + benchmarks + CodeQL
| `ci.yml`, `qa-gate.yml`, `codeql.yml`
|===

Branch protection (live): `develop`, `qa`, and `main` all require the `CI Success` check.
`develop` and `main` additionally enforce it for admins (`enforce_admins`); `qa` and `main`
require the branch to be up to date before merge (`strict`); `main` also requires linear
history (merge via rebase/squash, not a merge commit). Heavy scans (CodeQL) run only at the
`qa → main` boundary plus a weekly schedule. The canonical description of the tier contract
is `CLAUDE.md` Core Directive #9 (CI/CD Tiering & Security Governance); this section is the
operator-facing projection of it.

== Summary

Production readiness at ProximaDB means:

* ✅ **80%+ test coverage** for core functionality
* ✅ **Performance benchmarks met** and documented
* ✅ **Security validated** with no critical findings
* ✅ **Comprehensive documentation** with examples
* ✅ **Graceful error handling** with meaningful messages
* ✅ **Backward compatibility** with migration guides
* ✅ **Operational readiness** for production deployment

Features meeting these criteria earn "Production Ready" status in docs/SUPPORTED_SURFACE.adoc and can be deployed with confidence.
