| Field | Value
| Status | **Active.** Written 2026-08-12 after a promotion opened with 47 conflicts that were almost entirely phantom; exact-source routing adopted 2026-09-10.
| Applies to | Every PR route; branch protection enforcement on `develop`, `qa`, and `main`
| Enforced by | Trusted `Branch Route Policy` after default-branch rollout, plus `promotion-ancestry-guard`, `promotion-source-guard`, and `promotion-freshness`

== The one rule that matters

**Promotions use the exact same-repository source branch and are merged with a
MERGE COMMIT. Never use a snapshot branch and never squash.**

Squash is correct for `feature → develop`: it keeps develop's history readable and the
workspace tooling already detects squash-merged branches. It is wrong for a long-lived
release branch, and the failure is silent and compounding.

== Why squashing a promotion breaks the next one

A promotion branch normally merges its target in to resolve conflicts. Squashing the PR
**discards that merge**: `qa` receives develop's _content_ with no link to its _history_. The
merge-base between the two branches therefore stops advancing.

Measured on 2026-08-11, after several squashed cycles:

[source]
----
merge-base(develop, qa):  1ab38bac7   2026-07-21   <- the last real merge
develop ahead of it:      377 commits
conflicts in the next promotion: 47
----

Git was recomputing a three-week diff every time. The conflicts were not real divergence —
`qa` held no unique work — but they landed in `abac/context.rs`, `security/rls/abac_adapter.rs`,
`grpc/auth.rs` and `write_ahead_log/mod.rs`, where a careless resolution is a security or
durability bug rather than a formatting nit.

After one *merged* promotion the merge-base moved to the previous day and develop was 10
commits ahead; a dry-run of the following promotion reported **zero conflicts**.

NOTE: Nothing on the `feature → develop` path can catch this. develop is consistent and its
CI is doing its job — the defect is entirely in how the release PR is merged.

== Opening a promotion

. Open the PR from the exact long-lived source branch:
+
[source,sh]
----
gh pr create --base qa --head develop   # develop -> qa
gh pr create --base main --head qa      # qa -> main
----
+
The trusted route guard rejects topic, snapshot, release, and fork branches targeting
`qa` or `main`. Direct source branches mean a new source commit synchronizes the PR and
invalidates the previous check result. Merge only the newest exact-head run, after the
source branch has settled and every required gate is green.

. **Merge with a merge commit.**

WARNING: `gh pr merge --merge --auto` has been observed to arm **SQUASH** regardless of the
flag. Always verify: `gh pr view <n> --json autoMergeRequest`. If it reports `SQUASH`,
disable auto-merge and re-arm through the API with `mergeMethod: MERGE`.

== If the source moves while the gate runs

GitHub synchronizes the promotion PR automatically. Let the superseded run cancel or
finish and evaluate only the new exact-head run. Do not merge using a check result from
an older source SHA.

== Recovering a severed ancestry

If `promotion-ancestry-guard` fails, the target holds commits the source branch has never
seen. Reconcile the target back into the long-lived source branch in a dedicated PR before
reopening the promotion; do not create an alternate promotion branch to bypass the guard.

[source,sh]
----
git switch develop                  # for a develop -> qa ancestry repair
git merge origin/qa
----

Then merge the PR **with a merge commit**, or the next cycle repeats.

== Where this lives

* Trusted metadata-only route guard: `.github/workflows/branch-route-guard.yml`
* Ancestry guard + `main ← qa` defense in depth: `.github/workflows/qa-gate.yml`
* Exact-head freshness gate: `.github/workflows/ci.yml`
* Repository ruleset `promotion-merge-method` permits only merge commits on `qa` and `main`.

NOTE: `pull_request_target` loads this guard from the repository default branch. The
trusted check becomes authoritative after this workflow reaches `main`; at that point,
require `Branch Route Policy` from the GitHub Actions app in branch protection for
`develop`, `qa`, and `main`, then validate both an allowed PR and an intentionally invalid
draft PR. Off-route PRs to unprotected branches still receive a visible failed check, but
only protected branches can make that check a merge gate. An administrator bypass remains
a deliberate override and requires the same explicit authorization as any admin merge.
