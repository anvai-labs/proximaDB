= ProximaDB Competitive Landscape
:toc: macro
:icons: font

[.lead]
Where ProximaDB sits relative to adjacent systems, and where it honestly does not (yet).
This is a positioning summary derived from link:VISION.adoc[Vision] and link:PRD.adoc[PRD];
support claims defer to link:../SUPPORTED_SURFACE.adoc[the support contract].

== The Thesis

AI agents assemble context rather than retrieve an isolated vector. ProximaDB's direction is a
SQL-first context engine on object storage (link:../12-design/adr/ADR-096-product-direction-sql-first-context-engine.adoc[ADR-096]):
Postgres-compatible SQL in which vectors, JSON and relationships are first-class. Its executable MVP
thesis is one governed record carrying identity, typed JSON properties, and an embedding,
served by metadata scan and vector retrieval through one canonical API. Workload-specific graph,
document, temporal, and observability projections remain the longer-term architecture; they do not
enter the customer promise until recovery and conformance are proven.

== Category Comparison

[cols="1,2,2", options="header"]
|===
| Category | Representative systems | Limitation ProximaDB addresses

| Postgres with pgvector; serverless Postgres
| Supabase, Neon, Amazon Aurora (and Aurora Serverless), Azure Database for PostgreSQL, pgvector on any Postgres
| The most direct comparison for the SQL front door. These products own the Postgres ecosystem and
its OLTP maturity. ProximaDB's bet is data on object storage as the primary copy, vectors and JSON
as first-class projections of one record rather than an extension column, and per-query economics;
it must match their correctness before it can argue cost (ADR-095).

| Vector and hybrid retrieval
| Pinecone, Milvus, Weaviate, Qdrant, pgvector, Elasticsearch
| These products already provide substantial combinations of vectors, payloads/documents,
filters, hybrid retrieval, tenancy, or distributed operation. ProximaDB must demonstrate lower
context-assembly and object-I/O cost; feature-count rhetoric is not differentiation.

| Multi-model database
| ArangoDB, SurrealDB
| SurrealDB is a direct category competitor, not an adjacent generic database. ProximaDB's
distinct bet is canonical durable records plus rebuildable, workload-specialized projections
co-designed with cache, network, object storage, and governance.

| Data platform
| Snowflake, Databricks
| Incumbent distribution, governance, SQL, and lakehouse reach are formidable. The opening is a
smaller operational context-serving path with a single binary and transparent per-query economics.

| Single-model specialists
| Neo4j (graphs only), TimescaleDB (time-series only)
| Best-in-class execution remains the benchmark. ProximaDB should integrate or coexist until its
corresponding Beta projection earns durability, accuracy, and operator evidence.
|===

*Migration direction*: ProximaDB's Beta Postgres wire surface includes a pgvector-compatible
distance operator. It becomes a supported migration path only after the pgwire identity/ABAC and
SQL-subset conformance gates close.

== Honest Positioning

Per the link:../SUPPORTED_SURFACE.adoc[support contract]'s own positioning guidance,
ProximaDB is a SQL-first context engine whose *supported* path today is narrower: typed JSON
properties and vector retrieval through the canonical REST API on a single node, with pgwire SQL
at Beta.
It is "not yet a like-for-like replacement for best-in-class distributed vector, graph,
document, or observability platforms." For petabyte-scale batch analytics, use a
warehouse (Snowflake, BigQuery, Databricks) today; for general-purpose OLTP with complex
multi-table transactions, use PostgreSQL today (see the Non-Goals section of
link:VISION.adoc[Vision]).

The long-term bet is that agent context does not need five independently operated systems. The MVP
tests the smallest valuable portion of that thesis first: typed properties and vectors answered
from one governed record. Each additional projection must earn its place with recovery,
conformance, and economic evidence.

No benchmark numbers are claimed here. The GTM gate is reproducible **economic proof** against
pgvector, Qdrant, Milvus, Elasticsearch, and SurrealDB: recall, filtered accuracy, p95/p99 latency,
peak RSS, object requests, bytes transferred, and cost per query. Any published figure must trace
to a measured entry in the benchmark evidence ledger referenced by the support contract.
