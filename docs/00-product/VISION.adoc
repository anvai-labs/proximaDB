== Executive Summary

Modern AI agents and real-time applications do not operate on a single data model. They need
vector similarity for semantic retrieval, document storage for structured records, graph traversal
for relationship reasoning, time-series for temporal analysis, and event logs for audit and replay.
Today, this means stitching together five or more specialized databases with fragile ETL pipelines,
inconsistent governance, and compounding operational cost.

ProximaDB eliminates this fragmentation. It provides a single data plane with specialized
engine-per-workload architecture, unified SQL-extended query language, and shared catalog governance.
The architecture is not theoretical -- it is dogfooded daily in ibkrtrading, a production
algorithmic trading system that exercises vectors, documents, graphs, time-series, and events in a
single embedded process.

== Category Definition: "Context Database"

=== Why the Term

AI agents and modern applications do not just query data -- they assemble _context_. A retrieval-
augmented generation (RAG) pipeline needs vector similarity to find relevant passages, document
metadata to filter by source, graph traversal to understand entity relationships, time-series
history to ground temporal reasoning, and event logs to trace provenance. These are not separate
workloads; they are facets of a single context-assembly operation.

The term "Context Database" captures this reality: the database exists to provide complete,
multi-faceted context to applications that reason over data, not merely retrieve it.

=== How It Differs

[cols="1,3"]
|===
| Category | Limitation

| **Vector Database** (Pinecone, Milvus, Weaviate, Qdrant)
| Strong vector retrieval products increasingly include document payloads, metadata filters,
hybrid retrieval, tenancy, and distributed operation. ProximaDB must win on governed cross-context
composition and measured object economics, not on the obsolete claim that these products store
only vectors.

| **Multi-model Database** (ArangoDB, SurrealDB)
| This is the direct category comparison. ProximaDB's proposed advantage is a canonical record with
specialized rebuildable projections and one trace-driven cost model. That advantage remains a
hypothesis until reproducible workload and cost evidence proves it.

| **Data Platform** (Snowflake, Databricks)
| Too broad. Optimized for batch analytics and data warehousing, not for low-latency serving,
embedded deployment, or real-time event processing at the edge.
|===

=== The ProximaDB Approach

ProximaDB takes a different path: _specialized engine per workload, unified under one query
language and one data plane_.

**Vector Engines** (4 supported engines, each optimized for a distinct access pattern):

[cols="1,2,1"]
|===
| Engine | Optimization | Performance (10K vectors)

| SST | Write-optimized, real-time ingestion | ~5.32ms
| HELIX | Locality-optimized, Hilbert curve ordering | ~13.2ms
| VIPER | Columnar Parquet, analytics queries | ~89.5ms
| NOVA | Progressive columnar, mixed read/write | ~101.6ms
|===

NOTE: The SWIFT and RAPTOR engines also exist but are *experimental* -- off by default behind
the `experimental-engines` cargo feature and not part of the supported surface. They are
excluded from the table above and the performance narrative.

**Graph Engines** (native CSR format with Arc-based zero-copy memory):

[cols="1,2"]
|===
| Engine | Capability

| ORION | Graph projection runtime with WAL-backed compatibility recovery
| Relational distributed substrate | Placement, routing, fanout/fanin, and scale-out coordination below ORION
| xCatalog/storage policy | Projection retention, freshness, and hot/cold placement below ORION
|===

**Time and Event Foundations**:

[cols="1,2"]
|===
| Engine | Capability

| TST (Time-Series) | Beta time-series foundation with ASOF joins, downsampling, time-partitioning
| Event Store | Beta append-only immutable event-log foundation for compliance and audit
|===

All engines share the same catalog, the same query planner, and the same wire protocols (REST,
gRPC, Arrow Flight, PostgreSQL wire protocol).

== Builder-First Narrative

Adoption starts with individual developers solving concrete problems.

* **One surface area**: vectors, documents, graphs, time-series, and events in a single API.
  No need to learn five different query languages or manage five different connection pools.

* **Lower glue cost**: cross-model queries remove fragile ETL and application-side joins. A single
  SQL-extended query can combine vector similarity, graph traversal, and document filtering.

* **Predictable performance**: storage engines are chosen per workload, not forced into a
  one-size-fits-all architecture. The system selects the right engine automatically or allows
  explicit engine selection.

* **Fast start, portable deployment**: `docker run` or `cargo run` for local development.
  Object-store backends for production scale. No architecture changes between environments.

* **Clear primitives**: catalogs, schema, and indexes are explicit and inspectable. No hidden
  magic -- every optimization decision is observable and overridable.

== Executive Narrative

Developer adoption creates organizational value that executives care about.

* **Platform consolidation**: reduce database sprawl and duplicated pipelines. One system replaces
  the combination of a vector database, a document store, a graph database, a time-series database,
  and an event log.

* **AI velocity**: faster iteration from data ingestion to model deployment. Cross-model queries
  eliminate the data engineering overhead that slows AI teams.

* **Governance at scale**: shared catalog, lineage, and access controls across all data models.
  One policy framework, not five.

* **Cost control**: format-first storage and elastic compute reduce long-term TCO. Pay for storage
  once; query it from any engine.

* **Avoid lock-in**: open storage formats and documented wire protocols protect data investments.
  Data is always accessible regardless of compute engine choice.

== The ibkrtrading Dogfood Story

[.lead]
Built for, proven in, production trading.

=== The System

ibkrtrading is an event-driven algorithmic trading system built in Rust with 16 crates, connecting
to Interactive Brokers TWS/Gateway for live market execution. It processes real-time market data,
executes trading strategies, manages risk, and maintains complete audit trails for regulatory
compliance.

=== The Problem: Three Databases

The current ibkrtrading architecture uses three separate databases:

* **PostgreSQL**: OHLC price bars, historical market data
* **SQLite**: application state, order management, position tracking
* **JSONL files**: event logs at 119MB/day, audit trails, system events

This creates operational friction: three backup strategies, three failure modes, three sets of
connection management code, and no ability to run cross-model queries without application-side
joins.

=== The Goal: One Embedded Process

Replace all three databases with ProximaDB in embedded mode -- a single in-process database with
zero network overhead, unified query interface, and consolidated operational management.

=== Data Model Mapping

[cols="2,2,2"]
|===
| Trading Data | Current Store | ProximaDB Engine

| OHLC price bars | PostgreSQL | Time-Series engine (TST)
| Orders and positions | SQLite | Document store
| System events and audit | JSONL (119MB/day) | Event Sourcing engine
| RL training features | Parquet files | VIPER columnar engine
| Regime similarity vectors | Not yet integrated | SST vector engine
| Factor correlation graphs | Not yet integrated | ORION graph engine
| Trading performance metrics | Scattered | Time-Series engine (TST)
| Distributed traces | Scattered | Observability store
|===

=== Why This Matters

ibkrtrading is not a demo application. It executes real trades with real capital. If ProximaDB
cannot meet the latency, durability, and correctness requirements of production algorithmic
trading, it cannot meet the requirements of any serious application. This dogfood relationship
ensures that every architectural decision is validated under genuine production pressure.

== Design Principles

=== Format-First Storage

Storage formats and metadata define the contract, not the compute engine. Data written by one
engine is readable by any other engine that understands the format. This decouples storage
evolution from compute evolution.

=== Multi-Engine by Default

Specialized engines are modular and pluggable, not bolted on as afterthoughts. Each engine is
optimized for its workload: SST for write-heavy ingestion, VIPER for analytical scans, ORION for
graph traversal. The system selects the appropriate engine based on workload characteristics.

=== Catalog-Centric Governance

Schema, lineage, and access control live in a shared catalog that spans all data models. One
policy framework governs vectors, documents, graphs, time-series, and events uniformly.

=== Cross-Model Query

SQL, graph traversal, vector similarity, and time-series aggregation share one query planner. A
single query can combine `VECTOR_SEARCH`, `GRAPH_QUERY`, `DOCUMENT_QUERY`, and time-series
functions without leaving the database.

=== Continuous Serving + Continuous Discovery (CS/CD)

A context database is not just something you query -- it is a system that continuously *improves*
the unstructured data it holds. Two layers operate over one logical data foundation:

* **Serving**: low-latency retrieval for online RAG, recommendation, personalization, AI memory,
  and real-time agents.
* **Discovery**: offline refinement -- deduplication, reclustering, re-embedding as models evolve,
  quality/drift/bias scans, and agent-trajectory analysis.

These form a flywheel: serving generates feedback and new data; discovery analyzes and improves it;
the improvements (cleaner datasets, better embeddings, rebuilt indexes, richer metadata) flow back
into serving by *atomically* publishing a new catalog snapshot -- serving reads the prior snapshot
until the new data and indexes are ready, never exposing half-built state. The goal is that every
turn of the loop makes the next turn better, without the multi-day export/reprocess/re-import
pipelines that make most teams skip continuous discovery today.

This is the half of the architecture that turns ProximaDB from a serving engine into a data
foundation. The continuous-loop and elastic-compute work is tracked in
link:../12-design/VECTOR_LAKEBASE_ALIGNMENT_2026_05_28.adoc[the Vector Lakebase alignment trajectory]
and TD-086..TD-091.

=== Deployment Neutrality

Object store, local disk, or hybrid. Compute can be embedded (in-process) or distributed
(client-server). The same code runs in a Docker container, on bare metal, or as an embedded
library in a Rust, Python, Java, or Node.js application.

=== Operational Simplicity

Single control plane and consistent tooling across all data models. One backup strategy, one
monitoring dashboard, one set of operational runbooks.

=== Time-Series-Native

First-class time-series support with ASOF joins for point-in-time lookups, automatic downsampling
for long-term retention, and time-partitioned storage for efficient range queries. Time is not an
afterthought -- it is a core data dimension.

=== Event-Sourcing-Native

Append-only immutable event logs provide complete system history. Events are the source of truth;
materialized views are derived. This architecture supports replay, audit, and temporal debugging
as first-class operations.

=== Compliance-Ready

Regulatory compliance is built into the architecture, not bolted on:

* **MiFID II**: event immutability and complete order lifecycle audit trails
* **SEC Rule 17a-4**: immutable record retention with tamper-evident storage
* **SOC 2**: access controls, audit logging, and encryption at rest and in transit

== Non-Goals: What ProximaDB Is NOT

Clarity about boundaries is as important as clarity about capabilities.

* **Not a general-purpose OLAP warehouse in the current release.** For petabyte-scale batch
  analytics across structured data, use Snowflake, BigQuery, or Databricks today. ProximaDB's
  roadmap builds a Rust/DataFusion OLAP/MPP path over cataloged snapshots, but the current product
  optimizes for multi-model context assembly and single-node developer workflows.

* **Not a transactional RDBMS replacement for all workloads in the current release.** For
  general-purpose OLTP with complex multi-table transactions, full foreign-key semantics, triggers,
  and stored procedures, use PostgreSQL today. ProximaDB is explicitly designing PostgreSQL-style
  OLTP/HTAP foundations around xCatalog constraints, WAL, native row/delta storage, Volcano, and
  DataFusion snapshot reads; that work is tracked as TD-110 before any PostgreSQL-parity claim.

* **Not a real-time ML training platform.** For distributed model training, gradient computation,
  and hyperparameter optimization, use specialized ML infrastructure (PyTorch, Ray, SageMaker).
  ProximaDB serves features and stores embeddings -- it does not train models.

* **Not a blockchain or distributed ledger.** Event immutability in ProximaDB serves audit and
  compliance requirements, not decentralized consensus or cryptocurrency use cases.

* **Not a message queue.** For high-throughput message routing, pub/sub fan-out, and stream
  processing, use Kafka, NATS, or Pulsar. ProximaDB consumes events from message queues via CDC
  adapters -- it does not replace them.

== Adoption Strategy

=== Phase 0: ibkrtrading Dogfood (Prove the Architecture)

Validate every architectural decision against a real production workload before promoting to
external users. ibkrtrading exercises vectors, documents, graphs, time-series, and events in a
single embedded process under genuine trading pressure. Bugs found here cost nothing; bugs found
in production by external users cost credibility.

**Exit criteria**: ibkrtrading runs exclusively on ProximaDB embedded with zero data loss incidents
over 30 consecutive trading days.

=== Phase 1: Win Builders (Developer Experience and Single-Project Outcomes)

Target individual developers building AI applications who are frustrated by database sprawl.
Win on time-to-first-result: a developer should go from `docker run` to a working cross-model
query in under 10 minutes.

**Channels**: developer documentation, quickstart guides, example applications, conference talks.

**Exit criteria**: 100+ GitHub stars, 10+ community contributors, 3+ independent blog posts.

=== Phase 2: Expand to Teams (Standardize Catalogs, Schema, and Query Patterns)

Once individual developers adopt ProximaDB, help them standardize it within their teams. Provide
catalog management, schema evolution tooling, and query pattern libraries that make ProximaDB the
team's default data layer for AI workloads.

**Channels**: team onboarding guides, migration tooling, Slack/Discord community.

**Exit criteria**: 5+ organizations using ProximaDB in production across multiple teams.

=== Phase 3: Institutionalize (Governance, Cost, and Reliability for Executives)

Address enterprise requirements: multi-tenancy, RBAC, audit logging, SLA guarantees, and TCO
analysis. Provide the governance and operational tooling that executives need to approve
organization-wide adoption.

**Channels**: enterprise documentation, reference architectures, ROI calculators, partner program.

**Exit criteria**: 2+ enterprise contracts, SOC 2 certification, published TCO comparison.
