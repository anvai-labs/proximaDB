= TPC-H / TPC-DS Performance Evidence Ledger — methodology (TD-OLAP-4)

The harness `tests/tpc_perf_ledger_e2e.rs` promotes the TPC suites from
count-only *conformance* ratchets (`tests/{tpch,tpcds}_pgwire_e2e.rs`) toward
*measured* performance evidence (ADR-052 invariant 4). Per query x route x
temperature it records wall latency and the per-query I/O trace snapshot
(TD-158: `bytes_read`, `range_gets`, footer hits, per-engine `compute_ms`)
into a versioned JSON ledger artifact. ProximaDB latency and bytes-scanned on the TPC workloads are measured by this harness per query on both routes.

== How to run

[source,bash]
----
RUST_MIN_STACK=2097152 TPC_PERF_SCALE=0.001 cargo test --test tpc_perf_ledger_e2e -- --ignored --nocapture
# artifact: target/tpc-perf-ledger/ledger.json (override: TPC_PERF_LEDGER_OUT)
----

The full SF0.001 ledger completed on Linux x86-64 with Rust 1.100 and 2 MiB
workers after the pgwire dispatcher change. It exercised both native and
DataFusion routes, with 22/22 TPC-H queries succeeding on each, and 28/63 native
and 63/63 DataFusion TPC-DS queries succeeding. This measures the small test
profile run. Production worker sizing and larger-scale runs have separate
validation requirements.

== Full open-table SQL qualification

Generate both suites with the DuckDB extensions for the same release. Use the
extension's fixed parameters. The fixture contains all 22 TPC-H or 99 TPC-DS
query IDs, each SQL file and its SHA-256, and typed Arrow IPC reference answers
computed on the generated source tables. Each source table also has a declared
Arrow schema, NDJSON rows and a byte-range manifest, a versioned Delta log
and an Iceberg v2 metadata pointer. Keep the fixture at its original absolute
location for Iceberg reads.
https://duckdb.org/docs/1.4/core_extensions/tpch[DuckDB TPC-H],
https://duckdb.org/docs/1.4/core_extensions/tpcds[DuckDB TPC-DS]

[source,bash]
----
python -m pip install duckdb==1.4.4 pyarrow==26.0.1 deltalake==1.6.6 'pyiceberg[pyarrow,sql-sqlite]==0.12.0'
python -c 'import duckdb; c = duckdb.connect(); c.install_extension("tpch"); c.install_extension("tpcds")'
python scripts/bench/build_open_table_tpc_fixture.py tpch /tmp/open-tpch --scale 0.001
python scripts/bench/build_open_table_tpc_fixture.py tpcds /tmp/open-tpcds
----

Run this sweep once per fixture and format. The in-process test server
registers the pinned tables in pgwire, checks table counts, runs the full
hashed SQL inventory and saves wire values or SQL errors for every query.
The verifier checks typed row multiplicities, including exact decimal values
and a default floating-point tolerance of 1e-9 relative and absolute.
It evaluates the top-level `ORDER BY` against the typed wire rows, applies
explicit NULL placement or PostgreSQL defaults, and accepts any sequence
within a group of equal sort keys. An expression that cannot be evaluated
from the returned columns fails verification. LIMIT queries still compare
row membership against the fixture answer, including rows at tied cutoffs.

[source,bash]
----
TPC_OPEN_FIXTURE=/tmp/open-tpch TPC_OPEN_RESULTS=/tmp/open-tpch-iceberg.jsonl \
PROXIMADB_EXTERNAL_TABLE_ROOTS=file:///tmp/open-tpch/iceberg RUST_MIN_STACK=2097152 \
cargo test --features datafusion-integration --test pinned_iceberg_pgwire_e2e \
    pinned_external_full_tpc_sql -- --ignored --nocapture
python scripts/bench/verify_open_table_tpc_results.py /tmp/open-tpch /tmp/open-tpch-iceberg.jsonl
----

For NDJSON, set `TPC_OPEN_FORMAT=ndjson`,
`PROXIMADB_EXTERNAL_TABLE_ROOTS=file:///tmp/open-tpch/json` and use a new
`TPC_OPEN_RESULTS` path. For Delta, set `TPC_OPEN_FORMAT=delta` and
`PROXIMADB_EXTERNAL_TABLE_ROOTS=file:///tmp/open-tpch/delta`. The harness
uses the Delta version recorded for each table. The default format is Iceberg.

The storage integration lane generates an independent Delta fixture with
`scripts/bench/build_delta_checkpoint_fixture.py` and runs
`pinned_delta_checkpoint_replay` with `TPC_DELTA_CHECKPOINT_FIXTURE`
and the operator allowlist. Its delta-rs fixture
defines one BIGINT column named `id`. Version 0 contains 1 and 2, version 1
appends 3, version 2 overwrites the table with 4 and 5 and writes a checkpoint,
and version 3 appends 6. Retire the JSON commits through version 2 while
keeping the checkpoint, the version 3 commit and the referenced files.

The TPC-DS SF1 fixture contains about 19.6 million rows, and its NDJSON alone
took about 4.9 GiB in the local build. The named memory limit applies to DuckDB.
These fixtures record explicit source versions and compare each format
independently. The fixture and
conformance sweep are internal engineering evidence. An audited TPC run
requires the benchmark's prescribed parameters, streams and reporting.

=== Local SF1 evidence (Rust 1.100, 2 MiB workers)

Independent readers matched row counts and typed checksums for all 32 SF1
tables across NDJSON, Delta and Iceberg. The pgwire sweep registered the
Iceberg v2 fixtures and passed all 22 TPC-H and 99 TPC-DS executions. The
full inventory exposed three issues corrected in the sweep: catalog binding
for quoted names and nested queries, `SUBSTRING` coercion, and positional
`ORDER BY` losing the sort before LIMIT.

[cols="1,1,1,1,1",options="header"]
|===
| Suite | SQL success | Row multisets at 1e-9 relative and absolute | Wall time | Peak process RSS
| TPC-H | 22/22 | 20/22 | 7.0 s | 4.4 GiB
| TPC-DS | 99/99 | 87/99 | 44.7 s | 23.7 GiB
|===

All 121 row multisets matched with float tolerances of 2e-6 relative and 1e-6
absolute. The decimal, integer, date, text and null comparisons stayed exact.
The saved SF1 results from Iceberg, Delta and NDJSON each passed the sort
check for all 18 ordered TPC-H queries and all 90 ordered TPC-DS queries.
The stricter differences are in results DuckDB represents as floating point
and DataFusion evaluates with finite-scale decimal AVG or division. Retain
the 1e-9 comparison as a diagnostic. These debug-process wall times include
server startup, table registration and count checks. The performance gate
still needs release runs, bounded query memory and plan attribution,
especially for TPC-DS Q72, which took about 17 seconds in this sweep.

The same SF1 suites also ran through pgwire with pinned NDJSON. All 121
executions passed and the DuckDB comparator reproduced both the strict
and tolerant match counts above. The debug sweeps took 2m23s for TPC-H
and 18m28s for TPC-DS, with 4.9 and 24.6 GiB peak process RSS respectively.
These sweeps include raw JSON parsing, per-range SHA-256 verification and
table counts. Use the JSON route for direct file access and isolate parsing,
verification and query compute in release measurements.

Pinned Delta passed all 121 SF1 executions over pgwire at the same worker
stack size. Both DuckDB comparison counts matched the Iceberg and NDJSON
sweeps. Before Delta projection pushdown, the debug runs took 20.4 s and
2m20s, with 4.7 and 24.3 GiB peak process RSS. TPC-DS Q72 took 22.5 s.

Delta sends projected physical schemas to the Parquet reader for
positional transforms, including pure column renames, and for standard
partition-value insertions. Other transforms apply projection to the
logical output. Row-only and partition-only scans carry one physical
column through Kernel to preserve batch cardinality.
On a local fixture with 131,072 rows and a 256-byte payload column, Linux
`rchar` increased by 34.9 MB on a full scan and 0.79 MB on an ID-only
scan. The row count matched. These are process-read bytes and include
reads from the page cache.

The same row count and payload width in an independently written,
partitioned Delta fixture used 34.9 MB of process reads on a full scan
and 0.78 MB when selecting the ID and partition value. The projected
scan preserved all 131,072 rows, including 65,536 null partition values.

With projection pushdown, both local SF1 debug sweeps again passed all
121 queries and reproduced both DuckDB comparison counts. Wall time fell
from 20.4 s to 8.2 s for TPC-H and from 140.0 s to 54.5 s for TPC-DS.
Peak RSS was 4.4 and 23.7 GiB respectively. TPC-DS Q72 fell from 22.5 s
to 16.8 s and remained the slowest query.

The pgwire regression covers two versions of one Parquet file with an
on-disk deletion vector, a join across all three formats, outside-file
reference rejection, read-only enforcement and cancellation during log
replay. The delta-rs checkpoint fixture returned the expected rows at
versions 2 and 3 and declined expired version 0.

For long or isolated runs, set `TPC_PERF_LEDGER_OUT` to an absolute path outside the
worktree. The harness prepares the JSONL sidecar before starting the server and
publishes the final JSON with an atomic rename in that directory. Preflight refuses
estimates above the tighter available cgroup threshold (`memory.high` or `memory.max`).
The large-run acknowledgement also requires a finite hard limit and host headroom.
Load output reports completed batches and per-table `insert.acknowledged_rows`,
`insert.sql_bytes` and summed statement time. The row count comes from pgwire
command tags. SQL bytes measure client payload size.

CI: the `tpc-perf-ledger` job in `.github/workflows/ci.yml` runs at small scale
on develop pushes / manual dispatch, `continue-on-error: true` (ADVISORY — it
is not in the `ci-success` aggregator and must never gate a merge until
variance is bounded; mirror the pax-recall-ratchet advisory-until-stable
pattern when promoting).

== Methodology (pinned per ledger entry; regimes are never averaged)

|===
| Field | Value / rule

| storage regime
| `local-tempdir` (file:// object store on local disk). The local-NVMe regime
  is CPU-bound; the object-store regime is bytes-scanned-bound (ADR-052 first
  principles). They are separate ledger sections — never average across them.
  Object-store regimes (MinIO/Azurite/real cloud) are a follow-up section.

| routes
| The `native` sweep runs before MATERIALIZE, and the `datafusion` sweep runs after
  publication. Inspect each record's stamped `route` for the backend. With
  `PROXIMADB_NATIVE_TABLE_PROVIDER=1`, the pre-publication sweep can use DataFusion.
  Record the spill setting and read counters as well when comparing Layer A. The
  DataFusion Parquet leaf emits I/O counters through `TracingObjectStore`.

| temperature
| `first` vs `repeat` against a warm process. This is NOT a cold-page-cache
  measurement — true cold runs need a server restart per query (future slice).

| datagen
| `synthetic-tpc-shaped`: deterministic (seeded SplitMix64), TPC-schema
  row-ratio-scaled, power-law key skew, referentially intact. It is **not**
  audited dbgen/dsdgen output — no TPC-official or external-comparative claim
  may cite this ledger until a faithful generator + bulk-load path lands.

| scale
| `TPC_PERF_SCALE` (1.0 ≡ SF1 row ratios). CI runs 0.001 (~9k TPC-H rows);
  SF1 over per-row INSERTs is impractical — a bulk-load path is the
  prerequisite for real SF1/SF10 entries.

| baselines
| The harness can run DuckDB in-process with the `duckdb` feature or via `DUCKDB_BIN`
  in a build without that feature. Record which path ran, the version, layout and cache
  state. A skipped baseline contributes no comparison. Standalone DataFusion and deferred
  ClickHouse comparisons are tracked in link:td/TD-OLAP-4-tpcds-performance-evidence-ledger.adoc[TD-OLAP-4].

| honesty rule
| The ledger records where ProximaDB *loses* (e.g. DataFusion hash-join
  no-spill on large joins) — mandate #11: no "competitive" claim is cited in
  any doc without a ledger entry backing it.
|===

== Ledger JSON shape

`{ methodology: {engine_version, git_sha, scale, storage_regime, datagen,
temperature_semantics, routes}, records: [{benchmark, query, sweep,
temperature, ok, error?, rows, wall_ms, ...IoTraceSnapshot}] }`

`sweep` is the harness phase label (`native` / `datafusion` / `duckdb`); the
flattened snapshot's `route` is the stamped `(shape_class, backend)` the router
actually served (renamed from a colliding `route` label field 2026-07-13 —
duplicate JSON keys made parsers drop the label).

The `IoTraceSnapshot` fields are flattened per record: `get_ops`, `bytes_read`,
`range_gets`, `splits_total`/`splits_pruned` (TD-OLAP-3 skip ratio — the
runtime-filter promotion gate's evidence; totals accumulate across the static,
runtime, and bloom-semijoin pruning stages), `bytes_written`,
`footer_hits/misses`, `egress_bytes`, `compute_ms` (per-engine map).

== Bloom semi-join (TD-OLAP-3, high-NDV in-list) — evidence status

The bloom semi-join split-prune (default-ON since 2026-07-08 per ADR-056 MVP-1; opt out with `PROXIMADB_DF_BLOOM_SEMIJOIN=0`)
targets the case min/max zone-maps cannot cover: a positive `IN`-list whose key
set spans a fact split's `[min,max]` (cardinality ≥
`PROXIMADB_DF_BLOOM_SEMIJOIN_MIN_KEYS`, default 256 — a fact probe against
thousands of dimension keys). When it prunes a split, the skipped row-group read
is reflected in the same `splits_pruned` counter and `bytes_read` drop this
ledger already meters (the projected key-column read it pays up front is also
metered through the tracing store), so no new fields are needed.

**Measured status: integration-level (synthetic high-NDV `IN`), 2026-07-07.**
The reader test `bloom_semijoin_reduces_metered_bytes_scanned`
(`object_store_parquet_reader.rs`) drives the real `scan()` path over a wide fact
fixture (3 row groups × 300 rows; 1 Int64 key + 12 Float64 payload columns; the
store wrapped inside the `io_trace` scope so spawned-partition reads are
attributed) and records the metered `io_trace` snapshot with the flag OFF vs ON:

[cols="1,1,1,1", options="header"]
|===
| Metric | flag OFF (min/max) | flag ON (bloom) | delta

| rows returned      | 300     | 300     | identical (correctness)
| `bytes_read`       | 194,400 | 166,790 | **−14.2%**
| `splits_pruned`    | 1 / 3   | 2 / 3   | +1 split (rg0)
|===

The query is `SELECT p0..p11 FROM t WHERE k IN (150 even literals)`. rg0 holds
odd keys spanning `[1,199]` — its min/max window overlaps the even in-list so the
zone-map keeps it, but every key is absent, so the bloom prunes it and its wide
payload read is skipped; rg1 (`k∈[1000,1099]`) is min/max-pruned in both; rg2
(the even-keyed survivor) is read in both. The reduction is net of the projected
key-column read the prefetch pays. This is a *metered* `bytes_read` delta (not a
row-group-size estimate), reproducible by the test.

**Still pending: SF-scale TPC.** This is a synthetic fixture, not a faithful
TPC-H/DS query — those push fact predicates into the WHERE (Slice A) or reach the
fact via a join key (Slice B) rather than a large literal `IN`-list. An
SF1/SF10 entry through the `tpc_perf_ledger_e2e` harness (a real high-NDV
semi-join query) remains the bar before any "competitive at scale" claim
(mandate #6/#10).
