= TD-USUB-4: `set_storage_layouts` clobbers — a table cannot hold two representations, so cost-based routing is inexpressible

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Partial: publication is additive (upsert by layout `name`) and a table holds more than one representation (2026-09-22, #1920); open: the evidence-gate items not met by that change — a deterministic primary/landing layout (carried to TD-USUB-10), per-layout `snapshot_lsn` proven to drive the delta merge for a stale representation, and the old-clobber round-trip check.**

== History (shipped)

* Finding: `materialize_table_to_parquet` published with `set_storage_layouts(&table_id, vec![layout])`, **replacing** the layout list — so the catalog could record only one physical representation and cost-based routing across representations (TD-OLAP-1 slice-2 flip, ADR-033's native arm, ADR-094 §5) was inexpressible. The catalog schema already modeled multi-layout; only the write path collapsed it.
* Resolution: only the write side was broken (`set_storage_layouts` is a legitimate set primitive; both backing predicates already iterate). New pure merge `upsert_storage_layout(existing, incoming)` keyed on `CatalogStorageLayout::name`: same name replaced in place (repeat `MATERIALIZE` cannot duplicate), other names preserved, order stable; per-layout `snapshot_lsn` rides along. Current layouts are re-read fresh from the catalog at publish; a failed read degrades to the pre-fix behaviour.
* **Lesson — publication was destroying the native layout.** The filing assumed no layout existed before publication; in fact every `CREATE TABLE` carries an `InternalCanonical`/`ProximaBlock` landing layout, and `MATERIALIZE` erased it. Two existing tests asserted the defect (`storage_layouts.len() == 1`). Multi-representation became immediately real. Routing was checked unaffected: `pax_backed` is consulted only in the `(true, false)` arm, and a materialized table is `parquet_backed`.
* Known, deliberately not fixed (pinned in the e2e): a write landing after publication is not visible over the published base by default — the ADR-025 read-merge is a per-table opt-in; ADR-094 names publication staleness as a live design constraint.
* Evidence: `upsert_storage_layout_is_additive_and_idempotent`; `tests/additive_storage_layouts_e2e.rs` (materialize three times on a live server).

== Open: evidence gate (mandate #6)

* A test creating a table with both a native and a Parquet layout, asserting both are
  recorded, both are discoverable, and the primary is deterministic.
* Round-trip: a table materialized under the old clobbering behaviour still reads correctly
  after upgrade (no migration required).
* `snapshot_lsn` per layout proven to drive the delta merge correctly for a stale
  representation.
