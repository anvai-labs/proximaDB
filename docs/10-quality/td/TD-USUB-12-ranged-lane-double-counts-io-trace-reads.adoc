= TD-USUB-12: The vector ranged lane double-counts its io_trace reads and cannot see its own acquisition depth

[cols="1,3", options="header"]

== Correction — the first draft of this TD was wrong, in the opposite direction

This TD originally asserted that `RangedSegmentReader`'s pre-construction reads are **missing from
the metered `object_store_gets`**, "verified" on the grounds that `proximadb-object-store` contains
no tracing. That verification was bad and the conclusion is inverted.

`proximadb-object-store` carries a process-global recorder hook: `ProximaObjectStore::get_range`
calls `recorder.record_range_read(..)` and `get_ranges` calls `recorder.record_batched_ranges(..)`
(`crates/storage/proximadb-object-store/src/lib.rs`, `IO_RECORDER` / `io_recorder()`). The server
installs `IoTraceObjectStoreRecorder` at boot (`src/database.rs`), whose `record_range_read` calls
`io_trace::record_range_gets(1)` and `io_trace::record_bytes_read(..)`
(`src/storage/persistence/filesystem/mod.rs`).

The original search looked for the symbol `record_range_gets` inside the object-store crate. The
crate calls `record_range_read` — a **hook**, resolved at the install site in another crate — so
absence of the destination name proved nothing. *Searching for a name is not searching for a
mechanism.* This is precisely the premise-verification failure
`docs/12-design/HOW_TO_FILE_TD_AND_ADR.adoc` now requires checking for — a rule that landed in
**#1942, the immediately preceding PR** (commit `c1a3e7731`, the parent of the one filing this
TD). It was therefore already in force, and was not applied.

== What is actually true

All of these are verified against source.

=== a. The lane's ranged reads are counted TWICE

`ObjectStoreVectorRecordStore` forwards the reader's own stats into the trace
(`src/services/record_store.rs`):

[source,rust]
----
let st = reader.read_stats();
io_trace::record_bytes_read(st.bytes_read);
io_trace::record_range_gets(st.range_gets);
----

Those same body reads already went through `IcebergObjectStoreBridge::fetch_vector_segment_range`
→ `ProximaObjectStore::get_range` → the recorder → `io_trace`. So each block-body read contributes
**two** `range_gets` and its bytes **twice**. The batched path is worse: the recorder charges
`ranges.len()` for a `get_ranges`, and the manual forward then adds the reader's own count on top.

`metering_event.rs` maps `snap.range_gets` to the billed `object_store_gets`, so on this lane that
quantity is **inflated**, not low.

=== b. The index-acquisition reads ARE metered — but are invisible to the reader's own stats

`locate_index`'s suffix GETs go through the same bridge, so the recorder counts them. What they are
absent from is `SegmentReadStats`, because they happen inside `open_inner` **before** the reader —
and therefore its `range_gets` field — exists. Two details make the existing doc comment ("the
one-time index-locate suffix read") wrong on its own terms:

* `locate_index` is a `loop` that **grows the suffix** when the index does not fit, so it is *N*
  reads, data-dependent — not one;
* it is paid **per segment** inside the scan loop in `record_store.rs`, not once per query.

So the depth cost is billed but not *attributable*: nothing can say how much of a query's
`range_gets` was serial acquisition versus parallelisable body fetching. That is the observability
half of this TD, and it is the half that survives intact.

=== c. The HEAD is genuinely uncounted everywhere

`bridge.vector_segment_size` → `ProximaObjectStore::object_size` → `head`, and the recorder has no
head hook. It appears in no counter at all.

=== d. KOU egress genuinely under-reports

`record_kou_bytes(.., st.bytes_read)` is fed only from the reader's stats, so the acquisition bytes
never reach the KOU counter — the one metering sub-claim from the original draft that holds.

== Reachability — why this is not a live billing defect

The only non-test caller of `RangedSegmentReader::open*` is `ObjectStoreVectorRecordStore`
(`src/services/record_store.rs`). Outside tests that type is constructed in exactly one place —
`DmlService::with_object_store_bridge` (`src/services/dml/mod.rs`) — and **that constructor has
no callers anywhere in the repo**. Every other construction site is a test (`record_store.rs`
under `#[cfg(test)]`, and `dml/tests.rs`, which builds the store directly rather than through
that constructor). **No server boot path reaches it.**

Do not mistake the similarly named methods for callers when re-verifying this:
`DataFusionTableWriteExecutor::with_object_store_bridge` and
`IcebergRestService::with_object_store_bridge` are different methods on different types, and
neither constructs the vector record store.

That is why the priority is LOW-MEDIUM rather than HIGH: today this double-count bills nobody. It is
recorded now because the lane is intended to carry production vector reads, and a counter that is
wrong by a factor of two is far harder to notice once revenue depends on it.

== Proposed sequence

. **Slice 1 — stop the double-count.** Delete the manual `io_trace::record_range_gets` /
  `record_bytes_read` forward now that the object-store recorder covers those reads, keeping
  `read_stats()` for footer-cache accounting. Pin it with a test asserting that one ranged read
  through this lane yields exactly one `range_gets`. **This is the fix that must land before the
  lane is wired to production.**
. **Slice 2 — make acquisition depth attributable.** Add `index_acquisition_gets` (and a head
  counter) to `SegmentReadStats`, populated from `open_inner`, reported as their own trace fields
  rather than folded into `range_gets` — folding would corrupt the `bytes_read / range_gets`
  average-GET-size signal that `SegmentReadStats` documents. Route the acquisition bytes into KOU.
. **Slice 3 — then reduce it.** The `index_cache` hit path already skips `locate_index` but still
  pays the HEAD unconditionally, and the size is **already known and thrown away**, exactly as in
  TD-USUB-8 slice 0: `ObjectStoreBridge::list_objects` walks the listing's `ObjectMeta` — which
  carries `size` — and returns `Vec<Path>` (the trait default in
  `proximadb-catalog-schema/src/object_store_bridge.rs`, and the production override in
  `proximadb-iceberg-engine/src/lib.rs`, both discard it). Widening the listing helper to carry
  sizes removes S HEADs from an S-segment scan. Measured, not asserted.

== Evidence gate

Slice 1 lands a test pinning one-read-one-count (a double-count is invisible to any assertion that
only checks "> 0"). Slice 3 is gated on a `BENCHMARK_EVIDENCE.toml` entry counting acquisition
operations before and after — as operations, not a percentage; see the TD-USUB-8 slice 2 artifact
for why a percentage of total requests misleads on a depth claim.
