= TD-ENGINE-MVCC-1: flushed vector search does not resolve the newest version per id before the dead filter (HELIX/NOVA/SWIFT)

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Stage 1 resolved (2026-11-11); stage 2 is TD-DELVEC-2.** Found by the #2518 adversarial review and reproduced on develop. Stage 1 (read-time newest-copy resolution, exact over the rows a scan reads) landed together with the NOVA reader/compaction fixes below. Stage 2 (deletion vectors on supersede, per-engine) makes it structural, so it also holds for rows a pruned scan never reads.
| Invariant | CLAUDE.md 16a/16d, and `resolve_freshest` in `src/core/search/merge.rs`: pick the newest copy of an id FIRST, then drop it if dead (PR #2063).
| Owner | HELIX / NOVA / SWIFT engines. Related: TD-MVCCRES-1, TD-MEMTABLE-MVCC-1.
|===

== The defect

The flushed segment search paths in HELIX (`helix/proxima.rs::search_helix_sstable`),
NOVA (`nova/operations/search.rs::score_records_into_queue`) and SWIFT score each row
independently into a top-k queue (`BoundedPriorityQueue` does no per-id dedup), and
since #2518 skip dead rows before scoring. No step resolves the newest version per id
across segments. So an older live copy can win over a newer dead one:

* **Overwrite, then expire:** insert v1 (no TTL), flush; upsert v2 with a 3 s TTL,
  flush; wait. HELIX and NOVA return the victim (v1, `valid_to_ns = None`). SST hides
  it. Before #2518 they returned the expired v2 instead, so the visible outcome (the
  record is still returned) is unchanged.
* **NOVA flushed delete:** insert, flush, delete, flush, search. NOVA returns the
  deleted record (v1). HELIX and SST hide it.
* **HELIX get-by-id** (`helix/readers.rs::find_vector_by_id`, caller `helix/mod.rs`
  ~2051): returns `None` for a dead match and moves on to the next SSTable in listing
  order, not newest-first. So the same shape shows up on point reads.

Contributing: NOVA hit `version` is always `0`, because the reader downcasts the
`version` column to `Int64Array` but NOVA writes it as `UInt32`
(`columnar_query_reader.rs` ~1873). Version-based resolution cannot work for NOVA
until that is read correctly.

== Fix shape

. Resolve the newest version per id inside each engine's flushed search (version,
  then the canonical tiebreak), THEN apply `is_record_dead`. Over-fetch, or resolve
  before the top-k queue, so that dropping a resolved-dead id does not shrink the
  result below k.
. Fix the NOVA `version` column read (UInt32), keeping Int64 as a fallback for
  mixed-read safety.
. Make HELIX get-by-id search segments newest-first and stop at the first match,
  dead or alive.
. Add an overwrite-across-flushes case and a flushed-delete case per engine to
  `tests/engine_ttl_conformance_test.rs`; those are the acceptance gates.

== Resolution (stage 1)

* **One order, defined once:** `proximadb_records::VersionKey`
  (`updated_at` ms, then a tombstone wins the tie, then `version`) plus
  `NewestVersionIndex`. `merge.rs::supersedes` (the service `resolve_freshest`)
  now delegates to it, so the engines and the service cannot disagree.
* **HELIX:** each segment scan observes EVERY row it reads, before the dead and
  metadata filters. `readers::resolve_across_sstables` merges the per-segment
  indexes and keeps only globally newest hits (parallel, sequential and
  progressive callers). Hits now carry `updated_at`/`version`.
* **NOVA:** both columnar record builders decode `version` (UInt32, the writer's
  type; Int64 accepted), `updated_at` (falling back to `created_at`, never the
  read-time `now()`) and `expires_at` through one helper
  (`columnar_query_engine/version_columns.rs`).
  ** **Search, pruning off (every service query):** one pass with no extra I/O.
     Each file's rows feed the cross-file index, and each file keeps its top-k
     newest-in-file live candidates. Candidates pass the global newest-copy check
     only after every file has been seen.
  ** **Search, TD-040 bounds pruning on (direct-engine callers only):** two passes.
     Pass 1 is a key-only column projection (ranged GETs of id/timestamp/
     updated_at/version/expires_at, never vectors), because pruned row groups must
     still be indexed.
  ** **Get-by-id** uses the same order. It was version-first, so it returned a
     record that search hides.
  ** **Found during review round 2:** NOVA bounds pruning is UNREACHABLE on the
     service path. `StorageQueryContext` forces `force_exact` for NOVA/VIPER/RAPTOR
     (`proximadb-storage-traits/src/query.rs`), so TD-040's win never applies to
     service queries. That is recorded in TD-DELVEC-2. Re-enabling pruning there
     needs a measured per-query I/O trace (co-design #2), and the pass-1 round-trip
     cost (HEAD + footer + key GET per file, outside the caching filesystem) must
     be priced into that decision.
* **HELIX compaction (reviews H1, round 2 M-d, round 3 M1/M2):** production runs
  only L0 -> L1. Every path resolves the newest copy across its input. When the
  L0 input holds a dead winner, all of L1 joins the input. With no level >= 2
  holding files, the input covers every older copy, so dead winners are dropped
  together with what they shadow: real GC, and no kept tombstone for file-level
  Hilbert pruning to separate from its shadowed copy. With a deeper level present,
  dead winners are kept: a vectorless one takes its shadowed copy's vector when
  that copy is in the input, else a zero vector. In that case file-level pruning
  can still separate them (bound below). Consumed files are removed from the
  level map by path; `remove(&0)` used to drop L0 files flushed after the
  compaction snapshot. PCA trains on live records only.
* **HELIX Approximate (quantized) path (review M2):** resolves and dead-filters
  like the fp32 path, and its hits carry their TTL.
* **HELIX get-by-id (review round 2):** resolves the newest copy across every
  SSTable, then dead-filters. It returned the first file holding the id, so a
  dead newer copy in a later file let the older live copy win.
* **HELIX extractor:** skips dead rows on `valid_to_ns`. Its "no vector =
  tombstone" test no longer holds now that compaction keeps dead winners with a
  vector.
* **Order precision (review M1):** `VersionKey` compares ns, so a re-insert written
  within the same millisecond as its delete is not hidden. Remaining twins:
  TD-MVCC-ORDER-1.
* **NOVA, found along the way (data correctness):** search passed `10000` and
  compaction `100000` as `read_all_records`' **start offset**, silently skipping
  that many leading rows of any larger file. Compaction then deleted its inputs
  (data loss). Its "keep latest" dedup kept the FIRST occurrence (file order),
  not the newest. All three are fixed; compaction dedups by `VersionKey` and keeps
  tombstones.
* **SWIFT:** the per-file scan resolves within the file and passes newest-dead
  copies up as markers, so the cross-file layer can shadow older live copies
  before it dead-filters.
* **Acceptance:** the `MV_CONFORMANCE` overwrite-then-expire and
  delete-after-flush cases pass for SST/HELIX/NOVA/SWIFT.
* **Remaining bound:** NOVA is exact over every row it reads (with pruning off,
  which is every service query, that is every row).
  HELIX and SWIFT are exact over the rows a scan reads: a newer copy in a pruned
  HELIX block, or outside a SWIFT file's top-k, cannot shadow an older one.
  TD-DELVEC-2 closes that. Per-segment truncation to k BEFORE the cross-segment
  check can return fewer than k, and can also pick the WRONG top-k members: a
  segment whose top-k are all superseded elsewhere contributes nothing, even if
  its next-ranked rows belong in the global top-k (round 3 L3). A probe did not
  reproduce it at the service level (upstream over-fetch masked it), but it is
  real at the engine level. Same family as TD-SEARCH-DEAD-OVERFETCH-1.
* **Kept tombstones with a deeper level present:** file-level Hilbert-range
  pruning runs even in Exact mode, so a kept tombstone (zero vector) can sit in
  a pruned SSTable while the copy it shadows is searched. This needs a level >= 2,
  which production does not create today.
