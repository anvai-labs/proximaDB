== History

Star-schema scan-avoidance for the DataFusion OLAP route. Slice A: `supports_filters_pushdown` on
`ObjectStoreParquetTable`, so static WHERE predicates reach `scan()` and prune row-group splits (Inexact, so
the FilterExec stays). Slice B: DataFusion 54 natively builds join runtime filters (min/max + in-list,
`enable_join_dynamic_filter_pushdown`), so no custom wrapper was needed; `ProximaScanExec` absorbs the
`DynamicFilterPhysicalExpr` and prunes per split (`PROXIMADB_DF_RUNTIME_FILTER_PRUNE`, default ON, v6
2026-07-06) behind a `wait_complete()` rendezvous (fixes a real probe/build race). Bloom semi-join: when an
in-list has ≥ 256 keys, a low-fpr `proximadb-bloom` over the in-list prunes a split iff none of its (cached,
≤ 1M) distinct keys can match (`PROXIMADB_DF_BLOOM_SEMIJOIN`, default ON since #784).

Lessons that still apply:

* **The meter lied, not the pruning.** `IO_TRACE` was a `task_local!` that does not cross `tokio::spawn`;
  `CoalescePartitionsExec` drives partitions on spawned tasks, so 84/96 GETs recorded into nothing and
  `bytes_read` was constant regardless of pruning. Fixed with an `Arc<IoTrace>` handle captured in scope.
* Uniform synthetic data defeats zone maps; pruning needed sort-on-materialize (TD-OLAP-6) and an explicit
  `cluster_key` for INT date surrogates.
* Slices A and B are **complementary**: A for direct fact predicates, B for dimension-only predicates reaching
  the fact via the join.
* **Bloom direction is load-bearing:** test a split's bounded key set against a bloom over the IN-LIST; the
  reverse collapses to "never prune". A key-family tag keeps build/probe byte encodings identical.

Evidence: TPC-DS star joins q42/q52/q55 −44.1% `bytes_read` (suite −10.9%) from runtime filters, bloom 30–57%
on star joins; evidence v1–v6 in `docs/_internal/status/TPC_PERF_GATE_EVIDENCE_*`; the qa-gate `bytes_read`
ratchet fails CI on regression.
