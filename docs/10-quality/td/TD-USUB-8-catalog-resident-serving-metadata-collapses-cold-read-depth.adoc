== History (shipped)

* Finding: a cold PAX read is a serially dependent chain before the first data byte; ADR-033 ranks `DEPTH ≫ WIDTH ≫ BYTES ≫ CPU` (100 parallel GETs ≈ one GET's latency; three serial ≈ 3×). ADR-062's per-segment invariants cache elided only the hot path.
* **Lesson — the chain was FOUR round trips, not three** (re-measured 2026-09-24): `PaxSplitReader::load_ranged` began with a `metadata` HEAD for the object size that the design docs never counted. And `RangedSegmentSnapshot::range_gets` excludes both the HEAD and the index-locate suffix read, so a baseline built on it under-reports depth by **two** operations. Any measurement for this work must count them explicitly.
* Slice 0 (#1936): `FileSplit.object_size: Option<u64>`, filled by both PAX locators from the size `list()` already returned (it was being discarded); `None` falls back to the HEAD. **Lesson — never reuse `FileSplit.length` as the object size:** it is producer-defined (whole file for PAX, `file.block_size` per block for SST), and a wrong length makes `footer_tail_range` read the wrong bytes. Test asserts the recorded size equals the real on-disk length.
* **Lesson — the caches already existed and one caller used them** (2026-09-26): `FooterCache`/`SegmentIndexCache` and `RangedSegmentReader::open_with_cache` served only `record_store.rs`; the DataFusion lane re-paid the full chain on every read. Wire existing machinery before building catalog architecture.
* Slice 1 (#1941): `load_ranged` consults/populates the global `SegmentIndexCache`, keyed on path alone (PAX segments are immutable; the tenant component of the key is fair-share accounting, not isolation); inert when caches are not initialised. Lesson: the first cut populated only the v4 branch, and the legacy PAXZ tail-probe path (the more expensive one) stayed uncached — caught only because the test asserts the observable effect (`range_gets` warm < cold), not the mechanism.
* Slice 2 (#1943, `pax_datafusion_read_depth_index_acquisition`): cold 203 / warm 200 `range_gets`; index-acquisition dependent round trips 3 → 0. The residual 200 are WIDTH (independent stripe fetches). Ratchet `cold - warm == 3` in `warm_read_skips_the_index_fetch` — if the path changes, re-derive the constant from call sites. Not a percentage (fixture-dependent), and `range_gets` is a complete depth count on this lane only because no HEAD remains when `object_size` is present; `RangedSegmentReader` still pays one.

== Open: slice 3 — catalog-resident Layer B

=== The change

Promote ADR-045 **Layer B** — RowDirectory, ColumnMeta statistics, blooms, SegmentIndex,
deletion vector — into xCatalog. ADR-045 already classifies all of it as *rebuildable serving
metadata*, so **nothing authoritative moves**.

Cold read becomes: **catalog query (ms, no S3 round-trip) → fetch surviving slabs**.

[.text-center]
**Dependent GET depth 3 → 1.** (As originally filed. Superseded — slices 0–2 have since
delivered most of this on the *warm* path with a read-side cache and no catalog change; see the
Status row and "Slice 2 as landed".)

This is the DuckLake insight — metadata as queryable rows rather than files-in-bucket,
collapsing the `metadata.json → manifest list → manifest → data` chain — applied at the
segment layer, where ProximaDB already owns a catalog and does not need to invent one.

=== The object must stay self-describing

The in-object footer copy is **retained, not replaced** — an object must stay readable with
no catalog present (disaster recovery, external tools, BYOB), and on divergence the object
wins. That invariant and its rationale (sound precisely because Layer B is rebuildable by
definition) are stated once in the spec:
link:../../12-design/PAX_V3_UNIFIED_SUBSTRATE_SPEC_2026_09.adoc[PAX v3 unified substrate
spec] § _3.3 The object stays self-describing_.

=== Constraints

* **ADR-062 D1** — no sidecar object is introduced; a catalog row is not an object in the
  data path.
* **ADR-045** — Layer A (including the inviolable filter + vector stripe co-location) does not
  move.
* Catalog size and write rate become a scaling dimension: Layer B for a large collection is
  not small. Bound it (per-segment granularity, eviction, lazy population) before enabling.

=== Not all of Layer B is promotable — the RowDirectory is per-ROW

ADR-094 Decision 4 and this TD both say to promote "ADR-045 **Layer B** — RowDirectory,
ColumnMeta stats, blooms, SegmentIndex, deletion vector — into xCatalog". That list mixes two
very different granularities, and one of them cannot go.

`RowDirectory` is `Vec<RowEntry>` with `ROW_ENTRY_SIZE = 32` (`row_dir.rs`): **one 32-byte
entry per row**. Promoting it would make the catalog grow with *row count* rather than segment
count — of the order of 32 GB for a billion-row table. xCatalog is a control-plane store; that
is a data-plane index and it must stay in the object.

The correct split:

[cols="1,2,1", options="header"]
|===
| Structure | Granularity | Promote?
| `ColumnMeta` stats (min/max, null_count, distinct_hint) | per segment × column | **yes**
| Bloom filters | per segment × column | yes, by reference (size-bounded)
| `BlockHeader` zone summaries | per block | yes
| `SegmentIndex` / `BlockFooter` extents | per segment | **yes — this is the one that collapses the chain**
| Deletion vector (`PDV1`) | per segment, bounded by deletes | by reference
| **`RowDirectory`** | **per ROW** | **NO — stays in the object**
|===

**This does not weaken the decision.** The chain is footer → metadata ranges → stripes, and
what the planner needs in order to skip the first two hops is the *stripe extents and zone
stats* — `SegmentIndex` + `ColumnMeta`. The `RowDirectory` only serves point lookups *within* a
block, which happen after that block's bytes have been fetched, so leaving it in the object
costs the read path nothing. The 3 → 1 collapse (4 → 1 counting the `HEAD`, now removed by
slice 0) still holds.

What it does change is the **sizing argument**: catalog growth is
`O(segments × columns)`, not `O(rows)`. That is the number any design review should be given,
and the decision's own wording currently implies the latter.

=== What the catalog promotion is actually for

**Before** building catalog-resident Layer B — a new per-segment catalog entity, a write path,
a planner read path, a rebuild path, and an invalidation story — wire the **existing** caches
into the DataFusion lane. It is a fraction of the work and attacks the same dominant term.

That also sharpens what the catalog promotion is actually *for*. It is not "collapse a chain
that nothing collapses today". With caches wired, the remaining gaps are the ones a per-process
cache cannot close:

* **cold start** — a fresh process pays full depth until the cache warms;
* **sharing** — every node warms its own cache independently;
* **planning** — a read-side cache accelerates a decided plan; it cannot let the *planner*
  prune before choosing one, which is what "catalog-resident" buys.

Those are real and worth the architecture, but they are a smaller, sharper claim than 4 → 1,
and the sizing argument (`O(segments × columns)`, per the RowDirectory correction above) should
be made against *that* claim.

=== What this leaves for slice 3

A cache is per-process and every node warms independently, so a cold process still pays the 3.
That — cold start, cross-node sharing, and planner-time pruning a read-side cache cannot
provide — is the surviving case for catalog-resident Layer B, and it is the claim slice 3 must
be argued against. Not "4 → 1", which a cache has now largely delivered on the warm path.

=== Evidence gate (mandate #6)

* **Cold-read dependent-GET depth measured 3 → 1** via `io_trace` `range_gets` on a genuinely
  cold cache — the headline claim as originally filed. **Superseded:** slice 2 measured
  3 → 0 on the *warm* path from a read-side cache alone, so this is no longer the claim that
  justifies the work. Slice 3 must be gated on the *cold*-path and cross-node numbers instead
  (Status row; "Slice 2 as landed").
* Catalog growth (bytes and write rate) per 1 TB of segments recorded.
* **Catalog-unavailable recovery exercised**: read a segment with the catalog offline, then
  rebuild Layer B from the object and verify byte-equality with the catalog copy.
* Divergence handling tested: a deliberately stale catalog entry must not produce wrong
  results.
