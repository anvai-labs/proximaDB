= TD-XMODAL-7: cross-modal UDTF in an aggregating subquery stack-overflows the server over pgwire

[cols="1,3"]
|===
|Status|**Partial: the DoS-class crash is fixed by a 32 MiB tokio worker stack (#677); open: an explicit planner-depth bound and localizing the DataFusion pass that drives the depth (the filed follow-ups).**
|Priority|HIGH
|Scope|FEAT
|Date|2026-07-04
|Relates to|ADR-053 (cross-modal query fabric), `apps/proximadb-server/src/main.rs` (runtime), the pgwire→DataFusion fallback (`src/query/execution/datafusion_engine.rs::prepare_dataframe`, `src/network/postgres/relational_pipeline.rs`), `src/datafusion/cross_modal.rs`. Follow-on to TD-XMODAL-6.
|===

== History (shipped)

* **Symptom.** A derived table (or scalar subquery) wrapping a cross-modal UDTF, aggregated, then JOINed
  to a Parquet-backed table — the natural analytical shape that avoids CROSS JOIN fan-out — overflowed a
  tokio worker stack and aborted the whole server over pgwire: a single crafted query was a **DoS**.
* **Root cause.** Deep but **bounded** recursion in DataFusion's SQL planner + optimizer over the default
  2 MiB worker stack. Only the full shape crossed the guard page: top-level UDTF joins planned fine, and an
  in-process `MemTable` base did not overflow — the real Parquet provider (`ProximaScanExec`) plus the
  full session builder (~a dozen UDF/UDTFs) were needed. A 32 MiB stack completes with correct rows, so it
  is frame pressure, not a cycle. Debug builds overflow most readily.
* **Fix (#677).** `apps/proximadb-server/src/main.rs` builds an explicit multi-thread runtime with
  `thread_stack_size(32 * 1024 * 1024)`. Regression test
  `src/datafusion/cross_modal.rs::udtf_in_aggregating_subquery_does_not_recurse` pins the in-process
  planning shape; the pgwire end-to-end shape is exercised by `demo/data-engineering/`.

== Follow-up (open)

* **Bound the planner depth explicitly.** A 32 MiB stack is a safety margin, not a semantic limit; a
  future change could cap subquery/plan nesting (a `recursion_limit`-style guard) and return a clean
  SQL error instead of relying on stack size for pathological (adversarial) nesting depths.
* **Localize the DataFusion interaction.** Narrow which optimizer pass drives the depth (candidate:
  subquery decorrelation / projection pushdown interacting with the custom `TableProvider`) and, if a
  DataFusion upstream fix exists, adopt it so the large stack is belt-and-suspenders.
