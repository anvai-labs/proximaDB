== History (shipped)

* Direction (ADR-069): WAL on local reattachable disk; object store as the coalesced durable tier for SST/VIPER/metadata/checkpoints. Flush on `min(size, time, capacity-budget)`; two watermarks + backpressure; reclamation keeps pace with every flush; `PerBatch` fsync is a tested contract. Placement needed no engine change — the FilesystemFactory already selects WAL and SST backends independently.
* S1–S3 (#1117, #1118): four `[storage.wal_config]` knobs (`flush_interval_secs`, `wal_max_bytes`, `high_watermark_pct`, `critical_watermark_pct`) on the live `WriteBufferUserConfig` surface (the `From<&WalStorageConfig>` path is test-only); pure `FlushPolicy::evaluate` (precedence capacity-critical > capacity-high > size > time); the policy-gated `AutoFlushDriver` calls `materialize_collection(free_wal=true)`. Live reclamation is manifest-deletion inside `materialize_collection`, not the marker-gated `truncate_through_canonical_marker`.
* **Two latent live-path bugs found only by live verification:** `WALVectorBatch.total_size_bytes` was built as `0` on the live ingest path (blinding memtable backpressure and all size/capacity evaluation) — fixed with `estimate_records_size`; and `free_wal` cleared the inner memtable but never retired batches in the batch coordinator, so a periodic caller re-flushed forever (94 duplicate flushes, one per tick) — fixed with `mark_batch_flushed` + `clear_flushed_batches`.
* S4 (#1132, #1143): write admission rejects at the same `>= critical` line (`WalBackpressure`, default-OFF when `wal_max_bytes == 0`; recovery replay is never gated). The batch fold sites had stamped generic error codes, so a shed write looked like a 400/500 (records.rs even returned 200); `write_batch_error_code` walks the chain and both batch handlers map to 429 / `RESOURCE_EXHAUSTED`.
* S5 (#1142): SIGKILL crash-consistency test for `PerBatch` (RPO 0). Lesson: cooperative `drop`/`stop()` drains in-flight I/O and never exercises the fsync path.
* S6 (#1117, #1143): `proximadb_wal_flush_*{reason}`, WAL size/budget/watermark gauges, backpressure counters, `wal_truncation_segments_reclaimed_total`, `wal_replay_duration_seconds`; S1 guardrail warns on an object-store `write_buffer_directory` and errors when combined with `PerBatch`/`Always` sync.
* S7 (#1151): 10-minute soak — 2.61M inserts (~4,350/s flat), backpressure engaged 5×, WAL plateaued at 46.6 MB, 0 non-429 failures (`adr069_s7_wal_backpressure_soak`).
* Caveats that still apply: WAL is per-collection (a global budget would be a sum guard, not a replacement); the RTO tradeoff is a deployment choice (local WAL ⇒ a fresh node waits for volume reattach).

== Open

* *S7 multi-hour soak* — the recorded evidence is a 10-minute run; the slice called for a multi-hour sustained-write soak (bounded WAL util, flat object-store write-op rate). `scripts/soak_wal_backpressure.py --duration-s` supports it.
* *DELETE/tombstone admission* — `update_record`/`delete_record` route
  through `insert_record`, so tombstone/DELETE writes are gated like any write. Acceptable under
  default-OFF + the high-watermark force-flush (which drains regardless of op type), but a
  theoretical wedge if flush stalls — consider exempting DELETE/tombstone from admission so ingest
  backpressure can never block the operation that relieves it.
* *S5 coverage gap* — the crash test covers only the default WAL layout; a config-file `wal_local_dir` loses acknowledged writes on an immediate crash. Tracked as link:TD-WAL-5-config-wal-local-dir-not-replayed-after-crash.adoc[TD-WAL-5] (CRITICAL).

Non-goals: cross-region WAL replication; a replicated/consensus WAL; changing the SST/VIPER/metadata durable tier; automatic hot→cold tiering of the WAL itself (the flush *is* the tiering).
