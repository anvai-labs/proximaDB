== Problem

* `manifest_selected_files` reads the latest `metadata.json` (LIST), the manifest list and manifests
  on every query; the table-open cache is bypassed for every manifest-managed base.
* Row-group pruning uses footer stats, zone maps and Blooms, but the per-file bounds already in the
  manifests are not consulted, so every surviving file's footer is fetched.

== Fix

. Cache parsed snapshot file lists and per-file stats keyed by the **immutable** metadata path in
  `TenantCache` (byte-weighted, tenant-fair). The latest-version LIST still runs per query, so
  freshness and read-after-write are unchanged (mandate #16).
. Before generating splits, evaluate pushed-down filters against per-file `ColumnFileStats`, reusing
  the predicate evaluation in `prune_splits`. Conservative by construction: missing/null bound ⇒ keep;
  a string longer than 16 characters has a truncated lower bound and no upper bound (`truncate(16)`), so it is pruned only on the lower bound; type mismatch ⇒ keep.
. Emit files-pruned and manifest-cache hit counters in the query-scoped I/O trace.

== Acceptance

* Negative controls: a file holding a matching row is never pruned at boundary values, with nulls,
  and with string bounds.
* TPC-H 22/22 and TPC-DS pgwire ratchets unchanged.
* io-trace evidence (pgwire query on a MATERIALIZEd table): GETs/query and files pruned before vs
  after, recorded in `BENCHMARK_EVIDENCE.toml`.
* Write → read with a cached manifest returns the new rows (cache keyed on immutable path, not table).
