== History

Question: does a pgwire `SELECT` over a non-Parquet relational table share `documents()`'s exposure (missing
unflushed rows, or returning tombstoned rows)? Traced before assuming a gap: **no**, as of 2026-07-11.

* The path is `route_select` → Native (Volcano) → `scan_table_relational` → the shared
  `DirectWalTableRecordStore` (the route is *named* `ParquetIcebergStorage`, but production binds that slot to the
  WAL-backed direct store) → per-(tenant, collection) `MemtableRecordStorage`.
* (a) Nothing can be missed: that memtable was the **single authoritative tier**, WAL-durable and rebuilt from the
  WAL on restart, never flushed to PAX and never evicted. `documents()`/vector collections differ (flushed PAX + raw
  WAL delta), which is why only they need the explicit merge. Do not "fix" this path by adding one.
* (b) Nothing dead returns: DELETE is a physical `DashMap::remove` (memtable never tombstones, so #16d holds
  trivially), and every scan applies `RecordScanOptions::matches_record` → `is_visible_at(now_ns)` on `valid_to_ns` (#16a).

**Caveat that now applies:** TD-USUB-1 slice 1 bounded this memtable and slice 2a added a default-OFF
`SpillRecordStorage` (memtable ∪ durable segments, with tombstones). With spill enabled, argument (a) no longer
holds by construction; the merge and dead-filter obligations move to the spill read boundaries, which TD-USUB-1 owns.
Also noted, left as-is: `MemtableRecordStorage::get_record` is not `matches_record`-filtered (safe while the memtable
holds no tombstones; TTL point-get is outside pgwire relational INSERT).

Evidence: `tests/pgwire_relational_native_read_after_write_e2e.rs` (read-after-write completeness, delete
visibility, no tombstone resurrection on re-insert); the Parquet/MATERIALIZE sibling is `pgwire_olap_delta_merge_e2e`.
