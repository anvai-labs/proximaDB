== What happens

`deploy/docker/entrypoint.sh` rewrites `[server] bind_address` to `0.0.0.0`, because
`docker run -p` cannot reach a loopback listener. Every network surface derives its bind
interface from that value.

pgwire is the exception, and deliberately so. `src/database.rs` only re-derives the pgwire
bind when `[api] pg_port` is set:

[source,rust]
----
if let Some(pg_port) = config.api.pg_port {
    multi_config.postgres_config.port = pg_port;
    multi_config.postgres_config.bind_address =
        format!("{}:{}", config.server.bind_address, pg_port).parse()?;
}
----

With `pg_port` unset, pgwire keeps `PostgresServerConfig::default()`'s `127.0.0.1:5433` and the
container starts. REST/gRPC/Arrow Flight bind `0.0.0.0:5678` and are reachable; pgwire is not.

== Why it must not simply be switched on

Setting `pg_port` in the shipped config moves pgwire to `0.0.0.0:5433`, and
`validate_trust_only_listener` refuses that before any socket is bound:

----
Error: Failed to start multi-server: pgwire currently supports only unauthenticated
single-tenant loopback access unless the listener enforces its own per-connection
authentication; disable this listener in authenticated, multi-tenant, or non-loopback
deployments
----

The predicate admits a trust-mode listener only when there is no security coordinator, the
deployment is single-tenant, **and** the address is loopback. With `[security] enabled = false`
the shipped image is exactly that case, so `0.0.0.0` is refused. The server exits 1 — the whole
image dies rather than losing one port.

That is the right behaviour. An unauthenticated Postgres-wire listener on `0.0.0.0` inside a
published image would be a trust-mode database exposed to whatever the host publishes.

Measured both ways with the real binary in a container (2026-10-11, #1977):

[cols="2,1,2", options="header"]
|===
| Shipped config | Server | `curl /health` from the host

| `pg_port` unset
| starts, mux on `0.0.0.0:5678`
| `{"status":"healthy",...}`

| `pg_port = 5433` in `[api]`
| **exit 1** at the listener preflight
| connection refused
|===

== How it stayed hidden

`6a01497ff` (#1973) added `pg_port = 5433` with the comment "5433 is the value that was already
hardcoded, so this changes nothing outside a container." That is backwards: *setting* the key is
what makes `database.rs` re-derive the bind at all. It did not fail immediately because the same
image copied `/config/config.toml` after `chown -R ... /config`, leaving it root-owned while the
server ran as uid 999 — so `entrypoint.sh` could not rewrite `bind_address`, the listener stayed
on loopback, and the preflight passed. Two defects masking each other: the ownership bug hid the
config bug, and `docker logs | tail -100` hid the warning that would have named the first.

Pinned by `container_bind_regression_tests` in `bootstrap_config.rs`, which asserts the shipped
config does not set `pg_port` and that a `0.0.0.0` pgwire listener is refused.

== The actual unblock

Per-connection authentication on the pgwire listener (**TD-PGWIRE-AUTH-1**, pgwire SCRAM). Once
`listener_authenticated` is true the containment does not apply and the listener may bind
`0.0.0.0` at any tenancy. Until then:

* keep `pg_port` unset in the shipped config;
* document that `-p 5433:5433` is inert in the default image, so operators do not conclude the
  database is broken — and so nobody "fixes" it by setting `pg_port`;
* reconsider whether `deploy/docker/docker-compose.yml` and the Kubernetes manifest should
  publish 5433 at all while it cannot serve.

NOTE: TD-PGWIRE-AUTH-1 is itself **Resolved** — SCRAM-SHA-256 is live on pgwire with a
fail-closed posture ladder, and `MultiServer::validate_listener_security` passes
`pgwire_authenticated = true` once the posture resolves to `ScramRequired`. So the capability
exists; the container is simply not configured for it, because the shipped image runs
`[security] enabled = false` (trust) by design. Reaching pgwire from a host is therefore an
*operator* step now, not a pending feature:

. enable `[security]` with `[security.authentication] enabled = true` (or
  `[security.pgwire] auth = "password"`) and provision `[security.authentication.scram_users]`;
. set `[api] pg_port = 5433` so the bind follows `[server] bind_address`;
. publish the port.

Step 2 without step 1 remains fail-closed (exit 1). Whether the *shipped* image should default
to an authenticated pgwire is the open product question; it is not a default we can flip without
shipping credentials, so it stays opt-in.

== Documentation action item — DONE

Every place that told a reader pgwire/Postgres is reachable on 5433 in the default container, or
published it in a `docker run`/Compose invocation, now states the truth: the listener *runs*, on
loopback, so a published 5433 accepts nothing; it serves a host-local binary and a client inside
the container's network namespace; serving it from the host needs SCRAM first, then `pg_port`.

*Manifests / executable claims*

* `deploy/docker/docker-compose.yml` — the `"5433:5433"` mapping is **removed**, replaced by a
  comment giving the reason and the three-step re-enable recipe. A published port that accepts
  nothing is a false claim in executable form, it makes `docker ps` affirmative evidence of a
  listener that is not there, and it holds host 5433 (a common second local Postgres) for no
  benefit.
* `scripts/validate_capability_matrix.py` — the `maturity_contract` drift rule **required** the
  `'"5433:5433"  # PostgreSQL wire protocol'` substring, i.e. it enforced the untrue claim. It now
  forbids the active mapping (matched at its YAML indent, so the replacement comment cannot
  satisfy it vacuously) and requires the explanation plus this TD id. Mutation-checked: re-adding
  the mapping fails the guard.
* `deploy/docker/Dockerfile` — both published stages (`runtime`, `runtime-full`) keep
  `EXPOSE … 5433`, because `EXPOSE` publishes nothing by itself and is the right record of the
  port the server would use; each now carries a comment saying listing it is not a claim that a
  host can connect, and that `-P` would publish an inert port.
* `deploy/kubernetes/deployment.yaml` + `service.yaml` — **no change needed**: verified they
  never declared 5433 (only 5678/5679/5680/9090). The same holds for `deploy/helm/**`,
  `deploy/k8s/**`, `deploy/systemd/**`, `deploy/packaging/**` and `deploy/terraform/**`, none of
  which reference 5433 or pgwire.

was re-verified here. Architecture/design docs that merely label the port (`docs/README.md`,
`docs/architecture-diagrams/**`, `docs/12-design/**`) were left alone: they describe the surface,
not its container reachability.

== Secondary finding worth recording

`b2436f234` (#1885) changed `src/network/server_builder.rs` from a hardcoded
`unified_bind_address: "0.0.0.0"` to `unified_bind_address: bind_interface`, i.e. derived from
`server.bind_address`. That is what made the published image bind loopback in the first place —
`Test Container Health` had passed as recently as 2026-09-04 (run `33868485852`, on the commit
that is the `v0.3.0` tag) with a byte-identical step and the same `bind_address = "127.0.0.1"`.
The same commit introduced the containment that makes the obvious remedy unavailable. Whether the
image's reachability should come from a boot-time config rewrite or from that coupling is an open
design question; the rewrite is the containing fix, not necessarily the right layer.
