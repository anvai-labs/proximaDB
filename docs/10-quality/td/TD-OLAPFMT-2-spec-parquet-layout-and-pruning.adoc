== What landed

. `ParquetWritePolicy`: 65,536-row groups; explicit page statistics (ColumnIndex) with
  8,192-row pages and mini-batch alignment; spec SBBF Bloom on int/date/string/binary columns
  (minus the leading sort key), NDV estimated per row group from contiguous windows, fpp 0.01,
  none below 8,192 rows; `sorting_columns` from the MATERIALIZE cluster key.
  `PROXIMADB_PARQUET_WRITE_POLICY=legacy` restores the old layout for A/B.
. Reader: page-index `RowSelection` for static WHERE predicates and resolved join runtime
  filters (`read_split_with_predicates`); persisted-SBBF probe for `=` and `IN` of any size;
  Bloom fetch skipped when the chunk advertises no `bloom_filter_offset`.
. **Bug fix:** SBBF probes now hash the Parquet physical encoding (`sbbf_probe_bytes`: 4-byte LE
  for INT32/DATE, 8-byte for INT64, raw bytes for BYTE_ARRAY; floats decline).
. Iceberg manifests carry `column_sizes`, `value_counts`, `null_value_counts`, `lower_bounds`,
  `upper_bounds` from the footer (single-value serialization, truncate(16)).
. IoTrace: `bloom_splits_pruned`, `pages_total`, `pages_pruned`, `page_rows_skipped` (flow into
  the TPC ledger JSON automatically).
. Kill-switches registered in `ENV_GATE_REGISTRY.adoc` (`PROXIMADB_PARQUET_{READ,WRITE}_*`).

== Verification status (2026-10-18, 4-vCPU / 15 GB container)

* Run and green: storage-common (`parquet_write_policy`, `parquet_page_prune`, 11 tests),
  iceberg-engine (35 tests incl. manifest metrics), `tests/wal_change_feed_fast_path_e2e.rs`, and the
  TPC-DS ledger A/B. *Corrected 2026-10-18 (was: "row-identical across all 63 queries × 3 engines
  × 2 layouts"):* per the evidence doc, every query that succeeded in both arms returned identical
  **row counts** (values were not compared). Coverage differs by engine: DataFusion 63/63, DuckDB
  63/63 only after the empty-result fix in the same change (56/63 before), native 40/63 (17
  comma-joined `FROM` lists, 4 derived tables, 2 plan/scan expression errors — the same failures
  in both arms). Value comparison across engines is P6 work in
  link:../../current/LAKEHOUSE_PLAN.adoc[LAKEHOUSE_MULTIMODAL_SEAMS_2026_10].
* Written but **not run here**: the root-crate unit tests
  (`object_store_parquet_reader` SBBF INT32 probe + page pruning through `scan()`,
  `native_parquet_scan` row-group/page pruning). Compiling the root crate's `--lib` test
  binary is OOM-killed by the container's memory limit in rustc's frontend (codegen-units=64,
  jobs=1 did not help) — another data point for the root-crate decomposition (TD-DECOMP). CI with
  more memory must run them before merge. *Corrected 2026-10-18:* this line previously gave
  "~13.7 GB RSS"; that is the figure the evidence doc records for the SF 0.05 MATERIALIZE OOM
  (`TPC_DS_SPEC_PRUNING_EVIDENCE_2026_10_18.adoc`, "SF 0.05 could not run"), and no separate
  rustc peak was recorded. **Re-measure** the rustc peak RSS before citing a number.
