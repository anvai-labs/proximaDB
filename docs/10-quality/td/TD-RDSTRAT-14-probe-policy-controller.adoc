= TD-RDSTRAT-14: Probe-policy controller — the algorithm/band dial in one module
:status: Proposed
:date: 2026-11-04
:tags: [read-strategy, ivf, probe, policy, performance]

== Problem

The coarse-probe fan-out is the recall↔GETs dial of the IVF-family read
path, and it was ONE hardcoded power law: `geometric_nprobe =
ceil(sqrt(k_c) × multiplier)` clamped `[min, max]` — process-global, no
collection or query identity (the config doc said so verbatim: "no
per-collection retune without a signature change (TD-RDSTRAT-9 tracks
the missing controller)").

Measured consequence (e1 beds, 2026-10/11): cells/query grew 12 → 15 → 43
across 1M → 3M → 10M at a fixed recall gate — GET fan-out ×3.6 per ×10
corpus (worse than √N), while bytes/GET fell 4.29 → 2.37 MB (scatter
defeats coalescing). The 10M $/M-queries cost is ~2× the competitive
target band.

== Correlation with the known algorithm families

The read path is **IVF-family, deliberately not HNSW**: rank cells in RAM
(the tiny cached directory), then read the chosen cells' extents as
coalesced ranges matched to the 4-24 MB GET ladder. HNSW's graph hops are
random-access — one GET per hop on object storage, structurally wrong for
the dominant cost term (I/O round-trips). HNSW remains only in the
in-memory axis index where hops are free.

The cascade maps one-to-one onto the quantization families:

[cols="2,2,3,4"]
|===
| scheme | bits/dim | our region | role
| F32 | 32 | Region C (default-on) | exact distances for final winners
| F16 | 16 | — (absent by design) | SQ8 owns the middle; C is deliberately exact
| SQ8 | 8 | Region B | rerank; direct SIMD distance, no LUTs
| PQ4 | ~4 | — (not used) | needs codebooks + per-query LUTs
| RaBitQ | ~1 + O(1) | Region A | provable-error binary codes; 2-4× tighter than PQ4
|===

So: **IVF(RaBitQ codes) → SQ8 rerank → F32 exact** — published math; the
moat is that each tier is a separately placeable, cacheable, billable
region in one PAX object. This TD makes the tier-1 fan-out POLICY.

== Design

=== One module, named algorithms (never a formula interpreter)

`crates/storage/proximadb-storage-common/src/probe_policy.rs`:

* `ProbeAlgorithm` — closed enum: `Sqrt | CubeRoot | FourthRoot | Log |
  Fixed | ByteBudget`. Adding a formula = one variant + one pure fn + one
  unit test, in this file only.
* `resolve_probe_plan(policy, cells, corpus_rows, rowgroup_bytes,
  avg_cell_bytes) -> ProbePlan{cells, probe_bytes, band}` — THE one pure
  function both consumers call.
* `band_ladder(rowgroup_bytes)` — discrete rungs DERIVED from the
  rowgroup geometry (the per-backend IOPS budget: 4 MiB cloud/Azure,
  8 MiB S3, 1 MiB local): `[rg/4, rg/2, rg, 2rg, 4rg, 8rg]` — the 8x rung is REQUIRED: stopping at 4x put every budget above it on one rung, so the `byte_budget@8MB` and `@16MB` arms tied and the 32 MiB cap was unreachable (two tests pin this). Band edges live
  here and nowhere else.
* `resolve_probe_policy(properties, tags, server)` — the 4-layer chain
  (property > tag > server TOML > code; **only the server layer is fed
  today** — the caller passes empty properties and tags until the carrier
  lands), exported as the ONLY resolution
  path (no single-channel resolvers — the inert-property bug class stays
  dead at the type level).
* `validate_probe_properties` — fail-closed SET-time validation.

A formula string in config would be unvalidatable at SET time,
untestable, and a security/review surface — the enum is the deliberate
alternative.

=== ByteBudget — the cost-matched form

`budget = base_bytes × (corpus_rows / 1M)^0.25`, cells = budget /
avg_cell_bytes, snapped to the band ladder, capped by `cap_bytes`
(default 4 / 32 MiB). Quarter-power growth means 100× data costs ~3.2×
probe bytes; the cap bounds worst-case fan-out at ~8 coalesced ranges
regardless of corpus. This is the form that maps directly to GET bytes —
the planner plans in the unit the bill is written in.

=== Surfaces (this PR)

* Server TOML: `[storage.sst_config.coarse_probe]` gains `algorithm`
  ("sqrt" default — byte-for-byte the historical formula for `nprobe_min >= 1` (with `nprobe_min = 0` and a multiplier small enough to plan 0, the old formula probed ZERO cells — an empty result — and this plans 1); the
  module's regression test pins equality across k_c 1..4096), `base_mb`
  (4), `cap_mb` (32). Fail-closed at load: an unknown name aborts boot
  naming the section.
* DELIBERATE boot change (pre-GA): a NON-FINITE `nprobe_multiplier`
  (`inf`, NaN) fails boot — `inf` used to mean a silent full scan. A
  NEGATIVE multiplier keeps booting and keeps its historical meaning
  (same as 0: probe exactly `nprobe_min`), as do `0` and `cap_mb <
  base_mb` (round 9 restored negatives; round 8 had rejected them).
  `base_mb`/`cap_mb` above 1 TiB now fail boot instead of clamping
  silently, matching the property door.
* Env overrides (the harness/operator escape hatch, same precedence as
  every other probe knob): `PROXIMADB_PAX_READ_PROBE_ALGORITHM`,
  `PROXIMADB_PAX_READ_PROBE_BASE_MB`, `PROXIMADB_PAX_READ_PROBE_CAP_MB`.
* Both consumers rewired through the module: the per-segment probe
  (`coarse_probe_nprobe` — now carries `path` for the IOPS geometry and
  the parsed directory for rows/cell bytes) and the collection directory
  plan (`centroid_directory_nprobe`, closure into `plan_probe`).
* Bench harness: `--probe-algorithm/--probe-base-mb/--probe-cap-mb` ->
  env; the resolved policy pins into result.json.

=== Deferred slices (open)

* **Collection-level `probe.*` properties** — land WITH the search-path
  property carrier (service-resolved properties into the search arc), in
  the SAME PR so the keys are never accepted-but-inert. The chain resolver
  and the value validator ship now; until the carrier lands every write
  door (`CREATE`, `SET`, `PATCH`) **REFUSES** a `probe.*` property with an
  error naming the knobs that do work (`[storage.sst_config.coarse_probe]`,
  `PROXIMADB_PAX_READ_PROBE_*`). Accepting a key that cannot take effect is
  the bug class the boundary exists to prevent, so the honest interim
  answer is a refusal, not a silent success. KNOWN SCALING CAVEAT
  until then: the per-segment fallback path (filtered queries where
  `row_allow` is set, or pre-directorypublication) scales a byte_budget
  by SEGMENT rows — more probes than the collection-level plan takes,
  bounded by the cap; the filtered probe's own adaptive row-matching
  semantics and `cap_bytes`/`max_cells` keep it from being linear
  fan-out, but the collection path is the authoritative one.
* **Axis advisor mirror** — `ivf_param_advisor` keeps its own curves:
  its nprobe model is recall-target-driven (better than any blind power
  law where it matters). Revisit only if the PAX and in-memory bands
  need to co-tune.
* **Legacy file/block sqrt pruners** (`effective_nprobe`,
  `BlockPruneMode::Sqrt`, TD-040 seed, helix/swift siblings) — separate
  BlockPruneConfig plumbing.

== The default-selection experiment

The point of the policy: the DEFAULT becomes a measured decision. Arms
{sqrt (control), cbrt, fourth_root, log, byte_budget@4MB, @8MB, @16MB}
× beds {SIFT 1M, 3M (settled + S=1), 10M}; gates recall@10 ≥ 0.97 (plus
0.98 sensitivity rows); report GETs/q, MB/q, cells/q, $/M. A non-sqrt
arm holding recall at ≤50% of control GETs on 10M graduates to a default
-flip PR with the ledger claim + recall ratchet. If no single formula
dominates, a scale-conditional default (one more pure fn in the module)
is the fallback — though `byte_budget`'s `(rows/1M)^0.25` factor IS the
scale adaptation and is expected to win outright.

== Review follow-ups (#2419 round 7, deferred by decision)

The #2419 merge gate was set to "no correctness or mandate findings"
(2026-11-05) after seven review rounds. Round 7's must-fix items were
fixed in-PR: POST /collections and PATCH /properties now fail closed
instead of returning 200 for properties they never persist, `unreachable!()`
was removed from the probe path (mandate #4), and boot validation no longer
rejects `nprobe_multiplier = 0` ("floor only") or `cap_mb < base_mb`, both of
which booted before (negative / non-finite multipliers ARE now rejected,
deliberately — see above). These are filed, not fixed:

* *RDSTRAT-14-F1 — tag channel is inert and unvalidated.* A
  `probe.algorithm:` tag is stored and never read; nothing validates tags
  at create. Close together with the carrier, or refuse the tag prefix at
  create the way `probe.*` properties are refused.
* *RDSTRAT-14-F2 — wasted per-segment work.* `coarse_probe_nprobe(k_c,
  path, &dir)` walks all cells and parses the path on every segment even
  when the directory plan replaces `probed`, the env override is set, or
  the sqrt form ignores those inputs. Compute only when `directory_cells`
  is `None`, and gather byte/row inputs only for ByteBudget.
* *RDSTRAT-14-F3 — `ProbePlan` name collision + unmetered plan.* A second
  `ProbePlan` shares the crate with `centroid_directory::ProbePlan` (the
  root re-export picks the new one), and its `probe_bytes`/`band` are
  dropped by the only production caller, so the plan never reaches the
  query I/O trace the co-design mandate requires. Rename and emit it, or
  return a count.
* *RDSTRAT-14-F4 — mis-attached rustdoc.* The "Fold the flat settings …"
  doc block attaches to `static RESOLVED_PROBE_POLICY`, not
  `settings_policy`.
* *RDSTRAT-14-F5 — test can leak process-global settings on failure.*
  `toml_coarse_probe_config_wins_over_default_init` restores the default
  only on success; use a drop guard (nextest's process isolation hides it
  in CI).
* *RDSTRAT-14-F6 — redundant enum/string round trip.*
  `ServerProbePolicy.algorithm` is `Option<String>`, so `settings_policy`
  stringifies an already-parsed enum and `resolve_probe_policy` parses it
  back; the case-insensitive key lookup is hand-copied for algorithm and
  multiplier beside `property_usize`. Use `Option<ProbeAlgorithm>` and one
  `property_str` helper.
* *RDSTRAT-14-F7 — persist create-time properties instead of refusing.*
  POST /collections now 400s any non-empty `properties`, including plain
  keys like `team`. That is a status change (200 -> 400) but not a
  behaviour change: those keys were never stored either — the handler
  builds a `CollectionConfig` with no properties field, so the 200 was
  reporting a write that did not happen. The real fix routes
  `request.properties` into the path `CREATE TABLE ... WITH` uses (which
  persists and validates them), then lifts the refusal.
* *RDSTRAT-14-F8 — the generic IVF strategy has its own formula.*
  `ApproximateSearchStrategy::calculate_nprobe`
  (`src/core/search/strategies/approximate.rs`) hand-rolls
  `ceil(sqrt(n) × multiplier)` and does not follow the probe policy; the
  module doc now says so. Route it through `resolve_probe_plan` once its
  bounds semantics are reconciled.

== Round 8 (#2419) — fixed in-PR

Harness: inherited probe gates scrubbed per spawn; `--nprobe` refused with
a probe-policy flag; base/cap bounds mirror the server exactly and are
refused on arms that do not read them. Ladder: extends to the cap (a fixed
8x top made local-disk budget arms indistinguishable). Catalog: a SET of a
policy key replaces its case-variants (two SETs could store
`cache.index.mode` and `Cache.Index.Mode`, a map the resolver rejects).
Docs: parity claim scoped to `nprobe_min >= 1`; `cap_mb` documented as
byte_budget-only and per-pool; the module's "single place" claim scoped to
the PAX consumers; three handler docs that had slipped onto
`UpdatePropertiesRequest` reattached. A policy-properties test no longer
depends on `compaction.target_file_size_mb`, which #2418 refuses.
