== History (shipped)

Correctness invariants and lessons from the shipped slices are kept here because they still bind
every open slice.

* **The finding.** `MemtableRecordStorage` was a `DashMap<String, ProximaRecord>` with no flush,
  evict, spill or compact path; durability for every pgwire relational table was 100% replay of one
  file, `{data_dir}/pgwire/canonical-records.wal`. Unbounded heap, unbounded WAL, no tiering. The
  `TableRecordStoreRoute::for_schema` arm named `ParquetIcebergStorage` actually receives the
  canonical WAL store (no Parquet is written on INSERT) — the name is still to be corrected as part
  of this work.
* **Slice 1 (#1918) — observe + bound, cannot lose data.** Gauge
  `proximadb_relational_memtable_records`; optional fail-closed per-partition cap
  `PROXIMADB_RELATIONAL_MEMTABLE_MAX_RECORDS` (default unbounded). An update at the cap is admitted
  (rejecting it would make a full table un-correctable); an invalid cap reads as unset, never zero.
  The cap counts records, not bytes. Persistence was deferred because the module contract said the
  store "must not grow independent persistence" (ADR-010/020) and mandate #6 says measure first.
* **Two findings that re-scoped slice 2:** the canonical Parquet encoder could not round-trip
  `valid_to_ns`/`oid`/`tenant_id`, so a deleted row would have read back live (closed first as
  TD-USUB-11); and UNIQUE/PK enforcement (`ensure_unique_index_built`) scans the partition store, so
  an evicting store must still serve flushed rows — hence a read-merge (memtable ∪ segments,
  memtable wins, tombstones suppress), not a plain spill.
* **Slice 2a (#1923).** `SpillRecordStorage` behind the existing `RecordStore` + `RecordScan`
  traits: flush at a resident-row threshold (`PROXIMADB_RELATIONAL_SPILL_MAX_RESIDENT`, default
  unset ⇒ never flush), evict only after the object is durable, read-merge through the canonical
  `read_segment_records` router (Parquet via TD-USUB-5's `PAR1` arm). With no truncation the WAL
  stays authoritative, so 2a cannot lose data; it bounds the heap within a process run, not across
  restarts.
* **2a wiring (#1945).** `storage_factory` takes `(tenant_id, collection)`. Lesson: **default-OFF
  means the legacy TYPE** — with the gate unset `new_spilling` builds a `MemtableRecordStorage`,
  not a spill store configured never to flush (which would run different read-merge code on every
  production read). The shared-mode `Arc::ptr_eq` factory probe was replaced by a recorded
  `shared_storage` flag, because a factory that performs I/O must not be called just to compare.
* **Purge-on-DROP (#1947).** `RecordStore::purge_durable_objects` deletes the partition's spill
  objects, called from `drop_table_records` before the handle is released, propagating failure.
  Lesson: deletion needs no catalog — the prefix derived from `(tenant, collection)` *is* the
  reference, and listing it also reclaims orphans from earlier instances. Coupling deletion to
  catalog registration would have held a data-deletion fix behind unrelated work.
* **Fail-closed writes need `write_if_absent`, not `FileOptions { overwrite: false }`.** Only
  `LocalFileSystem::write` consults that flag; S3/Azure/GCS issue an unconditional PUT, so a
  local-backend test passes either way and the guarantee is absent exactly on cloud deployments.
  `write_if_absent` is a real conditional create whose default impl errors rather than silently
  downgrading. (Checked: no other live call site relied on the flag.) Also: wiring is what turned a
  correct-looking "fresh name" comment into a false one — a property can be vacuously true while
  code has no callers.
* **LSN plumbing + unflushed minimum (#1950).** Defaulted `upsert_record_at_lsn` /
  `min_unflushed_lsn` on `RecordStore` (11 implementors untouched); `write_mutations` binds the
  `append_operations` result it used to discard and passes LSNs positionally (a length mismatch
  disables association rather than guessing). `SpillRecordStorage` tracks `oid → lsn` for resident
  rows only and fails closed on any untracked resident row or pending tombstone. Pinned by
  `min_unflushed_lsn_is_not_the_high_water_mark`.
* **Dead-record predicate (#1952, then #1953 rounds 5–7).** `is_dead` is applied at every spill read
  boundary — `merged_records`, `get_record`, `delete_record`'s segment probe AND the resident
  (memtable) arms — with one `now_ns` per call so arms judge liveness against the same instant. A
  dead resident copy must shadow a stale live segment copy on every surface
  (`a_dead_resident_copy_shadows_a_live_segment_copy_on_every_surface`). Lesson: the same
  missing-predicate defect was found at three layers of one module — "the predicate was applied
  where the author was looking, not at every boundary"; enumerate the boundaries.
* **Ordering lesson (2026-10-05), recorded because it recurred:** durable tombstones were useless
  and their payoff unsafe until **segment discovery** existed — nothing rediscovered a segment, so
  releasing WAL entries on a tombstone held in an invisible segment loses every flushed row that was
  never deleted. When a step's value is "now X is possible", check whether X is also *safe* yet.
* **Segment discovery (#1953).** Segments are `spill-{seq:016x}.parquet` with the sequence resumed
  past durable state (the `cold_segment_store.rs` precedent, mandate #12); the per-instance UUID
  nonce added in #1945 bought uniqueness but made the set unorderable from a listing, and it is
  gone. `ensure_discovered` lists once per store under `flush_guard` at the head of `flush`,
  `merged_records`, `get_record` and `delete_record`, and **fails closed** on a segment-shaped name
  it cannot place. Discovery ahead of `delete_record`'s `!segments.is_empty()` decision is what
  stops a first-touch delete from skipping its tombstone
  (`a_delete_as_the_first_touch_still_suppresses_a_flushed_row`). Order is taken from names, not a
  catalog list, so a written-but-unregistered segment is still found in the right place.
* **A listing is not scoped to your prefix (#1953, and a fix to #1947).** Local `list` is a
  non-recursive directory; S3/Azure/GCS list a recursive key prefix, and GCS passes the prefix raw
  with no delimiter — so a partition at `…/order` also saw `…/orders/…`, and **purge of `order`
  deleted `orders`' segments** on GCS. The first fix (compare `DirEntry::url` to the prefix) failed
  in the dangerous direction — bare-relative `base_path` vs `root_dir`-anchored urls, and S3/Azure
  percent-encoding of identifiers `validate_id` permits — silently skipping our own segments.
  **Rule now: a listing only proposes candidate sequences; membership is confirmed by existence of
  the canonical path this store itself reads, writes and deletes** (`{base_path}/{spill_segment_name(seq)}`),
  via one shared `list_partition_objects` for discovery and purge. Don't compare a listing's
  strings to yours. S3/Azure are scoped only because `object_store` re-appends a delimiter itself —
  upstream behaviour this repo does not pin and the local test double cannot model. Tests use
  `ListInjectFs` and assert the sibling's *bytes* survive.
* **Require the allowed alphabet (round 5).** `u64::from_str_radix` accepts a leading `+`, so
  `spill-+00000000000000f.parquet` claimed sequence 15 and sorted before 0; the guard had
  enumerated a disallowed class (uppercase) instead of requiring `[0-9a-f]`. Found by executing the
  primitive, not reading it; the test now asserts the property (no two accepted names claim one
  sequence). Round 6 brute-forced 1536 single-byte mutants to confirm the bijection. The `seen`
  dedup in `list_partition_objects` is a cost guard, not a correctness guard. The fixed width is
  load-bearing for `parse_spill_seq`'s rejection, not for any sort of names.
* **Deliberate flag day.** The rename made the 2a names (`spill-{uuid}-{seq:010}`) unreadable;
  accepted pre-GA because the gate is default-OFF with no production caller and the old naming
  lived nine days. `is_spill_segment` stays permissive so purge still reclaims legacy objects — it
  must NOT be tightened to match `parse_spill_seq`. Disclosed in `ENV_GATE_REGISTRY`.
* **Tombstone persistence (#1957).** Post-flush deletes are written into the segment as a
  synthesised `ProximaRecord::tombstone` (the store holds only oids, so there is no record to copy),
  stamped with the partition tenant (`with_tenant`, which normalises `""` to `None` because
  `matches_tenant` treats an empty tenant as matching any tenant). A flush with an empty memtable
  now writes; tombstones are snapshotted and cleared only post-commit. `min_unflushed_lsn` needed
  no change: "in the set" now means "not yet durable" (durable ⇒ cleared; not a biconditional — a
  repeat DELETE re-pins, TD-USUB-14). Using the primitive exposed TD-USUB-17.
** Lesson: clearing in-memory tombstones is sound only because #1953 round 7 made
   `delete_record`'s probe stop at the newest copy — the second time a step's safety depended on a
   later step.
** Lesson — a live-row loss nearly shipped: appending tombstones to the post-commit eviction list
   would evict a fresh upsert of a tombstoned oid landing after the snapshot (upsert does not take
   `flush_guard`). Evicted and written lists are separate
   (`an_upsert_of_a_tombstoned_oid_after_the_snapshot_is_not_evicted`); all 40 prior tests passed
   with the bug because none exercised a tombstone-persisting flush.
** Lesson — refusing the *flush* on an unusable tenant was an outage (`""` is a real production
   tenant; the `Err` failed every later write and aborted WAL replay into a crash loop). Now the
   residents persist and the tombstone stays pending; and an empty tenant gets a plain
   `MemtableRecordStorage` (`an_empty_tenant_gets_no_spill_partition`), making the unbounded
   tombstone-set shape unconstructible.
** Lesson — TD-USUB-18's orphan flag became an **unresolved-PUT counter**: raised before the write,
   lowered only on success, so a flush future dropped mid-PUT (cancellation, timeout) leaves it
   raised; saturating `fetch_update`, never `fetch_add` (atomics bypass `overflow-checks`).
** Lesson — TD-USUB-16 was fixed in this slice (one row per oid, tombstone wins) after being
   mis-triaged twice: persistence had turned its fail-closed outcome into fail-open.
** Lesson — **a mutation verdict expires when the behaviour it probed changes**: the production
   tenant-wiring mutation was recorded as killed in round 2 and silently survived after round 3's
   warn-and-drop change; the test now asserts the durable effect (`min_unflushed_lsn == Ok(None)`)
   by value. Test-count claims are no longer quoted (five count errors came from substring-filter
   totals); `cargo fmt` does not reflow comments, so doc comments spliced onto the wrong test are
   invisible to every gate.
** Tests (all mutation-tested, in `record_spill.rs`): `a_tombstone_only_flush_persists_and_suppresses_across_instances`,
   `a_persisted_tombstone_round_trips_its_marker_and_tenant`,
   `a_segment_mixing_props_rows_and_a_tombstone_round_trips_both`,
   `an_unusable_tenant_refuses_the_tombstone_but_not_the_flush`,
   `with_tenant_normalises_an_empty_tenant_to_none`,
   `flush_through_the_record_store_trait_makes_the_buffer_durable`,
   `a_failed_write_fails_truncation_closed_until_purge`,
   `a_flush_cancelled_mid_put_fails_truncation_closed`,
   `min_unflushed_lsn_releases_once_the_tombstone_is_durable`,
   `an_upsert_of_a_tombstoned_oid_after_the_snapshot_is_not_evicted`,
   `an_oid_both_resident_and_tombstoned_is_not_flushed_and_stays_fail_closed`; in
   `record_store.rs` (production factory): `spilling_partition_persists_a_tombstone_through_the_production_wiring`,
   `an_empty_tenant_gets_no_spill_partition`.

== Open

The open items, in the dependency order this TD has had to correct twice. Each subsection below is
kept verbatim from the slice that found it.

=== Open list (verbatim from the pre-consolidation status line)

**Open:** (i) **deletion-obligation marker + drain** — DROP deletes on the success path only; a purge failure or a crash in the marker→purge window orphans objects permanently, because the catalog entry is already gone. **Design decided 2026-10-02** (positive-evidence obligation following TD-COMPACT-13, *not* a sweep for absence) and deliberately **gated with "wire the two production call sites"** below — see "Design decided"; (ii) **catalog registration of the segment PREFIX** — narrowed by the discovery work below: the segment *set and its order* are now recovered from the object names by listing, so what the catalog still owes is only *where* to list, which WAL replay cannot reconstruct (`CanonicalWalEntry` carries no namespace); (iii) wire the two production call sites, (iv) slice 2b (WAL truncation) — was also gated on **TD-USUB-15**, see below (that gate is now cleared: TD-USUB-15 was resolved 2026-10-19 by generation-checked eviction), (v) slice 2c (compaction) — gated on **TD-USUB-17**: a persisted tombstone is `is_dead` but NOT `is_tombstone_at`, which is the predicate compaction drops on, so a compactor following `pax_block.rs` would silently retain every tombstone it meant to reclaim.

=== Slice definitions (2b, 2c)

**Consequent slicing.** The filed step list below is more than one reviewable PR, and its
riskiest element (WAL truncation) is the one that can lose data. So:

* **Slice 2a — the durable spill path.** Read-merge store behind the existing `RecordStore`
  trait, flush at a threshold, catalog registration, default-OFF. **No WAL truncation**, so
  the WAL stays authoritative and the change cannot lose data: recovery replays exactly as
  today, and segments are a read-side representation of already-durable rows. Bounds the heap
  *within a process run* — the operational failure mode, since the process OOMs long before
  it restarts. Honest limitation: it does **not** bound the heap across restarts, because
  replay repopulates the memtable. That needs truncation.
* **Slice 2b — WAL truncation**, under ADR-094's rule (truncate only below the minimum LSN
  durably committed in a catalog-referenced segment), plus the crash-recovery evidence gate.
  This is what makes the bound survive restart, and it is legal only once 2a proves the
  segment is readable. **Its real prerequisites are not what this TD said — see
  "Slice 2b is not gated on catalog registration".**
* **Slice 2c — background compaction.**

Known cost carried into 2c (from slice 2a): `merged_records` reads **every segment on every scan**. Bounding that needs compaction plus
  a per-segment oid index — slice 2c. Acceptable only because the path is default-OFF.

=== How to apply (slice 2 — the durable store; original plan, ordering corrected below)

Implement a durable relational record store behind the **existing `RecordStore` trait**, so
no caller changes. Precedent to mirror: `src/graph/cold_segment_store.rs:399`.

. Memtable gains a size/age threshold and flushes to a durable segment (format per ADR-094
  Decision 1 — Parquet-encoded Layer A for relational-only tables).
. Segment is registered in the catalog (see TD-USUB-4 for additive layouts).
. **Only then** is the corresponding WAL range eligible for truncation, per the WAL
  truncation rule ADR-094 adds to ADR-010: *truncate only below the minimum LSN durably
  committed in a catalog-referenced segment.*
. Background compaction merges small segments.

Ship default-OFF behind an env gate registered in `ENV_GATE_REGISTRY` (the guard rejects
unregistered vars), so the existing WAL-only path remains the default until the gate flips.

=== (ii) Catalog registration — why it is required, and what it must supply

This TD's "How to apply" lists catalog registration as step 2 and truncation as step 3, and the
slice-2a notes list catalog registration as a 2b precondition. Both understate it: **the derived
segment path is not reconstructible at recovery at all.**

`replay_wal_entries` — the only thing that repopulates a partition after a restart — reaches
`partition()` carrying just the WAL entry's `tenant_id` and `collection_id`, and
`CanonicalWalEntry` has **no namespace field**. A `DrPathBuilder` prefix needs the namespace
(`object_store_write_base_path` takes it from `TenantContext`), so recovery cannot re-derive
where a partition's segments were written. Two further movers compound it:

* the partition key's collection component is **gate-dependent** — `memtable_partition_keys`
  returns the stable object id under `PROXIMADB_WAL_OBJECT_ID_KEY` and the table name otherwise,
  so flipping an unrelated gate moves the derived path;
* during an oid cutover a single table has **two** partition keys (primary + legacy), hence two
  derived paths.

This is harmless in 2a precisely because segments are tracked in memory and never read after a
restart — the WAL is authoritative and replay rebuilds everything. It is fatal the moment
truncation lands: truncation may only reference a segment whose location is recorded somewhere
recovery can read, and a path derived from mutable, gate-dependent, namespace-less identity is
not that.

**So the order is: catalog registration of segments (TD-USUB-4 additive layouts) → then 2b
truncation.** Registration is not an implementation detail of truncation; it is what makes a
segment addressable at all. Recorded here rather than discovered during 2b.

Segment discovery (landed 2026-10-06) then split "find my segments" into **two different durable
facts with different owners**:

[cols="1,3"]
|===
| Fact | Who must supply it, and why

| *Where* — the prefix a partition's segments live under
| **The catalog.** WAL replay reaches `DirectTableRecordWriter::partition` carrying only the
  entry's `tenant_id` and `collection_id`; `CanonicalWalEntry` has no namespace field, so a
  `DrPathBuilder` prefix is **not reconstructible at recovery**. Still open.

| *What, and in what order* — the segment set and its sequence
| **The object names.** Recovered by listing the prefix and sorting. Landed here.
|===

Taking order from the names rather than from a catalog-side list is the load-bearing choice, and
it is a safety argument, not a convenience one: the window between "object landed" and "list
updated" is unavoidable (two writes, no transaction across them). If order lived in the list, a
segment written but not yet registered would be **invisible** — harmless today, and silent data
loss the moment 2b truncates the WAL that still holds its rows. With order intrinsic to the name,
such a segment is found anyway, and found *in the right place*. The catalog then supplies only the
prefix, which is a single durable fact per partition rather than a list that must stay in step
with every flush.

=== (i) Deletion-obligation marker + drain

==== What purge-on-DROP does NOT cover — an orphan reaper is still needed

Deletion on the **success path** is now correct. Deletion under **failure** is not, and cannot be
without new machinery, because the catalog drop commits *first*:

* `DropTable::execute` drops the catalog entry, *then* purges the record tier. By the time a purge
  failure is known the table is gone, so **nothing will ever retry it** — the objects have no
  catalog entry naming them. Returning an error would report failure for a table that really is
  dropped and send the client into a retry that finds nothing, so the failure is instead made
  loud and alertable (`error!` + `proximadb_record_tier_purge_failures_total`, the TD-USUB-9
  pattern). A counter is a smoke alarm, not a fix.
* **WAL replay of `RecordPartitionDrop` does not purge**, only `drop_partition_state`. The marker
  is appended before the purge precisely so a crash replays the drop — which is right for
  *correctness* (no resurrected rows) but means a crash in that window orphans the objects
  permanently. Making replay purge is not obviously safe either: replaying a stale drop marker
  could delete objects belonging to a table since recreated under the same name.

Both roads lead to the same missing piece: **a way to finish a deletion whose catalog entry is
already gone.**

==== Design decided 2026-10-02 — a POSITIVE-EVIDENCE obligation, not a sweep for absence

An earlier draft of this section proposed "a sweep can enumerate prefixes under a tenant and
delete those with no live table". **Do not build that.** It deletes on *inferred absence*: a
catalog that is briefly unreadable, a listing that races a `CREATE`, or an entry that has not yet
replicated all read as "no live table", and the reaper then destroys live data. A deletion path
must fail closed (mandate #1); absence-inference is fail-open by construction.

The correct shape is the one this repo already uses for the identical problem. **TD-COMPACT-13**
(`src/storage/engines/sst/retirement_ledger.rs`) records a compaction's failed deletes as a durable
*obligation* in a per-collection sidecar (`retire-pending.json`) beside the segments, tracks them in
a process-global set the read path filters against, and exposes a gauge so un-drained obligations
are visible rather than silent. Nothing is deleted because it *looks* unreferenced; it is deleted
because something recorded the intent to delete it.

**Prefer widening that module to writing a second one (mandate #12).** Exactly one thing blocks
direct reuse: it is **local-disk coupled** — `sidecar_path` / `load_ledger` / `write_ledger` use
`std::fs::read`/`write`/`rename` over `&Path`, while the relational spill path goes through
`Arc<dyn FileSystem>` and must work on S3/Azure. Visibility is **not** a barrier, despite looking
like one: those functions are `pub(crate)`, and in this monolith `pub(crate)` is crate-wide —
`src/services/` and `src/storage/` are the same root `proximadb` crate, so `record_spill.rs` can
call them today. So the cheapest honest path is to give the ledger a `&dyn FileSystem` and reuse
it; a parallel implementation should be the fallback, not the plan.

So: **on purge failure, write an obligation marker under the partition prefix, and drain markers
later.** The drain acts only on prefixes carrying a marker — positive evidence — never on a prefix
that merely lacks a catalog entry.

[IMPORTANT]
====
**The marker MUST record the exact object paths, and the drain MUST delete only those paths —
never re-list the prefix.** This is not an implementation detail; it is the whole safety argument,
and an earlier draft of this section omitted it and was therefore unsafe.

The partition prefix is derived from `(tenant, collection)`, so a table dropped and **recreated
under the same name writes to the same prefix**. A drain that found a marker and then re-listed the
prefix for `spill-*.parquet` would delete the *new* table's segments. Recording exact paths is what
makes that impossible, because the per-instance nonce added with the 2a wiring gives every segment
a name unique to the store instance that wrote it (`spill-{instance}-{seq:010}.parquet`) — so the
recorded names cannot match anything a later instance writes.

Note the precedent already gets this right: `PendingRetirement` records `inputs: Vec<String>`, an
explicit path list, not a directory to re-scan. Follow it literally.

The nonce is therefore load-bearing for two independent properties: it prevents a second store
instance from silently overwriting the first's segments (the reason it was added, #1945), and it
makes a stale deletion obligation safe to complete. Neither is stated at the field itself; both
depend on it.

NOTE: *Consolidation note (2026-10-15).* The per-instance nonce this block relies on was **removed**
by segment discovery (#1953): names are now `spill-{seq:016x}.parquet` with the sequence resumed
past the highest name *found*. The exact-paths rule still holds, but the claim that recorded names
"cannot match anything a later instance writes" is no longer established by the naming alone (a
partially-completed purge can leave the highest sequences absent, and a recreated table would then
reissue them). Re-establish this argument before building the drain.
====

The purge already has the exact list in hand at the moment of failure — it listed the prefix to
build the delete set — so recording it costs nothing extra.

**Why not put the obligation in the canonical WAL** (extend `RecordPartitionDrop` with the paths):
it would work, and it *would* be mixed-read-safe — canonical entries are encoded with
`rmp_serde::to_vec_named` (`src/services/canonical_wal.rs`), so field-name-keyed maps plus
`#[serde(default)]` tolerate old and new readers in both directions. It is rejected on blast
radius: `wal_entry.rs` carries **no `#[serde(default)]` field today**, so this would be the first
format evolution of the most safety-critical structure in the system, for a gap that is still
latent. A prefix-local marker needs no format change and is self-describing to anyone reading the
bucket directly.

==== Sequencing: build this WITH production wiring, not ahead of it

The gap cannot be reached today — `new_spilling` has no production caller, so no deployment can
orphan a spill object. Building marker + drain now would be machinery exercised only by its own
tests, and the part that actually needs validating — does a drain reliably finish an interrupted
DROP against a real object store? — is not testable until something real writes segments.
**The deletion-obligation item is therefore gated with "wire the two production call sites", not ahead of it** (named rather than numbered: the Open list has been renumbered twice, and a numeral cross-reference silently went stale each time), and
`proximadb_record_tier_purge_failures_total` is what keeps the gap visible meanwhile.

==== Discovery reclassifies the deletion-obligation item as a CORRECTNESS gate

Discovery introduces no new gap, but it changes what an existing one costs, and that moves an
item's priority rather than its content.

The partition prefix is a pure function of `(tenant, collection)`, and with
`PROXIMADB_WAL_OBJECT_ID_KEY` default-OFF the collection key is the bare table **name**. So a
table dropped and recreated under the same name reuses its predecessor's prefix — the same
property that forced the obligation marker to record *exact paths* rather than a prefix
(2026-10-02). DROP purges the prefix before releasing the partition, so a surviving object
requires that purge to have **failed or crashed part-way** — precisely the window open item (i)
exists to close. Note also that WAL replay's `DropTable` arm calls only `drop_partition_state`,
never purge, and its comment asserts "a table recreated post-drop starts empty".

Before discovery, an object surviving that window cost **wasted storage**. With discovery it is
found and **served**: a dropped table's rows surface in a recreated one. So:

* The **deletion-obligation marker + drain is a correctness prerequisite for enabling the spill
  gate**, not hygiene deferrable behind it. The Open list keeps it first for that reason now,
  rather than only because it was discovered first.
* `an_unpurged_prefix_is_served_to_the_next_store_at_that_path` pins the premise (a second store
  over a non-empty prefix serves what the first left) rather than asserting resurrection as
  intended behaviour, so the hazard is a failing precondition on the record and not a hypothetical.

This is reachable only through an already-known gap, in a subsystem that is default-OFF and still
has no production caller — but it is the reason discovery alone does not license turning the gate
on. The honest sequencing is: obligation drain → enable. Discovery is what makes a durable
artefact *mean* something; the drain is what makes the prefix *trustworthy*.

=== (iv) Slice 2b is not gated on catalog registration — found 2026-10-02

This TD has said twice that catalog registration of segments is what gates 2b truncation. That is
wrong, or at least badly incomplete: **registration records where a segment is, but truncation
needs to know which WAL range it covers, and that information does not exist anywhere today.**

==== Finding 1 — the LSN is produced and thrown away

`ProximaRecord` has **no LSN field**, and the `proximadb-records` crate has no LSN concept at all
(checked: no `lsn` / `sequence_number` anywhere in it). So a flushed segment cannot record "every
record in here was durably committed at or below LSN X" — the exact quantity ADR-094's rule needs.

The LSN is not unavailable, it is **discarded**. `TableWalAppender::append_operations` returns
`Vec<CanonicalWalEntry>`, and `CanonicalWalEntry.sequence_number` is the LSN — but the write path
calls it as `self.wal_appender.append_operations(operations, tenant_id).await?;` with **no
binding** (`record_store.rs`, the `write_mutations` path), so every LSN is dropped on the floor
before the records reach the partition store. This is the same shape as the object size in
TD-USUB-8 slice 0 and the partition identity in 2a: *the value was already in hand.*

==== Finding 2 — a "WAL high-water at flush time" watermark would be UNSAFE

The tempting cheap fix is to skip per-record LSNs and have `flush()` stamp the segment with the
WAL high-water mark observed at flush time. **That loses data.** The WAL append and the memtable
insert are two separate, non-atomic steps: `append_operations(...).await?` completes, and only
then does the loop call `partition.upsert_record(record)`. So a record whose append has committed
but whose insert has not yet happened when `flush()` takes its snapshot is **counted under the
high-water mark while present in no segment.** Truncating below that mark discards the only
durable copy.

[WARNING]
====
**This needs no concurrency whatsoever — one ordinary multi-row statement is enough.**

`write_mutations` appends the **entire batch** in a single `append_operations` call, which assigns a
sequence number to every operation and bumps the per-collection high-water *before returning*. Only
then does a second loop insert the records one at a time. And `flush()` is triggered from inside
`upsert_record` the moment `memtable.len() >= flush_threshold`.

So on a single-task `INSERT` of N rows, if row 0 crosses the threshold, `flush()` fires mid-loop and
its snapshot **excludes rows 1..N** — whose LSNs are already committed, and already at or below
anything a high-water scheme would stamp on that segment. Concurrent writers widen the window; they
are not required to open it.

An earlier draft of this section implied the hazard needed a race. It does not, and the difference
matters: a race is something a reviewer may discount as unlikely, whereas this would fire on the
first multi-row insert that straddles the flush threshold.

**To be exact about what is and is not broken today: nothing.** This is a hazard of a design that
has *not been built*. It requires all four of — the watermark truncation scheme (does not exist),
the spill store rather than the default memtable, its gate set, and `new_spilling` wired to
production (it is not). No deployment can hit this. The point of recording it is that every one of
those four becomes true in the course of finishing 2b, and at that moment the shortcut looks
correct and is not.
====

The safe quantity is therefore the **minimum LSN among records not yet in a durable segment**,
which cannot be derived from a single watermark and does need per-record LSN tracking. Note the
memtable is a `DashMap` keyed by oid, not an LSN-ordered structure, so "flushed up to LSN N" is
not a property it can report.

==== What 2b actually requires, in order

. **Plumb the LSN to the store.** ✅ **Landed 2026-10-03.** `RecordStore` gained a *defaulted*
  `upsert_record_at_lsn` rather than a widened `upsert_record` — there are 11 implementors (graph,
  document, cedar, the test doubles) with no interest in relational WAL retention, so a signature change was the
  wrong instrument. `write_mutations` binds the `append_operations` result it used to discard;
  index *i* of those entries is the LSN for `storage_actions[i]`, which holds because the two are
  pushed in lockstep and the appender returns entries in input order **after `sync_data()`** (so a
  bound LSN is durable by construction). A length mismatch **disables** association rather than
  guessing a mapping, because a wrong LSN here becomes a wrong truncation point later.
. **Track the unflushed minimum** per partition, so a safe truncation point exists at all.
  ✅ **Landed 2026-10-03.** `SpillRecordStorage` keeps `oid → lsn` for *resident* rows only, beside
  the memtable rather than on `ProximaRecord` — so the central record type is untouched and the LSN
  never has to survive the Parquet round trip (a flushed row is durable in its segment and stops
  constraining the WAL, which is exactly when the association is dropped). `min_unflushed_lsn`
  **fails closed**: if any resident row is untracked (written via plain `upsert_record`) it returns
  an error telling the caller not to truncate, rather than a minimum that silently excludes that
  row. Pinned by `min_unflushed_lsn_is_not_the_high_water_mark`, where a resident row at LSN 40
  sits behind flushed rows at 80/90 — so the correct answer and a high-water answer differ, and
  truncating at the high-water would lose it.
. **Persist tombstones into the segment.** Found 2026-10-03 while implementing the minimum, and
  it is a *correctness* prerequisite, not a nicety. A tombstone is in-memory only and is **not**
  cleared by `flush()` — it must keep suppressing the segment copy until compaction removes that
  segment, so only a re-insert or a purge clears it. The sole durable evidence of a post-flush
  delete is therefore its WAL entry. A minimum computed over resident *rows* reports "no
  constraint" in that state, and truncating past it resurrects the deleted row on restart
  (mandate #16a). `min_unflushed_lsn` consequently **fails closed while any tombstone exists**,
  which means truncation cannot make progress at all until tombstones are durable. This TD's
  slice-2a notes already listed tombstone persistence as a hard 2b precondition; it is now also
  enforced in code rather than only written down.
. **Register segments in the catalog** — still needed, because truncation may only reference a
  segment whose location recovery can read (the reason recorded under "Correction" above). But it
  is the *last* prerequisite, not the first.
. Then truncation, behind the crash-recovery evidence gate below.

**Had 2b been built to this TD's previous ordering** — register segments, then truncate — the
result would have been a truncation point derived from a watermark that is unsafe by construction,
i.e. silent data loss on recovery. Recorded here rather than discovered then.

=== More gates on 2b, recorded by the tombstone-persistence review rounds

==== What this did NOT close, and why 2b is now gated on it

The residents/written split fixes which KEYS the post-commit loop evicts. It does not make the
eviction conditional on the VALUE at a key still being the one this flush made durable — and
`memtable.remove` is unconditional. `upsert_record` does not take `flush_guard`, and the window is
the whole object-store PUT, so a newer value written during a flush is discarded by it.

Today that is a stale read only: the WAL still holds the newer value and replay restores it. **Once
slice 2b truncates on `min_unflushed_lsn`, it becomes permanent and silent** — which is why
**TD-USUB-15 is now a stated prerequisite of 2b**, recorded in the Open list above. The tombstone
half of this exact hazard is what this change closed; the resident half is the dominant one, because
its window is a PUT rather than a few instructions.

Also filed from the same review: **TD-USUB-16** — appending tombstones after residents with no
dedup means one oid can appear live-then-dead in a single segment, and the three read surfaces then
disagree (`merged_records` takes the last row, `get_record`/`delete_record` the first). Narrow
(needs preemption between two adjacent non-`await` statements) and a consistency regression rather
than a data-loss one, since the pre-change behaviour was a uniformly-absent lost write. (Later re-triaged as fail-open under 2b and **fixed in this slice** — see History and TD-USUB-16.)

* **A non-spill partition answers `Ok(None)`, which slice 2b must not read as "safe to truncate".**
  `MemtableRecordStorage` overrides neither `upsert_record_at_lsn` nor `min_unflushed_lsn`, so it
  discards every LSN and reports no constraint while its rows exist only in the WAL. That is
  fail-OPEN, and the round-4 fallback (an empty tenant now gets a memtable) widened the set of
  partitions that answer that way. **Slice 2b must treat a store with no durable segment path as an
  unconditional refusal, not as `Ok(None)`** — otherwise "respect every store's answer" is
  satisfied by a store that has no answer. Recorded here as a 2b prerequisite; the fallback also
  now logs, since `""` is the normal tenant key for a single-tenant server today and a silent
  fallback would leave an operator who set the gate with no spill partitions and no signal.

* **The trait `flush` override has no production caller, so the defect it addresses is still open.**
  `DirectWalTableRecordStore` has no flush/shutdown/checkpoint method and never iterates
  `self.partitions` except in `partition()`, `partitions_for()` and `drop_partition_state()`; the
  only `dyn RecordStore` flush caller in the tree is the graph `flush_wal` path. So graceful
  shutdown still drops the buffer and `min_unflushed_lsn`'s "flush, then re-ask" is still
  uncarryable for a relational partition. The override is necessary and correct — dispatch is
  pinned by a test — but **not sufficient**, and round 3's message presented it as closing the
  defect. **Slice 2b additionally requires the caller** (`flush_partitions()` wired to shutdown);
  it is deliberately not added here, because an uncalled method is the #1945 dead-wiring class
  this TD already learned once.

* **The untenanted partition** keeps today's behaviour (an unbounded memtable) — still this TD's open defect for that case.

* **The `min_unflushed_lsn` safety argument covered only the safe direction.** "Absent from the set
  while NOT durable" is reachable via an orphan from a write that failed after the object landed —
  filed as **TD-USUB-18**, mitigated fail-closed here, and **now a gate on slice 2b** alongside
  TD-USUB-15.

* **Mandate #8 note.** A spill segment can now contain dead rows, and a tombstone-only flush
  produces a Parquet file whose schema is the 7 system columns and nothing else. Nothing on disk
  distinguishes a pre- from a post-change segment; correctness rests on deployment order (the
  `is_dead` filtering from #1952 and the newest-first rule from #1953 round 7). Acceptable only
  because the path is default-OFF with no production caller, so no data exists in either form — which
  is also the cheapest moment to add a marker. The zero-user-column shape is additionally a new
  constraint on open item (ii): anything that unions schemas across the prefix (e.g. DataFusion)
  must tolerate it.

=== Residual costs of segment discovery (and one residual resurrection), stated rather than implied

Recorded because an earlier draft of this section claimed the failed-purge case was the *only*
remaining resurrection, which is not true.

* **Concurrently-live instances (outside the single-writer design).** `drop_partition_state` only
  removes the map entry, so a caller still holding the old `Arc` keeps writing while the next
  access builds a second store over the same prefix. Discovery runs once per store, so a stale
  store's flush that lands *after* the new store's listing is invisible to it: a `delete_record`
  for a row living only in that segment records no tombstone and returns `false`, and a third
  instance then discovers the segment and serves the deleted row. Pre-discovery the same race lost
  the row instead. Neither is acceptable, and neither is in scope: one store per
  `(tenant, collection)` per process and one process per WAL is the design, and the fix if that
  ever changes is a lease, not a nonce — a nonce makes names unique while destroying the ORDER all
  three read paths depend on, which is the trade this change deliberately reversed.
* **A LIST on first touch of every partition.** Discovery adds one round-trip before the first
  read, write or delete a partition serves — and on an object store that LIST is *recursive* over
  the whole collection prefix, so it paginates at 1000 keys and returns the WAL/PAX/index subtrees
  too (all correctly skipped, but paid for), plus one existence check per spill-shaped candidate
  whose url does not match canonically. Under the co-design mandate round-trips are the
  dominant cost term, so this is the change's real cost, and it is not yet in the query-scoped
  I/O trace. It is paid once per store, not per query.
* **A partially-written orphan becomes a permanent read failure.** `flush`'s comment concedes only
  storage cost for an object that landed before the write failed. On the local backend
  `write_if_absent` creates the file and *then* writes it, so a mid-write ENOSPC/EIO leaves a
  truncated object under a canonical name. Before discovery that object was invisible (the segment
  list was RAM-only); now it is adopted and decoded on every read. Truncation routes to the legacy
  reader (Parquet needs `PAR1` at both ends), so the outcome is a decode error — the partition is
  unreadable until a DROP, not corrupted. S3/Azure are immune (`PutMode::Create` is atomic).
* **Discovery widens the window in which tombstones are minted.** `delete_record` inserts a
  tombstone whenever `segments` is non-empty, and `tombstones` is unbounded, not counted toward
  `flush_threshold`, and cleared only by a re-insert or a purge. Before discovery a fresh instance
  had no segments until it flushed, so its early deletes minted none; now the first delete can.
  That is the intended resurrection fix, but it means a DELETE-heavy workload grows the heap by a
  vector the module's "bounds resident memory within a process run" claim does not cover. Pre-existing
  in shape, amplified here, and worth bounding before the gate is enabled.
* **A permanent discovery error re-LISTs per request.** `OnceCell::get_or_try_init` does not cache
  failures — correct for a transient LIST error, since the next call retries. But for a permanent
  one (an unplaceable name, a nested object, an exhausted sequence) every read, write and delete
  pays a LIST and then fails, and does so while holding `flush_guard`, so the partition
  serializes on a failing LIST. Fail-closed is the right outcome; the cost of *staying* closed is
  unbounded. Bounding it (cache the permanent classes, keep retrying the transient ones) is
  deferred, and the escape hatch is a DROP.

Also noted in passing, pre-existing and not introduced here: `SpillRecordStorage` never overrides
`RecordStore::flush`, whose default is a no-op documented as something a buffered store "MUST
override". The spill store's `flush` is an *inherent* method with a different signature, so
`RecordStore::flush()` through `Arc<dyn RecordStorage>` does nothing. Not a data-loss path today
(the WAL replays every resident row), but the "flush always discovers first" reasoning above
covers only the inherent method. (Since #1957 the trait override exists; its production caller does
not — see "More gates on 2b".)

=== The deadlock invariant is enforced by prose, deliberately

`ensure_discovered` acquires `flush_guard` inside the `OnceCell` initializer, so a caller that
invoked it *while already holding* that guard would deadlock permanently — the holder awaits the
cell while the initializer awaits the guard. Every call site is correct today (verified by tracing
all three holders: `flush` and `delete_record` discover before taking it, `purge_durable_objects`
never discovers), and after the first success the cell short-circuits without touching the guard
at all, so the window is the first call only.

There is no cheap structural guard: `tokio::sync::Mutex` exposes no ownership query, so neither a
`debug_assert` nor a type-state can detect the violation. The alternative — dropping the guard —
is not available, because purge CLEARS `segments` under it and a discovery whose listing straddled
a purge would republish deleted paths. So the invariant stays a comment, and this records why that
is a choice rather than an oversight.
