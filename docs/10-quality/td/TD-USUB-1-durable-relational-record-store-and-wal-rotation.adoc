== The finding

`MemtableRecordStorage` (`src/services/record_memtable.rs:19-21`) is a
`DashMap<String, ProximaRecord>`. Its complete method set is `new`, `replay_wal_entries`,
`len`, `is_empty`, `upsert_record`, `get_record`, `delete_record`, `scan_records`,
`scan_records_with_options`, `scan_records_filtered`. There is **no flush, evict, spill, or
compact path of any kind**.

Durability for every pgwire relational table is therefore 100% replay of a **single file**,
`{data_dir}/pgwire/canonical-records.wal` (`src/network/shared_services.rs:1971-1977`),
appended by `FramedTableWalAppender::append_operations` (`src/services/canonical_wal.rs:133`)
via `DirectWalTableRecordStore::write_mutations` (`src/services/record_store.rs:1973`).

Consequences, all present today:

* **Unbounded heap.** Every row ever inserted stays resident for the process lifetime.
* **Unbounded WAL.** Nothing truncates or rotates it; recovery time grows without bound.
* **No tiering.** Relational data never reaches object storage, so none of the PAX/Parquet
  pruning, caching or cost machinery applies to it.
* **Misleading route name.** `TableRecordStoreRoute::for_schema` sends relational/HTAP/OLAP
  to a `ParquetIcebergStorage` arm (`src/services/record_store.rs:194-196`), but the pgwire
  wiring passes the canonical WAL store into that slot
  (`src/services/dml/mod.rs:948-952`) — no Parquet is written on INSERT. The name should be
  corrected as part of this work.

== Slicing — why slice 1 adds no persistence

The obvious move is "spill the memtable to a durable segment". That is slice 2, deliberately,
for two reasons.

**The module contract forbids it today.** `record_memtable.rs` states that the store "is
rebuildable from Layer 0 entries and **must not grow independent persistence**" — the
ADR-010/ADR-020 position that the canonical WAL is the authority. Adding a durable copy is a
change to that contract, not an implementation detail, and it is exactly what ADR-094's new
**WAL truncation rule** exists to govern: once the WAL is truncated, a segment becomes
recovery-authoritative *by reference*.

**Mandate #6 says measure first.** This TD's own evidence gate asks for resident-heap growth
per 1M rows and WAL size/replay time. Building a durable store before those numbers exist is
building against an assumption.

So **slice 1 does two things that cannot regress anything**:

* **Observe** — `proximadb_relational_memtable_records`, a gauge of live records, so growth is
  visible in the existing Prometheus surface.
* **Bound, fail-closed** — an optional per-partition record cap
  (`PROXIMADB_RELATIONAL_MEMTABLE_MAX_RECORDS`). The write that would exceed it is rejected
  with an actionable error naming the knob, instead of the process being OOM-killed. Default
  is **unbounded**, so with no configuration behaviour is byte-identical to before.

Slice 1 changes no recovery semantics and adds no durable state, so it **cannot lose data** —
the property worth having in a first increment that touches durability.

Two design details worth recording:

* **An update at the cap is admitted.** Only a write that *adds* an oid can exceed the bound.
  Rejecting in-place updates would make a full table permanently un-correctable — you could
  not even shrink it — which is worse than the condition being guarded.
* **An invalid cap reads as unset, never as zero.** A typo'd env var must not silently turn
  the database read-only.

**Known limitation, stated rather than hidden:** the cap counts *records*, not bytes. Row
width varies, so it is a proxy for memory, not a guarantee. Byte accounting needs a size
estimator `ProximaRecord` does not have; it belongs with slice 2, where eviction becomes
possible.

== Slice 2 re-scoped (2026-09-22) — two findings from starting it

**Finding 1 — the encoder could not round-trip a tombstone.** Slice 2 spills to an immutable
segment, so deleting a row already written can no longer remove it: deletion *necessarily*
becomes a `valid_to_ns` tombstone. The canonical Parquet encoder did not persist
`valid_to_ns` (nor `oid`, nor `tenant_id`), so a deleted row would have read back **live** —
a resurrection bug that would have been *built in* rather than found. Closed first as
**TD-USUB-11**; slice 2 is its first consumer.

**Finding 2 — eviction breaks UNIQUE/PK unless reads are served through.**
`ensure_unique_index_built` (`record_store.rs:1866`) builds UNIQUE/PK enforcement by
**scanning the partition store**. A store that evicts flushed rows from memory must therefore
still return them from `scan_records`, or duplicate-key enforcement silently stops catching
duplicates. The durable store is consequently a read-merge (memtable ∪ segments, memtable
wins, tombstones suppress), not a simple spill.

**Consequent slicing.** The filed step list below is more than one reviewable PR, and its
riskiest element (WAL truncation) is the one that can lose data. So:

* **Slice 2a — the durable spill path.** Read-merge store behind the existing `RecordStore`
  trait, flush at a threshold, catalog registration, default-OFF. **No WAL truncation**, so
  the WAL stays authoritative and the change cannot lose data: recovery replays exactly as
  today, and segments are a read-side representation of already-durable rows. Bounds the heap
  *within a process run* — the operational failure mode, since the process OOMs long before
  it restarts. Honest limitation: it does **not** bound the heap across restarts, because
  replay repopulates the memtable. That needs truncation.
* **Slice 2b — WAL truncation**, under ADR-094's rule (truncate only below the minimum LSN
  durably committed in a catalog-referenced segment), plus the crash-recovery evidence gate.
  This is what makes the bound survive restart, and it is legal only once 2a proves the
  segment is readable.
* **Slice 2c — background compaction.**

A further prerequisite for 2a: `storage_factory` is `Fn() -> Arc<dyn RecordStorage>`
(`record_store.rs:1727`) and receives **no partition identity**, so a durable store cannot
derive its own `DrPathBuilder` path. The signature must take `(tenant_id, collection)`. Note
the shared-mode probe at `:1991` calls the factory purely for an `Arc::ptr_eq` comparison and
must be updated with it.

== Slice 2a as landed (2026-09-22)

`src/services/record_spill.rs` — `SpillRecordStorage`, implementing the existing
`RecordStore` + `RecordScan` traits so no caller signature changes.

* **Flush** at a resident-row threshold: infer the schema from the resident rows
  (`infer_proxima_schema`), encode with TD-USUB-11's system-column encoder, write one
  fresh-named Parquet object, then evict. Resident rows are dropped only **after** the
  object is durable; a crash before that leaves them resident and the WAL replays them
  either way.
* **Read-merge** over `memtable ∪ segments`: memtable wins (strictly newer), a newer segment
  wins over an older one, tombstones suppress. Segments are decoded through
  `read_segment_records` — the canonical mixed-format router, which can decode Parquet only
  because TD-USUB-5 added the `PAR1` arm. The three slices compose exactly as ADR-094
  intended.
* **Tombstones** because a segment is immutable: once flushed, a row can only be suppressed,
  not removed. Re-inserting an oid clears its tombstone.
* **Default OFF** (`PROXIMADB_RELATIONAL_SPILL_MAX_RESIDENT` unset ⇒ never flush), so the
  shipped behaviour is the plain memtable's.

=== What it bounds, stated honestly

Resident memory **within a process run** — the operational failure mode, since the process is
OOM-killed long before it restarts. It does **not** bound the heap across restarts: the WAL
is still authoritative and replay repopulates the memtable in full. That needs slice 2b.

Keeping truncation out is precisely what makes 2a **unable to lose data**: recovery is
byte-for-byte what it is today, and a segment is a read-side representation of rows the WAL
already made durable. Deleting every segment would leave the store correct after replay.

=== Known costs, not hidden

* `merged_records` reads **every segment on every scan**. Bounding that needs compaction plus
  a per-segment oid index — slice 2c. Acceptable here only because the path is default-OFF.
* Tombstones are in-memory. They are rebuilt by WAL replay (a delete is a WAL entry), so they
  are not a durability hole today — but slice 2b must persist them into the segment/catalog
  before truncation removes the WAL entries that reconstruct them. **This is a hard
  precondition on 2b, recorded here so it is not discovered late.**
* Segment registration in the catalog (additive layouts, TD-USUB-4) is **not** wired yet;
  segments are tracked in memory. Catalog registration is required before truncation can
  reference a segment, i.e. also a 2b precondition.

== How to apply (slice 2 — the durable store)

Implement a durable relational record store behind the **existing `RecordStore` trait**, so
no caller changes. Precedent to mirror: `src/graph/cold_segment_store.rs:399`.

. Memtable gains a size/age threshold and flushes to a durable segment (format per ADR-094
  Decision 1 — Parquet-encoded Layer A for relational-only tables).
. Segment is registered in the catalog (see TD-USUB-4 for additive layouts).
. **Only then** is the corresponding WAL range eligible for truncation, per the WAL
  truncation rule ADR-094 adds to ADR-010: *truncate only below the minimum LSN durably
  committed in a catalog-referenced segment.*
. Background compaction merges small segments.

Ship default-OFF behind an env gate registered in `ENV_GATE_REGISTRY` (the guard rejects
unregistered vars), so the existing WAL-only path remains the default until the gate flips.

== Slice 2a wiring as landed (2026-09-27) — and a correction to this TD's ordering

The factory prerequisite above is now implemented: `storage_factory` takes
`(tenant_id, collection)`, which [`partition`] already had in hand and discarded. `new_spilling`
builds a `SpillRecordStorage` per partition, so slice 2a's store is no longer unreferenced code.

**Default-OFF means the legacy TYPE, not a disabled new one.** With
`PROXIMADB_RELATIONAL_SPILL_MAX_RESIDENT` unset, `new_spilling` builds a
`MemtableRecordStorage` — exactly what `new_partitioned` builds — rather than a spill store
configured never to flush. A spill store with `flush_threshold: None` would *behave* like the
memtable while running different read-merge code on every production read. Mandate #8 asks for
the legacy path when the marker is absent, and "the same type" is the only version of that
claim which cannot drift.

=== The shared-mode probe had to go, not just move

`drop_table_records` detected shared-storage mode by **calling the factory** and comparing the
product to a stored partition with `Arc::ptr_eq`. That worked only because every factory was
side-effect-free. A factory that builds a durable store performs I/O and claims an object path,
so probing it would construct a partition store on every `DROP TABLE` purely to discard it.
Replaced with a `shared_storage` flag recorded at construction — which is also simply the truth,
since only `new` produces that shape.

=== Correction: catalog registration must come BEFORE production wiring, not after

This TD's "How to apply" lists catalog registration as step 2 and truncation as step 3, and the
slice-2a notes list catalog registration as a 2b precondition. Both understate it: **the derived
segment path is not reconstructible at recovery at all.**

`replay_wal_entries` — the only thing that repopulates a partition after a restart — reaches
`partition()` carrying just the WAL entry's `tenant_id` and `collection_id`, and
`CanonicalWalEntry` has **no namespace field**. A `DrPathBuilder` prefix needs the namespace
(`object_store_write_base_path` takes it from `TenantContext`), so recovery cannot re-derive
where a partition's segments were written. Two further movers compound it:

* the partition key's collection component is **gate-dependent** — `memtable_partition_keys`
  returns the stable object id under `PROXIMADB_WAL_OBJECT_ID_KEY` and the table name otherwise,
  so flipping an unrelated gate moves the derived path;
* during an oid cutover a single table has **two** partition keys (primary + legacy), hence two
  derived paths.

This is harmless in 2a precisely because segments are tracked in memory and never read after a
restart — the WAL is authoritative and replay rebuilds everything. It is fatal the moment
truncation lands: truncation may only reference a segment whose location is recorded somewhere
recovery can read, and a path derived from mutable, gate-dependent, namespace-less identity is
not that.

**So the order is: catalog registration of segments (TD-USUB-4 additive layouts) → then 2b
truncation.** Registration is not an implementation detail of truncation; it is what makes a
segment addressable at all. Recorded here rather than discovered during 2b.

=== Two further preconditions found by reviewing the wiring

**DROP TABLE orphans every flushed segment, and `PURGE` does not purge.** `SpillRecordStorage`
has no delete path at all — no `filesystem.delete`, no purge method — and `drop_table_records`
clears only in-RAM state (`drop_partition_state`). Once the gate is on and the production sites
are wired, `DROP TABLE … PURGE` would drop the catalog entry and the partition map entry while
every `spill-*.parquet` object stays in the bucket forever, with nothing referencing it. That is
unbounded KSU billing against the tenant and a data-deletion gap under a statement whose whole
contract is deletion.

[NOTE]
====
**Fixed 2026-09-30 — and the sentence that stood here was wrong.** It said "the catalog reference
is what makes the objects findable for deletion, so neither can ship without the other."

Deletion needs no catalog. `base_path` is derived deterministically from `(tenant, collection)` —
which is exactly what the slice-2a wiring established — so the **prefix is** the reference.
`purge_durable_objects` lists it and deletes the `spill-*.parquet` objects it finds.

Listing the prefix is also strictly better than any tracked list would have been: it reclaims
segments written by *earlier* store instances at the same prefix — the orphans a restart or a
`drop_partition_state` eviction leaves behind, which neither this instance's in-memory list nor a
catalog row written by a previous process would surface.

Catalog registration remains a precondition for **2b truncation** (which must reference a segment
whose location recovery can read, per ADR-094's rule). It was never a precondition for deletion.
Coupling the two would have held a real data-deletion fix behind unrelated work.
====

==== What purge-on-DROP does NOT cover — an orphan reaper is still needed

Deletion on the **success path** is now correct. Deletion under **failure** is not, and cannot be
without new machinery, because the catalog drop commits *first*:

* `DropTable::execute` drops the catalog entry, *then* purges the record tier. By the time a purge
  failure is known the table is gone, so **nothing will ever retry it** — the objects have no
  catalog entry naming them. Returning an error would report failure for a table that really is
  dropped and send the client into a retry that finds nothing, so the failure is instead made
  loud and alertable (`error!` + `proximadb_record_tier_purge_failures_total`, the TD-USUB-9
  pattern). A counter is a smoke alarm, not a fix.
* **WAL replay of `RecordPartitionDrop` does not purge**, only `drop_partition_state`. The marker
  is appended before the purge precisely so a crash replays the drop — which is right for
  *correctness* (no resurrected rows) but means a crash in that window orphans the objects
  permanently. Making replay purge is not obviously safe either: replaying a stale drop marker
  could delete objects belonging to a table since recreated under the same name.

Both roads lead to the same missing piece: **a way to finish a deletion whose catalog entry is
already gone.**

==== Design decided 2026-10-02 — a POSITIVE-EVIDENCE obligation, not a sweep for absence

An earlier draft of this section proposed "a sweep can enumerate prefixes under a tenant and
delete those with no live table". **Do not build that.** It deletes on *inferred absence*: a
catalog that is briefly unreadable, a listing that races a `CREATE`, or an entry that has not yet
replicated all read as "no live table", and the reaper then destroys live data. A deletion path
must fail closed (mandate #1); absence-inference is fail-open by construction.

The correct shape is the one this repo already uses for the identical problem. **TD-COMPACT-13**
(`src/storage/engines/sst/retirement_ledger.rs`) records a compaction's failed deletes as a durable
*obligation* in a per-collection sidecar (`retire-pending.json`) beside the segments, tracks them in
a process-global set the read path filters against, and exposes a gauge so un-drained obligations
are visible rather than silent. Nothing is deleted because it *looks* unreferenced; it is deleted
because something recorded the intent to delete it.

**Prefer widening that module to writing a second one (mandate #12).** Exactly one thing blocks
direct reuse: it is **local-disk coupled** — `sidecar_path` / `load_ledger` / `write_ledger` use
`std::fs::read`/`write`/`rename` over `&Path`, while the relational spill path goes through
`Arc<dyn FileSystem>` and must work on S3/Azure. Visibility is **not** a barrier, despite looking
like one: those functions are `pub(crate)`, and in this monolith `pub(crate)` is crate-wide —
`src/services/` and `src/storage/` are the same root `proximadb` crate, so `record_spill.rs` can
call them today. So the cheapest honest path is to give the ledger a `&dyn FileSystem` and reuse
it; a parallel implementation should be the fallback, not the plan.

So: **on purge failure, write an obligation marker under the partition prefix, and drain markers
later.** The drain acts only on prefixes carrying a marker — positive evidence — never on a prefix
that merely lacks a catalog entry.

[IMPORTANT]
====
**The marker MUST record the exact object paths, and the drain MUST delete only those paths —
never re-list the prefix.** This is not an implementation detail; it is the whole safety argument,
and an earlier draft of this section omitted it and was therefore unsafe.

The partition prefix is derived from `(tenant, collection)`, so a table dropped and **recreated
under the same name writes to the same prefix**. A drain that found a marker and then re-listed the
prefix for `spill-*.parquet` would delete the *new* table's segments. Recording exact paths is what
makes that impossible, because the per-instance nonce added with the 2a wiring gives every segment
a name unique to the store instance that wrote it (`spill-{instance}-{seq:010}.parquet`) — so the
recorded names cannot match anything a later instance writes.

Note the precedent already gets this right: `PendingRetirement` records `inputs: Vec<String>`, an
explicit path list, not a directory to re-scan. Follow it literally.

The nonce is therefore load-bearing for two independent properties: it prevents a second store
instance from silently overwriting the first's segments (the reason it was added, #1945), and it
makes a stale deletion obligation safe to complete. Neither is stated at the field itself; both
depend on it.
====

The purge already has the exact list in hand at the moment of failure — it listed the prefix to
build the delete set — so recording it costs nothing extra.

**Why not put the obligation in the canonical WAL** (extend `RecordPartitionDrop` with the paths):
it would work, and it *would* be mixed-read-safe — canonical entries are encoded with
`rmp_serde::to_vec_named` (`src/services/canonical_wal.rs`), so field-name-keyed maps plus
`#[serde(default)]` tolerate old and new readers in both directions. It is rejected on blast
radius: `wal_entry.rs` carries **no `#[serde(default)]` field today**, so this would be the first
format evolution of the most safety-critical structure in the system, for a gap that is still
latent. A prefix-local marker needs no format change and is self-describing to anyone reading the
bucket directly.

==== Sequencing: build this WITH production wiring, not ahead of it

The gap cannot be reached today — `new_spilling` has no production caller, so no deployment can
orphan a spill object. Building marker + drain now would be machinery exercised only by its own
tests, and the part that actually needs validating — does a drain reliably finish an interrupted
DROP against a real object store? — is not testable until something real writes segments.
**Open item (i) is therefore gated with (iii), not ahead of it**, and
`proximadb_record_tier_purge_failures_total` is what keeps the gap visible meanwhile.

**A deterministic base path needs a per-instance nonce in the segment name.** The counter
(`next_segment`) is unique only within one store instance, and this PR made `base_path` a pure
function of `(tenant, collection)`. A second store at the same path — after a restart, or after
`drop_partition_state` evicts the partition and the next access rebuilds it — restarts at 0 and
re-issues `spill-0000000000`; `FileSystem::write` with `options: None` takes the overwrite
branch and clobbers the earlier object **silently**. Fixed here by putting a per-instance UUID in
the name and committing through `write_if_absent`, so a collision fails loudly instead of
destroying a segment. Worth recording because the fresh-name property was *vacuously* true while
the store had no callers: **wiring is what turned a correct-looking comment into a false one.**

**`FileOptions::overwrite` is not the way to get fail-closed writes, and a first attempt at this
fix used it.** Only `LocalFileSystem::write` consults that flag; `aws_s3`, `azure_blob` and
`gcs_store` ignore it and issue an unconditional PUT. A unit test on the local backend passes
either way, so the gap is invisible in CI — the guarantee would have been absent precisely on the
cloud deployments it exists for. The codebase's designated primitive is `write_if_absent`: a real
conditional create (`PutMode::Create` on S3, `create_new(true)` locally) whose trait contract
forbids emulating it with a racy exists-then-write, and whose default impl errors rather than
silently downgrading.

Checked rather than assumed: **no other live call site has this hole today.** The two remaining
`overwrite: false` occurrences in the storage layer are both inert — the SST flush path
(`engines/sst/flush/mod.rs`) already commits through `write_if_absent`, and RAPTOR
(`engines/raptor/engine.rs`) stores the options in a field nothing reads. So this is a **latent
hazard to avoid reusing**, not a live defect elsewhere: `FileOptions { overwrite: false }` on a
plain `write` looks like a safety property and is one only on the local backend.

== Evidence gate (mandate #6)

Before any default flip, record in `docs/_internal/roadmap/BENCHMARK_EVIDENCE.toml`:

* resident-heap growth per 1M inserted rows, before vs after;
* WAL size and recovery (replay) time at a fixed row count, before vs after;
* a crash-recovery test proving no data loss across flush + truncation, including the
  boundary case where a crash lands between segment write and catalog reference.
