| Field | Value
| Status | **Done.** All 11 document conformance queries are accurate on pgwire; root-caused into ADR-043 and fixed by its invariants (#480, #486, #502, #507).
| Severity | High — silent wrong answers (empty / divergent results), not errors
| Component | Document modality — JSON-path SELECT projection/filter (`src/network/postgres/`, `src/datafusion/udf.rs`)
| Relates to | link:../../12-design/adr/ADR-040-conformance-accuracy-ratchet.adoc[ADR-040] (TD-182 umbrella); link:../../12-design/adr/ADR-043-unified-relational-expression-evaluation.adoc[ADR-043]; link:TD-186-relational-expr-eval-unification.adoc[TD-186]

== History

JSON-path extraction (`->`, `->>`, `json_extract_path_text`, cast-wrapped filters) in a
SELECT projection or WHERE now returns correct rows on both the native and DataFusion engines.

Decisive findings (lessons that still apply):

* The UDFs were never broken (the same extraction was correct under GROUP BY). A plain
  projection/filter did not *engage* the relational pipeline, so it fell to store-type dispatch,
  where `JSON_EXTRACT` in the SQL misclassified it as a Document query that read an empty collection.
  Fix: `set_expr_engages` engages on JSON-extract calls (#480).
* The native pushed-down predicate evaluated against an empty function registry and coerced every
  eval `Err` to `false`, so *any* function in a pushed-down WHERE silently dropped all rows. Fix:
  evaluate against `builtins()` and fail loud on unresolved functions (#502).
* Registering JSON scalars in the engine-neutral registry shadowed DataFusion's typed Arrow UDFs and
  broke comparison coercion; that prototype was reverted. Cast unification (ADR-043 Inv 2/3, #507) closed d06/d11.

Evidence: `tests/document_json_pgwire_e2e.rs` `DOC_ACCURACY_RATCHET = 11`, `KNOWN_BAD_TD183` empty.
The separate native d09 `rebind_columns` planner error was out of scope here (see link:TD-REL-LOWER-3-pushdown-rebind-alias-sort-key.adoc[TD-REL-LOWER-3]).
