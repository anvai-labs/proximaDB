== History (shipped)

* **Gap.** Phase 1b scoped graph gRPC + Flight node/edge ops to `{tenant}/{graph_id}`, but creation stayed
  bare, and `get_or_create_graph_engine` was not lazy — it errored `Graph collection '{}' does not exist`
  on a cache miss. So scoped create→use failed for named tenants (as it already had under the old
  `{tenant}::` fold — not a regression). A default-tenant regression was fixed surgically by making
  `scoped_graph_id` return the BARE id for the DEFAULT tenant.
* **Fix — lazy auto-provision** (chosen over threading `TenantContext` through every create path):
  `GraphCollectionService::ensure_or_create_graph` (race-safe get-or-create, defaults: ORION engine,
  service default storage root) is called by `get_or_create_graph_engine`, so a tenant-scoped first write
  auto-registers under the scoped key; the bare default tenant is never double-provisioned.
* **Evidence.** `named_tenant_graph_auto_provisions_on_first_write_and_isolates` (v2 graph_service): a
  named tenant writes+reads with no explicit create; a second tenant on the same id is isolated.

== Remaining follow-ons (open)

* **Custom create metadata for named tenants.** Auto-provision uses DEFAULT engine/schema. A
  named tenant that wants a custom schema/engine still needs a tenant-aware create path (scope
  pgwire `create_graph_collection` + add `TenantContext` to a REST create, or add a v2 graph-create
  RPC that routes through `for_tenant().create_graph_collection`). _Re-verified 2026-10-15: the legacy
  REST v1 graph mount is gone; the canonical `POST /api/v2/graphs` (`create_graph_collection` in
  `rest/canonical/graph.rs`) now exists but builds the `CreateGraphRequest` from the bare `graph_id`
  with no tenant._
* **Default-tenant uniformity.** The default tenant stays bare (its create paths are bare). Once
  those creates scope, flip `scoped_graph_id` to also scope the default (`default/{graph_id}`).
* **List scoping.** The original item named REST v1 `list_graph_collections`, which is unscoped and
  would surface named tenants' scoped keys (`{tenant}/{graph_id}`) to a default-tenant/legacy caller —
  scope + strip. REST v1 is removed; re-verify the canonical REST v2 list before closing.
* **Scope creation in lockstep** — every create path that feeds a tenant-scoped read composes
  `{tenant}/{graph_id}` (via `scoped_graph_id` / a `for_tenant().create_graph_collection` forwarder that
  rewrites `req.graph_id`): the REST create, pgwire `CREATE`, and internal creators that are
  request-scoped. Internal/embedded/observability creators with no request tenant keep bare keys (they
  are single-tenant control-plane graphs).
* Gate with an end-to-end test: create a graph via the (scoped) REST/pgwire path under tenant A,
  node-op + traverse via gRPC under tenant A succeed; the same logical id under tenant B is isolated;
  a bare create→use under the default tenant still works.

== Constraints

* Keep net `proximadb_v1` references non-increasing (TD-123 ratchet, baseline 2917).
* Any change to the on-disk graph key shape must be mixed-read-safe (no flag-day).
* This is shared collection-lifecycle work with TD-DOC-TENANT-1 / TD-ENTITY-TENANT-1 — a
  single "scope collection creation across modalities" effort likely subsumes all three.
