= TD-DOCSITE-1: 30 user-facing AsciiDoc pages are absent from the mkdocs site because mkdocs cannot render AsciiDoc

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-08 when the mkdocs pipeline was introduced; the site ships with the Markdown pages and excludes `*.adoc` wholesale.
| Priority | **MEDIUM.** The site is coherent and strict-clean today, but a user following `05-concepts/index.md` hits links to pages that are not published. Content exists; it is unreachable from the site.
| Component | `mkdocs.yml` (`exclude_docs`, `validation`), `scripts/check_docs_site_coverage.py`, `docs/.site-coverage-baseline.json`, `docs/00-product`, `docs/02-guides`, `docs/03-api-reference`, `docs/04-operations`, `docs/05-concepts`
| Relates to | TD-VECEVAL-1 (filed alongside the guide that prompted the site), mandate #12 (don't bolt on a fragile duplicate)
| Blocked by | Nothing. Needs a decision on conversion vs a second renderer.
|===

== The finding

The documentation corpus is **overwhelmingly AsciiDoc** — roughly six `.adoc` for
every `.md`. mkdocs is Markdown-native and cannot render AsciiDoc.

Exact totals are deliberately not quoted here: they move with almost every PR, so
a number in this document is stale debt (an earlier revision of this TD carried
four counts that were all wrong within weeks). The per-directory table below is
indicative; the **only** count that is maintained is the guard's, in
`docs/.site-coverage-baseline.json`, because CI fails when it drifts.

Per-directory, the split matters because it separates "must publish" from
"internal engineering record":

[cols="1,1,1,3", options="header"]
|===
| Directory | .adoc | .md | Publish?

| `01-quick-start` | 1 | 4 | yes
| `02-guides` | 7 | 6 | yes
| `03-api-reference` | 6 | 1 | yes
| `04-operations` | 7 | 2 | yes
| `05-concepts` | 6 | 4 | yes
| `release-notes` | 2 | 0 | yes
| `docs/` root | 2 | 2 | yes — but only `SUPPORTED_SURFACE.adoc` counts toward the 30; `INDEX.adoc` is the repo-tree index and is excluded by name
| `00-product` | 4 | 0 | no — PRD/VISION/scorecards, internal product material
| `rfcs` | 3 | 0 | no — RFC drafts and templates
| `11-usecases` | 2 | 2 | no — dated internal design drafts
| `06-internals` | 17 | 8 | no — engineer-facing
| `09-roadmap` | 4 | 0 | no
| `10-quality` | — | — | no — TD/debt register (the bulk of the corpus)
| `12-design` | — | — | no — ADRs / design records (ditto)
|===

NOTE: the publish-yes `.adoc` column sums to **31**, while the baseline and the
guard both report **30**. The one-file difference is `docs/INDEX.adoc`: it sits in
a publish-yes directory but is excluded by name in `mkdocs.yml`, because the
site's entry point is `docs/index.md`. An earlier revision of this table recorded
the root as 1 `.adoc` and so summed to 30 by *undercounting* rather than by
reconciling — the two numbers are both right and count different things.

So the site's exclusion of `10-quality`/`12-design`/`_archive` is **correct and
deliberate**: publishing the internal debt register would make the product's docs
site a changelog of our own TODOs. The genuine gap is the **30 user-facing
`.adoc` files** in the publish-yes rows — which is exactly what the guard's
baseline holds, so the two cannot disagree.

`00-product` and `rfcs` were initially treated as publish-yes and are not. Neither
holds a single `.md` or a `nav` entry, so nothing in them could reach the site
anyway, and their content — PRD, VISION, COMPETITIVE_LANDSCAPE, the MVP
scorecards — is internal product material. `00-product` also held the one
non-Markdown leak worth naming: see "The second failure mode" below.

== The second failure mode: raw non-Markdown files served publicly

mkdocs copies **any** non-excluded, non-Markdown file into `site/` verbatim. That
is correct for images, which real pages reference, and wrong for everything else.
`docs/00-product/MVP_TRUST_CORRIDOR.toml` — an internal MVP scorecard carrying
`graduation_gate` and per-tier claims — was being served at
`<site>/00-product/MVP_TRUST_CORRIDOR.toml`.

Neither `--strict` nor an `.adoc`-only check can see this class, so the guard now
covers it: anything under a published directory whose extension is neither
Markdown nor a known asset type is a finding. Verified by mutation — a `.toml`
dropped into `docs/02-guides` fails the guard.

Consequence today: `mkdocs build --strict` passes, but with INFO lines such as
`'05-concepts/index.md' contains a link to 'SUPPORTED_SURFACE.adoc' which is
excluded from the built site`. A reader of the published Concepts page follows a
link to nothing.

== Why `*.adoc` is excluded wholesale rather than plugged in

Rejected: an AsciiDoc plugin for mkdocs. The maintained options are thin, and
adding a second renderer to make 30 files work would put a fragile dependency in
the publish path for every page (mandate #12 — do not bolt on a duplicate of a
tool we would then own).

Rejected for now: switching the site to **Antora** (AsciiDoc-native, versioned,
the natural fit for an 85%-AsciiDoc corpus). It is the better theoretical fit,
but it would discard the mkdocs/Material pipeline that now builds strict-clean in
0.5 s, and the *user-facing* subset is only 30 files — small enough to convert.

== How to apply

The gate is already in place, so this TD is a conversion backlog rather than an
open hole.

One honest limit: "the list can only shrink" is enforced by *review*, not by the
guard. The guard compares the tree against the baseline, so adding a line to the
baseline makes a new violation pass. What it does guarantee is that the addition
is **visible** — it cannot happen silently, which was the original failure mode.
Any baseline is editable by whoever edits the baseline; the point is that doing
so is a reviewable diff rather than an absence. `scripts/check_docs_site_coverage.py` freezes the set of unpublished
AsciiDoc pages in `docs/.site-coverage-baseline.json`: a NEW user-facing `.adoc`
fails CI, and converting one fails until its stale baseline entry is removed. The
list can therefore only shrink.

1. **Convert the 30 user-facing `.adoc` files to Markdown**, directory by
   directory, smallest first (`docs/` root and `01-quick-start` have 1 each,
   `release-notes` 2). Add each to the `nav` *and* drop its baseline entry in the
   same commit that converts it, so the page is reachable the moment it renders
   and the count stays truthful.
2. **Fix the dangling links as you go.** The `mkdocs build` log reports **52**
   links from published pages to excluded files — 51 to `.adoc` and one to
   `_archive/README.md`, so "all 52 are AsciiDoc" would be wrong.
   `05-concepts/index.md` and `05-concepts/quantization.md`/`unified-wal.md` point
   at `storage-engines.adoc`, `configuration.adoc` and `SUPPORTED_SURFACE.adoc`;
   those are the reader-visible breakage, so prioritise the targets they point at.
+
   Converting all 30 will **not** drive this to zero: some of the 52 target
   `12-design/*` and `_archive/*`, which stay excluded permanently. Those links
   are wrong in a different way — a published page should not link into an
   internal tree at all — and the fix is to rewrite or drop the link, not to
   publish the target. See how `05-concepts/index.md` now points at the GitHub
   tree for `06-internals`.
3. Leave `10-quality` / `12-design` / `06-internals` / `09-roadmap` /
   `11-usecases` / `00-product` / `rfcs` / `_archive` in AsciiDoc and excluded.
   They are not the product's documentation, and the TD/ADR convention
   (`HOW_TO_FILE_TD_AND_ADR.adoc`) depends on AsciiDoc.

== Rejected: narrowing `exclude_docs` as the gate

An earlier draft of this TD proposed that once the publish-yes directories hold no
`.adoc`, narrowing `exclude_docs` from `*.adoc` to the internal directories would
make a new user-facing `.adoc` fail the build. **Measured against mkdocs 1.6.1,
that is false in both halves**, which is why the out-of-band guard exists:

* Dropping `*.adoc` from `exclude_docs` builds **clean** — `--strict` exits 0 with
  zero warnings. mkdocs only treats `.md` as pages, so a `.adoc` is never a page
  whose absence from `nav` could be reported.
* Worse, all 30 files are then **copied into `site/` as raw unrendered AsciiDoc**
  (re-verified on the current config: `site/SUPPORTED_SURFACE.adoc` and
  `site/04-operations/production-readiness.adoc` both present), so the public
  site would serve markup as source text.
+
NOTE: an earlier revision of this TD cited `site/00-product/PRD.adoc` here. That
artifact was produced before `00-product/` was excluded, and the citation went
stale without the claim becoming false — the count is still 30 and the behaviour
is unchanged. Re-run the experiment rather than trusting the example.

Relatedly, a link *to* an excluded file is reported at `INFO`
**unconditionally** — setting every `validation:` category to `warn` leaves those
52 messages at INFO while surfacing only 13 other findings. So mkdocs cannot gate
this class at all, in any configuration.

== Watch item: MkDocs 2.0

`mkdocs-material` 9.7.7 emits an upstream notice on every build that MkDocs 2.0
removes the plugin system, rewrites theming, offers **no migration path**, and is
currently unlicensed. Our pipeline deliberately uses no third-party plugins
(mermaid rides on `pymdownx.superfences`), which limits the exposure, but the
toolchain is pinned in `requirements-docs.txt` for exactly this reason — do not
chase a 2.0 bump. If upstream makes 1.x untenable, revisit Antora, whose fit for
an 85%-AsciiDoc corpus was the runner-up here and would absorb this backlog
instead of working through it.
