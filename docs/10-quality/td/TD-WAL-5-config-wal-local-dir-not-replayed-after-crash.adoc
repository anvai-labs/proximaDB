= TD-WAL-5: with a config-file `wal_local_dir`, a crash shortly after an acknowledged write loses it

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-10-15).** Replay now resolves the local WAL root with the write path's own resolver (`local_wal_dir(&WALConfig)`); the env-only reader is private. Pinned end to end by `crash_restart_with_config_file_wal_local_dir`.
| Priority | **CRITICAL**: silent loss of acknowledged writes when a crash falls inside a window after the ack, for every deployment that sets `wal_local_dir` in the config file rather than in the environment.
| Component | `src/storage/persistence/write_ahead_log/mod.rs`: `local_wal_dir(&config)` (write path) vs `local_wal_dir_env()` (env-only, used by recovery/replay free functions that have no `WALConfig` handle). `[storage.wal_config] wal_local_dir` (ADR-069 S1).
| Relates to | TD-WAL-1 (ADR-069 local-disk WAL; its S5 crash test covers only the default layout), mandate #16 (read-after-write correctness), the cold backup/restore PR that surfaced it.
| Found | 2026-10-15, while adding a crash-consistent case to `apps/proximadb-server/tests/cold_backup_restore.rs`
|===

== Reproduction (Observed, real server binary, no backup involved)

Setup: SST collection, `sync_mode = "PerBatch"`, 6 records inserted over REST v2 and **acknowledged**, then SIGKILL, then restart on the same volumes, then a point read of every record.

[cols="2,1"]
|===
| Configuration | Acknowledged writes after crash and restart
| `enable_wal = true`, no `wal_local_dir` | ✅ all recovered
| `enable_wal = false`, no `wal_local_dir` | ✅ all recovered
| `enable_wal = true`, `wal_local_dir = "file://…"` **in the config file** | ❌ **all lost** (404)
|===

`enable_wal` is irrelevant. The trigger is a config-file `wal_local_dir`.

**The loss depends on timing.** The rows above SIGKILL *immediately* after the insert ack. An independent review re-ran the config-file case and killed about 2 s later, after some unrelated activity. Recovery then succeeded: restart produced an `L0_recovery_*.pax`, and the WAL manifest entry under `collections/wal/*.jsonl` carried `storage_url = file://…/<wal_local_dir>`. With the `PROXIMADB_WAL_LOCAL_DIR` env form, even the immediate kill recovered.

== Mechanism (partly traced; must be re-traced before a fix is designed)

* The write path resolves the WAL base with `local_wal_dir(&self.config)`. That honours the config field (and the env override), so WAL segments are written to `wal_local_dir`.
* Recovery and replay run as free functions without a `WALConfig` handle, and use `local_wal_dir_env()`. That reads **only** `PROXIMADB_WAL_LOCAL_DIR`. Its own doc comment admits the gap: _"for full write and replay consistency an operator sets the env"_.
* That explanation is **incomplete**. Part of recovery follows the WAL manifest's `storage_url`, which does record the config directory. The likely window is the interval before the manifest entry for new WAL segments is persisted: an immediate crash leaves segments that only the env-only path could find. This is a hypothesis; trace manifest persistence timing against recovery to confirm it.

The env-var form is consistent between write and replay; it is unaffected.

== Mechanism (traced 2026-10-15)

Startup replay belongs to the **storage engine's** WAL manager (`StorageEngine::recover_from_wal`). `StorageEngine::new_internal` built that manager's config from `WALConfig::default()` plus the storage locations. It never read `[storage.wal_config]`, so its recovery manager had no `wal_local_dir`. The write path's manager is built through the canonical converter (`WriteBufferUserConfig::to_engine_config`), so it did have the field and wrote segments under `wal_local_dir`.

Replay lists these candidate bases, in order:

. the local WAL root;
. the catalog `base_location`;
. every manifest `storage_url`;
. the configured primary.

The config-file directory therefore became a candidate only once a manifest entry had recorded it. A SIGKILL before that left the segments unlisted, and restart logged `Collection 1 recovered: 0 vectors from 0 files`.

**Lesson.** The first fix threaded the resolver into `RecoveryManager` but changed nothing: the test still failed with the same 404. The config the recovery manager received had already lost the field one layer up. The fresh-test-first discipline caught it; reading the code alone would not have.

== Fix (shipped)

* `StorageEngine::new_internal` carries `wal_local_dir` from the user config into the replay manager's `WALConfig`.
* `RecoveryManager::new` resolves `local_wal_dir(&config)` once, using the write path's own resolver (env override > TOML > None). It threads the value into `wal_candidate_bases`.
* `local_wal_dir_env()` is now private to the resolver, so no reader can consult only half of the precedence chain.
* Tests:
** Unit test `config_file_wal_local_dir_is_a_replay_candidate`.
** Real-binary test `crash_restart_with_config_file_wal_local_dir`: SIGKILL immediately after the ack, then restart; all 6 acknowledged records must be readable. It fails on the pre-fix code (`ctl-0` 404) and passes with the fix.

== Residual (not fixed here)

* The storage engine's replay WAL config is still built from `WALConfig::default()` rather than the canonical converter. Only `wal_local_dir` is carried across. Other `[storage.wal_config]` fields (for example `strategy_type` and the sync settings) do not reach this manager.
** It is mostly a replay-side handle, but the same drift class as TD-CONFIG-CONSOLIDATE-1.
** Routing it through `to_engine_config()` changes this manager's behaviour, so it needs its own crash/recovery verification.
* Found by the fresh-context review of the fix (none blocking):
** **Tokenless-orphan guard checks the WAL disk, not the data root.** `recovery_manager.rs` derives `storage_url` from the first replayed WAL URL. Under a local WAL dir, `collection_has_segments` therefore probes `{wal_local_dir}/{cid}/data/`, which is always empty. A *legacy* tokenless, unmanifested WAL object would then be replayed over existing segments rather than refused. New writes are tokenized, so this affects legacy files only. It also applied to env users before this fix.
** **Dead resolvers ignore the local dir.** `WriteAheadLogManager::insert_vectors` and `ParallelRecoveryManager::recover_collection_parallel` resolve bases without the shared resolver. Neither has a production caller; delete them, or route them through `local_wal_dir`.
