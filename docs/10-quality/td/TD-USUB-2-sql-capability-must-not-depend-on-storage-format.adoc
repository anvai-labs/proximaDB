== History (shipped)

* Finding: `allow_engine_sql_fallback = true` appeared at exactly one call site (the DataFusion floor in `relational_pipeline.rs`), so the whole `classify_unsupported` set (subquery, having, join, group_by, distinct, window) plus `DISTINCT ON`, `GROUP BY ALL`, `NATURAL JOIN`/`USING`, correlated scalar subqueries, `EXISTS`/`IN (SELECT)`, UDTFs and FROM-less `SELECT` — and a second tier `logical_lowering.rs` declines (semi/anti join without `ON`, null-aware anti join, `SUM`/`AVG(DISTINCT)`, `StringAgg`, `||`) — was reachable only on `parquet_backed` tables, i.e. after `ALTER TABLE … MATERIALIZE`. The CTE decline even named the workaround.
* **Lesson — not a storage problem.** Parquet was incidental: it was merely the only format with a registered table provider. The cliff closes by registering a provider through the existing ADR-039-legal `ProximaTableProvider` seam, with zero format change, zero publication, zero write amplification.
* Shipped: `src/query/execution/native_table_provider.rs`, gate `PROXIMADB_NATIVE_TABLE_PROVIDER` (registered in `ENV_GATE_REGISTRY`, OFF). With it ON, window functions on native tables return real values. E2E: `tests/native_table_capability_parity_e2e.rs`.
* Shipped (ADR-097 P3.1 PR 8): a query **mixing** Parquet-backed and native tables reaches the DataFusion floor too. It used to fit neither arm — the Parquet arm needs every table Parquet-backed, the native arm none — and fell back to Volcano, which declines a window function. With the gate ON and an ungoverned session (the Parquet side reads files and cannot apply an ABAC row filter, as on the Parquet arm), the floor registers the Parquet tables (with their ADR-025 delta merge) and the native ones side by side, each table exactly once. E2E: `tests/mixed_parquet_native_e2e.rs` (gate OFF declines; gate ON answers a join + window + aggregate over a materialized table with a post-snapshot update and a native one, by value).

== Open

=== Escalation — it is a silent-wrong-answer bug, not just a capability gap

Measured during implementation (`tests/native_table_capability_parity_e2e.rs`), against a
**native** table holding `val = 5, 20, 12, 40`:

[source,sql]
----
select id, val, val - lag(val) over (order by id) as delta from usub2_t order by id;
-- 1|5|5   2|20|20   3|12|12   4|40|40      ← delta == val on every row
----

The query does not decline. It returns **wrong data**, with the exact signature of
**TD-187** — `lag(...)` contributes nothing, so `val - lag(val)` comes back as `val`.

TD-187 was fixed, but **only for materialized tables**. Its engagement fix makes the query
engage the relational pipeline; however for a native table there is no DataFusion route, so
`try_run_select` returns `None` and the query falls through to the legacy single-table
path — whose projection extractor has no expression parser and re-reads the bare `val`
column. The fix closed the materialized path and left the native one open.

That makes this TD a **mandate #1 violation** (fail closed, never silently wrong), and is
why its priority is raised. Registering a provider routes these shapes to DataFusion's real
window executor, turning a wrong answer into a correct one.

**Fixed (fail-closed).** When lowering declines on pgwire's relational pipeline and the
top-level projection carries a window function, `try_run_select` (`relational_pipeline.rs`)
no longer returns `None` to the legacy single-table path; it returns SQLSTATE `0A000`
naming the function (e.g. `window function lag() OVER (...)`) and telling the user to set
`PROXIMADB_NATIVE_TABLE_PROVIDER=1` or `ALTER TABLE … MATERIALIZE`. With the gate ON the
DataFusion route serves the query before this point, unchanged. The former KNOWN-BAD pin in
`tests/native_table_capability_parity_e2e.rs` (`native_table_capability_parity`) now asserts
the `0A000` decline; the gate-ON phase still asserts the real `LAG` deltas.

=== How to apply

. Register a table provider for relational tables regardless of physical format, reusing the
  existing `ProximaTableProvider` seam (do **not** add a new adapter — ADR-039 confines
  `use datafusion::` to the sanctioned allow-list).
. Change the `allow_engine_sql_fallback` gate from `parquet_backed` to **"this query's tables
  all have a registered provider."**
. A table with no registered provider must produce an **explicit, observable decline** with a
  documented SQLSTATE — never a silent capability downgrade.
. Keep lane discipline: the DataFusion route may use `PaxSplitReader`; the native route must
  not (TD-USUB-5).

Ship default-OFF behind an `ENV_GATE_REGISTRY`-registered gate.

=== Evidence gate (mandate #6)

* A conformance test asserting the **same SQL surface** on a non-materialized table and a
  materialized one — CTE, window function, join, correlated subquery, `EXISTS`, `DISTINCT ON`.
* TPC-H and TPC-DS ratchets stay green (currently 15/16 and 11/11).
* No regression in the native/OLTP point-lookup path.
