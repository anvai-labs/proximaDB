= TD-USUB-6: Typed user columns are a duplicated advisory index — make declared columns authoritative

== The finding

P-Shred (ADR-055) writes typed user-column stripes, but they are explicitly **not
authoritative**:

[quote, 'crates/storage/proximadb-block-format/src/writer.rs:209-213']
____
These columns are a DUPLICATED pruning/projection index; the msgpack `PROPS` tail stays the
source of truth (the reader reconstructs from the tail and ignores `USER_BASE+` columns), so
this is additive and mixed-read-safe with no format-version bump.
____

That was the right call for an additive, no-version-bump change. Its costs are now the
blockers:

* **Every shredded value is written twice** — once in the typed stripe, once in the msgpack
  tail (`writer.rs:470-476` buffers by clone, deliberately never `remove`).
* **Typed columns are advisory only.** `build_shred_stripe` (`writer.rs:1250-1262`) infers
  the physical type from the *first non-null value* and coerces any value that does not fit
  to `None`. That is explicitly safe "because the msgpack `PROPS` tail is the source of truth
  for reconstruction" — so projection and pruning are best-effort by construction.

== How to apply

For columns **declared in `CatalogTableSchema`** (as distinct from schemaless props):

. The typed `ColumnRole::UserDefined` stripe **is** the value; readers read it directly.
. The msgpack `PROPS` tail carries only the **residual** — undeclared props.
. Column type comes from the catalog schema, not from first-value inference. A value that
  does not conform is a **write error**, not a silent `None` — the fallback that made
  coercion safe no longer exists.
. Requires the PAX v3 version byte (spec §2), and is mixed-read-safe: v2 blocks keep
  decoding via the existing tail-reconstruction path.

**Align the semantics with Iceberg v3 Variant shredding** (shredded fields authoritative,
residual blob for the rest). ProximaDB arrived at this design independently, which both
validates it and makes the §6 export mapping near-mechanical.

== Reconciliation and the ROI caveat

Legacy **TD-162a-2** describes the typed stripe + per-column zone maps and remains `Open`;
this TD evolves it (ADR-055 has since landed the *duplicated* form) and should supersede that
row.

Record honestly: **ADR-034 deliberately ranks TD-162a-2 last**, because typed columns buy
< 2× on scans. This TD does **not** overturn that ranking. It is justified on the grounds
ADR-033 already recast the work to — one unified store, a real second cost arm for the
router, uniform projection/pruning — plus the write-amplification removal above. It must not
be re-argued as a scan-throughput win.

== Evidence gate (mandate #6)

* **Losslessness ratchet:** declared columns + residual reconstruct the original
  `ProximaRecord` exactly, including nulls, type edge cases, and props whose declared type
  changed via schema evolution.
* Write-amplification delta (bytes written per row, before vs after) recorded in
  `BENCHMARK_EVIDENCE.toml`.
* Mixed-read test: a v2 segment and a v3 segment in the same collection both read correctly.
* Recall ratchet (recall@10 ≥ 0.93) stays green.

== Slicing (2026-09-22) — two prerequisites found while starting the work

=== Slice 1 (LANDED): the block header could not express v3 at all

"How to apply" step 4 says the change "requires the PAX v3 version byte". That byte could not
have worked as written, for two reasons found in `header.rs`:

. **`from_bytes` equality-rejected** anything that was not exactly `FORMAT_VERSION`
  (`if buf[4] != FORMAT_VERSION { bail!(...) }`). A v3 block would have been refused outright
  — the precise flag-day the module's own doc comment forbids ("any future `v3` MUST be
  mixed-read-safe — readers dispatch on the byte and keep decoding v2").
. **`BlockHeader` discarded the version.** Even had v3 been accepted, the struct carried no
  `format_version` field, so no decode path could branch on it. The information was validated
  and thrown away.

Also latent: `to_bytes` stamped the `FORMAT_VERSION` constant unconditionally, so any
read-modify-write of a v3 header would have silently **relabelled it v2**.

Slice 1 fixes all three — `SUPPORTED_FORMAT_VERSIONS` dispatch, a retained `format_version`
field with `is_v3()`, and `to_bytes` serializing the header's own version. It introduces **no
v3 semantics and no writer emits v3**, so it cannot change any byte on disk or any behaviour;
it only makes v3 expressible. Pinned by five tests including unknown-version fail-closed and
the no-relabel property. The recall@10 harness stays green (90/90 in the crate).

=== Slice 2 (OPEN, newly blocked): the block is not self-describing about shredded keys

**This is the finding that matters, and it changes the shape of the remaining work.**

Under today's duplicated form, the msgpack `PROPS` tail is complete, so the typed stripes are
advisory and the reader can ignore them. `FlatRow::into_record` takes the promoted
user-column keys from the **caller's schema, positionally** — and that is harmless precisely
because nothing depends on it: a wrong or stale key list costs nothing when the tail already
has every value.

Making declared columns authoritative removes that safety net. The value then lives **only**
in the typed stripe, and the only thing naming that stripe is a caller-supplied, positional
key list. A key list that drifts from what was written — reordered, truncated, or evolved —
would **silently drop props**, with no checksum or structural error to catch it.

The TD's own losslessness gate names the exact scenario that breaks it: *"props whose declared
type changed via schema evolution"*. Schema evolution is precisely when the caller's key list
and the block's stripes disagree.

**Therefore: before the tail can become a residual, the block must record its own shred
directory** — the `(col_id, prop_key)` pairs actually written — so reconstruction is driven by
the block, not by what a caller believes the schema to be. That directory is additive and can
land in v2 blocks harmlessly (a new stripe/footer section), which also means it can be written
and verified *before* any v3 block exists.

Revised order for the remaining work:

. **Slice 2a** — self-describing shred directory in the block; written in v2, ignored by
  existing readers, verified by a round-trip that reconstructs props using ONLY the block's
  own directory and a deliberately wrong caller key list.
. **Slice 2b** — v3 writer: residual tail + authoritative stripes, stamping `FORMAT_VERSION_V3`,
  default-OFF; v3 reader merging stripes + residual via the directory.
. **Slice 2c** — write-amplification measurement (bytes/row v2 vs v3) into
  `BENCHMARK_EVIDENCE.toml`, plus the mixed-read test (a v2 and a v3 segment in one
  collection) and the recall ratchet.

Doing 2b without 2a would ship a data-loss hazard whose trigger is routine schema evolution.
