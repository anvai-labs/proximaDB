Problem: filtered vector search on the PAX path was a whole-object brute-force
scan — the coalesced cascade declined any query with a filter and fell to
`search_pax_file_exact` (whole-object read, decode-all, per-record post-filter).
Measured vs Qdrant on identical data (TD-CTXCORR-1 harness): filtered p50
8.0→52.3 ms from 20k→80k rows (O(N)) vs 1.2→1.4 ms (flat); **38x at 80k and
widening**, at recall parity. ADR-089 decides the fix: metadata-first
cell/block pruning composed with the geometric A0 probe, one pipeline,
residual filter as the correctness backstop.

== History (shipped)

* *P1 — allow-aware cascade.* `RowAllow` bitset + allow-aware ranking in `proximadb-block-format`; Stage-F
  `pax_filtered_row_allow` (coalesced D-block fetch → conservative `evaluate_block` stats prune →
  row-accurate `evaluate_filter_proxima`, the *same* evaluator as the exact path, so match semantics are
  identical by construction). Fail-safe: any Stage-F failure or non-coalesced segment falls back to exact.
* *P2 — zero-GET footer pruning.* `FooterBlockStats` lifts filterable `ColumnMeta` bounds into the footer and
  implements `BlockZoneSource`, so `evaluate_block` runs unchanged (footer-prune == body-prune parity
  TDD-proven). After rebasing onto TD-PAXRG-1 (which claimed the per-entry `stats_len` frame), the payloads
  ride their own optional footer section `SECTION_BLOCK_FILTERABLE_STATS` (tag 7); predating parsers skip it.
* *Decisive finding — field-namespace gap.* Footer prune resolved only canonical columns, while user tags
  live in props, so user-tag filters pruned nothing. Fixed with a self-describing segment (option ii, zero
  catalog dependency): `SECTION_SHRED_FIELD_MAP` (tag 5) carries the writer's P-Shred `(name, col-id)` pairs.
  *Lesson:* the SST vector-flush path passed an EMPTY shred spec, so user-tag pruning was dark end-to-end until
  `CollectionFlushPlan` carried `filterable_columns` (M1/Gap-B); compaction preserves shredded columns (A1).
* *M3* re-armed the geometric A0 probe under a filter; *M2/C2* tag-aware two-level compaction layout
  (per-partition k-means over shared PCA; default-ON, kill-switch `PROXIMADB_PAX_PARTITION_LAYOUT=0`).
* *Flip (2026-08-31).* An adversarial review found the original promotion criterion vacuously dischargeable
  (the SIFT ratchet is unfiltered) and that the cascade dropped metadata; the flip added top-k rehydration
  (`read_records_by_positions`) and a filtered SIFT ratchet leg through the real dispatch.
  Attribution: `record_pax_footer_prune` → `pax_footer_{total,pruned}_blocks` in `IoTraceSnapshot`.

*Evidence:* filtered recall@10 = **0.996** vs filtered brute force (floor 0.90, N=10k, 8 partitions);
C1 integrated filtered stack **4.2× byte cut** at recall parity (correlated data); C2 unfiltered recall Δ=0.000.

== Open

* **P1 residual:** the D-resolve residual check (defense-in-depth; the P1 row set is
  already row-accurate). (The other P1 residual, P-Shred arming for `filterable`
  columns, was closed by M1/Gap-B.)
* **`PROXIMADB_PAX_FOOTER_STATS` stays default-OFF** (adversarial verdict: no promotion
  criterion of its own, read-inert while the cascade was off, unmeasured footer byte
  cost paid by every collection) until the cascade records io_trace evidence that
  the D-block fetch dominates and a footer byte-delta measurement lands.
  **2026-10-28: the dominance precondition is MET** — the E1 filter artifact's
  counters attribute 89% of filtered bytes (834 of 936.93 MB/q at 3M, n=1000) to
  the Stage-F whole-D fetch, with the cascade clean (whole_region_fallbacks=0).
  Remaining for the flip: the footer byte-delta measurement (one gated re-ingest
  arm on the e1p protocol — harness landed with the artifact).
* **Evidence gate (PARTIAL — 3M leg landed 2026-10-28):** the corridor
  benchmark (filtered p50/p99 at 20k/80k/1M vs the recorded Qdrant 8.0/52.3
  ms baseline, synthetic partition + Wikipedia `lang`, io_trace
  `object_gets`/`bytes_read` per filtered query) has NOT been run at those
  scales — but the E1 filter family supplies the same evidence class at 3M
  through the real dispatch: filtered p50 6.02 s / 277.55 req/q / 936.93 MB/q
  vs unfiltered 0.21 s / 52.74 / ~150 MB, 28× (n=1000, MinIO+toxiproxy, full
  per-query counters in result.json). The in-module C1 measurement (4.2× byte
  cut at recall parity on correlated data) remains the interim flip evidence;
  the Qdrant-corridor shape stays open.
* **P3 — per-cell stats (prune before any Region-A byte).** Optional
  footer/A0 section with per-cell dictionary/zone summaries for filterable
  columns; intersect with the geometric nprobe cut
  (`coarse_probe_survivors`, `segment_format.rs:2130-2204`) so metadata-dead
  cells are never fetched. Strongest when metadata correlates with clustering
  (tenant/lang); measure the uncorrelated case honestly — P2 block stats carry
  it. Budget-check against A0's ~120-300 KB envelope.
* **P4 — stats-driven selectivity policy.** Distinct-hint HLL + null counts +
  dictionary domains → per-segment selectivity estimate → route: ultra-selective
  ⇒ direct row fetch + exact rank (no ANN); moderate ⇒ pruned cascade;
  unselective ⇒ cascade + residual only. This is the real auto
  `AnnFilteringMode` (closes the TD-073 deferral) and subsumes the AXIS
  PreFilter/Inline/PostFilter modes as policy over capability.
* **P5 — residual-tail store-once** *(new 2026-10-28; measured rationale: the D
  region itself is 89% of filtered bytes and ~170 B/row for three int props —
  msgpack named-map keys repeated per row, values duplicated into shreds when
  `filterable_columns` are declared, residual-tail mode default-OFF)*. Flip
  `PROXIMADB_PAX_RESIDUAL_TAIL` to unset=ON (kill-switch opt-out): shredded
  values stop being duplicated into the props tail; the reader-side merge is
  already ungated (`record.rs:604-637`). Arithmetic target from the 3M
  measurement: D 834 → ~140 MB/q, total ~242 MB/q. Gates: round-trip prop
  equality; no change without declared filterable columns.
* **P6 — filter-aware directory planning** *(new; the filter still excludes the
  centroid directory end-to-end — `mod.rs:2116` + the probe-internal drop
  `segment_format.rs:3505-3517` and the `probed = cells` override
  `:3559-3561` — so filtered queries lose segment skipping and decode keys)*.
  Gate `PROXIMADB_PAX_FILTERED_DIRECTORY`: remove ONLY the
  `filter_expression.is_some()` half of the exclusion (`force_exact` stays —
  exact-mode contract); the directory choice becomes a stable order-prior on
  the M3 walk and never overrides the `nprobe && matched >= target` stop
  condition (the measured 0.974 filtered recall already includes cell
  skipping — no new miss class).
* **P7 — cell-scoped lazy Stage F** *(new; composes P3+P6)*. Refactor
  `pax_filtered_row_allow` into a lazy `AllowSource`: per walked cell,
  range-GET only its D blocks' filter data, extend the allow bitmap, check the
  stop condition (blocks nest inside cells — assert, fall back). Invariant:
  lazy allow bitmap byte-identical to eager for the same filter; every error
  falls back to today's eager path. Arithmetic target: total ~138 MB/q ≈
  unfiltered parity (~150 MB).

== Gates (per phase)

* `filtered_recall_at_10` vs exact ground truth (TD-CTXCORR-1 harness) —
  pruning is conservative; recall must match the unpruned path.
* Filtered p50/p99 at 20k/80k/1M vs the recorded Qdrant baseline
  (8.0/52.3 ms → target flat-ish scaling), synthetic partition (uncorrelated)
  AND Wikipedia lang filter (correlated).
* `io_trace` `object_gets`/`bytes_read` per filtered query — the pruning win
  must be visible in the physical-cost counters (feeds TD-CTXCORR-1 Slice 4
  economics).
* Mixed-read: new-stats segments and legacy segments coexist in one
  collection; recovery/readers default to legacy when markers absent.

== Related (non-goals here)

* AXIS REST `ann_filtering_mode` override: SUPERSEDED (2026-08-29 review).
  Mode selection is now catalog-`AnnFilteringPolicy`-driven with selectivity
  routing (`query_optimizer.rs` — "policy as the single source of truth"), and
  a post-hoc plan-field stomp would be overridden by the policy path. The
  former WIP branch was discarded; if a diagnostic lever is still wanted, wire
  a request field through to the existing `AnnFilteringPolicy.force_mode`
  (~30 lines + spec/SDK regen per mandate #15) — do not revive the old
  plan-stomp approach.
* WAL/unflushed side already filters at scan time
  (`search_unflushed_vectors`: bloom pre-filter + per-record eval before
  scoring) — no work needed there.
* In-memory per-tag payload indexes (Qdrant-style): possible future cache
  layer above this design; not the foundation (ADR-089 Alternatives).
