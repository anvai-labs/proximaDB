== The finding

The SDK ships two parallel "unified" clients. v2 was authored as the replacement ("eliminates
protocol-specific branching by delegating all operations to protocol adapters") but landed
covering only the vector core. It is public API (`ProximaDBClientV2`), so it must either be
completed or it will drift — a smaller, subtly different twin of the main client, exactly the
failure mode CLAUDE.md #19 forbids.

== Decision (2026-10-31)

Keep **v2 as the architectural target**; port the 54-method delta onto it incrementally. v1
remains the default `ProximaDBClient` until parity + soak; the swap then happens with one
release of deprecation warnings. Deletion of v1 is a separate, later decision.

== Program

1. **Batches**: port in consumer-visible batches (graph CRUD; document collections; timeseries +
   observability; routing/metrics; remainder), each batch landing with the v1 tests mirrored onto
   v2 plus an equivalence test (same adapter config → same wire calls).
2. **Parity gate**: a census test asserting `set(dir(v2_public)) >= set(dir(v1_public))` turns
   the 54-method gap into a ratchet (counts only go up).
3. **Swap**: flip `ProximaDBClient = v2` behind the deprecation cycle; v1 exported as
   `ProximaDBClientLegacy` for one minor release.
4. **Ratchet**: the duplication census should drop the unified_client family counts as batches
   land (v1 bodies replaced by delegation or deleted at swap time).
