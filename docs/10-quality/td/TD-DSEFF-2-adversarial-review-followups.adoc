== History (shipped)

An adversarial re-review of the merged DS-efficiency program (#1735/#1737/#1738/#1743) found six issues; three were fixed:

. *CatalogCache shared eviction ring* (#1772) — one ring across map families defeated the cache's own capacity bound under multi-family traffic; split per family (see TD-CAT-5).
. *NOVA `vector_by_id`* (#1788) — #1743's real point-read resolved by first-match-in-listing-order and never filtered tombstones/TTL. Now resolves the MVCC winner across *all* rows in *all* files before any liveness check, then gates with `ProximaRecord::is_dead`. *Lesson:* resolve MVCC first, liveness second — a tombstone is a newer version that must shadow an older live one (invariant 16d). Tests: `test_nova_vector_by_id_{returns_latest_version_across_flushes,hides_tombstoned_record,filters_ttl_expired_and_returns_live}`.
. *Embedded migration risk from #1743* (#1788) — a one-shot, log-only startup scan warns when a non-SST-declared collection holds only legacy `.sst` files (pure helper `engine_data_mismatch`, never fails startup), closing a mixed-read-safety gap (directive 8).

== VIPER byproduct findings (not fixed; VIPER is retiring per TD-VIPER-1 / ADR-093)

* VIPER's point-read compares the millisecond `expires_at` column against
  `chrono::Utc::now().timestamp_micros()` — a 1000x unit mismatch that makes
  any record with a real future expiry read as already-expired.
* VIPER's point-read also skips liveness mid-scan (`continue` on an
  expired/tombstoned row) *before* MVCC resolution, so a stale live version
  can win over a newer tombstone instead of being shadowed by it.
* NOVA's `FIELD_VERSION` Parquet column is `UInt32` (`schema_builder.rs`),
  while VIPER's own factory schema (`viper/factory.rs`) declares the same
  logical column `Int8` — a third VIPER-side type/unit inconsistency in this
  code family, also not fixed here.

== 4. raptor `select_nth_unstable_by` — nondeterministic tie-break vs. old stable sort

`src/storage/engines/raptor/` (matrix_builder / writer.rs partial-sort sites
from #1737): `select_nth_unstable_by` does not guarantee the same tie-break
order as the previous `sort_by` at exact float ties. Low severity (raptor is
`experimental-engines`-gated, not on the GA path) and narrow (only affects
ordering among exactly-tied distances, not correctness of the top-k set
itself). Recorded for completeness; not scheduled.

== 5. Skiplist memtable `clear_up_to` two-phase unlocked-gap race

`src/storage/memtable/implementations/skiplist.rs` (~lines 164-187, from
#1738): removal from the `key_index` BTreeSet and removal from the DashMap
happen as two separate un-atomic phases, leaving a window where a concurrent
reader could observe a key present in one structure but not the other.
Self-healing (both removals do complete) and narrow (only visible mid-clear
under concurrent access to the range being cleared). Not scheduled; revisit
if a range-scan-during-clear bug report ever surfaces.

== 6. gRPC BatchWriteStream — un-type-enforced all-or-nothing assumption

`src/network/grpc/v2/record_service.rs` (~lines 1723+, 1830-1840, from
#1738): batching groups consecutive same-write-mode records into one
pipeline call with per-record retry-on-failure, relying on the batch write
path being atomically all-or-nothing. `BatchOperationResult::partial()`
(`crates/platform/proximadb-runtime/src/batch_result.rs:81-93`) exists but
has zero callers in this path today — if a future change to the underlying
batch write ever returns a partial result, this call site would silently
mishandle it. Latent landmine, not a live bug. Candidate fix: either wire
`partial()` handling defensively now, or add a debug-assert that the
underlying result is never partial, so a future violation fails loudly
instead of silently. Not scheduled — no current caller returns partial.
