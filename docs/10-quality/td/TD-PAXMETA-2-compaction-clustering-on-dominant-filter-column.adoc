== Problem

The ADR-042 per-block prune statistics (bounds, null counts, capped distinct sets, string blooms;
footer section 9, PXCD v3) let a filtered query skip a block or a whole segment without reading
it. Bounds and distinct sets prune only when a block holds a narrow slice of the filter column's
values. The writer orders rows by vector locality (the A0/PCA cell order and the block-cluster
order), not by any scalar column, so an uncorrelated filter column (a tenant tag, a category,
a timestamp bucket ingested out of order) gives every block nearly the full value range and the
stats prune nothing. Today pruning pays off only when the data arrives clustered on the filter
column (time-ordered ingest filtered on time, one tag per flush batch).

== Fix direction

* Record a per-collection **dominant filter column** (off by default) — explicit config, or
  derived from the filter-column histogram the query path already observes.
* At compaction, order rows within each coarse cell (or within each output segment when the
  collection is untrained) by that column before cutting blocks, so blocks hold narrow ranges.
  Ordering inside a cell keeps the A0 cell extents and the vector-locality contract; ordering
  across cells is the TD-FPRUNE-3 partition layout, which cost unfiltered recall and is not
  this change.
* Gate on evidence: a filtered request-count arm (blocks and segments pruned per query, the
  directory counters `pax_directory_segments_pruned` / `pax_directory_blocks_pruned`) plus the
  unfiltered SIFT recall ratchet unchanged.

== Acceptance

. A collection with the column configured prunes ≥ 50% of blocks for a selective equality
  filter on uncorrelated ingest after one compaction (request counts, file:// and Azurite).
. Unfiltered recall@10 on the SIFT ratchet within tolerance of the unclustered layout.
. Off by default; unset leaves compaction output byte-identical.
