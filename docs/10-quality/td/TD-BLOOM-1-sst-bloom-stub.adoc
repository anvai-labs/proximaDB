== Problem

The SST read path decides `can_skip_file` using a fake bloom probe whose byte
layout matches nothing specified. Whether it is merely crude or actively wrong
depends on what the FLUSH path writes at `bloom_filter_offset` — which is
itself undocumented on this path. A real `SstableBloomFilter` serialization
read by the stub = systematic false negatives = silently missing vectors.

== Proposed direction

1. Trace the writer: what bytes land at `bloom_filter_offset` today (SST flush
   path, `has_global_bloom` in `sst_format_types.rs`)? Three possible answers:
   real-filter bytes (stub is WRONG), simple-scheme bytes (stub consistent but
   crude), or nothing/no writer (dead path — delete the probe).
2. If real bytes: replace the probe with the `proximadb-bloom` reader — mixed-
   read-safe per discipline #8 (version/magic detection; legacy fallback when
   the marker is absent), gated by round-trip + recall tests against the f32
   baseline.
3. If no writer exists: either build the writer (feature work, out of TD
   scope) or delete the bloom branch of `can_skip_file` (conservative false,
   honest) until one exists.

[[answer]]
== Answer (traced 2026-11-05): option 3 — no writer exists, and the reader fabricated one

Direction question 1 above, answered with code evidence:

* **There is no writer.** Nothing emits filter bytes into the region this path
  read. The reader *fabricated* the buffer itself: `extract_metadata` did
  `fs.read_range(file_path, BLOOM_OFFSET = 0, BLOOM_SIZE = 4096)` and stored
  those bytes as the "global bloom filter". Offset 0 is the file's **magic +
  header** — the real SST reader locates the filter at `8 + header.header_size`
  (`src/storage/engines/sst/readers/sst_query_engine.rs`). That is why no length
  check ever tripped: the buffer was always a plausible 4 KiB.
* **The direction is false negatives.** `check_bloom_simple` returned
  `bloom_data[hash % len] != 0`, and `can_skip_file` consumed a `false` as
  "definitely absent" → `return true` (skip the whole file). Header regions are
  padding-heavy, so `0x00` was the *likely* byte — skipping files that hold the
  id. (The likelihood is inferred; the direction is not.)
* **Two more defects in the same six lines:** `DefaultHasher` is explicitly not
  stable across Rust releases; and the override dropped the empty-buffer guard
  that the trait default in `proximadb-storage-common::zero_copy_traits` has,
  so `bloom_filter_size == 0` would panic on `hash % 0`. The unbounded slice
  `variable_data[offset..offset+size]` was a second panic site.
* **Why it was not a live bug:** zero production callers. The only wrapper
  (`zero_copy/metadata_cache.rs`) is `#[allow(dead_code)]`; its owning
  `ZeroCopyMetadataCache` is constructed only under `#[cfg(test)]`; the
  *production* cache is a different type (`FilesystemMetadataStore`) whose
  `can_skip` flag is hard-written `false`. Latent, not active.
* **The real primitive was already in hand:** `SstMetadata` imports
  `proximadb_bloom::SstableBloomFilter` and declares a `global_bloom` field of
  that type (`#[allow(dead_code)]`, never populated). One caution recorded in
  TD-FACADE-1: that crate's `xxhash64`/`cityhash64` are themselves
  self-declared placeholders, so "use `proximadb-bloom`" means use it with
  `murmur3_32`, or replace those first.

=== What shipped (remedy 3)

* The bloom branch of `can_skip_file` is removed; ID lookups now fall through
  to "cannot skip" (conservative, honest), with an in-code DO-NOT-REINTRODUCE
  note explaining all of the above.
* `check_bloom_simple` is deleted.
* The fabricated 4 KiB read is deleted (one fewer range read per metadata
  load); the header reports `bloom_filter_{offset,size} = 0/0` = no filter.
  0-size was already representable in the serialized metadata, so this changes
  values, not layout — no format migration.
* The HELIX and SWIFT readers had the same shape (guessed parameters; a size
  test wearing a bloom name) and now answer conservatively ("might be
  present" / claim nothing). HELIX does have a real writer — compaction stores
  real filter bits — but no persisted parameters, so the bits cannot be read
  back correctly. RAPTOR's all-zero-bitmap serializer now errors. All recorded
  in TD-FACADE-1.
* **Downgrade hazard (layout-safe, not rollback-safe).** SST metadata blobs can
  persist across restarts via the zero-copy mmap metadata cache
  (`zero_copy/metadata_cache.rs`, `serialize_metadata` → disk → `load_from_disk`).
  Old blob + new binary is fine: the new `can_skip_file` ignores the bloom
  fields, and nothing indexes `variable_data` by a hardcoded index offset (the
  4096 → 0 shift is harmless). New blob (0/0) + an *older* binary would reach
  the old probe's `hash % 0` and panic. Inert today — `ZeroCopyMetadataCache`
  has no production construction site — but anyone activating that cache
  must not roll back across this change.

=== Still open

Building real bloom pruning: a writer that emits a real filter **with its
parameters**, and a reader that parses them — under discipline #8 (version or
magic marker, legacy fallback when absent, default-OFF until baked, round-trip +
recall gate against the unpruned baseline). Until then, `can_skip_file` must
never answer "absent" for an ID lookup.

== Non-goals

Deduplicating bloom APIs across `proximadb-bloom` / `proximablocks/bloom_filter.rs`
(see the victor scan backlog); changing any persisted format without the
migration discipline.
