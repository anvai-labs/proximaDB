== History (shipped)

pgwire used to send `AuthenticationOk` unconditionally, so strict tenant policies had to *disable* pgwire tenant
selection rather than authenticate it. Now:

* **Posture ladder, resolved once at boot** (`PgwireAuthMode::resolve`): security absent ⇒ `Trust` (byte-identical
  to before; the pgwire e2e suites); `[security.authentication] enabled = true` ⇒ **`ScramRequired`, forced** — no
  config/env can lower it; otherwise `PROXIMADB_PGWIRE_AUTH` > `[security.pgwire] auth` > trust (can raise, never
  lower). `ScramRequired` with no coordinator is a startup error.
* **Secrets** live in `AuthenticationConfig.scram_users`, separate from `api_keys` so verifier material cannot
  replay as an API key. `AuthenticationData::ScramAuthenticated` is server-side-only (no HTTP surface can forge it).
* **Exchange** (RFC 7677/5802): advertises only `SCRAM-SHA-256` (no TLS to bind, so a `p=` flag is rejected);
  unknown users run the full exchange against a mock verifier and fail with the same 28P01 shape/timing
  (anti-enumeration); constant-time comparison; auth-time rate-limit check.
* **Identity**: the verified credential flows through the one resolver (`resolve_request_identity`), so pgwire
  carries a tenant binding and `tenant_stable_id` for the first time; the DEFAULT_TENANT pre-gate remains until
  TD-AUTHZ-1 L0.4 retires it.

Evidence: RFC 7677 §3 vector + ladder matrix (`protocol_tests.rs`); `tests/pgwire_scram_auth_e2e.rs` (real
`tokio_postgres`: correct password serves `SELECT 1`; wrong password and unknown user both 28P01 with identical text).

== Residual

* Channel binding (`SCRAM-SHA-256-PLUS`) lands with native TLS negotiation (ADR-018 P3.H).
* `ALTER ROLE`/`CREATE USER`-style on-wire user management: identities are config-provisioned.
* mTLS on pgwire remains tracked in the postgres.adoc security section.
