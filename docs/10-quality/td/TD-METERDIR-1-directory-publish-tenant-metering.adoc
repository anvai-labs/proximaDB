== Problem

From TD-PAXMETA-1 F-tenant (review L3, 2026-11-21), confirmed against develop @ `ea77dea50`.
The directory publish, at flush and at compaction, resolves its filesystem with an untenanted
`get_filesystem(dir_url)`. No `TenantContext` reaches it. Each flush does roughly 3 GETs (2
ranged plus the directory), 1 LIST, 1 PUT and, from the third flush on, 1 DELETE (TD-PAXMETA-1
Status). None of these requests is metered or billed per tenant.

Isolation is not affected. The directory path is derived by `DrPathBuilder` under the
collection's tenant prefix, so isolation stays structural. The gap is metering and billing only.

== Fix

. **Verify the premise first.** Identify the per-tenant I/O metering seam that the tenanted SST
  read and write paths already use, and count its callers. If that seam does not exist at this
  layer, say so here before building one.
. Plumb the flush's and the compaction's `TenantContext` into `refresh_directory_after_flush`,
  `refresh_centroid_directory` and `shared_collection_model`. Resolve the publish's filesystem
  through that seam so the GET, LIST, PUT and DELETE requests are attributed to the tenant.
. Fail closed per the boundary contract. A publish that cannot resolve its tenant does not run
  untenanted; it is skipped with a warning. The directory is a projection, so the flush still
  succeeds and readers keep the footer path.

== Acceptance

* A counting test runs flush and compaction publishes on a tenanted collection. It shows the
  publish's GET, LIST, PUT and DELETE requests attributed to that tenant in the metering output,
  and none recorded untenanted.
* Negative control: removing the `TenantContext` plumbing turns the test red.
* The existing directory tests (TD-PAXMETA-1 evidence) and the Azurite request-count harness
  (`sift-object-store-request-counts`) are unchanged.
