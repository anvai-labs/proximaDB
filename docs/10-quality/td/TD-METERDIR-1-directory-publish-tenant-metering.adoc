== Problem

From TD-PAXMETA-1 F-tenant (review L3, 2026-11-21), confirmed against develop @ `ea77dea50`.
The directory publish, at flush and at compaction, resolves its filesystem with an untenanted
`get_filesystem(dir_url)`. The same holds for the flush's segment write itself
(`get_filesystem(&staging_url)` and `get_filesystem(&final_url)` in `flush/mod.rs`) and, on a
first look, for the compaction output write (`get_filesystem(&output_path)` in `compaction.rs`).
So the directory publish is one known gap, not the only one. No `TenantContext` reaches it. Each flush does roughly 3 GETs (2
ranged plus the directory), 1 LIST, 1 PUT and, from the third flush on, 1 DELETE (TD-PAXMETA-1
Status). None of the directory requests is metered or billed per tenant. Whether the segment-write
bytes are metered some other way (for example by a decorator below `get_filesystem`) is not yet
verified; that is the census step below.

Isolation is not affected. The directory path is derived by `DrPathBuilder` under the
collection's tenant prefix, so isolation stays structural. The gap is metering and billing only.

[[premise]]
== Premise check (fix step 2)

Fix step 2 asks for the per-tenant I/O metering seam that the tenanted SST read and write paths
already use. It does not exist at the storage layer. A per-tenant billing module does exist one
layer up, and the storage layer never calls it for the operations a provider bills for.
Evidence, develop @ `be45e7122`.

The billing module exists and is always on:

* `src/metrics/consumption_metrics.rs` is installed unconditionally at boot
  (`install_billing_observer`, called from `src/database.rs`). It already has the meters this TD
  needs: `record_object_store_op(tenant, operation)`, `record_storage_bytes(tenant, kind, bytes)`
  and `record_object_store_write_bytes_by_tier(tenant, tier, bytes)`.
* Bytes at rest are snapshotted per tenant every 300 s (`record_storage_snapshot`, from the
  same file), and pushed to the durable metering writer every 3600 s.
* `build_kru` (`proximadb-observability-engine/src/metering_event.rs`) bills reads from a search
  plan trace and has one production caller. That is read-compute billing, not storage.

The storage layer does not reach those meters:

* **Two storage stacks, and neither is tenanted.**
  ** The `FileSystem` stack resolves through `FileSystemFactory::get_filesystem(&self, url)` in
     `src/storage/persistence/filesystem/mod.rs`, which takes no tenant.
  ** The second stack, `ProximaObjectStore` over upstream `object_store`
     (`crates/storage/proximadb-object-store/src/lib.rs`), has no factory. 18 production
     files call `ProximaObjectStore::from_url` directly.
* **Reads are counted, but not by tenant.**
  ** The `FileSystem` stack counts GETs and bytes into process-global `GetCounters`
     (`proximadb-storage-filesystem-types/src/counting.rs`).
  ** The second stack records reads into the per-query `IoTrace` through a process-global
     recorder (`install_io_recorder`, installed in production at `src/database.rs`).
  ** Neither is keyed by tenant, and neither is a billing record.
* **Writes, LISTs, HEADs and DELETEs are not counted at the provider layer.** On the second
  stack every provider call goes through the methods of `ProximaObjectStore` (`get`,
  `get_range`, `get_ranges`, `head`, `list`, `put_opts`, `put_if_absent`, `delete`). Only the
  three GET methods record anything.
* **The billing meters are called by hand from upper layers.** `record_object_store_op` has 8
  production call sites, in `src/services/record_store.rs` and
  `src/storage/flush_materializer.rs`. They count engine operations, not provider requests: one
  `"flush_write"` per flush, however many PUTs, LISTs and DELETEs that flush issued.
* `record_storage_bytes` has 0 callers outside the at-rest snapshot.
  `record_object_store_write_bytes_by_tier` has 3 production callers.
* No document under `docs/` defines a storage unit (`\bKSU\b` has no hit).

Consequence: every provider request the engines issue below those hand-placed sites reaches the
provider without being attributed to the tenant that caused it. Passing a `TenantContext` down
to `get_filesystem` by itself would change nothing, because neither stack reads a tenant at that
layer.

Limits of the at-rest snapshot, found while checking this:

* **Its size is the engine's own counter.** `aggregate_tenant_storage` sums
  `stats.data_size_bytes` from `list_collections()`. That is not a measurement of the bucket.
  Objects the engine does not count, such as directory objects, catalog shards, Iceberg
  metadata and superseded generations awaiting cleanup, are stored and billed by the provider
  but absent from the number.
* **Its tenant is `config.owner`.** A collection with no owner is attributed to `"default"`. A
  missing owner moves a collection's storage to an account nobody is billed for.

[[decision]]
== Direction (2026-11-28) and open questions

Direction given 2026-11-28: meter every operation that AWS, Azure or GCP bill for, so that the
cost of each request can be passed through to the tenant that caused it, with no cost left
unattributed. The approach is risk conservative.

Deployment assumptions stated with it:

* Compute (ECS/EC2) and storage are in the same region and availability zone.
* S3 is reached through a gateway endpoint, so there is no egress or bandwidth charge. Only S3
  API requests and GB-month at rest are billed.
* The WAL is on EBS or on S3 Standard. Final data is on S3 Standard.
* Compute is amortized through a per-user monthly fee carried by the tier, except for freemium,
  and is enforced through query limits measured in QPS per profile.
* No margin is taken on growth tiers. Margin comes from disk and memory caches in front of the
  cold tiers.

What follows for this TD:

. *What is metered.* Every provider request by kind (GET, ranged GET, LIST, HEAD, PUT including
  conditional PUT, DELETE, COPY where the backend issues one), with bytes for every GET and PUT.
  The ledger keeps raw requests and raw bytes, which is what each provider's price list is
  written in.
. *Bytes at rest* stay a periodic snapshot. They are out of scope for the per-request meter and
  are reconciled separately.
. *When no tenant resolves.* The request is recorded against an explicit operator account. It
  is never dropped, and it never fails the I/O: a segment write cannot be skipped. This makes
  unattributed cost visible instead of silently absorbed.

Open questions, put to the owner on 2026-11-28 and not yet answered. They change the shape of
the build and are recorded here so the answers land next to the work:

. *WAL placement.* Is the WAL on EBS or on S3 by default, and is it per tenant? A WAL on S3
  issues a PUT per commit, which makes it the most request-expensive path a write-heavy tenant
  can drive. On EBS it costs nothing per request.
. *At-rest accuracy.* Is the engine's size counter acceptable as the billable number, or must
  bytes at rest be measured from the bucket? Measuring costs LIST and HEAD requests. A hybrid
  is to measure daily and reconcile against the counter.
. *Storage classes.* Can tenant data move to Infrequent Access or Archive? A restore from
  Archive bills a per-GB retrieval fee and a per-request fee, far above a normal GET, and would
  need its own meter.
. *Ownerless collections.* Is every collection guaranteed to have an owner? If not, should one
  with no owner be refused at creation?
. *Freemium budget.* What hard S3 request budget does a freemium tenant get? Freemium tenants
  still generate request cost.
. *Unattributed cost.* Confirm that recording it to a visible operator account is preferred
  over failing the request.

The open design question is how the tenant reaches the provider-facing methods on the second
stack, which has no factory and 18 construction sites. That belongs in a metering design
record, not in this TD.

== Fix

. **Census.** DONE 2026-11-28, see <<census>>. List every filesystem resolution on the PAX flush and compaction paths (segment
  staging and final writes, compaction output, directory publish and directory load, deletes of
  superseded generations). For each one, record whether a `TenantContext` reaches it and whether
  its requests and bytes are metered per tenant. Commit the list here.
. **Verify the premise.** DONE 2026-11-28, see <<premise>>. No per-tenant metering seam exists at
  the storage layer. A per-tenant billing module exists one layer up, and the storage layer
  never calls it for provider-billed operations. Identify the per-tenant I/O metering seam that the tenanted SST
  read and write paths already use, and count its callers. If that seam does not exist at this
  layer, say so here before building one.
. **Meter provider requests.** Record every provider request by kind, with its bytes for GET and
  PUT, against the tenant that caused it. Do this at the provider-facing methods of both storage
  stacks, so no call site can forget it. Feed `record_object_store_op` and the byte meters in
  `src/metrics/consumption_metrics.rs`; do not build a second ledger. Scope is wider than this
  TD's original flush and compaction paths: every provider-facing method on both stacks. Tracked
  in the metering design record.
. **Plumb the tenant.** Carry the tenant to the provider-facing methods. For this TD's paths
  that means `refresh_directory_after_flush`, `refresh_centroid_directory`,
  `shared_collection_model` and the segment write. A request whose tenant cannot be resolved is
  recorded against the explicit operator account from <<decision>>.
. Fail closed per the boundary contract. A directory publish that cannot resolve its tenant does
  not run untenanted; it is skipped with a warning. The directory is a projection, so the flush
  still succeeds and readers keep the footer path. A segment write is not optional, so it is
  attributed to the operator account, as <<decision>> now specifies. It is never dropped from the
  ledger and it never silently goes unmetered.
. **Reconcile bytes at rest.** Compare the at-rest snapshot (the engine's `data_size_bytes`,
  attributed by `config.owner`) with the bucket, on a cadence set by the answer to the at-rest
  question in <<decision>>, and alert when they diverge.

== Acceptance

* The census is committed in this TD.
* A counting test runs a flush and a compaction on a tenanted collection. It shows every
  request of the segment writes and the directory publish (GET, LIST, HEAD, PUT, DELETE)
  recorded against that tenant in the billing meters, with its bytes where the request carries
  any.
* Negative control: removing the tenant plumbing turns the test red, because the requests land
  on the operator account instead of the tenant.
* No request is ever dropped from the ledger: a test with no resolvable tenant shows every
  request recorded against the operator account.
* The at-rest snapshot for a tenant equals the sum of that tenant's collections' sizes, and a
  collection with no owner is visible on the operator account rather than on `"default"`.
* The existing directory tests (TD-PAXMETA-1 evidence) and the Azurite request-count harness
  (`sift-object-store-request-counts`) are unchanged.
