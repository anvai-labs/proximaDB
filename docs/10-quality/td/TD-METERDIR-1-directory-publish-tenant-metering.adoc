== Problem

From TD-PAXMETA-1 F-tenant (review L3, 2026-11-21), confirmed against develop @ `ea77dea50`.
The directory publish, at flush and at compaction, resolves its filesystem with an untenanted
`get_filesystem(dir_url)`. The same holds for the flush's segment write itself
(`get_filesystem(&staging_url)` and `get_filesystem(&final_url)` in `flush/mod.rs`) and, on a
first look, for the compaction output write (`get_filesystem(&output_path)` in `compaction.rs`).
So the directory publish is one known gap, not the only one. No `TenantContext` reaches it. Each flush does roughly 3 GETs (2
ranged plus the directory), 1 LIST, 1 PUT and, from the third flush on, 1 DELETE (TD-PAXMETA-1
Status). None of the directory requests is metered or billed per tenant. Whether the segment-write
bytes are metered some other way was settled by the census: they are not. The segment PUT is
issued from `staged_write.rs`, outside any query trace, and nothing records it per request.

Isolation is not affected. The directory path is derived by `DrPathBuilder` under the
collection's tenant prefix, so isolation stays structural. The gap is metering and billing only.

[[census]]
== Census (fix step 1)

Done 2026-11-28 against develop @ `8a0d2ca27`. A first version of this census listed the 10
`get_filesystem` calls in `flush/mod.rs` and `compaction.rs` and stopped there. That was
incomplete in two ways. The PUT that publishes a segment is resolved in a third file,
`crates/storage/proximadb-sst-engine/src/staged_write.rs`, and compaction deletes superseded
generations through `factory.delete(path)`, which resolves a filesystem internally. Both were
missing. The table below covers them.

"Metered per tenant" means: reaches the always-on per-tenant billing meters in
`src/metrics/consumption_metrics.rs`.

Result: no site on the flush or compaction path receives a tenant, and only one of them is
metered at all, and that one per engine operation rather than per provider request. The
question this census was meant to settle (are the segment-write bytes metered by a decorator
below `get_filesystem`?) is answered: no.

[[premise]]
== Premise check (fix step 2)

Fix step 2 asks for the per-tenant I/O metering seam that the tenanted SST read and write paths
already use. One exists for *reads on the query path*. It does not exist for writes, for
deletes, or for any I/O outside a query. Evidence, develop @ `8a0d2ca27`.

What exists and is always on:

* `src/metrics/consumption_metrics.rs` is installed unconditionally at boot
  (`install_billing_observer`, called from `src/database.rs`). It has `record_object_store_op`,
  `record_storage_bytes` and `record_object_store_write_bytes_by_tier`.
* **Query-path reads are billed per tenant today.** At the physical boundary the `FileSystem`
  stack records every GET, ranged GET, LIST and HEAD, with bytes, into the per-query `IoTrace`
  (`record_physical_full_read` and its neighbours in `src/storage/persistence/filesystem/mod.rs`).
  That trace carries the tenant, and the billing observer reads it. The second stack's reads
  reach the same trace through `install_io_recorder`.
* An at-rest snapshot runs per tenant: every 300 s by default into the gauge, and every 3600 s
  by default into the durable metering writer. Both intervals are environment-overridable.
* KSU is defined as resident bytes times time, in
  link:../../12-design/adr/ADR-030-unified-hotpath-trace-meter-seam.adoc[ADR-030], which states
  that KSU is *not* metered there.

What is missing:

* **PUT and DELETE are not metered anywhere.** They fall outside a query, so no trace covers
  them. This is the gap that matters for a provider that bills per request.
* **The request meters are called by hand from upper layers.** `record_object_store_op` has 8
  production call sites, in `src/services/record_store.rs` and
  `src/storage/flush_materializer.rs`. They count engine operations, not provider requests: one
  `"flush_write"` per flush, however many PUTs, LISTs and DELETEs that flush issued.
* **`record_storage_bytes` has no caller outside the at-rest snapshot.**
  `record_object_store_write_bytes_by_tier` has 3 production callers.
* **The second stack has no choke point.** `ProximaObjectStore`
  (`crates/storage/proximadb-object-store/src/lib.rs`) has no factory: 10 production files
  construct it directly through `from_url`. It also exposes the raw upstream store, through
  `store()` and through the free function `store_for_url`, so a provider call can bypass its
  methods entirely.
* **On the second stack only the GET methods record anything.** `head`, `list`, `put_opts`,
  `put_if_absent` and `delete` do not.
* **The process-global `GetCounters` are not a billing input.** They are wrapped in only when
  `PROXIMADB_COUNT_FS_IO` is set, which only benchmarks set.

Consequence: adding a request meter without care would double-bill reads, which are already
billed, and would still miss the PUTs and DELETEs. The work is therefore narrower and more
specific than this TD first assumed: meter PUT and DELETE (and LIST and HEAD outside a query)
at the provider boundary, and leave the existing read path alone.

[[atrest]]
== Defect found: the at-rest snapshot reads a counter the server never updates

This is a billing defect, not a documentation gap. It is recorded here because it was found
during this check and it directly understates GB-month.

* `aggregate_tenant_storage` sums `stats.data_size_bytes` over `list_collections()`.
* That field is created as `0` (`src/services/collection/manager.rs`, collection creation).
* Its only writer is `CollectionManager::update_stats`, and the only production caller of that
  method is the embedded binding (`crates/binding/proximadb-embedded/src/lib.rs`). The server
  does not call it.
* The server's write path calls a different `update_stats`, on the write-buffer manager
  (`src/storage/metadata/atomic.rs`, `store.rs`, `write_ahead_log.rs`). That updates the write
  buffer's own in-memory statistics, not the catalog record the snapshot reads.

Result: for data written through the server, the per-tenant at-rest figure stays at whatever it
was at creation. The hourly durable snapshot records `0` for it. GB-month is therefore not
billed for server-ingested data.

Two further limits of the same snapshot:

* **Its tenant is `config.owner`.** A collection whose config is absent, or whose owner is
  absent or empty, is attributed to `"default"`. A missing owner moves a collection's storage
  to an account nobody is billed for.
* **Even where the counter is updated, it is the engine's own number**, not a measurement of
  the bucket. Objects the engine does not count, such as the directory objects written by
  `centroid_directory_publisher.rs`, are stored and billed by the provider but absent from it.

[[decision]]
== Direction (2026-11-28) and open questions

Direction given 2026-11-28: meter every operation that AWS, Azure or GCP bill for, so that the
cost of each request can be passed through to the tenant that caused it, with no cost left
unattributed. The approach is risk conservative.

Deployment assumptions stated with it:

* Compute (ECS/EC2) and storage are in the same region and availability zone.
* S3 is reached through a gateway endpoint, so there is no egress or bandwidth charge. Only S3
  API requests and GB-month at rest are billed.
* The WAL is on EBS or on S3 Standard. Final data is on S3 Standard.
* Compute is amortized through a per-user monthly fee carried by the tier, except for freemium,
  and is enforced through query limits measured in QPS per profile.
* No margin is taken on growth tiers. Margin comes from disk and memory caches in front of the
  cold tiers.

What follows, given what <<premise>> found:

. *Reads on the query path are already billed per tenant.* They must not be metered a second
  time. Any new meter has to exclude them, or the read bill doubles.
. *PUT and DELETE are the unmetered billable operations.* They are what this TD meters first.
  LIST and HEAD outside a query are metered the same way.
. *The ledger keeps raw requests by kind and raw bytes.* That is what each provider's price list
  is written in, so a price can be applied per provider later without re-measuring.
. *Bytes at rest need the counter fixed before they can be billed.* See <<atrest>>.
. *When no tenant resolves*, the request is recorded against an explicit operator account. It
  is never dropped from the ledger, and it never fails the I/O: a segment write cannot be
  skipped. Unattributed cost becomes a visible line rather than an absorbed one. This is the
  proposed rule and is listed below as still to be confirmed.

Open questions, put to the owner on 2026-11-28 and not yet answered. They change the shape of
the build and are recorded here so the answers land next to the work:

. *WAL placement.* Is the WAL on EBS or on S3 by default, and is it per tenant? A WAL on S3
  issues a PUT per commit, which makes it the most request-expensive path a write-heavy tenant
  can drive. On EBS it costs nothing per request.
. *At-rest source.* Now that the server's size counter is known not to move (<<atrest>>), should
  bytes at rest be measured from the bucket, or should the counter be fixed and kept as the
  source? Measuring from the bucket costs LIST and HEAD requests. A hybrid is to measure daily
  and reconcile against the counter.
. *Storage classes.* Can tenant data move to Infrequent Access or Archive? A restore from
  Archive bills a per-GB retrieval fee and a per-request fee, far above a normal GET, and would
  need its own meter.
. *Ownerless collections.* Is every collection guaranteed to have an owner? If not, should one
  with no owner be refused at creation?
. *Freemium budget.* What hard S3 request budget does a freemium tenant get? Freemium tenants
  still generate request cost.
. *Unattributed cost.* Confirm that recording it to a visible operator account is preferred
  over failing the request.

The open design question is how the tenant reaches the provider-facing methods on the second
stack. That stack has no factory, 10 production files construct it directly, and it exposes the
raw upstream store, so a meter on its methods alone can be bypassed. That belongs in a metering
design record, not in this TD.

== Fix

. **Census.** DONE 2026-11-28, see <<census>>. It was corrected the same day after review: the
  first version missed the file that issues the segment PUT and the path that deletes superseded
  generations.
. **Verify the premise.** DONE 2026-11-28, see <<premise>>. Reads on the query path are billed
  per tenant. PUT and DELETE are not metered anywhere.
. **Fix the at-rest counter.** See <<atrest>>. Give the server a writer for
  `stats.data_size_bytes`, so the per-tenant snapshot reflects server-ingested data. Then decide
  the at-rest source (question 2 above) and add a reconciliation against the bucket. This comes
  before any per-request meter, because GB-month is billed now and is wrong now.
. **Meter writes and deletes.** Record every PUT, conditional PUT and DELETE, with bytes for
  PUT, against the tenant that caused it, at the provider-facing boundary of both storage stacks.
  LIST and HEAD issued outside a query are metered the same way. Feed the existing meters in
  `src/metrics/consumption_metrics.rs`. Do not build a second ledger.
. **Do not double-bill reads.** Show, in a test, that a query-path read is billed once and only
  once after the write meter lands.
. **Close the bypass.** The second stack exposes the raw upstream store through `store()` and
  `store_for_url`. Either route those through the metered surface or record the gap explicitly.
. **Plumb the tenant.** Carry the tenant to the provider-facing boundary. For this TD's paths
  that means `staged_write.rs` (the segment PUT), `retire_compaction_input` (the DELETEs),
  `refresh_directory_after_flush`, `refresh_centroid_directory` and `shared_collection_model`.
  A directory publish that cannot resolve its tenant is skipped with a warning and is not run
  untenanted: the directory is a projection, so the flush still succeeds and readers keep the
  footer path. A request whose tenant cannot be resolved is recorded against the operator
  account, once that rule is confirmed.

== Acceptance

* The census is committed in this TD.
* A counting test runs a flush and a compaction on a tenanted collection. It shows every PUT and
  DELETE of the segment write, the directory publish and the superseded-generation cleanup
  recorded against that tenant in the billing meters, with bytes for each PUT.
* Negative control: removing the tenant plumbing turns the test red, because the requests land
  on the operator account instead of the tenant.
* No request is ever dropped from the ledger: a test with no resolvable tenant shows every
  request recorded against the operator account.
* A query-path read is billed exactly once. A test asserts the read count in the billing meters
  is unchanged by the write meter.
* The at-rest snapshot for a tenant grows after the server writes data to that tenant's
  collection. A test creates a collection, inserts through the server path, and asserts the
  snapshot is non-zero.
* A collection with no owner is visible on the operator account rather than on `"default"`.
* The existing directory tests (TD-PAXMETA-1 evidence) and the Azurite request-count harness
  (`sift-object-store-request-counts`) are unchanged.
