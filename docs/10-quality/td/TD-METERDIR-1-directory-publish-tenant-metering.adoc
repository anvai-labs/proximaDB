== Problem

From TD-PAXMETA-1 F-tenant (review L3, 2026-11-21), confirmed against develop @ `ea77dea50`.
The directory publish, at flush and at compaction, resolves its filesystem with an untenanted
`get_filesystem(dir_url)`. The same holds for the flush's segment write itself
(`get_filesystem(&staging_url)` and `get_filesystem(&final_url)` in `flush/mod.rs`) and, on a
first look, for the compaction output write (`get_filesystem(&output_path)` in `compaction.rs`).
So the directory publish is one known gap, not the only one. No `TenantContext` reaches it. Each flush does roughly 3 GETs (2
ranged plus the directory), 1 LIST, 1 PUT and, from the third flush on, 1 DELETE (TD-PAXMETA-1
Status). None of the directory requests is metered or billed per tenant. Whether the segment-write
bytes are metered some other way (for example by a decorator below `get_filesystem`) is not yet
verified; that is the census step below.

Isolation is not affected. The directory path is derived by `DrPathBuilder` under the
collection's tenant prefix, so isolation stays structural. The gap is metering and billing only.

(are the segment-write bytes metered by a decorator below `get_filesystem`?) is answered: no.

[[premise]]
== Premise check (fix step 2)

Fix step 2 says to identify the per-tenant I/O metering seam that the tenanted SST read and
write paths already use. It does not exist. Evidence, same commit:

* `FileSystemFactory` has one resolution method, `get_filesystem(&self, url)` in
  `src/storage/persistence/filesystem/mod.rs`. It takes no tenant.
* `crates/storage/proximadb-object-store/src/` contains no `TenantContext` and no tenant id.
  No object-store request carries one.
* `io_trace` (`crate::observability::io_trace`) is a task-local request counter used by tests.
  It records no tenant and feeds no billing record.
* The only per-tenant I/O metering in the tree is `build_kru`, in
  `crates/modalities/proximadb-observability-engine/src/metering_event.rs`. It bills *reads*,
  computed from a search plan trace, and has one production caller (`trace_batcher.rs`).
* Nothing meters storage. There is no KSU event, no producer of one, and no document that
  specifies it (`\bKSU\b` has no hit under `docs/`).

Consequence: passing a `TenantContext` down to `get_filesystem` would change nothing billable,
because nothing below it reads a tenant. The work in fix steps 3 and 4 (plumb the context,
attribute the GET, LIST, PUT and DELETE requests) therefore first needs a storage metering
seam to exist, and a decision on what a storage unit is.

[[decision]]
== Decision needed

Which of these this TD builds is a product and billing choice, not an implementation detail:

. *What is metered.* Requests by kind (GET, LIST, PUT, DELETE), bytes written and read, or both.
. *What a storage unit is.* The co-design mandate names KSU but no document defines it.
. *Where the tenant is attached.* At `get_filesystem` (a tenanted resolver that wraps the
  returned `FileSystem` in an attributing decorator), or at each call site.
. *What happens when no tenant resolves.* The directory publish is skipped with a warning, as
  this TD already specifies. A segment write cannot be skipped; it is either attributed to an
  explicit operator account or the flush fails.

Until that is decided, this TD stays Open and no code is changed. The acceptance criteria below
are unchanged and still apply once it is.

== Fix

. **Census.** DONE 2026-11-28, see <<census>>. List every filesystem resolution on the PAX flush and compaction paths (segment
  staging and final writes, compaction output, directory publish and directory load, deletes of
  superseded generations). For each one, record whether a `TenantContext` reaches it and whether
  its requests and bytes are metered per tenant. Commit the list here.
. **Verify the premise.** DONE 2026-11-28, see <<premise>>. The seam does not exist. Identify the per-tenant I/O metering seam that the tenanted SST
  read and write paths already use, and count its callers. If that seam does not exist at this
  layer, say so here before building one.
. **BLOCKED** on <<decision>>. Build the storage metering seam: a tenanted filesystem resolution
  that attributes each request and its bytes to the tenant.
. **BLOCKED** on the step above. Plumb the flush's and the compaction's `TenantContext` into every untenanted call the census finds,
  including `refresh_directory_after_flush`, `refresh_centroid_directory`,
  `shared_collection_model` and the segment write. Resolve each filesystem through that seam so
  the GET, LIST, PUT and DELETE requests are attributed to the tenant.
. Fail closed per the boundary contract. A directory publish that cannot resolve its tenant does
  not run untenanted; it is skipped with a warning. The directory is a projection, so the flush
  still succeeds and readers keep the footer path. A segment write is not optional, so the PR
  must state and test its behavior when no tenant resolves: either the flush fails, or the write
  is attributed to an explicit operator/untenanted account. It must never silently go
  unmetered.

== Acceptance

* The census is committed in this TD.
* A counting test runs a flush and a compaction on a tenanted collection. It shows every
  request of the segment writes and the directory publish (GET, LIST, PUT, DELETE) attributed to
  that tenant in the metering output, and none recorded untenanted.
* Negative control: removing the `TenantContext` plumbing turns the test red.
* The existing directory tests (TD-PAXMETA-1 evidence) and the Azurite request-count harness
  (`sift-object-store-request-counts`) are unchanged.
