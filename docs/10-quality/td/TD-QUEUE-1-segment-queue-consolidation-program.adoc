== 1. Problem

Five separate append-only log / queue implementations each re-roll sequence-counter + path
scheme + recovery scan + in-memory index on the raw `FileSystem`, and drift on correctness
(see ADR-079 §Context for the evidence). Meanwhile `proximadb-queue` already centralizes the
segment-based, per-topic-directory, producer/consumer, three-tier shape — **complete and
tested (74 tests)** — but was never adopted for internal use, which is precisely why the
silos exist.

== 3. Verification

Compile is not the gate here — the migrations change durability/recovery paths.

* **Per migrated topic (mandate #8):** round-trip (produce → consume → assert order + payload)
  + crash-recovery (produce → kill → reopen → resume → no loss/dup) on **both** `file://`
  and an object-store scheme (the `FileSystem::list` shape hazard already bit the audit-log
  recovery scan once).
* **Defect-becomes-regression tests:** (a) audit appends survive restart over the same
  `base_dir`; (b) AXIS compaction publishes once, no double-index; (c) MCP checkpoint
  get-by-thread returns persisted state after restart.
* Layering + workspace-boundary guards green after the move; `cargo build -p proximadb-server`
  (mandate #11); env-gate registry for any new `PROXIMADB_QUEUE_*` gate.
* Recall ratchet unaffected (queue is coordination).

== 4. Residual

The collection WAL stays separate (ADR-071) — it is the write-path durability floor, not the
async/coordination plane this primitive covers. The user-facing Queue *modality* is
unaffected (it shares the primitive; no client-visible API change).
