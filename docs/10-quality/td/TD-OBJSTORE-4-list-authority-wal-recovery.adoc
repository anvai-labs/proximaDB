== Measured root cause (supersedes the "zero-vector" attribution)

The batch-3 symptom was reported as "dim-1 zero-vector KV records not recovered". The
reproduction (`zero_vector_kv_record_survives_restart`,
`apps/proximadb-server/tests/object_store_restart_recovery.rs`, run against Azurite)
shows it is **not** zero-vector- or dim-1-specific: a non-zero `[0.5]` control record is
lost identically. The variable is **unflushed (WAL-only) data on an object-store
backend**. anvaiops' KV collections are simply the only collections small enough to
never flush — flushed collections survive via segment discovery, masking the bug.

Two stacked defects:

. **Pointer write is async while ack is sync.** `disk_manager.rs:273` registers each
  WAL batch in the global manifest via `append_async` → channel → background worker
  batching at 100 ms (`manifest/service.rs:44,133-177`). The `.bcwal` data PUT is
  synchronous (`PerBatch`), the ack returns, SIGKILL lands, the pointer dies in the
  channel. Evidence: post-crash blob listing shows the data object present and **zero**
  manifest objects under `{base}/wal/`; no warn/error anywhere in the boot-1 log.
. **The LIST fallback is dead code on object stores.** Catalog-driven recovery correctly
  enumerated the collection and registered its engine (TD-OBJSTORE-2 works), then
  `recover_collection_internal`'s best-effort `list_collection_files`
  (`disk_manager.rs:362`) gates on `filesystem.exists(dir_url)` for a directory prefix.
  Flat-key `exists()` is a HEAD on the literal key (`azure_blob.rs:277`) → false for
  prefixes → early-return 0 files. (`parse_wal_filename` and `collection_wal_url` are
  correct; the LIST would have found `8dWbZDDUPo.bcwal` had it run.)

Net: "Recovered 0 vectors from 0 files" while the data sits durable in the store.

== Fix specification (ADR-063 D3/D4/D5/D7 — r2, post-review)

_(r1's S3 claimed replay was already idempotent via mandate 16a/16d — WRONG: those are
read-merge semantics, not `do_flush` invariants; `do_flush` mints a fresh
time/random-named L0 segment per call, and legacy batch-ids are wall-clock +
process-local. The r2 spec below is the reviewed protocol.)_

*S1 — Kill the prefix-`exists()` gate; fail closed on LIST errors; paginate GCS.*
`list_collection_files` LISTs directly; an **empty result** is the absent signal, a
**LIST error** (auth/network/throttle) is retried then fails that collection's recovery
loudly — never treated as empty, and the legacy `write_buffer/` fallback must stop
swallowing errors through `if let Ok(...)`. All three backends' `exists()` are
exact-key probes (`azure_blob.rs:277`, `aws_s3.rs:226`, `gcs_store.rs:180`), so this
defect is backend-wide. **r3:** the production GCS backend consumes ONE
`list_objects` page and ignores `next_page_token` (`gcs_store.rs:213`) — add the
pagination loop + a multi-page conformance test on the production backend. Source-guard
test for the `exists(...)-before-list(...)` pattern on WAL paths (model:
`objstore_url_construction_test.rs::no_strip_and_reprepend_pattern_in_src`).

*S2 — Self-describing, pre-PUT-ordered WAL objects (r3: incarnation-unique epoch,
epoch-first keys).* Before the data PUT the writer allocates `{epoch, per-collection
sequence}` and encodes it **epoch-first** — `{epoch:020}-{sequence:020}-{batch_id}.bcwal`
(sequence-first is not lexicographically ordered across sequence resets) — and in a
**plaintext authenticated OUTER envelope** — `{magic/version, recovery token, payload
checksum, encryption key/version/nonce metadata}`, bound to the (possibly encrypted)
serialized batch payload as AEAD associated data (r3.1: the write path serializes then
encrypts at `disk_manager.rs:202`, so metadata INSIDE the serialized header could
never be read to decrypt it; today `WalFileInfo.encryption_metadata` is `None` on
recovery — the envelope closes that). The batch payload carries a per-record ordinal
(duplicate OIDs in one request replay in request order). The epoch comes from **`begin_writer_incarnation`** — a CAS generation bump
once per process incarnation, even for the same pod ID (plain lease renewal at
`partition_lease.rs:1988` reuses the generation for a matching pod, so a container
restart would reuse the epoch and reset the sequence). The manager caches
`{generation, AtomicU64, expiry}` (registry fast path exists at
`partition_lease.rs:2239`) so allocation costs no I/O per batch. Companion
requirements: canonical lease key = resolved collection **UUID** (RecordOps currently
leases by name while WAL persistence sees the UUID — one identifier only); token
threaded into the WAL layer via an injected `RecoveryTokenProvider` (tenant +
generation); renewal failure stops acks once the cached expiry passes; serverless-
certified mode makes WAL-token fencing **mandatory fail-closed** (not the default-OFF
`PROXIMADB_WRITE_FENCING`). Create with **put-if-absent**. The manifest LSN cannot be
reused: it is allocated after the data PUT.

*S3 — LIST-authority recovery with crash-idempotent materialization (r3: commit-record
segment + compaction suppression).* Per-collection recovery merges manifest entries
(cache: flushed-status skip-list) with the LIST of `{collection}/wal/`; batches present
in the store but unflushed are replayed regardless of manifest presence. Replay
resolves ALL same-key mutations in token order **in memory**, then materializes ONE
segment named from the replayed token range **plus a canonical content digest**,
written via a new **`FileSystem::write_if_absent`** (S3/Azure `PutMode::Create`, GCS
`if_generation_match=0`, local `create_new`, collision → typed `AlreadyExists`;
today's production `write` OVERWRITES on all backends — the capability must cover the
caching/encryption wrappers and be conformance-tested against the production
filesystem impls on the emulators). On `AlreadyExists`, verify the existing segment's
digest/footer before treating it as success; the already-materialized path returns
**before** AXIS/statistics side effects. **Suppress inline compaction during recovery
materialization until the WAL range is durably retired** — the synchronous post-flush
compaction (`sst/flush/mod.rs:554`) would otherwise consume the deterministic segment
and emit a random-named one before WAL deletion; a crash there duplicates records on
re-replay. `FlushParameters.trigger_compaction` does not control SST's decision — pass
a recovery hint that actually suppresses (the `engine-hints` map at
`proximadb-storage-traits/src/types.rs:19` threads a validated
`recovery_materialization_id` without breaking `FlushParameters` literals; typed field
later). Markers/manifest watermarks are NOT substitutes (two-object crash window) —
the digest-named segment is the commit record. `recover_all` must not early-return on
an empty manifest while the catalog has collections.

*S4 — Manifest-state fixes; manifest stays an async cache.* (a) Manifest load dedups
equal-LSN entries status-aware — `Flushed` supersedes `Active` at the same LSN (today
the earlier `Active` can survive reload). (b) On successful orphan recovery, register/
mark-flushed in the fresh manifest so later boots skip it. (c) No new synchronous PUT
on the write path (ADR-063 A2 stays rejected; the self-describing object is the
zero-round-trip answer).

*S5 — Single-recoverer fencing (r3).* The recoverer calls `begin_writer_incarnation`
on the collection's generation-fenced lease (a plain acquire is insufficient — same-pod
renewal reuses the generation) under the canonical UUID lease key, before replay; the
acquired incarnation epoch IS S2's token epoch. Concurrent recoverer pods and stale
writers are fenced by the same mechanism.

*S6 — Fail-closed legacy-orphan policy (r3: semantic, not count-based).* Token-less
orphan batches replay automatically only when **semantic non-overlap is provable** —
e.g. a fresh collection with no existing segments and no other WAL batches (the
batch-3 repro shape). A single orphan is NOT inherently unambiguous (it may hold an
older value than a manifested batch, or an update/delete against an existing segment,
or an OID shared with newer tokenized WAL). Anything else halts loudly for an explicit
operator ordering decision. Acceptable pre-GA: the token naming ships with this TD,
bounding the legacy window; the anvaiops testbed can re-seed.

== Gates (TDD)

* RED→GREEN: `zero_vector_kv_record_survives_restart` (Azurite strict; MinIO in the QA
  tier, gs:// nightly — TD-OBJSTORE-5) — both `rec-ctrl` and `rec-zero` readable by id

* NEW: **double-replay idempotency** test — flush succeeds, WAL deletion suppressed,
  restart again → no duplicate segments/records (S3); **recovery-compaction-suppression**
  test — recovery flush with compaction armed must NOT compact until WAL retirement
  (S3, r3); **write_if_absent conformance (shipped #1129)** on the production
  `FileSystem` implementations (Azure/S3 strict, fake-gcs best-effort because it does
  not enforce `ifGenerationMatch=0`) plus caching/encryption wrappers (S3, r3); **equal-LSN dedup**
  unit test (S4a); **out-of-order orphan** test — old same-key orphan + newer
  manifested batch → newer value wins (S2/S3); **epoch-incarnation** test — restart
  with same pod identity mints a HIGHER epoch (S2, r3); **multi-page GCS LIST**
  conformance on the production backend (S1, r3); source-guard for prefix-`exists()`
  (S1); backend contract tests (PUT→prefix-LIST positive, prefix-HEAD-negative,
  multi-page) against the production root FileSystem backends, all three emulators.
* Failure-mode coverage: every row of ADR-063's "Failure modes covered (r2)" table maps
  to a slice above; the ADR flips Accepted when each has a specified normative

== Deferred / adjacent (do not fold into this fix)

Durable surfaces classified by ADR-063 D6 (r3 inventory: TST timeseries local-temp
fallback, external-collections operational registry, collection-pinning registry,
primary-pod `SidecarOnly` default, legacy document WAL, observability WAL audit) — file
separate TDs per surface as they are prioritized. Env-var bootstrap consolidation stays
TD-OBJSTORE-3.

From the staged-segment-I/O review (defect-6 class close-out):

* *Streaming/multipart segment upload* — `StagedSegmentWrite::finalize` buffers the
  whole segment in RAM; bounded for flush (memtable-sized) but a compaction output
  merges N inputs. Needs a streaming `FileSystem` upload shape.
* *Segment cache for cloud reads* — `search_arrow_file` and the exact PAX scan are
  per-query full-object GETs on cloud bases (previously they read a broken local
  artifact); round-trips are the dominant cost term, so front them with the
  footer/segment cache.
* *Scratch sweep* — `StagedSegmentWrite`/`LocalizedSegment` now carry Drop guards,
  but crash-stranded files in `proximadb-flush-staging`/`proximadb-segment-scratch`
  need an age-based startup sweep (uuid names make it cross-process safe).
* *`sst/extraction.rs` audit* — retains a `file://` strip with a SILENT-skip failure
  mode (cloud URL survives the strip, `Path::exists()` false, file quietly dropped
  from AXIS extraction). Same class, different blast radius; also `nova`/`swift`
  extraction + the DataFusion `pax_adapter` (local-input paths today).
* *Cloud-compaction e2e* — the compaction staged-write arm is emulator-covered only
  transitively; add an armed-compaction restart proof on Azurite (flush ×2 →
  compaction:on → restart → verify) to the QA tier.
