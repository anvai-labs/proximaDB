= TD-S3STALL-1: server S3 read path blocks ~25 minutes on a proxy-torn connection (no request timeout)

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open** (filed 2026-11-24 from the ADR-098 M5 emulator campaign; one reproduced incident, no fix yet).
| Priority | MEDIUM (reliability of the cold query path against degraded networks; emulators and flaky proxies expose it, but any connection that dies mid-stream without a FIN/RST delivered to the reader can)
| Component | `src/storage/persistence/filesystem/aws_s3.rs` (the `AwsS3FileSystem` HTTP client used by the SST/vector read path)
| Relates to | ADR-098 (M5 emulator evidence), TD-BENCH-2 (the harness-side defensive posture for slow/hung endpoints — a different layer)
|===

== Incident (measured)

During the M5 RTT-ladder campaign (SIFT1M skip-ingest bed on MinIO behind toxiproxy with 50 ms
symmetric latency toxics; `scripts/bench/sift1m_get_reduction.py`, arm `--s3-endpoint
http://127.0.0.1:9100`), the FIRST 100-query arm stalled 25 minutes into the post-write phase
after 86/100 queries: the server's last log line was `phase done phase="per_file_scan"` for query
86 and then nothing — no error, no timeout, no progress — while the bench python held an
ESTABLISHED connection waiting for the query response. The toxiproxy log shows the client
connection had been torn down (`Source terminated` … `use of closed network connection`). The
process was killed; a fresh-proxy re-run with 25-query cohorts completed cleanly (exit 0) at every
RTT level, so the bed and the query were fine — the stall was the server blocking on a dead
connection.

== Why this is not covered today

- The bench-side defensive posture (TD-BENCH-2: explicit connect/read timeouts in the *harness's*
  boto3 geometry reader) is a different layer — it protects the settle loop, not the server.
- The server's S3 client on the query path apparently has no effective per-request timeout for a
  connection that dies mid-stream (torn down by a middlebox without a clean FIN reaching the
  reader): the stall outlived any plausible configured timeout by orders of magnitude (25 min and
  counting when killed; the API-level `timeout_seconds = 300` in the bench config bounds the REST
  call, but the server-side read continued independent of the abandoned request).

== Fix direction

Audit `aws_s3.rs`'s HTTP client construction: configure an explicit total/request timeout (and
TCP keepalive / read-idle deadline) on the object-store HTTP client used by query-path reads, so a
torn connection surfaces as an error the read planner can retry, not a silent permanent block. Add
a repro/regression test (local proxy that half-closes a connection mid-body; assert the read fails
within the configured bound).
