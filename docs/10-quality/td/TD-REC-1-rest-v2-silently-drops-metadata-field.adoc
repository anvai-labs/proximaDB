= TD-REC-1: REST v2 insert silently drops a `metadata` field, so filters over it match nothing

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-11-01), in three steps (+ review round 1 corrections).** (1) *Core (PR #2337, merged `64f518eef`):* the hypothesis below was confirmed at the DTO — `ProximaRecordInput` had `props` and no `metadata` field, so serde silently dropped the advertised spelling. Fixed by `#[serde(alias = "metadata")]` on `props` (records surface) plus the mirror bug on the documents surface (alias `props` → `IngestDocument.metadata`); both keys in one object fail loud (serde duplicate-field); OpenAPI + all 4 SDKs regenerated in-PR; unit tests pin the DTO boundary. (2) *E2e guard (this PR):* `tests/v2_records_metadata_alias_roundtrip_test.rs` pins the END-TO-END property against a live server — insert with the `metadata` spelling is accepted, persists (read-back by id), and is returned by BOTH filter paths (`/records/scan` equality-map and typed `/search`); the both-keys case is pinned e2e too (HTTP rejection). (3) *Unknown-field policy DECIDED and implemented (this PR):* `ProximaRecordInput` AND `IngestDocument` (documents surface — review round 1 closed this gap too) carry `#[serde(deny_unknown_fields)]` with the grandfathered alias set = {`props`, `metadata`} — a field outside the contract fails loud with a **400 ApiError envelope naming it** (both write handlers route rejections through `json_body`, TD-RESTGET-1's tool — plain `Json` extractors would have produced axum's plain-text 422, also a review round-1 fix), instead of the silent drop that shipped this bug. Review round 1 also swept the HAND-WRITTEN SDK facades the first blast-radius audit missed: the Python v1 client, the integrations records helper, code_knowledge and the node embedded builder all emitted a top-level `source` the server had ALWAYS silently dropped — they now carry that content in `text_fields` (where it persists), and the pinned Python unit test asserts the contract-compliant wire shape; `tests/api_v2_integration_test.rs` posted a legacy `typed_fields` key whose filter assertions were therefore vacuous — the typed values now ride in `props`, making that suite actually exercise persistence + filtering. The cross-surface audit behind the policy: **pgwire** INSERT already fails loud on an unknown column (SQLSTATE 42703, `RelationalConstraintKind::UndefinedColumn` in dml/mod.rs); **gRPC** is proto3, where unknown wire fields are ignored *by design of the format* — the generated stub is the contract and cannot carry an undeclared field, so there is nothing to deny (documented here, no action); **Arrow Flight** ingest is schema-driven (columns are positional in a declared Arrow schema; mismatches error at `validate_schema_compatibility`, catalog_bulk_write.rs, not silently). REST JSON DTOs were therefore the only surface with a free-form silent drop — and of those, the collections DTOs already had `deny_unknown_fields` with grandfathered aliases (TD-RESTGET-1); the record-shaped DTOs were the hole, now closed. Residuals (accepted, on the record): (a) the request ENVELOPES (`InsertRecordsRequest`/`IngestDocumentsRequest`) still drop unknown envelope keys silently — and this is LIVE today: the node `UpdateBuilder` sends a `replace_metadata` envelope key the server ignores as a silent no-op (clients/nodejs-embedded/src/collection.ts); same deny treatment when the envelope contract is next touched; (b) the published OpenAPI spec keeps the DTOs as open objects (`additionalProperties` unset) while the server now rejects unknown record fields — the accepted CreateCollectionV2Request precedent (deny in code, open in spec); the generated python model's `additional_properties` passthrough will 400 on the server for record bodies, by design of the deny.
| Surface | REST v2 batch insert (`POST /v2/collections/{c}/records`-shaped flows) and every filtered read over the same field.
| Severity | High for correctness-of-intent: data the client believes it stored is absent, and the failure is silent on both the write and the read.
| Evidence | v0.5.0 end-to-end smoke in the official `ghcr.io/homebrew/brew` container (Linux/amd64), 2026-10-31: create collection; batch-insert 3 records each carrying a `metadata` object (e.g. `{"category": "tech"}`); insert reports `3/3, failed_count: 0`; **filtered search `category=tech` returns zero records** while unfiltered fetch and vector search return all 3; the fetched records carry no trace of the field.
| Hypothesis | The v2 record model stores user key/value data in `props`; a top-level `metadata` key is not a known field, and deserialization drops it without error rather than rejecting the request (fail-open unknown-field handling on the write path).
|===

== Reproduction sketch

....
# against any v0.5.0/v0.5.1 server
curl -X POST :5678/v2/collections/demo/records -d '
  [{"id":"r1","vector":[...],"metadata":{"category":"tech"}},
   {"id":"r2","vector":[...],"metadata":{"category":"news"}},
   {"id":"r3","vector":[...],"metadata":{"category":"tech"}}]'
# -> {"success_count":3,"failed_count":0}
curl ":5678/v2/collections/demo/records?filter=category=tech"   # -> empty
curl ":5678/v2/collections/demo/records/r1"                      # -> no metadata/props
....

== Decision needed (why this is a TD, not a patch)

Unknown top-level fields on a write can be handled three ways; picking one is a
contract decision:

1. **Fail closed** — reject the request with a 4xx naming the unknown field.
   Safest, but breaks any client that sends extra keys (SDK forward-compat).
2. **Map `metadata` → `props`** — accept the alias on write and serve it on
   read. Most forgiving, but creates two names for one thing forever.
3. **Document `props` as the canonical field** and keep dropping unknowns —
   then the bug is only that the drop is *silent*; add a `warn`-level log or a
   strict-mode flag (`?strict_fields=1`).

Whichever is chosen, the same audit should cover: the pgwire INSERT path, gRPC,
Arrow Flight, and the SDKs' generated payload models, since the drop is
presumably in the shared record decode, not the REST layer.

== Guard to add with the fix

An e2e test that writes a record with a field, reads it back, and asserts the
field round-trips (or that the write was rejected) — the current suites assert
`success_count` and vector behavior, which is why 3/3 green masked an empty
record body.
