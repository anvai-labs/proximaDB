== Design: reuse by exact tree, proven by the jobs API

A promotion-tier run (`medium_tier`: a push to qa/main, or a PR into qa/main) uploads a tiny
artifact named `ci-tree-proof-<tree>` from its `changes` job. A later run's `changes` job calls
`scripts/ci_tree_reuse.py`. The script lists artifacts by that exact name (one API call), then
checks each producing run through the runs and jobs APIs. A job group is **proven** when a
trusted, completed run on the identical tree ran every job of the group to `success`. The script
writes `reused=,key,key,`. Each reusable job ANDs
`!contains(needs.changes.outputs.reused, ',<job-id>,')` into its `if:`, so a reused job shows as
`skipped`, which `CI Success` already treats as a pass. The `changes` job summary records one line
per group: "reused results from run <id> (tree <hash>)", with a link to the proving run.

The artifact is only an index. The claim that the jobs passed always comes from the jobs API, and
never from the artifact's content.

The reusable set has 19 job groups: `rust-test`, `feature-matrix`, `feature-matrix-enterprise-catalogs`,
`rust-compile-benches`, `rust-build`, the 7 `rust-integration-test-*` lanes, `object-store-emulator-tests`,
`object-store-restart-recovery`, `mlflow-conformance`, `sift-recall-ratchet`, `python-test`,
`python-sdk-round-trip` and `openapi-spec-drift`. These jobs do not reference the event, the base
or `extensive` in their steps, so given the tree and the medium tier they do the same work.

The following always run:

* **Main-only extras:** Code Coverage, Docker Build, Integration Tests and Benchmarks, and CodeQL,
  which is a separate workflow.
* **The `rust-compile` hard gate and the cheap guards:** fmt, clippy, proto, panic-policy,
  layering and docs. They are cheap, and they keep a fresh compile of the exact tree under
  `CI Success`.

=== Fail-open guarantees

Every guard below has a unit test, and a mutation test that deletes the guard and shows the outcome
flipping to "reuse".

* **Context:** reuse applies only to a push to qa/main, or to a same-repo PR into qa/main, at
  medium tier. feat→develop PRs, develop pushes, workflow_dispatch and forks never reuse.
* **Identity:** the lookup is by exact tree. For a push proof, the proving run's head commit is
  also resolved to its tree locally (with one fetch if needed), and must match.
* **Trust:** the proving run must be `.github/workflows/ci.yml` in this repository, not a fork.
  It must also be one of two kinds:
** a push to qa/main, whose workflow comes from the pushed commit on a protected branch; or
** a PR on an exact promotion route (develop→qa or qa→main). See "Trust model for PR proofs" below.
* **Evidence:** a group needs at least one job, and every one of its jobs must be `success`.
  Skipped, cancelled or incomplete jobs disqualify the run. A failed, timed-out or
  startup-failed reusable job on the identical tree, in any trusted run, vetoes all reuse. Every
  page of the jobs and pulls listings is read; a missing `total_count` never ends pagination
  early, and more than 20 pages raises, which fails open.
* **Freshness:** a proof must be no more than 168 h old. The proof artifact is kept for 14 days.
* **Dependency safety:** `rust-build` is reused only when all five integration lanes that `needs:`
  it are reused too. It is never reused at the FULL tier, because Integration Tests downloads its
  release binary and Benchmarks needs it. `rust-coverage` (which needs `rust-test`) and
  `integration-test` (which needs `python-test`) now treat a skip that the reuse step recorded as a
  pass. Any other skip still skips them as before. A wiring test fails if any future job `needs:` a
  reusable job without one of these protections.
* **Fail open:** any exception yields an empty `reused`, so everything runs. That covers API or
  network errors, a 403 from missing permission, malformed JSON, and git failures. The step is
  `continue-on-error`, and the script's entry point never exits non-zero, so the step cannot fail
  `changes`. A genuinely failed `changes` job still fails `CI Success`: that is #2043's invariant,
  and a wiring test pins it.

=== Trust model for PR proofs (review of #2051)

The first version of this gate trusted a `pull_request` proof run by its HEAD branch alone
(develop or qa). A review blocked it. A `pull_request` run executes the MERGE ref's `ci.yml`,
and that ref includes the BASE branch. At the time, `ci.yml` listed `development` in its
`pull_request:` and `push:` branches. That branch never existed and is unprotected.

The exploit worked like this. A user with write access pushes a `development` branch whose
`ci.yml` uploads `ci-tree-proof-<T>` and has trivially green jobs with the reusable names. T is
the predictable next promotion tree, essentially develop's tree. The user then opens
PR develop→development. Through the runs API, that run is indistinguishable from a real
develop→qa run: same `head_branch`, same `head_sha`, same repo, same path, and an empty
`pull_requests`. It passed every trust check. PR proofs got no tree re-verification, so the next
real promotion reused all 19 groups. A regression test reproduces this with the forged PR's base
set to `development` and to `develop`.

The fix has two parts.

* **The PR is resolved, not inferred.** `run.pull_requests` is empty on real promotion runs
  (checked on 38684845368 and 38697532716). So `pr_route_reason` lists every PR, of any state,
  whose head is `<owner>:<head_branch>`, through `pulls?state=all&head=…`, reading every page.
  It keeps only the PRs whose `head.sha` equals the run's `head_sha`. The run is trusted only when:
** exactly one PR matches;
** the PR's head and base repositories are both this repository;
** `head.ref` equals the run's head branch; and
** `base.ref` is that head's route base: develop→qa or qa→main.
+
If no PR matches, or more than one does (for example a forged develop→development PR sharing the
real promotion's head SHA), the run is not trusted and everything runs. Both sides of an allowed
route are protected branches, so the definition that wrote the proof is reviewed code. The
`changes` job gains `pull-requests: read` for this lookup. A 403 or any other error fails open.
Checked live: both real promotion runs resolve to #2038 and #2039 and are trusted. A forged
head SHA resolves to 0 PRs and is rejected.
* **The unprotected trigger is gone.** `development` is removed from `on.push.branches` and
  `on.pull_request.branches`. A wiring test pins both lists to exactly `{main, develop, qa}`.

**Re-review: retargeting.** The pulls API reports only a PR's *current* base, and that base can
be edited after a run. A write-access user could carry out these steps:

. push branch `evil` with a forged `ci.yml`;
. open PR develop→evil at head S1, so the forged run executes `evil`'s `ci.yml` with
  `head_branch` develop;
. edit the base to qa;
. close the PR.

Nothing re-runs, because `edited` is not one of `ci.yml`'s `pull_request` types and `state=all`
still lists the closed PR. The lookup would then find exactly one develop→qa PR for S1.

The fix reads the PR's **complete timeline** (`issues/<n>/timeline`, every page). A PR whose
timeline contains any `base_ref_changed` or `base_ref_force_pushed` event is rejected as a proof
source, whatever the from/to; the REST event does not carry them anyway.

* **Errors:** if any page cannot be read, the lookup fails open, so everything runs.
* **Event name:** checked live against #1995, a real qa→develop retarget, which shows
  `base_ref_changed`.
* **Real proofs:** #2038 (16 events) and #2039 (39 events) have no base events, and their runs
  38684845368 and 38697532716 remain trusted.
* **No timestamp rule:** requiring the run to post-date the last base change would only matter if
  a retargeted PR could ever be trusted. Since any base change rejects the PR, that rule is moot.
* **Reopening** does not change the base, so it adds no path.

**`edited` was considered and not added** to the `pull_request` types. It would trigger a full CI
run (657+ runner-min at promotion) on every title or body edit, and would cancel and restart
in-flight feature-PR runs. Re-running is not the fix in any case: the timeline check is.

**Alternative rejected: push-only proofs.** With proofs from push runs only, PR qa→main would have
nothing to reuse. The push-to-qa run skips the Rust suites, because paths-filter diffs against
develop, so its proof covers about 3 groups (OpenAPI, the Python round-trip, Python tests;
68 runner-min) instead of 17. The PR qa→main saving would drop from 566 to about 68 runner-min.

What remains trusted is a run whose definition came from develop, qa or main. Writing to those
branches requires a reviewed PR with `CI Success`, which is the same trust the promotion itself
relies on.

== Open residuals

* **QA Gate** repeats about 556 runner-min per release (the push qa and PR→main runs on a tree
  that PR→qa already proved). It has no aggregator. Its header says its job names are required
  checks on qa/main, but branch protection on both branches requires only `CI Success` (checked
  2026-10-15). Serving it from the same script needs a
  per-workflow group table and a `changes`-style job in `qa-gate.yml`. That is a follow-up slice.
* **TDD Test Suite**: closed by the CI redesign PR1 (below), which deleted `tdd.yml`.
  **CodeQL** (about 95 runner-min) still repeats the tree once. A CodeQL result is per commit
  for code-scanning alerts, so its repetition may be intended.
* **Re-measure** the first promotion cycle on the gate. Correct the projection table if the
  observed savings differ.
* **Residual risk, not removable by a tree hash:** a reused job is not re-exposed to runner-image
  drift, third-party downloads (the SIFT corpus, emulator images) or wall-clock-dependent tests
  inside the 168 h window. The same exposure exists today whenever a green run is merged without a
  re-run. The freshness window bounds it.

== CI redesign PR1: hygiene, dedup and release reuse (2026-10-16)

The first of three PRs of the CI redesign that followed the v0.4.1 release (about 5,050
runner-min per release; 0 of 15 heavy jobs restored a cache). Workflows and scripts only.

[cols="1,3",options="header"]
|===
| Change | What and why
| Concurrency per event | `ci.yml`'s group is now `workflow-event-branch`. Keyed on the branch
alone, a PR shared a group with the push of its own head: the qa→main PR queued about 70 min
behind the push-to-qa run of the same SHA. Pinned by `check_ci_concurrency_per_event`.
| Cache policy | One `shared-key` per build shape (`check`, `dev-test`, `release`, plus two
single-job shapes), `add-job-id-key: false`, and `save-if` true only on a push to develop: the
default branch is the one cache scope every PR and promotion can read. Each key has exactly one
writer (rust-compile `test` → `check`; rust-test `unit` → `dev-test`, enabled on develop push by
the new `warm` output; python-sdk-round-trip → `release`); every other step restores
read-only, and a writer's job must be able to run on a develop push (coverage and the
object-store emulator job, which never do, restore `dev-test` instead of owning a key that
would never be written). Job-level `CARGO*`/`RUST*` env moved onto build steps, because rust-cache hashes it
into the key. Pinned by `check_rust_cache_policy`.
| Guards that gated nothing | `hygiene-check`, `repository-identity` and
`oss-docs-decontamination` joined `ci-success.needs`. Their last 20 develop-push runs: every run
that started jobs was green (hygiene path-skipped in 3); 2 runs were cancelled whole.
| RAPTOR ratchet | qa-gate's `raptor_recall_test` step now builds and runs with
`--features experimental-engines`; the file is `#![cfg(feature = "experimental-engines")]`, so
it had compiled to zero tests and passed. The step now fails unless a
`raptor_recall_tests::` test ran.
| Flake Rerun | The matcher read check-run annotations, which only ever say "Process completed
with exit code 143"; the shutdown text is in the job log. `scripts/flake_rerun.py` reads each
failed job's log and accepts the shutdown line only among its last 5 non-empty lines (a step
printing `::error::` renders the same `##[error]` line, so position is the evidence), falls back to the exit-143 annotation only when the log is unreadable, and
still reruns once and only when every failure matches. Tested on real log excerpts
(`tests/scripts/test_flake_rerun.py`).
| Dead workflows deleted | `tdd.yml` (a duplicate of `ci.yml` on an unpinned toolchain; its
integration job was all `continue-on-error`), `capability-contract-tests.yml` (every job
`if: false`), `_shared-build.yml` and `_platform-packages.yml` (`workflow_call` with no
callers). `check_tdd_rust_warning_contract` went with `tdd.yml`.
| Release reuses Pre-Release binaries | `await_prerelease_ci.sh` writes `run_id` of the passing
run; release.yml `build-binaries` downloads that run's `binaries-<target>` artifact, checks its
SHA-256, and rebuilds only on a dry run or a missing/expired artifact (Pre-Release retention
raised to 14 days). A checksum mismatch fails the job. Pinned by `check_release_binary_reuse`.
| Release reuses the qa image | publish-image.yml tags each qa image `tree-<git tree>`; a release
tag whose tree matches re-tags those manifest lists with `imagetools create` instead of
rebuilding, and builds as before otherwise.
| npm OIDC publish | v0.4.1 failed twice with a bare `ENEEDAUTH`, because npm logs an OIDC
exchange refusal only at `verbose`. The job now preflights the same two requests npm makes
(GitHub id token, then `POST /-/npm/v1/oidc/token/exchange/package/<name>`, per npm/cli v11.19.0
`lib/utils/oidc.js`) and fails with the HTTP status, a fixed allowlist of the registry's error fields and the
id-token claims. setup-node no longer gets `registry-url` (no `_authToken` line is written anywhere), and
the publish uses an empty temp user config and `--loglevel verbose`. Pinned by
`check_npm_oidc_publish`.
|===

Deliberately NOT done: `cache-workspace-crates: true`. Cargo decides the freshness of workspace
(path) crates by source mtime, and a fresh checkout makes every source newer than any restored
artifact, so cached workspace-crate artifacts are always rebuilt and only crowd the 10 GB quota
(the rust-cache README calls it "generally not effective"). The monolith compile per job is what
PR2's nextest archives remove.

`qa-gate.yml` into `ci.yml`, one coverage job, the objstore matrix, push proof-mode). Measure
after one develop push that a new PR logs "Cache restored from key" on the heavy jobs.
