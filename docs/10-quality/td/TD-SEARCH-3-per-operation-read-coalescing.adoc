== Cost model: operations and bytes are different axes

For the Azure Blob **flat Blob endpoint** used by active PAX segments, every
HTTP ranged GET is a read transaction. Hot-tier pricing has no separate
per-GB *data retrieval* fee, so a 72-byte and a 24-MiB range each contribute
one read operation. The exact transaction rate is region, redundancy, and
account dependent; `$0.005/10K` must not be described as a universal Azure
price.

That does **not** make bytes free:

* larger ranges consume network/NIC and memory bandwidth and can increase
  tail latency;
* cross-region/public transfer can incur bandwidth/egress charges;
* ProximaDB's own scanned-byte KRU term still meters bytes;
* Cool/Cold/Archive tiers add data-retrieval charges;
* hierarchical-namespace/Data Lake endpoints can have different transaction
  categorization, but ProximaDB does not route to them: `az://`, `azure://`,
  `adls://`, and `abfs://` are aliases for the same flat Blob backend. Path
  spelling therefore cannot select a different range-cost policy.

Therefore a merge is admissible only when the saved round trip is worth its
bounded gap over-read. Optimizing GET count without a byte cap merely moves
the cost.

== Actual v3 layout and dependency chain

The persisted order is:

[source,text]
----
[fixed header, 72 B]
[A0 coarse model + cell directory, variable]
[Region A: RaBitQ header + presence bitmap + cell-major codes]
[Region B: SQ8 params/codes]
[optional OID-position resolver]
[Region D blocks: OIDs, metadata, optional f32 stripes]
[footer index, variable][footer_len][magic]
----

The fixed header is at byte zero and mirrors all region offsets, including
`footer_off/footer_len`. This is deliberate: the reader can discover the
footer with the first ranged GET and does **not** need an object-store `HEAD`
plus tail seek.

The footer is variable because it contains the block table, schema/encoding
map, and optional resolver metadata that are known only after blocks are
written. Keeping it at the tail preserves streaming assembly and mixed-version
readability. Moving it beside the header would require a second-pass rewrite
or a bounded reserved hole and would not eliminate the need for the fixed
header. Duplicating the entire footer in a prefix would also make format
evolution and integrity reconciliation harder.

The efficient policy is:

* keep the fixed routing header at byte zero;
* keep the authoritative variable footer at the tail;
* retain both in `SegmentInvariantsCache` and persistent L2;
* populate them from writer-owned bytes only after atomic publication.

Thus header/footer placement is not the steady-state GET problem. A working
warm tier makes their steady-state object GET count zero.

== Correct adjacency analysis

The prior version made three incorrect assumptions.

. **A0 is not always “a few KB.”** Its exact size is
  `fixed + 4*dim + 4*ncomp*dim + 4*k*ncomp + 4*k + 72*k + checksum`.
  It grows with dimension and cell count.
. **A0 is not generally adjacent to the first selected cell.** Region A has
  its own header and presence bitmap, and the nearest probed cell may occur
  after codes for unselected cells. Joining them can require gap over-read.
. **The footer is not adjacent to the last Region-B survivor range.** The
  optional resolver and Region-D blocks lie between Region B and the footer.
  A `B+footer` merge would read most of Region D and is rejected.

Adjacent *selected cell extents* can still be coalesced, and non-adjacent
extents can be joined when both `max_gap_bytes` and `max_range_bytes` admit the
over-read. Logical selected slices remain unchanged, so recall is invariant.

== Implemented remediation

=== S1: physical GET accounting

`FileSystem::read_ranges(path, ranges)` now has an explicit plan/execute split
(#1649). `plan_read_ranges()` converts logical ranges into physical reads plus
an input-order slice mapping under an optional `RangeCoalescePolicy`; execution
issues exactly the physical plan and reconstructs the original logical result
vector. With no policy the plan is the byte-identical identity path.

`CountingFileSystem` delegates policy lookup through its decorator chain and
meters `plan.physical.len()`, not `ranges.len()`. It separately records
coalesced over-read bytes so logical bytes returned and physical bytes fetched
cannot be conflated. The counter remains a prediction from the same plan;
`io_trace.range_gets` and the Azurite request log are the independent leaf/wire
measurements required for promotion. The encryption wrapper remains a
documented exception because it can materialize one encrypted object and slice
locally.

The invariant is:

[source,text]
----
unencrypted current backends with a stable policy:
planned physical reads == counted range operations == leaf range_gets
----

A Rust function call named `read_ranges` is still not evidence of one cloud
request; the physical plan and leaf/wire observations are.

=== S2: bounded prefix read

On a cold invariants miss, the reader now fetches a bounded prefix:

* default: 1 MiB;
* `PROXIMADB_PAX_PREFIX_PREFETCH_BYTES=0`: kill switch;
* explicit values are clamped to 8 MiB.

The same byte buffer supplies the fixed header and, when fully covered, A0,
the RaBitQ control header, and early selected-cell ranges. No bytes are
reinterpreted: every consumer takes its original exact logical slice.

This speculative prefix is intentionally bounded. If A0 or a selected cell
does not fit, the reader performs the normal exact ranged read. The expected
cold saving is workload/layout dependent and must be measured; it is not
asserted as “one GET per segment” for every segment.

=== S3: existing selected-range coalescer

`plan_probe_cell_ranges()` remains the correct cell-data seam. It sorts extents
in file order and merges only under `ObjectRangeCoalescePolicy` gap/range
bounds. It never changes `nprobe`, selected rows, or ranking inputs.

Region A now derives its unset policy from the same backend IOP target as
Regions B/D: `max_gap = max(target/4, 64 KiB)` and
`max_range = target`. The Azure profile is therefore a 1 MiB maximum gap and
4 MiB maximum range; local SSD remains 256 KiB/1 MiB. The two registered env
mirrors can override either value, including `0` for exact-adjacency/unbounded
diagnostics.

The 4 MiB Azure value is a **conservative read-planner policy**, not a flat
Blob billing quantum and not a proven SDK split boundary. The previous source
comment that described a hard 4 MiB SDK boundary was unsupported and is
removed. `AzureBlobFileSystem::read_range()` invokes
`object_store.get_range()` once, but the application counter above that call
cannot observe an HTTP-client retry or internal split. A wire-boundary
measurement is therefore required before interpreting application GETs as
Azure transactions for ranges larger than 4 MiB.

=== S3a: isolate range-cap effects before choosing cell count

The completed 4 MiB factorial remains the controlled baseline. One exact
768-dimensional BGE point on its immutable one-segment `k_c=30`, projection
width 32 bed, at `nprobe=12`, top-10, and 1,000 diverse queries measured:

[cols="2,1", options="header"]
|===
| Metric | Value

| Cells probed | 12 / 30
| Recall@10 | 0.9836
| Rows probed/query | 203,093.762
| Region-A bytes/query | 8,305,348.376
| Region-B bytes/query | 150,304,273.920
| Total bytes/query | 170,313,605.378
| Application physical GET/query | 49.542
| Invariants hit ratio | 0.999
| Survivor hit ratio | 0.0562387
|===

At this geometry, average Region-B bytes per cell are about 12.5 MiB. The
current 4 MiB maximum can therefore turn one selected cell extent into roughly
3–4 application ranges. That makes every cell-size/GET conclusion conditional
on the planner cap: it does **not** prove that smaller cells are inherently
required to reduce Blob operations.

`scripts/bench/range_cap_sweep.py` now defines the query-only falsification
experiment. It reuses the exact bed and fixed query slice, holds `nprobe=12`
and `max_gap=1 MiB` constant, varies only `max_range={4,8,16,32} MiB`, and runs
top-10 and top-20 in a fresh process per point. It records:

* application GETs and bytes from ProximaDB;
* actual GET requests received at the Azurite HTTP boundary, including range
  lengths, so SDK splitting/retries are visible;
* recall, p50/p95, Region-A/B attribution, cache hit and resident bytes; and
* sampled server peak RSS.

Azurite proves request shape/count through the production Azure backend; its
localhost latency is not Azure service latency evidence. Promote a larger Hot
Blob default only when recall is identical, wire GETs fall materially, bytes
are bounded, p50/p95/RSS do not materially regress, and the wire/application
ratio proves one HTTP request per issued large range. Repeat only eligible caps
on the natural `k_c=90` bed; use `k_c=200` afterward to measure the independent
byte/selectivity trade-off.

The harness snapshots the release binary into each run directory before
starting any server process and verifies its SHA-256. Cargo atomically replaces
profile binaries after a rebuild; launching later points from the mutable
`target/` path could otherwise mix revisions while retaining the hash captured
at startup. A pre-existing snapshot with a different hash now fails closed.

reported as measured context; the gate is the absolute floor. Context: the 10M
curve's best measured recall 0.9782 was already recorded as "0.98 explicitly
unattained rather than lowered" — 0.975 makes that point attainable too.
Historical numbers in this TD keep their original 0.98-era contexts. The
offline sweep tools' `--target-recall` defaults deliberately remain 0.98
(nprobe_sweep, cache_tier_sweep, range_cap_sweep, analyze_nprobe_geometry):
sweeps then over-provision slightly relative to the 0.975 floor, which is the
safe direction.

Exact ordered result equality is diagnostic, not an acceptance requirement.
The benchmark now records per-query ordered-ID, ID-set, recall-hit, and
result-count hashes without retaining user IDs, plus total hit delta and counts
of queries that gained or lost hits. An exact-current-binary rerun must rule out
a systematic result-set shift and confirm the paired non-inferiority result
before the default can change.

These measurements invalidate two prior shortcuts: 4 MiB is neither a Blob
billing quantum nor an SDK request quantum, and the `k_c=90` GET minimum
measured under the 4 MiB cap is not yet a provider-independent geometry result.
Repeat the eligible cap on `k_c=90` at iso-cap before choosing cell count.

[cols="1,1,1,1,1", options="header"]

The result disproves a universal range cap. At 1M, 8 MiB is the latency knee,
16 MiB is the GET knee, and 24 MiB adds no material benefit. The 24 MiB point's
18.0% byte amplification is not an Azure Hot retrieval charge, but it is 5.15
MiB/query of additional NIC, cache, and memory traffic. At one million queries
that is about 5 TiB of extra same-region traffic. A single-query latency win
therefore needs a concurrency/RSS guard rather than an arbitrary requirement
that bytes be identical.

The implementation successor is a deterministic estimator at the shared
engine-core read-planning seam:

. Preserve explicit range/gap env overrides as the highest-precedence
  diagnostic contract.
. Under the existing default-OFF
  `PROXIMADB_STORAGE_READ_STRATEGY_CHOOSER`, enumerate provider-bounded caps:
  Azure 4/8/12/16/24 MiB, S3/GCS 8/16 MiB, and local
  1/2/3/4/6/8 MiB. This is read-only policy; writer block/cell geometry remains
  unchanged.
. Run the real Region-A/B/D coalescing state machine for each candidate. The
  resulting `(cold-miss planned GETs, planned bytes)` are exact for the selected
  cells/rows, so vector count and dimension need not match a benchmark lookup
  table. Subsequent DRAM/disk hits can only remove canonical-store requests;
  cache residency is measured separately rather than guessed by this planner.
. Score `20*GETs + 5*MiB` for active Hot/standard cloud objects, matching the
  neutral ADR-052 route-cost ordering. Reject candidates above 1.25x baseline
  bytes. For retrieval-billed Cool/Cold/Archive objects, raise the byte weight
  and tighten the guard to 1.10x. Local storage prices requests at zero and
  admits no byte amplification.
. Treat scores within 0.5% as the same knee and choose the smaller cap.
  This selects 16 rather than 24 MiB for the measured 1M curve.
. Emit baseline/chosen GETs, bytes, cap, gap, cost class, and candidate count.
  Unset gate or an invalid/empty decision fails closed to the existing fixed
  policy.

The benchmark beds calibrate the latency/RSS weights and validate the policy;
they are not a brittle table keyed by exact `(N, dimension, k_c)`. Once A0 has
selected cells, their actual byte extents make the cold-miss plan exact.
Regression/telemetry remains useful for concurrency latency and for choosing
the recall-safe `nprobe`, which is a separate quality problem.

This first estimator slice intentionally keeps the backend-derived gap fixed.
Enumerating larger gaps would be mechanically easy but would optimize an
unmeasured second variable that can add bystander bytes discontinuously. A
paired gap sweep and concurrency/RSS evidence are required before admitting
gap candidates.

The engine-core contract accepts a canonical `ObjectAccessTier`, but the PAX
search caller does not yet receive per-object tier metadata. This slice passes
`None`, which deliberately resolves active object-store segments as
Hot/standard. Plumbing actual Cool/Cold/Archive placement to this leaf is a
prerequisite before enabling adaptive reads on retrieval-billed tiers; path
aliases alone must never guess a billing tier.

=== S4: remove the redundant PAX-as-SST1 magic probe

The first passing release run after the persistent-tier implementation reported
exactly 2 physical GETs/query and 16 bytes/query in the local-disk-warm phase
with exactly 2 PAX segments. The source was not PAX header/footer loading.
Two generic legacy-SST helpers could perform an 8-byte `SST1` magic probe for
every discovered file before returning “not a legacy SST” for PAX:
`load_sst_header_centroid()` during file pruning and
`segment_vector_count()` during the adaptive exact-route decision. Removing
the centroid probe reduced the object-cold total, but a release rerun retained
exactly 2 GETs/query and 16 bytes/query; that isolated the adaptive count probe.

Discovery already classifies current PAX segments by the durable `.pax` suffix,
and PAX stores its partition model in A0 rather than a legacy SST header.
Both helpers therefore return `None` for `.pax` before acquiring a filesystem
or reading bytes. Unknown and legacy paths retain the magic sniff, so
mixed-format reads are unchanged. Regression tests use a nonexistent `.pax`
object to prove both PAX branches perform no I/O and a nonexistent `.sst`
object to prove both fallbacks still probe.

Expected effect for the measured two-segment geometry is local-disk-warm
2→0 GETs/query and object-cold approximately 42→40. This expectation is not
promoted as evidence until the release benchmark is rerun.

== Cell-count / nprobe scale matrix

The writer's natural cell law is IOP-derived, not `sqrt(N)`:

----
k_c = clamp(floor(N_usable * dim / 4 MiB), 2, 4096)
----

For 128-dimensional SIFT this yields approximately:

[cols="1,1,2"]
|===
| Rows in one settled segment | Natural `k_c` | Role in the experiment

| 100 / 1K / 10K
| 2 (minimum clamp)
| Degenerate/fallback correctness; not an asymptotic data point.

| 100K
| 3
| Small natural geometry plus a forced-`k_c` calibration sweep.

| 1M
| 30
| Current acceptance and cost point.

| 3.3M
| 100 (measured)
| First scale-validation point above 1M; one PAX v3 L1 segment.

| 10M
| approximately 305
| Extrapolation gate before claiming one calibrated rule scales.
|===

The planned matrix therefore separates corpus scale from query confidence:

. SIFT100K prefixes at 100/1K/10K/100K validate training floors, clamps,
  empty cells, and exact fallback. At 100K, force
  `k_c={2,4,8,16,32}` and sweep absolute `nprobe=1..k_c` to map the geometry
  rather than repeatedly observing the two-cell floor.
. SIFT1M uses the natural 30-cell geometry and at least 1,000 independent
  queries per reported slice.
. BIGANN/SIFT10M uses natural 3.3M/10M points (measured 100 / expected
  approximately 305 cells) with the same selected policy; 10M is a validation
  set, not another place to retune.
. Every subset needs ground truth generated against exactly that corpus
  prefix. `sift1m_get_reduction.py` now rejects `--rows` when the declared
  ground-truth scope differs, preventing full-SIFT1M neighbors from being
  misreported as subset recall. `scripts/bench/sift_exact_groundtruth.py`
  generates exact L2 ivecs blockwise and emits a SHA-256 manifest for these
  subset runs.

For each point record cell row-count skew, empty-cell fraction, radius
distribution, training sample/cell, normalized `nprobe/k_c`, probed-row
fraction, Region A/B/D reads and bytes, recall, and latency. Query counts
(100/1K/10K) narrow confidence intervals; they do not define geometry.

The geometric multiplier remains a deterministic default. The likely
successor is query-adaptive stopping using the persisted centroid distances,
radii, and cell row counts: continue probing until an admissible lower bound
or covered-mass criterion proves another cell cannot improve top-k. That model
must first be calibrated by the matrix above.

* **nprobe=25 / top-10 fails ONLY on `rss_not_materially_regressed`** — 1.1019

open question is no longer "does the win reproduce" — it does, at −41% — but

follow-up is a ladder (4/8/16/24) on this bed at nprobe=25 to find the largest

=== S3d: the cap ladder (2026-08-21) — the knee is 16 MiB, and RSS is what binds

S3c established that 24 MiB fails only on RSS (1.1019 against the 1.10 bound) at
production geometry. The obvious follow-up is not "is the win real" — it is
"which cap is the largest that holds RSS", so the ladder was run on the same
immutable bed (`bge768-ncomp32`, `k_c=90`, `n_comp=32`), same operating point
(`nprobe=25`, top-10, 1000 queries, 1 MiB gap), binary `6bec1fde8`.

[cols="1,1,1,1,1,1", options="header"]
|===
| cap | recall | GET/q | GET reduction | bytes ratio | RSS ratio
| 4 MiB (baseline) | 0.9821 | 41.03 | — | — | 1.0000
| **8 MiB** | 0.9823 | 29.63 | **−27.8%** | 1.0373 | **1.0339** ✓ eligible
| **16 MiB** | 0.9819 | 25.24 | **−38.5%** | 1.0387 | **1.0549** ✓ eligible
| 24 MiB | 0.9821 | 24.28 | −40.8% | 1.0407 | **1.1000** ✗ not eligible
|===

All four points are **same-run** (`runs/cap-ladder-20260820`, `status: pass`,
4/4, zero measurement failures). `promotion_eligible` is the harness verdict, not
a hand calculation: **8 MiB and 16 MiB both pass all nine checks**; 24 MiB fails
exactly one, `rss_not_materially_regressed`, at **1.1000** — landing precisely on
the bound. S3c measured the same point at 1.1019 in a separate run. **24 MiB does
not sit under the guard with margin; it straddles it, and which side it lands on
varies run to run.** That is a stronger reason to reject it than a single
over-bound reading would have been.

**The knee is 16 MiB.** What each step actually buys:

* 4 → 8: −27.8% requests for +3.5% RSS
* 8 → 16: a further −10.7 points for **+2.0** points RSS
* 16 → 24: only **−2.3** more points, for **+4.7** points RSS — and that step is
  the one that breaches the bound

16 MiB captures **94% of the total available reduction at 55% of the memory
cost**. Expressed as the ratio that matters — request-reduction points per RSS
point — it is 8.0 at 4→8, 5.4 at 8→16, and **0.5** at 16→24. The economics
collapse an order of magnitude past 16 MiB.

==== The tension, named

The four quantities do not trade off symmetrically, and only one of them binds:

* **Recall is flat in the cap** — 0.9819–0.9825 across a 6× range, delta ±0.0002.
  Coalescing changes which bytes are fetched, never which rows rank. Recall is a
  constraint to satisfy, not a dimension to optimise; a recall-knee search over
  cap would return noise, which is why none was run.
* **Bytes are nearly flat** — ×1.037 to ×1.041 across the whole ladder. Gap
  over-read saturates almost immediately.
* **Requests fall steeply, then flatten** — the curve is essentially exhausted by
  16 MiB.
* **RSS rises super-linearly at the top** — +3.5, +2.0, then +4.7 points. It is
  the only quantity that breaches a declared bound, and therefore the only one
  that decides the answer.

==== Recommendation: Azure read cap = 16 MiB

Two arguments beyond the measurement:

. **16 MiB is already the sanctioned ceiling for S3 and GCS**
  (`IopsBudget::S3.max`, `IopsBudget::GCS.max`). Adopting it for Azure
  *converges* the backend profiles instead of making Azure exceptional.
. **It is already on the candidate ladder** `read_range_cap_candidates` emits for
  Azure — `{4, 8, 12, 16, 24}` — so no new value has to be invented, and the
  adaptive chooser can select it without a constant change.

**Do not promote 24 MiB.** It fails the declared RSS guard at production
geometry and buys 2.3 percentage points of request reduction for nearly the
entire remaining memory budget.

==== What is NOT established

* **One bed, one operating point.** 768-d, `k_c=90`, `n_comp=32`, `nprobe=25`,
  top-10. The *method* transfers; the constants are not claimed to.
* **top-20 is unmeasured at this operating point** — `nprobe=25` is the top-10
  floor; top-20 needs ≈30 and sits at 0.9784 here, below SLA for a reason
  unrelated to the cap.
* **RSS was measured by an external `ps` sampler on a shared host.** The ladder
  was interrupted twice by other sessions' compilers and the harness failed
  closed both times rather than measuring through contention; the banked points
  are from quiet windows.

== Remaining inefficiencies

* The filesystem trait's generic `read_ranges()` is bounded-concurrent but
  still N physical GETs. Concurrency reduces latency waves, not billable
  operations.
* Concurrent identical misses can race through the cache and issue duplicate
  object GETs. Singleflight by immutable `(path, offset, len)` is the next
  operation-only reduction.
* Exact range keys miss when one request asks for a subrange of a cached parent.
  The write-time SQ8 seed now has an explicit parent-range lookup; the general
  cache can later grow interval containment if evidence warrants it.
* `nprobe` multiplies both Region-A and Region-B work. A fixed reduction failed
  the current recall ratchet; radius/row-aware adaptive stopping is the safer
  path to fewer cells.
* Segment count remains the outer multiplier. Coalescing does not substitute
  for higher-level consolidation.

== Verification gate

Close this TD only with a benchmark that records, for the same fully
materialized segment geometry:

. physical GETs/query by PAX region/tier;
. bytes/query;
. cold and local-disk-warm p50/p95;
. segment count and level distribution;
. recall@10 (must not regress below the ratchet);
. prefix disabled (`0`) versus 1 MiB versus a justified alternative.

Before interpreting finer `k_c` as GET-optimal, repeat the adaptive policy on
the settled 3.3M and 10M beds and measure its DRAM/persistent-disk cache
interaction. Keep any
resulting policy tier-aware: Hot flat Blob in the same region may prefer fewer,
larger requests; Cool/Cold/remote placement must jointly price bytes and
requests. The measured sweep does not authorize a production-default change.

The benchmark must wait for flush/compaction quiescence and prove that all
1M vectors are searchable from materialized segments before restarting.
