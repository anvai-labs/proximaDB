= TD-S3STALL-1: server S3 read on the query path blocked ~25 minutes on a proxy-torn connection (mechanism unknown)

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open** (filed 2026-11-24 from the ADR-098 M5 emulator campaign; one reproduced incident; re-diagnosed 2026-11-24 after review round 2 — the original "no request timeout" premise was WRONG, see below).
| Priority | MEDIUM (reliability of the cold query path against degraded networks: emulators and flaky proxies exposed it, but any connection that dies mid-stream without a delivered FIN/RST could)
| Component | `src/storage/persistence/filesystem/aws_s3.rs` (the `AwsS3FileSystem` HTTP client used by the SST/vector read path)
| Relates to | ADR-098 (M5 emulator evidence), TD-BENCH-2 (the harness-side defensive posture for slow/hung endpoints — a different layer)

== Incident (measured)

During the M5 RTT-ladder campaign (SIFT1M skip-ingest bed on MinIO behind toxiproxy with 50 ms
symmetric latency toxics; `scripts/bench/sift1m_get_reduction.py`, arm `--s3-endpoint
http://127.0.0.1:9100`), the FIRST 100-query arm stalled 25 minutes into the post-write phase
after 86/100 queries: the server's last log line was `phase done phase="per_file_scan"` for query
86 and then nothing — no error, no timeout firing, no progress — while the bench python held an
ESTABLISHED connection waiting for the query response. The toxiproxy log shows the client
connection had been torn down (`Source terminated` … `use of closed network connection`). The
process was killed; a fresh-proxy re-run with 25-query cohorts completed cleanly (exit 0) at every
RTT level, so the bed and the query were fine — the stall was the server blocking on a dead
connection.

== Why the obvious explanation is WRONG (review round 2)

The store is built with `AmazonS3Builder::from_env()…build()`
(`src/storage/persistence/filesystem/aws_s3.rs`, the bucket-store constructor), so object_store
0.14.2's DEFAULTS apply: `ClientOptions::default()` carries a **30 s request timeout and a 5 s
connect timeout**, and `RetryConfig::default()` allows **max 10 retries within a 180 s window**.
A stalled read should therefore surface as an error within ~30 s (a `get_range` chain within
~3 min), and a timed-out read on this path is WARN-logged by the SST search layer — which the
incident log does NOT show. A plain "no timeout configured" does not explain a silent 25-minute
block, and prescribing a timeout change would prescribe the default. The mechanism is UNKNOWN.

== Fix direction (diagnosis first)

1. **Repro:** the toxiproxy tear-down recipe above (proxy under latency toxics, kill the
   client-facing connection mid-body during a cold query sweep) — cheap to script against MinIO.
2. **Capture at the moment of the hang:** a task/thread dump (e.g. `tokio-console`, a
   `backtrace::Backtrace` capture on a watchdog, or `lldb`/`sample` on the wedged process — the
   first attempt was killed without one) to localise WHERE the read is parked (inside the HTTP
   client's read, a retry loop, a lock, or an upstream caller that never observes the future again).
3. Only then decide the fix (per-request deadline observability, retry budget, or a caller-side
   bound); do NOT change the client timeout blindly — it is already set.
