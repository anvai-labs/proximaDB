== History (shipped)

* Finding: `materialize_collection` for 884k entries / 235 MB took 43.9 s on one core; the RaBitQ rotation apply (O(dim²)/row) was the hotspot.
* S1: both `encode_region`s were already two-pass — a sequential fit (float reductions that must stay ordered for bit-stable params) then an independent per-row encode. Only pass 2 is parallelized (ordered rayon `par_iter().collect`, threshold 4096 rows), so output is **byte-identical by construction**; pool width cannot affect output.
* Co-design rule that still applies: the shipped default is a bounded cores/2 scoped pool for query headroom (mirroring TD-SEARCH-2's morsel budget); `PROXIMADB_PAX_ENCODE_THREADS` tunes (1 = sequential).
* Evidence: 8.962 s at full width (10 cores), 26.2 s at the shipped bounded default (was 43.9 s); `parallel_encode_region_is_byte_identical` + SQ8 twin; zero `__flush` stragglers on shutdown.

== Open

Wrap the sync `write_pax_segment_full` call (in `flush/`) in `spawn_blocking` —
`block_in_place` panics on current-thread test runtimes; needs the
ownership-returning spawn_blocking form. The rayon offload already moves the CPU off
tokio workers' time budget (blocked window shrinks with the speedup).
