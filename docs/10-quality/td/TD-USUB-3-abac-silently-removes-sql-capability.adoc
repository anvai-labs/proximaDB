= TD-USUB-3: ABAC composition silently removes SQL capability — the same table behaves differently per connection identity

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (in-plan enforcement)** 2026-09-21, under ADR-094 Phase 1. A governed subject now reaches the DataFusion route through the native table provider, with rows filtered at the source. Gated with the rest of TD-USUB-2 behind `PROXIMADB_NATIVE_TABLE_PROVIDER` (default OFF).
| Priority | **HIGH** — a security-adjacent correctness trap: enabling row-level security silently *downgraded the SQL surface* rather than failing closed or enforcing in-plan.
| Component | `src/network/postgres/relational_pipeline.rs` (`native_registerable`, `query_has_table_function`, the dispatch gate), `src/services/dml/mod.rs` (`relational_abac_required`, `scan_table_relational`)
| Relates to | ADR-094 (Phase 1, defect **c**), ADR-087 (ABAC enforcement), TD-USUB-2 (same mechanism, storage-derived sibling), TD-ABAC-10c
| Blocked by | Nothing.
|===

== The finding

`relational_abac_required(&self, identity: PortIdentity<'_>)`
(`src/services/dml/mod.rs:1423`) derives entirely from:

[source,rust]
----
proximadb_tenant::read_enforcement_composition(
    self.abac_enforcer.is_some(),
    identity.subject.is_some(),
    identity.tenant_stable_id.is_some(),
    identity.auth_class,
)
----

It takes **no storage input whatsoever**. When the composition is anything other than
`Passthrough`, the relational pipeline forces `parquet_backed = false`
(`src/network/postgres/relational_pipeline.rs:1049`) and the entire DataFusion dispatch block
is skipped.

Combined with TD-USUB-2 — where the `ctx.sql` fallback is reachable only on the DataFusion
route — the consequence is:

[IMPORTANT]
====
The **same table** serves CTEs, window functions, joins and subqueries to a *passthrough*
connection, and silently loses all of them for an *authenticated tenant user*. SQL capability
varies by **who connects**, not by what is stored.
====

This is worse than a storage-derived cliff because it is invisible at the schema level:
nothing about the table indicates that its query surface shrinks under an authenticated
session. It also means no storage change — publication, format unification, or otherwise —
can fix it.

== Why it is currently shaped this way

The fail-closed intent is correct and must be preserved. The legacy single-table reader has
no row-filter wiring, so serving an ABAC-scoped subject through it would return unenforced
rows — the bypass TD-ABAC-10c closes. The defect is not the caution; it is that the caution
is expressed as a **silent capability downgrade** instead of either in-plan enforcement or an
explicit decline.

== Resolution (2026-09-21) — in-plan enforcement, the preferred option

Taken: **enforce in-plan**, not "decline visibly". The enabler landed with TD-USUB-2 — the
native table provider registers rows obtained from `scan_table_relational`, which resolves
the ABAC row filter itself (`Denied` → zero rows, `Restricted(p)` → predicate applied,
identity/storage tenant mismatch → error). Rows reaching DataFusion are therefore **already
governed**, so the route can be opened to a governed subject without adding an enforcement
bypass.

Three changes:

. `native_registerable` no longer requires `!relational_abac_required`.
. The dispatch gate splits the ABAC condition **per arm** rather than gating the whole block:
  the **Parquet** arm still requires `!relational_abac_required` (it reads files directly and
  cannot apply a row filter — the original, correct reason for the restriction), while the
  **native** arm may serve a governed subject.
. A new fail-closed guard, `query_has_table_function`, is the one thing that keeps this safe.

=== The hole the guard closes

`collect_table_names` gathers only `TableFactor::Table { args: None, .. }` — plain catalog
tables — so a **table-valued function never appears in the prepared `tables` map**. A UDTF
resolves instead through its registered DataFusion table function, backed by
`vector_ops`/`graph_ops`, which do **not** apply the relational ABAC row filter.

Without a guard, `SELECT … FROM governed_table JOIN vector_search(…)` would have satisfied
`native_registerable` (its only *catalog* table is native) and mixed governed rows with an
ungoverned source. `query_has_table_function` detects a UDTF at every nesting level —
including one hidden in a CTE body, which a FROM-clause-only check would miss — and fails
closed on shapes it does not decompose (set-ops, exotic factors).

=== Verification

The e2e (`tests/abac_relational_transport_e2e.rs::governed_subject_gets_full_sql_surface_with_rows_still_filtered`)
asserts **both halves**, which is the point — a test that only proved capability was restored
would not have proved enforcement survived:

* *Capability* — a CTE serves, and a window function returns the **real** lagged deltas
  (previously a silently wrong answer on the native path, the TD-187 residual).
* *Enforcement* — an unbound subject sees **zero** rows through those same shapes, and a hot
  revoke is observed through the new route.

The test was confirmed **non-vacuous**: reverting just the ABAC relaxation makes it fail, and
restoring it makes it pass. All 9 ABAC transport tests, plus the REST-record-search (16) and
vector-pushdown (7) suites, stay green.

== Original options considered (superseded by the resolution above)

Preferred — **enforce in-plan**:

. Push `AbacScanResult` (`src/services/dml/mod.rs:1436`) into the registered table provider
  (TD-USUB-2) so the row filter is applied inside the scan, and the DataFusion route becomes
  safe for ABAC-scoped subjects.
. `parquet_backed` then no longer needs to be forced false, and capability stops varying by
  identity.

Fallback, if in-plan enforcement is deferred — **fail closed, visibly**:

* Emit an explicit, documented SQLSTATE naming ABAC as the reason the shape was declined, so
  the user sees *"this query shape is not supported for a policy-governed subject"* rather
  than silently losing a feature. A decline of this kind already exists at
  `relational_pipeline.rs:4310`-style sites and should be the model.

Either way, the invariant to establish is: **enabling security must never silently change
which SQL is accepted.**

== Evidence gate (mandate #6)

* A test matrix running an identical query set as (i) passthrough and (ii) an authenticated
  ABAC-scoped subject, asserting either identical results (in-plan enforcement) or an
  explicit typed error — never a silent difference in accepted SQL.
* A row-leak test proving the filter is actually applied in-plan for every shape newly
  admitted to the DataFusion route.
* `auth_failclosed_e2e` and the ABAC ratchets stay green.
