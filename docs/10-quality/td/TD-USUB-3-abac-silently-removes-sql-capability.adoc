= TD-USUB-3: ABAC composition silently removes SQL capability — the same table behaves differently per connection identity

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Partial: resolved by in-plan enforcement (2026-09-21, #1919) — a governed subject reaches the DataFusion route through the native table provider with rows filtered at the source, plus a fail-closed UDTF guard; open: it is default-OFF behind TD-USUB-2's `PROXIMADB_NATIVE_TABLE_PROVIDER`, so in the default configuration the per-identity capability downgrade persists until that gate flips; and the full passthrough-vs-governed query matrix in the evidence gate.**
| Priority | **HIGH** — a security-adjacent correctness trap: enabling row-level security silently *downgraded the SQL surface* rather than failing closed or enforcing in-plan.
| Component | `src/network/postgres/relational_pipeline.rs` (`native_registerable`, `query_has_table_function`, the dispatch gate), `src/services/dml/mod.rs` (`relational_abac_required`, `scan_table_relational`)
| Relates to | ADR-094 (Phase 1, defect **c**), ADR-087 (ABAC enforcement), TD-USUB-2 (same mechanism, storage-derived sibling), TD-ABAC-10c
| Blocked by | Nothing.
|===

== History (shipped)

* Finding: `relational_abac_required` derives purely from identity (`read_enforcement_composition`), and any non-`Passthrough` composition forced `parquet_backed = false`, skipping the DataFusion block. **The same table served CTEs, window functions, joins and subqueries to a passthrough connection and silently lost them for an authenticated tenant user** — SQL capability varied by who connects, invisibly at the schema level, and no storage change could fix it.
* The fail-closed intent was right (the legacy single-table reader has no row-filter wiring — the TD-ABAC-10c bypass); the defect was expressing caution as a silent capability downgrade. **Invariant that still applies: enabling security must never silently change which SQL is accepted** — enforce in-plan, or decline with an explicit, documented SQLSTATE.
* Resolution: rows reaching DataFusion through the native provider come from `scan_table_relational`, which resolves the ABAC row filter itself (`Denied` → zero rows, `Restricted(p)` → predicate, tenant mismatch → error). `native_registerable` no longer requires `!relational_abac_required`; the dispatch gate splits per arm — the **Parquet** arm still requires it (it reads files directly and cannot filter rows).
* **Lesson — the guard that makes it safe:** `collect_table_names` gathers only plain catalog tables, so a table-valued function never appears in the prepared table map, and UDTFs (`vector_ops`/`graph_ops`) do not apply the relational row filter. `query_has_table_function` detects a UDTF at every nesting level (including inside a CTE body) and fails closed on shapes it does not decompose.
* Evidence: `tests/abac_relational_transport_e2e.rs::governed_subject_gets_full_sql_surface_with_rows_still_filtered` asserts both capability (real lagged deltas) and enforcement (unbound subject sees zero rows; hot revoke observed) and was confirmed non-vacuous by reverting the relaxation.

== Open: evidence gate (mandate #6)

* A test matrix running an identical query set as (i) passthrough and (ii) an authenticated
  ABAC-scoped subject, asserting either identical results (in-plan enforcement) or an
  explicit typed error — never a silent difference in accepted SQL.
* A row-leak test proving the filter is actually applied in-plan for every shape newly
  admitted to the DataFusion route.
* `auth_failclosed_e2e` and the ABAC ratchets stay green.
