== History (shipped)

* Symptom: after `flush()` with `free_wal=true`, Stage 1 search (`search_unflushed_vectors`) still returned every vector — vectors lived in 3+ in-memory places and flush cleared only the WAL write-buffer batches (and WAL files).
* Phase 1 (#562): `AxisManager::clear_collection_vectors(collection_id)` removes the in-memory `ProximaRecord` projection (and its `global_id_index` entries) but **not** the persistent HNSW/IVF/metadata indexes. It is wired into the shared `materialize_collection` core for both server and embedded flush, keyed by the canonical collection UUID (`plan.canonical_id`) — the same key `handle_flushed_vectors` populates, so the reap removes exactly what was inserted. Reap failure is logged and non-fatal (the durable segment is the source of truth).
* Tests: `src/index/axis/management/manager.rs::clear_collection_vectors_tests` (projection emptied, sibling untouched, idempotent, repopulates after reap — it is a cache, not the store).

== Phase 2 (open) — block-cache invalidation

The 1 GiB block cache (DashMap/moka) still retains entries for the flushed
collection. These are read-side caches over durable SST segments, so they are
correctness-neutral (a stale cache entry points at the same durable bytes), but they
hold memory that could be reclaimed. Deferred to a follow-up TD: the block cache has
no per-collection eviction API today, so adding one is its own scoped change.
