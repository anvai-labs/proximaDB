== Why no PR exists for these

Dependabot opens a PR when a patched version satisfies the existing requirement.
Here it does not: the alerts are against copies pinned to a line that was never
patched, so the tool is silent and the alerts simply accumulate. They were found
by reading the Dependabot **alerts API** rather than the PR list — which is the
transferable lesson: *the PR list is not the alert list.* Of 32 open alerts,
these two had no corresponding PR.

== The chains, read out of `Cargo.lock`

----
rustls-webpki 0.101.7   HIGH    vulnerable < 0.103.13, first patched 0.103.13
    <- rustls 0.21.12
        <- aws-smithy-http-client 1.1.13
        <- hyper-rustls 0.24.2
        <- tokio-rustls 0.24.1

jsonwebtoken 9.3.1      MEDIUM  vulnerable < 10.3.0, first patched 10.3.0
    <- google-cloud-auth 0.13.2
----

Two lower-severity `rustls-webpki` advisories (name-constraint handling,
patched 0.103.12) ride the same 0.101.7 copy.

**The workspace already resolves safe copies alongside** —
`rustls-webpki 0.103.15` and `jsonwebtoken 11.0.0` are both in the lock. So this
is not "we are on an old version"; it is "we are on an old version *as well*,
because a second dependency subtree pins it." A `cargo update --precise` cannot
help: `0.103.13` does not satisfy `rustls 0.21`'s `^0.101` requirement, and
bumping `rustls` to 0.23 inside that subtree is a semver-major change its
parents must make.

== Exposure

Both chains are feature-gated: `aws` / `gcp` (root `Cargo.toml` `[features]`).
A default build does not compile them. That bounds the blast radius but does not
remove it — those features are the cloud object-store backends, i.e. exactly the
configuration a deployment uses, and `Cargo.lock` is what the
`security-audit` CI job reads regardless of features.

The `rustls-webpki` advisory is a panic on a malformed CRL. Our TLS paths do not
knowingly load CRLs, so the practical reachability is likely low — but "likely
low" is an assertion, and this TD does not try to pass it off as a measurement.
Establishing reachability is part of the work below.

== We already declare the modern versions; two subtrees drag the old ones in

This is the part that makes the fix tractable. Our own direct declarations are
already current:

[source,toml]
----
rustls       = { version = "0.23" }   # Cargo.toml:695
tokio-rustls = "0.26"                 # Cargo.toml:697 -- comment even says "(rustls 0.23)"
----

Neither `hyper-rustls`, `aws-smithy-http-client` nor `google-cloud-auth` is a
direct dependency. Every old copy enters through exactly **two** roots, and one
of them is a direct dependency of ours:

----
aws-smithy-runtime 1.11.3            (transitive, via the aws-sdk stack)
  -> aws-smithy-http-client 1.1.13   (latest 1.5.0)
       -> hyper-rustls 0.24.2        (latest 0.27.10; 0.26+ is on rustls 0.23)
            -> tokio-rustls 0.24.1   (latest 0.26.6)
                 -> rustls 0.21.12
                      -> rustls-webpki 0.101.7     <-- HIGH

google-cloud-storage 0.15.0          (DIRECT, Cargo.toml:671, behind `gcp`)
  -> google-cloud-auth 0.13.2        (latest 1.17.0)
       -> jsonwebtoken 9.3.1         <-- MEDIUM
----

So the whole thing reduces to two dependency moves, both of which have upstream
releases available:

. **`google-cloud-storage` 0.15 -> 1.20** (ours to change, one line, `gcp`
  feature). It is a 0.x -> 1.x jump, so expect API churn in the GCS backend.
. **The aws-sdk stack** (`aws-config` 1.8.18 resolved today, latest 1.12.0),
  which should pull `aws-smithy-http-client` onto a rustls-0.23 line. Verify
  rather than assume: the smithy crates version independently of the SDK
  façades.

== It is NOT the object-store path, and the AWS half is a feature flag

Worth stating plainly, because the opposite is the natural assumption: **the
S3 + Azure object-store path is already clean.** It migrated to the canonical
`object_store` crate (documented at `Cargo.toml:661-665`, which explicitly
replaced "the heavy aws-sdk-s3 tree"), and `object_store` is now pulled by 18
workspace and DataFusion crates. No `aws-sdk-s3` remains in the lock.

The 23 remaining `aws-*` crates come from somewhere else entirely:

[source,toml]
----
# crates/control/proximadb-catalog/Cargo.toml:25,41-42
aws          = ["dep:aws-config", "dep:aws-sdk-glue"]
aws-config   = { version = "1.0", optional = true }
aws-sdk-glue = { version = "1.0", optional = true }
----

That is the **AWS Glue catalog** integration — not object storage.

**Probed, not assumed:** bumping the stack with
`cargo update -p aws-config --precise 1.12.0` moves
`aws-smithy-http-client 1.1.13 -> 1.5.0` but does **not** drop the old subtree —
after the bump the lock still carries `rustls 0.21.12`,
`rustls-webpki 0.101.7`, `hyper-rustls 0.24.2` and `tokio-rustls 0.24.1`
*alongside* the modern `0.23.45` / `0.103.15` / `0.27.9` / `0.26.5`. A lock
update alone cannot close this. (The probe was reverted; the lock in this PR is
unchanged apart from the `rustls` patch bump.)

The reason is a feature, and it is ours to turn off.
`aws-smithy-http-client` 1.5.0 declares the legacy path as **optional and NOT
in `default`**:

----
legacy-rustls-ring = ['dep:legacy-hyper-rustls', 'dep:legacy-rustls',
                      'dep:rustls-native-certs', 'hyper-014']
----

and it is reached because **`aws-sdk-glue`'s own `default` features include
`rustls`**, which maps to `aws-smithy-runtime/tls-rustls`:

----
aws-sdk-glue  default = ['rustls', 'default-https-client', 'rt-tokio']
              rustls  = ['aws-smithy-runtime/tls-rustls']
aws-config    default = ['default-https-client', 'rt-tokio',
                         'credentials-process', 'sso']   # note: no `rustls`
----

So `aws-config`'s defaults are already modern; `aws-sdk-glue`'s are not.

== What closing this needs

. **AWS half — one manifest line.** In
  `crates/control/proximadb-catalog/Cargo.toml`, take `aws-sdk-glue` with
  `default-features = false` and re-add only the modern features
  (`default-https-client`, `rt-tokio`), dropping the legacy `rustls`. Then
  confirm `rustls 0.21.12` and `rustls-webpki 0.101.7` leave the lock and the
  Glue catalog path still builds and passes its tests. This closes the **HIGH**
  alert and both **LOW** ones.
. **GCS half — DONE 2026-10-13 (see the section below).**
  `google-cloud-storage = "0.15"` (`Cargo.toml:671`, feature `gcp`) was five
  majors behind (latest 1.20.0) and carried the `jsonwebtoken 9.3.1` alert. The
  pin had been *deliberate*: `object_store`'s GCS backend speaks the XML API,
  which `fake-gcs-server` — our test emulator — does not serve, so it would be
  locally unverifiable. The chosen resolution keeps that constraint intact:
  bump to **Google's own 1.x SDK** (the crate was donated to the community as
  `gcloud-storage` and rewritten by Google as `google-cloud-storage` 1.x),
  which speaks the **JSON API** — the same wire surface the 0.15 backend used —
  so `fake-gcs-server` compatibility is preserved and the emulator stays the
  verification path. `object_store`-for-GCS was considered and declined on
  exactly that emulator ground; GCS remains the one object-store backend off
  the unified crate, now as a recorded decision rather than drift.
. If either is deferred, record the decision explicitly so the alert is
  *accepted* rather than silently ignored.

== AWS half: done, and what it measured

`default-features = false` on `aws-sdk-glue` (re-adding only
`default-https-client` + `rt-tokio`) removed the entire legacy subtree:

----
rustls         0.21.12 + 0.23.45  ->  0.23.45
rustls-webpki  0.101.7 + 0.103.15 ->  0.103.15     <- HIGH + 2 LOW closed
hyper-rustls   0.24.2  + 0.27.9   ->  0.27.9
tokio-rustls   0.24.1  + 0.26.6   ->  0.26.6
sct            removed entirely (only reachable via rustls 0.21)
duplicated crates  117 -> 113
----

**Glue did not lose TLS, it gained the modern stack.** Verified by resolving the
tree rather than inferring from a green build:
`aws-smithy-http-client` now resolves with
`['__rustls', 'default-client', 'rustls-aws-lc']` and reaches
`hyper-rustls 0.27.9 -> rustls 0.23.45 -> rustls-webpki 0.103.15`. So
`default-https-client` routes through `rustls-aws-lc`; only the *legacy* path
was dropped.

`cargo check -p proximadb-catalog --features aws --all-targets` is clean and
`cargo test -p proximadb-catalog --features aws` passes 477 + 1 + 16 + 3 (9
ignored). A whole-lock backwards-version scan reports **0** packages moving
backwards — the guard TD-AUDITGATE-1 proposes, run by hand here because a
reverted security bump is exactly how #2004 regressed earlier the same day.

== GCS half: done, and what it changed

`google-cloud-storage` 0.15 -> 1.20 (plus explicit `google-cloud-auth` 1.17
and `http` 1.x for the credential-header plumbing) is not a version bump —
the 1.x crate is **Google's full rewrite** of the API the yoshidan 0.x line
pioneered. The alert is closed because the **jsonwebtoken 9.3.1 copy is
REMOVED from the lock**: it rode `google-cloud-auth 0.13.2` via a
version-qualified dependency, and the 1.x auth line does not carry
jsonwebtoken at all. `jsonwebtoken 11.1.0` (patched; the advisory is against
< 10.3.0) remains in the lock — it was already present as the root crate's
own direct dependency and is untouched by this change.

`src/storage/persistence/filesystem/gcs_store.rs` was rewritten for the 1.x
shape, as a deliberate two-plane split; the trait surface (`FileSystem`) and
`GcsConfig` are unchanged, so no caller moved:

* **Data plane** — the 1.x `client::Storage`, which speaks the **JSON API**
  over HTTP (upload/download incl. ranged reads), buckets addressed as
  `projects/_/buckets/{bucket}`, custom endpoint supported.
* **Metadata plane** (get/delete/list) — a small hand-rolled JSON API client
  on the workspace `reqwest`, tokened by `google-cloud-auth` ADC, buckets
  addressed directly. The 1.x SDK's own metadata client
  (`client::StorageControl`) is **gRPC-only** (`google.storage.v2` over
  tonic — `generated/gapic/transport.rs`, no HTTP transport variant), and
  `fake-gcs-server` — the emulator every GCS contract test and the qa-gate
  lane verify against (TD-OBJSTORE-5) — serves the JSON API only, no gRPC.
  The JSON API is exactly what fake-gcs emulates and the same wire surface
  the 0.x client used for these verbs, so both the emulator verification
  path and production behavior are preserved. This was an
  adversarial-review catch: the first cut delegated metadata to
  `StorageControl` and broke every fake-gcs verification path.
* Conditional create: `set_if_generation_match(0)` on the upload, mapped to
  `FilesystemError::AlreadyExists` via the **HTTP status** (409/412,
  `Error::http_status_code()`) — the second review catch:
  google-cloud-gax derives `status.code` only from the response body's
  `status` string, which GCS error bodies do not carry (they carry
  `error.code` + `errors[].reason`), so the parsed `Code` is `Unknown` and
  code-based matching never fires.
* **TD-173 residual (a) closed in the same stroke**: `set_storage_class` on
  the 1.x write carries `ObjectAccessTier::as_gcs_storage_class()` per
  ADR-036 (default-safe: unset tier => bucket default). The 0.15 resumable
  path could not do this.
* The 90-line hand-rolled resumable chunk loop (forced by a 0.15
  `UploadStatus::ResumeIncomplete` Range-header gap) is replaced by
  SDK-managed `send_buffered()` resumable upload with checksum verification;
  small writes use `send_unbuffered()`. Recorded upload-mode drift: the SDK
  switches small writes to resumable at its 16 MiB
  `RESUMABLE_UPLOAD_THRESHOLD`, where 0.x used a simple PUT for every size —
  a latency-only difference on the flush/spill path (checksum + bounded
  buffers gained); revisit only if flush traces show it.
* Page-size control is **kept, not lost**: the metadata layer passes
  `maxResults` (the gRPC v2 model's lack of it is moot), and
  `PROXIMADB_GCS_LIST_PAGE_SIZE` — previously a dead env var — is now
  honored by `FileSystem::list`, so the multi-page emulator test really
  forces three pages again (pagination regression net, TD-OBJSTORE-4 S1).

== Two emulator-caught wire-protocol gaps, found by the contract tests during review remediation

The local emulator lane caught two real 1.x-SDK wire behaviors the code review
and the compile gates could not. Both are accommodated and each accommodation is
verified end-to-end by the GCS contract tests; recorded here because both would
bite a future reader of this backend.

. **Trailing `checksums` multipart part corrupts objects stored by
   fake-gcs-server.** The 1.x SDK's default single-shot upload appends a
   *third* multipart part carrying `{"crc32c":"<base64-be>"}` whenever
   on-the-fly checksums are active and no upfront crc32c is known
   (`google-cloud-storage 1.20`, `perform_upload/unbuffered.rs:265-285`).
   Real GCS consumes that part; fake-gcs **concatenates it into the stored
   object** (proved with curl: uploading `hello` yields a 27-byte object whose
   crc32c matches `hello` + the JSON part). Accommodation: every write path
   now passes `.with_known_crc32c(crc32c::crc32c(payload))` (new optional
   `crc32c` workspace dep — already a transitive dep of the SDK). A known
   CRC32C moves the checksum into the part-1 metadata and disables on-the-fly
   checksums, so no trailing part is emitted; the SDK still validates both
   known-vs-server and computed-vs-server checksums on the response
   (`validate_response_object`), so end-to-end verification is preserved, and
   real GCS additionally validates the upload server-side.
   `write_local_file` hashes with an incremental `crc32c_append` pass and
   rewinds the handle for the SDK.
. **The SDK's HTTP client sends a port-less `Host` header, and fake-gcs echoes
   it into the resumable upload `Location` — uploads to any nonstandard port
   die.** google-cloud-gax-internal sends `Host: <host>` with **no port**
   (its own `tests/http_host.rs::host_is_present` asserts that shape);
   fake-gcs echoes the request's Host header verbatim into the resumable
   upload's `Location` (both `-public-host` and `-external-url` lose to the
   echo — tested), and the SDK PUTs chunks to that `Location` verbatim, so a
   `:8080` endpoint is silently rewritten to `:80` and the upload fails with
   "cannot connect to endpoint". Accommodation: `scripts/run_cloud_emulator_tests.sh`
   serves fake-gcs on **port 80** (the http default port makes the port-less
   URL resolve); the script comment records the mechanism.

A third catch is ours, not the SDK's: **the multi-page list contract test
caught a silent truncation regression in this rewrite itself** — `GcsListPage`
was missing `#[serde(rename_all = "camelCase")]`, so `nextPageToken`
deserialized as `None` and listing stopped after page 1. Fixed; the test that
exists to catch exactly this (TD-OBJSTORE-4 S1) caught exactly this.

== Verification for the fix

* `gh api repos/anvai-labs/proximaDB/dependabot/alerts?state=open` no longer
  lists `rustls-webpki` or `jsonwebtoken`.
* `grep -A1 '^name = "rustls"$' Cargo.lock` shows a single version.
* GCS half: `grep -A1 '^name = "jsonwebtoken"$' Cargo.lock` shows a single
  entry at **11.1.0** (patched; the 9.3.1 copy is gone with the 0.x
  google-cloud subtree); `cargo check -p proximadb --lib --features gcp`
  green; `cargo clippy -p proximadb --lib --features gcp -- -D warnings`
  clean; the gcs unit tests pass (4/4); `check_lockfile_no_downgrade.py
  origin/develop` reports 0 backwards moves; and the **emulator lane was run
  locally against fake-gcs-server** (the pinned CI digest): all four GCS
  contract tests pass — prefix list+exists, resumable publish,
  `write_if_absent`, and the multi-page list forced to three pages via
  `PROXIMADB_GCS_LIST_PAGE_SIZE=2` — the point is to remove the old subtree,
  not to break the backends. The lane was **re-run to EXIT=0 after the
  wire-gap accommodations above** (known-crc32c writes, port-80 emulator,
  camelCase list token), i.e. the final state of this PR is verified
  end-to-end, not just the first cut. Honest caveat: the contract lane runs
  fake-gcs in NON-STRICT mode (the tests warn that it lacks
  ifGenerationMatch=0 enforcement), so the 409/412 → `AlreadyExists` mapping
  is NOT wire-exercised by the emulator; its correctness rests on the
  SDK-source evidence (gaxi's `to_http_error` populating
  `http_status_code()`), not on the emulator run.
