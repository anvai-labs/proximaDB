= TD-GCOLD-3: After sequence exhaustion the cold-segment buffer grows without bound and nothing alarms

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-07 by adversarial review of the TD-GCOLD-1 follow-up, which created this state deliberately by choosing to fail closed.
| Priority | **LOW.** Unreachable without a planted or corrupted segment name (`seg-fffffffffffffffe.gcseg` or `…ffff`), since a real workload cannot issue 2^64 segments. Recorded because the failure MODE is unbounded growth with no signal, which is worse to diagnose than it is to hit.
| Component | `src/graph/cold_segment_store.rs` (`write_segment`, `requeue`, the flush buffer)
| Relates to | TD-GCOLD-1 (whose fix produced this state), mandate #1
| Blocked by | Nothing.
|===

== The finding

`write_segment` now refuses when the sequence counter reaches `u64::MAX`, and requeues the pending
batch so no buffered write is lost — fail-closed, per mandate #1, and the right choice over wrapping
onto a live segment name.

But the refusal is **permanent and unsignalled**. Once the counter is at `u64::MAX`:

* every subsequent `flush()` takes the buffer, refuses, and requeues it;
* nothing can ever drain it, because the only drain path is the write that now always refuses;
* `upsert_record` keeps appending, so the buffer grows for as long as the process accepts writes;
* the module's bound is a byte/count flush threshold, which triggers a flush — and a flush now
  grows nothing but the retry count.

So the observable symptom is steadily increasing heap with an error on every flush, and no metric or
alarm that names the cause. The error text does name it ("segment sequence space exhausted"), so the
information is in the log, but there is nothing a bound or a dashboard would catch.

== Why it is filed rather than fixed

The alternative to failing closed is wrapping onto a live segment name, which
`put_with_tier` would silently overwrite — strictly worse. Fixing the *consequence* rather than the
choice means adding either a bound on the retained buffer or a counter/alarm, and both are policy
decisions about a capability that is default-OFF behind two env gates
(`PROXIMADB_GRAPH_SEGMENT_STORE` + `PROXIMADB_GRAPH_CANONICAL_RECOVERY`). Not worth a late edit to
the PR that found it.

== How to apply

1. Decide the policy: bound the retained buffer and shed (losing writes loudly), or keep retaining
   and surface the state. Shedding in a store whose engine is authoritative and whose recovery
   re-populates is defensible; silently retaining forever is not.
2. Emit a metric when the refusal fires — a counter, or a gauge for "writes retained after
   exhaustion" — so the condition is visible without reading logs. There is precedent:
   `RECORD_PURGE_FAILURES` in `src/services/ddl/mod.rs` is a lazy, tolerant `IntCounter` added for
   exactly this "must be visible, must not panic" shape.
3. Add a test that drives the store past exhaustion twice and asserts the chosen policy — today
   nothing covers the second refusal.
4. While there: the module doc still says "Capability only (not yet wired into production)", which
   is stale — `src/network/shared_services.rs` wires it via `from_storage_root` behind the two gates
   above. Correct it, since the staleness understates the blast radius of anything in this module.
