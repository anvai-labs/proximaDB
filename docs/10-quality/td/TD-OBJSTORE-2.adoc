== History (shipped)

* Failure: an object-store deployment acked creates and inserts and wrote durable WAL, but a fresh VM recovered zero collections. `SystemCatalog` kept per-DDL deltas in a local WAL and published the object-store snapshot only every 1,000 mutations, so the catalog row died with the local disk. Recovery is catalog-driven by design and **must not invent collections from WAL segment names** (that would bypass schema, engine, tenant and authorization metadata).
* Catalog durability: `CatalogSnapshotStore::requires_snapshot_on_commit()` — an object-store catalog publishes its generation-fenced snapshot before acknowledging every commit (a failed publish fails the DDL); local catalogs keep the 1,000-mutation cadence. `config/cloud-object-store.toml` roots metadata, storage locations, WAL and SST/VIPER under one `PROXIMADB_OBJECT_STORE_URL`, with mmap off.
* **Recovery invariant (still applies):** set the recovered catalog as the WAL/recovery authority, load catalog collections, register each assigned storage engine, *then* `recover_collection(id)` — replay before registration failed with `No storage engine registered`. Any registration or replay failure fails startup instead of serving a healthy endpoint with missing data.
* Lessons from the live runs: HELIX's shared caching wrapper was bound to `file://` and reused for every collection — it now resolves the filesystem from each collection's assigned data URL (and the extractor no longer applies `Path::exists` to object URLs). The point read used the service-wide SST lister on every WAL miss, so a recovered HELIX record flushed to ADLS read back 404 (and API-key auth 401); `VectorReadCoordinator` now owns the WAL-first point-read boundary and routes a miss to the collection's configured engine `point_lookup` with the persisted `StorageAssignment.base_location`. Graph collection metadata and discovery jobs moved under `<metadata_url>` via `FileSystem` (remote snapshot PUTs serialized through one ordered writer).
* Tests: `object_store_commit_survives_fresh_local_wal_without_checkpoint`; `wal_miss_routes_to_collection_engine_and_object_store_base_path`.

== Verification and closure (open)

=== Real process / real backend integration

`apps/proximadb-server/tests/object_store_restart_recovery.rs` launches the production
server binary three times against one unique `s3://`, `adls://`, `gs://`, or `gcs://`
prefix and creates
both SST and HELIX collections:

. VM 1: create both collections + insert records; SIGKILL.
. VM 2 with empty local disk: recover catalog, replay WAL, and find both records by
  v2 point GET and vector search; SIGINT to materialize SST/HELIX files and reclaim WAL.
. VM 3 with another empty local disk: recover catalog and find both records by point
  GET and search from cold object-store files.

Run:

----
PROXIMADB_OBJECT_STORE_URL=adls://container/proximadb-proof \
  scripts/prove_object_store_durability.sh
----

The harness requires the server's matching `aws`, `azure`, or `gcp` feature and ambient
IAM, managed-identity, or application-default credentials. It is ignored in
credential-free CI. OSS owns this backend-neutral proof mechanism; anvaiops owns
executing it against the deployed immutable image and retaining the evidence.
