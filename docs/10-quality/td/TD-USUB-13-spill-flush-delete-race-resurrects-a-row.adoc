= TD-USUB-13: A delete concurrent with a spill flush resurrects the row — no truncation required

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Done (2026-10-05).** `flush`, `delete_record` and `purge_durable_objects` are serialized on one per-partition `tokio::sync::Mutex` (`flush_guard`), so a delete can no longer slip between a flush's snapshot and its segment publication (#1951).
| Priority | HIGH once the spill path is wired — a silent wrong answer of the resurrection class (mandate #16a) that needs no WAL truncation.
| Component | `src/services/record_spill.rs` (`flush`, `delete_record`, `purge_durable_objects`)

== History

* Race: `flush()` snapshotted the memtable, wrote the object with nothing held, then pushed the segment path. A delete in that window saw `segments` still empty, recorded no tombstone and returned "deleted" — and the row was live in the segment flush just published. Two pgwire connections on one table suffice; no timing hacks.
* **Lesson — the obvious fix was wrong:** "always tombstone" would make `min_unflushed_lsn` (which fails closed on any tombstone) refuse forever — trading a correctness bug for a permanent liveness one. The predicate was wrong ("does a segment exist *now*" vs "could this row be in a segment, including one being written").
* Decision: serialize (option 3) over snapshot-scoped suppression, because suppression admits a tombstone for a row whose flush then fails, and a spurious tombstone pins WAL truncation forever. `purge_durable_objects` takes the same guard (a concurrent flush could publish after the purge's listing). The guard must be `tokio::sync::Mutex`, not a blocking mutex — the critical section spans the object-write `await`. Contention is currently zero (no production caller); measure before trading obviousness for it.
* Evidence: `delete_during_a_flush_does_not_resurrect_the_row`, mutation-tested (removing the guard reproduces the resurrection).
