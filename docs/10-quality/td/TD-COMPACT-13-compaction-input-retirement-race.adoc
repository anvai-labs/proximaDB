== History (shipped)

* Defect: the training-compaction chain published a higher level (an L3 over all 1M rows) but the superseded L2 inputs stayed in the serving set, often indefinitely, on remote (MinIO/S3-shaped) beds. MVCC dedup kept results correct; cost was paid twice. Timing-dependent; the file:// beds stayed clean.
* Measured at identical code: clean L3-only 11 cells / 58.5 MB / 21.95 GETs / **2977 ms** object-cold p50 @100 ms RTT vs overlapping L2+L2+L3 27 cells / 125.5 MB / 50.57 GETs / **9029 ms** — 3.03x p50, 2.1x billed bytes.
* Fix (#1799): `retire_inputs_with_retry` (3 attempts per input, shared by both executors and the reconciler); on residual failure the {output, inputs} obligation is recorded durably (`retire-pending.json` + process-global pending set + `proximadb_pax_pending_retirements` gauge) and the task **succeeds** — the output is published and correct; failing had only killed the follow-up chain. The idle worker reconciles every 30 s across restarts (delete + cache purge + DV removal). `discover_sstable_files` filters pending-retirement paths, so orphaned beds self-heal at zero extra GETs. `compactor_impl` deletes route by input scheme (NotFound-idempotent). An unreadable input aborts the compaction before publication (fail-closed).
* Lessons that still apply: the settle gate cannot see this (the overlap appears after a compaction-quiet window); the invariant is **row accounting** (live footer rows == ingested rows), not segment count — two-level states with new rows are legitimate.
* Tests: `sst_compaction_retirement_test`, `sst_compaction_retirement_fault_test` (17 surviving segments RED → converged GREEN; read-fault fail-closed), ledger round-trip units.
* Deployment note measured alongside (ADR-073): the SAS RAID10 campaign box did 626 random-4k IOPS / 16.9 MiB/s random 128 KiB — `PROXIMADB_DISK_CLASS=hdd` is mandatory on SAS/HDD RAID; use gp3 (not st1/sc1) for anything query-serving on AWS.

== Open

* **Acceptance re-run:** campaign re-run where every arm's query-time live set is single-level; object_cold p50 variance between arms of the same pair collapses; the clean-bed reference (2977 ms @100 ms proxy, 356 ms disk) becomes the stable recorded number. Then re-measure the ledger claim `rdstrat13_l3l2_retirement_race` to `fixed` (it is still `status = "measured"`). The harness settle gate may then drop its workaround once the engine guarantees it.
* **Follow-up:** `L0_recovery_{id}` naming vs `is_tiered_filename`.
* **Follow-up:** publication moves are themselves delete-sensitive (a transient staging-delete failure fails publication — fail-safe today, retry-worthy later).
* **Follow-up (found 2026-10-19):** the sidecar is written with `std::fs` to `PathBuf::from(data_url)`. On an object-store deployment (`data_url = s3://…`), the "durable" ledger therefore lands under a LOCAL relative directory named `s3:/…`. It survives a restart only on the same host with the same working directory, and never reaches a replacement container. The fix is to make the ledger generic over `FileSystem` and write it beside the segments; a plain PUT is already atomic on object stores. The Layer A deletion-obligation drain (TD-USUB-1 item i) needs the same change before it reuses this ledger.

* **Follow-up (found 2026-10-28, reader side — the mirror of this TD's writer-side race):**
  compaction deletes its inputs immediately after publishing the output
  (`retire_inputs_with_retry` → `delete_inputs_attempt`), with no grace period or
  reader lease. A query that listed segments BEFORE the publish and reads an input
  AFTER the delete gets a 404. Stage F's error falls through to the exact path,
  which also 404s, and `handle_per_file_scan_failure`
  (`src/storage/engines/sst/search/mod.rs`) then **drops the segment silently in
  Approximate mode** (warn + `Ok(())`): those rows are missing from the result with
  no error. Fix options: (a) retire after a grace window ≥ the maximum query
  duration, or under a reader lease; (b) a typed "segment vanished" error that
  triggers one re-discovery retry of the storage stage (the per-query
  `DISCOVERY_MEMO` is scoped per search, so a retry re-lists). Either needs a
  deterministic race test through the `PROXIMADB_TEST_FS_*` fault hooks (delete
  between list and read). Code path verified; the timing window is unmeasured.

== Hardening (2026-10-19)

Found while assessing the ledger for reuse by the Layer A drain:

* **`load_ledger` fails closed.** A missing sidecar is still an empty ledger. Before this, an unreadable or corrupt sidecar also read as empty, so the next `record_pending` wrote a fresh ledger over it and silently discarded every obligation it held. Now it is an error:
** `record_pending` fails loudly, so the compaction fails, as it already does for an unrecordable obligation.
** The drain returns the error.
** The corrupt file is left in place for repair.
* **`write_ledger` no longer pretends to lock.** Its `let _guard = ledger_lock();` built the lock future and never awaited it, so it took no lock. Every caller already holds the real lock across load, modify and write. The contract is now documented on the function. Awaiting the lock there would deadlock, because the async mutex is not re-entrant.
* **Boot reload.** The pending set is process memory. After a restart, recorded obligations left the discovery filter until the reconciler's next drain, so superseded inputs served beside the compacted output in the meantime. The first `register_collection_dir` of a dir in a process now loads that dir's sidecar into the set.
* **Tests:** `a_corrupt_ledger_fails_closed_and_is_not_overwritten`, `first_registration_reloads_recorded_obligations_into_the_filter`.
