== History (shipped)

* Original filing: zero `.pax` segments after a 1M ingest, a ~2 ms shutdown flush no-op, and segments appearing only at +300 s (the RPO timer). Memtable-only recall 0.9740 live / 0.9840 after restart vs 0.9880 through the flushed cascade.
* **S0 correction — lesson that still applies:** with debug logging the inline size trigger fired correctly (38× at 100k; at exactly the 884k floor crossing at 1M), but materializing 884k entries took 43.9 s, and segments stage under `__flush/` and become visible only on rename-at-completion — so every observation window closed too early. The "shutdown no-op" was SIGTERM racing an in-flight materialize; `shutdown_timeout(5s)` (#1199) killed it and `cleanup_temp_on_startup` deleted the straggler. The TD-LIFECYCLE-1 hang had masked this by giving the RPO timer unbounded post-SIGTERM time. Do not conclude "the trigger is dead" from segment visibility alone.
* `flush_threshold_bytes = global_memory_limit/2` is the **backpressure** guard, not the flush trigger: three separate knobs — size trigger, backpressure (2 GB), RPO timer.
* Fixes (#1207): `drain_inline_flushes(timeout)` (in-flight ticket counter around `spawn_inline_flush`) runs at the top of `ProximaDB::shutdown` with a 90 s bound; an info-level start line pairs the completion line. Encode speed moved to TD-FLUSH-5.
* Adjudicated: the claim that #1167 deleted the memtable/WAL search path (0.372 recall) was refuted (0.9740/0.9840 on three runs). A 0.372 indicates a harness defect — check explicit `distance_metric`, the RETURNED `collection_id`, ground-truth id mapping, a stale `target/release` binary, and a foreign server on 5678/15679.
