== The divergence

ADR-065's co-design premise is "one IVF cell ≈ one IOP-sized block", so the cell
count and the read-side range coalescing must agree on what an IOP *is*. They are
derived two different ways:

* **Write side** — `ivf_fine_cell_count()` computes
  `k = clamp((n_usable · dim) / iop_target, 2, 4096)` with `iop_target` taken from
  **`IopsBudget::CLOUD`** as a hard-coded constant, regardless of the actual
  backend the segment is being written to.
* **Read side** — the segment reader resolves its budget via
  `IopsBudget::for_path(path)`, which dispatches on the URL scheme and returns a
  **different** profile per backend.

Those profiles do not agree. `CLOUD` targets 4 MiB; the S3 profile targets 8 MiB.
So on an S3 deployment, cells are sized for 4 MiB while range coalescing is
planned against 8 MiB — the two halves of a co-design are calibrated to different
constants.

== Why it has not shown up

Every bed in the TD-IVF-3 width study, and every `k_c` sweep behind ADR-065's
4 MiB target, ran against **Azure Blob (Azurite)**. There, `CLOUD`'s 4 MiB is the
correct value, so the hard-code is indistinguishable from a correct
`for_path()` resolution. The 4 MiB target itself is well supported — it was
bracketed on both sides (12 MiB, 8 MiB and 1.2 MiB cells all measured worse on
GET/query at the recall floor) — but **only on Azure**.

This is therefore untested divergence, not a measured defect. It is filed so the
first non-Azure measurement is not spent rediscovering it.

== The real blocker (found 2026-08-16)

The fix this TD proposes — "a single helper consulted by both" — is now in place:
`iops_budget::write_target_block_bytes(Option<&str>)` is the one definition, and
`ivf_fine_cell_count` calls it. **But the divergence cannot actually be closed by
threading the path that is already in hand**, and that is worth recording because
it is the non-obvious part:

**The write path does not know its destination backend at clustering time.**
Compaction writes to a LOCAL staging file (`&staging_file_path` at
`src/storage/engines/sst/compaction.rs`) and publishes to object storage
afterwards. `write_pax_segment_compacted` therefore holds a `&Path` to local
scratch, not the destination URL. Passing it to `IopsBudget::for_path` would
resolve the **LOCAL** profile (1 MiB) — actively wrong for a segment destined for
Azure (4 MiB) or S3/GCS (8 MiB), and worse than today's hard-coded `CLOUD`.

So the helper takes `Option<&str>` and the write side passes `None`, which yields
the `CLOUD` target — exactly today's behaviour, with the unknown-destination case
now **explicit in the signature** instead of hidden inside a constant.

Closing this fully means plumbing the destination storage URL from the
flush/compaction caller (which does know it) down through
`write_pax_segment_compacted` → `cluster_plan_ivf_probe` → `ivf_training_shape` →
`ivf_fine_cell_count`. That is a signature change across the write path and is
not free; it should be done together with, not before, the decision about what
the target should be per backend.

== Proposed resolution

. **Do not "fix" it blind.** Switching `ivf_fine_cell_count()` to `for_path()`
  would change cell geometry on S3/GCS — a write-path change to the physical
  layout, which per the storage-format mandate needs to be measured and gated,
  not assumed. It is also not obvious which side is right: the measured optimum is
  a property of the *request* economics, and 4 MiB may well be correct on S3 too.
. **Measure before choosing.** Run the `k_c` bracket on an S3-compatible backend
  (MinIO serves for the request/coalescing shape) at 4 MiB and 8 MiB cells, at the
  recall floor. That answers whether the optimum tracks the backend's IOP profile
  or is a constant of the workload.
. **Then make the two sides share one resolution** — whichever value wins — so the
  write-side cell sizing and the read-side coalescing can never drift apart again.
  A single helper consulted by both is the fix; two independent constants is the
  defect.

== What is NOT established

* Whether 4 MiB or 8 MiB is better on S3. Untested. The Azure result does not
  transfer: it is a request-economics optimum, and the request pricing, minimum
  billable size and range behaviour all differ per provider.
* Whether GCS is affected in the same direction — its profile is a third value
  again, and GCS PUT tiering is separately still a TODO.
* Whether the divergence is observable at all below some corpus size, since `k` is
  clamped to `2..4096` and the clamp may mask the difference at both extremes.

== Resolution (2026-09-03, TD-IOBUDGET-2 batch)

The premise narrowed on re-exploration: the DEFAULT flush never reaches
`ivf_fine_cell_count` (flush IVF clustering is the eval knob
`PROXIMADB_PAX_FLUSH_CLUSTER=ivf`, default OFF) — the live path is COMPACTION,
and compaction always knew its destination (`SstCompactionTask.output_file` is
minted from the collection dir before any write; flush's `perform_atomic_flush`
holds `storage_url`). The fix threads `destination_url: Option<&str>` from the
seven production writer call sites (compaction: `task.output_file.to_str()`;
flush: `Some(storage_url)`; SST writer: `Some(fs_url.as_str())`) through the
segment_format internals into `cluster_plan_*` → `ivf_fine_cell_count` →
`write_target_block_bytes(destination)`.

With TD-IOBUDGET-1's registry seeded, the writer now resolves the SAME budget
per location that the reader's coalescing policies resolve — the "one IOP"
co-design premise holds on BOTH sides of the storage boundary. `None` remains
the explicit fallback for genuinely destination-less callers (the legacy/
test-only compactor path — `compact_level_tiered`/`compact_size_tiered` have
no production callers — and direct unit tests). New segments only; cell counts
are per-segment self-describing metadata — no format change.

=== The DEFAULT file:// deployment also shifts geometry (adversarial-review finding)

The narrative above called out the `s3://` case only. The DEFAULT deployment is
all-`file://` (`config/config.toml`; `StorageAssignment` default), and
`write_target_block_bytes(Some("file:///…"))` resolves LOCAL (1 MiB target) vs
the old hard-coded CLOUD (4 MiB): with compaction IVF write-train default-ON,
every NEW compacted segment derives `k` ×4 larger (clamp 2..4096) and the
reader's `nprobe = ceil(2·√k_c)` roughly doubles — the reader self-adapts via
each segment's own stored `k_c`. This is INTENDED (a 4 MiB writer cell against
the file:// reader's 1 MiB coalescing was the divergence this TD closes) but
UNMEASURED: the settled SIFT-1M acceptance geometry (30 cells / nprobe 11 /
recall 0.9822) was measured at the OLD k, and no CI gate pins `k`.

**Rollback levers available today** (no redeploy): `PROXIMADB_DISK_CLASS=hdd`
restores the CLOUD-on-file profile pod-wide; per-location TOML
`io_budget.disk_class = "hdd"` restores it for one location.

**MEASURED (required follow-up executed 2026-09-03 —
`iobudget2_file_geometry_sift1m`):** the A/B ran on byte-identical-SIFT-1M
`file://` beds, one binary, `--ivf-k 30` (old CLOUD-derived k) vs the shipped
destination-derived k (settled coarse_cells 30 vs 122 — the plumbing engaged in
vivo). Result: object-cold bytes/q −51.1% (58.53→28.62 MB), GETs/q −13.3%
(21.95→19.02), recall 0.9835→0.9794 (paired −0.0041). At the then-0.98 floor
this FAILED (paired loss 8× the −0.0005 tolerance); the product owner accepted
the trade and the recall floor drops 0.98 → 0.975 repo-wide (harness +
`sift_pax_recall_ratchet_test`; warm-GET gate recalibrated 10.0 → 12.5) — the
operating point is shippable as-is. Cross-host byte-determinism note: same
input compacted on hosts with different registries / `PROXIMADB_DISK_CLASS` now
yields different segment bytes — a pre-existing, config-driven class (cf.
`PROXIMADB_IVF_K`), mixed-read-safe regardless; no cross-host consistency test
exists (noted, not actioned).
