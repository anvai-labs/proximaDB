== History

ADR-065's premise is "one IVF cell ≈ one IOP-sized block", but the writer took the IOP target from hard-coded `IopsBudget::CLOUD` (4 MiB) while the reader resolved `IopsBudget::for_path` per scheme (S3 8 MiB, LOCAL 1 MiB). It never showed up because every `k_c` sweep ran on Azure, where CLOUD is correct. `write_target_block_bytes(destination)` is now the single definition for both sides; `None` remains only for destination-less legacy/test compactor paths. Cell counts are per-segment self-describing metadata (no format change).

*Decisive finding:* the first attempt stalled on "the writer does not know its destination" — compaction writes a local staging file, and passing that path would resolve LOCAL, worse than CLOUD. Re-exploration showed the default flush never reaches `ivf_fine_cell_count` (flush IVF clustering is the eval knob `PROXIMADB_PAX_FLUSH_CLUSTER=ivf`, default OFF) and compaction always knew its output (`SstCompactionTask.output_file`). *Lesson:* do not size a write-side layout from a staging path.
*Adversarial-review finding:* the default all-`file://` deployment also shifted (LOCAL 1 MiB vs old CLOUD 4 MiB ⇒ `k` ×4 on new compacted segments, reader `nprobe` ≈ ×2, self-adapting via the stored `k_c`). Rollback: `PROXIMADB_DISK_CLASS=hdd` pod-wide or per-location `io_budget.disk_class = "hdd"`.

*Evidence:* red→green `destination_url_resolves_the_iop_target`; `iobudget2_file_geometry_sift1m` (coarse cells 30 → 122): object-cold bytes/q −51.1%, GETs/q −13.3%, recall 0.9835 → 0.9794, accepted by lowering the repo-wide recall floor 0.98 → 0.975.

*Still unmeasured (no work item filed):* whether 4 MiB or 8 MiB cells are better on S3 (the Azure optimum is a request-economics result and does not transfer); GCS direction; cross-host byte-determinism when hosts carry different registries / `PROXIMADB_DISK_CLASS` (pre-existing config-driven class, cf. `PROXIMADB_IVF_K`; mixed-read-safe).
