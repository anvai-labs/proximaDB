= TD-SCANDEG-2: The morsel degree counts in-flight queries, not rank workers
:status: Open
:date: 2026-11-06
:tags: [search, concurrency, cpu]

== Problem

`morsel_degree()` returns `cores` when `INFLIGHT_SCANS == 1`. The counter
counts in-flight QUERIES (via `ScanGuard`, taken by the production entry), but a
single query fans out over D files concurrently (inter-file degree, default
cores/2), and EACH per-file rank reads the same count of 1 — so one lone
query can run `D × cores` rank workers. On a 16-core box with 8 segments that
is up to 128 rank workers on 16 cores. The documented "total CPU workers ≈
cores" invariant therefore holds across queries but not within one.

== What the evidence actually says

The only measurement on record — the 2026-07-25 cold A/B sweep — found the
lone-query win (c=1 cold 5.8 -> 10.4 QPS on 3 segments) WITH this D x cores
oversubscription, and found dividing ACROSS queries (cores/inflight) within
noise, with regressions in matched pairs; hence today's deliberately binary
`if inflight == 1 { cores } else { 1 }`. So the within-query oversubscription
is NOT an established cost — it may be part of the measured c=1 win. This
TD records the gap in the invariant's wording, not a known defect.

== If it is ever pursued

* Do NOT reintroduce a `cores / (inflight x files_in_flight)` formula: that
  is the cross-query division the sweep rejected, and it would shrink the
  measured c=1 degree.
* Reuse the existing mechanism: Stage F decode already bounds this same
  D x cores fan-out with the process-wide `stage_f_decode_permits()`
  semaphore (`cores` permits; its doc notes `morsel_degree()` alone does not
  bound the total). Gating rank `spawn_blocking` work on the same kind of
  permit caps total rank threads at `cores` without changing the c=1 degree.
* Measure c=1 and c>=4 before and after; ship only if c=1 latency holds.
