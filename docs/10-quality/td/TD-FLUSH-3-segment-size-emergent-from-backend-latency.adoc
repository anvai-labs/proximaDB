== History (shipped)

* Finding: segment size was emergent, not chosen — the background flush drained whatever accumulated while the previous flush ran, so the same config yielded 6 files locally and 104 over Azurite. The 16 MB threshold measured serialized `ProximaRecord` bytes (~1.6 KB/record ≈ 10k vectors), ~6× smaller than intended. On object storage GETs/query ∝ file count.
* Lesson: durability does not require flushing (the WAL is local disk); flush policy only trades memtable memory vs replay time, so small segments buy nothing.
* S1/S2: the SIZE trigger is gated on PREDICTED segment bytes (Σ dim×9/8+8 per batch — RaBitQ+SQ8 occupancy), tracked in the WAL coordinator; time (RPO) and capacity triggers override so trickle collections still drain; trigger reason logged with mem/predicted/floor bytes. 128 MB ⇒ ~883k vecs @128d … ~77k @1536d per segment, ~27–29 IVF cells/segment at every dim.
* S2b: the 4-not-2 segments were the AutoFlushDriver's ~30 s tick still calling legacy `evaluate()`; it now calls `evaluate_with_predicted`. `needs_global_flush` (`count >= 50_000`) had zero callers and was deleted; `vector_count_threshold` was a dead knob (retired, #1526/#1557). `predicted == 0` bypasses the floor so document/graph collections keep serialized-size flushing.
* Evidence (1M, floor 128 + caches armed): segments 10→4, recall 0.9825, cold c=16 18.2→59.4 QPS, zero compactions needed.

== Open

S3 — **Small-file self-healing**: when L0 accumulates >N small files (already
the case for existing deployments), a cheap L0→L0 stitch (concatenate
segments without re-encoding — same carry-forward machinery as TD-COMPACT-2's
streaming direction) restores the file-count floor without paying the current
compaction pathology.

S4 — **Retire the time trigger; bound recovery by WAL bytes.** Durability is
the WAL's job, and both things the 300 s timer bounds — recovery-replay time
and the read-path delta for slow-trickle collections — are byte-proportional,
not wall-clock-proportional. Replace `flush_interval_secs` with an enabled
`wal_max_bytes` cap (the knob exists, default 0/off): flush when predicted
segment bytes >= floor (S1), OR accumulated WAL bytes >= wal_max_bytes
(replay bound), OR memtable RAM pressure. All triggers become size-based; a
trickle collection flushes when it has enough bytes to deserve a segment, and
replay debt is capped in the unit that determines replay cost.

S5 — **Lane split: the floor governs the trickle/OLTP lane only.** Bulk loads
should use the guarded Flight `WriteLane::BulkAppendCommit` +
`DirectCommitAllowed` path (`src/services/write_intent.rs:58`): the client
already holds the complete dataset, so the server streams it into right-sized
L0 segments directly — no memtable cadence, no emergent sizing, no per-row
WAL amplification. Measured corroboration (2026-07-24, Azurite): when ingest
outpaced the flush loop and one explicit flush drained the whole 1M memtable,
the resulting few-large-file layout gave 84-168 GETs/query cold and a 100%
survivor-cache hot path (0 GETs, sub-ms) vs 1,812/279 GETs/query on the
104-file emergent layout — an 11-21x round-trip difference from layout alone.
