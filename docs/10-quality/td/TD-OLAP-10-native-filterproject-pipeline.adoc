== Why

ADR-054 §8 ships the native engine in non-breaking, flag-gated, ledger-gated phases. Phase 2's job is narrow but load-bearing: **prove the pipeline mechanics end-to-end on the ratified contracts**, so the expensive operator (the Phase 3 radix/spill/bloom hash join, TD-OLAP-11) targets a *working* `BatchStream` pipeline rather than building join build/probe fusion on top of a non-existent one. The cheapest operator that exercises the full chain (source → operator → fused filter+project → `RecordBatch` sink → Phase 1's `record_batches_to_pipeline_result`) is `FilterProject` — and it happens to be the highest-ROI fusion in any vectorized engine (DuckDB, Velox, Hyper all fuse it), because every analytical query is `SELECT cols FROM t WHERE pred`.

This is also where the **zero-DataFusion expression IR** (the BLOCKER-2 fix from ADR-054 v2 review) is first exercised. Lowering `proximadb_relational_types::Expr` → a native `ProximaPhysicalExpr` evaluated via `arrow-ord`/`arrow-compute` kernels is identical work whether the consumer is a filter mask or a join-probe residual predicate. Solving it once here de-risks TD-OLAP-11.

== Honest scope (what this phase does NOT move)

* It does **not** route real storage reads. Phase 2 supports only `PhysicalPlan::Values` (in-memory literal rows) as the pipeline source. `PhysicalPlan::Scan` → `Ok(None)` (Volcano fallback) — the real scan source (PaxSplitReader de-DataFusion'd, or a Volcano-row→Arrow converter) is Phase 2.5. This is deliberate: a `Values` source proves the pipeline without coupling to storage or paying the row→Arrow→row conversion tax the Volcano path would incur.
* It therefore does **not** close the Q3/Q14 join gap (that is TD-OLAP-11). On Q1/Q6-shaped scan/filter queries the Volcano is already 2–6 ms; Phase 2 targets **parity, not a win**, and the ledger gate says so explicitly.
* It does **not** include `HashAgg` (ADR-054 §8 lists it in Phase 2 alongside FilterProject). `HashAgg` is a *blocking* operator (full input before emit) and is split to a Phase 2.1 follow-on; FilterProject ships first because it is pipelined and unblocks the join.

== Design

=== The wire (the Phase 0 `try_vectorized` signature is corrected)

The Phase 0 hook (`native_engine.rs`) was sketched as `try_vectorized(sql, context)`. That signature does not match reality: the native engine is never handed raw SQL — it executes an already-planned `PhysicalPlan` via `NativeVolcanoEngine::execute_physical::<F: ReaderFactory>(physical, factory, controls)` (`engine.rs:278`), which is the single chokepoint every native execution path funnels through (the `relational_pipeline::execute_physical` wrapper at `relational_pipeline.rs:555` records `io_trace` then calls it; internal callers in `engine.rs` call it directly).

Corrected signature (consumes only what the `Values`-supported path needs):

[source,rust]
----
/// Try the native vectorized path. `Ok(Some)` = handled; `Ok(None)` = shape
/// unsupported, fall through to the Volcano; `Err` = attempted + failed.
pub fn try_vectorized(
    physical: &PhysicalPlan,
) -> Result<Option<ExecutionPipelineResult>, ExecutionError>;
----

Hook point: the first lines of `NativeVolcanoEngine::execute_physical`, before `cap_plan`/`build_executor`:

[source,rust]
----
pub async fn execute_physical<F: ReaderFactory>(
    physical: PhysicalPlan, factory: &F, controls: ExecutionControls,
) -> Result<ExecutionPipelineResult, ExecutionError> {
    controls.check_cancelled()?;
    if crate::query::execution::native_engine::native_vectorized_enabled() {
        if let Some(result) = crate::query::execution::native_engine::try_vectorized(&physical)? {
            return Ok(result);   // vectorized path served it
        }
    }
    // ... existing Volcano: cap_plan → build_executor → open → collect
}
----

Because the hook sits above `cap_plan`, the vectorized path honors `controls.max_rows` by lowering a trailing `PhysicalPlan::Limit` itself (it is in the supported set). `io_trace` `record_compute_ms("native", …)` is recorded by the `relational_pipeline` wrapper that *calls* `execute_physical`, so the vectorized path's compute time lands in the ledger automatically with no extra wiring.

=== Supported plan shapes (the routing gate)

`try_vectorized` lowers a plan iff it matches one of:

* `Values { rows, output_schema }` — every `Expr` in every row is `Expr::Literal` → `MemoryScanSource`.
* `Filter { input, predicate }` — `input` supported AND `lower_predicate(predicate)` succeeds.
* `Project { input, outputs }` — `input` supported AND every `NamedExpr` lowers to `Column` or `Literal`.
* `Limit { input, limit, offset }` — `input` supported (offset+limit applied at collect).
* A `Filter` directly under a `Project` (or under another `Filter`) is **fused** into one `FilterProjectOperator` (ADR-054 §4.3) — no intermediate `RecordBatch`.

Anything else (`Scan`, `Join`, `Aggregate`, `Sort`, `Distinct`, `SetOp`, `Union`, `AssertMaxOneRow`, or an unsupported `Expr` variant in the lowering) → `Ok(None)`. This is the honest scope boundary; the Volcano remains the floor and the fallback (ADR-054 §8: "At every phase, DataFusion remains the floor and the fallback").

=== Components (all in the binary; contracts crate unchanged)

*MemoryScanSource* — `impl ExecutionOperator`. Holds `Vec<RecordBatch>` (built once from `Values` rows). `execute` ignores its input stream and yields its batches one per poll. This is the harness source; Phase 2.5 swaps it for a real scan operator behind the same `ExecutionOperator` seam (non-breaking).

*FilterProjectOperator* — `impl ExecutionOperator`. Holds `predicate: Option<ProximaPhysicalExpr>` and `projection: Option<Vec<usize>>`. `execute` is an async stream over the input; for each `RecordBatch`:
. if `Some(pred)`: `let mask = pred.eval(&batch)?;` → `arrow_select::filter::filter_record_batch(&batch, &mask)?`;
. if `Some(proj)`: `batch.project(&proj)?`;
. emit. +
Fusion = one pass, no intermediate batch (matches §4.3). `arrow-select`/`arrow-ord` are added to the main crate's `Cargo.toml` deps (they are already workspace members in use elsewhere).

*ProximaPhysicalExpr* — the zero-DataFusion expression IR (BLOCKER-2 resolution). A small enum:

[source,rust]
----
enum PhysExpr {
    Column(usize),                 // Expr::Column(ColumnRef) resolved to ordinal
    Literal(ScalarValue),          // Expr::Literal
    Compare { op: BinaryOp, left: Box<PhysExpr>, right: Box<PhysExpr> },
    And(Box<PhysExpr>, Box<PhysExpr>),
    Or(Box<PhysExpr>, Box<PhysExpr>),
    Not(Box<PhysExpr>),
    IsNull { expr: Box<PhysExpr>, not: bool },
}
----
`eval(&self, batch: &RecordBatch) -> Result<BooleanArray, ExecutionError>` recurses; `Compare` maps the 6 comparison `BinaryOp`s (`Eq/NotEq/Lt/LtEq/Gt/GtEq`) to `arrow_ord::cmp::{eq,neq,lt,lt_eq,gt,gt_eq}` against a scalar; `And/Or/Not` to `arrow::compute::{and_kleene, or_kleene, not}` (Kleene = correct SQL three-valued logic, which ADR-019 mandates); `IsNull` to `arrow::compute::is_null`/`is_not_null`. `lower_predicate(&Expr)` returns `Err(NotImplemented)` for any other variant (`Cast`, `Between`, `In`, `Like`, `Case`, `Coalesce`, `NullIf`, `FuncCall`, arithmetic `BinaryOp`s, `UnaryOp`) — those lowerings land incrementally; the `Err` is the fallback signal, not a hard failure.

*lower_physical(&PhysicalPlan) -> Result<Pipeline, ExecutionError>* — walks the plan; collects a contiguous run of `Filter`+`Project` into one `FilterProjectOperator`, attaches a `MemoryScanSource` for the `Values` leaf, and folds a trailing `Limit` into the collect step. Returns `Err(NotImplemented)` (→ `Ok(None)` at the wire) for unsupported shapes.

*execute_pipeline(&Pipeline) -> Result<Vec<RecordBatch>, ExecutionError>* — `Pipeline::execute` (contracts crate) already chains operators (`output of each → input of next`); this drains the final `BatchStream` to `Vec<RecordBatch>`, applying offset/limit. The wire then calls the Phase 1 bridge `record_batches_to_pipeline_result(&schema, &batches)` to produce `ExecutionPipelineResult`.

*proxima_values_to_record_batch* — the reverse of Phase 1's `arrow_cell_to_proxima`: `Values { rows: Vec<Vec<Expr>> }` (each `Expr::Literal`) → column-major `RecordBatch` via the typed `arrow_array` builders. This is the only Phase 2 site that needs ProximaValue→Arrow; it is bounded (literals only).

=== Three-valued logic + NULL safety (ADR-019)

`And`/`Or` use the Kleene kernels (`and_kleene`/`or_kleene`), not the bitwise `and`/`or`, so `TRUE AND NULL = NULL`, `FALSE OR NULL = FALSE` — the SQL semantics `proximadb-relational-types` is designed around. Comparison kernels return null on null operands; `filter_record_batch` drops null-mask rows. A conformance test (below) cross-checks the vectorized path against the Volcano on NULL-bearing inputs to prove parity.

=== Shadow comparison + demotion (ADR-054 §7 / Phase 0.5)

A second flag `PROXIMADB_NATIVE_VECTORIZED_SHADOW=1` (default-off) runs the vectorized path, then *also* runs the Volcano, compares the row sets, and logs the mismatch count + rate to `io_trace`. A per-shape mismatch rate > 0.1% auto-demotes that shape (the vectorized path returns `Ok(None)` for it until fixed). This is the "no buggy operator stays live" contract. Phase 2 ships the shadow *harness*; it becomes the promotion gate once real scan wiring lands (Phase 2.5) — until then it is exercised by the conformance tests.

== Rollout (default-off, flag-gated, ledger-gated)

. Gate: `PROXIMADB_NATIVE_VECTORIZED` (default OFF). `try_vectorized` is a no-op until set.
. Shadow: `PROXIMADB_NATIVE_VECTORIZED_SHADOW` (default OFF).
. Promotion (per ADR-054 §8 Phase 2 gate): the vectorized path is eligible to default-on only when the TD-OLAP-4 ledger shows **≥ parity on in-memory FilterProject vs the Volcano, with conformance unchanged**. Phase 2 itself does not flip the default — it lands the capability + the benchmark harness; the flip is a separate, evidence-gated decision.

== Verification

*Unit (in `native_ops.rs`):*
* `filter_project_filters_and_projects` — `MemoryScanSource(1..1000)` → `Filter{x>500}` → `Project{[x]}`; assert rows = `501..=1000`.
* `phys_expr_lowers_each_supported_variant` — each `PhysExpr` arm produces the expected `BooleanArray` on a fixed batch (incl. NULL rows for Kleene + IsNull).
* `null_three_valued_logic_parity` — `AND`/`OR` with a null operand match the Volcano's `Expr` evaluator on the same inputs.
* `unsupported_shape_falls_back` — `Scan`/`Join`/`Cast`-bearing predicate → `try_vectorized` returns `Ok(None)`.

*Integration (`try_vectorized` wire):*
* `vectorized_serves_values_filter_project` — `PROXIMADB_NATIVE_VECTORIZED=1`, plan `Project{Filter{Values}}`; assert result rows equal the Volcano's on the same plan.

*Benchmark (#[ignore], run on demand, feeds the ledger):*
* `filter_project_throughput_1m_rows` — 1M-row `MemoryScanSource`, `Filter{x>500000}`+`Project{[x]}`; wall-time the vectorized path vs `NativeVolcanoEngine::execute_physical` on the identical `PhysicalPlan`. Target: parity-within-noise. The number goes into the TD-OLAP-4 ledger as the Phase 2 evidence row.

*Gates (local, before push):* `cargo fmt --all --check` (toolchain 1.95.0); `cargo clippy --lib --bins`; `check_td_adr_unique.py`; `grep -rn datafusion src/query/execution/native_ops.rs` → empty (zero leakage).

== Risks + mitigations

* **`PhysicalPlan` lowering drift.** The planner is non-destructive but evolves; `lower_physical` must track `PhysicalPlan` variants. Mitigation: the `Ok(None)` fallback makes drift *safe* (worst case = the Volcano runs), and the unsupported-shape test pins the supported set.
* **Over-claiming a win.** The temptation is to present Phase 2 as "the native engine is faster." It is not, on its supported shapes. Mitigation: the TD + the ledger row state parity explicitly; promotion is gated on parity, and the narrative in any status doc must say "foundational, not latency-moving."
* **Kleene-vs-bitwise bug.** A wrong AND/OR kernel silently corrupts NULL semantics. Mitigation: the `null_three_valued_logic_parity` test + the shadow comparison are both NULL-focused.
* **Scope creep into Scan.** Wiring PaxSplitReader pulls DataFusion types back in (BLOCKER-2 regression). Mitigation: Scan is explicitly Phase 2.5 and out of scope here; the `MemoryScanSource` seam keeps that future wiring non-breaking.

== Non-goals (deferred)

* `PhysicalPlan::Scan` source (Phase 2.5 — PaxSplitReader de-DataFusion'd, or Volcano-row→Arrow).
* `HashAgg` (Phase 2.1 — blocking operator).
* The hash join (TD-OLAP-11), morsel scheduler (TD-OLAP-12), fused ANN+filter+aggregate (TD-OLAP-13).
* Default-on flip (separate, ledger-gated).
