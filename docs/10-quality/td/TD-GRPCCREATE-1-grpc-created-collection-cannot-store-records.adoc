= TD-GRPCCREATE-1: a collection created over gRPC cannot store records

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-10-18).** Both catalog rewrite paths (`set_collection_schema_columns` and `upsert_collection_catalog_asset`) merge declared columns through one rule and validate before dropping the table. Pinned by the end-to-end tests in `tests/grpc_created_collection_e2e.rs` and the `merge_canonical_band` unit tests. Reproduced on 0.4.1 before the fix.
| Priority | **HIGH** — the Python SDK prefers gRPC by default, so every Python quick start stored nothing.
| Component | `src/services/collection/manager.rs` (`set_collection_schema_columns`, `upsert_collection_catalog_asset`), reached from gRPC v2 `CreateCollection` and from REST schema and collection updates
| Relates to | TD-SDKERR-1 (the failure is hidden), TD-ENGSEL-1; roadmap v0.5
|===

== Problem

After a Python SDK `CreateCollection` over gRPC succeeds, every later insert fails: the server logs
`Failed to process rich record batch: Collection <id> not found` and
`Table 'default.<name>' not found`, and the REST v2 collection listing omits the collection. (A
REST `GET` of the name returns 200, but that proves nothing: see TD-RESTGET-1.) A gRPC insert into a
collection created over REST succeeds, so the defect is on the create side.

Mechanism (confirmed by an end-to-end test that creates over raw gRPC and fails on `develop`, so
the server alone is at fault; the test ships with the fix): the gRPC handler provisions storage through the v1 bridge, then persists
a canonical schema whose columns always include `embedding` (and any filterable columns).
`set_collection_schema_columns` (`src/services/collection/manager.rs`) keeps the reserved band,
which already holds the v1 `embedding` column, appends the canonical columns, **drops the catalog
table, and only then** calls `create_table`, whose validation rejects the duplicate name
(`Duplicate column name: embedding`). The table is gone; the failure is only logged.

The same path breaks REST. Reproduced twice on 0.4.1: create with
`{"dimension": 3, "engine": "sst", "enable_proxima_record": true}`, then
`PUT /api/v2/collections/<name>/schema` with
`{"columns": [{"name": "embedding", "data_type": "vector", "vector_dimension": 3},
{"name": "category", "data_type": "text", "filterable": true}]}`: the PUT returns 500
(`Duplicate column name: embedding`) and every later insert fails with "Collection <id> not
found". The destruction happens when the PUT reaches a collection with no records yet: after a
first insert, the same PUT returns the same 500 but leaves the collection usable.

== Fix

Both functions that rewrite a collection's catalog table (`set_collection_schema_columns` for a
schema update, `upsert_collection_catalog_asset` for any collection update) now:

* merge declared columns through `merge_canonical_band` (`src/storage/metadata/collection_mapping.rs`).
  A declared column that repeats a reserved column's name folds into it when compatible
  (`embedding` with the collection's dimension; a filterable column whose declared type narrows to
  the stored filterable type, so `int32` folds into an `Int64` filterable column) and is rejected
  otherwise; system column names and duplicate declarations are always rejected;
* record a folded declaration on the reserved column itself (`proxima.declared`,
  `proxima.declared_ordinal`), so the typed catalog columns remain the one authority for the
  declared schema (ADR-048) and REST GetSchema returns every declared column in order;
* normalize and validate the new schema, as `create_table` does, before dropping the table.

Covered by `tests/grpc_created_collection_e2e.rs`: create over gRPC then insert, search and list
over both transports; a schema update naming `embedding`; making an existing column filterable
(the second path, which also deleted the collection); REST GetSchema completeness; declared types
that narrow to the filterable type (`int32`, `float32`, `decimal(10,2)`); a conflicting
`embedding` dimension rejected with the collection intact; and a forced duplicate-column update
rejected with the rows intact (a regression guard). gRPC GetSchema is not covered: see
TD-GRPCSCHEMA-1.

Out of scope here, filed as TD-CATREPLACE-1: the catalog's drop-then-create is still not atomic,
and a rejected schema update can be half applied.
