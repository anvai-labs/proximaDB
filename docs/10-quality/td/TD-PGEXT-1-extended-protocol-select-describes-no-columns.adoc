= TD-PGEXT-1: extended-protocol clients fail on relational and parameterized queries

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Partial (2026-10-22).** Describe(statement) and Describe(portal) now report the columns Execute streams, typed from the same source Execute uses: the legacy single-table reader's shape comes from the DML service's own column resolution (`SELECT *` included), a relational-pipeline SELECT of plain columns and `count()` is typed from the table schema, and the pgvector shape keeps its typed lowerer. Clients that send parameter OIDs are described too. Bind result-format codes are honored, with binary encoders for the describable types, and an Execute-time error is an ErrorResponse instead of a dropped connection. Pinned by `tests/pgwire_extended_relational_e2e.rs`, including a differential check against the simple protocol. Execute re-checks the shape it streams against Describe and answers 0A000 ("cached plan must not change result type") on any difference, so a parameter value that changes the route or DDL on a cached statement fails cleanly. After an extended-protocol error the server skips messages until Sync. Remaining: (a) pipeline shapes other than plain columns and `count()` (other aggregates, expressions, joins, set operations) are described as empty; (b) sparse/binary vectors and UInt64 above `i64::MAX` cannot be binary-encoded and fail the Execute with XX000 when a client requests binary; (c) pipeline column names and types on the DataFusion (MATERIALIZEd) route are not covered by the differential test — JSON, UUID and bytea pipeline columns are therefore described as empty, and a pipeline SELECT under a non-default `search_path` is too; (d) Describe of a no-result statement sends an empty RowDescription instead of NoData (pre-existing); (e) Parse now does one catalog lookup per SELECT — unmeasured; (f) an error in an implicit extended-protocol transaction does not roll back statements already executed before it in the same Sync batch; (g) a statement described as empty serves binary-format requests as text (pre-existing); (h) a COPY framing error inside an extended Execute leaves the connection desynced instead of closing it (the simple path already behaved this way).
| Priority | **HIGH** — JDBC, asyncpg, psycopg 3 and most ORMs use the extended protocol, so most real clients fail; ADR-096 makes pgwire the front door.
| Component | pgwire extended protocol (`Describe` for portals and statements, `src/network/postgres/protocol.rs`)
| Relates to | ADR-096, TD-102 (extended protocol, Slice A), roadmap v0.5
|===

== Problem

The server's `Describe` reports zero result columns for relational SELECTs and describes every
`$N` parameter as `text`, whatever the column type. Observed on 0.4.1:

[cols="2,2,2,2", options="header"]
|===
| Client | Relational SELECT, no parameters | Relational SELECT with `$1` | Vector search with `$1`
| asyncpg 0.31 | fails (`the number of columns in the result row (2) is different from what was described (0)`) | fails (non-string arguments are rejected because every `$N` is described as text; a string argument hits the same column error whenever rows come back) | works
| psycopg 3 | works until psycopg auto-prepares the query (from the 6th execution, `prepare_threshold=5`), then fails | fails | fails (`unexpected field count in "D" message`)
| psql `\bind` | fails (`unexpected field count in "D" message`) | fails | fails
|===

JDBC and ORMs use the extended protocol and are expected to be affected; not yet tested. The
existing test (`tests/pgwire_extended_param_e2e.rs`, tokio-postgres) covers only parameterized
vector search, which is why this was not caught. The simple query protocol works (psql, psycopg 2).
Workarounds for psycopg 3: `prepare_threshold=None` keeps unparameterized queries working, and
`psycopg.ClientCursor` makes parameterized relational and vector queries work.

== Fix (2026-10-22)

* Parse resolves the result shape for every client (`describe_select_shape` in
  `src/network/postgres/protocol.rs`), following the route Execute takes and reusing the
  dispatcher's own predicates: the pgvector lowerer; the legacy single-table reader via
  `DmlService::describe_select_columns` (the column list `execute_relational_query` emits, with
  its type mapping); a relational-pipeline SELECT of plain columns and `count()` via
  `describe::pipeline_projection` (the frontend's naming rules, the pipeline's type mapping).
  Anything else is described as empty — never a guess.
* Describe(portal) echoes the statement's shape with the portal's result-format codes (libpq,
  pgjdbc unnamed statements and Npgsql describe the portal).
* Bind's result-format codes are kept on the portal; the DataRow writers encode binary cells for
  every type a statement can be described with (bool, int2/4/8, float4/8, text, json, jsonb,
  bytea, date, timestamp, timestamptz, uuid, vector).
* Execute-time errors become an ErrorResponse (SQLSTATE XX000) and fail an open transaction,
  matching the simple protocol, instead of closing the connection. After any ErrorResponse to an
  extended-protocol message the server discards messages until Sync.
* Execute checks the columns it would describe against what Describe advertised and answers
  0A000 on a difference, before any DataRow (the RowDescription it suppresses, and the
  portal-paging pipeline route).
* Execute dispatches on the trimmed bound query, as the simple protocol does.

== Original fix proposal

Describe every SELECT with its real row description and parameter types. Add end-to-end tests with
tokio-postgres (`query` with and without parameters, relational and vector), and a driver smoke
with asyncpg, psycopg 3 and JDBC against the release image.
