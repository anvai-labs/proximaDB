= TD-HELMDUP-1: a second Helm chart under deploy/infrastructure is unrenderable, stale, and documented

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-08 during the v0.4.0 version-sync audit, which found it as the third instance of the "a version string nothing watches" class.
| Severity | **LOW**, and deliberately not raised. == What is wrong

`deploy/infrastructure/helm/proximadb/` holds exactly three files: `Chart.yaml`,
`values.yaml`, `templates/deployment.yaml`. It contains **zero `define`s**, has no
`_helpers.tpl`, no `charts/` subdirectory and no `dependencies:` in `Chart.yaml`
— yet `deployment.yaml` `include`s **six** named templates:
`proximadb.fullname`, `proximadb.labels`, `proximadb.selectorLabels`,
`proximadb.serviceAccountName`, `proximadb.name` and
`proximadb.imageConfiguration`.

Helm resolves named templates per chart (plus subcharts), so **all six are
unresolvable** and the render dies at the FIRST one —
`deployment.yaml:11`, `{{ include "proximadb.fullname" . }}` — not at the image
include. Five of the six do exist in the canonical chart's
`templates/_helpers.tpl`; `proximadb.imageConfiguration` is defined nowhere in
the repository at all (the canonical chart defines `proximadb.image`, a different
name). So `helm template` / `helm install` against this directory cannot
succeed.

`deploy/infrastructure/scripts/deploy-dev.sh` nevertheless sets
`HELM_DIR="${PROJECT_ROOT}/deploy/infrastructure/helm/proximadb"`, and
`deploy/infrastructure/README.md` plus
`deploy/infrastructure/DEPLOYMENT_GUIDE.md` document it. So the documented
dev-deploy path is broken independently of any version string.

The stale versions are a symptom of the abandonment, not the defect:

* `deploy/infrastructure/helm/proximadb/Chart.yaml` — `version: 0.1.0`, `appVersion: "0.2.0"`
* `deploy/infrastructure/helm/proximadb/values.yaml` — `image.tag: "0.2.0"`
* `deploy/infrastructure/terraform/environments/{dev,staging,production}/helm-values.yaml` — `image.tag: "0.2.0"` (x3)

The canonical chart gets this right and needs no per-release edit:
`deploy/helm/proximadb/values.yaml` has `tag: ""` and
`templates/_helpers.tpl:68` is `{{- $tag := default .Chart.AppVersion .Values.image.tag }}`,
so the image follows `appVersion`, which IS in the `version-sync.sh` gate.

== Why the versions were not bumped for 0.4.0

Deliberately. Editing `appVersion` and four `image.tag` pins in a chart that
cannot render would make the audit pass without making anything work, and would
hide the real problem behind five plausible-looking diffs. The honest options are
to reconcile or delete the duplicate — not to version it.

(`deploy/helm/legacy-proximadb/Chart.yaml` is also at 0.2.0 and unwatched. It is
named `legacy` and presumed intentional, but it has no exclusion note either, and
it IS referenced — `deploy/README.md:20` lists it as "Retained legacy chart
values", so "nothing references it" would be wrong.)

== How to apply

. **Decide: reconcile or delete.** `docs/_internal/status/CONSOLIDATED_REVIEW_AND_TRACKING_2026_05_26.adoc`
  already recommends consolidating onto one chart. If `deploy/infrastructure/helm`
  has no capability the canonical chart lacks, delete it and repoint
  `deploy-dev.sh`, the README and the DEPLOYMENT_GUIDE at `deploy/helm/proximadb`.
. **If it is kept**, it needs a `_helpers.tpl` defining all six names — switching
  the one `proximadb.imageConfiguration` call to `proximadb.image` is NOT
  sufficient, since the other five includes remain unresolved and the chart still
  dies at `deployment.yaml:11`. Then set `values.yaml` `tag: ""` so the image
  follows `appVersion`, add its `Chart.yaml` `version`/`appVersion` to the
  `version-sync.sh` file list, and drop the three terraform `tag` pins unless an
  environment genuinely needs to lag the chart.
. **Either way**, add the in-place exclusion comment the gate's other
  deliberately-unwatched file has, so the next audit does not re-derive this.
