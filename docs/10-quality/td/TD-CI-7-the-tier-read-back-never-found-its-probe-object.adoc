== History (shipped)

`object_store` 0.13 cannot surface a per-object tier on read, so the out-of-band read-back (`az … --query blobTier`, and now
`head-object --query StorageClass`) *is* the verification. It queried a key that does not exist: `from_url`'s path component is a
**prefix**, so the probe lands at `cold/probe-s3.bin/cold/probe-s3.bin`. The tier was applied correctly (`STANDARD_IA` was there),
and the check looked one segment short. The Azure arm was **warn-only**, so it printed `blobTier = '<unknown>'` every run, looking
exactly like a healthy check with nothing to say. `git log -S` shows the check never once found its blob, since #483.

* Both read-backs now resolve the key by listing plus suffix-match, which is robust whether or not the doubling is fixed.
* Both arms hard-fail on a wrong tier **and** on no object found ("no object" is vacuity too). A missing `az` is detected via
  `command -v az` and reported as a skip. Lesson: a check that cannot tell "absent tool" from "wrong tier" is the same defect in miniature.

== What is still open

1. **Fix the probe tests' `from_url` usage** so the key is not doubled — pass the bucket URL and let
   `Path` carry the key, or pass the full URL and write to `Path::default()`. Low priority (the
   doubling is harmless to the tests, which read through the same store), but it is a trap for the
   next person who writes an out-of-band check against these objects, which is exactly what happened
   here.
2. Consider whether any OTHER warn-only verification in this harness can distinguish "healthy" from
   "never ran" — the GCS arm self-skips, and this finding is the argument for auditing that too.
