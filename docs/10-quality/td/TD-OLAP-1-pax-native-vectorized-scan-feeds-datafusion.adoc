== Why

The native relational executor is a row-wise Volcano iterator
(`crates/query/proximadb-relational-executor/src/lib.rs:1`), evaluating expressions one
`ProximaValue` row at a time. For bulk analytical scan/agg/join that is 1–2 orders of
magnitude off the vectorized/codegen frontier (Kersten et al., PVLDB 2018). The
NATIVE_OLAP_ENGINE_BLUEPRINT's "NativeOlap route" must therefore be a **scan operator**, not
a parallel operator engine: own the PAX-native, ANN-co-designed SCAN; reuse DataFusion's
vectorized operators for everything above it.

== Evidence (measured, in-repo — 2026-07-15)

The "1–2 orders of magnitude" is not just literature here; it is the measured, end-to-end
per-query gap between the two ProximaDB routes on the **same** TPC-H data (pgwire, warm/
repeat, `tests/tpc_perf_ledger_e2e.rs`), and — critically — it **widens with scale**, the
row-wise-per-tuple signature:

[cols="1,1,1,1", options="header"]
|===
| scale | native Volcano (row-wise) median | DataFusion (vectorized) median | gap
| SF 0.001 (~9k rows) | 90 ms | 12 ms | ~7×
| SF 0.1 (~0.9M rows) | **6,388 ms** | **25 ms** | **~461× (max 770×, Q6)**
|===

Growth for 100× more data: **native ~71× slower, DataFusion ~2× (near-flat).** At SF 0.1 the
row-wise route also *times out* on Q21 (60 s budget) while DataFusion serves it in 33 ms.
This is the co-design case (dimensional cost term = per-tuple CPU × rows, which the row-wise
model pays and vectorization erases) grounded in a measured trace, per mandate #6 — not a
kernel microbenchmark. The recent frontend/planner coverage work (TD-REL-LOWER-4/6/7) raised
native TPC-H coverage to 16–17/22 for *correctness* on **fresh** (non-materialized) data;
this TD is the lever that makes that same fresh-data path **fast** by feeding PAX blocks into
DataFusion's vectorized operators instead of the row-wise iterator. Rerun with
`TPC_PERF_SCALE=0.1 TPC_PERF_BENCHMARK=tpch`.

**Prioritization (2026-07-15):** with the substrate + Slice 1/1.5 landed and this measured
gap, **Slice 2 (route flip behind the cost crossover, default-off) is the actively-tracked
next step**, still gated on the TD-OLAP-4 ledger promotion rule (observe → ingest → act,
ADR-052).

== Slice 2 wiring attempt + empirical boundary (2026-07-15)

A Slice 2 route-flip was prototyped end-to-end and **surfaced a boundary the design/scope
traces did not** — recorded here so the next attempt targets the right table class from the
start (measure-before-implement).

**Wiring built (correct + compiling, default-OFF):** an opt-in marker `pax_olap_route` (a
truthy table property, `CREATE TABLE … WITH (pax_olap_route='1')`, read from
`CatalogTableSchema.properties`) drives a `catalog_table_pax_route_base()` detector →
`QueryShape.pax_backed` → the existing `ComputeScheduler` PAX branch (which already gates on
`PROXIMADB_DF_PAX_READER`). Dispatch adds a `PaxTableSpec { name, base_path, arrow schema,
name_to_col_id }` (col_id from `CatalogColumn.id`; Arrow via `relational_schema_to_arrow`) to
`QueryExecutionContext`, and `DataFusionLocalEngine` registers each via the existing
`register_pax_location()` (`PaxSplitReader` over `discover_pax_segments`). All compiled clean.

**The blocker (empirical, decisive):** a pgwire **relational** collection (`CREATE TABLE`)
**does not flush its data to `.pax` segments at all** — after `force_flush_collection` + a 2 s
wait, an instrumented e2e found **zero `.pax` files** anywhere under the data dir (only
`observability/` + `pgwire/`). These tables are WAL + memtable-backed (the DirectWal→Memtable
relational path, correct-by-construction — see TD-REL-SCAN-1); the `.pax` segment format +
flush is the **vector/SST-engine** collection path. So a `PaxSplitReader` has nothing to read
for a relational table, and the restrict-to-flushed route can never serve one. A route-PROOF
e2e (insert-after-flush, so PAX would see only flushed rows) confirmed the query was served by
Volcano, not PAX.

Secondary gap found along the way: `CatalogStorageLayout.location` is **`None`** for these
native collections, so a PAX base path cannot be read from the catalog — it must be derived
via `DrPathBuilder::build(namespace, collection_id).segments_subprefix()` **prefixed with the
storage-root URL** (three inconsistent path conventions exist: SST-flush
`{base_location}/{collection_id}/data`, `DrPathBuilder` `data/{tenant}/{ns}/{coll}/segments/`,
and the native-engine MVP `{PROXIMADB_DATA_DIR}/collections/{table}` — reconcile before wiring).

**Corrected scope / next attempt.** Slice 2's PAX route is for **PAX-segment-producing
collections** (vector/embedding, or SST-materialized), queried relationally — **not** pgwire
`CREATE TABLE` relational tables, which correctly stay on the WAL/memtable Volcano path. The
next attempt MUST (a) create a collection class that actually flushes `.pax`, (b) resolve the
segments base path via `DrPathBuilder` + storage root (not `layout.location`), and (c) prove
row-exactness over real flushed segments before any promotion. Alternatively, giving relational
tables a flush-to-PAX materialization is separate storage-engine work, not part of the route.

== Rollout (observe → ingest → act; default-off)

. **Substrate (prereq, tracked elsewhere):** TD-162a-2 typed user-column stripes + TD-154
  hierarchical zone maps + TD-162a-3 `RecordReader` trait — the scan input.
. **PAX scan → Arrow bridge (default-off feature):** a `LogicalNode::Scan` lowering that
  produces a DataFusion `ExecutionPlan` (extend `src/datafusion/proxima_scan_exec.rs`) whose
  `Stream` yields **single-materialization** Arrow `RecordBatch`es — stripe bytes are decoded
  into Arrow buffers exactly once via `RecordReader` (compressed/quantized stripes cannot be
  zero-copy), with no further copies across the `TableProvider`/`ExecutionPlan` boundary.
  Projection narrows at the stripe level; predicates push into the prune stack.
. **Prune stack wired:** apply zone-map (TD-154) + bloom (`proximadb-block-format/src/stripe.rs`)
  + range coalescing (TD-151) *before* fetching stripe bytes; emit per-query `range_gets` /
  `bytes_read` into the TD-158 trace (TD-158 is **Resolved** — the trace substrate is available,
  not a pending dependency).
. **Route (act):** `compute_scheduler.rs::route_select` selects the PAX-scan+DataFusion path
  for PAX-backed analytical tables above the ADR-050 cost crossover, flag-gated, default-off;
  promote only where the measured trace beats DataFusion-on-Parquet on bytes-scanned. Until
  upstream DataFusion hash-join spill lands, route large joins (build side above a size
  threshold) to sort-merge — this step owns that mitigation; the TD-OLAP-4 ledger flags every
  affected query.
. **Retire (non-goal enforcement):** do NOT add native HashAgg/HashJoin/Sort for the OLAP
  path — those stay DataFusion. The row-wise Volcano remains the OLTP / point-lookup / no-DF
  build floor only.

== Verification

* TPC-H (22) / TPC-DS (16) pgwire conformance unchanged with OLAP on the PAX-scan+DataFusion
  route (they bind to `LogicalNode`, not the engine).
* ADR-039 leakage ratchet green (no new `datafusion::` import outside the adapter allow-list).
* TD-OLAP-4 ledger: SF1 scan-heavy query bytes-scanned vs DataFusion-on-Parquet — promotion

== Slice-2 dispatch design record (2026-08, TD-PAXRG-1 closeout pressure test)

The storage layout work (TD-PAXRG-1) is complete and default-ON, but the QUERY
route (`pax_backed` OLAP shapes → `DataFusionLocal`) remains default-OFF — and
must stay so until the **dispatch wiring** below lands. Exploration verified
that flipping `PROXIMADB_DF_PAX_READER` today changes only decision stamping
and metrics: the dispatch block requires `parquet_backed`, so Volcano still
serves — while `finalize_route` attributes Volcano's measured costs to
DataFusion cost-model cells (attribution poisoning) and EXPLAIN diverges from
the stamped decision.

=== Requirements before any route default changes

1. **WAL-delta reconciliation for the pax route.** `PaxSplitReader` scans only
   `.pax` segments under the discovered base path; there is no delta merge
   (`OlapDeltaConfig` is parquet-only). Freshness gate: row-exactness over
   real flushed segments *plus* un-flushed WAL tail before any promotion.
2. **Segment base-path reconciliation.** Three conventions coexist (SST
   `{base}/{collection}/data`, DrPathBuilder
   `data/{tenant}/{ns}/{collection}/segments/`, MVP
   `{PROXIMADB_DATA_DIR}/collections/{table}`); `layout.location` is `None`
   for native tables. The dispatch wiring must resolve the base path the way
   `DrPathBuilder` does (TD-OLAP-1 Test 2.2's contract).
3. **`pax_backed` predicate refinement.** `CatalogTableSchema::default()`
   ships one InternalCanonical/ProximaBlock layout, so EVERY freshly created
   native table is `pax_backed` — a false positive for relational tables
   whose rows live in WAL/RecordStorage. The route predicate needs a
   "has flushed PAX segments" signal (segment-directory non-empty), not the
   catalog layout alone.
4. **Dispatch wiring.** The unlanded slice-2 prototype (`pax_olap_route`
   table property → `catalog_table_pax_route_base` → `PaxTableSpec` →
   `register_pax_location`): rebuild against the current
   `route_select`/dispatch block, with the decision stamp and the actual
   dispatch driven by the SAME signal.
5. **EXPLAIN/decision alignment.** `classify_select_route` (both variants)
   must consume the same predicate as `try_run_select` so EXPLAIN never
   diverges from the executed route.

Until all five land: leave `PROXIMADB_DF_PAX_READER` default-OFF (both gate
definitions carry the warning); the cost model stays observe-only for
`olap/native` cells.
