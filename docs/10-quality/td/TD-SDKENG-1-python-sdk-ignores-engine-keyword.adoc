= TD-SDKENG-1: the Python SDK silently ignores an `engine=` keyword

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-10-24).** `engine=` aliases `storage_engine=` and `index_params=`/`index_specs=` alias `index_configs=`, applied on every create surface (v1, v2, async, the raw REST client) — including when `config=` is given (the alias overrides) — and index/quantization settings now REACH the server (the sync REST v2 body and the async body carry `index_configs` with `hnsw_config` and `quantization:{enabled,strategy}` — the REQUEST schema's names, verified against `CreateCollectionV2Request` (strategy is the server's enum: a concrete SDK quantization method sends `custom_levels`, the default sends no key)). Unknown keywords raise a `TypeError` naming the accepted spellings, EXCEPT the transport-consumed pass-through (`schema=`, `initial_capacity=`, `indexing_algorithm=`) which travels past the config as before; conflicting spellings (`engine=` with `storage_engine=`) are rejected. The `StorageEngine` docstring and the model default no longer claim VIPER (SST is the default; VIPER is deprecated, ADR-093); the AutoML recommender no longer recommends VIPER/SWIFT/RAPTOR (deprecated or experimental) and emits only create-able overrides. Correction from review: `quantization=` was never silently dropped — it is pydantic's own field alias; that claim is withdrawn. Pinned by `tests/unit/test_sdkeng_kwargs.py` (mutation-checked) and the AutoML suites.

Remaining: the gRPC adapter path still ignores `config.index_configs` (a V2IndexSpec mapping is a follow-up); the transport pass-through is asymmetric (`indexing_algorithm=` is REST-silent; `schema=`/`initial_capacity=` raise a raw TypeError on gRPC); TimeSeries/document create surfaces keep their lenient dict merge. The proto converter no longer defaults an unknown/None engine to VIPER — every `storage_engine_to_int`/`to_str` branch falls back to SST (ADR-093), and the unknown-index fallback stays HNSW. The recommender ceiling is {sst, nova, helix}: MMAP/HYBRID map to VIPER on gRPC and are absent from the v2 REST options. A `name=` conflicting with the positional name raises the friendly error. Reproduced: `create_collection('x', dimension=3, engine='helix')` created an SST collection; `storage_engine='helix'` created HELIX.
| Priority | **MEDIUM** — a user who asks for an engine silently gets a different one.
| Component | `clients/python/src/proximadb_sdk/unified_client.py`, `unified_client_v2.py` and `unified_client_async.py` (`create_collection(name, config=None, **kwargs)` builds `CollectionConfig` from keyword arguments and drops unknown ones)
| Relates to | TD-ENGSEL-1 (engine defaults); mandate #15 (spec-driven SDKs)
|===

== Problem

`create_collection` accepts arbitrary `**kwargs` and keeps only `CollectionConfig` fields. The
field is `storage_engine`; `engine`, which the REST API and most docs use, is silently discarded,
and the SDK's default (`storage_engine=SST`) is sent instead.

Related: the SDK's `StorageEngine` docstring (`models.py`) still says "Default: VIPER", and the
`AutoML` recommender can suggest VIPER, SWIFT or RAPTOR, which the server rejects.

Wider than the engine: `create_collection(index_params=..., quantization=...)` is accepted and
silently dropped (the server shows `index_specs: []` and default quantization), and an invalid
`quantization` type raises a validation error only for some values. The REST API stores both.

== Fix

Pass index and quantization settings through; reject unknown keyword arguments with a clear error, and accept `engine` as an alias for
`storage_engine` (or document only `storage_engine` and reject `engine`). Add a test for both.
