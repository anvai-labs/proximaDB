= TD-COMPACT-10: L2+ segment consolidation gap — GET/query 10× too high at 1M scale
:status: Implemented
:dim: D1
:pillar: PERF

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Implemented pending final SIFT1M evidence.** Pair consolidation, common→SST config propagation, worker follow-up, and real explicit compaction are covered by deterministic tests.
| Priority | **P0** — GETs/query = 205 at 1M makes retrieval COGS ($141/M) exceed the rate-card price ($50/M) → negative margin. Blocks competitive pricing.
| Component | `src/storage/common/compaction_utils.rs:264-350` (level scaling); `src/core/config.rs` (`CompactionConfig.level_multiplier`).
| Evidence | 2026-07-29 SIFT1M end-to-end benchmark: 9 segments (3 L0 + 1 L1 + 5 L2), 205 GETs/query cold, recall 0.978, retrieval COGS $141.83/M queries at $0.0065/10K Azure reads.
|===

== The measured problem

At SIFT 1M scale on merged develop (async compaction + D2 fix), a cold query
pays **205 object-store GETs** — 10× the competitive threshold (~20). This makes
the retrieval COGS ($141.83/M queries) exceed the KRU rate-card price ($50/M) by
2.8× → **negative 183% margin**. At 33% margin the price would be $211/mo —
uncompetitive with Turbopuffer ($16) or S3 Vectors ($2.53).

The later passing GET-reduction run at commit `484d7da84` established the
pre-pair baseline on the hardened harness: 1,000,000 rows, zero unflushed WAL,
two L1 PAX segments, object-cold 42.02 GETs/query with recall@10 0.9830, and
local-disk-warm 2.00 GETs/query (16 bytes/query) with recall@10 0.9850. The
remaining two 8-byte requests were subsequently traced to generic legacy-SST
classification and are covered by TD-SEARCH-3. These figures are historical
inputs; they are not promoted as final evidence for the threshold-2 build.

== Root cause

**Segment count is the GET multiplier.** Each segment adds ~7-8 reads per cold
query via the cascade:

```
QUERY → A0 (coarse probe, ~KB) → Region A (RaBitQ filter, ~3MB probed cells)
      → Region B (SQ8 rerank, ~5-10MB survivor cells) → Region D (top-k OID blocks, ~4KB)
      → RESULT

Per segment: 1 header + 1 A0 + 1-2 RaBitQ (coalesced) + 1-2 SQ8 (coalesced)
            + 1 footer + 1-2 OID blocks = ~7-8 GETs
```

Region D (OIDs + metadata) is INHERENTLY selective — only the top-k=10 final
result rows are fetched (~4KB), NOT the full ~500MB block region. The cascade
narrows 1M vectors → nprobe cells → ~500 RaBitQ survivors → 10 SQ8 top-k →
10 block reads. This is the co-design from ADR-065.

With 9 segments (3 L0 + 1 L1 + 5 L2): 9 × 8 × (1 − 0.22 cache hit) ≈ 56 base
+ ~149 overhead = 205 total GETs.

The compaction framework HAS a higher-level loop (`compaction_utils.rs:287-350`)
that checks L1+ thresholds. But `level_multiplier = 2.0` makes the L2 threshold
unreachable for a 1M collection:

[cols="3,2,3"]
|===
| Level | File threshold (`l0_file_threshold × level_multiplier^level`) | Actual files at 1M
| L0 | 5 × 2⁰ = 5 | 3 → no trigger (below threshold after compaction)
| L1 | 5 × 2¹ = 10 | 1 → no trigger
| L2 | 5 × 2² = **20** | **5** → **no trigger** ← the gap
|===

The 5 L2 segments (~1GB total, 183–226MB each) accumulate without merging.

NOTE: the small L0 segments (7.1MB each) are a test-config artifact
(`flush_floor_predicted_mb = 4` in the bench config). Production uses
`flush_floor_predicted_mb = 128` → fewer, larger L0 segments.

The L0 early-return at line 264 also starves the higher-level loop during
sustained ingest — L0 always has ≥5 files, so the loop never runs until ingest
settles.

== Fix

. **`level_multiplier: 1.0`** (was 2.0) plus
  **`higher_level_file_threshold: 2`** — L0 retains its batching threshold,
  while any pair at L1+ consolidates. A single-file guard prevents pointless
  promotion/retraining.
  Default carries a strong co-design comment (see ADR-080 D1) so future sessions
  don't revert it. **Bounded [1.0, 1.5]**: config validator WARNs outside this
  range. Below 1.0 = over-compaction (CPU churn). Above 1.5 = segment accumulation
  (defeats the purpose). 2.0 (RocksDB default) is explicitly WRONG for vector
  search.
. **Post-compaction settle pass** — after successful publication the worker
  immediately checks and enqueues the next due level, independent of another
  flush or timer.
. **Config propagation** — `StorageConfig::effective_sst_config()` injects the
  common policy into every SST runtime unless an explicit per-engine override
  exists. The observed TOML parse/SST-default split is now a regression test.
. **Explicit compaction** — the Flight action resolves catalog metadata and
  stable object identity, then calls the real SST scheduler. It no longer
  returns a false-success stub.
. **Production `flush_floor`** — the benchmark used `flush_floor=4MB` (test config),
  producing tiny 7.1MB L0 segments. Production uses 128MB.
