:status: Accepted
:date: 2026-11-03

== Problem

The leveled compaction policy never merges across levels and never triggers
on single files per level. A 3M-vector bed settles at L1+L2+L5 (3
stranded segments), each paying its own header/footer/probe overhead per
query (~61 GETs/q cold on the f32 bed). The ONLY way to collapse them
today is the manual `COMPACT TABLE FULL` (#2339).

For read-heavy collections, the segment count IS the query-cost dial:
each segment adds header, footer, probe and coalescing overhead. Operators
need a way to say "keep this collection at ~2 segments" and have the
system maintain that automatically.

== Observed evidence

* The f32 bed (3M vectors, ~2.6 GB) settles at 3 segments (L1+L2+L5).
* The compaction policy CANNOT merge them: cross-level is out of scope,
  and pairs at each level don't meet the count threshold.
* `COMPACT TABLE FULL` CAN merge them (verified by #2339's tests).
* The pre-#2407 FULL implementation paired the two LARGEST segments
  (O(N×D) write amplification); smallest-first GROUPING is O(D) —
  a 3.6× improvement (see §Smallest-first grouping; the ordering alone
  accounts for 2.0×, the group for the rest).

== Design

=== Strategy enum

`compaction.strategy` — per-collection property, same resolution chain as
the cache policy:

```
collection property > server [storage.compaction_config] > code default
```

(As designed. Background consolidate is refused — TD-COMPACT-16 — so this
chain is not live; see the status banner.)

| value | behavior | best for |
|---|---|---|
| `hybrid` (default) | current leveled policy | write-heavy |
| `consolidate` | merge smallest-first to target | read-heavy, batch-loaded |

=== Consolidate strategy

After every flush publish:
1. Discover live segments across ALL levels (same as FULL)
2. If count ≤ `compaction.target_segments`, stop
3. Sort by size **ascending** — greedily group the smallest segments
   whose combined size reaches `compaction.target_file_size_mb`
4. Each group merges to ONE output of ~target_file_size (the output's
   level is the level of the largest input — a tier hint, not a gate)
5. The target segment count is DERIVED (bytes and MB kept consistent —
   as implemented with `div_ceil` in the flush arm):
   `target_segments = ceil(total_bytes / (target_file_size_mb × 2^20))`
6. If a group exceeds the memory admission budget, take fewer (the
   smallest that fit); repeat next flush

The `target_file_size_mb` knob (not an explicit segment count) is the
primary dial because it produces uniform segments — each a predictable
I/O unit for reads, prefetch and cache warming. A `target_segments`
override exists for the "exactly 1 segment" case but is secondary.

**Why target_file_size, not target_segments:**
- Count-only degenerates into a geometric size ladder (merge 2 smallest
  → medium → merge with next → etc.), not uniform segments
- Count-only with target=1 on a large collection means rewriting the
  entire dataset per flush (catastrophic write amplification)
- Size-based grouping bounds the rewrite per merge to target_file_size
- Each segment becomes a predictable I/O unit (read, warm, prefetch in
  target_file_size chunks — aligned with the cache-policy region groups)

=== Smallest-first grouping (the write-amplification fix)

The current FULL implementation pairs the two LARGEST segments (N−1
merges, O(N×D) bytes). Two separate improvements, with distinct gains —
for files [100, 200, 400, 800, 1600] MB, target=1:

```
largest-first pairwise:  4 merges, 11,300 MB rewritten
smallest-first pairwise: 4 merges,  5,600 MB rewritten   (2.0×)
smallest-first GROUP:    1 merge,   3,100 MB rewritten   (3.6×)
```

* **Ordering alone (smallest-first, still pairwise)** yields 2.0×:
  300 + 700 + 1500 + 3100 = 5,600 MB — each merge output feeds the next.
* **The GROUP is the load-bearing half**: greedily accumulating the
  smallest inputs into ONE multi-way merge reaching the target rewrites
  each input exactly once (3,100 MB). #2407's `compact_collection_full`
  implements the greedy group, which is where the 3.6× comes from —
  ascending sort without grouping does not deliver it.

This also means:
* The admission budget is rarely the bottleneck (the smallest group
  always fits)
* The output of merging small files is small — it naturally cascades
  upward through subsequent merges (no explicit "promote at size X" logic)
* No file is ever "stuck between levels" — there ARE no level boundaries
  in the merge decision

=== The natural cascade IS the promotion

```
[L0:100, L0:100, L0:100] → merge → [L0:280]
[L0:280, L0:128]         → merge → [L1:408]     (level of largest input)
   (a new flush publishes [L1:280])
[L1:408, L1:280]         → merge → [L2:688]     (cross-level is fine)
[L2:688, L5:2000]        → merge → [L5:2688]    (biggest wins)
```

No "minimum size for next level" rule — that would REINTRODUCE the
stranded-file problem this strategy exists to solve.

=== Write-amplification guardrail

A tenant setting `target_segments=1` on a 1 TB write-heavy collection
would rewrite the entire 1 TB on every flush. The guardrail:
* Project the write amplification (total_bytes / flush_size)
* If > a configurable threshold (default 100×), log a warning and
  degrade to `hybrid` for that collection
* The degradation is reported in the collection's status

=== Property surface — as designed (#2407); the background half is refused

NOTE: this section records the background-consolidate resolution as it was
designed and reviewed. That half is refused (TD-COMPACT-16): today the
server layer below is never consulted and `consolidate` is refused at every
door. See "Surfaces, AS SHIPPED" further down for live behaviour.


Resolution is a 4-layer chain resolved by one pure function
(`resolve_effective_strategy`: property > tag > server > code). An
explicit `hybrid` at any layer WINS over a consolidate default below it —
silence falls through, an explicit choice does not:

```
collection PROPERTY `compaction.strategy`
    (carried on the flush path: catalog walk -> CatalogCollectionMeta
     -> CollectionFlushPlan.properties -> FlushParameters
     .collection_properties — the engine-facing proto Collection has no
     properties field, and projecting onto its tags would leak into
     read-modify-write catalog saves, baking policy into `tags`/
     `config_json` and surviving property removal)
  > operator TAG `compaction.strategy:consolidate` (legacy channel)
  > server TOML  [storage.compaction_config] consolidate_strategy = "hybrid"|"consolidate"
  > code default hybrid
```

The `compaction:off` tag disarms all background compaction including
consolidate (checked first, unchanged from TD-WLP-2).
`compaction.target_file_size_mb` is **refused at the door** (#2418 review
round 7): neither the consolidate trigger nor the FULL merge geometry reads
a per-collection value, so accepting it would be inert. Both read the
server `consolidate_target_file_size_mb` (default 512). See KNOWN GAP
below for what closing it takes.

PINNED TARGETS BOUND THE FOLLOW-UP CHAIN (final design, #2418 review
round 11). A per-request `target_segments > 1` sets a live-segment floor
(`SstCompactionTask.min_live_segments`) that every follow-up inherits. The
worker still runs the follow-up chain, including the layout/training
promotion, but `follow_up_input_cap` trims each follow-up to at most
`live - floor + 1` inputs (merging `g` inputs removes `g - 1` segments). At
the floor a plain merge is skipped, while a TRAINING follow-up still runs as
a single-input rewrite that trains without changing the count.

History: rounds 5-10 SUPPRESSED the follow-up instead (measured: without
any bound a target-2 request collapses to 1). That kept the target but left
outputs untrained (~180 GETs/104 MB per query vs 20-51 trained), could drop
a concurrent flush's training guard, and was then patched with a counter,
a WARN and a harness delta. Bounding the merge removes the cause, so the
counter and the harness delta are gone; the harness's trained-geometry gate
(every settled segment must carry a coarse A0 directory) remains the
refusal for an untrained arm.

Scope of "exact stop": the floor binds THIS request's chain. A flush-driven
background morsel from a concurrent WRITE can still merge below it. On a
settled bed — the case the override exists for — no such write arrives.

KNOWN GAP (open slice, found by the #2418 review round 3): the FULL
collapse's group-size target reads the SERVER
`consolidate_target_file_size_mb` directly
(`compaction.rs` `compact_collection_full`), and `CompactionParameters`
carries no properties, so a per-collection
`compaction.target_file_size_mb` does not reach the merge geometry. A
collection honouring it would compute a trigger target the merge cannot
reach and re-arm on every flush, which is why it is refused rather than
half-honoured. Closing it means plumbing the resolved target into the
compaction task alongside `full_target_segments`, then lifting the
refusal in the same change; until then operators wanting a specific merge
size must set the server value.

SERVER-DEFAULT VISIBILITY (history, superseded by TD-COMPACT-16):
rounds 5-8 built a server `consolidate_strategy` default and made
`FlushParameters.collection_properties` an `Option` so it applied only where
the catalog had been consulted. Background consolidate is now refused, so
that server layer and its decision function are gone; the `Option` carrier
stays as TD-COMPACT-16's prerequisite (F7).

Surfaces, AS SHIPPED:
* `COMPACT TABLE t [FULL]`, REST `POST /collections/{id}/compact` and the
  Flight `compact_collection` action, with optional `target_segments` — the
  live surface.
* `ALTER TABLE t SET (...)` / `CREATE TABLE ... WITH (...)` — validate
  `compaction.*`: `compaction.strategy = 'hybrid'` is accepted; `'consolidate'`
  and `compaction.target_file_size_mb` are REFUSED, each naming the reason.
* Collection tag `compaction.strategy:consolidate` — not validated at create;
  it runs hybrid with a once-per-collection WARN.
* REST `PATCH /collections/{id}/properties` and `POST /collections`
  `properties` persist nothing on this branch (stubs); #2419 makes both fail
  closed.
* Server TOML: `consolidate_target_file_size_mb` (read by the FULL merge's
  grouping; 0 fails boot); `consolidate_strategy = "consolidate"` fails boot;
  `consolidate_strategy = "hybrid"` and `consolidate_write_amp_limit` are
  accepted with a deprecation WARN (they shipped as settings in #2407, so
  refusing them would break upgrades).

NOTE: the legacy `[storage.compaction_config] strategy` field is the
count|size level heuristic (`compaction_utils.rs`). Since this PR it is
strictly validated (`count|size|hybrid`) — setting `consolidate` (or a
typo) aborts startup with an actionable message instead of silently
falling through the `_` arm to count/size (the dead-config hazard).

=== Interaction with COMPACT TABLE FULL

* FULL always works regardless of strategy (it's an operator override)
* FULL should use smallest-first (the fix applies to both paths)
* The consolidate strategy is FULL automated + policy-driven

== Considered and deferred

* **Per-level overrides** (`compaction.L1.target=2`): over-engineering;
  users shouldn't need LSM internals knowledge; the collection-level
  strategy + target captures the intent.
* **Runtime hot-reload**: restart-based config is fine for MVP; a
  hot-reload mechanism is a separate infrastructure concern.
* **Adaptive advisor**: the `CachePolicyAdvisor` seam (TD-COMPACT-2b)
  can eventually recommend the strategy from observed Q/W ratios; the
  seam exists, the implementation is future work.
* **Idle-time trigger**: for batch-loaded collections (write burst then
  read-heavy), a "compact after N seconds of write idle" trigger; defer
  until there's demand.

== Experiments

=== 1. S=1 collapse — MEASURED (2026-11-04T04:51-05:26 UTC; filed 2026-11-03 local)

The settled f32 bed (p5e-f32ev-build, 3M vectors, 2.60 GB, Region E +
cat3 filter, 1000 queries) measured as-settled (L1+L2+L5 = 3 segments)
versus collapsed to 1 segment via COMPACT FULL — same bed, same objects,
byte-identical rows/model/queries (harness `--skip-ingest` +
`--compact-full-before-measure`, which compacts through Arrow Flight
inside the harness and re-settles before measuring):

[cols="1,4,4,3,3", options="header"]
|===
| phase | metric | S=3 (settled) | S=1 (collapsed) | delta
| post_write | GETs/query | 53.47 | 18.31 | -65.8%
| post_write | $/M queries | 21.47 | 7.35 | -65.8%
| post_write | p50 | 458.30 ms | 147.14 ms | -67.9%
| local_disk_warm | GETs/query | 53.41 | 18.05 | -66.2%
| local_disk_warm | $/M queries | 21.44 | 7.26 | -66.1%
| object_cold | GETs/query | 61.32 | 45.63 | -25.6%
| object_cold | $/M queries | 24.58 | 18.29 | -25.6%
| all phases | recall@10 | 0.983-0.985 | 0.978-0.982 | -0.3..-0.5pp (gate >= 0.97 held)
|===

* The compact itself is byte-neutral: 2,604,342,955 -> 2,603,536,050
  bytes (-0.03%) for 3 -> 1 segments.
* Warm-path improvement (−66%) is larger than object-cold (−26%): cold
  runs still pay the centroid-directory/A0 loads, while the per-segment
  footer/probe overhead disappears entirely.
* One merged directory: cells/query 70.66 -> 21.00 (three per-segment
  directories become one).
* Recall dips 0.3-0.5pp — the known clustering-geometry effect of
  directory retraining at merge, within the f32-baseline tolerance.

Build-time corroboration (e1f beds, 2026-10-27, separate builds,
unfiltered): S=1 23.6 / S=2 41.7 / S=3 49.9 GETs/query object-cold —
the same shape from a different construction path.

Conclusion: **the segment count IS the dominant query-cost dial**; the
consolidate strategy automates exactly this collapse.

== Review follow-ups (#2418 round 7, deferred by decision)

The merge gate was set to "no correctness or mandate findings"
(2026-11-05). Round 7's correctness items were fixed in-PR: the inert
`compaction.target_file_size_mb` property is refused at the door; tag
opt-out visibility was tightened (later superseded by the round-8
`Option` carrier, see SERVER-DEFAULT VISIBILITY above); the harness measures
promotion suppression instead of inferring it from a CLI flag; a stated 0
for either consolidate knob fails boot; the suppression counter moves
only on a successful pass. Filed, not fixed:

* *COMPACT-15-F1 — `merge_section_over` covers only the three
  `consolidate_*` fields.* `full_target_segments`, `full_max_passes`,
  `full_timeout_ms`, `spill_enabled`, the thresholds etc. are still taken
  wholesale from an SST section, as before this TD. Closing it means
  making every `CompactionConfig` field `Option` (or merging from raw
  TOML).
* *COMPACT-15-F2 — the process-global `SHARED_COMPACTION_CONFIG` is a
  symptom fix.* The real defect is `FlushExecutionCoordinator::engine_for`
  building the flush engine with `SstEngine::new()` /
  `SstConfig::default()`, so its compaction manager also runs default
  budget/spill/FULL knobs, and the global is last-writer-wins across
  in-process `ProximaDB` instances. Build that engine from
  `effective_sst_config()` instead and delete the global.
* *COMPACT-15-F3 — catalog property clones.* `CatalogCollectionMeta`
  clones each collection's whole `schema.properties` (incl.
  `collection.config_json`, `stats.*`) on every catalog walk, including
  for callers that discard it, and `auto_flush_driver` does so twice per
  tick. Filter to the `compaction.`/`cache.` prefixes at construction.
* *COMPACT-15-F4 — REST/DDL copy `FullCompactionMetrics` field-by-field.*
  Flight serializes the struct; REST `CompactResponse` and DDL
  `CompactSummary` copy all nine fields by hand, so a new field silently
  misses two surfaces. Embed with `#[serde(flatten)]` / hold the struct.
