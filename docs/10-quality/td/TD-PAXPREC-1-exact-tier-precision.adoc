== Problem

Three facts, from a code trace on 2026-10-19:

* **Default PAX keeps no exact vectors.** Without a declared precision, a flushed segment holds
  only RaBitQ codes and the SQ8 rerank (`flush/mod.rs`:1360-1395, :1473-1476). Exact search and
  `include_vectors` read back lossy values, and the exact scan refuses such segments.
* **Declared fp16 is rounded, then widened back.** `canonical_embedding_precision=fp16` converts
  values before the WAL (`src/services/operations/vectors/legacy.rs`:1801-1827). The PAX writer
  then converts every vector back to f32 before encoding (`proximadb-block-format/src/record.rs`:336-344).
  The collection pays the precision loss and gets no on-disk saving.
* **An unknown precision value is silently dropped.** REST v2 maps an unrecognized
  `canonical_embedding_precision` to "not set" (`collections.rs`:686-703). The docs promise an
  fp32 fallback with a warning (`docs/05-concepts/embedding-precision.adoc`:93).

== Decision direction

* **Default exact tier = fp16**, stored in a cold Region C after Region D, so no ANN wave reads
  it. fp16 keeps an 11-bit significand (relative error ≤ 4.9e-4). That is near-lossless for
  normalized embeddings and halves rerank and rehydration bytes per query, the ADR-033 cost axis.
* **fp32 is opt-in**, via declared `fp32` precision or `pax_f32_tier`, for bit-exact round trips
  (audit, hashing, reproducibility).
* **A declared `fp16` is persisted as fp16** and never re-widened.
* **`lossy_ok`** keeps the RaBitQ+SQ8-only layout for collections that want no exact copy.
* **"Exact search" means exact over the stored precision.** Document it in
  `docs/05-concepts/embedding-precision.adoc`.
* **Ingest guards.** Vectors whose components exceed fp16 range (|x| > 65,504) route the
  collection to fp32 and are never clamped silently. Unknown precision values are rejected with
  a 400.

Market reference: fp32 is the common default copy. Half-precision storage is standard as an
option (pgvector `halfvec`, Milvus `FLOAT16_VECTOR`, Qdrant `float16`, turbopuffer and LanceDB),
usually as "full copy on cheap storage + compressed search tier".

== Acceptance

* E10 passes:
** recall@10 drops by ≤ 0.002 absolute and top-10 flips stay ≤ 1% versus the fp32 oracle, on
   SIFT1M, BIGANN 10M and a normalized 768d text set;
** rehydration MB/q falls by ≥ 45%.
* Then the default flips: a collection with no declared precision gets the fp16 Region C, and
  point reads and the exact scan are served from it.
* A declared-fp16 collection's segments carry fp16 bytes on disk (no f32 widening). A test pins
  the byte width.
* An unknown precision value returns HTTP 400, and the docs match.
* Mixed-read-safe: segments written before the change keep reading through the existing paths.
