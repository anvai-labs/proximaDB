= TD-PGPORTAL-1: the legacy pgwire reader ignores Execute's row limit

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-11-02).** Both symptoms fixed in `execute_portal_query`: (1) the legacy single-table reader's fetch is extracted into `legacy_relational_select_result` (fetch + ORDER BY sort, NO protocol output; the ABAC fail-closed gate and tenant scoping ride along — they are properties of the fetch), the portal branch materializes it into `PortalExecutionState` (mirroring the pipeline branch, including the TD-PGEXT-1 described-shape check) and serves `max_rows` pages ending in PortalSuspended; the simple protocol's `execute_relational_query` is now a slim sender over the same extractor, wire-identical for success paths. (2) The materialized-state paging check moved ABOVE the `max_rows > 0` gate, so `Execute(portal, 0)` after a suspension DRAINS the remainder (max_rows=0 is PostgreSQL's "no limit") instead of taking the non-paging branch and re-running the query. Scope: the Relational/Event stores this reader serves (dispatch-mirrored via `extract_table_name` + `detect_select_store_type`); other stores' portal queries keep the previous fall-through. Pinned by `execute_max_rows_pages_the_legacy_reader_e2e` (tests/pgwire_extended_relational_e2e.rs): raw-wire Parse/Bind + `Execute(1)` → exactly one DataRow + PortalSuspended (RED on develop: two rows + CommandComplete), then `Execute(0)` → exactly the one remaining row + CommandComplete — proving drain, not re-run. Known wire-order nuance: an ORDER BY resolution error now precedes RowDescription instead of following it (the fetch+sort moved ahead of the send) — more correct, and no test pinned the old order.
| Priority | **LOW** — clients that page with `Execute(max_rows)` get every row at once, and a second Execute re-runs the query.
| Component | `src/network/postgres/protocol.rs` (`execute_portal_query` → legacy single-table reader)
| Relates to | TD-PGEXT-1
|===

== Problem

On the extended protocol, a SELECT served by the legacy single-table reader returns all rows
plus CommandComplete even when Execute asks for `max_rows > 0`, instead of returning that many
rows and PortalSuspended; a second Execute on the portal runs the query again. The
relational-pipeline route suspends correctly, but after PortalSuspended an `Execute(portal, max_rows = 0)` takes the non-paging branch of `execute_portal_query` and re-runs the query, so the client receives duplicate rows instead of the remainder.

== Fix

Materialize the legacy reader's result into the portal's execution state, as the pipeline route
does, and serve it in `max_rows` pages with PortalSuspended. Test with an Execute(max_rows=1)
sequence over a raw-wire or JDBC fetch-size client.
