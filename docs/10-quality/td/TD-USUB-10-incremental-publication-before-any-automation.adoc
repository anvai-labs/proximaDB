= TD-USUB-10: Publication is a full-table overwrite bounded by memory — make it incremental before automating it

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **In progress.** Filed 2026-09-21 under ADR-094 Phase 4. **Slice 0 landed 2026-09-23** — manifest-driven file selection, the prerequisite without which the filed plan returns rows from multiple generations (see BLOCKER below). Slices 1–3 remain open.
| Priority | MEDIUM — a correctness-adjacent scaling limit, and a hard prerequisite for any automated publication policy.
| Component | `src/services/dml/mod.rs` (`materialize_table_to_parquet`), `crates/storage/proximadb-iceberg-engine/src/manifest.rs`
| Relates to | ADR-094 (Decision 1 rationale), ADR-062 (fresh-name + atomic manifest advance), TD-USUB-4 (additive layouts), TD-USUB-9

== The finding

`materialize_table_to_parquet` (`src/services/dml/mod.rs:1926`) is a **full overwrite**:

* it snapshots the table's *entire* current row set via `scan_table_relational` (`:1948`),
  materializing it in memory;
* it writes **one** object, `{prefix}/data/part-0.parquet` (`:2028-2031`);
* it then replaces the catalog layout wholesale (`:2052` — see TD-USUB-4).

Three consequences:

. **Republication is O(table), not O(delta).** Publishing a table that gained one row rewrites
  every row. Publication frequency × table size is the write-amplification curve.
. **It is bounded by memory.** The snapshot is resident, so the largest publishable table is
  capped by RAM, not by storage.
. **Single-object output** forecloses parallel scan and per-column-group pruning on the read
  side.

This is why ADR-094 **rejected** automated "publish a Parquet projection" as the
architecture: automating an O(table) rewrite would convert a manual, predictable cost into a
continuous background one, with the publication interval silently coupled to read cost
through the `snapshot_lsn` delta merge (`read_changes_since_scoped`, `:860`/`:872`).

== How to apply

. **Incremental publication.** Publish only rows changed since the layout's `snapshot_lsn`
  (already captured at `:1938` and persisted at `:2047-2048`) as *additional* objects.
. **Fresh-name + atomic manifest advance** — the mechanism ADR-062 already specifies, and the
  one `ManifestCommitter` (`crates/storage/proximadb-iceberg-engine/src/manifest.rs:89`,
  `commit_fenced` `:126`) already implements with optimistic concurrency. Never rename to
  commit: rename-commit is unsafe on S3, as ADR-045 records.
. **Multi-object layout** with per-object row ranges so scans parallelize and prune.
. **Streaming write** — do not materialize the whole table in memory.
. **Only then** consider an automated publication policy, and ship it **default-OFF** with an
  explicit publication-lag SLO, so staleness is a declared bound rather than an emergent
  property.

Retain `ALTER TABLE … MATERIALIZE` as an explicit user-invoked hint throughout; this TD
changes how publication *works*, not who triggers it.

== Inherited scope — the primary/landing layout marker (from TD-USUB-4)

TD-USUB-4 made publication **additive**, so a table *can* now hold more than one storage
layout. It deliberately did **not** model a designated **primary/landing** layout: with a
single layout the default is unambiguous, and inventing a primary marker before a second
representation existed would have been speculative design.

This TD is the first change that genuinely creates two representations for one table
(multi-object incremental publication alongside the landing format), so it inherits that
scope:

* Mark one layout as the **landing/primary** representation, so reads have a deterministic
  default when no cost signal is available — ADR-094 Decision 1 makes the landing format,
  chosen by modality, the natural primary.
* Teach the read predicates to prefer the primary rather than the **first match**, which is
  what `catalog_table_is_parquet_backed` (`.iter().find_map`) and
  `catalog_table_is_pax_backed` (`.iter().any`) do today.
* Keep `snapshot_lsn` per layout — TD-USUB-4 already carries it through the upsert — so a
  non-primary representation's staleness stays explicit.

Without this, *"which representation answers when the cost model has no sample?"* is decided
by list order: an accident rather than a decision.

== Evidence gate (mandate #6)

* Republication cost measured as a function of delta size, demonstrating O(delta) rather than
  O(table).
* Peak RSS during publication of a table larger than available RAM — the case that fails today.
* Atomicity test: a crash mid-publication leaves the previous manifest readable and no
  partially-visible rows.
* Concurrency test exercising `commit_fenced` under two racing publishers.
* If an automated policy is later enabled: publication lag measured against its declared SLO,
  and the read-side delta-merge cost attributed correctly in the cost model (TD-USUB-9).

== BLOCKER found 2026-09-23: the parquet read path globs, it does not read a manifest

**"How to apply" step 2 — "fresh-name + atomic manifest advance, the mechanism ADR-062
already specifies" — would produce WRONG ANSWERS as written.** That mechanism assumes readers
select data files from the manifest. On the live path they do not.

`ObjectStoreParquetTable::open_bridge_base`
(`src/datafusion/engine_adapters/object_store_parquet_reader.rs`) lists the location and takes
**every** object whose name ends in `.parquet` (immediate children, falling back to `data/`).
There is no manifest lookup anywhere in that path — no snapshot id, no file list, nothing.

Today that is correct *by accident of the very thing this TD wants to change*: publication
writes exactly ONE object at a FIXED name (`{prefix}/data/part-0.parquet`) and overwrites it,
so "every parquet object present" and "the current snapshot" are the same set.

Both halves of the plan break that identity:

* **Fresh-name publication** accumulates objects. The glob would union every historical
  generation — a query would see rows from several snapshots at once.
* **Multi-object output** breaks on re-publish: a later publication with fewer parts leaves
  the earlier `part-0000N` behind, and the glob unions the stale tail with the new set.

Neither failure is loud. Both return a plausible row set that is simply wrong, which is the
class mandate #1 exists to prevent — and note this is *more* dangerous than the single-object
overwrite it would replace.

=== Consequent prerequisite (new slice 0)

**Make the parquet read path select data files from the snapshot/manifest, falling back to the
glob when none is present (mixed-read-safe).** Only then can publication stop overwriting a
fixed name.

The manifest already exists on the write side: `publish_iceberg_table` emits Iceberg metadata
listing the data files. The reader simply ignores it. This also makes TD-USUB-9's new
`proximadb_warehouse_iceberg_publish_failures_total` counter **load-bearing** rather than
merely informational: once reads are manifest-driven, a failed publish is no longer an
interop-only concern, so the fallback path and the alert both matter.

Revised order: **slice 0** (manifest-driven file selection + glob fallback) → slice 1
(multi-object/streaming write) → slice 2 (incremental delta + atomic advance) → slice 3
(automated policy, default-OFF, with the publication-lag SLO).

Doing this TD in its filed order would ship a multi-generation read bug.

=== Slice 0 as landed (2026-09-23)

`ObjectStoreParquetTable::open_bridge_base` now tries `manifest_selected_files` first and
falls back to directory listing. Selection reads the snapshot via the bridge's existing
`latest_metadata_version` + `read_iceberg_snapshot`, which already returned the snapshot's
data-file keys — the reader simply never called them.

The bridge must be rooted at the **table base**, not the data directory: publication writes
parquet to `{base}/data/` and metadata to the SIBLING `{base}/metadata/`, so the manifest is
unreachable from the data dir. `table_base_of` derives the base only from a `…/data`
location, which is also what keeps external parquet directories (no manifest, no such shape)
on the listing path.

**Behaviour is unchanged today, by construction.** Publication still writes one object at a
fixed name, so the manifest lists exactly what listing would find. The fallback covers every
case where the manifest cannot be used — non-published layout, no metadata yet, unreadable or
empty snapshot — which is what makes this mixed-read-safe rather than a flag day. The value is
that fresh-name and multi-object publication become *expressible*: slices 1–2 can now change
what is written without the reader silently unioning generations.

**Evidence:** `manifest_selection_excludes_a_parquet_not_in_the_snapshot` publishes a real
snapshot while only `part-0.parquet` exists, then adds an unreferenced `part-9-stale.parquet`
and asserts the table opens with 2 splits, not 4 — listing would have unioned it.
`without_a_manifest_selection_falls_back_to_listing` pins the fallback (4 splits).
`table_base_is_derived_only_from_a_data_location` pins the shape guard.

**Interaction with TD-USUB-9:** this makes
`proximadb_warehouse_iceberg_publish_failures_total` load-bearing. A failed publish now means
a stale-or-absent manifest, and reads either fall back to listing (absent) or serve the prior
snapshot (stale) — so the counter USUB-9 added is the signal that the two have diverged.

=== P2.4 slice 1: readers fail closed (2026-10-22)

Slice 0's fallback listed the directory on *any* manifest failure, including an unreadable
`metadata.json`. That was safe only while publication wrote one fixed-name object. Multi-part,
generation-named publication (P2.4, tracker §5.3) leaves several generations in `data/`, and
listing them would serve rows from several snapshots at once. The selection now fails closed:

* `manifest_selected_files` returns `Ok(None)`, which means list the directory, **only when no
  metadata log exists**. That covers a non-published layout, or a table published before
  Iceberg metadata existed.
* Once a `v*.metadata.json` exists, an unreadable log, or a snapshot that names no parquet
  files, is an `Err` and the table open fails.
* The DuckDB engine registers each view as `read_parquet([...])` over the same manifest
  selection (`manifest_selected_uris`) instead of the directory. Both engines therefore read
  one generation, and an unreadable log fails the DuckDB query too. The `duckdb` feature now
  enables `datafusion-integration`, which owns the shared selection.

**Evidence:** `unreadable_manifest_fails_closed` garbles the only `metadata.json` beside a stale
part, then asserts that the open and `manifest_selected_uris` both error.
`view_reads_manifest_files_only` (feature `duckdb`) asserts that the DuckDB view returns the
snapshot's 4 rows, not 8. `without_a_manifest_selection_falls_back_to_listing` still pins the
no-metadata case.
=== P2.4 slice 2: publish an explicit file list (2026-10-22)

`publish_iceberg_snapshot` built the manifest by *listing* the data prefix, so it could not
publish one generation out of several. `ObjectStoreBridge::publish_iceberg_files(files,
parent, …)` publishes exactly the named files as the successor of metadata version `parent`:

* the Avro manifest and manifest list are named by the metadata version they commit under
  (`v{N:020}-{snapshot}-m0.avro`, `snap-{snapshot}-v{N:020}-list.avro`) and written
  `put_if_absent`, so a racing publisher cannot overwrite the winner's manifest;
* losing the slot is `Err(StorageError::AlreadyExists)`. The old MATERIALIZE caller treated
  `CommitOutcome::Conflict` as success;
* a named file whose footer cannot be read fails the publish, where a listed file used to
  degrade to count 0.

MATERIALIZE publishes its file through this API. Evidence:
`publish_iceberg_files_publishes_only_the_named_generation`,
`publish_iceberg_files_on_a_stale_parent_is_an_error`,
`publish_iceberg_files_requires_readable_footers`.

=== P2.4 slice 4: bounded, oid-ordered chunked scan (2026-10-22)

The MATERIALIZE input no longer has to be the whole table at once. `RecordScan::scan_record_chunks` yields a store's live records in strictly ascending oid order, in bounded chunks:

* `SpillRecordStorage` k-way merges its oid-sorted segments under the resident rows of `view()`. It decodes one row-group batch per segment through `FileSystemParquetReader`.
* `MemtableRecordStorage` serves a snapshot of its keys.

`TableRecordStore::scan_records_chunked` adds table membership and the primary-over-legacy merge. `DmlService::scan_table_records_chunked` adds the governed-read prelude.

Evidence: `chunked_scan_equals_the_merged_scan` builds several segments, updates, persisted and in-memory deletes, a re-insert and resident rows. It asserts strictly ascending oids, the chunk bound, and equality with `scan_records`.

=== P2.4 slice 2a: published files carry a hidden row key (2026-10-24)

Incremental append (slice 2b) must tell an insert from an update by probing what is already
published, so every published file now carries each row's oid as a hidden LAST column,
`__proxima_oid` (Utf8, non-null).

* It is always Bloom-filtered unless it leads the sort (`ParquetWritePolicy::bloom_columns`; spill
  segments, sorted by oid, are unchanged), subject to the policy's `min_rows` and enable flags.
* It is not in the Iceberg schema. Every column carries a `PARQUET:field_id` (PyIceberg treats a
  file with any id-less column as id-less and falls back to name mapping, which rejects an
  unknown column): table columns keep `1..N`, system columns take `SYSTEM_FIELD_ID_BASE`
  (2,000,000,000) and up, below Iceberg's reserved metadata range.
* Readers hide it. DataFusion drops `__proxima_*` columns from its planning schema and resolves
  each requested column to the file's column by name; the DuckDB view selects
  `COLUMNS(lambda c: NOT starts_with(c, '__proxima_'))` with `union_by_name`. Catalog validation
  already rejects user columns with that prefix.
* Being last keeps every table column at the same position in files written before and after
  the change. The semi-join Bloom lookup and the native route still index file columns by the
  table's position, so a snapshot must not mix files of different widths; every publication
  today is a full rewrite, and slice 2b appends only to files whose columns match exactly.

Gate: `published_files_carry_a_hidden_oid_column` (last column, oids aligned with their rows
through the cluster sort, field ids `[1, 2, 3, 2000000000]`, `SELECT *` without it).

=== P2.4 slice 2b: insert-only incremental append (2026-10-24)

A republication no longer always rewrites the table. It reads the oids written since the
published layout's `snapshot_lsn` from the route's change feed and classifies them against the
published files' hidden oid column (per row group: min/max statistics, then the Bloom filter):

* No changed oid: nothing is published (no new metadata version); the layout's `snapshot_lsn`
  advances under the publication fence.
* Every changed oid provably absent from the published files: their current rows are written as
  extra parts and the snapshot is the carried files plus the new parts; GC keeps the carried
  files. A changed oid with no current row (inserted and deleted in between) writes nothing.
* Otherwise a full rewrite, as before. The probe has no false negatives, so an update or delete
  of a published row always rewrites; a Bloom false positive only costs a rewrite.

An append is attempted only when it is provably sound, and rewrites otherwise:

* the store has a WAL change feed for the table's route (`TableRecordStore::has_change_feed`,
  which for the WAL-backed store is its appender's `has_readable_log`); an empty answer from a
  store without one proves nothing;
* the layout is at the location being published and its `snapshot_lsn` is not newer than the
  one this run captured;
* every carried file has exactly the columns this publication writes (a schema change since the
  last publication rewrites), carries the oid column (files from before slice 2a rewrite) and
  has oid statistics in every row group;
* the change feed is read under the keys the writes use (`wal_collection_id`: the table's name
  and, under `PROXIMADB_WAL_OBJECT_ID_KEY`, its `object_id`), taken from the table's own schema,
  never by re-resolving its bare name (which would look in `default` and miss every
  object_id-keyed write of a table elsewhere);
* the snapshot holds fewer than `APPEND_MAX_FILES` (64) files, so parts stay compacted and the
  probe, which reads every part's footer, stays bounded;
* the delta is at most `PROXIMADB_MATERIALIZE_APPEND_MAX_ROWS` rows (default 1,000,000, the rows
  held in memory while written; `0`/`off` disables append).

Accepted limits, each cleared by the next full rewrite:

* rows that expired by TTL stay in carried files;
* NDV statistics are not republished on an append;
* carried files are re-listed as added in each snapshot (an Iceberg `overwrite`), so
  `added-files`/`added-records` count them and v3 row ids are reassigned on every append.

An unchanged republication advances `snapshot_lsn` only on the layout it planned against (same
metadata version), so it never relabels a newer publication.

Gates: `an_insert_only_republication_appends_and_an_update_rewrites` (unchanged run publishes no
metadata version; insert-only carries the file and appends a part holding only the new rows; an
in-range new oid still appends; insert-then-delete publishes nothing; an update or a delete of a
published row rewrites; counts and sums correct throughout),
`an_update_under_object_id_keying_outside_default_rewrites` and
`classification_appends_only_rows_no_published_file_can_hold`.

=== P2.4 slice 3a: deletion vectors in the Iceberg engine (2026-10-25)

Slice 3 lets a republication delete published rows instead of rewriting the table. Published
tables are format v3, so the mechanism is the v3 **deletion vector** (a Puffin blob of deleted
row positions per data file), not v2 position-delete files, which v3 writers may no longer add.
It lands in three PRs, readers before the writer, so no reader ever meets a delete it ignores:
3a (this: format and engine), 3b (the DataFusion and DuckDB readers apply vectors), 3c
(MATERIALIZE writes vectors for updates and deletes).

* `deletion_vector`: a data file's deleted positions in the portable 64-bit Roaring encoding,
  inside the spec's `deletion-vector-v1` framing (big-endian length, magic `D1 D3 39 64`,
  CRC-32). The encoding is pinned byte for byte against CRoaring (`pyroaring` golden vectors);
  decoding also accepts run containers and the run cookie, which other writers emit, and
  checks every container against its declared cardinality (ascending arrays, ascending
  non-overlapping runs), so a hostile vector costs at most one pass per container. In memory
  each 2^16-position container is a sorted array or a bitmap built in bulk (the in-repo
  `RoaringBitmap` re-optimizes on every insert and serializes to a private layout).
* `puffin`: the Puffin file (`PFA1` magic, JSON footer) holding one vector per data file, each
  blob over `_pos` (field id 2147483645) with the `referenced-data-file` and `cardinality`
  properties. Compressed footers are rejected.
* Delete manifests (`iceberg::write_delete_manifest`): content `deletes`, entries
  POSITION_DELETES / PUFFIN with `referenced_data_file`, `content_offset`,
  `content_size_in_bytes` (field ids 143–145), inheriting the snapshot's sequence number. The
  manifest list now records each manifest's `content`. Reading back accepts only deletion
  vectors: an equality delete or a v2 position-delete file is an error (fail closed).
* The bridge: `write_deletion_vectors` (Puffin, create-only),
  `publish_iceberg_files_with_deletes` (v3 only; every vector names a data file of the same
  snapshot; at most one per file), `read_iceberg_snapshot_with_deletes` (checks both again) and
  `read_deletion_vector` (a ranged read of one blob, checked against its manifest cardinality).
* `read_iceberg_snapshot` / `read_iceberg_table` now **refuse** a snapshot that has deletion
  vectors. Every reader goes through them, and the DataFusion and DuckDB routes fail closed on
  that error, so until 3b no route can return a deleted row. Nothing writes vectors before 3c.

Interop check (manual, not in CI): a snapshot written by `publish_iceberg_files_with_deletes`
scans correctly in PyIceberg 0.12 (deleted positions dropped). DuckDB 1.5.6 could not be checked
in the sandbox (its extension download is blocked); 3c extends the CI read-back gate, which
installs both readers, to tables with deletion vectors.

Gates: the `deletion_vector`, `puffin`, `iceberg::deletes` and `snapshot_deletes` unit tests
(round trips, CRoaring byte equality, damaged blobs, invalid publishes refused, data-only reads
refused).
