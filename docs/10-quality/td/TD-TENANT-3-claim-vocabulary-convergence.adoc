== History (shipped)

Outcome targeted: **a tenant claim means exactly one thing, no matter which port it arrives on.** The
premise that REST and gRPC read different header names was false (`HeaderMap` keys are
case-insensitive; HTTP/2 mandates lowercase) and the decision layer was already shared
(`resolve_tenant_assertion`, `resolve_request_identity`, `resolve_tier_claim`); the defects were in the
per-surface **vocabulary** read before those primitives:

* **D1** — Flight accepted four tenant spellings that REST/gRPC silently ignored ("same request, two
  answers", worse than a 403 because nothing is observable). **S1** moved the names into one
  foundation vocabulary module with a lookup generic over `Fn(&str) -> Option<&str>` (no transport
  types leak into foundation). Convergence direction **narrow, do not widen**; the canonical name now
  wins on Flight (the only behavior change, recorded by inverting/renaming the precedence test).
* **D2** — Flight had no tier-claim surface (the highest cache-pressure surface ran at default tier).
  **S2** mirrors the gRPC gate exactly.
* **D3** — `set_tenant_tier` stored the raw claim; three consumers matched it literally against
  `cache_tiers.json` while one used alias-aware `Tier::from_claim`, so `pro` and `tier3` landed in
  different cache buckets. **S3** normalizes at the stamp, stores canonical + raw, and the cache
  resolver probes canonical then raw (operator alias-keyed configs keep working; garbage claims resolve
  to the default tier). `proximadb-cache` stays a dependency-free leaf.

Co-design framing that still applies: the tier claim is the only per-tenant input to cache
floor/ceiling/weight, so a missed bucket becomes extra object-store GETs (Dimension 1 via 3 and 5).
Non-goals: pgwire `database`-as-tenant (protocol-forced); renaming `proximadb_tier` (PG grammar forbids
`-`); hot reload of tier config (`OnceLock`, restart-required by design).

== S4 — open follow-ups

. Flight alias retirement — **honoring REMOVED 2026-08-29** (S4 item 1,
  evidence-closed early): the aliases no longer grant a tenant on any surface;
  presence is still detected (warn once per process + the
  `proximadb_deprecated_claim_uses_total` counter, now counting attempts).
  Residual for the next release boundary, then delete: the

  accumulated (no release shipped since it landed); honoring-removal had to
  precede that release regardless.

[NOTE]
====
**Retirement gate made measurable (2026-08-27).** "Warning silent" was
originally a log observation — but the warn fires **once per process**, so a
long-lived pod goes log-silent while clients keep using an alias every second,
and "quiet logs" would falsely read as "clients migrated". Every use now
increments the cumulative counter
`proximadb_deprecated_claim_uses_total{surface,name}` (per use, not per
process; the warn stays once-per-process to avoid log spam). **The gate is a
query: retire when `increase(proximadb_deprecated_claim_uses_total[7d]) == 0`**
on the serving fleet, evaluated across a release boundary. The same change
added `proximadb_tier_claims_dropped_total{surface,reason}` so ADR-0053 W8
drops (previously warn-once-per-tenant, invisible in aggregate — and fully
silent on pgwire) are countable per surface and rejection reason.
