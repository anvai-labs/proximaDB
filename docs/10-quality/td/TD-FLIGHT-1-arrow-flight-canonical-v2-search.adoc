== History

Flight search ran the v1 contract while REST/gRPC ran v2, and diverged four ways: the encoder kept only the first props key; it
skipped v2's `validate_tenant_collection_access` and the dead-record predicate; `bulk_search` hard-coded `top_k:10` and swallowed
errors; and the DoGet JSON ticket's keys never matched the Python SDK's, so **the query vector was silently dropped and Flight search
was effectively non-functional**. The structural blocker was that Flight held a write-only `RecordOpsPort`, while the v2 DTOs were
root-internal.

* Decision: converge on one search authority through a dedicated read port (`RecordSearchPort`, separate from the write port and
  implemented by the same `RecordOpsService`). The DTOs and `PredicateShortfall` were relocated behind `pub use` shims, following
  the TD-104 `rich_record` pattern.
* The v2 `FlightSearchTicket` (`"type":"vector_search"`) is a clean break: unknown tickets return `InvalidArgument`. Props travel
  as a JSON `properties` column. The io_trace route is `arrow_flight.v2.records.search`.
* Follow-ups: dead `api_port` removed (#1355); a `bulk_search` order-preservation e2e (#1356); a Flight-vs-REST harness asserting
  identical ordered ids, and therefore the same GETs and recall (#1358); `TenantStableIdResolver` wired (#1361).
* **Evidence:** `tests/flight_v2_search_e2e.rs`, `tests/flight_bulk_search_e2e.rs`, `tests/flight_v2_bench.rs`. No Flight-vs-REST
  latency/wire-bytes number is in `BENCHMARK_EVIDENCE.toml`, so do not cite a Flight speedup.
