|Priority|MED

== History

*Part A (perf).* The #634 c16 collapse on all-distinct Strong vector queries was an **allocator/memory-bandwidth**
signature, not shared retrieval. Fix A: `get_unflushed_batches` discarded and *rebuilt* each batch's bloom on every
read; it now clones the existing bloom. Fix B: `search_unflushed_vectors` built a full record + metadata clone for
all N tail records then truncated to top_k (~99.7% discarded); it now keeps `(score, batch_idx, record_idx)` tuples
and materializes only the survivors (tombstones stay exempt from the cut, TD-188).

Decision that still applies: **D3 (shared per-(collection, lsn) WAL-tail pool) is not needed** — it shares
retrieval, which was never the bottleneck. Re-measured on the `-full` image: x86 QPS 23→115, concurrent p99
1146→279 ms; arm QPS 35→192, p99 765→121 ms; the residual is CPU queueing on 2 vCPU.

*Part B (correctness, #649).* `unified_search` is reachable from the RAG engine, so a Strong read *could* reach an
ungated cache. Three `get_if_fresh` read sites (`unified_search_with_tenant_context`, `unified_search_with_hints`,
`execute_search_internal`) now serve cached entries only for `StaleOk`/`BoundedStale`; Strong recomputes (mandate
#16c). LSN-pinned caching of these secondary paths remains a possible perf follow-up, not a correctness need.

Evidence: `vector_ann_recall_e2e` + `filtered_ann_recall_bands`; `strong_read_bypasses_query_cache_on_tenant_context_path`;
anvaiops `tests/load/results/2026-07-04-arm-vs-x86-postfix/`.
