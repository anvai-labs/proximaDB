= TD-TENANT-1: credential-bound tenant identity — X-Tenant-ID header-trust policy
:icons: font

**Status:** Phase 2 shipped; follow-up (a) is **partially closed 2026-08-30**:
legacy config-backed API keys can now carry delegation-only gateway roles, while
ADR-090 registry-backed API keys, SSO, and mTLS role stamping remain open.
Follow-up (b) is re-scoped below as its own future TD (pgwire SCRAM bindings).
**Origin:** anvaiops live-UAT debugging (issues #949/#950, PR #956) — the fix
review raised the question: the engine honors a bare `X-Tenant-ID` header, so
any client that can reach the port can masquerade as any tenant unless a
well-behaved gateway fronts the engine. A tenant-isolation guarantee that
depends on network topology is a topology assumption, not a guarantee.

== Decision

Open-core split follows the cache-tier precedent: **mechanism in OSS, policy in
the control plane.** ProximaDB enforces *that* tenant identity is
credential-bound; the commercial layer (AnvaiOps) owns *which* tenants exist,
credential→tenant mapping UX, provisioning, and entitlements. No enforcement
lives outside the engine.

== Phase 1 (shipped with this TD)

`HeaderTrustPolicy` on `TenantExtractorConfig`
(`src/network/middleware/tenant.rs`), governing the **bare** header — a request
asserting a tenant with no authenticated binding (no JWT claim / API-key
mapping). When a binding exists, header≠binding is already rejected with 403
in every mode (pre-existing behavior, now audit-logged).

|===
| Mode | Bare header | Gateway delegation

| `open` (default; `Default`/`single_tenant` presets)
| accepted verbatim
| n/a (header==identity)

| `authenticated-only` (default for the `multi_tenant()` strict preset)
| 403 + `proximadb::tenant_audit` warn
| no — header must equal the credential's tenant

| `gateway-only`
| 403 + audit warn
| yes — an authenticated principal whose bound tenant is in `system_tenants`
  may set `X-Tenant-ID` to act on behalf of that tenant (delegation is
  audit-logged)
|===

Env override at server construction (never in constructors — tests stay
hermetic): `PROXIMADB_TENANT_HEADER_TRUST=open|authenticated-only|gateway-only`.
An unparseable value tightens to `authenticated-only` (fail-closed) rather than
silently running `open`. Unset ⇒ config value; default-safe, no flag-day.

== Phase 2 (shipped) — the follow-ups

1. **[DONE] One shared primitive, every surface.** The policy logic moved to
   the foundation crate: `proximadb_tenant::identity_trust::resolve_tenant_assertion`
   (pure; truth-table tested). All four surfaces call it:
   * REST middleware (`src/network/middleware/tenant.rs`) — delegates and maps
     onto `TenantIdSource` + 403.
   * gRPC auth layer (`src/network/grpc/auth.rs`) — resolves once per request,
     stores the verdict in `GrpcAuthContext::resolved_tenant`, rejects with
     `PERMISSION_DENIED`. This CLOSED a pre-existing gap: a non-capability
     credential's mismatched `x-tenant-id` used to be silently ignored.
   * Arrow Flight (`src/network/arrow_ipc/service.rs`) — replaces the
     hand-rolled mismatch match; also applies the policy when no
     SecurityCoordinator is wired (bare-by-definition assertions).
   * pgwire (`src/network/postgres/{mod,protocol}.rs`) — trust auth means
     every assertion is bare; enforced at the TWO assertion entry points:
     startup `database` (FATAL 28000 at handshake) and
     `SET proximadb.write.tenant_id` (ERROR 28000). The ~15 downstream
     resolve call sites are untouched — assertions are gated at entry.
2. **[DONE] config.toml surface.** `[security.tenant] header_trust` on
   `SecurityConfig` (serde kebab-case enum). Effective policy resolved ONCE in
   `database.rs` via `HeaderTrustPolicy::effective` (env > config > mode
   preset; unparseable env tightens to `authenticated-only`) and threaded
   through `MultiServer::with_tenant_header_trust` into every surface.
3. **[DONE] Stable-id resolution at the boundary (ADR-031/ADR-087).** The port
   (`proximadb_tenant::TenantStableIdResolver`) + carry
   (`MiddlewareTenantContext::tenant_stable_id`, stamped when a resolver is
   wired via `TenantExtractor::with_stable_id_resolver`) shipped. REMAINING:
   production resolver and both production mint authorities are wired. The
   WAL-backed `SystemCatalog` persists the mapping as a canonical catalog delta
   and snapshot state; `NativeCatalog` persists its account-registry sidecar.
   Bootstrap mints `default`, and ABAC provisioning mints any new tenant before
   its first policy write. The string `tenant_id` stays authoritative; the
   stable id is a derived policy/path key, never a second source of truth.
4. **[DONE] Gateway principal marker.** First-class
   `UnifiedUserContext::is_gateway_principal()` (a `gateway`/`operator` role
   or `gateway: "true"` metadata, stamped from credential data). The REST
   middleware keeps `system_tenants` membership as a compat fallback; the
   gRPC/Flight surfaces use the marker only (the desired end state).

== Follow-ups (still open)

* Credential-side stamping of the gateway role beyond JWTs — **legacy
  config-backed API keys: CLOSED 2026-08-30** (`ApiKeyInfo.roles`,
  `#[serde(default)]`; exact-match
  `gateway`/`operator` only — a typo grants nothing; grants NO
  `UnifiedPermission`, delegation-only). **Adversarial review 2026-08-31
  found and structurally closed an escalation**: arbitrary role pass-through
  would have satisfied `SecurityPredicate::RoleBased` RLS predicates
  (unrestricted row access on role-string match) — the conversion now passes
  ONLY the two delegation markers and drops every other configured role with
  a warn; pinned by `apikey_business_roles_are_dropped_not_passed_through`.
  **ADR-090 registry-backed `pxk_` API keys remain open:** that namespace is
  registry-authoritative and currently resolves principals with only
  `api_user`; adding roles requires an explicit registry role-provisioning
  authority, not inheritance from legacy config. **SSO/mTLS: half closed** —
  generic OIDC bearer (with the same seam sanitization for IdP role claims) is
  TD-SSO-1 (2026-09-01); the aws/azure enterprise SSO variants and mTLS role
  stamping remain open, and TD-SSO-1 carries the seam pattern for them.
* pgwire authenticated bindings — **re-scoped 2026-08-30 as its own future
  TD**, not a follow-up patch: it requires SCRAM/password wire-protocol
  authentication (a protocol-level work item). Until then, strict policies
  legitimately disable tenant selection over pgwire.
