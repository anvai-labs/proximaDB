== History (shipped)

Origin: anvaiops live-UAT (#949/#950, #956) — the engine honored a bare `X-Tenant-ID`, so tenant
isolation depended on a well-behaved gateway: a topology assumption, not a guarantee. **Decision
(still binding): mechanism in OSS, policy in the control plane** — the engine enforces *that* tenant
identity is credential-bound; AnvaiOps owns which tenants exist and the credential→tenant UX.

Phase 1: `HeaderTrustPolicy` governs the *bare* header (no authenticated binding) —
`open` (default; accepted verbatim), `authenticated-only` (strict preset; 403 + `tenant_audit`),
`gateway-only` (403, except an authenticated principal bound to a `system_tenants` tenant may delegate,
audit-logged); header≠binding is rejected in every mode. Env `PROXIMADB_TENANT_HEADER_TRUST`; an
unparseable value tightens to `authenticated-only` rather than running `open`.

Phase 2: the pure `resolve_tenant_assertion` primitive is called by REST, gRPC (closing a gap where a
mismatched `x-tenant-id` was silently ignored), Arrow Flight, and pgwire (gated at the two assertion
entry points: startup `database`, FATAL 28000; `SET proximadb.write.tenant_id`, ERROR 28000);
`[security.tenant] header_trust` resolved once (env > config > preset); `TenantStableIdResolver` port
wired with both production mint authorities (`SystemCatalog` WAL delta + snapshot, `NativeCatalog`
sidecar; bootstrap mints `default`) — the string `tenant_id` stays authoritative, the stable id is a
derived key; `UnifiedUserContext::is_gateway_principal()` marker (gRPC/Flight use it only; REST keeps
`system_tenants` as compat fallback).

== Follow-ups (still open)

NOTE (status re-verified 2026-10-15): `pxk_` registry keys still resolve with only `api_user`
(`src/security/auth_service.rs`); the aws/azure enterprise SSO variants were since **deleted as dead
code** (TD-SSO-3, b734d5dc4), so that half of the SSO residual is retired rather than implemented, and
**mTLS role stamping remains open**; pgwire SCRAM authentication with tenant-bound verifiers shipped as
TD-PGWIRE-AUTH-1 (2ef6cb577), but TD-AUTH-FC still requires authenticated deployments to disable
pgwire pending full pgwire authn/authz conformance. The original text is kept verbatim below.

* Credential-side stamping of the gateway role beyond JWTs — **legacy
  config-backed API keys: CLOSED 2026-08-30** (`ApiKeyInfo.roles`,
  `#[serde(default)]`; exact-match
  `gateway`/`operator` only — a typo grants nothing; grants NO
  `UnifiedPermission`, delegation-only). **Adversarial review 2026-08-31
  found and structurally closed an escalation**: arbitrary role pass-through
  would have satisfied `SecurityPredicate::RoleBased` RLS predicates
  (unrestricted row access on role-string match) — the conversion now passes
  ONLY the two delegation markers and drops every other configured role with
  a warn; pinned by `apikey_business_roles_are_dropped_not_passed_through`.
  **ADR-090 registry-backed `pxk_` API keys remain open:** that namespace is
  registry-authoritative and currently resolves principals with only
  `api_user`; adding roles requires an explicit registry role-provisioning
  authority, not inheritance from legacy config. **SSO/mTLS: half closed** —
  generic OIDC bearer (with the same seam sanitization for IdP role claims) is
  TD-SSO-1 (2026-09-01); the aws/azure enterprise SSO variants and mTLS role
  stamping remain open, and TD-SSO-1 carries the seam pattern for them.
* pgwire authenticated bindings — **re-scoped 2026-08-30 as its own future
  TD**, not a follow-up patch: it requires SCRAM/password wire-protocol
  authentication (a protocol-level work item). Until then, strict policies
  legitimately disable tenant selection over pgwire.
