== History

Question: does ProximaDB need a Lakebase/Neon-style SafeKeeper (Paxos quorum of local-disk nodes replicating
the WAL)? No. The object-store-backed WAL already gives stateless compute + durability + non-lossy restart:
the cloud `put` is awaited before the commit ack, and restart replays via `RecoveryMode::ViaMemtable`.
A quorum buys **only per-tx commit latency** (single-digit ms vs tens-to-hundreds of ms for a PUT), not
durability; for batch ingestion, per-batch PUT amortization makes that moot (Milvus, Pinecone, Vectorize
all use WAL + object storage). Research: `wf_93aa09c8-12b` (24/25 claims verified).

Deferred question (not work): **multi-AZ durability at commit.** S3 Standard is multi-AZ; S3 Express One Zone
is single-AZ. If multi-AZ-at-commit or sub-ms per-tx commits are ever required, the options are cross-region S3
replication of the WAL, a lightweight quorum on the object-store seam, or single-AZ + async cross-region.
References: Neon architecture + SafeKeeper protocol; Aurora 4-of-6 quorum; arXiv 2603.02108 (Milliscale); Vanlightly, replication vs S3 Express One Zone.
