= TD-SCANDEG-1: The adaptive concurrency back-offs were each dead on one search entry
:status: Accepted
:date: 2026-11-06
:tags: [search, concurrency, cpu]

== Problem

Two adaptive back-offs, each wired on only one of the two segment-scan
entries (legacy `direct_search_with` / production arc
`direct_search_arc_with`):

* **Morsel degree (intra-file rank).** `morsel_degree()` returns `cores` when
  `INFLIGHT_SCANS == 1`, else 1 — "a lone query uses every core; concurrent
  queries rank sequentially". The only `ScanGuard::enter()` was on the
  LEGACY path; the production arc path never took it, so `INFLIGHT_SCANS`
  stayed 0, `.max(1)` made it 1, and the degree was ALWAYS `cores`: at client
  concurrency c, every query spawned its own all-core rank.
* **Inter-file degree (S2b).** The mirror image: `InFlightSearchGuard` was
  acquired only on the ARC entry, so legacy-entry traffic never divided
  `resolve_search_parallelism` by concurrency.

== Decision

Both entries take both guards. On the arc path the `ScanGuard` is shared
(`Arc`) into every spawned per-file task, so the count lives until the LAST
task ends: a cancelled or early-returning parent cannot decrement while its
orphaned spawns keep ranking. By design, a deferred-retry attempt that starts
while attempt 1's orphans still rank therefore sees itself as not alone —
correct, since those orphans are using the cores.

Both fixes are mutation-verified: removing the arc guard fails
`arc_direct_search_counts_itself_in_inflight_scans`, which also proves that
test routes through the arc path.

== Scope / follow-ups

* The guards count in-flight QUERIES; they restore the cross-query back-off
  but do not bound workers WITHIN one query — TD-SCANDEG-2.
* The peek·discard·re-read defect originally bundled here was descoped —
  TD-SCANDEG-3.
