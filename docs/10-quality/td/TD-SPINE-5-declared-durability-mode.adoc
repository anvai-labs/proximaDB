*Amended 2026-11-25 (review round 1):* three corrections. (1) **Embedded scope:** the
default-root move applies to the SERVER path only — embedded bindings construct
`SharedServices` directly (no `ProximaDB::new`), so `data_dir=None` and WAL placement
keeps the legacy co-located form; internally consistent (write+replay agree), but identical
config files yield different WAL roots on server vs embedded — pinned as a known difference,
to be unified if embedded adopts `ProximaDB::new`. (2) **Mixed-shape callout (reasoned):**
`storage_locations = [s3://…]` with a default/local `write_buffer_directory` infers
`local_volume` from the LOCAL buffer dir (the ladder's input is the pre-overwrite
`data_directories[0]`), flipping WAL placement from the catalog's s3 assignment to
`{data_dir}/wal` — recovery-safe (the catalog base is still scanned; legacy files are
replayed then deleted) but an availability posture flip for ephemeral-disk serverless
deployments; such deployments MUST declare `durability_mode = "object_store_serverless"`.
(3) **Record root:** the durable_locations entry folds the env root into its effective root
(env>TOML>default, matching the engine) and materializes the local default `{data_dir}/wal`
at record time so symlinked-host cold backups canonicalize both sides identically.

== Problem

* `wal_local_dir` is opt-in. When unset, the WAL follows the catalog `base_location` or
  `data_directories[0]`, either of which may be object storage — the ADR-063 serverless posture,
  which `apps/proximadb-server/tests/object_store_restart_recovery.rs` depends on.
* Which contract applies is therefore decided by a default, is not logged, and is not recorded in
  `durable_locations`.

== Fix (owner decision: infer and log, no boot break)

. Add `durability_mode = "local_volume" | "object_store_serverless"` to `[storage.wal_config]`, with
  a mirror env gate registered in `ENV_GATE_REGISTRY.adoc` (naming per the registry rules).
. Resolution at boot (ADR-098 D3): declared wins; otherwise infer from one deterministic input,
  the global `wal_local_dir` if set (⇒ `local_volume`), else the scheme of `write_buffer_directory`
  (else `data_directories[0]`). Local path ⇒ `local_volume`, with `wal_local_dir` defaulting to
  `{data_dir}/wal` for every collection. Object URL ⇒ `object_store_serverless`, with per-collection
  WAL under the catalog-derived base location (`resolve_collection_base_location`,
  `write_ahead_log/mod.rs:1704`). Log the resolved mode and reason at INFO; record it in
  `durable_locations`.
. `local_volume` default root move: recovery also scans the legacy co-located WAL root so an upgrade
  never strands unflushed WAL objects.
. Replace the `write_buffer_directory`-only warning with the resolution above.
. `object_store_restart_recovery.rs` declares `object_store_serverless` explicitly.

== Acceptance

* Per-mode ratchet: the resolved WAL root's scheme matches the mode.
* Upgrade test: a WAL written at the legacy co-located root replays after the default moves.
* `wal_fsync_crash_recovery.rs`, `cold_backup_restore.rs` and `object_store_restart_recovery.rs`
  green; boot log names the mode in each.
* Coordinated with the TD-SEAM-14 owner so spill placement resolves to one of the two modes.

== Implementation notes (2026-11-24)

* **Config.** `[storage.wal_config].durability_mode = "local_volume" |
  "object_store_serverless"` (serde-exact spellings; an unknown DECLARED value
  fails the config load — fail-fast applies only to the declared key, never to
  an existing config). Env mirror `PROXIMADB_WAL_DURABILITY_MODE`
  (registry row: tier config-mirror; unset ⇒ INFER — this is not a
  kill-switch and gates nothing off; an invalid value is logged at error and
  treated as unset per the ADR-098 D3 no-boot-break rule).
* **Resolution (one pure ladder).**
  `write_ahead_log::config::resolve_durability_mode(declared, wal_local_dir,
  primary_wal_location, data_dir)`: declared wins; else a set global
  `wal_local_dir` (env > TOML) ⇒ `local_volume`; else the scheme of the
  primary WAL location (`write_buffer_directory` — the pre-overwrite
  `data_directories[0]`): object URL (`://` and not `file:`) ⇒
  `object_store_serverless`, local path ⇒ `local_volume` **with the WAL root
  defaulting to `file://{data_dir}/wal`**. `data_dir: None` (a conversion that
  cannot know it) skips only the default-root move, never the mode.
* **One stamp, stable evidence.** `ProximaDB::new` (server AND embedded —
  `main.rs` boots through it) calls
  `WriteBufferUserConfig::apply_durability_mode_resolution(&server.data_dir)`
  ONCE, caching the resolution on the user config. Every later conversion
  (`to_engine_config`, `engine.rs`'s replay manager, `SharedServices`)
  reads the CACHED resolution, so the `{data_dir}/wal` default flows to write
  path AND replay (TD-WAL-5's one-root rule) while the boot log keeps the
  ORIGINAL inference evidence (a naive stamp into `wal_local_dir` would have
  degraded a re-resolution's evidence to "wal_local_dir set").
* **The loud log** replaces the former ADR-069 S1 remote-WAL warning in
  `SharedServices::convert_toml_to_wal_config` (INFO):
+
```
durability_mode=local_volume resolved_from="primary WAL location scheme" \
evidence="./data/write_buffer" effective_wal_root="file:///data/wal" \
wal_root_defaulted=true \
pin_with="[storage.wal_config].durability_mode (env PROXIMADB_WAL_DURABILITY_MODE)" \
"ADR-098 D3 / TD-SPINE-5: WAL durability mode resolved — no silent legacy path"
```
+
The old guard's error/warn (remote `write_buffer_directory` + PerBatch) is
GONE by design: under ADR-098 D3 an object-store WAL is the *declared
posture*, not a misconfiguration; the contradictory shape (declared
`object_store_serverless` + explicit `wal_local_dir`) logs a WARN naming both.
* **Recovery.** `RecoveryManager::new` logs the mode + resolved root.
  `wal_candidate_bases` already unions, in order: the resolved WAL root (now
  possibly the `{data_dir}/wal` default), the catalog base, every manifest
  `storage_url`, and the configured primary base — the catalog and primary
  bases ARE the legacy co-located roots, so replay scans the configured root
  AND the legacy root; the upgrade ratchet below pins it.
* **Recording.** `durable_locations` gains an additive `durability_mode`
  field (`serde(default)` — pre-SPINE-5 records read back with `None`),
  carried on every WAL-serving entry; the resolution itself is an entry
  (source = `[storage.wal_config] durability_mode ({mode} — {label})`,
  location = the effective WAL root: explicit root, `{data_dir}/wal` default,
  or the primary WAL location under serverless). The defaulted root lives
  under `data_dir`, already a leased root, so cold backup's unleased check is
  unaffected.
* **Serverless e2e.** `object_store_restart_recovery.rs` now DECLARES
  `durability_mode = "object_store_serverless"` in its `[storage.wal_config]`,
  so the proof no longer rides on inference.

== Remaining scope (2026-11-25)

* **R1. Put `wal_fsync_crash_recovery` in a CI lane.** It SIGKILLs a real server, so it belongs
  beside `cold_backup_restore` in "Rust Build (dev)" or in the qa tier. *Acceptance:* a CI run id
  in which the step ran and passed, cited here.
* **R2. Assert the resolved mode in each suite (acceptance bullet 3, "boot log names the
  mode").** Only `object_store_restart_recovery` mentions the mode, and only by declaring it in
  its config. No suite asserts the resolved mode. *Acceptance:* each of
  `wal_fsync_crash_recovery`, `cold_backup_restore` and `object_store_restart_recovery` asserts
  its expected mode, either from the boot log line (`durability_mode=…`) or from the
  `durable_locations` record's `durability_mode` field. A wrong-mode mutation fails at least one
  of them.
* **R3. macOS cold-backup restore-path failures.** Resolved by #2575 (2026-11-25): cold backup's
  containment and restore root resolution now canonicalize the nearest existing ancestor
  (`writer_epoch::resolve`), and `backup_refuses_wal_manifest_outside_roots` and
  `backup_restore_round_trip_preserves_bytes` pass locally on macOS. No macOS CI leg exists.
* **R4. TD-SEAM-14 durability boundary (acceptance bullet 4).** So far the coordination is
  vocabulary only (see below). No separate spec is needed: the existing link:TD-SEAM-14-object-store-recovery-and-ownership-boundary.adoc[TD-SEAM-14] already has a
  "Durability boundary and operator recovery" section (§8), and its bounded delivery (§2)
  assumes an intact durable local WAL/metadata volume. *Acceptance:* TD-SEAM-14 §8 states which
  `DurabilityMode` its spill placement resolves to (one of the two, no third mode), and this
  TD cites that line.

== Coordination — TD-SEAM-14 (spill durability boundary)

TD-SEAM-14 owns the object-store spill placement durability/ownership boundary
(`src/services/spill_placement.rs`; runtime owner fence, epoch-stamped
segments, durability-boundary spec — per its design handoff). Its vocabulary
is `OwnerFence` / `OwnerMarker` / epoch-stamped `spill-{epoch}-{range}.parquet`
segment names — **no `durability_mode` key, enum, or config surface**, so this
TD's vocabulary (`DurabilityMode`, `durability_mode`,
`PROXIMADB_WAL_DURABILITY_MODE`) does not collide with the seam. Per ADR-098
D3, whatever durability boundary SEAM-14 documents for spill must resolve to
one of these two modes; when its durability-boundary spec lands
(*corrected 2026-11-25:* there is no separate planned file; the durability boundary is
§8 of TD-SEAM-14 itself), it should REFERENCE `DurabilityMode` rather than mint a third mode.

== Evidence (2026-11-24)

* **Inference, local scheme + default root (ratchet):**
  `spine5_local_scheme_infers_local_volume_with_default_root` — local
  `write_buffer_directory` ⇒ `local_volume`, root
  `file://{data_dir}/wal`, and the resolved root's scheme is local.
* **Inference, object scheme (ratchet):**
  `spine5_object_scheme_infers_serverless_without_local_root` — `s3://`,
  `az://`, `gcs://` primaries ⇒ `object_store_serverless`, NO local default
  root (per-collection WAL stays under the catalog base).
* **Declared wins, both directions:** `spine5_declared_mode_wins_over_inference`;
  a declared `local_volume` over an object primary still gets the
  `{data_dir}/wal` default. User-config level:
  `declared_toml_mode_wins`, `durability_mode_toml_default_and_rejection`
  (unset ⇒ None/infer; unknown declared value FAILS the load).
* **`wal_local_dir` ⇒ local_volume:** `spine5_wal_local_dir_infers_local_volume`
  (suppresses the default root);
  `explicit_wal_local_dir_wins_over_the_default_root`.
* **Boot stamp:** `boot_stamp_infers_local_volume_and_defaults_the_root`,
  `boot_stamp_is_idempotent_and_evidence_stable` (re-resolution keeps the
  ORIGINAL PrimaryScheme evidence after the root is in force),
  `to_engine_config_carries_mode_and_effective_root` (unstamped conversions
  resolve the mode but apply no root move — legacy placement).
* **Upgrade ratchet:** `spine5_legacy_root_wal_replays_after_the_default_root_move`
  — a WAL written at the legacy co-located root REPLAYS under the
  upgrade-shaped config (defaulted `wal_local_dir` + legacy primary base),
  proving recovery scans the configured root AND the legacy root.
* **Recording:** `wal_durability_mode_recorded_local_volume_default_root`,
  `wal_durability_mode_recorded_object_store_serverless`,
  `declared_durability_mode_wins_in_the_record`,
  `pre_spine5_record_reads_back_without_a_mode` (mixed-version record
  negative control), `record_round_trips` extended with the mode field.
* **Mutation check (observed, then restored):** hardcoding
  `resolve_durability_mode` to return `ObjectStoreServerless` flips
  `spine5_local_scheme_infers_local_volume_with_default_root` AND
  `boot_stamp_infers_local_volume_and_defaults_the_root` red (mode + root
  assertions); hardcoding `LocalVolume` flips
  `spine5_object_scheme_infers_serverless_without_local_root` and the
  durable-locations serverless record test red. The inference is load-bearing.
