== The finding

After publication V commits, `gc_older_generations` keeps only V's and V-1's files and
Puffins (`dv_mat_generation(name) < current` is deleted unless keep-listed). A reader still
pinned to V-2 — a long scan, an external Iceberg consumer holding a snapshot reference —
gets object-not-found partway through. Only files *exclusive* to V-2 die, so correctness of
the current view is untouched; the contract advertised (in code comments and the fence docs)
is V-1 only.

== The chosen design (decided here so implementation is mechanical)

Keep **N generations** (V, V-1, … V-N+1) behind an env gate, default **3**:

* `PROXIMADB_MATERIALIZE_GC_KEEP_GENERATIONS` (default 3; `1` restores today's exact
  behavior; registry row required in `docs/12-design/ENV_GATE_REGISTRY.adoc`).
* The keep-set builder extends from "committed snapshot ∪ parent manifest" to "committed
  snapshot ∪ the last N-1 manifests" — still positive evidence (committed snapshots only,
  never a listing), still fail-closed-keep when a manifest read fails.
* Document the reader-pinning contract beside `gc_older_generations`: a consumer may pin at
  most N-2 publications behind the head.

Alternatives declined: time-based grace (the generation design is deliberately clock-free —
"generation order never depends on a clock" — and a grace interval reintroduces wall-clock
semantics into GC safety); Iceberg-style snapshot leases with minSnapshotsToKeep/maxSnapshotAge
(churn without a demonstrated pinned-reader workload — N-generations answers the observed
failure with a fraction of the machinery).

== Acceptance criteria (include the review's missing tests — finding F14)

* `gc_older_generations` keeps V-2 at the default and collects it at `=1` (unit test).
* The 64-part fallback (`APPEND_MAX_FILES`) has a test: a snapshot with 64 stub parts must
  classify `Rewrite("the snapshot has many parts…")` — of the four changelog-advertised
  fallback thresholds, this is the one enforced only by an unexercised `if`.
* Boundary: `changed.len() == max_rows` stays incremental (unit test beside `classify`).
* The soak asserts at least one compacting rewrite occurred (a counter or classification
  assert), so the compaction leg is pinned rather than incidental to the seed — if the seeded
  mix drifts under future edits, the incremental-only path silently becomes the only one
  exercised.
* The soak's external read-back still passes at the new default.
