== Problem

Facts that routing and planning need for a whole collection are stored only inside each segment's
footer:

* row count (`row_count`);
* exact-f32 authority (`has_f32_tier`);
* quantization tier and rerank encoding;
* block/row-group stats (Stage F);
* the IVF cell directory (Region A0).

Every collection-level question therefore reads every segment's footer: two ranged GETs each
(header prefix, then footer body). Current consumers:

* The Adaptive exact-vs-ANN gate (`segment_vector_count`). TD-SEAM-11 now reads the PAX footer
  facts and caches them per immutable object URL, but the first query after a restart, or after
  compaction, still pays 2 × segments GETs before it can route.
* The AXIS rebuild coverage check (`durable_vector_count_for_rebuild`) does a full read of every
  `.pax` file to count rows.
* The coarse-RaBitQ rebuild guard (`all_segments_coarse_rabitq_pax_without_f32_tier`) also does a
  full read per segment.
* Coarse IVF probing reads each segment's A0 directory, which is why one query touches many
  segments (20–80 GET/q cold at 1M vectors versus turbopuffer's 3–4 round trips; seams doc Part C).

Parquet and Iceberg solve the same problem with a *manifest*: per-file record counts and column
statistics live one level up, so a planner prunes and routes without opening data files. PAX has
no equivalent level.

== Fix approach (amended 2026-11-19, link:../../12-design/adr/ADR-098-metadata-spine.adoc[ADR-098] D2)

The collection-level carrier is the **L1 collection segment directory**, a generalization of the
existing PXCD centroid directory rather than a new manifest. It is an S7 projection: LIST-validated,
never authoritative (ADR-063 D4 stands), and it does not grow the catalog with segment count.

. **Generalize PXCD.** Extend the centroid directory
  (`crates/storage/proximadb-storage-common/src/centroid_directory.rs`) so its entries carry facts
  for ALL live segments, not only segments covered by a trained coarse model: URL, size, row count,
  LSN range, quantization tier, `has_f32_tier`, and the A0 summary where one exists. A new PXCD
  version byte keeps it mixed-read-safe; readers fall back to the per-segment footer path when the
  version is unknown.
. **Publish at flush and at compaction**, create-only at generation g+1 (as PXCD already is at
  compaction). Each entry records the segment's ETag, and a reader trusts an entry only when the
  LIST it already issues reports that same ETag. A publish failure never fails the flush or the
  compaction.
. **Per-entry statistics per ADR-042** (`SegmentStatistics`), so planning and the ADR-037 envelope
  aggregate from directory entries, with footers as the fallback.
. **Delete the dead `src/storage/engines/sst/manifest.rs`** (`SstManifest` and friends). Its types
  have no users outside the module (only comments elsewhere name `SstManifest`; the `SstableFileInfo`
  in use is a separate struct in `sst/utils.rs`).
. **Both PAX read lanes consume the directory** (ADR-098 D2.4; carries TD-USUB-8 slice 3): the SST
  search route (the consumers listed under Problem) and the DataFusion PAX lane
  (`PaxSplitReader::load_ranged`, `src/datafusion/engine_adapters/pax_adapter.rs`; read-order planning in `crates/storage/proximadb-block-format/src/ranged.rs`), which takes
  footer and SegmentIndex extents from the entry's decode key instead of probing the tail. Blooms,
  deletion vectors and stripe data stay in the object and are fetched by reference.
. **Write gate `PROXIMADB_PAX_WRITE_DIRECTORY_AT_FLUSH`**, default OFF until baked, registered in
  `ENV_GATE_REGISTRY.adoc` with the code. Compaction-time publication stays on its existing
  `PROXIMADB_PAX_WRITE_CENTROID_DIRECTORY` gate.

The per-object footer-facts cache from TD-SEAM-11 stays as the fallback for segments with no valid
entry.

== Superseded proposal (2026-10-19)

_Kept for history. Superseded by the amended fix approach above. The "written atomically with the
segment set, through the same create-only CAS committer" wording conflicts with ADR-063 D4's
mode-independent discovery rule (LIST is the authority; manifests are caches): segments are made
durable and LIST-discoverable on their own; the directory is a cache that
follows them, not a commit that gates them._

=== Fix direction (to be validated by the PAX spec thought experiments)

* Publish a **collection-level segment manifest** with each segment set (flush or compaction
  commit). It holds, per segment: URL, size, row count, LSN range, quantization tier,
  `has_f32_tier`, A0 centroid summary and zone-map stats. It is written atomically with the
  segment set, through the same create-only CAS committer the Iceberg publisher uses.
* Routing, rebuild checks and coarse probing read the manifest: one object, cacheable, with no
  per-segment GETs.
* The manifest is the natural carrier for TD-SEAM-10's collection-global centroid directory, and
  for exporting PAX facts into Iceberg manifests (ADR-097 S4/S7).
* The per-object footer-facts cache from TD-SEAM-11 stays as the fallback for segments written
  before the manifest exists (mixed-read-safe).

== Request-count evidence harness (counts only)

`tests/sift_pax_recall_ratchet_test.rs` — `sift_get_counts_directory_at_flush_{off,on}` (`#[ignore]`d;
CI job `sift-object-store-request-counts`, `scripts/run_cloud_emulator_tests.sh --sift-get-counts`,
Azurite `adls://`, dispatch + develop→qa tier). Scenario per mode: SIFT N vectors ingested through
`SstEngine::do_flush` in fixed batches of `PROXIMADB_SIFT_FLUSH_BATCH` (one `.pax` per flush, so
segments = ceil(N / batch), asserted against the listing); then each cold arm runs in a **fresh
re-exec'd process** (every process-global cache empty): the first query with an explicit
`Approximate` intent vs the same first query with the production `Adaptive` intent (threshold 0, so it
asks `segment_vector_count` and still takes the ANN arm). `cold_metadata` = the difference — the
marginal cost of the collection-level question on a cold open; `steady` = 100 further Adaptive queries
in the same process; recall@10 vs SIFT ground truth. Latency is not measured: emulator latency is not
evidence, and real-cloud latency is a separate follow-up.

*Scope of what this measures.* The collection uses `compaction:off`, and the harness disables the
ADR-081 L0 admission ceiling (`PROXIMADB_L0_STOP_TRIGGER=0` / `_SLOWDOWN_TRIGGER=0`) because nothing
drains L0 without compaction. So in this scenario the directory exists **only** because of
`PROXIMADB_PAX_WRITE_DIRECTORY_AT_FLUSH` — positive control: `AT_FLUSH=0` leaves no
`centroids-*.pxcd` at rest, `AT_FLUSH=1` leaves the newest two generations. In production the
directory is otherwise published after a compaction (`PROXIMADB_PAX_WRITE_CENTROID_DIRECTORY`); a
compacted, A0-trained collection (directory-planned search) is not what this harness measures. Only
the SST `segment_vector_count` consumer is reachable from this public search path: the AXIS rebuild
coverage / coarse-RaBitQ checks run only for AXIS-orchestrated collections, and PUTs are not recorded
by the per-query trace (ingest reports GET/LIST/HEAD only).

Determinism: every GET / range-GET / LIST / HEAD count is identical across repeated runs on the same
inputs (file://, two runs × four configurations). `waves` is reported but is scheduling-derived and
can differ by one when the segment fan-out exceeds the scan concurrency (seen at 20 segments).

*Measured on Azurite (`adls://`, CI run 44788449721, 2026-11-20; N=10 000, 100 queries, top-10).*
Query-side counts are identical to the file:// runs; ingest counts are backend-specific but
deterministic.

|===
| Segments | Mode | Cold metadata GETs | Cold first query (Adaptive) | Steady GET/query | Ingest GET / LIST | Recall@10
| 10 | AT_FLUSH=0 | 20 (2/segment) | 65 GET + 1 LIST | 5.25 | 10 / 20 | 0.987
| 10 | AT_FLUSH=1 | 0 | 46 GET (45 ranged + 1 directory) + 1 LIST | 5.25 | 49 / 30 | 0.987
| 20 | AT_FLUSH=0 | 40 (2/segment) | 128 GET + 1 LIST | 6.71 | 20 / 40 | 0.992
| 20 | AT_FLUSH=1 | 0 | 89 GET (88 ranged + 1 directory) + 1 LIST | 6.71 | 99 / 60 | 0.992
|===

Reading: the collection-level question costs 2 GETs per segment without the directory and 0 with it
(the single directory GET is paid by every cold first query, including `Approximate` ones); steady
query cost and recall are unchanged; the price is ~4 GETs (3 ranged) + 1 LIST per flush to refresh the
directory, linear in flush count. Acceptance bullet 1 (≤ 1 metadata GET instead of 2N) is met on
this path. PUTs are not traced, so the directory's write-side PUT per flush is not in these counts.

== Acceptance

* Cold Adaptive routing on an N-segment collection: at most 1 metadata GET, not 2N.
* The AXIS rebuild coverage and coarse-RaBitQ checks read no segment bodies.
* The SIFT1M MinIO RTT-ladder bench (`RDSTRAT13`) shows the manifest removes the per-segment
  footer wave from the cold critical path.
* DataFusion PAX lane: a cold `PaxSplitReader` read of a directory-covered segment pays no
  index-acquisition round trip (extend the TD-USUB-8 ratchet `cold - warm == 3` in
  `docs/_internal/status/PAX_DATAFUSION_READ_DEPTH_2026_09_27.adoc` to `cold - warm == 0` when the
  entry's etag matches; a stale etag falls back to the tail probe — negative control).
