== The seam this fills (already landed)

Phase 0 (#755) shipped the contract; this TD is the impl:

[source,rust]
----
// crates/query/proximadb-execution-contracts/src/lib.rs — EXISTS today
pub const MORSEL_SIZE: usize = 2048;                       // DuckDB STANDARD_VECTOR_SIZE
pub type BatchStream = BoxStream<'static, Result<RecordBatch, ExecutionError>>;
pub trait ExecutionOperator: Send + Sync + Debug {          // async stream→stream
    async fn execute(&self, input: BatchStream) -> Result<BatchStream, ExecutionError>;
    fn output_schema(&self) -> SchemaRef;
}
pub struct Pipeline { pub operators: Vec<Box<dyn ExecutionOperator>>, .. }
#[async_trait] pub trait MorselScheduler: Send + Sync {     // <- Phase 4 impl target
    async fn schedule(&self, pipeline: &Pipeline, input: BatchStream)
        -> Result<BatchStream, ExecutionError>;
}
----

Today `Pipeline::execute` chains operators over a *single* `BatchStream` (serial). The
scheduler replaces that with **N parallel morsel lanes** and a fan-in merge, preserving the
exact `BatchStream` in/out signature — so it is a drop-in behind the `native_engine.rs` hook,
non-breaking.

== Architecture (morsel-driven, Leis SIGMOD 2014)

**Unit of work = a morsel** (`MORSEL_SIZE` rows). The scheduler splits the leaf input into
morsels and runs the pipeline segment on each in parallel, with a bounded worker pool.

=== Pipeline breaks (the barrier structure)
A `Pipeline` is a chain, but blocking operators (hash-join **build**, sort, blocking
aggregate) are **pipeline breaks**. The scheduler segments the pipeline at breaks:

....
[scan]→[filter]→[project]  ═╗ (break: hash build drains all morsels)
                            ╠═► [build barrier] ═► [probe]→[project]→[limit]
        parallel morsels    ║        parallel morsels
....

* **Within a segment:** morsels flow through the streaming operators (filter/project/probe)
  on independent worker lanes — no cross-morsel state, embarrassingly parallel.
* **At a break:** all morsels of the upstream segment must complete before the blocking
  operator emits (build the whole hash table / sort the whole input). The scheduler awaits
  the segment's join set, then starts the downstream segment.

=== Concurrent state at breaks (the shared risk with TD-OLAP-11)
The hash-join build is the one shared-mutable structure. Two admissible designs (Leis §4):

. **Partition-local + barrier merge (MVP):** each lane builds a local hash table over its
  morsels; a barrier merges them (or keeps them partitioned for a partitioned probe). No
  concurrent writers — simplest, correctness-first.
. **Concurrent CAS insert (Phase 4.1):** one shared lock-free table, HyPer-style 48-bit
  pointer + 16-bit tag CAS insert. Higher throughput, more risk.

MVP takes (1); (2) is a measured follow-up. This TD does **not** re-open TD-OLAP-11's join
correctness — it schedules the operators the join TD defines.

== The async/NUMA design decision (the load-bearing part)

The operator contract is **async stream-based** (Tokio `BoxStream`), by the ADR-054 BLOCKER-1
fix. NUMA pinning (ADR-054 §9(b)) wants **dedicated, core-pinned OS threads**, which is in
tension with Tokio's NUMA-oblivious work-stealing pool. Resolve in two gated stages:

* **Phase 4.0 — parallelism without pinning (MVP).** Spawn one Tokio task per morsel lane on a
  **bounded** runtime (`num_cpus - 2`, matching the repo's build-jobs discipline). This buys
  the multi-core speedup with zero new threading primitives and composes with the existing
  async operators unchanged. Honest limit: no NUMA locality; cross-socket morsel routing is
  left to the OS scheduler.
* **Phase 4.1 — NUMA-pinned worker pool (gated, `PROXIMADB_NATIVE_MORSEL_NUMA`).** A dedicated
  worker pool of OS threads pinned via `core_affinity`, each thread owning a Tokio
  `LocalSet`/current-thread runtime; morsels are routed to the socket that owns their input
  pages (first-touch). This is the only place a custom runtime is introduced, and only behind
  a flag — because NUMA wins are workload- and hardware-dependent and must be *measured*
  (ADR-052 mandate #11), not assumed. `core_affinity` degrades to a no-op where pinning is
  unsupported (e.g. some macOS/WSL configs) → falls back to 4.0 behavior, correctness-neutral.

Morsel size stays `MORSEL_SIZE = 2048` (const default) with a per-operator runtime override
hook (ADR-054 §12 Q3, ratified).

== Wire gate + fallback

`try_vectorized_stream` uses the scheduler only when `native_morsel_scheduler_enabled()`
(`PROXIMADB_NATIVE_MORSEL`, default OFF — distinct from `PROXIMADB_NATIVE_VECTORIZED` and
`PROXIMADB_NATIVE_JOIN`). When off, `Pipeline::execute` runs serially (today's behavior). Any
unsupported shape (e.g. an operator that opts out of parallel scheduling) falls back to serial
execution — the scheduler is additive, never a correctness dependency.

== Motivating evidence (TD-OLAP-4 shadow, 2026-07-10)

The TD-OLAP-4 native-parquet shadow now supplies the cost-term evidence this TD's P3
priority demanded ("do not build ahead of ledger evidence that a parallel scheduler moves a
cost term"). At **100M rows (real ClickBench `hits`)**, with the ungrouped `HashAggregate`
**vectorized** (Arrow kernels, single-threaded) and metadata elision on, native's residual
loss on **ungrouped scalar aggregates** is attributable *purely to single-threaded execution*:

[cols="2,1,1,1,3", options="header"]
|===
| Query | DataFusion | native (1 thread) | DuckDB | Attribution
| q03 `SUM,COUNT,AVG` | 186ms | 358ms (1.9×) | 61ms | single-thread vs DataFusion `AggregateMode::Partial` across `target_partitions`
| q04 `AVG(UserID)` | 240ms | 329ms (1.4×) | 127ms | single-thread vs DuckDB morsel-driven `LocalSinkState`→`Combine`
| q07 `MIN/MAX` | 1609ms | 66ms → ~1ms (elided) | 38ms | native WINS (elision / low overhead)
| q01 `COUNT(*)` | 12ms | 1ms (elided) | 26ms | native WINS (footer)
|===

Source review (DataFusion 54 `SumAccumulator<T>`, DuckDB `physical_ungrouped_aggregate`)
confirms both competitors are **native-type + multi-core**; native's vectorized operators are
per-op competitive but run on **one** `BatchStream`. The gap is the parallelism this TD adds —
**not** cast overhead (per-batch, ~8MB, negligible) and not the kernels. This is the measured
justification to sequence the impl. The vectorized `UngroupedState` (per-batch fold + associative
`finalize`) is precisely the **morsel partial-state + combine** shape this scheduler fans out.

== Risks + mitigations

* **Per-morsel Tokio task overhead** erasing the parallel win on small inputs. Mitigation:
  size-gate — schedule in parallel only above a morsel-count threshold; below it, run serial.
* **False sharing / cache-line contention** at the build barrier. Mitigation: partition-local
  build (MVP), cache-line-padded merge structures.
* **NUMA pinning portability** (`core_affinity` no-op on some targets). Mitigation: gated,
  default-off, falls back to 4.0; never a correctness dependency.
* **Interaction with the join's `OnceLock` handoff** (TD-OLAP-11). Mitigation: the scheduler
  treats the build segment as a barrier; the `OnceLock` publish happens at the barrier, read by
  the probe segment — the existing handoff is unchanged, just parallelized within each segment.
* **Determinism for tests** (parallel merge reorders rows). Mitigation: the merge preserves no
  order guarantee anyway (SQL is unordered without ORDER BY); order-sensitive tests already go
  through a Sort operator, which is a break.

== Non-goals

* **No distributed execution.** Single-node scheduler only; a morsel/hash-partition exchange
  for MPP is a separate future ADR (ADR-054 §7.2). Ballista stays the DataFusion-only
  distributed path (ADR-054 §7.3).
* **No codegen** (ADR-052 non-goal, inherited).
* **No promotion without the ledger** (default-off, demoted on regression).
