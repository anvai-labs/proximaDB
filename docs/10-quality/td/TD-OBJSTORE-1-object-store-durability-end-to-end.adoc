== History (shipped)

* Context: anvaiops runs a single VM with `storage.metadata_url = adls://…` (managed identity). The Azure `FileSystem` routed correctly (`adls`/`abfs`/`az`/`azure` alias the flat Blob endpoint, ADR-036); what broke was path construction between config and filesystem, plus subsystems bypassing the filesystem abstraction.
* **The bug class (still guarded):** (1) strip-and-re-prepend — `metadata_url.replace("file://", "")` then `format!("file://{}…")`/`PathBuf::from`, yielding `file://adls://…` or literal local `adls:` dirs; (2) `std::fs`/`tokio::fs` on config-derived durable paths that may carry an object-store scheme; (3) scheme *enumeration* allowlists instead of a generic `contains("://")` predicate.
* Batch 1 (#966, 2026-07-14): scheme-preserving `join_storage_url()` at every metadata_url join (metrics, document/observability WAL, audit/event log, multimodel store); `UnifiedWALWriter/Reader` normalize the base once instead of hard-prefixing `file://`; object-store WAL flush buffers the segment and overwrites per flush (block blobs have no `append`); eventlog/snapshot I/O through the injected `FileSystem` (and its snapshot cleanup, which never deleted, fixed); `FileAuditStorage` overwrote its log on every event — now appends, and a new `ObjectStoreAuditStorage` handles object-store URLs; delta catalog scheme check made generic; disk caches/tantivy/alert persistence fail fast on URL-shaped paths. Timeseries falls back to local non-durable with a loud warn (deferred).
* Batch 2 (2026-07-14): `SystemCatalog`'s durable path never engaged on `adls://`/`gcs://` (allowlist + upstream parser not knowing the aliases) — catalog metadata silently landed in a temp cache. Alias normalization is centralized in `proximadb-object-store::store_for_url`; `DeltaCatalog::new_with_filesystem` persists through the injected `FileSystem` (CAS/rename/checkpoints → TD-CAT-4; cache eviction → TD-CAT-5).
* Batch 3: dim-1 KV collections recovered empty after VM restart. **Lesson — the attribution was wrong:** a non-zero `[0.5]` control was lost identically; the variable was unflushed WAL-only data on an object store (KV collections were just the only ones too small to flush; flushed collections survived via segment discovery). Two stacked defects — async manifest pointer vs sync ack, and a LIST fallback gated on `exists()` of a directory prefix (HEAD-on-key = false on flat keyspaces). Fixed by TD-OBJSTORE-4's LIST-authority recovery; acked ⇒ durable AND LISTable, manifests are caches.
* Operational note still true: the WAL/SST `FilesystemFactory` reads `AZURE_STORAGE_ACCOUNT` while the catalog snapshot store reads `AZURE_STORAGE_ACCOUNT_NAME`; both must be set (consolidation: TD-OBJSTORE-3).
* Guards: `tests/objstore_url_construction_test.rs` (`join_storage_url` matrix asserting no `file://<scheme>://` or `<scheme>://<scheme>://`; `no_strip_and_reprepend_pattern_in_src` source guard); `supports_append` construction ratchets for queue roots and RAPTOR writers; WAL reopen resumes `sequence_number` at `max + 1`.

== Deferred (documented limitations — next cycles)

[cols="3,3", options="header"]
|===
| Item | Notes

| **Timeseries (TST engine) on object store**
| Engine is local-`PathBuf`-native (per-tenant WAL/partitions/segments). On an
  object-store `metadata_url` the service now falls back to a LOCAL, NON-DURABLE dir
  with a loud warn instead of mangling the URL. Durable path: route TST segment I/O
  through the filesystem abstraction, or flush-to-object-store tiering.

| **Delta catalog multi-writer CAS + rename relocation + log checkpoints**
| Core object-store durability LANDED in batch 2 (see inventory above); the
  remaining refinements are tracked in TD-CAT-4. The catalog pointer is
  last-writer-wins (single-writer warehouse model) until CAS lands.

| **RAPTOR writer format still requires append**
| Contained: `FileSystem::supports_append` makes the backend capability explicit and
  `RaptorWriter` rejects incompatible injected backends during construction. RAPTOR
  remains feature-gated/default-OFF. A full-buffer-overwrite or multipart format is
  still required before RAPTOR can support object stores.

| **Queue root format still requires append**
| Contained: `FactoryQueueFs::new` now rejects a root whose resolved backend does not
  advertise durable append. Object-store archive targets remain independent, but an
  object-store queue root is unsupported until the queue segment format becomes
  immutable/replace-based.

| **Filesystem trait retains the `append` method**
| `supports_append` prevents capability-blind constructors, but the method remains on
  the shared trait for local/HDFS compatibility. New append-dependent formats must
  check the capability at construction; removing/splitting the method is a later
  workspace-wide API migration.

| **Alerting persistence object-store port**
| `AlertPersistence` is a port; add an object-store-backed impl (layering: the
  modality crate cannot see root `FilesystemFactory`; inject from the composition
  root) when alerting persistence is wired into the server.

| **Per-event audit objects vs. batching**
| `ObjectStoreAuditStorage` writes one small object per event (correct, simple).
  If audit volume grows, batch by time window to cut PUT counts (KRU/KOU cost).
|===
