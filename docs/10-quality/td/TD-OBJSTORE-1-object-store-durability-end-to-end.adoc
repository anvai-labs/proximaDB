== History (shipped)

* Context: anvaiops runs a single VM with `storage.metadata_url = adls://…` (managed identity). The Azure `FileSystem` routed correctly (`adls`/`abfs`/`az`/`azure` alias the flat Blob endpoint, ADR-036); what broke was path construction between config and filesystem, plus subsystems bypassing the filesystem abstraction.
* **The bug class (still guarded):** (1) strip-and-re-prepend — `metadata_url.replace("file://", "")` then `format!("file://{}…")`/`PathBuf::from`, yielding `file://adls://…` or literal local `adls:` dirs; (2) `std::fs`/`tokio::fs` on config-derived durable paths that may carry an object-store scheme; (3) scheme *enumeration* allowlists instead of a generic `contains("://")` predicate.
* Batch 1 (#966, 2026-07-14): scheme-preserving `join_storage_url()` at every metadata_url join (metrics, document/observability WAL, audit/event log, multimodel store); `UnifiedWALWriter/Reader` normalize the base once instead of hard-prefixing `file://`; object-store WAL flush buffers the segment and overwrites per flush (block blobs have no `append`); eventlog/snapshot I/O through the injected `FileSystem` (and its snapshot cleanup, which never deleted, fixed); `FileAuditStorage` overwrote its log on every event — now appends, and a new `ObjectStoreAuditStorage` handles object-store URLs; delta catalog scheme check made generic; disk caches/tantivy/alert persistence fail fast on URL-shaped paths. Timeseries falls back to local non-durable with a loud warn (deferred).
* Batch 2 (2026-07-14): `SystemCatalog`'s durable path never engaged on `adls://`/`gcs://` (allowlist + upstream parser not knowing the aliases) — catalog metadata silently landed in a temp cache. Alias normalization is centralized in `proximadb-object-store::store_for_url`; `DeltaCatalog::new_with_filesystem` persists through the injected `FileSystem` (CAS/rename/checkpoints → TD-CAT-4; cache eviction → TD-CAT-5).
* Batch 3: dim-1 KV collections recovered empty after VM restart. **Lesson — the attribution was wrong:** a non-zero `[0.5]` control was lost identically; the variable was unflushed WAL-only data on an object store (KV collections were just the only ones too small to flush; flushed collections survived via segment discovery). Two stacked defects — async manifest pointer vs sync ack, and a LIST fallback gated on `exists()` of a directory prefix (HEAD-on-key = false on flat keyspaces). Fixed by TD-OBJSTORE-4's LIST-authority recovery; acked ⇒ durable AND LISTable, manifests are caches.
* Operational note still true: the WAL/SST `FilesystemFactory` reads `AZURE_STORAGE_ACCOUNT` while the catalog snapshot store reads `AZURE_STORAGE_ACCOUNT_NAME`; both must be set (consolidation: TD-OBJSTORE-3).
* Guards: `tests/objstore_url_construction_test.rs` (`join_storage_url` matrix asserting no `file://<scheme>://` or `<scheme>://<scheme>://`; `no_strip_and_reprepend_pattern_in_src` source guard); `supports_append` construction ratchets for queue roots and RAPTOR writers; WAL reopen resumes `sequence_number` at `max + 1`.

== Embedded bootstrap and end-job residual (2026-11-02)

At the pre-change baseline `9d25b5a20`, the embedded adapter retained the path bug class:
`StorageLocationConfig::to_url` and metadata-path construction special-cased `file://`, so a
cloud URI could become a local file URL. Embedded `build_storage_config` copied WAL enablement
but not its advertised `wal_sync_mode`. The general service constructor also needs a valid
local work/WAL root when metadata is remote. Fix the adapter using existing storage semantics,
not another filesystem implementation or implicit cache-based durable directory.

The foundation implementation now preserves schemes and validates/wires the effective sync
mode. The existing local constructor explicitly rejects remote data/metadata roots before
service initialization. This closes unsafe silent interpretation; it does not implement a
cloud writer. Explicit remote writer bootstrap, local durability configuration and cloud
reopen proof remain required actions for the requested embedded-cloud lifecycle (F3).

`flush_and_close(&mut self)` adds a fallible vector-only boundary: existing `flush` succeeds
before legacy `close` releases ownership, and a flush error leaves the handle open for retry.
Graph/policy work in `close` remains best-effort. Focused local tests now prove vector
materialization failure/retry, ownership retention and reopen; this F4 implementation still
does not provide all-modality completion or a cloud receipt.

Acceptance: preserve explicit storage schemes and configured locations; map and validate
all supported durability settings; reject unsupported configuration before initialization;
prove distinct metadata/data/local-work roots and error propagation. Invoke the existing
materializer in an explicit fallible end-job boundary with a documented collection/modality
scope. Prove successful publication with fresh-process reopen and failure without false
success. Unit mapping tests alone do not prove cloud durability or support every modality.

`SystemCatalog::open_follower`/`reload_if_stale` already exist. The foundation F5 implementation
adds a metadata-only `EmbeddedCatalogFollower`: explicit cloud catalog URI plus an absolute
local work directory, isolated temporary appender state, and refresh/list/lookup APIs. It
exposes no data query API and must not reuse an owner's stale local WAL. Two focused tests
passed for refresh/takeover without publication and missing/corrupt snapshot refusal. Full
read-only embedded query boot remains required foundational work: the
general writer startup initializes the global WAL manifest and `SharedServices`; its SST
lifecycle starts compaction and its vector service expects a writer WAL. Provide a read-only
engine lifecycle and injected read view before routing cloud queries through it. Gate with no
takeover, no remote mutations and a real query after
fresh-process open; reject unsupported writer operations. A local catalog copy does not
replace committed cloud metadata. These gates belong to this TD and the
link:../../current/PLATFORM_PLAN.adoc#embedded-cloud-lifecycle[platform lifecycle contract].
TD-WAL-2 still owns modality recovery, ADR-069 owns the reattachable-WAL default, and ADR-081
leaves persisted completion receipts/crash idempotency open. Do not claim cloud-headless
completion from URI preservation or follower construction alone.

Local evidence checkpoint: 11 focused embedded tests passed (nine F3/F4/lifecycle and two
F5 follower tests; command/result transcript `/private/tmp/foundations-embedded-tests.log`).
The complete `make work-commit-check` passed (`/private/tmp/foundations-work-commit-check.log`).
Latest fetched `develop` is unchanged at `9d25b5a20`. The root storage/cache cohort passed 146/146 tests; server/cloud
build validation remains pending. No hosted CI, merge or cloud-headless support completion
is asserted by these local checks.

=== Required next seams (reuse the existing owners)

`CollectionService::upsert_collection_catalog_asset` already persists vector collections as
`CatalogTableSchema`; `src/storage/metadata/collection_mapping.rs` owns the bidirectional
mapping. Reuse it for a read-only collection projection and invalidate its cached projection
on catalog snapshot-version changes. No new metastore is needed.

For cloud queries, inject a published-only read view instead of requiring a writer WAL
manager. Add a read-only lifecycle to the existing engine: no compaction, recovery publication
or training writes, and no `SharedServices` owner/default-namespace initialization side effects.
Prove catalog refresh, query visibility and authorization together; a snapshot version alone
is not a data-file visibility watermark.

Cloud writer bootstrap must take an explicit role, metadata URI, authorized data roots and
reattachable WAL/work root. Pass the concrete local work directory through composition rather
than using presence of `opt_config` as a proxy. Isolate process-global state/ownership across
contexts; catalog fencing and a collection write lease are distinct controls. Reuse the
existing flush/materializer after admission. These are required implementation/acceptance
actions, not capabilities supplied by the metadata-only follower.

== Deferred (documented limitations — next cycles)

[cols="3,3", options="header"]
|===
| Item | Notes

| **Timeseries (TST engine) on object store**
| Engine is local-`PathBuf`-native (per-tenant WAL/partitions/segments). On an
  object-store `metadata_url` the service now falls back to a LOCAL, NON-DURABLE dir
  with a loud warn instead of mangling the URL. Durable path: route TST segment I/O
  through the filesystem abstraction, or flush-to-object-store tiering.

| **Delta catalog multi-writer CAS + rename relocation + log checkpoints**
| Core object-store durability LANDED in batch 2 (see inventory above); the
  remaining refinements are tracked in TD-CAT-4. The catalog pointer is
  last-writer-wins (single-writer warehouse model) until CAS lands.

| **RAPTOR writer format still requires append**
| Contained: `FileSystem::supports_append` makes the backend capability explicit and
  `RaptorWriter` rejects incompatible injected backends during construction. RAPTOR
  remains feature-gated/default-OFF. A full-buffer-overwrite or multipart format is
  still required before RAPTOR can support object stores.

| **Queue root format still requires append**
| Contained: `FactoryQueueFs::new` now rejects a root whose resolved backend does not
  advertise durable append. Object-store archive targets remain independent, but an
  object-store queue root is unsupported until the queue segment format becomes
  immutable/replace-based.

| **Filesystem trait retains the `append` method**
| `supports_append` prevents capability-blind constructors, but the method remains on
  the shared trait for local/HDFS compatibility. New append-dependent formats must
  check the capability at construction; removing/splitting the method is a later
  workspace-wide API migration.

| **Alerting persistence object-store port**
| `AlertPersistence` is a port; add an object-store-backed impl (layering: the
  modality crate cannot see root `FilesystemFactory`; inject from the composition
  root) when alerting persistence is wired into the server.

| **Per-event audit objects vs. batching**
| `ObjectStoreAuditStorage` writes one small object per event (correct, simple).
  If audit volume grows, batch by time window to cut PUT counts (KRU/KOU cost).
|===
