= TD-XMODAL-8: cross-modal `vector_search` UDTF returns 0 rows — port ignores the tenant

[cols="1,3"]
|===
|Status|**Partial: `VectorOpsPort::search` resolves the collection under the tenant before searching (#677); graph tenant follow-up closed by the tenant-isolation program; open: confirm Strong-read freshness parity of the port's `search_v1` leg.**
|Priority|HIGH
|Scope|FEAT
|Date|2026-07-04
|Relates to|ADR-053 (cross-modal query fabric), `src/services/operations/vectors/legacy.rs` (`impl VectorOpsPort for VectorOperationsService`), `src/api_handlers/record_ops_service.rs::resolve_collection_id_internal`, `crates/platform/proximadb-runtime` (`CollectionPort::get_collection`), `src/datafusion/cross_modal.rs`. Follow-on to TD-XMODAL-6.

== History (shipped)

* **Root cause.** After TD-XMODAL-6 threaded the tenant into the UDTFs, `vector_search` still returned 0
  rows: the production `impl VectorOpsPort for VectorOperationsService` took `tenant_id` but **ignored
  it**, calling `search_v1` against the unscoped registry. Lesson: a vector collection is tenant-scoped by
  its (name, tenant) → id mapping, not by a folded name, so resolving the name without the tenant misses
  the collection.
* **Fix (#677).** With a tenant present, the port calls `collection_port.get_collection(&name,
  Some(tenant))` and replaces `request.collection_id` with the resolved canonical id (idempotent for
  `search_v1`; tenant-less callers unaffected), mirroring the REST
  `resolve_collection_id_internal` path. Verified live over pgwire under `dbname=<tenant>`.

== Follow-up (open)

* ~~Graph tenant isolation~~ — closed: `graph_traverse` now reads the structural `{tenant}/{graph_id}`
  scope the graph write path composes (see TD-GRAPH-TENANT-1).
* **Freshness parity:** the port's `search` uses the `search_v1` leg; confirm it crosses the same
  WAL/memtable freshness boundary the REST rich-search path (`search_records_with_tenant_context`)
  does for Strong reads.
