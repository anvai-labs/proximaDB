= TD-CI-5: The `feature-matrix` CI job has no `timeout-minutes`, so a hang holds a runner for 6 hours

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Partial: `feature-matrix` bounded (`timeout-minutes: 110`, sized from a measured max of 53 min over 14 runs) and every job in every workflow given a timeout (#1977 for `ci.yml`, #1967 for release jobs); open: no guard stops a *newly added* job inheriting the 360-minute default (step 3).**
| Priority | **MEDIUM.** It does not produce wrong results, but it converts a transient runner problem into a multi-hour block on a shared, finite resource — and `ci-success` depends on `feature-matrix`, so the PR cannot merge while it hangs.
| Component | `.github/workflows/*.yml`
| Relates to | Mandate #7 (CI runners are a shared finite resource); link:TD-CI-1-rust-test-compile-bottleneck.adoc[TD-CI-1]
|===

== History (shipped)

On PR #1956 the `cloud-full+onnx` leg hung for 121 minutes with 74/75 jobs green. Re-running only that job passed, which
establishes it as transient infra rather than code. The bug class is "the default is 6 hours and nobody noticed". So the fix was
applied across every workflow, not just this job: a `runs-on:` vs `timeout-minutes:` audit on 2026-10-15 finds zero unbounded jobs.

== Open residual

3. Consider whether a repo- or workflow-level default is expressible, so a newly added job inherits
   a bound instead of the 360-minute default. If it is not, a check in
   `scripts/check_deterministic_commit_contract.py` (with tests) that fails any job declaring
   `runs-on:` without `timeout-minutes:` would make the audit above durable.
