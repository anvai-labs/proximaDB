== The mechanism

`utoipa` serialises the OpenAPI document through `serde_json`'s map type. That
type is chosen by a **feature**:

* `serde_json/preserve_order` ON  -> `serde_json::Map` is an `IndexMap`
  (insertion order)
* OFF -> it is a `BTreeMap` (**alphabetical**)

Nothing in our manifests requested it. It arrived **incidentally**, from
`datafusion-physical-plan v55.0.0` enabling it transitively:

----
serde_json feature "indexmap"
  └── serde_json feature "preserve_order"
        └── datafusion-physical-plan v55.0.0
----

So the key order of a *generated, committed* artifact — the contract every SDK
is generated from — was a function of feature unification. Any dependency change
that perturbed it flipped the whole document to alphabetical order.

**The protection we thought we had does not exist.** Root `Cargo.toml` declares
`utoipa = { ..., features = ["axum_extras", "preserve_order", "yaml"] }`, but
upstream in utoipa 5.5.0:

----
preserve_order = []
----

It is an **empty feature list**. It forwards nothing to `serde_json`. We had
been declaring a no-op and believing it was the switch.

== How it presented

The drift gate failed with what looked like a wholesale rewrite: generated spec
starting at `components:`, committed starting at `openapi:`. Five hypotheses
were tested and killed before the real one — recorded because each is the
obvious guess:

[cols="3,2", options="header"]
|===
| Hypothesis | Killed by

| A serializer version bump reordered maps | `indexmap`, `serde_yaml`, `serde_norway`, `utoipa`, `serde` all byte-identical across the two sides
| Stale base (as first assumed for #1989) | `develop` passes the gate on both recent commits
| Our branch edited the spec | committed spec byte-identical to develop's; no handler touched
| Generator non-determinism | 3 consecutive regenerations produced one hash
| `utoipa`/`indexmap` feature drift | `cargo metadata` showed identical feature sets for both
|===

The decisive step was comparing **`serde_json`** feature sets, which had not
been checked because `utoipa`'s own `preserve_order` looked like the switch:

----
develop:  serde_json 1.0.151 features=[default, indexmap, preserve_order, raw_value, std]
branch:   serde_json 1.0.151 features=[default,                           raw_value, std]
----

Two *unrelated* changes both triggered it — `datafusion 55.0 -> 55.2`, and
declaring `sqlparser 0.62` — because neither causes reordering; each merely
perturbs unification until the incidental activation drops. Both produced the
**same** reordered hash, which is the fingerprint of a binary feature flip
rather than a content change.

== Measured blast radius

Semantically identical in every case (`yaml.safe_load` equality for the spec;
identical sorted line multisets for the SDK):

----
docs/openapi/proximadb-openapi.yaml              9,248 ins / 9,248 del
clients/nodejs-embedded/src/generated/schema.ts  8,606 changed lines (9,496 -> 9,496)
clients/python/.../_generated/rest               474 files / 2.9 MB   (not measured)
clients/rust/src/genrest.rs                      2.0 MB single file   (not measured)
----

Mandate #15 requires a spec change to regenerate every SDK in the same PR, so
the churn cannot be taken piecemeal.

== The fix

Declare it where it is load-bearing, so it is ours rather than inherited:

[source,toml]
----
serde_json = { version = "1.0", features = ["preserve_order"] }
----

**#2006 landed this for the root `[dependencies]` independently**, while this was
being diagnosed from the other direction -- two sessions converging on the same
one-line fix. Its commit also names the upstream trigger precisely: apache/
datafusion's *"Remove serde_json/preserve_order feature from library crate"*. So
55.2 did not break anything by accident; DataFusion deliberately stopped
supplying a feature we were silently depending on.

`[workspace.dependencies]` was still bare after #2006, and **68 members inherit
that entry** via `serde_json.workspace = true`. Cargo's feature unification makes
the built artifact correct regardless, so this is belt-and-braces rather than a
live bug -- but it puts the guarantee in the entry those crates actually read.

Verified: the drift gate passes, the committed spec is untouched, **and it holds
with `datafusion 55.2` applied** — which is what unblocks #1989, whose failure
on this gate was previously (and wrongly) attributed to a stale base.

== Follow-up: make it un-droppable

The fix is correct but silent — nothing fails if a future edit removes it. Add a
guard asserting `serde_json` is declared with `preserve_order` wherever the
OpenAPI document is serialised, beside the other workflow/manifest controls in
`scripts/check_deterministic_commit_contract.py`, with unit tests (a check added
there without tests shipped four evasions in #1993).

A stronger variant, if cheap: have `tests/openapi_spec_gen.rs` assert the
document's top-level key order is the struct order (`openapi` first, not
`components`), so the failure names the cause instead of printing a 9k-line
diff. That converts a confusing gate failure into a one-line diagnosis, which is
the actual cost paid here.
