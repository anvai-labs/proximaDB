= TD-PKG-2: the Windows MSI installs no service and splits config from the shortcuts

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-10-25).** `proximadb.wxs`:

* installs a `proximadb` Windows service (`ServiceInstall` + `ServiceControl` in the component that installs the exe), running the server with `--config "[CONFIGDIR]config.toml" --data-dir "[DATADIR]data"`;
* installs `config.toml` into `C:\ProgramData\ProximaDB\` (where the shortcuts and the service read it) instead of next to the binaries;
* the Start-menu server shortcut runs with the same arguments and `WorkingDirectory=DATADIR`, so the non-elevated `./log` write succeeds and data lands under `C:\ProgramData\ProximaDBData\data` (the `--data-dir` rebase moves the shipped `/tmp` roots).

The `.wxs` is validated by build (the MSI build compiles it) and by review. The release smoke's `windows` job installs the MSI with `msiexec /qn` on windows-latest; with `ServiceInstall Start="auto"` and `ErrorControl="normal"`, Windows starts the service during install, so **a service that fails to start now fails msiexec and reds the release smoke** — the service start is a release gate, exercised on first release. What is not automated: a client round-trip against the installed service. The rolling log lives under the data dir (`<data>/log`) rather than a cwd-relative `./log`, which for a service (no working directory) would have been `System32\log`. Windows path semantics of the rebased `file://` roots get their first real exercise in that same smoke. The WiX `ServiceInstall` pattern (service element inside the exe component, one file per component) is the canonical one.
| Priority | **MEDIUM** — the documented Windows service commands fail.
| Component | `deploy/packaging/wix/proximadb.wxs`
|===

== Problems

* There is no `ServiceInstall` element, so no `proximadb` Windows service exists:
  `Start-Service proximadb` fails.
* `config.toml` is installed next to the binaries in `C:\Program Files\ProximaDB\`, while
  `C:\ProgramData\ProximaDB\` (the config directory the Start-menu shortcuts point at) is created
  empty.
* The MSI creates `C:\ProgramData\ProximaDBData\` empty, but the shipped `config.toml` is the
  development config: every root is `/tmp/proximadb/…`, so data lands under `\tmp\proximadb\`
  on the current drive.
* The "ProximaDB Server" Start-menu shortcut runs from `C:\Program Files\ProximaDB\`, where a
  non-elevated user cannot create `./log`, so the server's log appender panics at startup.

== Fix

Install a Windows service (`ServiceInstall` + `ServiceControl`) that runs the server with an
explicit `--config`, place the config where the shortcuts and the service expect it, and add an
install-and-start smoke to the Windows release job.
