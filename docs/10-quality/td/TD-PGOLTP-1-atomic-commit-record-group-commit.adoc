== Premise correction (2026-10-16, filing rule 7)

**What this TD originally claimed.** The atomic unit was `disk_manager.rs::write_batch`; pgwire
OLTP fsync semantics were governed by `sync_mode = PerBatch`; and group commit should generalise
`batch_sync_coordinator`.

**What is true.** Verified by tracing `DmlService` →
`CatalogRoutingTableRecordStore` → `DirectWalTableRecordStore::write_mutations` →
`FramedTableWalAppender::append_operations`:

* Relational pgwire writes never touch the collection WAL (`disk_manager`, `sync_mode`,
  `batch_sync_coordinator`). `BatchSyncCoordinator` has **no production caller**.
* They go to **one shared framed log**, `<data_dir>/pgwire/canonical-records.wal`, for every table
  and tenant. A multi-table transaction therefore needs no cross-file coordination.
* `append_operations` wrote **one frame per operation**, then a single `sync_data`. A torn write
  could therefore leave a durable **prefix of one multi-row INSERT**, a second defect beyond the
  COMMIT one.
* A full-length tail of zero bytes, as left by a crash that extended the file before its data
  blocks landed, made boot **fail** rather than being treated as a torn tail.

**What it changes.** The group frame lives in `canonical_wal.rs`, not in `disk_manager`.
Cross-session group commit (S3) must be built in `FramedTableWalAppender`.

== Design as built (S1–S2)

1. **Group frame** (`FRAME_VERSION_GROUP = 2`). The header is unchanged. The payload is a msgpack
   `Vec<CanonicalWalEntry>` with one CRC, and each entry carries its own tenant. Readers expand it
   into ordinary entries, so replay, CDC and every `CanonicalOperation` consumer are unchanged.
   Group sequences must be contiguous from the header, or decoding fails. The format is
   mixed-read-safe: version 1 and version 2 coexist. Binaries that predate it reject version 2
   rather than apply part of a transaction. **A single version-2 frame blocks downgrading the
   binary** (the pgwire WAL is not compacted).
2. **Torn tail.** An incomplete trailing frame (existing behaviour) and an **all-zero**
   remainder are truncated. The dropped bytes are first copied, best effort and fsynced, to
   `canonical-records.wal.torn-<offset>-<nanos>`, and
   `proximadb_canonical_wal_torn_tail_truncations_total` is incremented.
   * These two rules apply to **every** framed WAL, including the system catalog's. Truncating an
     all-zero tail, where boot used to fail, is a deliberate change to the default path.
   * A complete frame with bad magic, a bad CRC, a bad payload or a bad sequence stays a hard error.
     A frame that is still incomplete when the file ends (including a corrupt `payload_len` in a
     frame that is not the last) takes the incomplete-frame path. That is pre-existing, and it is
     the reason point 2a matters.
2a. **Failed appends never leave junk** (review finding 1).
   * The appender records the file length before writing.
   * If the write fails part-way (for example ENOSPC), the file is truncated back to that length
     and fsynced, still under the append lock, and the error is a plain "nothing was written".
   * If the rollback fails, or `sync_data` itself failed (fsyncgate), the appender is **poisoned**:
     every later append is refused until a restart. The error is typed
     `WalAppendIndeterminate` and reported as 08007, never as "nothing committed".
   * Debug-only fault seams `fail_mid_write` and `fail_sync` test both paths.
3. **Staging decorator.** At COMMIT the buffered statements re-execute through the unchanged
   `DmlService` against `StagingTableRecordStore`. Writes are captured. Reads, unique checks and
   scans see base ∪ staged, so INSERT-then-UPDATE of one row works. Nothing is written until
   commit.
4. **`commit_atomic`.**
   * It re-validates INSERT-absent / UPDATE-exists against current partitions in staged order,
     because writers that do not take op-locks exist. A mismatch fails with `40001` and nothing
     becomes durable.
   * It then makes **one** `append_operations_atomic` call and applies the batches with positional
     LSNs.
   * **If the apply fails after the durable append** (review finding 2), the store is **poisoned**:
     every read and write is refused until a restart replays the WAL, so a half-applied commit is
     never served. pgwire sends **FATAL 08007** and closes the connection, so no ROLLBACK tag can
     follow a transaction that committed, and caches are invalidated whenever the commit may be
     durable.
   * The routing store refuses a commit that spans two stores (`0A000`).
   * All of these are typed errors (`TxnSerializationConflict`, `CommitOutcomeUnknown`,
     `AtomicCommitUnsupported`); no error text is string-matched.
4a. **PostgreSQL error semantics** (review finding 9).
   * A statement that fails at COMMIT keeps its own SQLSTATE (23505, 23503, …); 25P02 is only the
     fallback.
   * A statement timeout is 57014.
   * After any non-FATAL COMMIT failure, the transaction is over and the session returns to idle
     (`I`), as in PostgreSQL.
5. **Locks.** COMMIT holds the sorted op-locks of every buffered table and its cascade closure for
   the whole commit. The forked service asserts membership instead of re-acquiring, and fails
   closed if a table is not held.
6. **Cancellation.** The durable step runs in its own task, outside the statement timeout, so a
   disconnect cannot split the append from the apply.
6a. **Overlay keying and filtered scans** (review findings 6 and 7). Staged rows are keyed by the
    durable store's partition id (the stable object id under ADR-031 keying), not by bare name.
    Filtered scans push the predicate down to the base and overlay matching staged rows, rather
    than materialising whole tables while the commit holds their locks.
7. **Refusals with the gate on.** `INSERT … SELECT` / `INSERT OVERWRITE` inside a transaction are
   refused with `0A000`, because the table-write executor would bypass staging. The
   `oltp-integrity` key store is also refused with `0A000` (TD-PGOLTP-3).
8. **Fail closed.** With the gate on, failing to open or replay the shared canonical WAL is fatal at
   boot (it previously only `warn!`ed).

**Guarantee.** Crash atomicity and all-or-nothing, **not isolation**. Concurrent readers can
observe a commit mid-apply until TD-PGOLTP-4.

**Statistics are transactional (review finding 8, fixed).** The transaction fork queues row-count,
null-count, min/max and NDV bumps (`DeferredStatBump`) instead of applying them. The COMMIT routine
applies the queue only after `commit_atomic` succeeds and drops it on failure, so a failed
transaction never moves planner statistics. Covered by
`transaction_fork_defers_statistics_until_commit`.

**Test seams.** `PROXIMADB_TEST_TXN_COMMIT_FAULT` is compiled out of release builds
(`cfg!(debug_assertions)`), so a production server cannot be aborted through it (review
finding 10).

**S4a: autocommit, narrowed after the third review (2026-10-16).** With the gate on, the canonical
WAL writes each `write_mutations` call as one group frame. An autocommit statement that makes a
**single** write call is therefore already crash-atomic on the direct path: INSERT, UPDATE, UPSERT,
and a DELETE with no ON DELETE children. Only a **DELETE whose cascade closure is non-empty**
writes several tables in several calls. That one runs as a one-statement atomic unit through the
shared core (`services::atomic_txn`, also used by COMMIT), so child and parent rows commit
together. The first S4a cut staged every autocommit statement; narrowing removed a tenant-wide
catalog scan per INSERT and most of the defects below.

**Exceptions, all documented gaps:**

* **INSERT … SELECT is not atomic** (fourth review, finding 1). The table-write executor writes
  1024-row batches, one `write_mutations` call per batch, and checks UNIQUE/FK per batch. A large
  INSERT … SELECT can therefore leave a partial insert on a crash or a mid-statement conflict.
  That is pre-existing; staging it needs a staging-aware executor. A store PK conflict on this
  path is also still untyped (not 23505).
* **A cascading DELETE that cannot form an atomic unit runs non-atomically on the direct path.**
  This happens when lock-set resolution fails, or when the unit is refused as unsupported (a
  vector child, the `oltp-integrity` key store). The fallback is logged at `warn`.
* **With the gate on, every DELETE pays the cascade-closure catalog scan twice**: once to decide
  the route, once inside `execute_delete`. RESTRICT- and SET NULL-only children also route
  atomically.

Third adversarial review (of `706dd630e` and `3467cf1ec`) — findings and resolution:

* **F1** Vector-profile tables were refused with `0A000` on autocommit. They now take the direct
  path. An atomic unit that is refused as unsupported (nothing written) retries on the direct
  path. An explicit transaction into a vector table still fails closed with `0A000` rather than
  committing partially (`vector_tables_keep_working_with_the_gate_on`).
* **F2** An outcome-unknown autocommit on the simple-query path was swallowed: FATAL, then ERROR,
  then ReadyForQuery, and the connection stayed open. `handle_query` now propagates it and the
  connection closes (`autocommit_outcome_unknown_is_fatal_and_closes_the_connection`).
* **F3** With `oltp-integrity`, every autocommit was refused. Now fixed by the narrowing plus the
  unsupported fallback.
* **F4** Autocommit INSERT … SELECT was staged. It now takes the direct path, so the
  `fork_for_transaction` doc comment is true again.
* **F5** Cross-pod DML leases were released before the durable write. A fork now **retains** its
  lease guards (cascade children included), and the commit task releases them after
  `commit_atomic` (`transaction_fork_retains_dml_leases_until_released`, with a second pod as the
  competitor and a typed conflict asserted).
  * **Qualified (fourth review, finding 3, pre-existing):** DML leases are pod-reentrant and not
    reference-counted.
  * A same-pod writer can therefore take the same lease reentrantly. When the unit releases it,
    the durable lease is tombstoned while that writer still runs.
  * Retention widens that window. Fix: reference-count per (pod, scope), or take leases after the
    op-locks.
* **F6** Deferred statistics were applied after the op-locks were dropped, so concurrent bumps
  were lost. They are now applied inside the commit task, before the locks are released, which is
  also cancellation-safe.
* **F7** The lock set walked the cascade closure for every statement kind. It now does so only for
  DELETE.
* **F8** Setup/commit failures reported 25P02 on autocommit. They now use the caller's fallback
  (XX000 on autocommit; 25P02 on COMMIT).
* **F9** A poisoned appender's refusal was reported as outcome-unknown. A new
  `WalAppenderPoisoned` type maps it to "nothing written".
* **F10** Test fixes:
  ** faults are armed before server start (no `set_var` racing server threads);
  ** the duplicate-key code is asserted as `23505`;
  ** fault-dependent tests skip in release builds, where the debug-only seam does not exist.
* **F11** Caches are invalidated for every table a unit wrote, cascade children included, for both
  COMMIT and autocommit.

The REST `/api/v2/sql` and gRPC `ExecuteQuery` DML paths still call `DmlService` directly.

**Pre-existing defects surfaced by the new tests** (each fails identically with the gate off):

* **Fixed: a duplicate primary key reported `42P01`, not `23505`, in every tenant-scoped session.**
  * The existing-row PK probe in `enforce_row_write_constraints_inner` passed `tenant_context =
    None`, so it read the default partition and missed the row.
  * The duplicate then surfaced as the store's untyped `INSERT_CONFLICT` ("Insert failed", 42P01).
  * Fix: the probe uses the session's tenant, and a store `INSERT_CONFLICT` is mapped to the typed
    unique violation (23505) as a backstop.
  * Proven by `autocommit_statements_keep_their_tags_and_sqlstates`, which asserts `23505`.
* **Not fixed here: DELETE on a vector-profile table reports success and leaves the row
  visible**, with the gate on or off (a mandate #16 violation).
  * Tracked in TD-PGWIRE-VECDEL-1, with an `#[ignore]`d executable reproduction.
  * An attempted "write-side fix" (sending DELETE runs to `delete_records_with_tenant_context`)
    was **reverted** after the fourth review. The old path already wrote a tombstone, so the change
    was unproven. Its blast radius was also every relational DELETE on `DmlService::new` surfaces,
    and the reproduction still failed with it.
* **Not fixed here: a pgwire `CREATE TABLE … VECTOR(n)` gets a 1-dimension backing collection.**
  This is TD-PGWIRE-COPY-1. The vector-route test uses `VECTOR(1)`.

**Known gaps.**
* UNIQUE races with writers that take no op-locks (INSERT…SELECT, DDL, graph merge-back)
  pre-date this work and remain.

== Acceptance (evidence)

* Unit tests (`canonical_wal.rs`, `txn_staging.rs`):
  ** group round trip
  ** mixed v1/v2 replay order
  ** a torn group drops the whole group
  ** zero tail quarantined and truncated
  ** mid-file corruption still an error
  ** non-contiguous group rejected
  ** fenced appender refuses
  ** per-appender flag
  ** staged visibility, INSERT→UPDATE, delete hiding, merged limit, unique conflicts
  ** one append per commit, applied in order
  ** concurrent-insert abort with nothing durable
  ** router refusing a split commit
* pgwire e2e (`tests/pgwire_atomic_commit_e2e.rs`):
  ** a mid-COMMIT failure leaves **nothing** durable (red on the legacy path with
     `PROXIMADB_OLTP_ATOMIC_COMMIT=0`)
  ** multi-table all-or-nothing
  ** INSERT then UPDATE in one transaction
  ** `fail_before_append`
  ** INSERT…SELECT refusal
* Server-binary crash matrix (`apps/proximadb-server/tests/oltp_reattach_e2e.rs`):
  ** `abort_after_append` → the whole transaction recovered
  ** `torn_append` → boots, none of it, earlier commits intact, tail quarantined
* MinIO smoke (`scripts/smoke_oltp_reattach_minio.sh`): a bank-transfer workload preserves the
  total-balance invariant across forced failures, reattach and crash.

== Remaining slices

. S3: cross-session group commit in `FramedTableWalAppender` (one fsync per batch of concurrent
  commits), with metrics (`proximadb_wal_group_commit_size`, fsync latency).
. S4a ✅: autocommit pgwire DML through the same routine (one write path, ADR-095 D3).
. S4b: route the REST/gRPC DML paths through it too, then flip the default once the TD-PGOLTP-6
  ratchet is green.
