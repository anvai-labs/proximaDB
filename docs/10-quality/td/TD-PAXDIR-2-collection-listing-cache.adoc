== Problem

Every vector query lists the collection data directory to find its segments
(D7 made it one LIST per query; it used to be two). On the P5b gate bed
(SIFT1M, MinIO + 50 ms RTT) that LIST is a full sequential wave, so a warm
query — every byte it needs already cached — still takes the LIST plus at
least one wave: measured 2 waves at p50, against the design's 0–1
(link:../../history/evidence/P5B_D7_SIFT1M_GATE_RUN_2026_10_25.adoc[artifact]).

== Why it is not a simple cache

A cached listing hides a segment published after it was taken. A flush moves
rows out of the memtable into a new segment, so a query that misses that
segment loses those rows — a read-after-write violation (mandate 16). A
compaction swaps inputs for an output; a stale listing would read retired
inputs (already filtered by the TD-COMPACT-13 pending set, but deleted
objects then fail) or miss the output.

== Original plan (retained contract)

* A per-collection listing cache with a generation, invalidated **after**
  every flush publish and every compaction retire commits, through the
  existing `CacheInvalidationCoordinator` (the write path already invalidates
  the query and plan caches post-commit).
* Ordering: invalidate after the new object is durable and before the
  memtable rows it carries become unreachable in memory, or keep the memtable
  rows visible until the next listing is taken.
* Multi-process deployments: a process does not see another's flush. Either
  bound the cache by a short TTL there, or gate it to single-writer
  deployments until TD-PAXMETA-1 lands a manifest with a CAS commit.
* Default OFF behind an env gate; read-after-write tests (insert → flush →
  query sees the rows; compaction → query reads the output) are the gate.

== Remaining foundation gate (2026-11-02)

Publication/retirement invalidation landed in #2385. The foundation follow-up adds
resolver-based listing identity and cancellation coverage inside coordinator cleanup.
The combined storage/cache/embedded cohort passed 164/164 tests after #2385, including
legacy relative-path retirement suppression on warm and fresh listings. Fresh review is
CLEAR; cloud build/lint and 88 graph integration tests passed on `f68674e44`, before the
subsequent WAL-only #2361 rebase. Hosted CI remains
a separate acceptance gate. Required acceptance remains:
compaction-success invalidation through the existing publication
path, including post-publish cleanup/error branches: a committed output must become visible
even if a later best-effort step fails. A lookup begun before invalidation must not reinstall
its stale result. Failed publication attempts may conservatively invalidate; admission
decline before publication keeps a warm listing. Bound memo lifetime/capacity.

The cancellation regression covers publication already completed before the future is
dropped during coordinator cleanup. Backend I/O that completes after its future is dropped
(for example a queued blocking rename) still requires completion-owned invalidation or
cache bypass while publication is unresolved; the exit guard does not close that gate.

Derive keys and invalidation from the filesystem resolver's source identity. Preserve exact
object keys and backend endpoint namespaces, while matching the actual local-path resolution
semantics. Prefix strings, a guessed `/app` base or a generic slash normalizer are insufficient.
Persistent byte-cache/protection consumers are the related TD-TIER-1 acceptance gate; fixing
listing identity does not close those consumers. TTL still does not prove remote-writer
strong freshness. No per-flush generic manifest or new catalog authority is introduced.

== Acceptance

* Warm vector queries take ≤ 1 wave beyond discovery with the cache on, and
  0 LIST requests on a cache hit (`proximadb_object_store_requests_total`,
  `proximadb_pax_query_waves`).
* No read-after-write regression: flush and compaction tests pass with the
  cache on.
