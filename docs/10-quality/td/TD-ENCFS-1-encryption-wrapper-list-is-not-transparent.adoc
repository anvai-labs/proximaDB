= TD-ENCFS-1: The encryption filesystem wrapper renames objects on write but not on `list`

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-06, found by adversarial review of TD-USUB-1's segment discovery — the first code to depend on a listing round-tripping back to a readable path.
| Priority | **HIGH when filesystem encryption is configured**, which is a supported deployment (`FilesystemFactory::maybe_wrap_with_encryption` wraps every filesystem it hands out whenever `global_options.encryption` names an env var). Unreachable with encryption unconfigured.
| Component | `crates/storage/proximadb-storage-encryption/src/filesystem.rs` (`actual_path`, `list`)
| Relates to | TD-USUB-1 (segment discovery, which fails closed on the symptom), mandate #1
| Blocked by | Nothing.
|===

== The finding

`EncryptedFilesystem` is meant to be a transparent wrapper. It is not, because its `list` leaks
its own name mangling:

* `actual_path` (`:74-81`) appends `encrypted_extension` — `Some(".enc")` by default (`:44-60`) —
  to the path of every `read`, `write`, `write_if_absent`, `delete` and `exists`.
* `list` (`:300-302`) is a bare `self.underlying.list(path)`, with no un-mangling of the returned
  `DirEntry::name` / `url`.

So an object written as `foo/bar.parquet` is stored as `foo/bar.parquet.enc` and **listed as**
`foo/bar.parquet.enc`. Any caller that lists a prefix and then reads what it found gets a path
that `actual_path` will mangle a second time (`foo/bar.parquet.enc.enc`) or, if it filters by
extension first, does not recognise its own objects at all.

This breaks the wrapper's contract for every list-then-read caller, not just the one that found
it. A caller cannot compensate, because the extension is wrapper-private configuration.

== How it surfaced

TD-USUB-1's spill-segment discovery identifies its objects by name
(`spill-{seq:016x}.parquet`). Under configured encryption the listing reports
`spill-{seq:016x}.parquet.enc`, which is not spill-shaped, and every consequence is silent:

* discovery finds **no** segments, so flushed rows read as absent and `delete_record` records no
  tombstone (a resurrection path, mandate #16a);
* the resumed sequence restarts at 0, so the next flush re-issues `spill-0000000000000000.parquet`
  and `write_if_absent` collides with the existing underlying object — **every flush after a
  restart fails, permanently**;
* `purge_durable_objects` deletes nothing and returns `Ok(())`, so DROP leaks every segment.

== Interim mitigation already in place

The spill store does not attempt to compensate; it **fails closed**. `is_mangled_spill_segment`
detects a spill name carrying one extra extension and refuses to serve the partition rather than
report it empty, naming this TD in the error
(`a_wrapper_mangled_segment_name_refuses_rather_than_reading_empty`). That converts silent data
loss into a loud refusal; it does not make the spill store work under encryption.

== How to apply

1. Make `list` transparent: strip `encrypted_extension` from each returned entry's `name` and
   `url` when present, so a listing round-trips through `read`/`delete`.
2. Audit the wrapper's other passthrough methods for the same leak (`metadata`, `read_range`, and
   any directory-walking helper) — the bug class is "forgot that `actual_path` applies here too".
3. Add tests to that crate, which currently has **none** in `filesystem.rs`: a write→list→read
   round-trip asserting the listed name is the caller's name, and a delete-by-listed-name.
4. Once transparent, relax the spill store's detector to a plain skip, or keep it as a guard
   against future wrappers and note that it should no longer fire.
