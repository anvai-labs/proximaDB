= TD-ENCFS-1: The encryption filesystem wrapper renames objects on write but not on `list`

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **RESOLVED 2026-10-07** by `fc6fefe32` (#1954): `EncryptedFilesystem::list` now reports logical names, stripping `encrypted_extension` from `name`/`url`/`metadata.path` for files (directories are never mangled, since `create_dir` passes paths through). Pinned by five tests in that crate, which previously had none — including one that proves the round-trip by recording which path `exists` probes, and one that reproduces the WAL-manifest filter directly. == The finding

`EncryptedFilesystem` is meant to be a transparent wrapper. It is not, because its `list` leaks
its own name mangling:

* `actual_path` (`:74-81`) appends `encrypted_extension` — `Some(".enc")` by default (`:44-60`) —
  to the path of every `read`, `write`, `write_if_absent`, `delete` and `exists`.
* `list` (`:300-302`) is a bare `self.underlying.list(path)`, with no un-mangling of the returned
  `DirEntry::name` / `url`.

So an object written as `foo/bar.parquet` is stored as `foo/bar.parquet.enc` and **listed as**
`foo/bar.parquet.enc`. Any caller that lists a prefix and then reads what it found gets a path
that `actual_path` will mangle a second time (`foo/bar.parquet.enc.enc`) or, if it filters by
extension first, does not recognise its own objects at all.

This breaks the wrapper's contract for every list-then-read caller, not just the one that found
it. A caller cannot compensate, because the extension is wrapper-private configuration.

== How it surfaced

TD-USUB-1's spill-segment discovery identifies its objects by name
(`spill-{seq:016x}.parquet`). Under configured encryption the listing reports
`spill-{seq:016x}.parquet.enc`, which is not spill-shaped, and every consequence is silent:

* discovery finds **no** segments, so flushed rows read as absent and `delete_record` records no
  tombstone (a resurrection path, mandate #16a);
* the resumed sequence restarts at 0, so the next flush re-issues `spill-0000000000000000.parquet`
  and `write_if_absent` collides with the existing underlying object — **every flush after a
  restart fails, permanently**;
* `purge_durable_objects` deletes nothing and returns `Ok(())`, so DROP leaks every segment.

== The mitigation that preceded the fix, now redundant

Before `fc6fefe32` the spill store did not attempt to compensate; it **failed closed**.
`is_mangled_spill_segment` detects a spill name carrying one extra extension and refuses to serve
the partition rather than report it empty, naming this TD in the error
(`a_wrapper_mangled_segment_name_refuses_rather_than_reading_empty`). That converted silent data
loss into a loud refusal; it did not make the spill store work under encryption.

With the wrapper transparent, that detector is **redundant defence-in-depth rather than a live
mitigation**, and it is deliberately kept: it would still trip on a future wrapper that renames
objects on write without un-mangling `list`, and on the two shapes this one's fix does not cover
(a two-dot extension such as `.enc.v2`, or a dotless one), both reachable only through
`with_extension`, which has no callers.

== What was done

1. `list` made transparent — strips `encrypted_extension` from each entry's `name`, `url` and
   `metadata.path`, for files only (`create_dir`/`create_dir_all` pass paths through, so a
   directory name never carries the extension and is not ours to rewrite).
2. **The other passthrough methods were audited and are already correct**, which is worth recording
   because "forgot that `actual_path` applies here too" was the expected bug class and it is not
   present: `read`/`read_range`/`read_ranges` route through `read_encrypted`; `write`,
   `write_if_absent`, `write_atomic`, `append`, `sync_file`, `delete`, `exists`, `copy` and
   `move_file` all route through `actual_path`; `metadata` both uses `actual_path` AND rewrites the
   returned `metadata.path` back to the logical name; `open_file` always errors and `get_mmap`
   always returns `Ok(None)`, so neither has path semantics. The default `remove_dir_all`, the one
   trait method that consumes `list`, now hands `delete` a logical url, which mangles correctly.
3. Five tests added to a file that had none, including a round-trip proven by recording which path
   `exists` probes, and one that reproduces the WAL-manifest extension filter directly.
4. The spill store's `is_mangled_spill_segment` is **kept** rather than relaxed, now documented as
   redundant defence-in-depth — see the section above for why.

== Residual, deliberately not fixed

The wrapper marks encrypted files by extension, so a file genuinely named `x.enc` that is NOT
encrypted is indistinguishable from an encrypted `x`. That ambiguity is inherent to extension
marking and predates this work. Likewise the detector in the spill store catches only ONE extra
dot-extension, so `.enc.v2` or a dotless `enc` would evade it — both reachable only through
`EncryptedFilesystem::with_extension`, which has no callers in the repo.
