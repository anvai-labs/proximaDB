== History (shipped)

`tests/native_tpch_q18_q20_e2e.rs` failed flakily on a fresh server with `[42P01] DDL failed: Table
'customer' already exists`. It was **not** a converter regression: `Config::default()` sets
`storage.metadata_url = "file://./metadata"`, and `resolve_default_catalog_backend` places the WAL-backed
SystemCatalog at **`<process-cwd>/metadata/system-catalog.wal`**, regardless of `server.data_dir`. Every
unanchored harness therefore shared one catalog WAL per working directory (and concurrently, under
nextest), and run N+1 replayed run N's DDL. Only literal names a previous run created collided, which is
why `customer` failed and `txn_t_<nanos>` passed.

Lesson that still applies: the commit bisect that blamed #1852 was **fouled by leaked machine state**: the
parent-commit PASS runs seeded the WAL that the next commit's runs replayed.

Fix (#1898): the 10 harnesses that CREATE literal TPC-H/TPC-DS-named tables set
`config.storage.metadata_url = format!("file://{}", tmp.path().join("metadata").display())`;
`native_tpch_q18_q20_e2e` joined the `rust-integration-test-pgwire-accuracy` lane.
Evidence: with a deliberately poisoned workspace-root WAL, 5/5 passes; without the anchor, 2/3 failures.

== Residual

* ~55 other harnesses boot `db.start()` without anchoring `metadata_url`. They do not create
  colliding literal table names today, so they are dev-machine-flake carriers only; anchor them
  when touched.
* The production-shaped version of this hazard stands: a **relative** `metadata_url` makes the
  catalog location depend on the process CWD, so two servers started from the same directory
  share (and can corrupt) one catalog WAL. The principled fix — anchor a relative
  `metadata_url` to `server.data_dir` inside `resolve_default_catalog_backend` — moves the
  on-disk catalog location for default-config deployments and needs its own migration story
  (mixed-read-safe per the storage-format mandate). Filed here as the pointer; not done in #1898.
