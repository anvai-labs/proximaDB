== History (shipped)

* **Gap.** One `{tenant}::{collection}` fold was load-bearing for three modalities with different correct
  isolation mechanisms. A naive de-fold either leaked entity vectors across tenants (clean name, shared
  collection; fusion seed over-returns) or broke fusion (scoped name, pre-existing collection not found).
* **Fix (#692).** Graph leg routes through `for_tenant` with clean names. Vector leg: writes use
  `insert_batch_with_tenant_context`, and a new `unified_search_native_with_tenant_context` serves the
  fusion seed read — vectors are `TenantContext`-partitioned with CLEAN names, never name-folded (the
  co-design rule). `GraphFusionParams.tenant` scopes both fusion legs from one source (gRPC entity,
  gRPC fusion, REST `fusion_search_v2`). Provenance documents use `scoped_document_collection`.
* **Evidence.** Unit test `fusion_tenant_scopes_both_legs`.

== Remaining (open)

. **Collection lifecycle:** define/where entity + fusion vector collections are created and ensure
  creation is tenant-consistent with the read path (resolve the "collections pre-exist" assumption).
  The entity vector/fusion path was found untested end-to-end: embedding insert is best-effort
  (`warn`-on-fail), and no collection-creation path exists in the entity handlers/orchestrator —
  collections are assumed pre-created out-of-band.
. **Backstop + evals:** add an entity/fusion isolation test (two tenants, same clean collection, no
  cross-tenant seed or result; vector storage physically separated); gate `fusion_search_v2` with
  the same rubric. (The general `fusion_search_v2` path has no per-hit `for_tenant().get_node`
  re-fetch backstop, unlike the entity orchestrator.)

== Constraints

* Keep net `proximadb_v1` references non-increasing (TD-123 ratchet, baseline 2917) — prefer v2
  proto types in any new code/tests.
* Vector-format / partition-key changes must be mixed-read-safe (no flag-day), per the
  storage-format-migration mandate.
