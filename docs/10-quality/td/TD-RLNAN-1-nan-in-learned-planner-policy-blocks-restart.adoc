= TD-RLNAN-1: a NaN in the learned query-planner policy stops the server from restarting

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Resolved (2026-10-18).** Features, rewards and weight updates are kept finite, and an unreadable policy file is set aside at boot instead of aborting it. Pinned by `empty_collection_update_keeps_policy_loadable`, `feature_vector_is_finite_for_degenerate_state` and `unreadable_policy_is_set_aside`.
| Priority | **HIGH** — after a normal session, `docker restart` left a 0.4.1 server unable to boot.
| Component | `src/query/rl_planner/` (`state.rs` feature vector, `bandit.rs` updates, `mod.rs` persistence), `src/database.rs` boot
| Relates to | roadmap v0.5 "Correct and durable"
|===

== Problem

A review reproduced it on the 0.4.1 image: after a session, the restarted server exited with
`Error: invalid type: null, expected f64` while loading `/tmp/proximadb/data/rl_policy.json`.

* The planner's feature vector took `log10(collection_size)`, which is `-inf` for an empty
  collection, and divided by empty histories (`0/0`). A gradient step with a non-finite feature
  turned a learned weight into NaN.
* `serde_json` writes NaN as `null`; reading `null` back into an `f64` fails.
* Boot called `load_policy(...).await?`, so the unreadable file aborted startup. The policy is
  learned tuning state, not user data.

== Fix

* `as_feature_vector` clamps the log input and replaces any non-finite feature with 0.
* `BetaDistribution::update` ignores non-finite rewards and clamps to `[0, 1]`;
  `ContextWeights::update` skips any step that would make a weight non-finite.
* Boot sets an unreadable policy aside as `rl_policy.json.unreadable-<ms>`, logs a warning and
  starts with a fresh policy (`set_aside_unreadable_policy`). Existing 0.4.x files with `null`
  weights are handled the same way. If even the move fails (read-only data directory), boot logs a
  warning and continues with an in-memory policy.
* The policy file is always `<data_dir>/rl_policy.json`. It previously used `[rl_planner]
  log_path` when set, which is the execution logger's JSONL file, so the policy never parsed back.
* `ContextualBanditPlanner::update` ignores non-finite rewards and clamps before the gradient
  step; `BetaDistribution::update` (directly callable) clamps as well, so both paths see the
  same finite value.
