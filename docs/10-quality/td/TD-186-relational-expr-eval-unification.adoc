== History (shipped)

TD-183 had to be fixed across four code paths because cast lowering, function resolution and
predicate evaluation were fragmented. The load-bearing defect was a pushed-down `WHERE` predicate that
**silently dropped every row** on an eval error, a wrong answer that presents as a clean empty result.

* **Invariant 1 — fail-loud pushdown predicate (#502).** The storage-scan row predicate returns
  `Result<bool, ExprError>`; eval errors propagate instead of becoming `false`.
* **Invariant 2 — one cast lowering in the frontend (#521).** `SqlExpr::Cast` lowers to one typed,
  identity-folded `Expr::Cast`; the pgwire translator's cast-strip list was deleted. Closed TD-183 (doc ratchet 9 → 11).
* **Invariant 3 — one function definition (#507).** `json_extract` / `json_extract_text` kernels live in
  `proximadb-functions` (engine-neutral, accept `ProximaValue::Json`), while the DataFusion lowering keeps the
  typed Arrow UDFs authoritative (avoids the untyped-shadow regression TD-183 hit).

Evidence: `tests/document_json_pgwire_e2e.rs` `DOC_ACCURACY_RATCHET = 11`, `KNOWN_BAD_TD183` empty.

== Open

. **Tighten frontend scalar-name validation so unknown functions fail at planning, not row eval** (the
  remaining clause of Invariant 3). As of 2026-10 the relational frontend deliberately lowers unknown
  functions *permissively* (`proximadb-relational-frontend` `lib.rs`: "the DataFusion path may serve them;
  the Volcano path raises `UnknownFunction` at execution, not at parse"). Closing this needs a decision on
  whether planning-time rejection is still wanted given that DataFusion may serve functions the native
  registry lacks; if not, record the decision here and close.

== Verification

Cross-engine differential + anchored checks (ADR-040) confirm native ≡ DataFusion.
