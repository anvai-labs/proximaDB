== History (shipped)

* Found 2026-07-23: compacting 1M SIFT (763 MB, 6 L0) grew RSS from ~11 GB to a ~126 GB jetsam kill. The pipeline held 5–7 simultaneous full materializations of every input record and had no memory or input-size bound.
* **Lesson — the memory holder was not where the code trace pointed.** Copy math explained ~2 GB; the AXIS-only control showed the 55.6 GB at 120k was the concurrent insert-path AXIS trainer (TD-IVF-2); the stage-boundary memory profile (`PROXIMADB_TRACE_COMPACTION_MEM`, #1173) then put the whole +40.5 GB inside the segment write call while the writer's tracked buffers peaked at 65 MB. Encode slowness was a swap symptom, not the disease. Measure stage boundaries before rewriting the pipeline.
* **Root cause (#1175):** compaction passed `records.len()` as the writer's `embedding_count` (the embedding-*modality* count, normally 1) at all three PAX compaction call sites → 105,000 phantom embedding columns, ~2.5 MB/record of null `Option<Vec<f32>>` and ~42 s per block cut. Fixed by deriving the count from the records, plus a defense-in-depth `MAX_BLOCK_ROWS = 16 * 1024` cut (blocks never span cells; multi-block cells are format-compatible). Test: `two_level_row_bound_splits_giant_cells`.
* **S1 + S3 (#1384, ADR-086):** legacy `VectorRecord` round trips and merged-vector retention removed; MVCC resolves sorted canonical records in place; deterministic whole-file morsels are selected from a byte budget before decoding; `input_bytes × 12` is reserved process-wide (cgroup-visible capacity, live availability, optional ceiling) — see TD-COMPACT-4.
* **Bounded writer (#1384, 2026-08-02):** after admission, a 385 MB task still grew RSS 30.86× from per-row allocations (per-row `Vec<Option<Vec<f32>>>`, flattened SQ8 copy, per-row Region A/B outputs, a second whole-segment vector). Lesson: admission and allocation shape are separate controls. Fix: contiguous vector buffer + validity bitmap, SQ8 fit over segmented rows, pre-sized A/B payloads filled in place by bounded Rayon workers, per-worker RaBitQ scratch arena, early release of f32/clustering state, streamed header/A0/A/B/D/footer to local staging.
* Evidence: comparable large task 30.86× → 8.44× (−75.6% incremental RSS); largest observed ratio across five morsels 10.75×, so the 12.0× admission factor stays. Under the 5 GiB ceiling, 3.3M produced three segments, recall@10 0.981 object-cold, whole-process RSS 14,105 MiB (WAL/cache/allocator baseline is outside the compaction reservation).

== Open

S2 — **Stream the merge (the real fix):** replace the collect-everything design
with a k-way heap merge that pulls one record per input iterator and writes
straight to the PAX writer — MVCC/tombstone resolution happens incrementally
per-key as the sorted streams converge. This eliminates `all_vector_records`,
both `ProximaRecord` round-trips, and the dual clones; peak memory becomes
O(write-buffer), not O(input).

Closure condition (from the 2026-08-01 remediation): the admission work closes the
unbounded-start correctness gap; it does **not** close the longer-term
O(write-buffer) streaming objective — current compaction still materializes its
admitted morsel. The streaming design must remove the measured amplification factor
rather than merely budgeting it. Larger consolidation should use explicit local
spill with an independent scratch-byte reservation (TD-COMPACT-11); OS swap is not
an admission mechanism.

S3 remainder (not verified as shipped; `retrain_pca_model_for_compaction` still
receives the full merged slice): train compaction-time PCA on a reservoir sample, not
the full slice.

Related open idea (recorded 2026-07-23, before the root cause was found):
**carry-forward encoding** — compaction reuses the already-encoded RaBitQ codes from
input segments (carrying the model per TD-COMPACT-1 S3) and re-orders bytes instead
of re-encoding. A per-collection "compaction encode strategy" tag (reuse|re-encode)
is the operational valve — NOT a global encoding on/off switch, which would break the
read cascade (coarse stage requires the RaBitQ region). Encode kernels are scalar
(no NEON — separate, smaller lever; see TD-IVF-2 S1b).
