== Finding

The legacy collection root `{base}/{uuid}` is keyed by a UUID that is never reused. The typed root
`{base}/accounts/{a}/{n}/{c}` is keyed by the catalog's `collection_id`. Its allocation floor is
recovered as `max(live) + 1` (`SystemCatalog`, `system_catalog.rs` ~211–230). So after the
highest-id collection is dropped and the process restarts, the next create mints the same
`(a, n, c)`.

Drop runs storage cleanup synchronously before deleting the catalog record. But
`delete_collection` only logs a cleanup failure and still deletes the record. A typed root that
failed to delete therefore survives with no owner, and the next collection minted onto the same
triple finds the dropped collection's segments in its data directory. Search discovery lists
that directory, so the dropped rows come back.

`NativeCatalog` is worse (NOTE: fixed by #2336 — this paragraph records the pre-fix state; see the Status row). Its floors are recovered lazily, as tables load (`native.rs`
~1170–1183), and `namespace_registry` does not survive a restart. A fresh create can therefore
mint the triple of a live collection that has not been loaded yet, and dropping either
collection would delete the other's segments.

== Proposed fix

* Make the allocator floor durable: persist a monotonic collection-id high-water mark that
  survives drops and restarts, and is recovered eagerly at open rather than as tables load.
* Fail closed: when storage cleanup fails, drop either returns an error and keeps the catalog
  record, or records an orphan obligation, as the TD-COMPACT-13 ledger does, so the triple is
  never re-minted while its root still exists.
* Gate: a test that drops the highest-id typed collection with an injected `remove_dir_all`
  failure, restarts, creates a new collection, and asserts the new collection's data directory
  is empty (or that the create mints a fresh triple).

== Rollback protocol (older-binary publishers, shipped fix)

The durable artifacts and what each binary version does to them. Note the THREE writer
generations: pre-high-water (no field/sidecar, no stamp), #2316/#2336-era high-water-aware
(field/sidecar maintained, but UNSTAMPED — the stamp postdates them), and current
(writer_version 2). An unstamped artifact is therefore not proof of a pre-high-water
writer; the adoption WARNs are deliberately worded for both cases and are BENIGN NOISE on
a #2316/#2336-era artifact.

[cols="2,3,2,3", options="header"]
|===
| Artifact | Written by a current binary (writer_version 2) | Written by a #2316/#2336-era aware binary (unstamped) | Written by a pre-high-water binary
| `SystemCatalog` snapshot (`catalog.snapshot` / the object-store manifest log)
| Carries `ids_high_water` + `writer_version: 2`
| Carries `ids_high_water`, no stamp
| Carries neither (additive fields simply omitted); its checkpoint still compacts the WAL past the watermark
| `SystemCatalog` high-water sidecar (`catalog.hw` / `_operator/catalog/identity_high_water`)
| Fetch-max merged + stamped at the mint/drop durability point and before every WAL compaction
| Did not exist yet — never written
| NEVER touched — old binaries do not name it (local: they rename only their own snapshot+tmp paths; object store: manifest retention prunes only its own `_history/` archives)
| `NativeCatalog` sidecar (`_syscat/identity_high_water.json`)
| Stamped; raised at open, at every mint's durability point, at drop entry
| Written and raised, but unstamped (the #2336-era sidecar is current, not stale)
| Not written (a pre-TD-PATH-2 binary does not know it), so it can go stale below ids the old binary minted
|===

Upgrade (old → new) is safe in every ordering:

* New binary opens a legacy-published store: decodes the field-less snapshot (live schemas
  bound the floor, as before), folds the sidecar `fetch_max`, replays the WAL — and WARNs
  that the adopted snapshot's stamp lags.
* New binary opens a store whose NativeCatalog sidecar is stale (an old binary minted after
  the last aware writer): the EAGER typed-id fold from all table files re-bounds the global
  high-water above every live id before any mint, then persists the repaired sidecar.

[NOTE]
====
Ops prerequisite before upgrading an object-store catalog: the sidecar is written to a NEW
sibling key (`_operator/catalog/identity_high_water`) that pre-existing bucket policies have
never named. A policy that denies PUT outside its allowlisted keys fails EVERY checkpoint
(and every DDL commit on `requires_snapshot_on_commit` stores) after the upgrade — grant PUT
on the sidecar key BEFORE upgrading, not after the first failed checkpoint.
====

Rollback (new → old) is the asymmetric direction and the one that can destroy evidence:

* Rolling the `SystemCatalog` back to a pre-high-water binary and letting it CHECKPOINT is
  the destructive act: its snapshot drops the field and its WAL compaction deletes the
  create deltas. The floor survives ONLY through the sidecar it cannot touch — so never
  delete `catalog.hw` / `_operator/catalog/identity_high_water` when rolling back, and
  expect a WARN-storm from the aware binary when you upgrade again (each WARN is it
  telling you it is leaning on the sidecar).
* RESIDUAL — ids MINTED AND DROPPED BY THE OLD BINARY during the interregnum are lost to
  every mechanism this fix has: the old binary's snapshot carries no high-water, its WAL
  compaction deletes the create deltas, the dropped object is absent from every live
  schema, and the sidecar predates those mints. A rollback/mixed window is therefore only
  as safe as the old binary's DDL discipline: old binaries must NOT run create-then-drop
  DDL during such a window, or the window is accepted as re-issuance-exposed.
* Rolling `NativeCatalog` back does not lose the sidecar (old binaries never write it), but
  ids the OLD binary mints afterwards are invisible to it. If the old binary mints AND
  COMMITS, the next aware open re-bounds via the eager fold (the committed metadata file
  carries the id). But an old-binary mint that is then DROPPED is as invisible as the
  reserved-uncommitted case — the drop deletes the metadata file that was the id's only
  record, so the eager fold cannot see it either; the same create+drop prohibition during
  mixed windows applies. Between two aware opens, a second old-binary mint can also still
  collide with a live-but-unloaded collection before any aware open re-bounds — bounded by
  "run one aware binary open after any rollback window before trusting new mints".
