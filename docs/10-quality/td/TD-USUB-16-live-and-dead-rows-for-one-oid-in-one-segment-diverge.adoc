= TD-USUB-16: A live and a dead row for one oid in ONE segment make the read surfaces disagree

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Done (2026-10-08).** Fixed in the tombstone-persistence commit that introduced it: `flush` does not flush an oid that is both resident and tombstoned, so no segment holds a live and a dead row for one oid (#1957). Kept as a record because the triage errors are the instructive part.
| Priority | Filed LOW twice; both triages were wrong (see History).
| Component | `src/services/record_spill.rs` (`flush`, `merged_records`, `get_record`, `delete_record`)
| Relates to | link:TD-USUB-1-durable-relational-record-store-and-wal-rotation.adoc[TD-USUB-1] (tombstone persistence), link:TD-USUB-19-an-ambiguous-oid-pins-wal-truncation-with-no-alarm.adoc[TD-USUB-19] (the open liveness cost of this fix; durable fix = carry the LSN with the tombstone), mandate #16a
|===

== History

* Defect: `written` was residents followed by synthesised tombstones with no dedup, so an oid racing upsert-vs-delete could be written live-then-dead in one segment; `merged_records` (last row wins) read absent while `get_record`/`delete_record` (first row wins) read live.
* **Triage lessons:** round 1 said it needed OS preemption — wrong, production is multi-thread, so plain parallelism suffices. Round 5 found it was not a consistency nit but a **fail-OPEN for truncation**: the post-commit clear removed a half-durable tombstone, so `min_unflushed_lsn` answered `Ok(None)` and slice 2b would discard the DELETE's WAL entry — a client-acknowledged DELETE resurrected permanently.
* **Why neither side may win:** `tombstones` is a `DashSet` of oids with **no LSN**, so the store cannot know which operation came later. Letting the live row win could lose the delete; letting the tombstone win (first implementation) still evicted the resident row and dropped its LSN tracking — destroying an acknowledged INSERT and releasing its WAL entry. "A read answer is not a licence to discard state."
* Fix: the ambiguous oid is excluded from both `evicting` and `persisting` (so "evicted ⇒ written" and "cleared ⇒ written" hold by construction) and keeps `min_unflushed_lsn` refusing until an upsert of the oid, `delete_record`'s already-suppressed branch, or a purge resolves it. Only WAL replay (LSN order) can decide the order. The unbounded WAL pin this leaves is TD-USUB-19.
* Evidence: `an_oid_both_resident_and_tombstoned_is_not_flushed_and_stays_fail_closed` (builds the state directly; evicting by raw `residents` or clearing by raw `tombstoned` fails it).
