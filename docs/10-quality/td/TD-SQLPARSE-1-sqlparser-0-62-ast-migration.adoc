== Why this is forced, not optional

DataFusion 55.2.0 requires `sqlparser ^0.62.0`. We declare `0.59`. Until the
declaration moves, the workspace compiles **two sqlparser copies with divergent
ASTs** (confirmed: `sqlparser 0.59.0` and `0.62.0` both in `Cargo.lock`, plus
`sqlparser_derive` 0.3.0 and 0.5.0). Moving it is what this TD is about.

Note what is NOT in scope, because it looks like it should be: `arrow` and
`parquet` are **not** behind. We declare 59 and 59.3.0 is the newest in that
line; arrow 60 is unreachable because DataFusion's latest release (55.2.0)
requires `^59.2.0`. An earlier reading of "arrow 58.3.0" in the lock was a
*duplicate* copy pulled by `duckdb`, not our resolution.

== The upstream change

sqlparser 0.62 converted struct variants into **tuple variants wrapping named
structs**:

----
Statement::Update   { table, assignments, selection, .. }  ->  Statement::Update(Update)
Statement::Merge    { table, .. }                          ->  Statement::Merge(Merge)
Statement::AlterTable { name, if_exists, only, operations } ->  Statement::AlterTable(AlterTable)
TableConstraint::PrimaryKey { columns, .. }                ->  TableConstraint::PrimaryKey(PrimaryKeyConstraint)
TableConstraint::Unique     { name, columns, .. }          ->  TableConstraint::Unique(UniqueConstraint)
TableConstraint::ForeignKey { ... }                        ->  TableConstraint::ForeignKey(ForeignKeyConstraint)
TableConstraint::Check      { name, expr }                 ->  TableConstraint::Check(CheckConstraint)
ObjectName { value: Vec<Ident> }                           ->  ObjectName(Vec<ObjectNamePart>)
----

Mostly mechanical. **Three of them are not**, and each is a silent-correctness
trap rather than a compile error once the shape is fixed.

=== Trap 1: `PRIMARY KEY` demoted to `UNIQUE`

0.59 expressed a column-level primary key as
`ColumnOption::Unique { is_primary: true }`. 0.62 removed `is_primary` and added
a **separate variant**:

----
ColumnOption::PrimaryKey(PrimaryKeyConstraint)
ColumnOption::Unique(UniqueConstraint)       // UniqueConstraint has NO is_primary
----

So the obvious port of `ColumnOption::Unique { is_primary: true }` —
`ColumnOption::Unique(UniqueConstraint { .. })` — **compiles and loses
primary-keyness**. `src/query/ddl_dml/mod.rs:435` constructs exactly that, and
`src/query/sql_frontend/parser.rs:3518` matches on it. Both must route through
`ColumnOption::PrimaryKey`, and every *match* on the old single variant must
now cover **two**.

=== Trap 2: `Insert.columns` is no longer a list of identifiers

----
0.59:  Insert.columns : Vec<Ident>        // has .value
0.62:  Insert.columns : Vec<ObjectName>   // no .value
----

`ObjectName` is `Vec<ObjectNamePart>`, and `ObjectNamePart` is
`Identifier(Ident) | Function(ObjectNamePartFunction)` — a part can be a
*function call* in some dialects, so `as_ident()` returns `Option`. Reaching for
`ObjectName::to_string()` instead compiles and round-trips the name through the
dialect's *quoting* rules, so a column stored as `col` can come back as
`"col"`. `src/query/ddl_dml/mod.rs:583` does
`insert.columns.iter().map(|c| c.value.clone())` and must now go through the
parts explicitly, declining (not defaulting) a non-identifier part.

=== Trap 3: `VALUES` rows gained a wrapper

----
0.59:  Values.rows : Vec<Vec<Expr>>
0.62:  Values.rows : Vec<Parens<Vec<Expr>>>   (+ a new `value_keyword: bool`)
----

`src/query/ddl_dml/mod.rs:749` iterates rows directly. The fix is one deref,
and it is listed here only because it is the single error the compiler reports
as "`&Parens<Vec<Expr>>` is not an iterator", which reads like a trait problem
rather than an AST change.

=== Two things that did NOT change — corrected

An earlier revision of this TD claimed constraint `columns` changed type and
that `ObjectName` itself was restructured. **Both are wrong**, and the claims
were checked against the vendored 0.59 source rather than inferred:

* `PrimaryKeyConstraint.columns` / `UniqueConstraint.columns` are
  `Vec<IndexColumn>` in **both** versions, with identical field lists. Only the
  variant *shape* moved (struct variant -> tuple variant). The existing code at
  `ddl_dml/mod.rs:464` already handles `IndexColumn`.
* `ObjectName` is `pub struct ObjectName(pub Vec<ObjectNamePart>)` in **both**
  0.59 and 0.62, byte-identical. The `.value` error is about `Insert.columns`
  changing element type (Trap 2), not about `ObjectName`.

Recording the correction because the mistake is instructive: the error *message*
named `ObjectName`, so reading the message instead of diffing the two versions
pointed at the wrong type. Diff the versions.

There is also a **pre-existing** latent issue the migration should not
silently inherit: `ddl_dml/mod.rs:465` builds a primary-key column name with
`col.column.to_string()`, where `col.column` is an `OrderByExpr`. For
`PRIMARY KEY (c DESC)` that yields `"c DESC"` as the column name. That predates
0.62 and is out of scope here, but it should be filed rather than copied
forward.

The relational-frontend half (4 sites: `Distinct::All`,
`SelectItem::ExprWithAliases` x2, `FunctionArgExpr::WildcardWithOptions`) is
already done. `Distinct::All` is `SELECT ALL` — sqlparser documents it as "keep
duplicate rows", so it is a **no-op**; emitting a `Distinct` node there would
dedup a query that asked not to be.

== How to do it, and how NOT to

**Do not** drive this from the compiler error list. Every trap above compiles
once the *shape* is right; the compiler cannot tell you that a `PRIMARY KEY`
became a `UNIQUE`. Port **type by type** against the upstream struct
definitions, and for each, ask what the old code *meant*, not what it
destructured.

**Mandate #4 applies:** the new variants get real `Result` paths or explicit
`Unsupported` declines — never `unwrap`/`expect`/`panic!`/`unreachable!`.

== Gate

A green build is explicitly **not** sufficient evidence here (mandate #6), and
these are the suites that cover the affected surface:

. **Baseline first.** Run `tpch_pgwire_e2e` + `tpcds_pgwire_e2e` on `develop`
  and record the counts, *before* the migration — there is a known pre-existing
  `tpch_pgwire_e2e` INSERT failure (TD-CONV-1), so without a baseline a red
  result cannot be attributed.
. The TPC-H (22) / TPC-DS (16) pgwire ratchets must not regress — they only go
  up.
. The DDL/DML paths specifically: `CREATE TABLE` with a column-level
  `PRIMARY KEY`, a table-level `PRIMARY KEY (a, b)`, a `UNIQUE` constraint, and
  an `UPDATE ... WHERE` must round-trip, and an `INSERT (a, b) VALUES ...` must
  preserve unquoted column names. **Traps 1 and 2 are invisible to the TPC
  suites if those queries do not exercise column-level keys or named INSERT
  columns**, so add a direct test if coverage is absent rather than assuming
  the ratchets cover it.
