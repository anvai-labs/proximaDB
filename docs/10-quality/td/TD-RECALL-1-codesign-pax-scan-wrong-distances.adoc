== History (shipped)

Two independent defects stacked under one "0.35% recall" symptom:

. *Benchmark artifact:* the SIFT harness unpacked the whole `.fvecs` file as int32, so every f32's bit pattern became the value (`6.0` → `1086324736`). The server stored the garbage faithfully. Fixed to `[int32 dim][dim × f32]`.
. *Real server defect:* `apply_delta_merge_with_explain` re-scored the WAL delta with hardcoded `DistanceMetric::Cosine`, so delta scores (~0.9) always displaced storage scores (~0.005 on the Euclidean `1/(1+L2)` scale) and recall was capped at the memtable fraction. Every stage now derives the metric from the collection via `collection_distance_metric`; `try_pax_cascade` populates `similarity` (it was `None`, rendered as 0.0); the v1 display falls back to `score`.

*Lessons that still apply:* the score-scale contract ("`score` = normalized similarity, one metric per collection") spans four producers and nothing enforced it (TD-SEARCH-1). Instrument first: env-gated value dumps at ingest → materialize → encode (`PROXIMADB_CORRUPTION_DEBUG=1`) bisected the "corruption" to the client in one run. Direct-engine recall harnesses bypass the delta merge, which is exactly where this bug lived.

*Evidence:* clean-parse SIFT 100k storage-only search returns exact brute-force top-5 for self-queries; SIFT 100k over REST with a non-empty memtable reached recall@10 ≥ 0.90 (0.989 at fix time, #1159).

== Open
