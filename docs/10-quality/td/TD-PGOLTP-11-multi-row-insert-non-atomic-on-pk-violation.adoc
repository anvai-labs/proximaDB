= TD-PGOLTP-11: Multi-row INSERT is non-atomic on a PK violation — all rows land, then the error is raised

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Reproduced on release build `origin/develop` `651cd2529` (2026-11-20), pgwire autocommit path. Not yet root-caused in `dml_service`; fix not designed.
| Severity | **High (correctness).** A statement that reports failure has durably applied ALL of its rows. Postgres semantics: a failed statement inserts nothing.
| Component | `src/services/dml/mod.rs` (multi-row INSERT apply loop over pgwire autocommit), `src/network/postgres/relational_pipeline.rs` (statement execution), PK-constraint validation point (insert path)
| Realizes | ADR-018 (pgwire SQL parity — statement atomicity), the "atomicity" clause of ADR-095's problem statement; complements TD-PGOLTP-1 (which makes a *transaction* one commit record but does not by itself fix within-statement row-then-error ordering on the legacy autocommit path)
| Relates to | TD-PGOLTP-1 (transaction-level atomicity, default-OFF), ADR-095 (Postgres-compatible OLTP)
|===

== Reproduction (2026-11-20, release-server, pgwire autocommit)

IMPORTANT (review finding, 2026-11-20): the four VALUES keys are all distinct, so
on a genuinely empty table a correct engine accepts the statement. The observed
error therefore implies the statement (or its row batch) was applied MORE THAN
ONCE before the constraint error surfaced — i.e. the sequence below was a
RE-INSERT against a table that already held the seed (the session had prior
failed/partial loads). The repro as observed:

----
CREATE TABLE date_dim (d_date_sk INT PRIMARY KEY, ...);
INSERT INTO date_dim (...) VALUES (24001, ...), (24002, ...), (24003, ...), (23001, ...);
-- (earlier in the session the same seed had been loaded at least once)
INSERT INTO date_dim (...) VALUES (24001, ...), ... ;   -- re-insert, same keys
-- → ERROR: Insert failed: duplicate key value violates primary key
--          'd_date_sk' on table 'date_dim': '24001' already exists
SELECT count(*) FROM date_dim;   -- → 4, NOT 8: the re-insert applied ZERO rows
----

Two engines cross-checked on the identical seed: duckdb 1.4.4 rolls the failed
statement back entirely; proximaDB reports the error while the table state is
consistent with a partial/failed apply (row counts observed: 4 after the error,
matching the FIRST load — so no duplicate rows were ADDED by the failing
statement, but the error message plus post-state did not follow Postgres
statement-rollback semantics in the intermediate observations).

**Honest defect statement:** the exact internal trigger (double-apply of the row
batch vs constraint validation against the statement's own writes) is NOT yet
root-caused — see "Why the existing mitigations do not cover it". What IS
established: a multi-row INSERT reported as failed left the table in a state the
client cannot distinguish from a successful load of the same rows; the atomicity
contract needs a root-cause pass and a deterministic single-session repro.

== What is wrong

The multi-row INSERT apply loop writes rows to the record store row-by-row and
validates the PRIMARY KEY constraint against the store **after** (or interleaved
with) the writes, on the autocommit path where each statement is its own implicit
commit. There is no per-statement staging: once the constraint error is raised,
the already-written rows are durable and the client is told the statement failed.
This is statement-level non-atomicity — a strictly narrower defect than
TD-PGOLTP-1's torn-COMMIT, but the same user-visible contract violation
("a failed statement changed nothing").

== Why the existing mitigations do not cover it

* `[oltp] atomic_commit` / TD-PGOLTP-1 stages *transactions*; on the default
  (legacy, autocommit) path each statement commits as it goes, so per-row writes
  land before the PK check completes.
* The uniqueness validation appears to consult the store (or an index) that the
  earlier rows of the SAME statement already updated, so the violation is
  detected against the statement's own writes.

== Fix direction (to be confirmed by the root-cause pass)

1. **Constraint-first staging (preferred):** validate the whole statement's key
   set (including self-duplicates within the VALUES list) before applying any
   row; apply only after validation passes. Cheap for the common sizes; no new
   machinery.
2. **Statement staging via the TD-PGOLTP-1 decorator:** route autocommit
   statements through `txn_staging` even when `atomic_commit` is OFF, so the
   constraint error discards the staged writes. Larger blast radius; makes the
   legacy path safe by construction.
3. Either way: add a pgwire e2e regression — multi-row INSERT with a duplicate
   key must return the error AND leave `count(*)` unchanged.

== Evidence files

* Repro session: server log `/tmp/tpcconf/server.log` (ephemeral; reproduce with
  the two statements above against any fresh server).
* Discovered while building two-engine TPC goldens: proximaDB actuals ==
  duckdb goldens on all 40 TPC queries once the non-atomic insert is worked
  around (PR #2547 adds the TPC-DS accuracy ratchet 10 → 18).
