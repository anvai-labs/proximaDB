= TD-PKG-3: the published Docker image keeps all data in the container layer

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open** (filed 2026-10-17). Reproduced: `vjsingh1984/proximadb:0.4.1` run for 25 s wrote `d1 d2 d3 data metadata` under `/tmp/proximadb`; `/data/proximadb` held only `log/`.
| Priority | **HIGH** — `docker rm` (and every documented upgrade) loses all data, whatever volume is mounted.
| Component | `deploy/docker/Dockerfile` (copies `config/config.toml` to `/config/config.toml`; `VOLUME ["/data/proximadb"]`; `ENV PROXIMADB_DATA_DIR=/data/proximadb`); `config/config.toml`; the config loader
| Relates to | TD-PKG-1 (same `/tmp` config in the Linux packages), TD-PKG-2 (same in the MSI); roadmap v0.5
|===

== Problem

The image runs with `--config /config/config.toml`, the repository's development config. Every
storage root in it is under `/tmp/proximadb`: `data_dir`, `metadata_url`, the three
`storage_locations`, `wal_config.global_manifest_url` and the audit directory.
`PROXIMADB_DATA_DIR` does not reach the config loader (only three fallback call sites read it), and
the entrypoint rewrites only `bind_address`. The declared volume therefore receives no data.

== Existing deployments

Data written by a container started without a config mount lives only inside that container.
Copying it into `/data/proximadb` does not work, because the catalog and manifests store absolute
`file:///tmp/proximadb/…` paths; mounting the rescued data at `/tmp/proximadb` does (verified).
The fix must include a migration path for those deployments.

== Fix

* Ship a container config whose roots are under `/data/proximadb` (or make the loader honour
  `PROXIMADB_DATA_DIR` for every root).
* Add a release smoke: write, `docker rm`, run again on the same volume, read back.
