= TD-SIFTCOMPACT-1: the SIFT recall ratchets measured an L0-only layout, because a swallowed compaction error made the id defect invisible

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-08, found by adversarial review of the TD-IVF2ENGAGE-1 change.
| Severity | Medium-High — no incorrect query results, but published recall/GET evidence may describe a layout the tests were not meant to exercise.
| Component | `tests/sift_pax_recall_ratchet_test.rs` (shared `collection()` helper), `src/storage/engines/sst/flush/mod.rs`, `crates/storage/proximadb-storage-common/src/compaction_override.rs`
| Related | TD-IVF2ENGAGE-1 (the sibling fix), TD-WLP-4 / ADR-061 (armed-by-default compaction), TD-VECEVAL-1
|===

== The defect

The shared `collection()` helper passed the collection **name** where the flush
and compaction-admission boundaries are fail-closed on a decimal catalog object
id (`FlushParams::get_collection_object_id` and its compaction twin). Three
things then compose:

. Compaction is **armed by default** for these collections.
  `resolve_compaction_armed(&[])` is `true` under `GlobalCompactionGate::Default`,
  because `AppendBulk` is the default storage profile and the gate's own comment
  says so: *"profile default (TD-WLP-4: `AppendBulk` — including every untagged
  collection — armed)"*. There is an existing unit test pinning
  `resolve_compaction_armed(&[])`. No SIFT test sets
  `L0_COMPACTION_ENABLED_ENV`.
. The L0 threshold is 5 and the harness batches at 20 000, so any run inserting
  ≥100 000 vectors reaches it. The default arm inserts the **full 1M** — 50
  flushes.
. `flush/mod.rs` catches the admission error, logs it at `warn!`, assigns
  `compaction_error` and **continues**: *"a compaction failure is recorded on the
  result but never fails the flush."*

So the error fired, was logged where nothing was listening, and the flush
succeeded. The tests pass because none of them asserts `compaction_ran` — the
IVF2 ratchet is the only one that does, which is why it was the only one that
visibly broke.

== Why it matters more than the bug it hid

If compaction never ran, these ratchets measured an **L0-only, uncompacted,
un-reclustered** layout — not the clustered PAX-LSM layout they appear to
exercise. That affects `sift_pax_cascade_recall_at_10_ratchet`,
its `_rg_layout` sibling, and `sift_pax_filtered_cascade_recall_ratchet` (the
last only at N>=100 000; its own default N is 10 000, one sub-`BATCH_SIZE` flush,
so the threshold is never met there). These are the source of the recall and GET/byte figures published in
`docs/_internal/status/SIFT1M_RECALL_RATCHET_2026_06_30.adoc` and the
`pax_rabitq_sq8_sift1m_recall_at_10` ledger claim in
`docs/_internal/roadmap/BENCHMARK_EVIDENCE.toml`, and carried by the qa-gate
`sift-pax-recall` job.

=== Confirmed by execution, and the fix is NOT one line

Minting an id in the shared helper was the obvious fix. I made that change and
ran `sift_pax_cascade_recall_at_10_ratchet_rg_layout` at N=100 000:

[source]
----
flushed 100000 base vectors
ground truth rows=50: provided/filterable=33, brute-force=17
thread 'sift_pax_cascade_recall_at_10_ratchet_rg_layout' panicked at
  tests/sift_pax_recall_ratchet_test.rs:505:5:
assertion `left == right` failed: each ratchet query must report one physical
  vector access
----

It inserted and flushed all 100 000 vectors, built ground truth, then died on the
**first query**. With a valid id, compaction runs and the ratchet no longer gets
the vector-access record it asserts.

=== Correction: the failure is ZERO accesses, not more than one

An earlier revision of this TD read that panic as a *multi-segment* problem — "a
single-physical-access assumption that a compacted, multi-segment layout breaks"
— and proposed making `assert_single_vector_access` per-segment. **That reading
is impossible**, and the proposal would have masked the real defect.

Re-ran it and captured the values this time:

[source]
----
panicked at tests/sift_pax_recall_ratchet_test.rs:516:5:
assertion `left == right` failed: each ratchet query must report one physical
  vector access
  left: 0
 right: 1
----

**Zero accesses, not more than one.** That is also structurally the only
possibility: `record_completed_vector_access` has two call sites in
`src/storage/engines/sst/search/mod.rs` (`:689` and `:756`, with an `_arc` twin at
`:2228`/`:2277`), and the first is immediately followed by `return result;`, so
they are **mutually exclusive** — at most ONE access is recorded per
`search_vectors_unified` call, and `vector_accesses.len() > 1` cannot occur for a
single measured search. A "per-segment" assertion would therefore be asserting
something that cannot happen.

The first revision of this TD read the same panic as a multi-segment problem
because the quoted output was truncated exactly before the `left:`/`right:`
lines. Those two lines are the whole diagnosis; dropping them is what let the
misreading stand.

Zero accesses means the `Ann` site's guard did not fire:
`vector_ann_proof_count() > ann_proofs_before` (`search/mod.rs:753`). The only
emitter for this configuration is the PAX coalesced cascade (`:593`), so **the
ANN cascade declined on the compacted segment** — silently, with the search still
returning `Ok`.

That is a **product** finding, not a test-baselining one: ANN engagement is lost
on a compacted layout under this arm's write gates (`PAX_F32_TIER=1`,
`PAX_WRITE_RG_LAYOUT=1`, no `BLOCK_CLUSTER`/`COALESCED_RABITQ`/`A0_TRAIN`).
Relaxing the assertion to "per-segment" would convert a red test into a green one
while the engagement loss stayed. An existing test that fails your change is
evidence, not an obstacle.

The helper is therefore left unminted here, and the decision belongs below.

== Why it was invisible

Three independently reasonable decisions compose into silence:

* **arming is implicit** — untagged means armed, so no test opts in and none
  opts out;
* **the failure is best-effort by design** — a compaction failure must not fail a
  flush, which is correct for production and fatal for a test's intent;
* **`warn!` goes nowhere** — the SIFT test file initialises no tracing
  subscriber, so `RUST_LOG=warn` prints nothing. I attempted to confirm this
  defect by grepping a run's output for the error and got zero matches, which
  looked like a refutation and was simply an invisible log.

== How to apply

. **Investigate the ANN decline first — it is the lead, not a side effect.**
  Minting the id surfaces a query that returns `Ok` with no ANN proof on a
  compacted segment. Find which of the cascade's six `Ok(None)` declines fires
  (they are mutually indistinguishable today — see TD-IVF2ENGAGE-1, same root
  cause). Do NOT relax `assert_single_vector_access` to accommodate it: a
  per-segment assertion would go green while the engagement loss remained, and
  `len() > 1` is structurally impossible anyway, so a per-segment form would be
  asserting something that cannot happen.
. **State the current intent explicitly**, which this change now does: the shared
  helper tags its collections `compaction:off`. That is behaviour-preserving —
  compaction does not run today either — and converts "intent achieved by an
  admission failure" into "intent stated", so the ratchets no longer depend on a
  swallowed error to measure what they measure.
. **Then decide whether these ratchets SHOULD exercise compaction.** If yes, that
  is real work gated on the ANN decline above, and every published figure sourced
  from them needs re-baselining — `docs/_internal/status/SIFT1M_RECALL_RATCHET_2026_06_30.adoc`
  and the `pax_rabitq_sq8_sift1m_recall_at_10` claim in
  `docs/_internal/roadmap/BENCHMARK_EVIDENCE.toml` (`status = "measured"`, N=100k
  0.9905 / N=1M 0.9920), both taken at N>=100 000 where admission did fail.
. **Assert the intent.** Each ratchet that means to exercise a compacted layout
  should assert `compaction_ran`, as the IVF2 test already does. A test whose
  premise is silently unmet is worse than a missing test.
. **Make the swallow observable in tests.** The production behaviour is right,
  but a test harness should fail loudly. Either initialise a subscriber in the
  SIFT file, or have the ratchets read `compaction_error` off the flush result
  and fail on it.
. Do not treat the id as cosmetic: `get_collection_object_id`'s own doc comment
  warns that hashing the name at that boundary would create "a second,
  collision-prone identity domain that cannot be joined reliably with catalog,
  MVCC, deletion-vector, or compaction state". Mint an id
  (`next_object_id()`), keep the human name in `CollectionConfig.name`.
