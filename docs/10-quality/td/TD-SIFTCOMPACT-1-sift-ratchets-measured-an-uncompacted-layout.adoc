= TD-SIFTCOMPACT-1: the SIFT recall ratchets measured an L0-only layout, because a swallowed compaction error made the id defect invisible

[cols="1,3", options="header"]
|===
| Field | Value
| Status | **Open.** Filed 2026-10-08, found by adversarial review of the TD-IVF2ENGAGE-1 change.
| Severity | Medium-High — no incorrect query results, but published recall/GET evidence may describe a layout the tests were not meant to exercise.
| Component | `tests/sift_pax_recall_ratchet_test.rs` (shared `collection()` helper), `src/storage/engines/sst/flush/mod.rs`, `crates/storage/proximadb-storage-common/src/compaction_override.rs`
| Related | TD-IVF2ENGAGE-1 (the sibling fix), TD-WLP-4 / ADR-061 (armed-by-default compaction)
|===

== The defect

The shared `collection()` helper passed the collection **name** where the flush
and compaction-admission boundaries are fail-closed on a decimal catalog object
id (`FlushParams::get_collection_object_id` and its compaction twin). Three
things then compose:

. Compaction is **armed by default** for these collections.
  `resolve_compaction_armed(&[])` is `true` under `GlobalCompactionGate::Default`,
  because `AppendBulk` is the default storage profile and the gate's own comment
  says so: *"profile default (TD-WLP-4: `AppendBulk` — including every untagged
  collection — armed)"*. There is an existing unit test pinning
  `resolve_compaction_armed(&[])`. No SIFT test sets
  `L0_COMPACTION_ENABLED_ENV`.
. `should_trigger_compaction` has **two** arms, and an earlier revision of this
  TD described only the first:
+
  * **COUNT arm** — L0 threshold 5, and the harness batches at 20 000, so any
    run inserting >=100 000 vectors reaches it. The default arm inserts the
    **full 1M** — 50 flushes.
  * **TD-COMPACT-5 TRAINING arm** — threshold **1**: a single untrained L0 at or
    above `PROXIMADB_TRAINING_COMPACTION_MIN_MB` (default 32 MB) arms it, gated
    only on `ivf_probe_enabled()`, which is **default ON**. This matters for the
    enumeration below: `sift_coalesced_rabitq_scan_rerank_eval` flushes the
    entire base in ONE batch, so it never reaches count 5 — but its single L0 is
    far over 32 MB and untrained, so the training arm armed it and it hit the
    same swallowed admission error. It is a fourth `collection()` user and is now
    tagged too. It also means the filtered ratchet's exemption at default
    N=10 000 holds because 10 000 SIFT vectors are under the 32 MB floor, not
    merely because the flush count is below 5.
. `flush/mod.rs` catches the admission error, logs it at `warn!`, assigns
  `compaction_error` and **continues**: *"a compaction failure is recorded on the
  result but never fails the flush."*

So the error fired, was logged where nothing was listening, and the flush
succeeded. The tests pass because none of them asserts `compaction_ran` — the
IVF2 ratchet is the only one that does, which is why it was the only one that
visibly broke.

== Why it matters more than the bug it hid

If compaction never ran, these ratchets measured an **L0-only, uncompacted,
un-reclustered** layout — not the clustered PAX-LSM layout they appear to
exercise. That affects `sift_pax_cascade_recall_at_10_ratchet`,
its `_rg_layout` sibling, and `sift_pax_filtered_cascade_recall_ratchet` (the
last only at N>=100 000; its own default N is 10 000, one sub-`BATCH_SIZE` flush,
so the threshold is never met there). These are the source of the recall and GET/byte figures published in
`docs/_internal/status/SIFT1M_RECALL_RATCHET_2026_06_30.adoc` and the
`pax_rabitq_sq8_sift1m_recall_at_10` ledger claim in
`docs/_internal/roadmap/BENCHMARK_EVIDENCE.toml`, and carried by the qa-gate
`sift-pax-recall` job.

=== Confirmed by execution — and superseded by the `compaction:off` tag

Minting an id in the shared helper was the obvious fix. I made that change and
ran `sift_pax_cascade_recall_at_10_ratchet_rg_layout` at N=100 000:

[source]
----
flushed 100000 base vectors
ground truth rows=50: provided/filterable=33, brute-force=17
thread 'sift_pax_cascade_recall_at_10_ratchet_rg_layout' panicked at
  tests/sift_pax_recall_ratchet_test.rs, in assert_single_vector_access:
assertion `left == right` failed: each ratchet query must report one physical
  vector access
----

It inserted and flushed all 100 000 vectors, built ground truth, then died on the
**first query**. At the time, with a valid id, compaction was attempted and the
ratchet no longer got the vector-access record it asserts.

**SUPERSEDED.** The shared `collection()` helper is now tagged `compaction:off`,
and `should_trigger_compaction` returns `Ok(None)` on
`!resolve_compaction_armed(tags)` **before** `params.get_collection_object_id()`
is reached. So minting an id is now **behaviour-neutral** here: compaction runs
neither with nor without one, and the id is never parsed. Everything below is the
diagnosis as it stood, which is why the helper still passes a name — not a
current statement that minting would break anything.

=== Correction: the failure is ZERO accesses, not more than one

An earlier revision of this TD read that panic as a *multi-segment* problem — "a
single-physical-access assumption that a compacted, multi-segment layout breaks"
— and proposed making `assert_single_vector_access` per-segment. **That reading
is impossible**, and the proposal would have masked the real defect.

Re-ran it and captured the values this time:

[source]
----
panicked in assert_single_vector_access
  (tests/sift_pax_recall_ratchet_test.rs; line numbers below are from the probe
  tree, which carries the extra mint lines, so they do not match HEAD):
assertion `left == right` failed: each ratchet query must report one physical
  vector access
  left: 0
 right: 1
----

**Zero accesses, not more than one.** That is also structurally the only
possibility: `record_completed_vector_access` has two call sites in
`src/storage/engines/sst/search/mod.rs` (`:689` and `:756`, with an `_arc` twin at
`:2228`/`:2277`), and the first is immediately followed by `return result;`, so
they are **mutually exclusive** — at most ONE access is recorded per
`search_vectors_unified` call, and `vector_accesses.len() > 1` cannot occur for a
single measured search. A "per-segment" assertion would therefore be asserting
something that cannot happen.

The first revision of this TD read the same panic as a multi-segment problem
because the quoted output was truncated exactly before the `left:`/`right:`
lines. Those two lines are the whole diagnosis; dropping them is what let the
misreading stand.

Zero accesses means the `Ann` site's guard did not fire:
`result.is_ok() && vector_ann_proof_count() > ann_proofs_before`
(`search/mod.rs:753`). **No ANN proof was emitted** — which is what the data
supports, and is weaker than the claim an earlier revision made here ("the only
emitter … so the cascade declined").

**Four** things produce that, and this observation does not separate them. The
fourth was added in round 5 and is now the most likely, because the same defect
was confirmed by execution in the sibling IVF2 test (TD-IVF2ENGAGE-1):

. The PAX coalesced cascade (`:593`) declined — the most plausible reading,
  since it is the emitter this configuration normally uses.
. `discover_sstable_files_with_centroid_pruning` (`:2418`) also emits a proof and
  sits on the same non-orchestrated path (reached from `:1347` and `:2033`), so
  "the only emitter" was wrong. (`execute_orchestrated_search` at `:1141` IS
  unreachable here, though the mechanism stated in an earlier revision was wrong:
  it is not `index_configs`. `use_orchestrated_search` is
  `ctx.metadata.use_axis_indexes && self.axis_manager().is_some()`, and the SIFT
  context builds `StorageQueryMetadata { collection_id, ..Default::default() }`,
  so the default-false `use_axis_indexes` closes that path.)
. The search returned `Err`. The guard is `result.is_ok() && …`, so a failing
  search yields the identical `len() == 0`. "Still returning `Ok`" was asserted,
  not shown.
. **The experiment had no compaction-quiescence barrier** (round 5; most likely).
  `compaction_ran` means *enqueued*, not finished. At N=100000 with
  `BATCH_SIZE = 20_000` the count arm fires on flush 5, the enqueue happens, and
  the harness then builds ground truth and issues its first query *while* the
  worker is writing the compacted output and running `delete_inputs_attempt` on
  the L0 segments it just read. A query that enumerates a file and reads it after
  retirement lands on exactly the `Ok(None)`/fail-over arms this TD is trying to
  attribute. The sibling test's barrier is now in place; this experiment should
  be re-run behind one before any of the three readings above is preferred.

NOTE: the `compaction:off` tag that PR #1964 adds to the shared `collection()`
helper makes this follow-up **un-runnable as shipped** — the tag wins over
`GlobalCompactionGate::Armed`, so not even
`PROXIMADB_L0_COMPACTION_ENABLED=1` re-arms those collections. Re-running it
means temporarily dropping the tag in a scratch branch. That is a deliberate
trade (the tag is what makes the three CI-carried ratchets deterministic), but it
is a cost on this TD and is recorded rather than discovered.

Separating them needs the per-decline recording in the work below. Until then
"no proof emitted" is the finding and "the cascade declined" is the hypothesis —
a distinction this document exists to respect, having already had one
single-observation inference overturned.

**If** the cascade reading is the right one, it is a product finding rather than
a test-baselining one — ANN engagement would be lost on a compacted layout under
this arm's write gates (`PAX_F32_TIER=1`, `PAX_WRITE_RG_LAYOUT=1`, no
`BLOCK_CLUSTER`/`COALESCED_RABITQ`/`A0_TRAIN`). That conditional is the whole
point: an earlier revision of this paragraph asserted it flatly, one paragraph
after the sentence above says it is a hypothesis, and candidate (4) — no
quiescence barrier — is rated the most likely of the four. The two cannot both
stand, and the hedge is the one supported by the evidence.

What does NOT depend on which reading is right: relaxing the assertion to
"per-segment" would convert a red test into a green one without resolving
anything, and `len() > 1` is structurally impossible, so the per-segment form
would assert something that cannot happen. An existing test that fails your
change is evidence, not an obstacle.

The helper was therefore left unminted, and the decision belongs below. (With
the tag in place that reason has lapsed: minting is now safe. It is also no
longer *sufficient* — the tag is what blocks the attribution experiment, so that
step needs the tag dropped as well.)

== Why it was invisible

Three independently reasonable decisions compose into silence:

* **arming is implicit** — untagged means armed, so no test opts in and none
  opts out;
* **the failure is best-effort by design** — a compaction failure must not fail a
  flush, which is correct for production and fatal for a test's intent;
* **`warn!` goes nowhere** — the SIFT test file initialises no tracing
  subscriber, so `RUST_LOG=warn` prints nothing. I attempted to confirm this
  defect by grepping a run's output for the error and got zero matches, which
  looked like a refutation and was simply an invisible log.

== How to apply

. **Investigate the ANN decline first — it is the lead, not a side effect.**
  Minting the id (and dropping the tag) surfaces a query with **no ANN proof**.
  Do not describe the segment it read as "compacted" without checking: under
  candidate (4) the query read a *retiring L0*, not the compacted output, which
  is a different layout and a different bug.
  (Whether that query returned `Ok` is itself unshown — candidate (3) above —
  because the guard is `result.is_ok() && …`, so an `Err` produces the identical
  zero. Record that first; it is one line and it eliminates a candidate.) Then
  find which of the cascade's six `Ok(None)` declines fires — they are mutually
  indistinguishable today, see TD-IVF2ENGAGE-1, same root cause. Do NOT relax
  `assert_single_vector_access` to accommodate it: it would go green without
  resolving anything, and `len() > 1` is structurally impossible anyway.

  **Prerequisite, added after the fact:** this experiment needs a quiescence
  barrier, or it reproduces candidate (4) rather than testing against it. The
  sibling IVF2 test now has one; copy it.
. **State the current intent explicitly**, which this change now does: the shared
  helper tags its collections `compaction:off`. That is behaviour-preserving —
  compaction does not run today either — and converts "intent achieved by an
  admission failure" into "intent stated", so the ratchets no longer depend on a
  swallowed error to measure what they measure.
. **Then decide whether these ratchets SHOULD exercise compaction.** If yes, that
  is real work gated on the ANN decline above, and every published figure sourced
  from them needs re-baselining — `docs/_internal/status/SIFT1M_RECALL_RATCHET_2026_06_30.adoc`
  and the `pax_rabitq_sq8_sift1m_recall_at_10` claim in
  `docs/_internal/roadmap/BENCHMARK_EVIDENCE.toml` (`status = "measured"`, N=100k
  0.9905 / N=1M 0.9920), both taken at N>=100 000 where admission did fail.
. **Assert the intent.** Each ratchet that means to exercise a compacted layout
  should assert `compaction_ran`, as the IVF2 test already does. A test whose
  premise is silently unmet is worse than a missing test.
. **Make the swallow observable in tests.** The production behaviour is right,
  but a test harness should fail loudly. Either initialise a subscriber in the
  SIFT file, or have the ratchets read `compaction_error` off the flush result
  and fail on it.
. Do not treat the id as cosmetic: `get_collection_object_id`'s own doc comment
  warns that hashing the name at that boundary would create "a second,
  collision-prone identity domain that cannot be joined reliably with catalog,
  MVCC, deletion-vector, or compaction state". Mint an id
  (`next_object_id()`), keep the human name in `CollectionConfig.name`.
  **Necessary but no longer sufficient:** with `compaction:off` on the helper,
  minting alone changes nothing observable — the tag has to come off too, which
  is the trade recorded above.
