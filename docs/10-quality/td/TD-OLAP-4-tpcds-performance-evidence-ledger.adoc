== Why

Today `tests/{tpcds,tpch}_pgwire_e2e.rs` assert *query counts* (TPC-H 22, TPC-DS 16) over a
tiny deterministic dataset — a SQL-conformance harness, not a performance benchmark. No scale
factor, no latency/throughput, no baseline. "Competitive with Photon/Snowflake" is therefore
unmeasured. The co-design mandate is explicit: a green conformance test does not prove the
integrated path is fast, and no optimization lands without a trace + evidence ledger.

== Rollout

. **SF1 first, SF10 next:** generate TPC-DS/TPC-H at SF1 (1 GB) and SF10 into the object
  store as Iceberg/Parquet (the OLAP path) AND PAX (the native-scan path) so both routes are
  measured.
. **Baseline harness:** run the same SF on DuckDB, plain DataFusion-on-Parquet, and
  ClickHouse on the same object store / instance class. **Methodology (pinned per ledger
  entry):** engine versions; each baseline's storage configuration (local NVMe vs object
  store — ClickHouse-on-S3 ≠ local MergeTree, DuckDB is local-first); cold vs warm cache
  state, recorded separately. The two cost regimes (object-store: bytes-scanned-dominant;
  local-NVMe: CPU-dominant) are reported as separate ledger sections — never averaged.
  Record latency-per-query + total bytes-scanned (TD-158 trace, **Resolved** — available)
  into a versioned evidence ledger (JSON/Markdown under `docs/10-quality/` or a bench
  artifact).
. **ClickBench track (single-node / embedded regime):** add https://github.com/ClickHouse/ClickBench[ClickBench] (one wide table, ~43 queries — the de-facto single-node OLAP signal where DuckDB / DataFusion / ClickHouse publish) as a ledger track *alongside* TPC-DS. TPC-DS stays primary for the **object-store / scan-avoidance** regime (star joins, DPP, TD-OLAP-3 promotion); ClickBench is primary for the **local-NVMe / single-node / embedded** regime (the "win single-node first" non-goal) where DataFusion's per-op CPU ceiling vs Velox/DuckDB is the binding constraint. Mostly mechanical wiring into the existing `tests/tpc_perf_ledger_e2e.rs` dual-route harness, plus a ClickBench data-gen/loader step (a ~100 M-row `hits` table — the one non-trivial piece).
. **CI tier (advisory→gate):** add a `tpcds-perf` job that records the ledger on develop
  pushes; gate (ratchet on a *budget*, not a single run) only once variance is bounded —
  mirror the `pax-recall-ratchet` pattern (advisory until evidence is stable).
. **Honest trade capture:** the ledger must record where ProximaDB *loses* (e.g. DataFusion
  hash-join no-spill on large joins; per-op ceiling vs Velox) so ADR-052's tradeoffs stay
  visible, not hidden.

== Verification

* A ledger entry exists for SF1 TPC-DS with ProximaDB vs DuckDB/DataFusion/ClickHouse
  latency + bytes-scanned before any "competitive" claim is cited in a doc or ADR.
* Each ledger entry records per-query **peak memory + join-build bytes** (calibrates the TD-OLAP-1 hash-join-no-spill routing threshold and future per-tenant memory budgeting).
* Conformance ratchets (TPC-H 22 / TPC-DS 16) remain green and monotonically non-decreasing.
