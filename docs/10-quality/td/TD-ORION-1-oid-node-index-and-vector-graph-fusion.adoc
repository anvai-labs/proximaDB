== Why the original premise was wrong (verified 2026-07-15)

The filing assumed "ORION has no `oid`→node index, so match-then-traverse must build one first." Both
halves are false:

* **No index is needed — `NodeId` *is* the `oid`.** The SDK mints one id via `record_symbol_id()`
  (ADR-044, `graph/{repo}/node/{key}`) and uses it for BOTH the vector record id AND the graph node
  id (`clients/python/.../code_knowledge.py`: vector `id` at `:527`, `node_id` at `:561`, with the
  explicit comment "node_id below uses the same value"). ORION's `node_to_index`
  (`crates/modalities/proximadb-orion-engine/src/lib.rs`) is therefore already keyed by the `oid`; `get_outgoing_edges`/
  `get_neighbors` resolve an `oid` directly.
* **The fusion already exists and is wired.** `src/graph/rag/` implements the full pipeline
  (TD-045): `VectorNodeRetriever::retrieve` does a vector search and returns record `oid`s as seeds
  (`engine_impls.rs:63`, `.map(|r| r.oid)`); `KHopSubgraphBuilder::build` k-hop BFS-expands them via
  `get_outgoing_edges(oid, edge_type)`; `RagPipeline::run` composes retrieve → filter → prune → build.
  This *is* ADR-061 D4's match-then-traverse. Its REST entry point (`POST /graphs/{graph_id}/rag`)
  was an unmounted duplicate and has been removed, so the capability is not reachable over REST
  until a route is mounted (see the Component row).

So the vector→graph fusion capability is **shipped** as a pipeline, not blocked. ADR-061 D4's fusion intent is
to be satisfied by a mounted `/rag` endpoint (a dedicated graph-RAG surface — cleaner than overloading the Churn
vector-search path).

[#_residual_the_eval]
== Residual: the relevance eval (mandate #13)

The only real gap. `tests/graph_rag_integration_test.rs::test_rag_pipeline_integration` exercises the
pipeline plumbing with a **mock retriever** — it is a deterministic test, not a relevance **eval**.
Per mandate #13 (evals for non-deterministic/ranked surfaces), graph-RAG retrieval needs an eval
suite with a real rubric covering **output** (are the returned neighbours the right symbols) and
**trajectory** (was the seed→expand path sound), gated on a threshold and versioned with the code.

This is the follow-up if we want the surface eval-gated. It is a distinct kind of work (eval
authoring over a small code-graph corpus), not a code-capability gap. File/scope on demand.

== Not doing (measure-don't-assert)

* No `oid`→node index (does not need to exist).
* No re-implementation of match-then-traverse (shipped as TD-045 / `/rag`).
* No Churn-search-seam integration unless a use case wants fusion *inside* vector search rather than
  via the dedicated `/rag` endpoint.
