== History (dismissed / closed classes)

* **§1 `rust/hard-coded-cryptographic-value` (5 critical) — dismissed.** All in
  `src/network/postgres/scram.rs`: four are RFC 7677 test vectors / fixed salts inside
  `#[cfg(test)] mod tests`; the fifth (`:57`) is a zero-initialised buffer immediately overwritten by
  `ring::rand::SystemRandom` (fails closed). No production hardcoded cryptographic value.
* **§2 `rust/cleartext-logging` (37 high) — systemic false positive.** Every site is an assertion
  format string inside `#[cfg(test)]`; the two auth files were read in full. No production log emits
  a credential. 25 of the 37 sit in inline test modules inside production files, so a path filter
  cannot reach them.
* **§3 `py/clear-text-logging-sensitive-data` (2 high) — false positive:** a demo script printing its
  own synthetic clinical-text fixture.
* **§6 `rust/path-injection` (2 high) — REAL; host-path access CLOSED (#1992).** `POST
  /api/v2/external-collections` passed an unvalidated body path to `fs::metadata`/`read_dir`
  (arbitrary host-path traversal, a filesystem oracle via the error string, and a read path outside
  `DrPathBuilder`). The status below records how it was closed and what stays open.
* **§7 `rust/access-invalid-pointer` — false positive:** `#[napi]` proc-macro expansion
  (`FromNapiRef`), no hand-written `unsafe`; accepted as upstream's model.
* **§9 dependency reachability — no advisory exploitable in a published v0.4.0 artifact.** UI and
  generator-toolchain advisories are not shipped; the Go `grpc` alert is stale (pins patched).
  `rustls-webpki 0.101.7` is present via the `aws` feature (`aws-smithy` outbound client) but CRL
  parsing is unreachable (both `WebPkiClientVerifier` sites use rustls 0.23 / webpki 0.103.15 with no
  `.with_crls`) — remediate by bumping the AWS SDK. `jsonwebtoken 9.3.1` arrives via
  `google-cloud-auth`, which decodes only to read `exp` with signature validation disabled and takes
  no authorization decision — remediate by bumping `google-cloud-storage`.
* **Release verdict:** nothing blocked v0.4.0; the two real defects were pre-existing (also open on
  `refs/heads/main`).

== Open items (verbatim)

=== §4 `rust/non-https-url` — the real hardening gap alongside 7 false positives

All seven alerts are cloud IMDS endpoints (`http://169.254.169.254/...`,
`http://metadata.google.internal/...`), which no provider serves over TLS — unfixable as written.

**However**, reading them surfaced a genuine inconsistency the rule did not
flag. `warming.rs` uses hardened **IMDSv2**:

[source,rust]
----
let token = client.put("http://169.254.169.254/latest/api/token")
    .header("X-aws-ec2-metadata-token-ttl-seconds", "300") // ... then
client.get("http://169.254.169.254/latest/meta-data/spot/instance-action")
    .header("X-aws-ec2-metadata-token", token.trim())
----

while `environment_detector.rs:536` issues a bare **IMDSv1** GET with no token:

[source,rust]
----
client.get("http://169.254.169.254/latest/meta-data/instance-id").send()
----

IMDSv1 is the SSRF-reachable variant AWS recommends disabling. This is a
low-severity hardening item (it reads only `instance-id`, for environment
detection), but the two call sites should agree. **Open.**


=== §5 `rust/uncontrolled-allocation-size` — the real hit

(The other 3 of 4 are `with_capacity` over an already-deserialised request `Vec`, bounded by the
64 MiB axum body limit — false positives.) Verified still open 2026-10-15: `TopKHeap::with_capacity`
still calls `BinaryHeap::with_capacity(k)`, and `PROXIMADB_SEARCH_MAX_TOP_K` is still read only in
`src/network/rest/v2/records.rs`.

==== REAL (1 of 4) — `crates/foundation/proximadb-search-types/src/bounded_queue.rs:163`

[source,rust]
----
pub fn with_capacity(k: usize) -> Self {
    Self { capacity: k.max(1), inner: BinaryHeap::with_capacity(k) }
}
----

The doc comment on this very function says `k` comes from `top_k` query
parameters. `BinaryHeap::with_capacity(k)` allocates `k * size_of::<Reverse<E>>()`
**eagerly**, before a single candidate is scored. Production callers pass `top_k`
straight through:

* `src/index/axis/management/manager.rs:4501` — `TopKHeap::with_capacity(query.top_k)`
* `src/index/axis/indexes/dual_store_ivf.rs:1739` — `TopKHeap::with_capacity(k)`

A `top_k` cap exists — but at **exactly one entry point**:

[source,rust]
----
// src/network/rest/v2/records.rs:1579
let max_top_k: usize = std::env::var("PROXIMADB_SEARCH_MAX_TOP_K")
    .ok().and_then(|s| s.parse().ok()).unwrap_or(10_000);
if request.top_k > max_top_k { return Err(ApiError::InvalidArgument(..)); }
----

`git grep PROXIMADB_SEARCH_MAX_TOP_K` returns that handler and the env registry
and nothing else. Arrow Flight declares `top_k: Option<u32>` in its
`app_metadata` control message (`src/network/arrow_ipc/service.rs:78`, defaulted
to 10 at `:3278`) with **no cap**; gRPC and the pgwire/UDTF vector path are
likewise uncapped. A Flight client sending `top_k = u32::MAX` requests a
~4.3e9-element heap allocation — tens to hundreds of GB — aborting the server
process.

The defence is in the wrong place: it is a per-handler check in one REST handler
instead of a clamp at the shared sink. **Open. This is the highest-value fix in
this TD and it is small**: clamp inside `TopKHeap::with_capacity` (e.g.
`BinaryHeap::with_capacity(k.min(CAP))`, growing on demand), which fixes every
surface at once, and additionally reject over-cap `top_k` at the Flight and gRPC
boundaries so clients get an error rather than a truncated result.


=== §6 `rust/path-injection`

==== Status: host-path access CLOSED (2026-10-12); tenant isolation still OPEN

Fixed by confining the location before any filesystem access, reusing the
**existing** `PROXIMADB_EXTERNAL_TABLE_ROOTS` allowlist that `CREATE EXTERNAL
TABLE` already enforced (`src/services/ddl/mod.rs`, promoted to `pub(crate)`).
Deliberately NOT a new gate: a second near-miss name is the `PROXIMADB_IVF2` /
`PROXIMADB_IVF2_PROBE` mistake the ENV_GATE_REGISTRY was written to prevent.

Two layers, because each catches what the other cannot:

1. the shared textual allowlist — fail-closed (unset ⇒ every location rejected),
   rejects `..`, matches on a path boundary so a root `/data` does not admit
   `/data-evil`, and works for URI locations (`s3://`) where canonicalisation is
   meaningless;
2. canonicalisation for a local path — a **symlink inside an allowed root**
   pointing outside it passes a textual check, because the kernel resolves the
   link and not the string. Directory entries are re-confined for the same
   reason.

Also fixed: the single-file branch had no extension check at all, so a location
naming any file was pushed and then stat'ed by `snapshot_fingerprint`, leaking
its length and mtime — now `is_parquet` on both branches. And every rejection
returns one opaque message that does not distinguish "absent" from "forbidden"
and does not echo the path, which removes the filesystem oracle.

Pinned by nine tests in `path_confinement_tests`, including two that guard the
**call site** rather than the helpers — without those, deleting `confine()` from
`list_parquet_files` would leave the rest of the module green while restoring the
original defect.

**Still open — this fix does not deliver tenant isolation.** The allowlist is
process-wide, so tenant A can still register a location under an allowlisted root
that tenant B uses; the read path still does not go through `DrPathBuilder` and
carries no tenant prefix. ADR-090 already records that this gate "cannot express
*tenant A may read X*", and TD-AUTHZ-1 **L3.4** tracks replacing it with
per-tenant location policy. Treat the mandate-violation point above as
outstanding until that lands.


=== §8 `py/redos` (1 high) — real pattern, non-exploitable context


`scripts/check_mvp_trust_corridor.py:191` uses
`([a-zA-Z0-9_-]+(?:-[a-zA-Z0-9_-]+)+)`, which does backtrack exponentially on
`--`-heavy input. The input is `release_notes`, a slice of the repo's own
`.github/workflows/release.yml` read from disk by a CI guard. Not attacker-
controlled, not shipped, worst case a hung CI job on a self-inflicted edit.
Low-priority hygiene; the regex should be rewritten anyway.


== Process finding: CodeQL's signal-to-noise is why this went unread

63 code-scanning findings, 2 real. The 37-alert `rust/cleartext-logging` class
alone is 59% of the volume and 0% real, and it is the reason a network-reachable
path-traversal in `external_collection` sat at the bottom of an unread list
through a release promotion.

Recommended, in priority order:

1. **Fix the two real classes** — clamp `TopKHeap::with_capacity` and cap
   `top_k` at the Flight/gRPC boundaries (§5); confine
   `external_collection` `location` under `DrPathBuilder` + `TenantContext`
   (§6).
2. **Do not reach for a `paths-ignore` fix — it does not work here.** The
   obvious response is "exclude test code from the scan", and this TD
   deliberately does **not** ship that change, because it would not help:
   * There is no CodeQL config file in this repo
     (`.github/codeql*` does not exist) and `codeql.yml` passes only
     `languages` / `build-mode`.
   * `paths-ignore` filters **files**. 25 of the 37 `cleartext-logging` alerts
     and 4 of the 5 criticals live in inline `#[cfg(test)] mod tests` blocks
     **inside production files** (`src/security/auth_service.rs`,
     `src/network/postgres/scram.rs`, …). No path filter can reach them without
     excluding the production code in the same file.
   * A `query-filters` exclusion by rule id would suppress
     `rust/cleartext-logging` and `rust/hard-coded-cryptographic-value`
     everywhere, production included — trading 37 false positives for blindness
     to the first real one.
   The honest position is that this noise is **not currently filterable** and
   the repo should keep triaging these two rules **by class, as this TD does**,
   rather than per alert. Note also that dismissals do not survive new instances
   on new refs — which is why the same five benign criticals reappeared on
   `refs/pull/1970/merge`. Revisit if CodeQL's Rust extractor gains a
   `cfg(test)`-aware exclusion.
3. **Fix the IMDSv1 call site** (§4) and the ReDoS regex (§8).
4. **Decide whether CodeQL stays non-blocking.** It need not gate `CI Success`,
   but "5 critical alerts on the promotion PR" should at minimum be a
   promotion-checklist read rather than something nobody is required to look at.
5. **Close the scanning blind spot**: `third_party/mlflow-ui/3.16.0/build` is a
   vendored, minified third-party JS bundle `include_dir!`-embedded into the
   server binary with no `package.json`, so no Dependabot ecosystem covers it.
   Harmless for v0.4.0 (the `mlflow-ui` feature is off by default and
   `cloud-full` does not enable it), but it should not stay invisible if that
   feature is ever turned on.
