== Open items (verbatim)

=== §4 `rust/non-https-url` — the real hardening gap alongside 7 false positives

All seven alerts are cloud IMDS endpoints (`http://169.254.169.254/...`,
`http://metadata.google.internal/...`), which no provider serves over TLS — unfixable as written.

**However**, reading them surfaced a genuine inconsistency the rule did not
flag. `warming.rs` uses hardened **IMDSv2**:

[source,rust]
----
let token = client.put("http://169.254.169.254/latest/api/token")
    .header("X-aws-ec2-metadata-token-ttl-seconds", "300") // ... then
client.get("http://169.254.169.254/latest/meta-data/spot/instance-action")
    .header("X-aws-ec2-metadata-token", token.trim())
----

while `environment_detector.rs:536` issues a bare **IMDSv1** GET with no token:

[source,rust]
----
client.get("http://169.254.169.254/latest/meta-data/instance-id").send()
----

IMDSv1 is the SSRF-reachable variant AWS recommends disabling. This is a
low-severity hardening item (it reads only `instance-id`, for environment
detection), but the two call sites should agree. **CLOSED 2026-10-15** (see status below).

==== Status: CLOSED (2026-10-15)

Both call sites now go through ONE helper,
`src/core/utils/aws_imds.rs::aws_imdsv2_get` (PUT `/latest/api/token`, then
the GET carrying `X-aws-ec2-metadata-token`; a failed or non-2xx token request
is an error and never falls back to a token-less GET). Environment detection
calls it via `environment_detector::aws_imds_reachable(client, base)` (the base
URL is a parameter so it is testable); the spot-eviction watch in `warming.rs`
replaced its inline copy with the same helper. Besides the SSRF point, the v1
probe was also functionally wrong: an instance with `HttpTokens=required`
answers a token-less GET with 401, so a hardened EC2 host was detected as
"not AWS".

Operator caveat: IMDSv2 tokens are subject to the instance's packet TTL /
hop limit (default 1). In container/Kubernetes deployments where the hop
limit is not raised, the token PUT fails and detection now reports
"not AWS" after the 5 s timeout where the old token-less v1 probe could
still succeed — on such hosts, raise the hop limit (or set
`HttpTokens=optional`) rather than reverting to v1.

Evidence — `tests/aws_imds_v2_test.rs`, against an httpmock IMDS stand-in that
refuses token-less GETs with 401:

* before (seam extracted, v1 GET unchanged): both tests FAILED —
  `aws_detection_uses_imdsv2_session_token`: "detector issued a token-less
  IMDSv1 GET"; `aws_detection_never_falls_back_to_imdsv1`: "fell back to a
  token-less GET";
* after: both pass (token PUT hit once, token-bearing GET hit once, token-less
  GET hit zero times; a refused token request reports "not reachable").


=== §5 `rust/uncontrolled-allocation-size` — the real hit

(The other 3 of 4 are `with_capacity` over an already-deserialised request `Vec`, bounded by the
64 MiB axum body limit — false positives.) Verified still open 2026-10-15: `TopKHeap::with_capacity`
still calls `BinaryHeap::with_capacity(k)`, and `PROXIMADB_SEARCH_MAX_TOP_K` is still read only in
`src/network/rest/v2/records.rs`.

==== REAL (1 of 4) — `crates/foundation/proximadb-search-types/src/bounded_queue.rs:163`

[source,rust]
----
pub fn with_capacity(k: usize) -> Self {
    Self { capacity: k.max(1), inner: BinaryHeap::with_capacity(k) }
}
----

The doc comment on this very function says `k` comes from `top_k` query
parameters. `BinaryHeap::with_capacity(k)` allocates `k * size_of::<Reverse<E>>()`
**eagerly**, before a single candidate is scored. Production callers pass `top_k`
straight through:

* `src/index/axis/management/manager.rs:4501` — `TopKHeap::with_capacity(query.top_k)`
* `src/index/axis/indexes/dual_store_ivf.rs:1739` — `TopKHeap::with_capacity(k)`

A `top_k` cap exists — but at **exactly one entry point**:

[source,rust]
----
// src/network/rest/v2/records.rs:1579
let max_top_k: usize = std::env::var("PROXIMADB_SEARCH_MAX_TOP_K")
    .ok().and_then(|s| s.parse().ok()).unwrap_or(10_000);
if request.top_k > max_top_k { return Err(ApiError::InvalidArgument(..)); }
----

`git grep PROXIMADB_SEARCH_MAX_TOP_K` returns that handler and the env registry
and nothing else. Arrow Flight declares `top_k: Option<u32>` in its
`app_metadata` control message (`src/network/arrow_ipc/service.rs:78`, defaulted
to 10 at `:3278`) with **no cap**; gRPC and the pgwire/UDTF vector path are
likewise uncapped. A Flight client sending `top_k = u32::MAX` requests a
~4.3e9-element heap allocation — tens to hundreds of GB — aborting the server
process.

The defence was in the wrong place: it was a per-handler check in one REST handler
instead of a clamp at the shared sink. **Was open (CLOSED 2026-10-15, status
below). This is the highest-value fix in this TD and it is small**: clamp inside `TopKHeap::with_capacity` (e.g.
`BinaryHeap::with_capacity(k.min(CAP))`, growing on demand), which fixes every
surface at once, and additionally reject over-cap `top_k` at the Flight and gRPC
boundaries so clients get an error rather than a truncated result.


==== Status: CLOSED (2026-10-15)

Enforced at three layers — the shared limit, the canonical choke points, and
the shared sinks (no third constant anywhere):

1. **Shared cap.** `proximadb_search_types::top_k_limit` owns
   `PROXIMADB_SEARCH_MAX_TOP_K` (default `DEFAULT_MAX_TOP_K = 10_000`) and
   `check_top_k(u64) -> Result<(), TopKLimitExceeded>`. The REST v2 inline
   env read was replaced by it. **Boundary rejects (client gets an explicit
   invalid-argument error)** — proven per route by the e2e test below: REST v2
   record + entity search, the legacy REST entity search
   (`POST /api/v1/collections/{id}/entities/search` — this handler carried its
   own hardcoded `top_k > 10000` bound and "between 1 and 10000" message,
   both now routed through the shared limit; its `top_k == 0` rejection is
   this surface's existing contract, kept as-is and consistent with REST v2
   record search, while the shared `check_top_k` alone permits 0), REST v1
   progressive search, REST hybrid search,
   REST graph fusion-search (`limit` AND `max_seeds`), REST analytics
   entanglement (`limit`), gRPC v2 `Search` / `SearchStream` /
   `SearchEntities`, gRPC `FusionSearch` (`limit` AND `max_seeds`), Arrow
   Flight `DoGet` `vector_search` tickets and every `bulk_search` DoExchange
   control frame, pgwire `vector_search(...)` UDTF and pgvector
   `ORDER BY … LIMIT n`. A malformed or zero override now falls back to the
   default instead of disabling (or zeroing) the cap.
2. **Choke points (internal callers, error or clamp).** The shared search
   authorities enforce the cap: `VectorOperationsService::search_v1`
   (progressive/hybrid v1 leg), `unified_search_native[_with_tenant_context]`
   (hybrid/fusion-seed/entanglement leg) and — added in the 2026-10-15
   follow-up after the adversarial review of #2046 found the earlier claim
   that every default-mounted route bottoms out in the first two was wrong —
   `VectorOperationsService::unified_search_v1`, the authority under AQL
   `SEMANTIC_MATCH` (`POST /api/v2/aql/execute`, `vector` and `memory`
   sources), MCP agent-memory retrieval (`VectorMemoryStore::retrieve_similar`),
   the legacy entity store and the SQL executor's vector-query step; plus
   `handle_record_search_for_tenant` as defense in depth. The AQL route maps
   the rejection to HTTP 400 naming `PROXIMADB_SEARCH_MAX_TOP_K` (the AQL
   executor now surfaces `InvalidInput` instead of folding it into a 200 with
   a `Failure` audit outcome); the memory source's internal 5x recall
   oversample is clamped to the cap rather than rejected, so an at-cap
   `top_k` is still served. The MCP `memory` search tool rejects an over-cap
   `k` as invalid params at its boundary. The AQL `vector` source now reads
   its query vector from an `Equals { vector | embedding | query_vector }`
   predicate (and `SemanticMatch.top_k` under `And`); the executor's WHERE
   post-filter treats that vector-valued `Equals` as consumed by the source
   (result rows carry no `vector` field, so re-applying it dropped every hit).
3. **Query-vector validation + kernel backstop (release-gating, v0.4.1).** A
   wrong-dimension or empty query vector reached `assert_eq!` in the distance
   kernel (`compute_distance_simd`); under `release-server`
   (`panic = "abort"`) one unauthenticated request killed the server
   (REST v2 collection search — present in v0.4.0 —, gRPC v2 `Search` /
   `SearchStream`, AQL `vector` / `memory`, MCP memory, the SQL executor,
   the legacy entity store and the embedded `vector_search`). Fixed at two
   layers: (a) `unified_search_v1_inner` — the authority all of these reach —
   now rejects an empty vector and runs `validate_query_vector_for_search`
   (finite + dimension) right after resolving the collection, and
   `unified_search_native` runs the same check for non-empty vectors (empty
   stays allowed there: analytics entanglement passes `vec![]` to load
   records). The typed `InvalidQueryVector` error maps to HTTP 400 on REST v2
   and AQL and `InvalidArgument` on gRPC via `is_client_argument_error`
   (which also covers `TopKLimitExceeded`). (b) The kernel no longer panics:
   a length mismatch scores the pair as worst-possible (`+inf` distance,
   `-inf` dot product) and logs once. The check had to stay in release
   builds — the SIMD kernels index both slices by `a.len()` inside `unsafe`,
   so equal length is a memory-safety precondition — and it costs the same
   single compare the `assert_eq!` did (mismatch path `#[cold]`), so there is
   no hot-path regression. A `debug_assert` was rejected so debug and release
   builds behave the same and tests exercise the production path. `GraphFusionService::graph_fusion_search_with_labels`
   clamps `limit` and `max_seeds` to the cap, and the external-collection hybrid
   pool saturates its `k * HYBRID_POOL_FACTOR` product. Both clamps use the
   *configured* cap (`max_top_k()`), not `DEFAULT_MAX_TOP_K` — before the
   follow-up, an operator override above 10,000 was accepted at the boundary
   and then silently truncated to 10,000 here. A route whose handler
   maps these to `Internal` (rather than `InvalidArgument`) is capped but
   reports a 500 — the list above names the routes that return 400 because
   the e2e test proves it; untested internal callers are capped, not proven.
4. **Shared sinks.** `TopKHeap::with_capacity(k)` /
   `BoundedPriorityQueue::new(k)` pre-allocate only
   `top_k_limit::bounded_prealloc(k)` (≤ 10,000) and grow on demand;
   `pax_rabitq_pool_for_top_k(k, n)` is clamped to the segment's row count
   and the RaBitQ morsel merge buffer is built via
   `morsel_merge_capacity(pool, n_rows, degree)` (`pool.min(n_rows)` ×
   degree, saturating) — the review-pass finding that `k = u32::MAX` on a
   coalesced RaBitQ segment ≥ 65k rows with morsel degree > 1 requested a
   multi-TB `Vec::with_capacity(pool * degree)` is closed by unit test. The
   optimizer's `u16` `top_k` hint is clamped with a warning
   (`optimizer_top_k_hint`) instead of `k as u16` truncating. Results are
   never truncated by any of these layers.

==== Residuals: CLOSED (2026-10-16, `fix/secscan1-residuals`)

Two sets of residuals were recorded here when the clamp closed. One was the
bare `as u16` narrowing of a `top_k` into `SearchParams::top_k: Option<u16>`.
The other was the non-blocking review findings on the query-vector fix.
Neither could abort the process: one was a result-correctness wart, the other
error quality. All are now closed.

1. **Invalid query vector → 400, not 500.** The typed errors
   (`InvalidQueryVector`, `TopKLimitExceeded`) and the classifier moved down
   to `proximadb_search_types::client_argument`. The root crate re-exports
   them, so the API crate's handlers (which cannot see the root crate) apply
   the same check. `client_argument_message` returns the typed cause's own
   text and walks the whole `anyhow` chain. Newly mapped to HTTP 400 /
   `InvalidArgument`:
   * v1 progressive search (`progressive_search_handler.rs`);
   * hybrid search (`proximadb-api` `hybrid.rs`): `RestHybridPortImpl` also
     re-wrapped the vector leg's error with `anyhow!("..: {}", e)`, which
     flattened the type. It now uses `.context(..)`;
   * the legacy v1 entity search (`canonical/entities.rs`) and v2 entity
     search (`rest/v2/entities.rs`);
   * REST graph fusion-search (`rest/v2/graphs.rs`);
   * gRPC `FusionSearch` and gRPC `SearchEntities`;
   * Arrow Flight `DoGet` `vector_search` tickets (`arrow_ipc/service.rs`);
   * REST rank search (`POST /api/v2/rank/search`). `ProductionHybridBackend`
     maps the vector leg's typed error to a new `RankError::InvalidArgument`,
     the rank route answers it as 400, and the coordinator closure keeps the
     typed `RankError` in the chain (`anyhow::Error::new`, not
     `anyhow!("{e}")`). This is unit-tested at the backend; the e2e skips it
     because `RankServices` is not injected in the test server (501).

   Every other failure stays 500 / `Internal`. Already 400 before this work:
   REST v2 collection search, gRPC v2 `Search` / `SearchStream`, AQL
   `vector` / `memory` and MCP memory.

   Still not a client error (documented, not fixed here):
   * **pgwire `<->` / `vector_search(...)` UDTF.** `relational_pipeline.rs`
     stringifies the error as `native collection vector search failed: <cause>`.
     The SQL client gets the dimension cause in the message, but under the
     generic server SQLSTATE rather than a 22xxx/42xxx class. A client
     SQLSTATE needs a typed error path through `protocol.rs`, which several
     open PRs are touching.
   * **Arrow Flight `bulk_search` DoExchange** reports per-query failures as
     in-band error frames rather than a call status. This is unchanged and
     not a 500.

   Analytics entanglement
   (`GET /api/v2/analytics/collections/{id}/entanglement`) deliberately calls
   `unified_search_native` with an EMPTY vector to load records. That path is
   exempt from the gate and still works: the e2e test records `200 OK` with
   an Entanglement Index on current code. Static reading agrees, since only
   `unified_search_v1_inner` rejects an empty vector and the native path
   never calls it.
2. **User-facing collection name, and only one the caller supplied.**
   `InvalidQueryVector` is now structured: an optional `collection` label plus
   a `QueryVectorProblem` (`Empty` / `NonFinite` / `Dimension` / `Other`).
   * **The validator labels conservatively.** `client_collection_label` uses
     the identifier the validator received only when it is not the internal
     object id. Otherwise the message says "the collection".
   * **Rewrite sites restore the caller's name.** Authorities that rewrite the
     caller's name to the object id before validating add the caller's own
     identifier on the way out with `label_client_collection`. They are
     `handle_record_search_for_tenant` (REST v2 / gRPC v2 / Flight),
     `VectorOpsPort::search` (progressive and other v1 port callers) and
     `unified_search_native_with_tenant_context` (fusion seed, v2 entities).
     `unified_search_with_tenant_context` keeps the requested identifier in
     scope. `label_client_collection` fills only a missing label.
   * **The catalog name is never used.** An error message echoes only what
     the request contained. A first draft of this fix used the catalog name;
     review finding F1 replaced it, because a request that addressed a
     collection by object id would get back a name it never sent.
   * Pinned by `object_id_reference_never_echoes_the_catalog_name` (unit) and
     an e2e check that requests addressing collections by object id never get
     the collection's name back.
3. **Graph fusion keeps the cause.** `retry_vector_search` used to re-format
   the last error into a string (losing the type) and retried client errors
   twice (≈300 ms of backoff for a guaranteed failure). It now returns a
   client-argument error at once and keeps the last server error's chain via
   `.context(..)`. A genuine server failure on fusion-search (REST and gRPC)
   or hybrid search logs the full chain server-side and returns a stable
   generic message ("fusion search failed" / "hybrid search failed"; the REST
   envelope carries the request id). Internal detail is kept out of the body.
4. **AQL consumed predicate.** `executor::post_filter_predicate` replaces the
   always-true special case in `evaluate_predicate`. A vector-valued `Equals`
   on `vector` / `embedding` / `query_vector` is stripped from the WHERE
   post-filter at the top level or as an AND conjunct, which are the only
   positions `VectorAqlSource::walk_predicate` consumes. Under `Not` or `Or`
   it is rejected as `InvalidInput` (HTTP 400) before the source runs. A
   scalar `Equals` on those field names is still an ordinary filter.
5. **`as u16` narrowings.** The saturating idiom of `optimizer_top_k_hint` was
   hoisted to `top_k_limit::u16_top_k_hint`, which `optimizer_top_k_hint` now
   delegates to. The NOVA, SST (4) and VIPER (2) engine sites use it, because
   their `k` is already within the cap. The two boundaries that are not capped
   needed a different fix, because there the `u16` is a hard result limit and
   saturating would silently truncate results:
   * The federated SQL vector-search node now calls `check_top_k` on the full
     `usize` before either leg narrows it. Previously the `as u32` on the
     `search_v1` leg could also wrap. The engine leg converts with
     `engine_result_limit`, which errors above 65,535.
   * The cold-tier id lookup splits `ids` into batches of at most `u16::MAX`,
     so every id is looked up. Before, 65,536 ids asked the engine for 0
     results.
6. **`calculate_pq_distance`** got the same length check as
   `compute_distance_simd`, sharing the `#[cold]` `dimension_mismatch_score`.
   It was not routed through `compute_distance_simd` because PQ scores metrics
   differently (negated dot product, Manhattan inline, Euclidean fallback for
   all other metrics), so delegating would change results. The added cost is
   one predictable `usize` compare per subvector, next to slicing that is
   already bounds-checked. The two slices are equal-length by construction,
   so the check is a backstop that keeps this invariant checked rather than
   assumed. No input reaches it today.
   * **Mismatch score: `+inf` for every metric.** PQ accumulates a DISTANCE
     for every metric, including dot product (as `-dot`), so `+inf` is the
     worst value under its own convention.
     `dimension_mismatch_score`'s dot-product value (`-inf`, the kernel's
     similarity convention) would have been the best.
   * **Pre-existing sign inconsistency, not changed here.** PQ hands its
     accumulated `-dot` to `SimilarityResult::new(.., DotProduct)`, which
     treats the raw value as a similarity. INT8 passes a raw dot product, so
     PQ and INT8 disagree on the sign of the dot-product raw value.

=== §6 `rust/path-injection`

==== Status: host-path access CLOSED (2026-10-12); tenant isolation still OPEN

Fixed by confining the location before any filesystem access, reusing the
**existing** `PROXIMADB_EXTERNAL_TABLE_ROOTS` allowlist that `CREATE EXTERNAL
TABLE` already enforced (`src/services/ddl/mod.rs`, promoted to `pub(crate)`).
Deliberately NOT a new gate: a second near-miss name is the `PROXIMADB_IVF2` /
`PROXIMADB_IVF2_PROBE` mistake the ENV_GATE_REGISTRY was written to prevent.

Two layers, because each catches what the other cannot:

1. the shared textual allowlist — fail-closed (unset ⇒ every location rejected),
   rejects `..`, matches on a path boundary so a root `/data` does not admit
   `/data-evil`, and works for URI locations (`s3://`) where canonicalisation is
   meaningless;
2. canonicalisation for a local path — a **symlink inside an allowed root**
   pointing outside it passes a textual check, because the kernel resolves the
   link and not the string. Directory entries are re-confined for the same
   reason.

Also fixed: the single-file branch had no extension check at all, so a location
naming any file was pushed and then stat'ed by `snapshot_fingerprint`, leaking
its length and mtime — now `is_parquet` on both branches. And every rejection
returns one opaque message that does not distinguish "absent" from "forbidden"
and does not echo the path, which removes the filesystem oracle.

Pinned by nine tests in `path_confinement_tests`, including two that guard the
**call site** rather than the helpers — without those, deleting `confine()` from
`list_parquet_files` would leave the rest of the module green while restoring the
original defect.

**Still open — this fix does not deliver tenant isolation.** The allowlist is
process-wide, so tenant A can still register a location under an allowlisted root
that tenant B uses; the read path still does not go through `DrPathBuilder` and
carries no tenant prefix. ADR-090 already records that this gate "cannot express
*tenant A may read X*", and TD-AUTHZ-1 **L3.4** tracks replacing it with
per-tenant location policy. Treat the mandate-violation point above as
outstanding until that lands.
