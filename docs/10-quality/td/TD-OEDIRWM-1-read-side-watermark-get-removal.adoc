= TD-OEDIRWM-1: The read-side directory-watermark fetch is a net-negative GET — removed
:status: Accepted
:date: 2026-11-06
:tags: [cost, gets, voe-directory, freshness]

== Problem (investigated before removal)

`apply_delta_merge_with_explain` fetched the object-economy directory's
freshness watermark (`cached_directory_watermark`) on every Strong and
BoundedStale vector query — the default mode is Strong, so effectively every
query. `load_directory_for` issues exactly ONE object-store GET for the
per-collection sidecar `{collection_root}/oedir/v0.bin`; a missing sidecar is
a swallowed 404, and the directory cache's SLIDING 30s recheck TTL
(`loaded_at` refreshes on every query) means the negative GET fires on the
first strict query after every >=30s idle gap per collection, plus
first-touch after process start. Sustained <30s-gap traffic pays ~nothing.

== The trade, measured against the co-design cost spine

The watermark's ONLY live consumer was the delta-scan skip
(`should_scan_delta_with_time`): when `current_lsn <= watermark_lsn`, the
WAL/memtable delta scan is skipped for Strong. But the skipped work is an
empty-memtable lookup the code itself calls "cheap when empty". A real
object-store round-trip to skip a cheap in-memory check is a strictly
negative trade under the I/O-round-trip cost spine — and pure waste on
sidecar-less collections (never-flushed, non-SST engines — HELIX/NOVA/VIPER
never emit the sidecar), which are exactly the ones that 404 forever.

The directory's CONTENTS have no live reader: TD-RDSTRAT-5 and
TD-RDSTRAT-11 are both Superseded, the retired .sst reader's
object-economy route is disabled without a hint, the RL planner's use is a
`disabled()` stub, and the REST diagnostics endpoint reads the cache
NON-loading (unchanged by this removal).

== Decision

The read-side fetch is REMOVED: `(0, 0)` is passed to the scan helper —
byte-identical to the fallback the fetch already produced for
sidecar-less collections (`ns=0` = time unknown = conservatively scan).
Strict-freshness queries now always run the delta scan; correctness is
unchanged, the EXPLAIN payload reports the same `freshness_watermark_lsn`
it reported for the common case. Flush-side sidecar emission and the
non-loading diagnostics status are intentionally KEPT (retiring the write
side is a separate decision — the sidecar is default-ON and harmless to
write; it costs one PUT per flush against a GET that no longer happens).

If a future change wants the delta-skip back, the honest form is
negative-caching `Missing` entries (never TTL-replace a handle whose last
status was Missing; the flush-side writer already invalidates on write),
not restoring the per-gap GET.

== Follow-ups

* Retiring flush-side `emit_after_flush` (and the sidecar surface
  entirely) is a stacked decision once no other consumer appears.
