== The central design fact (row-oriented engines behind an Arrow contract)

The `ExecutionOperator` contract is **Arrow `RecordBatch`** (`BatchStream`); every domain
engine this phase fuses is **row-oriented**:

[cols="2,3,2", options="header"]
|===
| Engine | Real entry point (verified) | Output shape
| ANN / vector | `search_vectors_unified(ctx: &StorageQueryContext) -> Vec<OptimizedSearchRecord>` (`viper/engine.rs:2220`); AXIS fast path `axis_manager.query(IndexHybridQuery) -> IndexQueryResult` | **row** (`OptimizedSearchRecord`)
| Pre-filter | `proximadb_filter_expression::FilterExpression` → AXIS `metadata_filters: HashMap<String, MetadataFilter>` (ADR-011 Inline mode) | **row predicate**
| Document | `DocumentStorageEngine::query_documents(params) -> DocumentQueryResult` over `DocumentRecord { props: ProximaTree }` (`document/mod.rs:49`) | **row** (`ProximaTree`, jsonpath via `serde_json::Value`)
| Graph | *prerequisite — traversal engine not built* (scaffolding: `src/storage/knowledge_graph/` `TenantKnowledgeGraph`/`RelationshipStore`; algorithms: `crates/modalities/proximadb-graph/src/algorithms.rs`) | *(to be designed)* row
|===

**Therefore each multimodal operator is a row→Arrow adapter** wrapping a row-oriented engine
call, batched to `MORSEL_SIZE` (2048) and emitted as `RecordBatch` through the #758
Arrow↔`RelationalRow` bridge. The batching is not incidental — it is what lets the operator
compose with the relational plane (filter/agg/join) in one pipeline. The "fused" win is
**pushing the predicate *into* the search**, not adapting the output.

== The four operators (ADR-054 §6.1 — grounded)

=== `VectorSearchOperator`
Wraps `search_vectors_unified` (VIPER — the only engine wired today; SST/HELIX/NOVA/RAPTOR/SWIFT
fall back to engine-specific paths). Input carries the query vector + `top_k`; output is a
`RecordBatch` of `(id, score, similarity, [vector], metadata columns)`, converting
`Vec<OptimizedSearchRecord>` in `MORSEL_SIZE` chunks. Quantization (RaBitQ/SQ8/F32 rerank) is
applied by `StorageQuantizationEngine` during decode, unchanged.

=== `FusedAnnFilterAggregate` (the wedge — DataFusion structurally cannot host this)
One operator: **pre-filter → ANN → aggregate**, no materialization between. The pre-filter is
the load-bearing part: lower the SQL `WHERE` to a `FilterExpression`, convert to AXIS
`metadata_filters`, and pass it *into* `axis_manager.query(hybrid_query)` so the filter
constrains the graph walk (ADR-011 **Inline** mode) — it does **not** post-filter the ANN
result. ADR-011's routing thresholds decide the mode by selectivity (pre-filter ≤ 0.05,
post-filter ≥ 0.50, candidate-set in between), with the minimum candidate set
`|C| ≥ max(ef_search × 4, top_k × 10)` to preserve recall. The aggregate runs on the filtered
top-k batch in the same pipeline. This is why the operator must be native: DataFusion has no
ANN operator and cannot express pre-filter-inside-search.

=== `GraphTraversalOperator` (**has a prerequisite**)
BFS/DFS/shortest-path over a PAX edge table, iterative with data-dependent termination.
**Blocked:** the traversal *engine* is not built — only tenant knowledge-graph scaffolding
(`knowledge_graph/`) and graph algorithms (`proximadb-graph`) exist; there is no
operator-consumable `traverse(start, mode, limit)` API yet. This TD specifies the *operator*;
a prerequisite sub-task (or a dedicated graph-engine TD) must land the traversal API first.
Marked explicitly so this is not mistaken for a ready seam.

=== `DocumentProjectionOperator` (**vectorized decode is new work**)
Project a JSON path as a typed Arrow column **once** (columnar), not per-row `serde_json`. The
storage path exists (`DocumentStorageEngine::query_documents`, `ProximaTree` +
`structural_projection.rs`), but it is row-oriented and evaluates jsonpath over
`serde_json::Value` per record. The operator's value-add — a vectorized `ProximaTree`-path →
typed Arrow column decode that avoids the per-row parse — **does not exist yet** and is the
real work here; the MVP may wrap the row path first (correctness), then vectorize behind the
ledger.

== Gate (ADR-052 mandate #4 — measured, not asserted)

Ships behind a flag, default-off, shadow-compared, demoted on regression. Promotion requires
the **TD-OLAP-4 ledger**:

* **Correctness (the load-bearing claim):** a vector+SQL join returns **>99% recall@k** vs the
  >30% loss cited for the CDC/replica post-filter stack (arXiv 2506.23071). Shared gate with
  TD-OLAP-11 Phase 5. This is measured against the f32 baseline (co-design recall discipline).
* **Performance:** per-query ledger vs a **naive post-filter baseline** (DataFusion cannot serve
  the fused shape at all), same object store, in CI — the claim is bytes/latency saved by
  pre-filtering the search vs filtering its output.
* **Conformance unchanged:** TPC-H (22) / TPC-DS (16) ratchets stay green — the multimodal
  operators are additive and do not touch the relational conformance path.

== Prerequisites + sequencing (explicit, so the gaps are visible)

. **Graph traversal engine** — an operator-consumable `traverse()` API over the
  `knowledge_graph` stores / `proximadb-graph` algorithms. Blocks `GraphTraversalOperator`.
. **Vectorized `ProximaTree`-path → Arrow decode** — the columnar projection that makes
  `DocumentProjectionOperator` worth owning. MVP may wrap the row path first.
. **Multi-engine `search_vectors_unified`** — today only VIPER; the operator either targets
  VIPER first or the other engines gain the unified path.
. Depends on TD-OLAP-10/11 (operators + join) and benefits from TD-OLAP-12 (scheduler).

== Non-goals

* **No new external surface** — internal verticality behind the Arrow / `LogicalNode` / pgwire
  seams (ADR-054 §10 "vertical inside, standard outside").
* **No overclaim of five-mode parity** — vector + OLAP + lakehouse is the defensible niche;
  graph/document are stretch modes served by the same plane (ADR-052/054 non-goal).
* **No build before the plane** — building the wedge on a borrowed engine is the anti-pattern
  this ADR exists to avoid.
