== History (shipped)

TPC-H Q2/Q7 over pgwire crashed with a **SIGABRT** stack overflow on `tokio-rt-worker` (2026-07-10). It was a
pre-existing *planner* bug, identical without native enabled: the planner lowers recursively (one frame per plan
node), and the pgwire runtime ran on the 2 MB tokio default while the embedded PyO3 server used 8 MB, so the
deep-plan path had only ever been exercised with 8 MB.

Decision that still applies: **separate safety from the estimate.** `stacker::maybe_grow` at the recursion
entries makes correctness hold for any depth on any worker stack (#851, also retiring native's
`MAX_WALK_DEPTH=32` decline); the flat 8 MB was a blunt band-aid. Phase 1 measurement became TD-EXEC-2
Slice 1: lowering ≈ 1.46 KB/frame, executor build ≈ 2.35 KB/frame (release), and the executor builder
does recurse too (answering first-principles questions 1–3).

Evidence: release conformance gate executes Q2 (TPC-H 22/22, TPC-DS 18/18).

== Open

=== Phase 2: Iterative planner (efficiency)
Convert the planner's recursive `Box::new(lower_to_physical(child))` calls to an iterative work-list:
- Maintain an explicit stack (Vec) of `(node, parent_slot)`.
- Process each node: lower it, push children onto the work list, fill the parent slot.
- Eliminates the call-stack pressure entirely — any plan depth runs in O(1) stack frames.
- Precedent: DuckDB's `PhysicalPlanGenerator`, Velox's `PlanBuilder` — both iterative.
- This is a LARGE refactor but the architecturally correct one. With `maybe_grow` in place it is a
  *performance* optimization (fewer segment allocations, better locality), and covers the executor builder too.

=== Phase 3: Tiered worker pools (the co-design end-state; = TD-EXEC-2 Slice 2)
- OLTP worker pool: 1 MB stack, `num_cpus` workers (high concurrency, shallow plans).
- OLAP worker pool: 8 MB stack, `num_cpus / 2` workers (lower concurrency, deep plans).
- The router's shape classification (#840's operation dimension) assigns queries to the right pool.
- Total memory: `num_cpus × 1MB + num_cpus/2 × 8MB` = e.g., 16 + 64 = 80 MB on a 16-core box — less than the flat 128 MB, with better OLTP concurrency.

=== Open questions

. **What's the pgwire protocol stack overhead?** Each pgwire connection adds protocol state (message framing, prepared statements, SSL). Measure this to separate the protocol stack from the query-execution stack.
. **Can we set the stack size per-connection (not per-worker)?** Tokio doesn't support this directly (all tasks on a worker share the worker's stack). But a custom executor or a spawn-with-stack-size pattern (like Go's goroutine stack growth) could. This is the long-term co-design question.

== Non-goals
- **Process-per-connection model** (PostgreSQL's approach). We use thread-multiplexed tokio — the fix should work within that model.
