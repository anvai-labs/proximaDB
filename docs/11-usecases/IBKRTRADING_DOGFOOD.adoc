== Executive Summary

ibkrtrading is an event-driven algorithmic trading system built in Rust with 16 crates, connecting to Interactive Brokers TWS/Gateway for stocks, crypto, forex, and options trading. It currently uses 3 separate databases (PostgreSQL, SQLite, JSONL) plus external services (Prometheus, Jaeger). The goal is to replace all data stores with a single ProximaDB embedded instance, proving the "Context Database" architecture in production trading.

This blueprint details the six-phase migration plan, data model mapping, cross-model query patterns, and success criteria for consolidating six separate data backends into a single ProximaDB embedded process with zero network latency.

== Six-Phase Integration Plan

=== Phase 1: Replace JSONL with Event Sourcing (4 weeks)

==== Goal

Eliminate 119MB/day JSONL files with indexed, immutable event store.

==== Deliverables

* Event sourcing engine with append-only WAL
* Indexed queries on event_type, order_id, timestamp, symbol
* Temporal replay: query state at any historical timestamp
* MiFID II compliance: immutable events with tamper detection

==== Integration Points in ibkrtrading

* Replace `EventLogger` trait implementation
* Replace `jsonl_writer` crate with ProximaDB embedded client
* Migrate historical JSONL files to event store

==== Success Criteria

* 119MB/day ingest without performance degradation
* Query any event by order_id in <1ms
* Temporal replay of order lifecycle
* Zero JSONL files written after migration

==== Risks

Event sourcing engine is not yet built. This phase depends on ProximaDB implementing the event store model.

=== Phase 2: Replace SQLite with Document Store (4 weeks)

==== Goal

Eliminate SQLite write contention and single-file limitations.

==== Deliverables

* Document collections for orders, positions, fills, state
* ACID transactions for order lifecycle (new -> submitted -> filled -> closed)
* Real-time queries on position state and order status
* Historical position snapshots for reconciliation

==== Integration Points

* Replace `sqlite3` dependency in `ibkrtrading-monitoring` crate
* Implement ProximaDB document store adapter
* Migrate 8 SQLite tables to document collections

==== Success Criteria

* All 8 SQLite tables migrated
* Order state transitions are atomic
* Concurrent read/write without contention
* SQLite file no longer written

=== Phase 3: Replace PostgreSQL with Time-Series Engine (6 weeks)

==== Goal

Eliminate PostgreSQL dependency for OHLC bar storage.

==== Deliverables

* TST engine with time-partitioned OHLC storage
* ASOF joins for point-in-time price lookups
* Automatic downsampling (5s -> 5m -> 1h -> 1d)
* Historical data migration from PostgreSQL

==== Integration Points

* Replace `sqlx::PgPool` in `ibkrtrading-data` crate
* Implement ProximaDB time-series adapter
* Migrate historical bars from PostgreSQL

==== Success Criteria

* Sub-ms OHLC queries for any symbol/timeframe
* ASOF join accuracy matches PostgreSQL
* Downsampled bars match current computed values
* PostgreSQL process no longer required

=== Phase 4: Extend Vector Search (3 weeks)

==== Goal

Multi-timeframe regime vectors and strategy pattern matching.

==== Deliverables

* Multi-timeframe regime vectors (5m, 1h, 1d simultaneously)
* Strategy pattern matching: find historical periods with similar strategy performance
* Cross-model query: "similar regimes WHERE factor exposure was high"

==== Integration Points

* Extend existing `proximadb-integration` crate
* Add multi-timeframe regime computation
* Connect regime search to strategy selection

==== Success Criteria

* Regime similarity search across 3 timeframes in <5ms
* Strategy backtesting uses historical regime matches
* Cross-model regime + factor query returns results in <50ms

=== Phase 5: Graph Integration (4 weeks)

==== Goal

Factor correlations and asset relationship network in ORION.

==== Deliverables

* Factor correlation graph (Asset -> Factor edges with rolling correlation weights)
* Asset correlation network (symbol pairs with rolling correlation)
* Strategy dependency graph (strategy -> signals -> indicators)

==== Integration Points

* Replace in-memory `FactorStore` with ORION graph
* Compute rolling correlations and update graph edges
* Expose portfolio risk via graph traversal queries

==== Success Criteria

* Factor correlation graph updated in real-time as bars arrive
* "What assets are most correlated with AAPL this week?" in <1ms
* Portfolio risk query: "Which positions have >70% correlation?" in <5ms

=== Phase 6: Unified Observability (3 weeks)

==== Goal

Replace Prometheus + Jaeger with built-in observability.

==== Deliverables

* Trading metrics stored in ProximaDB time-series (Grafana-compatible)
* Traces stored in ProximaDB observability store
* Correlation: link traces to trading events and order lifecycle
* Pre-built Grafana dashboards for trading metrics

==== Integration Points

* Replace Prometheus metrics exporter with ProximaDB metrics writer
* Replace OTLP/Jaeger exporter with ProximaDB trace writer
* Configure Grafana to query ProximaDB directly

==== Success Criteria

* All trading metrics visible in Grafana via ProximaDB backend
* Trace-to-event correlation: click a slow trace, see the trading event
* Prometheus and Jaeger processes no longer required

== Cross-Model Query Examples

After full integration, ibkrtrading can execute unified queries spanning vectors, graphs, time-series, documents, and events in a single SQL statement. These are the core query patterns that demonstrate the "Context Database" value proposition.

=== Find Similar Market Regimes and Their Subsequent Returns

[source,sql]
----
-- 1. Find similar market regimes and their subsequent returns
SELECT r.timestamp, r.regime_label, r.similarity_score, ts.close_return_5d
FROM VECTOR_SEARCH('regimes', current_regime_vector, 20) r
JOIN time_series('bars_1d', r.timestamp, r.timestamp + interval '5 days') ts
  ON ts.symbol = r.symbol
WHERE r.similarity_score > 0.85
ORDER BY r.similarity_score DESC;
----

=== Correlated Assets During High-Volatility Regimes

[source,sql]
----
-- 2. Correlated assets during high-volatility regimes
SELECT g.source_symbol, g.target_symbol, g.correlation,
       ts.avg_return, ts.max_drawdown
FROM GRAPH_QUERY('correlations',
  'MATCH (a:Asset)-[c:CORRELATED]->(b:Asset)
   WHERE c.weight > 0.7 RETURN a.symbol, b.symbol, c.weight') g
JOIN LATERAL (
  SELECT avg(return) as avg_return, min(drawdown) as max_drawdown
  FROM time_series('bars_1d')
  WHERE symbol = g.target_symbol
    AND timestamp > now() - interval '30 days'
) ts ON true;
----

=== Order Audit Trail with Event Correlation

[source,sql]
----
-- 3. Order audit trail with event correlation
SELECT o.order_id, o.symbol, o.side, o.quantity, o.status,
       e.event_type, e.timestamp, e.details
FROM DOCUMENT_QUERY('orders', 'symbol = "AAPL" AND status = "filled"') o
JOIN LATERAL (
  SELECT * FROM events
  WHERE order_id = o.order_id
  ORDER BY timestamp
) e ON true
WHERE e.timestamp > now() - interval '1 day';
----

=== Risk Analysis: Positions in Correlated Assets with High Drawdown

[source,sql]
----
-- 4. Risk analysis: positions in correlated assets with high drawdown
SELECT p.symbol, p.quantity, p.unrealized_pnl,
       g.correlated_with, ts.current_drawdown
FROM DOCUMENT_QUERY('positions', 'quantity > 0') p
JOIN LATERAL GRAPH_QUERY('correlations',
  'MATCH (a:Asset {symbol: "' || p.symbol || '"})-[:CORRELATED]->(b)
   RETURN b.symbol') g ON true
JOIN LATERAL (
  SELECT max_drawdown as current_drawdown
  FROM time_series('metrics')
  WHERE symbol = g.correlated_with
    AND metric = 'drawdown'
    AND timestamp > now() - interval '1h'
) ts ON true
WHERE ts.current_drawdown > 0.05;
----
