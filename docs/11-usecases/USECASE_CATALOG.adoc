== Overview

ProximaDB's multi-model architecture enables cross-model queries that single-model databases cannot serve. Where traditional vector databases (Pinecone, Milvus, Weaviate) excel at one data model, ProximaDB unifies vector search, graph traversal, document queries, observability, and time-series within a single query engine. This eliminates the need to stitch together multiple specialized databases and removes the application-side join logic that adds latency and complexity.

This catalog maps 6 primary use cases to industries, data models, query patterns, and ProximaDB capabilities. Each use case includes a fit score reflecting current feature completeness, a detailed data model mapping, cross-model query examples using ProximaDB's SQL extensions, and an honest assessment of critical gaps.

== Detailed Use Cases

=== Use Case 1: AI Agent Context Engine

**Industry**: AI/ML, SaaS

**Persona**: AI/ML Engineer building autonomous agents (LangChain, CrewAI, AutoGen)

**Fit Score**: 8/10

==== Problem Statement

AI agents need rich context combining semantic memory (vectors), knowledge graphs, conversation history (documents), and real-time events. Current solutions require stitching Pinecone + Neo4j + MongoDB + Redis, with application-side join logic that adds latency, increases failure modes, and complicates deployment. A single embedded database that serves all four data models eliminates this fragmentation.

==== Data Model

[cols="2,2,1,2",options="header"]
|===
| Data Type | ProximaDB Model | Engine | Collection

| Semantic Memory (embeddings)
| Vector
| SST
| agent_memory

| Knowledge Graph
| Graph
| ORION
| knowledge_graph

| Conversation History
| Document
| Document Store
| conversations

| Agent Metrics
| Observability
| Observability Store
| agent_metrics

| Tool Call Logs
| Event
| Event Store (planned)
| tool_calls
|===

==== Query Patterns

* **RAG retrieval**: `VECTOR_SEARCH('agent_memory', query_embedding, 20)` with BM25 hybrid reranking
* **Knowledge enrichment**: `GRAPH_QUERY('MATCH (e:Entity)-[:RELATED_TO]->(r) RETURN r')`
* **Cross-model**: Find relevant docs, enrich with graph context, filter by recency
* **Conversation search**: `DOCUMENT_QUERY('conversations', 'agent_id = "agent_1"')`

==== Cross-Model Query Example

[source,sql]
----
SELECT v.content, v.score, g.related_entities, d.conversation_context
FROM VECTOR_SEARCH('agent_memory', '[0.1, 0.2, ...]', 10) v
JOIN LATERAL GRAPH_QUERY(
  'MATCH (e:Entity {name: "' || v.entity || '"})-[:RELATED_TO]->(r)
   RETURN collect(r.name)') g ON true
JOIN LATERAL DOCUMENT_QUERY(
  'conversations', 'entity = "' || v.entity || '"') d ON true
ORDER BY v.score DESC;
----

==== ProximaDB Advantage

Single database replaces 3-4 separate systems. Cross-model queries eliminate application-side joins. The in-process (PyO3) embedded mode has zero network latency; the Python SDK's managed-subprocess embedded mode communicates over UDS+HTTP and does not. Latency claims here are governed by `BENCHMARK_EVIDENCE.toml`: the previously cited "sub-6ms vector search" was never registered as measured there, and the measured end-to-end route (warm, 10K vectors) is ~20 ms; the in-process search body measured ~0.024 ms at small scale. Do not quote latency numbers from this catalog -- quote the evidence ledger.

=== Use Case 2: Algorithmic Trading Platform

**Industry**: Finance (Quantitative Trading, Asset Management)

**Persona**: Quantitative Developer building automated trading systems

**Fit Score**: 7/10

==== Problem Statement

Trading systems generate diverse data -- OHLC bars, orders, events, regime vectors, factor correlations, metrics -- across multiple databases (PostgreSQL, SQLite, JSONL). This fragmentation increases query latency (cross-database joins over the network), operational complexity (multiple backup/recovery procedures), and makes cross-model analysis like "find similar market regimes where correlated assets had drawdown > 5%" impossible without custom ETL pipelines.

==== Reference Implementation

ibkrtrading -- 16 Rust crates, IBKR TWS/Gateway integration. Currently uses PostgreSQL (OHLC bars), SQLite (state/orders), and JSONL (events at 119MB/day). The `proximadb-integration` crate provides Phase 1 regime similarity search.

==== Query Patterns

=== Use Case 3: Real-Time Recommendation Engine

**Industry**: E-commerce, Media, Social

**Persona**: Platform Engineer building personalization systems

**Fit Score**: 8/10

==== Problem Statement

Recommendation engines need user preference vectors, product catalogs (documents), user-product interaction graphs, and real-time behavior streams. Current architectures use Redis + Elasticsearch + Neo4j + feature stores, resulting in stale recommendations (batch sync delays), complex orchestration (4+ database clients), and inability to combine collaborative filtering + content matching + graph context in a single query.

==== Data Model

[cols="2,2,1,2",options="header"]
|===
| Data Type | ProximaDB Model | Engine | Collection

| Product Embeddings
| Vector
| SST
| product_embeddings

| User Preference Vectors
| Vector
| SST
| user_preferences

| Product Catalog
| Document
| Document Store
| products

| User-Product Interactions
| Graph
| ORION
| interactions

| Behavioral Events
| Event
| Event Store (planned)
| user_events

| Recommendation Metrics
| Observability
| Observability Store
| rec_metrics
|===

==== Query Patterns

* **Collaborative filtering**: Vector similarity on user preference vectors
* **Content-based**: Vector search on product embeddings with metadata filters
* **Graph-based**: Traverse interaction graph for "users who bought X also bought Y"
* **Hybrid**: BM25 text search + vector similarity for product discovery
* **Real-time**: Streaming subscriptions for behavior-triggered recommendations

==== Cross-Model Query Example

[source,sql]
----
SELECT v.product_id, v.score, d.name, d.price, g.also_bought
FROM VECTOR_SEARCH('product_embeddings', user_preference_vector, 50) v
JOIN LATERAL DOCUMENT_QUERY(
  'products', 'id = "' || v.product_id || '"') d ON true
JOIN LATERAL GRAPH_QUERY(
  'MATCH (p:Product {id: "' || v.product_id || '"})<-[:BOUGHT]-(:User)-[:BOUGHT]->(rec)
   RETURN collect(DISTINCT rec.id)') g ON true
WHERE d.in_stock = true
ORDER BY v.score DESC
LIMIT 10;
----

=== Use Case 4: Observability Platform

**Industry**: DevOps, SRE, Platform Engineering

**Persona**: SRE building unified observability

**Fit Score**: 7/10

==== Problem Statement

Observability requires logs + metrics + traces, typically served by Elasticsearch + Prometheus + Jaeger. Correlation across these three pillars is manual and slow -- an engineer must query each system independently and mentally join the results. Blast radius analysis during incidents requires cross-referencing service dependency graphs with error logs and metric anomalies, which is impossible without custom scripting across siloed tools.

==== Query Patterns

* **Log search**: Full-text search with time-range filtering
* **Metric queries**: Time-series aggregation with downsampling
* **Trace correlation**: Link traces to logs and metrics by correlation ID
* **Service impact**: Graph traversal for blast radius analysis
* **Anomaly detection**: Vector similarity for similar error patterns

==== Cross-Model Query Example

[source,sql]
----
SELECT l.timestamp, l.message, g.service_dependencies, v.similar_incidents
FROM LOGS('errors') l
JOIN LATERAL GRAPH_QUERY(
  'MATCH (s:Service {name: "' || l.service || '"})-[:DEPENDS_ON]->(d)
   RETURN collect(d.name)') g ON true
JOIN LATERAL VECTOR_SEARCH('error_patterns', l.error_embedding, 5) v ON true
WHERE l.timestamp > now() - interval '5m';
----

=== Use Case 5: Knowledge Management

**Industry**: Enterprise, Legal, Healthcare

**Persona**: Enterprise Architect building knowledge bases

**Fit Score**: 7/10

==== Problem Statement

Enterprise knowledge spans documents, relationships between concepts, and semantic search needs. Current solutions use Confluence + Elasticsearch + knowledge graph tools separately. Finding the right document requires knowing the right keywords (keyword search) or having a semantic query (vector search) -- but the best results come from combining both with knowledge graph context. No single existing system provides this combination.

| Observability
| Observability Store
| access_logs

| Change Events
| Event
| Event Store (planned)
| doc_events
|===

==== Query Patterns

* **Semantic search**: Vector similarity on document embeddings
* **Keyword search**: BM25 full-text search with filters
* **Hybrid**: Combined semantic + keyword for best recall and precision
* **Concept navigation**: Graph traversal through taxonomy
* **Cross-reference**: Find documents related to a concept via graph + vector

==== Cross-Model Query Example

[source,sql]
----
SELECT d.title, d.content, v.score, g.related_concepts
FROM VECTOR_SEARCH('doc_embeddings', query_embedding, 20) v
JOIN LATERAL DOCUMENT_QUERY(
  'documents', 'id = "' || v.doc_id || '"') d ON true
JOIN LATERAL GRAPH_QUERY(
  'MATCH (d:Document {id: "' || v.doc_id || '"})-[:ABOUT]->(c:Concept)-[:RELATED_TO]->(r)
   RETURN collect(r.name)') g ON true
ORDER BY v.score DESC;
----

=== Use Case 6: IoT Analytics

**Industry**: Manufacturing, Energy, Smart Cities

**Persona**: IoT Platform Engineer managing sensor networks

**Fit Score**: 6/10

==== Problem Statement

IoT generates high-frequency time-series data from sensors, requires anomaly detection (vector similarity on sensor reading patterns), and needs device relationship graphs for impact analysis. Currently uses InfluxDB + custom ML pipeline + separate graph store. Edge deployment requires lightweight embedded databases, but most time-series databases are server-only.

==== Query Patterns

* **Time-series**: High-frequency sensor data with downsampling and aggregation
* **Anomaly detection**: Vector similarity for known failure patterns
* **Impact analysis**: Graph traversal for device dependency chains
* **Predictive maintenance**: Cross-model queries combining sensor trends + anomaly patterns + device graph

==== Cross-Model Query Example

[source,sql]
----
SELECT s.device_id, s.reading, v.pattern_name, v.score, g.downstream_devices
FROM time_series('sensor_data', now() - interval '1h', now()) s
JOIN LATERAL VECTOR_SEARCH('anomaly_patterns', s.reading_vector, 5) v ON true
JOIN LATERAL GRAPH_QUERY(
  'MATCH (d:Device {id: "' || s.device_id || '"})-[:FEEDS_INTO*1..3]->(downstream)
   RETURN collect(downstream.id)') g ON true
WHERE v.score > 0.90
ORDER BY v.score DESC;
----

**Key observations from the cross-reference**:

* **Vector Search** and **Graph Traversal** are universally required -- every use case depends on them. These are ProximaDB's strongest existing capabilities.

* **Hybrid Search (BM25)** is required by 3 use cases (Agent, RecSys, KnowMgmt) -- all customer-facing applications where recall quality directly impacts user experience.
* **Embedded Mode** is required by 3 use cases and already exists, representing a strong competitive advantage.
