= Embedding Precision (per-collection storage type)
:toc: macro
:toc-title: Contents

toc::[]

== What it is

Each collection has a `canonical_embedding_precision` that controls the
scalar type of the embedding column on disk and in memory. The default
is `fp32` (32-bit float, the legacy behavior). Switching to a smaller
type trades a small recall delta for substantial storage reduction:

[cols="1,1,1,2", options="header"]
|===
| Type   | Bytes / element | Storage vs fp32 | Notes

| fp32   | 4 | baseline | Default; no change for existing collections.
| fp16   | 2 | ~50%     | Common choice for embeddings; ~bit-exact for the typical range BGE / OpenAI / Cohere produce.
| bf16   | 2 | ~50%     | Same width as fp16 with the dynamic range of fp32; useful for embeddings that hit fp16's range limit.
| int8   | 1 | ~25%     | Scalar-quantized; per-cell scale; lossier. Best for very large corpora where recall budget allows ~1-3% delta.
| uint8  | 1 | ~25%     | Unsigned scalar quantization with zero-point.
|===

== Setting it

The same field is accepted across every protocol that creates a
collection. Set it once at collection-create time; it's an immutable
property of the collection's schema (catalog row).

[cols="1,4", options="header"]
|===
| Protocol | Example

| REST `POST /api/v1/collections`
a|
[source,bash]
----
curl -X POST http://localhost:5678/api/v1/collections \
  -H "Content-Type: application/json" \
  -d '{
    "collection_id": "docs_fp16",
    "collection_config": {
      "dimension": 768,
      "canonical_embedding_precision": "fp16"
    }
  }'
----

| gRPC `CreateCollection`
a|
[source,python]
----
from proximadb_sdk import EmbeddingPrecision, Protocol, ProximaDBClient

client = ProximaDBClient(url="http://localhost:5678", protocol=Protocol.REST)

client.create_collection(
    "docs_fp16",
    dimension=768,
    canonical_embedding_precision=EmbeddingPrecision.FP16,
)
----

| pgwire SQL `CREATE TABLE ... WITH (...)`
a|
NOTE: In a table without a JSON or JSONB column, a `VECTOR(n)` column created over pgwire is checked against
dimension 1 today, so inserts of `n`-dimensional vectors fail (TD-SQLCOLL-1). Set precision on a REST-created collection instead.

[source,sql]
----
CREATE TABLE docs_fp16 (
    id BIGINT PRIMARY KEY,
    embedding VECTOR(768)
) WITH (canonical_embedding_precision = 'fp16');
----

| Arrow Flight _(experimental)_ `do_action("create_collection", ...)`
a|
[source,json]
----
{
  "name": "docs_fp16",
  "dimension": 768,
  "canonical_embedding_precision": "fp16"
}
----
|===

Accepted values (case-insensitive, matched across all protocols):

* Proto enum discriminants: `1`=fp32, `2`=fp16, `3`=bf16, `4`=int8, `5`=uint8
* SCREAMING label: `EMBEDDING_PRECISION_FP16`, etc.
* Shorthand: `fp16` / `f16` / `half` / `float16`, `bf16` / `bfloat16`,
  `int8` / `i8` / `int8_scalar`, `uint8` / `u8` / `uint8_scalar`

Unknown values fall back to `fp32` with a warn-level log (the
collection still gets created so a typo doesn't block deployment).

== What happens after creation

Once a collection is set to a non-fp32 precision, every ingest path
coerces records to that precision before WAL append:

* REST / gRPC `POST /api/v1/vectors/batch` — coerced at
  `VectorOperationsService::vector_batch_v1`.
* Async embedding drainer (queue-driven ingest) — coerced at
  `BulkLoadDrainerSink`.
* Compaction read+rewrite — preserves the source precision via the
  `precision_hint` channel from the compaction scheduler.

The on-disk Arrow column for an fp16 collection is `Float16Array`
(native fp16 bytes, not fp32 padded). The byte savings are visible
immediately at WAL flush and persist through compaction.

== Verifying the storage win

The metric family `proximadb_embedding_precision_canonical_bytes`
exposes the per-(collection, precision) byte total at the
`/metrics/prometheus` endpoint:

[source,bash]
----
curl -s http://localhost:5678/metrics/prometheus | grep canonical_bytes
# proximadb_embedding_precision_canonical_bytes{collection="docs_fp16",precision="fp16"} 1572864
# proximadb_embedding_precision_canonical_bytes{collection="docs_fp32",precision="fp32"} 3145728
----

For equal record counts at the same dimension, the fp16 collection's
bytes should be ~50% of the fp32 baseline (the ~3% overhead vs the
ideal 50% comes from Arrow file framing — schema, index, footer — and
amortizes below the noise floor at production scales).

== Recall impact

fp16 is bit-exact for any value the fp16 format can represent, and
fp32-to-fp16 conversion is deterministic. Embeddings from BGE / OpenAI
ada / Cohere typically sit well inside fp16's representable range, so
recall delta is below the noise floor of ANN search (HNSW
`ef_construction`, IVF `nlist`, PQ quantization usually dominate).

bf16 has fp32's dynamic range with fp16's bit width — choose it for
embeddings that hit fp16's range limit (very large magnitudes,
unusual normalization, or pre-attention activations).

int8 / uint8 are scalar-quantized with a per-cell scale; expect a
~1-3% recall@10 delta vs fp32 baselines on typical embedding
distributions. Use them when the byte-quartering matters more than
the recall floor.
