== Vision Statement

Build a multi-model database platform that treats storage formats and catalogs as the long-lived
contract, enabling specialized engines (SQL, graph, vector, search) to interoperate on the same
data with unified governance, deployment flexibility, and cross-model semantics.

== Problem Statement

Organizations manage data across multiple modalities (text, graphs, embeddings, structured
tables, logs, and media). Specialized databases are powerful but siloed, forcing teams to
duplicate data, manage inconsistent governance, and stitch together query workflows. A unified
platform is needed to preserve best practices from domain-specific databases while providing a
coherent, scalable, and evolvable data plane.

== Executive One-Pager (Talk Track)

=== What It Is

ProximaDB is a modular, multi-model data platform where storage formats and catalogs are the
long-lived contract, and specialized engines (SQL, graph, vector, search) interoperate on shared
data. It delivers a single data plane for AI and analytics without forcing a single database
paradigm.

=== Why Now

* AI and analytics workloads span multiple data modalities.
* Specialized databases are powerful but expensive to integrate and govern.
* Teams need faster iteration without long-term lock-in.

=== Business Impact

* **Faster AI delivery**: fewer handoffs between storage systems and model pipelines.
* **Lower integration cost**: fewer bespoke ETL jobs and data sync processes.
* **Governance at scale**: consistent policies, lineage, and access controls.
* **Cost efficiency**: decoupled storage and compute reduces over-provisioning.
* **Future-proofing**: stable formats protect data investments as workloads evolve.

* Time-to-first-result for a new use case (days to hours).
* Pipeline reduction (number of services and ETL jobs eliminated).
* Cost-per-query or cost-per-ingest vs. current stack.

== Builder Day-1 Workflow (Developer Narrative)

=== Goal

Build an AI labeling pipeline that ingests assets, creates embeddings, organizes labels in a
taxonomy graph, and serves hybrid search (semantic similarity + structured filters).

=== Steps

1. **Create a document collection** for raw assets and labeling metadata.
2. **Ingest assets** with dataset, source, and label status fields.
3. **Attach embeddings** in a vector collection for semantic search.
4. **Build a label taxonomy** in a graph for label relationships and suggestions.
5. **Query** for unlabeled items using semantic similarity plus structured filters.

=== Outcome

In one API surface, you get a labeling queue driven by semantic search, structured filters, and
graph context, without moving data across multiple systems.

=== Builder Quickstart: AI Labeling + Hybrid Search

This workflow uses canonical `/api/v2` record endpoints for embedding writes and
search. Document and graph examples that still use `/api/v1/*` are deprecated
compatibility facades while those modality routes converge on record-backed
surfaces.

[source,bash]
----
# 1) Create a document collection for labeling assets
curl -X POST http://localhost:5678/api/v1/documents/collections \
  -H "Content-Type: application/json" \
  -d '{"name": "labeling_assets"}'

# 2) Ingest assets with labeling metadata
curl -X POST http://localhost:5678/api/v1/documents/collections/labeling_assets/documents \
  -H "Content-Type: application/json" \
  -d '{
    "document": {
      "asset_id": "asset_1",
      "uri": "s3://labels/raw/asset_1.txt",
      "label_status": "unlabeled",
      "dataset": "support",
      "source": "tickets"
    }
  }'

# 3) Create a record collection for embeddings
curl -X POST http://localhost:5678/api/v2/collections \
  -H "Content-Type: application/json" \
  -d '{
    "name": "labeling_embeddings",
    "dimension": 2,
    "engine": "sst",
    "distance_metric": "cosine",
    "enable_proxima_record": true
  }'

# 4) Insert records with embeddings and props for hybrid filtering
curl -X POST http://localhost:5678/api/v2/collections/labeling_embeddings/records/batch \
  -H "Content-Type: application/json" \
  -d '{
    "records": [
      {
        "id": "asset_1",
        "vector": [0.1, 0.2],
        "props": {
          "asset_id": "asset_1",
          "label_status": "unlabeled",
          "dataset": "support"
        }
      }
    ]
  }'

# 5) Create a label taxonomy graph
curl -X POST http://localhost:5678/api/v1/graph/graphs \
  -H "Content-Type: application/json" \
  -d '{"graph_id": "label_taxonomy"}'

curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "node": {
      "id": "label:refund",
      "labels": ["Label"],
      "properties": {"name": "Refund"}
    }
  }'

curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "node": {
      "id": "label:billing",
      "labels": ["Label"],
      "properties": {"name": "Billing"}
    }
  }'

curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/edges \
  -H "Content-Type: application/json" \
  -d '{
    "edge": {
      "from_node_id": "label:refund",
      "to_node_id": "label:billing",
      "edge_type": "RELATED_TO",
      "weight": 1.0
    }
  }'

# 6) Hybrid search: semantic similarity + structured filters
curl -X POST http://localhost:5678/api/v2/collections/labeling_embeddings/search \
  -H "Content-Type: application/json" \
  -d '{
    "vector": [0.1, 0.2],
    "top_k": 10,
    "filter": {
      "label_status": "unlabeled",
      "dataset": "support"
    }
  }'

# 7) Optional: traverse taxonomy for label suggestions
curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/traverse \
  -H "Content-Type: application/json" \
  -d '{"start_node_id": "label:refund", "max_depth": 1}'
----

[source,python]
----
from proximadb_sdk import ProximaDBClient

client = ProximaDBClient("http://localhost:5678")

client.create_document_collection("labeling_assets")
client.insert_document("labeling_assets", {
    "asset_id": "asset_1",
    "uri": "s3://labels/raw/asset_1.txt",
    "label_status": "unlabeled",
    "dataset": "support",
})

client.create_collection(
    name="labeling_embeddings",
    dimension=384,
    storage_engine="sst",
    distance_metric="cosine",
)

client.insert_records("labeling_embeddings", [
    {
        "id": "asset_1",
        "vector": [0.1, 0.2],
        "props": {"asset_id": "asset_1", "label_status": "unlabeled", "dataset": "support"},
    }
])

results = client.search("labeling_embeddings", vector=[0.1, 0.2], top_k=10)
print(results)
----

=== Labeling Loop (Writeback + Re-Query)

When a labeler makes a decision, write it back to the system so the next search only returns
unlabeled items. Use a decisions collection for audit, and update the embedding metadata by
re-inserting the vector with the new label status.

[source,bash]
----
# 1) Record the labeling decision
curl -X POST http://localhost:5678/api/v1/documents/collections \
  -H "Content-Type: application/json" \
  -d '{"name": "labeling_decisions"}'

curl -X POST http://localhost:5678/api/v1/documents/collections/labeling_decisions/documents \
  -H "Content-Type: application/json" \
  -d '{
    "document": {
      "asset_id": "asset_1",
      "label": "Refund",
      "labeler": "user_42",
      "decision_ts": "2025-01-01T00:00:00Z"
    }
  }'

# 2) Update embedding metadata by delete + re-insert
curl -X DELETE http://localhost:5678/api/v2/collections/labeling_embeddings/records/asset_1

curl -X POST http://localhost:5678/api/v2/collections/labeling_embeddings/records/batch \
  -H "Content-Type: application/json" \
  -d '{
    "records": [
      {
        "id": "asset_1",
        "vector": [0.1, 0.2],
        "props": {
          "asset_id": "asset_1",
          "label_status": "labeled",
          "label": "Refund",
          "dataset": "support"
        }
      }
    ]
  }'

# 3) Optional: link asset to label in the taxonomy graph
curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "node": {
      "id": "asset:asset_1",
      "labels": ["Asset"],
      "properties": {"asset_id": "asset_1"}
    }
  }'

curl -X POST http://localhost:5678/api/v1/graph/graphs/label_taxonomy/edges \
  -H "Content-Type: application/json" \
  -d '{
    "edge": {
      "from_node_id": "asset:asset_1",
      "to_node_id": "label:refund",
      "edge_type": "LABELED_AS",
      "weight": 1.0
    }
  }'

# 4) Re-query for unlabeled items only
curl -X POST http://localhost:5678/api/v2/collections/labeling_embeddings/search \
  -H "Content-Type: application/json" \
  -d '{
    "vector": [0.1, 0.2],
    "top_k": 10,
    "filter": {"label_status": "unlabeled"}
  }'
----

[source,python]
----
from proximadb_sdk import ProximaDBClient, ProximaRecord

client = ProximaDBClient("http://localhost:5678")

# Write back the label decision by upserting the same record ID
client.insert_records(
    "labeling_embeddings",
    records=[
        ProximaRecord(
            id="asset_1",
            vector=[0.1, 0.2],
            flexible_fields={
                "asset_id": "asset_1",
                "label_status": "labeled",
                "label": "Refund",
                "dataset": "support",
            },
        )
    ],
)

# Re-query only unlabeled items
results = client.search(
    "labeling_embeddings",
    vector=[0.1, 0.2],
    top_k=10,
    metadata_filter={"label_status": "unlabeled"},
)
print(results)
----

=== Unified Query (Cross-Model SQL)

Unified SQL + vector + graph queries are now available via the Federated Query endpoint.
The syntax extends standard SQL with functions for each data model.

[source,sql]
----
-- Cross-model query: Find unlabeled assets similar to a reference,
-- with their taxonomy context from the label graph
SELECT
    v.id AS asset_id,
    v.score AS similarity,
    d.uri AS asset_uri,
    g.related_labels
FROM VECTOR_SEARCH('labeling_embeddings', '[0.1, 0.2, ...]', 10) v
JOIN LATERAL DOCUMENT_QUERY('labeling_assets',
    json_build_object('asset_id', v.id, 'label_status', 'unlabeled')) d ON true
JOIN LATERAL GRAPH_QUERY(format(
    'MATCH (a:Asset {id:"%s"})-[:LABELED_AS]->(l:Label)-[:RELATED_TO]->(r)
     RETURN collect(r.name) as related_labels', v.id)) g ON true
ORDER BY v.score DESC;
----

[source,bash]
----
# Execute through pgwire/SQL when possible. The REST v1 endpoint remains a
# deprecated compatibility facade for existing automation.
curl -X POST http://localhost:5678/api/v1/unified/federated \
  -H "Content-Type: application/json" \
  -d '{
    "sql": "SELECT v.id, v.score FROM VECTOR_SEARCH('\''labeling_embeddings'\'', '\''[0.1, 0.2]'\'', 10) v WHERE v.id IN (SELECT asset_id FROM DOCUMENT_QUERY('\''labeling_assets'\'', '\''{\"label_status\": \"unlabeled\"}'\''))"
  }'
----

**SQL Extensions Available:**

|===
| Function | Purpose | Example

| `VECTOR_SEARCH(collection, vector, k)`
| Similarity search
| `VECTOR_SEARCH('embeddings', '[0.1,0.2]', 10)`

| `embedding <-> vector`
| pgvector-compatible distance
| `ORDER BY embedding <-> '[0.1,0.2]'::vector`

| `GRAPH_QUERY(cypher)`
| Graph traversal
| `GRAPH_QUERY('MATCH (a)-[:KNOWS]->(b) RETURN b')`

| `DOCUMENT_QUERY(collection, filter)`
| Document retrieval
| `DOCUMENT_QUERY('assets', '{"status":"active"}')`

| `LOGS(namespace)`
| Log search
| `LOGS('production') WHERE level = 'ERROR'`
|===

== Architecture Approach

=== Data Plane (Format and Storage)

* Write path uses a unified WAL and memtables to support durability across models.
* Storage formats are versioned and documented to allow multiple engines to read and write.
* Tiered storage supports HTAP and elastic scaling: WAL plus native row/delta state for
  strong-freshness OLTP, PAX/HTAP blocks where mixed point/scan access is useful, and
  Parquet/Iceberg/Arrow publications for OLAP/open-format reads.

=== Compute Plane (Engines and Execution)

* Vector, graph, document, and relational engines remain modular and optimized for their
  workloads.
* A unified planner translates queries into a multi-stage execution plan across engines.
* Native/Volcano execution owns latency-sensitive OLTP and constraint-sensitive plans; DataFusion
  owns OLAP/MPP over cataloged snapshots and explicit delta-union routes.
* Runtime adapters support external compute engines (Trino, Spark, custom runtimes) when useful,
  without making them schema, policy, or write authorities.

=== Control Plane (Catalog and Governance)

* Unified catalog tracks schema, indexes, embeddings, relationships, lineage, and access policy.
* Supports internal information schema and external catalogs (Glue, Hive, Iceberg, Delta).
* Security and governance apply consistently across models (row, column, edge, and embedding
  policies).

=== Indexing and Search

* Multiple indexes can coexist on the same dataset (B-tree, inverted, vector, graph adjacency).
* Index selection is query-aware and cost-based rather than hard-coded to a single model.

== Use Case Portfolio

=== AI Data Labeling and Curation at Internet Scale

* Ingest multi-modal data from object stores and streaming sources.
* Create embeddings and link them to raw assets and metadata.
* Use graph relationships for ontology, taxonomy, and provenance tracking.
* Provide filtered semantic search for labeling workflows and dataset slicing.
* Enforce governance and access policies for multi-tenant teams.

=== Cross-Model Semantic Search

* Search documents by text and embedding similarity with structured filters.
* Traverse graph relationships to add context and reduce hallucinations.
* Combine inverted index relevance with vector similarity for hybrid ranking.

=== HTAP Analytics and Operational Queries

* Serve transactional writes and analytical queries from the same data plane.
* Run real-time filters on operational metadata and aggregate across time.
* Keep PostgreSQL-style constraint semantics on the native row/delta path while exposing
  snapshot-safe analytics through DataFusion.

=== Data Engineering and Model Building

* Feature store across structured tables, documents, and embeddings.
* Lineage and versioned datasets for reproducible training.
* Cross-domain joins for feature enrichment.

=== Specialized Vertical Workloads

* Knowledge graphs for security, compliance, or supply-chain analytics.
* Observability data combined with service graphs for root-cause analysis.
* Enterprise search that spans logs, documents, and embeddings.

== Inspiration From Domain-Specific Databases

* **Neo4j**: graph traversal semantics, relationship indexing.
* **Cassandra**: partitioned storage and replication for high-ingest paths.
* **MongoDB**: flexible document model and aggregation pipelines.
* **Milvus / Pinecone / Vespa**: vector index lifecycle and search performance.
* **Solr / Elastic**: inverted index, relevance ranking, and aggregations.

== Suggested Design Approach (Phased)

=== Phase 1: Format and Catalog Contract

* Define storage format boundaries and compatibility rules.
* Extend catalog to model datasets, embeddings, edges, and lineage.

=== Phase 2: Cross-Model Query and Indexing

* Unify query planner for graph + vector + document + relational operators.
* Implement hybrid ranking (inverted + vector) and graph-aware filters.

=== Phase 3: Deployment and Ecosystem Integration

* External catalog integration and object-store-first deployments.
* Compute adapters for Trino/Spark and embedded runtime options.
