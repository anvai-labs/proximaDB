= Architecture Overview
:toc: left
:toclevels: 2
:icons: font

[.lead]
ProximaDB is a SQL-first context engine on object storage: a Postgres-compatible database in
which vectors, JSON documents and relationships are first-class
(link:../12-design/adr/ADR-096-product-direction-sql-first-context-engine.adoc[ADR-096]).

NOTE: This is the short concept overview. The authoritative whole-system view is
link:../12-design/SYSTEM_MAP_2026_05_30.adoc[SYSTEM_MAP_2026_05_30]; what is Supported, Beta or
Experimental is decided only by link:../SUPPORTED_SURFACE.adoc[SUPPORTED_SURFACE.adoc]. This page
deliberately carries no status tables.

== Principles

* **SQL is the front door.** PostgreSQL wire carries SQL and transactions; vectors, JSON and
  graph appear inside SQL. REST v2, gRPC v2 and Arrow Flight serve SDKs, typed RPC and bulk
  columnar transfer on one multiplexed port (Flight's canonical `vector_search` is Supported; Flight as a general customer transport is
  experimental).
* **One canonical record.** A record has an identifier, typed properties and embeddings. The
  relational row, vector index, document view and graph are projections of it
  (link:../12-design/adr/ADR-094-unified-storage-substrate-and-compute-seam.adoc[ADR-094]).
* **The engine routes.** `ComputeScheduler::route_select` picks one backend per plan: DataFusion
  for Parquet-backed analytical tables
  (link:../12-design/adr/ADR-052-analytics-execution-competitiveness-codesign.adoc[ADR-052]), the
  native Volcano executor otherwise; similarity search runs on the vector engines.
* **Tenancy is structural.** Tenant identity enters at the network edge and flows as
  `TenantContext` to every I/O boundary; every object key is built by `DrPathBuilder` under
  `data/{tenant}/{namespace}/…`.
* **Co-designed for object storage.** Format, cache, engine and network are tuned together against
  object-store round trips and egress, measured per query.

== Write path

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
  participant C as Client
  participant API as pgwire / REST / gRPC
  participant WAL as WAL (fsync)
  participant MEM as Memtable
  participant OBJ as Object storage
  C->>API: INSERT / UPDATE / DELETE (or COMMIT)
  API->>WAL: append (one group frame per commit when atomic commit is on)
  WAL-->>API: durable
  API->>MEM: apply
  API-->>C: acknowledge
  MEM->>OBJ: flush to Parquet / PAX segments (async)
----

A write is acknowledged after the WAL append completes under the configured sync mode (per-write
fsync gives the durable-on-acknowledge guarantee). A delete is a tombstone meant to supersede the
live version on every read surface until compaction removes both; one known gap remains open
(TD-MEMTABLE-MVCC-1: the in-memory version order is not total). With the
`[oltp] atomic_commit` gate on, a transaction commits as one checksummed WAL frame
(link:../12-design/adr/ADR-095-postgres-compatible-oltp-on-object-storage.adoc[ADR-095]).

== Query path

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
  participant C as Client
  participant FE as SQL front end
  participant S as ComputeScheduler
  participant E as Chosen engine
  participant T as Unflushed delta + flushed segments
  C->>FE: SELECT … (may include vector_search / <-> / JSON operators)
  FE->>S: logical plan
  S->>E: one backend per plan
  E->>T: read: newest version per record, dead records dropped
  E-->>C: rows (route disclosed by EXPLAIN)
----

Native cross-modal queries that SQL cannot express go to `POST /api/v2/query`; see the query
surface table in link:../SUPPORTED_SURFACE.adoc[SUPPORTED_SURFACE.adoc].
