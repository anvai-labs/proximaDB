= Architecture Overview
:toc: left
:toclevels: 2
:icons: font

[.lead]
ProximaDB is a multi‑model database that unifies vectors, documents, graphs, and observability data behind a single data plane.

== Core Principles

* **Unified data plane**: vector, document, and observability writes share WAL semantics.
* **Pluggable engines**: storage engines are optimized for different workloads.
* **Model adapters**: each model (vector/document/graph/obs) has a dedicated service layer.
* **Developer‑first**: REST + gRPC are primary; pgwire is experimental.
* **Time-series-native**: first-class time-partitioned storage with ASOF joins and downsampling.
* **Event-sourcing-native**: append-only immutable event logs for compliance and audit trails.

[NOTE]
====
Regardless of entry point, ranking is owned by a *single shared `FusionService`*. Vector
`/search`, hybrid dense+BM25 retrieval, and graph `fusion-search` all delegate to one fusion
engine (calibrated candidate-set fusion over the `oid`-keyed seam). Per-surface fusion is an
anti-pattern — each model service above is a *source of candidates*, not a ranker. See
link:hybrid-fusion.adoc[Hybrid Fusion] and
link:../12-design/SEARCH_SURFACE_CONTRACT_2026_06_24.adoc[Search Surface Contract].
====

=== SQL Extensions

ProximaDB extends SQL with functions that route to the appropriate data model:

|===
| Extension | Syntax | Purpose

| `VECTOR_SEARCH` | `VECTOR_SEARCH(collection, vector, top_k)` | Similarity search
| `<->` operator | `embedding <-> '[...]'::vector` | pgvector-compatible distance
| `GRAPH_QUERY` | `GRAPH_QUERY('MATCH (a)-[:REL]->(b) ...')` | Cypher traversal
| `DOCUMENT_QUERY` | `DOCUMENT_QUERY(collection, filter)` | JSON document query
| `LOGS` | `LOGS(namespace)` | Log query
| `METRICS` | `METRICS(namespace)` | Metric query
|===

=== Cross-Model Query Example

[source,sql]
----
-- Find products similar to user preferences, get reviews, check inventory via graph
SELECT u.name, v.product_id, v.score, d.review_text, g.in_stock
FROM users u
JOIN LATERAL VECTOR_SEARCH('products', u.preference_vector, 10) v ON true
JOIN LATERAL DOCUMENT_QUERY('reviews', 'product_id = "' || v.product_id || '"') d ON true
JOIN LATERAL GRAPH_QUERY('MATCH (p:Product {id: "' || v.product_id || '"})-[:STOCKED_IN]->(w:Warehouse) RETURN w.quantity > 0 as in_stock') g ON true;
----

=== Result Fusion Strategies

When combining results from multiple models, the engine supports:

* **Intersection** (AND) - Records must match all sub-queries
* **Union** (OR) - Records from any sub-query
* **Reciprocal Rank Fusion (RRF)** - Weighted rank combination
* **Ranked Fusion** - Custom weights per model

== Hybrid Search Architecture

Hybrid search combines BM25 keyword matching with vector similarity for improved retrieval accuracy.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart LR
    Q[Query] --> BM25[BM25 Index\n(tantivy)]
    Q --> VEC[Vector Search\n(engine)]
    BM25 --> RRF[Reciprocal Rank\nFusion]
    VEC --> RRF
    RRF --> RES[Ranked Results]
----

=== Fusion Strategies

* **Reciprocal Rank Fusion (RRF)**: Default. Combines ranked lists without score normalization. Robust across different score distributions.
* **Weighted Linear**: User-specified weights for BM25 vs vector scores. Useful when one signal is known to be more reliable.
* **Learned Fusion**: RL-based weight optimization using the existing Thompson Sampling planner.

=== Integration Points

* BM25 index maintained alongside vector index per collection
* Queries can specify `search_mode`: `vector_only`, `keyword_only`, `hybrid` (default)
* Filter predicates applied before fusion for efficiency

== CQRS and Event Sourcing Pattern

For workloads like algorithmic trading, ProximaDB supports Command Query Responsibility Segregation (CQRS) combined with Event Sourcing.

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
flowchart TB
    subgraph Commands[Command Path]
        CMD[Write Command] --> VAL[Validation]
        VAL --> EVT[Event Store\n(append-only)]
        EVT --> PROJ[Projections]
    end

    subgraph Queries[Query Path]
        QRY[Read Query] --> CACHE[Cache Layer]
        CACHE --> MAT[Materialized Views]
        MAT --> IDX[Indexes]
    end

    PROJ --> MAT
    EVT --> CDC[CDC Stream]
----

=== Key Properties

* **Immutability**: Events are append-only. No updates or deletes. Required for MiFID II and SEC compliance.
* **Projections**: Materialized views are derived from the event stream. Can be rebuilt from scratch.
* **Temporal Queries**: Query state at any point in time by replaying events up to a timestamp.
* **CDC Integration**: Event stream can be consumed by external systems via CDC sinks (Kafka, webhooks).

== Current Implementation Notes

* **Phase 1 Complete**: SST is Supported; VIPER/HELIX/NOVA are Beta; SWIFT/RAPTOR are Experimental. WAL, APIs, quantization, and AXIS indexes are present at the tiers listed in the support contract.
* **Phase 2 Complete**: Cross-model queries, graph database (ORION), document store, observability.
* **Phase 3 In Progress**: External catalogs, streaming/CDC, distributed operations.
* **Phase 4 Foundations Beta**: Time-series (TST) and event-sourcing engines are complete; hybrid search (BM25) is wired. Product packaging, API parity, and at-scale validation are in progress -- these are Beta surfaces in v0.2.
* Document and observability services use WAL‑backed recovery.
* Unified query execution supports VECTOR_SEARCH, GRAPH_QUERY, DOCUMENT_QUERY, LOGS, METRICS.
