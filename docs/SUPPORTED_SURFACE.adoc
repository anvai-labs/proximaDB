== MVP Trust Corridor

The broad matrix below describes the whole product. The smaller customer acquisition promise is
**Object-storage-native context serving for SQL, JSON, and vectors**, delivered initially through
single-tenant, single-node SST and canonical REST v2 record operations. Its machine-readable contract is
link:./00-product/MVP_TRUST_CORRIDOR.toml[MVP_TRUST_CORRIDOR.toml].

The corridor is intentionally stricter than this matrix: create, typed batch write, get, filtered
scan, filtered vector search, delete, and route-health form one hard-failing roundtrip. pgwire,
hybrid retrieval, multimodel projections, alternate engines, and distributed execution do not
enter the MVP promise until their listed security, recovery, conformance, and evidence gates close.
The quickstart uses local storage. S3, Azure, and GCS are co-design/evidence targets and remain Beta
for the MVP until the same correctness, crash/restart, bounded-memory, and economic suite passes on
each backend.
Metadata filters in the smoke are query correctness boundaries, not authorization evidence.
Multi-tenant ABAC remains Beta until stable tenant IDs are total, missing IDs fail closed, and the
cross-surface REST/gRPC/Flight/pgwire admit/deny matrix passes.

== Canonical API Surface

REST `/api/v2` is the **sole canonical surface** for all ProximaDB clients as of 2026-08-03.

[IMPORTANT]
====
* *REST /api/v2* — canonical; all new clients and integrations must target this prefix.
* *REST /api/v1* — deprecated compatibility adapter. Requests are still accepted but must
  lower into v2 handlers internally. The v1 prefix will be retired; do not document or
  advertise it in new collateral.
* *REST /api/v3* — **removed**. The document-ingest handler lives canonically at
  `POST /api/v2/collections/{id}/documents`; the former v3 308-redirect alias was
  deleted (it was never an OpenAPI/released surface). Target `/api/v2` for all clients.
* *gRPC v1 (`proximadb.v1.*`)* — **REMOVED** (sunset completed). The v1 services were
  hard-deleted; the former opt-in (`enable_grpc_v1_compat` / `PROXIMADB_GRPC_V1_COMPAT`)
  no longer exists — setting it does nothing. The v1 *proto types* remain in-tree as
  internal message shapes only (ratchet-tracked by `scripts/check_v1_proto_usage.py`);
  they are not a served surface. Target `proximadb.v2.*` exclusively.
====

=== Query Surfaces (which language goes where)

Query languages are served by distinct, non-overlapping surfaces. pgwire is *not* a universal
query endpoint, and `/api/v2/query` is *not* SQL-over-REST. Route by language:

[cols="1,2,2,1"]
|===
| Surface | Language(s) | Use for | Status

| *pgwire* (PostgreSQL wire)
| ANSI *SQL* (DataFusion execution)
| SQL clients and tools — psql, psycopg2/asyncpg, JDBC, BI/ORM ecosystem.
| Beta — autocommit SQL subset; multi-tenant identity/ABAC closure is still tracked by TD-ABAC-10/11

| *REST `POST /api/v2/sql`*
| One authenticated *SQL* statement: tenant-scoped relational SELECT/DDL/DML
  plus the existing vector/graph SQL extensions.
| HTTP/JSON clients that need SQL without a PostgreSQL or gRPC driver. This is
  a thin transport adapter over the same typed SQL port and relational
  planner/executor as gRPC; execution cells remain `ProximaValue` until JSON
  serialization. Request parameters are not yet supported, so clients must not
  send or interpolate parameter payloads through this endpoint.
| Beta (single statement; API-key/JWT identity + ABAC live-ratchet covered)

| *gRPC `proximadb.v2.ProximaRecordService.ExecuteQuery`*
| *SQL with vector/graph extensions* (e.g. `VECTOR_SEARCH`) *and tenant-scoped
  relational SQL* — SELECT reads + DDL (`CREATE`/`ALTER`/`DROP`) + DML
  (`INSERT`/`UPDATE`/`DELETE`).
| Token/SSO-authenticated programmatic queries: gRPC carries bearer/JWT in
  metadata (pgwire cannot) and uses HTTP/2 + protobuf. Relational SELECTs route
  through the same pipeline as pgwire (ComputeScheduler → DataFusion/Volcano);
  DDL/DML route through the same tenant-scoped `DdlService`/`DmlService` seams —
  all scoped to the `x-tenant-id` tenant (TD-064). This RPC is single-statement;
  pgwire is also autocommit-only and rejects transaction control with SQLSTATE `0A000`.
| Beta — programmatic SQL exists, but broader relational and cross-modal parity is not in the MVP corridor

| *REST/gRPC `/api/v2/query`* (unified query port)
| *UQL* (unified multi-modal), *Federated* SQL extensions, *AQL*
| ProximaDB-native cross-modal queries (vector + graph + relational) that SQL cannot express.
| UQL/Federated Beta; AQL Planned

| *gRPC `proximadb.v2.ProximaGraphService`*
| Node/edge/query/traversal/shortest-path/stats + analytic
  (GetConnectedComponents, HasCycle), batch (BatchCreateNodes/Edges),
  unique-constraint DDL, and server-streaming (StreamTraverse) RPCs (TD-124).
| Programmatic graph access from the SDK.
| Beta

| *Graph `ExecuteQuery`* (Cypher)
| Declarative graph query — supported openCypher subset (single-node patterns
  and linear traversal chains with equality property constraints) on v2 (TD-124).
| Now on v2 `ProximaGraphService`. GREMLIN reserved/unbacked.
| Beta (subset)

| *Graph `ExecuteHybridQuery` / `CreateGraphWithEngine` / `GetPulsarStats`*
| Cross-modality hybrid query; engine-typed graph create; PULSAR stats
| **Absent from v2; the v1 surface they were deferred to is REMOVED** (the
  `enable_grpc_v1_compat` gate no longer exists). Hybrid search is served by
  REST `/api/v2/hybrid/search`; a v2-native gRPC hybrid RPC would be a new
  design, not a port. `CreateGraphWithEngine`/`GetPulsarStats` are
  retired/unimplemented (PULSAR/QUASAR). See TD-124 + the v2 graph.proto
  service comment.
| Not planned (absent)
|===

[NOTE]
====
* pgwire is *SQL-only* and cannot serve UQL/AQL/Cypher; those non-SQL languages require the
  unified query port (`/api/v2/query`) or the graph service — they are not replaceable by pgwire.
* SQL is served by *three adapters over one execution authority* (TD-121/TD-135).
  *pgwire* serves the PostgreSQL ecosystem
  (psql/JDBC/BI/ORM, Postgres-native auth) in autocommit mode. `BEGIN`, `COMMIT`, `ROLLBACK`,
  savepoints, and other transaction-control statements return SQLSTATE `0A000`; a simple-query
  batch containing transaction control is rejected before any statement in the batch executes.
  REST `POST /api/v2/sql` serves authenticated HTTP/JSON clients and deliberately supports
  one statement without parameter binding in its initial beta contract. The gRPC
  `ProximaRecordService.ExecuteQuery` RPC is *token/SSO-authenticated* (bearer/JWT in metadata,
  which pgwire's password/MD5 auth cannot carry) and serves vector/graph-extension SQL (e.g.
  `VECTOR_SEARCH`) plus *tenant-scoped relational SQL — SELECT reads AND DDL/DML writes*: SELECTs
  route through the *same* pipeline pgwire uses (`ComputeScheduler::route_select` →
  DataFusion/Volcano); DDL (CREATE/ALTER/DROP) and DML (INSERT/UPDATE/DELETE) route through the
  *same* tenant-scoped `DdlService`/`DmlService` seams — all scoped to the `x-tenant-id` tenant
  (TD-064). *Out of scope on gRPC:* multi-statement transactions — the RPC is single-statement.
  It is *not* deprecated. For large
  columnar result sets prefer Arrow Flight.
* *Apache Calcite*, if adopted, is an *internal* federated-SQL planner behind pgwire and the
  Federated path — not a client surface, and not a substitute for the non-SQL languages.
* SSO/governance (auth, RLS, tenancy) is enforced uniformly at the `TenantContext` I/O boundary,
  independent of query language — never as a per-language interface.
====

=== Endpoint And Composition Ownership

The same domain objects appear through record, document, graph, hybrid, and
entity-shaped APIs. Treat this table as the guardrail against adding another
storage path when the requirement is really orchestration over existing
primitives.

[cols="1,2,2,2", options="header"]
|===
| Shape | Existing reachable surface | Owns today | Proposal / rule

| Record / vector
| REST `/api/v2/collections/{id}/records/*`, REST `/api/v2/collections/{id}/search`, gRPC `proximadb.v2.ProximaRecordService`
| Canonical vector-bearing records, typed props, collection/schema lifecycle, ANN/vector search, SQL-over-gRPC
| Keep as the durable authority for embeddings and typed metadata. Multi-version embeddings are modeled as records/embedding cells or derived history, not as a separate entity store.

| Document
| REST `/api/v2/document-collections/*`, REST `/api/v2/collections/{id}/documents` text ingest, gRPC `proximadb.v2.ProximaDocumentService` CRUD
| JSON/document body, evidence chunks, document query/aggregate compatibility path
| Keep as beta document convenience and provenance/evidence lane. Durable convergence remains `ProximaRecord` + `props`; do not duplicate entity metadata here and in an entity store.

| Graph
| REST `/api/v2/graphs/*`, gRPC `proximadb.v2.ProximaGraphService`
| Nodes, edges, labels, properties, traversal, graph stats, Cypher subset
| Keep topology and relationship traversal here. ORION/CSR is a rebuildable projection over canonical records; graph node embeddings are a convenience for single-vector nodes, not the place to own multi-version semantic embeddings.

| Hybrid / fusion
| REST `/api/v2/collections/{id}/search` for dense+BM25 hybrid; REST `/api/v2/graphs/{graph_id}/fusion-search` for the TD-137 vector-seed -> graph-expand fusion instance
| Candidate-set fusion and calibrated ranking across existing modalities
| Converge every cross-modal blend on the `oid`-keyed fusion seam (`seed -> expand -> calibrate -> fuse-by-oid -> rank`). Do not add one-off entity/vector/document/graph join handlers.

| Entity / SKS
| gRPC v1 `proximadb.v1.EntityService` removed (sunset completed — no opt-in flag remains); legacy REST v1 entity routes and split `ProximaEntityStore` exist as compatibility/transition code
| Semantic convenience shape: entity id, metadata, embeddings, provenance, relations, temporal fields
| Do not create v2 entity storage. A future v2 entity surface, if exposed, must be an orchestration facade over record/vector + graph + document/provenance + event/temporal history, with `TenantContext` and structural tenant paths at every I/O boundary.
|===

[NOTE]
====
An entity is a projection/composition of existing primitives: a graph node for
topology, one or more vector-bearing records for embeddings, document records
for evidence/provenance, and event/history records for temporal state. The v1
`EntityService` proto shape is not authority to add a fourth durable substrate.
====

== Status Tiers

|===
| Tier | Meaning | Guidance

| Supported
| Primary product path with coherent API behavior on the canonical single-node surface.
| Safe default for adoption, examples, and positioning.

| Beta
| Implemented and useful, but still has known execution or operator gaps.
| Use with review and explicit scope control.

| Experimental
| Foundations exist, but behavior, transport, or support expectations are still in flux.
| Feature-gate and avoid broad product claims.

| Planned
| Roadmap item without a coherent product surface yet.
| Do not market as implemented.

| Security runtime
| Beta
| JWT, API key, SSO hooks, mTLS identity, and CRL-backed revocation reload/freshness checks are present. Tenant identity is credential-bound by policy on EVERY network surface (TD-TENANT-1, one shared primitive in `proximadb-tenant`): an assertion that contradicts an authenticated tenant binding is always rejected (HTTP 403 / gRPC PERMISSION_DENIED / SQLSTATE 28000); the bare assertion (REST `X-Tenant-ID`, gRPC/Arrow Flight `x-tenant-id` metadata, pgwire startup `database` + tenant session vars) is governed by `HeaderTrustPolicy` (`open` default / `authenticated-only` in the multi-tenant strict preset / `gateway-only` for trusted-gateway delegation via a first-class gateway-principal role marker), configurable via `[security.tenant] header_trust` and overridable via `PROXIMADB_TENANT_HEADER_TRUST`. Rejections emit `proximadb::tenant_audit` warns. The entitlement claim (`x-tenant-tier` on REST, gRPC, and Arrow Flight; `proximadb_tier` pgwire startup param) is governed by the same ladder via `[security.tenant] tier_header_trust` / `PROXIMADB_TIER_HEADER_TRUST` (ADR-0053 W8): an untrusted claim is dropped — never a 4xx — and the tenant resolves its default tier; under strict policies the pgwire startup parameter is inert (trust auth carries no binding). Generic OIDC bearer authentication is supported via `[security.authentication.oidc]` (TD-SSO-1: Kanidm, Keycloak, Okta, Azure Entra ID, Google Workspace; JWKS-validated RS256/ES256, any-of audience list, issuer aliases for bare-hostname `iss` forms, nested claim paths for Keycloak `realm_access.roles`, custom CA for internal PKI, configurable clock-skew/JWKS-TTL/timeout; IdP role claims cross only through the sanitized seam — gateway/operator delegation markers plus an operator allowlist, everything else dropped). REST request rate limiting is opt-in via `PROXIMADB_REST_RATE_LIMIT_RPM` (TD-RATE-1; default off — unset adds no middleware layer; per observed client IP, `/health` exempt, process-global ceiling at 10x the per-IP cap). Deprecated claim use and dropped tier claims are metered (`proximadb_deprecated_claim_uses_total`, `proximadb_tier_claims_dropped_total`) — the Flight legacy-alias retirement gate is `increase(proximadb_deprecated_claim_uses_total[7d]) == 0`. Claim *names* come from one shared vocabulary across all four surfaces (TD-TENANT-3): `x-tenant-id` / `x-tenant-tier` are canonical everywhere, Arrow Flight additionally DETECTS three deprecated tenant-alias names (`x-proximadb-tenant-id`, `tenant-id`, `tenant_id`) for deprecation warning only — they no longer grant a tenant (honoring removed 2026-08-29; the names are deleted at the next release boundary), and a stamped tier claim is normalized to a canonical tier id at the boundary so an alias and its canonical spelling resolve to the same cache entitlement.
| Security admin/status APIs and stronger online revocation policy are incomplete. pgwire authentication is dual-mode (TD-PGWIRE-AUTH-1): the dev default is trust, and `[security.authentication] enabled` (or `PROXIMADB_PGWIRE_AUTH=password`) requires SCRAM-SHA-256 — under SCRAM, strict policies AUTHENTICATE pgwire tenant selection and the `proximadb_tier` claim through the credential's binding instead of disabling them. ADR-031 tenant stable-id minting behind the `TenantStableIdResolver` port is pending (TD-TENANT-1).

| Beta

The former `/api/v1/hybrid/search` facade is a deprecated compat alias only. | Document chunking (Python SDK)
| Supported
| `proximadb_sdk.chunking_strategies` -- fixed-size, sentence, paragraph, recursive, sliding-window, semantic and token-budget strategies over a single span-first spine (ADR-091). A chunk is a span, so `source[start:end] == chunk.text` holds exactly wherever `offset_contract` is `exact`; totality, non-overlap, order preservation and the `max_chunk_size` cap are structural post-conditions enforced at one chokepoint, not per-strategy conventions. Grid (where a cut may land), measure (how a span is counted: `char` or `token`) and budget (window/overlap/floor/cap) are independently selectable. Conformance is an absolute gate, not a ratchet: 70 of 70 strategy x corpus cases clean, 0 violations, plus a golden-output oracle proving refactors are behaviour-neutral and an eval suite scoring retrieval quality (containment, fragmentation, structure preservation, attributability). Four post-partition capabilities run through one `ChunkPass` seam (ADR-091 D7), each declaring which of a chunk's three faces it touches -- the span it is, the text embedded, the text returned -- so ordering is derived rather than configured and is verified after every pass: heading-path annotation (default ON, free), near-duplicate elision (MinHash + exact Jaccard), structural context enrichment, and small-to-big parent linkage.
| The `token` measure needs the whole document, so it is refused on the streaming path rather than measured against a bounded buffer. Token-measured chunks are deliberately NOT char-contiguous (inter-token whitespace falls between chunks); totality is defined over non-whitespace characters. `deduplicate_chunks`, `enrich_context` and `link_parent_chunks` are all **default-OFF** because each changes what is stored: dedup is lossy by construction, enrichment costs KEU on every chunk (measured +4%), and parent linkage costs ~1.74x KSU (measured; it buys containment 0.75 -> 0.875 on the returned unit). Enrichment's *recall* gate is deliberately NOT in the chunking eval harness -- that harness is model-independent so its failures stay attributable to chunking, and enrichment changes only what a model sees; gate it in the ANN/recall harnesses. Chunk-policy fields on the wire (`EmbeddingPolicy.chunk`) are NOT connected to this subsystem -- see TD-CHUNK-5; configure chunking through the SDK, not the wire.

| Code chunking / symbol extraction (Python SDK)
| Experimental
| `CodeChunkingStrategy` delegates to the shared, commercially neutral `victor-codegraph` package (ADR-029; TD-CG2 deleted the duplicate in-SDK parsers). **Symbol extraction is measured against `victor-codegraph` 0.9.0, which is NOT YET PUBLISHED** (latest on PyPI: 0.8.1). On 0.8.1 the acceptance suite fails 30 of 54 and R1 fails for **15 of the 16** languages below, so the delegated chunker returns almost no symbols there. The extra therefore pins `>=0.9.0`, which is deliberately unsatisfiable from PyPI today: an install-time error naming the version is the honest form of that gap, and `code.py` carries a matching runtime guard for environments already holding an older copy. The per-language assertion (`SYMBOL_EXTRACTING_LANGUAGES`, R1) covers **16 languages** -- bash, c, cpp, csharp, go, java, javascript, kotlin, lua, php, python, rust, scala, swift, tsx, typescript -- across 40 file extensions. Relations (calls/imports/inheritance) are extracted for the same set and drive the code knowledge graph's edges. Chunks carry `offset_basis="byte"` (UTF-8 byte offsets, unlike every text strategy) and honour `max_chunk_size`.
| Requires the `codegraph` extra at **>= 0.9.0**; without it — or with an older copy — code chunking **fails loudly** naming what is missing, rather than degrading to unlabelled text windows or to a package that silently extracts nothing. The acceptance suite skips (naming the installed version) rather than running against a version its claims were never measured on. **No CI job installs the extra today**, so the delegated path is not yet exercised in CI; wiring it is gated on an adequate release. Two advertised languages are detected and chunked but yield **no symbols** (`ruby`, `sql` -- `COVERED_WITHOUT_SYMBOLS`), and six were withdrawn from the advertised map entirely (`perl`, `haskell`, `elixir`, `json`, `xml`, `yaml` -- `WITHDRAWN_LANGUAGES`); files of any unrecognised type still chunk through a fallback labelled `chunk_type="code_fallback"`, so a symbol-less window can never be mistaken for a symbol. Two upstream defects are pinned as strict xfails: a Rust `impl` block emits a window chunk alongside its nested `fn` (double-embedded body), and a JS/TS/Java class yields a header chunk leaving the closing brace uncovered. Do not quote "20+ languages": the three sets above partition the surface exactly, asserted in both directions.
|===

== Not Supported in v0.2

The v0.2 release ships **single-node**, **CRUD-only** writes, and **per-request** freshness/route
controls. The items below are out of scope for v0.2; do not document, demo, or release-note them as
supported. The live source of truth for write contract is the
`WriteContractHealth` block in route-health (`src/network/rest/v2/collections.rs:869-880`,
GET `/api/v2/_diagnostics/collections/{collection_id}/route-health`):

|===
| Surface | Status in v0.2 | Live signal

| Optimistic versioning (compare-and-set on insert/upsert)
| Not supported
| No `version` / `if_match` / `if_none_match` field on `InsertRecordsRequest` or
  `UpsertRecordsRequest`. `WriteContractHealth.conditional_write = false`.

| Conditional writes (predicate-gated insert/upsert/delete)
| Not supported
| `WriteContractHealth.conditional_write = false`.

| Update-by-filter / delete-by-filter
| Not supported
| `WriteContractHealth.filter_write = false`. Delete is single-record / batch-of-ids only.

| Patch / partial-record update
| Not supported
| `WriteContractHealth.patch = false`. Full-record upsert is the only mutation shape.

| Collection-default freshness mode
| Not supported (per-request only)
| `FreshnessHealth.collection_level_modes_wired = false`
  (`src/network/rest/v2/collections.rs:1114-1126`). Per-request `freshness_mode`
  (`Strong`/`BoundedStale{max_staleness_ms}`/`StaleOk`) is honored;
  collection-default is not catalog-persisted in v0.2. See TD-074.

| Filtered ANN per-collection policy
| Not supported (default policy only)
| `AnnFilteringPolicy` runs from the default in v0.2; per-collection catalog
  policy plumbing tracked in TD-073. A deterministic recall-band harness exists
  at `tests/filtered_ann_recall_bands.rs`, but it is intentionally ignored
  while ADR-011 remains Beta; no recall SLA is claimed.

| `RecallProbeGate` enforced route selection
| Not supported (diagnostic only)
| Gate state is readable via route-health and EXPLAIN; route selection in
  `AxisManager` does not consult the gate. Quantized-route enforcement
  tracked in TD-075.
|===

If a release note or SDK doc implies any of the above works, file a doc fix before the cut.

== Experimental in v0.2 (do not market as implemented)

These surfaces have code foundations but are not part of the v0.2 product story. Release collateral
must not list them under "supported", "production", or "ready":

* Distributed cluster execution (Raft transport / remote execution placeholders).
* PULSAR and QUASAR graph engines (retired; use ORION).
* Full SQL parity (ADR-018 Phase 2/3 — Postgres parity).
* PostgreSQL-style OLTP/HTAP parity: full MVCC transactions, FK/PK/unique/check enforcement,
  native row/delta indexes, DataFusion snapshot-plus-delta reads, and distributed consistency gates
  are tracked in TD-110 and are not part of v0.2.
* External-table execution (Iceberg / Delta / Hudi as Proxima-owned hot authority).
* Iceberg v3 interop _write/export_ — `ALTER TABLE … MATERIALIZE` over pgwire emits a
  spec-shaped Iceberg v3 table (`v*.metadata.json` referencing an Avro manifest list + manifest)
  to the warehouse so external Iceberg engines can read it (verified by `tests/iceberg_interop_e2e.rs`).
  One-way publish only; this is distinct from the hot-authority item above (still experimental), and
  external read-back plus multi-writer coordination are unverified.
* Columnar vector quantization (RaBitQ / SQ8) in PAX vector segments — _flag-gated, default OFF_.
  Enabled with `PROXIMADB_PAX_VECTOR_SEGMENTS=1` plus `PROXIMADB_PAX_VECTOR_QUANT=rabitq|sq8|auto`
  (deployment-level env selector; per-collection proto config is the productionization follow-up).
  Reads are mixed-format-safe — existing ProximaBlocks segments still read back when the flag is on.
  Codecs/kernels are tested; no per-collection policy or recall SLA is claimed.
* Arrow Flight / gRPC service multiplexing as a customer-facing transport.
* Trino / Spark compute adapters — _scaffolded_ (Spark JNI bridge per TD-097; Trino Flight per TD-098). Structural contract gates land in 2026-05-30 connector sprint (`tests/connectors_flight_contract.rs`); end-to-end wire impl deferred.
* Hadoop InputFormat / OutputFormat — _write-side wire-true_ (`ProximaRecordWriter::flush_now` posts spec-true `/api/v2/.../records/batch`); read-side unblocked: the records-scan endpoint pages by cursor (TD-099; the cursor-identity 400 fixed 2026-08).
* DuckDB connector — _Rust-side wire-true for bind / search / insert_ (`src/connectors/duckdb.rs`); DuckDB extension binary compilation + scan-via-Flight are separate follow-ups.
* All "Not Supported in v0.2" items above.

== Positioning Guidance

ProximaDB should currently be positioned as a developer-first context database:

* MVP wedge: object-storage-native context serving for typed JSON properties and vector retrieval.
* One canonical REST v2 record path with SST as the safe single-node default.
* Best fit today for metadata-aware semantic retrieval without a separate vector/payload join.
* Not yet a like-for-like replacement for best-in-class distributed vector, graph, document, or observability platforms.

== Near-Term Exit Criteria

The next maturity step is to move from "broad but uneven" to "narrow but reliable":

* One canonical execution path for vector, hybrid, graph, document, and observability queries.
* Canonical `ProximaRecord`/xCatalog/WAL authority is default for document, graph, and observability writes; modality engines are cataloged projections.
* No roadmap or README claims that exceed the supported surface defined here.
* Distributed claims backed by real transport and failover verification.
