= AXIS Indexing EventLog
:toc:
:toclevels: 3

== Overview

The AXIS EventLog subsystem coordinates **asynchronous indexing** after storage engine flushes and compactions. It ensures that AXIS indexes are built for newly flushed files before those files can be compacted or deleted.

== Purpose

*Primary Goal*: Coordinate storage operations (flush/compact) with async AXIS indexing to prevent data loss.

=== Problem Solved

When a storage engine flushes vectors to disk:

1. Storage writes vectors to Parquet/SSTable files
2. AXIS indexes need to be built for fast search
3. Building indexes takes time (seconds to minutes for large batches)
4. Storage might compact/delete files before indexing completes → **data loss**

The EventLog prevents this by:

* Recording all flush/compaction events persistently
* Tracking which files have pending index builds
* Blocking compaction until all indexes are ready

=== Key Components

==== 1. IndexEvent (event_log.rs)

Represents a single flush/compaction event:

[source,rust]
----
pub struct IndexEvent {
    pub event_id: String,           // Unique ID
    pub collection_id: String,       // Which collection
    pub file_paths: Vec<String>,     // Files to index
    pub vector_count: usize,         // # vectors
    pub storage_engine: StorageEngineType,  // SST, VIPER, etc.
    pub has_quantized: bool,         // Contains quantized vectors?
    pub has_fp32: bool,              // Contains FP32 vectors?
    pub timestamp: u64,              // When created
    pub operation_type: OperationType, // Flush or Compaction
}
----

==== 2. EventLogService Trait

Defines the contract for event log implementations:

[source,rust]
----
#[async_trait]
pub trait EventLogService: Send + Sync {
    /// Add new flush/compaction event
    async fn add_event(&self, event: IndexEvent) -> Result<()>;

    /// Check if file can be compacted (all indexes built)
    async fn can_compact(&self, collection_id: &str, file: &str) -> bool;

    /// Mark event as processed (indexes complete)
    async fn mark_processed(&self, event_id: &str) -> Result<()>;

    /// Get pending events for AXIS indexing
    async fn get_pending_events(&self, limit: usize) -> Vec<IndexEvent>;
}
----

==== 3. EventLogServiceAdapter (event_log.rs)

Production implementation using filesystem persistence:

* Stores events in `<base_url>/eventlog/<collection_id>/events/`
* Uses atomic file operations for cloud storage compatibility
* Recovers on restart by scanning event directories

==== 4. EventLogServiceFactory

Creates EventLog instances based on deployment mode:

[source,rust]
----
pub enum ServiceMode {
    Embedded,       // Single-node deployment
    Distributed,    // Multi-node with shared storage
}
----

== Integration Points

=== 1. Storage Engines → EventLog

**When**: After flush/compaction completes
**Who**: All storage engines (SST, VIPER, NOVA, SWIFT, RAPTOR, HELIX)
**How**: Via `src/services/events/log.rs` wrapper

[source,rust]
----
// In storage engine flush
let event_log = event_log_service();  // Get global instance
event_log.notify_flush(
    collection_id,
    flushed_files,
    vector_count,
    has_quantized,
    has_fp32,
    StorageEngineType::VIPER,
).await?;  // Blocks until event persisted
----

=== 2. AXIS Indexers ← EventLog

**When**: Continuous background processing
**Who**: AXIS indexing workers (via `integration/eventlog_consumer.rs`)
**How**: Poll for pending events and build indexes

[source,rust]
----
// AXIS indexer worker loop
loop {
    let events = event_log.get_pending_events(10).await;
    for event in events {
        // Build HNSW/IVF/PQ indexes for event.file_paths
        axis_indexer.build_indexes(&event).await?;

        // Mark complete
        event_log.mark_processed(&event.event_id).await?;
    }
    sleep(Duration::from_secs(1)).await;
}
----

=== 3. Storage Compaction ← EventLog

**When**: Before compacting files
**Who**: Storage engine compaction threads
**How**: Check if all indexes are ready

[source,rust]
----
// Before compaction
let can_compact = event_log.can_compact(collection_id, &file_path).await;
if !can_compact {
    info!("Skipping compaction - AXIS indexes pending");
    return Ok(());
}

// Safe to compact
compact_files(&files).await?;
----

== Relationship with `src/services/events/`

The `src/services/events/log.rs` module is a **thin service wrapper** around this EventLog:

=== Purpose of Service Wrapper

1. **Lifecycle Management**: Initialized at server startup like other services
2. **Dependency Injection**: Shares collection cache and filesystem factory
3. **Clean API**: Provides ergonomic methods for storage engines
4. **Global Access**: Singleton pattern via `event_log_service()` function

== Persistence Strategy

=== Filesystem Layout

[source]
----
<base_storage_url>/eventlog/
├── <collection_id_1>/
│   ├── events/
│   │   ├── <event_id_1>.json
│   │   ├── <event_id_2>.json
│   │   └── ...
│   └── processed/
│       ├── <event_id_3>.json  # Moved after indexing
│       └── ...
├── <collection_id_2>/
│   └── ...
└── metadata/
    └── last_cleanup.json
----

=== Atomic Operations

1. **Add Event**: Write to temporary file, then rename (atomic on most filesystems)
2. **Mark Processed**: Move from `events/` to `processed/` directory
3. **Cleanup**: Periodic deletion of old processed events (>7 days)

=== Cloud Storage Compatibility

* Uses list operations for recovery (no local state required)
* Atomic renames work on S3/GCS/Azure via eventual consistency
* No distributed locks needed (events are immutable once written)

== Performance Characteristics

* **Add Event**: ~5-20ms (single file write)
* **Can Compact Check**: ~1-5ms (directory scan + in-memory cache)
* **Get Pending Events**: ~10-50ms (directory list + deserialize)
* **Recovery Scan**: ~100ms per 1000 events

== Configuration

[source,toml]
----
[index.axis.eventlog]

== Future Enhancements

=== Planned Features

1. **Distributed Mode**: Use etcd/consul for coordination in multi-node deployments
2. **Priority Queue**: High-priority collections get indexed first
3. **Batch Indexing**: Group multiple events for efficiency
4. **Metrics**: Track event throughput, lag, and processing time
5. **Dead Letter Queue**: Handle failed index builds

=== Migration Path

Current filesystem-based approach is designed for easy migration:

* All interfaces are trait-based
* Factory pattern allows swapping implementations
* Event format is serialization-agnostic (currently JSON, could use Protobuf)
