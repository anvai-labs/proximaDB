= AXIS - Adaptive eXtensible Indexing System
:toc: left
:toclevels: 3
:icons: font

[abstract]
AXIS is ProximaDB's intelligent indexing layer providing high-performance vector similarity search through multiple adaptive indexing algorithms. It automatically selects optimal indexes based on data characteristics and query patterns, with zero-downtime migration as workloads evolve.

== Overview

AXIS (Adaptive eXtensible Indexing System) serves as ProximaDB's primary indexing layer for vector similarity search. Unlike traditional static indexing systems, AXIS dynamically adapts to your data and query patterns, automatically selecting and migrating between indexing strategies to maintain optimal performance.

**Key Features**:

* Six specialized indexing algorithms (HNSW, IVF, LSH, Annoy, PQ, Flat)
* Automatic index selection based on collection characteristics
* Zero-downtime migration between index types
* Query pattern analysis and optimization
* Event-driven updates via EventLog integration
* Seamless integration with all storage engines
* Hardware-accelerated distance computation

**Status**: ✅ PRODUCTION-READY

=== 1. HNSW (Hierarchical Navigable Small World)

**Description**: Graph-based indexing using hierarchical layers for navigable small-world graphs.

**When to Use**:

* High recall requirements (95%+)
* Real-time search applications
* Collections with 10K-10M vectors
* Low-latency requirements (< 10ms)

**Configuration**:

[source,rust]
----
IndexAlgorithm::HNSW {
    m: 16,                    // Bi-directional links (typical: 12-48)
    ef_construction: 200,     // Build quality (higher = better)
    ef_search: 50,            // Search quality (higher = better)
    max_elements: 1000000,    // Maximum vectors
}
----

**Performance Characteristics**:

* Build: O(n log n)
* Search: O(log n)
* Memory: ~200-300 bytes per vector
* Recall: 95-99% at ef_search=100

**Pros**:

* Excellent recall with low latency
* Good for dynamic updates
* Predictable performance
* Well-suited for real-time systems

**Cons**:

* High memory usage
* Parameter tuning required
* Not ideal for very large datasets (>100M)

=== 2. IVF (Inverted File Index)

**Description**: Clustering-based indexing that groups similar vectors into partitions.

**When to Use**:

* Large-scale datasets (10M-1B vectors)
* Batch query workloads
* Memory-efficient search
* Acceptable recall tradeoff (85-95%)

**Configuration**:

[source,rust]
----
IndexAlgorithm::IVF {
    nlist: 1000,              // Number of clusters (sqrt(n) typical)
    nprobe: 10,               // Clusters to search (higher = better recall)
    quantizer: None,          // Optional PQ compression
}
----

**Performance Characteristics**:

* Build: O(n * k * iterations) - requires training
* Search: O(nprobe * (n/nlist))
* Memory: ~50-100 bytes per vector + centroids
* Recall: 85-95% at nprobe=10

**Pros**:

* Scales to billions of vectors
* Memory-efficient
* Good balance of speed and recall
* Can combine with PQ for compression

**Cons**:

* Requires training phase
* Recall depends on clustering quality
* Not ideal for frequently changing data
* Static nlist parameter

=== 3. LSH (Locality Sensitive Hashing)

**Description**: Hash-based approximate search using random projections.

**When to Use**:

* Approximate search acceptable
* Very large datasets (100M+ vectors)
* Low memory budgets
* High throughput requirements

**Configuration**:

[source,rust]
----
IndexAlgorithm::LSH {
    n_projections: 10,        // Hash functions per table
    n_hash_tables: 5,         // Independent hash tables
    hash_width: 4.0,          // Bucket width
}
----

**Performance Characteristics**:

* Build: O(n * L * k) - L tables, k hashes
* Search: O(L * bucket_size)
* Memory: ~20-50 bytes per vector
* Recall: 70-85% (tunable)

**Pros**:

* Very low memory usage
* Fast build and search
* No training required
* Simple to implement and tune

**Cons**:

* Lower recall than graph methods
* Parameter tuning affects quality
* Hash collision tradeoffs
* Not suitable for high-precision search

=== 4. Annoy (Approximate Nearest Neighbors Oh Yeah)

**Description**: Tree-based indexing using random projection trees.

**When to Use**:

* Static or infrequently updated datasets
* Read-heavy workloads
* Disk-based indexing
* Predictable memory usage

**Configuration**:

[source,rust]
----
IndexAlgorithm::Annoy {
    n_trees: 10,              // Number of trees (more = better recall)
    search_k: -1,             // Nodes to inspect (-1 = auto)
    max_leaf_size: 8,         // Vectors per leaf
}
----

**Performance Characteristics**:

* Build: O(n log n * n_trees)
* Search: O(log n * n_trees)
* Memory: ~100-150 bytes per vector
* Recall: 80-90% at n_trees=10

**Pros**:

* Good for static datasets
* Memory-mappable (disk-friendly)
* Simple tree structure
* Predictable performance

**Cons**:

* Not optimized for updates
* Requires rebuild for major changes
* Recall lower than HNSW
* More memory than LSH

=== 5. PQ (Product Quantization)

**Description**: Vector compression through subspace quantization.

**When to Use**:

* Memory-constrained environments
* Large vectors (1536D+)
* Acceptable recall loss
* Batch processing workflows

**Configuration**:

[source,rust]
----
IndexAlgorithm::PQ {
    m: 8,                     // Number of subquantizers
    nbits: 8,                 // Bits per subquantizer (256 centroids)
    train_size: 10000,        // Training vectors
}
----

**Performance Characteristics**:

* Build: O(train_size * m * 2^nbits * iterations)
* Search: O(n) - but with compressed vectors
* Memory: m bytes per vector (typically 8-16)
* Recall: 75-90% (depends on m and nbits)

**Pros**:

* Extreme memory compression (10-100x)
* Fast distance computation with lookup tables
* Scalable to billions of vectors
* Can combine with IVF

**Cons**:

* Requires significant training data
* Recall loss from quantization
* Not suitable for low-dimensional data
* Complex parameter tuning

=== 6. Flat (Brute Force)

**Description**: Exact search through exhaustive comparison.

**When to Use**:

* Small datasets (< 10K vectors)
* 100% recall required
* Benchmarking and validation
* Simple baseline

**Configuration**:

[source,rust]
----
// Flat index has no configuration - always exact
----

**Performance Characteristics**:

* Build: O(1) - just store vectors
* Search: O(n * d) - check all vectors
* Memory: ~4 * dimension bytes per vector
* Recall: 100% (exact)

**Pros**:

* Perfect recall
* No training required
* Simple implementation
* Good for small datasets

**Cons**:

* Does not scale
* Slow for large datasets
* No optimization opportunities

=== Selection Criteria

**Collection Size**:

* **< 10K vectors**: Flat (exact search is fast enough)
* **10K-1M vectors**: HNSW (optimal for medium scale)
* **1M-100M vectors**: IVF or HNSW with partitioning
* **> 100M vectors**: IVF + PQ or distributed HNSW

**Dimensionality**:

* **< 128D**: HNSW or IVF (lower memory overhead)
* **128D-768D**: HNSW, IVF, or Annoy
* **> 768D**: IVF + PQ (compression beneficial)

**Query Patterns**:

* **High recall (95%+)**: HNSW or IVF with high nprobe
* **Balanced (85-95%)**: IVF with moderate nprobe
* **Fast approximate (70-85%)**: LSH or Annoy
* **Filtered queries**: IVF + metadata indexes

**Memory Budget**:

* **Unlimited**: HNSW (best quality)
* **Limited**: IVF or Annoy
* **Very Limited**: LSH or PQ
* **Disk-based**: Annoy (memory-mappable)

**Update Frequency**:

* **Static**: Annoy (optimized for reads)
* **Occasional updates**: HNSW (handles updates)
* **Frequent updates**: IVF with incremental rebuild
* **Real-time streams**: HNSW with background optimization

== Zero-Downtime Migration

AXIS enables seamless migration between index types as your data and query patterns evolve:

[source,mermaid]
----
%%{init: {"theme": "neutral"}}%%
sequenceDiagram
    participant Monitor as AXIS Monitor
    participant Engine as Migration Engine
    participant Old as Old Index
    participant New as New Index
    participant Query as Query Router

    Note over Monitor: Detects degraded performance
    Monitor->>Engine: Trigger migration evaluation
    Engine->>Engine: Analyze current vs optimal
    Engine->>New: Build new index in background
    Note over New: Index build (non-blocking)
    New-->>Engine: Build complete
    Engine->>Engine: Validation phase
    Engine->>Query: Shift 10% traffic to new index
    Query->>New: Test queries
    New-->>Query: Results
    Query-->>Engine: Performance metrics
    Engine->>Query: Shift 50% traffic
    Query->>Old: 50% queries
    Query->>New: 50% queries
    Engine->>Query: Shift 100% traffic
    Note over Old: No longer serving queries
    Engine->>Old: Cleanup old index
    Old-->>Engine: Cleanup complete
----

=== Migration Workflow

**1. Detection Phase**:

* Monitor tracks query performance metrics
* Detects degradation or suboptimal patterns
* Analyzes collection growth and changes

**2. Planning Phase**:

* Evaluate current index performance
* Recommend optimal index type
* Estimate migration duration and resources
* Create rollback plan

**3. Build Phase**:

* Construct new index in background
* Parallel build using available CPU cores
* No impact on existing queries
* Progress tracking

**4. Validation Phase**:

* Verify index consistency
* Sample query testing
* Performance validation
* Quality checks

**5. Traffic Shifting**:

* Gradually shift query traffic (10% → 50% → 100%)
* Monitor performance at each stage
* Automatic rollback on degradation
* Minimal user impact

**6. Cleanup Phase**:

* Remove old index after stability period
* Free resources
* Update monitoring baselines

=== Migration Example

[source,rust]
----
use proximadb::index::axis::{AxisManager, MigrationEngine};

// AXIS detects collection growth
let collection_stats = axis_manager.analyze_collection("my_collection").await?;

// Recommend migration from HNSW to IVF
if collection_stats.total_vectors > 5_000_000 {
    let migration_plan = MigrationEngine::create_plan(
        "my_collection",
        current_strategy,
        recommended_strategy
    ).await?;

    // Execute migration with automatic rollback
    migration_engine.execute_plan(
        migration_plan,
        MigrationConfig {
            max_duration: Duration::from_hours(2),
            traffic_shift_steps: vec![0.1, 0.5, 1.0],
            auto_rollback: true,
            ..Default::default()
        }
    ).await?;
}
----

=== EventLog Integration

AXIS consumes events from ProximaDB's global EventLog for real-time index updates:

[source,rust]
----
use proximadb::index::axis::integration::EventLogConsumer;

// Create EventLog consumer
let consumer = EventLogConsumer::new(
    collection_id,
    event_log_service,
    ConsumerConfig {
        batch_size: 1000,
        flush_interval: Duration::from_secs(5),
        ..Default::default()
    }
).await?;

// Start consuming events
consumer.start().await?;

// Events automatically update indexes:
// - VectorInserted -> add to index
// - VectorUpdated -> update in index
// - VectorDeleted -> remove from index
// - CollectionFlushed -> rebuild if needed
----

=== WAL Flush Coordination

AXIS coordinates with the global WAL system for consistent index updates:

[source,rust]
----
use proximadb::index::axis::integration::FlushIntegration;

// Coordinate flush with WAL
let flush_integration = FlushIntegration::new(
    collection_id,
    wal_manifest,
    FlushConfig {
        enable_background_rebuild: true,
        rebuild_threshold: 0.3, // Rebuild when 30% changed
        ..Default::default()
    }
);

// On WAL flush, update indexes
wal_manifest.on_flush(|flushed_records| {
    flush_integration.update_indexes(flushed_records).await?;
}).await?;
----

== Troubleshooting

=== Common Issues

**Issue**: Poor search recall

**Solutions**:

1. Increase index quality parameters:
   * HNSW: Increase `ef_search` (e.g., 50 → 100)
   * IVF: Increase `nprobe` (e.g., 10 → 20)
   * LSH: Add more hash tables
   * Annoy: Increase `n_trees`

2. Check index training:
   * IVF: Ensure sufficient training data (10K+ vectors)
   * PQ: Use representative training sample

3. Verify distance metric matches use case

**Issue**: High query latency

**Solutions**:

1. Reduce search scope:
   * HNSW: Decrease `ef_search`
   * IVF: Decrease `nprobe`
   * Use metadata filtering to prune candidates

2. Consider index migration:
   * HNSW → IVF (if recall can be reduced)
   * IVF → LSH (for approximate results)

3. Enable caching and prefetching

4. Check hardware acceleration (SIMD, GPU)

**Issue**: High memory usage

**Solutions**:

1. Enable compression:
   * Add PQ quantization to IVF
   * Use INT8 quantization
   * Enable memory tiering

2. Reduce index parameters:
   * HNSW: Decrease `m` (e.g., 16 → 12)
   * IVF: Decrease `nlist`

3. Consider memory-efficient alternatives:
   * HNSW → IVF
   * IVF → LSH
   * Add PQ compression

**Issue**: Slow index builds

**Solutions**:

1. Increase parallel build threads
2. Reduce training iterations (IVF, PQ)
3. Use fast approximation mode
4. Build incrementally with smaller batches
