= SST Storage Engine
:toc: left
:toclevels: 2
:icons: font

[abstract]
Hybrid columnar storage engine with write optimization and three-stage filtering architecture for real-time queries and frequent updates.

== Overview

The SST (Sorted String Table) engine is ProximaDB's hybrid columnar storage engine optimized for write-heavy workloads with real-time query requirements. It uses ProximaBlocks format where all fields are stored columnar (id, timestamp, version, metadata, vectors).

**Metadata Storage**: Type-safe columnar storage with compression markers
* Filterable metadata stored as typed columns (String, Int64, Float, Boolean)
* Collection config (filterable_columns) defines types at flush time
* Compression algorithm markers enable independent column decompression
* Uses ProximaDB standard compression markers (consistent with ProximaCodec)

**Vector Encoding**: Configurable strategies (TransposeFieldEncoded, GroupedFieldEncoded, or FullVector) with automatic SIMD optimization.

**Key Features**:

* Write-optimized with minimal flush overhead
* Three-stage filtering: Metadata → Bloom → Vector
* Hybrid columnar storage with ProximaBlocks format
* Real-time insertion without blocking
* Automatic compaction and optimization

== Three-Stage Filtering

The SST engine uses a three-stage filter to minimize I/O:

=== Stage 1: Metadata Filter (Type-Safe)

**Purpose**: Fast elimination using type-safe FilterExpression evaluation

**Supported Data Types**:
* String (StringValue)
* Integer (Int64Value)
* Float (NumberValue)
* Boolean (BoolValue)
* DateTime (Int64Value timestamp)

**Supported Operators**:
* Comparison: =, !=, <, <=, >, >=
* Logical: AND, OR, NOT
* Complex nested expressions

**Type Resolution**:
* Uses Collection.config.filterable_columns as source of truth
* Eliminates type ambiguity (Int64 vs Float64)
* Collection config passed through StorageQueryContext

**Performance**: O(1) per record, evaluated using sql_value_filter::evaluate_filter

=== Stage 2: Bloom Filter

**Purpose**: Probabilistic filter to avoid disk reads

**Characteristics**:
* False positive rate: 1%
* Per-SST-file bloom filters
* Fast membership testing

**Performance**: O(1) lookup, ~100 ns per test

=== Stage 3: Vector Scan

**Purpose**: Actual vector distance computation

**Only Executes If**:
* Metadata filter passes
* Bloom filter returns "possibly present"

**Performance**: O(n*d) where n=vectors, d=dimensions

== Write Path

=== Memory Buffer

New insertions go to in-memory buffer:

[source,rust]
----
pub struct SstEngine {
    memory_buffer: Arc<RwLock<Vec<VectorRecord>>>,
    wal: WriteAheadLog,
    flush_threshold: usize,  // Default: 10,000 vectors
}
----

=== Flush Trigger

Flush occurs when:

* Memory buffer reaches threshold (10K vectors)
* Manual flush requested
* Shutdown/checkpoint

=== Flush Process

[source,rust]
----
async fn flush(&self) -> Result<()> {
    // 1. Acquire write lock
    let records = self.memory_buffer.write().await;

    // 2. Sort by vector ID (for efficient lookup)
    records.sort_by_key(|r| &r.id);

    // 3. Write SST file
    let sst_file = self.write_sst_file(&records).await?;

    // 4. Build bloom filter
    let bloom = self.build_bloom_filter(&records).await?;

    // 5. Update metadata index
    self.update_metadata_index(&records).await?;

    // 6. Clear memory buffer
    records.clear();

    Ok(())
}
----

== Search Algorithm

[source,rust]
----
async fn search(&self, request: SearchRequest) -> Result<SearchResponse> {
    let mut candidates = Vec::new();

    // Stage 1: Metadata filtering
    let sst_files = self.filter_by_metadata(&request)?;

    for sst_file in sst_files {
        // Stage 2: Bloom filter check
        if !self.bloom_filter_check(&sst_file, &request)? {
            continue;  // Skip this SST file
        }

        // Stage 3: Load and scan vectors
        let vectors = self.load_vectors(&sst_file).await?;
        let results = self.compute_distances(&vectors, &request)?;
        candidates.extend(results);
    }

    // Merge and return top-k
    candidates.sort_by(|a, b| a.distance.partial_cmp(&b.distance).unwrap_or(std::cmp::Ordering::Equal));
    Ok(SearchResponse {
        results: candidates.into_iter().take(request.top_k).collect(),
    })
}
----

|===
| Stage | Time | Reduction

| Metadata Filter
| 1-10 μs
| 90% files eliminated

| Bloom Filter
| 100 ns × N files
| 99% false positives eliminated

| Vector Scan
| 1-10 ms

**Total Search**: 5-50 ms for typical queries (1M vectors, 768D)

== Best Practices

=== When to Use SST Engine

✅ **Good For**:

* Real-time insertions
* Frequent updates
* Point queries (lookup by ID)
* Mixed read/write workloads
* Small to medium datasets (<10M vectors)

❌ **Not Ideal For**:

* Pure analytical workloads (use VIPER)
* Very large batch inserts (use NOVA)
* Sparse vectors (use specialized sparse engine)

=== Optimization Tips

**Write Optimization**:

[source,rust]
----
// Batch insertions for better throughput
let records: Vec<VectorRecord> = /* ... */;
engine.insert_batch(records).await?;  // Better than N inserts
----

**Search Optimization**:

[source,rust]
----
// Use metadata filters to reduce search space
let request = SearchRequest {
    filters: vec![
        MetadataFilter::key_equals("category", "product"),
        MetadataFilter::timestamp_range(start, end),
    ],
    top_k: 10,
    ..Default::default()
};
----

== Compaction

SST files are automatically compacted to maintain performance:

=== Compaction Trigger

* Number of SST files > threshold (default: 10)
* Periodic timer (default: 1 hour)
* Manual compaction request

=== Compaction Process

[source,rust]
----
async fn compact(&self) -> Result<()> {
    // 1. Identify candidate files
    let files = self.select_compaction_candidates()?;

    // 2. Merge files
    let merged_records = self.merge_sst_files(&files).await?;

    // 3. Write new SST file
    let new_file = self.write_sst_file(&merged_records).await?;

    // 4. Update bloom filters
    self.rebuild_bloom_filter(&new_file).await?;

    // 5. Delete old files
    self.delete_old_files(&files).await?;

    Ok(())
}
----

== Troubleshooting

=== Write Latency Spikes

**Symptom**: Periodic slow writes every 10K insertions

**Cause**: Flush operation blocks writes

**Solution**:
[source,toml]
----
[storage.engines.sst]
flush_threshold = 20000  # Increase threshold
----

=== Search Performance Degradation

**Symptom**: Search getting slower over time

**Cause**: Too many SST files, compaction needed

**Solution**:
[source,rust]
----
// Manual compaction
engine.compact().await?;

// Or adjust auto-compaction
[storage.engines.sst]
compaction_threshold = 5  # More frequent compaction
----

=== Bloom Filter False Positives

**Symptom**: Unnecessary disk reads

**Solution**:
[source,toml]
----
[storage.engines.sst]
bloom_filter_fp_rate = 0.001  # Lower false positive rate (larger bloom filter)
----
