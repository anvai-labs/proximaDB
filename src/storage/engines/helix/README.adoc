= HELIX Storage Engine
:toc: left
:toclevels: 3
:icons: font

[abstract]
High-Efficiency Locality-Indexed eXecution (HELIX) - Production-ready locality-optimized storage engine leveraging Hilbert space-filling curves for 90%+ query pruning through spatial clustering.

== Overview

The HELIX engine is ProximaDB's sophisticated locality-optimized storage engine that uses space-filling curves (Hilbert curves) combined with PCA dimensionality reduction to physically co-locate similar vectors on disk, enabling dramatic improvements in range query performance and spatial locality.

**Key Features**:

* Hilbert curve spatial locality preservation
* PCA dimensionality reduction for clustering optimization
* 90%+ query pruning through spatial range filtering
* Liquid clustering with query pattern adaptation
* Disk-only LSM architecture with no memtable/WAL overhead
* SIMD-optimized Proxima columnar blocks
* Zone maps for fine-grained dimension-level pruning

**Status**: ✅ PRODUCTION-READY

== Core Design Principles

=== Hilbert Curve Spatial Locality

**Purpose**: Preserve multi-dimensional similarity in 1D storage layout

The Hilbert curve is a continuous fractal space-filling curve that maps n-dimensional points to a 1D sequence while preserving locality. Points that are close in n-dimensional space remain close on the curve.

**How it works**:

1. **Dimensionality Reduction**: PCA projects high-dimensional vectors (768D, 1536D) to lower dimensions (16D-64D)
2. **Quantization**: Continuous coordinates are discretized into integer bins
3. **Hilbert Encoding**: Multi-dimensional coordinates are mapped to a single 64-bit integer
4. **Sorting**: Vectors are sorted by Hilbert key before storage

**Benefits**:

* Similar vectors cluster together on disk
* Range queries become efficient sequential scans
* 90%+ of irrelevant data can be skipped using range pruning
* Cache-friendly access patterns

**Implementation**: `hilbert_curve.rs` - Supports 2D, 3D, and arbitrary n-dimensional encoding

=== PCA Dimensionality Reduction

**Purpose**: Reduce dimensionality for efficient Hilbert mapping

PCA (Principal Component Analysis) projects high-dimensional vectors to a lower-dimensional space while preserving maximum variance. This makes Hilbert curve encoding practical for high-dimensional data.

**Configuration**:

* Default: 16 dimensions (configurable via `pca_dimensions`)
* Trained on first 1000+ vectors or sampled from larger batches
* Model persisted and reused across flushes
* Periodic retraining based on data distribution

**Implementation**: `pca_impl.rs` (eigendecomposition-based) and `pca_manager.rs` (lifecycle management)

=== LSM-Tree with Spatial Awareness

**Architecture**: Leveled compaction with Hilbert-ordered merging

Unlike traditional LSM-trees, HELIX maintains spatial locality during compaction:

* **L0 Files**: Newly flushed data, sorted by Hilbert key
* **L1+ Files**: Progressively compacted, maintaining Hilbert order
* **Compaction**: Merges overlapping Hilbert ranges across levels
* **Splitting**: Large files are split at Hilbert boundaries for balance

**Advantages**:

* No memtable/WAL overhead (uses global infrastructure)
* Spatial locality preserved across levels
* Efficient range queries at any level
* Background compaction doesn't disrupt queries

**Implementation**: `compaction.rs` - LeveledCompactor with Hilbert-aware merging

=== Liquid Clustering

**Purpose**: Adapt data layout based on query patterns

Liquid clustering monitors query access patterns and reorganizes data to optimize for frequently accessed regions. This creates "hot zones" that are physically co-located for faster access.

**Features**:

* Query pattern tracking with access frequency
* Hot region identification (most frequently queried areas)
* Adaptive re-clustering during compaction
* Configurable sensitivity and update frequency

**Use Cases**:

* Recommendation systems with popularity biases
* Content libraries with trending items
* Geospatial data with regional hotspots
* Time-series data with recent query focus

**Implementation**: `liquid_clustering.rs` - Query pattern-based adaptive reorganization

=== Zone Maps for Pruning

**Purpose**: Fine-grained dimension-level filtering

Zone maps track min/max values per dimension for each data block, enabling early pruning during query execution.

**Structure**:

* Min/max values per dimension
* Mean, standard deviation statistics
* Bloom filter for vector IDs
* Cardinality estimates

**Query Flow**:

1. **Hilbert Range Pruning**: Skip 90%+ of files using spatial ranges
2. **Zone Map Filtering**: Skip blocks within files using dimension ranges
3. **Metadata Filtering**: Type-safe FilterExpression evaluation on typed metadata (String, Int64, Float, Boolean)
4. **Bloom Filter**: Quick ID existence checks
5. **Final Scan**: SIMD-optimized vector comparison

**Metadata Filtering** (NEW):
* Uses FilterExpression with sql_value_filter::evaluate_filter
* Collection config (filterable_columns) provides type information
* ProximaBlock format with compression markers
* Supports all comparison and logical operators

**Implementation**: `zone_maps.rs` - Dimension statistics and pruning

== When to Avoid HELIX

**Not Recommended For**:

* **Random Access Patterns**: HELIX optimizes for spatial locality. Random point lookups should use SST or SWIFT.
* **Heavy Write Workloads**: PCA computation adds overhead to flushes. VIPER or SST handle writes better.
* **Small Collections**: Overhead not justified for <10K vectors. Use SST for small datasets.
* **Frequent Schema Changes**: PCA model becomes outdated when data distribution changes dramatically.
* **Uniform Query Distribution**: If all regions are queried equally, liquid clustering provides no benefit.

**Alternative Engines**:

* **SST**: Random access, write-heavy workloads
* **SWIFT**: Hierarchical organization, multi-tenant
* **VIPER**: Analytics, batch operations
* **RAPTOR**: Dynamic adaptive access patterns

**Pruning Logic**:

[source,rust]
----
pub fn can_prune(&self, query: &[f32], threshold: f32) -> bool {
    // Calculate minimum possible distance to any vector in block
    let mut min_distance_sq = 0.0;

    for (i, &q) in query.iter().enumerate() {
        if q < self.dim_min[i] {
            let diff = self.dim_min[i] - q;
            min_distance_sq += diff * diff;
        } else if q > self.dim_max[i] {
            let diff = q - self.dim_max[i];
            min_distance_sq += diff * diff;
        }
    }

    // Prune if minimum possible distance exceeds threshold
    min_distance_sq.sqrt() > threshold
}
----

=== Performance Tuning

**PCA Dimensions**:

* Fewer dimensions (8-16): Faster, less accurate clustering
* More dimensions (32-64): Slower, better clustering
* Typical: 16 (good balance)

**Hilbert Bits Per Dimension**:

* Lower (8-12): Coarser clustering, faster encoding
* Higher (16-21): Finer clustering, slower encoding
* Typical: 16 (65,536 bins per dimension)

**Proxima Block Size**:

* Smaller (64-128): Better pruning, more metadata
* Larger (256-512): Less metadata, slower scans
* Typical: 128 vectors per block

== Troubleshooting

=== Common Issues

**Issue**: Poor query performance despite spatial data

**Solution**:

1. Check PCA dimensions: `pca_dimensions` should be 16-64
2. Verify Hilbert bits: `hilbert_bits_per_dimension` should be 16-21
3. Enable liquid clustering if query patterns are concentrated
4. Increase cache size: `block_cache_size_mb`
5. Check pruning ratio in metrics (should be >80%)

**Issue**: Slow flush operations

**Solution**:

1. Reduce PCA training frequency: Increase `pca_skip_threshold`
2. Use fast approximation: Set `use_fast_approximation = true`
3. Reduce training samples: Lower `pca_min_training_vectors`
4. Skip PCA for small batches: Increase `pca_skip_threshold`
5. Increase `proxima_block_size` to reduce metadata

**Issue**: High memory usage

**Solution**:

1. Reduce cache size: Lower `block_cache_size_mb`
2. Decrease PCA dimensions: Use fewer dimensions
3. Enable quantization: Reduces in-memory vector sizes
4. Reduce parallel search threads: Lower `max_search_threads`

**Issue**: Ineffective pruning (low pruning ratio)

**Solution**:

1. Data may not have natural clustering
2. Increase PCA dimensions for better projection
3. Increase Hilbert bits for finer granularity
4. Consider alternative engines (SST, SWIFT)
5. Enable liquid clustering for adaptive optimization
