= VIPER Storage Engine
:toc: left
:toclevels: 2
:icons: font

[abstract]
Columnar Parquet-based storage engine with advanced quantization and bloom filter optimization for analytics and batch operations.

== Overview

VIPER (Vectorized Intelligent Parquet Engine with Rebalancing) is ProximaDB's columnar storage engine optimized for analytical workloads and high compression ratios.

**Key Features**:

* Columnar Parquet format for efficient compression
* Advanced quantization (Binary, INT8, PQ)
* Dictionary encoding for metadata
* Bloom filter per column group
* Branched filtering architecture
* Optimized for batch operations

== Columnar Storage

=== Why Columnar?

**Advantages**:

* Better compression (similar values grouped)
* Faster analytical queries (column scans)
* Skip unnecessary columns
* Dictionary encoding for metadata

**Trade-offs**:

* Slower point queries (row reconstruction)
* Higher write overhead (transposition)

=== Parquet Format

VIPER uses Apache Parquet for storage:

[source]
----
Parquet File Structure:
┌─────────────────────────────┐
│ File Metadata               │
├─────────────────────────────┤
│ Column Group 0 (Dims 0-31)  │
│  ├─ Column 0: f32 values    │
│  ├─ Column 1: f32 values    │
│  └─ ...                     │
├─────────────────────────────┤
│ Column Group 1 (Dims 32-63) │
│  ├─ Column 32: f32 values   │
│  └─ ...                     │
├─────────────────────────────┤
│ Metadata Column (Dict)      │
│  ├─ Key: "category"         │
│  └─ Values: [0,1,2,...]     │
└─────────────────────────────┘
----

== Quantization Integration

VIPER supports multiple quantization levels:

=== Quantization Levels

[source,rust]
----
pub enum QuantizationLevel {
    Binary,    // 1 bit per dimension (32x compression)
    INT8,      // 8 bits per dimension (4x compression)
    PQ4,       // 4-bit product quantization
    PQ8,       // 8-bit product quantization
    PQ16,      // 16-bit product quantization
    None,      // Full precision (f32)
}
----

=== Storage Strategy

**Columnar Quantization**:

Each dimension stored in separate column with quantized representation:

[source]
----
Column 0:
  Full: [0.123, 0.456, 0.789, ...]  (f32)
  INT8: [31, 116, 201, ...]         (u8)
  Binary: [0, 1, 1, ...]            (bit)

Column 1:
  Full: [0.234, 0.567, 0.890, ...]  (f32)
  INT8: [60, 144, 227, ...]         (u8)
  Binary: [0, 1, 1, ...]            (bit)
----

=== Quantization Selection

[source,rust]
----
// Automatic quantization based on query requirements
let request = SearchRequest {
    collection_id,
    query_vector,
    top_k: 10,
    quantization_hint: Some(QuantizationLevel::INT8),  // User hint
    ..Default::default()
};

// VIPER selects optimal level:
// - Fast filter: Binary (32x faster)
// - Precision: INT8 (4x faster, good accuracy)
// - Final rerank: Full precision
----

== Branched Filtering

VIPER uses a multi-stage filter with per-column bloom filters:

=== Filter Stages

**Stage 1**: Bloom Filter Check

* Per-column group bloom filter
* Fast membership testing
* Skip entire column groups

**Stage 2**: Quantized Distance

* Use INT8/Binary quantization
* Fast approximate distance
* Candidate selection

**Stage 3**: Full Precision

* Load full f32 vectors
* Exact distance computation
* Top-k results

=== Implementation

[source,rust]
----
async fn search(&self, request: SearchRequest) -> Result<SearchResponse> {
    // Stage 1: Bloom filter
    let candidate_groups = self.bloom_filter_columns(&request)?;

    // Stage 2: Quantized search
    let mut candidates = Vec::new();
    for group in candidate_groups {
        let quantized = self.load_quantized_column_group(&group).await?;
        let approx_distances = self.compute_int8_distances(&quantized, &request)?;
        candidates.extend(approx_distances.into_iter().take(request.top_k * 10));
    }

    // Stage 3: Full precision rerank
    candidates.sort_by_key(|c| c.approx_distance);
    let top_candidates = &candidates[..request.top_k.min(candidates.len())];

    let mut final_results = Vec::new();
    for candidate in top_candidates {
        let full_vector = self.load_full_precision_vector(&candidate.id).await?;
        let exact_distance = self.compute_exact_distance(&full_vector, &request.query_vector)?;
        final_results.push(SearchResult { id: candidate.id, distance: exact_distance });
    }

    final_results.sort_by(|a, b| a.distance.partial_cmp(&b.distance).unwrap_or(std::cmp::Ordering::Equal));
    Ok(SearchResponse { results: final_results })
}
----

== Configuration

Add to `config/config.toml`:

[source,toml]
----
[storage.engines.viper]
# Parquet configuration
row_group_size = 10000  # vectors per row group
column_group_size = 32  # dimensions per column group

# Quantization
default_quantization = "INT8"  # Binary, INT8, PQ8, None
enable_quantized_index = true

# Bloom filter
bloom_filter_enabled = true
bloom_filter_fp_rate = 0.01  # 1% false positive

# Compression
parquet_compression = "zstd"  # none, snappy, gzip, zstd, lz4
compression_level = 3  # 1-22 for zstd

# Dictionary encoding
enable_dictionary = true
dictionary_page_size = 1048576  # 1MB
----

== Best Practices

=== When to Use VIPER

✅ **Good For**:

* Analytical workloads
* Large batch inserts
* High compression requirements
* Column-selective queries
* Time-series data

❌ **Not Ideal For**:

* Real-time single insertions
* Point queries by ID
* Small datasets (<100K vectors)
* Very frequent updates

=== Optimization Tips

**Batch Sizing**:

[source,rust]
----
// Optimal batch size: 10K-100K vectors
let batch: Vec<VectorRecord> = /* ... */;
assert!(batch.len() >= 10_000, "Batch too small for VIPER");

engine.insert_batch(batch).await?;
----

**Quantization Selection**:

[source,rust]
----
// Use quantization hints for better performance
let request = SearchRequest {
    quantization_hint: Some(QuantizationLevel::INT8),  // 4x faster
    recall_target: 0.95,  // Acceptable recall
    ..Default::default()
};
----

**Column Group Sizing**:

[source,toml]
----
# For 768D vectors: 24 column groups (32 dims each)
[storage.engines.viper]
column_group_size = 32

# For 1536D vectors: 48 column groups
column_group_size = 32
----

== Dictionary Encoding

VIPER uses dictionary encoding for metadata columns:

=== How It Works

[source]
----
Original Metadata:
  Vector 0: {"category": "electronics"}
  Vector 1: {"category": "books"}
  Vector 2: {"category": "electronics"}
  Vector 3: {"category": "clothing"}

Dictionary:
  0: "electronics"
  1: "books"
  2: "clothing"

Encoded Column:
  [0, 1, 0, 2]  (integer codes instead of strings)

Compression: 60-80% for low-cardinality metadata
----

=== Configuration

[source,toml]
----
[storage.engines.viper]
enable_dictionary = true
dictionary_threshold = 0.5  # Use dict if <50% unique values
----

== Troubleshooting

=== High Memory Usage During Write

**Symptom**: OOM during large batch inserts

**Cause**: Column transposition requires full batch in memory

**Solution**:
[source,toml]
----
[storage.engines.viper]
row_group_size = 5000  # Smaller row groups
max_batch_size = 50000  # Limit batch size
----

=== Slow Search Performance

**Symptom**: Searches taking >100ms

**Cause**: Not using quantization, too many column groups loaded

**Solution**:
[source,rust]
----
// Enable quantization
let request = SearchRequest {
    quantization_hint: Some(QuantizationLevel::INT8),
    ..Default::default()
};

// Or tune bloom filter
[storage.engines.viper]
bloom_filter_fp_rate = 0.001  # Stricter filter
----

=== Poor Compression Ratio

**Symptom**: Parquet files larger than expected

**Solution**:
[source,toml]
----
[storage.engines.viper]
parquet_compression = "zstd"
compression_level = 9  # Higher compression (slower write)
enable_dictionary = true
----
