= SWIFT Storage Engine
:toc: left
:toclevels: 3
:icons: font

[abstract]
Storage With Indexed Fast Traversal (SWIFT) - Production-ready hierarchical storage engine with three-tier architecture for large-scale organized data management.

== Overview

The SWIFT engine is ProximaDB's sophisticated hierarchical storage engine featuring a unique three-tier SuperBlock → DataBlock → Records architecture optimized for organized large-scale data management with multi-level indexing.

**Key Features**:

* Three-tier hierarchical architecture
* Multi-level indexing with O(log n) access patterns
* Optimized for millions to billions of vectors
* Tenant isolation and resource management
* Incremental updates without disruption
* SIMD-optimized encoding with intelligent compression

**Status**: ✅ PRODUCTION-READY

== Three-Tier Hierarchical Architecture

=== SuperBlock Level (Top Tier)

**Purpose**: High-level organizational units for coarse-grained filtering

**Use Cases**:
* Tenant isolation in multi-tenant systems
* Department/division organization
* Geographic region separation
* Product line segregation

**Features**:
* Independent resource management
* Isolation boundaries
* Top-level metadata indexing
* Efficient pruning for hierarchical queries

**Implementation**: `hierarchical_blocks.rs` - SuperBlock struct

=== DataBlock Level (Mid Tier)

**Purpose**: Fine-grained organization within SuperBlocks

**Use Cases**:
* Project/campaign organization
* Version control grouping
* Category/subcategory structure
* Time-based partitioning

**Features**:
* Proxima compression integration
* Mid-level indexing
* Balanced query granularity
* Efficient range scans

**Implementation**: `hierarchical_blocks.rs` - DataBlock struct

=== Record Level (Bottom Tier)

**Purpose**: Individual vector storage with full metadata

**Features**:
* SIMD-optimized vector encoding (ProximaBlock format)
* Type-safe metadata preservation with compression markers
* Filterable metadata: String, Int64, Float, Boolean support
* FilterExpression evaluation using sql_value_filter
* Collection config for type resolution during deserialization
* Compression with quality control
* Fast point lookups

**Implementation**: `hierarchical_blocks.rs` - Record storage

=== Progressive Search

**Hierarchical Search Strategy**: `progressive_search.rs:1-400`

SWIFT implements progressive search that traverses the hierarchy efficiently:

1. **SuperBlock Filtering**: Identify relevant SuperBlocks based on query constraints
2. **DataBlock Selection**: Within selected SuperBlocks, identify relevant DataBlocks
3. **Record Scanning**: Scan records within selected DataBlocks
4. **Result Aggregation**: Merge results maintaining quality guarantees

[source,rust]
----
pub async fn progressive_search(
    &self,
    query: &[f32],
    superblock_filter: Option<SuperBlockFilter>,
    k: usize,
) -> Result<Vec<SearchResult>> {
    // Stage 1: SuperBlock filtering
    let relevant_superblocks = self.filter_superblocks(&superblock_filter)?;

    // Stage 2: DataBlock selection
    let relevant_datablocks = self.select_datablocks(&relevant_superblocks, query)?;

    // Stage 3: Record scanning
    let results = self.scan_records(&relevant_datablocks, query, k).await?;

    Ok(results)
}
----

=== Unified Reader

**Strategy-Based Reading**: `unified_reader.rs` and `unified_strategy_reader.rs`

The SWIFT engine implements a unified reading system that automatically selects the optimal strategy:

**Read Strategies**:
* **Hierarchical**: Full three-tier traversal (best for organized data)
* **Flat**: Direct record access (best for point queries)
* **Range**: Efficient range scans within DataBlocks
* **Batch**: Batched reads for multiple records

**Strategy Selection**:
[source,rust]
----
pub enum ReadStrategy {
    Hierarchical { max_depth: u32 },
    Flat { direct_access: bool },
    Range { start: RecordId, end: RecordId },
    Batch { batch_size: usize },
}

impl SwiftEngine {
    pub fn select_read_strategy(&self, query: &Query) -> ReadStrategy {
        match query.query_type {
            QueryType::Hierarchical => ReadStrategy::Hierarchical { max_depth: 3 },
            QueryType::PointLookup => ReadStrategy::Flat { direct_access: true },
            QueryType::RangeScan => ReadStrategy::Range { start, end },
            QueryType::BatchLoad => ReadStrategy::Batch { batch_size: 1000 },
        }
    }
}
----

=== Flush with Quantization

**Optimized Writes**: `flush_with_quantization.rs:1-350`

SWIFT integrates unified quantization during flush operations:

**Flush Pipeline**:
1. Organize records into hierarchical structure
2. Apply quantization at DataBlock level
3. Compress with Proxima encoding
4. Write SuperBlock → DataBlock → Records
5. Update hierarchical indices

[source,rust]
----
pub async fn flush_with_quantization(
    &mut self,
    vectors: Vec<VectorRecord>,
    hierarchy_config: HierarchyConfig,
    quantization_level: QuantizationLevel,
) -> Result<FlushStats> {
    // Organize into hierarchy
    let hierarchy = self.organize_hierarchy(vectors, &hierarchy_config)?;

    // Apply quantization
    let quantized = self.quantize_datablocks(hierarchy, quantization_level).await?;

    // Flush to disk
    let stats = self.flush_hierarchy(quantized).await?;

    Ok(stats)
}
----

== Performance Characteristics

=== Time Complexity

[cols="2,2,3"]
|===
|Operation |Complexity |Notes

|Point Lookup
|O(log n)
|Hierarchical index traversal

|Range Query
|O(log n + m)
|m = result set size

|Insert
|O(log n)
|Append to appropriate DataBlock

|Hierarchical Search
|O(h * log(n/h))
|h = hierarchy depth

|Tenant-Isolated Search
|O(log(n/t))
|t = number of tenants

|Update
|O(log n)
|Locate and update in place
|===

=== Space Efficiency

**Storage Overhead**:
* SuperBlock metadata: ~1KB per SuperBlock
* DataBlock metadata: ~500B per DataBlock
* Hierarchical indices: O(n) total
* Cache overhead: Configurable (default 100MB)

**Compression**:
* Proxima encoding at DataBlock level
* Quantization support (INT8, PQ)
* Metadata compression
* Typical compression ratio: 4-8x

=== Scalability

**Tested Scale**:
* Up to 1B vectors per collection
* 10K+ SuperBlocks per collection
* 100K+ DataBlocks per SuperBlock
* 1K-10K records per DataBlock

**Resource Requirements**:
* Memory: 1GB + (cache_size_mb)
* Disk: Depends on compression (typical 4-8x compression)
* CPU: SIMD-optimized operations

== Troubleshooting

=== Common Issues

**Issue**: Slow hierarchical search

**Solution**:
1. Increase SuperBlock cache size
2. Verify hierarchical organization matches query patterns
3. Enable progressive search
4. Check DataBlock size (optimal: 1K-10K records)

**Issue**: High memory usage

**Solution**:
1. Reduce SuperBlock cache size
2. Enable quantization
3. Decrease DataBlock size
4. Use progressive search with early termination

**Issue**: Inefficient tenant isolation

**Solution**:
1. Use SuperBlockStrategy::Tenant
2. Organize data during flush
3. Enable tenant-specific indices
4. Use tenant-filtered searches

== Performance Tuning

=== SuperBlock Configuration

**Optimal SuperBlock Count**:
* Small systems (< 1M vectors): 10-100 SuperBlocks
* Medium systems (1M-100M vectors): 100-1K SuperBlocks
* Large systems (> 100M vectors): 1K-10K SuperBlocks

**Rule of thumb**: Aim for 10K-1M records per SuperBlock

=== DataBlock Sizing

**Optimal DataBlock Size**:
* Real-time queries: 1K-5K records
* Batch analytics: 5K-10K records
* Very large scale: 10K-50K records

**Tradeoff**: Smaller = more index overhead, Larger = slower scans

=== Cache Tuning

**SuperBlock Cache**:
* Minimum: 50MB (for small datasets)
* Recommended: 100-500MB
* Maximum: 2GB (for very large datasets)

**Cache size formula**: `cache_mb = superblock_count * 0.1`
