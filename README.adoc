= ProximaDB
:toc: left
:toclevels: 2
:icons: font

[.lead]
**Object-storage-native context serving for SQL, JSON, and vectors**

ProximaDB's MVP gives AI application teams one typed record and one canonical REST API for
metadata-aware vector retrieval. The broader document, graph, time-series, event, observability,
and SQL-extension architecture remains the product direction, but it graduates only through the
link:docs/00-product/MVP_TRUST_CORRIDOR.toml[machine-checked MVP trust corridor].

---

== Why Developers Use ProximaDB

* **One canonical record** for an identifier, typed JSON properties, and an embedding
* **One supported API path** for create, batch write, get, scan, vector search, and delete
* **Metadata filters on both scan and vector search**, proven by the same first-run smoke
* **SST as the safe default**, backed by the canonical WAL on the single-node path
* **Object-storage-aware internals** with measured request, byte, cache, and compute signals

=== Context Serving: The MVP Differentiator

Modern vector systems increasingly include document payloads, metadata filters, hybrid search,
and distributed operation. ProximaDB therefore does not differentiate by pretending those features
are absent. Its wager is narrower: one typed context record, served through standard interfaces,
with workload-specific projections and object-economics evidence behind it.

|===
| Capability | MVP trust corridor | Broader ProximaDB direction

| Typed context records | *Supported* | Canonical authority for every modality
| Metadata scan + vector search | *Supported* | Hybrid and cross-modal retrieval
| SST single-node storage | *Supported* | Object-storage-aware projection placement
| pgwire SQL subset | Beta | Wider relational/context query surface
| Document, graph, observability | Beta | Rebuildable projections over canonical records
| Distributed execution | Excluded | Evidence-gated post-MVP capability
|===

*Beta vision example — outside the MVP trust corridor:*
[source,sql]
----
-- Find similar products for a user, then get reviews from the document store
SELECT u.name, v.product_id, v.score, d.review_text
FROM users u
JOIN LATERAL VECTOR_SEARCH('products', u.preference_vector, 10) v ON true
JOIN LATERAL DOCUMENT_QUERY('reviews', 'product_id = "' || v.product_id || '"') d ON true;
----

== Quick Start

The supported first-run path is Docker plus the canonical v2 smoke. It fails on any incorrect
status, missing record, filter leak, unsupported write-contract signal, or deprecated route.

[source,bash]
----
docker run --rm -d --name proximadb-mvp -p 5678:5678 vjsingh1984/proximadb:latest
python3 scripts/mvp_smoke.py --base-url http://127.0.0.1:5678
----

See link:docs/01-quick-start/CONTEXT_SERVING_MVP.adoc[Context Serving MVP Quickstart] for the
verified request sequence and production caveats. Release archives currently cover Linux x86_64
(glibc) and Windows x86_64; the release page is authoritative for available assets.

=== From Source (Rust)

[source,bash]
----
git clone https://github.com/anvai-labs/proximaDB
cd proximaDB
cargo run --release --bin proximadb-server
----

== Core Models

=== Vectors
Embeddings + metadata with similarity search and filtering.

=== Documents
Beta JSON/document projection; canonical-record convergence and recovery parity are incomplete.

=== Graphs
Beta nodes/edges and traversal through ORION; shared-WAL replay parity is incomplete.

=== Observability
Beta logs, metrics, and traces with modality-specific ingestion and incomplete canonical recovery.

== API Examples (REST)

=== Vector Search

[source,bash]
----
curl -X POST http://localhost:5678/api/v2/collections/docs/search \
  -H "Content-Type: application/json" \
  -d '{
    "query_vector": [0.1, 0.2, 0.3],
    "top_k": 10,
    "filters": [
      {"field": "category", "op": "eq", "value": "tech"}
    ]
  }'
----

=== Document Insert

[source,bash]
----
curl -X POST http://localhost:5678/api/v2/document-collections/docs/documents \
  -H "Content-Type: application/json" \
  -d '{
    "document": {"title": "Runbook", "service": "api", "severity": "warn"}
  }'
----

=== Graph Traverse

[source,bash]
----
curl -X POST http://localhost:5678/api/v2/graphs/topology/traverse \
  -H "Content-Type: application/json" \
  -d '{

    "max_depth": 2
  }'

== SQL Extensions

ProximaDB extends standard SQL with functions for each data model:

=== Vector Search

[source,sql]
----
-- pgvector-compatible distance operator
SELECT * FROM products ORDER BY embedding <-> '[0.1,0.2,...]'::vector LIMIT 10;

-- Explicit function call
SELECT * FROM VECTOR_SEARCH('products', '[0.1, 0.2, 0.3]', 10);
----

=== Graph Traversal

[source,sql]
----
-- Embedded Cypher syntax
SELECT * FROM GRAPH_QUERY('MATCH (a:Person)-[:KNOWS]->(b) RETURN b.name');

-- Find friends-of-friends
SELECT * FROM GRAPH_QUERY('MATCH (a:Person {name: "Alice"})-[:KNOWS*2]->(fof) RETURN fof');
----

=== Document Query

[source,sql]
----
-- Query with JSON path filter
SELECT * FROM DOCUMENT_QUERY('orders', 'status = "pending"');
----

=== Observability

[source,sql]
----
-- Query logs
SELECT * FROM LOGS('production') WHERE timestamp > now() - interval '1h';

-- Query metrics
SELECT * FROM METRICS('system') WHERE metric_name = 'cpu_usage';
----

=== Cross-Model Joins

[source,sql]
----
-- Vector + Document: Similar products with reviews
SELECT v.product_id, v.score, d.review_text
FROM VECTOR_SEARCH('products', '[0.1,0.2]', 10) v
JOIN LATERAL DOCUMENT_QUERY('reviews', 'product_id = "' || v.product_id || '"') d ON true;

-- Vector + Graph: Similar items filtered by category relationships
SELECT * FROM VECTOR_SEARCH('products', '[0.1,0.2]', 100)
WHERE id IN (
  SELECT target FROM GRAPH_QUERY('MATCH (:Category {name:"Electronics"})-[:CONTAINS]->(p) RETURN p.id')
);

-- Logs + Graph: Errors with service dependencies
SELECT l.timestamp, l.message, g.dependency
FROM LOGS('errors') l
JOIN LATERAL GRAPH_QUERY('MATCH (s:Service {name: "' || l.service || '"})-[:DEPENDS_ON]->(d) RETURN d.name as dependency') g ON true;
----

== Feature Status (Builder View)

Statuses use the support-contract ladder from
link:docs/SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`]:
*Supported* / *Beta* / *Experimental* / *Planned*.

|===
| Capability | Status | Notes

| Vector search + filters | Supported | SST is the supported storage engine; VIPER/HELIX/NOVA are Beta. AXIS (HNSW/IVF) indexes and metadata filters
| Document store | Beta | WAL‑backed, JSON path queries, full‑text search; canonical record storage is the convergence path
| Graph traversal | Beta | ORION (in‑memory CSR), WAL persistence, algorithms; some v1-only RPCs deferred
| Observability logs | Beta | WAL‑backed, partitioned storage, 6 SIEM adapters
| Observability metrics | Beta | Time‑series aggregation, downsampling
| Unified multi‑model query | Beta | Cross‑model joins, parallel execution; strongest on function-backed sources
| Postgres wire protocol | Supported | ANSI SQL for SQL clients (psql/JDBC/ORM), autocommit statements, pgvector-compatible operator; transaction control returns `0A000` and full Postgres/SQL parity remains Experimental
| Unified port mode | Experimental | Arrow Flight / gRPC service multiplexing is an experimental customer-facing transport
| Web UI dashboard | Beta | SQL editor, graph visualization, dark/light theme; fronts Beta surfaces
| Python SDK | Beta | Graph analytics, AutoML, observability, security; wraps Beta surfaces
|===

Authoritative status: link:docs/SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`] — where
this table and that contract disagree, the contract wins.

NOTE: Tier detail lives in link:docs/SUPPORTED_SURFACE.adoc[`docs/SUPPORTED_SURFACE.adoc`]. A
few capabilities in the tree are *not* in the supported surface above: the SWIFT and RAPTOR
storage engines are **experimental** (off by default behind the `experimental-engines` cargo
feature), Arrow Flight is an **experimental** customer-facing transport, and distributed
cluster execution is **experimental**.

== Branching and Releases

- `develop` is the integration branch: feature branches open PRs into `develop` (CI-gated).
- Promotion is staged: `develop` -> `qa` (staging validation) -> `main` (release); releases are tagged on `main`.
- `qa` and `main` always reflect promoted states; nothing merges directly to either without passing through the previous stage.
